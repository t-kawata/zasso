## §1: Purpose — Audio-Only SIP Client via PJSUA [N0001 → RFC-ROOT §1]

### 1.1 Crate Mission

The `siprs` crate provides a safe, asynchronous SIP client for audio-only voice communication by wrapping PJSUA (PJSIP v2.17) FFI bindings in a Rust-native tokio API. It enables multiple SIP accounts, multiple transports, incoming/outgoing calls, audio processing, DTMF, ICE/TURN/STUN, TLS, SRTP, and application-integrated event delivery — all without exposing FFI details to consumers.

**Video is explicitly excluded.** The crate limits its responsibility to audio only.

### 1.2 RFC Authoritative Reference

The crate's purpose is defined in RFC-ROOT.md §1 (lines 14–16):

> 本 crate の目的は、Rust から PJSUA を安全かつ非同期的に利用し、複数 SIP アカウント、複数トランスポート、発着信、音声処理、DTMF、ICE/TURN/STUN、TLS、SRTP、およびアプリケーション統合向けイベント配信を、tokio ネイティブな API で提供することである。映像機能は対象外であり、音声のみに責務を限定する。

### 1.3 Normative Scope (Functional Requirements)

Per RFC-ROOT §5 (lines 124–141), the following 15 items constitute the normative scope:

1. Simultaneous holding of multiple `SipAccount` instances
2. Dynamic addition and removal of accounts
3. Per-account register/unregister and dynamic register-enable toggling
4. Outgoing-call-only mode (no registration required)
5. UDP/TCP/TLS transport support
6. TLS/SRTP toggling via feature flags
7. Full ICE support with multiple STUN/TURN configurations
8. Codec limited to PCMU and Opus only
9. DTMF send/receive via Inband, SIP INFO, and RFC 4733
10. Comprehensive event bus
11. IN/OUT paired chunk audio delivery
12. High-quality resampling and type conversion
13. Multi-source mixing with real-time source swapping
14. Unified `Result<T, SipError>` API
15. `SipClient: Send + Sync` guarantee

## §2: Non-Goals & Tauri Boundary [N0004 → RFC-ROOT §2 + §2.1]

### 2.1 Explicit Non-Goals

Per RFC-ROOT §2 (lines 68–70), the following are explicitly excluded from this crate's responsibility:

| Non-Goal | Rationale |
|----------|-----------|
| SIP server implementation | Out of scope — the crate is a client only |
| PBX implementation | Out of scope — no call routing/switching logic |
| Custom RTP stack | Reuses PJSIP's built-in RTP/RTCP via PJSUA conference bridge |
| Recording file output | `AudioChunkPair` is provided; file containerization is the consumer's responsibility |
| GUI | This is a Rust library crate — no UI of any kind |
| Persistent config storage | Configuration is supplied at construction time; persistence is the integrator's concern |
| Call billing | No accounting, CDR, or rating logic |
| Video processing | Audio-only mandate — video is explicitly excluded |

**Invariant**: Any future feature that touches one of the above areas **must** require explicit scope amendment before implementation. This is a hard architectural boundary.

### 2.2 Tauri Integration Boundary

Per RFC-ROOT §2.1 (lines 72–87), the crate is Tauri-independent. The following responsibility split defines the integration boundary:

**Crate responsibilities (`siprs`):**
- Rust public API: `SipClient`, `SipEventPayload`, and related types
- Structured logging via `tracing` (Tauri's `tracing-subscriber` integration is the consumer's task)
- `serde::Serialize`/`Deserialize` provided as an optional feature (`serde`) for utility types. `SecretString` (from the `secrecy` crate) is always serialized as `"***REDACTED***"`.

**Consumer (Tauri plugin layer) responsibilities:**
- Converting `SipEventPayload` into DTOs (Data Transfer Objects) for frontend delivery
- Efficient transfer of `AudioChunkPair` (binary data) — e.g., Base64 encoding via `tauri::ipc::Channel`, or shared memory references
- Conversion of `std::time::Instant` (used internally by `PairAligner`) to `SystemTime` before exposing in DTOs
- Adapter layer translating frontend commands (call button, answer incoming, etc.) into this crate's Rust API

**Invariant**: This crate MUST NOT depend on Tauri or expose Tauri types (`tauri::ipc::Channel`, etc.).

## §3: Domain Glossary [N0005 → RFC-ROOT §3]

| Term | Definition | Used In |
|------|-----------|---------|
| **Client** | A `SipClient` instance — the top-level handle through which all operations are performed | All subsystems |
| **Account** | A logical SIP entity holding REGISTER/authentication/outgoing-call context. Each account can be independently registered or unregistered. | Registration, Calls, Config |
| **Call** | A single SIP session (INVITE → dialog → BYE). One call belongs to exactly one account. | State machine, Media, Events |
| **Media Session** | The execution unit for RTP/RTCP/codec/ICE/SRTP tied to one Call. Lifetime matches the call's media phase. | Audio pipeline, State |
| **Source** | Any input that supplies audio to the OUT direction. Sources can be dynamically added, removed, or swapped. | AudioMixer, AsyncAudioSource |
| **Chunk Pair** | An IN/OUT paired audio buffer aligned to the same timestamp. The fundamental unit of audio I/O. | AudioBridge, AudioChunkPair |
| **Raw SIP Event** | A received/transmitted SIP message with its full body and parsed metadata. Carries the complete message for inspection. | EventBus, EventPayload |

### 4.3 Build Strategy

Two-stage build strategy per RFC-ROOT §4:
1. **Prebuilt-first**: Attempt to use prebuilt PJSIP binaries from `vendor/prebuilt/`
2. **Fallback**: If prebuilt binaries are missing, fall back to source build from `vendor/pjsip/`

### 4.4 Versioning Policy

Per RFC-ROOT §4.1 (lines 103–121):

**0.x phase (active development):**
- API does not strictly follow semver. Breaking changes are permitted as needed to stabilize the API.
- All public API changes are documented in `CHANGELOG.md` and a migration guide.
- Adding variants to `SipEventPayload` is NOT considered a breaking change (marked `#[non_exhaustive]`).

**1.0+ phase (stabilized):**
- Strict semver adherence (MAJOR.MINOR.PATCH)
- **MAJOR**: Breaking public API changes (enum variant removal/rename, struct field removal, trait method signature changes)
- **MINOR**: Backwards-compatible additions (new enum variants, new struct fields, new traits). `SipEventPayload` expansion is MINOR scope.
- **PATCH**: Bug fixes, refactoring, internal optimizations. No public API changes.

**Exceptions allowing breaking changes in PATCH:**
- Security vulnerability fixes (annotated in CHANGELOG)
- Runtime behavior changes that do not affect compile-time type compatibility (e.g., timeout/retry changes in `SipClient::new()`)

## §8: Investigation Findings

### 8.1 Crate State

`siprs` v0.1.0 is in a pre-implementation skeleton phase:
- Cargo.toml declares **zero dependencies** with the explicit comment: `"# 本チケットでは依存 crate を追加しない"`
- No `lib.rs`, `main.rs`, or `mod.rs` exists — the crate cannot compile
- **65 design-artifact `.rs` files** exist across 13 subdirectories under `src/`
- All 65 files are stubs with `Initial Design Artifact — RFC-driven Implementation` headers and `[::STUB::]` markers
- Each stub contains a single placeholder: `pub trait Service {}`, `pub struct Config {}`, `pub enum Error {}`, or `pub enum State {}`

## §9: Boy Scout Rule — Translatability Plan

### 9.1 Within Scope (this spec document)

The following translatability improvements are applied to `specs/P0-1.md`:

1. **Section headings as assert statements**: Each § heading reads as a complete assertion (e.g., "§1: Purpose — Audio-Only SIP Client via PJSUA") rather than a generic label. The table of contents is translatable as a sentence sequence.
2. **Node-ID provenance annotations**: Every architectural claim is annotated with its RFC node ID and section number (e.g., `[N0001 → §1]`). This enables traceability without separate cross-reference tables.
3. **Verified cross-references**: All RFC-ROOT section numbers were verified against the actual document. No unverified "see section X" references exist.
4. **One concept per paragraph**: Each glossary term, non-goal, and compliance rule gets its own paragraph. No run-on sentences combine multiple architectural decisions.
5. **Error/edge cases documented**: The "[Error case]" and "[Edge case]" acceptance criteria are restated as concrete spec sections rather than silent assumptions.

- The 65 design-artifact `.rs` stubs under `src/` all use generic placeholder patterns (`pub trait Service {}`, `pub struct Config {}`, etc.). These are intentional `[::STUB::]` markers per the First-Class Rule and will be resolved by downstream implementation tickets (P0-2 through PX series).
