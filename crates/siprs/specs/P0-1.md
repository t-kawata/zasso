**Universal Testing Rules**

Write all code under the following non-negotiable rules:

1. Tests must be comprehensive and exhaustive for all observable behavior, including edge cases, failure modes, and invariants. Any behavior not covered by tests is considered undefined and unacceptable.

2. Do not write or accept any implementation whose correctness cannot be fully validated through tests. If correctness cannot be proven via tests, the implementation is invalid and must be redesigned.

3. If a feature cannot be completely and deterministically tested, treat this as a design failure. Refactor the architecture until full testability is achieved.

4. Tests are not a scoreboard and must never be treated as a goal in themselves. Passing tests does not imply correctness unless the tests fully capture the intended behavior.

5. It is strictly forbidden to modify or weaken tests to make an implementation pass. The implementation must conform to the tests, not the other way around.

6. Implementation is considered complete only when:
   - The tests fully and precisely specify the intended behavior.
   - The implementation passes all tests without exception.
   - The implementation's correctness is demonstrably guaranteed by those tests.

7. Any gap between test coverage and intended behavior is a critical defect. Resolve such gaps before considering the work complete.

## Boy Scout Rule

## 翻訳可能性改善計画

本チケットのコード成果物は新規作成（versioning_policy.rs, Cargo.toml, CHANGELOG.md）が中心であり、既存コードの改修は発生しない。新規作成において以下の翻訳可能性を確保する：

### versioning_policy.rs
- **関数名は動詞句**: `crate_version()` / `msrv()` / `supported_os_list()` / `pjsip_version()` — 関数名を読めば「どのバージョン情報を返す関数か」が即座に理解できる
- **定数名は UPPER_SNAKE_CASE + ドメイン接頭辞**: `SIPRS_VERSION` / `SIPRS_MSRV` / `PJSIP_VERSION` / `SUPPORTED_OS_TARGETS` — 名前空間で所属を明確に
- **一関数一責務**: 一つの関数は一つのバージョン情報のみを返す。複合情報は構造体を別途定義
- **ハードコード禁止**: 全ての値は名前付き定数として定義し、関数はその定数を返す
- **コメントは「なぜ」を記述**: 0.x フェーズでは semver 非厳密とする のように運用ルールの背景を説明

### スコープ外だが Boy Scout Rule 範囲
- 既存 src/ 以下の設計文書ファイルは編集対象外（本チケットのスコープに含まれない）だが、`src/api/` ディレクトリを新規作成する過程でディレクトリ構成を一貫させる
- 次チケット（P0-2 ClientConfig等）が読みやすいように `src/api/mod.rs` を新規作成し、pub mod versioning_policy; を宣言する

## Notes

本チケットはコード実装よりも設計文書の確認が主目的である。バージョニングポリシーの定数定義（MSRV, crate version）のみが実際のコード成果物となる。

- [Implementation steps]
  1. crates/siprs/Cargo.toml 新規作成（name=siprs, version=0.1.0, edition=2021, rust-version=1.95）
  2. ワークスペースルート Cargo.toml の members に crates/siprs を追加
  3. src/api/ ディレクトリ新規作成
  4. src/api/versioning_policy.rs 実装（定数 + 純関数）
  5. src/api/mod.rs 新規作成（pub mod versioning_policy;）
  6. src/lib.rs 新規作成（mod api;）
  7. CHANGELOG.md 新規作成
  8. cargo check でコンパイル確認

- [Risks]
  - ワークスペースルート Cargo.toml に members = ["crates/siprs"] を追加する際、既存の workspace 設定との競合リスクが低い（src-tauri のみの単純構成）
  - edition = "2021" は既存の zasso 全体と一致するため問題なし

- [Caveats]
  - src/ 下の既存 .rs ファイルは設計文書であり、crate のコンパイル対象からは除外する必要がある。Cargo.toml の default members に含めないこと。
  - Cargo.toml の path 指定は crates/siprs/ を正しく指すこと

- [Open items]
  - PJSIP 2.17 の実際のバインディングコードは本チケットのスコープ外。本チケットでは定数 "2.17" を返す関数まで。
  - versioning_policy.rs の正確なパブリックAPI設計は /start-ticket 時に精査

- [Future improvements]
  - 1.0 移行時に versioning_policy.rs を拡張し、semver 厳格準拠のロジックを追加
  - バージョン境界テスト（MSRV 未満・以上）を CI で自動化
