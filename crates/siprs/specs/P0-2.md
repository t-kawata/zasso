# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

## Goal
Establish the single-core-reactor concurrency foundation for the siprs crate. The runtime/ module delivers a dedicated reactor thread that serializes all PJSUA control API calls through an unbounded MPSC channel, achieving Send+Sync safety without exposing PJSUA thread-safety constraints to library users.

## Purpose
PJSIP internally spawns native threads and fires callbacks on arbitrary threads. Calling pjsua_* functions from multiple threads concurrently causes data races, undefined behavior, and panics. This ticket implements the CoreReactor thread that owns the single source of truth (ClientState) and processes all commands sequentially.

## Motivation
Every higher-level feature (accounts, calls, audio, events) depends on thread-safe access to PJSIP. Without this foundation, the crate cannot provide any safe public API. The MPSC+oneshot pattern is the architectural invariant that unlocks all downstream tickets (P0-3 through P1+).

## Constraints
- Single-core-reactor: exactly one std::thread::JoinHandle<()> for all PJSUA control
- RuntimeCommand uses tokio::sync::mpsc::UnboundedSender for submission (never bounded channels - must not deadlock on backpressure)
- Each command variant carries a tokio::sync::oneshot::Sender<Result<_, SipError>> for async reply
- Four execution contexts explicitly modeled but only #1 (User async) and #2 (Core reactor) are instantiated in P0-2; #3 (PJSIP callbacks, P0-6) and #4 (Audio worker, P1+) are interface contracts only
- Lock rules: read().await for query snapshot APIs; write().await for reactor state mutation; blocking_read() prohibited
- ClientState source of truth is owned exclusively by reactor thread, not by RwLock - RwLock is only for snapshot sharing
- conf_port_id lives in PjsuaBackend, not in CallEntry

### Key Architectural Decisions
1. **Enum dispatch rather than trait dispatch**: RFC section 7.2 specifies a concrete RuntimeCommand enum with named variants. This is intentional - it enables exhaustive match in the reactor loop and compile-time verification that every command is handled.
2. **Unbounded MPSC (not bounded)**: PJSIP operations can have unpredictable completion times; a bounded channel would risk deadlock under load. Memory is bounded by the rate of command submission from the single user async context.
3. **reactor thread is not equal to tokio runtime thread**: The reactor runs on a dedicated std::thread (non-tokio) to avoid blocking the async runtime with synchronous pjsua_* calls. The reactor can block; tokio tasks must not.
4. **ClientState ownership**: Single-writer (reactor) + multiple-reader (async queries) pattern via tokio::sync::RwLock. The RwLock guards the SNAPSHOT, not the source of truth - the source of truth is the reactor thread's local state variable.

## Acceptance Criteria

- [Happy path] CoreReactor::spawn(boot_config) starts a dedicated OS thread. RuntimeHandle::submit(command) enqueues it via MPSC. Reactor thread processes it in FIFO order, calls the corresponding Backend trait method, and sends the result back via oneshot. RuntimeHandle::is_terminated() == false while reactor runs.
- [Happy path] Shutdown command completes all prior commands, sends Ok(()) reply, reactor thread exits JoinHandle, is_terminated() == true.
- [Error case] Reactor panics during dispatch: std::panic::catch_unwind captures the panic, sets is_terminated() = true, subsequent submit() returns Err(ReactorDown) immediately without blocking the caller.
- [Error case] Shutdown submitted before Initialize: reactor returns Err(NotInitialized) but stays alive to accept further commands.
- [Error case] Double Shutdown: after first Shutdown completes, second submit(Shutdown) returns Ok(()) immediately - reactor already stopped.
- [Edge case] 10,000 rapid consecutive dummy commands: all processed without overflow, each reply received in order, no memory exhaustion.
- [Edge case] Command submitted immediately after spawn() before reactor thread has entered its loop: command is buffered by MPSC and processed as soon as reactor starts receiving.

## Invariants

- [Normal] Reactor thread is_running() is true after successful spawn() until Shutdown completes
- [Normal] All commands are processed in the order they were submitted (FIFO per MPSC channel)
- [Error] On reactor thread panic: is_terminated() returns true; submit() immediately returns Err without blocking or spin-waiting
- [Error] Shutdown command never partially executes - all commands enqueued before Shutdown complete before the shutdown ack is sent
- [Internal state] ClientState (initialized bool, accounts BTreeMap, calls BTreeMap) is only mutated on the reactor thread - never from user async context or PJSIP callbacks
- [Internal state] oneshot::Sender is always .send()'d exactly once per command; dropped Sender is a bug (RecvError::Closed propagates as dispatcher error)
- [Boundary] Unbounded MPSC channel has no capacity limit; 10,000+ enqueued commands must not cause memory exhaustion within reasonable bounds
