# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Establish the authoritative versioning policy specification for the siprs crate — a single self-contained design document (specs/P0-2.md) that codifies the two-phase versioning strategy (0.x development phase and 1.0+ stable phase) defined in RFC-ROOT §4.1, along with helper functions for programmatic policy enforcement.

### Purpose
Provide a clear, enforceable policy that governs API compatibility expectations across the crate lifecycle. During 0.x development (pre-1.0), rapid iteration with breaking changes is permitted to accelerate stabilization. After 1.0, strict semver compliance protects downstream consumers from unexpected breakage. The policy serves as both documentation for humans (CHANGELOG.md) and a programmatic API for CI tooling (semver-checks integration in P2-2).

### Motivation
The siprs crate is at version 0.1.0 with a 48-ticket multi-phase implementation roadmap spanning P0-P7. Without an explicit versioning policy: (1) downstream consumers cannot predict when API breaks occur, (2) CI tooling cannot enforce semver compliance, (3) crate maintainers lack guidance on which changes require MAJOR vs MINOR vs PATCH bumps. Establishing the policy now, at the outset of the implementation phase, prevents confusion and miscommunication about API stability expectations throughout the development lifecycle.

### Constraints
(1) Versioning policy must be implementable as pure Rust code — no external dependencies for policy evaluation (semver parsing uses the semver crate optionally; core logic is dependency-free). (2) Policy must be fully unit-testable without PJSUA or tokio — plain #[test] functions only. (3) Policy must align with cargo semver conventions for eventual CI integration in P2-2. (4) Must not introduce unsafe code. (5) Must maintain backward compatibility with Cargo.toml version field parsing (std::env! or include_str! based).

## Invariants

- 【Normal establishment】VersionPhase classification must correctly reflect the crate version from Cargo.toml — 0.x.x versions always produce VersionPhase::Dev, 1.x.x+ versions always produce VersionPhase::Stable. Phase classification is purely a function of MAJOR version number: MAJOR==0 → Dev, MAJOR>=1 → Stable.
- 【Invariant on error】Erroneous version string parsing (non-numeric segments, empty string, malformed semver) must return Err with a descriptive message — never panic, never silently return a default phase. The versioning_policy module must maintain functional correctness even when supplied with invalid version input.
- 【Internal state invariant】VersionPhase is an immutable property determined at VersionPolicy construction time — once constructed, the phase never changes within the lifetime of the policy instance. CHANGELOG requirement flag (is_changelog_required) depends only on ChangeKind and VersionPhase, not on external mutable state. #[non_exhaustive] on SipEventPayload must never be removed.
- 【Boundary invariant】MAJOR version 0 boundary: version 0.x.x always behaves as Dev phase regardless of MINOR/PATCH values. MAJOR version 1 boundary: version 1.0.0 is the exact transition point — is_stable() first returns true at 1.0.0, making semver-check enforcement plan effective. Security exception: always applies regardless of phase — security fixes bypass MAJOR delay in both Dev and Stable.

### Exceptions

- Exception entry 1 — Item: Cargo.toml version change validation cannot be fully automated in unit tests because crate version is a compile-time constant read from Cargo.toml metadata, not a runtime value. It is NOT TESTABLE to validate version numbering policy compliance through runtime code. Reason: The Cargo.toml version is consumed by cargo publish toolchain and semver-compliance is enforced by external tools (cargo semver-checks, cargo release). Runtime code cannot programmatically verify that the publish process observed versioning rules. This is NOT AN ARCHITECTURAL DEFECT — versioning policy is a development-process constraint enforced by CI tools, not by runtime code. NOT A DESIGN DEFECT. Alternative verification: CI pipeline with `cargo semver-checks` in P2-2 validates semver compliance at merge time; spec_validation.rs tests verify that versioning_policy.rs constants match the declared Cargo.toml version string via string comparison.
- Exception entry 2 — Item: CHANGELOG format validation beyond existence checks is out of scope for automated tests. It is NOT TESTABLE to validate CHANGELOG prose quality through runtime assertions. Reason: CHANGELOG.md is a human-authored Markdown file whose format correctness (version heading format, date format, migration guide completeness) is a documentation-quality concern, not a runtime behavior concern. Automated tests can check file existence and version heading presence but cannot validate prose quality or migration guide completeness. This is NOT AN ARCHITECTURAL DEFECT — CHANGELOG standards are enforced by code review, not by runtime tests. NOT A DESIGN DEFECT. Alternative verification: is_changelog_required() return value is testable (UT [Normal] CHANGELOG notification requirement). Manual review verifies CHANGELOG content quality.
