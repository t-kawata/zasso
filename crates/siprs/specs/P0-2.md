# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0009 defines the four execution contexts (User async, Core reactor, PJSIP callbacks, Audio worker tasks), the core reactor thread model, and command serialization via unbounded MPSC. This is the threading foundation for the entire crate.

### Goal
Produce a complete specification document for siprs concurrency model, covering the four execution contexts, single-reactor threading architecture, RuntimeCommand serialization pattern, and the Send+Sync contract rationale.

### Purpose
The concurrency model is the architectural spine of the siprs crate. PJSUA (PJSIP) is a C library that spawns internal native threads and fires callbacks from them — the public Rust API must never execute directly on those callback threads. This spec defines the isolation boundaries and serialization strategy that make a safe async Rust wrapper possible.

### Motivation
The choice of execution context model, thread count, and command serialization determines every subsequent design decision (FFI wrappers, audio pipeline, state management). Without a precisely documented concurrency model, implementors have no basis for reasoning about thread safety, lock ordering, or the Send+Sync boundary. This specification must be written before any implementation code (P2).

### Constraints
- PJSUA thread safety: certain pjsua_* APIs must be called from the same thread; the spec must document how this is guaranteed via MPSC serialization.
- Single-reactor scalability ceiling: ~30 concurrent calls; the 100-accounts/300-calls threshold for partitioning is documented but not implemented.
- No unsafe code escapes ffi/ module (Rule C038).
- Audio RT callback prohibits blocking operations, allocations, or .await calls.
- The spec must be a standalone document — no external references that expire.

## Acceptance Criteria

- Four execution contexts are documented with their responsibilities
- Command serialization via MPSC is specified

- - [Edge case] The spec must document the boundary between AudioWorkerTask (async, may .await) and PJSIP RT callback (no blocking, no allocation, no .await). The lock-free queue (crossbeam_queue::ArrayQueue) is the only mechanism crossing this boundary. The spec must document the ~30 call ceiling as a deliberate design choice with the trigger conditions for architectural change (100 accounts / 300 calls).

## Invariants

- [Normal establishment] All four execution contexts MUST be explicitly documented with: (a) thread model (tokio task / std::thread / C native / blocking pool), (b) responsibilities and permitted operations, (c) communication mechanism with adjacent contexts. The RuntimeCommand enum MUST enumerate exactly the 10 variants from RFC §7.2 with consistent reply channel typing.
- [Invariant on error] Even if the reactor thread panics, the MPSC sender side MUST remain usable (drop-only semantics). The Shutdown command MUST be accepted exactly once; subsequent commands MUST be rejected with SipErrorKind::RuntimeShutdown. The oneshot::Sender MUST NOT be used after sending (documented as a programming error that panics).
- [Internal state invariant] The reactor is the sole owner of mutable runtime state (ClientState, AccountEntry, CallEntry). All mutations go through RuntimeCommand dispatch. The concurrency_contexts/ module MUST NOT import from runtime/, ffi/, or audio/. The RuntimeCommand enum and its dependency types (ClientConfig, AccountConfig, AccountId, CallId, OutgoingCallRequest, HangupReason, DtmfMethod, SipError) MUST all implement Send.
- [Boundary invariant] The audio RT callback path MUST NOT contain any blocking operation, memory allocation, or .await call — communication MUST be via lock-free queue (crossbeam_queue::ArrayQueue) only. The reactor MPSC channel is unbounded; no backpressure mechanism is specified for the initial design because the reactor processes commands faster than the user can submit them under the ~30-call load target.
