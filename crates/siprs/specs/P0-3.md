**Universal Testing Rules**

Write all code under the following non-negotiable rules:

1. Tests must be comprehensive and exhaustive for all observable behavior, including edge cases, failure modes, and invariants. Any behavior not covered by tests is considered undefined and unacceptable.

2. Do not write or accept any implementation whose correctness cannot be fully validated through tests. If correctness cannot be proven via tests, the implementation is invalid and must be redesigned.

3. If a feature cannot be completely and deterministically tested, treat this as a design failure. Refactor the architecture until full testability is achieved.

4. Tests are not a scoreboard and must never be treated as a goal in themselves. Passing tests does not imply correctness unless the tests fully capture the intended behavior.

5. It is strictly forbidden to modify or weaken tests to make an implementation pass. The implementation must conform to the tests, not the other way around.

6. Implementation is considered complete only when:
   - The tests fully and precisely specify the intended behavior.
   - The implementation passes all tests without exception.
   - The implementation's correctness is demonstrably guaranteed by those tests.

7. Any gap between test coverage and intended behavior is a critical defect. Resolve such gaps before considering the work complete.

## Background

**Goal:**
siprs crate のモジュール分割構成（RFC §6 定義のディレクトリツリー）を lib.rs + 各モジュールファイルとして実装し、単一 core reactor thread による全 pjsua_* 呼び出しのシリアライズ設計（§7 並行性モデル）の型骨格（RuntimeCommand enum, SipClient 構造体, ClientInner）を定義する。

**Purpose:**
siprs は zasso エコシステム内で音声通話の基盤を提供する。本チケットは crate 全体の「骨格」— モジュール構成・公開API境界・並行性制御の型定義 — を確立する。これにより後続チケット（P0-4, P4-9, P5-1 等）は確立されたモジュール境界に沿って個別機能を実装できる。

**Motivation:**
RFC §6 で設計されたモジュール構成と §7 の並行性モデルは、siprs 全体のアーキテクチャの根幹である。これを最初に固定しないと、各チケットが独自の判断でモジュール構成や型定義を行うリスクがあり、後で大規模な整合性修正が発生する。RFC フェーズ（P0）の最初の実装チケットとしてモジュール骨格を確立する。

**Constraints:**
- 本チケットでは Cargo.toml に新しい依存 crate を追加しない（標準ライブラリのみ）。依存を要する型（tokio, thiserror, crossbeam 等）は後続チケットで導入する
- config/client_config.rs の ClientConfig / ClientAudioConfig は依存未解決（P0-5, P1-1）のためコメントアウト状態を維持
- concurrency_model 配下の各ファイルの完全実装は後続チケット（P4-9, P5-1, P0-4）に委譲。本チケットではモジュール構造と型スケルトンのみ

- **Response:** 影響を受けるのは同一 crate 内のモジュールのみ。外部クレートへの影響は本フェーズでは発生しない

## Acceptance Criteria

- [Happy path] モジュール構成定義の完了確認:
  1. lib.rs に pub mod api, config, concurrency_model が宣言され、cargo check が通過する
  2. concurrency_model/mod.rs が存在し、6つの子モジュールを pub mod 宣言する
  3. concurrency_model 配下の各ファイルが RFC §7.2 / §8.1-8.5 の型定義スケルトンを持つ
  4. SipClient が #[derive(Clone)] を実装し、Send + Sync を静的に満たす
  5. lib.rs から pub use で再公開された型（SipClient, config::LogLevel 等）が外部テストコードからインポート可能
  6. SipError enum（Error::Io, Error::InvalidInput）が thiserror の Display 実装を持つ
  7. RuntimeCommand enum が全10バリアントを持ち、Debug トレイトを derive する
- [Error case] 不完全なモジュール宣言の検出:
  1. concurrency_model 内のいずれかのファイルが存在しない場合、cargo check がコンパイルエラーとなること
  2. 誤った型名での pub use 再公開はコンパイルエラーとなること
  3. SipClient が Send + Sync を満たさない場合、コンパイル時に static_assertions または トレイト境界チェックでエラーとなること
- [Edge case] 空のモジュール/スタブファイルの許容:
  1. 後続チケット委譲のため [::STUB::] マーカーが付与されたファイルでも cargo check が通過すること（pub trait Service {} のみのスタブ）
  2. 標準ライブラリ以外の依存 crate なしでモジュール構成全体が cargo check を通過すること
  3. lib.rs に実装ロジックが含まれず、モジュール宣言と pub use 再公開のみであること

## Boy Scout Rule

【翻訳可能性改善計画】

本チケットで新規作成/編集するファイルにおいて、以下の翻訳可能性ルールを徹底する:

1. **関数名は動詞句にする**:
   - 例: `fn process()` → `fn execute_runtime_command()` / `fn dispatch_to_reactor()`
   - メソッド名は API の意図を正確に反映（`add_account`, `make_call`, `hangup` 等は RFC で既に決定済み）

2. **変数名はドメイン概念を表現する**:
   - 例: `let cmd = ...` → `let runtime_command = ...`
   - 例: `let tx = ...` → `let reply_channel = ...`
   - 例: `let inner = ...` → `let client_inner = ...`

3. **一関数一責務**:
   - RuntimeCommand のハンドラーメソッドは各バリアントごとに個別のメソッドとして抽出
   - lib.rs はモジュール宣言と pub use 再公開のみに限定（実装ロジックを書かない）

4. **ハードコード値は名前付き定数に**:
   - マジックナンバーの代わりに const を定義（例: const DEFAULT_EVENT_BUS_CAPACITY: usize = 2048）
   - ただし本チケットでは Cargo.toml に依存 crate を追加しないため、定数定義のみ行う
