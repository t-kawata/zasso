# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P0-3: RuntimeCommand Enum & Command Serialization

**Ticket Key**: P0-3 · **Phase**: 0

## RFC Reference

~/shyme/zasso/crates/siprs/RFC-ROOT (§7.2)

## Background

### Goal
Establish the authoritative RuntimeCommand enum definition and MPSC serialization model for the siprs crate — the single input path through which all PJSUA operations (init, account management, calling, DTMF, shutdown) are serialized and dispatched to the reactor thread. This design ensures PJSUA thread-safety constraints are never exposed to crate consumers.

### Purpose
Provide a type-safe, Send+Sync-compatible command enum that (a) enumerates all PJSUA-facing operations as typed variants, (b) carries per-command oneshot reply channels for asynchronous result delivery, (c) is serializable through a single unbounded tokio::sync::mpsc channel, and (d) supports future extension via M20 feature-gated variants without breaking existing match arms.

### Motivation
PJSUA (PJSIP) is fundamentally not thread-safe — all API calls must execute on the same thread that initialized the library. Without an explicit serialization layer, consumers would need to manage PJSUA thread safety themselves, defeating the crate's safety promise. The RuntimeCommand+MPSC pattern encapsulates this constraint from the start: all 10 base operations (Initialize through Shutdown) plus 4 M20 operations are defined as enum variants, each carrying a oneshot reply channel. This is the foundational concurrency primitive that all higher-level APIs (P0-7 SipClient, P0-8 AccountConfig) will be built upon.

### Constraints
(1) Must use tokio::sync::oneshot::Sender for replies — no shared-state callback patterns. (2) Must achieve Send+Sync without requiring PJSUA types on the enum (PJSUA types are !Send). (3) Enum variants use type aliases for future types (ClientConfig, AccountConfig, AccountId, CallId, SipError, etc.) that will be defined in later tickets — the enum compiles as long as these types exist as minimal placeholder definitions. (4) M20 variants (ConfConnect, ConfDisconnect, GetAccountInfo, SubscribeAudio) must be feature-gated behind #[cfg(feature = "m20")]. (5) No unsafe code — the serialization model must be purely safe Rust.

## Invariants

- 【Normal establishment】All RuntimeCommand variants carry exactly one oneshot::Sender for reply delivery. Every variant construction must supply the sender. No variant may be constructed without a valid reply channel.
- 【Invariant on error】Even when a reply Sender is dropped (receiver cancelled) before the command executes, the RuntimeCommand enum itself must not panic or corrupt. The drop behavior of oneshot::Sender is idempotent — send() on a closed channel simply returns Err. No error handling code in command dispatch should unwrap or assume the receiver is alive.
- 【Internal state invariant】RuntimeCommand is pub(crate) — not accessible outside the crate. No public API may expose a RuntimeCommand reference. The enum discriminants are matched exhaustively in the reactor dispatch loop (future P0-7); a match on RuntimeCommand variants must never use a catch-all `_` arm because the compiler's exhaustiveness check on sealed enums prevents missing a new variant.
- 【Boundary invariant】The Send+Sync auto-trait implementation of RuntimeCommand must be verified at compile time. If any variant field is changed to a !Send or !Sync type (e.g., raw PJSUA pointers), the compile-time assertion must fail immediately. This prevents accidental thread-safety violations when extending the enum.
