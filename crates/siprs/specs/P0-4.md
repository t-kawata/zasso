# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P0-4: RuntimeCommand & EventBus Implementation

**Ticket Key**: P0-4 · **Phase**: 0

## RFC Reference

## Background

### Goal
Define the RuntimeCommand enum (10 variants with one-shot reply channels) as the sole dispatch mechanism for PJSUA operations, and implement the EventBus with split control/raw_sip broadcast channels for observable event delivery.

### Purpose
The RuntimeCommand enum enables thread-safe PJSUA command dispatch by serializing all operations through an unbounded MPSC channel, isolating consumers from PJSUA thread-safety constraints. The EventBus provides a loss-tolerant observation mechanism for UI updates and logging, with a dedicated raw_sip bus that prevents high-volume SIP message events from overwhelming control event delivery.

### Motivation
Without RuntimeCommand, every PJSUA call would expose unsafe thread-safety constraints to the consumer, violating the crate design goal of safe async-first SIP communication. Without EventBus, consumers would have no structured way to observe registration state changes, call lifecycle events, or raw SIP message traffic. The split-bus design (C021/N0020) is motivated by the requirement that raw SIP message volume must not cause control event loss.

### Constraints
(1) No tokio runtime yet — std::sync::mpsc provides the MPSC foundation (upgraded to tokio::sync::mpsc in P2 when tokio is added as crate dependency). (2) Placeholder types for SipError, AccountId, CallId, ClientConfig, AccountConfig until downstream P0-* tickets define them. (3) EventBus depends on tokio::sync::broadcast — tokio must be added as a crate dependency during this ticket implementation. (4) SipEventPayload variant payload structs reference downstream types — variants exist as skeletons with unit-like placeholders. (5) No PJSIP FFI bindings exist yet — RuntimeCommand is purely an in-process command enum, not an FFI boundary type.

## Acceptance Criteria

- RuntimeCommand covers all 10 operations: Initialize, AddAccount, RemoveAccount, SetRegistration, MakeCall, Hangup, Hold, Unhold, SendDtmf, Shutdown — verified by construction and exhaustive pattern match test
- EventBus provides control bus (always) and raw_sip bus (optional) via tokio::sync::broadcast with new/subscribe_control/subscribe_raw_sip/publish/publish_raw_sip methods — verified by channel creation and publish/subscribe tests
- AccountEventReceiver filters by account_id — only SipEvent where meta.account_id == receiver account_id are returned; others are silently dropped — verified by multi-account filtering test
- **[Happy path]** RuntimeCommand enum with 10 variants constructs correctly with ReplySender. EventBus::new(1024, Some(1024)) creates both channels; publish sends events to all subscribers. AccountEventReceiver receives only events for its account_id. SipEventPayload includes all 40+ event variants with Debug+Clone and #[non_exhaustive]. SipEvent wraps payload with EventMeta (event_id, timestamp, account_id, call_id, direction, headers, status_code, reason_phrase, logical_context).
- **[Error case]** Broadcast overflow: slow subscriber exceeds capacity → RecvError::Lagged(n) with n=number of dropped messages. Error is normal (not a panic). Subscriber can continue receiving subsequent events after Lagged. ReplySender::send() on dropped receiver returns Err — caller handles via ? propagation.
- **[Edge case]** EventBus::new(1, Some(1)) with minimum capacity: one unread message, second publish causes Lagged(1) for slow subscriber. EventBus::new(0, None): publication succeeds but any receive is immediately Lagged. AccountEventReceiver::recv() with no matching events: must not hang (timeout with tokio::time::timeout(100ms) returns Elapsed). EventMeta event_id wraps at u64::MAX (documented, not a bug).

## Invariants

- 【Normal condition】RuntimeCommand enum must be Send+Sync for thread-safe MPSC dispatch. EventBus control/raw_sip channels are initialized with configurable capacity. SipEventPayload enum covers all 40+ event variants with #[non_exhaustive]. All SipEvent+SipEventPayload+EventMeta implement Debug+Clone for loggability.
- 【Error invariant】RecvError::Lagged(n) on broadcast channels must not panic — it is a normal condition for slow consumers. ReplySender::send() must not panic on dropped receiver. RuntimeCommand construction with invalid placeholder types is prevented at compile time.
- 【Internal state invariant】EventBus internal state: control Sender always exists after new(); raw_sip is Option (None when disabled). AccountEventReceiver always has an account_id. Channel capacity is immutable after construction.
- 【Boundary invariant】EventBus::new(0, ...) with zero capacity: publications succeed but any receive lag causes immediate Lagged. EventMeta event_id is u64 — wraps silently at MAX (acceptable for crate lifetime). broadcast channel capacity ceiling: tokio allows up to isize::MAX, but practical limit is 2048 per design spec.
