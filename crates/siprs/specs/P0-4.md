# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P0-4: Error Design — SipError, SipErrorKind, and M20 RuntimeCommand Error Mapping

**Ticket Key**: P0-4 · **Phase**: 0

## RFC Reference

## Background

- **Goal**: Implement SipError struct + SipErrorKind enum (23 variants) per RFC §14 N0016, plus M20 RuntimeCommand error converters (N0017) reusing existing variants (no new variants for M20).
- **Purpose**: Uniform type-safe error type across all siprs public API. SipErrorKind classification enables app-level error handling without message parsing. retryable flag guides retry logic. native_status preserves PJSUA diagnostic code for logging/debugging.
- **Motivation**: P0-3 has minimal 3-variant placeholder enum. Without this ticket, callers cannot distinguish transient errors (Timeout=retry recommended) from permanent errors (InvalidConfig=fix config). M20 commands need clear error semantics without enum bloat — no command-specific variants.
- **Constraints**: (1) AccountId/CallId newtypes deferred to P0-7 — use Option<u64> forward-compatible design. (2) PJSUA FFI deferred to P0-6 — pj_status_t uses manually-defined sentinel constants matching PJSIP documentation. (3) Must replace existing SipError enum in src/error.rs — update all downstream callers (config.rs validate(), client.rs SipClient methods). (4) Pure error design — no feature creep beyond error types.

## Acceptance Criteria

- 【Happy path】SipError with InvalidConfig constructible: SipError { kind: InvalidConfig, message: "bad host", native_status: None, account_id: None, call_id: None, retryable: false }. All 23 SipErrorKind variants display their variant name in Display output. M20 ConfConnect converter returns Ok(()) on PJ_SUCCESS, Err(SipErrorKind::InvalidState) on conf_port unresolved (PJ_EINVALIDOP). From<ReactorError> maps all 3 ReactorError variants correctly.
- 【Error case】PJSUA FFI error (pj_status_t=1234) converts to NativeError with native_status=Some(1234), retryable=true, message containing operation context. ReactorError::BackendError converts to NativeError preserving the error message. M20 ConfConnect non-EINVALIDOP PJSIP error converts to NativeError (RFC N0017 table says "InternalError" but this maps to actual variant NativeError per N0016 definition — NativeError is the only catch-all FFI variant in SipErrorKind). GetAccountInfo with deleted account returns AccountNotFound (retryable=false, permanent deletion).
- 【Edge case】SipError with all Option fields None (native_status=None, account_id=None, call_id=None) is valid — Display output still shows "{kind}: {message}". Empty message string accepted (no panic). account_id=Some(0) treated as valid non-None sentinel (not treated as None). pj_status_t=PJ_SUCCESS returns None from convert_pj_status (no error). Unknown/undefined pj_status_t falls back to NativeError. SipErrorKind exhaustive match over exactly 23 arms compiles — a 24th arm added would fail compilation.

## Invariants

- 【Normal establishment】SipError struct constructible with 6 fields. SipErrorKind has exactly 23 discriminant variants. Both implement Send + Sync for async API compatibility. retryable flag set per variant: transient errors (AccountNotFound, CallNotFound, Timeout) retryable=true; config/terminal errors (InvalidConfig, ShutdownInProgress, InternalInvariantBroken) retryable=false.
- 【On error】Error conversion functions (convert_pj_status, convert_conf_connect_error, From<ReactorError>) never panic. No uninitialized SipError instances. SipErrorKind always from valid set of 23 variants.
- 【Internal state】SipError is a pure data struct with no mutable state. Once constructed, immutable (no setters — only with_* builder-style constructors return new instances). SipErrorKind is Copy enum (no heap allocs).
- 【Boundary】account_id/call_id use Option<u64>: None = context N/A, Some(0) = valid non-None sentinel for future newtype upgrade. native_status Option<i32>: None = no FFI code, Some(status) = pj_status_t value. message always String (constructors accept Into<String>).
