# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P0-4: Comprehensive Error Design — SipError & M20 Command Error Handling

**Ticket Key**: P0-4 · **Phase**: 0

## RFC Reference

~/shyme/zasso/crates/siprs/RFC-ROOT (§14)

## Background

N0016 defines SipError struct (kind, message, native_status, account_id, call_id, retryable) and SipErrorKind enum. N0017 defines error design for M20 RuntimeCommands reusing existing SipErrorKind variants. Maps to src/error/error_design_siperror.rs and src/error/m20_runtime_command_error.rs.

### Goal
Implement the SipError struct and SipErrorKind enum as specified in §14 of RFC-ROOT, providing a unified error type for all siprs public APIs. Implement M20 RuntimeCommand error conversion functions that reuse existing SipErrorKind variants.

### Purpose
Centralize all SIP error handling into a single, well-typed error type with stable classification (SipErrorKind), native PJSUA error preservation (native_status: Option<i32>), domain context (account_id, call_id), and recoverability information (retryable: bool). This eliminates ad-hoc error string passing and enables systematic retry/fallback logic.

### Motivation
P0-3 (RuntimeCommand enum) depends on SipError for the SipReply<T> = oneshot::Sender<Result<T, SipError>> pattern. Without SipError, all MPSC reply channels would use String-based errors, losing type safety and classification. M20 commands (ConfConnect, ConfDisconnect, GetAccountInfo) need error conversion but must NOT introduce new SipErrorKind variants to keep error handling exhaustive and manageable.

### Constraints
1. No new SipErrorKind variants for M20 commands — reuse InvalidState, AccountNotFound, NativeError only. 2. thiserror v2 must be used for Error derive. 3. SipError must implement Send + Sync (oneshot channel requirement). 4. All types must be pub(crate) at minimum (internal crate usage). 5. Must compile with the existing Cargo.toml dependency set (thiserror = "2" already added). 6. AccountId and CallId types must be imported from crate::concurrency_contexts (stub types from P0-3) until P0-9 replaces them.

## Investigation

- [Architecture] RFC-ROOT §14 defines SipError as the unified error type for all siprs public APIs. SipError wraps: kind (SipErrorKind enum), message (human-readable), native_status (Option<i32> for PJSUA error codes), account_id/call_id (domain context), retryable (bool for recoverability).
- [Source evidence] src/error/error_design_siperror.rs: currently pub enum Error {} — complete stub (N0016). src/error/m20_runtime_command_error.rs: currently pub enum Error {} — complete stub (N0017). Both files have the Initial Design Artifact header with N0016/N0017 node IDs.
- [Source evidence] src/concurrency_contexts/command_serialization.rs lines 29-35: defines a stub pub(crate) struct SipError(pub(crate) String); with a STUB marker that says "Replace with use crate::error::SipError once P0-4 implements it." P0-4 explicitly resolves this.
- [Source evidence] src/concurrency_contexts/command_serialization.rs defines SipReply<T> = oneshot::Sender<Result<T, SipError>> (line 105). All RuntimeCommand variants use SipReply<T> in their reply fields. This confirms the dependency: P0-3 -> P0-4.
- [Dependency analysis] Cargo.toml already has thiserror = "2" (added by P0-3 as a STUB for P0-4). AccountId and CallId are stub types from P0-3; they will be replaced by real types from P0-9 (crate::model).
- [Pattern analysis] The RFC defines 22 SipErrorKind variants. M20 error conversion functions (convert_conf_connect_error, convert_conf_disconnect_error, convert_get_account_info_error) must only produce InvalidState, AccountNotFound, NativeError — no new variants allowed.
- [Retryable classification] RFC specifies retryable=true for recoverable errors (Timeout, Transport init, Registration, Auth, Invite, Media negotiation, ICE, NativeError). retryable=false for unrecoverable (InvalidConfig, InvalidState, AlreadyInitialized, NotInitialized, AccountNotFound, CallNotFound, MediaInitFailed, TlsFailed, SrtpFailed, AudioFormatUnsupported, AudioPipelineBroken, DtmfFailed, ChannelClosed, ShutdownInProgress, InternalInvariantBroken).

## Invariants

- [Normal condition] SipError.kind must always be a valid SipErrorKind variant — no invalid/uninitialized discriminant state. SipError.message must always be a valid UTF-8 String (not null, not uninitialized).
- [Error invariant] Even when SipError is constructed with native_status=None, account_id=None, call_id=None, the struct remains fully functional and Display/Debug produce valid output — no partial initialization state.
- [Internal state invariant] The retryable flag must be consistent with the SipErrorKind: once assigned, it must not be changed implicitly. The convenience constructors (invalid_state, not_found, internal_error) must set retryable according to the error classification table.
- [Boundary invariant] native_status field accepts the full i32 range (−2^31 to 2^31−1), including PJ_SUCCESS=0. account_id accepts the full u64 range (0 to 2^64−1). call_id accepts the full u64 range (0 to 2^64−1). message accepts any valid String length (0 to usize::MAX).
