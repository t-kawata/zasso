# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

This ticket implements the complete event system: EventBus with control/raw_sip broadcast channels (N0019), design decisions for loss-tolerant delivery with Lagged detection (N0020), NativeEvent to SipEventPayload conversion for all P0/P1/P2 priority events (N0021), CallState/CallMediaState mapping from pjsip_inv_state and media_status (N0022), RegistrationStateChanged via RuntimeCommand::GetAccountInfo pattern (N0023), DtmfSent two-phase design with timeout fallback (N0029), and Dual Client PJSIP callback routing with account_id-based EventBus dispatch (N0038).

## Goal
The P0-5 event system provides the complete bridge between PJSIP C callbacks and Rust async event consumers. It defines the SipEventPayload enum (all P0 variants: Registration/Call/DTMF; P1: Transport/ICE; P2: supplemental), the EventBus with split control/raw_sip broadcast channels, the NativeEvent-to-SipEventPayload conversion functions, and the Dual Client routing infrastructure. Every PJSIP callback-generated event is delivered to the correct SipClient's EventBus as a typed SipEvent struct.

## Purpose
SipClient consumers (UI layer, audio pipeline, logging) need observable, structured notifications about SIP state changes. Without this event system, application code would need to poll for state or interpret raw PJSIP callbacks directly. The EventBus provides a decoupled publish-subscribe pattern where:
- Reactor publishes SipEvents onto broadcast channels
- Multiple consumers independently subscribe and filter (via AccountEventReceiver)
- RawSIP messages are isolated on a separate bus to prevent control event loss

This is the primary async communication channel between the synchronous PJSIP thread (C callbacks) and the async Rust world (tokio tasks).

## Motivation
This is the foundational event infrastructure for the entire crate. All observable SIP behavior — registration status changes, call state transitions, DTMF events, media state changes — flows through this system. Every downstream feature (P2-2 error payloads, P2-4 audio pipeline, P4-1 registration state machine) depends on events being delivered. The current stub (src/client.rs uses mpsc::Receiver<()>) blocks all downstream development.

Without this ticket:
- No SipEventPayload type exists (all stubs)
- NativeEvent conversion is unimplemented
- SipClient returns dummy event receiver (cannot observe any SIP events)
- Dual Client mode (multiple SipClient instances) has no event routing

## Constraints
- Broadcast channel (lossy delivery): tokio::sync::broadcast is the only supported channel type. No reliable delivery, no per-subscriber retransmission. This is by design (N0020).
- PJSUA dependency: NativeEvent types mirror PJSIP callback signatures (pjsip_inv_state, pjsua_call_media_status). Any PJSIP version mismatch may require updating the mapping.
- Single Reactor constraint: global_runtime() must remain unchanged. Dual Client uses EventBus dispatch only — no second Reactor.
- All implementation targets are stub files (pub enum State {} / pub trait Service {}). This is net-new implementation, not refactoring of existing code.
- DtmfSent 500ms timeout: This is a fallback for when PJSIP does not fire a send-complete callback. The timeout may race with actual PJSIP callback delivery (firing both DtmfSent events) — consumer must handle duplicates.

## Acceptance Criteria

- EventBus delivers all control events; loss is detectable via Lagged(n)
- AccountEventReceiver filters precisely to one account_id
- All P0 NativeEvent types convert correctly to SipEventPayload
- CallState maps all 5 pjsip_inv_state values without panic
- RegistrationStateChanged produces correct Succeeded/Failed events
- DtmfSent fires via PJSIP callback or 500ms timeout fallback
- Dual Client routes events to correct client EventBus by account_id
- [Happy path] A single SipClient is initialized, registers a SIP account, makes a call, and receives the call state transition events (OutgoingCallStarted -> OutgoingCallTrying -> CallConnected) on the AccountEventReceiver subscribed to that account_id. Each event has correct EventMeta (timestamp, event_id, account_id, call_id).
- [Error case] A NativeEvent::RegistrationStateChanged fires for an account where pjsua_acc_get_info() fails (returns error). The EventBus delivers a RegistrationFailed event containing the SipError with details. The client is not left in an indeterminate state — the query API returns the correct registration state.
- [Edge case] Two SipClient instances share the same PjsuaBackend (Dual Client mode). An incoming call event for account_id=A is published. Client A's AccountEventReceiver receives CallStateChanged; Client B's AccountEventReceiver (subscribed to account_id=B) must NOT receive the event. account_id=None lifecycle events (ClientInitialized, ClientShutdown) must be received by both clients.

## Invariants

- [Normal condition] EventBus::publish() must never block — broadcast::Sender::send() is non-blocking by design. SipEventPayload must be Clone + Debug. EventBus must be Clone (all clones share same Sender). NativeEvent conversion must be total over defined P0 variants.
- [Error invariant] On Lagged(n), the receiver skips n messages and resumes from current position — no crash or state corruption. AccountEventReceiver must not panic on Lagged(n). DtmfSent timeout must not abort ongoing operations.
- [Internal state invariant] EventBus Sender is shared across all Clones. AccountEventReceiver holds its own broadcast Receiver. Reactor owns the EventBus Sender + client_event_buses map. client_event_buses is only mutated by SipClient initialization/shutdown, not by event dispatch.
- [Boundary invariant] EventBus default capacity 2048 must accommodate ~100 concurrent calls (~20 events/call). RawSIP channel capacity must be configured independently. DtmfSent timeout default 500ms must be less than typical PJSIP DTMF duration.

        },

    }
