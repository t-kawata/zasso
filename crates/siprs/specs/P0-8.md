# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0034 specifies AudioWorkerTask driving mechanism and audio source lifecycle APIs (add/remove/set_gain/mute). N0038 defines Dual Client PJSIP callback routing with single Reactor + EventBus split and account_id-based event dispatch.

### Goal
Specify the architecture and contracts for (1) AudioWorkerTask driving mechanism with AsyncAudioSource lifecycle management (add/remove/set_gain/mute) per N0034, and (2) Dual Client PJSIP callback routing with single Reactor + EventBus split per N0038. Produce spec documents that P0-9 (AudioWorkerTask) and P0-10 (Dual Client Reactor) can implement against.

### Purpose
These two subsystems form the foundation of zasso's voice communication architecture. The AudioWorkerTask bridges the gap between async Rust audio sources (user code running on tokio) and the PJSIP real-time audio callback (C-level lock-free queue boundary). The Dual Client routing enables integration testing with multiple independent SipClients sharing a single PjsuaBackend — a requirement imposed by PJSIP's singleton initialization constraint (pjsua_init() can be called only once). Without Dual Client routing, tests requiring two SipClients would be impossible without modifying PJSIP itself.

### Motivation
Both specifications are gate dependencies for downstream implementation work. Audio mixing (P3-3), IN/OUT pair alignment (N0035), resampling (N0036), and media bridge (N0049) all depend on the AudioWorkerTask frame processing design. Dual Client routing is required for P0-10 (Reactor integration) which in turn enables P5-3 (PJSIP Callback Implementation). The current codebase has all event types and error types defined (P0-4 through P0-7) but no audio pipeline or multi-client orchestration yet — P0-8 bridges that gap with concrete specifications.

### Constraints
(1) PJSIP singleton constraint: pjsua_init() can be called exactly once per process. The PjsuaBackend must use OnceLock or similar. (2) RT boundary: AudioWorkerTask runs on tokio blocking pool, never on PJSIP's real-time callback thread. The only cross-boundary communication is the lock-free queue. (3) No new dependencies on audio libraries — mixing is done via pure Rust (saturating i16 arithmetic). (4) Audio source lifecycle mutations must be frame-boundary-safe (RwLock pattern). (5) The global_runtime() pattern from P0-3 must remain unchanged — single Reactor for all clients.

## Scope

## Invariants

- [Normal condition] (1) AudioMixer must have at least one registered AsyncAudioSource before process_frame produces non-silent output. (2) AudioWorker must be constructed with frame_duration > 0. (3) DualClient Reactor must have at least the default_event_bus initialized. (4) SourceHandle values must be valid Slab keys (non-zero, within capacity).
- [Error invariant] (1) Even if process_frame encounters errors from individual AsyncAudioSource::next_chunk(), the mixed output frame is best-effort: available sources' frames are mixed, absent sources are skipped. (2) DualClient dispatch_event must never panic regardless of account_id value. Unknown account_ids silently fall back to default_event_bus. (3) out_queue overflow on the lock-free queue never causes data corruption — it silently drops oldest (lossy by design, matching EventBus guarantees).
- [Internal state invariant] (1) AudioMixer.sources is always behind RwLock — concurrent reads (process_frame) and writes (add/remove) are safe. (2) SourceEntry fields: source (Box<dyn AsyncAudioSource>), gain (f64, always clamped to [0.0, 1.0] or defaulting to 1.0), muted (bool). (3) AudioWorker.mixer reference is Arc<AudioMixer> — shared ownership between worker and audio API layer. (4) DualClient Reactor.client_event_buses is a HashMap<AccountId, EventBus>. The default_event_bus entry is never removed.
- [Boundary invariant] (1) AudioMixer source capacity is bounded by Slab's capacity (default 32 or configurable). Adding beyond capacity returns SipError::InvalidState. (2) process_frame output buffer size = frame_samples = sample_rate * channels * frame_duration_secs. (3) set_gain accepts f64 in [0.0, 1.0]. Values outside this range are clamped. (4) frame_duration must be ≥ 1ms and ≤ 100ms. Values outside this range are rejected at AudioWorker construction.

This ticket is a specification (spec) ticket — it does not produce implementation code or modify existing files. Therefore, the Boy Scout Rule translatability improvements will be applied in the implementation tickets (P0-9, P0-10).

**Planned improvements for P0-9 (AudioWorkerTask):**

This is not a design defect: the architecture places a lock-free queue at this boundary; the producer side (AudioWorker) is fully testable, and only the consumer side (RT callback) is untestable without PJSIP.
- [Alternative verification] Simulated consumer thread reads from out_queue matching RT callback pattern. → Covered by IT: AudioWorkerTask ↔ AudioMixer out_queue.
- - [Item] DualClient PJSIP callback dispatch not testable with real PJSUA backend.
- [Reason] pjsua_init() is a singleton — callable only once per process. Unit tests cannot use real PJSIP. This is not an architectural defect: the dispatch_event routing logic is a pure function of account_id → EventBus, testable with mock events.
- [Alternative verification] Unit tests with mock SipEvent/account_id values verify routing. → Covered by UT: DualClient dispatch_event variants.
- - [Item] Full end-to-end audio pipeline (source → worker → queue → PJSUA conf_port → network) not testable without PJSUA + network peers.
- [Reason] PJSUA conference port is FFI-bound. This is not an architectural defect: the pipeline is segmented at trait/queue/FFI boundaries, each independently testable.
- [Alternative verification] Stage-pair integration tests: source→worker, worker→queue, queue→conf_port (P5-3 mock). → Covered by ITs across P0-9/P5-3.

## Notes

- [Implementation steps] (1) P0-9 (AudioWorkerTask): Implement AudioMixer + AudioWorker + process_frame + source lifecycle API + mix_i16_frame(). New audio/ module. Add crossbeam and slab deps. (2) P0-10 (Dual Client Reactor): Implement Reactor with client_event_buses HashMap, dispatch_event routing logic, default EventBus tracking. Integrate with existing RuntimeCommand enum. (3) P0-9 depends on N0032 (AsyncAudioSource trait) and N0030 (AudioFormat). These are currently stubs — their concrete implementation is a prerequisite. (4) P5-3 (PJSIP Callback Implementation) depends on P0-10 reactor for event routing.
- [Risks] (1) AudioWorker on tokio blocking pool may cause pool exhaustion with 30+ concurrent workers. Mitigation: Use dedicated std::thread if blocking pool proves insufficient. (2) crossbeam::ArrayQueue is fixed-capacity; overflow silently drops frames. Mitigation: Monitor queue occupancy via health metrics; size should be 2-3 frame periods. (3) Slab compaction after source removal may cause fragmentation. Mitigation: Monitor Slab::len() vs capacity and log when fragmentation exceeds threshold. (4) DualClient HashMap lookup latency on critical path. Mitigation: AccountId is u32 — HashMap is O(1); acceptable.
- [Caveats] (1) The AudioWorker does NOT interface with the PJSIP conference bridge directly — that is the responsibility of N0049 (Media Bridge & PJSUA Conference Port, P3-3+). This spec covers the worker → out_queue path only. (2) The DualClient dispatch_event does NOT define how enqueue_native_event is called from PJSIP callbacks — that is P5-3's responsibility. This spec covers the routing (Reactor side) only. (3) SourceHandle is defined as a newtype over u32 (Slab key). It must not be confused with AccountId or CallId.
- [Open items] (1) Detailed AudioFormat struct fields (sample_rate: u32, channels: u8, frame_samples: usize) — defined by N0030 (P0-8 prerequisite but currently a stub). P0-9 implementation may need to define a minimal AudioFormat locally. (2) mix_i16_frame() algorithm: i32 accumulation with saturating_cast to i16. Need to define overflow behavior precisely (clamp vs wrap). RFC §24.3 specifies saturating. (3) Slab vs alternative (Vec with tombstone, generational arena) — Slab chosen for O(1) insert/delete and contiguous iteration. Revisit if fragmentation becomes problematic.
- [Future improvements] (1) Slab-based source storage with generational indices (prevent use-after-free on SourceHandle). (2) AudioWorker priority scheduling (VoIP frames prioritized over non-real-time sources). (3) DualClient reactor scalability: partitioning by account group for >300 concurrent calls. (4) Configurable frame_duration per AudioMixer (currently fixed at construction).
