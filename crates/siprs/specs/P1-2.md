# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0021 defines complete NativeEvent to SipEventPayload mapping table. N0022 provides pjsip_inv_state to CallState mapping and media_status conversion. N0023 defines the RegistrationStateChanged processing via RuntimeCommand::GetAccountInfo pattern. Maps to src/state/m20_native_event_conv.rs, src/state/m20_callstate_mapping.rs, src/state/m20_registr_cmd_pat.rs.

### Goal
Implement three pure conversion functions + one data struct that bridge PJSIP NativeEvent callbacks to the siprs SipEventPayload event system: (1) convert_native_event_to_payload in m20_native_event_conv.rs — maps all 12 NativeEvent variants to Option<SipEventPayload> with P0/P1/P2 priority tiers; (2) convert_call_state + convert_call_media_state in m20_callstate_mapping.rs — maps pjsip_inv_state values 0-4 and pjsua_call_media_status values 0-4 to SipEventPayload; (3) AccountInfoSnapshot struct + RegistrationStateChanged flow in m20_registr_cmd_pat.rs — bridges RegistrationStateChanged through RuntimeCommand::GetAccountInfo.

### Purpose
These conversion functions are the bridge between the PJSIP C callback layer (NativeEvent) and the typed Rust event system (SipEventPayload). Without them, PJSIP events like registration state changes, call state transitions, media state changes, and DTMF digits would remain as opaque C structs and never reach the application layer as typed, inspectable Rust events. The CONNECTING state discrimination (Trying vs Ringing) is essential for correct call-progress UI.

### Motivation
M20 phase requires P0 NativeEvent events (Registration/CallState/CallMediaState/DTMF) to be functional for integration testing. These are the minimum events needed to verify end-to-end SIP call flows in tests. The current stub files (pub enum State {}) must be replaced with real implementations.

### Constraints
(1) FFI boundary: pjsip_inv_state and media_status are C integer enums — Rust code matches on documented constant values, not PJSIP types. (2) Stateless pure functions: converters must not hold mutable state; CONNECTING discrimination receives previous_state as parameter. (3) No EventBus dependency in this layer — conversion layer returns Option<SipEventPayload>; publish responsibility lives upstream in Reactor (P0-5/P0-7). (4) All 12 NativeEvent variants must be matched exhaustively — no wildcard _ arm.

## Acceptance Criteria

- Happy path: All 5 P0 NativeEvent variants (RegistrationStateChanged, RegistrationStarted, CallStateChanged, CallMediaStateChanged, DtmfDigit) map to correct SipEventPayload variants with correct field values. CONNECTING state correctly discriminates Trying vs Ringing based on previous_state. RegistrationStateChanged produces RegistrationSucceeded when AccountInfoSnapshot.status==200 and RegistrationFailed for 4xx/5xx/6xx status.
- Error case: P1 NativeEvent variants (TransportStateChanged, IceTransportError) return None (intentional P0 priority skip). P2 variants return None. convert_call_state with CONNECTING and unknown previous_state defaults to Trying. convert_call_media_state with NONE media_status returns None. RegistrationStateChanged with GetAccountInfo returning Err results in RegistrationFailed.
- Edge case: pjsip_inv_state values outside 0-4 range return None from convert_call_state. AccountInfoSnapshot with registration_status=0 (unregistered) returns RegistrationFailed. call_id=0 and call_id=u64::MAX propagate correctly through conversions. RegistrationStarted acc_id=0 (sentinel) constructs correctly.

## Invariants

- [Normal condition] NativeEvent must be converted deterministically — same event always produces same SipEventPayload. pjsip_inv_state must be in range 0-4 before pattern matching. CONNECTING discrimination requires previous_state parameter.
- [Error invariant] On any unrecognized NativeEvent variant or out-of-range pjsip_inv_state value, the function returns None rather than panicking. GetAccountInfo error never produces a registration success event. Empty/zero-length digit in DtmfDigit never panics.
- [Internal state invariant] convert_call_state is stateless (pure function) — all state needed for CONNECTING discrimination is passed via previous_state parameter. convert_call_media_state takes backend reference for media_status query — no mutable state held across calls.
- [Boundary invariant] pjsip_inv_state values 0 and 5+ must both return None (distinct boundary behavior at both ends). call_id=0 and call_id=u64::MAX must propagate unchanged. AccountInfoSnapshot.registration_expires=0 maps to RegistrationFailed.

## Boy Scout Rule

Translatability improvements for P1-2 implementation:

1. Function naming (verb phrases): convert_native_event_to_payload, convert_call_state, convert_call_media_state, registration_state_to_event — all read as explicit actions. No abbreviations or acronyms beyond standard ones.

2. Variable naming (domain concepts): Use previous_call_state not prev; registration_status not rs; native_event not ev. AccountInfoSnapshot field names match RFC prose: registration_status, registration_expires, online_status.

3. One function, one responsibility: convert_native_event_to_payload dispatches by variant to dedicated functions (convert_call_state, convert_call_media_state). No monolithic match-within-match logic. CONNECTING discrimination logic is self-contained in convert_call_state.

4. Hardcoded values as named constants: PJSIP_INV_STATE_NULL=0 through PJSIP_INV_STATE_DISCONNECTED=4 as named constants. MEDIA_STATUS_ACTIVE=0 through MEDIA_STATUS_ERROR=4 as named constants. Avoid raw integer literals in match patterns.

5. No error swallowing: All match arms return explicit values — no wildcard _ that silently ignores unexpected values. Out-of-range values log via tracing::warn! before returning None.

6. Existing code cleanup (Boy Scout): The placeholder pub enum State {} in all three files will be replaced with real implementations. The TODO: STUB comments will be removed. The src/state/mod.rs file (currently non-existent) will be created to properly declare module structure — this follows the Rust module file responsibility pattern (mod.rs = declarations only, no logic).

### Exceptions

- Exception: PJSIP FFI integration — NativeEvent enum definition depends on pjsip_inv_state C enum values and pjsua_call_media_status C enum values. These cannot be unit tested as they require PJSIP headers at compile time (not testable). This is NOT a design defect — the C enum values are documented constants (0-4 for inv_state, 0-4 for media_status) and the conversion logic uses these documented integer values via matching; if these constants were incorrect at the FFI level the error would be caught at integration test time rather than compile time, but the match logic itself is fully unit-testable with the documented integer values.
- Exception: EventBus publish destination — This ticket implements the NativeEvent→SipEventPayload conversion functions and AccountInfoSnapshot struct. The actual EventBus publish call is owned by the Reactor (P0-5/P0-7) and is not accessible from this layer (cannot test). This is NOT a design defect — the separation of concerns (conversion layer returns Option<SipEventPayload>, Reactor handles publish) is intentional architecture validated by RFC section M20. Integration tests in Layer 2 (MockBackend) can construct the full flow by plumbing the converter output to EventBus manually, proving the gap is not architectural.
- Exception: AccountInfoSnapshot registration_expires timing — The expiry value depends on real PJSIP registration flow and cannot be precisely asserted in unit tests (not testable). This is NOT a design defect — the struct carries Option<u32> as a data container; field propagation can be verified with fixed values (Some(3600), None, Some(0)). The timeline-dependent expiry behavior is exercised by integration tests with real PJSIP registration flows.
