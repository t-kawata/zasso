# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0052 defines 4-layer test strategy: Unit (PJSIP-free), State-Machine (MockBackend), SIP Integration (Docker), Interop (real PBX). N0053 maps M20 features to test layers with placeholder resolution conditions. N0054 specifies CI matrix, Docker integration test job, and prebuilt refresh pipeline.

### Goal
Establish a comprehensive 4-layer test strategy and CI/CD pipeline for the siprs crate, ensuring all M20 features have assigned test layers with documented verification criteria, and that the CI pipeline provides automated build/test across all 3 target OSes with Docker-based SIP integration testing and macOS prebuilt refresh automation.

### Purpose
Define a structured testing approach that provides fast developer feedback (Layer 1/2 unit tests, ~seconds) while ensuring real SIP protocol compatibility (Layer 3 Docker tests) and production PBX interoperability (Layer 4). The CI/CD pipeline eliminates manual build steps and ensures every commit is tested against all target platforms.

### Motivation
Current test infrastructure is minimal (stub files only: `test_strategy_4layer.rs`, `m20_test_dual_client.rs`, `cicd_docker_prebuilt.rs` all contain `[::STUB::]` markers). No CI workflows exist. M20 feature implementation (P0-2 through P1-3) has outpaced test infrastructure; without documented test layers, each new feature lacks a defined verification strategy, risking regressions as the codebase grows.

### Constraints
- Must maintain PJSIP-free compilation for fast developer feedback — Layer 1/2 tests cannot depend on pjsua FFI
- Layer 3 tests must be gated behind `#[cfg(feature = "pjsip")]` or `#[ignore]` since they need Docker

- CI matrix limited to GitHub Actions runners (windows-latest, macos-14, ubuntu-22.04) per §28 Build Strategy

### Exceptions

- **Exception 1: Docker-based SIP integration tests (Layer 3)**
  - Item: Docker Asterisk/FreeSWITCH integration tests are not testable via `cargo test --lib` because they require Docker daemon with port bindings (5060/udp, 5061/tcp), which is only available on ubuntu-22.04 GitHub Actions runner
  - Reason: These tests use actual pjsua library via `--features pjsip` and cannot run without Docker. Core unit tests must remain PJSIP-free for fast `cargo test` feedback (Layer 1 and Layer 2 constraints).
  - Justification: This is not a design defect — the feature is testable in Docker CI environment, just not in `cargo test --lib`. The architectural separation of PJSIP-dependent vs PJSIP-independent tests is intentional. This is a CI environment constraint, not an architectural defect.
  - Alternative verification: The spec document includes complete Docker configuration (image: asterisk:20.6.0, port maps, env vars) and CI job definition. A #[cfg(feature = "pjsip")] gated integration test file verifies the spec document references Docker correctly.
- **Exception 2: Layer 4 interop tests with real PBX/Proxy**
  - Item: Interop tests against real Asterisk LTS, FreeSWITCH, OpenSIPS, Kamailio, and 3CX SBC are not testable in CI because they require network access to live infrastructure
  - Reason: These tests require PBX instances with specific configurations (SRTP mandatory on 3CX, TLS transport on OpenSIPS, etc.) that cannot be replicated in ephemeral CI containers.
  - Justification: This is not a design defect — each interaction with each PBX is deterministic and could be tested given the infrastructure. The limitation is purely operational (no live PBX CI runners). This is an environmental constraint, not an architectural defect.
  - Alternative verification: Spec documents P0/P1 priority split with detailed test catalog per PBX (REGISTER, INVITE, BYE, DTMF, SRTP, etc.). Manual test procedures are referenced. Layer 3 Docker tests verify the code paths that Layer 4 will exercise in production.
- **Exception 3: Prebuilt PJSIP refresh pipeline end-to-end verification**
  - Item: The full prebuilt refresh pipeline (cmake configure/build on macos-14, artifact upload) is not testable during `make test` because it requires specific macOS toolchain and network access. It is impossible to test within the unit test framework.
  - Reason: cmake build takes 5-10 minutes, requires specific macOS toolchain (Xcode CLT, CMake), and needs network access to upload artifacts.
  - Justification: This is not a design defect — the pipeline execution is fully deterministic and testable in its native environment (GitHub Actions macos-14 runner).
