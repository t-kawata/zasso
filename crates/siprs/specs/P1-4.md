# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P1-4: M20 Dual Client PJSIP Callback Routing

**Ticket Key**: P1-4 · **Phase**: 1

## RFC Reference

~/shyme/zasso/crates/siprs/RFC-ROOT (§27)

## Background

N0038 defines single Reactor + EventBus split for multiple SipClient instances sharing PjsuaBackend singleton. Account_id-based event dispatch. Maps to src/state/m20_dual_client_routing.rs (no direct file in Dirs-Tree, grouped with Dual Client routing logic).

### Goal
Implement the Dual Client callback routing mechanism — Reactor::dispatch_event() that routes SipEvents to the correct client's EventBus based on account_id, supporting multiple SipClient instances sharing a single PjsuaBackend singleton.

### Purpose
Enable multiple SipClient instances (dual/multi-client) to coexist in the same process by routing PJSIP callbacks to the correct client's EventBus, maintaining event isolation between clients while sharing the single PjsuaBackend singleton (pjsua_init() once-per-process constraint).

### Motivation
The M20 phase requires dual-client integration tests (call rejection, call transfer) where two logical SipClient instances share the same PjsuaBackend. Without account_id-based routing, events from one client's account would leak to the other client's EventBus, breaking isolation. The P2 priority reflects that single-client operation works via default EventBus — this is the multi-client routing extension.

### Constraints
PjsuaBackend is a OnceLock singleton — cannot be instantiated twice per process. global_runtime() returns a single Arc<Reactor> — no per-client Reactor. EventBus is per SipClient, registered in the shared Reactor. Routing key is AccountId(u64) — events without account_id (None) go to default EventBus. Call events (CallStateChanged, CallMediaStateChanged) carry call_id only, not acc_id — reactor must maintain call_id→account_id mapping. No new crate dependencies beyond tokio (broadcast channel) already in Cargo.toml.

## Investigation

- **RFC analysis**: Dual Client callback routing is defined in RFC-ROOT.md §27 (M20 Dual Client PJSIP Callback Routing, §~1918-1981). Key design: single Reactor (global_runtime unchanged) + EventBus split per client. Account_id-based dispatch with HashMap<AccountId, EventBus> routing table. RFC includes pseudo-implementation of dispatch_event().
- **Existing code — NativeEvent conversion layer** (`src/state/m20_native_event_conv.rs`): NativeEvent enum has 12 variants. Registration events carry acc_id: AccountId field; Call events carry call_id: CallId (no acc_id). This means call events need call_id→account_id mapping at the Reactor level.
- **Existing code — CallState mapping** (`src/state/m20_callstate_mapping.rs`): CallState enum (13 states), pjsip_inv_state constants (0-4), media_status constants (0-4). convert_call_state() and convert_call_media_state() are fully implemented and tested.
- **Existing code — EventBus stubs** (`src/api/eventbus_receiver.rs`): Currently `pub trait Service {}` only. Real EventBus will be implemented by P1-0 with tokio::sync::broadcast.
- **Existing code — RuntimeCommand** (`src/concurrency_contexts/command_serialization.rs`): AccountId(u64) and CallId(u64) are stub newtypes (Copy+Clone+PartialEq+Eq). They need to be full types before P1-4 routing can use them as HashMap keys.
- **Existing code — Dual Client test stub** (`src/tests/m20_test_dual_client.rs`): Minimal test file (N0053) with TODO comment. Will be filled by P2-2.
- **Existing code — Error design** (`src/error/error_design_siperror.rs`): SipError with account_id and call_id fields. Ready to reuse for routing errors.
- **No existing routing implementation**: dispatch_event(), register_client_event_bus(), and the routing table do not exist in any file yet. This is entirely greenfield within this ticket's scope.
- **Key finding**: Call events (CallStateChanged, CallMediaStateChanged) carry call_id but not acc_id. The reactor must maintain a call_id→account_id mapping (CallEventRouter). This mapping is populated when SipClient::add_account() creates an account and the account initiates or receives calls.
- **Key finding**: NativeEvent → SipEventPayload conversion is purely functional (no side effects). convert_native_event_to_payload() returns Option<SipEventPayload>. The SipEventPayload is currently a minimal enum (13 unit variants) — the full version (30+ variants with typed payload structs) will come from P1-1.
- **DualClientContext design** (RFC §43, ~line 2822-2853): Struct with client_a, client_b, account_a, account_b. Constructor creates two SipClients where client_b shares PjsuaBackend singleton from client_a. Pattern is: client_a=SipClient::new(config_a) → creates Reactor + default EventBus + PjsuaBackend; client_b=SipClient::new(config_b) → shares existing PjsuaBackend, registers new EventBus in Reactor.

## Acceptance Criteria

- Multiple SipClient instances share PjsuaBackend singleton safely — No duplicate pjsua_init(), no data race on backend state.
- Events are routed to correct Client EventBus by account_id — Registration events (with acc_id) route to the owning client's bus. Call events (with call_id) resolve account_id via call→account mapping then route correctly.
- **[Happy path]** Two SipClients (A, B) registered with distinct AccountIds. Dispatch event for account_a → only client_a's EventBus receives it. Dispatch event for account_b → only client_b's EventBus receives it.
- **[Error case]** Dispatch event for unknown AccountId (no client registered for that id) → falls back to default EventBus (first registered client's bus). No panic, no event loss.
- **[Edge case]** Non-account event (account_id=None) → published to default EventBus only. Never published to all client buses. Non-account event with empty client_event_buses map → still handled by default EventBus.

## Invariants

- 【Normal establishment】Reactor's default_event_bus must always be initialized before any client EventBus registration (PjsuaBackend singleton must exist). All client EventBus registrations must carry at least one AccountId. Reactor routing table HashMap<AccountId, EventBus> must remain in sync with active SipClient instances.
- 【Invariant on error】On dispatch_event failure (e.g., broadcast channel send error), the Reactor must not panic — the error is logged and the event is dropped. The routing table is never corrupted by failed publishes. The default EventBus must always accept events even if all client buses are dropped.
- 【Internal state invariant】The Reactor holds exactly one default_event_bus: EventBus and N client_event_buses: HashMap<AccountId, EventBus>. No two entries in client_event_buses map to the same EventBus instance pointer (distinct clones). The Reactor instance is behind Arc<Reactor> (shared ownership, not cloned per client).
- 【Boundary invariant】AccountId values range from 0 to u64::MAX. The routing table must handle all values without overflow or wrapping. An empty client_event_buses map (no clients registered) must still function — all events route to default EventBus.

## Boy Scout Rule

- **dispatch_event function naming**: Name the main routing function `dispatch_event_to_correct_bus` (reads as a verb phrase: "dispatch event to the correct bus"), not `route` or `handle_dispatch`. Internal helper functions named as verb phrases: `resolve_client_bus(account_id) -> Option<&EventBus>`, `route_to_default_or_client(event, maybe_bus)`.
- **Variable naming as domain concepts**: Use `routing_table: HashMap<AccountId, EventBus>` instead of `buses` or `map`. Use `call_owner: HashMap<CallId, AccountId>` instead of `call_map`. Use `default_event_bus` instead of `default` or `main`.
- **One function one responsibility**: dispatch_event does one thing — look up account_id in routing table and call publish on the correct bus. Registration/unregistration are separate methods. CallEventRouter is a separate struct with its own methods (register_call, resolve_account_for_call, unregister_call). No function exceeds 15 lines.
- **Hardcoded value extraction**: No hardcoded channel capacities, timeouts, or magic numbers in routing logic. Extract `DEFAULT_BROADCAST_CHANNEL_CAPACITY: usize = 256` as a named constant.
- **No error swallowing**: dispatch_event returns `Result<(), RoutingError>` where RoutingError has variants: `UnknownAccount { account_id }`, `BusClosed { account_id }`. The caller (Reactor) logs and drops on error — the dispatch itself never silently swallows.
- **Existing code outside scope**: No refactoring needed in existing files (m20_native_event_conv.rs, m20_callstate_mapping.rs) — they are already translatable. The `m20_dual_client_routing.rs` is new code built to translatability standards from the start.

### Exceptions

- Item: End-to-end SIP integration test with real PJSIP callback routing cannot test in unit-test environment (requires live PJSIP stack and SIP server). Reason: PJSIP C callbacks fire from pjsua background threads — the callback-to-Reactor bridge inherently depends on pjsua_init() which can only be called once per process (singleton constraint). This is not a design defect — the callback→NativeEvent→Reactor→EventBus path is fully deterministic in its data flow; verification relies on Layer 2 (MockBackend) injection of NativeEvent + Layer 3 (Docker integration) for full callback loop. Alternative verification: MockBackend's emit_event simulates the callback path by constructing NativeEvent directly and feeding it to Reactor::enqueue_native_event.
- Item: Timing-dependent verification not testable in unit test — DualClientContext::call_a_to_b involves async event propagation across tokio tasks. Reason: The exact delivery latency is non-deterministic due to inherent async broadcast channel semantics (tokio::sync::broadcast). This is not a design defect — the data flow (account_id → EventBus mapping) is deterministic and independently verifiable without timing dependency. Alternative verification: Use tokio::test with controlled pacing and assert event delivery within a reasonable timeout window.
- Item: Real PJSIP transport layer callbacks not testable via MockBackend — on_incoming_call callback receiving correct account_id requires a running SIP stack. Reason: pjsua_acc_get_id / pjsua_call_get_acc_id are C FFI calls that require an initialized pjsua instance. This is not a design defect — the account_id routing logic at the Reactor level is independent of how account_id is obtained in the callback. Alternative verification: Unit-test dispatch_event with artificial account_id values; verify the routing table logic independently of PJSIP.
