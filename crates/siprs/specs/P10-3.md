# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the account and transport configuration lifecycle fully functional on the public API and through the runtime: SipClient::add_account/remove_account/account/add_transport facades that validate then dispatch, a real SipAccountHandle::update_config (replacing the no-op), and reactor dispatch that keeps the authoritative ClientState in lockstep with backend operations.

### Purpose
P3-1 specified the configuration types (AccountConfig, TransportConfig, ClientConfig) but deferred the lifecycle methods behind the src/lib.rs:54 stub. Without these methods the crate cannot add, modify, or remove accounts at runtime — the core of any SIP client. This ticket turns the deferred stub into real, tested behavior.

### Motivation
Source ticket P3-1 explicitly deferred account/call/transport lifecycle methods because AccountConfig/TransportConfig/OutgoingCallRequest were not yet stable. Those types are now stable (P3-1, P4-1, P10-1 landed). The prior no-op update_config (P11-7, previously P8-14) and the reactor AddAccount reply that discards the assigned account_id make the facade unable to return a real handle. This ticket removes the deferred stub and the no-op.

### Constraints
- All lifecycle methods are async fn returning Result<T, SipError> (C017); SipClient/SipAccountHandle stay Clone + Send + Sync (C012).
- Validation must occur before dispatch (fail-fast, C052): invalid config/patch returns Err(InvalidConfig) with zero state mutation.
- SipCall lifecycle (make/answer/hangup/hold/transfer/send_dtmf) is OUT of scope (P8-9); real CallId wiring is P8-13; startup account restoration is P8-15; real PJSUA FFI is P3-2/P4-2.

## Acceptance Criteria

- 【Happy path】SipClient::add_account(AccountConfig) validates the config, submits RuntimeCommand::AddAccount (via submit_add_account), and returns a SipAccountHandle with a non-zero account_id on success; the account is immediately visible in accounts() and query_state.
- 【Happy path】SipAccountHandle::update_config(patch) merges the patch with the stored AccountConfig, validates the merged result, and submits RuntimeCommand::UpdateAccount; the changed config is reflected in the reactor's authoritative ClientState without dropping or recreating the account (same account_id).
- 【Happy path】SipClient::remove_account(account_id) submits RuntimeCommand::RemoveAccount and the reactor removes the account from client_state.accounts; the account no longer appears in accounts().
- 【Happy path】Transport configuration (TransportConfig UDP/TCP via SipClient::add_transport) is accepted and reflected in the reactor's client_state.transports as TransportRuntimeState (transport_id/type/port).
- 【Error case】add_account with an invalid AccountConfig returns Err(SipErrorKind::InvalidConfig) before any RuntimeCommand is submitted — no state mutation on validation failure (MockBackend records zero calls).
- 【Error case】update_config/remove_account on a non-existent account_id returns Err (AccountNotFound), never panics.
- 【Edge case】AccountConfig with register_on_start=false and allow_outbound_without_register=true validates successfully and can be added.
- 【Edge case】All lifecycle methods are async fn returning Result<T, SipError>; SipClient/SipAccountHandle remain Clone + Send + Sync.

## Invariants

- 【Normal establishment】All account/transport lifecycle API functions return Result<T, SipError> (C017); add_account/update_config succeed only after AccountConfig::validate() passes (C015); a successful add_account yields a SipAccountHandle with a non-zero account_id and the account is visible in the reactor's authoritative ClientState (C021).
- 【Invariant on error】Validation failures return Err(SipErrorKind::InvalidConfig) BEFORE any RuntimeCommand submission — no partial state mutation (C052 fail-fast); a downed reactor maps to Err(NativeError); missing accounts map to Err(AccountNotFound), never panic.
- 【Internal state invariant】The reactor's ClientState is the single source of truth (O-004): AccountEntry.config holds the full AccountConfig, entry.id is the logical account id, and remove_account must remove the entry from client_state.accounts (not just the backend registry). Registration state is independent of config updates (C026).
- 【Boundary invariant】AccountConfig with register_on_start=false + allow_outbound_without_register=true is valid (RFC §11.1); TransportConfig TLS variant is feature-gated and never present at runtime without the tls feature (C016/C043); codec policy accepts only PCMU and Opus (C041).

### Exceptions

- Item: Real PJSUA registration/transport FFI binding. Reason: the real PJSUA registration/transport behavior is NOT TESTABLE in unit tests because it requires a running PJSIP stack linked via the pjsua-native feature, which is not available in this environment; we cannot test it without the FFI dependency. This is NOT a design defect — the SipBackend abstraction (backend.rs:20, C038) intentionally isolates FFI behind MockBackend/PjsuaBackend, which provide a deterministic in-process stand-in for every lifecycle command; the real FFI binding is a P3-2/P4-2 dependency by design, not an untested behavior gap.
- Item: TLS compile-time feature gating. Reason: the absence of the TransportConfig::Tls variant when the tls feature is disabled is NOT TESTABLE at runtime because the variant is removed at the type level (RFC §12) — we cannot test a type that does not compile into the test binary. This is NOT an architectural defect — the feature gate is an explicit, deterministic compile-time contract. Alternative verification: `cargo check --no-default-features` (variant absent) vs `cargo check --features tls` (variant present), plus a cfg-gated #[test] that only compiles under the feature.
- Item: Actual socket binding of TransportConfig.bind_addr. Reason: the real socket bind is NOT TESTABLE because PjsuaBackend::create_transport is unimplemented until P3-2/P4-2 wires pjsua_transport_create, and a real bind requires a live network stack; we cannot test it without those dependencies. This is NOT a design defect — the reactor's TransportRuntimeState recording and CreateTransport dispatch are deterministic and fully unit-tested with MockBackend (which returns Ok(()) for create_transport); only the FFI layer is deferred, by design (C038).
