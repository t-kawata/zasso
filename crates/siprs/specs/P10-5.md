# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P10-5: Remove the TransportType re-export once all callers migrate to TransportConfig directly

**Ticket Key**: P10-5 · **Phase**: 10

**RFC Source**: `RFC-ROOT.md`

---

## RFC Reference

~/shyme/zasso/crates/siprs/RFC-ROOT (§8, §11, §12, §42)

## Background

### Goal
Remove the redundant standalone `TransportType` enum from `src/transport.rs` (lines 12-20) now that every caller uses `TransportConfig` directly, leaving `TransportConfig` as the single transport type in the crate.

### Purpose
`TransportType { Udp, Tcp, Tls }` is a public enum that duplicates the variant names of the canonical `TransportConfig` enum (`Udp(UdpTransportConfig)`, `Tcp(TcpTransportConfig)`, `Tls(TlsTransportConfig)`). Two enums with identical variant concepts split the transport-API surface and force consumers to choose between them; the standalone enum also lacks the payloads (`SocketAddr`, `TlsConfig`) that the canonical type carries, so it is strictly less useful. Removing it makes `TransportConfig` the one and only transport type.

### Motivation
P3-1 introduced `TransportConfig` as the canonical type (transport_ice_spec.rs:28) and left `TransportType` behind as a `[::STUB::] P10-5` marker with the note that it must be removed once all callers migrate to `TransportConfig` directly. The workspace audit in this ticket confirms zero in-repo callers of `TransportType` (grep matches only the definition and its STUB comment in `src/transport.rs`). All account/transport config lifecycle work (P10-3) and public API re-exports (P8-22) build on `TransportConfig`. The migration precondition is satisfied, so the redundant type can be deleted.

### Constraints
- Must not touch the canonical `TransportConfig` enum or its re-export set (C016).
- Must not alter the crate-root re-export block (lib.rs:120-145) — `TransportType` is already absent there.
- `pub mod transport;` (lib.rs:60) must remain valid; the module body keeps only the re-export.
- Feature-gated TLS (`#[cfg(feature = "tls")]`) paths must be untouched.
- TDD: write the failing source-tree-scan test first (RED), delete the enum (GREEN), keep the suite green (Refactor).

## Investigation

Source-code evidence gathered during make-stage investigation (P10-5):

1. **src/transport.rs:7-10** — The module already re-exports `IceConfig, StunServerConfig, TransportConfig, TurnServerConfig, TurnTransport, UdpTransportConfig` from `crate::config::transport_ice_spec`, i.e. the canonical config types are re-exported at the `transport` module root.

2. **src/transport.rs:12-20** — A redundant standalone `pub enum TransportType { Udp, Tcp, Tls }` (derive Debug, Clone) carries the `[::STUB::] P10-5` marker at line 14. This is the exact removal target. It duplicates the variant names of the canonical `TransportConfig`.

3. **src/config/transport_ice_spec.rs:28-33** — The canonical enum is `pub enum TransportConfig { Udp(UdpTransportConfig), Tcp(TcpTransportConfig), #[cfg(feature = "tls")] Tls(TlsTransportConfig) }`. It is the single source of truth for transport selection (RFC N0015 §12, C016). `TcpTransportConfig`/`UdpTransportConfig` structs and (feature-gated) `TlsTransportConfig`/`TlsConfig` are defined in the same file.

4. **src/lib.rs:55-60** — `pub mod transport;` is declared (line 60) and remains valid after removal since the re-export module body (transport.rs:7-10) is untouched.

5. **src/lib.rs:120-145** — The crate-root `pub use` block re-exports `config::transport_ice_spec::{IceConfig, TcpTransportConfig, TransportConfig, TurnServerConfig, TurnTransport, UdpTransportConfig}` (lines 136-139) and feature-gated `TlsConfig` (line 140-141). **`TransportType` is NOT in the crate-root re-export list** — it was only reachable via `siprs::transport::TransportType`. Removing it therefore shrinks only the `transport` module path, not the crate root API.

6. **Workspace-wide grep** (`grep -rn "TransportType" --include="*.rs" .`) returns exactly two matches, both inside `src/transport.rs`: the STUB comment (line 14) and the enum definition (line 16). **Zero callers exist anywhere in the workspace** (lib, tests/, siprs-server, examples).

7. **RFC graph** N0015 (§12 TransportConfig & §13 ICE/STUN/TURN) confirms TransportConfig is the canonical transport type; N0011 (§8 Public API Design) crate-root re-exports do not include TransportType; N0051 (§42 Validation) requires ClientConfig to carry transport/ICE and validate fail-fast.

8. **Feature gates** — Tls variant is `#[cfg(feature = "tls")]` in both the canonical enum and the re-export; the removal does not touch feature-gated code.

Conclusion: removal is a pure 8-line deletion in `src/transport.rs` (doc comment lines 12-13, STUB marker line 14, derive line 15, enum lines 16-20). No other file needs to change.
