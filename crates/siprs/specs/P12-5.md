# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

[::INSPECTION_FLAGGED::]
This ticket has been flagged for rejection due to detection of implementation deficiencies, unresolved STUB markers, or other violations. It has been returned for re-implementation. A complete implementation free of all defects, STUB markers, and violations must be achieved in this final implementation round. Complete it this time.

Source ticket P3-2 specified AudioWorkerTask with a Tokio JoinHandle for the blocking-pool worker. The handle is stored as `Option<tokio::task::JoinHandle<()>>` (src/runtime/audio_worker.rs:279) and marked #[allow(dead_code)], so the worker's task lifecycle is not actively managed. This work item replaces the unused Option<JoinHandle> with a non-optional active JoinHandle and integrates shutdown so the handle is always awaited on shutdown.

### Goal
Replace the `#[allow(dead_code)] handle: Option<tokio::task::JoinHandle<()>>` field in AudioWorkerTask (src/runtime/audio_worker.rs:273-275) with a bare non-optional `tokio::task::JoinHandle<()>`, and rewrite `shutdown()` so it always joins the worker task deterministically — logging a JoinError (worker panic) instead of silently discarding it. The worker lifecycle becomes fully managed: no 'no-handle' state is representable while the worker is alive, and shutdown guarantees the blocking-pool task has terminated when it returns.

### Purpose
AudioWorkerTask runs the per-call audio processing loop on the Tokio blocking pool. Its task handle is the only way to observe whether that loop is still alive and to deterministically join it on shutdown. The current Option-typed, `#[allow(dead_code)]` handle leaves a representable-but-invalid 'no handle' state, swallows the join result, and gives no compile-time guarantee that the worker is ever joined. Making the handle non-optional turns 'always own a live worker task' into a type-enforced invariant and makes shutdown's join behavior a guaranteed postcondition.

### Motivation
This is a flagged re-implementation round: the previous round left the Option<JoinHandle> + #[allow(dead_code)] in place, meaning the worker task lifecycle was not actively managed and a join error could be silently swallowed (`let _ = handle.await;`). The RFC contracts C034 (handle always present while worker alive) and C035 (shutdown stops frame production) require deterministic lifecycle management. Tech-debt driver: FFI audio capture/playback (RustMediaPort) is still deferred, so now is the time to make the worker lifecycle robust before real media flows through it.

### Constraints
- Public API unchanged: `spawn(mixer: Arc<AudioMixer>, call_id: u64, frame_duration: Duration) -> Self`, `shutdown(&mut self)`, `is_running(&self)`, `mixer(&self)`, `call_id(&self)`, `frame_duration(&self)` keep their signatures; existing spawn/shutdown tests (src/runtime/audio_worker.rs tests + tests/runtime_audio_lifecycle.rs) must keep passing.
- No unsafe added — runtime/ must remain unsafe-free (C038); the change uses only safe Tokio/std primitives.
- FFI audio capture/playback (RustMediaPort get_frame/put_frame) is explicitly out of scope until FFI audio integration is available; AudioMixer behavior is unchanged.
- The worker must be joinable exactly once and double-shutdown must be idempotent (the second `shutdown()` returns promptly without panic).

- src/runtime/audio_worker.rs:273-275 — the `[::STUB::] P12-5` marker sits directly above `#[allow(dead_code)] handle: Option<tokio::task::JoinHandle<()>>` (lines 274-275). `spawn()` (lines 284-314) creates the handle via `tokio::task::spawn_blocking` and stores `handle: Some(handle)` (line 312). `shutdown()` (lines 317-322) does `if let Some(handle) = self.handle.take() { let _ = handle.await; }` — the Option is partially used but still Option-typed and marked dead_code, leaving a 'no handle' state representable and the JoinError silently discarded.
- AudioWorkerInner.run() (lines 375-383) loops `while !self.shutdown_signal.load(Ordering::Acquire)` calling `process_frame()` then `tokio::time::sleep(self.frame_duration())`. process_frame (lines 392-434) snapshots source_ids from the DashMap, pulls each source via next_chunk, applies gain/mute, mixes with `mix_i16_frame` (i32 accumulation → saturating i16 clamp), and pushes to `out_queue`. The shutdown signal is the only mechanism that terminates the loop.
- is_running() (lines 325-327) returns `!self.shutdown_signal.load(Ordering::Acquire)` — it reflects the signal, not `handle.is_finished()`. After `shutdown()` the signal is true so is_running() is false.

- Design evidence: RFC §24 (N0033) specifies the two-layer architecture with the lock-free queue boundary; the worker must be spawned on the blocking pool (C034) and shutdown must stop frame production (C035). C038 requires runtime/ to stay unsafe-free — the fix uses only `tokio::task::JoinHandle`, `spawn_blocking`, `AtomicBool`, and `std::mem::replace`.

## Acceptance Criteria

- **【Happy path】**
-   - After `spawn()`, the worker holds a non-optional `JoinHandle` — the in-module test `handle_is_non_optional_and_running_after_spawn` asserts `!worker.handle.is_finished()` right after spawn, which only compiles if the field is a bare `JoinHandle<()>` (no Option unwrap needed).
-   - `shutdown()` sets the shutdown flag and awaits the JoinHandle; after it returns, `is_running() == false` and the worker task has terminated — `shutdown_joins_handle_and_stops_worker` asserts both `!worker.is_running()` and `worker.handle.is_finished()`.
-   - A worker with active sources keeps producing mixed frames until shutdown, then stops cleanly — `worker_keeps_producing_frames_until_shutdown` asserts frames are produced while running and none are pushed after shutdown.
- **【Error case】**
-   - `shutdown()` called twice is idempotent — `double_shutdown_is_idempotent` calls it twice and asserts the second call does not panic and returns promptly (the `swap` guard short-circuits).
-   - If the worker task panics, `shutdown()` still resolves — `shutdown_resolves_when_worker_panics` uses a panicking source and asserts the join returns `Err` which is logged, not re-panicked, and `shutdown()` returns normally.
- **【Edge case】**
-   - `spawn()` from a tokio runtime context always yields a running `JoinHandle` (`handle.is_finished() == false` immediately after spawn) — asserted at t=0 by `handle_is_non_optional_and_running_after_spawn`.
-   - `Duration::ZERO` frame cadence and `u64::MAX` call_id do not deadlock or misroute shutdown — `boundary_values_round_trip_exactly` remains green and the zero-cadence loop still observes the shutdown signal within one iteration.
-   - Existing lifecycle integration tests (`audio_worker_spawns_and_produces_mixed_output`, `multiple_audio_workers_use_independent_mixers`) remain green with the non-optional handle — no regression in the multi-worker path.

## Invariants

- AudioWorkerTask is spawned on the Tokio blocking pool via spawn_blocking and the JoinHandle is always present while the worker is alive (C034).
- The shutdown flag is set atomically; the worker loop exits on the next iteration after the flag is set; no new frames are pushed after shutdown (C035).
- No unsafe added; runtime/ remains unsafe-free (C038).

- [Normal condition] The `handle` field is a bare `tokio::task::JoinHandle<()>` (never `Option`) from `spawn()` until the first `shutdown()`; `handle.is_finished() == false` immediately after spawn (C034 precondition). `shutdown()` requires a live Tokio runtime context (`#[tokio::test]` or reactor) so the join can be awaited.
- [Error invariant] A JoinError from the joined task (worker panicked) must never propagate as a panic from `shutdown()` — it is logged via `tracing::warn!` and `shutdown()` returns normally. A second `shutdown()` after the first has completed must not touch the already-consumed handle (idempotency guard via `shutdown_signal.swap(true, Ordering::AcqRel)`), so no use-after-join or double-join is possible.
- [Internal state invariant] `shutdown_signal` is an `Arc<AtomicBool>`; it is set to `true` exactly once by the first `shutdown()` and read by `is_running()` (Acquire) and the worker loop (Acquire). While the signal is `false`, the worker loop keeps producing frames; once `true`, the loop exits after the current iteration and the task completes, making the handle finish.
- [Boundary invariant] `Duration::ZERO` frame cadence and `u64::MAX` call_id must not deadlock `shutdown()`; the loop observes the shutdown signal within one iteration even at zero cadence. The replacement handle slot after shutdown holds an already-completed task, so `handle.is_finished()` is `true` post-shutdown and remains a valid (non-Option) handle.
