# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
client.rs と reactor.rs が別々に持つ EventBus を単一化し、reactor の dispatch_event が SipClient 所有の単一 EventBus へ直接 publish する配線を実装する。RawSipEventConfig.enabled（default true）に応じた raw_sip チャネル生成と、subscribe_account の account_id フィルタ死滅の解消を同時に達成する（§62.3 / §15.6）。

### Purpose
現状、SipClient::new は client.rs:115 で自前の EventBus を生成し、reactor.rs:110 は CoreReactor::spawn 内で別の default_event_bus を生成する。reactor が publish した SipEvent は reactor 側バスに流れるため、SipClient::subscribe() / subscribe_account() のレシーバ（client 側バス）には ClientInitialized（client.rs:139-142）しか到達しない。subscribe_account は client 側バス上で meta.account_id をフィルタするため常に 0 件（フィルタ死滅）。また両バスとも EventBus::new(_, None) で生成されるため subscribe_raw_sip() は常に None を返す。単一バス化により、reactor イベントが購読者へ到達し、§15 のイベントモデルが観測用途として機能する。

### Motivation
§62 RESIDUE の根因 R3「イベントバス分断」の解消。P15-1 で §62 全体の typed design data（impl_integration_design.rs、DesignDecisionId::EventBusUnification を含む）を実装済みであり、P15-2（ConfigUnification）・P15-3（BackendSelection）が先行解決済み。R3 は残る最後の RESIDUE 根因であり、P15-4 で閉じる。P15-2 で ClientConfig に event_bus_capacity / raw_sip_event_capacity / raw_sip_events が揃ったため、ここで raw_sip 条件生成と単一バス配線を実装できる。

## Investigation

【調査で得た証拠 — イベントバス分断の実態】

**1. 二重バス所有（R3 根因）**
- src/client.rs:114-116 — `SipClient::new` は reactor spawn 後に自前の `EventBus::new(DEFAULT_EVENT_BUS_CAPACITY, None)` を生成し、`ClientInner.events` に格納する（raw_sip は常に None）。
- src/runtime/reactor.rs:110-117 — `CoreReactor::spawn` は**別の** `default_event_bus = EventBus::new(DEFAULT_EVENT_BUS_CAPACITY, None)` と、常に空の `client_event_buses: ClientEventBuses = HashMap::new()` を生成する。
- 結果: reactor が publish したイベントは reactor 側バスにのみ流れ、client 側バス（`subscribe()` / `subscribe_account()` の購読先）には到達しない。

**2. dispatch_event の振り分け（reactor.rs:560-580）**
- `Some(account_id)` が client_event_buses に一致 → そのバスへ。一致なし → default_event_bus へ。
- `None` → default_event_bus + 全 client bus。
- 空の HashMap では全イベントが default_event_bus へ落ちるが、そのバスを購読しているのは handle の観測 accessor のみ。

**3. process_native_event は meta.account_id を既に付与済み（reactor.rs:597-657）**
- RegistrationStateChanged: `EventMeta::new(0, account_id, None)`（613 行）。
- その他: `extract_event_ids` で call テーブルから account 解決し `EventMeta::new(0, account_id, call_id)`（650 行）。
- ⇒ フィルタ死滅の原因は「account_id が付いていない」ことではなく「イベントが client バスに届かない」こと。単一バス化で解消する。

**4. handle.rs:26-41, 92-94 — RuntimeHandle は default_event_bus の Clone を保持・公開**
- `RuntimeHandle::new(..., default_event_bus)` が reactor.rs:504-510 から呼ばれる。`default_event_bus()` accessor は観測/テスト用。

**5. EventBus 型（eventbus_receiver.rs:42-47）**
- `struct EventBus { control: broadcast::Sender<SipEvent>, raw_sip: Option<broadcast::Sender<RawSipMessage>> }`。
- `EventBus::new(control_capacity, raw_sip_capacity: Option<usize>)` が raw_sip 有無を決定（§15.4 契約）。

## Acceptance Criteria

- **[Happy path] — 本チケット完了を確認するシナリオ:**
  - RawSipEventConfig::default()（enabled=true）で SipClient::new が成功する。
  - reactor が publish した SipEvent（例: RegistrationStateChanged → RegistrationSucceeded）が SipClient::subscribe() の receiver で受信される（バス分断が解消）。
  - subscribe_account(id) が account_id に一致するイベントのみ受信する（フィルタ死滅が解消）。
  - subscribe_raw_sip() が Some(broadcast::Receiver<RawSipMessage>) を返し、raw_sip メッセージを受信できる。
  - RuntimeHandle::event_bus() と client.events が同一バス（client 側 publish が handle 側購読へ届く）。
- **[Error case] — 本機能が処理すべきエラーシナリオ:**
  - config.validate() 失敗時（event_bus_capacity < 16）に SipClient::new が Err(SipErrorKind::InvalidConfig) を返し、reactor が起動されない。
  - raw_sip_events.enabled=false で subscribe_raw_sip() が None を返し、制御系イベント（subscribe / subscribe_account）に影響しない。
  - 購読者がいない状態で dispatch_event が panic せず、イベントが静かに破棄される（§15.7 lossy 配送）。
- **[Edge case] — 検証すべき境界/例外:**
  - raw_sip_event_capacity=1 の最小容量で enabled=true の場合、チャネルが生成され publish が届く。
  - event_bus_capacity=16（§42 最小許容値）で SipClient::new が成功する。
  - 購読者遅延による Lagged(n) が単一バスで検知され、観測用途として許容される。
  - account_id が None のイベント（クライアントライフサイクル）と Some のイベントが同一バスに流れ、AccountEventReceiver が None アカウントイベントを正しくスキップする。

## Invariants

- 【Normal establishment】SipClient は config.validate() を通過した ClientConfig から単一 EventBus を生成する。raw_sip_events.enabled == true なら EventBus::new(event_bus_capacity, Some(raw_sip_event_capacity)) で raw_sip チャネルが生成され、subscribe_raw_sip() は Some(receiver) を返す。enabled == false なら None で生成され subscribe_raw_sip() は None を返す。
- 【Invariant on error】broadcast チャネルは lossy 配送のため、購読側が遅延した場合の Lagged(n) はイベント欠落として許容される（§15.7 観測用途）。dispatch_event の publish は決して panic せず、購読者数 0 でも send 失敗を unwrap_or(0) で吸収する。reactor スレッドが panic した場合も SipEventPayload::Error 経由でエラーイベントが publish され、ループは停止しない。
- 【Internal state invariant】単一 EventBus は SipClient（ClientInner.events）が所有し、reactor はその Clone を保持する。reactor 内に独立した EventBus（default_event_bus）や ClientEventBuses HashMap を生成してはならない（§62.3 一元化）。購読側のフィルタは AccountEventReceiver の meta.account_id 比較のみで行う。
- 【Boundary invariant】event_bus_capacity >= 16（§42）を維持する。raw_sip_event_capacity は enabled=true 時に >= 1 であること（enabled=false 時は None で未生成）。raw_sip チャネルは制御系イベントと分離され、raw_sip 高負荷が制御系イベントの取りこぼしに影響しない（§15.6）。

**変更対象の既存コードで改善する点:**
- reactor.rs の `dispatch_event(client_event_buses, default_event_bus, event)` は「2 つのバスを引数に振り分ける」という複雑な英語構造を持つ。単一バス化により `dispatch_event(event_bus, event)` → `event_bus.publish(event)` の一文に単純化され、「単一バスへ publish する」という動詞句として読めるようになる。

### Exceptions

- **Exception entry:**
  - Item: SipClient::new 起動直後における、reactor 内部イベントと ClientInitialized の受信順序（絶対的なイベント到着順序）
  - Reason: reactor は別 OS スレッドで動作し、SipClient::new は reactor spawn 後に ClientInitialized を同一バスへ publish する。reactor 初期化中に publish されるイベントと ClientInitialized の厳密な順序はスレッドスケジューリングに依存するため、決定論的にテスト不能（cannot test deterministically）である。これは設計欠陥（design defect）ではない — 並行タイミングの本質であり、§15.7 でイベントは観測用途（確実配送を保証しない）と定義されているため、順序保証は仕様外である。
  - Alternative verification: event_rx（SipClient::new の戻り値）で ClientInitialized が「いずれ受信される」ことを順序非依存で検証する。決定論的な配線検証は、reactor が処理した NativeEvent の publish → subscribe() 受信という後続イベントで行う（IT: Verification）。
