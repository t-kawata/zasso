# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
着信 INVITE（on_incoming_call 由来の NativeEvent::IncomingCall）を reactor が ClientState.calls に CallEntry（CallDirection::Incoming、account 解決済み、CallState::Incoming）として登録し、IncomingCall / CallConnected / CallDisconnected イベントを publish 可能にする。handle_answer を CallEntry の account 解決 + typed CallState 遷移（200→Active）に修正し、CallRejected を削除して reject（486/603）を CallDisconnected に統一し、convert_call_state を CallState 全遷移の Some() 化へ拡張する（§62.14 / N0083）。

### Purpose
現状、NativeEvent::IncomingCall は reactor で CallDirection::Incoming を記録するだけで CallEntry が ClientState.calls に登録されない（reactor.rs:1011-1090）。そのため (a) 着信 call が SipClient::calls() / call_state(call_id) で解決できず (b) handle_answer が account_id を解決できない（着信の answer が不可能）(c) convert_call_state が INCOMING(2)/EARLY(3) を None 化し inv_state の全状態を観測できない。本チケットは「着信 call が state に存在し、answer で Active へ遷移し、CallConnected が観測できる」という §18/§19 の基本ライフサイクルを閉じ、reject 観測を CallDisconnected に一元化する。

### Motivation
- §62 実装整合設計ラウンド 2 の Q4（62.14）として、着信 CallEntry 登録・answer 修正・CallRejected 統一・CallState 全遷移のスコープが RFC 設計として確定した（N0083）
- 既存の CallRejected バリアント（event_model_payload_bus.rs:343）は定義のみで生成経路が無く、reject は handle_answer の 486/603→CallDisconnected が実体。呼称と実装の不一致（RESIDUE）を解消する
- §62.19 の Asterisk（docker）実 SIP 統合テストの前提として、着信 → answer(200) → CallConnected の経路が必須
- SipCall の偽ドキュメント（call.rs:41-42「answer_call() で生成」）が公開 API と矛盾 — 実在しない API を参照するコメントは修正必須

### Constraints

**9. RFC 根拠（N0083 / N0068 §62.14 / N0022 / N0027 / N0048）**
- §62.14 決定: (1) on_incoming_call 由来の NativeEvent::IncomingCall を reactor が ClientState.calls に CallEntry（CallDirection::Incoming、account 解決済み）として登録 (2) handle_answer を修正し CallEntry から account_id を解決して backend.answer を呼び、200 応答で CallState::Active 遷移 + CallConnected publish (3) CallRejected を SipEventPayload から削除し、reject（486/603）は CallDisconnected として観測。SipCall の偽ドキュメント修正 (4) convert_call_state を拡張し、PJSIP inv_state の 5 状態 + CallMediaStateChanged から CallState 全 13 状態へのマッピングを Some() 化
- I/O 境界: 入力 = NativeEvent::IncomingCall（on_incoming_call 由来）/ RuntimeCommand::Answer{call_id, code} ／出力 = ClientState.calls への登録、IncomingCall / CallConnected / CallDisconnected publish、CallState 遷移。CallEntry の account_id が常に解決されることが calls() / call_state(call_id) / answer の整合の前提
- N0022 §15 マッピング表: CALLING→Calling、CONNECTING→Trying/Ringing（遷移元判別）、CONFIRMED→Active、DISCONNECTED→Disconnecting→Disconnected
- N0027 §19.1 answer semantics: 180=着信継続 / 183=SDP 付き provisional / 200=通話受諾 / 486=Busy Here / 603=Decline。answer() は incoming call 以外に InvalidState
- N0048 §37: 着信時は IncomingCall イベントを emit し、同時に state に CallEntry を作成

**設計判断（本チケットで確定）**
- D1. CallEntry を拡張: `direction: CallDirection`（pub(crate)）+ `remote_uri: String` を追加し、`state: String` を `CallState` に typed 化（SipCall.state と同じ型）。native_id は i32 のまま（RFC 擬似コードの Some() は「常に存在」の意図で、Option 化は backend.rs への波及が大きく不要）
- D2. process_incoming_call は reactor.rs の process_native_event 内（NativeEvent::IncomingCall 分岐）に統合し、CallEntry 構築は incoming_call_events.rs の純関数（例: build_incoming_call_entry）に分離
- D3. handle_answer は 200 で CallState::Active、486/603 で CallState::Disconnected、180/183 で CallState::Connecting へ typed 遷移。CallConnected の remote_uri は CallEntry.remote_uri を引き継ぐ（String::new() ハードコード撤廃）

- D6. SipCall の偽ドキュメントを「make_call() で生成、着信は IncomingCall イベントで通知」に修正

## Acceptance Criteria

- **[Happy path] — 着信 → answer(200) → CallConnected の基本経路が成立:**
  - NativeEvent::IncomingCall { acc_id: 5, call_id: 42 } を process_native_event に投入すると、ClientState.calls に CallEntry（direction=Incoming, state=CallState::Incoming, account_id=AccountId(5)）が登録され、SipClient::calls() に現れ、call_state(CallId(42)) が Ok(CallState::Incoming) を返す
  - handle_answer(42, 200) で backend.answer_call(42, 200) が呼ばれ、calls[CallId(42)].state が CallState::Active に遷移し、SipEventPayload::CallConnected(ConnectedCallInfo { call_id: CallId(42), account_id: AccountId(5), remote_uri }) が subscribe() で受信できる
- **[Error case] — reject / エラー時の安全な観測と伝播:**
  - handle_answer(42, 486)（Busy Here）または 603（Decline）で calls[CallId(42)].state が CallState::Disconnected に遷移し、SipEventPayload::CallDisconnected が publish される（CallRejected は受信されない — バリアント自体が存在しない）
  - CallEntry 不在の call_id で handle_answer を呼ぶと Err（account 解決失敗）を返し、backend.answer_call が呼ばれない
  - backend.answer_call 失敗時は state を変更せず、イベントも publish しない
- **[Edge case] — 境界・例外を検証:**
  - acc_id=0 / call_id=0 の無効センチネルは IncomingCall 登録をスキップ（None 化）
  - 180/183 の provisional answer は terminal イベントを publish せず、calls[CallId(42)].state が CallState::Connecting のまま
  - convert_call_state が INCOMING(2) → Some(IncomingCall)、EARLY(3) → Some(EarlyMediaReceived)、未知値 99 → None を返し、全 pjsip_inv_state 値で panic しない
  - SipEventPayload::CallRejected を参照するコードがコンパイルエラーになる（バリアント削除の compile-time proof）

## Invariants

- 【Normal establishment】着信 INVITE 由来の NativeEvent::IncomingCall は reactor の process_native_event で ClientState.calls に CallEntry（direction=CallDirection::Incoming, state=CallState::Incoming, account_id 解決済み）として登録され、SipEventPayload::IncomingCall が単一 EventBus（dispatch_event, P15-4）に publish される。handle_answer(200) は CallState::Active 遷移 + CallConnected publish、reject（486/603）は CallState::Disconnected 遷移 + CallDisconnected publish。
- 【Invariant on error】handle_answer が CallEntry 不在の call_id で呼ばれた場合は backend.answer_call を呼ばず Err を返す（account 解決失敗の guard）。backend.answer_call 失敗時は state を変更せずイベントも publish しない。convert_call_state は unknown inv_state（例 99）で None を返し panic しない。CallEntry 不在の CONFIRMED は CallConnected を生成しない（C030）
- 【Internal state invariant】CallEntry.account_id が常に解決される（着信は acc_id から、発信は make_call で設定）— calls() / call_state(call_id) / answer の整合の前提。call_directions は C039 provenance に従い NativeEvent から導出（ペイロードから読まない）。SipEventPayload に CallRejected バリアントが存在しない
- 【Boundary invariant】acc_id=0 / call_id=0 は PJSUA の無効センチネルとして IncomingCall 登録をスキップ（from_u64 の Err で None 化）。pjsip_inv_state の全 7 値（0-6）+ 未知値を total に処理。answer code は 180/183/200/486/603 のみ受理（それ以外は入力検証エラー）
