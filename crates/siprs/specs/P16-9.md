# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Investigation

Evidence from the RFC graph and source tree:
- RFC N0087 (62.18) fixes five example binaries and the shared common modules. Its code skeleton uses impl AccountConfig / AccountTransportPolicy::Prefer(TransportKind::Udp) / AccountCodecPolicy::default_voice() / DtmfPolicy::all_methods(). None of these compile today: AccountTransportPolicy is a plain Udp/Tcp/Tls enum (src/config/account_config_spec.rs:26), AccountCodecPolicy and DtmfPolicy have only Default (account_config_spec.rs:85,105), and DtmfMethod has exactly three variants Rfc4733/Info/Inband (src/model/dtmf_spec.rs:27).
- examples/common/cli.rs already implements the shared CLI (CliArgs, parse, require, build_client_config) with tests; examples/common/client.rs implements require + add_account_and_resolve + required_field but lacks for_sip_uri (grep for for_sip_uri returns no hits).
- The five example binaries already exist, compile (cargo check --examples: Finished, warm cache) and are declared in Cargo.toml [[example]] sections.
- AccountConfig::validate() (§11.1) requires non-empty username/domain/password, ≥1 codec (PCMU or Opus), ≥1 DTMF send and receive method, and registration_expires > 0 (account_config_spec.rs:196-250).
- SipAccountHandle::register() and make_call() -> Result<u64, SipError> live in src/api/public_api_design.rs:56,142. SipEventPayload has RegistrationStateChanged(RegistrationState), CallConnected(ConnectedCallInfo), CallDisconnected, and ClientInitialized(ClientCapabilities) (src/api/event_model_payload_bus.rs:287-403). RegistrationState is Disabled/Idle/Registering/Registered/Unregistering/Failed/Expired (src/state/registr_state_machine.rs:77).
- The siprs root re-exports everything for_sip_uri needs: AccountConfig, AccountCodecPolicy, AccountMediaConfig, AccountTransportPolicy, DtmfMethod, DtmfPolicy, SecretString, RegistrationState, SipAccountHandle, SipEventPayload (src/lib.rs:105-153).
- The orphan rule (E0116) forbids inherent impls on foreign types, so `impl AccountConfig` in an example crate cannot compile; for_sip_uri is designed as a free function in examples/common/client.rs.

## Acceptance Criteria

- **[Happy path]** cargo check --examples succeeds for all five binaries; for_sip_uri("sip:1001@asterisk.local") returns an AccountConfig that passes AccountConfig::validate(); each example run against TestBackend prints its §62.18 contract marker (ClientInitialized / RegistrationStateChanged::Registered / CallConnected / audio tap frames / tts source added).
- **[Error case]** for_sip_uri rejects malformed URIs with an Err naming the expected sip:user@host form; any API failure in an example propagates as Err from main → non-zero exit code; E4 without a live call prints the unknown-call notice and exits cleanly (no panic).
- **[Edge case]** for_sip_uri handles the boundary inputs — missing sip: prefix, missing @, empty username (sip:@host), empty domain (sip:user@) — all returning Err; the config built by for_sip_uri passes §11.1 validate() while carrying register_on_start=false and allow_outbound_without_register=true so E3 can place calls unregistered.

## Invariants

【Normal】Each example prints its §62.18 contract marker to stdout: E1 "client initialized: event_bus_capacity=… max_calls=…", E2 "registration: … Registered/Failed", E3 "call placed: call_id=…" then CallConnected/CallDisconnected, E4 "audio tap: … in_samples=… out_samples=…", E5 "tts source added: source_id=… gain=…".
【On error】Examples fail fast: every API error propagates from main as Err (non-zero exit code); no error is swallowed and no placeholder value is printed as success.
【Internal state】All five examples share one CLI convention (examples/common/cli.rs) and one account-helper module (examples/common/client.rs); no example re-implements argument parsing or account construction; for_sip_uri output always passes AccountConfig::validate() (§11.1).
【Boundary】for_sip_uri rejects malformed URIs (missing sip: prefix, missing @, empty username, empty domain) with an Err naming the expected sip:user@host form; the DtmfPolicy always carries all three DtmfMethod variants so the §62.18 "all methods" invariant survives the current API.
