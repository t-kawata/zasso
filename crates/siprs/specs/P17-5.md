# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P17-5: CallEntry.state native transition reflection (§62.25)

**Ticket Key**: P17-5 · **Phase**: 17

**RFC Source**: `RFC-ROOT.md`

---

## Background

【Goal】Eliminate the H11 stale-state defect: after a remote hangup (DISCONNECTED), call_state(call_id) must return CallState::Disconnected, consistent with the latest native transition. The CallStateChanged arm of process_native_event must write CallEntry.state from the same CallStateTransition used to publish the SipEventPayload (RFC N0094 §62.25).
【Purpose】Restore the §62.14 consistency premise: CallEntry (direction/account/state) is the authoritative per-call record, so the native transition path must update state exactly as the command path (answer/hangup/transfer) already does, sharing one conversion result between publish and state.
【Motivation】H11 (round-3 residue): process_native_event currently converts NativeEvent::CallStateChanged to a payload and publishes it, but never updates CallEntry.state; after a remote DISCONNECTED the user-facing call_state() (client.rs:462 / handle.rs:433) returns a stale pre-disconnect value. §62.14 made account/direction consistent on the native path; state was the missing element (Q4).
【Constraints】No public API change (CallStateTransition and map_inv_state_to_call_state are pub(crate)); no new dependencies; the command-path state updates (answer_call_state) and the §18 transition-table validation are untouched; the actual PJSIP enum numbering (NULL=0, CALLING=1, INCOMING=2, EARLY=3, CONNECTING=4, CONFIRMED=5, DISCONNECTED=6 — not the old §15 numbering) must be respected.

## Scope

## Investigation

【Evidence from source + RFC investigation】
- src/state/m20_callstate_mapping.rs:126-139 — convert_call_state_with_previous currently returns Option<SipEventPayload> (publish-only). CONNECTING/Outgoing→OutgoingCallTrying, CONNECTING/Incoming→OutgoingCallRinging, otherwise delegates to convert_call_state (which returns None for NULL/unknown, Some for CALLING/INCOMING/EARLY/CONFIRMED/DISCONNECTED). Per N0094 it must be extended to Option<CallStateTransition { payload, state }>.
- src/runtime/reactor.rs:1107-1112 — the CallStateChanged arm of process_native_event resolves direction via resolve_call_direction(cid, call_state.call_directions) and converts to a payload; the payload is published via dispatch_event but CallEntry.state is never written. This is the H11 stale-call_state root cause.
- src/runtime/state.rs:78-94 — CallEntry { id: u64, native_id: i32, account_id: AccountId, state: CallState, media: String, direction: CallDirection, remote_uri: String }; state is the typed 13-state §18 CallState (state.rs:86).
- src/state/call_state_model.rs:53-80 — CallState 13 states (New/Calling/Trying/Ringing/EarlyMedia/Incoming/Connecting/Active/Held/Transferring/Disconnecting/Disconnected/Failed) with the TRANSITIONS table and transition()/can_transition_to(). N0094's state mapping reflects the native state directly — it does NOT re-validate against TRANSITIONS.
- src/runtime/handle.rs:433 and src/client.rs:462 — call_state(call_id) reads ClientState.calls[call_id].state via query_state (C021); stale if the native path never writes it.
- src/api/call_api_expansion.rs:47 — answer_call_state(code) is the command-path state mapping (200→Active, 486/603→Disconnected, _→Connecting); the native path needs its own map_inv_state_to_call_state, which does NOT exist yet (grep found zero hits).
- src/state/m20_native_event_conv.rs:156 — convert_native_event_to_payload's CallStateChanged arm delegates to convert_call_state (publish-only); it is not the state-update site.
- RFC N0094 (62.25) specifies: pub(crate) struct CallStateTransition { payload: SipEventPayload, state: CallState }; convert_call_state_with_previous computes the payload first (convert_call_state + CONNECTING discrimination) then state = map_inv_state_to_call_state(state, direction); the reactor arm does entry.state = transition.state inside .map() before returning transition.payload for publish.

- Existing tests that must be updated to the new return type: m20_callstate_mapping.rs inv_state_connecting_outgoing_direction / inv_state_connecting_incoming_direction / inv_state_with_previous_forwards_account_for_confirmed (lines 267-339) destructure Option<SipEventPayload>; they must destructure CallStateTransition.payload instead.

## Acceptance Criteria

- 【Happy path】A registered outgoing call receives NativeEvent::CallStateChanged { state: DISCONNECTED }; process_native_event publishes SipEventPayload::CallDisconnected AND updates calls[call_id].state to CallState::Disconnected; the subsequent call_state(call_id) query returns Disconnected — H11 resolved. TDD red: the reactor test asserting calls[&cid].state == Disconnected fails before the arm change and passes after.
- 【Error case】CallStateChanged for an unknown/invalid state (e.g. 99) or NULL produces no payload and no state mutation — CallEntry.state retains its previous value and the EventBus receives nothing (the established silent-drop contract, C030).
- 【Edge case】CallStateChanged { state: DISCONNECTED } for a call_id with NO registered CallEntry still publishes CallDisconnected (the payload conversion does not require the entry) but must not panic and must not fabricate a CallEntry; the state reflection is a no-op for the missing call.

## Invariants

- 【Normal establishment】For every CallStateChanged event, the published SipEventPayload and the CallEntry.state update are derived from ONE CallStateTransition — the same conversion result is the single source of truth for both the EventBus payload and the §18 13-state update (C128).
- 【Invariant on error】When convert_call_state_with_previous returns None (NULL/unknown state, or CONFIRMED with a missing CallEntry), NO state mutation occurs and NO payload is published — a missing CallEntry never fabricates an account and never corrupts CallEntry.state (C030).
- 【Internal state invariant】CallEntry.state always holds the value produced by map_inv_state_to_call_state for the latest processed CallStateChanged event; the command path (answer/hangup/transfer via answer_call_state) and the native path both write the same §18 CallState domain, so call_state() never reports a stale pre-transition value.
- 【Boundary invariant】The mapping is total and deterministic: every u32 input (0..8 and any other value) maps without panic, and repeated processing of the same (state, direction) input yields the same CallState; the reactor's serial loop (§33) makes the update-before-publish ordering explicit and deterministic (C128).
