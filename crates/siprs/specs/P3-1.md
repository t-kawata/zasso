# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0011 defines the complete public API: crate root re-exports, SipClient struct/methods, SipAccountHandle API, OutgoingCallRequest. N0014 defines AccountConfig with codec, DTMF, media policies. N0015 defines TransportConfig (UDP/TCP/TLS), ICE/STUN/TURN configs. These form the public interface of the crate.

### Goal
Define the complete public API surface of the siprs crate — struct definitions, method signatures, type aliases, and re-exports — for `SipClient`, `SipAccountHandle`, `AccountConfig`, `TransportConfig`, and supporting configuration types, enabling users to construct a SIP client, manage accounts, configure transport, and initiate calls.

### Purpose
Establish the single, authoritative public interface (`pub` types and methods) that downstream consumers (zasso desktop app, CLI tools, integration tests) use to interact with the SIP voice communication system. Without this definition, all downstream development is blocked on knowing which types and methods will be available.

### Motivation
P0 through P2 tickets have established the foundational config layer (ClientConfig), concurrency model (RuntimeCommand), error types (SipError), event system (EventBus), and ID types. These foundations are now ready to be composed into a coherent public API. N0011 (§8), N0014 (§11), and N0015 (§12-§13) from RFC-ROOT specify exactly what the API surface should look like.

### Constraints
1. **No runtime behavior**: This ticket defines the public API surface, types, and validation rules only. Runtime dispatch (connecting API calls to PJSUA) is deferred to P3-2 (Runtime inner + FFI).
2. **Feature gates**: `tls` and `srtp` features must be respected — TLS transport variant conditionally compiled, SRTP in AccountMediaConfig conditionally compiled.
3. **Backward compatibility**: Once published, struct field additions require `#[non_exhaustive]` or semver-major releases. All enums that may grow must be `#[non_exhaustive]`.
4. **Ownership**: All public API types must be `Send + Sync` and use `Arc<ClientInner>` for shared mutable state. Cloning SipClient must be cheap.`

## Acceptance Criteria

- Public API defined with all structs and methods
- AccountConfig covers all account settings
- TransportConfig supports UDP/TCP/TLS
- **[Happy path] — All public types compile and are accessible at crate root:**
  1. `SipClient`, `SipAccountHandle`, `ClientConfig`, `AccountConfig`, `TransportConfig` are re-exported at `siprs::*` level.
  2. `SipClient::new(ClientConfig{..})` compiles and returns `Result<SipClient, SipError>`.
  3. `SipClient::add_account(AccountConfig{..})` adds an account and returns `SipAccountHandle`.
  4. `SipAccountHandle::make_call(OutgoingCallRequest{..})` returns `Ok(CallId)`.
  5. `AccountConfig` with valid fields (non-empty username/domain/password, at least one codec) passes all validation rules.
  6. `TransportConfig::Udp(..)` / `Tcp(..)` / `Tls(..)` (with tls feature) all constructable.
- **[Error case] — Invalid configurations are rejected:**
  1. `AccountConfig` with empty `username` → `Err(SipError::invalid_config(...))`.
  2. `AccountConfig` with empty `domain` → `Err(SipError::invalid_config(...))`.
  3. `AccountConfig` with empty `password` → `Err(SipError::invalid_config(...))`.
  4. `AccountCodecPolicy{enable_pcmu: false, enable_opus: false}` → validation error.
  5. `DtmfPolicy{send_methods: [], ..}` → validation error (must have at least one send method).
  6. `DtmfPolicy{receive_methods: [], ..}` → validation error (must have at least one receive method).
  7. `OutgoingCallRequest{target_uri: ""}` → validation error.
  8. `CallMediaPreferences{preferred_codecs: vec![Codec::G722]}` → validation error (only PCMU, Opus allowed).
  9. Without `tls` feature, `TransportConfig::Tls(..)` does not compile.
- **[Edge case] — Boundary conditions handled correctly:**
  1. `register_on_start=false` + `allow_outbound_without_register=true` → valid config.
  2. `register_on_start=false` + `allow_outbound_without_register=false` → valid config (no-call, no-register account).
  3. `registrar_uri=None` → auto-derived as `sip:{domain}` string.
  4. `OpusConfig{complexity: 11}` → rejected (out of 0-10 range).
  5. Multiple outbound proxies, multiple custom headers → accepted.
  6. IPv6 bind addresses in transport config → accepted.
  7. ICE disabled (no STUN/TURN servers required), ICE enabled (STUN/TURN required) — structural validation.

## Invariants

- [Normal establishment] All AccountConfig required fields (username, domain, password) must be non-empty; AccountCodecPolicy must have at least one codec enabled; DtmfPolicy send_methods and receive_methods must each contain at least one element; TransportConfig TLS variant only available when `feature = "tls"` is active.
- [Invariant on error] On validation error, the system must not create partial/inconsistent state — AccountConfig validation is all-or-nothing, returning `Err(SipErrorKind::InvalidConfig)` before any side effects or state mutation. No account is created from an invalid config.
- [Internal state invariant] ClientInner state (account list, shutdown flag) is protected by `tokio::sync::RwLock` — all reads use `read().await`, all writes use `write().await`. The account index invariants: (a) no duplicate AccountId values exist, (b) remove_account removes exactly the matching entry, (c) accounts() returns a snapshot consistent at the time of the read lock acquisition.
- [Boundary invariant] Input gains/output gains are stored as `f32` with no artificial clamp — the PJSIP layer interprets gain values; the Rust layer passes through. OpusConfig.bitrate: 6000-510000 bps (Opus spec range). OpusConfig.complexity: 0-10 (inclusive). registration_expires: minimum 30 seconds.

## Boy Scout Rule

- **Translatability improvements (Boy Scout Rule) — P3-1 scope:**

  **1. `src/api/public_api_design.rs` (new file):**
  - Function names as verb phrases: `subscribe()`, `subscribe_raw_sip()`, `add_account()`, `remove_account()`, `make_call()` — already verb-phrase shaped by design, ensure naming remains consistent.
  - Variable names as domain concepts: Use `SipClient`, `SipAccountHandle`, `AccountId`, not generic names like `handle` or `id` in ambiguous contexts.
  - One function one responsibility: Each SipClient method should delegate to a named inner function, not inline logic. E.g., `add_account` calls `self.validate_and_store_account(config)` rather than inlining the validation + insertion.
  - Hardcoded values as named constants: Minimum registration expiry (30s), Opus bitrate range (6000-510000) extracted as `const MIN_REGISTRATION_EXPIRY_SECS: u64 = 30;` etc.
  - No error swallowing: All public methods return `Result<T, SipError>`. Internal helper functions also return Result — never use `.ok()` or `.unwrap_or()` that discards error context.

  **2. `src/config/account_config_spec.rs` (new file):**
  - Struct field documentation: Each field annotated with doc comment explaining its purpose, SIP semantics, and default (if any).
  - Validation extracted to `validate()` method rather than inline checks in `new()` — reads as "construct then validate" prose.
  - `OpusConfig` validation for complexity (0-10) and bitrate (6000-510000) as named constants, not magic numbers.

  **3. `src/config/transport_ice_spec.rs` (new file):**
  - `cfg(feature = "tls")` gated types clearly documented with `// Available only with feature = "tls"` annotation on each gated item.
  - TransportConfig variants in documentation order (UDP → TCP → TLS) matching protocol layering.

  **4. `src/lib.rs` (modified):**
  - Re-exports grouped by RFC node: `// §8 Public API` / `// §11 AccountConfig` / `// §12 TransportConfig` comment headers.
  - Existing test module left intact; new P3-1 tests added as a separate `#[cfg(test)] mod p3_1_tests { ... }` or inline per-file.

### Exceptions

- **Exception 1: Actual SIP network registration and deregistration**
  - [Item/Reason] Cannot test actual SIP registration against a real server because it requires live PJSUA library and network connectivity.
  - [This is not a design defect] The feature is deterministic and testable in principle — it only requires external infrastructure unavailable in unit tests. Alternative verification via MockBackend-based integration tests validates the same logical path without network dependency.
  - [Alternative verification] MockBackend (from N0037 SipBackend trait) simulates registration responses. Existing tests/example_validation.rs validates example compilation against the public API.
- **Exception 2: Actual RTP media stream setup and audio transmission**
  - [Item/Reason] Cannot test actual RTP media streaming because it requires PJSUA media engine initialization, audio device access, and real-time audio I/O.
  - [This is not a design defect] The media pipeline design is deterministic and will be tested via integration tests once the audio backend (P3-2/P4-3) is implemented. The test gap exists solely at the hardware boundary — not a design flaw.
  - [Alternative verification] OutgoingCallRequest and CallMediaPreferences struct validation are unit-tested. Audio format validation (codec policy) is tested via AccountConfig validation.
- **Exception 3: TLS transport handshake and certificate validation**
  - [Item/Reason] Cannot test TLS handshake because it requires a TLS-capable transport stack, certificates, and platform-specific PKI infrastructure. The tls feature gate makes this conditionally compiled.
  - [This is not a design defect] TLS is a standard protocol with well-defined behavior. The structural guarantee (Tls variant absent without feature flag) is a type-level invariant verified at compile time — this is correct by construction, not a testing gap.
  - [Alternative verification] TlsConfig struct construction tested under #[cfg(feature = "tls")]. Compile-time assertions verify the type-level gating.
- **Exception 4: ICE candidate gathering and connectivity checks (STUN/TURN)**
  - [Item/Reason] Cannot test ICE connectivity checks because they require external STUN/TURN servers and real ICE agent initialization.
  - [This is not a design defect] The ICE configuration types (IceConfig, StunServerConfig, TurnServerConfig) are data-only structs with defined validation rules — fully testable in isolation. The runtime ICE agent execution is deferred to PJSUA FFI (P3-2), which is deterministic and separately testable.
  - [Alternative verification] IceConfig/StunServerConfig/TurnServerConfig construction and field validation are unit-tested. The structural contract (full ICE support, trickle ICE optional) is verified via field presence in config types.
