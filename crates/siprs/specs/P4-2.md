# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0025 defines RegistrationState enum (7 states: Disabled/Idle/Registering/Registered/Unregistering/Failed/Expired) with transition rules. N0026 defines CallState enum (12 states: New/Calling/Trying/Ringing/EarlyMedia/Incoming/Connecting/Active/Held/Transferring/Disconnecting/Disconnected/Failed) with outgoing/incoming diagrams. N0043 defines idempotent shutdown sequence.

### Goal
Define and implement the three state machines that govern the lifecycle of registration, calls, and shutdown in the siprs crate. Each state machine must be fully typed (Rust enum), enforce RFC-defined transition rules, and expose a try_transition() interface for the runtime module.

### Purpose
These state machines are the backbone of siprs correctness. Without them, the runtime cannot enforce legal call flows (e.g., answer only on incoming), manage concurrency limits (max_calls), or guarantee safe teardown without resource leaks. They exist to make illegal states unrepresentable and to provide a single source of truth for state-dependent operations.

### Motivation
Currently all three state machine files are stubs (pub enum State {} with a STUB marker). The runtime module (P3-2) and the public API (P3-1) depend on these types being defined before they can dispatch commands. Without this ticket, the entire runtime layer is blocked. The state machine definitions themselves are purely structural enums with transition validation — no FFI or I/O — making them the ideal first concrete implementation in the crate.

### Constraints
- RegistrationState must remain independent from call ability (no cross-gating per §17)
- CallState must contain exactly 13 variants as specified by §18; no more, no fewer
- Shutdown MUST be idempotent (AtomicBool guard) to prevent double-free of PJSUA resources
- No external dependencies beyond std and crate-internal types (SipError, SipErrorKind)
- All three state modules must be pub(crate) and exported from state/mod.rs
- The existing RegistrationState enum in public_api_design.rs (4-variant) is the public API type; the internal 7-variant RegistrationState in registr_state_machine.rs is a separate, more granular state machine for runtime use

## Acceptance Criteria

- [Happy path] Registration, call, and shutdown lifecycle: Create SipClient, add account, register (Disabled→Registering→Registered), make_call (New→Calling→Trying→Ringing→Connecting→Active), hold/unhold (Active→Held→Active), hangup (Active→Disconnecting→Disconnected), unregister (Registered→Unregistering→Idle), shutdown (Idle→ShuttingDown→ShutdownComplete). All transitions validate successfully, no errors returned.
- [Error case] Invalid transitions and flow control: Attempt unregister from Idle (should fail InvalidState), attempt answer() on Outgoing/Ringing call state (should fail InvalidState), attempt make_call when active_calls >= max_calls (should fail InvalidState), attempt shutdown twice (second call returns Ok but no-op), attempt ConfConnect during shutdown (should fail InvalidState with 'shutting down'). All assertions confirmed.
- [Edge case] Boundary and absorbing states: RegistrationState::Disabled — only register() valid, all other transitions rejected. CallState::Failed — no valid transitions from terminal state. CallState::Disconnected — no valid transitions, absorbing. Shutdown with 0 active calls and 0 accounts — teardown completes Ok with no actual work but no errors. max_calls=0 — all make_call() attempts rejected without creating call state. RegistrationState::Expired→Registering — re-registration from expiry succeeds.

## Invariants

- [Normal establishment] Preconditions that must hold for correct behavior:
  - RegistrationState transitions must follow the RFC §17 transition matrix (Disabled→Registering→Registered→Unregistering→Idle cycle, with Failed/Expired paths)
  - CallState transitions must follow the RFC §18 transition matrix (outgoing: New→Calling→Trying→[Ringing|EarlyMedia]→Connecting→Active; incoming: New→Incoming→Connecting→Active; active-session: Active↔Held, Active→Transferring→[Active|Disconnecting])
  - Shutdown sequence must execute in order: BYE/CANCEL all calls → unregister accounts → drain audio → pjsua_destroy

- [Error invariant] Invariants that must never be violated even on error:
  - A failed transition must never leave the state machine in an inconsistent/undefined state — if try_transition() returns Err, the current state is unchanged (atomicity)
  - Even if PJSUA native calls fail during shutdown, the internal ShutdownState must still advance; the idempotent guard prevents re-entry regardless of PJSUA errors
  - max_calls violation must reject the call without creating any CallState entry; no orphan state on rejection

- [Internal state invariant] Invariants the module's internal state must always satisfy:
  - RegistrationState enum value is always one of exactly 7 valid variants (no undefined state)
  - CallState enum value is always one of exactly 13 valid variants
  - ShutdownState transitions only forward: Idle → ShuttingDown → ShutdownComplete; never backward
  - The AtomicBool shutdown guard and the ShutdownState enum must be consistent (guard=true iff state != Idle)

- [Boundary invariant] Invariants related to boundary values / thresholds:
  - max_calls = 0 means no outgoing calls permitted (all make_call() attempts rejected). This is a valid config allowed by ClientConfig validation.
  - max_calls = u32::MAX means effectively unlimited calls (constrained only by system resources)
  - Disabled state in RegistrationState: once set, all non-register transitions are invalid until register() or set_enabled(true) is called
  - Failed and Disconnected/DisconnectedStates are absorbing — once entered, no further transitions are valid

- [Risks]
  - Risk: The try_transition() function signatures need to align with the future runtime module's expected interface. Mitigation: make try_transition(&self, target) -> Result<(), SipError> simple and generic; the runtime can wrap it as needed.
  - Risk: The 7-variant RegistrationState differs from the 4-variant public RegistrationState in public_api_design.rs. Mitigation: the runtime maps between them; the spec documents this explicitly.

- [Caveats]
  - The internal RegistrationState (7 variants) and public RegistrationState (4 variants: Unregistered/Registering/Registered/Failed) coexist. They are NOT the same type. The public one's Unregistered maps to the internal Disabled or Idle depending on context.
  - The Transferring state in CallState is transient — the runtime must never leave a call in Transferring indefinitely. A timeout or NOTIFY resolves it.

- [Open items]
  - Whether try_transition should consume self or take &self depends on the runtime's ownership model. Currently designed as &self (borrowing) to avoid unnecessary cloning in the runtime's state map lookup.
  - The exact mapping between internal RegistrationState (7) and public RegistrationState (4) needs to be confirmed during runtime implementation (P3-2).
