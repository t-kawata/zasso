# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0030 defines audio format types and AudioChunkPair. N0035 defines PairAligner for IN/OUT alignment. N0036 defines ResamplePipeline using rubato. N0040 defines codec policy with NegotiatedCodec and CodecSelectionPolicy.

### Goal
Define and implement the foundational audio data types (AudioFormat, AudioChunkPair), the IN/OUT alignment algorithm (PairAligner) for RTP-vs-mixer timebase reconciliation, the resampling pipeline (ResamplePipeline) with stereo IN/OUT mapping, and the codec negotiation/fallback policy (NegotiatedCodec, CodecSelectionPolicy). These four nodes form the audio processing layer that all higher-level audio features (AudioMixer, Media Bridge, Audio Subscribe) depend on.

### Purpose
Provide type-safe, testable audio primitives that decouple the inner audio pipeline from PJSUA's native format and codec model. Callers work with AudioFormat/AudioChunkPair regardless of the underlying FFI format; PairAligner absorbs the timing skew between RTP arrival (network jitter) and mixer scheduling (Tokio async); the resampler bridges sample rate gaps; the codec policy ensures only PCMU and Opus are active after initialization (C041 invariant).

### Motivation
P3-2 (AudioMixer) introduced mix_i16_frame and the mixer/source infrastructure but left the data representation layer abstract. Without AudioFormat/AudioChunkPair, callers must reason about raw Vec<i16> and sample rates manually — a fertile ground for off-by-one and format mismatch bugs. Without PairAligner, the RTP ingress timebase (realtime) and AudioWorkerTask timebase (Tokio async) diverge and cause audio artifacts. Without the codec policy, all PJSUA codecs remain enabled (including G.722, iLBC, etc.), violating the Opus-only/PCMU-fallback security and quality requirement (C041).

### Constraints
1. No PJSUA dependency in pure-data types (AudioFormat, AudioChunkPair, NegotiatedCodec) — they must be testable without an initialized PJSIP stack. 2. PairAligner must not block or allocate on the RT callback path — only VecDeque push/pop in AudioWorkerTask context. 3. ResamplePipeline uses rubato FftFixedIn as the single resampling backend — no fallback to linear interpolation. 4. Codec priority assignments follow the M20 spec: Opus=255, PCMU=254, all others=0 in auto mode. 5. The codec policy fallback file (codec_policy_fallback.rs) must remain consistent with the already-implemented m20_codec_auto_mode.rs.

## Acceptance Criteria

- 【Happy path】Construct AudioFormat with all valid field combinations (4 sample rates × 2 bit depths × 2 channel layouts × 4 frame_ms values = 64 valid combinations). Create AudioChunkPair with matching IN/OUT AudioChunk data. Push timed IN and OUT frames into PairAligner within tolerance — try_pair returns the paired (in, out) data. Configure ResamplePipeline for 48kHz→16kHz conversion — resample a known signal and verify correct output dimensions. CodecAutoMode::apply with PCMU/Opus/other codecs returns {PCMU=254, Opus=255, other=0}. NegotiatedCodec::Opus(OpusConfig) round-trips through AccountCodecPolicy storage.
- 【Error case】AudioFormat::new with frame_ms=0 or 70 (out of range) returns Err. AudioFormat::new with frame_ms=17 (not divisible by 10) returns Err. PairAligner::try_pair on both empty queues returns None. PairAligner drops the earlier frame when timestamp delta exceeds tolerance. ResamplePipeline::new with same in_rate==out_rate but unsupported combination returns Err. CodecAutoMode::apply with duplicate codec_ids returns Err(SipError).
- 【Edge case】AudioChunk::I16 with empty Vec<i16> is valid (len=0). AudioChunk::F32 with empty Vec<f32> is valid. AudioFormat frame_ms at minimum (10) and maximum (60) boundaries both construct successfully. PairAligner where only IN data arrives (no OUT data for extended period) produces zero-padded OUT with incrementing drift counter. interleave_in_out with in_mono shorter than out_mono truncates to the shorter length. Stereo interleave of empty inputs produces empty output vec.

## Invariants

- 【Normal establishment】AudioFormat fields must always have valid values: sample_rate in {Hz8000,Hz16000,Hz24000,Hz48000}, bit_depth in {I16,F32}, channel_layout in {Mono,StereoInOut}, frame_ms in {10,20,40,60} only. AudioChunkPair must always pair IN and OUT data under the same timestamp. PairAligner must only produce paired output when |ts_in - ts_out| <= tolerance. Codec auto mode must assign Opus=255 and PCMU=254 invariantly.
- 【Invariant on error】On any validation error (e.g., invalid frame_ms), the AudioFormat is not constructed — no partial or inconsistent AudioFormat instance is ever created. If PairAligner encounters a timeout during queue draining, it zero-pads rather than returning corrupt data. Aligner drift is reported as a counter metric, never as a hard error unless sustained loss exceeds a future configurable threshold.
- 【Internal state invariant】PairAligner in_q and out_q are VecDeque<TimedFrame<Vec<i16>>> that grow monotonically until try_pair is called — the queue depths reflect the cumulative IN/OUT imbalance. ResamplePipeline holds in_rate/out_rate AudioFormat references and is stateless between resample calls. CodecSelectionPolicy is a pure configuration enum with no mutable state.
- 【Boundary invariant】frame_ms=10 is the minimum valid frame duration (at 48kHz=480 samples), frame_ms=60 is the maximum (at 8kHz=480 samples). PairAligner tolerance must be > 0 (zero tolerance would prevent any matching; practically set to >=20ms to accommodate jitter). AudioChunk::I16 with empty Vec<i16> and AudioChunk::F32 with empty Vec<f32> are valid edge states. NegotiatedCodec has exactly 2 variants (Pcmu, Opus).
