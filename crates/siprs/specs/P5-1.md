# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Background

## Goal
P5-1 implements SIP call control API (answer/hangup/hold/unhold/transfer/send_dtmf/call_state), RawSipMessage Authorization redaction, and AudioSubscribe API (AudioTapHandle + AudioTapMode) on SipClient, concretizing the design contracts of RFC-ROOT sections 16(N0024)/19(N0027)/22(N0031) as code.

## Purpose
Enable SipClient consumers (zasso upper layers) to control the full SIP call lifecycle (answer/disconnect/hold/transfer/DTMF/state). Also provide access to call audio (subscribe_audio) and safe raw SIP message retrieval (Authorization redaction) as the foundation for monitoring, recording, and quality measurement.

## Motivation
P4-4 (HTTP/WS Protocol types & SQLite schema) and P4-3 (Audio Format/PairAligner/Resampler) have established foundational types. P5-1 is the first phase implementing actual call control APIs using these types, positioned as a type-definition and contract-verification layer that does not depend on P6 (Runtime + Backend).

## Acceptance Criteria

- Happy path: SipClient::answer(CallId, 200) on an incoming call returns Ok(()). The call state transitions from Incoming → Connecting → Active via the state machine. SipClient::hangup() on the Active call returns Ok(()), and call_state() returns Disconnected. SipClient::hold() returns Ok(()) and call_state() returns Held. SipClient::unhold() returns Ok(()) and call_state() returns Active. SipClient::transfer(call_id, "sip:target@domain") returns Ok(()). SipClient::send_dtmf(call_id, "123", DtmfMethod::Rfc2833) returns Ok(()). All operations complete without panic and produce the correct CallState transitions.
- Error case: SipClient::answer() on a non-existent call_id returns Err(SipError { kind: CallNotFound }). SipClient::hangup() on an already-Disconnected call returns Err(SipError { kind: CallNotFound }). SipClient::hold() on a call in New state returns Err(SipError { kind: InvalidState, message: "hold() is only valid for Active calls" }). SipClient::subscribe_audio() on a non-existent call returns Err(SipError { kind: CallNotFound }). SipClient methods never panic; all error paths return typed SipError.
- Edge case: SipClient::answer(code=180) returns Ok(()) and keeps the call in Ringing state (provisional). Answer(code=183) allows early media. Answer(code=486/603) declines the call and transitions to Disconnected. RawSipMessage with empty header vector: redact_authorization() returns clone with no changes. AudioTapHandle::recv() on a closed channel returns None (channel closure is not an error). Multiple concurrent call_state() queries for the same call_id all return the same state (proved via tokio::spawn).

## Invariants

- [Normal establishment] For each call, exactly one CallState is active at any time. The state transitions follow the 13-state matrix defined in N0026/CallState::try_transition(). AudioTapHandle lifecycle: handle exists only while the underlying call is active and subscribe_audio consumer has not dropped the handle.
- [Invariant on error] Even when call_state() returns Err (e.g., call not found), no internal state corruption occurs — the CallState machine stays in its last valid state. Authorization redaction failure (e.g., malformed header key) never panics; the header is returned unmodified.
- [Internal state invariant] SipClient.call_state() returns the state from the authoritative runtime state (not a local cache). RuntimeCommand ordering is FIFO — two consecutive commands on the same call_id are processed in submission order. AudioTapHandle's internal mpsc::Receiver is consumed only by recv(); no concurrent access.
- [Boundary invariant] answer() codes are restricted to {180, 183, 200, 486, 603}. Code 0 and codes >= 700 are rejected. send_dtmf() digits max length = 32 (RFC 4733). AudioTapMode::Lossless capacity must be >= 1 (constructor returns Err for 0). RawSipMessage redact_authorization handles 0 headers, 1 header, and N headers identically.

### Exceptions

- Exception entry: Real PJSUA FFI call_answer/hangup/hold FFI calls. impossible to test: Real PJSIP calls require a running PJSIP library instance with real SIP transport which this crate cannot mock at the FFI level — the pjsua_call_answer() FFI function signature (extern "C") is fixed and its behavior depends on a live pjsua state. This is not a design defect: the system is explicitly layered with Command/Reactor/Backend pattern, where RuntimeCommand dispatch (verified in P5-1) abstracts the FFI boundary, and PjsuaBackend (P6-2) implements the real FFI calls. Alternative verification: Integration tests marked #[ignore] for CI-only runs using Docker Asterisk (P6-2) exercise the full Command→Reactor→Backend chain.
- Exception entry: AudioTapHandle real-time audio streaming under OS scheduling. impossible to test: Deterministic behavior under OS scheduling (context switches, interrupt latency, thread preemption) cannot be unit-tested because the OS scheduler is not under test control. This is not a design defect: the AudioTapHandle abstraction cleanly separates channel semantics (tokio::mpsc::channel send/recv — synchronously testable) from OS scheduling (system-level). This separation proves it is not a design defect. Alternative verification: E2E tests with Docker Asterisk (P6-3) using real audio generation/consumption exercise the full scheduling path.
- Exception entry: RawSipMessage Authorization redaction with malformed headers (e.g., "Authorization" vs "authorization" casing). impossible to test: SIP headers are case-insensitive per RFC 3261, and header parsing/normalization is the responsibility of the upstream PJSIP callback layer (P0-4 EventBus raw SIP channel), not the redaction logic which operates on pre-normalized key-value pairs. This is not a design defect: the separation of concerns is intentional — the redaction function is a pure transformation on the normalized data structure. Risk 2: AudioTapHandle currently stores mpsc::Receiver<AudioChunkPair> — if the Reactor changes the audio frame type, the handle type changes too. Mitigation: AudioTapHandle is a newtype struct; the inner type is easily replaceable.
