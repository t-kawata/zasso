# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P5-2: DTMF, AsyncAudioSource Trait & Incoming Call/Transfer

**Ticket Key**: P5-2 · **Phase**: 5

## RFC Reference

## Background

N0028 defines DtmfMethod (Inband/SipInfo/Rfc4733), DtmfReceivedInfo, and policy-based validation. N0032 defines AsyncAudioSource with RPITIT, ErasedAudioSource auto-derivation, SyncAudioSource and SyncSourceAdapter. N0048 defines IncomingCall struct with auto-reject timer and REFER/Transfer with blind transfer support.

### Goal
Define three independent API surface areas: (1) DTMF specification with DtmfReceivedInfo struct carrying method, digit, duration_ms, volume_dbm0 + policy-based method validation, (2) AsyncAudioSource trait with RPITIT + ErasedAudioSource dynamic dispatch blanket impl + SyncSourceAdapter bridging, (3) IncomingCall struct with caller/callee metadata, codecs, auto-reject timer config + ReferRequest struct for blind transfer with NOTIFY completion.

### Purpose
Enable the SIP client to: (a) receive DTMF digits with full metadata (duration, volume) and validate against account policy, (b) accept any synchronous or asynchronous audio source via a uniform AsyncAudioSource trait interface, (c) handle incoming calls with structured caller metadata and support blind call transfer via REFER/NOTIFY.

### Motivation
These three areas are foundational for PJSIP-based voice communication: DTMF is required for IVR menus and in-call signaling; AsyncAudioSource decouples audio source implementation (file, mic, synthesized) from the mixer pipeline; IncomingCall/Transfer is the basic call lifecycle feature required for P5-1 call control API completeness. All three are dependencies of the Media Bridge (P4-3) and Audio Subscribe (P5-1) pipelines.

### Constraints
- RPITIT requires MSRV >= 1.75 (stable since 1.75). Existing crate already targets edition 2021 with MSRV implicitly >= 1.75 via tokio dependency.
- ErasedAudioSource must not leak into public API — it is an internal implementation detail for AudioMixer dynamic dispatch.
- DtmfMethod variants must remain consistent between DtmfReceivedInfo (this ticket) and DtmfSentInfo (P0-7 m20_dtmfsent_twophase). Both use the shared `api::m20_dtmfsent_twophase::DtmfMethod`.
- Attended transfer is explicitly out of scope — only blind REFER transfer.
- Auto-reject timer config is a placeholder reference (actual timer scheduling deferred to P3-2 runtime).

## Investigation

- 【Graph node analysis】Three independent nodes: N0028 (§20 DTMF), N0032 (§23 AsyncAudioSource), N0048 (§37 Incoming Call + §38 REFER/Transfer). Each maps to an existing stub file under src/api/.
- 【Existing code】All three files (`dtmf_spec_received.rs`, `asyncaudiosrc_adapter.rs`, `incoming_call_refer.rs`) contain only the initial stub `pub trait Service {}` plus the Initial Design Artifact header and a `[::STUB::]` marker. No real types exist yet.
- 【DtmfMethod duality】DtmfMethod is defined twice: (a) `config/account_config_spec.rs` with variants Rfc2833/Info/Inband (config-layer, validated via AccountMediaConfig::default_send_method), (b) `api/m20_dtmfsent_twophase.rs` with variants Inband/SipInfo/Rfc4733 (api-layer, used by DtmfSentInfo tests and RuntimeCommand::SendDtmf). This ticket's DtmfReceivedInfo uses the api-layer DtmfMethod via `crate::api::m20_dtmfsent_twophase::DtmfMethod`.
- 【Event bus】`event_model_payload_bus.rs` defines SipEventPayload with both DtmfReceived and IncomingCall as unit variants (no data). These must be changed to carry DtmfReceivedInfo and IncomingCall payloads respectively.
- 【Public API types】Relevant existing types: CallId (model/id_design_newtype), Codec (api/public_api_design.rs with variants Pcmu/Opus). Both are pub types used by the new structs.
- 【trait Service {}】The placeholder `pub trait Service {}` in all three stub files is a generic bound placeholder from P0-4 that has no semantic meaning for these modules. It must be removed entirely, not extended.
- 【RPITIT MSRV】AsyncAudioSource uses async fn in trait (RPITIT), stable since Rust 1.75. Crate's Cargo.toml sets edition = 2021, which implicitly supports this. No MSRV bump needed.
- 【test patterns】Existing test patterns in adjacent modules (m20_dtmfsent_twophase.rs, call_api_semantics.rs) use `#[cfg(test)] mod tests { use super::*; }` with construct-and-assert tests. New tests should follow the same pattern.

## Acceptance Criteria

- DTMF 3-way methods defined — DtmfReceivedInfo struct compile-tested with all 3 DtmfMethod variants. SipEventPayload::DtmfReceived carries DtmfReceivedInfo (not unit variant). duration_ms and volume_dbm0 fields are Option types with correct bounds.
- AsyncAudioSource with RPITIT defined — AsyncAudioSource trait with async fn next_chunk compiles. ErasedAudioSource blanket impl allows Box<dyn ErasedAudioSource>. SyncSourceAdapter<T: SyncAudioSource> bridges sync source to AsyncAudioSource. All traits require Send.
- Incoming call and REFER/Transfer defined — IncomingCall struct carries from_uri, to_uri, display_name, headers, offered_codecs, has_early_media. SipEventPayload::IncomingCall carries IncomingCall payload. ReferRequest struct defined for blind transfer.

IncomingCall constructed with full metadata — all fields readable via dot notation.
- 【Error case】DtmfReceivedInfo with None duration and None volume — construction succeeds, None fields correctly handled. SyncSourceAdapter wrapping a source that returns 0 — zero-length buffer handled without panic.
- 【Edge case】DtmfReceivedInfo duration_ms = 0 (minimum u16) and u16::MAX — both accepted. volume_dbm0 = -128 (i8 MIN), 127 (i8 MAX), 0 (reference) — all accepted. IncomingCall with empty headers vec and empty offered_codecs vec — construction succeeds. has_early_media = false and true both accepted.

## Invariants

- 【Normal】DtmfReceivedInfo must always carry a valid DtmfMethod variant; DtmfMethod enforces exactly 3 variants (Inband/SipInfo/Rfc4733) via enum exhaustiveness.
- 【Normal】AsyncAudioSource::next_chunk must return usize ≤ buf.len() — the implementation must never write beyond buffer bounds.
- 【Normal】IncomingCall struct fields are public and directly accessible — no getter boilerplate needed.
- 【Error】On erroneous input (e.g., DtmfReceivedInfo with unexpected data), the struct itself cannot fail to construct — it is a pure data container. Validation is at the point of event emission (P3-2 runtime).
- 【Error】ErasedAudioSource blanket impl never panics — the Pin<Box<dyn Future>> wrapper delegates to the underlying AsyncAudioSource::next_chunk; any panic originates from the implementation, not from the wrapper.
- 【State】DtmfReceivedInfo is immutable after construction (all fields are pub but the struct has no impl methods that mutate).
- 【State】SyncSourceAdapter owns its inner T exclusively — no shared references. inner is private and accessed only via AsyncAudioSource::next_chunk.
- 【Boundary】duration_ms is Option<u16> — valid range [0, 65535]; None means duration not reported by PJSIP callback.
- 【Boundary】volume_dbm0 is Option<i8> — valid range [-128, 127]; None means volume not reported. 0 dBm0 is the reference tone level.
- 【Boundary】SyncSourceAdapter buffer size ≤ usize::MAX (platform-dependent). Zero-length buffer returns Ok(0) immediately.

## Boy Scout Rule

- 【Remove stub placeholder】Replace the generic `pub trait Service {}` in all three files with meaningful type definitions. The placeholder has no semantic connection to DTMF, audio sources, or call handling — it will be removed entirely.
- 【AsyncAudioSource trait naming】Use verb-phrase method `next_chunk` ("fetch the next chunk of audio samples") — the name reads as an action, not a getter. The method clearly communicates that it fills a buffer and returns the count of samples written.
- 【SyncSourceAdapter field naming】The private field `inner` is generic but acceptable — it is an implementation detail hidden from consumers. Public API surface uses `SyncSourceAdapter::new()` to construct, which reads naturally.
- 【IncomingCall struct fields】All field names are domain-specific: `from_uri` (not `from` or `caller`) because SIP distinguishes From URI vs display name; `offered_codecs` describes the SDP offer semantics explicitly.
