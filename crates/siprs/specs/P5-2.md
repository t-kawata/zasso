# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0028 defines DTMF methods (Inband, SipInfo, Rfc4733). N0032 defines AsyncAudioSource trait with RPITIT and SyncSourceAdapter. N0048 defines incoming call handling and REFER/blind transfer.

### Goal
Define and implement DTMF specification (DtmfMethod, DtmfReceivedInfo with method field), AsyncAudioSource adapter types (ErasedAudioSource, SyncAudioSource, SyncSourceAdapter), and IncomingCall/Refer transfer types per RFC N0028/N0032/N0048. Replace existing stubs in src/api/ with full typed implementations and register new modules in api/mod.rs.

### Purpose
Provide type-safe DTMF signalling primitives for SIP call control. Enable downstream crates to implement custom async audio sources for AudioMixer. Expose incoming call metadata (URI, headers, codecs, early media) and REFER-based transfer capabilities to application code via typed events.

### Motivation
Current stub files prevent compilation of dependent modules and block P5-1 (Call API) which depends on DTMF types and DtmfReceived event. Incoming call handling is required for zasso's call routing and auto-attendant features. Audio source abstraction is mandatory for the AudioMixer integration pipeline.

### Constraints
MSRV 1.95 — RPITIT stable; use native async fn in traits with ErasedAudioSource for dynamic dispatch. Do NOT add new crate dependencies — all required derives (Clone, Debug, PartialEq) are std. Maintain backward compatibility with existing DtmfReceivedInfo consumers (P0-5 event model). The DtmfMethod enum in m20_dtmfsent_twophase.rs must stay separate or be unified — unification is preferred but needs careful migration.

## Acceptance Criteria

- [Happy path] A downstream crate creates a DtmfReceivedInfo with method=DtmfMethod::Rfc4733, digit='5', duration_ms=Some(100), volume_dbm0=Some(-15). SyncSourceAdapter wraps a SyncAudioSource and AsyncAudioSource::next_chunk returns correct data. IncomingCall constructed with from_uri, to_uri, headers, codecs. ReferRequest created from refer_to URI. Blind transfer TransferInfo carries status_code=200.
- [Error case] DtmfPolicy::send_methods does not contain requested DtmfMethod → dtmf validation returns Err(InvalidConfig). SyncSourceAdapter inner source returns 0 → adapter AsyncAudioSource::next_chunk returns 0 (exhausted). IncomingCall with empty from_uri does not panic.
- [Edge case] DtmfReceivedInfo duration_ms=None (no duration info from caller), volume_dbm0=None (no volume info) — struct still well-formed. IncomingCall with empty offered_codecs vec (pre-negotiation) accepted. has_early_media=false works the same as true.

## Invariants

- 【Normal establishment】DtmfPolicy always has >=1 send_method and >=1 receive_method (validated in AccountConfig::validate()). DtmfReceivedInfo always has at least `method` and `digit` populated by construction. AsyncAudioSource::next_chunk returns 0 when exhausted, never panics. SyncSourceAdapter delegates all calls to inner source without adding logic.
- 【Invariant on error】DTMF method validation returns InvalidConfig error — never panics. SyncSourceAdapter with exhausted inner source returns 0, never produces garbage. IncomingCall construction with empty from_uri/to_uri does not panic.
- 【Internal state invariant】ErasedAudioSource blanket impl compiles for all T: AsyncAudioSource + Send — no manual impl per type. DtmfReceivedInfo types always implement Clone + Debug + PartialEq. SyncSourceAdapter<T> implements Send when T: Send.
- 【Boundary invariant】duration_ms range [0, u16::MAX] accepted without truncation. volume_dbm0 range [i8::MIN, i8::MAX] accepted. SyncAudioSource buf size at extremes (0, 65535) handled without overflow. IncomingCall offered_codecs empty vec accepted (pre-negotiation state).
