# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.

- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.

## Background

### Goal
Resolve the `[::STUB::] P9-2` marker in `src/api/audio_subscribe_bp.rs` (line 23) by implementing the Audio Subscribe API per RFC §22 (N0031): `AudioTapMode { Realtime, Lossless }`, `AudioTapHandle` with `recv() -> Option<AudioChunkPair>`, and `SipClient::subscribe_audio(call_id, format, capacity, mode) -> Result<AudioTapHandle, SipError>` with the §22.1 backpressure policy.

### Purpose
The audio tap is the crate's hook for monitoring, recording, and quality analysis of a call's audio. It exposes a call's paired IN/OUT audio (`AudioChunkPair`) to application code without coupling that code to the PJSIP conference bridge. Without it, the only way to observe call audio is inside the backend, which defeats the crate's safe-Rust facade.

### Motivation
The source ticket P5-1 left this as a stub because the call model and audio pipeline were not yet final. The call model (`CallId`, `call_state()`), the audio format model (`AudioFormat`/`AudioChunkPair`), and `AsyncAudioSource` (N0032) now exist, so the API and its backpressure policy can be defined and tested. The `audio_tap` example (P9-1) is gated behind `spec-examples` because it awaits this API — resolving the stub un-gates it.

### Constraints
The backend media path (PJSIP `conf_port` → `AudioChunkPair`) is NOT yet available (N0033/N0050), so the policy and handle must be defined and fully tested against a synthetic producer over the same `tokio::sync::mpsc` the handle wraps. `capacity == 0` is invalid (a zero-capacity channel cannot carry a pair). Realtime mode must never block the audio pipeline; Lossless mode is best-effort integrity and may induce jitter (RFC §22.1).

## Acceptance Criteria

- **[Happy path] — AudioTapMode is defined with exactly the `Realtime` and `Lossless` variants and `AudioTapMode::default() == Realtime` (RFC §22.1); `AudioTapHandle` wraps a `tokio::sync::mpsc::Receiver<AudioChunkPair>` and `recv()` returns `Some(pair)` when a frame is buffered and `None` after the producer closes; `SipClient::subscribe_audio(call_id, format, capacity, mode) -> Result<AudioTapHandle, SipError>` exists with the RFC §22 signature; Realtime overflow keeps the newest pair and reports the dropped-oldest without blocking the pipeline; Lossless overflow backpressures the producer and drops nothing.**
- **[Error case] — subscribe_audio with `capacity == 0` returns `Err(SipError::new(SipErrorKind::InvalidConfig, ...))` and creates no handle; subscribe_audio for an unknown `call_id` returns `Err(SipError::not_found(...))` (`SipErrorKind::CallNotFound`) and creates no handle; `recv()` and `push()` never panic.**
- **[Edge case] — `MIN_TAP_CAPACITY == 1` is the smallest valid capacity; a capacity-1 Realtime tap that overflows keeps the newest pair and reports the evicted oldest (`Some(dropped)`); a capacity-1 Lossless tap backpressures (no drop) even under a sustained producer; the handle is single-consumer (`Send`, not `Clone`).**

## Invariants

- 【Normal establishment】`subscribe_audio` returns a handle only after validation passes: `capacity >= MIN_TAP_CAPACITY (1)` and the `CallId` exists in the reactor call registry (`call_state()`, `src/client.rs:205`); otherwise `Err(SipError)`.
- 【Invariant on error】`subscribe_audio` never panics: `capacity == 0` → `SipErrorKind::InvalidConfig`; unknown call → `SipErrorKind::CallNotFound` (via `SipError::not_found`); a failed call creates no handle.
- 【Internal state invariant】each tap has exactly one consumer — `AudioTapHandle` is `Send` and not `Clone`; the producer side (`AudioTapSender`) is the only writer; `recv()` returns `None` exactly when the producer closes.
- 【Boundary invariant】`MIN_TAP_CAPACITY == 1`; Realtime overflow keeps the newest frame and reports the evicted oldest (`Some(dropped)`); Lossless overflow never evicts and backpressures the producer.
