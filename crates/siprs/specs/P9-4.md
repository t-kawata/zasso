# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Implement full SIP message parsing per the Raw SIP Message Specification (RFC §16, NODE_ID=N0024): a `RawSipMessage` struct carrying `direction`, `transport`, `start_line`, `headers`, `body`, `text`, `content_length`, `remote_addr`, `local_addr` — with header/SDP extraction accessors and `Authorization`/`Proxy-Authorization` redaction — so the `raw_sip` event bus delivers typed, parsed messages.

### Purpose
P5-1 left `RawSipMessage` as a minimal wrapper (`pub struct RawSipMessage { pub data: Vec<u8> }`) in `src/api/event_model_payload_bus.rs` and an empty shell (`pub struct Model {}`) in `src/model/raw_sip_message_spec.rs` because the full raw SIP message spec (N0024) was deferred. This ticket resolves the two `[::STUB::] P9-4` markers by implementing the parser and the RFC §16 struct shape, so downstream consumers (logging, debugging, untrusted forwarding) get structured access instead of raw bytes.

### Motivation
The PJSIP callback bridge (P5-3/P8-21) needs a total, typed parser to feed the `raw_sip` broadcast bus; the event model (N0018) already declares `raw_sip: Option<broadcast::Sender<RawSipMessage>>` and `subscribe_raw_sip()`/`publish_raw_sip()`. Without this ticket the raw_sip bus can only ship untyped byte buffers, defeating the event model's typed-contract design.

### Constraints
- The parser must be total (no `panic!`, no `unwrap` on input bytes) and return `Err(SipError)` for malformed input; use `SipError::invalid_argument` (kind `InvalidArgument`, non-retryable) — `SipErrorKind` has a fixed 24-variant invariant, so no new variant may be added.
- The struct must match RFC §16 exactly; the public `data` field is removed — bytes are reachable only via `text()` and the parsed fields.
- Redaction must follow the immutable pattern (return a new message) and cover both `Authorization` and `Proxy-Authorization` when enabled.
- No new dependency crates; reuse existing `TransportKind` and `RawSipEventConfig`.

## Acceptance Criteria

- **[Happy path] —** `RawSipMessage` exposes the RFC §16 fields (direction, transport, start_line, headers: Vec<(String, String)>, body: Option<Vec<u8>>, text, content_length: usize, remote_addr/local_addr: Option<SocketAddr>); `parse(bytes)` parses request/response start line → `start_line` + `direction`, header block → `headers`, CRLF-CRLF body → `body` (Some when present), `content_length` derived from the actual body; accessors `start_line()`, `header(name)` (case-insensitive), `headers()`, `body()`, `text()`, `content_length()`, `direction()`, `transport()`, `remote_addr()`, `local_addr()` work; `redact_authorization()` replaces password values in `Authorization` and `Proxy-Authorization` when enabled and returns a new message (immutable pattern).
- **[Error case] —** Parsing a non-SIP/malformed byte sequence (empty input, non-method/status start line, status line missing a status code) returns `Err(SipError)` with `kind == InvalidArgument` instead of panicking.
- **[Edge case] —** Message with no body → `body: None`, `content_length: 0`; empty header block → `headers: vec![]`; `Content-Length` absent but body present → `content_length` derived from actual body bytes; `max_body_bytes` truncation keeps the content-length invariant; `include_bodies = false` drops the body; LF-only separators accepted as best-effort.

## Invariants

- [Normal condition] C025: RawSipMessage exposes exactly the 9 RFC §16 fields (direction, transport, start_line, headers, body, text, content_length, remote_addr, local_addr); `parse` is total — every input yields `Ok(RawSipMessage)` or `Err(SipError)`, never a panic; `content_length == body.map(|b| b.len()).unwrap_or(0)`.
- [Error invariant] On parse failure the function returns `Err(SipError::invalid_argument(..))` with no side effects and no partially-constructed message escaping; the input bytes are never mutated; callers (bridge) must surface the Err rather than swallow it.
- [Internal state invariant] `headers` is `Vec<(String, String)>` preserving original header names verbatim (matching is case-insensitive only in `header(name)`); `text` always reflects the complete message; redaction touches only redactable header values and rebuilds `text`, leaving `body`/`direction`/`transport`/addresses unchanged.
- [Boundary invariant] body `None` ⇒ `content_length == 0`; empty header block ⇒ `headers == vec![]`; truncation to `max_body_bytes` keeps `content_length == body.len()`; `Content-Length` header mismatches are overridden by the actual body length.
