# M2-1: run.sh — サーバー・プロキシ起動スクリプト

## Summary

2 つのプロセス（MTPLX 推論サーバー、Claude Code Proxy）を正しい順序で起動し、各プロセスの readiness 確認後にユーザーにエンドポイント情報を表示する。Ctrl+C で両プロセスをグレースフルに終了する。プロセス管理はバックグラウンドジョブ + `trap` で実現する。

## Background

Claude Code をローカルの LLM（Qwen3.6-27B）で動作させるには、MTPLX 推論サーバーと OpenAI→Anthropic API 変換 Proxy の 2 プロセスが必要である。手動起動では以下の問題がある：

- 起動順序の誤り（Proxy を先に起動してしまう）
- ポート占有の検出漏れ
- モデル不在時の起動試行
- Ctrl+C での片方プロセスの取り残し

本スクリプトはこれらの課題を解決し、ワンコマンドで安全に 2 プロセスを起動する。

**決定事項 Q3（ポート空き確認＋エラー表示）**、**Q5（バックグラウンドジョブ + trap で一括終了）** を実装する。

## Scope

- `run.sh` ファイルの新規作成
- `#!/usr/bin/env bash` + `set -euo pipefail`
- `SCRIPT_DIR` / `PROJECT_ROOT` の解決（`$(cd "$(dirname "$0")" && pwd)`）
- `.env` 読込（`set -a; source .env; set +a`）— 不在時はエラー終了＋`setup.sh` 実行促し
- `MTPLX_PORT` / `PROXY_PORT` / `MODEL_DIR` のデフォルト解決（環境変数優先）
- `cleanup` 関数 — `kill $PID_MTPLX $PID_PROXY` + `wait`、`trap cleanup SIGINT SIGTERM EXIT`
- `check_port` 関数 — `lsof -i :$port -P -n` で LISTEN 確認、占有時エラー＋ポート変更提案
- モデルディレクトリ確認 — `config.json` の存在確認、不在時 `setup.sh` 実行促し
- `detect_serve_cmd` 関数 — `mtplx serve` / `lightning-mlx serve` の動的検出（RFC §4 完全実装）
- MTPLX 起動（background）+ PID 記録: `uv run $SERVE_CMD --model "$ABS_MODEL_DIR" --port "$MTPLX_PORT" --max-tokens 32768 --temp 0.6 --top-p 0.95 &`
- MTPLX Readiness ポーリング（最大 120 秒、2 秒間隔、`curl -sf http://127.0.0.1:${MTPLX_PORT}/v1/models`）
- Proxy 起動（background）+ PID 記録: `cd claude-code-proxy && uv run uvicorn server:app --host 127.0.0.1 --port "$PROXY_PORT" &`
- Proxy Readiness ポーリング（最大 30 秒、1 秒間隔）
- 起動完了表示（OpenAI / Anthropic / Claude Code 各エンドポイント + テストコマンド）
- `wait`（フォアグラウンド待機）でプロセス終了を待機
- 実行権限付与（`chmod +x run.sh`）
- テスト: `tests/test-run.sh` の作成（test-setup.sh と同一パターン: モックベースのシェルテスト）

### 実装上の注意点

1. **source common.sh 不使用の判断**: RFC コードは `echo` を直接使用し、common.sh のカラー関数（`info`/`warn`/`error`/`die`）を使用しない。推論: `.env` 不在時でもエラーメッセージを表示する必要があり、その前に common.sh が source できないケースを考慮して、あえて依存を排除している。本実装でもこの判断を継続する。
2. **`set -euo pipefail` と `kill`**: `cleanup` 関数内で `kill "$PID"` が失敗してもスクリプト全体が終了しないよう、`|| true` または `2>/dev/null` でハンドリングする必要がある（RFC コードは `2>/dev/null` で対応済み）。
3. **`detect_serve_cmd` の呼出し**: `$(detect_serve_cmd)` で実行し、結果を `SERVE_CMD` に格納。`detect_serve_cmd` 内で `exit 1` するケースがあるため、関数内でエラー終了する設計。
4. **シグナルハンドラの二重実行防止**: `trap cleanup EXIT` と `trap cleanup SIGINT SIGTERM` を設定すると、Ctrl+C 時に `SIGINT → cleanup → EXIT → cleanup` と二重実行される可能性がある。RFC コードは `kill` に `2>/dev/null` を付けているため二重実行は無害だが、フラグ管理の有無を検討する。

## Test Plan

### ユニットテスト計画

テストファイル: `tests/test-run.sh`
フレームワーク: test-setup.sh と同一のシェルベース単体テスト（record 関数によるカウンタ管理）

**基本方針: モック（外部コマンドの代替バイナリを仕立てる方法）は原則禁止。**
代わりに以下の技法でテスト可能な範囲を最大化する：

| 技法 | 説明 | 適用対象 |
|------|------|---------|
| **PATH 操作** | テスト用のディレクトリを `PATH` 先頭に挿入し、特定コマンドの存在有無や出力を制御する。ただしこれは「モック」ではなく「実行環境の構成」であり、本物のコマンドを隠蔽する最小限の範囲に留める | `detect_serve_cmd` のコマンド検出/不在テスト |
| **関数の分離テスト** | 副作用のある呼び出し（kill, wait）を含む関数は、関数定義のみを切り出して source し、テストコードから呼び出す。kill/wait はシェル組み込みであり、実際に実行しても問題ない（PID が実在しなければ無害） | `cleanup`, `check_port`（ロジックのみ） |
| **ファイルシステム操作** | .env の有無、モデルディレクトリの有無を一時ディレクトリで制御する | `.env` 読込、モデル確認 |
| **タイムアウト短縮** | `MTPLX_TIMEOUT`, `PROXY_TIMEOUT` を環境変数で短縮し、タイムアウトテストを実時間で完了可能にする | readiness ポーリングのタイムアウトテスト |

**「モック」と「PATH 操作による制御」の境界:**

- ❌ 禁止: `lsof` の代替バイナリを置き、LISTEN 出力を偽装する
- ✅ 許可: `check_port` 関数を単体でテストする（lsof が実際に LISTEN を返す状況はテスト実行者の環境に委ね、関数のロジック（エラーメッセージ生成、exit 1）のみ検証する） — ただし **「ポートが占有されているケース」のテストは、結合テストや E2E に回す**
- ❌ 禁止: `mtplx` の代替バイナリを置き、`--help` の出力を偽装する
- ✅ 許可: `PATH` から `mtplx` を外した状態で `detect_serve_cmd` を実行し、コマンド不在時のエラーパスをテストする
- ❌ 禁止: `kill`/`wait` の代替スクリプトを置く — これらはシェル組み込みであり、実 PID がなければ無害
- ❌ 禁止: `curl` の代替バイナリを置く — readiness ポーリングのタイムアウトテストは `MTPLX_TIMEOUT=1` に短縮して実行し、`curl` が（当然ながら）応答しないことでタイムアウトを検証する

### ユニットテスト不可能な項目（例外）

真にユニットテスト不可能な項目のみを、理由を添えて列挙する：

- **理由1: 実際のポート占有検出**: `check_port` が実際にポート占有状態を検出できるかの検証には、実際にポートを LISTEN しているプロセスが必要。`lsof` 自体は macOS に標準搭載されており「コマンドの不在」が理由ではない。しかし、テスト実行時に特定ポートを占有するプロセスを用意することは CI 環境等で困難。結合テストまたは E2E テストに委ねる。
  - 代替: `check_port` の「空きポート通過」ケースはユニットテストでカバー。占有検出のロジック（エラーメッセージ生成、exit 1）は、関数の構造（`lsof | grep -q LISTEN` → 該当あり → exit 1）が自明であるため、コードレビューで担保する。

- **理由2: MTPLX サーバー + モデルロードの実際の起動**: `uv run mtplx serve --model ...` が実際にサーバープロセスを起動し、`/v1/models` が 200 を返すことを確認するには、27B のモデルファイルと MTPLX 推論エンジンが必要。これは E2E テスト範囲とする。
  - 代替: readiness ポーリングの**タイムアウト**は `MTPLX_TIMEOUT=1` の短縮設定でテスト可能（curl 先のサーバーが存在しないためタイムアウトする）。

- **理由3: Ctrl+C シグナルハンドリング**: スクリプトに SIGINT を送信し、`trap cleanup` が発動して両プロセスが kill されることを確認するには、実際の子プロセスを起動した上でシグナルを送る必要がある。これは E2E テスト範囲とする。
  - 代替: `cleanup` 関数のロジック（kill + wait + フラグによる二重実行防止）は関数単位のユニットテストでカバーする。

### E2E テスト計画（統合テスト時）

- `setup.sh` 完了状態を前提に `./run.sh` を実行
- プロセス起動確認: `lsof -i :$MTPLX_PORT` / `lsof -i :$PROXY_PORT`
- エンドポイント応答確認: `curl http://127.0.0.1:$MTPLX_PORT/v1/models`

## Boy Scout Rule — 翻訳可能性計画

本チケットで新規作成する `run.sh` は新規ファイルのため、既存コードの翻訳不可能部分の修正は発生しない。以下の方針で翻訳可能なコードを最初から書く：

1. **関数名は動詞句**: `check_port` / `detect_serve_cmd` / `cleanup` — 関数呼び出しの並びが処理の流れを物語る
2. **変数名はドメイン概念**: `PID_MTPLX` / `PID_PROXY` / `ABS_MODEL_DIR` / `SERVE_CMD` — 役割が一目でわかる名前
3. **一関数一責務**:
   - `check_port`: ポート空き確認のみ（エラーメッセージも内部で完結）
   - `detect_serve_cmd`: サーバーコマンド検出のみ
   - `cleanup`: プロセス終了 + 後片付けのみ（kill + wait）
4. **ハードコード値は全て名前付き定数**: `TIMEOUT=120` / `TIMEOUT=30` / スリープ間隔も `2` / `1` として明示
5. **マジックナンバーの排除**: ポート番号は `MTPLX_PORT` / `PROXY_PORT` で環境変数経由、起動パラメータ（`--max-tokens 32768` 等）もコメント付きで明示
6. **エラー握りつぶし禁止**: `kill` のエラーは `2>/dev/null` で抑制する根拠をコメントで説明。RFC コードの設計判断を尊重する
7. **コメントで「なぜ」を補完**: 「何を」は関数名で表現し、「なぜこうしているか」（例: trap の二重実行防止理由）のみコメントする

### 共通レイヤーとの関係

`common.sh` の `info`/`warn`/`error`/`die` 関数を使用せず、`echo` を直接使う判断（RFC 由来）については以下の理由で追認する：

- `.env` 不在時にもエラーメッセージを表示する必要があるが、`source common.sh` は `SCRIPT_DIR` ／ `PROJECT_ROOT` に依存しないため技術的には可能
- しかし、run.sh は独立した起動スクリプトとしての責務が明確であり、`source common.sh` を前提とすると common.sh の移動・変更に引きずられる
- 既存の setup.sh が `source common.sh` を使用しているのに対し、run.sh は runtime スクリプト（setup.sh は setup スクリプト）という違いを明確にするために、あえて依存を最小化する設計判断は妥当
