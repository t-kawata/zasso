# M2: 第一級規則（スタブマーカー絶対義務）の明記と甘い記述の修正

## Summary

以下の 5 ファイルの全てに「不完全な実装には例外なく `[::STUB::]` マーカーを付けなければならない。これは死んでも守るべき絶対的法規である」という第一級規則を明記する。併せて、当該規則が甘く認識される可能性のある既存記述を洗い出し、書き換える。

**対象ファイル**:
1. `CLAUDE.md`（プロジェクトルート）
2. `.claude/commands/make-ticket.md`
3. `.claude/commands/plan-ticket.md`
4. `.claude/commands/start-ticket.md`
5. `.claude/commands/review-ticket.md`

## Background

現在の CLAUDE.md には `[::STUB::]` マーカーに関する規定が「スタブポリシー」として存在するが、以下の問題がある：

- 「スタブは原則として極力多用しない」とあり、スタブ自体を許可するかのようなニュアンスがある
- 「一時的な仮実装」であることが明記されているが、不完全な実装全般にマーカーが必須であることが強調されていない
- 「第一級規則」「絶対的法規」といった強い強制力の表現がない
- コマンドファイル（make-ticket.md 等）にはスタブポリシーの記載が一切なく、各コマンドのワークフロー内でスタブを認識・解決するプロセスが弱い

本チケットではこれらを修正し、不完全な実装には名称を問わず全てにマーカーが必須であり、違反は「犯罪」として Malfeasance.json に記録されることを明確にする。

### 修正方針

1. **CLAUDE.md**: 「スタブポリシー」セクションを全面的に書き換え、「不完全実装ゼロ tolerance — [::STUB::] マーカー絶対義務」として再定義する。既存の緩い表現を削除または強化する。
2. **4 コマンドファイル**: それぞれのワークフロー説明内に、第一級規則の明記と Malfeasance.json との連携を追加する。
3. **甘い記述の洗い出し**: 「スタブは原則として極力多用しない」「真に必要な場合に限定する」「解決条件を明記する」など、マーカー未付与を許容するように読める表現を特定し修正する。

## 現状分析

### CLAUDE.md の該当記述（スタブポリシー）

```
### [::STUB::] マーカー

未実装の箇所を仮置き（スタブ）する場合、コメント先頭に `[::STUB::]` を付与し、後で一括検出可能にする：

```rust
// [::STUB::] M3-1 で registry.rs::resolve() に置き換える
fn resolve_stub() -> Result<()> { Ok(()) }
```

### ルール

1. **スタブは原則として極力多用しない** — スタブの仮置きは真に必要な場合に限定する
2. **解決条件を明記する** — スタブを実装する場合、どのチケットのどこでどのように解決されるかをコメントに明記し、**不確実性がない場合のみ**許容される
3. **全フェーズでスタブをチェックする** — `make/plan/start/review` のいずれのタイミングでも `[::STUB::]` を発見したら、当該スタブを現時点で解決可能か判定する。解決可能なら実装し、不可なら計画や設計に反映する
4. **未マークのスタブを発見したら直ちにマーカーを追加する** — コードの内容から明らかにスタブ（仮実装、未実装の `return`、`panic!`、`todo!`、空実装等）と判断されるにも関わらず `[::STUB::]` が付与されていない場合、**その場でマーカーを追加する**。解決先チケットが不明な場合は `[::STUB::] 要解決: <判明している限りの情報>` の形式で暫定マーカーを付与する
5. **review では全スタブを検証する** — `find-all-stubs.js` で全スタブを抽出し、解決可能なものは解決し、残るものは理由をユーザーに報告する
```

### 問題点

| # | 問題 | 該当箇所 | 修正方針 |
|---|------|---------|---------|
| 1 | 「スタブは原則として極力多用しない」→ スタブの存在を許容しているように読める | ルール1 | 「スタブは禁止。やむを得ない場合のみ [::STUB::] マーカー必須」に変更 |
| 2 | 「不確実性がない場合のみ許容される」→ 許容条件を緩くしている | ルール2 | 削除し、不確実性がなくてもマーカーは必須であることを明記 |
| 3 | モック実装や不完全な実装全般にマーカーが必須という記述がない | 全体 | 定義を拡張し「不完全な実装には名称を問わず全てマーカー必須」に |
| 4 | 「第一級規則」「絶対的法規」という強制力表現がない | 全体 | 最上位に絶対的規則として独立セクションを追加 |
| 5 | Malfeasance.json との連携がない | 全体 | 違反は犯罪として記録される旨を明記 |
| 6 | コマンドファイルに全くスタブポリシーの記載がない | make/plan/start/review | 各ファイルに第一級規則を追記 |
| 7 | 「コードの内容から明らかにスタブと判断される」の基準が不明 | ルール4 | `todo!()`, `unimplemented!()`, `panic!()` など具体的パターンを明示 |

## 修正仕様

### 1. CLAUDE.md への追加セクション（最上位、critical として独立）

既存の「スタブポリシー」セクションと置き換える。新セクションでは以下を明記：

- **絶対的法規の宣言**: 「不完全な実装には全て [::STUB::] マーカーを付与しなければならない。これは例外なく適用される第一級規則であり、死守すべき絶対的法規である。」
- **対象の明確化**: スタブ、モック、トークン実装、仮実装、プレースホルダー — 名称を問わず、不完全な状態のコード全てが対象
- **違反の結果**: 未マーカーの不完全実装は「犯罪」であり、Malfeasance.json に記録される
- **具体的な犯罪パターン**: `todo!()`, `unimplemented!()`, `panic!()`, 空の関数本体、未実装の `return Ok(())`, コメントアウトされた実装、`TODO`/`FIXME`/`HACK`/`XXX` コメント
- **例外の不存在**: テストコード、サンプルコード、プロトタイプも例外ではない

### 2. 各コマンドファイルへの追記

各コマンドファイルの最上部付近に以下を追加：

> **第一級規則 — [::STUB::] マーカー絶対義務**:
> 不完全な実装（スタブ・モック・仮実装・プレースホルダー等、名称を問わず）には全て `[::STUB::]` マーカーを付与しなければならない。これは死守すべき絶対的法規であり、違反は「犯罪」として Malfeasance.json に記録される。
>
> 本コマンドの全フェーズにおいて、Malfeasance.json を読み取り未解決の犯罪がないことを確認すること。違反を発見した場合は直ちに解決するか、その場でマーカーを追加・記録する。

### 3. 甘い記述の修正箇所（CLAUDE.md スタブポリシー）

| 修正前 | 修正後 |
|--------|--------|
| 「スタブは原則として極力多用しない — スタブの仮置きは真に必要な場合に限定する」 | 削除（スタブの使用許可自体を否定）→ **スタブ実装の禁止** に変更 |
| 「解決条件を明記する — ...不確実性がない場合のみ許容される」 | 削除（許容条件の緩和を防止）→ マーカーは不確実性の有無に関わらず必須と明記 |
| マーカーに関する記述のみで、モック・仮実装等への言及がない | 対象を「不完全な実装（スタブ・モック・仮実装・プレースホルダー等）」に拡張 |
| 「未マーカーのスタブを発見したら直ちにマーカーを追加」は保持するが弱い | 強化: 発見したら**その場で必ず**マーカー追加 + Malfeasance.json に犯罪記録 |
