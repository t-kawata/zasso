### 不足しているテスト（AC#3/4/5/6）

#### AC#3 — Translate Non-Stream 応答形式検証

`translate_non_stream_proxies_via_openai_wire`（L532）は以下を確認していない：
- `body["type"] == "message"`
- `body["content"][0]["type"] == "text"`
- `body["id"].starts_with("msg_")`
- `body["role"] == "assistant"`

mock upstream は OpenAI Chat Completions 形式の応答を返しているが、テストはステータスコード範囲の確認のみ。

**RFC02 §8.1 の要件**: 応答 body の全 Anthropic 互換フィールドを検証する。provider名は"translate"モード用として `transparent: false` + `openai_wire_api: Some(OpenAiWireApi::Auto)` で設定する必要がある。

#### AC#4 — Translate Stream テスト

translate stream の統合テストが存在しない。現状の stream テストは `transparent_stream_proxies_sse_from_upstream`（L414）のみ。

src/provider/translate.rs には `transform_chunk` のユニットテストが存在する（L492-L853）が、リクエスト→変換→応答の End-to-End パイプラインは未検証。

**RFC02 §8.2 の要件**:
- Mock SSE upstream が複数チャンク（`data: {delta...}`）→ `[DONE]` を返す
- Content-Type: text/event-stream が維持される
- ストリーム内容に `content_block_delta` が含まれる

#### AC#5 — Non-Stream Key Failover テスト

`non_stream_key_failover_handles_error`（L258）は：
- mock upstream がない（upstream 不在でエラーになるだけ）
- failover 発火を確認していない
- AtomicUsize で attempt 回数を追跡していない

**RFC02 §8.3 の要件**:
- `attempt: AtomicUsize` で 1回目 503、2回目成功を制御
- 2つの api_keys を設定
- 最終的に 200 OK
- attempt == 2 で failover 発火を確認

#### AC#6 — Stream No-Failover テスト

`stream_no_failover_returns_error`（L288）は：
- mock upstream がない
- 2つの api_keys を設定していない（failover 非発火を確認できない）
- サーバーエラー（5xx）かどうか確認していない（4xx でも通る）

**RFC02 §8.4 の要件**:
- Mock upstream が常に 503 を返す
- 2つの api_keys を設定
- サーバーエラーステータス（5xx）を確認

## Test Plan

### ユニットテスト計画

本チケットのテストはすべて統合テスト（`tests/mock_server.rs`）として追加するため、単体のユニットテストは不要。

理由：AC#3/AC#4 は HTTP リクエスト→ルーティング→変換→レスポンス の End-to-End 結合テストであり、axum::test サーバーと mock upstream が必要。AC#5/AC#6 は KeyScheduler + ProviderClient の結合テストであり、同様に実 TCP サーバーが必要。

ただし、`transform_chunk()` の単体テストは既に `src/provider/translate.rs` に十分なカバレッジ（全ブランチ網羅）があるため追加不要。

### ユニットテスト不可能な項目（例外）

- AC#3/AC#4: translate モードの結合テスト — HTTP リクエストパイプライン全層の結合が必要
- AC#5/AC#6: failover 結合テスト — KeyScheduler + HTTP クライアント + 実 TCP サーバーの結合が必要

#### 2. `translate_stream_proxies_via_openai_wire` — AC#4

```rust
#[tokio::test]
async fn translate_stream_proxies_via_openai_wire() {
    // Arrange: Mock SSE upstream（複数チャンク → DONE）
    let upstream_app = axum::Router::new().route(
        "/v1/chat/completions",
        axum::routing::post(|| async {
            let chunks = vec![
                "data: {\"choices\":[{\"delta\":{\"content\":\"Hello\"}}]}\n\n",
                "data: {\"choices\":[{\"delta\":{\"content\":\" world\"}}]}\n\n",
                "data: [DONE]\n\n",
            ];
            let stream = futures::stream::iter(
                chunks.into_iter().map(|c| Ok::<_, std::convert::Infallible>(Bytes::from(c)))
            );
            Response::builder()
                .header("Content-Type", "text/event-stream")
                .body(Body::from_stream(stream))
                .unwrap()
        }),
    );
    let base_url = start_mock_upstream(upstream_app).await;

    // translate モードの ProviderConfig
    let mut config = AppConfig::default();
    config.global.port = test_port();
    config.providers.insert(
        "translate".to_string(),
        ProviderConfig { /* AC#3 と同様 */ },
    );

    let server = build_proxy_test_server(config).await;

    // Act
    let resp = server
        .post("/v1/messages")
        .json(&serde_json::json!({
            "model": "translate/model",
            "messages": [{"role": "user", "content": "Hello"}],
            "stream": true,
            "max_tokens": 100,
        }))
        .await;

    // Assert — SSE ストリーム検証
    assert_eq!(resp.status_code(), 200);
    let content_type = resp.headers().get("content-type").unwrap();
    assert!(content_type.to_str().unwrap().contains("text/event-stream"));

    let body = resp.text();
    assert!(body.contains("content_block_delta"));
    assert!(body.contains("text"));
}
```

## Boy Scout Rule — 翻訳可能性計画

このチケットで新規追加するテストコードにおいて：

- **関数名は動詞句**: `translate_non_stream_response_format`、`non_stream_key_failover_recovers_from_503` 等、何を検証するか関数名から明確に読み取れる
- **変数名はドメイン概念**: `attempt`, `upstream_app`, `base_url` 等、処理内容を反映
- **一関数一責務**: 各テストは単一の AC 検証のみに責務を限定
- **ハードコード値は名前付き定数**: `MOCK_SERVER_BASE_PORT` を既存の定数として参照
- **エラー握りつぶし禁止**: テスト関数内でも `unwrap()` / `expect()` は避け、`?` で伝播するよう `async fn ... -> Result<()>` を検討（ただし既存テストのスタイルに合わせる）

既存コードは変更しない（新規テストのみ追加のため）。
