# コード品質改善（n#13〜n#16）

**参照設計書:** `crates/anthropx/RFC02.md §9 コード品質改善`
**依存・関連チケットID:** 先行実装必須なし（独立して実施可能）。M6-1 と並行可能。

## Summary

4件の Nit 項目（n#13〜n#16）を一括対応。いずれも機能的動作は現状維持したまま、保守性と可読性を向上させる。

## Background

RFC02 §9 で指摘された以下のコード品質課題を解決する:

- **n#13**: `IntoResponse` 内のステータスコードマッピングが `status_code()` と重複しており、片方の修正漏れがバグの原因となる
- **n#14**: ApiFormat 中間型は llm-bridge-core 移行完了までの暫定状態。本チケットでは変更しない（現状維持）
- **n#15**: `try_acquire_owned()` 高速パスの設計意図（current_queue 非増加の正当性）がコメントから読み取れない
- **n#16**: `record_request()` の呼び出しが複数箇所に散逸すると二重計上のリスクがある。現状は単一箇所だが、契約を明示するコメントがない

## Scope

## Investigation

### n#13: `status_code()` と `IntoResponse` の統合

**現状:**

1. **`status_code()`**: 既存。`src/config/mod.rs:416-429` に実装済み。

```rust
pub fn status_code(&self) -> u16 {
    match self {
        ProxyError::UnknownProvider(_) | ProxyError::InvalidModel(_)
        | ProxyError::MissingField(_) | ProxyError::TransformLossy(_) => 400,
        ProxyError::Unauthorized => 401,
        ProxyError::Forbidden => 403,
        ProxyError::QueueFull => 429,
        ProxyError::Upstream(_) | ProxyError::UpstreamError(_) => 502,
        ProxyError::Timeout => 504,
        ProxyError::Internal(_) | ProxyError::Config(_) => 500,
    }
}
```

2. **`error_type()`**: **未実装。** 現在の `IntoResponse`（`src/http/errors.rs:32-80`）にインラインで error_type 文字列がベタ書きされている：

```rust
let (status, error_type, message) = match &self {
    ProxyError::UnknownProvider(_) | ProxyError::InvalidModel(_)
    | ProxyError::MissingField(_) | ProxyError::TransformLossy(_) => (
        StatusCode::BAD_REQUEST, "invalid_request_error", self.to_string(),
    ),
    ProxyError::Unauthorized => (
        StatusCode::UNAUTHORIZED, "authentication_error", self.to_string(),
    ),
    // ... 全 variant で status と error_type が重複
};
```

3. **`IntoResponse` が `self.status_code()` を呼び出していない**: ステータスコードと error_type の両方を `IntoResponse` 内で独自にマッチしており、`status_code()` との二重保守状態。

4. **メッセージ生成**: 大半の variant は `self.to_string()` を使用している。`QueueFull` / `Timeout` / `UpstreamError` のみハードコードまたは `msg.clone()` を使用しているが、いずれも `self.to_string()` と同じ値になる（thiserror Display と一致することを確認済み）。

### n#14: ApiFormat 中間型

**現状:** `src/routing/mod.rs:24` に `[::STUB::]` コメントが存在。本チケットでは変更しない。

```rust
/// [::STUB::] M5-2 で llm_bridge_core::model::ApiFormat に完全置き換え予定。
#[derive(Debug, Clone, PartialEq)]
pub enum ApiFormat { ... }
```

### n#15: `ConcurrencyLimiter::acquire()` の try_acquire 高速パス

**現状:** `src/provider/limiter.rs:51-76` に実装済み。コメントは以下の状態:

- 「まず非ブロッキング acquire を試行（セマフォに空きがある場合の高速パス）」 — 意図は説明しているが、**try_acquire 成功時に current_queue を増加させない理由**（= Semaphore の permits のみで in-flight 管理が完結するという設計判断）が明示されていない。
- try_acquire と current_queue 操作の関係についての記述がない。

### n#16: `record_request` 二重計上リスク

**現状:**
- `record_request()` の呼び出しは `src/http/routes.rs:175,178` の `handle_messages` 後処理ブロックにのみ存在する。
- `src/provider/transparent.rs` および `src/provider/translate.rs` には `record_request()` の呼び出しは**存在しない**（grep で確認済み）。
- 現時点では二重計上のリスクは顕在化していないが、今後の改修で provider ハンドラ内に metrics 出力が追加されるリスクを防ぐ契約コメントがない。

## Boy Scout Rule — 翻訳可能性計画

本チケットで触るコードに対して、以下の改善を計画する：

1. **n#13 — `IntoResponse` の翻訳可能性向上**: 現在の `IntoResponse` は 50 行超の巨大な `match` で status + error_type の両方を抱えており、「何をしているか」が一読で把握しにくい。`self.status_code()` と `self.error_type()` の呼び出しに置き換えることで、`IntoResponse` の責務を「ステータスコードとエラータイプを取得し、JSON ボディを組み立てる」という単一の散文に還元する。

2. **n#15 — コメントで設計判断を語る**: try_acquire 高速パスの「なぜ current_queue を増加させないのか」という設計判断をコメントで明示する。これは「何を」（コードが語る）と「なぜ」（コメントが語る）の役割分担に従う。

3. **n#16 — 契約の明示**: `record_request()` の単一呼び出し契約をコメントで明示する。これにより、将来の改修者が誤って provider ハンドラ内に metrics 出力を追加することを防ぐ。
