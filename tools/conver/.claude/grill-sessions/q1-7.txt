Q1: contracts 配列の構造 — 各契約に pre/post/invariants を持たせるか？

背景: targetStubs/targetCrimes の各エントリは複数の契約と紐づく必要がある。前回のあなたの指摘で contractIds が別配列 + pre/post/invariants がトップレベル別配列の構造は破綻すると修正した。しかし、契約情報の保持方法には複数の選択肢がある。特に instance-specific な記述と契約原文の関係が問題。契約原文と異なる場合のみ記述できれば理想的だが、全文常に記述必須だと二重保守が発生する。一方、IDのみだと「この targetStub が契約 C001 をどういう観点で参照しているか」が機械的に判断できない。

選択肢:
- A) contracts 配列の各要素に { id, preconditions, postconditions, invariants } を持たせ、契約原文と同一なら省略可（自動補完）。差分のみ記述。
- B) contracts は id の配列のみ。pre/post/invariants は targetStub トップレベルに持つ。
- C) contracts は id の配列のみ。pre/post/invariants は一切持たない。契約原文のみが信頼される情報源。
- D) contracts 各要素に pre/post/invariants を常に全文記述必須。省略不可。

推奨: A。instance-specific な差分のみ書けばよく、契約原文と同一の場合は自動補完に任せられる。

Q2: 各フェーズの検証スコープ — ticket-scoped と directory-scoped の分割

背景: 全5フェーズの各 validate スクリプトがどの範囲をスキャンするか。全フェーズでディレクトリ全体をスキャンすると重複が多く、速度も遅い。一方、ticket-scoped のみだと「このディレクトリに別のチケットの未解決STUBが残っている」を見逃す。また、既存の resolve-ticket.md は directory-scoped の性質を持つ。どのフェーズがどの範囲を担当するかを確定する必要がある。

選択肢:
- A) make/plan/start/review は ticket-scoped（自分の targetStubs/targetCrimes のみ検証）。resolve のみ directory-scoped（全STUB/全犯罪をスキャン）。resolve が最終的な網羅性保証を担当。
- B) 全フェーズ directory-scoped。常にディレクトリ全体をスキャンする。
- C) make のみ directory-scoped で全量棚卸しを行い、以降は ticket-scoped。make で全量を Tickets.json に記録する。

推奨: A。resolve が directory-scoped の最終ゲートとして機能し、上流4フェーズは範囲限定で高速に保てる。

Q3: resolve フェーズでの新規 STUB 作成禁止の徹底

背景: 現在の resolve-ticket.md は Step 2 で「警告が出たら #[allow] で抑制し STUB を追加」することを許可している。これは「最後の砦」で新しい STUB を生産する矛盾を生む。実際、今回の139件の問題は各フェーズで「確認しろ」と言いながら新規 STUB 追加を止めなかった結果とも言える。一方、cargo check が通らないと resolve を通過できない。警告を黙らせるには (a) コード修正、(b) #[allow] + STUB、(c) 放置 の選択肢がある。

選択肢:
- A) resolve での #[allow] 追加・STUB マーカー新規作成を完全禁止。cargo check が通らない場合はコード修正のみ許可。STUB が必要な設計判断は make への差し戻し。
- B) やむを得ない場合に限り許可するが、犯罪として即座に malfeasance-create.js で登録。犯録に deferred_to を記録。
- C) 現状維持。resolve 内で STUB 追加を許可する。

推奨: A。「最後の砦で新しい問題を作らない」原則。コード修正は許可される（STUB 作成ではなく実装だから）。

Q4: ブロッキングゲートの機構 — ACP セッション分離環境での状態維持

背景とトレードオフ: conver.js のアーキテクチャは各フェーズを独立した ACP セッション（別プロセス）で実行する。この設計ではシェルの exit code（0/1）は次のセッションに伝搬しない。つまり validate スクリプトが exit 1 で失敗しても、次のフェーズの ACP セッションはそれを知らない。ゲートを実質的に機能させるには何らかの永続化が不可避である。永続化先として Tickets.json は既に全フェーズから参照可能な唯一の共有状態である。しかしチェックポイントの書き込みには「書き込み時と検証時の競合」「書き込みに失敗した場合のフォールバック」「ACP セッションの起動元（runner.ts）での exit code 評価」の3つの考慮が必要。runner.ts が exit code を即時評価して次のセッション起動を抑制する方法はレイテンシが低いが、runner.ts がクラッシュすると状態が失われる。Tickets.json チェックポイントは堅牢だが、書き込みI/Oが発生する。両方の併用が最も堅牢だが実装コストが2倍になる。

選択肢:
- A) validate スクリプトが exit 1 + Tickets.json に phaseCheckpoints を書き込む。次フェーズの最初のスクリプトがチェックポイントを確認し、前フェーズ未通過なら exit 1 でブロック。二重構造。
- B) exit 1 のみ。runner.ts の exit code 評価で次のセッション起動を抑制する。Tickets.json への書き込みは行わない。
- C) Tickets.json チェックポイントのみ（exit は常に 0）。Tickets.json 上の状態管理だけで進行を制御する。runner.ts の改修は不要。

推奨: A。ACP レイヤー（runner.ts）で exit code による即時停止が最も応答性が高く、Tickets.json チェックポイントが永続的な証跡となる。両方実装することで一方が機能しなくても他方が担保する。特に runner.ts がクラッシュして再起動した場合でも、Tickets.json のチェックポイントが「どこまで終わったか」を保持している。

Q5: 犯罪の deferred（先送り）と DAG 循環検出

背景とトレードオフ: あるチケットで発見された犯罪を「このチケットでは解決せず Px-y で解決する」と先送り（deferred_to）する運用は現実的に必要である。例えば「P0-9 用の FFI クレートがない」という理由で解決できない犯罪は、P0-9 が将来作られるまで待つしかない。しかし deferred_to を無制限に許可すると「P3-2 → deferred_to: P4-3 → deferred_to: P3-2」のような循環参照が発生し、犯罪が永久に未解決になる。この循環は有向グラフ（DAG）の閉路検出として決定論的に検出可能であり、機械検証のコストは極めて低い（全チケット数は高々数十）。一方、deferred を完全禁止すると、真に依存関係のある犯罪を抱えたまま次のチケットに進めずパイプラインが停止する。B と A のトレードオフは「運用の柔軟性」と「永久未解決の防止」のバランスである。

選択肢:
- A) deferred を完全禁止。解決できない犯罪は make で false_positive として記録するか、人間が Tickets.json を再構成する。パイプラインは停止するが安全。
- B) deferred を許可する。ただし validate スクリプトが Tickets.json 全体の deferred_to 参照から有向グラフを構築し、Floyd または DFS で循環を検出してブロックする。循環があれば具体的な循環パス（例: P3-2 → P4-3 → P3-2）を stderr に出力し、修正を促す。循環がなければ通過。
- C) deferred を許可し、循環検出は行わない。すべて人間の責任。

推奨: B。循環検出は決定論的で計算コストが低く、完全に機械化できる。一方で deferred 自体を禁止すると現実的な運用が回らない。B は deferred の柔軟性を残しつつ、機械的に検出可能な問題だけを確実にブロックする。

Q6: 契約とテストの紐づけ方法と空テスト防止

背景: 「各 contract に対するテストが存在すること」を機械確認する必要がある。前回の提案はテストコード内に // [::TICKET::] P3-2_C001 アノテーションを記述し、grep で実在確認する方法だった。しかし、空のテスト関数（assert なし）にアノテーションだけ書けばゲートを通せる抜け穴がある。この穴を塞ぐ必要がある。

選択肢:
- A) テストコード内に // [::TICKET::] P3-2_C001 アノテーションを記述。grep で実在確認 + アノテーション行から30行以内に assert! / assert_eq! / assert_ne! が含まれることを検証。空テストはブロック。
- B) アノテーションの実在確認のみ。空テスト防止は行わない（AI と人間のレビューに委ねる）。
- C) アノテーション不要。テストファイル名と契約IDの命名規則（例: test_P3-2_C001_runtime_handle.rs）で自動対応付け。ファイルが存在すれば OK。

推奨: A。空テストの機械検出は決定論的且つコストが低い。as_doc(assert) の有無を grep するだけ。B はレビュー負荷が高く、C は命名規則の強制力が弱い。

Q7: enumerate の冪等性と手動編集の衝突解決

背景: enumerate-ticket-targets.js は「冪等」であるべきだが、人間が Tickets.json を手編集した後にもう一度 enumerate を実行すると、手編集が上書きされる可能性がある。一方、全く上書きしないと、存在しなくなった STUB が残り続ける。このバランスをどう取るか。

選択肢:
- A) 人間が手編集したエントリに _editedByHuman: true フラグを立てる。enumerate はフラグ付きエントリを上書きしない。--force で強制上書き可能。存在しなくなったフラグなしエントリは自動削除。
- B) enumerate は常に全上書き（冪等の定義を strict に解釈）。手編集は常に失われる。
- C) enumerate は追記のみ。既存エントリの削除・変更は一切行わない。手編集か自動生成かの区別なし。

推奨: A。冪等性と手動編集の両立にはフラグによる排他制御が最も安全。--force で人間が明示的に上書きを指示できる。
