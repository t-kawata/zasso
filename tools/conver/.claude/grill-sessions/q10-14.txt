Q10: 各フェーズの内部収束ループのアーキテクチャ（D03-2）

背景: 「パイプラインは決して停止しない。各フェーズの内部ループで解決して必ず進む」という原則に基づく。validate スクリプトは exit 1 でセッションを止めるのではなく、各フェーズのコマンド定義内で「実行 → 検証 → 修正 → 再検証 → 通過」のループを駆動するための情報提供者として機能する。
具体的には、各コマンド定義（make-ticket.md等）は以下の構造を持つ:

```
[Step N]: 作業（planを書く／実装する等）
[Step N+1]: validate-ticket-targets.js <ticketKey> を実行
  → 成功: 次のフェーズへ
  → 失敗: stderr の指示に従って修正し、[Step N]または[Step N+1]に戻る
[Step N+2]: ループ収束確認
```

このループは ACP セッション内でAIが自己駆動する。runner.ts は関与しない。

選択肢:
- A) 上記のループ構造を各コマンド定義に明示的に記述する。validate スクリプトは stderr に修正指示を出力するだけで、exit code は成功時 0 のみ（失敗時も 0）。ループ制御はコマンド定義内のAIに対する指示で行う。
- B) validate スクリプトは exit 1 するが、コマンド定義内で「失敗したらループ」するよう記述する。exit 1 で runner.ts が例外を投げる前に、コマンド定義内のループが catch する。
- C) ループ機構を runner.ts に実装する。各フェーズの validate が終わるまで進まない。

推奨: A。exit code を一切使わず、AIの自己駆動ループのみで収束させるのが「パイプラインは停止しない」に最も適合する。B は exit 1 が runner.ts に漏れるリスクがある。C は runner.ts の破壊的変更が必要。

Q11: 収束不能時の最終手段（D03-2 フォローアップ）

背景とトレードオフ: 内部ループが収束しない場合（AIが何度修正しても validate が通らない）の最終手段を決める。パイプラインは停止できないという制約のもとで、以下の3つの選択肢が考えられる。選択肢 A は「新しいチケットを作成して deferred_to で解決先を明示する」方法で、Q2-R で確定した /make-ticket 経由の新チケット作成フローと整合する。選択肢 B は「スキップして後回し」であり、今回の139件問題の原因となった放置を公式に認めることになる。選択肢 C は理想主義的だが、AI に無限ループを強制しても収束する保証はない。
A のリスクは「安易な新チケット作成による乱立」だが、justification の厳格化（100文字必須＋具体型名＋合理的理由）と /make-ticket の厳格なスクリプト経由で悪用を防止できる。

選択肢:
- A) 収束不能な場合、AI は新しいチケットを /make-ticket 経由で作成し（強制 justification 付き）、該当箇所に [::STUB::] + deferred_to を追加する。validate は deferred_to の実在チケットを確認して通過。これによりループが収束する。
- B) 収束不能な場合、該当 issue を standard output に報告してスキップし、次のチケットに進む。後で人間が対応する。
- C) 収束不能は許容されない。AI は無限ループでも修正を試み続ける。

推奨: A。Q2-R の「新しいチケット作成による解決」と整合する。C は現実的でなく、B は放置を産む。A であれば justification の厳格化（100文字必須＋具体型名）で悪用を防止できる。

Q12: 各フェーズの cargo check / test 実行要否（D10）

背景とトレードオフ: make/plan では cargo 実行不要は前回確定済み。start/review/resolve での cargo 実行方針を決める。start は実装直後、review はコードレビュー時、resolve は最終確認時であり、各フェーズで独立に cargo check + cargo test を実行するのが最も堅牢だが、実行時間が重複する。特に cargo test は時間がかかる。一方で「review では cargo check のみ」にすると、review で新しいバグが入り込んだ場合に resolve まで発見されない。リポジトリ全体のテスト時間（siprs の場合〜30秒）と、発見の遅延リスクのトレードオフ。

選択肢:
- A) start: cargo check + cargo test 必須。review: cargo check + cargo test 必須。resolve: cargo check + cargo test 必須。各々の内部ループに組み込む。
- B) start: cargo check のみ。test は review に任せる。resolve: cargo check + cargo test。
- C) start: cargo check + cargo test。review: cargo check のみ。resolve: cargo check + cargo test。

推奨: A。start/review/resolve の各フェーズで cargo check + cargo test を独立して実行するのが最も堅牢。重複を恐れて省略すると「上流で通ったはず」が「下流で壊れていた」を見逃す。siprs のテストは〜30秒と軽量であり、3回実行しても実害はない。

Q13: crimeType enum の確定（D01-2）

背景とトレードオフ: 犯罪（targetCrimes）の機械的分類に必要な enum 値。過不足のない分類が目標。犯罪は機械的に検出可能でなければならず、検出ロジックが複雑すぎるとバグの温床になる。以下の各候補を検討する:(1) ORPHAN_TICKET_REF — 存在しないチケットIDを参照。grep でチケットID抽出 → Tickets.json 照合で決定論的検出可能。(2) COMPLETED_TICKET_STALE — 完了チケットなのにSTUBが残存。find-all-stubs + Tickets.json status 照合で検出可能。(3) MISSING_MARKER — todo!(), unimplemented!(), 空メソッド本体、return Ok(()) プレースホルダに [::STUB::] がない。AST or パターンマッチで検出可能。(4) SUPPRESSION_WITHOUT_STUB — #[allow(dead_code)] があるのに近接行に [::STUB::] がない。grep + 近接行検査で検出可能。(5) STUB_WITHOUT_SUPPRESSION — [::STUB::] があるのに #[allow(dead_code)] がない。これはコンパイル警告が出なければ問題なく、犯罪とみなすのは過剰。(6) AMBIGUOUS_TICKET_REF — チケットIDが存在するが担当フェーズ外。検出ロジックが複雑で Tickets.json のフェーズ構造に依存する。機械化に適さない。

選択肢:
- A) 上記のうち(1)〜(4)の4種:
  - ORPHAN_TICKET_REF
  - COMPLETED_TICKET_STALE
  - MISSING_MARKER
  - SUPPRESSION_WITHOUT_STUB
- B) 上記4種 + STUB_WITHOUT_SUPPRESSION
- C) 上記4種 + AMBIGUOUS_TICKET_REF

推奨: A。(1)〜(4)は全て決定論的かつ機械的に検出可能。B は「#[allow] がない」だけでは犯罪にならない（コンパイル警告が出なければ問題ない）。C の AMBIGUOUS_TICKET_REF は検出ロジックが複雑で Tickets.json のフェーズ構造に依存するため機械化に適さない。

Q14: targetStubs/targetCrimes の status ライフサイクル（D01-3）

背景とトレードオフ: targetStubs（将来解決予定の未実装）と targetCrimes（即時解決必須の犯罪）では status の遷移が異なるべきか。以下の2軸で検討する。軸1: crime は deferred できない（即時解決必須）→ false_positive のみ例外。stub は deferred_to が可能。軸2: enumerate が毎回全上書き（strict 冪等）する場合、専用スクリプトで更新した status が消える。Q5-R で enumerate は status を保持する方針を推奨したが、この方針と各 status 値の組み合わせを確定する必要がある。また false_positive の悪用防止として justification の文字数要件も併せて決める。

A) targetStubs と targetCrimes で統一:
   - pending → resolved (deferred 不可)
   - pending → false_positive (justification 必須)
   - 遷移は専用スクリプト経由のみ。enumerate は上書きしない（status は保持）。
   - deferred_to は使えない（どちらも不可）。
B) targetStubs は pending → resolved OR deferred_to, targetCrimes は pending → resolved OR false_positive で分ける。false_positive に justification 要件なし。
C) targetStubs: pending → resolved / deferred_to。targetCrimes: pending → resolved / false_positive。false_positive には justification 必須（100文字以上 + 具体型名含む）。deferred_to 先は実在チケットID必須。enumerate は status を保持（上書きしない）。deferred_to が設定された targetStub は、deferred_to 先チケットの enumerate 時に targetStubs として自動コピーされる。

推奨: C。Q2-R の crime≠stub の区別と整合。false_positive は justification 必須で悪用防止。deferred_to された targetStub の自動コピーにより、deferred_to 先チケットの enumerate で見落としが発生しない。
