Q6: 新機能チケット（targetStubs/targetCrimes が空）の扱い（D07）

背景: 全く新しい機能を追加するチケットでは targetStubs が空になりうる。しかし targetCrimes も空だと validate が bloックされる可能性がある。一方で「確認もせずに空で通過」を許すと、実は犯罪があるのに見逃す。

A) targetStubs が空でも targetCrimes が空でも通過させる。ただし enumerate の実行ログに "0 crimes confirmed" のタイムスタンプを Tickets.json に記録する。犯罪が後で発見された場合、このタイムスタンプが「確認済み」の根拠となる。
B) 空配列を禁止。targetStubs か targetCrimes の少なくとも一方は非空でなければならない。新機能チケットでも既存コードベース上の犯罪を1件以上発見してから開始する。
C) 空配列を許可するが、enumerate の結果が空であることを示す明示的な空配列（[] ではなく "verified_empty"）と、未確認を示す undefined/null を区別する。

推奨: C。未確認（null/undefined）と確認済み空（verified_empty）を区別することで、「enumerate を実行していないチケット」と「実行したが0件だったチケット」を機械的に区別できる。

Q7: deferred_to の参照先チケット実在検証と DAG 循環防止（D05-3 再質問）

B) 実在検証のみ。循環検出は行わない。

Q8: 各 validate ゲートの exit code 統合場所（D03-1 再質問、単純化版）

背景とトレードオフ: 前回の Q1-R であなたが「何のためにこの管理が必要なのかわからない」と指摘した通り、私は過剰に複雑化していた。根本に立ち戻る。ブロッキングゲートの機能には二つの要素しかない: (1) validate スクリプトが exit 1 で失敗すること、(2) その結果次のフェーズに進めないこと。runner.ts は Session A 内で make→plan→start→review を逐次実行する。したがって、validate スクリプトが exit 1 すれば、runner.ts の execSync が例外を投げ、Session A 全体が停止する。これが唯一のブロッキング機構であり、追加の管理機構は一切不要である。
問題は「各 validate スクリプトを誰が・どこで呼び出すか」だけ。選択肢は3つ: コマンド定義（make-ticket.md等）の中で明示的に呼び出す、runner.ts 側で各フェーズ前に強制実行する、または両方。コマンド定義内での呼び出しは各フェーズの独立性を保ち、runner.ts 側での呼び出しは「万が一コマンド定義に書き忘れても」の保険になるが、runner.ts の改修が必要。

選択肢:

A) 各フェーズのコマンド定義（make-ticket.md / plan-ticket.md / start-ticket.md / review-ticket.md / resolve-ticket.md）の中で validate スクリプトを明示的に呼び出す。exit 1 でコマンド全体が停止する（Session A 内なら次フェーズに進めない）。
B) runner.ts（conver.js）側で各フェーズの前に validate を強制実行する。
C) コマンド定義と runner.ts の両方で二重に実行する。

推奨: A。最もシンプル。各コマンド定義の最後に validate スクリプトを追加するだけ。runner.ts の改修は不要。

Q9: targetStubs/targetCrimes 専用の validate スクリプトの設計（D04 フォローアップ）
