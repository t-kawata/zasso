## 0. 専門家への依頼（この文書の中心）

### 0.1 誰に頼んでいるか

次のいずれかに該当する方に依頼する。

- 複数言語にまたがる**ソースコード解析基盤**を設計・運用した経験がある方（コードインデクサ、静的解析器、コードインテリジェンス基盤、大規模リファクタリングツール）
- **tree-sitter / LSP / SCIP / LSIF / Glean / Kythe / Joern / CodeQL / Semgrep / stack-graphs** のいずれかを、実際に製品または研究で使った方
- 言語処理系の内部（AST、プリティプリンタ、マクロ展開、名前解決）に通じている方
- **動的機構（FFI、リフレクション、動的ディスパッチ、コード生成、実行時登録）の静的検出**を扱った方

### 0.2 依頼は5つである

#### 依頼 1 — 技術選定（我々が知らないものを教えてほしい）

**6言語に対して、§2 の抽出要求を満たす解析基盤をどう構成すべきか。** 単一技術である必要はない。言語ごとに最適が異なるなら、その組み合わせと、それらを単一スキーマに写像する方法を教えてほしい。

§4 に我々が検討した候補を列挙した。**しかし §4 は我々の予想であり、それに縛られないでほしい。** 我々が知らない技術、社内ツール、新しい論文、あるいは「その要求はそもそも無理だ」という結論のいずれでも構わない。

#### 依頼 2 — 実現可能性の切り分け（何ができて、何ができないか）

§2 に列挙した抽出項目は、**我々が「必要だ」と考えたものであって「可能だ」と確認したものではない。** 各項目について、各言語で:

- **決定論的に、対象をビルドせずに、実用的なコストで抽出できるか**
- できないなら、**なぜできないのか**（原理的に不可能 / 技術的に困難 / コストが見合わない）
- できない場合の**代替**（部分的に取れる / 人間に回す / 諦める）

特に **§2.3 の契約候補（guard / invariant / 状態機械）** を我々は最も困難だと予想している。ここへの率直な評価を求めている。**「シンタックスでは取れない」という答えは、我々にとって価値のある答えである。**

#### 依頼 3 — 配置の設計（どこに置くか、なぜそこか）

解析基盤は**我々のリポジトリの中に**置かれ、Node.js のスクリプトから呼ばれる（§1.7 の制約を参照）。この制約の下で:

- 何を外部ツールとして呼び、何を自前で書くべきか
- インストール・バージョン固定・再現性をどう確保するか

#### 依頼 4 — 単一スキーマへの写像

我々の出力スキーマは**言語によらず一つ**である（§2.4）。6言語の解析結果をこの一つに写像するとき、**何が失われ、何が嘘になるか**を教えてほしい。言語ごとに意味が異なる概念（Rust の trait と Go の interface と TypeScript の structural typing、Python の動的屬性、C++ のテンプレート）を同じ箱に入れて、どこで破綻するか。

## 1. 背景（前提知識なしで読めるように書いてある）

### 1.1 我々が作っているもの

我々は **conver** という開発パイプラインを作っている。狙いは一つ、**「設計の意図を、実装の隅々まで届いた状態に保ち続けること」** である。

一般的な開発では、設計文書とコードが時間と共に離れていく。誰かが仕様を変え、コードが変わり、設計文書は更新されない。数月後には、コードが唯一の真実になり、なぜそうなっているのかを誰も説明できない。

conver はこれを、**チケット駆動のループ**で防ぐ。設計文書を出発点にし、それを機械的に分解し、作業単位（チケット）に切り、チケットごとに「仕様を詳細化する → 実装計画を立てる → 実装する → レビューする」を回す。各段階で元の設計との対応が記録されるので、**コードのどの行が設計のどの部分から来たのかが常に辿れる。**

このパイプラインは 4 つのループから成る。我々はこれを**「順回転」**と呼んでいる。

| ループ | 何をするか |
|---|---|
| **上流** | 設計意図を RFC として書き、それをノードと辺からなるグラフに分解し、境界のあるディレクトリ構造に割り当て、チケットに切る |
| **実装** | チケットごとに 仕様詳細化 → 計画 → 実装 → レビュー を回す |
| **出荷** | 実装から読み取れることを文書化し、未解決事項を洗い出す |
| **進化** | 設計が変わったとき、影響する範囲を辿って更新する |

**順回転は既に完全に動作している。** 実プロジェクト（音声処理ライブラリ、Rust、5 万行規模）を、この 4 ループで最初から最後まで通した実績がある。

### 1.2 順回転には入口の閉ざされた問題がある

順回転は強力だが、**「設計文書が既に存在すること」を前提にしている。**

現実のソフトウェアのほとんどは、そうして生まれていない。多くのプロジェクトは設計文書なしに始まり、あるいは設計文書が陳腐化し、**コードだけが真実**になっている。こういうプロジェクトに順回転を適用したいと思っても、**入口が閉じている。** 上流ループに流し込むべき RFC が存在しないからである。

**これは我々のパイプラインの適用範囲を大きく狭めている。** 世の中のプロジェクトの大半は、この入口を通れない。

### 1.3 逆回転 — 今回作ろうとしているもの

そこで、**逆向きに回す**ことを考える。**既に実装が進んでしまったプロジェクトを持ってきて、そこから上流（RFC）を再構成し、4 層ループに載せ直す。**

```
[既存プロジェクト]                        [conver ワークスペース]
  コード                                       RFC（再構成された設計意図）
  テスト                    ──逆回転──▶         グラフ（境界のあるノード構造）
  設定                                        ディレクトリツリー（境界の割り当て）
  git 履歴                                     チケット（作業単位）
                                               ↓
                                          以降は順回転で回せる
```

これを**「逆回転」**と呼ぶ。順回転が「設計 → コード」なら、逆回転は「コード → 設計」である。

**なぜこれが欲しいのか。** 逆回転が成立すれば、あらゆる既存プロジェクトが conver のループに乗る。設計意図が失われたコードベースに、辿れる来歴を取り戻せる。これは我々のパイプラインの適用範囲を、順回転で生まれたプロジェクトから、**世の中の全てのプロジェクト**に広げる。

**そして、これは非常に難しい。** 人間のプロフェッショナルでも成功率が極めて低い作業である。理由は本質的で、**コードは「何をするか」を語るが「なぜそうするのか」を語らない。** 我々はこの困難を正面から扱う設計をしてきた（§1.6）。

### 1.4 逆回転の成功条件と、機械・AI・人間の役割分担

逆回転には**終わりの判定**が要る。我々はそれを「出荷ループが残した未解決事項（我々は RESIDUE と呼ぶ）が 0 になること」と定めている。未解決事項とは、解析しても決まらなかったこと、人間が判断を保留したこと、証拠が足りなかったことの総体である。

**重要なのは、その判定を機械がしてはならないということである。**

我々の設計は、役割を三層に分けている。

| 層 | 誰が | 何をするか | 何をしてはならないか |
|---|---|---|---|
| **機械** | スクリプト | 決定論的に確定できることを確定する | **「成功した / 失敗した」を言ってはならない。** 機械が語ってよいのは「**証明できた / 証明できなかった**」だけである |
| **AI** | 言語モデル | 意味論的判断（これは意図か偶然か、この候補は妥当か） | 判断材料を与えられずに推測してはならない。**判断の直前に、必要な材料を親切な形で差し出す**（我々はこれを「給仕」と呼ぶ） |
| **人間** | 開発者 | **成功したかどうかを決める** | — |

**この分担が、本依頼の要求仕様を強く規定している。** 逆回転が成功したかどうかは、ループを複数回回した後で人間が判断する。**機械的な成功判定は放棄した。** だから我々が解析器に求めているのは、**判定ではなく、人間が判定できる形の材料**である。この点は §2 で繰り返し効く。

### 1.5 逆回転の出力は「文書」ではなく「命題と証拠の集合」

ここが最も誤解されやすい点なので独立した節にする。

素朴に考えると、逆回転の出力は「再構成された設計文書」だろう。**我々の設計はそうなっていない。** 出力は**命題（claim）の集合**であり、各命題は次のものを持つ。

| フィールド | 内容 |
|---|---|
| `claim_id` | 識別子 |
| 命題文 | 「この関数は入力 X が空でないことを前提とする」のような、真偽を問える文 |
| `scope` | この命題がどの範囲について述べているか |
| **反証条件** | **この命題が偽であることを示す観測は何か。** これが書けない命題は捨てる |
| **provenance（来歴）** | 下記の 4 値のいずれか |
| `evidence` | 根拠となった抽出物のリスト。各々が `file:line` を持つ |
| `derivation_group` | その証拠が「どこから派生したか」の識別子（§2.5） |

**provenance の 4 値**は、その命題をどこまで信じてよいかを表す。これが逆回転の品質管理の中心である。

| 値 | 意味 |
|---|---|
| `observed` | **観測された。** 実装が実際にそうしていることを、証拠をつけて示せる |
| `inferred` | **推論された。** 証拠からそう考えるのが自然だが、実装が明示しているわけではない |
| `normative` | **規範的。** 「そうあるべき」と人間が承認した。**人間の承認が無ければこの値にはできない** |
| `unresolved` | **未解決。** 決まらなかった。**これが残っていること自体が記録であり、隠してはならない** |

**重要な原則が 2 つある。**

1. **動的機構が関与する命題は、動的証拠なしに `observed` と名乗れない。** たとえば関数ポインタ経由で呼ばれる関数について、静的に見つけたという理由だけで「観測された」と言ってはならない。これは §2.2 の E6 の存在理由である。
2. **逆回転の出力は「一致していること」ではなく「不一致が記録されていること」を合格とすることがある。** 特に、解析結果と既存実装の間に差が無いことは、**正常ではなく異常の signal であることがある**（§1.6 の追認 RFC を参照）。

### 1.6 我々が最も恐れている失敗（**これが要求仕様を決めている**）

§2 の要求仕様は、抽象的な理想から出たものではない。**すべて、具体的な失敗を防ぐために存在する。** 専門家が要求の妥当性を判断できるよう、6 つの失敗を説明する。

#### 失敗 1 — 追認 RFC（最大の失敗）

逆回転の出力は「RFC」と呼ばれる設計文書になる。**最も起きやすい失敗は、その RFC が既存コードの文章化に終わることである。**

既存実装がある状態で「この機能は何をすべきか？」と問うと、答は「今やっていること」になる。すると RFC は、コードを自然言語に翻訳しただけの文書になる。それは**設計意図の再構成ではなく、コードの言い換えである。** 我々はこれを「追認 RFC」と呼び、最大の失敗モードと位置づけている。

これを防ぐには、**「この挙動は意図されたものか、それとも偶然か」を必ず問う**仕組みが要る。そして解析器には、**既存実装と独立な証拠**を出すことが求められる。ここから §2.5 の証拠独立性の要求が出る。

#### 失敗 2 — 偽の green

テストは、実装より後に書かれることがある。その場合、**そのテストは生まれた瞬間から成功している。** 一度も失敗したことがない。

テストが緑であることは、実装が正しいことを何も意味しない。**赤（失敗）を経験していない緑は、根拠の無い緑である。** 我々はこれを「偽の green」と呼ぶ。

逆回転では、既存テストの大半がこれに該当する。だから我々は、**「このテストは赤を経験したことがあるか」を判定し、無いものについては Red を再構成する**必要がある（§2.2 の E10）。これは逆回転に固有の、最も深い論点である。順回転ではテストを先に書くので自動的に赤を経験するが、逆回転ではそれを**工作しなければならない。**

#### 失敗 3 — 静的解析の盲点

import グラフを「結合のグラフ」とみなすこと。**これは嘘である。**

実際の結合は、関数ポインタ、リフレクション、動的ディスパッチ、コード生成、設定ファイル、FFI などで起きる。これらは import 文に現れない。import グラフだけを見た解析は、**「結合が無い」と主張するが実際にはある**、という静かな嘘をつく。

具体的な実例を一つ挙げる。我々の最初の対象プロジェクト（Rust）で、`include_str!("../README.md")` という記述が見つかった。これは**コンパイル時に、存在しないファイルを埋め込もうとする**もので、import グラフには一切現れない。実際にビルドを走らせて初めて表面化した。

ここから §2.2 の E6（動的機構の検出）が出る。

#### 失敗 4 — 証拠の水増し

同じ源泉から生まれた複数の成果物を、独立した複数の証拠として数えること。

例: 実装の中の `if` 文、その `if` を検査するテスト、その `if` を説明するコメント。**この 3 つは 3 本の独立証拠ではない。1 本である。** すべて同じ設計判断から派生している。

3 本と数えると、**証拠が 3 倍あるように見える。** そして「証拠がこれだけあるのだから確かだ」という判断を生み、追認 RFC（失敗 1）に直結する。

ここから §2.5 の証拠独立性の要求が出る。**これが本依頼で最も難しい技術要求の一つである。**

#### 失敗 5 — 未観測を不存在として扱う

解析のスコープ外にしたものを、「存在しない」と書いてしまうこと。

解析しなかった範囲と、解析した結果何も無かった範囲は、**全く別物である。** 前者は「不明」であり、後者は「無い」である。これを混同すると、**危険な見落としが「問題なし」として報告される。**

我々は、スコープを 3 値（対象内 / 対象外 / 未確定）で管理し、**「対象外」を「存在しない」と書くことを禁じている。**

#### 失敗 6 — oracle の共犯

「oracle」とは、テストが正しさを判定する基準のことである。

実装から導いた oracle は、**実装と必ず一致する。** 実装を読んで期待値を作れば、その期待値は実装が何をするかを述べているだけであり、**実装が正しいかどうかは何も言えない。** 我々はこれを「共犯の oracle」と呼ぶ。

共犯の oracle を破るには、**実装とは独立な基準**（差分 oracle、変成 oracle、別実装との比較）が要る。ここから §2.2 の E13・E14 が出る。

### 1.7 決定的な制約 — 解析は「他人のプロジェクト」に対して行う

これが技術選定を最も強く制約する。**逆回転の対象は、我々が管理していない、任意のプロジェクトである。**

そこから次が従う。

| 制約 | 内容 | なぜ |
|---|---|---|
| **ビルドできなくても解析できなければならない** | 対象がコンパイル・テストに通る保証はない。依存が欠けている、ツールチェインが古い、プラットフォームが違う、といった状況が普通に起きる | コンパイラの API に依存する技術は、**ビルドできない対象で沈黙する。** これは「解析できなかった」ではなく「解析を試みなかった」であり、逆回転の前提を壊す。**そして沈黙は、失敗 5（未観測を不存在として扱う）と結びついて最も危険な形の誤りになる** |
| **対象を一切変更してはならない** | 解析は読み取り専用である。`Cargo.toml` を書き換える、`target/` を作る、`node_modules` を入れる、いずれも許されない | 対象は我々のものではない。また変更は「実測」という前提そのものを汚染する |
| **決定論的でなければならない** | 同じ入力から同じ出力が出ること。ハッシュで固定できること | 我々の設計は「決定論で確定できることはスクリプトが確定判断を下す」（§1.4）という原則の上に立っている。非決定論的な解析結果は証明に使えない |
| **すべてに `file:line` が付かなければならない** | 抽出物はすべて位置を持つ | 我々の原則は「証拠の無い主張は主張ではない」である（§1.5） |
| **実用的なコストで動かなければならない** | 5 万行で数分、50 万行でも現実的な時間 | 逆回転はループを複数回回す。1 回が遅いと成立しない |
| **言語を後から足せること** | 今は 6 言語だが、将来増える | 言語追加が基盤の作り直しになるなら、その設計は誤りである |

**加えて、抽出したいものの一部は本質的に意味論的である。** 「この `if` は事前条件か、事後条件か、単なる防御か」はソースに書かれていない。§1.6 の失敗 1 がそれである。

**我々は解析器に答えを求めてはいない。** 我々が求めているのは、**人間が判断できる形の候補と、その候補がどこから来たかの記録**である。この区別は §2 で繰り返し効く。

### 1.8 なぜソース解析技術が最大の未解決問題なのか

我々の設計文書は 1,800 行あり、失敗モードを 21 個列挙し、専門家 2 名のレビューを経ている。**しかしその中で「ソースをどう解析するか」は一度も決められていない。**

これは意図的な先送りではない。**「何を抽出したいか」を決め切る前に「どう抽出するか」を決めると、抽出したいものが技術に合わせて矮小化される**という理由で後回しにしていた。いま、抽出要求（§2）が固まったので、技術を決める段階に来た。

そして我々の実装計画を精査した結果、**これが最大のリスクであることが判明した。** 理由は三つある。

1. **4 つの独立した作業単位が同じソースを解析する。** 我々の実装は複数のセッションに分かれて進み、**セッション間でコンテキストが共有されない。** 技術が決まっていなければ、**別々のパーサを選んでも互いのテストは全部通ってしまう。** 統合時に初めて破綻する。
2. **我々のリポジトリに継承できる前例が無い。** 既存のソース解析スクリプトは正規表現ベースであり、guard や invariant の抽出には使えない。
3. **6 言語に耐える必要がある。** 最初の対象は Rust 単一言語の単一クレートである。ここだけで動く技術を選ぶと、**まさに「そのプロジェクトに最適化して成功したように見える」実装**を作ることになる。これは我々が明示的に禁じていることである。

## 2. 何を抽出しなければならないか（要求仕様）

### 2.1 逆回転の全段（R0〜R8）

逆回転は次の段階で構成される。**★ がソース解析に依存する段である。**

```
R0   スコープ確定        ── 対象範囲の列挙（ファイル探索）
R0.5 境界確定            ── 垂直スライスの特定
R1   構造実測            ── ★ パッケージ・公開面・型
R2   依存実測            ── ★ 依存グラフ
R2.5 実行面実測          ── ★ 動的機構の検出
R3   意味論素材の抽出    ── ★ 契約候補の抽出（最重要）
R3.5 命題台帳の構築      ── ★ 証拠独立性の付与
R4   意図の考古学        ──   git 履歴（ソース解析ではない）
R5   欠落と矛盾          ── ★ 死コード・赤の不在の検出
R5.5 oracle 妥当性       ── ★ 変異と等価性判定
R6   Red 再建計画        ──   R3 の出力に依存
R6.5 能動的反証          ── ★ 不変条件からのテスト自動生成

```

下流にも解析依存がある。

| 段 | ソース解析への依存 |
|---|---|
| RFC のグラフ化 | **ノードを実在ファイルパスに接地する** |
| ディレクトリ構造の生成 | **ヘッダ後付けのみ**（ファイル本体を変更しない） |
| チケット分割 | **既存テストのチケットへの写像、赤の不在の検出** |

**つまり解析基盤は逆回転のほぼ全体の土台である。** ここが弱いと、上に載るすべてが弱くなる。

### 2.3 抽出項目の定義 — 特に難しいもの

#### E6: 動的機構（R2.5）

**なぜ必要か。** §1.6 の失敗 3 そのものである。import グラフは実行時の結合を代表しない。見落とすと、解析は「結合が無い」と主張するが実際にはある、という静かに嘘をつく状態になる。

**言語ごとに何を探すか（我々の予想。検証してほしい）:**

| 言語 | 予想される動的機構 |
|---|---|
| Rust | `include_str!` / `include_bytes!` / `macro_rules!` / proc macro / `dlopen` / trait object 経由の動的ディスパッチ / `build.rs` による生成 / feature flag による条件コンパイル |
| JS/TS | `require()` の動的呼び出し / `import()` / `eval` / `Proxy` / デコレータ / DI コンテナ / `package.json` の `exports` 条件分岐 / モンキーパッチ |
| Go | `reflect` / `init()` / build tag / `//go:generate` / `plugin` パッケージ / interface の暗黙実装 / struct tag 駆動 |
| Python | `importlib` / `__getattr__` / メタクラス / デコレータ / `entry_points` / `getattr` / `eval` / `__init_subclass__` |
| C/C++ | 関数ポインタ / `dlopen`/`dlsym` / 仮想関数 / テンプレート特殊化 / `#include` の条件分岐 / マクロ / weak symbol / リンカスクリプト |
| 共通 | 設定ファイル・環境変数による分岐（コード外） |

**問い:** これらのうち、静的解析で**決定論的に**検出できるものはどれか。できないものはなぜか（チューリング完全な計算、外部入力依存など）。そして**検出漏れを人間に可視化する**には何を出力すればよいか。

#### E7 / E8 / E11: guard・状態機械・契約候補（R3）— **最も難しい**

**なぜ必要か。** 逆回転の中心課題である。既存実装から「この関数は何を前提とし、何を保証するか」を候補として取り出し、人間が裁定できる形にする。**「既存の実装がそうしているから」を「正典の契約」に昇格させてはならない**（それが失敗 1 の追認 RFC である）。

**何が難しいか。** 実装にある `if !x.is_valid() { return Err(...) }` は:

- **事前条件**かもしれない（呼び出し側が守るべき）
- **事後条件**かもしれない（この関数が保証する）
- **不変条件**かもしれない（常に成立する）
- **単なる防御**かもしれない（起こらないが念のため）
- **歴史的遺物**かもしれない（かつて必要だった）

**ソースはこの区別を書いていない。** だから我々は「候補」と「その候補がどこから来たか」だけを求め、**分類は人間が行う**設計にしている（§1.5 の provenance）。

**問い:** この区別に対して、既存の研究・ツールで**どこまで迫れるか**。特に:

- 契約を**言語機能として持つ**言語・ライブラリ（Rust の契約クレート、Eiffel、Dafny、SPARK、JML、Python の `icontract` など）から、契約を**持たない**言語へ、何が移植できるか
- **データフロー解析**（Joern の CPG、CodeQL）は、guard を「事前条件らしさ」の順に並べるのに使えるか
- **テストからの逆推**（既存テストが何を前提しているかを読む）は有効か
- **docstring / コメント**は証拠として使えるか。使えるなら、**実装と同じ派生元である場合が多い**ため独立証拠として数えてはならない（§2.5、失敗 4）という制約をどう扱うか

#### E13: 等価性判定（R5.5）

**なぜ必要か。** 変異テスト（コードを少し変えて、テストがそれを検出できるか調べる手法）で生き残った変異体の中には、**元と意味的に等価**なものがある（例: `i < n` と `i <= n-1`）。これを「テストが見逃した」と数えると、**存在しない穴を追いかける**ことになる。

我々は「公式 AST ＋ 公式プリンタで足りる」と結論している。つまり、変異体と元をそれぞれ公式の AST に変換し、公式のプリンタで正規化して文字列比較する。正規化して一致すれば等価とみなす。

**問い:** 6言語それぞれについて、**公式 AST と公式プリンタの組**は何か。次は我々の予想である — 検証し、間違いを訂正してほしい。

| 言語 | 予想 | 我々の確信度 |
|---|---|---|
| Rust | `syn` でパース ＋ `prettyplease` で出力。または `rustc -Zunpretty=expanded`（nightly 依存） | 中 |
| TypeScript/JS | TypeScript Compiler API の `createSourceFile` ＋ `createPrinter` | 高 |
| Go | `go/ast` ＋ `go/printer`（`go/format`） | 高 |
| Python | `ast` モジュール ＋ `ast.unparse`（3.9+）。ただしコメントが落ちる | 中 |
| C/C++ | libclang ＋ clang のプリンタ。マクロ展開の扱いが問題 | 低 |
| 共通 | **マクロ・テンプレート・デコレータ・コード生成**が絡むと「公式 AST」自体が自明でなくなる | — |

**特に知りたいこと:** マクロ展開後の AST と展開前の AST、どちらを等価性判定の基準にすべきか。展開後は判定が正確になるが、**ソース上の位置情報が失われる**（§1.7 の `file:line` 要求と衝突する）。

#### E14: テスト自動生成（R6.5）

**なぜ必要か。** §1.6 の失敗 2（偽の green）と失敗 6（共犯の oracle）への対策である。既存実装のテストは最初から緑であり、**赤が無ければ緑は根拠を持たない。** 反例を能動的に探す必要がある。

我々は「生成できる範囲を既知カテゴリに限定する」と結論している。無限定の生成は、**実装が満たしようのない性質を作り出して**失敗する。

**問い:** 6言語それぞれで、**不変条件から property-based test を生成する**実用的な道はあるか。既存の PBT ライブラリ（Hypothesis, fast-check, proptest, QuickCheck, gopter, RapidCheck など）を**生成対象として**使う場合の限界は何か。「既知カテゴリ」として何を選ぶべきか。

### 2.4 出力スキーマ（単一。6言語がこれに写像される）

抽出物は**一つのスキーマ**に収まる。

```
抽出単位（1件）= {
  kind:             E1〜E16 のいずれか
  file:             対象ファイルのパス（対象ルートからの相対）
  line:             開始行
  language:         検出された言語
  symbol:           対象の名前（あれば）
  detail:           種別ごとの詳細
  derivation_group: この抽出物がどの派生元から来たか（§2.5）
  independence_class: 独立証拠として数えてよいかの分類
}
```

**問い:** 6言語の解析結果から `derivation_group` を決定論的に計算できるか。**同じ派生元であることを、どうやって機械が知るのか。**

### 2.5 証拠独立性の要求

§1.5 と §1.6 の失敗 4 の繰り返しになるが、これが要求仕様の核心なので独立した節にする。

逆回転の出力は、**命題ごとに証拠の本数を数える。** しかし本数が意味を持つのは、**各証拠が独立である場合だけ**である。我々の要件は:

- 各証拠に `derivation_group`（派生元の識別子）を付ける
- 同じ `derivation_group` の証拠は**独立証拠として加算しない**
- `independence_class` で、独立 / 同一派生 / 不明 を区別する

直感的な例で言うと、**実装の `if` 文と、その `if` を検査するテストと、その `if` を説明するコメントは、1 本の証拠である。** 3 本ではない。

**問い:** この計算を、6言語にわたって決定論的に行う具体案を求めている。

## 4. 我々が検討した候補（**暫定。これに縛られないでほしい**）

我々は既にいくつかの候補を認識している。**列挙するのは、専門家に「これはもう知っている」と伝えるためであり、選択肢を狭めるためではない。** §4.4 の評価は我々の予想であり、**検証を求めている。**

## 前提の修正

まず、設計上もっとも重要な修正は三つです。

- `observed` を「静的解析器が見つけた」に使わないでください。静的抽出で観測できるのは、厳密には **ソーステキスト／構文木上の事実**です。実行上の挙動、動的ディスパッチ先、条件コンパイル後の構成、生成後コードを伴う主張は、実行・ビルド・トレースなしには `observed` ではありません。`observed_source` と `observed_runtime` を分けるか、少なくとも `evidence_mode: source_static | build_semantic | runtime_dynamic` を追加すべきです。 
- `derivation_group` を「同じ設計判断に由来するか」という真の因果単位として決定論的に計算することは、不可能です。コード、テスト、コメントが同じ人間の同じ意図から生じたかは、ファイル内容だけから識別できません。機械が計算できるのは、**観測可能な系譜近似**だけです。この差をスキーマ上で明示しない限り、誤った独立性判定を“証明”のように扱う危険があります。 
- E13 の「ASTを正規化して一致すれば意味的等価」は誤りです。AST の正規化で分かるのは、せいぜい構文等価または限定した変換規則に関する同値です。`i < n` と `i <= n - 1` は、整数のオーバーフロー、型、`n` の副作用、言語仕様、未定義動作の有無によって等価でない場合があります。一般プログラムの意味等価性は決定不能です。E13 は **TCE（trivial / syntactic / compiler-normalization equivalence）** に改名し、完全な等価性判定を目的から外すべきです。 

この三点を修正しない限り、逆回転は「不確実性を表に出す」仕組みではなく、「不確実な推論に決定論的なラベルを付ける」仕組みになり得ます。

## Q1–Q4：基盤構成

### Q1. 具体的な解析基盤

推奨は、単一ツールではなく、**四層のアーキテクチャ**です。中心は tree-sitter でも Joern でも SCIP でもなく、あなた方自身が管理する「不確実性を保持する中間表現」です。

| 層 | 責務 | 実装方針 | E項目 |
|---|---|---|---|
| A. 読取り専用採取層 | ファイル列挙、ハッシュ、言語・設定・ビルド記述の発見、解析スコープの記録 | Node.js主体。対象ツリー外にキャッシュ・出力を置く | E1の前提、E6の外部設定、E15 |
| B. 共通構文層 | 壊れたコードも含むCST/AST、位置、構文パターン、import/include、宣言、guard候補 | tree-sitter + 言語別query/extractor | E1–E5の下限、E6–E10の候補 |
| C. 言語適応意味層 | 名前解決、型、参照、実装関係、CFG、限定的データフロー | 言語別アダプタ。成功時のみ利用し、失敗を成果物化 | E2–E5の精度向上、E7–E12 |
| D. 証拠・命題層 | provenance、coverage、解析失敗、派生近似、候補ランク、反証可能性を統合 | 自前実装。JSON/SQLite/Parquet等で固定スキーマ | E11、E13–E16、命題台帳 |

tree-sitter は、6言語の壊れたソースも対象にできる**共通の構文フォールバック**として適切です。これはインクリメンタル構文解析ライブラリであり、エラー回復を持ち、構文的な抽出の基盤として使えます。 ただし、tree-sitter は意味解決器ではありません。名前解決、trait/interface 実装、C++テンプレート実体化、Python 実行時属性、JSの実行時プロパティは tree-sitter 単独では回収できません。 

言語別には以下を推奨します。

| 言語 | 構文下限 | 意味アダプタ | 建てられない場合の扱い |
|---|---|---|---|
| Rust | tree-sitter-rust、必要なら `syn` | rust-analyzer の解析・SCIP、または CodeQL Rust | macro/proc macro/依存解決不能を明示し、構文結果へ退避 |
| TS/JS | tree-sitter + TypeScript Compiler API | TypeScript `Program` / `TypeChecker`、CodeQL | `tsconfig`、package exports、bundler依存の解決不能を明示 |
| Go | tree-sitter-go | `go/packages`、`go/types`、`go/ast`、`golang.org/x/tools` | build tags、モジュール・依存欠落の構成別失敗を記録 |
| Python | tree-sitter-python | Pyright 系または独自の限定的名前解決、CodeQL | import hook、metaclass、monkey patchは未知として残す |
| C/C++ | tree-sitter-c/cpp | Clang/clangd/LibTooling。ただし `compile_commands.json` がある構成に限定 | DBなしは構文・プリプロセッサトークン・heuristicのみ |
| 横断参照 | 各抽出器の独自AST | SCIPを任意の意味索引出力として採用 | 索引なしは symbol identity を `unknown` とする |

SCIP は言語非依存のコード索引プロトコルであり、定義・参照・実装関係を表す用途に向いています。しかしそれは解析器ではなく、言語ごとの解析結果を載せる**交換形式**です。SCIP自体が6言語の意味差を解消するわけではありません。 Rust AnalyzerにはSCIP生成機能が存在し、Rustアダプタで活用できる余地があります。 

Joern は CPG により AST・制御フロー・データフローをまとめて扱えるため、C/C++、JavaScript、Python、Go の guard候補の探索には有用です。一方で、公式の現行対応一覧には Rust がありません。従って「6言語の意味層」として採用することはできず、**一部言語で候補発見力を上げる補助バックエンド**と位置付けるべきです。 

CodeQLについては、文書の「Rust非対応」は現在は古くなっています。CodeQL は Rust を含む対象言語をサポートしており、2025年には Rust と C/C++ の build-free scanning が一般提供されたと案内されています。ただし、これは「任意の壊れたプロジェクトを完全に意味解析できる」ことを意味しません。CodeQL抽出器がどの構成・依存・マクロ展開・ビルド情報を復元できたかを、必ず解析成果物として保存する必要があります。 

### Q2. 暫定案の評価

暫定案は **60%正しく、40%危険**です。

正しい部分は以下です。

- tree-sitter を共通の構文フォールバックにする。
- 動的機構について完全検出を約束せず、検出不能性を表面化する。
- 言語ネイティブの構文・意味ツールを併用する。
- 契約を確定せず、候補と証拠に留める。

危険な部分は以下です。

- 「tree-sitter / Joern / native AST」という三層を、全言語で同じ能力を持つ解析パイプラインとして扱うこと。実際には Rust、C++、Pythonで大きな能力差があります
- Joernを“guardとデータフローを扱える唯一の層”と見なすこと。CodeQL、各言語のCFG/型解析器、独自の構文・CFG抽出でも一部は可能です。ただし同じ定義・精度・欠落条件にはなりません
- 正規化したAST文字列の一致を意味的等価性とすること
- コンパイラ／LSPが失敗したとき、構文抽出だけで「関係がない」と出力してしまうこと

特に C/C++ について、意味解析に必要なコンパイルコマンドはコンパイルデータベースに記録されます。`compile_commands.json` の各エントリには、翻訳単位、作業ディレクトリ、実際のコンパイルコマンドが含まれます。 したがって、これがない C/C++ プロジェクトに対して Clang AST の完全性を期待する設計は誤りです。 

推奨する能力モデルは、各結果に次を持たせるものです。

```json
{
  "analysis_mode": "syntax_only | partial_semantic | configured_semantic | runtime",
  "coverage": {
    "files_discovered": 0,
    "files_parsed": 0,
    "files_with_error_nodes": 0,
    "files_semantically_resolved": 0,
    "configs_enumerated": 0,
    "configs_analyzed": 0
  },
  "limitations": [
    {
      "code": "CPP_NO_COMPILE_COMMANDS",
      "scope": "src/**",
      "effect": "include resolution, macro expansion, type resolution incomplete"
    }
  ]
}
```

これにより「何も検出されなかった」と「その領域を意味解析していない」を機械可読に分離できます。

### Q3. 見落とし得る技術

優先度順に挙げます。

- **CodeQL**：Rust対応は現在あります。複数言語にまたがるデータフロー・制御フロー・構文問い合わせの一候補として、再評価すべきです。ただし対象プロジェクトの状態に対する抽出可能性を、実測ベンチマークで確認してください。 
- **SCIP**：共通スキーマの代替ではなく、定義・参照・symbol identity を受け渡すための副次的な共通形式として有効です。E5、E10、E15、E16に直接効きます。 
- **rust-analyzer のバッチ索引**：Rustの参照、定義、hover、symbol metadata を静的索引として出力できます。最初のRust対象には tree-sitterだけより有力です。 
- **Clang compilation database**：C/C++における「ビルドしない意味解析」の現実的な入口です。ビルドを実行しなくても、既存の `compile_commands.json` を読むことで、翻訳単位ごとのフラグ・作業ディレクトリ・インクルード条件を再生できます。 
- **言語別テスト収集器**：テスト探索は共通ASTだけに頼らず、Rust `#[test]`、Vitest/Jest/Mocha の呼出形式、Goの `TestXxx` と `ExampleXxx`、Python pytest fixture/parametrize/unittest、C++ の GoogleTest/Catch2/doctest を検出する言語別ルールとして設計してください。テストフレームワークの「登録規約」は言語構文より重要です
- **Gitの系譜情報**：R4だけでなく、E10の独立性近似にも使えます。テストと実装が同一コミット／同一PR／同一変更系列で導入されたなら、別ファイルでも独立証拠として数えない強い根拠になります。ただし、共同変更は同じ設計意図を証明しません

### Q4. 言語ごとの品質差

品質差は **許容すべき**です。ただし、隠してはなりません。

「6言語すべてで同じ品質」は、解析深度まで同じにする意味では幻想です。C/C++は構成依存の前処理、RustはマクロとCargo feature、TS/JSは構成・bundler・型有無、Pythonは実行時変更を持ち、言語が提供する静的意味情報の上限が違うためです。 

品質を揃えるべき場所は、意味解析能力ではなく **報告の契約**です。

- 各言語で E1〜E16 ごとに `not_attempted`、`attempted_partial`、`attempted_complete_under_config`、`unsupported_in_principle` を返す
- 各抽出物に `evidence_mode`、`resolution_status`、`configuration_id`、`source_span` を必須化する
- 各候補に「何を検出したか」だけでなく「何を解析できなかったか」を付ける
- 言語ごとの capability matrix をバージョン管理し、欠落を仕様として公開する
- 人間に示す画面で、候補数より先に coverage と blind spots を表示する

つまり品質の均一性は「同じ答えを出す」ことではなく、**同じ誠実さで不確実性を伝える**ことです。

## Q5–Q7：契約・等価性・動的機構

### Q5. 契約候補の抽出

結論は明確です。**guardから契約の種類を決定することはできません。** 構文、局所データフロー、テスト、コメント、Git履歴を組み合わせても、「これは呼出側が守る事前条件か」「この関数が防御しているだけか」「歴史的遺物か」は最終的に設計判断です。 

ただし、契約候補の発見と優先順位付けはできます。E7/E8/E11を「契約抽出」ではなく、次の二段階へ分割してください。

1. **決定論的な候補事実抽出**
   - 条件式、支配する分岐、早期return、`throw`、`panic`、`assert`、`unwrap`、`expect`
   - 返却するエラーvariant、エラーコード、ログ、計測、例外型
   - 引数・フィールド・グローバル・I/Oへの読み書き
   - ループの条件、状態enum、状態フィールドへの代入、状態遷移表らしい `match` / `switch`
   - テストに出る入力境界値、例外期待、property assertion、fixtureの前提
2. **非決定論的な意味候補生成**
   - 「`x != 0` を満たさないと `DivisionByZero` を返す」
   - 「状態 `Closed` から `send` は失敗する」
   - 「成功時、出力長は入力長以下である可能性がある」

重要なのは、候補文を「仕様」ではなく **ソース上で反証できる観測命題**に制限することです。

悪い候補:

> `send` の事前条件は接続済みである。

良い候補:

> `send` の本体には、receiver の状態が `Connected` でない場合に `NotConnected` を返す分岐が存在する。呼出側責務か内部防御かは未裁定である。

人間への給仕は、候補単体ではなく「判定束」にしてください。

- guard の原文・構文正規形・`file:line`
- その条件に支配される成功経路と失敗経路
- エラー／例外／panicの到達先
- 同一条件または否定条件を持つ呼出側
- 関連テスト、期待される例外、境界入力
- コメント／docstring。ただし実装由来の可能性を明記
- 導入・変更・削除のGit履歴
- 解析に失敗したdispatch／macro／reflection境界
- 「precondition / defensive check / invariant / unresolved」の選択肢と、その選択が変える反証条件

状態機械も、一般に自動復元できるのは **状態遷移候補グラフ**までです。特にPythonの属性更新、JSのオブジェクト変異、Rustのtypestate、C++のRAII・例外経路では、一つの“状態変数”に還元できない場合があります。状態機械の確定版を出すのでなく、次のような根拠付き候補を出すのが適切です。

```text
state_candidate:
  carrier: Connection.status
  states_seen: [Idle, Connecting, Connected, Closed]
  transitions_seen:
    - Idle -> Connecting at src/connection.rs:81
    - Connecting -> Connected at src/connection.rs:112
    - Connected -> Closed at src/connection.rs:155
  missing:
    - Dynamic callback target unresolved at src/connection.rs:127
  classification: inferred
```

JoernやCodeQLのCFG・データフローは「どのチェックがどの失敗出口や副作用を支配するか」を求めるのに役立ちます。しかし、そこから契約の規範性や歴史的正当性は出ません。JoernはCPGを通じた横断解析基盤ですが、Rustを含む均一な6言語解にはなりません。 

### Q6. E13：等価性判定

文書の「公式AST＋公式プリンタで意味等価を判定する」前提は棄却してください。次表の用途は **構文正規化・差分ノイズ削減** に限るべきです。

| 言語 | 構文正規化候補 | 正確に言えること | 言えないこと |
|---|---|---|---|
| Rust | `syn::parse_file` + `prettyplease::unparse` | `syn` が表せる範囲でのAST丸め・整形一致 | macro展開後の挙動、型・trait解決、cfg条件下の意味等価 |
| TS/JS | TypeScript Compiler API `createSourceFile` + `createPrinter` | TS/JS構文木を再印字した一致 | 型検査、モジュール解決、実行時dynamic property・evalの等価 |
| Go | `go/parser` / `go/ast` + `go/format` または固定版`gofmt` | Go構文の正規化 | build tags、型情報、整数・浮動小数点・副作用を跨ぐ代数的同値 |
| Python | `ast.parse` + `ast.unparse` | Python ASTに関する往復可能な表現 | 元ソース一致、コメント・空白・実行時メタプログラミングの同値 |
| C | Clang AST dump/独自canonicalizer、または token/preprocessor trace | 固定コンパイルコマンド下の一翻訳単位の構文・一部意味情報 | 全構成での意味等価、マクロ・UB・ABIを跨ぐ同値 |
| C++ | Clang AST/AST matcher + 固定compilation database | 固定構成下のAST事実 | テンプレート実体化・ODR・マクロ・条件コンパイルを跨ぐ全体同値 |

Rustについて、`prettyplease` は `syn::File` の構文木を整形済みソースへ戻すプリンタです。しかしこれは `rustc` の公式AST／公式プリンタではなく、`syn` のAST用のサードパーティクレートです。コメントが脱落し得る点も、証拠位置やドキュメント証拠を扱う用途では注意が必要です。 

TypeScript Compiler API は `SourceFile` のASTとPrinterを提供し、`createProgram` を用いれば型検査も利用できます。しかし `createSourceFile` だけは構文解析であり、意味情報は持ちません。 

Goの `go/format` は標準の整形を提供しますが、Go自体のドキュメントは、整形が時間とともに変わり得るため、再現性を必要とするツールは固定バージョンの `gofmt` を実行するよう注意しています。ここはあなた方の「ハッシュで固定できる」制約に直結します。 

Python `ast.unparse()` は「再びパースしたとき等価なASTを作るコード」を生成するもので、元のソース文字列と一致するとは保証しません。従ってコメント・書式・一部の表記の証拠性は失われます。 

C/C++に「libclang＋clangのプリンタ」という、GoやPythonに相当する単純な公式ペアがあるという理解は正確ではありません。Clang ASTは提供されますが、ソースを忠実かつ一意に再生成する一般目的の公式アンパーサを、TCEの基盤として期待すべきではありません。プリプロセッサ、マクロ展開、複数のソース位置、テンプレート、条件コンパイルがその理由です。ClangのASTを使うツールは、通常、コンパイルデータベースによる構成情報を必要とします。 

マクロと生成コードは、**展開前と展開後の両方を別物として保持**してください。

- 展開前：ユーザーが保守するソース上の責務、`file:line`、レビュー可能性、設計意図の手がかり
- 展開後：固定構成における型検査・名前解決・実行意味に近い解析
- 両者の関係：`origin_span`、`expansion_span`、`configuration_id`、`generator_identity` を使った多対多の来歴グラフ

E13の実用的な分類は、以下の順で止める設計がよいです。

1. テキスト同一
2. トークン正規化同一
3. AST正規化同一
4. 限定規則による局所書換え同値
5. コンパイラ／型検査器が同一IRや同一診断を出すという限定的観測
6. テスト・property・差分実装で区別できなかった
7. `unknown`

段階4以上は、言語・型・評価順・副作用・算術モデル・構成条件を明示しなければ危険です。「等価」と一語で集約しないでください。

### Q7. E6：動的機構の検出可能性

静的に決定論的にできるのは、**動的機構を使う構文的入口を列挙すること**であり、一般に「実行時にどの結合が実現するか」の完全列挙ではありません。

| 言語 | 静的に高確度で検出可能 | 限定条件下で追跡可能 | 原理的・実務的に完全追跡不能 |
|---|---|---|---|
| Rust | `extern`、`#[link]`、`include_*`、`macro_rules!`定義・呼出、`build.rs`、`cfg`、trait object型、`unsafe`境界 | Cargo metadata・固定feature下のmodule/依存、既知macroの展開 | proc macroの任意I/O、`dlopen`先、任意関数ポインタ値、外部環境依存 |
| TS/JS | static import/export、literal `require` / dynamic import、`eval`、`Proxy`、decorator、DI API、package manifest | literal specifier、既知frameworkの登録規約、固定tsconfig/package exports | 非literal module path、任意eval、monkey patch、動的property、環境・ネットワーク入力 |
| Go | import、`init`、`reflect`呼出、`plugin`、`go:generate`、struct tag、build tag | 固定build tagとGOOS/GOARCH下の型解析、既知reflection規約 | `reflect.Value`経由の実呼出、plugin内容、生成物未存在、外部設定 |
| Python | import文、`importlib`、`getattr`、`setattr`、`eval`/`exec`、metaclass、decorator、entry point API | literal module/name、既知frameworkの登録規約、型注釈のある範囲 | 任意コード実行、import hook、monkey patch、動的属性、plugin discovery、実行順序依存 |
| C/C++ | `#include`、macro定義・呼出、`dlopen`/`dlsym`、関数ポインタ、virtual、weak symbol、pragma、linker属性 | `compile_commands.json` の固定構成、関数ポインタの局所points-to、仮想呼出の限定CHA | macro構成全体、任意ポインタ値、ABI・リンカ・ロード順、外部ライブラリ、UBを含む実挙動 |

C/C++は、固定されたコンパイルコマンドなしに「正確なAST」すら定義しにくいという意味で、文書の予想は正しいです。`compile_commands.json` は翻訳単位をどうコンパイルしたかを再生するための情報であり、これがない場合のClang解析は、解析器が勝手に選んだ近似構成に過ぎません。 

人間への可視化は「動的機構なし」ではなく、次の四値にしてください。

```text
dynamic_surface:
  status:
    - absent_under_scanned_patterns
    - syntactically_present_unresolved
    - partially_resolved_under_configuration
    - runtime_observed
  confidence: high | medium | low
  unobserved_channels:
    - process environment
    - generated files unavailable
    - unresolved reflective name
    - missing compilation database
```

たとえば `require(variable)` を検出した場合、出力すべき命題は「動的ロードがない」ではなく、**「動的ロード呼出が存在し、モジュール指定子が静的に解決不能である」**です。これこそが失敗5への防御になります。

## Q8–Q10：スキーマと沈黙

### Q8. 単一スキーマで壊れる意味

現行スキーマは「抽出物の共通メタデータ」としてはよいですが、言語概念を `kind` と `detail` だけに押し込むと、後で必ず意味が壊れます。

| 概念 | 同一箱に入れると起きる嘘 | 必要な表現 |
|---|---|---|
| Rust trait | associated type、default method、blanket impl、object safety、coherenceを失う | `relation_kind=trait_impl` とRust固有detail |
| Go interface | 明示宣言なしの構造的実装を、宣言的継承のように誤認する | `evidence=method_set_satisfies`、対象package/config |
| TS structural typing | 代入可能性をnominalなimplements関係と誤認する | `relation_kind=assignable_under_checker`、compiler options |
| Python属性 | `obj.x` を確定した属性参照と誤認する | `resolution_status=dynamic/unknown`、runtime hookの兆候 |
| C++ template | template定義を実体化済み関数と混同する | `template_phase=definition/instantiation`、compile config |
| C/C++ macro | 呼出地点と展開地点の一対一対応を仮定する | `spelling_span` と `expansion_span` の分離 |
| module/import | import構文を実行結合そのものとみなす | `edge_kind=syntactic_import | resolved_module | runtime_observed` |

したがって、単一スキーマを維持するなら、最低限次を追加してください。

```text
identity:
  symbol_id: optional, namespaced, configuration-scoped
  symbol_resolution: resolved | partial | unresolved | not_attempted

source:
  spelling_span: file/line/column
  expansion_spans: zero-or-more
  generated_origin: optional

semantics:
  relation_kind: closed vocabulary
  analysis_mode: syntax_only | semantic_partial | semantic_configured | runtime
  configuration_id: optional
  confidence: not a probability; evidence-bound category

portability:
  common_detail: cross-language normalized fields
  language_detail: lossless raw language-specific payload
```

重要なのは、**共通化は“上位の検索・集計用”にだけ使い、言語固有データを破棄しない**ことです。単一スキーマは単一意味論ではありません。

### Q9. `derivation_group` の決定論的計算

「同じ派生元」をソースから真に判定することはできません。よって `derivation_group` という一つのIDに、人間の設計因果と機械的系譜を混ぜないでください。

代わりに、複数の独立性関係を明示的なグラフで持つべきです。

| 関係 | 機械判定 | 強さ | 用途 |
|---|---|---|---|
| 同一構文起源 | 同じAST node/span、macro展開関係 | 高 | 同一コード由来の重複除去 |
| 同一生成起源 | 同じgenerator、入力、生成時刻/ハッシュ | 高 | 生成コードと源泉の重複除去 |
| 同一変更系列 | 同一commit、PR、patch-id、blame範囲 | 中 | 実装・テスト・コメントの共同導入を控除 |
| 同一データフロー起源 | 同じ定義、同じguard、同じerror pathを参照 | 中 | 同じ実装分岐を複数証拠として数えない |
| 類似文言 | コメント・テスト名・docstring類似 | 低 | 人間レビュー候補。自動統合禁止 |
| 同一設計意図 | ソースだけでは不能 | 不明 | 人間が裁定 |

実装上は `derivation_group` を一意IDにせず、以下のようにします。

```json
{
  "evidence_id": "ev:...",
  "lineage_edges": [
    {
      "relation": "same_guard_ast",
      "target": "ev:...",
      "confidence": "high",
      "basis": ["src/x.rs:42-46"]
    },
    {
      "relation": "cointroduced_in_commit",
      "target": "ev:...",
      "confidence": "medium",
      "basis": ["git:abc123"]
    }
  ],
  "independence_assessment": "unknown"
}
```

そして、命題台帳での証拠本数は単純な本数ではなく、「強い系譜エッジで結ばれた連結成分を一票とする」などの**明示的な集計ポリシー**にします。ポリシーと入力エッジを保存すれば、後から人間が訂正できます。

テストが同一commitで実装と追加されたからといって、常に独立でないとは限りません。一方で、そのテストが同じ分岐を直接検査しているなら独立性は低い可能性が高い。この判断は「事実」として出してよく、「独立でない」という結論は `inferred` に留めるべきです。

### Q10. ビルド不能時の沈黙

沈黙を検出できます。ただし、ツールが黙ることを検出するには、**期待された解析単位の母集団**を先に固定する必要があります。

必須の出力は「成功した抽出物」だけではなく、ファイル・構成・ツールごとの解析試行台帳です。

```text
analysis_attempt:
  target: src/foo.cpp
  configuration: config:linux-clang-17-debug
  tool: clang-adapter@<digest>
  phase: parse | preprocess | name_resolution | typecheck | cfg | dataflow
  status: success | partial | failed | skipped
  diagnostics: [...]
  extracted_count: 0
  reason: missing_compile_command | parser_error | dependency_missing | timeout | unsupported
```

この形式にすると、`extracted_count: 0` が「解析したが該当物なし」なのか「解析できなかった」なのかを区別できます。

言語別の典型的な沈黙点は次です。

- Rust：Cargo workspace・feature・target・proc macro・依存クレートが揃わず、名前解決やmacro展開が部分的になる
- TS/JS：`tsconfig` の継承、path mapping、package exports、JS/TS混在、bundler解決規則の不在で、import先や型解析が不完全になる
- Go：module cache、build tags、GOOS/GOARCH、生成済みGoファイルの不在でpackage解析が部分化する
- Python：実行時import、依存パッケージ、stub、import hook、framework登録規約により、静的名前解決が不完全になる
- C/C++：`compile_commands.json`、include path、`-D`、`-std`、target、generated headerの不在により、ASTと型検査の前提そのものが崩れる。 

「ビルドはしない」と「ビルドメタデータを読まない」は別です。対象を変更せず、ビルドを実行せずとも、`Cargo.toml`、`Cargo.lock`、`package.json`、`tsconfig*.json`、`go.mod`、`pyproject.toml`、`requirements*.txt`、`compile_commands.json`、CMake/Ninja/Bazel設定を**読み取り専用で収集**するべきです。

## Q11–Q12：運用とテスト生成

### Q11. Node.jsからの運用設計

Node.jsはオーケストレータとして適切ですが、6言語の全意味解析をNode内で実装しようとしてはいけません。対象プロジェクトと解析器を分離した、再現可能な実行環境を作ってください。

推奨するディレクトリ概念は次です。

```text
conver/
  analyzers/
    core/
    adapters/
      rust/
      typescript/
      go/
      python/
      clang/
  toolchains/
    lock/
  schemas/
  fixtures/
  golden/
  runner/
```

対象リポジトリ側には、原則として一切書き込みません。

- 解析出力、SQLite DB、SCIP index、CodeQL database、ログ、キャッシュ、temporary file はすべて conver 側の作業ディレクトリに置く
- 対象は read-only mount または少なくとも書込み検出付きで開く
- `HOME`、`TMPDIR`、`XDG_CACHE_HOME`、`CARGO_HOME`、`GOMODCACHE`、`npm` cache、Python cache を解析用作業ディレクトリにリダイレクトする
- ネットワークを既定で遮断し、依存取得をしない。依存の欠落は解析失敗として記録する
- ツール本体と文法、query、ルール、adapter、コンテナ／Nix／OCI image digest、OS/arch、環境変数、実行コマンドをmanifestに残す
- 実行ごとに対象ファイルのcontent hashと解析ポリシーhashを記録し、結果の再現性を照合する
- 解析器自身の更新は、golden corpusに対する差分を必ずレビューする

Goの整形出力を再現性に使うなら、固定バージョンの `gofmt` を実行するという公式の注意に従うべきです。標準ライブラリの整形仕様は時とともに変わり得ます。 

C/C++では `compile_commands.json` を対象側から読取り専用で取り込み、出力先にコピーしてパスを仮想化する方式がよいです。ただし、その中の絶対パス・外部SDK・生成headerが対象スナップショット外を参照する場合は、再現不能として必ずmanifestに残してください。 

また、ツールのバージョン固定だけでは不十分です。結果は少なくとも以下に依存します。

- 解析器バイナリと文法のバージョン
- OS、CPUアーキテクチャ、C標準ライブラリやSDK
- 言語ツールチェインと標準ライブラリ
- package/module cache の内容
- 環境変数
- feature flags、build tags、target triple
- 入力ツリーの全ファイルハッシュ
- 時刻・乱数・ネットワークアクセスの遮断状態

### Q12. E14：既知カテゴリに限定したテスト生成

生成対象は、言語ごとに微調整してよいですが、中心カテゴリは共通にすべきです。まず「ソースから見えた事実」をテスト化し、規範的契約を自動生成しないことが重要です。

推奨カテゴリは以下です。

| カテゴリ | 生成する性質 | 生成しないもの |
|---|---|---|
| パーサ・シリアライザ | round-trip、parse成功後の再serialize、invalid input拒否 | 意味論を伴うcanonicalizationの正しさ |
| 境界値guard | 空、最小/最大、境界直前直後、null/None/undefined、不正enum | guardが呼出側責務だという主張 |
| 純粋関数 | 決定性、参照透過的な再実行、入力非破壊 | 外部状態を含む関数の同一出力 |
| collection変換 | 長さ、要素保存、順序保存または順序非保証の明示 | 実装由来の並び順を仕様化すること |
| encode/decode | `decode(encode(x)) ≈ x`、サイズ制限、拒否ケース | 表現が唯一であるという主張 |
| 状態遷移候補 | 明示された拒否遷移、success/failure後の局所状態 | 完全なプロトコル仕様 |
| エラー型 | 既知の入力で既知のエラーvariantが返る事実 | エラーが望ましいAPI契約という規範 |
| 差分比較 | 参照実装・旧版・別backendとの一致範囲 | 同一実装から作ったoracle |

言語別PBTの使い分けは、生成器の実装面では有効です。

- Rust：`proptest` / `quickcheck` 系。`Arbitrary`、範囲制約、shrinkを活用
- TS/JS：`fast-check`。JSON値、文字列、配列、tagged union、schema由来生成に向く
- Go：標準のfuzzingと `rapid` / `gopter` 等。byte入力からのfuzzと型付き生成を分離
- Python：Hypothesis。例外・境界・stateful testingを含む強力なshrinkingを活用
- C/C++：RapidCheck、Catch2 generators、libFuzzer/AFL++の入力探索を別枠で利用

ただし、PBTライブラリは **テストケースを生成するエンジン**であり、正しいpropertyを発明する機構ではありません。propertyが実装の分岐を言い換えただけなら、あなた方が恐れる「共犯のoracle」になります。 

自動生成するテストには、必ず以下を付けてください。

```text
property_origin:
  source_fact: src/parser.rs:88-101
  category: decode_encode_roundtrip
  oracle_independence:
    - implementation-derived
    - external-format-derived
    - differential
    - metamorphic
  status: generated_candidate
  requires_human_approval: true
```

特に強い証拠になるのは、次の順です。

- 外部標準、RFC、プロトコル仕様、ファイルフォーマット仕様に由来するoracle
- 独立実装との差分oracle
- 変成関係。ただしその関係自体が外部仕様または数学的性質に根差す場合
- 実装から抽出した局所的な事実
- 実装から逆算した期待値

最後の二つは「現実装を記述する」用途では価値がありますが、「現実装が正しい」根拠にはなりません。

## 最終提言

採用判断を一文で述べるなら、次です。

> **tree-sitterを“全言語・全状態で必ず動く構文的証拠採取器”として固定し、言語ネイティブ解析、SCIP、CodeQL、Joern、Clangを“能力宣言付きの追加証拠器”として接続し、契約・独立性・等価性の確定は絶対に自動化しない。**

具体的には以下を決定してください。

1. 共通コアの責務を E1–E10 のうち「構文的に観察できる事実」に限定する  
2. E11、E13、E14を、確定出力ではなく候補・限定的判定・人間承認待ちとして型レベルで分離する  
3. `observed` を静的ソース観測と実行時観測に分ける  
4. `derivation_group` を単一IDから系譜グラフへ変更する  
5. C/C++は `compile_commands.json` の有無を品質境界として明文化する  
6. Rustは tree-sitterだけで終えず、rust-analyzerのSCIP出力またはCodeQLの実測評価を最初の50k LOCコーパスで行う  
7. 各言語・各E項目について「成功、部分成功、未試行、失敗、原理的限界」を必ず出力する  
8. 順回転済みの正解コーパスとの照合では、精度点数ではなく、**誤りの種類と未観測の種類**を差分として残す

この構成なら、6言語の能力差を消せなくても、能力差がRFC再構成の中で見えなくなるという、最も危険な失敗を防げます。これは文書が最初から掲げている「機械は成功を宣言せず、証明できたことと証明できなかったことだけを言う」という原則に最も整合的です。
