## エグゼクティブ・サマリ（結論）

現在の R0〜R8 の設計は「静的解析の極大化」としては非常に優れていますが、「歴史的偶然・技術的負債・潜在バグ」を「正典（仕様）」としてロックインしてしまう危険性（追認 RFC の高度化）を防ぎきれません。本設計が L3（完全成功）に到達するためには、1) **動的実行トレースによる静的解析の補正**、2) **AI が判断を誤る前の早期の手動介入（Early HITL）**、3) **等価ミュータントを排除した高度な Red 再建** の 3 点の組み込みが不可欠です。

## 4. 依頼 4 — 妥当性の検証（欠陥・誤り・危険の指摘）【最重要】

この設計における最大の論点と、根底を揺るがしかねない欠陥を指摘します。

### 4.1 新たな失敗モード「F11: 未定義動作・バグの正典化」の存在

* **指摘:** F1（追認 RFC）は「既存の挙動を追認してしまう」ことですが、それ以上に危険なのは「既存のバグや、たまたま動いている未定義動作（歴史的偶然）を、『絶対の仕様』として正典化してしまうこと」です。
* **症状:** 逆回転パイプラインが、「入力が Null の時は DB をロックしたままタイムアウトする」という既存のバグを観測し、それを **`ORIGIN-LONG-SPEC` の必須契約（Postcondition）として記述**してしまう。後続の順回転パイプラインは、このバグを忠実に守るようにテストと実装を生成し続けます。
* **対策:** R3（意味論素材）および R5（矛盾）において、「エラーハンドリングの非対称性」や「デッドロックの可能性」などの**Code Smell を静的解析で検知した場合、それを自動的に `unresolved`（人間への residual）へ隔離**し、決して `observed` な仕様として AI に確定させない（Gateを設ける）必要があります。

### 4.2 §7.7 段階的・増分戦略の「スパイク方式」に対する致命的欠陥

* **指摘:** 「1ディレクトリで全工程を1周し、成否を判定する」というスパイク方式は、順回転（トップダウン）では機能しますが、**逆回転（ボトムアップ）では原理的に破綻**します。
* **根拠:** リバースエンジニアリングにおいて、モジュール `A` の仕様（契約）は、モジュール `B` が `A` をどう使っているか（Incoming Dependencies）を見なければ確定しません。1ディレクトリ単体で R0〜R8 を回すと、外部からの利用文脈（「なぜその関数が存在するのか」）が欠落するため、AI は 100% 誤った（または極端に矮小化された）追認 RFC を生成します。
* **提案する変更:** スパイク方式を「ドメイン横断的な薄いスライス（Thin Slice）方式」に変更すべきです。1つのディレクトリではなく、「1つの主要なユースケース（例: ログインからDB保存まで）が通る全ディレクトリの特定の実行パス」を対象に R0〜R8 を走らせる方が、遥かに成功率（L3到達率）が高くなります。

### 4.3 「物理ディレクトリ ＝ 論理境界」という仮定の危険性

* **指摘:** §3.6 の適格条件に「ディレクトリ構造に意味がある」とありますが、レガシーシステムでは「物理的なディレクトリ構造」と「論理的なドメイン境界」が乖離しているのが常です。
* **根拠:** `T1（構造一致）` は、既存の実測ディレクトリ集合を `TREE-MANIFEST` と一致させることを要求（A1 安全保証の反転）していますが、既存のディレクトリが「歴史的偶然」の産物であった場合、**本設計は「間違ったアーキテクチャ」を強制的に保存し、それを正典として永久凍結**してしまいます。
* **提案する変更:** R1 と R2 の間に、「仮想ディレクトリ再構築（Virtual Restructuring）」の層（AI + 人間の HITL）を置くべきです。既存のファイルパスを変えずに、`WORKSPACIFY-TREE-MANIFEST` 上の論理名前空間（Virtual Namespace）にマッピングする層を持たせない限り、レガシー近代化としては「失敗を仕様化する」ことになります。

### 4.4 結論：「この設計で成功するか」

現在の設計（§6・§7）は、**「L1（一部ディレクトリでの RESIDUE 0）」までは到達可能ですが、「L3（Red再建完了および真の成功）」には到達しません。**

理由は、F2（赤の偽装）を防ぐための「Red 再建」が、結局のところ「既存のテストが何を保証しているか」の文脈理解に依存しているからです。既存テスト自体が間違っている（または不十分な）場合、いくら Mutation（変異）を注入して Red を作っても、それは「偽の仕様に対する自己満足の Red」に過ぎません。

この限界を突破するためには、**「コードには現れないが、ドメインには存在する語彙」を R0 の段階で人間の専門家から `zg` のベクトル検索にシード（種）として注入**し、その語彙にマッチしないコードの挙動はすべて `unresolved` として人間に差し戻す「演繹的制約」を、ボトムアップの解析に掛け合わせる必要があります（トップダウンとボトムアップの挟み撃ち）。

**Q2. Thin Slice（垂直スライス）と Package（水平パッケージ）の併用評価**

単一の Thin Slice（例: リクエスト受信から DB 書き込みまでの1経路）だけでは、パッケージ内部の多角的な不変条件（例: 境界値、異常系状態遷移）を網羅する厚みは得られません。ご提案の「垂直スライスで結合契約、水平パッケージで内部契約」という二段構え（2-Pass Hybrid）は極めて合理的であり、本パイプラインの推奨解となります。

```
Pass 1: 垂直スライス (Vertical Pass)
  └─ 主要ユースケースの実行パスに沿ってパッケージ間の「結合契約（I/O Boundary）」を確定。
Pass 2: パッケージ水平掃海 (Horizontal Sweep)
  └─ Pass 1 で確定した境界の内部に閉じ、パッケージ単体テストと AST 解析で「内部不変条件・状態遷移」を全数抽出。

```

この分離により、Pass 2 実行時に「他パッケージとの相互作用」を考慮する必要がなくなり、AI の判断面積がパッケージ局所に限定されます。

**Q3. JS/TS エコシステムにおける Equivalent Mutant（等価ミュータント）の判定と代替策**

JavaScript/TypeScript のような動的要素を含む言語では、完全な等価ミュータントの静的判定は不可解（Undecidable）です。実用的なアプローチと代替手法は以下の通りです。

**実用的な判定手法・ツール**

1. **TCE（Trivial Compiler Equivalence）の活用**:
Stryker JS などのミューテーションフレームワークで変異コードを生成した後、SWC または Babel/TypeScript Compiler API で AST を最適化・標準化（Minify/Canonicalize）します。**「元コードの AST」と「変異コードの AST」がコンパイル後に完全一致すれば、100% 等価ミュータント**として機械的に廃棄できます。
2. **`ts-morph` による型情報駆動の変異制限**:
単なるテキスト・AST のランダム変異ではなく、TS 型チェッカー（TypeChecker）を利用し、型定義に反する無効な変異や、意味を持たない式変異（例: `void` 関数の戻り値変異）を最初から生成しない手法です。

**動的型付け/メタプログラミング領域における代替策**

コード変異ではなく「不変条件アサーションの無効化（Invariant Mutation）」に切り替えます。

* コードのロジックを書き換える代わりに、R3 で抽出した Guard Clause（`if (!input) throw ...`）や `zod` / `io-ts` などのスキーマ検証、アサーション式のみを一時的に削除（No-op 化）します。
* テストが落ちなければ、「そのアサーション（不変条件）をテストが検証していない（Red 不在）」と確実に判定できます。

**Q5. Oracle 共犯（既存コードとテストの共謀）の破壊と、成功境界の再定義**

**Oracle 共犯を破る最小の追加: プロパティベーステスト（PBT） / メタモルフィックテストの自動生成**

既存テストと実装が共に間違っている場合、既存の単体テストをいくら回しても Red は再建できません。最小の破砕装置は、R3 の不変条件から `fast-check` (JS/TS) 用の **PBT（Property-Based Testing）コードを自動生成すること**です。

```typescript
// R3 の不変条件「返金後の残高は常に 0 以上」から自動生成される PBT コード
fc.assert(
  fc.property(fc.integer(), (refundAmount) => {
    const result = processRefund(account, refundAmount);
    return result.balance >= 0; // 不変条件の検証
  })
);

```

既存の単体テストがパスしていても、PBT が反例（Counterexample）を見つけた瞬間、Oracle 共犯は破壊され、Red の証拠が確定します。

**PBT の生成すら不可能な領域での成功境界（L2.5）の定義**

PBT のジェネレータが組めない複雑な状態依存領域では、成功定義を **「L2.5: 構造的整合性の完全証明 ＋ 未証明 Oracle の明示的隔離」** に下げます。

* **L2.5 の条件**:
1. 静的・動的な型/依存/境界カバレッジが 100% 証明されている。
2. 機械が証明できなかった Oracle 共犯の疑い（テストが単なる `isNotNull` しかしていない等）を、全件 `Tickets.json` 内に `unverified_oracle_risk` としてマーキング完了している。
3. 人間が `/crystalize-readme` にてそのリスク一覧を確認し、手動承認（`APPROVED`）を与えている。



機械は「100% 成功した」と嘘をつかず、「機械的証明の限界に達し、リスクを全数可視化した」状態をもって人間の最終判定へと引き継ぎます。

**結論:** 「案3（RFC-SEED と RFC のみに伝播させ、GRAPH / Dirs-Tree / Tickets は RFC の ID を間接参照する）」が最適解です。

初期の評価軸（provenance追跡のコスト、順回転スキーマの保護、進化ループの駆動、欠落の逆探知）および既存制約との突合は検証済みです（案1はハッシュ不変条件や既存スキーマを広範に破壊し、案2は外部参照化によりAIへの文脈供給を分断するため棄却）。

本案を採用する最終的なアーキテクチャ上の根拠は以下の通りです。

* **正典への集約**: conver の順回転は「RFC 設計書が正典（canon）である」という大前提で稼働しています。不確実性メタデータ（claim_id / residual_id 等）を正典である RFC-SEED と RFC にのみ注入することで、中間生成物（`*-GRAPH.json` や `Tickets.json`）のスキーマやハッシュ計算を一切改変せずに済みます。


* **間接参照による逆探知**: 下流の実装ループやグラフは元々 RFC のノード（要件）を間接参照する構造を持っています。そのため、`/find-omissions` や `/crystalize-readme` が実装の欠落や RESIDUE を検出した際、既存のポインタを辿るだけで自動的に RFC 層の不確実性記述へと遡ることができます。


* **進化ループの駆動**: `/drill-rfc-down` は正典である RFC を起点として差分更新を行う責務を持ちます。進化の判断材料となる不確実性や妥協の記録が RFC 層に直に存在することで、AI は別ファイルの sidecar を照合することなく即座に再評価を実行できます。
