# TMP001 — Mechanical Distribution to RFC.md, GRAPH, Dirs-Tree, and Tickets

Status: design only. The PX-306 implementation described in §2 is committed; the
distribution-map design in §4 onward is not implemented.

Audience: an implementation session that has no access to the conversation that produced
this document. Everything needed to implement, test, and verify the design is stated here.

---

## 1. Goal

Make the distribution of every sequence, operation, boundary and surface unit from the
SEQUENCES view to the four downstream artifacts **mechanical**:

1. each package `RFC.md`;
2. the package's `*-GRAPH.json`;
3. the package's `*-Dirs-Tree.json`;
4. the tickets in `Tickets.json`.

The distribution must not depend on an AI judgement at distribution time. It must survive
the evolution loop, which rewrites `RFC.md` after the first pass. It must respect the
existing command arguments and the existing execution directories.

The guarantee is about **ids and mappings**, not about prose semantics. Whether an RFC
paragraph correctly describes a unit remains a review question; the certificate residue
already states that limit. The design closes the question "did every distributed unit
reach every layer, and did every layer invent nothing?".

## 2. Background

### 2.1 Pipeline order and execution directories

The pipeline is:

```
/workspacify-*  ->  /educe-sequences  ->  /explain-seed  ->  /grill-me-for-rfc
    ->  /smooth-sequences  ->  /graphify-rfc  ->  /boundify-graph  ->  /split-to-tickets
```

The execution locations are fixed:

| Command | Working directory | Existing input contract |
|---|---|---|
| `/workspacify-tree` | workspace root | specification path |
| `/workspacify-allocate` | workspace root | tree manifest path |
| `/workspacify-order` | workspace root | existing arguments |
| `/educe-sequences` | workspace root | specification path |
| `/explain-seed` | each package directory top | `RFC-SEED.md` path |
| `/grill-me-for-rfc` | each package directory top | material file/directory arguments |
| `/smooth-sequences` | workspace root | workspace root / existing flags |
| `/graphify-rfc` | each package directory top | **`RFC.md` only** |
| `/boundify-graph` | each package directory top | `*-GRAPH.json` |
| `/split-to-tickets` | each package directory top | `RFC.md`, `*-GRAPH.json`, `*-Dirs-Tree.json` |

Hard constraints:

- The command arguments must not change.
- If a stage needs information that is not in its current arguments, that information must
  travel through an artifact the stage already reads, not through a new argument.
- `/graphify-rfc` must continue to take only `RFC.md`. A sidecar map passed to graphify is
  therefore forbidden.
- `/workspacify-*`, `/educe-sequences` and `/smooth-sequences` run at the workspace root.
  The other commands run at each package directory top.
- Script paths in the command files keep their existing convention. This design does not
  change how a command locates the conver scripts; it only adds data files inside the
  package directory and inside the artifacts those commands already read.

### 2.2 Where the view comes from

The per-package `SEQUENCES.json` is produced by:

```bash
node .claude/scripts/sequences-slice/run.mjs "<workspace>/<spec>-sequences.json" "<package-dir>"
```

This projection is generated during `/grill-me-for-rfc` (the command already invokes it).
The view is generated; it must not be hand-edited. It carries four unit arrays:

- `ownedOperationUnits` (`op-<operationId>`)
- `ownedSequenceUnits` (`seq-<sequenceId>`)
- `crossBoundarySequenceUnits` (`xdir-<sequenceId>`)
- `obligationUnits` (`ctr-<boundaryId>`, `obl-<surface>`, and `op-`/`seq-` assignments)

The distribution ledger is an appendix inside each package `RFC.md`. It is currently
authored by the AI during `/grill-me-for-rfc`; the gates only read and validate it.

### 2.4 What PX-306 does not close

1. **The RFC ledger and anchors are still authored by AI.** There is no writer that
   derives the ledger, the anchors and the unit→section mapping from the view.
2. **`/graphify-rfc` does not read the view.** It reads only `RFC.md`; if the RFC does not
   carry the units, graphify cannot know them.
3. **The view→ledger link is not wired into `/split-to-tickets`.** The gate supports
   `--view`, but the split command currently passes only `--graph` and `--ledger`.
4. **An empty ledger passes.** If the RFC carries no ledger, the comparison set is empty
   and the gates are vacuously green.
5. **The registry chain is optional.** If `ALLOCATE_MANIFEST_PATH` is unset, the boundary
   registry → graph → ticket checks are skipped.

### 2.5 Measured mapping feasibility in the current corpus

Measured on `~/shyme/gaia` (29 packages, 627 units):

- unit id or subject appears in exactly one RFC heading: **80 / 627**
- appears in no heading: **529 / 627**
- appears in two or more headings: **18 / 627**

Example: `ctr-boundary-001` in `gaia-foundation/RFC.md` appears in prose and in the
ledger but not in a heading. `ctr-boundary-051` in `gaia-asset/RFC.md` appears in two
headings.

Therefore a rule of the form "derive unit→section by matching the unit token against
headings" cannot work on the current corpus. The mapping must be **declared**, not
inferred. The existing `Distribution ledger` "RFC location" column is such a declaration;
it is authored, but it is a frozen input, not a distribution-time guess.

### 2.6 Rejected approaches

These approaches are known to be contradictory or unsafe; do not implement them.

- **Sidecar `SEQUENCES-DISTRIBUTION.json` passed to `/graphify-rfc`.**
  Contradicts "graphify takes only RFC.md".
- **Putting `nodeIds`, `dirs`, `ticketIds` into a map generated during
  `/grill-me-for-rfc`.**
  Those artifacts do not exist at that stage. Contradicts the pipeline order.
- **Heading-token uniqueness as the mapping source.**
  Fails on 529/627 units in the current corpus.
- **An empty ledger passing when the view is non-empty.**
  A no-op gate is not a gate.
- **Letting an AI re-decide the mapping at distribution time.**
  The result is not reproducible and cannot be digested.

## 3. Requirements

| ID | Requirement |
|---|---|
| R1 | Every view unit reaches at least one RFC section, one graph node, one Dirs-Tree entry, and one ticket. |
| R2 | No unit is invented at any layer. |
| R3 | The distribution is deterministic and idempotent; a second run over unchanged inputs is byte-identical. |
| R4 | `/graphify-rfc` reads only `RFC.md`. No sidecar input. |
| R5 | No existing command argument changes. New information travels inside artifacts. |
| R6 | Root commands run at the workspace root; package commands run at the package top. |
| R7 | The mechanism survives the evolution loop rewriting `RFC.md`. |
| R8 | A view with units and no RFC mapping is a failure, not a vacuous pass. |
| R9 | A package with no view and no units keeps its old verdict (additivity). |
| R10 | Every layer records the digest of the mapping generation; stale layers fail. |
| R11 | Writes are atomic; a failed distribution writes nothing. |
| R12 | Every new check has a seeded negative fixture and a positive fixture. |

### 3.1 Constraint compliance matrix

| Constraint | How the design satisfies it |
|---|---|
| Pipeline order (`workspacify` → `educe` → `explain-seed`/view → `grill` → `smooth` → `graphify` → `boundify` → `split`) | The map is written in `grill`, after the view exists and before `smooth`. Graphify, boundify and split only consume the later artifacts. No stage reads an artifact that does not yet exist. |
| Root commands at the workspace root | `workspacify-*`, `educe`, `smooth` read workspace-level inputs and each package's local files by convention; no package command is moved to the root. |
| Package commands at the package top | `grill`, `graphify`, `boundify`, `split` read `./RFC.md`, `./SEQUENCES.json`, `./*-GRAPH.json`, `./*-Dirs-Tree.json`, `./Tickets.json` from the current directory. |
| Existing arguments unchanged | The map is inside `RFC.md`; the digest is inside the artifacts. The only new script has its own flags; the commands invoke it with defaults. The existing command arguments are untouched. |
| `/graphify-rfc` takes only `RFC.md` | The map block, ledger and anchors are in `RFC.md`. No sidecar is passed to graphify. |
| New information travels without arguments | Map digest: RFC → GRAPH → Dirs-Tree → Tickets. View digest: RFC map. Unit sets: view + RFC map. |
| Evolution loop rewrites `RFC.md` | The block/ledger/anchors are preserved regions or regenerated by the renderer; section loss fails; digest mismatch forces downstream rerun. |
| No AI at distribution time | The renderer, graph attach, dirs-tree index, ticket copy and all gates are deterministic scripts. The only authored input is the initial unit→section/ground mapping. |
| Empty ledger must not pass | A non-empty view requires a map; a missing map/ledger is `DISTRIBUTION_MAPPING_MISSING`, not a vacuous pass. |
| Additivity for old packages | No view or empty view: no map required; old verdict unchanged. |

### 3.2 Explicit non-goals

- Proving that the RFC prose correctly designs the unit.
- Proving that every operation the specification needs was enumerated.
- Replacing the `/educe-sequences` census or the certificate residue.
- Choosing the design home of a unit without an authored mapping.
- Editing the live gaia workspace as part of the implementation.

## 4. Architecture

### 4.1 One mapping, inside RFC.md

The only mapping that cannot be derived is **unit → RFC section**. It is declared once and
stored inside `RFC.md`, because `/graphify-rfc` may read only `RFC.md`.

The other layers are derived from the node:

```
unit  ->  RFC section  ->  graph node  ->  directory / file
                                      ->  ticket
```

- The RFC carries the unit→section mapping, the ledger and the anchors.
- Graphify attaches each unit to the node built from its section.
- Boundify ensures every unit-bearing node is mapped to a directory/file.
- Split copies each node's units into the ticket that owns the node.
- No layer re-decides the unit→section mapping.

The map is deliberately minimal: it contains **no** `nodeIds`, `dirs` or `ticketIds`.
Those are produced by later stages.

### 4.2 The `distribution-map` block

Inside the RFC, after the Distribution ledger appendix, write a fenced JSON block:

````markdown
```json distribution-map
{
  "schemaVersion": 1,
  "packageId": "pkg-0001",
  "sourceViewDigest": "<64 hex>",
  "units": [
    {
      "unitId": "op-ProduceFact",
      "kind": "operation",
      "sections": ["3.2 ProduceFact"],
      "ground": "the operation is designed in this section"
    }
  ],
  "residuals": [
    {
      "unit": "CommunityCertificate",
      "ground": "declared residual; not distributed to this package"
    }
  ],
  "digest": "<64 hex>"
}
```
````

Rules:

- `sections` are **exact heading texts** without the leading `#` characters, trimmed.
  Exact text is used instead of token matching. The RFC's G0 deduplication guarantees
  heading uniqueness.
- A unit may list more than one section. Each listed section receives the unit anchor.
  The graph may carry the unit on more than one node; the gate requires at least one.
- `residuals` are ledger rows of kind `declared-residual`. They have no section and no
  anchor. They are preserved from the existing ledger.
- `sourceViewDigest` binds the map to the view. Its computation is defined in §4.3.
- `digest` is the sha256 of the canonical map body **excluding** the `digest` field. Its
  computation is defined in §4.3.
- The block is machine-readable; the ledger table beside it is human-readable. The ledger
  is generated from the block, not the reverse, after bootstrap.

### 4.3 Canonicalization and digests

All digests are SHA-256 over a canonical JSON string:

- object keys sorted lexicographically;
- arrays in the order specified below;
- no insignificant whitespace (`JSON.stringify` of the canonical object);
- UTF-8.

`sourceViewDigest` is computed over a stable projection of the view, not the entire view
file:

```json
{
  "ownedOperationUnits": [{"unitId": "...", "operationId": "..."}],
  "ownedSequenceUnits": [{"unitId": "...", "sequenceId": "..."}],
  "crossBoundarySequenceUnits": [{"unitId": "...", "sequenceId": "...", "ownerPackageIds": ["..."]}],
  "obligationUnits": [{"unitId": "...", "relation": "...", "subject": "...", "direction": "...", "counterpart": "..."}]
}
```

Each array is sorted by `unitId`; `ownerPackageIds` is sorted lexicographically as well.
Missing fields are omitted. This digest changes when the unit set or a relation changes,
and not when unrelated view metadata changes.

Before digesting, `ground` is whitespace-normalized (collapse runs of whitespace, trim).
The ledger renders the normalized text. A formatting-only edit therefore does not churn
the digest; a semantic edit does.

`mapDigest` is computed over:

```json
{
  "schemaVersion": 1,
  "packageId": "...",
  "sourceViewDigest": "...",
  "units": [ ... sorted by unitId ... ],
  "residuals": [ ... sorted by unit ... ]
}
```

The `digest` field is excluded from its own computation.

### 4.4 Ledger format

The ledger appendix title is a heading whose text ends with `Distribution ledger` (the
existing `LEDGER_TITLE_SUFFIX`).

The appendix contains:

1. A precedence sentence containing the word `canonical`, e.g.:
   `RFC.md is canonical for this package; the projection and the generated views are inputs, not authorities.`
2. A summary line naming the unit count.
3. The table with exactly these five columns in this order:

```
| Unit | Kind | Owner | RFC location | Ground |
|---|---|---|---|---|
```

Rows are sorted by `Unit` lexicographically. `Kind` is one of:

| Prefix | Kind |
|---|---|
| `op-` | `operation` |
| `seq-` | `sequence` |
| `xdir-` | `cross-boundary-sequence` |
| `ctr-` | `contract` |
| `obl-` | `surface` |
| residual | `declared-residual` |

`Owner` is the package id. `RFC location` is `§` plus the section number(s), or the
section text when it has no number; multiple sections are comma-separated in the map
order. `Ground` is the map's `ground` (or the residual's ground). It must be non-empty.
Escape `|` as `\|` and replace newlines with a single space inside table cells; the map
stores the unescaped text.

The ledger is generated from the map. It must never be edited by hand after the map
exists.

### 4.5 Unit set and additivity

The unit set is the deduplicated union of the four view arrays, filtered by `isUnitId`.

- If the unit set is empty and there are no residuals: no map block is required. The
  existing RFC verdict is unchanged. This is the additivity rule.
- If the unit set is non-empty and the view exists: a map block is required. Its unit set
  must equal the view unit set. A missing map, a missing unit, or an extra unit is a
  failure.
- If the view is absent: additivity applies; the renderer does nothing. This is the state
  of a package that predates the view.
- A non-empty view with only `declared-residual` ledger rows still requires a map for the
  view units; residuals do not replace units.
- A residual unit may not also be a view unit. The renderer fails
  `RESIDUAL_IS_A_VIEW_UNIT` if the same id appears in both sets.

## 5. Stage by stage

### 5.1 `/grill-me-for-rfc` (package top)

Existing stage order inside the command is unchanged. After the view is generated and the
RFC body is authored, and before the final ledger/discharge gates, run:

```bash
node .claude/scripts/grill-me-for-rfc/render-distribution.mjs
```

The script reads, by convention from the current directory:

- `./RFC.md`
- `./SEQUENCES.json`
- `./OBLIGATION.json` if present (for residual grounds)
- the existing `Distribution ledger` rows, if the map block is absent (bootstrap)

It writes only `./RFC.md`, atomically.

It does not take new command arguments. `--check` is available for a dry run:

```bash
node .claude/scripts/grill-me-for-rfc/render-distribution.mjs --check
```

`--check` prints the map it would write and exits non-zero if it cannot.

Input absence:

- no `./SEQUENCES.json`: exit 0, write nothing (additivity; the package predates the
  view);
- no `./RFC.md`: exit 2 (misuse);
- a view with units and no ledger/map: exit 1 with the unit list.

#### Bootstrap algorithm

1. Read the view. Collect units.
2. Read `RFC.md`. Look for the `distribution-map` block.
3. If the block exists:
   - Parse it. If it is malformed, fail `INVALID_DISTRIBUTION_MAP`.
   - Compare its unit set with the view. Missing → `MISSING_UNIT`; extra →
     `INVENTED_UNIT`.
   - Compare `sourceViewDigest` with the current view. Mismatch →
     `STALE_DISTRIBUTION_MAP`; the author must update the map.
   - Use the block as the source of truth.
4. If the block is absent:
   - Read the existing `Distribution ledger` rows.
   - For each view unit, require exactly one row. Zero rows → `DISTRIBUTION_MAPPING_MISSING`
     with the unit id; more than one → `DUPLICATE_LEDGER_ROW`.
   - Strip surrounding whitespace and backticks from every cell before comparison.
   - Require the row's `Kind` to match the unit prefix (`KIND_MISMATCH`), its `Owner` to
     equal the package id (`OWNER_MISMATCH`), and its `Ground` to be non-empty
     (`EMPTY_GROUND`).
   - Parse the row's `RFC location` into section texts:
     - strip backticks;
     - split on commas and semicolons;
     - a token beginning with `§` or a digit is a section reference. Parse it as a dotted
       number and match the heading whose **leading dotted number equals it exactly**
       (`2.2` matches `2.2 Canonical encoding`, not `2.2.1 The normative scheme`). A token
       that is a path or prose is `UNPARSEABLE_LEDGER_LOCATION`;
     - an exact heading text is also accepted as a reference;
     - zero matches → `MISSING_RFC_SECTION`; more than one → `AMBIGUOUS_RFC_SECTION`.
   - Build the map from these rows. Preserve each row's `Ground`.
   - Preserve `declared-residual` rows as `residuals`.
   - If any view unit has no row, fail and list every missing unit; write nothing.
5. Resolve every `sections` entry to a unique heading. Fail on zero or multiple.
6. Generate the ledger from the map.
7. Remove every `<!-- unit: <managed unit> -->` anchor for the managed units from the
   whole RFC. Do not touch anchors for units outside the view.
8. Insert each unit's anchor at the end of each of its sections, before the next heading
   of the same or a higher level. A section already carrying the anchor after step 7 is not
   duplicated.
9. Write the `distribution-map` block immediately after the ledger table (or immediately
   before the appendix's end). The block's `digest` is computed last.
10. Write `RFC.md` atomically (temporary file + rename). A failure at any step leaves the
    original bytes untouched.

#### Idempotence

A second run over the same view and RFC:

- reads the block (now present);
- validates it against the view and `sourceViewDigest`;
- regenerates the same ledger and anchors;
- writes byte-identical RFC content.

No timestamps, no random ordering, no environment-dependent text.

### 5.2 `/smooth-sequences` (workspace root)

The command already loads each package's RFC and view. Add a distribution check, either as
a new check id (recommended: `S5.distribution-map`) or as an extension of the existing
distribution family. It must verify, for every package:

1. If the view has units: a `distribution-map` block exists.
2. The block's unit set equals the view unit set.
3. `sourceViewDigest` equals the computed view digest.
4. `digest` equals the computed map digest.
5. Every `sections` entry resolves to exactly one RFC heading.
6. Every managed anchor appears in every listed section, and nowhere else.
7. The ledger's unit set equals the map's units plus residuals.
8. Every ledger row's kind, owner, location and ground are well formed; the location
   resolves to the same sections as the map.
9. A view with units and no map is a finding, not a pass.

The check is a finding class `deficiency` with a repair route that names the renderer and
the offending unit. It does not modify the workspace.

### 5.3 `/graphify-rfc` (package top)

Input remains `RFC.md` only. The command's Step 2 already invokes
`attach-unit-ids.js --graph=... --rfc=... --ledger=...`. Extend the script:

1. Parse the `distribution-map` block from `RFC.md`.
2. Validate the map digest and view digest present in the block. If the block is absent
   but the RFC has no units, continue (additivity).
3. Build the node→section relationship from `headingRefs[].texts` as today. Normalize
   both sides identically: strip leading `#` and `§`, collapse internal whitespace, trim.
   If the section text begins with a dotted number, match the node whose heading text has
   the same leading dotted number. If it has no number, match the exact normalized text.
   Do not fall back to substring or token matching.
4. For every map unit, attach `<!-- unit: ... -->` / `unitIds` to every node whose
   heading matches one of the unit's sections.
5. Require at least one node per map unit. Missing → `MISSING_UNIT_AT_LAYER`.
6. Require every node `unitId` to be in the map. Extra → `INVENTED_UNIT`.
7. Write `distributionDigest` (the map digest) into the graph document. The graph schema
   has `additionalProperties: false`, so add an optional top-level
   `distributionDigest` string to `graph.schema.json`.
8. The `--ledger` argument may remain for backward compatibility. The map block is the
   source of truth; the ledger is a rendering of it. If both are present and disagree on
   a unit, section, kind, owner or ground, fail `DISTRIBUTION_LEDGER_MISMATCH`.

No new command argument is added. The script's `--graph`, `--rfc`, `--ledger` flags are
unchanged.

### 5.4 `/boundify-graph` (package top)

Input remains `*-GRAPH.json`. The command already writes `*-Dirs-Tree.json`. Add a
post-step, either inside `boundify-graph-to-dirs.js` or as a new script invoked by the
command:

```bash
node .claude/scripts/rfc-graph/attach-unit-ids.js --graph="$graphPath" --dirs-tree="$dirsTreePath"
```

The extended script:

1. Collect every `nodeId` in `mappedNodeIds` across all language trees.
2. For every graph node carrying `unitIds`, require its id in that set. Missing →
   `MISSING_UNIT_AT_LAYER`.
3. Add a top-level distribution index to the Dirs-Tree:
   ```json
   "distribution": {
     "digest": "<graph distributionDigest>",
     "units": { "op-X": ["N0007"], "ctr-boundary-001": ["N0012"] }
   }
   ```
   Do not modify the existing `mappedNodeIds` entries; the top-level index avoids
   disturbing consumers.
4. Require every graph unit to appear in the index.
5. Write the Dirs-Tree atomically. Keep the graph unchanged except for the already
   attached units.
6. Update `.claude/scripts/rfc-graph/validate-dirs-tree-schema.js` to accept the optional
   top-level `distribution` object; otherwise the existing schema gate would reject the
   new field.

The directory/file mapping itself remains boundify's design output; the gate makes it
mandatory rather than trusting it. A unit mapped only to a non-implementation section
will fail here; move the unit to the section that designs the implementation, or record
it as a `declared-residual` if it is genuinely not implemented by this package.

### 5.5 `/split-to-tickets` (package top)

Input remains `RFC.md`, `*-GRAPH.json`, `*-Dirs-Tree.json`.

0. The command derives `SEQUENCES_PATH="$DOC_DIR/SEQUENCES.json"` from the RFC path it
   already has and passes `--view="$SEQUENCES_PATH"` to the coverage gate. This is not a
   new user argument; it is the existing per-package view.
1. `add-tickets-for-phase.js` already receives the graph path. Before its
   `verifyTicketUnits` check, mechanically populate each ticket's `distribution`:
   - for every ticket, for every graph node in `ticket.nodeIds`, add a record for each
     unit the node carries, with the placement the Dirs-Tree index resolved;
   - add the obligation slice derived from the view: the operation payload for an
     implementer, a reference for a consumer, and the ordered steps whose operations the
     ticket implements for a sequence;
   - keep `nodeIds` as graph node ids only; do not mix unit ids into it;
   - write the per-ticket digest and the Tickets aggregate.
2. `verifyTicketUnits` then requires every graph unit in at least one ticket, and no
   ticket unit outside the graph.
3. Add a top-level `distributionDigest` to `Tickets.json`, copied from the Dirs-Tree's
   `distribution.digest`. If the Tickets validator
   (`.claude/scripts/lib/validate-tickets.js`) rejects extra top-level fields, add the
   field as optional there.
4. The final gates already run:
   - `verify-all-ticket-coverage.js --graph --ledger` (add `--view` in the command or rely
     on the RFC map; the map is the source);
   - `verify-ticket-closure.js --registry` for boundary contracts;
   - `merge-contracts-to-tickets.js --registry` for boundary contracts.
5. A graph unit with no ticket → `MISSING_UNIT_AT_LAYER`.
   A ticket unit not in the graph/map → `INVENTED_UNIT`.

No new command argument is added. The existing positional arguments are unchanged.

### 5.6 Boundary contract chain

The map distributes `ctr-<boundaryId>` units like any other unit. The contract clauses
themselves are still checked by the PX-306 gates:

- `verify-graph-contracts.js --registry=<ALLOCATE-MANIFEST>`: every registry boundary
  reaches a graph node and a contract edge.
- `merge-contracts-to-tickets.js --registry=<ALLOCATE-MANIFEST>`: every boundary ticket
  carries its contract; no invented ticket contract.
- `verify-ticket-closure.js --registry=<ALLOCATE-MANIFEST>`: closure and boundary
  presence.

The allocate manifest is not a new command argument. The package command discovers the
workspace root by walking up from the current directory until it finds
`WORKSPACIFY-TREE-MANIFEST.json` or `WORKSPACIFY-ALLOCATE-MANIFEST.json`, then uses
`<root>/WORKSPACIFY-ALLOCATE-MANIFEST.json`.

- If the map contains any `ctr-` unit and the manifest is not found:
  `REGISTRY_MISSING`, and the stage fails. The registry chain is no longer optional for a
  package that carries a boundary unit.
- If the map contains no `ctr-` unit, the registry gate is not applicable and the stage
  reports `not_applicable` rather than a pass.

This closes the PX-306 gap where `ALLOCATE_MANIFEST_PATH` being unset silently skipped the
boundary chain.

## 6. Digest chain and per-ticket penetration

The placement chain records the map generation each layer consumed:

```
RFC.md distribution-map.digest
  -> GRAPH.json distributionDigest
  -> Dirs-Tree.json distribution.digest
  -> each ticket.distribution.sourceMapDigest
  -> Tickets.json distribution.digest (aggregate over sorted ticket digests)
```

The placement chain is necessary but **not** the penetration certificate. A layer can
copy a digest while carrying no unit, and a single file-level digest cannot localise a
stale ticket. The penetration certificate is the per-ticket record:

```json
{
  "sourceMapDigest": "<64 hex>",
  "sourceViewDigest": "<64 hex>",
  "units": [{
    "unitId": "op-Produce",
    "kind": "operation",
    "role": "implementer",
    "surface": null,
    "placement": { "nodeIds": ["N0007"], "paths": ["src/produce.rs"] },
    "obligation": { "...": "operation fields, ordered steps, or reference" },
    "obligationDigest": "<64 hex>",
    "specRefs": [{ "path": "SPEC.md", "line": 412, "quote": "..." }]
  }],
  "digest": "<64 hex>"
}
```

Rules:

- Every ticket that owns a node carrying a unit carries the unit's record. A unit that
  reaches one ticket and not another owning ticket fails.
- The union of the tickets' obligation records reconstructs the unit payload. An
  operation has one implementer; a sequence's steps are assigned to the tickets that
  implement their operations and reconstruct in artifact order; a contract clause reaches
  every participating side.
- A consumer carries a reference and the boundary contracts, not the full implementation
  payload.
- `Tickets.json.distribution.digest` is the digest of the sorted `ticketDigests` map, not
  a copied scalar.
- Every gate compares the adjacent digests. A mismatch is
  `DISTRIBUTION_DIGEST_MISMATCH` and blocks the stage. A missing required digest is
  `MISSING_DISTRIBUTION_DIGEST`.
- A map change (view change, section change, ground change) changes the RFC digest and
  forces all downstream stages to rerun. There is no silent stale layer.

The digest does not certify prose. It certifies that every layer was produced from the
same mapping generation, and the per-ticket records certify that the obligation reached
the finest granularity.

## 7. Evolution loop

The evolution loop rewrites `RFC.md`. The distribution mechanism must survive that.

### 7.1 Requirements on the RFC writer

- The `distribution-map` block, the Distribution ledger appendix and the unit anchors are
  **preserved regions**.
- The RFC writer (the generator behind `/grill-me-for-rfc`, including `canon-state.js` and
  the edit-surface guard) must either preserve them byte-for-byte or run
  `render-distribution.mjs` immediately after the rewrite.
- `render-distribution.mjs` is the only writer of the ledger, the map block and the
  managed anchors. No other script writes them.

### 7.2 What happens when the RFC changes

- If a heading text changes but the map section text no longer exists:
  `MISSING_RFC_SECTION`. The author updates the map (or restores the heading).
- If a heading is added and the view gains a unit:
  `MISSING_UNIT`. The author maps the new unit.
- If the view loses a unit:
  `INVENTED_UNIT`. The author removes the stale map entry.
- If the map changes:
  the RFC digest changes. GRAPH, Dirs-Tree and Tickets carry the old digest and fail
  `DISTRIBUTION_DIGEST_MISMATCH` until each stage reruns.
- If the map block is lost:
  the renderer bootstraps from the ledger. If the ledger is also lost, it fails with
  `DISTRIBUTION_MAPPING_MISSING` and lists the units; it does not guess.

### 7.3 Root verification after evolution

`/smooth-sequences` at the workspace root rereads every package's RFC and view. It
reports `MISSING_RFC_SECTION`, `MISSING_UNIT`, `INVENTED_UNIT`,
`DISTRIBUTION_DIGEST_MISMATCH`, or a clean distribution. A package that was not evolved
keeps its old verdict.

## 9. Data schemas

### 9.1 `distribution-map` block

```json
{
  "schemaVersion": 1,
  "packageId": "string",
  "sourceViewDigest": "64 lowercase hex",
  "units": [
    {
      "unitId": "op-<id> | seq-<id> | xdir-<id> | ctr-<id> | obl-<id>",
      "kind": "operation | sequence | cross-boundary-sequence | contract | surface",
      "sections": ["exact heading text", "..."],
      "ground": "non-empty string"
    }
  ],
  "residuals": [
    {
      "unit": "non-empty string",
      "ground": "non-empty string"
    }
  ],
  "digest": "64 lowercase hex"
}
```

Constraints:

- `units` sorted by `unitId`; no duplicates.
- `sections` non-empty, unique, order preserved as authored.
- `residuals` sorted by `unit`; no duplicates.
- `packageId` equals the package's id in `WORKSPACIFY-TREE-MANIFEST.json`.
- A unit id must match `^(op|seq|xdir|ctr|obl)-.+`.

### 9.2 GRAPH

Add to the top-level graph document:

```json
"distributionDigest": "<64 hex>"
```

`graph.schema.json` has `additionalProperties: false`; add an optional
`distributionDigest` string with the hex pattern. Nodes already have optional `unitIds`.

### 9.3 Dirs-Tree

Add a top-level object:

```json
"distribution": {
  "digest": "<64 hex>",
  "units": {
    "op-X": ["N0007"],
    "ctr-boundary-001": ["N0012"]
  }
}
```

The `units` object is a map from unit id to the graph node ids that carry it. The Dirs-Tree
schema validator, if any, must accept this extra top-level field.

### 9.4 Tickets

Each ticket carries a `distribution` object:

```json
{
  "sourceMapDigest": "<64 hex>",
  "sourceViewDigest": "<64 hex>",
  "units": [{
    "unitId": "op-Produce",
    "kind": "operation",
    "role": "implementer",
    "surface": null,
    "placement": { "nodeIds": ["N0007"], "paths": ["src/produce.rs"] },
    "obligation": { "...": "..." },
    "obligationDigest": "<64 hex>",
    "specRefs": [{ "path": "SPEC.md", "line": 412, "quote": "..." }]
  }],
  "digest": "<64 hex>"
}
```

`Tickets.json` carries the aggregate:

```json
"distribution": {
  "sourceMapDigest": "<64 hex>",
  "sourceViewDigest": "<64 hex>",
  "ticketDigests": { "1": "<64 hex>", "2": "<64 hex>" },
  "digest": "<64 hex>"
}
```

The ticket `nodeIds` array remains graph node ids only. Unit ids live in
`distribution.units`; mixing them into `nodeIds` made an id look like an obligation and
made per-unit obligations unrepresentable. The ticket-level `nodeIds` is still the
consumer-read field (`verify-consistencies.js` reads `phases[].tickets[].nodeIds`).

### 11.1 What if a ledger row has multiple sections?

Allow it. `sections` is an array. The renderer places the anchor in each section. The graph

a row or a map entry. The renderer never invents a section.

### 11.3 What if a heading is duplicated?

The RFC's G0 step deduplicates headings. If duplicates still exist, the renderer fails
`AMBIGUOUS_RFC_SECTION`; the RFC must be deduplicated first.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Mapping review burden (627 units) | Bootstrap from the existing ledger; fail with a precise list; one-time review. |
| Section drift after evolution | Exact heading text; `MISSING_RFC_SECTION`; re-review. |
| Multiple sections per unit | Allowed; anchor in each; gate requires at least one node. |
| Graph node construction is AI | The map attaches to nodes by heading; a missing node fails. |
| Dirs-Tree mapping is a design decision | The gate requires every unit-bearing node to be mapped; it does not guess. |
| Ticket phase grouping is a design decision | The gate requires every unit to reach a ticket; the copy is mechanical. |
| Digest churn | Canonical JSON; digest only the map body; no timestamps. |
| Schema rejection of new fields | Update `graph.schema.json` and the tickets validator; add optional fields. |
| Ledger ground loss | The map stores `ground`; the ledger is rendered from it. |
| Bootstrap from a stale ledger | `sourceViewDigest` and unit-set equality fail before writing. |
| Empty view hiding a missing map | A non-empty view requires a map; an empty view is explicit. |

## 15. Decisions to confirm during implementation

These are the remaining choices; each has a recommended default:

1. **Block marker**: fenced `json distribution-map` (recommended) rather than an HTML
   comment, because JSON may contain `--`.
2. **Multiple sections per unit**: allowed (recommended).
3. **Residuals**: included in the map as `residuals`; no anchors.
4. **Digest placement**: top-level `distributionDigest` in GRAPH; top-level
   `distribution` object in Dirs-Tree and Tickets, with a per-ticket `distribution`
   record and an aggregate over sorted ticket digests.
5. **Smooth check id**: `S7.distribution-map`, `S7.owner-role-undeclared` and
   `S7.root-unit-uncovered`. S5 already names the authored-source and boundary families;
   S7 is the artifact-view consistency family.
6. **Bootstrap source**: the existing ledger's `RFC location` column (recommended).
7. **Graph schema**: add an optional `distributionDigest` string with a 64-hex pattern.
8. **Tickets schema**: add an optional per-ticket `distribution` object and an optional
   top-level aggregate; keep `nodeIds` as graph node ids only.
9. **Dirs-Tree schema**: add an optional top-level `distribution` object; do not modify
   `mappedNodeIds` entries.
10. **Operation role**: a multi-owner operation declares `role: implementer | consumer`
    in the map. Single-owner operations default to `implementer`. Exactly one implementer
    is required unless each implementer declares a distinct `surface` from
    `rest | websocket | cli`. A consumer carries a reference obligation, not the full
    implementation payload.

## 16. What is still not mechanical

- Whether the RFC prose correctly designs the unit. The map proves the unit is named and
  placed; it does not prove the prose.
- Which section or directory is the right design home. That is authored once in the map
  and checked thereafter.
- Whether every operation the specification needs was enumerated. That is the
  `/educe-sequences` census and the certificate residue, not this distribution layer.

The design therefore guarantees **distribution completeness and non-invention**, not
**semantic completeness**. State this boundary in every report.
