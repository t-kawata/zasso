# explain-seed の転換: 「論点ごとに聞く」から「方向性を聞いて束ねる」へ

この文書は、`/explain-seed` コマンドの旧版と新版の違いを、背景から説明する。前提知識は要らない。旧版を「旧」、新版を「新」と呼ぶ。

---

## 1. 背景

### 1.1 何のためのコマンドか

システムを設計するとき、人間は AI と設計の対話を行う。この対話を、この文書では「grill」と呼ぶ。AI が人間に質問を重ね、設計の曖昧な点を詰めていく作業である。

設計の対象は、パッケージ(1つの機能のまとまり)に分けて扱う。各パッケージには `RFC-SEED.md` という設計の種になる文書がある。種には、まだ決まっていない事項が記録されている。

`/explain-seed` は、1つの `RFC-SEED.md` を読み、設計の対話の前に次の2つを用意するコマンドである。

- `INFO-RFC-SEED.md`: 事実の記録。英語。スクリプトが書き、AI の作業材料になる。説明も評価も含まない。
- `EXPLAIN-RFC-SEED.md`: 説明。日本語。人間が読み、人間の判断が書き込まれる。

人間が書き込んだ判断は、この後の設計の対話(下流)が読む。つまり、このコマンドは人間の判断を設計の対話の前に集める役目を持つ。

### 1.2 用語

| 用語 | 意味 |
|---|---|
| 論点 | `RFC-SEED.md` に記録された、まだ決まっていない事項1件 |
| 先に決めておいたこと | AI または近隣パッケージが、根拠を付けて決めた事項を載せる節 |
| 根拠 | 決定を支える出典。マニフェストの ID、近隣の文書、または人間の回答 |
| 覆す条件 | その決定を変えるべき事実。決定ごとに書く |
| 近隣 | 境界(パッケージ同士の接点)の反対側にあるパッケージ |
| 方向性質問 | 優先順位、目指す姿、誰の体験を先にするかを聞く質問。1つの答えで、多くの論点をAIが自分で決められる |
| 台帳 | 全論点について、未解決・質問に束ねた・解決済みのどれかを記録する帳簿 |
| 巡 | 質問をして、答えを受け、論点を解決するまでの1周 |

### 1.3 旧版で起きていた問題

旧版を使ったところ、次の3つの問題が出た。

1. **質問が多すぎる。** 論点の数だけ質問が出る。
2. **質問が分かりにくい。** 実装を知らない人には、何を選ぶのか読み取れない。
3. **AI が決められることまで人間に聞く。** 本来 AI が判断できる論点も、安易に人間へ回される。

質問の作成基準は、すでに「高校生でも答えられる平易な日本語で、方向性や体験への影響を聞く」と定めてあった。それでも問題は直らなかった。

## 2. 旧版の設計と、問題の根

### 2.1 旧版の動き

旧は、記録された論点を1件ずつ、人間に1回ずつ質問する設計だった。

1. スクリプトが事実と文書の枠を作る。
2. AI が枠を埋める。論点ごとに「技術の判断か、人間の判断か」を仕分ける。
3. 人間の判断に仕分けた論点を、1件ずつ質問にする。
4. 全質問に回答があれば終了する。

### 2.2 問題の根は、書き方ではなく粒度にあった

旧は、質問の書き方(平易さ、選びやすさ)を細かく定めていた。しかし、何を人間に聞くか(質問の粒度と数)は定めていなかった。この点を、次の4つの規則が、質問の洪水へ向けて作用していた。

| 旧の規則 | 何が起きるか |
|---|---|
| 「記録された未決の論点は、どれも消してはならない。人間に聞くか、先に決めておくかのどちらかにする」 | 論点の数が、そのまま質問の数になる |
| Q2「後続の技術者が、事実ではなく感じ方で意見を割りそうなら、人間に聞く」 | 体験に少しでも関わる論点が、すべて人間に回る |
| U2「体験の論点を黙って AI が決めてはならない」 | AI が決める余地を、規則が閉じている |
| 終了条件「全質問に回答がある」 | 終わりの判定が「質問を聞き終えたこと」にあり、「AI が全論点を決められたこと」にない |

さらに、次の2点が人間の読む量を増やしていた。

- 質問の下に、記録の原文が複写されていた(「読まなくてよい」と注記はあるが、視界に入る)。
- 質問の数にも、本文の長さにも、上限がなかった。

### 2.3 旧版の具体的な動き(架空の例)

通知を扱う架空のパッケージで考える。記録された論点は、次の10件だったとする。

1. エラー画面の文言の調子
2. 再試行中に、その旨を表示するか
3. 通信に失敗したとき、前回の内容を見せるか
4. 前回の内容を見せる場合の、有効期間
5. 一部だけ取得できたとき、その一部を見せるか
6. 失敗したことを、利用者に知らせるか
7. 入力内容を、端末に保存してよいか
8. 他の端末と同期するか
9. 削除したとき、サーバー上の扱いをどうするか
10. 退会後、データをいつまで保持するか

旧では、10件のどれも体験に関わるため、Q2により人間の判断に回る。人間は、次のような10問に、1問ずつ答える。それぞれに、文脈、A/B、推奨、理由、覆す事実、記録の複写が付く。

> Q4: 前回の内容を見せる場合の、有効期間はどうしますか。
> A: 短くする。B: 長くする。

選択肢の違いを、実装を知らない人が判断するのは難しい。答えるたびに、人間は設計を学ばされる。

## 3. 新版の設計

### 3.1 基本方針

新の核心は、1つの規則にまとまっている。

> 個別の論点を、人間に直接聞かない。聞くのは、方向性質問だけ。

これを支える方針は次のとおり。

1. **AI がまず自分で決める。** 技術の判断だけでなく、結果が軽く、容易に戻せる体験の論点も、AI が根拠と覆す条件を付けて決める。
2. **決められないものだけを束ねる。** 結果が重く、戻しにくく、根拠のない論点だけを、少数の方向性質問に束ねる。
3. **方向性質問を人間に聞く。** 人間は、方向を選ぶだけでよい。
4. **答えから AI が個別に決める。** 答えを根拠にして、束ねた論点を1件ずつ AI が決める。
5. **決められなければ、もう一巡する。** 決められなかった論点だけで、新しい軸の方向性質問を作る。
6. **終わりは、AI が全論点を決められたとき。** 人間が答え終わったときではない。

grill という行為は禁止されていない。複数巡の方向性質問が、そのまま grill である。禁止するのは、別のコマンドをこのコマンドの内部で起動することだけである。

### 3.2 方向性質問とは何か

方向性質問は、**範囲は広く、言葉は具体的**でなければならない。次の3点を、各選択肢から読み取れる必要がある。

- 誰が
- どんな場面で
- 何を得て、何を失うか

「曖昧に聞く」ことは、「方向性を聞く」ことではない。たとえば、「使う人の手間と見落としのどちらを重く見るか」は、誰の手間か、何の見落としかが分からないので、選べない。

良い例を3つ示す(人間に見せる形)。

> Q1: サーバーの調子が悪いとき、このアプリを使っている利用者にどう振る舞ってほしいですか。
> A: 「いまは使えません」と正直に止めて知らせる。使えない時間が出るが、間違った内容は見ない。
> B: 古い情報や簡単な結果でも出し続ける。使い続けられるが、古い内容を見ることがある。

> Q2: 利用者が入力した内容を、どこに置きますか。
> A: 利用者の端末の中だけに置く。他の端末では見られないが、外に漏れる危険は小さい。
> B: サーバーにも保存する。どの端末でも見られるが、サーバーが攻撃されると内容が漏れる危険がある。

> Q3: このシステムを後から引き継ぐ開発者の、どの負担を軽くしますか。
> A: 最初に覚えることを減らす。機能を足すとき、作り直しが出やすい。
> B: 機能を足しやすくする。引き継いだ直後は覚えることが多い。

悪い例は次の3種類である。

| ラベル | 例 | 何がだめか |
|---|---|---|
| 個別論点の質問 | 「失敗時の再試行は3回か5回か」 | 技術判断であり、AI が決める |
| 主語不明の抽象質問 | 「手間と見落としのどちらを重く見るか」 | 誰の何かが不明で、選べない |
| 同じ軸の質問の乱立 | 「エラー表示は?」「キャッシュは?」「再試行は?」を別々に聞く | 1つの方向性を、複数の質問に割っている |

### 3.3 新版の具体的な動き(同じ例で)

2.3 と同じ10件の論点に、新版を当てはめる。

**Step 2: AI が先に決める。** 論点を、次の順に判定する。

| 論点 | 判定 | 扱い |
|---|---|---|
| 1 エラー画面の文言の調子 | 軽く、戻せる | AI が決める。覆す条件を付ける |
| 2 再試行中の表示 | 軽く、戻せる | AI が決める。覆す条件を付ける |
| 3, 4, 5, 6 | 重く、利用者の体験を大きく左右し、根拠がない | 「障害時の基本姿勢」の軸に束ねる |
| 7, 8, 9, 10 | 重く、戻しにくく、根拠がない | 「入力内容の置き場所」の軸に束ねる |

**第1巡。** 人間に見えるのは、次の2問だけである(3.2 の Q1 と Q2)。論点の一覧、番号、記録の複写は見えない。

人間の回答が「Q1: A」「Q2: A」だったとする。AI はこれを根拠に、次のように決める。

| 論点 | 決定 | 根拠 |
|---|---|---|
| 3 前回の内容を見せるか | 見せない | Q1: A(間違った内容は見せない) |
| 4 有効期間 | 不要(3により消える) | Q1: A |
| 5 一部だけの結果 | 見せない | Q1: A |
| 6 失敗を知らせるか | 知らせる | Q1: A(正直に知らせる) |
| 7 端末保存 | 保存する | Q2: A(端末の中に置く) |
| 8 同期 | しない | Q2: A |
| 9 サーバーの削除 | 対象なし(サーバーに置かない) | Q2: A |
| 10 退会後の保持 | 対象なし。ただし端末内の扱いは、答えからは決まらない | Q2: A では決まらない |

論点10の端末内の扱いは、答えから導けなかったので、未解決のまま残す。AI が推測で決めることは許されない。

**第2巡。** 残った論点で、新しい軸の質問を作る。前の質問を言い換えるのではなく、前の答えが決めなかった範囲だけを対象にする。

> Q3: 利用者がこのアプリをやめるときや、端末を買い替えるとき、入力内容はどうなってほしいですか。
> A: 端末の中から消える。やめた利用者の内容は残らないが、買い替えたときは入力し直しになる。
> B: 何らかの形で残る。買い替えても続けて使えるが、やめた後も内容が残る。

回答を受け、AI が残りを決める。未解決が0件になった時点で、ループが終わる。

**結果の比較。**

| 項目 | 旧 | 新 |
|---|---|---|
| 人間が答える質問数 | 10問 | 3問(2巡) |
| 人間が見る情報 | 文脈・選択肢・記録の複写が10組 | 文脈と選択肢のみ、3組 |
| AI が決めたこと | 技術判断のみ | 技術判断、軽い論点2件、答えから導いた論点8件 |
| 論点の追跡 | 質問に回答があれば完了 | 全論点に根拠付きの決定があって完了 |

## 4. 規則ごとの変更点

### 4.1 役割

| | 旧 | 新 |
|---|---|---|
| Does | 記録された質問を、1問ずつ1回聞く | AI が決められるものを決め、少数の方向性質問を複数巡で聞き、残りを答えから決める |
| Does not | grill をしない | 人間の代わりに決めない。他のコマンドを起動しない |
| grill の位置づけ | 「別物」として除外 | このコマンド内の複数巡ループが grill |

### 4.2 論点の扱い

| | 旧 | 新 |
|---|---|---|
| 不変条件 | 論点は、人間に聞くか、先に決めておくかのどちらか | 論点は、未解決、質問に束ねた、解決済み(根拠付き)のどれか |
| 判定 Q2 | 感じ方で意見が割れるなら、人間に聞く | 結果が軽く戻せるなら AI が決める |
| 判定 Q3 | なし | 残りを方向性ごとに束ねる |
| 体験の論点を AI が決める | 禁止(U2) | 軽く戻せるものは可。重く根拠がないものは禁止 |
| 回答による解決 | 概念なし | 回答が決定を含意しているときだけ、根拠として使える |

### 4.3 質問

| | 旧 | 新 |
|---|---|---|
| 粒度 | 論点1件につき1問 | 方向性1つにつき1問。2件以上の論点を束ねる |
| 数 | 上限なし | 1巡3問まで。5巡まで |
| 選択肢 | A/B。C は記録が第三の読みを残すときのみ | A/B に加え、C も可 |
| 本文の量 | 上限なし | 文脈3文、選択肢2文、理由1文、覆す事実1文 |
| 見せる情報 | 質問の下に記録の複写あり | 質問のみ。論点一覧、ID、条項名、記録の複写、検討経緯は見せない |
| 具体性 | 規則なし | 誰が・どんな場面で・何を得て何を失うかを必ず書く(W12) |
| 質問枠の生成 | スクリプトが論点ごとに作る | AI が方向性ごとに作り、スクリプトが枠を追記する |

### 4.4 ループ

| | 旧 | 新 |
|---|---|---|
| 終了条件 | 全質問に回答がある | 全質問に回答があり、かつ未解決の論点が0件 |
| 残りがあるとき | 同じ質問を聞き直す | 残った論点だけで、新しい軸の質問を作る |
| 聞き直し | 許容 | 禁止(U14)。答え済みの軸は再度聞かない |
| 打ち切り | なし | 5巡で停止し、残った論点を報告する |

### 4.5 スクリプト

| スクリプト | 旧 | 新 |
|---|---|---|
| `info` | 事実と、論点ごとの質問枠を書く | 事実と、枠と台帳を書く。質問枠は作らない |
| `next` | なし | 質問枠を追記する。1巡3問まで、5巡まで |
| `check` | 構造の検査 | 加えて、束ねた論点が2件以上、導出範囲の行がある、解決済みに根拠と覆す条件がある |
| `answers` | 全質問に回答があれば成功 | 加えて、未解決の論点が0件であることを要求する |

## 5. 守るための仕組み

方向性に束ねる設計には、2つの危険がある。

**危険1: 束ねを口実に、AI が人間に聞くべきことを勝手に決める。**
対策は次のとおり。

- 回答から決める論点には、根拠として質問番号と選択肢の文字を必ず付ける。付かなければ、ゲートが拒否する。
- 回答が決定を含意していなければ、その回答は根拠にならない。
- AI が自分で決める論点にも、覆す条件を必ず付ける。
- 最後の報告で、AI が決めた論点と、その理由を一覧にする。人間は後から検証し、覆せる。

**危険2: 質問を束ねるうちに、方向性が曖昧になる。**
対策は次のとおり。

- W12 と U15 で、誰が・どんな場面で・何を得て何を失うかが読み取れない質問を、不適格とする。
- 「実装用語を使わない」「選択肢の結果を書く」という旧からの規則(W1〜W5)を、すべて維持する。

もう1つの注意点がある。「軽く戻せるかどうか」の判定は、AI の判断である。スクリプトでは機械化できない。誤って重い論点を軽いと判断すると、AI が人間の判断を奪う。これを防ぐ仕組みは、覆す条件の記載と、報告での開示だけである。運用で誤判定が見つかれば、この判定基準(Q2)を見直す必要がある。

## 6. 変えなかったもの

- ゲートの順序(G0〜G5)と、親が通らなければ子も通らないという関係
- 事実を書くスクリプトの実行時機
- 先に近隣の決定を確認し、近隣が決めた境界は聞かないという規則
- 公開済みの実装順序は記録であり、質問ではないという規則
- 人間の代わりに回答を書いてはならないという禁止
- 言語の分け方(人間向けは日本語、それ以外は英語)
- 事実の文書と説明の文書を分ける構造

## 7. 実装が必要な箇所

`explain-seed.md`(コマンド定義)は、スクリプトの契約を定めただけである。次のスクリプトの実装が別途必要になる。

1. `run.mjs next` の新設
2. `run.mjs info` の変更(論点ごとの質問枠をやめ、台帳を書く)
3. `run.mjs check` の拡張(束ね数、導出範囲、根拠と覆す条件)
4. `run.mjs answers` の拡張(未解決0件の判定)

上限値(1巡3問、5巡、文脈3文など)は初期値であり、運用で調整できる。調整するときは、定義文書の Core Rule、Invariants、Criteria を同時に直す。
