## ディレクトリと名前空間でつくる安全な境界（Rust/Go/TypeScript）

### Rust（crate + mod）

- 「ディレクトリはただの物理配置、**境界は crate と mod の階層で定義する**」。 
- ディレクトリは crate/mod の構造を反映させるが、“ディレクトリ＝境界” ではなく “crate/mod の論理境界をディレクトリで表現する” と捉える。
- 各ファイルは自分のモジュールを定義し、モジュール階層とディレクトリ階層を概ね一致させるが、**意味論は常に `crate::foo::bar` のパスで考える**。 
- ディレクトリを増やすのは、「モジュール境界の意味が増えたときだけ」であり、**過剰なネストを避けてフラットなモジュール構造を優先する**。 
- 外部 API は crate ルートの `pub` でのみ露出し、**下位モジュールでは `pub(crate)` を基本として内部実装を閉じ込める**。 
- I/O や副作用を扱うコードは明示的なモジュール（ディレクトリ）に集約し、**ドメインロジック側からは trait などの抽象のみが見えるようにする**。 

### Go（module + package）

- 「**ディレクトリ＝package＝境界**」として扱い、1ディレクトリ1責務・1名前空間を基本とする。 
- パッケージ名は「何を含むか」ではなく「何を提供するか」で決め、`utils` や `common` のような曖昧な名前空間は作らない。 
- 依存は「上位から下位」へ一方向とし、**循環依存を起こすようなディレクトリ構造は作らない**。 
- 外部に公開すべきでないコードは `internal/` 以下のパッケージに置き、**Go の可視性ルールとディレクトリ境界を組み合わせてプライバシーを確保する**。 
- ディレクトリのネストは 1〜2 レベルに抑え、**フラットなパッケージ構造を優先し、複雑さが増えたときだけ新しいディレクトリと境界を導入する**。 

### TypeScript（ディレクトリ + modules + barrel）

- module はファイル単位だが、**ディレクトリを論理名前空間とみなし、ディレクトリ単位で責務と境界を設計する**。 
- 各ディレクトリに barrel (`index.ts` 等) を置き、そのディレクトリ配下の「公開したいシンボルだけ」を再 export することで、**ディレクトリ＝public surface を明示する**。 
- 他ディレクトリからの import は原則として barrel 経由とし、**ファイルを直接相対 import して境界を迂回しない**。 
- ディレクトリを増やすのは、新しいドメイン・レイヤ・I/O 境界が必要になったときだけで、**細かすぎる分割や無意味な共有ディレクトリ（`utils` 的なもの）の乱立を避ける**。 
- 型と lint（strict TS, ESLint）で、「ディレクトリ間依存の方向」と「barrel 経由 import」をチェックし、**構造的な境界違反を機械的に検出できるようにする**。
