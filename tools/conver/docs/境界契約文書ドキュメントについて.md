## 修正・確定した前提

### 1. 人間境界の粒度
人間の境界となり得るのは **ワークスペース単位とパッケージ単位のみ**。それ未満（モジュール、関数、operation 等）で人間の境界が発生する想定はしない。したがって境界契約文書の生成対象も、この2単位に限定される。

人間境界の契約は、AI に対する境界契約と**大きく区別する必要はない**。同じ契約を、AI は機械的に消費し、人間は意味を理解して消費する。必要なのは別系統の契約体系ではなく、**同じ境界契約が人間にも読める形で完全に存在していること**。

### 3. 人間境界の契約文書の内容
求められているのは、次の3層を持つ文書だと理解しました。

**第1層：意味層（自然言語）**
- 何のための機能動作なのか／何のためのワークスペースなのか／何のためのパッケージなのか
- 何をどのように IN すると、何がどのように OUT し、結果として何が起こるのか
- これを使って何をすることができるのか

これを意味的にわかりやすく自然言語で記述する。ここが人間の理解の入口になる。

**第2層：言語利用層**

## 確定した理解

### 1. 読み手はプロのエンジニア
人間境界の契約文書の読み手は、素人ではなく**プロのエンジニア**。したがって「わかりやすさ」のために契約内容を簡略化・再定義してよい理由はない。

### 2. 伝統的な境界契約文書を再定義しない
伝統的に、人間が作成した境界契約文書を人間が読み、人間が結合プログラムを書くことで、システム・ワークスペース・パッケージ・モジュールは安全に連結されてきた。conver が作る文書も、**その伝統的な意味での境界契約文書そのもの**でなければならない。新しい様式や AI 向けの別解釈を持ち込む話ではない。変わるのは読み手が人間だけではなく AI も加わる、という点だけ。

### 3. 品質基準は「人間が手作業で正確に結合できるか」
conver の境界契約文書は、AI だけでなく**人間が生身で解釈し、人間がその結合プログラムを正確に手作業で書ける**情報の質でなければならない。これは受入基準としてそのまま使える。すなわち、**その文書だけを読み、内部を一切読まずに、プロのエンジニアが結合プログラムを正確に書けること**。

### 4. 境界契約の存在理由
境界契約は、**内部の細部を知らずとも完全かつ安全に結合を成せるようにするため**に存在する。したがって:

- **隠蔽すべきもの**＝内部の実装細部。これは情報ノイズであり、境界契約文書に書いてはならない。
- **書くべきもの**＝境界を跨ぐ結合に必要な情報のすべて。ここが欠けてはならない。
- この両面を同時に満たす状態が「**過不足なく必要十分**」。

内部アルゴリズム、私有データ構造、内部モジュール分割、実装上の都合といったものは、隠蔽によってノイズを減らすべき部分であり、記載対象外。逆に、目的、IN とその与え方、OUT とその受け取り方、結果として起こること、前提と事後条件、失敗時の振る舞い、制約、提供形態（ライブラリ／インターフェース）、各言語からの扱い方、各プロトコルの完全仕様、これらは結合に必要であり、一つでも欠ければ不足。

### 5. 過不足の判定
- **不足**：その文書だけでは結合プログラムを正確に書けない（内部を読まないと埋まらない情報がある）。
- **過剰**：内部細部が混入している（読み手に隠蔽すべきノイズを読ませている）。
- **必要十分**：内部を読まずに完全かつ安全な結合が書け、かつ内部情報が一切混入していない。

### 6. AI と人間は同じ文書を読む
AI はこの文書を機械的に消費して結合を生成し、人間は同じ文書を解釈して手作業で結合を書く。両者が同じ契約から同じ結合に到達できることが、この文書の正しさの証になる。別系統の文書は作らない。

- 内部細部の混入を機械的に検出・排除する必要がある。

| G2 | 内部設計と境界契約が未分離 | RFC.md の `3. Design` は内部設計を含む | 内部細部が混入するか、境界情報が不足する |
| G3 | 公開面の許可リストがない | `api-consistency` はクロスパッケージ利用を検査するが、境界公開面の全量を定義しない | 不足も過剰も証明できない |
| G4 | 言語別の完全な利用方法がない | README 未生成、RFC に言語別手順なし | Rust 以外の言語から結合できない |
| G5 | インターフェース文書の完全性モデルがない | `rust-interface-law` は実装規則、`effective-policy` は技術選定のみ | REST/WS/CLI/gRPC/MCP/A2A の完全仕様が保証されない |
| G6 | 存在保証・鮮度保証がない | 生成は任意、更新は手作業 | 古い契約が残り、摩擦の原因になる |
| G7 | 文書だけからの結合証明がない | 例が実行可能である保証がない | 「読めば結合できる」が検証されない |
| G8 | ワークスペース契約（構成・横断レシピ）がない | パッケージ文書は点在、ルートは SYSTEM-DESIGN のみ | ワークスペース全体の使い方が分からない |
| G9 | 境界発見が一様でない | gaia は map 不在、crystal はルート被覆、gaia は入れ子 | プロジェクトごとに特別扱いが必要になる |
| G10 | 人間用の入口・索引がない | 契約の標準パスも索引もない | 「どの文書を読むか」から摩擦が生じる |
| G11 | パイプライン強制がない | plan/start/review/resolve に境界契約のゲートがない | 実装AIのブラックボックスが境界を越える |
| G12 | 既存プロジェクトの移行設計がない | 完成済みパッケージに契約がない | 一括適用は不可能、放置は無保証 |
| G13 | 「必要十分」の定義がない | 内部情報の混入と境界情報の欠落を区別する基準がない | 文書の品質が属人的になる |

## 3. 設計原則

| ID | 原則 | 内容 |
|---|---|---|
| P1 | 境界粒度は2単位のみ | ワークスペースとパッケージ。それ未満は人間境界にしない |
| P2 | 契約は一つ、表現は二つ | JSON は機械可読な正規表現、Markdown は人間可読な規範的描画。別契約ではない |
| P3 | 伝統的形式を踏襲 | 目的・入出力・効果・前提/事後/不変・エラー・制約・利用方法・例。再定義しない |
| P4 | 正本性は既存資産 | コード/IDL・RFC-SEED・GRAPH・OBLIGATION・manifest・workspace-map・effective-policy が正本。契約は射影 |
| P5 | 必要十分は機械判定 | 不足（gap）と過剰（leak）を別々に判定する |
| P6 | 存在と鮮度は不変条件 | 任意生成ではなく、境界が存在する限り常に存在し、常に最新 |
| P7 | プロの人間が単独で結合できる | 内部を読まず、他者に質問せず、手作業で正確に書ける |
| P8 | 一般化・fail closed | プロジェクト名・役割・言語・インターフェースをハードコードしない。判定不能は通過させない |
| P9 | 決定論 | 同一入力から同一出力。順序・キー・改行を固定 |
| P10 | 安全 | 秘密情報・内部専用情報・実在資格情報を混入させない |

## 4. 成果物設計

### 4.1 配置

```text
<workspace-root>/
├── BOUNDARY-CONTRACT.md              # ワークスペース境界契約（人間用）
├── BOUNDARY-CONTRACT.json            # 同（機械用・正規表現）
├── BOUNDARY-INDEX.md                 # 全パッケージ契約とインターフェースの索引
├── BOUNDARY-INDEX.json
├── BOUNDARY-CONTRACT-Status.json     # 検証結果（決定論的）
├── boundary-contract.toml            # 任意設定
├── BOUNDARY-CONTRACT-BASELINE.json   # 移行モード専用（後述）
│
├── <package-root>/
│   ├── BOUNDARY-CONTRACT.md
│   └── BOUNDARY-CONTRACT.json
│
├── examples/boundary/                # 実行可能な例の正本（任意ではなく推奨）
│   └── <capability>/<language-or-interface>/...
│
└── # ルート被覆 unit がある場合のみ
    BOUNDARY-CONTRACT.package.<unit-id>.md
    BOUNDARY-CONTRACT.package.<unit-id>.json
```

**衝突規則（crystal の `crystal` unit 対策）**: unit の root がワークスペース root と一致する場合、ワークスペース契約は `BOUNDARY-CONTRACT.md`、パッケージ契約は `BOUNDARY-CONTRACT.package.<unit-id>.md` に置く。索引が両方を明示する。

**README を使わない理由**: README は既に plugin 等の別用途で存在し、上書き危険がある。また「どの README が契約か」が曖昧になる。専用名で探索を決定論にする。

### 4.2 二表現の関係

- `BOUNDARY-CONTRACT.json` が**構造の正本**。AI は直接編集せず、CRUD ツール経由でのみ更新する（conver の既存不変条件に合わせる）。
- `BOUNDARY-CONTRACT.md` は JSON から**決定論的に描画**される。見出し順・アンカー・用語集も固定。
- 両者は同一契約の二表現であり、内容の不一致は検証で落とす。

### 4.3 対象単位

- **ワークスペース契約**: ワークスペースの目的、構成パッケージ、依存トポロジ、外部境界、公開インターフェース、横断的な結合レシピ、非目標。
- **パッケージ契約**: パッケージの目的、機能、IN/OUT/効果、前提/事後/不変、エラー、制約、言語別利用、インターフェース仕様、例。

パッケージが「消費境界でない」（conformance、prebuilt 等）場合も契約は必須。`consumption: none` とその理由、代替経路を明示する。**契約の不在を許さない。**

## 5. 契約文書の構造（伝統的形式）

### 5.1 人間用 Markdown の固定見出し

1. **この境界は何か** — 何のための機能/ワークスペース/パッケージか。適用範囲と非目標。
2. **これで何ができるか** — 機能・能力の一覧。各能力の用途。
3. **入力** — 何を、どのように渡すか。必須/任意、形式、制約、前処理。
4. **出力** — 何が、どのように返るか。形式、保証、順序、ストリーム/非同期。
5. **結果として何が起こるか** — 状態変化、イベント、外部作用、順序、冪等性、補償、失敗時の部分効果。
6. **前提条件・事後条件・不変条件** — 呼び出し前後と常時成立する条件。
7. **失敗時の振る舞い** — エラー分類、コード、発生条件、呼び出し側の回復行動。
8. **制約** — 性能、同時性、レート、サイズ、禁止事項、バージョン互換性。
9. **利用方法（言語別）** — 対応言語ごとの完全な手順。後述のマトリクス。
10. **インターフェース仕様** — REST / WebSocket / CLI / gRPC / MCP / A2A の完全仕様。後述。
11. **例** — 言語別・インターフェース別。実行可能な例への参照と埋め込み。
12. **境界の相手** — 提供/消費する境界 ID、相手パッケージ、方向、契約範囲。
13. **境界用語** — 境界を理解するための用語だけ。内部用語は入れない。

この並びは伝統的な境界契約文書の並びであり、新しい様式ではない。読み手は上から順に読めば、内部を知らずに結合できる。

### 5.2 言語別マトリクス（第2層）

必須列:

| 列 | 内容 |
|---|---|
| language | `rust` / `typescript` / `python` / `go` / その他 |
| status | `native` / `ffi` / `sdk` / `via_interface` / `unsupported` |
| entry | パッケージ名、モジュール、クレート、SDK、エンドポイント |
| version | 対応バージョン、制約 |
| setup | 依存追加、初期化、認証 |
| capabilities | どの能力がどの入口で使えるか |
| examples | 実行可能な例への参照 |
| limitations | その言語固有の制限、未対応能力 |

**必須言語集合**は設定で指定する（既定: `rust`, `typescript`, `python`, `go`）。各言語は必ず1行を持ち、`unsupported` でも理由と代替経路を書く。これにより「全言語無限」ではなく「宣言した全言語について完全」を保証する。

### 5.3 インターフェース層（第3層）

`workspace-map` / `manifest` の `interfaces` と `effective-policy` を起点に、宣言された種別ごとに完全仕様を要求する。

| 種別 | 必須内容 |
|---|---|
| REST | base URL、認証、バージョニング、全エンドポイント（method/path）、入力/出力スキーマ、ステータス/エラー、冪等性、ページング/ストリーム、例 |
| WebSocket | ハンドシェイク、認証、メッセージ封筒、クライアント/サーバーメッセージ全量、順序、再接続、エラー、例 |
| CLI | コマンドツリー、引数/環境変数、stdin/stdout/stderr、終了コード、例 |
| gRPC | proto パッケージ/サービス/メソッド、メッセージ、ステータスコード、メタデータ/認証、ストリーミング、例 |
| MCP | サーバー情報、ツール/リソース/プロンプト、スキーマ、トランスポート、エラー、例 |
| A2A | エージェントカード、スキル、メッセージ/タスク遷移、認証、エラー、例 |

**宣言と実装の一致**を検証する。宣言されたのに実装がない、実装があるのに宣言がない、どちらも fail。抽出不能なら「未検証」として通過させず、fail closed にする。

### 5.4 「必要十分」の定義

- **不足（gap）**: 公開境界の要素 — 到達可能な公開入口、入力/出力フィールド、エラーコード、インターフェース操作、宣言された効果 — のいずれかが契約に現れない。
- **過剰（leak）**: 契約に現れる識別子・パス・シンボルが公開許可リストにない、または内部アルゴリズム・私有モジュール・内部 DB スキーマ・実在秘密情報が含まれる。
- **必要十分**: gap 0 かつ leak 0。かつ、例がコンパイル/実行でき、文書だけの結合テストが通る。

許可リストは**文書からではなくコード/IDLから生成**する。これが「内部を隠蔽しつつ不足を許さない」ための要である。

## 6. 生成パイプライン

### 6.1 新規コマンド

**`/contractify-boundary`**

```text
/contractify-boundary [--workspace=<root>] [--unit=<id>] [--check-only] [--migration]
```

処理:

1. **Preflight** — ワークスペース/単位/設定を発見。曖昧なら fail closed。
2. **証拠収集** — RFC-SEED の Coupling Contracts、RFC-STEP-CONTRACTS、OBLIGATION、GRAPH の `api_contract` / `error_policy` / `data_model` / `state_machine` / `security` / `config` ノード、workspace-map、manifest、tree manifest、effective-policy、law closure、公開面、インターフェース面。
3. **単位分類** — workspace/package、role、interfaces、artifact kind、言語、提供/消費。
4. **意味層の執筆** — 固定見出しに対する grill。事実は証拠参照付き。未解決は fail closed（推測で埋めない）。
5. **構造化書き込み** — `contract-crud` 経由で JSON を更新。AI は JSON を直接編集しない。
6. **描画** — JSON から Markdown を決定論的に生成。
7. **検証** — V1〜V10 を実行。失敗時は成果物を確定しない。
8. **索引/状態更新** — `BOUNDARY-INDEX.*` と `BOUNDARY-CONTRACT-Status.json`。

**`/verify-boundary-contract`**

```text
/verify-boundary-contract [--workspace=<root>] [--unit=<id>] [--json]
```

読み取り専用。CI と review/resolve から呼ぶ。終了コード:

- `0` 合格
- `1` 契約上の欠陥（gap/leak/stale/example 失敗）
- `50` 証拠不足・抽出不能（fail closed）

### 6.2 既存コマンドの変更

| コマンド | 変更 |
|---|---|
| `/plan-ticket` | 必須節「Boundary impact」— 触れる unit、公開面/インターフェース変更の有無、契約更新の要否 |
| `/start-ticket` | 依存先の契約を読む。不在/陳腐化なら開始不可 |
| `/review-ticket` | 影響 unit の契約を検証。コード差分と契約差分の整合を確認 |
| `/resolve-ticket` | 契約検証失敗なら解決不可 |
| `/find-omissions` | 境界契約の欠落（未生成、stale、未文書化入口、未文書化インターフェース）を omission として列挙 |
| `/amend-rfc-up` / `/drill-rfc-down` | RFC 変更後に影響 unit を stale 化し、契約再生成を完了条件に含める |
| `/crystalize-readme` | 変更しない。契約の前提にしない。将来、ユーザー向け README を契約から描画する統合は可能 |

### 6.3 パイプライン上の位置

```text
... → /crystalize-readme
    → /contractify-boundary        # 新規: 境界契約の生成/更新
    → /verify-boundary-contract    # 新規: 機械ゲート
    → /drill-rfc-down / /amend-rfc-up
```

ただしこれは一括実行ではなく、**単位ごとのライフサイクル**である。

- パッケージ実装完了時（resolve 後）: その unit の契約を生成/更新。
- ワークスペース完了時: ワークスペース契約と索引を生成。
- RFC 変更時: 影響 unit を stale 化し、再生成。
- plan/start/review/resolve/find-omissions: 常に検証。

## 7. 検証設計（機械ゲート）

| ID | 検証 | 入力 | 判定 | 失敗時 |
|---|---|---|---|---|
| V1 | 存在 | 発見された全 unit + workspace | `.md` と `.json` が存在し、索引に載る。孤児契約なし | exit 1 |
| V2 | スキーマ | JSON Schema、Markdown 見出し順 | 必須フィールド・見出し・アンカーが揃う | exit 1 |
| V3 | 鮮度 | 証拠ダイジェスト（GRAPH、RFC-SEED、OBLIGATION、公開面、インターフェース面、manifest、map、例） | 全ダイジェストが現在値と一致 | exit 1（stale） |
| V4 | 公開面網羅 | コード/IDL から生成した公開許可リスト | 全到達可能公開要素が能力に割当済み。未割当 0 | exit 1（gap） |
| V5 | 言語マトリクス | 必須言語集合、検出された binding | 全必須言語に行がある。`native/ffi/sdk` は setup・entry・例あり。`via_interface` は対応操作を参照。`unsupported` は理由と代替経路 | exit 1 |
| V6 | インターフェース完全性 | 宣言 interfaces、抽出した実面 | 宣言 = 抽出 = 文書。操作・スキーマ・エラー・認証・例が完全 | exit 1 |
| V7 | 非混入 | 公開許可リスト、内部パス/私有シンボル/秘密パターン | leak 0 | exit 1 |
| V8 | 例の実行 | 例の正本、パッケージ | 全例がコンパイル。実行可能な例は実行成功 | exit 1 |
| V9 | 参照整合 | ワークスペース契約、パッケージ契約、tree manifest、RFC-SEED | 構成員・依存・提供/消費・境界 ID が一致。dangling 0 | exit 1 |
| V10 | 文書だけの結合 | 契約の例と能力マップ | 契約だけから生成したコンシューマがリンク/コンパイルし、能力を呼べる | exit 1 |
| V11 | 人間試行 | リリース時のサンプル | 実装者に質問せず、契約だけで結合を完了できる | リリース不可（QA 証跡） |

**V10 の意味**: AI に自由にコードを書かせて判定するのではなく、契約に含まれる例と能力マップから**決定論的に**コンシューマを組み立て、コンパイル/リンク/実行する。これにより「文書だけから結合できる」を再現可能に検証する。

**V11 の意味**: 最終的な人間十分性は機械では証明できない。リリースごとに、そのパッケージを書いていないプロのエンジニアが契約だけを使って結合し、実装者への質問が0件であることを確認する。これは承認フィールドではなく QA 証跡であり、契約文書自体には入れない。

## 8. 一般化（3プロジェクト非依存）

### 8.1 境界発見の優先順位

1. `boundary-contract.toml` の明示 unit（実態と一致しなければ fail）
2. `workspace-map.auto.toml` の `[[unit]]`
3. `manifest.json` の `units` + 言語ワークスペースメンバー
4. `WORKSPACIFY-TREE-MANIFEST.json` の inventory/structure
5. `Cargo.toml` workspace members / `package.json` workspaces / `pyproject.toml` / `go.work`
6. ディレクトリ走査は**候補提示のみ**。自動で合格にしない

衝突時は差分レポートを出して fail closed。**プロジェクト名による分岐は禁止**。

### 8.2 特殊形状の扱い

| 形状 | 扱い |
|---|---|
| map 不在（gaia） | tree manifest と言語 manifest から発見。なければ bootstrap を要求 |
| 入れ子パッケージ（gaia adapters、crystal adapters） | 最寄りの言語 manifest ディレクトリを package root とする |
| ルート被覆 unit（crystal） | 衝突規則で別名に退避 |
| ルート RFC/GRAPH 不在（doors/gaia） | パッケージ契約と tree manifest からワークスペース契約を構成。ルート RFC を必須にしない |
| インターフェースが map 未宣言（gaia） | 実装成果物を検出し、宣言なしなら fail。宣言を追加させる |
| 日本語ソース（gaia） | 意味層の言語を設定で `ja` にできる。機械フィールドは英語固定 |
| 非コード成果物（pjsip-prebuilt） | `artifact_kind: native-library`。C ABI / FFI として言語マトリクスに記載 |
| 消費境界でないパッケージ | `consumption: none` と理由・利用者を明示。契約は必須 |

### 8.3 ハードコード禁止

- 役割（core/adapter/operation/rest/...）は schema の enum ではなく、設定/宣言から読む。
- インターフェース種別はアダプタ登録制。未知種別は fail。
- 言語は manifest から検出。必須集合は設定。
- プロジェクト固有パス・クレート名・インターフェース名をコードに埋めない。
- テストは合成 fixture を使い、3プロジェクトは「現場監査」コマンドで別途検証する。

## 9. 移行設計

### 9.1 監査先行

`/contractify-boundary --audit` は何も書かず、全 unit の gap/leak/stale を列挙する。既存プロジェクトの実態を把握してから生成する。

### 9.2 bootstrap

- 完全に検証を通る unit だけ契約を書く。
- 通らない unit は契約を書かず、`BOUNDARY-CONTRACT-GAPS.md` に欠落を列挙して exit 1。
- **未完成の契約を書かない**。`[::STUB::]` を文書に埋め込まない。不完全な契約は、存在しない契約より危険だから。

### 9.3 移行モード

既存プロジェクトには `--migration` を許す。

- `BOUNDARY-CONTRACT-BASELINE.json` に既知 gap を unit 単位で記録（ダイジェスト付き、チケットキー付き）。
- baseline は**増やせない**。新しい gap は即 fail。
- baseline 対象 unit に変更が入ったら、gap を減らすか維持することを要求。増加は fail。
- リリース時は strict モード。baseline は除去期限とチケットを持つ。
- これは「移行のための会計」であり、恒久的な免除ではない。

### 9.4 適用順

設計は3プロジェクトに最適化しないが、検証順は次が自然。

1. crystal — ルート conver 状態が揃い、ルート被覆 unit の試験になる。

## 12. 危険と対策

| 危険 | 対策 |

## 15. 実装への移行

本設計は、複数ファイルの新規追加、公開成果物の追加、パイプラインのアーキテクチャ変更を含むため **Tiny ではありません**。

したがって、実装は `/make-ticket` パイプライン（make → plan → start → review）で起票して進める必要があります。私は設計の提示で停止し、勝手に実装を開始しません。

実装に進む場合、T1〜T10 をチケット化します。特に次の3点は、起票前に確定したい設計パラメータです。

1. **成果物名と配置** — `BOUNDARY-CONTRACT.{md,json}` を各パッケージ直下、ワークスペース直下、ルート被覆時は `.package.<unit-id>` に退避する案。
2. **意味層の言語** — 既定 `en`、プロジェクト設定で `ja` を許可する案。
3. **移行モード** — 既存3プロジェクトは baseline 付き migration から開始し、新規変更は strict で落とす案。

この設計で進めてよいか、ご判断ください。

# Q5
様々なコマンドに無闇に分散強制せず、/crystalize-readme にまとめることが合理的且つ安全(既存の conver を破壊してしまう可能性を最小限にするという意味の安全)だと思うが、違うのか。

# A5
いいえ、違わない。**その判断の方が正しい。** 前案の「6コマンド変更 + 2新規コマンド + 4新規トップレベル成果物」は、要件は満たせても conver への侵襲が大きすぎました。生成・執筆・描画は `/crystalize-readme` に集約すべきです。

ただし、**「生成の集約」と「強制の集約」は分けて考える**必要があります。全部を一つの対話コマンドに埋め込むと、CI から検証できず、「常に存在する」を保証できなくなります。結論は次の3層です。

| 層 | 置き場所 | 理由 |
|---|---|---|
| 生成・執筆・描画 | `/crystalize-readme` に集約 | 既存の usage README 生成器であり、人間向け文書の唯一の生産者。成果物と学習コストを増やさない |
| 検証 | 同じコマンドの `--verify` と、同一ロジックの独立スクリプト | CI と review が対話なしで呼べる。ロジックは一箇所 |
| 強制 | **単一の閉じゲート**（`/resolve-ticket` または `make`） | 分散させない。0ゲートでは「保証」にならない |

## 1. 前案から撤回するもの

- `/contractify-boundary`（新規コマンド）— 不要
- `/verify-boundary-contract`（新規コマンド）— 不要。`/crystalize-readme --verify` と同一スクリプトに統合
- `plan-ticket` / `start-ticket` / `review-ticket` / `find-omissions` / `amend-rfc-up` / `drill-rfc-down` の変更 — 原則すべて撤回
- `BOUNDARY-CONTRACT.md` / `BOUNDARY-INDEX.md` という新しい人間向け成果物 — 不要。**README を境界契約にする**
- パッケージ直下への新しい契約ファイル — 不要。README と sidecar JSON だけ

## 2. なぜ README を契約にするのが安全か

- `/crystalize-readme` はもともと「利用者向け README」を生成するコマンドであり、目的が一致している。
- パイプライン上でも `find-omissions → crystalize-readme` の位置にあり、実装と漏れ検出の後、人間に渡す直前の段階である。境界契約の生成位置として自然。
- パッケージ直下に README は現状存在しない（gaia / crystal / doors の README は plugin 用のみ）。衝突が少ない。
- 人間にとって「特別な契約文書を読む」は「パッケージの README を読む」で済む。新しい名前を覚えなくてよい。
- 既存の `CRYSTALIZE-Status.json` をそのまま検証状態に使える。新しい status 体系を増やさない。

前案で「README を使わない」としたのは、統合と侵襲最小化の観点では誤りでした。README の衝突は、マーカーと `--adopt` で防げばよい。

## 3. 統合後の `/crystalize-readme`

### モード（既定動作は不変）

| モード | 用途 | 出力 |
|---|---|---|
| 既定 | 既存の usage README 生成 | `README.md` |
| `--boundary --unit=<id>` | パッケージ境界契約 | `README.md` + `BOUNDARY-CONTRACT.json` |
| `--boundary --workspace` | ワークスペース境界契約 | ルート `README.md` + `BOUNDARY-CONTRACT.json` |
| `--boundary --verify` | 検証のみ（読み取り専用） | `CRYSTALIZE-Status.json` の `boundary` 名前空間 |
| `--boundary --audit` | gap/leak/stale の監査のみ | stdout |
| `--boundary --migration` | 移行 baseline の記録 | `BOUNDARY-CONTRACT-BASELINE.json` |

**既定モードのコードパス・出力・テストは一切変えない。** 境界モードは追加分岐であり、既存の会話的 TOC 生成とは別経路にする。これが「既存 conver を壊さない」ための最重要条件です。

### 境界モードの処理

1. 証拠収集 — RFC-SEED の Coupling Contracts、RFC-STEP-CONTRACTS、GRAPH、OBLIGATION、workspace-map、manifest、tree manifest、effective-policy、公開面、インターフェース面。
2. 固定見出しへの執筆 — 伝統的な境界契約の並び。任意 TOC は使わない。
3. `BOUNDARY-CONTRACT.json` への構造化書き込み — CRUD 経由。AI は JSON を直接編集しない。
4. `README.md` の決定論的描画。
5. 検証 V1〜V10 を同一コマンド内で実行。失敗なら README を確定しない。
6. `CRYSTALIZE-Status.json` の `boundary` に結果を記録。

### worksspace モード

- doors / gaia のようにルート RFC/GRAPH がなくても動く。
- 各パッケージの README と sidecar、tree manifest、manifest からワークスペース契約を構成する。
- ルート README には、ワークスペースの目的、パッケージ一覧、依存トポロジ、公開インターフェース、横断レシピ、非目標を書く。索引は別ファイルにせず、この README の一節にする。

### README 衝突の安全策

- README が存在し、`<!-- [::BOUNDARY-CONTRACT::] -->` マーカーがある → refine。
- README が存在し、マーカーがない → **拒否**。`--adopt` 指定時のみ、元ファイルを `README.pre-boundary.md` に退避して生成。
- README が存在しない → 新規生成。

これにより、既存の人間が書いた README を無言で破壊しない。

## 4. 検証と強制

### 検証ロジックは一箇所

`scripts/crystalize-readme/boundary/verify.mjs` に置く。`/crystalize-readme --boundary --verify` はこのスクリプトの薄いラッパー。CI はスクリプトを直接呼ぶ。

```bash
node .claude/scripts/crystalize-readme/boundary/verify.mjs --workspace=. --json
```

V1〜V10（存在・schema・鮮度・公開面網羅・言語マトリクス・インターフェース完全性・leak・例の実行・参照整合・文書だけの結合）は前案のまま。ただし**呼び出し口は1コマンド + 1スクリプト**に集約する。

### 強制は単一ゲート

- `/resolve-ticket` の完了検証で、影響 unit に対して `--boundary --verify` を1回実行する。
- あるいは、プロジェクトの `make check` に `boundary-check` を追加し、`resolve-ticket` が既存どおり `make` を呼ぶ。この場合、**コマンド変更は0**。
- `plan-ticket` / `start-ticket` / `review-ticket` / `find-omissions` / `amend-rfc-up` / `drill-rfc-down` は変更しない。
- 早期検出したければ review で同じ `--verify` を任意実行してよいが、**強制はしない**。強制点を増やすと侵襲が増えるため。

### 「常に存在」の意味

- 新規・完了 unit: `resolve` の時点で README 契約が存在し、verified であることを保証する。
- 実装順序（`WORKSPACIFY-IMPLEMENTATION-ORDER`）により、提供側は消費側より先に resolve される。したがって消費側が結合を始める時点で、提供側の契約は存在する。
- 既存プロジェクト: baseline に未移行 unit を明示し、新規 gap は即 fail。baseline は期限とチケットを持つ。
- stale な契約は存在するが、`resolve` ゲートで handoff を止める。存在保証と鮮度保証を分けて扱う。

| リスク | 対策 |

`/crystalize-readme` は、繰り返し実行されるたびに過去の記述を利用し、より洗練された README になる機構でなければならない。

- refine モードでは、既存 README と既存 status を読み、**過去の完成済み記述を再利用**する。
- 前回実行時からの証拠差分（sourceFile、GRAPH、Tickets、公開面、インターフェース面、例、コード）を計算し、差分のある節だけを再評価する。差分のない完成済み節は、原則として保持する。
- 見出し構造も、既存の妥当な見出しを保持し、証拠の変化に応じて追加・削除・統合する。毎回ゼロから作り直さない。
- ワークスペース README は、パッケージごとの管理ブロックを冪等に更新し、全体に関わる節は現在のパッケージ README 群から再計算する。再計算結果が前回と同じなら本文を保持する。
- 実行順に依存しないよう、パッケージブロックは独立・冪等にし、全体節は「現在存在するブロックの集合」から決定論的に再構成する。
- 同一パッケージの複数回実行、動的な順序、途中からの再開を受け入れる。

## 4. 「実装も含めて完成している場合にのみ書ける」という大前提を崩さない

これは絶対条件として維持する。

- README の節は、**その節に書かれた用法どおりに実装が完全に動く場合にのみ**書ける。
- 契約文書が存在する、境界契約の三層が揃っている、という理由だけで「書ける」と判断してはならない。契約の存在は実装の証拠ではない。
- 判定順序は固定する。
  1. 実装がその用法を満たして完全に動くか（specs / src / tests / 実行証拠）
  2. その実装境界が、意味層・言語利用層・インターフェース層として過不足なく必要十分に記述できるか
  3. パッケージ／ワークスペースの構成として矛盾・欠落がないか
- 1 が満たされないなら、2 と 3 がどれだけ揃っていても RESIDUE。実装未完成を契約の存在で覆してはならない。
- 2 だけが欠ける場合も RESIDUE。ただしその補強はコードとは限らず、インターフェース仕様、言語別利用手順、例、公開面の整理などであり得る。
- 実装と契約の記述が矛盾する場合も RESIDUE。契約を実装に合わせて書き換えるのではなく、どちらが正しいかを証拠で判断し、必要な補強を設計する。

## 5. 機械化と AI 判断の分担を固定しない

機械的検査器は十分に与えるが、**過剰な決定論化で AI の適切な判断を阻害しない**。

| 種類 | 例 | 扱い |
|---|---|---|
| 構造的不変条件 | ファイル存在、schema、marker 文法、リンク切れ、書き込み失敗、秘密情報パターン、例のコンパイル失敗 | 機械的に停止・不合格にしてよい |
| 機械的証拠 | 公開面の抽出、インターフェース面の抽出、言語 manifest、依存関係、ダイジェスト、被覆一覧 | 検査結果を証拠として AI に渡す。最終判断は AI |
| AI 判断 | 実装が用法を完全に満たすか、意味層が十分か、プロのエンジニアが内部を読まずに結合できるか、RESIDUE が行動可能か、重複か、収束に寄与するか | AI が高度に思考して判断する |
| 禁止 | 機械的なチェックリストだけで「書ける／書けない」を決めること | 過剰な決定論化として避ける |

- 機械的検査は「証拠提供者」であり、意味判断の代替ではない。
- 機械的 finding が誤検出である場合、AI は理由を記録して棄却できる。ただし、構造的不変条件と秘密情報は棄却できない。
- 機械化できる割合は高いほどよいが、機械化によって判断の質が落ちるなら、その部分は AI に委ねる。
- 決定論は再現性のために使うが、意味の完成度を決定論だけで判定しようとしない。

## 6. 粗探しではなく収束機械にする

`/crystalize-readme` は、次のループを過剰に引き出して発散させる機構ではなく、**収束させる機構**でなければならない。

- RESIDUE は、実装補強または契約補強の**具体的な設計**を持つものだけにする。「ドキュメントが足りない」という一般論は RESIDUE にしない。
- 同一の根本原因を複数の節で重複して RESIDUE にしない。能力・インターフェース・境界単位で集約する。
- 証拠が変わっていないのに、既に解決した節や完成済みの節を再び RESIDUE にしない。
- 前回の RESIDUE には安定した識別子を持たせ、new / persisting / resolved を追跡する。再実行で重複生成しない。
- 新しい証拠がないのに RESIDUE が増える場合、それは過剰検出のシグナルとして扱い、集約・降格・棄却を検討する。
- 体裁、表現の好み、軽微なスタイルは RESIDUE にしない。必要ならその場で直すか、無視する。
- コマンドの終了条件は「絶対完成」ではなく、**現在の証拠のもとで新たに行動可能な RESIDUE がない**こと。RESIDUE が残っていても、それが次の実装ループに渡すべき明確なものであれば、コマンドは正常に終了する。
- 外側の収束は、RESIDUE → `/drill-rfc-down` → 実装 → 再実行のループが担う。コマンド内部で無限に完璧を目指さない。

## 維持する不変条件

- `/crystalize-readme` だけがパッケージ README とワークスペース README を書く。他のコマンドは契約を生成・更新しない。
- 境界契約文書は、ワークスペース README とパッケージ README 群の総体である。新しい契約ファイル種別を増やさない。
- RESIDUE は README 内に置き、単独ファイルにしない。証拠と補強設計を伴う。
- RESIDUE → `/drill-rfc-down` → チケット化 → 実装ループ、という出荷判定機構を壊さない。
- パッケージ README は従来どおり。ワークスペース README は管理ブロック方式で、人間の非管理領域を破壊しない。
- AI は README を直接編集しない。書き込みはスクリプト経由。
- 非対話・自走完走。Step 1 の例外はもう存在しない。

## 結論

この修正により、`/crystalize-readme` は「完成を証明する検証器」ではなく、**実装完了を大前提に、境界契約としての README 群を反復的に洗練し、行動可能な RESIDUE だけを残して次の実装ループへ収束させる機械**になります。完成の保証はせず、機械化は証拠提供に留め、最終判断は AI に残す。この理解で設計を確定します。

## 5. Non-interactive TOC

### 5.1 Required section families

The TOC must cover the three contract layers. Derivation checks presence; AI writes the content. A non-applicable family needs an explicit waiver with evidence.

| Family | Required when | Purpose |
|---|---|---|
| Purpose / what this is for | always | semantic layer entry |
| Quick start | always | first successful use |
| Capabilities / what you can do | always | semantic layer |
| Input / output / effects | always | semantic layer |
| Preconditions / postconditions / invariants | always | contract semantics |
| Errors / failure behavior | always | recovery |
| Constraints / non-goals | always | safe use |
| Language usage matrix | package is consumable as a library/binding | language layer |
| Interface documentation | declared interfaces non-empty | interface layer |
| Examples | always, last | complete usage design |

Required language set: manifest languages plus declared SDK/binding languages; default `[mainLanguage]`. No infinite language demand. Each required language gets a row with `native|ffi|sdk|via_interface|unsupported`, entry, setup, capabilities, limitations, example reference.

Interface kinds: `rest|websocket|cli|grpc|mcp|a2a`; adapter registry, unknown kind -> fail closed. Each declared kind gets complete documentation: entry, auth, schema, operations, errors, examples. Declared-but-unimplemented and implemented-but-undeclared both become residue.

### 5.2 Candidate derivation

Inputs, in precedence order:

1. Refine: prior `grill.toc.nodes` and prior README headings.
2. Graph usage nodes: nodes in `contractChain`, or kind in configurable usage-kind set; fallback to non-internal top-level nodes.
3. `sourceFile` usage-oriented headings.
4. Public surface capabilities grouped by domain.
5. Declared interfaces.
6. Required families above.

`derive-toc.js` outputs candidates with `id`, `level`, `heading`, `sources[]`, `existing`, `carryForwardEligible`, `coverage[]`. It does not decide semantics.

### 5.3 Structural validation

`validate-toc-structure.js` accepts `{nodes, priorNodes, waivers, retirements}`:

- IDs match `/^H[1-9][0-9]*(-[1-9][0-9]*)*$/`, depth <= 6, parents exist, unique.
- Last heading is `TRAILING_SECTION_TITLE` (`Examples (implementation samples) spec and design`).
- No duplicate normalized heading.
- Refine: removing a prior heading whose section is `complete` requires a `retirement` record with reason + evidence; otherwise reject.
- Coverage: unassigned capability/interface/language families are reported as warnings. AI must assign or waive in `set-toc`. Default is not a hard fail (avoid over-mechanization); the command requires the AI to resolve the warning list.
- Waivers contain `{family|capability, reason, evidence}`.

### 5.4 Status and completion

- New subcommand `update-step-status.js set-toc`: writes all `grill.toc.nodes` atomically with `status:'derived'`; `tocApproved=true` when structurally valid.
- `isTocComplete` accepts `derived` or `confirmed`.
- `end-step 1` no longer requires human confirmations.
- Keep `propose-heading`/`confirm-heading`/`delete-heading` for legacy status and tests; mark deprecated in the command text, do not remove.

### 5.5 Command Step 1 rewrite

Replace 1-2 through 1-7 with:

1. Read prior README/status (refine).
2. Run `discover-boundary.js`, `collect-evidence.js`, `derive-toc.js`.
3. AI finalizes TOC; run `validate-toc-structure.js`; run `set-toc`.
4. Run `plan-refine.js`; run `emit-readme-skeleton.js --plan=<path>`; apply section states.

Delete the CRITICAL exception paragraph and the `**ask; stop**` line.

## 6. Refine by evidence

### 6.1 Evidence digest

Per section, digest a canonical JSON of sorted entries:

- graph digest for the section's `contractChain` nodes
- `sourceFile` digest
- RFC-SEED / OBLIGATION / RFC-STEP-CONTRACTS digest for the section's contracts
- `specs/<ticket>.md` digests for mapped tickets
- public surface digest for the section's capabilities
- interface surface digest for the section's interfaces
- examples digest for referenced examples
- source file digests for graph-referenced files (bounded set)

If no fine-grained mapping exists, fall back to a package-level digest; `digestScope` records `section|package`. A package-level digest is safe but re-analyzes more sections.

### 6.2 Carry-forward rule

| Prior state | Evidence | Action |
|---|---|---|
| complete | unchanged | `preserve` (body copied byte-identically) |
| complete | changed | `reanalyze` (TEMPLATE) |
| residue | any | `reanalyze` (residue must be re-tested) |
| absent | any | `new` (TEMPLATE) |

AI may override `preserve` -> `reanalyze` with a recorded reason. AI may not override `reanalyze` -> `preserve`. This keeps I2: preservation is allowed only for text written under complete implementation and unchanged evidence.

### 6.3 Skeleton emission

`emit-readme-skeleton.js` gains `--plan=<path|stdin>`:

- `preserve` nodes: heading + prior body, no marker.
- `reanalyze|new`: heading + `<::TEMPLATE-README::>`.
- Examples: preserve only if prior examples complete and digest unchanged; else `<::TEMPLATE-EXAMPLES::>`.
- Atomic write.
- Human README safety: if `README.md` exists without crystalize markers and without `CRYSTALIZE-Status.json`, copy it once to `README.pre-crystalize.md`, then write. Never overwrite an existing backup. Implementation note: Step 1 writes the status before the skeleton, so the runtime test is marker absence plus `COPYFILE_EXCL`, not status absence; the observable outcome is the same one-time human copy.
- `reset-sections` remains for a deliberate full rebuild. New `set-section-states --plan` updates only reanalyzed/new sections; preserved sections keep their prior state and digest.

### 6.4 Evidence providers (mechanical, recomputed)

All evidence is recomputed at run time. Nothing is stored unless it cannot be recomputed. This is why no upstream command changes.

| Evidence | Source | Contract |
|---|---|---|
| Graph contracts | `RFC-GRAPH.json` nodes/edges/`contractChain` | direct read; digest |
| RFC coupling contracts | `RFC-SEED.md`, `RFC-STEP-CONTRACTS.json`, `OBLIGATION.json` | direct read; digest |
| Declared Rust surface | `api-consistency/parse-rust-surface.mjs` | ESM; `parseRustSurface({rfcText, packageId, rfcPath})`; parses RFC code fences, not source |
| Implemented Rust surface | new `parse-rust-source-surface.js` | `rustdoc` JSON when available; otherwise lexical `pub` scanner; unparsed constructs reported, advisory |
| TS / Python / Go surface | new `parse-language-surface.js` | TS exports, Python `__all__`, Go exported identifiers; advisory |
| Unit / role / interfaces | `workspace-map.auto.toml`, `manifest.json`, `WORKSPACIFY-TREE-MANIFEST.json`, `effective-policy.json` | TOML subset reader + JSON readers; declaration conflicts reported |
| Interface implementation | source scan for routes/listeners/commands/proto services/MCP tools/A2A skills | presence and file refs; unparsed advisory |
| Tickets / specs | `Tickets.json`, `specs/<key>.md` | mapping + digests |
| Examples | `examplesDir` | file list + digests |
| Language manifests | `Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod` | direct read |

Module-system constraint: `crystalize-readme/` is CommonJS. ESM assets (`api-consistency/*.mjs`) are loaded with dynamic `import()` inside an async main, never `require()`. The TOML reader is a local ~60-line subset (`[[unit]]`, tables, arrays, strings) modelled on `rust-interface-law/scripts/lib/toml.mjs`; do not depend on that skill being installed.

Advisory means: the finding is evidence for AI judgment, not a hard failure. Only unreadable/invalid structure fails closed.

## 7. Structured RESIDUE

### 7.1 Shape

Keep residues in README. Add machine records in `CRYSTALIZE-Status.json` under `grill.residues[]`:

```
{
  "id": "RSD-<12 hex>",
  "sectionIds": ["H1-2"],
  "heading": "...",
  "level": "package" | "workspace",
  "layer": "implementation" | "semantic" | "language" | "interface" | "consistency",
  "element": "<capability | interface operation | contract element>",
  "evidence": [{ "kind": "...", "ref": "...", "detail": "..." }],
  "reinforcement": { "design": "...", "acceptance": "..." },
  "evidenceDigest": "sha256:...",
  "state": "new" | "persisting" | "resolved",
  "firstRun": 1,
  "lastRun": 4
}
```

- `id = sha256(level|layer|element|scope)[:12]`, stable across runs.
- `evidence` >= 1; `reinforcement.design` and `acceptance` non-empty. A general "documentation is missing" residue is rejected as structurally invalid.
- Evidence kinds: `missing-artifact`, `unimplemented-entry`, `interface-gap`, `language-gap`, `contract-contradiction`, `test-gap`, `example-failure`, `workspace-gap`.
- README rendering: script inserts an invisible HTML comment after the marker so drill and later runs can key the residue without visual noise:

```
<::README-RESIDUE::>
<!-- crystalize-residue: id=RSD-... level=package layer=interface element=... -->
```

- Dedup: same `id` in multiple sections -> one canonical record with `sectionIds[]`; duplicate sections carry a one-line pointer to the canonical residue ID. Same `id` with different evidence is rejected; AI must consolidate.
- `mark-residue` accepts optional `residue`. New command path requires it for new residues. Legacy prose-only residues remain readable and are reported as advisories.

### 7.2 Lifecycle and convergence

`reconcile-residues` runs after Step 3:

- seen this run, existed before -> `persisting`
- seen this run, new -> `new`
- not seen, section now complete -> `resolved` (history retained)
- not seen, section still residue -> keep `persisting` and report a warning

Over-detection guard: if new residue count exceeds `max(3, 0.25 * sections)` and the package evidence digest is unchanged from the prior run, emit `POSSIBLE_OVER_DETECTION`; AI must consolidate or waive with a recorded reason. No hard fail.

Command exit condition: `--check` (all usage sections complete/residue, grammar clean) and `--check-residues` (structured records valid, IDs unique, resolved IDs absent from README) both pass. Residue count may be > 0; the command does not wait for zero.

## 8. Workspace README

### 8.1 Managed block grammar

```
<!-- [::CRYSTALIZE:WORKSPACE:BEGIN] -->
...
<!-- [::CRYSTALIZE:WORKSPACE:END] -->

<!-- [::CRYSTALIZE:PACKAGE:<unit-id>:BEGIN] -->
...
<!-- [::CRYSTALIZE:PACKAGE:<unit-id>:END] -->
```

- Exactly one workspace block; at most one block per unit id.
- No nesting. Begin without end, duplicate block, unknown block id -> structural error, exit 1, no write.
- README absent -> create with a title, workspace block, package block(s).
- README present without blocks -> append blocks; preserve the existing prefix byte-for-byte.
- README present with blocks -> replace only the managed block bodies.
- Atomic write + lock `.crystalize-workspace.lock` (O_EXCL; retry 5 x 100 ms; then fail closed).
- Deterministic order: unit id lexicographic; no timestamps.

### 8.2 Workspace block content

AI supplies, script writes:

1. Purpose: what the workspace is for; what can be done with it.
2. Package table: unit id, path, role, one-line purpose, README link, contract state.
3. Dependency/topology: providers, consumers, direction, interfaces.
4. Exposed interfaces: kind, entry, link to package interface section.
5. Cross-package recipes: how to combine packages for a use case.
6. Workspace IN/OUT/effects when a workspace-level API/CLI exists.
7. Non-goals.
8. Workspace residue, same marker grammar, `level=workspace`.

Package block content:

1. Unit id, path, role, purpose one-liner.
2. Exposed interfaces.
3. Link to package README and its section anchors.
4. Contract state (`complete|residue`) and residue IDs.
5. Dependency edges to other units.

Aggregate recomputation reads all present package blocks and package READMEs. Missing packages are listed as `not crystallized`; this is not a failure. No workspace completion gate.

### 8.3 Drill integration

`/drill-rfc-down` preflight extends read-only discovery:

- `$RFC_DIR/README.md` (existing)
- `<WORKSPACE_ROOT>/README.md` (new)

Both optional; dedup by resolved path; no new writer; no change to ticketization. This is the only other-command change, and it is read-only.

## 9. Section judgment order

Fixed, per section:

1. Does an implementation exist that fully works per the section's usage? Evidence: specs, src, tests, run artifacts, interface surface, examples.
2. Can that boundary be described exactly sufficient in semantic, language, and interface layers?
3. Is the section consistent with the package/workspace composition?

1 fails -> residue (`layer=implementation`). 1 passes, 2 fails -> residue (`semantic|language|interface`). 1 and 2 pass, 3 fails -> residue (`consistency`). Contract existence alone never passes 1.

## 17. Compatibility audit — second pass over the current implementation

The first design pass read the command, the core scripts, and the marker grammar. The second pass read the tests, the drill discovery path, and the status consumers. It found six constraints that change the plan. They are corrections, not a redesign.

### 17.1 The command file is installed three times, byte-identical

`tests/crystalize-readme/command-file.test.cjs` hashes three installs and asserts one digest:

```
tools/conver/.claude/commands/crystalize-readme.md
crates/siprs/.claude/commands/crystalize-readme.md
.claude/commands/crystalize-readme.md          # repository root
```

Every command edit must update all three. T1 includes this sync. A one-file edit fails C001-Post.

### 17.2 The command-file tests encode the old human checkpoint

`command-file.test.cjs` currently asserts:

- C001-Pre: the CRITICAL block carries an exception paragraph and it names a step.
- C001-Post: the exception names `1-2`.
- C001-Pre: a file with no exception (`SILENT_FILE`) is refused by the guard.

Removing the exception therefore changes the specified behavior. This is a deliberate spec change, not a regression. T1 rewrites these tests to assert:

- the prohibition keeps all five terms;
- there is no exception paragraph;
- the command contains no `ask; stop`, `propose-heading`, `confirm-heading`, A/B/C, or "user answers" token;
- all three installs remain byte-identical.

### 17.3 `check-command-steps.js` must accept an absolute prohibition

Current `inspectCommandSteps` returns `fault: NO_EXCEPTION` when the exception paragraph is absent. Change:

- no exception -> valid (`fault: null`, `unresolved: []`);
- no block -> still `NO_BLOCK`;
- an exception, if present, still must resolve every named step.

The guard's original purpose was to catch a dangling exception, not to require one. The new non-interactive form is the absence of an exception. The separate token scan in 17.2 prevents an accidental return of interactive language.

### 17.4 `MAX_STEP` stays 3

`tests/crystalize-readme/update-step-status.test.cjs` asserts `MAX_STEP === 3` and `validateStepNumber(4) === false`. `tests/conver/stage-timestamps.test.mjs` also writes steps `0..3`.

Do not add a Step 4. The workspace README update runs before `end-step 3`. Workspace progress lives in `grill.workspace`, outside `steps`. This preserves the step machine and its timestamp semantics.

`isTocComplete` accepts `derived` in addition to `confirmed`. Existing tests still pass: a proposed-only tree remains false; a confirmed tree remains true. `end-step 1` still throws while the TOC is incomplete.

### 17.5 Default script behavior stays byte-compatible (one recorded exception)

Existing tests assert the current default behavior:

- `emit-readme-skeleton.test.cjs`: no-plan refine overwrites the README and re-marks every section TEMPLATE.
- `e2e.test.cjs`: refine re-emits the skeleton and re-analyzes every section.
- `derive-output-paths.test.cjs`: `deriveOutputPaths` returns exactly `{rfcDir, examplesDir, readmePath}`, with no `residuesDir`.
- `loop-drive-readme.test.cjs`: `--check`, `resolve-section`, `mark-residue`, and the examples transitions keep their current semantics.

Therefore:

- carry-forward is enabled only by the new explicit `--plan` path; the no-plan path is unchanged;
- workspace discovery is a new `discover-boundary.js`; `derive-output-paths.js` is untouched;
- structured residue is an optional payload; legacy `{id, heading, content}` calls still work;
- `--check` is unchanged; `--check-residues` is new.

**English metadata exception (PX-452).** The skeleton metadata lines are `> Source RFC:` and `> Generated graph:`. Changing them from Japanese to English is the one intentional default-output change; every other default behavior listed above stays byte-compatible.

### 17.6 Drill discovery is split across two files

`preflight.cjs` imports `resolveDrillMaterial` from `resolve-material.js`. `WORKSPACE_ROOT` is already computed in `preflight.cjs` from the nearest `WORKSPACIFY-TREE-MANIFEST.json`. `resolve-material.js` currently discovers only `packageDir/README.md`.

The minimal change:

- pass `workspaceRoot` into `resolveDrillMaterial`;
- discover `<workspaceRoot>/README.md` when it exists;
- append it after the package README and before the sequences view, deduplicated by resolved path;
- add `workspaceReadmePath` and `workspaceReadmePresent` to the result and the Preflight table;
- keep `readmePresent`/`readmePath` meaning the package README;
- keep the resumed-record path authoritative.

`tests/drill-rfc-down/resolve-material.test.cjs` asserts specific fields, not the whole object; additive fields are safe. No new writer, no ticketization change.

### 17.7 Package root versus RFC directory

`deriveReadmePath` uses `rfcDir`. Existing tests rely on `readmePath = rfcDir/README.md`. `discover-boundary.js` may report a `packageRoot` above `rfcDir` when a language manifest or unit declaration says so. In that case the new planned writer targets `packageRoot/README.md`, and Preflight displays the divergence. The legacy no-plan path keeps `rfcDir/README.md`. This avoids a silent move of an existing README.

### 17.8 `api-consistency` is ESM and parses RFC fences, not source

`api-consistency/index.mjs` exports `parseRustSurface({rfcText, packageId, rfcPath})`. It reads Rust code fences in the RFC, not the implementation. It is ESM; `crystalize-readme/` is CommonJS.

Consequences:

- declared surface evidence is available and reusable via dynamic `import()`;
- implemented surface evidence is not available from that parser;
- add `parse-rust-source-surface.js` with a two-tier strategy: `rustdoc` JSON when available, lexical `pub` scanner otherwise; unparsed constructs are reported as advisory;
- do not `require()` an `.mjs` file; use `await import()` in an async main.

### 17.9 There is no TOML parser in `crystalize-readme`

`workspace-map.auto.toml` needs the `[[unit]]` subset. A reusable `parseToml` exists in `rust-interface-law/scripts/lib/toml.mjs`, but a conver project may not install that skill. Add a local `parse-toml-subset.js` (~60 lines) modelled on that shape. Do not create a cross-skill hard dependency.

### 17.10 Final verdict

The first pass was grounded in the command and core scripts but not complete against the tests, the module systems, and the consumers. The second pass found nine concrete constraints:

1. three byte-identical command installs;
2. command-file tests encode the removed checkpoint;
3. `check-command-steps.js` must accept an absolute prohibition;
4. `MAX_STEP` stays 3; workspace state lives outside `steps`;
5. default script behavior stays byte-identical; new behavior behind explicit flags/subcommands;
6. drill discovery spans `resolve-material.js` and `preflight.cjs`;
7. package root may differ from `rfcDir`; the legacy path keeps `rfcDir/README.md`;
8. `api-consistency` is ESM and parses RFC fences only; implementation surface needs a new advisory extractor;
9. no local TOML parser; add a subset reader.

All nine are incorporated. The design is complete enough to ticket. The one deliberate spec change is the replacement of the command-file tests for the human checkpoint, together with the three-install sync.
