# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Establish the siprs crate's public identity as a safe asynchronous SIP audio client library. Define SipClient as the top-level facade that integrates with P0-2's CoreReactor/RuntimeHandle/RuntimeCommand infrastructure.

### Purpose
Provide Rust application code with a safe, async-native facade over PJSUA SIP functionality, limited to audio-only voice communication. This crate exists to eliminate unsafe FFI boilerplate and deliver SIP calling capabilities through idiomatic Rust APIs — Result propagation, tokio async/await, typed events, and structured configuration.

### Motivation
P0-3 is the gateway ticket that establishes the crate's architectural identity before downstream tickets implement specific sub-systems: error types (P0-4), event system (P0-5), FFI layer (P0-6), audio pipeline (P1+). Without a defined SipClient + ClientConfig, no downstream implementation has a cohesive host. This ticket crystallizes the purpose defined in RFC 1 (§1) into concrete public API surface.

### Constraints
- Audio-only: no video API surface (RFC §1, §2). Enforced by compile-time assertions.
- All async public APIs must return Result<T, SipError> (RFC §1 constraint on N0001).
- PJSIP v2.x via FFI only — no raw socket-level SIP stack.
- Single crate with modular internal structure (RFC §6, C009).
- Shutdown must be cancellation-safe and idempotent (RFC §32, C044).
- SecretString for password storage (RFC §35-36, C048).
- Microphone input is optional via cpal-input feature flag (RFC §40, C051).
- MSRV 1.95, OS targets per RFC §4 (C006).

## Acceptance Criteria

- [Happy path] SipClient::new is called with a valid ClientConfig — returns Ok(SipClient) with initialized CoreReactor. All five module declarations (client, config, account, call, transport) are active in lib.rs. SipClient::shutdown() terminates cleanly. The compile-time invariant tests pass (no video types, all APIs return Result, SipClient is Send+Sync).
- [Error case] SipClient::new is called with empty sip_proxy_host — returns Err(SipError::InvalidConfig("sip_proxy_host must not be empty")). CoreReactor is NOT spawned. No orphaned resources.
- [Edge case] SipClient::shutdown() is called twice — first call succeeds (returns Ok(())), second call is a no-op (also returns Ok(()), verifying C044: Shutdown is idempotent). Calling any method after shutdown returns Err(SipError::Shutdown).

## Invariants

- [Normal condition] P0-2 CoreReactor must be initialized before SipClient accepts commands — SipClient::new spawns CoreReactor via RuntimeHandle and blocks until initialization confirms. After successful construction, initialized == true.
- [Error invariant] On SipClient::new failure, no resources leak — If CoreReactor spawn fails or initialization returns Err, all allocated resources (channels, threads) must be cleaned up. No orphaned threads.
- [Internal state invariant] SipClient must hold a valid RuntimeHandle at all times after construction — RuntimeHandle is protected by Arc and cannot be invalidated externally. Drop order: SipClient first, then RuntimeHandle.
- [Boundary invariant] ClientConfig fields must pass validation before construction — sip_proxy_host must be non-empty, sip_proxy_port in [1, 65535], user_agent max 256 bytes, credentials password must use SecretString for zeroization on drop.

## Boy Scout Rule

Translatability improvements for P0-3:
1. lib.rs: Uncomment module declarations — convert [::STUB::] comments into active pub mod statements. Each module gets a one-line comment explaining its responsibility (noun phrase).
2. BootConfig → ClientConfig migration: Rename BootConfig::config: String to typed ClientConfig fields. This improves reader comprehension because "config" as a String tells nothing about its structure, while ClientConfig.sip_proxy_host etc. are self-documenting.
3. RuntimeCommand::Initialize { config: String } → { config: ClientConfig }: Replace opaque String with typed struct. This transforms a function that reads as "initialize with string" to "initialize with client configuration" — a transparent statement of intent.
4. ClientConfig validation: Extract validate() method with named error variants (InvalidConfig::EmptyHost, InvalidConfig::InvalidPort) instead of leaving validation implicit. This turns "check config" into "validate config structure" — a verb phrase that communicates what happens.
5. SipClient::new constructor: Implement the Builder pattern (already designed in client_config_spec.rs) for optional fields, keeping required fields in a non-optional constructor. This makes the calling code read as SipClient::builder().stun(...).ice(true).build() instead of SipClient::new(config_with_15_fields).
6. Apply the Boy Scout Rule to any runtime code touched during migration: ensure all functions read as verb phrases, all variables as domain nouns, no single-letter variable names, no hardcoded magic values.

Runtime testing of each method's specific error return path requires downstream tickets (P0-4 for SipError variants, P0-5 for event types, P0-6 for FFI integration). This ticket establishes the convention and verifies it at compile time. This is not a defect — this is a deliberate design choice for the facade layer.
