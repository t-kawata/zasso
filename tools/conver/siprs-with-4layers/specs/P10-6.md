# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
The P10-6 event system provides the complete bridge between PJSIP C callbacks and Rust async event consumers. It defines the SipEventPayload enum (all P0 variants: Registration/Call/DTMF; P1: Transport/ICE; P2: supplemental), the EventBus with split control/raw_sip broadcast channels, the NativeEvent-to-SipEventPayload conversion functions, and the Dual Client routing infrastructure (single Reactor + account_id-based EventBus dispatch). Every PJSIP callback-generated event is delivered to the correct SipClient's EventBus as a typed SipEvent struct. This is the re-implementation round closing the five ABC-inspection gaps (O-001..O-005) so every contract (C020-C024, C030, C039) is verifiable against production code.
### Purpose
SipClient consumers (UI layer, audio pipeline, logging) need observable, structured notifications about SIP state changes. Without this event system, application code would poll for state or interpret raw PJSIP callbacks directly. The EventBus provides a decoupled publish-subscribe pattern: the Reactor publishes SipEvents onto broadcast channels; multiple consumers independently subscribe and filter (via AccountEventReceiver); RawSIP messages are isolated on a separate bus to prevent control event loss. This is the primary async communication channel between the synchronous PJSIP thread (C callbacks) and the async Rust world (tokio tasks).
### Motivation
The prior implementation produced green tests that did not exercise the production publication/dispatch flows: RegistrationStateChanged never published an event (O-001), DtmfSent never fired as a timeout (O-002), dual-client routing existed only inside test bodies (O-003), the query API did not exist (O-004), and Lagged(n) was asserted loosely (O-005). The ABC Inspection Pipeline confirmed contracts' pre/post/invariants were not translated into tests of production behavior. Downstream tickets (P2-2 error payloads, P2-4 audio pipeline, P4-1 registration state machine, P0-6 FFI bridge) depend on these events actually being delivered. Leaving the gaps means contract violations are undetectable.
### Constraints
- Single Reactor constraint: global_runtime() unchanged — dual-client dispatch is EventBus-only (C039). dispatch_event/process_native_event are pub(crate) and wired into the reactor loop only when the FFI callback bridge (P0-6/P3-2) delivers NativeEvents ([::STUB::] P12-7).
- Broadcast channel (lossy delivery): tokio::sync::broadcast is the only supported channel type. No reliable delivery, no per-subscriber retransmission (N0020).
- PJSUA dependency: NativeEvent types mirror PJSIP callback signatures (pjsip_inv_state, pjsua_call_media_status). CallMediaStateChanged currently hardcodes media_status=1 ([::STUB::] P11-10).
- DtmfSent 500ms timeout may race with the real PJSIP callback — consumers must tolerate duplicate DtmfSent events (N0029). spawn_dtmf_sent_timeout is invoked by the SendDtmf handler only when P5-2 completes wiring ([::STUB::] P11-6).
- tokio::time::pause() requires the `test-util` tokio feature — enabled in Cargo.toml (test-time only, no runtime dependency change).
- No new crates; the production flow must be testable with MockBackend (no live PJSIP). Real pjsua_acc_get_info() is deferred to P4-2.

## Acceptance Criteria

- **[Happy path]** Production RegistrationStateChanged flow: NativeEvent::RegistrationStateChanged{acc_id=1} → Reactor::process_native_event → backend.get_account_info() (MockBackend 200) → registration_status_to_payload → dispatch_event publishes RegistrationSucceeded on client A's EventBus; the AccountEventReceiver for acc_id 1 receives it. DtmfSent flow: SendDtmf accepted (reply Ok) then spawn_dtmf_sent_timeout publishes DtmfSent{Err(Timeout)} after the configured 500ms (tokio::time::advance) — both the synchronous return and the async event are observed (O-001, O-002). Single SipClient call-state transition events (OutgoingCallStarted → OutgoingCallTrying → CallConnected) arrive with correct EventMeta (timestamp, event_id, account_id, call_id).
- **[Error case]** RegistrationStateChanged with backend.get_account_info() returning Err(ReactorError::BackendError): the production flow publishes exactly one failure SipEvent (SipEventPayload::Error or RegistrationFailed) — no silent drop, no panic, no duplicate; then SipClient::accounts()/call_state() still returns authoritative state consistent with the mock (O-001 + O-004, C021 + C024). Dual-client dispatch with an unmatched account_id falls back to default_event_bus — no panic, no misrouting (O-003).
- **[Edge case]** Dual Client production dispatch: two SipClient instances with account_ids A and B registered in client_event_buses; dispatch_event(event for A) → client A's bus receives it and client B's bus does not (TryRecvError::Empty) — proving the C039 isolation invariant against production code, not a test-local HashMap. account_id=None lifecycle events reach both buses plus default_event_bus. Exact Lagged(2) is asserted for capacity-2 overflow (O-003 + O-005). DtmfSent timeout does not fire before the deadline (499ms → no event; 500ms → event).

## Invariants

- [Normal condition] EventBus::publish() must never block — broadcast::Sender::send() is non-blocking by design (eventbus_publish_non_blocking). SipEventPayload must be Clone + Debug. EventBus must be Clone (all clones share the same Sender — eventbus_clones_share_same_sender). NativeEvent conversion must be total over defined P0 variants; convert_call_state total over pjsip_inv_state 0-4 with explicit match arms.
- [Error invariant] On Lagged(n), the receiver skips n messages and resumes from the current position — no crash or state corruption; AccountEventReceiver must not panic on Lagged(n) (account_receiver_lagged_propagated). RegistrationStateChanged with backend.get_account_info() returning Err must still publish a failure event (SipEventPayload::Error) — no silent drop, no reactor state corruption (process_native_event_registration_err_publishes_failure, C024). DtmfSent timeout fallback must not abort any ongoing call operation — it only publishes DtmfSent{Err(Timeout)} (C030).
- [Internal state invariant] EventBus Sender is shared across all Clones. AccountEventReceiver holds its own broadcast Receiver. The Reactor owns the EventBus Sender + client_event_buses map; client_event_buses is only mutated by SipClient initialization/shutdown, not by event dispatch. DtmfConfig::sent_timeout_ms is read once at SendDtmf dispatch time; later config changes do not affect already-queued timers (C030). SipClient::accounts()/call_state() read the authoritative ClientState, not the event stream (C021, O-004).
- [Boundary invariant] EventBus default capacity 2048 must accommodate ~100 concurrent calls (~20 events/call); RawSIP channel capacity must be configured independently. DtmfSent timeout default 500ms must be less than typical PJSIP DTMF duration; sent_timeout_ms is configurable via DtmfConfig::sent_timeout_ms (C030). Lagged(n) count equals the number of skipped messages (broadcast channel semantics) — asserted exactly, not matched with a wildcard (eventbus_lagged_detection asserts Lagged(2), C020/O-005).

## Boy Scout Rule

Boy Scout Rule — Translatability improvements (P10-6 re-implementation):
1. src/client.rs — the event channel field reads as a domain noun ('events'); subscribe()/subscribe_account()/subscribe_raw_sip() are verb phrases returning typed receivers. accounts()/call_state() read as 'give me the authoritative account list' / 'give me the authoritative call state' (C021 source-of-truth).
2. src/runtime/reactor.rs — dispatch_event(&client_event_buses, &default_event_bus, event) and process_native_event(&backend, &client_event_buses, &default_event_bus, event, &calls) are named, single-responsibility functions that read as 'dispatch this event to the right bus' / 'process this native event and publish the outcome'; extract_event_ids keeps the id-resolution paragraph separate.
3. src/api/m20_dtmfsent_twophase.rs — spawn_dtmf_sent_timeout(call_id, method, digit, timeout_ms, event_bus) is a free function returning a JoinHandle, extracting the timer logic so the two-phase semantics (return=accepted, event=sent) read as prose.
4. src/config.rs — DtmfConfig { sent_timeout_ms: u64 } is a domain struct with Default (= DEFAULT_DTMF_SENT_TIMEOUT_MS) replacing any magic 500 literal with the named constant.
5. Named constants — DEFAULT_DTMF_SENT_TIMEOUT_MS = 500 (exists); DEFAULT_EVENT_BUS_CAPACITY = 2048 is used as a literal in client.rs:99 and should be extracted into a named constant; MAX_CONCURRENT_CALLS = 100 for the capacity-sizing comment.
6. src/api/eventbus_receiver.rs — remove the buggy dual_client_dispatch_routes_to_correct_bus (both buses inserted under the SAME AccountId 1 — the second insert overwrites the first, so the test never proves isolation); production dispatch tests in reactor.rs supersede it.
7. src/runtime/command.rs — from_runtime_command() is a single large match; split into per-variant helper functions (dispatch_initialize, dispatch_add_account, dispatch_send_dtmf, dispatch_get_account_info, dispatch_query_state) so the code reads as sequential paragraphs.
8. Outside scope: convert_call_state_with_previous is #[allow(dead_code)] until the FFI bridge wires CallDirection (P3-2); keep the [::STUB::] marker so the deferral is explicit and the function's purpose is documented.

### Exceptions

- Exception: Real pjsua_acc_get_info() FFI call for NativeEvent::RegistrationStateChanged is not testable in a pure Rust unit environment — it requires a live pjsua library with registered accounts. Reason: pjsua_acc_get_info() is a C FFI function needing a running pjsua instance; not testable without the live PJSIP stack. This is not an architectural defect — MockBackend::get_account_info() (src/runtime/backend.rs:276-287) provides the identical data shape (AccountInfoSnapshot) for deterministic unit tests, and the real FFI call is covered by P0-6+ integration tests. Alternative: MockBackend with configurable get_account_info_result validates the full conversion + publication logic without FFI.
- Exception: Actual PJSIP callback invocation (on_reg_state2, on_call_state, on_dtmf_digit) is not testable in a pure Rust unit environment — these are C→Rust callbacks triggered by a live PJSIP stack. Reason: FFI callback registration and invocation requires a live PjsuaBackend (P0-6); not testable without the real PJSIP stack. This is not an architectural defect — NativeEvent injection (constructing NativeEvent values directly) deterministically covers the conversion/dispatch logic, and P0-6+ integration tests cover the real callback path. Alternative: construct NativeEvent values directly for process_native_event/convert_native_event_to_payload tests.
- Exception: Real-time DTMF callback-vs-timeout race timing variance is not testable deterministically — the actual PJSIP callback may arrive just before or after the 500ms wall-clock timeout. Reason: the timeout is a wall-clock timer; system scheduling makes the race non-deterministic and thus not testable in a deterministic unit environment. This is not an architectural defect — tokio::time::pause()/advance() provides a deterministic simulation (test-util feature), and production behavior is verified by P0-6+ integration tests. Alternative: tokio::time::pause() drives the deadline deterministically in unit tests.
- Exception: Dual Client concurrency race (a NativeEvent arriving during client registration/deregistration) is not testable automatically without a complex concurrency harness. Reason: client registration/deregistration is a rare operation serialized through the reactor command queue, making the race window theoretically present but practically zero and not testable in an automated unit environment. This is not an architectural defect — dispatch_event is a pure function over (client_event_buses, default_event_bus, event) with no shared mutable state; deterministic routing tests cover all three branches (matching/default/broadcast). Alternative: deterministic dispatch tests; QA-phase stress test for the registration/deregistration race.
- Exception: A live SIP registrar's registration timeout/error response is not testable in a deterministic unit environment. Reason: a real registration timeout depends on the network peer's non-response, which cannot be simulated without a live network peer and is therefore not testable deterministically. This is not an architectural defect — MockBackend::get_account_info() can be configured to return Err(ReactorError::BackendError) or any status code, deterministically exercising the production failure publication path. Alternative: MockBackend returns Err and the test asserts SipEventPayload::Error is published exactly once.
