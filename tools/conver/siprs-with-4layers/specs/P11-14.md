# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Invariants

- [Normal condition] P0-2 CoreReactor must be initialized before SipClient accepts commands — SipClient::new spawns CoreReactor via RuntimeHandle and blocks until initialization confirms. After successful construction, initialized == true.
- [Error invariant] On SipClient::new failure, no resources leak — If CoreReactor spawn fails or initialization returns Err, all allocated resources (channels, threads) must be cleaned up. No orphaned threads.
- [Internal state invariant] SipClient must hold a valid RuntimeHandle at all times after construction — RuntimeHandle is protected by Arc and cannot be invalidated externally. Drop order: SipClient first, then RuntimeHandle.
- [Boundary invariant] ClientConfig fields must pass validation before construction — sip_proxy_host must be non-empty, sip_proxy_port in [1, 65535], user_agent max 256 bytes, credentials password must use SecretString for zeroization on drop.

- [Normal condition] `SipClient::new` returns `Ok` only after the reactor thread is spawned and `backend.initialize(&config)` succeeds; the returned `RuntimeHandle.is_terminated() == false`. The facade never hands back a client whose reactor is down (C002 precondition).
- [Error invariant] On `SipClient::new` failure (invalid config or spawn error), no resources leak: the `Err` path returns before `Self` is constructed, the command-channel sender is dropped, and no `siprs-reactor` thread remains orphaned (acceptance error case).
- [Internal state invariant] `SipClient` holds `Arc<RuntimeHandle>` + `EventBus` + `ClientConfig` for its whole lifetime; `handle()` always returns a live handle; drop order is `SipClient` first (dropping `EventBus` receivers) then `RuntimeHandle`.
- [Boundary invariant] `ClientConfig.validate()` enforces `sip_proxy_host` non-empty, `sip_proxy_port ∈ [1, 65535]` (the `u16` type makes >65535 unrepresentable), `user_agent ≤ 256` bytes; `AuthCredentials.password` is `SecretString` (zeroized on drop, never visible in `Debug`).

### Exceptions

- Exception: Video API absence is a structural invariant, cannot test as runtime assertion — Reason: The crate purpose explicitly excludes video (RFC §1). No video-related types exist in any src/ file. This is a compile-time property verified by the type system and module visibility. Any future addition of video types would fail the compile-time invariant tests defined in testUnit. This is NOT an architectural defect — the RFC deliberately scopes to audio-only, and the type system enforces this at compile time. Alternative verification: compile-time invariant checks in testUnit (UT: [Boundary] Audio-only API surface, UT: [Invariant] No video types in public module exports).
- Exception: SipClient::new returning Result is a type-level invariant, cannot test as individual runtime assertion — Reason: The function signature SipClient::new(config: ClientConfig) -> Result<(Self, Receiver<SipEvent>), SipError> is enforced by the Rust compiler at compile time — every caller must handle both Ok and Err. The Err branch IS tested in testUnit for invalid config. Alternative verification: compile_fail tests in testUnit cover the error path at the type level. This is NOT an architectural defect — returning Result from fallible operations is idiomatic Rust design.
- Exception: All public async fn signatures returning Result<T, SipError> cannot test individually at runtime — Reason: This architectural invariant is enforced by the Rust compiler and verified by compile-time tests in testUnit. Runtime testing of each method's specific error return path requires downstream tickets (P0-4 for SipError variants, P0-5 for event types, P0-6 for FFI integration). This ticket establishes the convention and verifies it at compile time. This is not a defect — this is a deliberate design choice for the facade layer.
- **Exception entry — CoreReactor::spawn is the single reactor-thread factory**
- [Item] The invariant "exactly one reactor thread exists per SipClient, created only via `CoreReactor::spawn`" **cannot test** as a single runtime assertion: other code could spawn additional threads, and the reactor thread terminates on shutdown, so a liveness check alone cannot assert exclusivity.
- [Reason] This is a crate-wide *structural* property, not a single-function behavior. A runtime test can observe the reactor it spawns (`JoinHandle`, `is_terminated`) but cannot observe threads created elsewhere. This is **not testable** as one assertion, yet it is NOT an architectural defect: the thread *factory* is fully testable (O-004 type assertion + `"siprs-reactor"` thread name), and only the exclusivity of the factory is a source-review property. Stating it is "not a defect" because the testable part is fully covered by testUnit.
- [Alternative verification] (1) O-004 closure: `let _: std::thread::JoinHandle<()> = join;` in `reactor_spawn_creates_thread` proves `spawn` uses `std::thread`. (2) `make stubs` / source review enforces that `thread::Builder`/`thread::spawn` appear only in `src/runtime/reactor.rs`. (3) Integration tests join the `JoinHandle` and assert `is_terminated()` to prove the reactor thread lifecycle.
- **Exception entry (copy this block for each non-testable item):**
- [Item] The RFC-presence tests assert heading markers, not the semantic completeness of each RFC section's prose.
- [Reason] RFC-ROOT.md is a natural-language design document; the contract Pre/Post conditions reference section *presence* (`## 34. 観測性`, `## 35. セキュリティ`, etc.), which is precisely and deterministically testable via exact heading assertions. The semantic completeness of each section's prose is not testable as a single assertion without fragile keyword heuristics that carry false-positive risk. This is not a design defect — the presence invariants ARE testable (exact headings), and the remaining prose-quality review is a documentation-review property, not a code invariant. The item is not testable only in the sense that prose quality is a non-deterministic documentation property, which is not an architectural defect.
- [Alternative verification] Source review of RFC-ROOT.md in the review phase; content-keyword assertions where a contract demands semantic content (e.g. purpose_scope_remains_audio_only already asserts `音声のみ`).
