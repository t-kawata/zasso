# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

### Purpose
Observability ensures debuggability of production SIP calls; SecretString prevents accidental credential leaks via log output (investigating an incident should never expose passwords); ClientCapabilities enables consumers to adapt their feature usage to what the runtime supports; platform documentation reduces build friction across three target OSes. The final round exists because the ABC re-inspection proved that the C047 postcondition ("every public SipClient/SipAccountHandle method carries #[tracing::instrument]") is not yet fully satisfied in source and not fully enforceable by tests, and that the C048 platform-documentation postcondition is enforced only at OS-name granularity. Closing these two gaps is the last step before the first production deployment of siprs.

### Motivation
Without tracing, diagnosing call failures in production is guesswork. Without SecretString, any error-format! or Debug-impl on AuthCredentials leaks the password to logs. Without ClientCapabilities, consumers cannot determine at runtime whether ICE, SRTP, or a specific codec is available. The ABC re-inspection confirmed 2 testable gaps remain in the current source: (new O-001) src/api/public_api_design.rs:43 and :48 are public methods without #[instrument], and all_public_client_methods_are_instrumented cannot detect their removal because its checks omit new/id/remove (SipAccountHandle) and add_account/remove_account/account/add_transport (SipClient); (new O-002) platform_docs_contain_os_notes stays green even if the specific build-note content (MSVC, CoreAudio, CoreFoundation, alsa, openssl, uuid) is stripped while the OS names remain. These gaps block the first production deployment of siprs.

### Constraints
Must work with the existing SipClient facade (P0-3) and EventBus (P0-5). SecretString must be zeroize-compatible but optional (behind the zeroize feature). All types must be serde-compatible (behind the serde feature) for WebSocket serialization (P4-4). tracing spans must not change public API signatures — the new #[instrument(skip(self))] attributes on SipAccountHandle::new/::id are attribute-only additions with no signature change. cpal-input is optional and non-default. ### Exceptions

- **Exception entry: tracing span runtime emission** — This item is not testable in a deterministic unit test; this is not an architectural defect. [Item] Runtime span enter/exit emission of #[tracing::instrument] (acceptance criterion 9). [Reason] Span output depends on the subscriber installed at runtime; asserting it requires tracing-subscriber as a dev-dependency, which is not currently in Cargo.toml. The compile-time contract (every public method carries #[instrument]) IS deterministically testable and is captured by the O-001 source-inspection test all_public_client_methods_are_instrumented — runtime emission is the tracing crate's own macro behavior, tested upstream, so this is not a design defect. [Alternative verification] O-001 source-inspection test asserting #[instrument(...)] presence on all public SipClient/SipAccountHandle methods; CI compiles with tracing enabled.
- **Exception entry: platform-specific OS linkage** — This item cannot test across all target OSes in a single run; this is not an architectural defect. [Item] Actual build linkage for Windows/MSVC, macOS system frameworks, Linux system libraries. [Reason] Each target OS requires its own build environment; a single cargo test run on one OS cannot link-verify the other two platforms. The platform documentation is a compile-time contract verified by the O-006 include_str! test, and per-OS linkage is proven by CI build-matrix compilation on each target — this is not a design defect. [Alternative verification] O-006 platform_docs_contain_os_notes (include_str! assertion) + CI matrix per-OS builds.
- **Exception entry: live microphone hardware capture in CI** — This item is not testable in a headless CI environment; this is not an architectural defect. [Item] End-to-end capture through a physical default input device. [Reason] The cpal-backed source (CpalMicrophoneSource, src/api/asyncaudiosrc_adapter.rs:312) is fully implemented and compiles under the cpal-input feature, but a real capture test requires a physical audio device that a headless CI runner does not provide. The deterministic, hardware-free behavior IS tested: SampleQueue drain semantics via CpalMicrophoneSource::from_queue unit tests, and the RFC §40 signature via open_default_microphone_source_has_correct_signature. Hardware absence is an external-environment limitation, not a deterministic-but-untestable design — this is not an architectural defect. [Alternative verification] open_default_microphone_source_has_correct_signature type-check under #[cfg(feature = "cpal-input")] + from_queue-based unit tests; manual smoke test on a device-equipped host.
- **Exception entry: Proxy-Authorization / WWW-Authenticate redaction** — This item is not testable in this ticket; this is not an architectural defect. [Item] Redaction of Proxy-Authorization and WWW-Authenticate headers in RawSipMessage. [Reason] The RFC-scoped contract (C048) for this ticket names only the Authorization header; Proxy-Authorization/WWW-Authenticate handling is a separate feature deferred to P2-6, so there is no production code path in this ticket against which a test could assert. The absence of the feature is a scope boundary imposed by an external dependency (the P2-6 ticket), not a deterministic-but-untestable design — the testable Authorization: redaction is fully covered by the redact_authorization_* tests. [Alternative verification] RawSipMessage::redact_authorization tests for single/multiple/no-header Authorization; P2-6 will add the extended-header fixtures.

#[tokio::test]
async fn client_initialized_event_carries_capabilities() {
    let config = ClientConfig::builder()
        .sip_proxy_host("sip.example.com")
        .sip_proxy_port(5060)
        .build();
    let (_client, mut rx) = SipClient::new(config).await.expect("new must succeed");
    // Reactor publishes nothing during Initialize; ClientInitialized is the
    // first control event. Loop defensively in case future reactor behavior adds
    // earlier events.
    let deadline = tokio::time::Instant::now() + std::time::Duration::from_secs(2);
    loop {
        let timeout = tokio::time::sleep_until(deadline);
        tokio::pin!(timeout);
        tokio::select! {
            _ = &mut timeout => panic!("ClientInitialized not emitted within 2s"),
            ev = rx.recv() => match ev {
                Err(tokio::sync::broadcast::error::RecvError::Lagged(_)) => continue,
                Err(e) => panic!("channel closed: {e:?}"),
                Ok(ev) => match ev.payload {
                    SipEventPayload::ClientInitialized(caps) => {
                        assert_eq!(caps.event_bus_capacity, 2048);
                        assert_eq!(caps.max_calls, u32::MAX);
                        return;
                    }
                    other => { tracing::debug!(?other, "skipping non-ClientInitialized event"); }
                },
            },
        }
    }
}
