# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P11-6: Wire spawn_dtmf_sent_timeout into the reactor SendDtmf handler and implement the two-phase DTMF-sent timeout once the reactor owns an EventBus

**Ticket Key**: P11-6 · **Phase**: 11

**RFC Source**: `RFC-ROOT.md`

## RFC Reference

~/shyme/zasso/crates/siprs/RFC-ROOT (§20, §23, §37)

## Background

### Goal
The reactor SendDtmf dispatch path must invoke `spawn_dtmf_sent_timeout` (src/api/m20_dtmfsent_twophase.rs:78) after `backend.send_dtmf` succeeds, so the C030 two-phase DTMF-sent flow is actually exercised: `send_dtmf()` returns `Ok(())` synchronously for command acceptance, and a `DtmfSent` completion/timeout event is published asynchronously on the reactor-owned `EventBus`.

### Purpose
The two-phase design (C030) was specified in P5-2 and the fallback timer implemented in P7-2, but `spawn_dtmf_sent_timeout` was left `#[allow(dead_code)]` because the reactor had no `EventBus` publish target. This ticket removes the dead-code marker by giving the reactor an owned `default_event_bus` and wiring the function into the SendDtmf handler.

### Motivation
Without this wiring the DtmfSent timeout fallback is unreachable — callers of `send_dtmf()` can confirm synchronous acceptance but never receive the asynchronous completion/timeout notification, leaving the two-phase contract unimplemented. P11-6 was flagged (INSPECTION_FLAGGED) and returned for a final defect-free re-implementation round; all three target STUBs (TS-001/TS-002/TS-004) are already resolved and the remaining crime TS-003 is a resolved/out-of-scope ORPHAN_TICKET_REF.

### Constraints
Real PJSIP send-complete callback wiring stays out of scope (P8-29 / pjsua-native FFI). The two `DtmfMethod` enums (account_config_spec vs m20_dtmfsent_twophase) are NOT unified — a total `From` conversion at the call site is required. `dispatch_event`/`process_native_event` remain gated behind P12-7; this ticket introduces the minimal reactor-owned `default_event_bus` so the timeout event has a publish target.

## Acceptance Criteria

- 【Happy path】After `backend.send_dtmf` succeeds, the reactor SendDtmf handler spawns `spawn_dtmf_sent_timeout` so a `DtmfSent { method, digit, status: Err(SentDtmfError::Timeout), pjsip_status: None }` event is published to the reactor-owned `default_event_bus` when no PJSIP completion callback arrives within `DEFAULT_DTMF_SENT_TIMEOUT_MS` (configurable via `DtmfConfig::sent_timeout_ms`). `send_dtmf()` still returns `Ok(())` synchronously for command acceptance — the two-phase separation (C030) is preserved.
- 【Error case】When `backend.send_dtmf` returns `Err`, the handler does NOT spawn the timeout timer and propagates the error; no spurious DtmfSent Timeout event is published.
- 【Edge case】When the real completion callback fires before the timer (future P8-29), the retained `JoinHandle` is aborted so DtmfSent is published at most once per digit (never a duplicate Timeout) — aborting the handle before the deadline suppresses publication. The EventBus used as the publish target is the reactor-owned bus (per-account when the event account_id matches, otherwise the default bus), consistent with `dispatch_event` routing.

## Invariants

- 【Normal establishment】After a successful `backend.send_dtmf`, the reactor SendDtmf handler spawns `spawn_dtmf_sent_timeout` for every digit in the command, so a `DtmfSent { method, digit, status: Err(SentDtmfError::Timeout), pjsip_status: None }` event is eventually published on the reactor-owned `default_event_bus` when no PJSIP completion callback arrives within `sent_timeout_ms`. `send_dtmf()` returns `Ok(())` synchronously — the two-phase separation (C030) is preserved.
- 【Invariant on error】When `backend.send_dtmf` returns `Err`, the handler replies `Err` and spawns NO timer — no spurious `DtmfSent Timeout` event is published for a failed command acceptance.
- 【Internal state】`DtmfSent` is published at most once per digit. The `JoinHandle` returned by `spawn_dtmf_sent_timeout` is retained so a real completion callback (P8-29) can abort it before the deadline; aborting suppresses the Timeout event. The reactor owns exactly one `default_event_bus`; per-account routing follows `dispatch_event` semantics (matching client bus when registered, else the default bus).
- 【Boundary】`DEFAULT_DTMF_SENT_TIMEOUT_MS == 500`; `DtmfConfig::sent_timeout_ms` defaults to 500 via `ClientConfig`. A timeout never fires before the deadline (tokio::time control) and the published event carries `call_id`/`account_id` in `EventMeta` with the correct `method`/`digit`.
