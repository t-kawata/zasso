# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## RFC Reference

## Background

### Goal
Give SipAccountHandle::update_config a real runtime account-configuration update path: accept an AccountConfigPatch, merge it with the authoritative ClientState config, validate the merge (C052 fail-fast), submit RuntimeCommand::UpdateAccount through the reactor, and surface the outcome as Result<(), SipError> instead of the historical silent no-op.

### Purpose
Callers (config UI, runtime policy changes) must be able to change a live account's mutable settings — registrar_uri, transport policy, register_on_start, codec/DTMF policy, registration_expires — without tearing down and recreating the account. The patch type makes partial updates explicit, and the reactor round-trip keeps the backend and ClientState in lockstep (C021).

### Motivation
P3-1 defined AccountConfig and its validation rules (C015/C052) but update_config was a `_patch`-discarding no-op because no incremental update path existed (historical public_api_design.rs:146-152). P10-3 implemented the lifecycle — AccountConfigPatch, RuntimeCommand::UpdateAccount, SipBackend::update_account, reactor ClientState mutation. This ticket makes that implementation the verified, spec'd behavior, closes the silent-drop gap definitively, and adds the missing error-path tests.

### Constraints
- Public API change: update_config now takes AccountConfigPatch (must be Send+Sync, Default no-op); RuntimeCommand gains an UpdateAccount variant so every exhaustive match (name(), from_runtime_command, Debug) must be updated.
- The merged config is validated before dispatch (C052) — the reactor never receives an unvalidated config (RuntimeCommand::UpdateAccount doc comment, command.rs:113-116).
- Real PJSUA application (pjsua_acc_modify) is out of scope (P8-20); only the patch/validation/dispatch/state path is implemented and tested against MockBackend.

## Acceptance Criteria

- **[Happy path]** update_config(patch) merges the patch with the authoritative ClientState config, submits RuntimeCommand::UpdateAccount, and returns Ok(()) when the reactor applies it — a subsequent query_state()/accounts() shows the patched config on the same account entry (entry.id unchanged).
- **[Error case]** A patch that fails AccountConfig validation (C015/C052) returns Err(SipErrorKind::InvalidConfig) BEFORE dispatch with the stored config unchanged; a reactor Err from UpdateAccount (backend failure, lost reply) is surfaced as Err(SipError) via the awaited reply channel — never a silent Ok; a missing account returns Err(AccountNotFound) before dispatch.
- **[Edge case]** AccountConfigPatch::default() (no-op) is accepted and returns Ok(()) without modifying the ClientState account entry; Option<Option<T>> fields support both set (Some(Some)) and clear (Some(None)); registration state is preserved across an update (C026).

## Invariants

- [Normal condition] AccountConfigPatch::apply(base) returns Ok only when the merged AccountConfig satisfies every AccountConfig::validate rule (C015/C052) — an invalid patch fails fast before any RuntimeCommand::UpdateAccount is submitted.
- [Error invariant] update_config never silently drops a patch — a non-Ok reactor reply (ReactorError) from RuntimeCommand::UpdateAccount is surfaced as Err(SipError) via SipClientHandle::submit()'s awaited reply channel (handle.rs:191); the ClientState account entry is left unchanged on error.
- [Internal state invariant] The reactor's ClientState.accounts[aid].config is the authoritative source of account config (C021); after a successful UpdateAccount the reactor replaces entry.config with the merged config and never recreates or reorders the account (entry.id unchanged).
- [Boundary invariant] AccountConfigPatch::default() is a no-op — applying an all-None patch yields a merged config identical to the base and must not alter ClientState; account_id is validated via AccountId::from_u64 and a missing account is rejected before dispatch.
