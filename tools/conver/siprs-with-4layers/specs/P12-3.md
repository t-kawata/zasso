# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Investigation

- src/model/memory_ownership_defaults.rs is 23 lines: header + `pub struct Model {}` (line 20) + `// [::STUB::] P12-3` (line 23). No implementation exists.
- RFC §47 (RFC-ROOT.md:2965-2970) defines the 4 ownership rules (callback pointers not held beyond scope; immediate copy to Rust; no pj_pool_t in Rust structs; pj_str_t always Rust-owned). §48 (RFC-ROOT.md:2972-2980) lists 7 defaults (transport UDP+TCP; codec Opus>PCMU; DTMF RFC4733; audio 16kHz/i16/stereo L=IN R=OUT; raw SIP enabled; SRTP disabled; ICE enabled).
- Contract C057 (N0056→N0037 inbound) is the governing contract; C038 (unsafe isolation) and C034 (non-blocking RT path) also apply to this ticket.
- ffi/pj_str.rs already provides PjOwnedStr (lines 23-28) with a Rust-owned Vec<u8> backing and slen excluding NUL; its constructor is `new(&str)` (copies bytes), `as_raw()` returns a copy of the pj_str_t, and it has `unsafe impl Send` + Debug/Display/PartialEq<str>. It is the concrete Rust-owned primitive the ownership model classifies.
- ffi/mod.rs declares pub mod bindings / pj_str / callback / backend_calls and documents the unsafe-isolation boundary (C038). model/mod.rs re-exports id/audio/aligner/resampler/media-bridge/raw-sip types and currently does NOT declare memory_ownership_defaults.
- Config defaults drift from §48: ClientConfig::default().transports = [udp:5060, tcp:5060] matches "UDP+TCP"; RawSipEventConfig::default().enabled=true matches "raw SIP enabled"; SrtpPolicy::default()=Disabled matches "SRTP disabled"; ClientAudioConfig::default().default_delivery_format="16000Hz/i16/stereo" matches the audio default (as a String placeholder). But AccountMediaConfig::default().ice=false contradicts §48 "ICE: enabled", and AccountCodecPolicy::default() (two booleans) does not express the Opus>PCMU order.
- AudioDelivery can reuse model::SampleRate::Hz16000, BitDepth::I16, ChannelLayout::StereoInOut (all exist in audio_format_chunkpair.rs). BitDepth derives PartialEq (not Eq), so AudioDelivery/DefaultPolicies derive PartialEq only.
- `make test` runs `cargo test` (Makefile line 12). `pub mod ffi` and `pub mod model` are public in lib.rs, so integration tests can reach siprs::ffi::pj_str and siprs::model.

## Acceptance Criteria

- - 【Happy path】memory_ownership_defaults.rs defines the ownership model (MemoryOwnership distinguishing Rust-owned vs PJSUA-pool-owned, plus NativePtrClassification and MemoryOwnershipTag) and the §48 DefaultPolicies record; the module compiles and the new types re-export through model/mod.rs.
- 【Happy path】The default policy matches C057: pj_str_t values outside FFI calls always point to Rust-owned memory (PjOwnedStr::classification() returns RustOwned); the original PJSUA ptr is only used as an immediate copy source, never stored (no raw-pointer constructor).
- 【Happy path】PjOwnedStr remains the concrete implementation of the Rust-owned backing (Vec<u8>) and satisfies the ownership model's Rust-owned policy via the MemoryOwnershipTag impl.
- - 【Error case】The model forbids embedding pj_pool_t-owned memory in Rust structs (type-level/documentation invariant): CALLBACK_ONLY classification is pool-owned + callback-scope; PjOwnedStr exposes no raw-pointer constructor, so no owned pj_pool_t memory can enter a Rust struct.
- - 【Edge case】Empty strings (slen=0, non-null ptr) and large inputs (>4096 bytes) remain valid and Rust-owned under the ownership model; classification helpers are const (no allocation) so the C034 non-blocking invariant holds on the RT path.

## Invariants

- 【Normal establishment】pj_str_t values outside FFI calls always point to Rust-owned memory (C057). Every pj_str_t held by Rust is backed by a PjOwnedStr's Vec<u8>; classification returns MemoryOwnership::RustOwned + OwnershipScope::RustOwned.
- 【Invariant on error】Native callback pointers are not held beyond callback scope; pj_pool_t memory is never embedded in Rust structs (C057). Because PjOwnedStr has no raw-pointer constructor, there is no code path — success or failure — that can store a pool-owned pointer.
- 【Internal state】All unsafe code is isolated to the ffi/ module; model/ and runtime/ contain no unsafe keyword (C038). The ownership-model module declares only types, consts, and pure classification helpers.
- 【Boundary】No blocking operations (lock acquisition, dynamic memory allocation, syscall, .await) in any function called from the PJSIP RT callback thread (C034). Ownership classification helpers are const fn; PjOwnedStr construction is synchronous and needs no Tokio runtime. Empty strings (slen=0) and >4096-byte inputs remain valid under the ownership model.

### Exceptions

- EX: [C057] Live pj_pool_t lifetime semantics is impossible to test without a real PJSUA stack (not testable here).
Reason: verifying that a pj_pool_t-allocated pj_str_t becomes invalid after the pool is freed requires a live PJSIP installation (pjsua-native feature) and a running media stack; without it there is no pj_pool_t to allocate from. This is not a design defect (not an architectural defect): the ownership model is a data-model contract fully specified as type-level/documentation invariants, and every observable rule is verified against the concrete Rust-owned primitive (PjOwnedStr). The pool-lifetime rule is enforced by construction — PjOwnedStr exposes no raw-pointer constructor, so a pool-backed pj_str_t can never be adopted into a Rust struct.
Alternative: verify the mirror-image invariant instead — PjOwnedStr (the only pj_str_t holder in Rust) is Rust-owned and its classification is asserted in unit tests; the §47 doc-comments on MemoryOwnership::PjsuaPoolOwned carry the pool-lifetime warning.
- EX: [C057] "pj_pool_t memory never embedded in Rust structs" cannot be tested by the Rust type system alone.
Reason: a C pointer (pj_pool_t-derived) is an opaque address; the borrow checker cannot prove where the pointee was allocated.
