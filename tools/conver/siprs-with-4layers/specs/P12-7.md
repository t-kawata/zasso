# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P12-7: Wire dispatch_event and process_native_event (with its extract_event_ids helper) into the reactor loop so NativeEvents delivered by the FFI callback bridge are processed

## RFC Reference

## Background

- 【Goal】Wire dispatch_event, process_native_event, and extract_event_ids into the reactor loop so NativeEvents delivered by the FFI callback bridge are converted to SipEvents and routed to the correct EventBus — eliminating the three #[allow(dead_code)] markers (reactor.rs:532,570,618) and the [::STUB::] P12-7 marker at reactor.rs:531.
- 【Purpose】P3-2 specified the dual-client EventBus dispatch (C039) and the NativeEvent→SipEvent conversion pipeline, but left the three helpers as dead free functions with no call site because the FFI callback bridge that feeds NativeEvents to the reactor was not yet linked. This ticket completes the production event flow: PJSIP callbacks → enqueue_native_event → reactor loop → process_native_event → dispatch_event → SipClient EventBus.
- 【Motivation】Without the wiring, events published by the FFI callback bridge (ffi/callback.rs:63-74 enqueue_native_event to the global ArrayQueue) have no consumer: RegistrationStateChanged would never produce RegistrationSucceeded/Failed (O-001), CallStateChanged would never produce CallConnected (O-003), and the entire observable event stream of siprs would be silent. RFC §27.3 (N0038) callback-routing design depends on the reactor receiving and processing these events.
- 【Constraints】No unsafe code added to runtime/reactor.rs, command.rs, handle.rs (C038). The reactor stays a single std::thread with the MPSC channel as the sole ingestion path (C039 single-Reactor invariant). EventBus publish remains a loss-tolerant broadcast; DEFAULT_EVENT_BUS_CAPACITY=2048 (client.rs:111) preserved. FFI callback-bridge enqueue itself (P8-21) is out of scope — this ticket provides the reactor-side ingestion receiver only.

## Acceptance Criteria

- - 【Happy path】A NativeEvent injected through RuntimeHandle::enqueue_native_event (the new ingestion receiver) is received by the reactor loop, passed to process_native_event with the backend, client_event_buses, and default_event_bus, converted to a SipEvent, and routed via dispatch_event to the correct client/default EventBus — verified by subscribing to handle.default_event_bus() and receiving the converted payload. RegistrationStateChanged events query the backend via get_account_info and publish RegistrationSucceeded (200) / RegistrationFailed (non-200) / Error (backend Err) with the correct EventMeta.account_id — no silent drop (reactor.rs:579-592), verified by the existing registration 200/403/err tests (reactor.rs:881,958,923) staying green.
- - 【Error case】Backend errors during NativeEvent processing are published as SipEventPayload::Error (reactor.rs:583) and never crash the loop — after an error event, the loop continues processing subsequent commands. enqueue_native_event on a terminated reactor returns Err(ReactorError::ReactorDown) rather than hanging.
- - 【Edge case】P1/P2 events (TransportStateChanged, NatDetected, etc.) are dropped without publication as documented (convert_native_event_to_payload returns None) — the loop must not panic and must keep processing (existing reactor.rs:1103 stays green). The reactor owns at least a default_event_bus; client_event_buses maps account_id to the registered SipClient bus (empty until P9-6) so no event is duplicated across clients (C039 invariant) — verified by the existing dispatch isolation tests (reactor.rs:790,820,854) staying green.

## Invariants

- 【Normal establishment】Single Reactor pattern (C039): every NativeEvent — whether enqueued by the FFI callback bridge (P8-21) or injected in tests via RuntimeHandle::enqueue_native_event — is processed serially on the one reactor thread through process_native_event, converted to a SipEvent, and routed via dispatch_event. The reactor owns default_event_bus (EventBus::new(DEFAULT_EVENT_BUS_CAPACITY=2048, None), reactor.rs:85-88) and the client_event_buses HashMap (reactor.rs:92); the loop reaches both.
- 【Invariant on error】Backend failures during NativeEvent processing never crash the loop: process_native_event maps get_account_info Err to SipEventPayload::Error (reactor.rs:583) and publishes it; a missing CallEntry / unresolved account_id yields no payload (convert_call_state CONFIRMED with None account -> None, m20_callstate_mapping.rs:86-92) — a documented silent drop, never a panic. EventBus::publish stays a loss-tolerant broadcast (control.send Result ignored). C039/C046.
- 【Internal state invariant】client_state remains the single source of truth owned by the reactor thread (C046): the NativeEvent arm reads client_state.calls to resolve owning accounts (reactor.rs:597-600) and never mutates it; QueryState returns a clone (reactor.rs:479), so event processing never races command dispatch or the query API.
- 【Boundary invariant】acc_id/call_id of 0 are PJSUA invalid sentinels and yield None (AccountId::from_u64 / CallId::from_u64 reject 0; extract_event_ids reactor.rs:1148). EventBus capacity 2048 is preserved (client.rs:111, DEFAULT_EVENT_BUS_CAPACITY eventbus_receiver.rs:29); NativeEvent ingestion is loss-tolerant, so exact delivery counts are asserted only for single-subscriber control receivers in unit tests.
