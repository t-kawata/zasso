## Acceptance Criteria

- 【Happy path】A phase that completes within the configured timeout returns Ok and records no timeout (existing shutdown tests stay green).
- 【Error case】A phase (e.g. CancelCalls) that exceeds the configured timeout produces ShutdownError::PhaseTimeout { phase, timeout } — and, per C044, subsequent phases still execute and the first error is returned.
- 【Edge case】The timeout is applied per phase boundary (per-call deadline plus an overall phase deadline), not as an unbounded per-call wait.
- 【Edge case】A zero or very small timeout does not panic — it degrades to an immediate PhaseTimeout for slow backends.
- **[Happy path] — Scenario confirming this ticket is complete:** ShutdownSpec::new(Duration::from_secs(5)) drives execute_sequence with MockBackend (call_ids=[1], account_ids=[1,2]); all five phases complete within budget; returns Ok(()); no PhaseTimeout is recorded; existing shutdown tests stay green.
- **[Error case] — Error scenario the feature must handle:** A CancelCalls phase whose per-call deadline is exceeded produces Err(ShutdownError::PhaseTimeout { phase: ShutdownPhase::CancelCalls, timeout }) with timeout == the configured value; per C044, UnregisterAccounts/DrainAudio/InvokeDestroy still execute and backend.initialized becomes false; execute_sequence returns the first error (the PhaseTimeout).
- **[Edge case] — Boundary/exception to verify:** timeout = Duration::ZERO (or a very small value) with non-empty call_ids produces PhaseTimeout without panic (per-call deadline check fires immediately); a phase with empty call_ids/account_ids still completes Ok under zero timeout; a second execute_sequence after a PhaseTimeout returns Ok(()) (idempotency preserved).

## Invariants

- 【Normal establishment】ShutdownSpec.timeout is consumed by every execute_sequence call: each phase runs under the configured per-phase budget (tokio::time::timeout), and a phase that completes within budget returns Ok and records no PhaseTimeout.
- 【Invariant on error】ShutdownError::PhaseTimeout never aborts the remaining phases: execute_sequence continues the loop, records the first error (C044 continue-on-error), and returns it only after all phases have run.
- 【Internal state invariant】The timeout path never re-enters execute_sequence: the is_started AtomicBool guard (mark_shutdown_started) is consulted before any phase work, so a second execute_sequence returns Ok(()) immediately. No dead code remains — the timeout field is always read and #[allow(dead_code)] is removed.
- 【Boundary invariant】A zero or very small timeout does not panic: phase_deadline = now + timeout makes the first per-call deadline check immediately true for a phase with work, producing PhaseTimeout; a phase with no work (empty call_ids/account_ids) still completes Ok.

### Exceptions

- Exact wall-clock durations for a phase that blocks cannot be asserted as fixed literal values in unit tests (not testable as deterministic literals) because the outcome depends on scheduler timing. This is not a design defect — the shutdown phase behavior is deterministic and fully testable via the tokio mock clock; the exempted item is only the literal wall-clock number. Alternative verification: assert the ShutdownError::PhaseTimeout variant, its phase, and its timeout value, plus continuation behavior, driven by tokio::time::pause()/advance() instead of asserting elapsed seconds.

## Notes in Prior Implementation Rounds

- [Implementation steps] (1) Remove #[allow(dead_code)] and the P12-9 STUB marker on timeout (lines 144-146); (2) add ShutdownSpec::ensure_within_phase_deadline helper; (3) in execute_sequence, wrap each execute_phase call in tokio::time::timeout(self.timeout, ...), mapping Elapsed → PhaseTimeout; (4) in execute_phase, compute phase_deadline and add per-call deadline checks + tokio::task::yield_now().await in CancelCalls/UnregisterAccounts; (5) add Clone/PartialEq/Eq derives to ShutdownError; (6) write the deterministic #[tokio::test] cases (pause/advance/spawn) — RED first, confirm they fail before implementation; (7) cargo fmt + make test.
- [Risks] tokio::time::timeout drops the phase future on expiry — the future borrows backend and slices; dropping mid-yield is safe because no resources are owned across the await. Timing tests can be flaky without tokio::time::pause(); all timeout tests must use the mock clock.
- [Caveats] The per-call deadline cannot preempt an already-blocking synchronous FFI call (e.g., a PJSUA hangup that blocks on a mutex); it bounds the phase at the per-call boundary. Preempting a truly-blocking sync FFI requires moving the backend off the async executor — documented as future work.
- [Open items] Wiring TimeoutConfig.shutdown_timeout (client_config_spec.rs:111, default 15s) into ShutdownSpec::new is not done here; the reactor Shutdown handler (reactor.rs:458) still calls backend.shutdown() directly and does not invoke execute_sequence.
- [Future improvements] Consider a shared timeout constant for ShutdownSpec::new; consider moving sync backend work to spawn_blocking to preempt truly-blocking FFI; derive Eq on ShutdownError is possible since ReactorError is Eq.
