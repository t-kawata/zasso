# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Production SIP traffic is driven exclusively by the real PJSUA backend (`PjsuaBackend`) selected through the `pjsua-native` feature; the `MockBackend` production implementation is deleted; deterministic Layer-2 reactor tests are driven by a `cfg(test)`-only `TestBackend`; a build with neither the feature nor test mode fails fast with an explicit error instead of silently running on a mock.

### Purpose
RESIDUE root cause R2 ("backend is Mock-fixed") — evidence `src/runtime/reactor.rs:92-93` unconditional `Box::new(MockBackend::new())` — means the production runtime currently operates on a canned test double with no real SIP signaling. §62.2 makes backend selection explicit and feature-driven so a production build can never silently degrade to mock behavior.

### Motivation
The Mock-fixed backend violates §3.1 (production must use real PJSUA) and blocks §43 Layer 3/4 integration and interop testing. The current `MockBackend` is production code carrying heavy test-injection fields (`get_account_info_result`, `conf_connect_calls`, `hold_calls`, ...) — test infrastructure living in the production path. RFC §62.2 mandates the change now, in the v0.x breaking-change window, as step 2 of the 8-step `BREAKING_CHANGE_ORDER`. The `impl_integration_design.rs` `evidence_matches_actual_source` test still asserts `reactor_src.contains("MockBackend::new()")` — a stale expectation that must be flipped when R2 is resolved.

### Constraints
- `SipBackend` trait (§27a) must be preserved with all 17 existing method signatures — no public API change.
- No new `mock-backend` feature; `pjsua-native` is the only production-selection feature (already declared in Cargo.toml, P10-2/P11-5).
- The error type is `ReactorError` (variants `ReactorDown`, `NotInitialized`, `BackendError`) — not `SipError`; §62.2's `SipError::unsupported` sketch is translated to `ReactorError::BackendError` through the shared `unsupported_backend_error()` helper.

## Invariants

- 【Normal establishment】Every compiled build selects exactly one SipBackend through `create_backend`: PjsuaBackend when `pjsua-native` is enabled, TestBackend when compiled as a test without the feature, and a hard error otherwise. `create_backend` is the only entry point that constructs a backend inside `CoreReactor::spawn` — no other production site may instantiate a backend directly.
- 【Invariant on error】When `create_backend` returns `Err(ReactorError::BackendError(...))` (non-feature non-test build), the reactor must not spawn a half-initialized thread: `SipClient::new`/`CoreReactor::spawn` propagate the error and leave no backend handle behind. The unsupported error is produced only by the `all(not(feature), not(test))` branch via the shared `unsupported_backend_error()` helper — TestBackend and PjsuaBackend never emit it.
- 【Internal state invariant】`TestBackend` keeps `accounts` and `registrations` in lockstep: every id in `registrations` has a matching `AccountEntry` in `accounts`, and `AccountEntry.registration` (String) stays consistent with the `RegistrationState` in `registrations`. `add_account` assigns monotonically increasing native ids starting at 1. Injection fields (`get_account_info_result`, `make_call_result`, `conf_connect_calls`, `conf_disconnect_calls`, `hold_calls`, `unhold_calls`) never mutate the accounts registry by themselves.
- 【Boundary invariant】A non-feature, non-test build must compile and reject backend creation with the exact message "SipClient requires the `pjsua-native` feature", sourced from the single `unsupported_backend_error()` helper. The `mock-backend` feature must never be added to Cargo.toml (absence enforced by a grep-based test).

### Exceptions

- [Item] 実 PJSIP シグナリング（SIP REGISTER 送信・200 OK 受信・メディア確立）の自動テストは cannot test — PJSUA 実機呼び出しは `pjsua-native` feature 有効かつ libpjsua 導入済みビルドでのみ実行可能であり、デフォルトの `cargo test`（feature なし）環境では FFI 呼び出しが stub alias（RFC §28, C058）に置き換わるため実シグナリングが発生しない（外部依存による非テスト可能性）。これは not a design defect — 選択機構そのもの（create_backend の cfg 分岐）は pjsua-native 有効ビルドで単体テスト可能であり、PjsuaBackend 内部の pj_status 変換（map_pjsua_status, C111）も unit テスト済み。実シグナリングは §43 Layer 3/4 のスコープ。代替検証: PJSUA 導入環境で `make test`（pjsua-native 有効）を実行し、create_backend の PjsuaBackend 分岐と各 FFI メソッドが Ok を返すことを確認。
- [Item] 非 feature 非 test ビルド（`all(not(feature), not(test))` 分岐）の実行経路は not testable — cfg(test) が有効な単体テスト実行環境ではこの分岐がコンパイル時に除外されるため、同一ビルド内からこの実行経路を叩くことができない。これは not an architectural defect — Rust の cfg 機構に起因する必然であり、エラー構築を `unsupported_backend_error()` に抽出して cfg(test) 下で unit テスト可能にし、分岐の存在自体はソーススキャンテストで担保する（「決定的だがテスト不能 → テスト可能へ再設計」の要請を満たす）。代替検証: ① unsupported_backend_error() の戻り値・文言を unit テスト。② `cargo build`（feature なし・非テスト本番ビルド）がコンパイル成功すること。③ そのビルドで SipClient::new が明示エラーを返すことを client_init example で確認。
- [Item] TestBackend が FFI（PJSUA）を一切呼ばないことの正の証明は not testable — 成功応答を返す正のテストでは「FFI を呼ばない」ことを直接証明できず、FFI 呼び出しはコンパイル時に cfg(feature) で排除されるため、負の検証（TestBackend 実装に ffi:: / bindings:: 参照が存在しないこと）はソーススキャンでのみ確認可能。これは not a design defect — コンパイル時排除による保証の性質であり、テスト可能性の欠如ではない。代替検証: ソーススキャンテストで TestBackend 実装部（cfg(test) 領域）に `bindings::` / `ffi::` 参照が存在しないこと、および reactor Layer 2 テストが feature なしで完走することを assert。
