# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P15-8: Shutdown wiring — ShutdownSpec.execute_sequence production wiring, ClientShutdown publish, command router gate

**Ticket Key**: P15-8 · **Phase**: 15

## Background

### Goal
Wire the reactor Shutdown arm to the §32 full shutdown procedure (ShutdownSpec.execute_sequence: BYE/CANCEL → unregister → audio drain → pjsua_destroy, PhaseTimeout included) and connect the M20 ShutdownCommandRouter as the command-loop gate, so production shutdown notifies subscribers (ClientShutdown), sets the is_terminated gate, and rejects in-flight commands.

### Purpose
The reactor Shutdown arm currently only calls backend.shutdown() (pjsua_destroy) and never publishes ClientShutdown nor gates commands; this ticket makes the reactor honor §32's complete phased shutdown and M20 command routing in production, closing the gap between the already-implemented ShutdownSpec (P4-3) / ShutdownCommandRouter (P1-1) and the reactor.

### Motivation
RFC §62.7 (N0076) resolves the RESIDUE where ShutdownSpec.execute_sequence and ShutdownCommandRouter exist as standalone components but are not connected to the reactor loop; the production wiring makes the idempotent sequence, the termination gate, and the drop/reject behavior observable end-to-end (SipClient.shutdown → reactor → backend → EventBus → subscriber).

### Constraints
No public API changes (wiring functions are pub(crate)); ShutdownSpec / ShutdownCommandRouter / SipEventPayload::ClientShutdown are reused as-is; no pjsua-native calls at this layer (real pjsua_destroy is validated by Layer 3+); the reply-exactly-once invariant must hold for every gated command; existing reactor shutdown tests must remain green.

## Acceptance Criteria

- **Happy path:** SipClient::shutdown() runs the full §32 sequence (BYE/CANCEL → unregister → audio drain → pjsua_destroy) via ShutdownSpec.execute_sequence, publishes SipEventPayload::ClientShutdown on the client bus, sets is_terminated, and returns Ok(()); commands submitted afterward are rejected with an error (no hang).
- **Error case:** A phase failure or PhaseTimeout during the sequence is logged, does not abort the remaining phases, ClientShutdown is still published, is_terminated is set, and the Shutdown reply surfaces the error (mapped to ReactorError::BackendError).
- **Edge case:** A command queued while the reactor is shutting down is rejected via the M20 gate with an error reply (caller does not hang); an empty ClientState yields a destroy-only sequence; shutdown_timeout == 0 still reaches InvokeDestroy.

## Invariants

- 【Normal establishment】The reactor Shutdown arm runs the §32 sequence via ShutdownSpec.execute_sequence with native ids collected from the authoritative ClientState (accounts.native_id, calls.native_id); on completion it publishes SipEventPayload::ClientShutdown, sets is_terminated (before replying), and replies Ok.
- 【Invariant on error】A phase failure or PhaseTimeout is logged and surfaced in the Shutdown reply (mapped to ReactorError::BackendError) but does not abort the remaining §32 phases; ClientShutdown is still published and is_terminated is still set so the client never deadlocks.
- 【Internal state invariant】The reactor owns a single ShutdownSpec (per-reactor idempotency via mark_shutdown_started); is_shutting_down == shutdown_spec.is_shutdown_started(); every gated DispatchCommand has its reply resolved exactly once (or is a reply-less NativeEvent) so no caller hangs.
- 【Boundary invariant】An empty ClientState (no accounts/calls) yields a destroy-only sequence; shutdown_timeout == Duration::ZERO still reaches InvokeDestroy (PhaseTimeout on per-item phases does not abort); the drain loop exits when the channel is empty (try_recv Empty) or closed (Disconnected).
