# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- **[Happy path]** make_call が CONFIRMED に到達すると `conf_connect(source=sink=call_id)` が自動発行され、`RustMediaPort` が `out_queue` / `in_queue` を消費する。conf port キャプチャコールバックが購読 tap へ `AudioChunkPair` を供給し、`AudioTapHandle::recv` が実データを受信する。`write_stereo_wav` が AudioChunkPair 列を指定 bit / hz / channel の WAV へ書き出し、`WavFileSource` が読み戻せる。
- **[Error case]** conf_connect が PJSUA エラーを返すと `ReactorError` が伝播する。書き込み不可パスへの `write_stereo_wav` は `SipError` を返す。不正 WAV ヘッダ / ファイル不在の `WavFileSource` は `SipError` を返す。RT コールバック内ではエラーをパニックせずログ + 計測のみ（キュー満杯はドロップ、非購読 call は no-op）。
- **[Edge case]** 非購読 call のキャプチャフレームは no-op。out_queue 空の get_frame はゼロフィル（無音）。in_queue 満杯の put_frame は最新優先でドロップ（非ブロッキング）。空フレーム列の write_stereo_wav は 44 バイトヘッダ + data サイズ 0。F32 chunk は [−1.0, 1.0] クリップ後に i16 変換。WavFileSource はファイル末尾で next_chunk が 0 を返す。

## Invariants

### 正常成立条件
メディア経路は §21–§24 と矛盾しない: `AudioChunkPair::from_processed_frame` の L=IN / R=OUT マッピング（§22 / §62.6）、`MIXER_FRAME_SAMPLES`=160（§24）、`AudioBridge` の lock-free キュー（§39）が維持される。WavWriter のチャネルマッピングも同一の L=IN / R=OUT 規則に従う。

### エラー時不変条件
conf port キャプチャコールバックは非ブロッキング（Realtime `try_push`）で、非購読 call は no-op。RT コールバック上で lock 待ち / await / 動的確保 / システムコールを行わない（§24.0）。conf_connect 失敗は `ReactorError` として伝播し、WAV 書き出し失敗は `SipError` として返る — エラーを握りつぶさない。

### 内部状態不変条件
`RustMediaPort` が `out_queue` / `in_queue` の唯一の消費点であり、`AudioWorkerInner::process_frame` は push のみ行う。`conf_connect` が call ごとのメディア接続を確立する。tap レジストリの購読状態と conf コールバック配線は整合し、購読解除後は tap へ供給しない。

### 境界値不変条件
アンダーラン時（out_queue 空）はゼロフィル（無音）、キュー満杯時（in_queue 満杯）は最新優先でドロップ（非ブロッキング、パニックしない）。WAV 出力は 44 バイトヘッダ + サンプル数 × チャネル数(2) × 2 バイト（PCM16）で、空フレーム列は data サイズ 0 を出力する。

- **Postcondition**: 62.16 が conf port コールバック配線を規定する — pjsua_conf_set_callback によるキャプチャフレーム取得 → AudioTapRegistry 参照 → AudioTapSender::try_push で購読 tap を駆動。bindgen allowlist に pjsua_conf_set_callback が追加され、pjsua-native feature で FFI シンボルが生成される。
- **Invariant**: push_media_frame は tap を駆動する — 非購読 call は no-op（Ok(()) を返しパニック・ブロックしない）、Realtime モードの try_push で常に非ブロッキング。RT コールバック上で lock 待ち / await / 動的確保 / システムコールを発生させない（§24.0）。

### C110 — N0085→N0033

- **Precondition**: N0033（§24 AudioMixer RT 境界）が RT コールバック上の禁止操作（lock 取得 / async 待機 / 動的確保 / システムコール）を定義している。AudioMixer の out_queue / in_queue（crossbeam_queue::ArrayQueue<Vec<i16>>）が P15-7 で実装済みだが、消費点は存在しない。AudioWorkerInner::process_frame は push のみ行う。
- **Postcondition**: 62.16 が out_queue / in_queue の消費と conf_connect を規定する — RustMediaPort::get_frame が out_queue を pop（アンダーラン時ゼロフィル）してネットワーク送信 / ローカル再生へ接続し、RustMediaPort::put_frame が受信フレームを in_queue へ push（満杯時ドロップ）。make_call / answer の call connect（CallConnected 発行）時に conf_connect(source=sink=native_call_id) が自動発行される。
- **Invariant**: RustMediaPort が out_queue / in_queue の唯一の消費点である — キューは RT コールバック（get_frame / put_frame）からのみ pop され、AudioWorkerInner::process_frame は push のみ行う。conf_connect が call ごとのメディア接続を確立する。

## Boy Scout Rule

- **WavWriter / WavFileSource / RustMediaPort を翻訳可能に実装する**: 関数名は動詞句（`write_stereo_wav`、`write_stereo_pair`、`finalize`、`next_chunk`、`pop_out_frame`、`push_in_frame`）、変数名はドメイン概念（`in_samples` / `out_samples`、`riff_size`、`data_size`、`block_align`）、1 関数 1 責務（ヘッダ生成・データ書き込み・finalize を分離）、マジックナンバー（44 バイトヘッダ / RIFF チャンクオフセット / PCM=1 / チャネル=2 / bits=16）を命名定数（`WAV_HEADER_LEN`、`PCM_FORMAT_TAG`、`BYTES_PER_I16` 等）として抽出。
- **既存コードの翻訳可能性を改善する（スコープ内外）**:
  - `src/runtime/backend.rs` の `push_media_frame` は既に翻訳可能だが、conf コールバック追加時に `conf_capture_cb` を「フレーム取得 → レジストリ参照 → tap 供給」の小さな関数群へ分割する（1 コールバック内で全てやらない）。
  - `src/runtime/audio_worker.rs` の `process_frame` は push のみで消費しない旨がコメントで明記されている — RustMediaPort 追加時に「キュー唯一の消費点」をコード構造（`RustMediaPort` 型）で表現し、コメントでなく型で保証する。
  - `src/model/media_bridge.rs` の `AudioBridge` は `to_rt` / `from_rt` の lock-free 境界を提供する — RustMediaPort 実装で既存 `AudioBridge` を再利用する場合はメソッド名（`push_out_frame` / `pop_in_frame` 等）をそのまま活かし、未使用の冗長なパスを作らない。
  - `src/api/audio_subscribe_bp.rs` の `tap_channel` / `validate_tap_capacity` は命名済み定数（`MIN_TAP_CAPACITY`）を利用しており、既存の良いパターンを WAV 定数でも踏襲する。
- **エラー握りつぶしを排除する**: `WavWriter` の各書き込みは `Result` を返し、Io エラーを `SipError` へ変換して伝播する（`?` 演算子）。`WavFileSource` の読み込みも不正ヘッダを `SipError` で返す。RT コールバック内の `try_push` / キュー操作は戻り値（`Option` / `bool`）を `debug_assert!` + `tracing::trace!` で監視し、無視したドロップを計測に載せる。

- **Exception entry 1**
  - **Item**: 実 pjmedia_port / pjsua_conf_set_callback による実メディア転送（RTP 送受信）の E2E 検証

  - **Reason**: RT スレッドのスケジューリング特性は OS 環境に依存する非決定的要因であり、CI 上で決定的にテスト不能（cannot test / not testable）。ただしこれは not a design defect であり、設計欠陥ではない — lock-free キュー + 事前確保 + 非ブロッキングという設計不変条件（§24.0）をコードで保証する。設計不変条件自体は決定的に検証可能。
