# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P17-9: Subscription unsubscribe API & mic source documentation (§62.29)

**Ticket Key**: P17-9 · **Phase**: 17

**RFC Source**: `RFC-ROOT.md`

---

## Background

- 【Goal】Provide an explicit, user-friendly subscription-cancel API (`Subscription<T>::unsubscribe()`) that wraps the subscribe APIs, and document in README / RFC that `open_default_microphone_source` is an independent capture source — NOT the call microphone.
- 【Purpose】Today cancellation is drop-only (RFC §8.3): a caller who subscribes via `subscribe()` / `subscribe_account()` / `subscribe_raw_sip()` gets a raw `broadcast::Receiver` with no named unsubscribe, and the microphone source's role is undocumented, inviting misuse as the call's send-path input. P17-9 removes both frictions.
- 【Motivation】H8/Q8/Q8a from RFC §62.29: user feedback and the public-API expansion (§62.5, N0074) require an explicit subscription handle; the audio-source documentation decision (N0098) resolves the README RESIDUE item 3 left by P16-7.
- 【Constraints】Backward-compatible event semantics — the broadcast drop-based contract (§8.3) must still hold; `AccountEventReceiver` account filtering must be preserved inside `Subscription` (C134); the three subscribe methods' return types change but `SipClient::new`'s receiver return stays `broadcast::Receiver<SipEvent>`; no new external dependencies (`async-trait` already in Cargo.toml); all changes testable without a live SIP server (TestBackend).

## Scope

- src/api/eventbus_receiver.rs — add — `Subscription<T>` handle type + private `SubscriptionSource<T>` trait (async recv / try_recv) + `unsubscribe()` / `is_subscribed()` / `recv()` / `try_recv()` / `Debug`; keep `EventBus` and `AccountEventReceiver` behavior unchanged.
- src/api/eventbus_receiver.rs — modify — replace `AccountEventReceiver`'s Debug hardcoded `"broadcast::Receiver<SipEvent>"` string with a state-accurate description (e.g. `filter` + whether the receiver is live) so the Debug output cannot lie.
- src/client.rs — modify — change the three subscribe method signatures to return `Subscription<T>` and delegate construction to `Subscription::new(Box::new(...))`; update doc comments (lines 184-213) to describe the explicit unsubscribe.
- Before → After: `subscribe() -> broadcast::Receiver<SipEvent>` → `Subscription<SipEvent>`; `subscribe_account(AccountId) -> AccountEventReceiver` → `Subscription<SipEvent>`; `subscribe_raw_sip() -> Option<broadcast::Receiver<RawSipMessage>>` → `Option<Subscription<RawSipMessage>>`.
- API contract: the three methods gain `unsubscribe()` (idempotent, `&mut self`), `recv()` / `try_recv()` (delegation; `Closed` after unsubscribe); account filtering and raw-sip None-when-disabled semantics unchanged; `SipClient::new`'s second return value stays `broadcast::Receiver<SipEvent>`.
- No data schema change — `SipEvent`, `RawSipMessage`, `EventMeta`, `AccountId` are untouched.
- No config/env change.
- No new dependency — `async-trait = "0.1"` already present (Cargo.toml:59).

Why: not requested by N0098; converting it would ripple through `SipClient::new` callers and tests; a follow-up consistency ticket can address it.
- Out of scope — the public `AccountEventReceiver` type and its C020 tests stay; it becomes the account-filter source inside `Subscription`. Why: it is the tested filter primitive and is publicly re-exported; removing it would be a breaking change.
- Impact — `tests/verify_spec_p9_1.rs`, `examples/make_call.rs`, `examples/account_register.rs`, and `src/client.rs` subscribe tests consume the new `Subscription` type.
- Impact nature — public API surface change (subscribe methods' return types); all downstream callers must recompile; no runtime/performance impact beyond one `Box` allocation per subscription.
- Response — YES: update the example helper signatures (`await_call_events` / `await_registration`) to `&mut siprs::Subscription<SipEvent>`; the integration test and client tests compile unchanged because they only call `recv()`.

## Acceptance Criteria

- Happy path: `client.subscribe_account(account_id)` returns `Subscription<SipEvent>`; `account_events.recv().await` delivers the account-matching event after `account.register()` (TestBackend); `account_events.unsubscribe()` drops the subscription and a subsequent `recv()` returns `RecvError::Closed`; the README documents both `unsubscribe()` and that `open_default_microphone_source` is not the call microphone.
- Error case: after `unsubscribe()`, `recv()` / `try_recv()` return `Closed` / `TryRecvError::Closed` (never a panic, never a stale event); broadcast overflow still surfaces as `RecvError::Lagged(n)`; `subscribe_raw_sip()` returns `None` when the raw bus is disabled.
- Edge case: the account filter skips non-matching events (a `try_recv()` with only non-matching events returns `Empty`); `unsubscribe()` is idempotent (double call is a no-op); capacity-1 bus still delivers a single buffered event without overflow; `Subscription<T>` Debug prints a truthful state.

## Invariants

- 【Normal establishment】`SipClient::subscribe` / `subscribe_account` / `subscribe_raw_sip` always return a `Subscription<T>`; `subscribe_account`'s Subscription filters to the configured `account_id` (non-matching `SipEvent`s are silently skipped); `subscribe_raw_sip` returns `None` exactly when the raw SIP bus is disabled.
- 【Invariant on error】After `unsubscribe()`, the underlying receiver is dropped; `recv()` returns `RecvError::Closed` and `try_recv()` returns `TryRecvError::Closed` — never a panic, never a stale event. `unsubscribe()` is idempotent (repeated calls are no-ops). Broadcast overflow propagates as `RecvError::Lagged(n)` exactly like `AccountEventReceiver` (error transparency preserved).
- 【Internal state invariant】`Subscription<T>::inner` is `Some(_)` iff the subscription is live, `None` iff unsubscribed; `is_subscribed()` reflects exactly that state; the boxed `SubscriptionSource<T>` is always one of {plain `broadcast::Receiver<T>`, `AccountEventReceiver`} and the account-filter variant is only ever constructed for `T = SipEvent`.
- 【Boundary invariant】Capacity-1 bus behavior is preserved (a single buffered event is received; further publishes drop oldest without blocking); the account filter must never deliver an event whose `meta.account_id` differs from the subscribed account and must never drop a matching event; `open_default_microphone_source` (cpal, `#[cfg(feature = "cpal-input")]`) remains an injectable capture source distinct from the call microphone.
