# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

N0011 defines the complete public API surface (crate root re-exports, SipClient, SipAccountHandle, OutgoingCallRequest). N0014 and N0015 define AccountConfig, TransportConfig with ICE/STUN/TURN specs. N0051 defines config validation rules (fail-fast). These form the user-facing configuration and API layer.

### Goal
Establish the complete, stable public API surface (SipClient, SipAccountHandle, AccountConfig, TransportConfig) for the siprs crate. All user-facing interactions with the SIP stack go through these types. Every public item is re-exported at crate root so application code writes siprs::SipClient not siprs::client::SipClient.

### Purpose
The public API is the contract between siprs and its consumers. Without a defined API surface, all internal refactoring breaks downstream code silently. By fixing the types, method signatures, validation rules, and re-exports in this ticket, we establish a stable foundation that downstream tickets (P3-2 FFI, P4-1 IDs, P5-1 Call lifecycle) can build on.

### Motivation
Existing code uses raw u64/String placeholders in RuntimeCommand and stub structs (account.rs, call.rs, transport.rs all have stub pattern). Before FFI bindings (P3-2) can be integrated, the typed API layer must exist so the FFI layer calls typed methods rather than manipulating raw pjsua handles. Additionally, the current src/config.rs ClientConfig is a simplified proxy-only config — the full N0013/N0014/N0015 configs must replace it.

### Constraints
(1) No PJSUA FFI dependency — all validation and API surface must work with MockBackend at Layer 2. (2) TLS variants are feature-gated behind #[cfg(feature = "tls")] — the public API must not expose TLS types when the feature is off. (3) SecretString via zeroize feature for password fields — memory zeroization is optional but the SecretString wrapper is mandatory. (4) Existing test in client.rs references old ClientConfig builder API with sip_proxy_host/sip_proxy_port — P3-1 must either update or deprecate these tests.

## Acceptance Criteria

- All public APIs are async fn returning Result<T, SipError>
- AccountConfig validation rejects all invalid configurations
- TransportConfig TLS variant only exists with tls feature
- SipClient is Clone, Send, and Sync
- Happy path: User creates SipClient::new(ClientConfig with event_bus_capacity=2048, transports=[Udp, Tcp], ice=default), subscribes to events via subscribe(), adds AccountConfig(alice@sip.example.com) via add_account(), gets back SipAccountHandle with correct account_id, calls register() which succeeds. subscribe_raw_sip() returns Some(Receiver). accounts() returns vec of 1 handle.
- Error case: User creates AccountConfig with empty username — validate() returns Err(SipErrorKind::InvalidConfig("username must not be empty")). User creates AccountCodecPolicy with both enable_pcmu=false and enable_opus=false — validate() returns Err. User creates DtmfPolicy with empty send_methods — validate() returns Err. SipClient::add_account(invalid_config) returns Err before reaching reactor.
- Edge case: AccountConfig with register_on_start=false and allow_outbound_without_register=true — validates successfully (valid combination). TransportConfig TLS variant compilation checked via cargo test --no-default-features — TLS types not available in API. AccountConfig with all Optional fields set to None works (display_name=None, auth_username=None, registrar_uri=None, outbound_proxy=[], contact_params=[]).

## Invariants

- 【Normal establishment】All public API functions return Result<T, SipError>. SipClient is Clone, Send, Sync. AccountConfig validation enforces: username && domain && password are non-empty, at least one codec (enable_pcmu or enable_opus) is true, send_methods and receive_methods each have >= 1 entry. TransportConfig TLS variant is gated by #[cfg(feature = "tls")] — never present at runtime without the feature. Codec policy only accepts PCMU and Opus (C041).
- 【Error invariant】All validation failures return Err(SipErrorKind::InvalidConfig) — never panic, never return Ok. Error messages are non-empty and describe the specific violated rule. Validation happens before any RuntimeCommand submission — no state mutation on validation failure.
- 【Internal state invariant】SipClient.inner is Arc<ClientInner> — clone shares the same underlying RuntimeHandle and EventBus. RuntimeCommand::AddAccount, MakeCall, SetRegistration use typed config/request/account_id payloads (not String/u64 stubs). ClientInner.runtime is RuntimeHandle (Send+Sync), never leaked outside crate.
- 【Boundary invariant】event_bus_capacity must be >= 16, raw_sip_event_capacity >= event_bus_capacity when raw_sip_events enabled. registration_expires must be > Duration::ZERO. OpusConfig.bitrate range [500, 512000], complexity [0, 10], ptime_ms in {10, 20, 40, 60}. sample_rate only Hz8000/16000/24000/48000.

## Boy Scout Rule

Translatability improvements for P3-1 scope:

1. **src/config/account_config_spec.rs**: Extract AccountConfig constructor as `AccountConfig::build()` builder pattern instead of direct field manipulation. Method names as verbs: `validate()`, `with_username()`, `with_domain()`. Extract OpusConfig magic numbers (bitrate range, ptime options) into named constants. Map validation rules to sentences: "username must not be empty", "at least one codec must be enabled".

2. **src/config/transport_ice_spec.rs**: Rename ICE config booleans as is/has prefixes: `is_enabled`, `has_aggressive_nomination`, `supports_trickle_ice`. Extract TlsConfig path fields as `PathBuf` rather than raw String. Make TransportConfig pattern match read as prose: `match transport { Udp { .. } => "use UDP", Tcp { .. } => "use TCP" }`.

3. **src/api/public_api_design.rs**: SipAccountHandle method names as verb phrases: `register().await`, `unregister().await`, `make_call(request).await`. OutgoingCallRequest fields as noun phrases: `target_uri`, `auth_override`, `preferred_transport`. Replace the existing `pub trait Service {}` placeholder with meaningful struct/impl.

4. **src/runtime/command.rs**: Replace String stubs with typed struct fields so that RuntimeCommand::AddAccount reads as "add account with AccountConfig" rather than "add account with opaque string". The from_runtime_command conversion currently uses Box::new closures — extract into named helper functions like `handle_add_account(backend, config)`.

5. **src/client.rs**: The existing SipClient::new() method uses a long chain of operations (validate, spawn, create, send). Extract into helper methods: `validate_config()`, `spawn_reactor()`, `initialize_reactor()` so new() reads as "validate, spawn, create event bus, initialize".

6. **src/account.rs, src/call.rs, src/transport.rs**: Replace stub structs (`pub id: u64`, `pub config: String`) with properly named fields and accessor methods. Use domain types: `AccountId` not `u64`, `OutgoingCallRequest` not `String`.

Existing code that violates translatability outside strict scope but touched during P3-1: RuntimeCommand Debug/Display manual impls (17+ variants duplicated code in Debug, Display, and from_runtime_command) — these can be extracted to a shared name function to reduce repetition.

### Exceptions

- Exception: Feature-gated TLS variant compile-time presence — TransportConfig::Tls variant exists only when #[cfg(feature = "tls")] is active. This is a compile-time gate, not a runtime behavior, and is deterministic — the Rust compiler performs conditional compilation based on feature flags. However, a single test binary cannot test both presence and absence of a feature-gated variant because compilation is a one-shot process. This is NOT a design defect: the conditional compilation pattern is idiomatic Rust for optional features, and the variant's absence when the feature is disabled is guaranteed by the compiler, not a testing gap. Alternative verification: (1) CI matrix runs `cargo test --features tls` and `cargo test --no-default-features` separately, confirming compilation succeeds in both cases. (2) A `#[cfg(not(feature = "tls"))]` compile-fail test in a separate file or crate confirms TLS types are absent when feature is off. (3) Manual review of Cargo.toml #[cfg] attributes and feature definitions.
