# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Define and implement the foundational FFI layer for PJSUA integration, the AudioMixer with lock-free real-time boundary, and the typed runtime internal state (ClientState, AccountEntry, CallEntry). These three subsystems enable SipClient to drive real PJSIP calls with safe abstractions.
### Purpose
- FFI Layer (N0037): Isolate all unsafe PJSUA FFI calls behind a safe SipBackend trait, enabling testability via MockBackend and eventual backend switching.
- AudioMixer (N0033): Provide a safe, async-native audio mixing pipeline that respects PJSIP real-time thread constraints by using lock-free queues at the RT boundary.
- Runtime State (N0045): Define the type-safe source-of-truth state model that the reactor thread owns and query APIs snapshot via async RwLock, preventing deadlocks.
### Motivation
P0-6 established the AudioWorkerTask skeleton (AudioMixer, AsyncAudioSource, mock). P3-2 hardens this into production form: mix_i16_frame with overflow safety, MixerSourceEntry with gain/mute/EOF, and full crossbeam queue separation. The FFI layer is the gateway to real PJSUA interaction — without it all existing infrastructure remains mock-only. Typed ClientState is the prerequisite for state machine transitions (P6+).
### Constraints
- Bindgen must use allowlist patterns only (pjsua_*, pj_*, PJSUA_*, PJ_*) — no blanket generation.
- extern C callbacks must NEVER lock, allocate, or await — mechanical enqueue only.
- ClientState must use BTreeMap for deterministic iteration order, not HashMap.
- conf_port_id MUST NOT appear in CallEntry — PjsuaBackend exclusively owns resolution.
- Implementation order: ffi module -> SipBackend trait -> AudioMixer refinements -> ClientState types -> PjsuaBackend stub.

## Invariants

- 【Normal establishment】AudioMixer lock-free queues (out_queue/in_queue) are initialized with positive capacity on creation. PjOwnedStr ptr/slen always reflects owned Vec<u8> content. ClientState is default-false initialized; accounts/calls/transports start empty.
- 【Invariant on error】ClientState remains internally consistent after any SipBackend error — partial account additions roll back fully. AudioMixer source iteration continues after a source returns next_chunk=0 (EOF). FFI callback errors enqueue NativeEvent with error payload, never panic.
- 【Internal state invariant】ClientState holds the single source of truth for accounts/calls/transports — never duplicated externally. AccountEntry.native_id maps 1:1 to pjsua_acc_id. CallEntry does NOT contain conf_port_id. AudioMixer.source_count never negative. conf_port_id resolved fresh on each call via PjsuaBackend::resolve_conf_port.
- 【Boundary invariant】mix_i16_frame output sample values always clamped to [i16::MIN, i16::MAX] via saturating i32->i16 conversion, never overflow. crossbeam::ArrayQueue capacity is the hard upper bound on queued frames — producer never blocks (drops on full). ffi/ module contains ALL unsafe code — zero unsafe in runtime/ or client.rs.

### C034 — N0033→N0009

- **Precondition**: Tokio async runtime must be initialized (tokio::runtime::Handle::current() succeeds). AudioWorkerTask must be spawned on Tokio blocking pool via tokio::task::spawn_blocking.
- **Postcondition**: AudioMixer struct created with lock-free queue boundary: crossbeam::ArrayQueue<Vec<i16>> out_queue separates AudioWorkerTask (async context) from RustMediaPort (PJSIP RT callback context). AudioWorkerTask runs process_frame loop in blocking pool.
- **Invariant**: No blocking operations (lock acquisition, dynamic memory allocation, syscall, .await) are permitted inside any function called from PJSIP RT callback thread (get_frame/put_frame). Only lock-free queue pop/push, memcpy, and zero-fill are allowed.

Sources added/removed via AudioMixer are reflected at next frame boundary.
- **Invariant**: Sources are added and removed at frame boundaries. Source iteration uses snapshot of source_ids to avoid DashMap invalidation during iteration.

- **Invariant**: Zero-padding is applied when pair delta exceeds tolerance. Long-duration drift tracked as alignment_drift metric until threshold crossed.
