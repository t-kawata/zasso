# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

- [Goal] Fully define the type system foundation for the siprs crate: newtype ID identifiers (AccountId, CallId, AudioSourceId) as NonZeroU64 with BiMap runtime-to-native mapping; complete SipEventPayload enum with 25+ variants spanning all event categories; RegistrationState machine with 7 states and 8 transition rules; CallState machine with 13 states and all transition paths.
- [Purpose] These types form the shared language across all siprs modules (API, event system, state machines, FFI bridge, audio processing). Without them, module boundaries use raw integers (u64, pjsua_acc_id, pjsua_call_id) leading to type confusion, parameter swap bugs, and opaque error messages. The BiMap specifically solves PJSUA id reuse — native IDs are recycled by PJSUA after session teardown, and public API consumers must never see recycled IDs.
- [Motivation] P0-5 (Event System) delivered SipEventPayload, EventBus, and basic CallState as a Minimum Viable Event System. However, P0-5 used placeholder AccountId(pub u64)/CallId(pub u64) with NonZeroU64 requirements stubbed out, only 6 CallState variants (vs 13 required by N0026), and no RegistrationState. These gaps must be resolved before downstream tickets (P3-1 Public API, P5-1 Call API) can depend on correct types.
- [Constraints] (1) model/ module is currently gated behind #[cfg(feature = "sqlite-storage")] — id_design_newtype.rs must be made unconditionally compilable. (2) BiMap must use existing dependencies (dashmap) — no new crate additions without justification. (3) SipEventPayload must remain #[non_exhaustive] — existing downstream consumers (P0-5 tests, EventBus, AccountEventReceiver) must continue to compile. (4) RegistrationState and CallState must be Copy+Clone — they are used in hot paths (per-event, per-call). (5) RFC 12 states for CallState are actually 13: Disconnected and Failed are separate terminal states.

## Acceptance Criteria

- [Happy path] A test creates AccountId(1), CallId(1), AudioSourceId(1) — all types are distinct, non-interchangeable, and typed as NonZeroU64. BiMap stores a (runtime_id→native_id) pair and returns correct lookups. RegistrationState follows all 8 transition rules without error. CallState follows the full outgoing path (New→Calling→Trying→Ringing→Connecting→Active) and termination path (Active→Disconnecting→Disconnected). SipEventPayload enum includes all 25+ variants including new categories (ICE, Transport, Account, Client, Error).
- [Error case] AccountId::from_u64(0) returns Err(ZeroValue). CallState::transition(New→Active) returns Err(TransitionError). RegistrationState::transition(Idle→Disabled) returns Err(TransitionError). BiMap::get_native(unknown_id) returns None. SipEventPayload variant enum compiled with _ => {} wildcard (non_exhaustive check).
- [Edge case] BiMap handles native ID reuse: insert(a1, n1), remove(a1), insert(a2, n1) — get_runtime(n1) returns a2. RegistrationState transition Expired→Registering (auto retry) followed by Failed (no network) then Registering again (retry). CallState transfer path Active→Transferring→Disconnecting (NOTIFY fail) verifies transfer failure branch. CallState Failed reached from Ringing (4xx), EarlyMedia (5xx), and Connecting (6xx) via 3 distinct paths.

## Invariants

- [Normal condition] Newtype ID construction: AccountId::from_u64(x) succeeds iff x > 0, returns ZeroValue error iff x == 0. BiMap insert/lookup round-trip: insert(r, n) guarantees get_native(r) == Some(n) and get_runtime(n) == Some(r) until remove(r) is called. RegistrationState transitions: every transition follows exactly one of the 8 defined rules; no implicit transitions exist. CallState transitions: every transition follows the DAG defined in §18.1; all non-terminal states can reach Disconnected or Failed.
- [Error invariant] Zero-value ID construction (from_u64(0)) never succeeds — returns Err(SipErrorKind::ZeroValue). BiMap never loses data on concurrent access — dashmap interior mutability guarantees crash-consistency. Invalid state machine transitions never mutate internal state — Err is returned, state unchanged. RegistrationState::Failed and Expired do not prevent make_call() — this invariant is enforced by the absence of registration checks in the Call API.
- [Internal state invariant] BiMap internal state: for all (r, n) pairs, r is unique (RuntimeId is the primary key). NativeId n may be reused; the newest (r, n) pair wins on insert. RegistrationState machine: internal transition table enumerates exactly (7 states × 7 targets) = 49 boolean predicates, of which exactly 10 are true (the 8 rules plus 2 reflexive). CallState machine: transition table enumerates exactly (13 states × 13 targets) = 169 boolean predicates, covering all outgoing/incoming/hold/transfer paths.
- [Boundary invariant] AccountId/CallId/AudioSourceId NonZeroU64 domain: [1, u64::MAX]. BiMap capacity: unbounded (backed by dashmap). EventBus capacity impact: AccountId/CallId size is 8 bytes each, negligible on bus capacity. RegistrationState transitions: Failed→Registering retry must not cause infinite loop — controlled by ClientConfig::registration_retry_count (P3-1 scope). CallState: max_calls concurrent limit enforced by Call API (P3-1 scope), not by state machine itself.
