# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

N0061 defines the siprs-server main.rs entry point: SipClient initialization from config, DatabasePool initialization, saved account restoration from SQLite, and Axum server startup on configured bind address. Supports both standalone binary mode and Tauri-embedded library mode.

### Goal
Define the standalone server entry point (main.rs) and supporting types (ServerConfig, AppState, build_router) that initialize SipClient, DatabasePool, restore saved accounts from SQLite, and start an Axum HTTP/WS server on the configured bind address. The server provides at minimum a health check endpoint (GET /api/v1/health) and a shutdown endpoint (POST /api/v1/shutdown). Concretely: `ServerConfig::from_args()` (cli feature, clap) parses CLI args; `AppState { sip_client: Arc<SipClient>, db: Arc<DatabasePool>, server_start_time: Instant }` is the axum shared state; `build_router(state: AppState) -> axum::Router` registers the two endpoints behind the `server` feature; `run_server(config: ServerConfig) -> Result<(), SipError>` wires startup in RFC §53.1 order. The 5 ABC omissions (O-001 critical + O-002..O-005 minor) must be 100% resolved by new/updated tests in this round.

### Purpose
Enable external applications (external SIP clients, Tauri frontend, monitoring tools, CLI scripts) to control siprs via HTTP REST APIs and WebSocket event streams without linking to the siprs Rust library directly. The standalone server bridges the Rust SIP client implementation with any HTTP-capable consumer. The health endpoint gives monitoring/readiness probes a PJSIP-free liveness signal; the shutdown endpoint gives operators and the future Tauri sidecar a clean stop path. This ticket is the minimal verifiable server skeleton that unblocks P4-2 (auth middleware) and P4-3 (full REST/WS routes + crate split).

### Motivation
The RFC defines siprs as a crate with both library and server modes. Standalone server mode is required for the P2P network layer (server-side components), monitoring/observability tooling (health checks, metrics export), and future Tauri desktop integration where the server runs as an embedded sidecar. Without this entry point, all SIP operations would require direct Rust FFI, limiting integration options. This round is motivated by ABC Inspection: the prior P3-3 implementation shipped a compile-time-only router test (`test_build_router_returns_router_type` at src/api/standalone_server_config.rs:728) that never constructs AppState or executes the health handler, leaving the central observable behavior (health returns HTTP 200 before accounts are registered) unenforced. A behavioral axum::test must replace it.

### Constraints
1. Must support two entry modes: standalone binary (with clap CLI arg parsing, `cli` feature) and embedded library (programmatic ServerConfig, no CLI dependency — default features exclude `cli`).
2. Axum server must bind only after SipClient and DatabasePool are fully initialized and saved accounts restored — never expose an uninitialized state (RFC §53.1 startup order).
3. Health check must respond HTTP 200 before any accounts are added (readiness probe) — O-001 demands a behavioral axum::test proving this.
4. AuthConfig defaults to LocalhostOnly for security — server must not listen on external interfaces without explicit auth configuration (`AuthConfig::validate` rejects non-loopback in LocalhostOnly mode).
5. No external crate split in this ticket — server types live in the siprs crate, behind the `server`/`cli` feature gates. siprs-server crate split is tracked in P4-3.
6. All new tests must run under `make test` (Makefile exists) with the `server`/`cli`/`sqlite-storage` feature matrix; no PJSIP native init required (reactor uses MockBackend).
