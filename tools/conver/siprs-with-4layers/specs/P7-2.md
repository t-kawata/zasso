# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Goal
The P0-5 event system provides the complete bridge between PJSIP C callbacks and Rust async event consumers. It defines the SipEventPayload enum (all P0 variants: Registration/Call/DTMF; P1: Transport/ICE; P2: supplemental), the EventBus with split control/raw_sip broadcast channels, the NativeEvent-to-SipEventPayload conversion functions, and the Dual Client routing infrastructure. Every PJSIP callback-generated event is delivered to the correct SipClient's EventBus as a typed SipEvent struct.

## Purpose
SipClient consumers (UI layer, audio pipeline, logging) need observable, structured notifications about SIP state changes. Without this event system, application code would need to poll for state or interpret raw PJSIP callbacks directly. The EventBus provides a decoupled publish-subscribe pattern where:
- Reactor publishes SipEvents onto broadcast channels
- Multiple consumers independently subscribe and filter (via AccountEventReceiver)
- RawSIP messages are isolated on a separate bus to prevent control event loss

This is the primary async communication channel between the synchronous PJSIP thread (C callbacks) and the async Rust world (tokio tasks).

## Motivation
This is the foundational event infrastructure for the entire crate. All observable SIP behavior — registration status changes, call state transitions, DTMF events, media state changes — flows through this system. Every downstream feature (P2-2 error payloads, P2-4 audio pipeline, P4-1 registration state machine) depends on events being delivered. The current stub (src/client.rs uses mpsc::Receiver<()>) blocks all downstream development.

Without this ticket:
- No SipEventPayload type exists (all stubs)
- NativeEvent conversion is unimplemented
- SipClient returns dummy event receiver (cannot observe any SIP events)
- Dual Client mode (multiple SipClient instances) has no event routing

## Constraints
- Broadcast channel (lossy delivery): tokio::sync::broadcast is the only supported channel type. No reliable delivery, no per-subscriber retransmission. This is by design (N0020).
- PJSUA dependency: NativeEvent types mirror PJSIP callback signatures (pjsip_inv_state, pjsua_call_media_status). Any PJSIP version mismatch may require updating the mapping.
- Single Reactor constraint: global_runtime() must remain unchanged. Dual Client uses EventBus dispatch only — no second Reactor.
- All implementation targets are stub files (pub enum State {} / pub trait Service {}). This is net-new implementation, not refactoring of existing code.
- DtmfSent 500ms timeout: This is a fallback for when PJSIP does not fire a send-complete callback. The timeout may race with actual PJSIP callback delivery (firing both DtmfSent events) — consumer must handle duplicates.

## Invariants

- [Normal condition] EventBus::publish() must never block — broadcast::Sender::send() is non-blocking by design. SipEventPayload must be Clone + Debug. EventBus must be Clone (all clones share same Sender). NativeEvent conversion must be total over defined P0 variants.
- [Error invariant] On Lagged(n), the receiver skips n messages and resumes from current position — no crash or state corruption. AccountEventReceiver must not panic on Lagged(n). DtmfSent timeout must not abort ongoing operations.

- [Boundary invariant] EventBus default capacity 2048 must accommodate ~100 concurrent calls (~20 events/call). RawSIP channel capacity must be configured independently. DtmfSent timeout default 500ms must be less than typical PJSIP DTMF duration.
- [Normal condition] Reactor::dispatch_event() must route each event to exactly one destination: Some(account_id) matching a client_event_buses key → that bus only; Some(account_id) matching no key → default_event_bus; None (lifecycle) → default_event_bus + every registered client bus (C039). SipClient::accounts()/call_state() read the authoritative ClientState, not the event stream (C021).
- [Boundary invariant] Lagged(n) count equals the number of skipped messages (broadcast channel semantics) — asserted exactly, not matched with a wildcard (C020). EventBus default capacity 2048 must accommodate ~100 concurrent calls (~20 events/call); DtmfSent timeout default 500ms must be less than typical PJSIP DTMF duration; sent_timeout_ms is configurable via DtmfConfig::sent_timeout_ms (C030).

### Exceptions

- Exception: NativeEvent::RegistrationStateChanged actual pjsua_acc_get_info() FFI call cannot be tested in unit environment — it requires a live pjsua library initialized with accounts. Reason: pjsua_acc_get_info() is a C FFI function that requires a running pjsua instance with registered accounts (not testable in pure Rust unit context). This is not an architectural defect — the MockBackend::get_account_info() alternative provides the same data shape for unit testing, and the real FFI call is covered by integration tests (P0-6+). Alternative: MockBackend::get_account_info() validates conversion logic without FFI.
- Exception: Actual PJSIP callback invocation (on_reg_state2, on_call_state, on_dtmf_digit) cannot be unit-tested — these are C→Rust callbacks triggered by a live PJSIP stack. Reason: FFI callback registration and invocation (not testable without PjsuaBackend from P0-6). This is not an architectural defect — MockBackend simulated NativeEvent injection covers the conversion logic, and integration tests with PjsuaBackend (P0-6+) cover the full callback path. Alternative: MockBackend supplies NativeEvent directly for conversion tests.
- Exception: Real-time DTMF timing variance cannot be precisely tested — actual PJSIP callback vs timeout race depends on system scheduling. Reason: The 500ms timeout is a wall-clock timer; actual PJSIP callback may arrive just before or after (not testable deterministically). This is not an architectural defect — tokio::time::pause() provides deterministic simulation for unit tests, and production behavior is verified by integration tests with real PJSIP. Alternative: tokio::time::pause() simulates deterministic timing.
- Exception: Dual Client concurrency race condition (simultaneous NativeEvent arrives during client registration/deregistration) — not testable automatically without complex concurrency harness. Reason: Client registration/deregistration is a rare operation; race window is theoretically present but practically zero (not testable in automated unit environment). This is not an architectural defect — the dispatch function is deterministic, and registration/deregistration is serialized through the reactor command queue, eliminating the race in practice. Alternative: Manual stress test in QA phase; unit dispatch tests cover deterministic routing logic.
- Exception: RegistrationStateChanged pjsua_acc_get_info() returning a timeout/error status from a live PJSIP stack cannot be simulated in a unit test. Reason: A live registration timeout depends on the SIP registrar's actual non-response, which requires a real network peer and is not testable in a deterministic unit environment. This is not an architectural defect — MockBackend::get_account_info() can be configured to return Err or any status code, exercising the production failure publication path deterministically. Alternative: MockBackend returns Err(ReactorError::BackendError) and the test asserts RegistrationFailed/Error is published on the EventBus.
