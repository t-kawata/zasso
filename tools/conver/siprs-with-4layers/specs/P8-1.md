# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

### Goal
Close the ABC Inspection gaps and make the runtime infrastructure layer provably correct: (1) RuntimeCommand covers all 18 variants (incl. QueryState from P7-2, M20 ConfConnect/ConfDisconnect, and the 4 audio-source lifecycle commands), (2) RuntimeHandle exposes working audio-lifecycle submit methods that route through the reactor to a reactor-owned AudioMixer, (3) AudioWorkerTask's process_frame is test-verified end-to-end (next_chunk → gain/mute → mix → out_queue), and (4) MockBackend.conf_connect/conf_disconnect record observable side effects so the ConfConnect/ConfDisconnect dispatch path is provably wired.

### Purpose
The RuntimeCommand enum is the universal command interface that SipClient uses to drive the SIP stack. Every async public API call on SipClient eventually becomes a RuntimeCommand variant submitted via MPSC. The AudioWorkerTask enables per-call audio processing on dedicated Tokio blocking tasks, keeping audio computation off the reactor thread and the async runtime. Source lifecycle (add/remove/gain/mute) becomes a first-class RuntimeCommand capability.

### Motivation
P0-2 established the concurrency model with the base RuntimeCommand variants. P0-4 added the SipError type and M20 error converters. P0-5 added the EventBus and GetAccountInfo variant. P7-2 added QueryState. P0-6 extended the enum with M20 conference commands and the audio-source lifecycle. The ABC Inspection confirmed that although the implementation exists, the test suite does not detect regressions in the ConfConnect/ConfDisconnect dispatch path (O-001), the AudioWorker mix pipeline (O-002), or the audio-lifecycle reactor path (O-003). This re-implementation exists to close those detection gaps.

### Constraints
- Must not break existing RuntimeCommand API (backward-compatible extension).
- AudioMixer uses dashmap::DashMap (not std::sync::Mutex<HashMap>) for lock-free concurrent reads.
- AudioWorkerTask runs on Tokio blocking pool — no tokio::spawn on the reactor thread.
- No real PJSIP FFI calls in this ticket — all backend operations use MockBackend.
- AsyncAudioSource trait uses i16 (PCM S16LE), not f32 (migration is a future concern).
- The reactor must own the AudioMixer instance that audio-lifecycle commands mutate (single-writer rule on the reactor thread).

## Invariants

[Normal condition] RuntimeCommand has 18 distinct enum discriminants, each carrying a typed oneshot::Sender; reply channels are always created at construction and replaced by RuntimeHandle::submit()'s fresh channel (never reused). AudioMixer source_id starts at 0 and increments monotonically; per-source gain defaults to 1.0 and muted to false on add_source.
[Error invariant] oneshot::Sender is always resolved (send() called) in every code path of reactor dispatch — including the panic path, which replies Err(ReactorError::BackendError) before setting terminated. AudioMixer state is never partially modified: add_source fully inserts source+gain+mute or is a no-op; remove_source removes all three maps together.
[Internal state invariant] The reactor's AudioMixer is the single source of truth for the default-call audio sources; AudioWorkerTask holds its own Arc<AudioMixer> per call. RuntimeCommand reply channels are consumed exactly once by the reactor. process_frame snapshots source_ids before iteration so concurrent add/remove cannot corrupt iteration.
[Boundary invariant] u64 source_id wraps correctly from MAX to 0 (fetch_add wraps; the next available id after MAX is 0). Max 32 sources documented for slab optimization (future P1+). AudioWorker::process_frame must handle 0 sources (zero-filled silence) and 1 source (passthrough). gain clamped to [0.0, 2.0] on both bounds (negative clamps to 0.0, above 2.0 clamps to 2.0).
