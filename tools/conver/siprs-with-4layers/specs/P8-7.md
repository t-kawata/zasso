# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Replace the P8-4 placeholder body of `open_default_microphone_source` (src/api/asyncaudiosrc_adapter.rs:167-176) with real cpal device capture by adding cpal as an optional dependency behind the `cpal-input` feature, so the RFC §40 API returns `Result<Box<dyn AsyncAudioSource>, SipError>` backed by the platform default microphone, plus a feature-gated integration test.

### Purpose
The `cpal-input` feature has been declared empty (Cargo.toml:27) since P1-3, and the microphone source is the only RFC-required audio source that is not device-backed. Downstream consumers (AudioMixer via P5-2, the audio_tap example via P8-6, AI TTS source insertion) rely on opening the default microphone as an AsyncAudioSource; without this ticket the function is a stub that always returns a typed error.

### Motivation
P8-4 delivered the AsyncAudioSource adapter machinery (ErasedAudioSource/SyncAudioSource/SyncSourceAdapter) under a no-new-dependencies constraint, deferring the cpal dependency and leaving the `[::STUB::] P8-7` marker. This ticket removes that deferral: the adapter types are stable, the feature gate exists, and the remaining work is wiring cpal in and resolving the marker.

### Constraints
- cpal must be an optional dependency reachable only via `cpal-input`; default builds must not pull the cpal crate (feature-additive invariant). Cargo.toml:40 already declares `check-cfg = ['cfg(feature, values("cpal-input"))']`.
- MSRV is 1.95; pin a cpal version whose API is stable and documented. cpal 0.15/0.16/0.18 differ — v0.18 requires an explicit `stream.play()` after build and pins the sample rate/config explicitly.
- The public `open_default_microphone_source` signature must not change (C051 precondition); the returned source must implement AsyncAudioSource + Send.

## Acceptance Criteria

- - 【Happy path】With `--features cpal-input`, open_default_microphone_source(format) opens the platform default input device and returns Ok(Box<dyn AsyncAudioSource>) whose next_chunk fills an i16 buffer with captured PCM (>= 1 sample on a real device). The returned source is AsyncAudioSource + Send and can be stored as Box<dyn AsyncAudioSource + Send> in AudioMixer (compile-time check).
- - 【Error case】When no default input device exists, the function returns Err(SipError) with a clear message (SipErrorKind::NativeError) instead of panicking. When the requested AudioFormat cannot be matched by the device (non-convertible sample format), the function returns Err(SipError) describing the format mismatch (SipErrorKind::AudioFormatUnsupported).
- - 【Edge case】With the feature disabled (default), the function and CpalMicrophoneSource are compiled out and the crate builds without cpal — no device capture is attempted and `cargo tree -e normal` shows no cpal. Sample conversion clamps at i16 boundaries; an empty queue / zero-length buffer returns 0 without panicking.

## Invariants

- 【Normal condition】With `cpal-input` enabled and a default input device present, open_default_microphone_source returns Ok(Box<dyn AsyncAudioSource + Send>) and next_chunk fills the i16 buffer with device PCM. The cpal crate compiles only under the feature (Cargo.toml: cpal-input = ["dep:cpal"]).
- 【Invariant on error】Device-open, default-config, build-stream, and play failures never panic — they surface as Err(SipError). Sample formats outside the convertible set {I16, F32, U16} map to SipErrorKind::AudioFormatUnsupported; other device errors map to SipErrorKind::NativeError.
- 【Internal state invariant】CpalMicrophoneSource holds a cpal::Stream plus an Arc<Mutex<VecDeque<i16>>> sample queue; the queue grows only from the cpal callback thread and shrinks only via next_chunk; next_chunk returns 0 when the queue is empty (end-of-stream).
- 【Boundary invariant】Sample conversion is bijective at the extremes and clamped in between: u16::MAX↔i16::MAX, 0↔i16::MIN, 0x8000↔0; f32 in [-1.0, 1.0] maps linearly with clamping. A zero-length buffer returns 0 without panicking; a 65536-sample buffer (AudioMixer boundary) drains without overflow.
