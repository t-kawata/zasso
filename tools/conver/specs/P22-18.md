# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

- The reset-first ordering is the same discipline the project applies elsewhere: the supreme law forbids skipping safe ordering on the grounds that it appears to work, and a destructive transition without a recorded reset is exactly that failure.
- Record-replay matters because destructive transitions cannot be repeated freely. Without it, a falsification plan could only be run once, which would make the counterexample plan of P22-7 unrunnable in the general case.
- **The expert answer appended to `docs/ABOUT-ANALYSIS-TECH.md` fixes the shape of what this environment must report.** Static analysis can enumerate the syntactic entrances to dynamic behaviour — `extern` and `#[link]` and `include_*`, `macro_rules!`, `build.rs`, `cfg`, trait objects and `unsafe` boundaries in Rust — but it cannot in general enumerate which binding is realised at run time. The answer therefore requires a four-valued `dynamic_surface` status rather than a boolean, a `confidence`, and an explicit `unobserved_channels` list, because an environment that reports only "nothing found" makes the absence of a search look like the absence of a mechanism. The concrete phrasing rule matters as much as the status: a variable module specifier is recorded as *a dynamic load call exists whose specifier is not statically resolvable*, never as *there is no dynamic loading*.

Until this sandbox exists, that refusal can never be discharged, so every such proposition stays unresolved for a reason that has nothing to do with the project under analysis. Building the capability is the correct response; accepting the permanently-satisfied condition would leave every such proposition unresolved for a reason that belongs to the instrument rather than to the project.
- The production-path digest comparison reuses the same measurement discipline as the P22-1 gate, so the isolation claim is checked the same way the regression claim is.

## Acceptance Criteria

- **[Happy path]:** A sandbox is created, a session runs, dynamic evidence is collected, and the reset returns the environment to its initial digest.
- **[Error case]:** A failed reset is reported and the environment is marked unusable rather than silently reused.
- **[Edge case]:** A sandbox with no recorded transitions resets to its initial state unchanged, and the production tree is byte-identical afterwards.

## Invariants

- 【Normal establishment】`createSandbox(root)` produces an isolated environment in which the target can be started and dynamic evidence collected. `resetSandbox(handle)` returns that environment to its recorded initial state. `recordReplay(session)` captures a session so that it can be replayed without re-running the original side effects.
- 【On error】A sandbox that cannot be created produces a descriptive error naming the reason. A reset that fails is reported rather than ignored, and the environment is marked as unusable rather than reused.
- 【Internal state】Production state is never touched — asserted by comparing the production paths before and after every operation. No destructive transition is executed before its reset has been recorded.
- 【Boundary】A target that cannot be started is reported as unstartable rather than producing an empty evidence set that looks like a clean result. A sandbox with no recorded transitions resets to its initial state unchanged.

An independent adversarial code review was run against the implementation, and it found four real defects that the 37 green tests of the start phase had not exercised. Every one was reproduced empirically before being fixed, and each fix carries a new test.

1. CRITICAL - an undeclared channel list read as 'everything was looked at'. buildDynamicSurface({}) and collectDynamicEvidence(handle, session, {}) both defaulted unobserved_channels to [] and returned a VALID absent_under_scanned_patterns claim with confidence 'high'. A caller who simply omitted the field received an authoritative absence claim nobody made - exactly the failure this ticket exists to prevent. Fixed: an undeclared list is now read as all four channels unobserved (resolveUnobservedChannels), and collectDynamicEvidence passes the caller's value through untouched so the safe default applies. Test: 'C1 a caller who names no channel has not said that every channel was looked at'.

2. HIGH - the validator never re-derived the status. A record could state absent_under_scanned_patterns while carrying an observation of a construct it had seen, and validateDynamicSurface returned valid: true. Fixed: the validator now re-derives the status from the observations and runs and refuses any disagreement (statusOfEvidence). Tests: 'H2 a status that disagrees with the evidence filed under it is refused'.

3. HIGH - the reset gate was a mutable field, not a capability. A fabricated handle with resetArmed: true and a stub resetHandle ran a destructive transition. The module docstring claimed the ordering was enforced structurally; it was not. Fixed: the arming is a module-private WeakSet, the readable handle.resetArmed is a getter over it (assignment throws), and every handle-taking entry point first requires isObservedSandbox. disposeSandbox now refuses a handle this module did not create, so it cannot be used to remove an arbitrary directory. Test: rewritten UT-11.

4. HIGH - a symlink could carry a way out of the sandbox, and production was only checked when a caller asked. cpSync copies symlinks verbatim, so a link in the target still pointed at its production original, and no operation re-measured production. Fixed: a symlink whose target resolves outside the target root is refused at copy time (symlink-escapes-target), and production is re-measured after every runTransition and resetSandbox, marking the sandbox unusable and raising production-touched on drift. Tests: 'H4 a symlink that leaves the target is refused rather than copied' and 'H4 a transition that reaches production is reported and the sandbox marked unusable' (the latter asserts the escape really happened, so the refusal is not vacuous).

5. MEDIUM - a reset erased what a session had done. session.transitions was a live view over handle.transitions, which resetSandbox replaced with [], so a session recorded before a reset silently reported zero transitions and a different sessionId - the same 'empty evidence set that looks like a clean result' failure. Fixed: the session keeps the log it began in, by reference. Tests: 'a reset does not erase what a session already did'.

6. MEDIUM - a reset left a stale replayHandle advertising a session the sandbox no longer held. Fixed: resetSandbox clears it. Test: 'a reset clears the handle of the session it no longer holds'.

7. MEDIUM - sandbox.mjs was 988 lines, over the project's 800-line limit. Split into sandbox.mjs (766), dynamic-surface.mjs (375) and sandbox-error.mjs (17); the error class lives in its own module so the environment and the answer model do not import each other.

All fixed with tests where the behaviour was observable.

9. LOW - the suite depended on cargo being on PATH while only guarding on the target tree's presence, so a machine without cargo would fail with a wrong-reason error. A CARGO_MISSING_SKIP guard now skips those 22 tests with a stated reason. Verified both ways: 45 pass with cargo; 23 pass, 22 skipped, 0 fail without it.
