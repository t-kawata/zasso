# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Investigation

- **Measured 2026-09-10.** The target is a git working tree, so an isolated worktree is a native operation rather than something that must be simulated. The repository carries a `.gitignore` entry for `siprs-for-reverse/target/`, added during PX-203 after `git add -A` would otherwise have staged 5,154 build artefacts — evidence that the build directory is large enough to make worktree handling a real cost to manage.
- The R-4 resolution constrains annotation scope: `[::TICKET::]` annotations are applied to the files the loop touched, not to everything. Worktree isolation is what makes that limitation safe, since the execution cannot reach beyond its own tree.
- The restoration requirement is grounded in a concrete near-miss: during PX-203, running `annotate-ticket-context-by-git-diff.js` would have re-contaminated `siprs-for-reverse` because line 393 includes untracked files. The remedy was to skip the script entirely. That is the class of silent main-tree modification this ticket must make impossible.
- The failure path matters as much as the success path: a reconstruction execution can fail to observe Red, throw partway, or be interrupted, and each of those must still destroy its worktree.
- The implementation loop integration is what makes reconstruction practical, since running one ticket per session means a reconstruction ticket is a session like any other and needs the same execution scaffolding.

## Acceptance Criteria

- **[Happy path]:** A reconstruction ticket executes in an isolated worktree, Red evidence is recorded, and the main tree is byte-identical afterwards.
- **[Error case]:** A restoration failure is reported and treated as blocking, and a worktree creation failure never falls back to the main tree.
- **[Edge case]:** A worktree is destroyed even when the execution throws partway through.

## Invariants

- 【Normal establishment】A Red reconstruction ticket executes inside an isolated worktree and the resulting Red evidence is recorded. On completion the worktree is restored or destroyed with certainty, and the main tree is byte-identical afterwards.
- 【On error】A worktree that cannot be created is reported rather than falling back to executing in the main tree. A restoration that fails is reported and treated as a blocking failure.
- 【Internal state】The main tree is never modified — asserted by comparing its digest before and after every execution. The isolation applies to every execution path without exception.
- 【Boundary】A ticket whose Red cannot be observed is reported as such rather than being recorded as a successful reconstruction. Zero reconstruction tickets produces an explicit result rather than a vacuous success.

## RFC Discrepancies found in Prior Implementation Rounds

- P22-19 Test Plan > Exceptions > Alternative verification. Claim: "assert that the worktree is created from the same commit as the main tree, that its digest matches the main tree digest at creation, and that the execution and destruction paths leave the main tree byte-identical". Observed: the first and third clauses are implemented and tested; the middle clause is not satisfiable literally for a git worktree, because a worktree checks out tracked content only and gitignored paths (for example .claude/scripts/workspacify-reverse/node_modules/) are legitimately present in the main tree and absent from the worktree, so the two digests differ in a correct execution. Measured on a dirty tree: the main tree held "UNCOMMITTED", the worktree held "COMMITTED". Resolution: implemented the achievable and non-silent form the clause was aiming at — outcome.mainTreeCleanAtCreation records whether HEAD and the working tree held the same bytes at creation time (true/false, or null when the reading could not be taken), asserted by a test on both the clean and dirty paths. Flagged for the loop-integration round: a reconstruction ticket whose target files carry uncommitted changes has its Red observed against the committed revision, and the caller can now see that.
