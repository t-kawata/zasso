# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- **[Happy path]:** Two or three holdouts are frozen, the answer key is extracted with its measured counts recorded, `verifyIsolation` exits 0, and both protocol documents exist.
- **[Error case]:** Planted ground truth, a post-freeze holdout modification, or a reconciliation attempted against a modified oracle is reported by name and refused.
- **[Edge case]:** An empty ledger exits 0 and states that none were selected. Zero disagreements is reported as a finding requiring scrutiny rather than as agreement.

## Invariants

- 【Normal establishment】The ledger loads, every recorded sha256 recomputes, and `verifyIsolation(root)` confirms that no ground-truth artefact is reachable from the target root. The answer key is extracted into a frozen oracle bundle recording, for `siprs-with-4layers`, the 113 graph nodes and 153 edges, the Dirs-Tree, the 146 tickets across 21 phases, the 8 omission files, the 232 `@verifies` annotations, the 379 files carrying `[::TICKET::]` and the 143 files carrying an `Initial Design Artifact` header. Each ineligible candidate is accompanied by the reason it was rejected. **The bundle also records the known structural delta between the two trees**, measured rather than assumed, so that a known difference is never presented as a finding.
- 【On error】A post-freeze modification of a holdout or of the answer key is detected as a sha256 mismatch naming the artefact. Planted ground truth is reported by filename. Neither condition is silently tolerated, and a reconciliation run against a modified oracle is refused rather than reported.
- 【Internal state】The ledger and the oracle bundle are append-only: a frozen sha256 cannot be rewritten. Verification never writes to the holdout tree, and never writes to `siprs-with-4layers` — that tree is the answer key and any modification to it destroys every measurement taken against it.
- 【Boundary】Zero holdouts exits 0 with the explicit statement that none were selected, rather than being read as failure. A holdout whose language cannot be determined is reported as unknown rather than raising. A reconciliation that finds zero disagreements is reported as a finding requiring scrutiny, because zero disagreement between two independent derivations is a signal of contamination rather than of accuracy.

## Boy Scout Rule

- Functions are verb phrases (`loadLedger`, `freezeHoldout`, `verifyIsolation`, `evaluateEligibility`, `freezeOracle`, `reconcile`); variables are domain concepts (`holdoutId`, `frozenDigest`, `isolationViolations`, `capabilityProfile`, `oracleArtefact`, `disagreementKind`). The `is`/`has` prefix convention is used for booleans as the coding-style rule requires.
- The contamination filename list is a named constant, not an inline literal repeated in three places.
- The stage-to-oracle mapping is a declared table rather than a chain of conditionals, so adding a stage means adding a row and the comparison for every stage is readable as a list.
- Reading and verifying the ledger and the oracle are separated from writing them, so both read paths can be asserted side-effect free.
- Both protocol documents are written so that they can be read top to bottom as instructions, matching the Readability is Translatability principle applied to prose.

### Exceptions

- **Item**: Deciding what a reconciliation disagreement means. **Why it is not testable**: each disagreement is one of three things — the analysis missed something the forward rotation had, the analysis found something the forward rotation did not have, or the forward rotation's own artefact was a free choice rather than a necessary one — and distinguishing them depends on intent, which neither tree records. This is not a design defect; it is the deliberate boundary of the design, which builds the instrument that makes the question concrete and leaves the judgement to a human. Mechanising it would be exactly the mechanical success judgement the design rejects. **Alternative verification**: assert that `reconcile()` returns a list of individually named disagreements, that it carries no score, ratio or verdict field, that the run refuses to proceed against an oracle whose sha256 has changed, and that `siprs-with-4layers` is byte-identical afterwards. Those four assertions are UT-8, UT-18, UT-19 and IT-4.
- **Item**: The final eligibility judgement for a holdout candidate. **Why it is not testable**: eligibility is a human decision, and mechanising it would invent a fixed threshold that is a false criterion — exactly the failure ABOUT-REVERSE 7.7.2 warns against. This is not a design defect; it is the core principle of the design, which places success judgement with a human and not with a script. **Alternative verification**: assert that `evaluateEligibility` returns capability, observability, falsifiability and risk dimensions and never returns a boolean `eligible` key. That assertion is UT-7 and it is executable.
