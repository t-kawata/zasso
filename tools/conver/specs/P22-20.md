# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## This ticket — P22-20

**Goal**: Make the adjudication of boundaries a choice between candidate models rather than the authoring of a model from scratch.

**Purpose**: Assuming that the physical layout is the logical architecture freezes the existing technical debt into the canonical record permanently, which is F14. Presenting candidates converts an open-ended design task into a bounded choice.

**Motivation**: ABOUT-REVERSE 7.4 item 9 and 7.7.1. Because `mappedNodeIds` already exists in the forward index chain, recording mismatches on top of it is cheaper than building a new structure alongside it.

**Constraints**: The human is the adjudicator between candidate models, not their author. The AI's judgement surface is not widened beyond adjudication: generating candidates mechanically and deciding between them are separated deliberately.

## Investigation

- **Measured 2026-09-10.** `mappedNodeIds` exists in the forward index chain at `rfc-graph/boundify-helpers.js:89`, which is why candidates can be recorded on top of it rather than in a new structure. This is the concrete fact behind the 7.4 item 9 claim that the mismatch approach is cheaper.
- The F14 risk has a visible instance in this target: `siprs-for-reverse` has a top-level layout mixing `src/`, `tests/`, `examples/`, `docker/`, `vendor/` and build configuration, which reflects the project's history rather than a clean architecture. Treating that layout as the logical architecture would canonise it permanently.
- The 2-Pass structure follows 7.7.1: vertical at boundaries, horizontal inside. The vertical pass is where a boundary is adjudicated, and the horizontal pass is where a package's interior is understood, which is why Pass 2 must not reason about other packages.
- The card structure is constrained by 7.4.1: a card's subject is a falsifiable proposition, and free-form prose is never demanded. That constraint is what makes a card adjudicable in bounded time.
- The existing gate vocabulary from P22-11 (T5) is reused rather than restated, so the "a missing record is the failure" principle has one definition in the phase.

## Acceptance Criteria

- **[Happy path]:** Multiple candidate models are generated and adjudicated, with every mismatch recorded in `ARCHITECTURE-DELTA`.
- **[Error case]:** A mismatch that is not recorded produces a FAIL, matching T5.
- **[Edge case]:** A package with a single candidate produces a valid single-option card, and no candidate is ever lost.

## Invariants

- 【Normal establishment】Multiple candidate logical models are generated mechanically from the R1 and R2 measurements. Each candidate is presented as a decision card carrying its consequences, its supporting evidence and its counterexamples. Mismatches against the physical structure are recorded in `ARCHITECTURE-DELTA`.
- 【On error】A candidate is never deleted; one that cannot be adjudicated remains `unresolved`. A mismatch that is not recorded is a FAIL, matching T5 in P22-11. A card that demands free-form prose is not emitted.
- 【Internal state】Pass 2 stays local to a package and never reasons about interactions with other packages, which is what keeps the horizontal pass bounded. Candidates are recorded on top of `mappedNodeIds` rather than in a parallel structure.
- 【Boundary】A package with a single candidate produces a card with one option and remains valid. A package with no measurable structure produces no candidate rather than an empty card.

## RFC Discrepancies found in Prior Implementation Rounds

- P22-20 plan (Step 4) scoped the 2-Pass Hybrid's Pass 2 by the dependency edges internal to a package (buildHorizontalPass returned `edges` filtered to from === to). The Red phase measured the real R2 artefact and found 0 internal edges among the 55 measured: R2 records imports at directory granularity, so a package importing itself is not an edge. An edge-scoped Pass 2 would therefore have received no input at all on siprs-for-reverse and its 'never reasons about other packages' invariant would have held vacuously. Pass 2 is now scoped by the package's measured members (the material 7.7.1 describes), and buildHorizontalPass does not accept the dependency graph as a parameter, so the boundedness is structural. The contract C003 itself is unchanged; only its test code and the module API were corrected against the measurement.

Review report:

FINDINGS FOUND AND FIXED (4):
1. [Major] mapDirNodes stripped the tree's root directory from every path. The real RFC-ROOT-Dirs-Tree.json is keyed by language (`trees.rust`) but the node under that key is the top-level DIRECTORY, named `src` -- not `rust`. Dropping it produced paths like `api` where the tree's own `dependencyDirections` names `src/api`, so every mismatch came out with an EMPTY mappedNodeIds and the candidate/ARCHITECTURE-DELTA anchoring was silently broken on the real subject. Fixed by indexing the root too; pinned by UT-12c, by UT-12d (the index must carry every path the tree's dependencyDirections names) and by IT-1 (the real mismatches must carry a non-empty anchor). This was found only by running the implementation against the real artefacts.
2. [Major] A candidate need not be a partition. cycle_collapsed pushed each measured cycle as its own group without checking disjointness, so an overlapping cycle list put one directory in two groups; the card the human answers and the mismatch the delta records could then name different units for it. Fixed by assertIsPartition in buildCandidate, which every rule now inherits; pinned by UT-1c.
3. [Minor] assertCardIsAdjudicable required subjectKind to be present but never checked its value, so the closed vocabulary of CARD_SUBJECT_KINDS was unenforced. Fixed; pinned by UT-5b.
4. [Minor] A candidate's `proposition` was a conjunction joined by ', and' when it merged more than one group -- a field named for one proposition holding several. Renamed to `propositions`, one falsifiable proposition per merged group (7.4.1); pinned by UT-2c.

TEST-PLAN TRACEABILITY GAPS FOUND AND CLOSED (2):
- UT-11 was implemented but carried only its C003 label; the label was added so the ticket's Test Plan maps to a findable test.
- IT-1 and IT-2 were only covered on synthetic data. Added an integration test that generates from the real R1/R2 measurements, derives and records the mismatches, asserts the mappedNodeIds anchor is non-empty, and confirms no candidate is lost.

OBSERVATIONS (no change made, with the reason):
- `dirsTree` stays optional in generateCandidates. Measured: siprs-for-reverse carries no *-Dirs-Tree.json (the forward artefacts are stripped), so a run without one is a legitimate case and requiring the tree would make the module unusable on the reverse target.
- On a `merged` mismatch, mappedNodeIds carries the union for the logical unit the directory joined, so every member of one merge repeats it. That is deliberate: for a merge decision the material is what the resulting unit would be responsible for. It is not a per-path claim.
- The run-quality-checks single-letter-variable regex `(let|const|var|mut)\s+([a-df-z])` matches the English verb in prose such as "would let a reader". It flagged a comment line; the comment was reworded rather than the checker changed, and the trap is recorded here for later sessions.
- annotate-ticket-context-by-git-diff.js maps changed lines only to non-exported function definitions, so a ticket that changes only `export const` declarations can never be auto-placed and re-emits [::AMBIGUOUS::] on every run. Resolved by placing truthful annotations (the CARD_SUBJECT_KINDS docblock P22-20 edited; the three directoryOf-related definitions) and a file-level annotation, and by not re-running the annotate step afterwards.
