# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## This ticket — P22-22

**Goal**: Classify high-risk propositions into a separate lane and require human authority and strong falsification for them.

**Purpose**: A weak authorization check, a tenant mix-up or a poorly managed secret must never be promoted to the status of an existing contract merely because the code does it that way (F15).

**Motivation**: ABOUT-REVERSE 6.13 Phase 4 and 7.4 item 14. The lane exists because for these propositions the code is evidence of what happens, not of what should happen.

**Constraints**: A proposition concerning safety, authorization, money, deletion, cryptography or audit is never canonised without a human normative approval, no matter how strong the evidence for its current behaviour. The lane classification is kept separate from the ordinary lanes, because merging them is what would let a dangerous proposition be canonised silently.

## Investigation

- **Measured 2026-09-10.** The risk categories are not hypothetical for this target. `siprs-for-reverse` is a SIP implementation with `verify_unsafe_isolation.rs` and `ownership_ffi_boundary.rs` among its test files, an FFI boundary (`wrapper.h`, `build.rs`), and a `watcher-config.json` that governs file-system watching. Authorization, secrets, deletion and audit are all plausible categories in that surface, which is why the lane cannot be treated as a formality.
- The authority requirement has an established mechanism to build on: P22-13 records `normative_authority` as a stable role or team identifier and rejects personal names, so G5 and this lane share one definition of authority.
- The reason a code-derived security claim must not be canonised is the same reason the ratification RFC is the central failure mode of reverse rotation. For a security check, "the code does this" is especially weak evidence, because a missing or incorrect check is invisible in the code that is present.
- The lane separation is what makes the requirement enforceable rather than advisory: if lane claims travelled through the ordinary canonisation path, the authority requirement would be a step that could be skipped, and a skipped step is indistinguishable from a satisfied one after the fact.
- This is the last ticket in the phase, and it gates the release loop, which is the loop that would otherwise publish the canonical record.

## Acceptance Criteria

- **[Happy path]:** High-risk claims are classified into the lane and none is canonised without a human authority record and a strong falsification.
- **[Error case]:** A high-risk claim without an authority record is refused canonisation, and an authority recorded as a personal name is rejected.
- **[Edge case]:** A run with no high-risk claims reports that there were none, and an ambiguous claim is reported rather than silently placed in the ordinary lane.

## Invariants

- 【Normal establishment】Claims concerning authorization, tenancy, secrets, deletion and audit are classified into the security lane. Each such claim requires a human authority record and a strong falsification before it can be canonised.
- 【On error】A high-risk claim without an authority record is not canonised. A claim that cannot be classified into or out of the lane is reported rather than defaulting to the ordinary lane.
- 【Internal state】The lane classification is never merged with the ordinary lanes — asserted so that a security claim cannot be canonised by the ordinary path. No authority is recorded as a personal name.
- 【Boundary】A run with no high-risk claims reports that there were none rather than producing an empty lane that looks like a clean result. A single high-risk claim is classified and gated correctly.

### Exceptions

- **Item**: Verifying that the classification captures every genuinely high-risk proposition. **Why it is not testable**: completeness of a risk taxonomy over an arbitrary codebase cannot be established by a finite test suite, since the taxonomy is a judgement about what matters. This is not a design defect — the design handles the residual risk the only way that is sound, by requiring human authority for anything classified into the lane, so that a misclassification results in a human decision rather than in silent canonisation. **Alternative verification**: assert that every classified claim carries a lane marker, that no lane claim can be canonised through the ordinary path, that an ambiguous claim is reported rather than defaulted, and that no authority is recorded as a personal name.
