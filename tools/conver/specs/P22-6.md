# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Investigation

- **Measured 2026-09-10.** The target `/Users/kawata/shyme/zasso/tools/conver/siprs-for-reverse` is a git working tree and retains readable history, so R4 has material to work with rather than a degenerate case.
- PX-203 produced a concrete instance of the F17 problem. Ten test files had been named after the ticket keys that generated them (`verify_spec_*.rs`), and source comments carried `@verifies` annotations referencing contract ids. Those tests were written from the design, so they agree with the implementation by construction and cannot detect a divergence between the two. That is precisely the co-conspirator oracle R5.5 exists to expose.
- PX-203 also produced a concrete absent-Red instance: the ten ticket-keyed test files were test-only, and P22-16 later needs to detect exactly this category.
- The TCE requirement is language-specific, and **the earlier wording of this ticket was wrong about Rust.** `rustc` has no official source printer. The available pair is `syn` for parsing plus `prettyplease` for printing — a third-party crate over `syn`'s AST, not the compiler's, and one that can drop comments. That matters here specifically, because comment-borne evidence (`@verifies` annotations and contract-id comments) is part of what this project reasons about, so a normaliser that discards comments discards evidence. **The claim must be weakened accordingly: TCE proves syntactic equivalence under a named configuration and never semantic equivalence.** `i < n` and `i <= n - 1` are not interchangeable once overflow, types, side effects in `n` or undefined behaviour are considered, and general program equivalence is undecidable. A normaliser chosen for a different language would silently discard non-equivalent mutants and manufacture a false clean result, so it is chosen per language and recorded in `docs/P22-ANALYSIS-TECH.md`.
- **The comparison ladder stops at the first step that applies, and never claims more than that step proves.** In order: (1) text identical; (2) token-normalised identical; (3) AST-normalised identical; (4) equal under a limited set of local rewrite rules; (5) the compiler or type checker emits the same IR or the same diagnostics; (6) no test, property or differential implementation could distinguish them; (7) `unknown`. **Step 4 and beyond are unsafe unless the language, the types, the evaluation order, the side effects, the arithmetic model and the configuration are all named.** The ladder is never collapsed into the single word "equivalent" anywhere in the output: a mutant discarded at step 6 and a mutant discarded at step 1 are different kinds of claim, and flattening them is exactly how an undecided mutant comes to be presented as a decided one.
- **Pre-expansion and post-expansion code are two objects, not one.** For each, keep the pre-expansion source a human maintains — with its own `file:line`, review surface and design intent — and the post-expansion form under a fixed configuration, which is what name resolution and type checking actually see. Connect them by a many-to-many provenance graph carrying `origin_span`, `expansion_span`, `configuration_id` and `generator_identity`, never by a one-to-one assumption, because a macro call site and its expansion do not correspond one to one. This corpus makes the distinction concrete rather than hypothetical: `build.rs` and `wrapper.h` mean generated and macro-produced code is present.
- **Reproducibility is a property of the output, not of the tool version.** Where Go normalisation is used, run the formatter at a pinned version **and record its output**, because formatter behaviour is version-scoped and the manual warns that its output can change incompatibly between releases. Pinning the version without storing and comparing the output is not evidence of reproducibility. The request-side verification record in `docs/ABOUT-ANALYSIS-TECH.md` §7 could not confirm the exact manual sentence the expert cited, which is a further reason not to rest the design on that citation alone.
- The dead-code and stub categories have a real population here: the crate is a SIP implementation with an FFI boundary (`wrapper.h`, `build.rs`) and `#[non_exhaustive]` types, both of which generate unreachable and unobservable surfaces.
- ABOUT-REVERSE 7.6 lists F21 alongside F12 and F17; the gap enumeration is the point at which all three are addressed, which is why they share a ticket.

## RFC Discrepancies found in Prior Implementation Rounds

- Step 0 and IT-4 prescribe `run.mjs oracle compare --stage r5`, but the declared CLI requires a candidate document: `run.mjs oracle compare --stage r5 --candidate <path>`. Without `--candidate` the dispatcher prints the usage block and exits 2, so the prescribed command cannot run as written. Verified 2026-09-10 against the current `run.mjs`. The comparison is therefore run with an explicit `--candidate` produced by `buildGapCandidate`.
- The ticket names `docs/P22-ANALYSIS-TECH.md` as the artefact that fixes "the mutation and normalisation technology". It does not. The document declares tree-sitter as the layer-B syntax instrument, marks E13 (equivalence) `unsupported_in_principle` for all six languages, and explicitly leaves the per-language normaliser question open: §7 lists "that `prettyplease` drops comments, that Python's `ast.unparse()` does not round-trip" among the items §7 did not verify and that "P22-5 onward must measure ... before building on them". Neither a mutation runner nor any of the normalisers named in ABOUT-REVERSE §11.5 R-2 (SWC/Babel, `go/ast`+`go/printer`, `syn`+`prettyplease`, `ast.parse`+`ast.unparse`, `com.sun.source`, Clang AST) is declared or installed. P22-6 does not re-decide the technology: it builds the TCE ladder on the declared tree-sitter instrument and records the resulting limitation as a field.
- About the sidecar names. The ticket's "Produces — exact artefacts" and its scope both name `GAPS.json`. That name appears nowhere in `docs/ABOUT-REVERSE.md`. §6.12.3 names `HISTORY-PROVENANCE.json` and `GAP-REGISTER.json` as the stage products for this range. - ABOUT-REVERSE §11.5 R-2 and this ticket both record that `rustc` has no official source printer and that `syn` + `prettyplease` is a third-party printer that can drop comments. P22-ANALYSIS-TECH.md §7 confirms this is unverified. P22-6 therefore does not adopt `prettyplease`: comment-borne evidence (`@verifies` annotations, contract-id comments) is part of what this project reasons about, and a printer that drops comments would discard that evidence silently. ## Review report — P22-6

### What was reviewed

The three new modules (`lib/history.mjs`, `lib/gaps.mjs`, `lib/oracle-gap.mjs`), the wiring in
`lib/scope.mjs`, `lib/structure.mjs` and `run.mjs`, the test helper, and the three new test files.
An adversarial pass was run against the design rules the ticket must honour — that a commit message
is never proof of intent, that a mutation score is never contract coverage, that an unobserved region
is never called absent, that zero gaps is never a pass, and that a mutant the normaliser cannot decide
is retained. Every finding below was reproduced by running the module before it was fixed.

### Blocker findings — fixed

**B1 — rung two manufactured false equivalences.** `tokenNormalised` collapsed whitespace in the raw
text, so whitespace *inside a string literal* was normalised away: `"hello world"` and `"hello  world"`
were discarded as equivalent at rung two. That is a false clean result, the exact failure the ladder
exists to prevent. Rung two is now built from the syntax tree's leaves, so only whitespace *between*
tokens is discarded. Reproduced: `discarded: 1` before, `discarded: 0` after.

**B2 — a mutant with no text was called byte-identical.** `mutant.original ?? ''` turned an absent text
into an empty string, so a mutant carrying no text at all reached rung one and was discarded. An absent
text is missing evidence, not equivalence. Reproduced: `discarded: 1` before, `survivors: 1, cause:
unclassified` after.

### Major findings — fixed

**M1 — a commit of pure modifications was invisible.** `M` lines were requested from git but had no
entry in the status map, so they were skipped; a commit made only of modifications had no changes and
was dropped entirely, taking its co-changes, its provenance anchor and its place in the commit count.
Reproduced on a two-commit repo: `commitsInScope: 1` and the provenance dated to the creation commit;
now `commitsInScope: 2`, the anchor is the newest commit, and the coupling has two commits behind it.

**M2 — non-ASCII paths were silently dropped.** git escapes non-ASCII bytes by default, so a path like
`src/café.rs` arrived quoted and did not match the population. The commit touching it was mis-read and
the co-change pair destroyed. Reproduced: `transitions: ["src/plain.rs"]`; now both files and the pair
survive. Fixed with `core.quotepath=false` plus a decoder for the quoting git still applies to paths
containing a quote or a backslash.

**M3 — a substring test hid the stage's most important finding.** `findAbsentRed` used
`testText.includes(symbol)`, so `id` was reported covered because a test said `valid`, and `get` because
one said `forget`. Reproduced: `gaps: 0` where two were due; now `["get","id"]`.

**M4 — comment drift was wrong in both directions.** A name surviving only in a trailing inline comment
suppressed the finding, and prose was reported as drift. Both boundaries now come from the tree: comment
nodes are the only text searched, and the code names are read from the source with comments blanked.

**M5 — the empty-body check was line-scoped.** It reported `let s = "fn quoted() {}";` and
`// fn documented() {}` as empty implementations, and missed a body whose braces are on separate lines.
It is now a tree check. Reproduced: lines `[3,4,5]` with two false positives and one miss; now
`[2,3,5]` with the function names attached.

**M6 — an undeclared language aborted the stage.** `normaliseForComparison` threw for a language with no
grammar, so one file in an undeclared language discarded every mutant in the run. It now returns null and
the mutant is retained, which is what the module's own contract said it should do.

**M7 — the two entry points disagreed on the default.** `analyzeProject` defaulted to `r2.5` while the
command line defaulted to the last declared stage, so the library silently skipped five stages the CLI
ran. Both now derive the default from `ANALYSIS_STAGES`. The R0-R2.5 suites name their own boundary.

### Minor findings — fixed

The unknown rung could be cited as support for an equivalence claim; two co-change pairs were merged
when a path contained the joining character; the mass-change and vendoring signals were computed over
the filtered population, so the vendoring factor could never fire; lineage spans were mutable inside a
frozen container. A further defect was found while fixing M4: Rust nests a `doc_comment` inside the
`line_comment` carrying its `///`, so one comment's drift was reported twice under one gap id.

### Test quality

The reviewer found the suite green while these defects lived, and named the reason: no fixture created a
modify-only commit, `findStubs` asserted only `length >= 4`, and the drift and absent-Red fixtures
avoided the cases that break. Fifteen regression tests were added, one per defect, each written to fail
against the old behaviour. Two tautological assertions the reviewer identified were replaced with
assertions that constrain behaviour.
