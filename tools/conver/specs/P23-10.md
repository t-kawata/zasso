# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-10: RFC-SEED compatibility across conver versions

**Ticket Key**: P23-10 · **Phase**: 23

---

## Background

### Goal
An `RFC-SEED.md` written by an **older conver** is handled honestly. The seed's format version is determined mechanically and recorded; a seed declaring an older format parses under **that format's** declared section list; and a seed that matches no declared format is reported **with what would make it compatible**, without the run stopping and without the malformed seed being accepted.

### Purpose
Design §7.3 records the question as **not verified**: "Whether `seed-parse.mjs`'s exact heading-count check (14) rejects an `RFC-SEED.md` produced by an **older** conver — §2.4 / A4. A pattern-2 or pattern-3 project may carry a seed written under different rules." The gate A4's row in §2.4 states the current rule: "§1 carries the reverse index; heading count remains exactly 14 — `seed-parse.mjs` enforces exact equality with `SEED_REQUIRED_SECTIONS`."

### Motivation
**Measured** on 2026-09-11, reading `.claude/scripts/workspacify-allocate/lib/seed-parse.mjs`: `parseSeed` checks `lines[0].startsWith(SEED_TITLE_PREFIX)`, then `if (headings.length !== SEED_REQUIRED_SECTIONS.length) throw new WorkSpacifyTreeError(seed has N headings, expected 14, { gateId: 'G3.6' })`, then checks each heading's index and title against the same list. `SEED_REQUIRED_SECTIONS` (`seed-model.mjs:22`) declares fourteen entries from `{ index: 1, title: 'Identity and Position in the Whole System' }` to `{ index: 14, title: 'Source Traceability Index' }`. The module already anticipated the reverse rotation's need to *count* a seed it is about to reject — P22-12 split `scanSeedHeadings` out with the comment "The reverse rotation has to count the headings of a seed it is about to reject — a fifteenth section is the exact defect the heading contract exists to catch — so the count cannot come from a parser that throws on the count being wrong." What does not exist is any answer to what happens when the seed is *not* defective but *older*: a subject carrying a seed from a conver that declared a different set is refused by a check that cannot tell the two apart.

### Constraints
- Gate A4's exactness is preserved **within a declared format**. A seed declaring the current format with fifteen headings still fails, and a seed whose heading titles are reordered still fails. The compatibility path must not weaken the check it exists beside — that would trade a false refusal for a false acceptance, which is worse.
- Design §1.2 governs the outcome: an incompatible seed is **worked through**, not refused. The reverse rotation must not stop because a subject carries a seed written under different rules; the incompatibility is material and is reported.
- The seed's own §1 carries the reverse index and must keep doing so (A4). A seed that omits it is a defect of the current format, not a version difference.
- No new file format is invented. If a version marker is needed, it is added as an optional field in the seed's existing machine block, following `ABOUT-REVERSE` §6.12's "Option 2.5-refined" discipline: additions are limited to optional fields, intermediate artefacts keep their forward schemas and their canonical hashes.
- A seed that carries no version marker is reported as **unversioned**, which is the honest reading of a document written before the marker existed, and is not defaulted to the current format.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §7.3 (the unverified seed-compatibility question) → .claude/scripts/workspacify-allocate/lib/seed-parse.mjs

- **Precondition**: A seed text is presented for parsing, and the declared seed formats are available as a table, each carrying its version identifier and its ordered section list.
- **Postcondition**: The seed's format is determined mechanically and reported as one of: a declared format version, if the seed declares one; unversioned, if it declares none; or unrecognised, if it declares one that is not in the table. The determination names the marker it was read from, or states that no marker was present.
- **Invariant**: The format is never inferred from the heading count. A seed with fourteen headings and no declaration is unversioned and not assumed current, because inferring the format from the very property the format defines would make the check unfalsifiable.

### C002 — .claude/scripts/workspacify-allocate/lib/seed-parse.mjs (SEED_REQUIRED_SECTIONS, gate A4)

- **Precondition**: A seed has been determined to declare a format, and that format carries an ordered section list.
- **Postcondition**: The seed parses under its own declared format's section list, so a seed declaring an older format with a different heading set parses successfully and its parsed sections are addressed by that format's indices.
- **Invariant**: Exactness is preserved within a format: a seed declaring the current format with fifteen headings, with a reordered heading, or with a mismatched title still fails gate A4 with the existing messages. The compatibility path adds formats; it does not relax any format.

### C003 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §1.2 (incompleteness is the input, never a refusal condition)

- **Precondition**: A seed is unrecognised, or parses under a format whose section list does not match the one the run needs, so that a compatibility gap exists.
- **Postcondition**: The incompatibility is published as a finding naming the seed, the format determined, the format the run needs, and the concrete change that would make the seed compatible — and the run continues, so the subject reaches its terminal state by carrying the seed forward rather than by being refused.
- **Invariant**: No gate in the reverse chain refuses the run on a seed-format incompatibility. A test runs the allocate reverse path over a subject carrying a foreign-format seed and asserts the run publishes every document it would publish for a current-format seed, differing only in the compatibility finding.

## Boy Scout Rule

- **The format is data, and the parser reads it.** `SEED_FORMATS` is a frozen table and `parseSeed` resolves a row rather than branching on a version. Adding a format is adding a row, and `CURRENT_SEED_FORMAT_VERSION` names the row the writer targets, so writer and reader read the same declaration.
- **Function names as verb phrases.** `determineSeedFormat` determines, `reportSeedCompatibility` reports, `parseSeed` parses. `scanSeedHeadings` keeps its name because P22-12 chose it for a reason its comment states.
- **Variable names as domain concepts.** The locals are `determinedFormat`, `requiredFormat`, `declaredVersion`, `markerEvidence`, `sectionsExpected` — never `data`, `info` or `tmp`. Existing locals `headings`, `expected`, `actual` are kept, since each lives within a few lines of its declaration.
- **Hardcoded values as named constants.** The marker's field name and the version strings become constants, so the writer that emits the field and the reader that looks for it cannot spell it differently.
- **No error swallowing.** An unrecognised format is reported with the version string, never defaulted to the current one; a malformed machine block fails the parse rather than yielding an empty determination. Both defaults would convert a real incompatibility into a silent acceptance.
- **Boy Scout improvement outside this ticket's scope.** `parseSeed`'s body performs five checks in sequence, each throwing separately, with the heading loop containing two more. This ticket extracts the per-heading check into `assertHeadingMatches(heading, expected)` so `parseSeed` reads as the six sentences it performs — title, count, then for each heading: index, title, body — and the messages move beside the check that raises them. Every existing message is preserved character for character, pinned by the tests that already assert them.

DEFECT 1 (Major) — A4 threw instead of returning a record. `assertSectionOneIndex` called `determineSeedFormat`, which throws on a missing or malformed machine block, so `runReverseAllocateGates` raised an exception and returned no records at all. That broke the runner's documented contract ('every gate is judged even after one of them fails'), skipped A5, and turned a gate verdict into a stack trace. Fixed by catching the determination failure and returning a BLOCKED record carrying the existing parse message. Test: 'review 1'.

DEFECT 2 (Major) — the published finding did not name the seed. `reportSeedCompatibility` accepts a seed label, but the A4 call site never supplied one, so every finding read '### the seed' and an operator with several seeds could not tell which one was being reconciled. The unit test passed because it supplied the label itself, which is exactly the shape of defect that passes a test while failing the behaviour. C003's postcondition requires the finding to name the seed. Fixed by deriving the label from the seed's own title line (`readSeedPackageName`); the A4 path now publishes '### alpha'. Test: 'review 2'.

DEFECT 3 (Major) — the finding reported a difference it could not know. The 'Difference' line printed '0 section(s)' whenever the declared format was unrecognised or absent, because the resolved row was null and the count defaulted to zero. Zero reads as 'no difference', which is the opposite of what the finding exists to say. Fixed by stating the comparison only when it is knowable: a declared row reports its count, an absent declaration and an unrecognised version each say why no count can be given. Test: 'review 3'.

DEFECT 4 (Minor) — a format table could describe itself two ways. `determineSeedFormat` resolves a format from the seed's *first* section, while `parseSeed` reads the machine block from the section whose index is `machineSectionIndex`. A row whose machineSectionIndex was not its first section's index made the two disagree, and parseSeed would silently yield a null reference block. `defineSeedFormats` now refuses such a row. Test: 'review 4'.

DEFECT 5 (Minor, translatability) — `SEED_CONTRACT_SECTION_INDEX` (an index, 2) was passed to `seedFormatSectionAt`, whose parameter is a position. The two coincide only because the current format numbers its sections in order, so the call site required the reader to know that. `SEED_CONTRACT_SECTION_POSITION` now names the position and `SEED_CONTRACT_SECTION_INDEX` is derived from it, so they cannot drift. Test: 'review 5'.

DEFECT 6 (Minor) — a seed that could not be parsed was reported with `counts.compatible: true`, the opposite of the truth. Now false. Test: 'review 6'.
