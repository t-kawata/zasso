# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Two things exist that do not today. **Pattern detection**: a mechanical function that reads the disk and returns exactly one of the four declared patterns, with the presence and absence it read. **Two more representatives**: a pattern-3 subject holding some conver artefacts and not the set, and a pattern-4 subject holding a specification and nothing else — so that the detection and the §1.2 invariant are exercised over all four patterns rather than over the two the repository happens to carry.

### Purpose
Design §1.1 defines the four patterns as distinguished "by **what conver scaffolding already exists on disk**, and by nothing else", and §5.4's Step 0 says identification happens by reading the disk — "Presence and absence are facts, read from the filesystem. The pattern must **not** be inferred by asking, and must **not** be a gate." §1.3 names the existing pair as the pattern-1 and pattern-2 representatives. Nothing names a pattern-3 or pattern-4 representative, and nothing detects a pattern at all.

### Motivation
**Measured**: the repository carries exactly two subject trees, `siprs-with-4layers` and `siprs-for-reverse`, and both are Rust and both are the same codebase in two states (design §1.3). So every claim about pattern 3 and pattern 4 is a design claim with no input behind it. This matters most for **pattern 3**, which §1.1 describes as the case where a project "holds some artefacts, not the set" and whose invariant obligation is the sharpest: §1.2 says none of the four may be blocked on the grounds that the project is an incomplete conver project, and pattern 3 *is* the incomplete-conver-project case. §5.8's two-mode table and §5.7's forbidden formulations both exist because the current design aborted exactly these subjects. Without a pattern-3 input, the invariant is a sentence in a document. Also measured: `run.mjs detect` reports forward-rotation traces (L1-L4), which is a different question from which pattern a project is; and `holdout isolation` refuses a pattern-2 tree by design (§7.1). Neither is pattern detection.

### Constraints
- Detection reads the filesystem and nothing else. It never asks, never writes, and never has a side effect. §5.4 Step 0's two prohibitions are the specification.
- Detection is **not a gate**. No value it returns may stop the run, and a test asserts that the published document set is identical across all four patterns. This is §1.2 measured rather than asserted.
- The declarations the detection is defined against are §1.1's own: root `RFC-*.md`, `*-GRAPH.json`, `*-Dirs-Tree.json`, `Tickets.json`, `DesignTree.json`; per-directory `RFC-SEED.md`; `WORKSPACIFY-*MANIFEST*`; and, for pattern 4, the presence of a long specification with no implementation. The lists are declared once, as data.
- The two new representatives are **subjects**, not fixtures with synthetic contents. They live under `tests/workspacify-reverse/fixtures/patterns/` and each is a directory a real run can be pointed at. They are small; the ticket states that they are representatives of the pattern rather than of a project's scale, and names what a fuller representative would need.
- The existing two trees are not modified, moved or renamed: they are P22's measuring instrument and the memory of this repository records them as not to be rewritten.
- Pattern 4's representative must genuinely be "empty, plus a long specification document" — no implementation, so nothing is reconstructed. §1.1's entry for pattern 4 says exactly that, and the entry point is `workspacify-tree` with no reverse rotation.

## Invariants

- [Normal condition] `detectPattern` returns exactly one of the four declared identifiers over any subject, and the returned presence and absence lists together account for every marker the declaration names for the patterns considered.
- [Error invariant] A subject matching no declared pattern — an empty directory, or one holding only unrelated files — is reported as an explicit no-pattern result naming every marker that was searched for, rather than being forced into the nearest pattern. ## Boy Scout Rule

- **The markers are data.** `PATTERN_MARKERS` is a frozen table keyed by pattern identifier, so detection iterates rather than branching on pattern names, and adding a marker is adding a string to a list. The alternative — four `if` blocks — is the shape that let the capability matrix's Rust row go stale.
- **Function names as verb phrases.** `detectPattern` detects, `renderPatternDetection` renders, `listPatternMarkers` lists. Each names what it does.
- **Variable names as domain concepts.** The locals are `present`, `absent`, `markersSearched`, `artefactPaths` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The four pattern identifiers and the no-pattern result are named constants read by both the detection and its tests, so the count asserted and the count produced cannot drift.
- **No error swallowing.** An unmatched subject produces a named no-pattern result rather than a default, and an unreadable root is reported by path rather than skipped. A default here would make an unclassifiable project read as pattern 1, which is the most permissive answer and therefore the most dangerous.
- **Boy Scout improvement outside this ticket's scope.** The fixtures directory currently holds four Rust fixture trees with no README explaining what each is for. This ticket adds a README to `tests/workspacify-reverse/fixtures/` naming each fixture, the one property it exercises, and — for the two new representatives — that they represent a pattern rather than a project's scale. Naming what each fixture is for is what stops a later ticket adding a fifth fixture that duplicates the fourth.

## Notes in Prior Implementation Rounds

- [Implementation steps] 1) Build the two representatives first, because the tests need them. 2) Write the failing tests: four detections, the set equality, the no-pattern result, the purity assertion and the published-key-set invariance. Every one fails red because no detection exists. 3) Implement `PATTERN_MARKERS` as data and `detectPattern` as a pure function over the artefact list. 4) Wire it into the R0 prefix and publish the document. 5) Re-run the R0-R2 suites over all four representatives.
- [Risks] The risk is a detection that classifies by proximity — "some artefacts" is a vague criterion and a small representative makes proximity tempting. The mitigation is C001's invariant requiring the presence and absence lists to account for every declared marker, so a proximity match would have to name markers it did not look for and would fail.
- [Caveats] Pattern 3's criterion is the least crisp of the four: "some artefacts, not the set". The declaration resolves it by naming which artefacts constitute "the set" — §1.1's root list plus §2.3's fifth-layer list — so the criterion is a set membership rather than a count. A subject holding four of the five root artefacts is pattern 3, and the detection states which one is missing.
- [Open items] Whether a pattern-3 project that has been partly driven through the reverse rotation should still detect as pattern 3 is not settled. The detection as specified answers "what scaffolding exists", which is what §1.1 says distinguishes the patterns; a project mid-rotation is a state the design does not name, and it is recorded here rather than resolved by invention.
- [Future improvements] Once P24-1's language representatives exist, the detection runs over trees in six languages, which is where a marker that is language-specific rather than conver-specific would show up — for instance a project whose only build manifest is a `CMakeLists.txt`.
