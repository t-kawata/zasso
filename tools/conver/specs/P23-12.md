# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-12: The §1.2 invariant audit: no gate in the reverse chain refuses incompleteness

**Ticket Key**: P23-12 · **Phase**: 23

## Background

### Goal
The design's §1.2 invariant stops being a sentence in a document and becomes a **measurement**. Every gate in the reverse chain is enumerated with its identifier, its family and its source location; every refusal reason a gate can produce is collected into a declared vocabulary; and both are audited against the invariant — **no gate refuses a run on the grounds that the subject is an incomplete conver project**. The audit is a test that runs on every test run, not a review that happens once.

### Purpose
Design §1.2 states it as the load-bearing sentence of the whole design: "**None of the four may be blocked or aborted on the grounds that the project is an incomplete conver project.** Incompleteness is the *input*, not a refusal condition. … Every gate, every precondition and every early exit in the reverse rotation has to be measured against it." §5.7 lists six formulations that violate it or its neighbours, each of which was tried and rejected while the design was written. §7.4 records the first of its four errors as exactly this: "**Designing the experiment protocol and making it a precondition.** Steps 0/2/6 of the first design (`holdout isolation`, `scrub`, `oracle compare`) abort exactly the projects the feature exists for."

### Motivation
The gates are declared in three places — `workspacify-tree/lib/reverse-mode.mjs` (`REVERSE_GATE_IDS = {T1..T6}`), `workspacify-allocate/lib/reverse-mode.mjs` (`REVERSE_GATE_IDS = {A1..A6}`) and the analyse path's gate families G4-G5, GF1-GF2, B1-B3, S1-S6 and §6.14.7 — and §2.4 tabulates them with their predicates. Nothing today reads that table against the code. The design's own §5.7 table has six rows, each a formulation that was actually written down before being removed, which is evidence about how easily the invariant is violated by a well-intentioned edit: every one of those six would have looked like a reasonable safety check to the person adding it. An invariant that lives only in prose is one more such edit away from being violated, and the failure it produces is silent — the project that most needs the reverse rotation is the one that gets refused.

### Constraints
- The audit **observes**; it does not add a gate. It must not be able to stop a run, and its own failure mode is a test failure rather than a runtime refusal.
- The gate families are read from the code, not restated. A second copy of the gate list would drift from the first — the shape the capability matrix's Rust row demonstrates.
- The representatives the audit runs over are the four from P23-11. Without them the audit is over two inputs and cannot see a pattern-3 refusal, which is the case the invariant is most about.
- The audit must distinguish a **refusal** from a **recorded disagreement**. Design §2.4: "Reverse-rotation gates sometimes PASS on 'the disagreement is recorded' rather than on 'the two agree' (T5, GF2, S2)." A gate that reports a disagreement and continues is not a refusal and must not be reported as one.
- The audit reads text as well as behaviour: §5.7's six formulations are strings, and the design's own record of them is that each was written in prose before being removed. A behavioural audit that never reads the refusal messages would miss a gate that refuses for the right reason with the wrong words, and a text audit that never runs the gates would miss an early exit no message describes.

## Boy Scout Rule

- **The formulations are data, and each is named.** `FORBIDDEN_REFUSALS` is a frozen table of `{ id, description, matches }` rows, so a finding names the formulation rather than quoting a regex, and adding one is adding a row. The design's §5.7 table and this constant then name the same six in the same order, and a test asserts the counts agree.
- **Function names as verb phrases.** `enumerateReverseGates`, `collectRefusalReasons`, `auditAgainstInvariant`, `classifyGateOutcome`, `renderInvariantAudit` — each names what it does, and the sequence reads as the audit it performs: enumerate, collect, audit, classify, render.
- **Variable names as domain concepts.** The locals are `declaredGateIds`, `enumeratedGates`, `refusalReasons`, `matchedFormulations`, `classification` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The gate families and the formulation identifiers are constants read by both the audit and its tests, so the count asserted and the count produced cannot drift.
- **No error swallowing.** An unreadable gate module is reported by path with its reason rather than skipped, and a gate with no refusal reason is classified as never-refusing rather than omitted from the classification. An omitted gate would shrink the audit's subject silently, which is the shape the audit exists to catch in the gates themselves.
- **Boy Scout improvement outside this ticket's scope.** `tests/workspacify-reverse/regression/rotation-gate.test.mjs`'s `fixture(name, lines)` helper writes a throwaway file and returns its path, and this ticket's new test needs the same thing. Rather than a second copy, this ticket moves `fixture` into `tests/workspacify-reverse/helpers/scratch.mjs` — which already exists for shared test helpers — and has both test files import it. The move is verified by `rotation-gate.test.mjs` staying green unchanged.
