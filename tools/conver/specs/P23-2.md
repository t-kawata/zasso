# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
R2's measurement gains the three quantities design §5.6 names as the ground the terminal structure stands on — **cohesion** (internal coupling against external coupling, per candidate directory boundary), **dependency density**, and **boundary-crossing call counts** — and they are published into `DEPENDENCIES.json`, rendered into `R0-R2-REPORT.md`, and served in prose immediately before Step 5's partition decision.

### Purpose
§5.6: because the terminal state is a per-directory re-instantiation of the four layers, **every downstream artefact is instantiated from the partition**. A wrong partition does not produce one wrong file; it produces a whole wrong structure, in every directory, at every level. `REVIEW-2` warned of exactly this: "if the boundary decision at R2 is wrong and R3-R8 run on top of it, everything is garbage — a hallucinated specification." The measurements are not decoration; they are what makes the decision answerable from material rather than from taste.

### Motivation
Measured on 2026-09-11: `grep -rln "measureCohesion|internalCoupling|externalCoupling|dependencyDensity" .claude/scripts/` returns **0 files**. The published `DEPENDENCIES.json` from the R8 probe carries the keys `analysis_mode, attempts, coupling_claim, coverage, cycles, declaredModules, edges, external, limitations, packages, represents_runtime_binding, runtime_binding_caveat` — and **no cohesion, no density, and no boundary-crossing call count**. Two neighbouring quantities do exist, which is why the absence is easy to miss: SCC condensation is real (`findPackageCycles`, `dependencies.mjs:166`, and the probe found 1 cycle), and co-change history is real (`HISTORY-PROVENANCE.json` carries `coChanges` with 12,403 entries and 963 commits). The design's §5.6 names three things and the instrument produces none of them. `ABOUT-REVERSE` §6.2 names the design home for two of them — `measure-cohesion.mjs` at 100% determinism and `measure-dynamic-coupling.mjs` at 80% — and neither file exists.

### Constraints
- `COUPLING_CLAIM = 'hypothesis'` (`dependencies.mjs:41`) is not upgraded, and `represents_runtime_binding: false` stays false. The measurement is static; E5 stays `partial` and never becomes `success`.
- Every quantity is a count with its population named. No composite score, no ranking, no threshold that reads as a verdict — the machine's vocabulary is `proved` / `not proved`, and a "cohesion score" is neither.
- R2 must remain runnable when R3 has not run: boundary-crossing **call counts** need R3's call sites, so the measurement degrades to "not measured, and here is why" rather than to zero. That is the F12 distinction the attempt ledger already exists to keep.
- The measurement must not read the tree it measures twice: it consumes the edges `measureDependencies` already produced and the structure `measureStructure` already produced, so the population cannot differ between two measurements of the same run.

## Acceptance Criteria

- **[Happy path] — Describe the scenario that confirms this ticket is complete:**
  - A run over a two-package fixture publishes a `DEPENDENCIES.json` carrying `cohesion`, `density` and `boundaryCrossings` with the exact expected counts; `R0-R2-REPORT.md` renders them as prose naming the packages, embedding `file:line`, and stating the question the reader must answer; and for every package `internalCoupling + externalCoupling === incidentEdges`.
- **[Error case] — Describe an error scenario the feature must handle:**
  - `analyze --through=r2` (R3 not run) publishes crossing rows with `measured: false` and a reason naming R3, and publishes no row with `callSiteCount: 0`. The distinction is asserted, so a run that could not measure a crossing never reads as a run that measured zero crossings.
- **[Edge case] — Describe any boundary or exception to verify:**
  - A package with one member file and no incident edges yields `externalRatio: null` rather than `0`, and a single-package project yields a density denominator of 1 rather than 0. Both edges are asserted directly, because both are places where a zero would read as a finding when the truth is an undefined quantity.

## Invariants

- [Normal condition] For every package in the run, `internalCoupling + externalCoupling === incidentEdges`, and the sum is asserted over every package rather than over a sample. `density` lies in the closed interval [0, 1] and equals zero if and only if `measuredEdges` is zero.
- [Error invariant] When R3 has not run and `callSites` is absent, `countBoundaryCrossings` reports each crossing as **not measured with the missing input named**, and never as a count of zero. "We could not measure it" and "we measured it and found none" are different facts, and merging them is failure F12 — the same rule `buildAttemptLedger`'s `extractedNothingCount` and `couldNotRunCount` already exist to enforce.
- [Internal state invariant] The measurement consumes the package set and edge set that R2 already produced and recomputes neither. Two measurements of the same run therefore cannot disagree about the population, and the cohesion identity holds against the same edges the dependency report renders.
- [Boundary invariant] A package with one member file and no edges yields `internalCoupling: 0`, `externalCoupling: 0`, `incidentEdges: 0`, `externalRatio: null` — null rather than zero, because a ratio over an empty denominator is undefined and writing it as zero would read as "no external coupling" when the truth is "nothing to divide".

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §5.6 → .claude/scripts/workspacify-reverse/lib/dependencies.mjs (measureDependencies)

- **Precondition**: A measured package set (from collectRustModules) and the measured edge set (from collectRustUses plus declared modules) are both present, and every edge names a source package and a target package that are members of that set.
- **Postcondition**: For each package, two counts are produced: the internal coupling (edges whose source and target are both in the package) and the external coupling (edges that cross the package boundary), each with the member files named, and the external-to-total ratio stated alongside both raw counts rather than instead of them.
- **Invariant**: For every package, internal coupling plus external coupling equals the number of measured edges incident to that package. The identity is asserted over every package in the run, so a measurement that dropped an edge fails rather than producing a smaller number that reads as cleaner.

### C002 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §5.6 (dependency density as the ground of the partition)

- **Precondition**: The package set and the edge set are present, and the package count is at least one, so that the number of possible ordered package pairs is defined.
- **Postcondition**: Dependency density is reported as the measured edge count divided by the number of possible ordered package pairs, with both the numerator and the denominator reported beside it, and with the population named (which packages, after which exclusions).
- **Invariant**: The reported density is always within the closed interval zero to one, and it is zero only when the measured edge count is zero — never when the measurement could not run, in which case the field states that it was not measured and names the missing input.

### C003 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §5.6 (boundary-crossing call counts) → R3 call-site material

- **Precondition**: The R3 semantic material is available, carrying call sites with their source file and the callee name, and the partition under measurement is the one R2 measured.
- **Postcondition**: For each boundary-crossing edge, the number of call sites in the source package that name the target of that edge is reported as a count, and each edge states whether the count came from call sites or was not measured.
- **Invariant**: A boundary-crossing edge with zero matching call sites is reported as a count of zero and never dropped from the output: a crossing whose calls the syntax layer cannot see is material for the gap list, and removing it would let an unmeasured crossing read as an absent one (F12).

## Boy Scout Rule

- **Function names as verb phrases.** The three new exports name what they do: `measureCohesion`, `measureDependencyDensity`, `countBoundaryCrossings`. The existing `findPackageCycles` follows the same pattern and is left alone; the new names are chosen to sit beside it without repeating the `find`/`measure`/`count` distinction ambiguously.
- **Variable names as domain concepts.** Inside the new functions the locals are `incidentEdges`, `crossingEdges`, `memberFiles`, `possibleOrderedPairs` — never `data`, `info` or `tmp`. The existing `measureDependencies` carries short locals (`records`, `files`, `parsed`) that are acceptable because each is used within a few lines of its declaration; the new functions keep that property rather than introducing longer-lived generic names.
- **Hardcoded values as named constants.** The interval endpoints and the not-measured marker become `DENSITY_MINIMUM`, `DENSITY_MAXIMUM` and `NOT_MEASURED` rather than inline `0`, `1` and `null`, so the boundary assertions and the implementation read the same constants.
- **One function, one responsibility.** `countBoundaryCrossings` counts; it does not decide whether a count is acceptable and does not filter rows. The filtering question — which crossings matter — belongs to the reader at Step 5, and a function that pre-filtered would be making the partition decision the design reserves for the AI.
- **No error swallowing.** The not-measured path returns a row with a reason rather than an empty array, and the null ratio is explicit rather than a falsy default. A caller cannot silently receive "nothing" where the truth is "not measured".
- **Boy Scout improvement outside this ticket's scope.** `renderDependencyReport`'s existing body builds its Markdown by string concatenation with inline section separators. This ticket extracts the section separator into a named constant and splits the report body into one function per section (`renderCyclesSection`, `renderPackagesSection`, `renderCouplingSection`), so the new subsection follows the same shape as the old ones instead of being appended as a special case. The refactor is verified by the existing report assertions staying green.
