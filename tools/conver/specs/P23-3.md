# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-3: N5 — the exit serves the layered decision cards, not a flat cap of one hundred

**Ticket Key**: P23-3 · **Phase**: 23

## Background

### Goal
`analyze`'s R7 serves the **layered decision cards** the spike calibrated, not a flat list capped at one hundred. `R7-SERVING.md` groups the unresolved claims by the levels design §7.4.1 names, states how many cards each layer holds, and states how many claims were withheld and why.

### Purpose
Design §6 records N5 as **a defect, not an absence**: "the exit serves a different shape from the one the spike calibrated". `renderDecisionCards` — layered, with `CARD_LAYERING_THRESHOLD = 12` — is called only from `runSpike` (`scope.mjs:265`). `analyze`'s R7 calls `renderServing` (`scope.mjs:1117`), which is flat and capped at `SERVING_LIMIT = 100` (`packet.mjs:313`). The design's own anti-decision-fatigue mechanism, failure mode F7, therefore does not operate at the exit. It operates only in the experiment that validated it.

### Motivation
**Measured** on `/tmp/wsp-r8-probe`: the ledger holds 3,714 unresolved claims and `R7-SERVING.md` says so in its own words — "100 unresolved claim(s) are set out below … 3614 further unresolved claim(s) were not printed here". The cap is honest, which is why the defect is easy to miss: the document states what it withheld. But stating a number is not the same as serving the material. The reader is handed the first hundred claims in `claim_id` order — an ordering that has no relationship to what a human needs to decide first — and told that thirty-six times as many exist. The instrument was calibrated for exactly this and the calibration is not in the path.

### Constraints
- The materials of the layering are the design's §7.4.1 rules, already implemented in `renderDecisionCards`: a scope with an `unresolved` boundary withholds its contract level whole; a scope whose boundaries are all settled hangs its contract level from **one** of them, never from every sibling; a scope with no boundary claim bundles its local conditions under the first of them.
- R7 must stay a **serving** stage: it decides nothing. It must not filter, rank or drop a claim. What changes is the shape and the ordering, not the population.
- The count of claims withheld must always be stated. `renderServing`'s existing discipline — a silent cap reads as "everything was considered" — survives the change.
- The machine may not say whether the engineering succeeded; a layered packet is material and carries no verdict.
- `runSpike` must keep working unchanged: it is the experiment that calibrated the shape, and a change that altered its output would destroy the calibration rather than apply it.

## Invariants

- [Normal condition] For every ledger, `servedCount + withheldFromServing === unresolvedCount`, and the layered packet's total card count equals `servedCount`. The two identities hold over the real probe ledger (3,714 unresolved) and over a synthetic ledger below the threshold.
- [Error invariant] A claim withheld by a layering rule is reported with the rule that withheld it and the scope it belonged to. A claim cannot be silently absent from both the served set and the withheld counts: the identity above is the mechanical guard, and it fails a run rather than shrinking the packet.
- [Internal state invariant] The analyze path and the spike path call the same selection function over the same ledger and produce the same card sequence. A test compares the two sequences element by element, so the shape the spike calibrated is structurally the shape the exit serves.
- [Boundary invariant] At exactly `CARD_LAYERING_THRESHOLD` claims the packet is flat and reports `layered: false`; at `CARD_LAYERING_THRESHOLD + 1` it is layered and reports `layered: true`. Both boundaries are asserted, because "exactly at the threshold" is where a `>` written as `>=` would change the shape without changing any count.

## Boy Scout Rule

- **One function, one responsibility.** `renderDecisionCards` today both selects the cards and decides the layering, and `renderServing` both selects and renders. This ticket extracts the selection into `selectServingCards` so that "which claims are served, and in what structure" is one function with one job, and the two callers differ only in what they do with the result. The extraction is behaviour-preserving and is proven so by the spike tests staying green.
- **Function names as verb phrases.** `selectServingCards` selects; `renderServingMarkdown` renders; `buildServedClaim` builds. The new name follows that pattern rather than introducing a noun-named helper.
- **Hardcoded values as named constants.** The layering levels are referred to by the names the design gives them (`boundary`, `contract`, `bundle`) held in a named constant, so the rendering and the selection agree on the vocabulary instead of both spelling the strings.
- **No error swallowing.** The withholding path returns a structured entry with its rule and its scopes rather than returning a count, so a caller cannot render "1,614 withheld" without also being able to render why. The existing refusal for a claim without a `grill_question` is preserved on the new path rather than being caught and skipped.
- **Boy Scout improvement outside this ticket's scope.** `renderServingMarkdown`'s body currently builds its output as one long array of lines with the counts interpolated mid-sentence. This ticket splits it into `renderPacketHeader`, `renderLayer` and `renderWithholdingNote`, each named after the part of the page it produces, so the Markdown reads as the document it is. The existing rendering assertions stay green and pin the wording that must not change.
