# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
The R0 stage gains a **mechanised eligibility assessment** over the subject population and publishes it, in the form `ABOUT-REVERSE` §3.6 requires: the six necessary conditions, the six danger signals, each with its evidence and its `file:line`, and — where a condition cannot be settled from source — a statement of what would settle it. It carries **no verdict**: no eligible flag, no score, no threshold. It is material for a human's decision about whether to start, not a gate on the run.

### Purpose
Design §6 records **N6** as *not implemented*: "`ABOUT-REVERSE` §3.6 requires the eligibility assessment to be mechanised and presented at R0; `REVIEW-2` Q1 specifies it. Nothing computes it." §3.6's own words are explicit about both halves — 「この評価自体を機械化し、`/workspacify-reverse` の R0 で提示すべきである」 and 「これは「成功するかどうかの判定」ではない——**人間が着手可否を判断するための材料**である」. The second half is why this is not a gate: §1.2 of the design forbids any gate that stops the run on the grounds that the subject is incomplete, and an eligibility gate would be exactly that in a different costume.

### Motivation
The design's §1.2 records the error it exists to prevent: treating *"not yet required"* as a licence for the thing to be absent at the end. The mirror-image error is treating *"this project may not be a good candidate"* as a refusal condition. §3.6 says the opposite: the assessment is presented so a human can choose between continuing and rebuilding from zero, which §4.1 records as the choice most often taken in practice. Presenting it at R0 — before the analysis runs — is what makes the choice available at the point where it is cheap. Today nothing computes it, so the reader of `R7-SERVING.md` has already spent the analysis before learning that no test exists and the history was squashed.

### Constraints
- **No verdict of any kind.** `capability-profile.mjs`'s header states the repository's rule for R8 — "There is no `eligible` field and no verdict of any kind. A score would look objective while encoding a threshold nobody chose (`ABOUT-REVERSE` 7.7.2)" — and the same rule binds R0. An `eligible: true/false` field is the shape this ticket must not produce.
- **No gate.** Nothing may branch on the assessment to abort, warn-and-stop, or refuse to publish. §1.2 is the load-bearing sentence of the whole design and the procedure built by P23-1 states it; a stage that could stop the run would contradict the file that describes it.
- **The evidence rule applies.** A condition settled from the source text is `source_static`. A condition that needs a build is `build_semantic`. A condition that needs the program to run is `runtime_dynamic`. §3.6's first two conditions — *builds* and *tests exist and can be run* — are build and runtime facts, and the analysis is read-only by construction (`scope.mjs:1128` refuses to publish if a byte moved). So those conditions are reported at the strength the static channel supports, with the stronger channel named as what would settle them.
- The stage runs inside the existing R0 prefix and must not change the evaluation order or add a stage name; it is part of R0's output, like the boundary and the scope.

## Boy Scout Rule

- **The six conditions are data, not branches.** Declaring `ELIGIBILITY_CONDITIONS` as a frozen table means adding a condition is adding a row, and the test that asserts six conditions present reads the same table the implementation iterates. The alternative — six `if` blocks — would let the count in the test and the count in the code drift, which is exactly the staleness that made the capability matrix's Rust row false.
- **The six signals are the same shape.** `DANGER_SIGNALS` is declared beside the conditions, each with its identifier, its question and the evidence it is read from.
- **Function names as verb phrases.** `assessEligibility` assesses; `renderEligibility` renders. The per-condition reader is `readCondition(condition, population)` and the per-signal reader is `readSignal(signal, population)`, so the call sequence reads as "for each condition, read it; for each signal, read it".
- **Variable names as domain concepts.** The locals are `artefacts`, `conditions`, `signals`, `dominantLanguage`, `largestDirectoryShare` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The three states (`established_statically`, `not_established_statically`, `not_measurable_statically`) and the forbidden key fragments are named constants, so the walk in the test and the construction in the module read the same list.
- **No error swallowing.** An unreadable evidence source is reported with its reason and never treated as absence, following `listArtefacts`'s established shape.
- **Boy Scout improvement outside this ticket's scope.** `scope.mjs`'s R0 block builds its stage results with the same three-line `stagesRun.includes(...) ? runStage(...) : null` shape repeated for each stage. This ticket extracts that into one helper (`stageResult(stagesRun, name, produce)`) and uses it for the new stage, leaving the existing call sites to be migrated by a later Boy Scout pass rather than in this ticket — the extraction is introduced where the new code needs it, which keeps this ticket's diff honest.

- [Open items] The danger signal for dominant metaprogramming depends on E6, which is `partial` for Rust and `not_attempted` for the other five languages today.
