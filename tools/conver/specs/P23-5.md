# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-5: N1a — generalise the measurement sandbox away from the siprs experiment

**Ticket Key**: P23-5 · **Phase**: 23

## Background

### Goal
`sandbox.mjs` stops naming one project. The subject root and the guarded production paths come from the caller; the start plan is produced from a **declared ecosystem registry** rather than a two-entry list; and the database kinds are discovered rather than enumerated. The experiment's own use is preserved by passing the paired trees explicitly, so `siprs-with-4layers` and `siprs-for-reverse` stay guarded where they must be.

### Purpose
Design §6 records **N1**: the sandbox, record-replay and dynamic-surface modules are unreachable from `run.mjs`, and R2.5's dynamic half is therefore absent. The design's stated home for that half is `measure-dynamic-coupling.mjs` (80% determinism, `ABOUT-REVERSE` §6.2), which does not exist. The naive fix — call the sandbox from R2.5 — would make the dynamic half work on exactly two Rust directories and nowhere else, because the module cannot name any other project. This ticket removes that limit first, so P23-6's wiring generalises by construction instead of inheriting the experiment.

## Boy Scout Rule

- **Data instead of branches.** `START_PLAN_ECOSYSTEMS` and `DATABASE_INDICATORS` are frozen tables the detector iterates, replacing a two-entry priority list and a two-entry kind list. The detector has no `if (ecosystem === 'cargo')` anywhere, which is the property that makes adding a language a data change.
- **Function names as verb phrases.** `resolveGuardedPaths`, `detectStartPlan`, `discoverDatabaseKinds`, `assertSubjectUntouched` — each names what it does, and the rename of `assertProductionUntouched` fixes a name that had become a lie once the guard stopped being about production trees.
- **Variable names as domain concepts.** The locals are `subjectRoot`, `guardedPaths`, `matchedManifest`, `searchedEcosystems` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The reason codes `sandbox-disposed` and `sandbox-unusable` are already named constants and stay so; the ecosystem identifiers become constants rather than inline strings, so a test and the registry read the same names.
- **No error swallowing.** A refused handle, an unreadable manifest and an unmatched subject each produce a named result with a reason. The generalisation must not introduce a `catch` that returns an empty plan, which would make "could not read" indistinguishable from "none present".
- **Boy Scout improvement outside this ticket's scope.** `sandbox.mjs` currently interleaves its constant declarations with long prose comments and its function definitions with private `WeakSet` declarations. This ticket groups the module into three clearly separated blocks — the declared vocabulary, the private token state, and the exported operations — and moves each block's rationale to the block it explains. The change is comment and ordering only; every export keeps its name and behaviour, verified by the existing sandbox tests staying green.

## RFC Discrepancies found in Prior Implementation Rounds

- Signature: the Scope section declared discoverDatabaseKinds(artefacts), but an artefact record carries path/kind/size/readStatus and no content, and C003 requires the kinds to be discovered from what the configuration artefacts name. Discovery therefore needs the subject root to read the manifests, and it is implemented as discoverDatabaseKinds(root, { indicators, artefacts }) with the artefact walk injectable and defaulted to analysis-tech listArtefacts(root). The declared behaviour of C003 and its unit cases are satisfied; only the shorthand signature differs.
- Scope wording: the Scope section said a caller declaring a guarded path outside the subject root is refused by name. The refusal is implemented for a RELATIVE declaration that escapes its subject, while an absolute guard is taken as declared. P22-19s worktree suites guard a tmpdir beside the subject (mkdtempSync under tmpdir()), and a blanket refusal would have broken all 21 of them, whereas the same Scope section expects those suites to change only by the option rename. Refusing the relative escape keeps the error case real without removing the ability to guard a tree beside the subject; the rule and its reason are stated in resolveGuardedPaths own comment.

Design decisions beyond the ticket text, stated for review:
1. resolveGuardedPaths refuses only a RELATIVE declaration that escapes the subject; an absolute guard is taken as declared. The P22-19 worktree suites guard a tmpdir beside the subject (mkdtempSync under tmpdir()), and a blanket refusal of outside guards would have broken all 21 of them, while the ticket expects only an option rename. Refusing a relative escape keeps the error case real without making the API unable to express what P22-19 built.
2. digestMainTree loses its default parameter rather than gaining a subject-aware one: a default parameter cannot see the caller subject root, and no call site omitted the argument, so the old default encoded the experiment without ever running.
