# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-6: N1b — R2.5's dynamic half: the static/dynamic coupling difference and rule R-1

**Ticket Key**: P23-6 · **Phase**: 23

---

## Background

### Goal
R2.5 gains its **dynamic half**: the mechanisms the static reading lists are exercised in a disposable sandbox, the result is recorded as `runtime_dynamic` evidence, the **difference between the static and the dynamic surface** is computed and published, and rule **R-1** is enforced — a claim whose statement touches a dynamic mechanism and whose evidence is only `source_static` is demoted to `inferred` or `unresolved`, never left as `observed`.

### Purpose
Design §6 records **N1**: `sandbox.mjs`, `record-replay.mjs` and `dynamic-surface.mjs` are unreachable from `run.mjs`, and R2.5's dynamic half is therefore absent. Its design home is `measure-dynamic-coupling.mjs` (80% determinism, `ABOUT-REVERSE` §6.2), which does not exist. What is lost is stated in the design's own words: "**Measured**: the capability profile reports 792 activation mechanisms, all read statically, and says of the rest — 'Mechanisms that leave no static trace … are invisible to a static reading and are not counted above.' Rule R-1 therefore fires wherever a mechanism is listed and `observed` is never reached there."

### Motivation
`ABOUT-REVERSE` §5.5 states the rule this ticket makes mechanical: `observed` "may only ever mean *a fact read from the source text or its syntax tree*. Runtime behaviour, dynamic dispatch targets and generated code are not `observed` without execution, build or trace evidence, so every evidence item carries `evidence_mode`." `ANALYSIS-TECH` §7 repeats it as a build instruction: "`observed` is a narrow word … Anything that depends on what runs needs `runtime_dynamic` evidence, and the guard is mechanical." Today the guard is not mechanical and the channel does not exist, so 792 activation mechanisms are listed and none of them can ever reach `observed` — the analysis is structurally unable to promote them, and equally unable to say which of them it actually looked for at run time.

### Constraints
- The analysis is read-only over its subject: R2.5's execution happens inside a sandbox or a disposable worktree, never in the subject tree. `scope.mjs:1128` refuses to publish when a byte of the subject moved, and the sandbox generalised by P23-5 is what makes "a copy was changed, the original was not" checkable.
- Nothing here may reach the network or a daemon. The sandbox's own comment bounds the start plan: "Both commands are bounded, offline and need no daemon."
- `EVIDENCE_MODES` is the existing three-value vocabulary and is not extended. `UNOBSERVED_CHANNEL_KINDS` and `DYNAMIC_CONSTRUCT_KINDS` are the existing declarations of what a dynamic channel is and are consumed rather than re-invented.
- R-1's demotion is a change of `claim_type`, not a deletion. A demoted claim keeps its statement, its evidence and its `grill_question`, because §4 of the design records that `unresolved` claims are the raw material the chain downstream consumes.
- When no execution is possible at all — no start plan, no sandbox, no permission — the stage must report that the dynamic channel did not run and must not report an empty difference as agreement. The design's §2.4 rule applies: "A difference of zero, or a disagreement of zero, can be a signal of abnormality rather than of health (F1)."

## Invariants

- [Normal condition] For every activation mechanism in the static list, the published record carries exactly one of the three states — observed dynamically, not exercised in this session, or not reachable by this channel with a reason — and the three counts sum to the static list's length.
- [Error invariant] When no execution was possible, `dynamicChannel.ran` is `false` with the reason, and `difference` is published as three empty sets with their counts, not as an agreement. The document states in its own prose that an unrun dynamic channel has looked at nothing and that the empty `dynamicOnly` set is therefore not evidence that no mechanism hides from the static reading.
- [Internal state invariant] The subject tree is byte-identical after the measurement: the session ran inside the sandbox copy, and `assertSubjectUntouched` compares the subject's digest before and after. The run's own before-and-after digest at `scope.mjs:1128` is the second, independent check.
- [Boundary invariant] R-1's demotion is total over its predicate: a claim that depends on a dynamic mechanism with only `source_static` evidence is demoted, and a claim with no dynamic dependency is not. Both directions are asserted, so the rule neither under- nor over-fires — a rule that demoted everything would empty the ledger of `observed` claims and read as a clean, wrong result.

## Boy Scout Rule

- **The measurement is three steps, named as three functions.** `observeDynamically(...)` runs the session and builds the record, `diffSurfaces(staticMechanisms, dynamicRecord)` computes the three sets, and `demoteObservedDynamicClaims(ledger)` enforces R-1. The call sequence reads as the sentence it is: observe, diff, demote. A single function doing all three would be untranslatable and untestable in parts.
- **Function names as verb phrases.** `measureDynamicCoupling`, `observeDynamically`, `diffSurfaces`, `demoteObservedDynamicClaims`, `renderDynamicCoupling` — each names what it does.
- **Variable names as domain concepts.** The locals are `staticMechanisms`, `dynamicRecord`, `unmatchedMechanisms`, `demotedClaims`, `sessionScope` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The three mechanism statuses and the three difference-set names are declared as frozen constants read by both the implementation and the tests, so the partition sum's operand and the assertion's expectation cannot drift.
- **No error swallowing.** A failed session, an invalid dynamic record and a failed replay each produce a named reason rather than an exception that stops the run or a catch that returns an empty difference. The distinction between "the channel did not run" and "the channel ran and found nothing" is carried by `ran` and is asserted.
- **Boy Scout improvement outside this ticket's scope.** `EXECUTION-SURFACE.json`'s existing `attempts` array is currently concatenated with the structure and dependency attempts at `scope.mjs` in a single expression with three spreads. This ticket extracts the assembly into `buildAnalysisAttemptLedger(...)`, named once, so the three sources and the new dynamic source are gathered in one readable place rather than in a widening expression. The existing assertions about the ledger stay green.

  - [Item] Whether the dynamic channel's session exercises enough of the program for its negative results to be meaningful.
  - [Reason] It is impossible to test this: how much of a program a bounded offline start plan reaches depends on the program, and no fixture population bounds it. This is not a design defect and not an architectural defect: the design answers this by never making the dynamic channel's silence a finding — C001's invariant asserts that a mechanism the session did not exercise is recorded as not-exercised rather than as absent, and C002's prose assertion states that an empty `dynamicOnly` set is a signal rather than a clean result. Both are deterministic and both are tested. What is untestable is the adequacy of one session, and the instrument's answer is to report its scope rather than to claim coverage.
  - [Alternative verification] The mechanical half is verified: the status partition sums to the static list, the three difference sets are disjoint and cover the union, R-1's demotion is total over its predicate and fires in neither direction beyond it, and the subject is byte-identical afterwards. The adequacy half is verified by the record stating which transitions the session performed, so a reader can see the session's scope and weigh it.
