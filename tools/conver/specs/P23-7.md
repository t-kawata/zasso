# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-7: N2 — R6.5's executor: the counterexample channel actually falsifies

**Ticket Key**: P23-7 · **Phase**: 23

## Background

### Goal
R6.5 stops falsifying nothing. The counterexample set is **derived from R6's Red reconstruction plan** rather than passed as a literal empty array, each counterexample is **executed inside a disposable git worktree**, and the result records `proved` / `not-proved` per counterexample with the status `executed` or `nothing-to-execute`. A counterexample that could not be executed is recorded with its reason; it is never dropped.

### Purpose
Design §6 records **N2**: "`scope.mjs` calls `applyCounterexamples([], ledger)` with a **literal empty array**. **Measured**: `COUNTEREXAMPLE-RESULTS.json` is `{empty: true, applied: []}`. The falsification stage falsifies nothing." Its design home is `worktree-isolation.mjs` (`ABOUT-REVERSE` §9 design problem 3, recorded as **unfinished**).

### Motivation
The whole reverse rotation rests on Red. `ABOUT-REVERSE` §3.5 records that a reconstruction ticket exists so that "the Red that `/start-ticket`'s Red phase demands can be reconstructed after the fact", and `conver/red-reconstruction.js` was built by P22-19 for exactly that: it isolates an existing implementation in a worktree, breaks it on purpose, and observes whether the test fails. But nothing in the analysis path ever calls it. The measured §4 of the design records `COUNTEREXAMPLE-RESULTS.json` as `{empty: true, applied: []}` over a run of 4,460 claims and 9,748 gaps — the falsification stage is present in the pipeline, publishes a document, and has never falsified anything. A stage that runs and produces nothing is worse than an absent stage, because its output reads as a result.

### Constraints
- The analysis is read-only over its subject. Execution happens in a disposable git worktree created by `worktree-isolation.mjs`, which digests the main tree before and after and refuses if it moved. The run's own before-and-after digest at `scope.mjs:1128` is the second, independent check.
- The vocabulary is fixed and already declared: `RED_PROVED = 'proved'`, `RED_NOT_PROVED = 'not-proved'` (`RED_VERDICTS`), and `PASS_STATUSES = ['executed', 'nothing-to-execute']`. "Succeeded" and "failed" remain unavailable to the machine (`ABOUT-REVERSE` §3.3).
- A ticket is a reconstruction ticket if and only if it carries `counterexample_plan_id` (`RECONSTRUCTION_PLAN_FIELD`). `assertReconstructionTicket` refuses one that does not, and that refusal is repeated at the analysis path rather than assumed from upstream — its own comment says why: "the alternative to running a ticket isolated is not running it at all, and a ticket with no plan would carry its uncertainty straight into implementation."
- Zero counterexamples is an explicit result, not a vacuous success: `executeReconstructionTickets`' own comment states "Nothing needed reconstructing" and "everything was reconstructed" are different claims.
- The empty-input discipline `scope.mjs:1103` already documents survives: a stage that ran nothing must not read as a stage that found nothing. What changes is that the input stops being *manufactured* empty and starts being *derived*.

## Invariants

- [Normal condition] Every counterexample derived from R6's plan appears in the published result exactly once, carrying a verdict from `RED_VERDICTS` and a pass status from `PASS_STATUSES`, or a refusal carrying its `RED_REASONS` code. The published entry count equals the derived count.
- [Error invariant] A counterexample that could not be executed is refused with its reason code and stays in the set. `plan-id-missing`, `executor-missing` and `invalid-execution-result` are the three declared reasons and no fourth is introduced; a refusal is never rendered as a not-proved verdict, because "we could not test it" and "we tested it and it held" are different facts.
- [Internal state invariant] The main tree is byte-identical after the pass. The isolation's own before-and-after digest and the run's digest at `scope.mjs:1128` are two independent checks, and both must pass. The disposable worktree is destroyed or its destruction is recorded as failed with the reason.

The two emptinesses are distinguishable from the published document alone, which is the property the current literal destroys.

### C004 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §2.4 (an unrecorded inconsistency is the contradiction) and §4 (gaps are raw material)

- **Precondition**: A derived counterexample was refused before execution, or was executed and its observation could not be interpreted — its plan identifier was absent, its executor was missing, or its execution result was invalid.
- **Postcondition**: The counterexample remains in the published set carrying the reason code from the declared vocabulary (`plan-id-missing`, `executor-missing`, `invalid-execution-result`), and the count of refused counterexamples is stated separately from the count executed.
- **Invariant**: No counterexample is dropped from the published set: the number of entries in the published result equals the number derived from the plan, whatever happened to each. The equality is asserted, so a refusal cannot shrink the record and read as a smaller, cleaner stage.

## Boy Scout Rule

- **Three steps, three verbs.** `deriveCounterexamples` derives, `runCounterexamples` runs, `applyCounterexamples` applies. The call site at `scope.mjs:1103` then reads as the sentence it is — "derive the counterexamples from the plan, then apply them to the ledger" — instead of passing a literal whose emptiness needs a paragraph of comment to justify.
- **Function names as verb phrases.** The three above, plus `refuseCounterexample` for the refusal path, each naming what it does.
- **Variable names as domain concepts.** The locals are `derived`, `executed`, `refused`, `observation`, `reasonCode`, `worktreeRecord` — never `data`, `info` or `tmp`; `applied` in the published document keeps its existing name because consumers read it.
- **Hardcoded values as named constants.** The two verdicts, the two statuses and the three reason codes become constants re-declared in the analysis layer's own vocabulary rather than string literals, with a test asserting the two declarations name the same values as the conver layer's — so the vocabularies cannot drift while the layer direction keeps them separate.
- **No error swallowing.** The refusal path records and continues; it does not catch and discard. A thrown executor is converted into a recorded refusal with its message, never into a silent absence.
- **Boy Scout improvement outside this ticket's scope.** `scope.mjs:1103`'s counterexample block and the property block immediately below it are two near-identical `stagesRun.includes('r6.5') && ledger !== null ? runStage(...) : null` expressions whose only difference is the production function. This ticket extracts a named helper for the pair — `runR65({ stagesRun, ledger, redPlan })` returning both — so the stage's two halves are built together in one readable place, and the existing assertions about both documents stay green.

### Exceptions

- **Exception entry (copy this block for each non-testable item):**
  - [Item] Whether a counterexample that reports `proved` is genuinely un-falsified rather than merely un-executed.
  - [Reason] It is impossible to test this with the instrument: distinguishing "the counterexample ran and the claim held" from "the counterexample ran in a way that could not have failed" requires an oracle the analysis does not have, and `REVIEW-2`'s oracle-collusion concern is recorded in the design's ladder as the L2.5 condition.
