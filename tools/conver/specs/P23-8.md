# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
R7 publishes **two more lanes** that today exist as code with no caller: the **security lane** (`classifySecurityLane`, `renderLaneReport`) and the **adjudication cards** (`renderAdjudicationCards`). Both become reachable from `analyze`, both publish a document, and both keep the disciplines their own modules declare — lanes separate from one another, authority recorded, canonisation blocked where falsification is thin, and no candidate lost between the physical and the logical partition.

### Purpose

### Constraints
- R7 decides nothing. Both lanes **present** material; the adjudication itself is an AI judgement (`ABOUT-REVERSE` §6.2 item 1: the final determination of the package boundary), and the security lane's canonisation block is a refusal to canonise, not a decision to reject.

- §2.4 of the design governs the output: "A contradiction is an *unrecorded* inconsistency. A recorded inconsistency is not a contradiction." A logical/physical mismatch that the cards surface must be **recorded**, and `assertNoCandidateLost` exists precisely so that surfacing cannot become dropping.
- Neither lane may block the run. `blockCanonisation` blocks a *claim* from being canonised; it does not stop the stage. A lane that could stop the analysis would be the gate §1.2 forbids.
- P23-3 changed R7's shape from flat to layered. Both new lanes render through the same packet discipline: the counts are stated and nothing is withheld silently.

### C004 — docs/WORKSPACIFY-4-PATTERNS-COMPLETE-DESIGN.md §2.4 (a recorded inconsistency is not a contradiction, and a zero difference can be a signal)

- **Precondition**: The cards carry mismatch kinds, and the published document states the count of each kind.
- **Postcondition**: Every logical/physical mismatch is recorded with the candidate it belongs to and the kind of the mismatch, and the document states the count of each kind and the count of cards carrying no mismatch.
- **Invariant**: The recorded mismatch count equals the derived mismatch count: the number of mismatch entries in the published document equals the number deriveMismatches produced over the same candidates. A mismatch cannot be dropped in rendering, and a zero difference is published with the statement that it is a signal rather than a clean result.

- **One rendering discipline, one implementation.** The "state what you withheld and why" rule now appears in three R7 documents. This ticket extracts `renderWithholdingNote` into `packet.mjs` and uses it in all three, so a fourth document added later inherits the discipline instead of reimplementing it — and so the three cannot drift into stating different things.

- **Variable names as domain concepts.** The locals at the wiring site are `classification`, `candidates`, `publishedCards`, `withheldReason` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The two new document names are named constants beside the existing `R7-SERVING.md` name, and the assertions are called with the module's declared vocabularies rather than with string literals repeated at the call site.
- **No error swallowing.** The two assertions run on the path and throw rather than logging a warning; a lane whose separation property fails must not publish. Conversely, a blocked claim and a withheld card are recorded and the run continues — the distinction between "this document is wrong" and "this claim is blocked" is carried by which of the two happens.

### Exceptions

- **Exception entry (copy this block for each non-testable item):**
  - [Item] Whether a published adjudication card set actually helps a reader pick the right partition, and whether a blocked canonisation was the right block.
