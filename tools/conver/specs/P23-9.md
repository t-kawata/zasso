# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P23-9: Pattern 2's bookkeeping: the interrupted cycle's in-flight work and the seam

**Ticket Key**: P23-9 · **Phase**: 23

## Background

### Goal
Pattern 2's two obligations are discharged. First, **work in flight**: when a running four-layer cycle is interrupted and the boundaries are redrawn, every non-terminal ticket of the old `Tickets.json` is either **re-homed** under a package of the new partition or **named as re-homed-nowhere** with its key and its lifecycle status. Second, **the seam**: the old partition and the new partition differ, the difference is **recorded** rather than eliminated, and it is recorded in the receptacle that fits a discontinuity rather than one that fits an increment.

### Purpose
Design §3.3: "A cycle that was running has unfinished work: tickets at `planned` or `in_progress`, a phase partway implemented, a `DesignTree` mid-drill. Re-partitioning redraws the boundaries underneath that work, so **in-flight items can end up belonging to no package in the new partition**. This must not be silent. … **This obligation is not currently discharged anywhere in the code** — see §7.2." Design §7.2 confirms the measurement: "`reverse-split.js:590` reads the existing `Tickets.json` for its **declared key set only** (`readDeclaredTicketKeys`). No ticket lifecycle status is consulted. Line 525 writes a **new** ledger into `--out`. S1-S6 address *tests without tickets*; they do not address *tickets with work in flight*. **The two are different populations, and only the first has a gate**."

### Motivation
§3.2 states what the old artefacts become: material, the old partition, and the prior against which the new partition's difference is taken — and "the last row is the one that bites. Reading the old `RFC-ROOT-Dirs-Tree.json` as *the* partition would freeze the too-coarse boundaries into the new canon — that is failure mode **F3** (boundary mis-estimation) in its most expensive form, because the whole reason the act was taken was that those boundaries are wrong." §3.4 names the two receptacles and their owners — `ARCHITECTURE-DELTA.json` belongs to the reverse rotation (T5) and `<X>.json.delta.json` to the evolution loop — and §7.3 records the open question: "Whether the pattern-2 structural discontinuity can be expressed through the existing `.delta.json` mechanism, or needs a record of its own." This ticket answers that question by measurement and then implements the answer.

### Constraints
- The old artefacts are **not deleted and not rewritten**: `RFC-ROOT.md`, `RFC-ROOT-GRAPH.json`, `RFC-ROOT-Dirs-Tree.json`, `Tickets.json`, `DesignTree.json` and the `*-Status.json` files stay where they are. §3.2.
- The old `RFC-ROOT-Dirs-Tree.json` is read as a **prior**, never as the partition. The new partition is decided by the procedure's Step 5, and the old one is only ever a column in a comparison.
- The written record follows §2.4's definition: "A contradiction is an *unrecorded* inconsistency. A recorded inconsistency is not a contradiction." T5's gate passes on "the disagreement is recorded" rather than on "the two agree".
- Adding a ticket lifecycle read to `reverse-split.js` must not change S1-S6's behaviour over the tests-without-tickets population. The two populations are measured separately and the report states both.
- The write allow-list is unchanged: on the subject, additions are limited to `RFC-SEED.md` and the manifest (A2). The re-homing record and the seam record are published to `--out`, outside the subject, exactly as every other analysis document is.

## Boy Scout Rule

- **Two populations, two names.** `readDeclaredTicketKeys` and `readTicketLifecycles` read the same document for two different questions, and the names say which. The alternative — one function returning both — would let a caller pass the lifecycle data where the key set was expected, which is the confusion §7.2 records.
- **Function names as verb phrases.** `readTicketLifecycles`, `planInFlightRehoming`, `buildLayerStructureSeam`, `classifyPartitionDifference` — each names what it does, and the call sequence reads as the accounting it performs.
- **Variable names as domain concepts.** The locals are `ticketLifecycles`, `rehomed`, `rehomedNowhere`, `owningPackage`, `oldPartition`, `newPartition`, `differenceClass` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The five difference classes and the terminal-status set are declared as frozen constants read by both the classifier and its tests, so the vocabulary cannot drift between the count and the assertion.
- **No error swallowing.** A ticket that cannot be attributed is reported with its reason rather than defaulted to the root package; a status that is absent is reported as absent rather than defaulted to terminal. Both defaults would turn a loss into a clean count.
- **Boy Scout improvement outside this ticket's scope.** `serializeTicketSet` currently returns a flat object literal of eight keys mixing identity (`root`, `stage`, `language`), counts (`mappingCoverage`, `absenceCount`) and collections (`tickets`, `refused`, `unclassified`). This ticket groups it into `{ subject, coverage, gates, tickets, inFlight }` while keeping every existing key at its existing path, so the new block has an obvious home and the existing consumers are unaffected. The existing reverse-split assertions pin the old paths.

### Exceptions

- **Exception entry (copy this block for each non-testable item):**
  - [Item] Whether the re-homing attribution — "the package that owns the files this ticket names" — is the right home for a ticket whose work spans a boundary the new partition redrew.
  - [Reason] It is impossible to test this: a ticket can legitimately name files that the new partition puts in two packages, and which package inherits the work is a design decision of the same kind as the partition itself, which `ABOUT-REVERSE` §6.2 reserves for the AI. This is not a design defect and not an architectural defect: the *accounting* is fully deterministic and is asserted by C001 — every non-terminal ticket appears exactly once, re-homed or named as re-homed-nowhere, and the counts reconcile; a ticket whose files span packages is reported with both packages rather than being forced into one. What is untestable is whether the attribution is the right one, and the design's answer is that the record is material for the operator's decision, which §3.3 asks for in exactly those words: "Either the work is re-homed under the new partition, or it is named as re-homed-nowhere."
  - [Alternative verification] The mechanical half is verified: the counts reconcile, no ticket is dropped or double-counted, a spanning ticket names every owning package, a ticket naming no file is named with that reason, and the two populations stay separate. The judgement half is surfaced by the record naming each package a spanning ticket touches and stating the question, so the operator decides with the material in front of them.
