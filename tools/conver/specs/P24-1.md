# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Five frozen subject trees exist beside the two siprs trees — one each in TypeScript, JavaScript, Go, Python and C/C++ — each a real project with a build manifest, a test suite, a directory structure deep enough for a partition to be non-trivial, and a pinned revision. They are the population every later ticket in this phase measures against, and they are declared in one place so that "which languages have we exercised?" is answerable from a file rather than from memory.

### Purpose
Design §1.3 names the two siprs trees as the pattern-1 and pattern-2 representatives. They are also, today, the whole language population: **measured**, every fixture under `tests/workspacify-reverse/fixtures/` is `.rs` only — `sample-project` 10 files, `r3-subject` 5, `mixed-l3-project` 2, `unclosed-header-project` 1 — and `structure.mjs:67` declares `LANGUAGES_WITH_EXTRACTORS = Object.freeze(['rust'])`. ### Motivation
The instrument's own report states the situation in its own words. `R0-R2-REPORT.md`'s `## Language coverage` section reads: "`rust` — 33165 fact(s)" and then "Not exercised by this population: `typescript`, `javascript`, `go`, `python`. The vocabulary for these is declared and its correctness is unverified here — an untested table, not an absence of the material in the project." That last clause is the correct reading and also the reason this ticket exists: an untested table is a liability, and the only way to test it is to run it over material. `P22-ANALYSIS-TECH.md` §7 states the direction for the phase: "Publish gaps; do not hide them. The matrix has five values so that a gap can be recorded as a property of the instrument. **Adding a language means adding a row-ful of honest cells**, not deleting the ones that read badly."

### Constraints
- The two siprs trees are **not** modified, moved or renamed. They are P22's measuring instrument and this repository records them as not to be rewritten. The five new trees are additions, and the existing two are added to the declaration rather than re-created.
- Each representative carries a **pinned revision** and a tree digest, following the instrument's own rule that the record that matters is the combination of tool version, target-tree hash, OS, architecture and the full command line (`P22-ANALYSIS-TECH.md`, "Tool version pinning alone is insufficient").
- A representative is chosen for the **constructs it contains**, not for its size. Each one must carry at least one construct that the later tickets' extractors are specified to find — for TypeScript a re-export and a declaration merge; for JavaScript a computed property name and a dynamic `require`; for Go a build tag and an embedded struct; for Python a decorator and a metaclass; for C/C++ a macro and a conditional compilation block.
- A representative that cannot be built offline is reported with that fact rather than dropped. §5.8's two-mode separation means an unbuildable representative is still a valid subject for the static measurements and an invalid one for the execution channels, and the declaration says which.
- The representatives are for the **instrument's** validation. They are not the experiment's input: `siprs-for-reverse` remains the experiment subject and the four pattern representatives remain that audit's input. The three populations are named separately.

## Boy Scout Rule

- **The population is data.** `LANGUAGES.json` is a single declaration read by every later ticket, so "which languages have we exercised?" is answered from one file rather than from a directory listing. The alternative — tests hardcoding paths — is what would let a language be dropped by being dropped from one test file at a time.
- **Function names as verb phrases.** The declaration's reader is `loadLanguageRepresentatives()` and its verifier is `verifyRepresentative(entry)`; both name what they do, and the call sequence reads as "load the representatives, verify each".
- **Variable names as domain concepts.** The locals are `representatives`, `treeDigest`, `pinnedRevision`, `declaredConstructs`, `dominantLanguage` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The construct markers per language are named constants read by both the declaration and its verification, so a marker's spelling cannot drift between the tree and the declaration.
- **No error swallowing.** A digest mismatch, a missing construct and an unbuildable representative each produce a named finding. A missing `offline` flag is treated as an error rather than as "assume buildable", because an assumed-buildable representative would be handed to an execution channel that cannot run it.
- **Boy Scout improvement outside this ticket's scope.** `tests/workspacify-reverse/fixtures/` currently has no README, so a reader cannot tell what `mixed-l3-project` or `unclosed-header-project` is for. This ticket adds a README naming every fixture and the one property it exercises, and pointing at `languages/LANGUAGES.json` for the language population — so the fixtures directory describes itself rather than requiring a grep through the tests that use it.

### Exceptions

- **Exception entry (copy this block for each non-testable item):**
  - [Item] Whether five small representatives are an adequate population for validating six-language extraction.
  - [Reason] It is impossible to test this: adequacy is a claim about coverage of the constructs that occur in real projects, and `P22-ANALYSIS-TECH.md` §6 records that the adequacy of a 50k-LOC corpus is one of the items §7 explicitly did not verify, so no measured threshold exists to test against. ## Notes in Prior Implementation Rounds

- [Implementation steps] 1) Build the five representatives, each carrying the constructs the later tickets' specifications name. 2) Write the declaration by reading each tree, not by hand, so the digest and the construct lines are measured rather than transcribed. 3) Write the failing tests: the set equality, the digest reproduction, the construct markers, the population disjointness. 4) Add the grammar entries to `ENV-DEPS.json`. 5) Re-run the reverse suite over the six to confirm the runs complete.
- [Risks] The highest risk is a representative written to match the extractor that will be built for it — a fixture that is easy to parse rather than representative. The mitigation is that the constructs are named in the declaration *before* the extractors exist, and each is a construct the language's own specification names as syntax-invisible in the sense the capability matrix records. A representative chosen for convenience would have to name a construct it does not contain, which the `file:line` assertion catches.
- [Caveats] The representatives are the instrument's validation population, not the experiment's. `siprs-for-reverse` against `siprs-with-4layers` remains the experiment, and the four pattern representatives remain P23-12's audit input. Three populations with three purposes, and the declaration says which is which.
- [Open items] The scale question is open: five small trees exercise constructs, not volume. If a later round needs a volume measurement, the declaration's shape accommodates a second representative per language, and the set equality would become a coverage assertion rather than a one-to-one one.
- [Future improvements] Once P24-7 derives the matrix from the ledger, the derivation reads which representatives were attempted and the declaration's construct list becomes the explanation for each `partial` cell — the reason a reader can act on rather than a bare value.
