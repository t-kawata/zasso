# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-10: The four structures converge: the observation taken and recorded

**Ticket Key**: P24-10 · **Phase**: 24

## Background

### Goal
Design §7.3's unverified claim stops being a claim. The three-command chain is driven to the terminal state over the four pattern representatives, the terminal structures are measured against §2.3's inventory, compared dimension by dimension, and the outcome is recorded with the ladder position and the material a human needs to judge it.

### Purpose
§7.3 records it in its own words: "Nobody has ever observed a project reaching the terminal state through the reverse rotation. Every statement in §2 is a design claim, not a measurement. This is the thing the design is for, and it is unmeasured." P24-8 built the instrument that measures it and P24-9 makes the chain reach it. This ticket is the measurement.

### Motivation
The instrument exists and is tested: `measureTerminalState` checks a tree against §2.3's declared list element by element, `compareTerminalStates` reports every dimension for every representative including the zeroes, and `renderTerminalStateReport` states the outcome in the machine's own vocabulary. What has never happened is a run of the whole chain producing a terminal state for the measurement to read. That is what this ticket takes.

### Constraints
- The outcome is `proved` or `not proved` and nothing else, and only L3 may be called success, which is a human's judgement after several rounds. One round is the command plus the whole downstream chain.
- `omission 0` is material for that judgement and is not the success condition.
- A difference is recorded, not removed. A difference of zero is reported as a signal rather than as health.
- Every representative is driven over a scratch copy, and each representative is asserted byte-identical afterwards.
- A representative that cannot reach the terminal state is reported as not proved for that representative while the others' observations stand.

## Acceptance Criteria

- [Happy path] The chain runs over all four representatives, each either reaches the terminal state or names the stage that refused, the comparison reports the package paths, artefact names and gate outcomes per representative with every difference recorded, and `TERMINAL-STATE.json` is written and committed with the ladder position and the decisions digest.
- [Error case] A representative whose chain still refuses is reported as not proved for that representative with the stage named, while the others' observations stand. A representative whose frozen decisions input is absent is refused by name rather than run with defaults. A full-depth walk of the record finds no verdict key and the report contains no line claiming success except the one that denies it.
- [Edge case] Two identical terminal structures produce a report that states the agreement rather than a clean run. A representative carrying no prior partition reaches the state with a delta saying no prior existed. Every representative is byte-identical after the whole chain.

## Invariants

- [Normal condition] Each of the four representatives reaches the terminal state or names the stage that refused, and the terminal inventory matches §2.3's list element by element.
- [Error invariant] No stage is worked around: a refusal is reported with its stage and its input, and a representative that cannot reach the terminal state is recorded as not proved while the others' observations stand.
- [Internal state invariant] No representative is modified: each subject's digest before and after the whole chain is equal, and the oracle tree is never written to.
- [Boundary invariant] A difference of zero is reported as a signal rather than as health, and a recorded difference is not a contradiction: the record distinguishes agreement from a difference and reports both rather than one.
