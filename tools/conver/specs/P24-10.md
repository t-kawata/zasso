# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-10: The four inputs the reverse command reads: graph, measured edges, sidecars and the architecture delta

**Ticket Key**: P24-10 · **Phase**: 24

## Background

### Goal
`workspacify-tree reverse` passes **T1 through T6** over a representative whose decisions input reaches COMPLETE, and publishes the fourth layer.

### Purpose
P24-8 measured the six T gates by hand and every one is an input requirement rather than a defect. This ticket supplies those inputs.

### Motivation
Measured. `run.mjs reverse` accepts `--graph`, `--measured`, `--sidecars` and `--delta` beside `--spec`, `--decisions` and `--root`, and its readers fix the shapes: `readGraphNodes` takes `{nodes:[{id,file}]}`, `readMeasuredEdges` takes `{edges:[...]}` and the run already publishes `DEPENDENCIES.json` in exactly that shape, `listSidecarFiles` lists a directory, and `--delta` defaults to `<out>/ARCHITECTURE-DELTA.json` which `architecture-delta.mjs` produces. The gates judge: T1 that no measured directory is extra, T2 that no measured file is unowned, T3 that every graph node carries the file it is grounded in, T4 that the implementation order is proved from measurement, T5 that the layout was examined, T6 that the sidecar bundle hash resolves against files it names.

### Constraints
- **Every input is read from a document the chain produced.** The measured edges are the run's own `DEPENDENCIES.json`; the graph nodes are read from the origin spec; an absent input is reported rather than fabricated.
- **The representative is never written to.** The chain writes `RFC-SEED.md` and the manifest into the tree it is pointed at, so every run is over a scratch copy.
- **The sidecar directory and the delta's producer are the open question this ticket answers.**

## Acceptance Criteria

- [Happy path] `workspacify-tree reverse` over a scratch copy reports T1 through T6 as PASS and publishes the fourth layer, with every input read from a document the chain itself produced.
- [Error case] An input that cannot be read is reported naming the path, and a gate that still fails names the artefact it is about. Nothing is synthesised to satisfy a gate.
- [Edge case] A run with `spec-only-project`, which cannot be configured, is reported as not proved naming R5.5 rather than as a T-gate failure.

## Invariants

- [Normal condition] T1 through T6 all PASS and the fourth layer holds the artefacts §2.2 names.
- [Error invariant] A gate that fails names the artefact it is about, and an unreadable input is reported by path. No input is fabricated.
- [Internal state invariant] No representative is modified: each digest is equal before and after.
- [Boundary invariant] A representative that cannot be configured is reported as not proved naming R5.5, not as a T-gate failure.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — workspacify-tree run.mjs (readGraphNodes, readMeasuredEdges, listSidecarFiles) -> the T gates

- **Precondition**: A run has published its analysis documents and the decisions input reaches COMPLETE.
- **Postcondition**: T3 judges a node set in which every node carries the file it is grounded in, T4 proves the implementation order from the run's own measured edges, T5 finds the architecture delta record, and T6 resolves the sidecar bundle hash against the files it names.
- **Invariant**: Each input is read from a document the chain produced; a missing input is reported by path rather than replaced with an empty one, and no input is synthesised to satisfy a gate.

### C002 — workspacify-tree run.mjs (runReverse) and reverse-mode.mjs (WRITE_ALLOW_LIST)

- **Precondition**: The reverse run is pointed at a scratch copy rather than a representative.
- **Postcondition**: The fourth layer is written into the copy and the representative it was copied from is byte-identical afterwards.
- **Invariant**: Nothing the chain writes touches a representative: each is digested before and after, so a run accidentally pointed at one fails rather than editing a frozen instrument or the oracle's answer key.

## RFC Discrepancies found in Prior Implementation Rounds

- The Goal and the [Happy path] acceptance criterion require `workspacify-tree reverse` to pass T1 through T6 and publish the fourth layer over a representative whose decisions input reaches COMPLETE. Measurement falsifies this for `siprs-for-reverse`, and the two requirements are jointly unsatisfiable rather than merely unmet: T1 PASS requires the manifest's package paths to equal the measured directory set in both directions, which fixes an 18-way partition of the subject; that partition's measured dependency DAG (the run's own DEPENDENCIES.json) contains 18 cycles among `src` and its eight sibling packages, so T4 fails by ABOUT-REVERSE 6.14.1's own rule ('循環があれば当然 FAIL'). A run whose gate fails publishes nothing, so the fourth layer is not published for this subject. Supplying edges that would let T4 pass would mean synthesising a measurement, which the ticket's Constraints and C001's invariant forbid. Recorded so the next round can choose between the two repairs this exposes: relax T1 so a partition need not mirror every measured directory (the design's F3 warns that an accidental directory division must not be frozen as canonical), or treat a cyclic measurement as material for the human's judgement — the design's 'proved / not proved' ladder — rather than as a blocker to publication. P24-11 consumes the fourth layer and is affected by whichever is chosen.
- Review finding (contradiction, for the ticket text rather than the code): the [Happy path] acceptance criterion ('reports T1 through T6 as PASS and publishes the fourth layer') is unsatisfiable for `siprs-for-reverse`. Evidence measured in review: T1 forces the manifest's package paths to equal the measured directory set in both directions (18 paths, measured directories from measureDirectoryTree, compared by assertStructureParity); the measured DAG over that partition carries 18 cycles built from real edges, e.g. `src/account.rs:5` uses `crate::api::public_api_design::SipAccountHandle` while `src/api/call_api_semantics.rs:107` uses `crate::call::SipCall`.
