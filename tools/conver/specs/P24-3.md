# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
E5 and E6 reach all six languages. **E5** — the inter-module dependency edges — is extracted for each language from the modules E1 produces, replacing the explicit skip that records every non-Rust file as `no_edge_extractor_for_language`. **E6** — the dynamic mechanisms (FFI, reflection, dynamic dispatch, code generation, runtime registration, config-driven dispatch, compile-time embedding) — is extracted per language as a declared inventory and fed into the dynamic channel P23-6 built.

### Purpose
E5 is what R2's dependency hypothesis is made of, and R2 is what the partition is measured from: design §5.6 says "every downstream artefact is instantiated from the partition", and the partition rests on "cohesion, dependency density, SCC condensation, co-change history, and **boundary-crossing call counts**". Three of those five are computed from E5. E6 is the defence against failure 3, which `ABOUT-ANALYSIS-TECH.md` §2.3 states as the reason it exists: "import グラフは実行時の結合を代表しない。見落とすと、解析は「結合が無い」と主張するが実際にはある、という静かに嘘をつく状態になる."

### Motivation

## Boy Scout Rule

- **The queries and the inventories are data, keyed by language.** `EDGE_QUERIES_BY_LANGUAGE` and `DYNAMIC_MECHANISMS_BY_LANGUAGE` are frozen tables, and neither `measureDependencies` nor the dynamic measurement branches on a language. Adding a seventh language is adding two rows.
- **Function names as verb phrases.** `collectDependencyEdges`, `collectDynamicMechanisms`, `verifyMechanismInventory`, `recordUnverifiedClasses` — each names what it does, and the sequence reads as the measurement and its verification.
- **Variable names as domain concepts.** The locals are `edgeQueries`, `mechanismInventory`, `observedClasses`, `unverifiedClasses`, `producingStatement` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The seven mechanism classes and the six language identifiers are named constants read by the declarations, the collectors and the tests, so the partition's operands and its assertions cannot drift.
- **No error swallowing.** The skip path is preserved and named, an unverified class is recorded rather than dropped, and an undeclared class is refused. The one thing that must not happen is a `catch` producing an empty edge set, which would turn "could not extract" into "no dependencies".
- **Boy Scout improvement outside this ticket's scope.** The branch at `dependencies.mjs:265` currently builds its skip record inline inside an `if` with the reason as a string literal. This ticket extracts `recordSkippedLanguage({ file, language, reason })` and names the reason `NO_EDGE_EXTRACTOR_REASON`, so the skip is one named act rather than a literal inside a loop, and the new languages' path and the old skip read as the two branches they are. ## Notes in Prior Implementation Rounds

- [Implementation steps] 1) Write the failing tests first: the six languages' edges, the skip's disappearance, the mechanism partition, the unverified record, the per-language reasons and the Rust invariance. The mitigation is C002's invariant requiring each language's observed classes to be drawn from its own representative, plus the unverified record: a copied inventory would report every class unverified for five languages, which the test names.

- [Open items] Whether a mechanism site should also produce a *candidate* E5 edge — a dynamic dispatch that probably calls into another module — is not settled. Recording it as a mechanism rather than an edge is the conservative choice this ticket makes, and it is recorded because the alternative would inflate the graph with hypotheses.
- [Future improvements] Once P24-6 lands, C/C++'s E5 gains a declaration of which translation units it saw, and its reason can distinguish "the preprocessor hides this" from "we did not have the compile database" — two different limits that today share one cell.
