# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-3: E5–E6 — R2 and R2.5 across the six languages

## Background

### Goal
E5 and E6 reach all six languages. **E5** — the inter-module dependency edges — is extracted for each language from the modules E1 produces, replacing the explicit skip that records every non-Rust file as `no_edge_extractor_for_language`. **E6** — the dynamic mechanisms (FFI, reflection, dynamic dispatch, code generation, runtime registration, config-driven dispatch, compile-time embedding) — is extracted per language as a declared inventory and fed into the dynamic channel P23-6 built.

### Purpose
E5 is what R2's dependency hypothesis is made of, and R2 is what the partition is measured from: design §5.6 says "every downstream artefact is instantiated from the partition", and the partition rests on "cohesion, dependency density, SCC condensation, co-change history, and **boundary-crossing call counts**". Three of those five are computed from E5. E6 is the defence against failure 3, which `ABOUT-ANALYSIS-TECH.md` §2.3 states as the reason it exists: "import グラフは実行時の結合を代表しない。見落とすと、解析は「結合が無い」と主張するが実際にはある、という静かに嘘をつく状態になる."

### Motivation
**Measured**: `dependencies.mjs` skips every non-Rust file explicitly. The branch is at line 265: `if (language !== 'rust') { attempts.push(recordAttempt({ target: file, configuration: 'syntax-only', tool: \`tree-sitter-\${language}\`, outcome: { phase: 'parse', status: 'skipped', extractedCount: 0, reason: 'no_edge_extractor_for_language' } })); continue; }`. Its honesty is worth noting — the skip is *recorded*, not silent, which is why the report can say "Not exercised by this population" rather than printing a graph that omits five languages. The module consumes `collectRustModules` and `collectRustUses` (imported at lines 33-34, used at 299 and 320), so E5 depends on E1's modules and on P24-2's collectors. On E6: the capability profile from the probe reports **0 entrypoints and 792 activation mechanisms, all read statically**, with its own caveat that "Mechanisms that leave no static trace … are invisible to a static reading and are not counted above" — and `ABOUT-ANALYSIS-TECH.md` §2.3 records that the per-language mechanism list is a hypothesis to be verified: "言語ごとに何を探すか（我々の予想。検証してほしい）".

### Constraints
- `COUPLING_CLAIM = 'hypothesis'` (`dependencies.mjs:41`) is not upgraded and `represents_runtime_binding` stays `false`. A second language's edges are no more than a static hypothesis than Rust's are.
- The E5 cells are `partial` in all six languages, with per-language reasons naming that language's syntax-invisible dependency form — a re-export whose target is resolved at type-check time, a dynamic import, a Go build tag excluding a file, a Python import inside a function, a `#include` whose content depends on flags.
- The dynamic mechanism identity is a **string**, which is the property P23-6 built its channel to accept so that a second language's extractor feeds it without a schema change. This ticket supplies the second extractor.
- The per-language mechanism inventory is **declared as data and then verified against a representative**, not asserted. `ABOUT-ANALYSIS-TECH.md` §2.3 marks the list as a prediction; this ticket is where the prediction is tested.
- The skip at line 265 is not deleted. It stays for languages outside the six and for a language whose extraction genuinely did not run; what changes is that it stops firing for the six.

R2.5 runs before R1 and R2 in `ANALYSIS_EVALUATION_ORDER` because "the dependency graph's caveat has to state how many mechanisms stand between it and the running program".
- **The E6 material each language presents**, and where a representative can carry it: **Rust** — `#[no_mangle] extern "C"`, trait objects, `include!`, proc macros, `ctor`-style registration. **TypeScript/JavaScript** — `Reflect`, `eval`, dynamic `import()`, a DI container's decorator metadata, `require` with a computed path. **Go** — `cgo`, `reflect`, build tags, `init()` registration, struct tags. **Python** — `ctypes`/`cffi`, `getattr`/`setattr`, metaclasses, entry points, decorators, `importlib`. **C/C++** — `dlopen`/`dlsym`, function pointers, the preprocessor, linker sections, `__attribute__((constructor))`.
- **The reason the two items belong in one ticket**: E6's mechanism list is *the caveat on E5's graph*. R2.5 runs before R2 precisely so the caveat exists when the graph is read, and a language whose E5 edges are extracted without its E6 mechanisms produces a graph whose caveat understates the gap — which is the silent lie `ABOUT-ANALYSIS-TECH.md` §2.3 describes.
- **The Rust-idiom risk this ticket must not repeat**: `NAME_FILTERS` carries `typescript.unwrap_expect = /^(?:unwrap|expect)$/`, and the same entry in `javascript` and `python` — `unwrap` is a Rust idiom. A mechanism inventory written by transliterating the Rust one would repeat the same error at the E6 layer, which is why the inventory is verified against a representative rather than asserted.

## Boy Scout Rule

- **The queries and the inventories are data, keyed by language.** `EDGE_QUERIES_BY_LANGUAGE` and `DYNAMIC_MECHANISMS_BY_LANGUAGE` are frozen tables, and neither `measureDependencies` nor the dynamic measurement branches on a language. Adding a seventh language is adding two rows.
- **Function names as verb phrases.** `collectDependencyEdges`, `collectDynamicMechanisms`, `verifyMechanismInventory`, `recordUnverifiedClasses` — each names what it does, and the sequence reads as the measurement and its verification.
- **Variable names as domain concepts.** The locals are `edgeQueries`, `mechanismInventory`, `observedClasses`, `unverifiedClasses`, `producingStatement` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The seven mechanism classes and the six language identifiers are named constants read by the declarations, the collectors and the tests, so the partition's operands and its assertions cannot drift.
- **No error swallowing.** The skip path is preserved and named, an unverified class is recorded rather than dropped, and an undeclared class is refused. The one thing that must not happen is a `catch` producing an empty edge set, which would turn "could not extract" into "no dependencies".
- **Boy Scout improvement outside this ticket's scope.** The branch at `dependencies.mjs:265` currently builds its skip record inline inside an `if` with the reason as a string literal. This ticket extracts `recordSkippedLanguage({ file, language, reason })` and names the reason `NO_EDGE_EXTRACTOR_REASON`, so the skip is one named act rather than a literal inside a loop, and the new languages' path and the old skip read as the two branches they are. The existing attempt-ledger assertions stay green.
