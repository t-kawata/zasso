# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

**Ticket Key**: P24-4 · **Phase**: 24

## Background

### Goal
R3's five extraction items reach all six languages. **E7** guards — early returns, assertions, panics, thrown exceptions, contract macros; **E8** state machines — state-carrying types and their transitions; **E9** effects — I/O, global mutation, external calls; **E10** tests — test functions and what they touch; **E11** contract candidates — the pre- and post-conditions and invariants derived from the four above. Each language's declared vocabulary is **exercised** over its representative, every entry that cannot fire is repaired or removed, and the run records in `limitations` **which tables it actually exercised** — an obligation the module declares about itself and does not currently discharge.

### Purpose
R3's material is what the claim ledger is built from, and the ledger is what everything downstream consumes: design §4 traces the path from an `unresolved` claim through `grill_question` → RFC-SEED §1 → `/grill-me-for-rfc` → `normative_decision` → the RFC's clause → the graph node → the Dirs-Tree → the ticket → the implementation. E11 is the population the contract candidates come from, and contracts are what `S2`, `S4` and `S5` gate.

### Motivation
`semantics.mjs` states the obligation in its own header and states it accurately: "The tables below are the declaration; **which of them a given run actually exercised is a fact about the run, recorded in `limitations`**." Nothing records it. And the tables carry defects that only an exercised run can reveal — **measured** on 2026-09-11:
- `NAME_FILTERS.typescript.unwrap_expect = /^(?:unwrap|expect)$/`, and the byte-identical entry in `javascript` and `python`. `unwrap` is a Rust idiom; `expect` exists in JavaScript's test frameworks and in neither of the other two. An entry that describes another language is worse than a missing entry, because it reads as coverage.
- `NAME_FILTERS.go.error_return = /^(?:Errorf|New)$/` — `New` is a constructor, and a filter that fires on constructors reports error returns that are not error returns.
- `state_field` and `state_assignment` are the same regex, `/state|status|phase|mode/i`, in TypeScript, JavaScript, Go and Python. `semantics.mjs` then declares `STATE_NAME = /state|status|phase|mode/i` with the comment "The word a state field's name must contain, **for every language**" — so E8 is a name heuristic wearing a node-type table's clothes, and no run has ever tested whether the names it matches are state fields in five of the six languages.
- `RUST_FIELD_DECLARATION = 'field_declaration'` is a node type from one grammar, declared at module scope beside the language-agnostic declarations.

### Constraints
- **E13 is out of scope and stays `unsupported_in_principle` in all six.** It is a decision from P22-4 and the note gives the reason: "Semantic equivalence is undecidable for general programs. E13 is TCE — trivial, syntactic, compiler-normalisation equivalence — and only that is ever claimed." P24-5 handles TCE; this ticket does not touch the cell.
- **A repair is a removal when the entry cannot fire.** An entry naming a construct the language does not have is deleted rather than left as a no-op, because a no-op entry reads as coverage. That is a change to a declared table, and the test asserts the deletion rather than the repair.
- **Per-language entries stay per language.** The tables are keyed by language and a shared value is copied, not referenced; the four-way identical `state_field` is the evidence that sharing by reference hides the drift.
- **The cells stay `partial`.** E7-E11 are syntactic-channel extractions in all six, and the reason names that language's invisibility.
- **The `limitations` obligation is discharged mechanically.** The run records per table whether it was exercised, and a table that was not exercised is reported rather than omitted — the F12 rule the whole instrument follows, and the same discipline `buildAttemptLedger` applies to files.

## Boy Scout Rule

- **The tables are data and the exercise status is data about the data.** The per-table record is a frozen shape produced by iterating the tables, so a new table is exercised and reported without a new branch — which is what makes the `limitations` obligation stay discharged as the tables grow.
- **Function names as verb phrases.** `measureSemantics`, `extractGuards`, `extractStateMachines`, `extractEffects`, `extractTests`, `deriveContractCandidates`, `recordTableExercise` — each names what it does, and the R3 site reads as the five items the design names.
- **Variable names as domain concepts.** The locals are `factKinds`, `observedKinds`, `unexercisedKinds`, `nameFilters`, `stateFields`, `contractCandidates` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The five item identifiers and the table identifiers become constants read by the extraction, the limitation record and the tests, so the count asserted and the count produced cannot drift.
- **No error swallowing.** An unexercised kind is recorded rather than omitted, and a filter that cannot fire is a finding rather than a no-op. The one outcome that must never occur is a silent empty extraction, which would read as a language with no guards.
- **Boy Scout improvement outside this ticket's scope.** The four byte-identical state regexes are currently four separate literal declarations, which is how the drift stayed invisible. This ticket replaces them with one named constant, `LANGUAGE_STATE_NAME_PATTERN`, referenced by the rows that still need a name-based read, and per-language node-type reads where the grammar offers one — so the sharing is explicit in the code rather than accidental in the text, and a fifth language copying it copies a name rather than a literal.

- [Risks] The risk is a repair that makes a filter fire without making it correct — widening `go.error_return` to match any identifier containing `err`, for instance. The mitigation is C002's invariant tested against a per-language construct list, so a widened pattern would match a construct the language does not treat as an error return and fail.
- [Caveats] Removing an entry narrows the population E11 draws on, which narrows the contract candidates, which narrows the ledger. That is the correct direction — a candidate drawn from a construct that does not exist is a false contract — but it means the claim count will fall for the five languages rather than rise, and the report must not present a falling count as a regression. The design's §4 point applies: `unresolved` claims are raw material, and a smaller honest population beats a larger dishonest one.
- [Open items] Whether E8 should be a node-type read in the four languages whose grammars distinguish field declarations is not settled.
