# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Boy Scout Rule

- **Three items, three named modules.** `reachability.mjs` answers E12, `tce.mjs` answers E13, and `property-tests.mjs` answers E14. The stage site then reads as the three items the design names rather than as one function doing three things.
- **Function names as verb phrases.** `measureReachability`, `compareTrivially`, `normaliseUnderGrammar`, `runGeneratedProperties` — each names what it does, and the E13 pair reads as "normalise under the grammar, then compare trivially".
- **Variable names as domain concepts.** The locals are `reachableRegions`, `unreachableRegions`, `notAnalysableRegions`, `normalisedOriginal`, `normalisedMutant`, `trivialVerdict`, `engineName` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The two TCE verdicts, the three reachability states, the two execution statuses and the engine names are named constants read by the implementations and the tests, so the vocabularies cannot drift.
- **No error swallowing.** A grammar that cannot be loaded throws rather than falling back to a text comparison; a property that cannot run is recorded rather than dropped; a region that cannot be analysed is a third state rather than a default. Each of the three would otherwise convert an unknown into a finding.
- **Boy Scout improvement outside this ticket's scope.** `property-tests.mjs` currently builds each language's property text by concatenating strings with the engine's boilerplate inline. This ticket extracts `renderPropertyForEngine({ language, property, engine })` so the per-engine form is one named function per engine rather than one function with six branches, and the existing Rust rendering assertions stay green against the extracted function.

## Notes in Prior Implementation Rounds

- [Implementation steps] 1) Write the failing tests first: the reachability partition, the TCE vocabulary, the generated-versus-executed separation, the no-semantic-equivalence walk and the grammar provenance. Every one fails red because E12 and E13 have no implementation and E14 does not execute. 2) Build `reachability.mjs` over the call graph E5 produces and the entrypoints R2.5 measures. 3) Build `tce.mjs` against `GRAMMAR_BY_LANGUAGE`, comparing tree shapes rather than source text. 4) Add the property execution to the worktree isolation. 5) Re-run the R5, R5.5 and R6.5 suites together.
- [Risks] The risk is a TCE normaliser that is a text diff in disguise — trimming whitespace and comparing strings would produce a plausible verdict vocabulary while answering a different question. The mitigation is C002's precondition that the comparison happens under the declared grammar and the postcondition that the normalisation is recorded: a text diff has no normalised tree to record, so the record's shape forces the tree comparison.
- [Caveats] TCE depends on the grammar version. Two grammars for the same language would normalise differently and the verdict would change silently. The grammar is therefore recorded with each verdict alongside the tool identity, following the instrument's rule that the record is the combination of grammar version, target-tree hash, environment and command line — not the tool name alone.
- [Open items] Whether E12's unreachable regions should feed the gap list directly or only after the dynamic channel has had its say is not settled. A region unreachable statically may be reached through a mechanism E6 finds, so reporting it as dead before E6's material is read would overstate the gap. This ticket records the three states and leaves the classification to R5, and the open question is recorded here.
