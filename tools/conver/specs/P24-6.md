# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-6: C/C++'s build database: compile_commands.json discovery and the refusal to degrade

**Ticket Key**: P24-6 · **Phase**: 24

---

## Background

### Goal
C/C++'s hard quality boundary becomes **addressable and honest**. A C/C++ subject's build database is discovered and its per-translation-unit flags, working directory and include conditions are recorded; when the database is absent, the C/C++ analysis **lowers its declared `analysis_mode`** and records a limitation naming the absence and its effect — it never degrades silently and never emits a thin result indistinguishable from a complete one.

### Purpose
`docs/P22-ANALYSIS-TECH.md` states the boundary under its own heading, "C/C++ has a hard quality boundary": "With `compile_commands.json`, per-translation-unit flags, working directory and include conditions can be replayed. Without it, a Clang AST is an approximation the analyser chose for itself. A run that cannot find the database **must say so in `limitations` and must not silently degrade**. The `c_cpp` column of the matrix is `not_attempted` today for that reason among others."

### Motivation
The mechanism that makes "must say so" mechanical already exists and is unused for this purpose. `analysis-tech.mjs` declares `ANALYSIS_MODES = ['syntax_only','partial_semantic','configured_semantic','runtime']` with the reason written into the module: "A language adapter that cannot resolve its configuration must **lower this value** rather than emit a thin result indistinguishable from a complete one." `COVERAGE_FIELDS` already carries `configs_enumerated` and `configs_analyzed` as two of its six counters, so "we found the configuration" and "we analysed under it" are already separable. And `validateLimitation` already refuses a limitation that names no code, no scope or no effect. C/C++ is where all three meet: the language whose static reading is most dependent on configuration is the one for which the instrument has the least to say, and the difference between a C++ file read under its real flags and one read under a guess is the difference between an analysis and an approximation.

### Constraints
- **The absent case is the common case and must be the honest one.** Most C/C++ trees do not carry `compile_commands.json`. The response is a lowered mode and a named limitation, never a refusal and never a silent approximation — §1.2's invariant applies here as everywhere: a subject that cannot supply its build database is still a subject.
- **A found database is used, not merely noted.** `configs_enumerated` counts what was found; `configs_analyzed` counts what the analysis actually ran under. A run that finds the database and does not use it reports the two numbers differently, which is what makes the pair worth having.
- **The C/C++ cell's reason names the database** rather than the preprocessor alone, because the preprocessor's effect depends on the flags. A cell that named only the preprocessor would be true of every C/C++ run and would explain none of them.
- **No new dependency.** Reading the database is JSON parsing of a file the subject already carries; no Clang, no build system and no daemon is invoked by the analysis, which remains read-only over its subject.
- **The limitation meets the existing contract.** `validateLimitation` requires a code, a scope and an effect; the C/C++ limitation supplies all three, with the effect stated as what the conclusion loses rather than as what the run did.

## Boy Scout Rule

- **The database names are data.** `BUILD_DATABASE_NAMES` is a declared list with the search order stated, so a second database format is a row rather than a branch, and the search order is visible rather than implied by the order of `if` statements.
- **Function names as verb phrases.** `discoverBuildDatabase`, `readTranslationUnits`, `recordConfigurationUse`, `reportMissingDatabase` — each names what it does, and the sequence reads as the discovery and its accounting.
- **Variable names as domain concepts.** The locals are `translationUnits`, `workingDirectory`, `includePaths`, `compileFlags`, `configsEnumerated`, `configsAnalyzed` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The four analysis modes, the limitation code for the absent database and the database file names are named constants read by the implementation, the limitation and the tests.
- **No error swallowing.** The absent, unreadable and empty cases produce three different records with three different codes. The one outcome that must not occur is a `catch` returning an empty database, which would make an unreadable file indistinguishable from a project that never had one.
- **Boy Scout improvement outside this ticket's scope.** `analysis-tech.mjs`'s `emptyCoverage()` and the coverage accumulation in the extractors are separate, so a counter's name appears once in the declaration and again at each accumulation site. This ticket routes the accumulation through a named `addCoverage(target, source)` used by the C/C++ path, so the six field names are read from `COVERAGE_FIELDS` rather than respelled, and the existing coverage assertions stay green.

The mitigation is the integration assertion that the extraction under a database differs from the extraction without it for the same fixture, and the boundary test that a define changing an include's resolution changes the resulting E5 edge.
- [Caveats] The flags a database records are the flags one build used, not the flags the project has; a database generated for a debug build and one for a release build describe different compositions of the same source. The record therefore carries the flags verbatim and the limitation states which database was read, so a reader can tell which build the analysis saw. Stating the build is the honest form of the claim; choosing one silently is not.
