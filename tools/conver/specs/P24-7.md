# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-7: The capability matrix derived from the attempt ledger, and served

## Background

### Goal
The capability matrix stops being a declaration and becomes a **derivation**. A cell's value is computed from the run's own analysis attempt ledger, so a cell cannot read `partial` unless an attempt supports it; `failed` becomes reachable from a failed attempt; `not_attempted` requires that no attempt of that family was made for that language; and `unsupported_in_principle` remains asserted by a decision rather than a run. The matrix is then **served** — published in the report — where today it is built and never shown.

### Purpose
`capabilityRow(language)` is a pure function of the language name. It returns the same cells whatever the run did, which is **why the Rust row went stale**: `CAPABILITY_NOTES['rust/E7-E16']` reads "Not attempted by this instrument version. R3 and later stages consume these, and the semantic adapters they need are declared but not built here." That sentence was written at P22-4, before P22-5, P22-6 and P22-7 built R3 through R6.5. Today R3 produces 4,460 claims for Rust, and the note is false.

### Motivation
Two measurements, both taken on 2026-09-11.
- **The matrix is built and never served.** `CAPABILITY_MATRIX` and `renderCapabilityMatrixMarkdown` are referenced only by `analysis-tech.mjs` itself and by `tests/workspacify-reverse/unit/r0-r2.test.mjs:410-425`, whose assertions are shape-only: six keys, sixteen keys each, values drawn from `CAPABILITY_VALUES`. Nothing else reads it. The report's `## Language coverage` section is rendered from `measureStructure`'s limitations instead, so the reader is told which languages were not exercised in prose while the matrix that says so precisely is never shown.
- **The values are barely used.** Over all 96 cells the tally is `{ partial: 6, not_attempted: 84, unsupported_in_principle: 6 }` — **zero `success` and zero `failed`**. Two of the five declared values have never been produced by anything.
- **The ledger that can drive it exists and is populated.** `ANALYSIS-ATTEMPTS.json` from the R8 probe is `{ couldNotRunCount: 0, extractedNothingCount: 122, rows: [604 rows] }`, each row `{ configuration, diagnostics, extracted_count, phase, reason, status, target, tool }` with statuses from `ATTEMPT_STATUSES = ['success','partial','failed','skipped']`. The tool name carries the language (`tree-sitter-rust`), the phase carries the depth, and the count and status carry the outcome. The ledger's `success` is a **run** status and the matrix's `success` is a **capability** value: two vocabularies that must not be conflated, and the derivation is where they meet.

### Constraints
- **Fixing the value without fixing the derivation resets the clock.** The Rust row is false because nothing connected it to the run; a hand-corrected row would go stale again at the next build. The derivation is the deliverable.
- **`partial` is the maximum for a syntactic channel in all six languages**, and the reason must be per language — the judgement P24-2 recorded. A derived matrix that could produce `success` would be able to overclaim, which the instrument may not do.
- **`unsupported_in_principle` is not derived.** It is a decision about decidability — E13 in all six — and the derivation leaves it alone, asserted rather than computed.
- **The two vocabularies stay apart.** A ledger row with `status: 'success'` is a run that ran; it is not a claim that the cell is `success`. The derivation maps run outcomes to capability values explicitly, and the mapping is declared.
- **The matrix is served, not gated.** It is material; it carries no verdict, exactly as `capability-profile.mjs` states for its own five dimensions. A cell reading `not_attempted` must never read as "the project lacks this".
- **The served matrix and the constant agree.** `docs/P22-ANALYSIS-TECH.md` already contains the rendered matrix verbatim and a test holds the document and the constant together; the served report version extends that property to the run.

## Boy Scout Rule

- **The mapping is data and the two vocabularies are named distinctly.** `ATTEMPT_TO_CAPABILITY` is a frozen table, and the published document's run-status fields and capability-value fields carry names that say which vocabulary they belong to — so the confusion the shared three names invite is prevented by the naming rather than by a comment.
- **Function names as verb phrases.** `deriveCapabilityMatrix`, `explainCell`, `renderDerivedMatrixMarkdown`, `carryDecisionCells` — each names what it does, and the derivation site reads as the three steps it performs: carry the decisions, derive from the ledger, render.
- **Variable names as domain concepts.** The locals are `attemptRows`, `cellExplanation`, `decisionSourcedCells`, `derivedFrom`, `supportingRows` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The five capability values and the four attempt statuses are read from their existing declarations rather than respelled, and E13's item identifier is a constant shared with the decision that carries it.
- **No error swallowing.** An unattributable row is reported by row; a contradictory derivation names both rows; an empty ledger is stated as empty rather than rendered as a matrix of zeros. Each of the three would otherwise convert an unknown into a clean value.
- **Boy Scout improvement outside this ticket's scope.** `analysis-tech.mjs` declares the matrix, the notes, the row builder and the gap finder in four places separated by other declarations, so a reader assembling the matrix's behaviour reads four regions of the file. This ticket groups them — the values, the notes, the builder, the derivation and the renderer — into one section under one heading, keeping every export at its existing name and value. The existing shape assertions in `r0-r2.test.mjs` stay green and pin the grouping.
