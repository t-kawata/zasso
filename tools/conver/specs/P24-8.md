# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
The design's central claim stops being a claim. The whole chain — `workspacify-reverse` → `workspacify-tree` reverse → `workspacify-allocate` reverse — is driven to the **terminal state** over the four pattern representatives, and the terminal states are **compared**: the package sets, the per-package artefact sets, and the consistency web's gates. Every difference is **recorded**; nothing is eliminated and nothing is silently preserved. **A project is observed reaching the terminal state through the reverse rotation for the first time.**

### Purpose
Design §7.3 records it as the largest unverified item in the document: "Whether the four patterns genuinely converge to an identical terminal structure — **Nobody has ever observed a project reaching the terminal state through the reverse rotation.** Every statement in §2 is a design claim, not a measurement. **This is the thing the design is *for*, and it is unmeasured.**" §2 defines the terminal state, §2.1 through §2.3 give the layout and the artefact inventory, §2.4 gives the consistency web and the definition of a contradiction — "a contradiction is an *unrecorded* inconsistency" — and §2.5 gives structural indistinguishability. All five sections are design claims. This ticket is where they are measured.

### Motivation
Three things make this the observation that closes the phase rather than one more ticket. First, **the instrument is proven capable**: `analyze --through=r8` on `siprs-for-reverse` exits 0 in about three minutes and publishes 21 documents (Appendix A.1). The reverse half works. Second, **the downstream entry points exist and are wired**: `workspacify-tree run.mjs reverse --spec=<origin-spec.md> --decisions=<path> --root=<dir>` and `workspacify-allocate run.mjs reverse --root=<dir> --decisions=<path>`, with `ALLOCATE_MODES.REVERSE`, `buildReverseIndex` and the A1 refusal. Third, **nothing has ever joined them**: §2's terminal state has been described in a document since the design was written and has never been produced by a run. And the tickets before this one are what make the observation worth taking — the procedure exists (P23-1), the partition material exists (P23-2), the exit serves the right shape (P23-3), the sandbox generalises (P23-5), the dynamic and counterexample channels run (P23-6, P23-7), the lanes are reachable (P23-8), the seam is recorded (P23-9), the patterns are detectable (P23-11), the invariant is audited (P23-12), and six languages are covered (P24-1 through P24-7). ### Constraints
- **The `--decisions` file is AI-authored** from the packet material Step 5 serves. An automated test therefore needs a **frozen decisions input per representative**, produced once and pinned, so the run is reproducible and the comparison is between structures rather than between two readings of the same page.
- **Neither representative is modified.** The two siprs trees are P22's measuring instrument; the four pattern representatives are P23-12's audit input. The runs publish to `--out`, outside the subject, and the write allow-list on a subject is `RFC-SEED.md` and the manifest (A2).
- **A difference is recorded, not removed.** §2.4 states it twice — T5, GF2 and S2 "sometimes PASS on 'the disagreement is recorded' rather than on 'the two agree'", and "a difference of zero, or a disagreement of zero, can be a signal of abnormality rather than of health". The comparison therefore reports differences rather than minimising them.
- **The outcome is `proved` or `not proved`, and nothing else.** §5.9: "The machine's vocabulary is **`proved`** and **`not proved`**, and nothing else." The ladder L0-L3 is recorded with L3 as the only success, and L3 is a human's judgement — "Only L3 may be called success."
- **`omission 0` is not the success condition.** §5.9: "Success is **RESIDUE 0 in `/crystalize-readme`**, reached only after several rounds and judged by a human. `omission 0` from `/find-omissions` is **not** the success condition; it is material for the human's decision."
- **One round is the command plus the whole downstream chain**, not the command alone, and "No separate 'R7.5 human norm-setting' stage exists and none may be created."
- **§2.5's mechanism is asserted, not assumed**: uncertainty metadata is injected only into RFC-SEED §1 and the RFC, the intermediate artefacts keep their forward schemas and canonical hashes, and a byte-identical `manifest_hash` over the forward fixtures is mandatory (P22-10).

## Boy Scout Rule

- **The inventory is data.** `TERMINAL_ARTEFACTS` is the §2.3 list as a frozen table, so the assertion reads the same declaration §2.3 tabulates and adding an artefact to the terminal state is adding a row. The alternative — a hand-written list in the test — is what would let the design document and the test drift into describing two different terminal states.
- **Function names as verb phrases.** `measureTerminalState`, `compareTerminalStates`, `renderTerminalStateReport`, `assertIndistinguishable`, `reportLadderPosition` — each names what it does, and the sequence reads as the observation it performs: measure, compare, render, report.
- **Variable names as domain concepts.** The locals are `terminalStates`, `packagePathSets`, `artefactNameSets`, `recordedDifferences`, `ladderPosition`, `decisionsDigest` — never `data`, `info` or `tmp`.
- **Hardcoded values as named constants.** The four ladder positions, the two machine verdicts and the terminal artefact names are named constants read by the measurement, the comparison and the tests, so the count asserted and the count produced cannot drift.
- **No error swallowing.** A refusing stage, a missing artefact and a missing decisions input each produce a named finding. The one outcome that must not occur is a `catch` that turns a failed stage into an absent artefact, which would make an incomplete terminal state read as a complete one with fewer packages.
- **Boy Scout improvement outside this ticket\'s scope.** The three commands\' entry points each parse their arguments and resolve their root independently, and this test is the first caller that invokes all three in sequence. This ticket extracts the shared argument resolution into a named helper used by the test — so the three invocations read as the chain they are — and leaves the commands themselves untouched, because changing three entry points inside an observation ticket would make the observation measure the change rather than the instrument.
