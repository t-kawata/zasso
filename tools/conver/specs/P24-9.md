# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-9: The chain reaches the terminal state: the inputs the reverse commands require

**Ticket Key**: P24-9 · **Phase**: 24

---

## Background

### Goal
The three-command chain actually reaches the terminal state over a representative. `analyze` runs to R8, `workspacify-tree reverse` passes its T gates, and `workspacify-allocate reverse` passes A1 and writes the fifth layer, so §2.2's layout exists on disk because a run produced it rather than because a document describes it.

### Purpose
P24-8 delivered the instrument that measures the terminal state and took the observation as far as the chain would go. Driving it by hand established exactly what stops the chain, and every stop is an input the reverse commands require rather than a defect: T1/T2 need a `workspace[]` and `ownership[]` covering the measured tree, T3 needs `--graph=<{nodes:[{id,file}]}>`, T4 needs `--measured=<{edges:[...]}>`, T5 needs `--delta` to exist, and T6 needs `--sidecars=<dir>`. That list is the whole of this ticket.

### Motivation
Measured rather than assumed. `workspacify-tree run.mjs reverse` over a copy of `partial-conver-project` passes G2 once the decisions input carries `semantic_review` and settles every spec-pulse candidate, both authored under P24-8, and then reports T1 through T6 as the failures above. The command's own readers fix the shapes: `readGraphNodes` accepts `{nodes:[{id,file}]}`, `readMeasuredEdges` accepts `{edges:[...]}` and the run already publishes `DEPENDENCIES.json` in that shape, `listSidecarFiles` lists a directory, and `--delta` defaults to `<out>/ARCHITECTURE-DELTA.json`. What each T gate judges is fixed too: T1 that no measured directory is extra, T2 that no measured file is unowned, T3 that every graph node carries the file it is grounded in, T4 that the implementation order is proved from measurement, T5 that the layout was examined, T6 that the sidecar bundle hash resolves against something.

### Constraints
- No representative is modified. The chain writes `RFC-SEED.md` and the allocate manifest into the tree it is pointed at, which is the A2 write allow-list, so every run is over a scratch copy and the representative is asserted byte-identical afterwards. `siprs-with-4layers` is the answer key the oracle rests on and must never be written to.
- A partition is authored from the measured tree, not invented from the spec. `partial-conver-project` produces an origin spec with zero claims, so a workspace cannot be derived from claims; the measured directories are the honest source.
- A subject with no source in any target language cannot be configured. `spec-only-project` refuses at R5.5 and is recorded as not proved rather than worked around.

## Acceptance Criteria

- [Happy path] `workspacify-tree reverse` over a scratch copy of `partial-conver-project` reports every T gate as PASS and publishes the fourth layer, and `workspacify-allocate reverse` over the same copy reports A1 as passed and writes `RFC-SEED.md` and `WORKSPACIFY-ALLOCATE-MANIFEST.json` into it.
- [Error case] A representative whose chain still stops is reported with the stage and the gate that refused and the input it named, while the other representatives' results stand. A run pointed at a representative rather than a copy is refused by the test before anything executes.
- [Edge case] A representative carrying no source in a target language is reported as not proved for that representative rather than as a failure of the chain, and the report names R5.5 and the language it could not determine.

## Invariants

- [Normal condition] For each representative, the chain's stage records show every declared stage reached and every gate passed, and the terminal layout holds the artefacts §2.2 names.
- [Error invariant] A gate that refuses is reported with its name and the input it reported missing. Nothing is worked around and no input is fabricated to satisfy a gate.
- [Internal state invariant] No representative is modified: each subject's digest before and after the whole chain is equal, and the oracle tree is never written to.
- [Boundary invariant] A representative that cannot be configured is reported as not proved for that representative while the others' results stand; the chain's failure is not reported as the subject's.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — structure-parity.mjs (T1 and T2) -> the decisions partition

- **Precondition**: A representative's measured tree is presented, and a decisions input declares a workspace and an ownership set for it.
- **Postcondition**: Every directory the measured tree holds is covered by a declared package, and every measured file is owned by exactly one of them, so T1 reports no extra directory and T2 reports no unowned file.
- **Invariant**: The partition is derived from the measured tree rather than from the origin spec's claims: over a subject whose spec carries zero claims, the workspace is still complete, because a directory exists whether or not a claim names it.

### C002 — run.mjs (readGraphNodes, readMeasuredEdges, listSidecarFiles) -> the reverse command's inputs

- **Precondition**: A run has published its analysis documents, and the reverse command is invoked with `--graph`, `--measured`, `--sidecars` and `--delta`.
- **Postcondition**: T3 judges a node set in which every node carries the file it is grounded in, T4 proves the implementation order from the R2 measurement, T5 finds the architecture delta record, and T6 resolves the sidecar bundle hash against the files it names.
- **Invariant**: Each input is read from a document the chain itself produced or from a record this ticket authors, never synthesised to satisfy a gate: the measured edges are the run's own DEPENDENCIES.json, and a missing input is reported rather than fabricated.

### C003 — run.mjs (runReverse) and reverse-mode.mjs (WRITE_ALLOW_LIST) -> the subject

- **Precondition**: A reverse run is pointed at a tree, and the tree is a scratch copy rather than a representative.
- **Postcondition**: The fourth and fifth layers are written into the copy, and the representative the copy was made from is byte-identical afterwards.
- **Invariant**: Nothing the chain writes touches a representative. The invariant is asserted by digesting each representative before and after the whole chain, so a test that accidentally pointed the chain at one would fail rather than edit a frozen instrument or the oracle's answer key.

### Exceptions

- [Item] Whether the authored partition is the partition a human would have chosen. [Reason] It is impossible to test this: a partition is a judgement about where boundaries belong and no assertion decides it. This is not a design defect and not an architectural defect. The mechanical half is fully asserted - the partition is complete over the measured tree, every file is owned, and it is derived from measurement rather than invented - and the judgement half is surfaced by the manifest the chain publishes for a human to read. [Alternative verification] The completeness and ownership assertions, plus the manifest record of what each package claims.

## Notes in Prior Implementation Rounds

- [Implementation steps] 1) Write the failing assertions first: the partition completeness, the graph node shape, the digest invariant. 2) Author `workspace[]` and `ownership[]` for `partial-conver-project` from its measured tree and iterate until T1 and T2 pass. 3) Supply `--graph`, `--measured`, `--sidecars` and `--delta` and iterate until T3 through T6 pass. 4) Repeat for the other representatives until each either passes or names its refusing stage. 5) Update the chain runner in the integration test to pass the same inputs.
- [Risks] The highest risk is synthesising an input to satisfy a gate. The mitigation is C002's invariant: the measured edges are the run's own document, the graph nodes are read from the origin spec, and an absent input is reported rather than fabricated.
- [Caveats] The partition is a judgement taken once and then pinned. A different operator would draw different boundaries and produce a different terminal state, which is why the record names the decisions input and its digest.
- [Open items] Whether `--delta` and `--sidecars` have a producer elsewhere in the pipeline, or are operator-supplied inputs, is not settled. If they turn out to need a producer, that producer is a finding to record and a candidate for its own ticket.
- [Future improvements] Once the chain passes, the same runner drives the two siprs representatives, which P24-10 needs for the convergence claim.
