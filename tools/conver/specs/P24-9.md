# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P24-9: The decisions input a claim-carrying representative needs: the partition, the ownership and every pulse candidate settled

**Ticket Key**: P24-9 · **Phase**: 24

---

## Background

### Goal
`siprs-for-reverse` has a decisions input that carries `workspacify-tree gate` to **COMPLETE**: a `workspace[]` partition authored from the measured tree, an `ownership[]` derived mechanically from the run's own origin spec, and every specification-pulse candidate settled in `spec_defects` or `residual_questions`.

### Purpose
The chain cannot start without this input, and the input cannot be guessed: it is the AI-authored judgement the design's Step 5 requires. P24-8 measured what stops the chain and P24-9's first half established that the two fixture representatives can never produce one. This ticket produces it for the representative that can.

### Motivation
Measured, not assumed. `workspacify-tree extract` over `siprs-for-reverse`'s origin spec returns `harvested: 7036`, `confirmed: 7036`, `review_required: 0`, `unresolved: 0`, `invariants: 3518`, and a `spec_pulse` of more than one hundred candidates. `gate` therefore stops at G3 with `production-library pkg-0001 owns no objects or claims` when ownership is empty and `REVIEW_REQUIRED` when a pulse candidate is unsettled. The ownership set is mechanical - every harvested object is named in the spec and belongs to exactly one package - so it is derived by a script rather than typed; the pulse settlements are judgement and are authored one candidate at a time.

### Constraints
- **The representative is never written to.** Every run is over a scratch copy, and `siprs-with-4layers` is the answer key the oracle rests on.
- **A package that owns nothing cannot be declared a production-library.** The gate calls that a speculative split. A subject whose spec carries no claim therefore cannot carry a production-library partition at all, and is reported as not proved rather than given a partition it cannot justify.
- **The pulse settlements are judgements taken once and pinned.** The record names the decisions input and its digest, so a different operator can reproduce or replace the reading.

## Acceptance Criteria

- [Happy path] `workspacify-tree gate --spec=<origin spec> --decisions=<DECISIONS.json>` over `siprs-for-reverse` prints COMPLETE, with a workspace whose every package owns at least one object or claim, an ownership set covering every harvested object exactly once, and every spec-pulse candidate settled.
- [Error case] An unsettled pulse candidate is named by id with the gate reporting REVIEW_REQUIRED; a package owning nothing is named as a speculative split. Neither is worked around.
- [Edge case] A representative whose origin spec carries zero claims is reported as not proved for that representative, with the gate and the reason named, rather than given an empty partition.

## Invariants

- [Error invariant] An unsettled candidate or an empty package is reported with its name rather than worked around.
- [Internal state invariant] The representative is byte-identical after every run: all work happens over a scratch copy.
- [Boundary invariant] A subject whose spec carries zero claims is reported as not proved rather than given an empty partition.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — workspacify-tree gate-advice.mjs (G3's reasons) -> the decisions input

- **Precondition**: A representative carries an origin spec with harvested objects, and the measured tree is presented.
- **Postcondition**: Every harvested object is owned by exactly one package, every package owns at least one object or claim, and the workspace tree's leaves match the package paths one for one, so G3 reports COMPLETE.

- **Precondition**: The origin spec carries specification-pulse candidates.

- **Invariant**: No candidate is settled twice and none is left unsettled: the settled count equals the candidate count, asserted over the run's own candidate list rather than over a fixture.
