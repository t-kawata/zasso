# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P25-3: The arrival instrument counts the packages the partition declares

**Ticket Key**: P25-3 · **Phase**: 25

---

## Background

### Goal
Make `measureTerminalState` measure the scopes the partition declares rather than the top-level directories that happen to exist, so that a `complete: true` result means what the design means by it and can be trusted before any real project is attempted.

### Purpose
`terminal-state.mjs:129-138` computes `packagesUnder(root)` as the non-dot subdirectories directly under the root, and `measureTerminalState` at 164-199 uses that list as its entire scope. The design of record section 2.1 and 2.2 says the fifth layer re-instantiates the four layers once per package directory, and its own example places one at `src/auth/`, which is nested. The partition the reverse command decides is nested too: measured, the `DECISIONS.json` for the siprs-for-reverse representative declares eighteen packages with paths such as `src/api`, `src/architecture`, `src/audio`, `src/runtime`, `src/state`.
The arithmetic shows the consequence. The inventory is eleven root artefacts plus eight per package. For siprs-for-reverse the record reports `packages: 5` and `missing: 50`, which is 5 times 8 plus 11 minus one present. Counting the eighteen declared packages instead gives 17 times 8 plus 11, which is 147. The recorded figure is roughly a third of the scope the design describes, so the instrument cannot yet witness the state it exists to witness.

### Motivation
Every claim about reaching the terminal state rests on this measurement. `TERMINAL-STATE.json` is the record the design cites in section 7.3, and `terminal-state.mjs` is the module the ladder position is derived from. An instrument that under-counts its own scope turns a false positive into a machine verdict, which is the class of error section 2.4 names when it says a zero can be a signal of abnormality rather than of health.

### Constraints
The scope must remain derivable without the manifest when the manifest is absent, because the instrument is also run over a bare fixture tree in its unit tests and over a tree whose manifest has not been written. The existing `manifestPresent` and `prior` fields already record that distinction, and the fix must keep a tree with no manifest measurable rather than refusing it, which section 1.2 forbids in any case.

### Out of scope
Driving any representative to the terminal state is not attempted. This ticket makes the instrument able to report the arrival correctly; whether any representative arrives is real-project validation, and the record already states that all four stop at a named gate.

## Acceptance Criteria

- **[Happy path]** A tree carrying every artefact for every declared package, including nested ones, reports `complete: true` with an empty `missing` list and records that the scope came from the partition; the regenerated `TERMINAL-STATE.json` counts the declared packages for each representative rather than the top-level directories; and the terminal-state unit and integration suites pass.
- **[Error case]** A partition naming a path absent from disk is reported as that condition; an unreadable manifest is reported by name and never folded into the fallback; a tree missing one artefact in one nested package reports the scope and the artefact.
- **[Edge case]** A package at path `.` is measured at the root. A tree measured with no manifest falls back to the walk and says so, and its state is distinguishable from a partition measurement. An empty partition reports the root artefacts alone rather than reporting complete.

## Invariants

- [Normal condition] The scope is the partition the manifest declares when one is supplied, and the directory walk only when it is not.
- [Error invariant] An unreadable or absent-path partition is reported as itself and never folded into the fallback or into a clean result.
- [Internal state invariant] The state records which scope source was used, so the two measurements are never confused for one another.
- [Boundary invariant] A package at path `.` is measured at the root; an empty partition reports the root artefacts alone.

## Boy Scout Rule

Function names as verb phrases: `packagesUnder` becomes `directoriesUnder` for the fallback, and the partition reader is `packagesFromPartition`, so a call site says which question it answers.
Variable names as domain concepts: `scope` and `artefact` already name their domain; the scope source is `scopeSource` with two named values rather than a boolean.
One function one responsibility: deciding the scope list, building an artefact path, and judging completeness are three functions rather than one.
Hardcoded values as named constants: the two scope source values join `TERMINAL_ARTEFACTS` as named constants rather than string literals at the call site.
No error swallowing: an unreadable manifest propagates as a named failure instead of returning the fallback silently.
Outside the scope: the comment at 140-147 explains two paths for two scope kinds and stays true after the change; it is reread and corrected rather than left to rot.
