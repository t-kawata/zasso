# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P25-4: The operational path carries no project-specific value, and the library verification is established

**Ticket Key**: P25-4 · **Phase**: 25

---

## Background

### Goal
Remove the one project-specific value that reaches runtime code on the operational path, and establish the branch coverage of the reverse library so that its correctness is a measurement rather than an assumption.

### Purpose
Measured, exactly one project name appears as a value in code reachable from the operational entrance. `red-reconstruction.mjs:129-135` declares `PRODUCTION_MARKERS` as `["production", "prod/", "live", "cluster", "siprs-with-4layers"]`, and `assertNoProductionTarget` at 282-296 refuses a mutation plan whose target reference contains any of them. The module is imported directly by `scope.mjs`, so the guard runs on every operational analysis.
The defect is not that the guard is too strict; it is that a deny-list tuned to one project protects that project and leaves the others. A tree that must not be mutated is refused only if its path happens to contain one of the other four markers. The same shape was already corrected once in this tree: P23-5 replaced the module-level `PRODUCTION_PATHS` in `sandbox.mjs`, which named the two experiment trees, with an empty default plus a caller declaration through `resolveGuardedPaths({ subjectRoot, declared })`. `red-reconstruction.mjs` still carries the earlier form.
The second half is a gap rather than a defect found: every module in the reverse library is exercised by some test, but the coverage of its branches has never been measured. The project standard treats an implementation whose correctness cannot be proven as invalid, and c8 is available, so the measurement is the work.

### Motivation
The instruction under which this phase exists is that no implementation may be optimised for one project. This is the only place where that instruction is violated in runtime code. It is cheap to fix and the correct shape already exists in the tree, so leaving it would be leaving a known violation in the one path every project must traverse.

### Constraints
The guard must keep refusing what it refuses today for the trees it protects. The experiment trees are this repository own material, so their protection is legitimate and moves to the experiment configuration rather than disappearing. The primary isolation is unchanged: a plan executes in a disposable worktree and the guarded tree is digested before and after, so the marker check is a second line rather than the only one.

### Out of scope
No behaviour of the reverse analysis changes for any subject. The ecosystem table and the language collector set remain as they are: measured, a subject outside them is reported by name and the run continues, which is the designed degradation and not an optimisation for any project.

## Acceptance Criteria

- **[Happy path]** `assertNoProductionTarget` refuses each of the four generic markers and admits a target that carries none; a declared set refuses its entries when supplied and not when omitted; `red-reconstruction.mjs` exports no project name as a value; the sweep over the operational closure finds none in a run of the real pipeline; and the reverse library branch coverage meets the stated threshold with the gate applied.
- **[Error case]** A target reference that is not a string is refused by name; a declared entry that is not a string is refused at the boundary; the sweep fails when a fixture carrying a project name is introduced into the closure, so it is shown falsifiable rather than vacuous.
- **[Edge case]** An operational caller declaring no set is a legitimate caller and refuses only the generic markers. A reference equal to a marker and one merely containing it are both refused. The threshold assertion fails when coverage drops below it, so the gate is live.

## Invariants

- [Normal condition] The guard admits every plan whose target is the isolated environment and whose reference carries no marker.
- [Error invariant] A declared entry that is not a string is refused at the boundary rather than compared and never matching.
- [Internal state invariant] No module reachable from the operational entrance exports a project name as a value.
- [Boundary invariant] An empty declared set refuses the generic markers and is a legitimate operational configuration, not a missing one.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — P25-4 to red-reconstruction.mjs assertNoProductionTarget

- **Precondition**: A plan entry is supplied whose target carries a kind and a reference, together with a declared set that may be empty.
- **Postcondition**: The entry is refused when its kind is not the isolated environment or when its reference contains a generic marker or a declared entry, and admitted otherwise.
- **Invariant**: The declared set is an input with an empty default, and no project name is compiled into the module.

### C002 — P25-4 to tests/workspacify-reverse operational-closure sweep

- **Precondition**: The import closure from the operational entrance is computed in the same run that the sweep reads.
- **Postcondition**: No runtime value in the reachable modules equals or contains a project name, and a fixture that carries one is reported by name.
- **Invariant**: The sweep is driven by a positive fixture, so an empty result is a finding rather than a vacuous pass.

### C003 — P25-4 to the coverage gate

- **Precondition**: The reverse library is executed by its own suite in the same process that the coverage tool instruments.
- **Postcondition**: Branch coverage over `.claude/scripts/workspacify-reverse/lib` is measured and compared against the stated threshold, and a figure below it fails.
- **Invariant**: The measurement is over the library and not over the tests, and the threshold is applied rather than reported.

## Boy Scout Rule

Function names as verb phrases: `assertNoProductionTarget` keeps its name and gains an input; the reader for the declared set is named for what it returns rather than for where it came from.
Variable names as domain concepts: `declared` and `guarded` are already the domain words in the sandbox module, and the same words are used here rather than new ones.
One function one responsibility: deciding the refusal, rendering it, and collecting the declared set are three functions.
Hardcoded values as named constants: the four generic markers stay a named frozen list; the project-specific set becomes an input rather than a constant.
No error swallowing: a non-string reference or declaration is refused by name rather than compared and silently not matching.
Outside the scope: the comment above the constant is rewritten because the change makes the old one false, which is the rule the project applies to comments as code.
