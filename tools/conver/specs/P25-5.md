# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P25-5: The integration suite runs the pipeline once per tree rather than once per test

**Ticket Key**: P25-5 · **Phase**: 25

---

## Background

### Goal
The workspacify-reverse integration suite performs each distinct pipeline run over a real tree once per suite run instead of once per test that needs one, so the measured 174.7s wall time falls and the suite can return to the routine run.

### Purpose
The suite exists to hold the reverse instrument to its invariants over the real inputs. It currently pays for that by re-running the whole pipeline inside every test that needs a published run: `analyzeProject` costs about 23s over `siprs-for-reverse` (1.1G / 7,945 files) and about 70s over `siprs-with-4layers` (3.0G / 22,042 files), and those figures are recorded in `pattern-detection.test.mjs:19`. Measured 2026-09-15 with the spec reporter, the top fifteen tests sum to 686s of 775.3s of test time, and every one of them is the same shape — a full run over a real tree.

### Motivation
The suite is deferred from the routine run by commit `4d0d7b3f`, which measured it at 156s and named a single representative-tree test at 161s. A guard that is deferred is a guard that does not run on the routine path, so what it would catch is found at release instead. Recovering the time is the precondition for returning it, and no assertion has to be weakened to get it.

### Constraints
- No test's assertions may be weakened, deleted or reordered to obtain the saving. The implementation must conform to the tests.
- A run must not write into the tree it measures; runs publish into a scratch directory passed as `out`. A shared run must preserve that.
- `node --test` gives each test file its own process, so the duplication is across files and no in-memory sharing is available. Any sharing must be on disk.
- Files run concurrently — the 2026-09-15 run reported 426% CPU — so a shared run must be safe when two files request the same one at the same moment.
- The measurement must remain a measurement. A shared run handed to a test must be byte-identical to the run that test would have produced itself, or the sharing converts a measurement into an assumption.

## Scope

- Scope of changes — path: `tests/workspacify-reverse/helpers/shared-run.mjs`
- Scope of changes — action: add
- Scope of changes — detail: a new helper exporting `requestPipelineRun({ root, through })`, `disposeSharedRuns()` and the run-directory marker protocol. It materialises one pipeline run per `(root, through)` under a shared root and returns the directory, executing `analyzeProject` only when no completed run for that key exists.
- Scope of changes — before/after: before, each test that needs a published run allocates its own temporary directory, calls `analyzeProject`, and removes it — `pattern-detection.test.mjs:52-66` is the named form of this and the other files hold it inline. After, each test calls `requestPipelineRun` and reads what it published; the allocation and the run happen once per key.
- Scope of changes — API contract change: none to the pipeline. `analyzeProject` is called with the same arguments it is called with today; the helper adds a caller-side protocol, not a library interface.
- Scope of changes — data schema change: none. The artefacts a run publishes are unchanged in name and content; only how many times they are produced changes.
- Scope of changes — config change: the shared root's location, declared as a named constant. Its value is an open item; both candidates are named in `notes`.
- Scope of changes — dependency added/removed: none. `node:fs`, `node:os` and `node:path` cover it.
- Out of scope — item: `tests/workspacify-reverse/unit/r0-r2.test.mjs`'s roughly twenty-five `analyzeProject` calls.
- Out of scope — why: they run over synthetic trees built by `createSyntheticTree`, whose cost is milliseconds. Moving them would add churn to the largest unit file for no measurable saving; the measurement is what excludes them, not convenience.
- Affected areas — component: the ten integration files that call `analyzeProject` or spawn `run.mjs` over a real tree, and the deferred integration suite as a whole.
- Affected areas — nature: performance only. No artefact's content, no assertion's strength, and no library behaviour changes.
- Affected areas — response needed: yes — each affected file is edited to call the helper, and the suite is re-measured so the saving is a recorded figure rather than a claim.

## Investigation

Measured 2026-09-15 by running the deferred suite once with `node --test --test-reporter=spec` over `tests/lib/test-discovery.mjs`'s expansion of `tests/workspacify-reverse/integration`: 224 tests, 775.3s summed test time, 174.7s wall, 576.4s user, 426% CPU, exit 0. Slowest single tests: 155.60s (`pattern-detection.test.mjs`, "a full run over each of the four representatives"); 95.59s; 61.25s; 46.90s; 44.55s; 40.82s; 36.00s; 35.55s; 35.04s; 34.85s; 30.86s.

Call sites that reach the real trees through `analyzeProject` — `integration/r0-r2.test.mjs:66,123,130,431` (all `root: REVERSE_ROOT`), `integration/r6-r6.5.test.mjs:271`, `integration/r7-r8.test.mjs:256,277,376`, and `integration/pattern-detection.test.mjs`, which runs four representatives of which two are the real trees. `unit/r0-r2.test.mjs` also calls it about twenty-five times, but over synthetic trees, so it is not part of this cost.

Three structural facts bound the design. First, `scope.mjs:1601` computes `const artefacts = listArtefacts(scope.root)` once per run and injects it into `detectPattern`, `classifyArtefacts` and `discoverBuildDatabase`, so a run's cost is one walk and not a repeated one; the cost is therefore the run itself, not a missing memo. Second, `node --test` starts each test file in its own process, so `r0-r2.test.mjs` and `r7-r8.test.mjs` cannot share a value through a module — measured indirectly by the 426% CPU figure, which only arises from concurrent file processes. Third, the two big trees are tracked files of this repository and are not skipped, by design: `pattern-detection.test.mjs:15` states that a run reaching three of four representatives would be the silent narrowing the file exists to prevent.

## Acceptance Criteria

- Happy path: the suite runs with every real-tree assertion intact, each distinct (root, stage) pipeline run is executed once, and the wall time of `tests/workspacify-reverse/integration` is materially below the measured 174.7s. The evidence is the re-measured spec-reporter run, recorded with both figures.
- Error case: a request for a root that does not exist, or for a stage the pipeline refuses, fails at the requesting test with the root and stage named, and leaves no directory that a later test could read as a completed run.
- Edge case: two test files request the same (root, stage) concurrently, as the 426% CPU figure shows they do. Exactly one pipeline run is performed, the other waiter reads the completed directory, and both receive byte-identical output.

## Invariants

- [Normal condition] A shared run is produced by executing the pipeline, never by copying a fixture or a previously frozen artefact. The directory a test reads is one `analyzeProject` published during this suite run, or one whose inputs are proven identical to what the requester asked for.
- [Error invariant] A request that cannot produce a run — a missing tree, a stage the pipeline refuses — fails by name at the requesting test, and no partial directory is left where a later test would read it as a whole run.
- [Internal state invariant] The shared root is never inside a measured root. Every path the helper writes lies outside every path it reads, which is the same rule `analyzeProject` already enforces for `out`.
- [Boundary invariant] Stage is part of the run's identity. A request for `through: 'r8'` over a root never receives the output of `through: 'r6.5'` over that root, and a request for a stage the pipeline does not know fails rather than falling back to a neighbour.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — P25-5 — the shared run is a measurement and not an assumption

- **Precondition**: Two callers in two test files request the same `{ root, through }`, with `root` naming a directory that exists and `through` naming a stage `analyzeProject` accepts. Both callers run in separate processes, and no run for that pair has been produced in this suite run.
- **Postcondition**: Exactly one `analyzeProject` execution occurs for that pair. Both callers receive a path whose file names and file bytes equal those a fresh `analyzeProject` call with the same arguments would publish. The second caller's read is the same bytes as the first's.
- **Invariant**: No path the helper writes is inside any path it reads, and no caller observes a directory that is still being written: the marker file that names the completed stage is written only after the pipeline has returned, and a reader that finds no marker does not read the directory.

### C002 — P25-5 — stage is part of the run's identity

- **Precondition**: Two callers request the same root with different `through` values, both accepted by the pipeline.
- **Postcondition**: Each receives the output published for its own stage. The two directories differ in the artefacts the later stage adds, and neither caller receives the other's directory.
- **Invariant**: For every request, the directory returned was produced by a run whose `through` equals the requested `through`. A request whose stage is unknown to the pipeline raises rather than being served by a neighbouring stage's directory.

## Boy Scout Rule

The extraction this ticket performs is itself the translatability fix. `integration/pattern-detection.test.mjs:52-66` currently holds `scratchDirectory(prefix)` and `runsOverEverything({through, prefix})`, and the same `mkdtempSync` + `analyzeProject` + `rmSync` shape is repeated in each of the calling files, unnamed and inline. It moves to `tests/workspacify-reverse/helpers/shared-run.mjs` as a verb-named function — `requestPipelineRun({ root, through })` — with `disposeSharedRuns()` beside it, so a reader of any integration file sees one sentence ("ask for the run, read what it published") instead of the allocation ritual. The file-scoped temporaries each caller currently names differently are renamed to the domain term the helper uses. No change is made to library code: `scope.mjs` and `analysis-tech.mjs` are P25-6's subject, and touching them here would put a library change and a test-structure change in one review.

### Exceptions

- Item: the wall-clock saving itself is not asserted as a threshold in any test. Reason: the saving is not testable as a duration bound, because such an assertion is machine-dependent and fails on a loaded or slower host for reasons unrelated to this ticket — the exempted quantity is non-deterministic. This is not a design defect: the behaviour this ticket delivers is a deterministic count of distinct pipeline runs, which is asserted exactly, and only a redundant duration restatement is exempted. It is not an architectural defect either, because the property is measurable and is measured by hand. Alternative verification: the distinct-run counter is asserted exactly; the wall time is re-measured and recorded in `changes` beside the 174.7s baseline, which is what the acceptance criterion names.
- Item: cross-process concurrency — two `node --test` file processes requesting the same run — is not reproduced inside the unit suite. Reason: that interleaving is not testable in a single-process suite without spawning a second runner, which would cost more than the behaviour it checks; the boundary is the test process, not the design. This is not a design defect and not an architectural defect: the cross-process mechanism is a marker file written after the pipeline returns plus an atomic rename, that mechanism is exercised with two worker threads in one process, and the integration run exercises the real case. Alternative verification: worker-thread interleaving in the unit suite, plus the integration run over the real trees.
- Item: the byte-identity of a shared run is not asserted for every artefact the pipeline can publish. Reason: an exhaustive list of artefacts is not testable as a fixed set, because the pipeline's output changes shape as stages are added and the list would rot into a second copy of the pipeline's contract. This is not a design defect: identity is testable and is tested. It is not an architectural defect either, because the comparison is made over the whole published tree rather than over named files. Alternative verification: the unit test compares whole directory trees file by file, which covers every artefact the stage currently publishes without naming any of them.

### Risks
The saving depends on how many distinct (root, stage) pairs the suite actually needs, and that number is not yet measured — the call sites imply about a dozen requests but fewer distinct keys. If the distinct count is small the saving is large; if every test asks for a different stage the saving is small and the ticket should be re-scoped rather than forced.

### Caveats
A shared run makes the suite's tests order-dependent in a new way: a defect that only appears on the second run of a stage would no longer be exercised. The helper's marker file and the counters in `instrumentation` are what make that visible, and the first-run-only behaviour it removes was never asserted by any test — no test asserts that a run is fresh.

### Open items
Whether the shared directory should live under the system temporary directory or under a suite-local ignored path. Temporary is cleaner; a suite-local path survives a killed run and makes a stale directory inspectable, at the cost of a cleanup rule.

### Future improvements
If the distinct-run count turns out to be large, the next step is not more caching but asking why so many stages need a real tree at all: a stage whose invariants hold over a representative fixture does not need the 3.0G tree.

### The acceptance criterion was NOT met, and the measurement says why

The happy-path criterion asked for the integration suite's wall time to fall materially below the 174.7s baseline.

| | before | after |
|---|---|---|
| wall clock | 174.7s | **169.8s** (−2.8%) |
| user CPU | 576.4s | **510.7s** (−11.4%) |
| distinct runs executed | ~13 over the real trees | **7** (11 entries including fixtures) |

The change does what it says — six duplicate executions are gone and the CPU time shows it — but the wall clock barely moved, and the reason is structural rather than a tuning miss. Wall time is set by the slowest file, not by total work, and `pattern-detection.test.mjs` is that file: its full-run test requests r8 over both real trees and pays their sum (112s) because it is the first to ask. Every other file that wants those runs now waits on the lock instead of building its own copy, which converts duplicated parallel work into serialised waiting: the same wall for the waiter, minus the CPU. Requesting the four representatives concurrently was tried and made it worse (146s, disk contention), so it was reverted.

A second effect is worth recording because it is new coupling rather than a saving: `r7-r8.test.mjs` IT-1 went from 35.5s to 140.4s, since it now waits for a run another file is building. Sharing put one file's duration on another file's progress.

The conclusion the measurement supports: the suite cannot be made materially faster by sharing runs. It can only be made faster by making one run cheaper, which is P25-6's subject — a full run costs 23s over a 1.1G tree whose source is 2.0M and whose 154 `.rs` files sit beside 2,879 `.o` and 1,172 `.h`.

### Measured while implementing

- **`outcome` cannot cross a process.** A run read from disk in another process has no in-memory return value, which is what forced every reading onto a published artefact. Checked with `isDeepStrictEqual` before rewriting, not after: the artefact and the return agree exactly, differing only in JSON key order.
- **Concurrent requests over one disk are slower than sequential ones here** (146s against 112s for the four representatives). The helper handles the concurrency correctly — one execution, two identical reads, asserted by a worker-thread test — but correctness is not speed, and the sequential request was kept on the measurement.
- **The annotator cannot distinguish this ticket's edits from an uncommitted backlog**, which put ten false provenance claims one line away from being written into files this ticket never touched.

### Open items

- The acceptance criterion is unmet and P25-5 is closed with that recorded rather than re-scoped silently. Whether to re-express it as a CPU-time criterion, or to treat the wall-time goal as P25-6's to deliver, is a decision the ticket record now has enough evidence to support.
- The shared root persists across suite runs, not only across the concurrent processes of one run. Reuse across runs is sound by the same argument as reuse within one — the key names the instrument — but it means the first run after a library change pays and later ones free-ride. Whether a fresh shared root per suite run is wanted is not decided here.
- The lock has no liveness check: a builder killed mid-run leaves a lock directory and every later request for that key waits five minutes and then fails by name. On a fresh shared root this cannot happen; across runs it can.

### Future improvements

A single declaration point for the shared run root, so the integration suite and `make test` agree about what a run is worth reusing rather than each deriving its own.
