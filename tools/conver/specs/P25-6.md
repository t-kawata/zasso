# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P25-6: An excluded subtree is recorded as one entry rather than descended file by file

**Ticket Key**: P25-6 · **Phase**: 25

---

## Background

### Goal
An excluded subtree appears in the artefact record as one entry that stands for it, rather than as one entry per file inside it, so both a run's cost and the size of the boundary it publishes scale with the source it measures instead of with the build output it has already decided not to measure.

### Purpose
`listArtefacts` (`analysis-tech.mjs:654`) walks into excluded directories rather than skipping them, recording every file it finds; the comment above it states the reason — dropping an excluded subtree would make "we did not measure it" indistinguishable from "it is not there", which is failure F12. `scope.mjs:519-522` declares `target`, `dist` and `build_output` as `BUILD_OUTPUT_KIND_DIRECTORIES` beside `vendor` and `node_modules` in `DEPENDENCY_KIND_DIRECTORIES`. The walk's record is published as `SCOPE-BOUNDARY.json` at `scope.mjs:1832`.

### Motivation
Measured 2026-09-15. A full `analyzeProject` costs about 23s over `siprs-for-reverse` and about 70s over `siprs-with-4layers`, figures recorded at `pattern-detection.test.mjs:19`. The first tree is 1.1G across 7,945 files, of which `target/` is 1.1G and `src/` is 2.0M; its extension census is 2,879 `.o`, 1,172 `.h`, 645 `.c`, 314 `.cc` and 242 `.rmeta` against 154 `.rs`. The frozen artefact that results, `tests/workspacify-reverse/analysis/SCOPE-BOUNDARY.json`, is 1,760KB and holds exactly 7,945 `path`+`coverage` entries, of which 7,785 are `out_of_scope`. So both the run's time and the artefact it publishes are about 98% devoted to files the run has already classified as not measured. This is also what makes the suite slow: P25-5 can only share runs, and each shared run still pays this.

### Constraints
- F12 is not negotiable. An excluded subtree must remain distinguishable from an absent one, so the record must still say the subtree is there. Removing the entries without a replacement entry would be the silent shrink the walk exists to prevent.
- `listArtefacts` is consumed across the library: `claim-ledger.mjs:334`, `dependencies.mjs:132,472,807`, `execution-surface.mjs:285`, `semantics.mjs:1060`, `structure.mjs:369`, `sandbox.mjs:452,504`, `pattern-detection.mjs` and `scope.mjs:1601,700`. Every consumer that reads the entry shape is in scope, and none may be left assuming one entry per file.
- `SCOPE-BOUNDARY.json` is frozen and read by `unit/r0-r2.test.mjs`, `integration/pattern-detection.test.mjs`, `integration/language-representatives.test.mjs`, `integration/r0-r2.test.mjs`, `regression/forward-schema.test.mjs` and `tests/grill-me-for-rfc/reverse/questions.test.cjs`. It must be re-measured and regenerated inside this ticket, with the new entry count recorded.
- The exclusion rule set itself is unchanged: this ticket changes how an excluded subtree is recorded, not which subtrees are excluded.

## Investigation

Measured 2026-09-15. `analysis-tech.mjs:654` `listArtefacts` walks with `readdirSync(directory).sort(compareText)` and pushes one record per entry, with `exclusion: isExcludedPath(relativePath)` computed per file; directories recurse at line 690 and files are recorded at line 700. `isExcludedPath` (`analysis-tech.mjs:632`) splits on `/` and tests each segment against `EXCLUSION_RULES`, which is `NEVER_WALKED_DIRECTORY_NAMES` plus `DEPENDENCY_DIRECTORY_NAMES`; `NOT_ENUMERATED_DIRECTORY_NAMES` is `['.git']` alone, so `.git` is the one directory absent from the record and everything else excluded is present file by file.

`scope.mjs:1601` computes `const artefacts = listArtefacts(scope.root)` once per run and injects it into `detectPattern`, `classifyArtefacts` and `discoverBuildDatabase`, and `classifyArtefacts` (`scope.mjs:692`) accepts an injected `artefacts` and defaults to walking only when none is given. So one run walks once; the 23s is a single walk of 7,945 files plus its classification, not a repeated walk. That measurement rules out memoisation as the fix and leaves the population itself.

Measured population and persisted result: `siprs-for-reverse` is 7,945 files, 1.1G, of which `target/` is 1.1G and `src/` is 2.0M; extensions are 2,879 `.o`, 1,172 `.h`, 645 `.c`, 314 `.cc`, 242 `.rmeta`, 154 `.rs`. `tests/workspacify-reverse/analysis/SCOPE-BOUNDARY.json` is 1,760KB and holds 7,945 entries carrying `path` and `coverage`, of which 7,785 are `out_of_scope`. `DEPENDENCIES.json`, `STRUCTURE.json` and `EXECUTION-SURFACE.json` carry `coverage` but no per-path entries, so the boundary is the artefact whose shape this ticket changes; the other three are regenerated only if the run's inputs to them shift.

## Acceptance Criteria

- Happy path: over `siprs-for-reverse`, the record holds one entry per excluded subtree instead of one per file inside it, `SCOPE-BOUNDARY.json` is regenerated with a materially smaller entry count and byte size than 7,945 / 1,760KB, every in-scope file's entry is byte-identical to the frozen record's, and one `analyzeProject` run costs materially less than the recorded 23s.
- Error case: an excluded directory whose contents cannot be listed is still recorded — once, as an unreadable entry naming the path and the errno — and the run completes rather than failing or dropping the subtree from the record.
- Edge case: a tree holding only an excluded subtree and no in-scope file still publishes a boundary naming that subtree, so the F12 distinction survives in the degenerate case; and a file named `target` is recorded as a file rather than collapsed as a subtree.

## Invariants

- [Normal condition] Each excluded subtree appears in the record exactly once, as an entry whose `path` names the directory, whose `exclusion` is true, and which carries the file count and byte total of the subtree it stands for.
- [Error invariant] An excluded directory whose own contents cannot be listed is still recorded — once, with the reason — and is never dropped. The existing `unreadable` handling for a directory that cannot be listed survives the change.
- [Internal state invariant] Paths in the record remain unique and in the order the walk produces them today, and the number of in-scope entries is unchanged by this ticket: exactly the files a run measures before it, exactly the same files after.
- [Boundary invariant] A directory named `target` at any depth is excluded by segment as today, while a *file* named `target` is not a subtree and is recorded as a file. An excluded directory that is itself the root is not a subtree of anything and is handled by the rule for the root rather than by this one.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — P25-6 — an excluded subtree is one entry, and it is still present

- **Precondition**: A root holding at least one in-scope file and a directory whose name is in `EXCLUSION_RULES`, the directory holding at least one file with a non-zero size, nested at a depth greater than one.
- **Postcondition**: The record holds exactly one entry for that directory: `path` naming it, `exclusion` true, and a file count and byte total equal to what the subtree holds. No file beneath it appears as its own entry. The in-scope file's entry is identical to the entry the current walk produces for it.
- **Invariant**: The subtree is present in the record — an entry names it — so "not measured" remains distinguishable from "not there". No path under the excluded directory appears as its own entry, and no excluded directory is absent from the record.

### C002 — P25-6 — the record's cost is proportional to the measured population

- **Precondition**: Two trees with identical in-scope file populations, one of which additionally holds an excluded subtree of at least two files, the other holding no excluded directory at all.
- **Postcondition**: Both records carry identical entries for the in-scope population. The tree with the excluded subtree differs from the other by exactly one entry, whatever the subtree's size.
- **Invariant**: Adding a file inside an excluded subtree increases that entry's count by one and changes no other entry; the number of entries in the record does not grow with the size of the excluded subtree.

## Boy Scout Rule

The walk in `listArtefacts` is one function holding three responsibilities — list a directory, decide whether to descend, and record an entry — and the third is what this ticket changes. It is extracted so each is named: `recordUnreadableEntry`, `recordFileEntry` and the new `recordExcludedSubtree`. The magic of the entry shape (the string `'file'`, `'directory'`, `'unreadable'`, `'readable'`) is currently written inline at each push site and becomes a named constant set, so the shape this ticket extends is declared in one place rather than spelled three times. The two try/catch blocks that build `unreadable` records by hand — at the directory-list failure and at the stat failure — are collapsed onto the extracted recorder, which is how the same reason string stops being written twice with slightly different wording.

The size measurement is decisive and the count may not fall as far as expected: if the in-scope population of `siprs-for-reverse` is small, the boundary collapses from 7,945 entries to roughly 160 plus a handful of subtree entries, and the walk's own readdir cost falls with it.
