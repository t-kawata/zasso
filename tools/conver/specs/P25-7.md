# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
The reverse rotation no longer serves, probes or declares a search tool: `zg` (zvec-grep) is removed from the entrance, the library, the command file, the environment declaration, the environment record, the tests and the design document; the published artefact the tool's presence once produced is removed with it; and both installed copies are advanced to the source of record, so that no live surface in this repository still names it.

### Purpose
Measured 2026-09-15 against the installed tool itself (`/opt/homebrew/bin/zg` → `@zvec/zvec-grep` 0.2.2, the CLI the declaration's remedy installs):

- **The advertised mode cannot be reached.** `probeZg` is called at `run.mjs:324` with `{ root, query }` and no `mode`, so only `candidate` can run — while `workspacify-reverse.md:198` documents the `--rg` enumeration to the reader.
- **The parser cannot read that mode even if it were reached.** `parseHits` expects `path:line:text` (`zg-probe.mjs:86`), and `zg query --rg` writes the path on one line and `  <line>:\t<text>` on the next. Every row therefore renders as `(no location reported)`, while the section heading states the enumeration is "complete for the literal given" — the `path:line` the command file promises at line 199 is absent for every hit, so the reader is told the literal is located and given no location.
- **The candidate mode needs an index built with a chosen embedding model.** On a tree with no index, `zg query` exits 1 with `ZVEC_GREP.ENGINE.SERVICE.WORKSPACE_INDEX_NOT_FOUND`; `probeZg` passes that stdout through `parseHits` and the report renders it as zero rows with the error text as a note — including an `agent_prompt:` line addressed to whichever agent reads the report.
- **The declaration and the code disagree.** `ENV-DEPS.json` marks the tool `optional: false` for the reverse rotation while the code treats its absence as the normal condition (`zg-probe.mjs:20-23`); `minVersion` is declared and never compared.
- **Removing it costs the analysis nothing, measured rather than argued.** IT-4 ran the entrance twice, with and without the tool on `PATH`: the published documents were byte-identical apart from the candidate file (4 pass / 0 fail, 1,978 ms, 2026-09-15).

### Motivation
A tool that cannot be reached, cannot be parsed when it is reached, and states a completeness the artefact cannot support is not material served beside the analysis — it is a claim the instrument makes on the tool's behalf. The design's own rule is that a missing search must never read as a search that found nothing; the measured behaviour is worse, because the search ran, failed, and its failure was rendered as a table of results.

### Constraints
- No unexcluded heavy test run: `DEFERRED_TEST_PATH` keeps the integration suite out of the routine run, and this ticket's evidence is gathered the same way.
- No test is weakened to make the removal pass. The property IT-4 asserted — the published set does not depend on the environment — is re-expressed for a world without the tool rather than dropped with its subject.
- The installed copies are advanced by the installer, not edited by hand. The installer copies and never deletes, so a file the copies carry and the source no longer has is removed deliberately and recorded.
- Frozen historical records are not rewritten: `specs/`, `tickets/specs/`, past tickets' `changes` and the dated handoff and review documents record what was done and keep their text.

## Boy Scout Rule

The code this ticket touches is `run.mjs`'s argument and entrance surface, which is where the translatability work belongs.

- **`runAnalysisPipeline` holds three responsibilities** — resolve the destination, run the stages, publish and report — and the removal takes the third's tool-dependent part with it. The function keeps its name and its narrative (resolve → run → publish → report), and the report becomes one call rather than two writers interleaved: the stage report, then the destination line. The `candidateSearch` local disappears rather than becoming an unused binding.
- **The refusal gets a verb of its own.** The unknown-stage refusal is a `throw` inside stage selection that `reportStage` renders. The refused option is the same kind of thing — a caller asking for something the entrance no longer does — so it is expressed as the same kind of failure rather than as a branch that prints and returns, and the message names the option the way the stage message names the stage.
- **`VALUE_TAKING_FLAGS` loses a member and gains a reason**: the list is where an option is declared to take a value, and the ticket leaves it holding only the options the entrance reads, so the constant keeps meaning "the switches that consume the next argument" rather than "the switches that once did".
- **The comments this ticket edits are the ones that would otherwise lie.** `run.mjs`'s header (21-23) and `runAnalysisPipeline`'s doc comment (312-315) both describe a serving layer that will no longer exist; they are rewritten to describe the entrance as it is, and no explanatory paragraph is left standing in place of a deleted call.
- **Ownership of the residue scan.** The scan is a test rather than a script, because a one-off measurement cannot guard anything; it lives with the conventions suite, where the other records that hold a document to the repository already are, and it names its exemptions as data so a reader sees what is excluded rather than inferring it from a filter.

 * A reader who meets the name there learns it is gone; a reader who meets it
