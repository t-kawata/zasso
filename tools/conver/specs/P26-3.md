# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is P26-3: `/workspacify-reverse`'s nine Steps each name the script that performs their mechanical half, and the entrance exposes that half on the command line: the pattern, the inventory, the published set, the seam and the report

**Ticket Key**: P26-3 · **Phase**: 26

## Background

### Goal
Every one of the nine Steps of `.claude/commands/workspacify-reverse.md` names, in its `**Run**` line, the command that performs that Step's mechanical half; and every part of the procedure a machine can settle is reachable from the entrance as a subcommand rather than reconstructed by the reader.

### Purpose
Measured 2026-09-17 against the file at `tools/conver/.claude/commands/workspacify-reverse.md` (333 lines) and the entrance at `.claude/scripts/workspacify-reverse/run.mjs`.

Of the nine Steps, **two name a command**: Step 2 (`run.mjs analyze`) and Step 5 (`run.mjs gate`). The other seven carry a `**Run**` line that reads "nothing" and then describes work the reader is to perform by eye:

- Step 0 — "Run: nothing. Read the disk and record what conver scaffolding is present"
- Step 1 — "Run: nothing. Assemble the inventory in your working notes"
- Step 3 — "Run: nothing. The entrance reached R8 in Step 2"
- Step 6 — "Run: nothing. Pattern 1 has no seam"
- Step 8 — "Run: nothing. Report what happened."

**Step 0's work is already implemented and tested, and is unreachable from the command line.** `lib/pattern-detection.mjs` exports `detectPattern({ root, artefacts })` (line 381) and `renderPatternDetection(detection)` (line 428); `lib/scope.mjs:1635` calls them inside stage `r0` and `scope.mjs:1050` publishes the render as `PATTERN.json`. Nothing on the command line reaches either function: `SUBCOMMANDS` (`run.mjs:77`) holds `detect, scrub, verify, regression, holdout, oracle, spike, analyze, gate`, and no subcommand answers "which pattern is this directory". The reader is therefore asked to re-derive by eye what a tested pure function computes, and can only check the reading against a three-minute `analyze` run.

The remaining six Steps have no implementation at all: nothing computes the Step 1 inventory (artefacts found, `Tickets.json` lifecycle statuses, `DesignTree.json`, the existing partition), nothing checks that the destination holds the exit's published set (Step 3) or that the five documents Step 4 reads are present and non-empty, nothing computes the Step 6 seam (the difference between the partition already on disk and the one the analysis fixed), nothing renders the Step 8 report, and Step 5 asks the reader to hand-write `DECISIONS.json` rather than hand the answers to a writer that validates them against `schemas/workspacify-reverse-decisions.schema.json`.

### Motivation
The file states the rule this ticket enforces, in its own first principle: "**Maximise the deterministic analysis.** Whatever can be extracted mechanically is extracted. Fourteen stages run in one command, and you neither run them nor decide when to run them." A Step that answers "Run: nothing" while a pure function for its work sits in the library inverts that principle exactly where it is cheapest to honour.

The reader is an AI forbidden from asking questions (`# CRITICAL — NON-INTERACTIVE EXECUTION`). Prose it must interpret is prose it can get wrong, and a wrong reading of Step 0 or Step 6 is invisible until several rounds later; an exit code cannot be argued with and a printed table leaves a record. The same reasoning that moved fourteen stages into one command applies to the eleven Steps: where a script can answer, the script answers.

Two costs are already measured: the reading is duplicated (the machine re-derives the pattern in `r0` after the reader derived it by hand, and the two disagree only in a document nobody is told to diff), and the check is late (the reader learns the destination is incomplete only when Step 4's prose says a document it cannot find must be missing).

### Constraints
- **The entrance takes no arguments, and its subject is the directory it is run in.** Every new subcommand obeys that: it is argument-free, it reads the current directory, and it joins `ARGUMENT_FREE_SUBCOMMANDS` (`run.mjs:93`) so that a bare path is still refused by name rather than ignored.
- **`USAGE` is the declared surface.** `argument-surface.test.mjs` reads the `USAGE` block and holds the document and the entrance to each other, so a subcommand absent from `USAGE` does not exist and a subcommand documented but undeclared fails a test. The new surface is declared in one place, in the block that already declares the other nine.
- **`analyze` and `gate` keep their behaviour, their output and their exit codes exactly.** They are the two Steps that already work; a working Step is not rewritten to look uniform with the new ones.
- **Nothing writes into the subject.** `analyze` already digests the tree before and after and refuses to publish if a byte moved (`scope.mjs:1833-1837`). The new read-only subcommands must not put that guarantee at risk, and `decide` writes only into the reserved destination, which is a member of the never-walked set.
- **No new dependency.** Every subcommand is a handler over the existing library, in the module system the directory declares (ESM, by extension).
- **The three copies of the command file stay byte-identical**: the source of record at `tools/conver/.claude/commands/`, the repository-root install and the `crates/siprs` install.

## Boy Scout Rule

- **Handlers are verb phrases, one per Step.** `runPatternStep`, `runInventoryStep`, `runDecideStep`, `runStatusStep`, `runSeamStep`, `runReportStep` — each named after the Step it serves, so the dispatch reads as the procedure it implements and a reader can map file section to function without a comment.
- **One responsibility per module.** The library modules are named for the question they answer, not for the artefact they touch: `published-set.mjs` answers "what does the destination hold against what it owes", `seam.mjs` answers "where do the two partitions differ", `inventory.mjs` answers "what is already on disk". A module that grew a second question would be split.
- **The threshold for "partly published" is a named constant.** `status` distinguishes absent from empty from present, and the three are three exported names rather than three comparisons inline, because the difference is the whole point of the check and an inline `length > 0` would hide it.
- **No swallowed errors in what this ticket touches.** The existing handlers return codes; the new ones do the same, and a read that fails produces a finding rather than an empty list. Where `run.mjs`'s tail already states the rule ("a gate's job is to name what is wrong"), the new handlers follow it rather than restating it in a comment.
- **Outside the scope, left cleaner where touched:** the `USAGE` block is one template literal per line, so the six new lines are added in the block's own shape rather than as a second list; the command file's `## Scripts used` table gains a row per new subcommand in the table's existing four-column shape, and the existing rows whose description read "Not used by this procedure" are left as they are.
