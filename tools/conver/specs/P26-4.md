# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make `ORIGIN-LONG-SPEC.json` and the Markdown rendered from it the single aggregation point of the reverse rotation: every finding the fourteen stages produce is present inside the spec, and the other published documents carry nothing that is not also in it.

### Purpose
The next rotation reads the spec. `/workspacify-tree` reverse mode consumes `workspacify/reverse/ORIGIN-LONG-SPEC.md` and `DEPENDENCIES.json` and nothing else, so any finding that lives only in a sidecar is a finding the chain's next command never sees. The spec is also the only document a human reads to judge the analysis, and today it is a flat claim list: four top-level sections (`Scope`, `Provenance`, `Claims`, `Demotions`) with 4,460 claim entries in `claim_id` order, so one directory's semantics are scattered from line 1 to line 62,058 of the file.

### Motivation

The spec is already 62,058 lines — 4.4x `~/shyme/gaia/docs/GaiaSekkeiShiyousho_v31.md` (13,973) and 12x `crates/siprs/RFC-ROOT.md` (5,311) — so the defect is not volume but form: one family of facts (claims) is expanded flat while every other family is absent.

### Constraints
- The claim contract is fixed: four provenance values (`observed` / `inferred` / `normative` / `unresolved`), `observed` requires evidence, `inferred` requires a non-empty `basis`, `unresolved` requires a `grill_question`, `normative` requires the whole provenance chain (`origin-spec.mjs:292-330`).

- Publishing stays atomic: `replacePublishedDocuments(out, documents)` is called once (`scope.mjs:1981`), and a run that stops publishes nothing.
- The judgement surface stays closed to six: `JUDGEMENT_ITEMS` / `DECISION_KEYS` / `readAnswers` refuse a seventh, and `assertJudgementSurface` counts the six numbered items in the command file.
- The existing tree is inviolable; the only writes are into the reserved destination.
- An authored claim may never re-open a measurement: no id collision with a measured claim, no change to a measured claim's `claim_type`, no removal.

## Acceptance Criteria

- [Happy path] A full run publishes `ORIGIN-LONG-SPEC.json` and `ORIGIN-LONG-SPEC.md` in which every one of the 29 published documents is represented: the spec's registered sections cover the whole published set, the Markdown re-parses to the sidecar exactly, the claims are grouped by package so each directory's semantics read as a unit, and `run.mjs status` reports 3 of 3 owed documents present.

- [Edge case] A run shallower than r8 renders the sections its stages did not reach as explicit absences naming the stage, and the round trip still holds; a subject holding no claim at all still publishes a spec whose every section is present and whose claims section states the emptiness explicitly.

## Invariants

- [Normal condition] The spec's registered sections cover the whole published document set in both directions, and the Markdown re-parses to the sidecar exactly — asserted over a fresh run, not a fixture.
- [Error invariant] A refused `--semantics` file leaves the destination exactly as it was: no partial spec, no partially merged claim set, and the refusal naming the entry and the reason.
- [Internal state invariant] No measured claim is re-opened: for every claim the ledger produced, the published spec carries the same id and the same `claim_type`, with the authored claims added beside them and none replacing one.
- [Boundary invariant] A section whose stage did not run is rendered as an explicit absence naming the stage, so two runs of different depth differ in content and not in shape.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — ORIGIN-LONG-SPEC ↔ the published document set

- **Precondition**: a run has published a document set D into the reserved destination, and a spec S assembled from that run
- **Postcondition**: every name in D is registered to a section of S, and every registered projection names a document present in D
- **Invariant**: no document is published that no section carries, and no section names a document that is not published — checked in both directions by `spec-absorption.test.mjs` over a real run

### C002 — renderOriginSpec → parseOriginSpec

- **Precondition**: a spec carrying every registered section, with each section populated
- **Postcondition**: `parseOriginSpec(renderOriginSpec(spec))` is deeply equal to `spec`, so `assertRoundTrip(spec).equal === true`
- **Invariant**: the renderer and the parser agree on every registered section for every spec the run can produce; scope.mjs throws before publication when they do not

### C003 — the ledger's claims ↔ the Markdown's per-package grouping

- **Precondition**: a ledger whose claims carry `scope` values, at least one of which is shared by two or more claims
- **Postcondition**: the Markdown carries each claim exactly once, under the subsection of its scope, in declared scope order and `claim_id` order within each scope; the parser reconstructs the flat list
- **Invariant**: the number of claim entries in the Markdown equals `claims.length`, and the multiset of ids read back equals the multiset of ids in the sidecar

### C004 — --semantics=<path> → the spec's Design semantics section

- **Precondition**: a file holding entries of `{statement, falsification, basis[], scope}`, with `basis` naming claim ids
- **Postcondition**: each entry whose basis ids all resolve and whose falsification is non-empty becomes an `inferred` claim in the `clm-design-` namespace, published inside the spec
- **Invariant**: an entry with an unresolved basis id, an empty falsification, or an id already carried by a measured claim is refused by name and nothing is written

### C005 — the ledger's measured claims ↔ the spec after the authored semantics are merged

- **Precondition**: a ledger of measured claims and a `--semantics` file, admitted or refused
- **Postcondition**: for every measured claim, the id and `claim_type` in the published spec equal the ones the measurement produced
- **Invariant**: an authored claim never shares an id with a measured claim, never changes a measured claim's `claim_type`, and never removes one; a file that tries is refused by name

### C006 — ORIGIN-LONG-SPEC ↔ each registered sidecar document

- **Precondition**: a published spec S and the sidecars the registry projects from it
- **Postcondition**: regenerating each registered sidecar from S alone yields content equal to what the run published
- **Invariant**: a sidecar's content is a function of the spec alone, so no sidecar is the only home of anything

## Changes in Prior Implementation Rounds

| Before | After | Description |
|--------|-------|-------------|
| ORIGIN-LONG-SPEC was built from the claim ledger alone, in four fixed sections (Scope, Provenance, Claims, Demotions); 20 of the 29 documents a run publishes were named nowhere and read by nothing | lib/spec-sections.mjs declares every section and the documents it projects; lib/spec-assembly.mjs builds the spec from the published set, so each section carries the published value verbatim and the closure is checked in both directions | The spec became the rotation's single aggregation point |
| claims were rendered as one flat list in claim_id order, so a package's semantics were spread across the whole document | claims are grouped by package under `## Packages`, each claim once, and the parser reconstructs the flat list in claim_id order | Per-package grouping, proved invertible |
| no way for an engineering reading to enter the spec | run.mjs accepts `--semantics=<path>` and lib/design-semantics.mjs admits each entry as an `inferred` claim with a resolving basis and a non-empty falsification, refusing the whole file otherwise | The AI's design semantics are admitted, and only as inferences |
| the spec's Markdown carried no fenced payloads | carried documents are rendered in three-backtick json fences, with the document's name as a field rather than in the heading | A heading naming CLAIM-LEDGER.json made the next rotation harvest twelve megabytes of JSON as claim candidates |
| lib/markdown.mjs computed line offsets in UTF-8 bytes while every caller sliced the string | lineStartOffsets returns string offsets; headings, segmentation and extraction read them | A two-byte drift over one em dash became a nineteen-thousand-byte drift over fourteen thousand of them, and section bodies began mid-line |
| spec-pulse read identifiers and chapter length from every line, fenced or not | quoted blocks are excluded from the document's prose, so a payload's identifiers are not the specification's | The next rotation no longer reads quoted material as its own assertions |

## Notes in Prior Implementation Rounds

- [Implementation steps] (1) Declare `SPEC_SECTIONS` with heading, producing stage and projected documents, and make the published-set reader and the registry read the same list. (2) Teach the renderer to emit every registered section and the parser to read each back, keeping `assertRoundTrip` exact. (3) Convert the flat claims list to per-package grouping and prove the inversion. (4) Absorb the orphaned families section by section, each with its own round-trip test. (5) Add `lib/design-semantics.mjs` and `--semantics`, then wire it into r8. (6) Add the closure gate and re-measure the design doc.
- [Risks] The round trip is exact and unforgiving: a section whose parse loses one field makes the run publish nothing, so each section is added with its round-trip test before the next. The second risk is scope: absorbing 26 documents is a large single change, and the ordering above is chosen so that each step is independently green.
- [Caveats] `DECISIONS.json` is written by `run.mjs decide` after the run publishes, so the spec's `## Decisions` section can only render what the re-run finds. The section therefore states the absence explicitly when the decisions are not yet written, and the re-run is the mechanism that fills it — the same loop `--semantics` uses.
- [Open items] Whether the absorbed sections should be claims (one uniform contract) or declared sections (one shape per family). This ticket chooses declared sections for the families that are measurements *about* the analysis (capability, attempts, terminal state) and claims for the families that are propositions *about the subject* (gaps, semantics), because a claim that cannot be falsified is refused by the existing validator and that refusal is worth keeping.
- [Future improvements] Once the spec carries everything, the tree could read the spec alone and stop reading `DEPENDENCIES.json`; that is a change to the next rotation's contract and is deliberately left to it.
