# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- [Happy path] A full run over a multi-package subject with an authored semantics file: exit 0; the matrix is closed at every package; the published spec carries one `clm-design-*` inferred claim per reading under its own package in `## Packages`; `## Design semantics` is `recorded` and shows the coverage table, the declined list with reasons, and the source path; `## Decisions` is `recorded` and rendered as a record; every registered document is still carried verbatim; the round trip is exact; and `run.mjs readings` exits 0.
- [Error case] A semantics file leaving one cell unfilled: `run.mjs analyze --semantics=<path>` exits 1, stderr names the package and the item, no document is published, and the destination is byte-identical to what it was. A file naming an unresolvable basis exits 1 and names the id. A declined cell with a boilerplate reason exits 1 and names the phrase. A run whose `stages_run` contains `r8` but which was given no semantics file renders `not-authored` and never says the stage did not run.
- [Error case, ordering] The rotation's closing gates are green after the last re-run: `analyze --semantics=` erases `DECISIONS.json` (measured), so the Step 7 sequence re-runs `decide --answers=` and then `gate` exits 0; a run that stops after the re-run without the closing `decide` has a red `gate` and is not complete, and the spec it published still carries the decisions so the loss is in the destination rather than in the document.
- [Edge case] A package with no measured claims is still a matrix row, closed by declined entries, and appears in the coverage table with zero written cells. A subject with a single package closes and publishes. Declining all 21 items of every package is a legal file that admits zero claims and is refused for nothing. A re-run over the same tree with the same file produces the same spec byte for byte, because the claim id is a function of the cell and the statement and not of the order.

## Invariants

- [Normal establishment] Every cell of `packages x SEMANTICS_ITEMS` is either a reading or a declined entry with a non-empty, non-boilerplate reason, and the two counts sum to the matrix size. A published spec given an authored file therefore carries a semantics for every package, and the `## Design semantics` coverage table reproduces those counts.
- [Invariant on error] A refused file admits nothing and publishes nothing: `claims` is `null`, `analyzeProject` throws before `replacePublishedDocuments`, and the destination is byte-identical to what it was before the run. No partial merge exists at any point.
- [Internal state invariant] No measured claim is re-opened and no measured document is displaced: for every claim in `CLAIM-LEDGER.json`, the published spec carries the same id and the same `claim_type`; every registered document is still carried verbatim, and the projection check (deep equality with the file on disk) still passes.
- [Boundary invariant] The schema is the single authority for the item set and the unit is the package: no code path derives the 21 items from the command file, from a count, or from the authored file itself, and no code path treats the spec as the unit. A subject with one package and a subject with a hundred obey the same rule.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — design-semantics-schema.mjs -> design-semantics.mjs, readings-view.mjs

- **Precondition**: A frozen constant `SEMANTICS_ITEMS` holding exactly 21 entries, each with `key`, `group`, `heading`, `requires` and `checks`; the keys are unique and the groups partition them.
- **Postcondition**: The validator, the locator and the tests each obtain the item list from this constant, so a test can assert that the set the validator enforces is the set the locator prints and the set the schema declares.
- **Invariant**: The 21 keys are a closed set: a file naming an item outside it is refused by name, and no code path derives the item list from anywhere else.

### C002 — design-semantics.mjs -> scope.mjs, readings-view.mjs

- **Precondition**: The package set is the union of the packages `DECISIONS.json` declares under `package_boundary` and the scopes the ledger's claims carry, sorted; it is passed into the validator.
- **Postcondition**: A validated file accounts for every cell of `packages x SEMANTICS_ITEMS`: each is either a reading or a declined entry, and the count of the two equals the size of the matrix.
- **Invariant**: The matrix is over packages, not over the spec: two packages produce two independent sets of 21 cells, and a file that satisfies one package and not another is refused.

### C003 — design-semantics.mjs -> scope.mjs (publication gate)

- **Precondition**: A file in which at least one cell is neither written nor declined.
- **Postcondition**: `validateDesignSemantics` returns `{claims: null, findings}` naming the unfilled cell by package and item; `analyzeProject` throws before `replacePublishedDocuments`; the destination is byte-identical to what it was.
- **Invariant**: Refusal is total: no entry of a refused file is admitted, so a published spec can never carry a subset of an authored file.

### C004 — design-semantics.mjs (thinness checks)

- **Precondition**: A reading whose `statement` reproduces its basis claim's statement, or whose statement appears verbatim in another cell, or whose declined reason is a boilerplate phrase.
- **Postcondition**: Each case is refused with a finding naming the cell and the rule broken.
- **Invariant**: A reading must say something the measurement does not already say; the check is a floor on distinctness, not a judgement of quality, and the command file says so.

### C005 — design-semantics-schema.mjs (per-item checks) -> design-semantics.mjs

- **Precondition**: A schema carrying per-item `checks`; a reading for an item whose check demands a named counterpart, and a package whose measured claims include `boundary_crossing` claims.
- **Postcondition**: `boundary` must account for every `boundary_crossing` claim in its scope; `invariants`, `collaboration`, `impact`, `ownership`, `failure_semantics`, `peers`, `alternatives` and `open_questions` must each name their counterpart, and "none" is expressible while an empty string is not.
- **Invariant**: The per-item checks are derived from the schema, so adding an item with a check adds its enforcement with no change to the validator.

### C006 — design-semantics.mjs -> origin-spec.mjs

- **Precondition**: A closed, admitted file over a ledger of measured claims.
- **Postcondition**: Each reading becomes one `inferred` claim whose id is a function of `{scope, item, statement}`, whose `basis` is the measured claim ids it named, whose `evidence` is empty, and which appears in the published Markdown under its own package among that package's claims.
- **Invariant**: No measured claim is re-opened: no id collision, no `claim_type` change, no removal, and every measured claim's id and type in the spec equal the ledger's.

### C007 — run.mjs (analyze branch) -> analyzeProject

- **Precondition**: `run.mjs analyze --semantics=<path>` with a path that does not resolve, and with a file whose basis names an id no claim carries.
- **Postcondition**: Exit 1, stderr naming the unresolvable id and the cell, and the destination holding no spec.
- **Invariant**: The option is honoured on the entrance: the CLI reaches the same validation the library does, so no acceptance criterion is satisfiable only through the library.

### C008 — spec-assembly.mjs -> origin-spec.mjs

- **Precondition**: A run whose destination holds `DECISIONS.json`, and a run given an admitted semantics file.
- **Postcondition**: `sections.decisions.status` and `sections.design_semantics.status` are `recorded`, the rendered sections carry their material, and `assertRoundTrip(spec).equal` is true.
- **Invariant**: A section whose content is not null is recorded, so no section can carry material and still report an absence.

### C009 — origin-spec.mjs (absence rendering)

- **Precondition**: A run in which `stages_run` contains `r8` and no semantics file was passed.
- **Postcondition**: The `## Design semantics` section says the semantics was not authored and names the Step that authors it; it does not say R8 did not run.
- **Invariant**: The stated reason for an absence is the true one in every case: `not-run` is printed only when the producing stage is absent from `stages_run`. The new status is a first-class value of the section record, not a rendering-only distinction: the parser reproduces it from the published line, because `assertRoundTrip` compares the sidecar to itself and a status the parser normalised back to `not-run` would make the two files disagree.

### C010 — run.mjs readings -> readings-view.mjs

- **Precondition**: A destination holding a published spec and an authored file, with an optional `--scope` and `--item` narrowing.
- **Postcondition**: Markdown naming each requested cell and its state, the basis claim and the `file:line` it anchors to, and a source window of at most `SOURCE_WINDOW_LINES` around each anchor; exit 0 only when the matrix is closed and no deterministic finding remains.
- **Invariant**: The locator judges nothing: it prints no verdict about whether a statement is true of the code, and every finding it does print is a deterministic one.

### C011 — workspacify-reverse.md -> run.mjs (USAGE)

- **Precondition**: The command file after the two Steps are inserted.
- **Postcondition**: The Arguments section names exactly `--answers` and `--semantics`; both Steps exist with a gate and a failure route; the Scripts-used table lists `readings` and the `--semantics` form of `analyze`, and the closure guard finds no subcommand in the runner that the table omits and none in the table the runner lacks.
- **Invariant**: The procedure and the entrance cannot drift: the guard compares them in both directions, and the judgement surface still counts six numbered decisions.

### C012 — workspacify-reverse.md Step 7 -> run.mjs decide / gate

- **Precondition**: A run that has reached Step 7 with `DECISIONS.json` in the destination and a closed semantics file, whose Step 7 re-runs `analyze --semantics=`.
- **Postcondition**: Immediately after that re-run `DECISIONS.json` is absent, because the entrance erases the destination before it writes; after the closing `decide --answers=` it is present again and `run.mjs gate` exits 0; and the spec that re-run published carries `## Decisions` recorded.
- **Invariant**: No Step leaves a later Step's gate red. Every re-run of the entrance is followed by the writes the entrance erases, and the rotation's closing gate is evaluated over the destination as it stands at the end, not as it stood before the last re-run.

### C013 — design-semantics.mjs -> origin-spec.mjs (claim shape)

- **Precondition**: An admitted reading, and a claim shape whose scalar and optional field lists do not include the semantics item.
- **Postcondition**: The published claim carries its `semantics_item`; the Markdown renders it; the parser reads it back; `assertRoundTrip` is exact; and `run.mjs readings` reconstructs which cells are written from the published spec alone.
- **Invariant**: Every field the validator admits is a field the document can carry: no admitted value is dropped between validation and publication, and the round trip is what proves it.

## Boy Scout Rule — Translatability Plan

- `run.mjs`: the option list is read once per branch today, so `optionTokens(second, rest)` is called twice in the fall-through return and the `analyze` branch computes it a third time. Extract the token list into one local binding per branch so the option set is read once and the two returned objects cannot disagree about which options exist.
- `spec-assembly.mjs`: `sectionsFrom` decides `recorded` from a projection count and then asks `contentFor` a second, unrelated question. Rename the decision to what it actually computes — whether the section has material at all — and make it consult both sources in one predicate, so the defect fixed here cannot be reintroduced by editing one half.
- `origin-spec.mjs`: the absence sentence is built by a ternary inside `renderSection` with the two reasons distinguished by `entry.stage === null`. Extract `renderAbsence(entry, spec)` so the three reasons — no stage, stage did not run, stage ran and produced nothing — are three named branches rather than a nested condition.
- `design-semantics.mjs`: `validateDesignSemantics` currently walks the entries once and returns findings as strings built inline. Extract `checkCell(entry, context)` returning a finding or `null`, so the 21 item checks are a table of predicates over one shape and adding an item is data rather than a new branch.
- Hardcoded values touched: `SOURCE_WINDOW_LINES`, `MIN_STATEMENT_LENGTH`, `BOILERPLATE_REASONS` and the two status constants are named where they are used, replacing the literals the change would otherwise introduce.
- Comments: the two comments in `run.mjs` that describe `--semantics` as an option the operator may pass are currently false, because the branch they sit in does not carry it. They are corrected by the change that makes them true; a comment stating a capability the code does not have is the worst case of the rule that a comment must not lie.

### Exceptions

- IT: [Item] whether an authored reading is *good* engineering judgement — whether it names the right invariant, whether the rationale it gives is the true one. [Reason] the property is a judgement about meaning, not a value: no assertion distinguishes a plausible rationale from the correct one, and a test that tried would be asserting a preference, so the item is **not testable** by an assertion. This is **not a design defect**: everything decidable is decided — the matrix is closed, the basis resolves, the falsification is runnable, the statement is not a restatement, the per-item counterpart is named — and the residue is exactly the part a human reviewer reads. [Alternative verification] every reading carries a falsification, so a wrong one is refutable by the same means as a measured claim; `run.mjs readings` puts the reading and the source it must be compared against in one place; and the review reads the published section.
- UT: [Item] whether the AI actually *opens* the source during Step 8, rather than judging from the window the locator printed. [Reason] the window is a locator and the reading of the file is an act; no assertion observes which file a model read, so the act is **not testable**. This is **not a design defect**: the tool is deliberately built to print where to look rather than what to conclude, its output carries `file:line` so the claim is checkable, and the command file states the rule that the window is not the evidence. [Alternative verification] the review samples readings and checks each against the file it names; `readings` prints the anchor so the check is a two-line comparison rather than a search.
- UT: [Item] whether 21 items per package produce prose a Gaia-level reader would call rich, as opposed to 21 filled fields. [Reason] richness of a document is not a predicate any script can compute, and a length threshold would reward padding rather than meaning, so the item is **not testable**. This is **not a design defect**: the schema fixes what must be addressed so nothing central can be silently omitted, the distinctness and counterpart checks remove the mechanical ways of appearing complete, and the remainder is the judgement the tool is explicitly built not to make. [Alternative verification] the acceptance criteria name the comparison to `~/shyme/gaia/docs/GaiaSekkeiShiyoushou_v31.md` and are read by a human; instrumentation records the measured coverage over the real experiment input so thinness is a number rather than an impression.

## Notes in Prior Implementation Rounds

- [Implementation steps] (1) Declare `SEMANTICS_ITEMS` with the 21 items, their groups, their `requires` and their `checks`. (2) Extend `design-semantics.mjs` to the matrix closure and the per-item checks, with the boilerplate list and the minimum statement length as named constants. (3) Fix the three wiring breaks — the `analyze` branch, `sectionsFrom`'s `recorded`, and the absence renderer — because until they are fixed nothing the rest produces can be observed. (4) Add `readings-view.mjs` and the `readings` subcommand, and prove the locator judges nothing. (5) Render the semantics and decisions sections as records. (6) Insert the two Steps as Steps 6 and 7, renumber the three that follow to 8, 9 and 10, and re-measure the anchors, the `step:` fields and the cited lines in the same change; give Step 7 the closing `decide --answers=` and `gate` exit 0, because the re-run it performs erases `DECISIONS.json`. (7) Re-sync the three installed copies. (8) Measure over the real experiment input.
- [Risks] The largest risk is that the gate is satisfied mechanically: 21 fields per package is 357 cells on the real input, and a tired author can fill them with true but empty sentences. The distinctness and counterpart checks remove the mechanical routes, but they cannot remove the last one, and the mitigation is the review reading the published section rather than the exit code. The second risk is the size of the change: the command file renumbering touches the judgement surface, and the anchors must move with it or the guard goes red for the wrong reason. A third is the erasure: every `analyze` wipes the destination, so any future Step that re-runs the entrance inherits the same obligation to re-run the writes it destroyed, and the rule is now stated once in Step 7 rather than rediscovered per Step. The third is that closing the matrix over a subject with many packages multiplies the authored volume, which is the requirement working as asked rather than a defect.
- [Caveats] The decline is a first-class outcome, not a failure: a package with no concurrency genuinely has nothing to say under `concurrency`, and a file that declines every cell of every package is legal and closes. That is deliberate — the alternative forces filler — and it means the exit code alone does not prove richness. The coverage table is what makes the difference between "written" and "declined" visible to a reader, and the review is what judges which declines were honest.
- [Open items] Whether the authored semantics should eventually be re-derived when the tree changes: the current design authors once and re-runs, so a changed tree leaves a reading whose basis still resolves but whose statement may no longer be true of the code — the `falsification` is what a later run would execute to find out. Whether `run.mjs readings` should also be usable as a standalone audit of a spec authored elsewhere is left open; it reads only the spec and the tree, so it already can be, and no caller does it.
- [Future improvements] Once the matrix is proven closed at every package, the next rotation could read the semantics section as the statement of intent to check the code against, which turns the reverse rotation from a description into a specification the forward rotation can be measured against. That is a change to the next rotation's contract and is left to the ticket that takes it.
