# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-118: Add remove-stub.js for fail-safe STUB marker removal and wire usage into start/review/resolve commands

**Ticket Key**: PX-118 · **Phase**: -1

## Background

### Goal
Provide a deterministic, fail-safe script (remove-stub.js) that removes a single resolved [::STUB::] marker line from a source file — and update the three pipeline commands (start-ticket / review-ticket / resolve-ticket) to instruct its use, so that marker removal is scripted and verifiable instead of manual and error-prone.

### Purpose
In the make→plan→start→review→resolve pipeline, resolving a STUB means (a) replacing the stub code with real implementation and (b) deleting the [::STUB::] marker comment line. Today (b) is done by hand-editing source files. There is no removal script, no wrong-line protection, no idempotency guard, and no test. Because find-all-stubs.js reports any line containing [::STUB::], a forgotten or botched manual removal leaves an orphan marker that fails later gates; a wrongly targeted deletion can destroy real code. remove-stub.js exists to make (b) mechanical, validated, and testable.

### Motivation
A repository audit (PX-118 investigation) found: (1) insert-stub.js is defensive (argument validation, ticket-exists check, duplicate-at-line guard, single-line invariant) but removal has no scripted counterpart; (2) the three command files instruct the AI to "remove the [::STUB::] marker" with no tool to do it safely; (3) no test anywhere covers marker removal. The pipeline First-Class Rule and gates already punish unmarked stubs, so the tooling must not be the weak link.

### Constraints
- remove-stub.js is Node.js CommonJS (project standard for .claude/scripts), no new dependencies.
- It must never write Tickets.json or Malfeasance.json; it only edits source files.
- It must never delete a non-marker line (wrong-line guard) nor a line carrying executable code.
- Removal targets only single-line // comments: marker format is "// [::STUB::] <ticket>: <reason> -- <plan>" per validate-stub-format.js / insert-stub.js.
- Follows existing defensive script patterns: insert-stub.js validation style, resolve-ambiguous-markers.js bottom-up editing.
- TDD Red→Green→Refactor is mandatory.

## Invariants

- [Normal condition] Inputs must pass validation before any mutation: --file is a non-empty existing path; --line (or each --lines entry) is a 1-indexed integer within [1, lineCount]. Only then may a line be removed.
- [Error invariant] On any RemoveStubError the target source file is never written — its bytes are untouched. A failed call has zero side effects.
- [Internal state invariant] Line numbers are resolved against a single snapshot read of the file; batch removal processes lines in strictly descending order so earlier line numbers remain valid after each deletion; a marker line is recognized only as a comment-only line (trimmed content starts with "//" and contains "[::STUB::]").
- [Boundary invariant] line 1 and line == lineCount are both valid targets; line 0, negative, NaN, and line > lineCount are rejected; a marker-only file (single marker line) is allowed and its removal yields an empty file; a file ending without a trailing newline is preserved without appending one.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — resolved stub → marker line removal

- **Precondition**: removeStub is called with an existing --file and a 1-indexed --line whose content is a single-line // [::STUB::] <ticket>: <reason> -- <plan> comment
- **Postcondition**: After removal the marker line is gone; every other line (code, comments, blank lines) is byte-identical in content and relative order
- **Invariant**: The file line count decreases by exactly the number of removed markers; no non-marker line is ever modified

### C002 — target line without marker → fail loudly

- **Precondition**: The target --line does not contain [::STUB::]
- **Postcondition**: removeStub throws RemoveStubError, the file is not written, and no line is deleted
- **Invariant**: A line is deleted only if its trimmed content starts with // and contains [::STUB::]

### C003 — code + marker on same line → refuse

- **Precondition**: The target --line contains [::STUB::] but also non-comment code (e.g. `const x = 1; // [::STUB::] ...` or inside a block comment)
- **Postcondition**: removeStub throws RemoveStubError and the file is left unchanged; no executable code is deleted
- **Invariant**: remove-stub.js never removes a line that is not a // comment-only marker line

### C004 — already-removed marker → deterministic result

- **Precondition**: The target --line no longer contains [::STUB::] because a previous call already removed it
- **Postcondition**: removeStub throws RemoveStubError reporting no marker exists at that line — a loud failure, never a silent no-op
- **Invariant**: Repeated invocation never corrupts the file and never reports a false success

### C005 — multiple markers in one file → bottom-up removal

- **Precondition**: --lines accepts an array of 1-indexed line numbers, each holding a [::STUB::] marker, in any order
- **Postcondition**: All specified markers are removed in descending line order so earlier line numbers stay valid; remaining lines keep content and relative order
- **Invariant**: After removal none of the specified lines contains [::STUB::]; atomicity holds — if any line is invalid, no line is removed
