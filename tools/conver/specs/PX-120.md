# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-120: find-omissions: Preflight stub cleanup & No-External-Excuse enforcement

**Ticket Key**: PX-120 · **Phase**: -1

## Background

The find-omissions pipeline does not converge: 63 unresolved [::STUB::] markers in the siprs crate still reference old completed ticket keys (P0-2, P1-3, P3-1, P3-2, P4-2, P4-3, P5-1, P5-2). On the first run of get-next-check-target-ticket.js, create-tmp-omissions.js runs find-all-stubs.js and mechanically clones each ticket by the key written in the marker. Every find-omissions round therefore re-clones past tickets into new todo tickets, and the loop diverges. Root cause: the AI used external dependency and awaiting human approval as terminal excuses instead of converting each blocker into an AI-executable work item (vendor and build PJSIP in build.rs, add cpal as an optional dependency, run bindgen). Absolute rule: there is no external; every blocker is a work item and approval is not a terminal state.

### Goal
Make find-omissions converge: after this ticket, no [::STUB::] marker may reference a past or non-existent ticket key, no marker may carry a terminal excuse (external / awaiting approval) without an AI-executable work item, and the command runs end-to-end without abort.

### Purpose
The marker key is a forward declaration of which future ticket resolves the stub. A stale key breaks provenance and mechanically re-clones past tickets on every round. The purpose of this ticket is to enforce that invariant mechanically and to give the executing AI concrete, self-contained instructions (stdout/stderr) for every required action.

### Motivation
Two implementation rounds already failed to clear 63 stubs and the loop diverged. The previous design allowed terminal excuses (requires external PJSIP, awaiting human approval) which stopped work instead of scheduling it. The user mandated an absolute rule: no external, no approval-shirking; every blocker is internal AI work.

### Constraints
- Generic, not siprs-specific: the validator and preflight must work on any directory plus any Tickets.json.
- The find-omissions command must never abort; it loops validate-fix-revalidate until green.
- New stdout/stderr messages must be English, self-contained, and Action-directive (remove-stub.js Error/Cause/Action pattern).

## Acceptance Criteria

- Happy path: find-omissions on a tree with resolved-but-stale markers removes them via remove-stub.js; excuse stubs are converted to actionable plans or removed; after phasify every marker references an active ticket key; the command completes end-to-end without abort.
- Error case: a stub containing a terminal excuse without a work item fails validate-no-external-excuses.js with exit 1; phasify rejects a merge containing an excuse stub; stderr messages give concrete file:line and an Action directive.
- Edge case: MUST RESOLVE with no key is classified orphan and must gain a ticket key or be removed; a marker referencing a nonexistent ticket is orphan; an excuse phrase WITH an actionable plan passes; a marker referencing an R-round (past) ticket fails Check C.

## Invariants

- [Normal condition] All marker keys extracted by STUB_TICKET_KEY_RE must reference a ticket that exists in Tickets.json with an active status (todo/in_progress/planned/remanded) before any clone is created.
- [Error invariant] On any validation failure, no ticket clone is created and no marker is modified; the pipeline state (Tickets.json and source files) is unchanged.
- [Internal state invariant] The four preflight classes (resolvedCandidates/pendingObligations/orphans/excuses) are mutually exclusive and jointly exhaustive; every stub belongs to exactly one.
- [Boundary invariant] A marker whose resolution plan crosses the actionability boundary (imperative verb present vs absent) is classified deterministically by the verb-plus-deliverable regex, never by AI judgment.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — marker-content to verdict

- **Precondition**: Input is a [::STUB::] marker content string.
- **Postcondition**: Returns PASS or FAIL; FAIL carries the specific failing check and a required resolution.
- **Invariant**: A marker whose content contains a terminal-excuse phrase and no imperative work item always FAILS; a marker with an imperative work item always PASSES the lexicon check regardless of the phrase.

### C002 — marker-key to Tickets.json

- **Precondition**: Tickets.json is parseable and a ticket key is extracted from the marker.
- **Postcondition**: Returns PASS iff the key references a ticket whose status is todo, in_progress, planned, or remanded.
- **Invariant**: A marker referencing a completed (reviewed or R-round), nonexistent, or absent key always FAILS.

### C003 — stub plus Tickets.json to class

- **Precondition**: A valid stub list and parseable Tickets.json are provided.
- **Postcondition**: Every stub is assigned to exactly one of resolvedCandidates, pendingObligations, orphans, excuses.
- **Invariant**: Classification is deterministic; pendingObligations contains only stubs whose key references an active ticket; resolvedCandidates contains only stubs whose key references a completed ticket.

### C004 — clone plus newKey to rewritten stubs

- **Precondition**: phasify clones a stub-derived ticket into a new phase.
- **Postcondition**: The clone stubs[].content ticket key and the source marker line (when --src-dir is given) are rewritten to the new ticket key.
- **Invariant**: No clone in the phasified output carries a marker key referencing a past ticket; a clone with a failing excuse stub is not merged.

### C005 — validate to fix loop to proceed

- **Precondition**: find-omissions is running and stubs exist.
- **Postcondition**: The command proceeds to Step 1 only when validate-no-external-excuses.js passes with zero failures; it never aborts on failures.
- **Invariant**: Each fix round either removes the marker, rewrites its content or key, or creates a resolving ticket, so the loop converges; a round with zero changes yet still failing is a hard-stop diagnostic.
