# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-121: resolve-ticket: No-External-Excuse enforcement & integer step renumbering

**Ticket Key**: PX-121 · **Phase**: -1

---

## Background

The resolve-ticket command is the implementation and resolution phase: the AI resolves warnings, stubs, and crimes here. It currently has three escape points that let the AI be lazy: (1) Step 5 allows deferral for vague reasons without forcing an AI-executable work item; (2) the Step 7.5 escape hatch explicitly lists blocked on external dependency and awaiting another team as valid reasons to defer, which is exactly the terminal excuse the project forbids; (3) the convergence loop checks stub and crime counts but never detects excuse-language markers. This ticket integrates the mechanisms built in PX-120 (preflight-stub-cleanup.js for the resolved-stub sweep, validate-no-external-excuses.js for excuse detection) into resolve-ticket.md as hard gates, renumbers all steps as integers (no decimals, no Step 7.5), and adds creation-time excuse rejection to insert-stub.js so a lazy marker can never be written. The resolve command must never abort: excuse detection enters a validate-fix-revalidate loop until zero excuses remain.

### Goal
Make resolve-ticket converge: after this ticket, every resolve run removes resolved-but-stale markers (Step 4), refuses lazy deferrals (Step 6), and completes only when stub count, crime count, and excuse count are all zero. No terminal-excuse marker can be created or survive a resolve run.

### Purpose
The resolve phase is where the AI has the strongest temptation to defer rather than implement. The purpose is to make deferral structurally impossible without an AI-executable work item and an active ticket key, and to give the executing AI concrete, self-contained instructions (stdout/stderr) for every required action.

### Motivation
The pipeline already diverged twice on the siprs crate (63 stubs referencing past tickets). The same lazy pattern appears in resolve: the escape-hatch text itself teaches the AI that blocked on external dependency is an acceptable reason to stop. The user mandated an absolute rule: no external, no approval-shirking; every blocker is internal AI work.

### Constraints
- Generic, not siprs-specific: applies to any directory plus any Tickets.json.
- The resolve command must never abort; it loops validate-fix-revalidate until green.
- All step numbers are integers (1-10); decimal steps are forbidden.
- The Prohibition (no ticket status changes in Tickets.json) is preserved; deferral uses /make-ticket.
- New stdout/stderr messages must be English, self-contained, and Action-directive.
- TDD: all new script changes follow Red-Green-Refactor with contract coverage C001-C004.

## Acceptance Criteria

- Happy path: resolve-ticket on a tree with resolved-but-stale markers removes them in Step 4; a lazy deferral is rejected in Step 6; the Step 9c convergence loop exits with zero excuses; the command completes end-to-end without abort.
- Error case: a terminal-excuse resolution plan is rejected by insert-stub.js at creation; validate-no-external-excuses.js fails with exit 1 in the convergence loop; stderr gives file:line and an Action directive.
- Edge case: both command docs contain only integer step headings (no decimals); every cross-reference resolves; a marker with an excuse phrase plus actionable plan passes; a marker referencing a past key fails Check C.

## Invariants

- [Normal condition] Every marker created or deferred through resolve-ticket references a ticket with an active status (todo/in_progress/planned/remanded); no marker references a past or non-existent key.
- [Error invariant] On any validation failure no marker is created, modified, or removed; Tickets.json and source files stay unchanged.
- [Internal state invariant] The four preflight classes (resolvedCandidates/pendingObligations/orphans/excuses) are mutually exclusive and jointly exhaustive for every stub.
- [Boundary invariant] A resolution plan crossing the actionability boundary (imperative verb present vs absent) is classified deterministically by the verb-plus-deliverable regex, never by AI judgment.
