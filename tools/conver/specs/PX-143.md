# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-143: Set forNextRound=true in all ticket-creation cores

**Ticket Key**: PX-143 · **Phase**: -1

---

## Background

### Goal
All mid-pipeline ticket creation (start/resolve/find) marks new tickets forNextRound=true so they are excluded from the current round's processing.

### Purpose
Preserve the 1-round-per-invocation boundary of conver.js: tickets added while a round is in progress must not be picked up by the same run's re-fetch waves.

### Motivation
Without the flag, the re-fetch wave design (PX-146) would immediately re-pick find-generated tickets and blur round boundaries. The current runner counts a ticket as reviewed without verifying terminal status, silently leaving holes.

### Constraints
Initial/setup creation (split-to-tickets, add-tickets-for-phase via bulkAddTickets) must NOT set the flag; only mid-pipeline creation paths set it. The shared low-level utility bulkAddTickets is untouched; the flag is set at the mid-pipeline call sites.

## Scope

- [Change] create-ticket-from-source.js stripCompletedResidue() adds forNextRound: true to the cloned ticket
- [Change] generic-ticket-creation.js createTickets() ensures every created ticket carries forNextRound: true for all seed types
- [Change] batch-create-resolving-tickets.js marks created resolving tickets forNextRound: true
- [Change] add-omission-ticket.js marks appended omission tickets forNextRound: true
- [Change] tickets-schema.json adds forNextRound: { type: boolean } to the ticket definition
- [Non-change] bulkAddTickets.js itself is NOT modified (setup utility used by add-tickets-for-phase)
- [Non-change] command definition files (start-ticket.md / resolve-ticket.md / find-omissions.md) are unchanged
- [Impact] create-resolving-ticket.js / create-deferral-ticket.js / create-crime-deferral-ticket.js inherit the flag via the shared core
- [Impact] loadPendingTickets (PX-145) will filter forNextRound===true; this ticket only writes the field
- [Impact] phasify-omissions.js (PX-144) clears the field at round transition; this ticket only writes it
- [Dep] PX-145 (readers), PX-144 (transition), PX-146 (runner) consume this field
- [Schema] tickets-schema.json must keep forNextRound optional (absent = processable)
- [Config] no runtime config change; the flag is a data-level marker

## Investigation

Evidence: create-ticket-from-source.js stripCompletedResidue() sets status='todo' and strips completedAt/startedAt — the natural insertion point for forNextRound: true. generic-ticket-creation.js createTickets() dispatches by seed.type (resolving/deferral/crimeDeferral/bulk) and is the single atomic creation core (C002/C003). batch-create-resolving-tickets.js is find Step 1 and creates resolving tickets. add-omission-ticket.js appends to _tmp-omissions-*.json (PX-100/106). tickets-schema.json is the Tickets.json JSON Schema. bulkAddTickets.js is shared with add-tickets-for-phase.js (setup) and must NOT set the flag.

## Acceptance Criteria

- Happy path: all mid-pipeline creation paths mark new tickets forNextRound===true
- Error case: no mid-pipeline creation writes a ticket without the flag; schema rejects non-boolean forNextRound
- Edge case: absent field on existing tickets is treated as processable; setup creation (bulkAddTickets) is untouched

## Invariants

- [Normal condition] Every ticket created by a mid-pipeline flow carries forNextRound===true and status='todo'.
- [Error invariant] A failed creation (seed validation failure) aborts atomically with zero writes; no partial forNextRound state is observable.
- [Internal state invariant] The shared creation cores (createTicketFromSource / createTickets) produce tickets that pass validate-tickets.js.
- [Boundary invariant] Tickets without forNextRound (absent field) are treated as processable; bulkAddTickets (setup utility) never sets the flag.
