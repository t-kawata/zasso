# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-146: Runner loop: re-fetch waves, retry cap, and break-after-find

**Ticket Key**: PX-146 · **Phase**: -1

---

## Background

### Goal
Restructure runLoop so (1) it re-fetches pending in waves to rescue tickets that did not actually reach reviewed, (2) retries are bounded by --max-retries, (3) find runs exactly once when checkAllReviewed becomes true, (4) the loop breaks after find completes (incl. Slack) and conver.js exits.

### Purpose
When conver auto-terminates, far fewer tickets are left as holes, with no other UX change.

### Motivation
The current loop counts a ticket as reviewed after /review-ticket returns without verifying the terminal status, silently skipping holes.

### Constraints
maxCount stays a per-invocation budget of distinct tickets (retries do not consume it); reviewedCount stays a process-cadence counter (resolveEvery timing unchanged); retry-cap exceed notifies and continues (exit 0); break-after-find makes 1 invocation = 1 round.

## Scope

- [Change] runLoop re-fetches pending at each wave top (while loop)
- [Change] maxCount bounds DISTINCT tickets processed per invocation; retries of already-processed tickets do not consume the budget
- [Change] post-condition check after review: ticket must reach terminal (reviewed or R<round>)
- [Change] per-ticket retry counter bounded by --max-retries (default 3); exceed -> Slack error notify and continue (ticket left as notified hole)
- [Change] reviewedCount increments once per distinct ticket (first processing) preserving resolveEvery cadence
- [Change] find trigger redefined to !noFind && checkAllReviewed()===true (evaluated at resolveEvery boundaries and end-of-wave)
- [Change] after find completes: final resolve -> sendSlackSuccess -> consolidate -> find -> sendFindOutcomeNotification -> return (break)
- [Change] runLoop entry calls clearForNextRound (PX-145) before the first loadPendingTickets
- [Non-change] printCommandHeader and per-command session flow unchanged
- [Non-change] resolveEvery interval semantics unchanged
- [Impact] consumes PX-145 (loadPendingTickets exclusion, maxRetries, clearForNextRound) and PX-143/144 (forNextRound lifecycle)
- [Dep] requires PX-145; best after PX-143 and PX-144
- [Edge] noFind=true: loop exits when pending empty; forNextRound tickets released next invocation by entry safety net
- [Edge] a hard failure (process.exit) still aborts; forNextRound tickets released next invocation by entry safety net

## Implementation Target Files

- `tools/conver/src/runner.ts`

## Investigation

Evidence: runner.ts runLoop currently does pending = loadPendingTickets(...).slice(0, maxCount) then iterates target once, increments reviewedCount unconditionally after /review-ticket, triggers resolve at reviewedCount % resolveEvery === 0 || reviewedCount === target.length, and runs find when !noFind && checkAllReviewed. checkStepDeadline (watcher) gates per-ticket. withSession abstracts ACP sessions, mockable in tests. LoopOptions has maxCount/resolveEvery.

## Acceptance Criteria

- Happy path: when conver auto-terminates, every processed ticket reached a terminal status (no silent holes)
- Error case: a persistently failing ticket exceeds maxRetries, is notified via Slack, and the run still exits 0
- Edge case: 1 invocation = 1 round; after find completes (incl. Slack) the loop breaks and conver.js exits

## Invariants

- [Normal condition] At most maxCount distinct tickets are processed per invocation; every processed ticket reaches a terminal status before find/exit.
- [Error invariant] retryCount > maxRetries notifies via Slack and continues (exit 0); no infinite loop on a permanently failing ticket.
- [Internal state invariant] resolveEvery cadence and per-command session flow are unchanged.
- [Boundary invariant] find runs at most once per invocation; after find the loop returns.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — runLoop wave loop

- **Precondition**: valid LoopOptions (maxRetries >= 1)
- **Postcondition**: at most maxCount distinct tickets processed per invocation; re-fetch excludes forNextRound; loop ends when pending empty, budget exhausted, or after find
- **Invariant**: resolveEvery cadence and per-command session flow unchanged

### C002 — post-condition verification

- **Precondition**: after /review-ticket session returns
- **Postcondition**: ticket verified against Tickets.json terminal status; non-terminal tickets remain pending for the next wave
- **Invariant**: reviewedCount increments only on first processing of a distinct ticket

### C003 — retry cap

- **Precondition**: retryCount[ticket] tracked per invocation
- **Postcondition**: retryCount > maxRetries -> Slack error notify and continue (ticket left as notified hole)
- **Invariant**: no infinite loop on a permanently failing ticket

### C004 — find trigger and break

- **Precondition**: !noFind && checkAllReviewed()===true
- **Postcondition**: sequence final resolve -> sendSlackSuccess -> consolidate -> find -> sendFindOutcomeNotification -> return; loop breaks
- **Invariant**: find runs at most once per invocation

### C005 — entry safety net

- **Precondition**: runLoop invocation starts
- **Postcondition**: clearForNextRound invoked before the first loadPendingTickets
- **Invariant**: stranded forNextRound tickets from an aborted round are released

## Boy Scout Rule

Extract helpers: isTerminalStatus(ticket) for the post-condition check, resolveTicketStatus(ticketsPath, key) to read a ticket's fresh status, and buildRetryTracker() for the per-ticket retry map. Name the wave loop as runRoundWaves(pendingLoader, budget) so the loop's intent reads as prose. Remove the now-dead reviewedCount === target.length condition.
