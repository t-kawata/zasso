# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-149: conver.js EPIPE resilience: conver must not crash on SDK child-process errors

**Ticket Key**: PX-149 · **Phase**: -1

---

## Background

### Goal
Make conver.js resilient to the claude-agent-acp child process crashing with an unhandled `write EPIPE` during session teardown, and make conver surface a fast, phase-attributable error instead of a generic `ACP connection closed` when a child dies mid-command.

### Purpose
The ACP pipeline is currently disrupted by an EPIPE crash in the claude-agent-acp child. The SDK's `nodeToWebWritable(process.stdout)` (utils.js:42-57, used only in `runAcp()` at acp-agent.js:3617) attaches no `error` handler to the wrapped stream, so when conver closes the child's stdout read-end and the child writes again, the socket emits an unhandled `error` event and the child dies. Conver must (1) prevent the child from hitting EPIPE by guaranteeing the child is dead before the SDK `connectWith` teardown closes the pipe (`shutdownChildProcess`), and (2) fail fast with a clear error when a child dies anyway (`runCommand` child-exit race). A process-level crash guard (`installCrashHandlers`) converts any residual unhandled error into a clean, logged exit.

### Motivation
The user observed the raw trace `Unhandled 'error' event / Error: write EPIPE / Node.js v26.5.0` right after the `🟢 /resolve-ticket P13-3: resolve` banner. The run then aborts via the generic error path with phase `unknown`, which is both confusing and unactionable. The parent conver process does not crash today (session.ts:116-117 attaches `on('error')` to proc.stdin/proc.stdout), but the child crash disrupts the run and the resulting error is misattributed.

### Constraints
- The SDK (`@agentclientprotocol/claude-agent-acp` at ^0.52.0) cannot be modified from conver; the defense must live entirely on the conver side.
- `withSession` spawns a real child process (`spawnAgent`, session.ts:71-128), so unit tests must use a mocked `AcpSession` / EventEmitter proc; real-pipe behavior is verified by integration.
- Child shutdown grace must stay short (CHILD_GRACE_MS = 2000ms) so the pipeline is not stalled by teardown.
- Existing error-path contract is preserved: command failures route through notifier.sendSlackError (3 retries) and then process exit.
- The new fail-fast error message must embed the command so runner.ts `getCurrentPhase` (keyword match) attributes the phase without modifying runner.ts.

## Acceptance Criteria

- Happy path: runCommand fails fast (well before timeoutMs) with an Error embedding the command, exit code, and signal when the child dies mid-command; shutdownChildProcess guarantees the child is dead (exitCode !== null) before the SDK teardown closes the stdout pipe, so normal session teardown produces no 'write EPIPE / Unhandled error event' trace; all session.test.ts / conver.test.ts unit tests are green under `make test-conver`.
- Error case: a child exiting via code N or signal S makes runCommand reject immediately with the code/signal in the message; if the child ignores SIGTERM, shutdownChildProcess applies SIGKILL after CHILD_GRACE_MS and still resolves; every command failure still routes through the existing Slack+exit path with the correct phase (the message embeds the command for getCurrentPhase).
- Edge case: runCommand with the child already dead (exitCode set) rejects before session.prompt is called; shutdownChildProcess on an already-dead process returns immediately with no kill/end; disposeSession remains idempotent across multiple calls; a stop completion removes the exit listener so a later child exit produces no unhandled rejection.

## Invariants

### Normal establishment
- The claude-agent-acp child process is alive and responsive while a runCommand is in flight; runCommand resolves with fullResponse only after a stop update.

### On error
- If the child dies before a stop update, runCommand rejects immediately (never waits past timeoutMs) with an Error whose message embeds the command, exit code, and signal — the error is never swallowed.

### Internal state invariant
- shutdownChildProcess leaves the child process dead (exitCode !== null) when it resolves, and never throws (stdin.end / kill errors are swallowed). runCommand removes its exit listener in all completion paths (normal, error, timeout) so no listener leak or delayed unhandled rejection occurs.

### Boundary
- Child shutdown grace is bounded by CHILD_GRACE_MS (2000ms): if the child does not exit within the grace window it is force-killed with SIGKILL. runCommand's fail-fast applies even when timeoutMs is large; the already-dead-child check runs before session.prompt is called.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — runCommand → child-process exit → fail-fast

- **Precondition**: A runCommand is in flight (no stop update received) and the claude-agent-acp child exits with code N or signal S
- **Postcondition**: runCommand rejects without waiting for timeoutMs; the error message contains the command, exit code, and signal
- **Invariant**: On normal stop completion the exit listener is removed (no unhandled rejection); timeout behavior is unchanged

### C002 — session teardown → child termination

- **Precondition**: Session disposal begins while the child process is alive or already dead
- **Postcondition**: When shutdownChildProcess resolves the child is dead (exitCode !== null); if it did not exit within graceMs it is force-killed with SIGKILL
- **Invariant**: shutdownChildProcess never throws (stdin.end / kill errors are swallowed) and is a no-op on an already-dead process

### C003 — conver process → unhandled error

- **Precondition**: An uncaught exception or unhandled promise rejection occurs anywhere in the conver process
- **Postcondition**: The process prints a clear error message and exits with code 1 instead of dying with a raw stack trace
- **Invariant**: The handlers do not interfere with normal operation or the existing main().catch error path

### Risks
A child blocked in a write syscall (pipe buffer full) may not exit on SIGTERM — mitigated by SIGKILL after CHILD_GRACE_MS. Awaited teardown adds up to 2s per session; if the SDK's connectWith teardown ever precedes the finally, the child EPIPE could still occur, so the fail-fast race is the safety net. Replacing the silent `uncaughtException` swallow with exit(1) changes failure behavior from 'silently continue in unknown state' to 'log + exit' — intended, but must be verified against the night-loop use case.

### Caveats
The root cause lives in the SDK's `nodeToWebWritable` (no error handler on process.stdout); conver-side defense is a mitigation. The parent's per-stream `on('error')` handlers (session.ts:116-117) already prevent a parent-side EPIPE crash and are retained. `disposeSession` becomes a thin wrapper over `shutdownChildProcess` and is no longer dead code.

### Open items
Whether the loop should continue (skip the dead session and proceed to the next ticket) instead of exiting on child death — the current runner contract is stop-on-error; continuing is a design change for a separate ticket. Whether `uncaughtException` should send a Slack notification (needs error context that process-level handlers lack).

### Future improvements
Propose an upstream SDK fix: attach an `error` handler in `nodeToWebWritable` (or `runAcp`) so an EPIPE on the child's stdout is a handled disconnect, not a crash. Consider draining the child's stdout during teardown instead of kill-first if telemetry shows the SIGKILL path is hit often.
