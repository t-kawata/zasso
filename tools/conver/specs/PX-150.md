# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-150: conver.js completion resilience: never crash on ACP connection close; reconnect and continue to full completion

**Ticket Key**: PX-150 · **Phase**: -1

---

## Background

The ACP connection closes during resolve-session establishment (observed at P13-3 and P14-3, both right after the resolve banner). Two cascading failures occur: (1) the discarded connectWith return value (SDK runUntil) rejects with 'ACP connection closed' as an unhandledRejection, and PX-149's installCrashHandlers converts it into process.exit(1); (2) the claude-agent-acp child crashes with an unhandled EPIPE while writing its stdout via nodeToWebWritable. The runner also calls process.exit(1) on any session error (runner.ts:480). Requirement: conver must never exit except at a clearly defined completion point; it must reconnect and continue even when the internal ACP connection drops or unexpected errors occur, so the whole ticket set completes unattended (night loop).

### Goal
Make conver.js complete the full unattended ticket run even when the internal ACP connection drops or unexpected errors occur. Concretely: (1) the conver process must never exit on a recoverable session error (connection closed, child crash, EPIPE, timeout) - it disposes the broken session and continues, retrying the affected phase and, if it still fails, notifying and proceeding to the next ticket; (2) no unhandledRejection/uncaughtException may escape the session layer, and the crash handlers log-and-continue instead of process.exit(1); (3) the only exits are clearly defined completion points: all tickets terminal, maxCount budget exhausted, watcher time-window exited, or a startup config error that prevents any progress.

### Purpose
The ACP pipeline is a long unattended 'night loop': the user starts conver, sleeps, and expects every ticket processed by morning. Today a single ACP connection close during /resolve-ticket kills the whole process (PX-149's installCrashHandlers turns the unhandledRejection 'ACP connection closed' into exit(1); runner.ts:480 also exits(1) on any session error). A mid-run crash wastes the night and forces a manual restart. This ticket makes the session layer and the loop resilient so one transient failure never aborts the run.

### Motivation
The same crash has been observed at P13-3 (recorded in specs/PX-149.md) and again at P14-3 (the current report): the raw trace 'write EPIPE / Unhandled error event' plus '致命的エラー (unhandledRejection): ACP connection closed' right after the resolve banner. PX-149 addressed teardown-time EPIPE but not the connection-close at session establishment, and its new crash handlers made any unhandled rejection fatal (exit 1). The user requirement is explicit: the script must never exit except at a clear completion point.

### Constraints
- The SDK packages @agentclientprotocol/claude-agent-acp (^0.52.0) and @agentclientprotocol/sdk (^1.0.0) are external; the fix must live entirely on the conver side.
- The existing error-reporting contract (sendSlackError with 3 retries) and the PX-146 retry/giveUp ticket mechanism are preserved and reused, not rebuilt.
- Session teardown must stay bounded (CHILD_GRACE_MS = 2000ms) so the pipeline is not stalled.
- TDD Red-Green-Refactor is mandatory; the process-level crash behavior must be testable (mock-based), and real-pipe behavior is covered by integration.
- Exit is only allowed at defined completion points; recoverable errors must never reach process.exit.

## Investigation

- Evidence from source investigation (PX-150):

1. Crash output anatomy: the report interleaves two stderr streams. (a) conver: '致命的エラー (unhandledRejection): ACP connection closed' - emitted by installCrashHandlers (src/conver.ts reportFatalError) which then calls process.exit(1). (b) claude-agent-acp child (stderr inherited, stdio:['pipe','pipe','inherit']): 'throw er; // Unhandled error event / Error: write EPIPE' at claude-agent-acp/dist/utils.js:46:28 inside nodeToWebWritable().write() - the child wrote to its stdout after conver closed the read-end; nodeToWebWritable attaches no error handler to process.stdout (utils.js:42-57).

2. unhandledRejection source (the discarded connectWith return value): src/session.ts:186 'app.connectWith(stream, async (ctx) => {...})' - the return value (rawConnection.runUntil(...), SDK acp.js connectWith) is discarded with no await/.catch. SDK jsonrpc.js runUntil: 'const closedPromise = this.closed.then(() => { if (opSettled) return new Promise(()=>{}); throw this.closedReason(); }); return Promise.race([opPromise, closedPromise]).finally(...)' - when the connection closes before the withSession callback settles, runUntil rejects with closedReason() = new Error('ACP connection closed') (jsonrpc.js:647). That rejection is unhandled.

3. SDK 'ACP connection closed' construction points: jsonrpc.js:452 (close() rejects pendingResponses), jsonrpc.js:647 (closedReason()), acp.js:180 (attachSession failUpdatesOnClose -> updates.fail). runCommand consumes the same rejection via nextUpdate (SDK acp.js:471 updates.reject), so the loop error path is reachable once the crash is prevented.

4. runCommand fire-and-forget prompt: src/session.ts:255 'void acpSession.session.prompt(command)'. SDK acp.js prompt() attaches .then(onRejected) internally (line 464-472) so the response promise is nominally handled, but hardening with .catch is still required so no rejection path can escape and the failure surfaces deterministically.

5. runner exits on any error: src/runner.ts:458-481 catch block calls sendSlackError then process.exit(1) (line 480). This is the loop's only error handler; a session failure therefore always kills the run today.

6. Crash handlers exit: src/conver.ts reportFatalError (line 16-20) logs and process.exit(1); installCrashHandlers (line 22-31) registers uncaughtException + unhandledRejection -> reportFatalError; entry.ts installs them before main(). dist/conver.js contains them (minified; '致命的エラー' is the 致命的エラー escape), confirming the deployed binary crashes identically.

7. spawnAgent already guards conver's own pipes: session.ts:124-125 proc.stdin?.on('error',()=>{}) / proc.stdout?.on('error',()=>{}) - conver does not crash on its own pipe EPIPE; the crash is the child's stdout (the child has no handler).

8. child lifecycle: claude-agent-acp/dist/index.js redirects console.* to stderr, registers an unhandledRejection logger, handles SIGTERM/SIGINT -> shutdown() (agent.dispose + exit 0), and connection.closed.then(shutdown). It does NOT handle a stdout 'error' event -> EPIPE crash.

9. PX-149 (787212e3) is an incomplete fix for the same symptom: its spec Motivation records the identical crash at P13-3 right after the resolve banner. It fixed teardown-time EPIPE (kill child before SDK teardown via shutdownChildProcess) and added fail-fast child-exit detection + crash handlers, but did NOT address the connection-close at session establishment, and the new crash handlers made any residual unhandled error fatal (exit 1).

10. Root-cause hypothesis for the resolve-start connection close: the resolve session spawns a fresh claude-agent-acp + claude-code immediately after the previous session's teardown. If the previous claude-code (grandchild) survives teardown (orphaned when the child is SIGKILLed after CHILD_GRACE_MS), it holds the working-directory session, and the new claude-code fails to establish -> the ACP connection closes -> the cascade above. Confirmation needs runtime logs (child exit code / stderr) in verbose mode. This is why the scope includes killing the grandchild at teardown (process-group kill).

## Acceptance Criteria

- **[Happy path] — With an ACP connection that closes mid-session (connectWith/runUntil rejects 'ACP connection closed'), conver survives: withSession rejects cleanly (no unhandledRejection), the session is disposed, the runner classifies the error as recoverable, retries the phase with backoff, and either succeeds on retry or gives up with a Slack notification and continues to the next pending ticket. After all pending tickets are processed (terminal or give-up), the loop returns normally and the process exits 0.**
- **[Error case] — A persistent recoverable failure on one ticket (e.g., every session-establishment attempt fails) retries up to maxRetries, then the ticket is recorded in giveUp with a Slack notification (sendSlackError, phase attributed via getCurrentPhase), and the loop proceeds to the next ticket without exiting. The process never calls process.exit(1) inside the loop for a recoverable error.**
- **[Edge case] — No unhandledRejection/uncaughtException escapes the session layer: process-level crash handlers (installCrashHandlers) log a distinctive '致命的エラー (uncaughtException/unhandledRejection)' line and do NOT exit. The process exits only at a defined completion point: all tickets terminal, maxCount budget exhausted, watcher window exited, or a startup config error that prevents any progress.**

## Invariants

- 【Normal establishment】While a session command is in flight, the conver process holds no pending unhandled promise rejection: every promise created by withSession (connectWith), runCommand (prompt), and the SDK is either awaited or has an explicit .catch/.then rejection handler. The claude-agent-acp child is alive and responsive.
- 【Invariant on error】On any recoverable error (ACP connection closed, child exit, EPIPE, timeout), the conver process survives: the error is caught and routed to the loop error handler; the session is disposed; the child (and grandchild) are terminated; no unhandledRejection/uncaughtException escapes. process.exit is never called from within the ticket loop for a recoverable error.
- 【Internal state invariant】retryCount/giveUp bookkeeping is monotonic and bounded: each ticket's retry counter increments at most once per loop iteration, never exceeds maxRetries before give-up is recorded, and a give-up ticket is not reprocessed in the same invocation. shutdownChildProcess leaves the child dead (exitCode !== null) when it resolves and never throws.
- 【Boundary invariant】Retry/backoff parameters are finite and positive: establishment retries <= RETRY_MAX_ATTEMPTS, backoff delays within [RETRY_BASE_DELAY_MS, RETRY_MAX_DELAY_MS] with bounded jitter; the loop exits only when (a) no pending tickets remain, (b) maxCount budget is exhausted, (c) watcher window is exited, or (d) a startup config error prevents any progress - never mid-ticket.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — session.ts withSession/runCommand -> loop error handler

- **Precondition**: ACP connection closes during withSession or runCommand (child exit, stream end, connection abort)
- **Postcondition**: conver process survives; the failure is delivered to the loop error handler as a caught rejection; the session is disposed; no unhandledRejection escapes
- **Invariant**: No unhandled rejection or uncaught exception escapes the session layer.

### C002 — runner.ts ticket loop -> next ticket

- **Precondition**: A ticket phase fails with a recoverable error (or retries exhausted)
- **Postcondition**: The loop retries up to maxRetries with backoff, then marks the ticket as give-up with Slack notification and proceeds to the next ticket; the process does not exit
- **Invariant**: process.exit is never invoked inside the ticket loop except at a defined completion point.

### C003 — withSession establishment -> retry

- **Precondition**: Session establishment fails with a recoverable error
- **Postcondition**: Establishment is retried up to a bounded number with backoff+jitter; on persistent failure the error propagates to the loop error handler
- **Invariant**: Establishment retry count is bounded.

### C004 — session teardown -> next session spawn

- **Precondition**: Session teardown begins
- **Postcondition**: The claude-agent-acp child and its claude-code grandchild are terminated before the next session is spawned
- **Invariant**: No orphaned claude-code process holds the working directory after teardown.
