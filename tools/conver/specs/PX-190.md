# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Implement the allocation core of /workspacify-allocate: (1) a deterministic model that turns the stage-1 manifest ownership entries and dependency edges into per-package allocation expectations and machine-supplied authoring packets (owned inventory with source excerpts plus neighbor boundary context), (2) an RFC-SEED.md authoring and rendering and parsing contract with 15 required headings and a machine-extractable Allocation Index, and (3) the machine gates that make seed authorship honest: seed-to-manifest bijective parity, per-seed local checks, REVIEW_REQUIRED handling, and an AI semantic-approval presence gate. No CLI composition yet (PX-191).

### Purpose
The corrected stage-2 contract rejects the erroneous doc WIC JSON blocks (doc section 10.4) and Workspace Integration Graph (doc sections 13-14). Instead every package directory must receive exactly one RFC-SEED.md that (a) faithfully carries the normative material stage-1 assigned to that package (objects, claims, invariants, state machines, error codes, required tests) with source traces, (b) records the dependency and forbidden-boundary context copied from the stage-1 manifest (never re-invented), and (c) is dense enough for /grill-me-for-rfc to turn it into that package canonical RFC, after which the per-directory conver 4-loop (grill, graphify, boundify, split, make/plan/start/review) owns further integration. This ticket provides the modules and gates that make those seeds correct, complete, and exclusively owned, without over-mechanizing the AI prose authorship.

### Motivation
A seed that drops an invariant, misplaces an object into a neighbor seed, cites a source ref that does not resolve, or invents an owner that stage-1 never assigned would silently corrupt the per-directory pipeline downstream: grill would build the wrong RFC, graphify would emit edges that contradict stage-1. Because stage-1 already proved ownership/DAG/layer consistency, stage-2 must only prove faithful transfer: no loss, no addition, no displacement. Machines can and must enforce exactly that transfer; they must NOT decide the seed prose semantics.

### Constraints
- Node.js ESM (.mjs) only, stdlib only; no network/hooks/Python. Reuse stage-1 sibling lib by import (hash, canonical-json, normalization, workspace-model, errors, report) and PX-189 readManifestSource. Do not fork those modules.
- Output of this ticket = modules + schemas + tests only; no run.mjs subcommand wiring (PX-191) and no command markdown (PX-191).
- The only machine-readable source of truth for who owns what is manifest.workspace.ownership.entries (category + inventory_ref + owner_package). packages[].owns is a mirror used for cross-checks only.
- Seeds are Markdown consumed by humans and grill. Required headings are fixed and ordered; bodies must be non-empty or explicitly typed not_applicable with a reason; a machine-extractable Allocation Index (Markdown table) must list exactly the owned inventory of that package.
- WIC/WIG/ContractEdge/proof-lifecycle/state-effects/semantic-flow global machinery is explicitly NOT implemented (rejected design). Cross-package facts are copied from the manifest into each seed as context only.
- AI writes the semantic body; machine renders scaffolding, parses back, and enforces parity/local/semantic-presence gates. Machine never fabricates prose; AI never silently drops or moves an allocated item.

## Acceptance Criteria

- **[Happy path] — Faithful seed set for a realistic multi-package manifest:** deriveExpectedAllocation and buildAuthoringPacket produce, for every package, exactly the owned items with excerpts resolving to real co-located spec text plus neighbor edges; renderSeed and parseSeed round-trip recover the same Allocation Index; runSeedParity over all packages reports ok with zero missing/extraneous/crossPackage/duplicate/unknown; seed-local checks pass; decisions.semantic_review.status is APPROVED; every planned directory has exactly one RFC-SEED.md carrying all 15 required headings.
- **[Error case] — A seed that drops, moves, or invents an item must FAIL:** removing one row from a seed Allocation Index, adding a neighbor inventory_ref into a non-owner seed index, duplicating a row, or referencing an inventory_ref unknown to the manifest each yields a non-ok parity report naming the offending package and ref; an empty required heading, a missing/out-of-order heading, or a malformed index table yields a typed seed-parse error; decisions without semantic_review APPROVED or with an unresolved REVIEW_REQUIRED item never render to a publishable seed.
- **[Edge case] — Boundary values:** empty workspace yields zero seeds and ok parity; a package owning zero items still renders a seed with an empty Allocation Index and all required headings; an object + invariant + error_code + required_test mix under one package groups rows correctly; repeated canonical_name occurrences resolve deterministically to the first occurrence; excerpt refs beyond the file yield REVIEW_REQUIRED rather than a crash; rendering identical decisions twice yields byte-identical seeds.

## Invariants

- [Normal condition] A package expected allocation set is exactly the entries of manifest.workspace.ownership.entries where owner_package equals the package id, grouped by category; the union over all packages equals the full ownership entry set with every inventory_ref appearing exactly once across the whole workspace (bijection: no loss, no duplicate, no cross-package placement).
- [Error invariant] On any FAIL/BLOCKED (schema-invalid decisions, parity mismatch, unknown inventory_ref, missing required heading, empty body, unresolvable source excerpt, semantic review not APPROVED, unresolved REVIEW_REQUIRED) no RFC-SEED.md is published and the workspace is left byte-identical to its pre-run state.
- [Internal state invariant] Every rendered seed contains all 15 required headings in the fixed order; the Allocation Index table (section 3) rows equal the package expected allocation set; identity/ownership/index scaffolding is derived deterministically from the manifest and is identical across renders of the same input.
- [Boundary invariant] An inventory_ref appears in exactly one package index across all seeds (exclusivity); a seed never indexes an inventory_ref that stage-1 assigned to a different package; a seed body may mention a neighbor item only as dependency_context or consumer_obligation prose, never as an ownership claim; empty workspace yields zero seeds.
