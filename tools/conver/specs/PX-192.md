# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the stage-1 artifact (WORKSPACIFY-TREE-MANIFEST.json) carry the four facts stage 2 must be able to verify mechanically: (a) the persisted dependency proof (topological order + parallel levels + the canonical edge list it was computed from), (b) a frozen contract-clause vocabulary in which the five core clauses are mandatory for every dependency boundary, (c) proof that the spec segmentation is a total partition of the normalised specification and that every inventory item points at the segment it came from, and (d) non-empty package responsibilities plus a stage2_handoff whose ordering semantics are defined and machine-checked.

### Purpose
Stage 2 (/workspacify-allocate) must write, for every directory, a complete coupling contract (preconditions, postconditions, invariants) and prove that no part of the original long specification was dropped. Both proofs are impossible to compute from stage 1 today: `lib/dag.mjs` computes `topological_order` and then throws it away (only `final_audit.cycle_count` survives), `run.mjs` hardcodes the same unnamed 15-clause list onto every boundary, `structure.segments` totality is implied by `verifyReconstruction` but never stated in the manifest, inventory `source_refs` are line references with no segment identity, and `validation.mjs` merely counts packages whose `responsibilities` are empty.

### Motivation
Workspace coupling is the one artefact whose failure is unrecoverable: a directory whose I/O boundary is under-specified cannot be implemented without inventing an interface that contradicts its neighbours, and a single such directory collapses the whole workspace. The user's standing instruction is that this area decides the fate of the entire development effort, so stage 1 must hand over proof material rather than hints.

### Constraints
- Deterministic only: every new manifest field must be recomputable from the spec plus the AI's structured decisions, and must be reproducible byte-for-byte (canonical JSON, sorted keys, stable tie-breaks).
- No new dependency; Node.js standard library only (project rule from the stage-1 instruction).
- The existing manifest self-hash contract must keep holding: `computeSelfHash` covers the whole manifest, so every added field automatically enters the integrity proof.
- Existing stage-1 behaviour and tests (191 tests under tests/workspacify-tree) must stay green; new fields are additive and every added constraint must be reflected in the tree command document.
- The clause vocabulary is frozen by name: adding a clause later is a breaking change for the stage-2 contract schema and must be an explicit, reviewed edit.

## Acceptance Criteria

- **[Happy path] — A real spec produces a manifest carrying all four proofs:** running the stage-1 CLI over a fixture spec in a temp directory yields status COMPLETE with `dependencies.dag` (edge_count, cycle_count 0, topological_order, levels, canonical_edges), every boundary's stage2_contract_scope containing the five core clauses, `structure.segment_count`/`covered_bytes` reporting a total partition, every inventory item carrying a resolvable `segment_id`, every package carrying responsibilities, a non-empty contract-item `stage2_handoff.contract_definition_order` and a package-level `dependencies.dag.topological_order`/levels that is a valid topological order; the self-hash verification passes on reload.

- **[Edge case] — Degenerate and boundary manifests:** a spec with no level-2 heading (single segment covering the whole document) still yields is_total_partition true with segment_count 1; a workspace with zero packages yields an empty but present DAG proof; a workspace with one package yields levels [[pkg]]; a scope list that repeats a clause is rejected as a duplicate; and a ref whose byte offset falls exactly on a segment boundary is attributed to the segment that contains that offset.

## Invariants

- [Normal condition] A manifest may reach status COMPLETE only if: dependencies.dag is present with edge_count, cycle_count === 0, canonical_edges identical to dependencies.normal_edges in canonical order, topological_order (the existing Kahn order over the persisted edge direction, consumers before providers) and implementation_order whose serial and levels place every provider before each of its consumers; every boundary stage2_contract_scope contains the five core clauses and only vocabulary members; structure.segments partitions the normalised spec with covered_bytes === source_bytes; every inventory item and normative candidate carries at least one source_refs[].segment_id that exists in structure.segments; every package has non-empty responsibilities; and stage2_handoff.contract_definition_order (the contract-item order) is non-empty whenever the inventory declares contract items.
