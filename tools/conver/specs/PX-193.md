# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Rewrite the stage-2 authoring half so that a rendered RFC-SEED.md (a) opens with the section that proves the directory is an independent implementation that is not independent, (b) carries its complete I/O boundary as machine-readable coupling contracts with typed clause groups (preconditions, postconditions, invariants and the rest of the frozen stage-1 vocabulary), (c) proves that every segment of the original long specification is carried by at least one seed, and (d) receives its three reference paths (original spec, WORKSPACIFY-TREE-MANIFEST.json, WORKSPACIFY-ALLOCATE-MANIFEST.json) by machine injection so an AI can neither omit nor rewrite them.

### Purpose
The 15-heading grammar shipped by PX-190 puts integration context in the middle of the document and explicitly forbids a machine-readable contract block; the authoring packet offers only the package's own owned items. Both choices came from the discarded reading of the instruction document that treated the contract machinery as the fatal mistake. The contract machinery is in fact the point: a workspace in which one directory cannot state its coupling completely collapses as a whole, which is why coupling and dependency must be the first thing every seed states and the only thing every gate cross-checks.

### Motivation
Every downstream directory loop (grill, graphify, boundify, split, make/plan/start/review) starts from the seed. If the seed does not carry the counterpart package, the required clause list and the surrounding dependency order, the implementing AI must invent an interface, and invented interfaces are exactly the failure mode this command exists to prevent.

### Constraints
- The stage-1 contract from PX-192 is the input authority: clause names come from the frozen vocabulary, core clauses are mandatory, order comes from the verified DAG proof and is never invented by stage 2.
- Determinism: rendering is a pure function of (manifest, expected allocation, authoring decisions, machine facts); identical inputs must produce byte-identical seeds, and the machine-injected block must not depend on the wall clock, environment or process id.
- A seed must never contain a TODO/TBD placeholder for a coupling or dependency fact; unresolved design choices belong in the grill-questions section.
- No new dependency (Node.js standard library only) and no change to the publish/atomicity model delivered by PX-189/191.
- The three reference paths are written relative to the workspace root so the workspace stays portable, and the allocate manifest is referenced by path only (no hash) to avoid a circular hash with the manifest that records seed hashes.

### Language note
Seed bodies are English (the language the implementing AI reads most reliably); the surrounding command document stays Japanese for the operator.

## Invariants

- [Normal condition] Every rendered seed parses into exactly the 14 required sections in order; its first section carries the machine-injected block (package identity, source spec path and hash, stage-1 manifest path and hash, stage-2 manifest canonical path, implementation order, contract ids, covered segments) and its second section carries the contract edges whose clause sets equal the boundary scopes declared by stage 1; the authoring decisions supply no text for either section.

- [Boundary invariant] Degenerate cases are explicit: a package with no edges renders no_external_contracts with a typed reason and no contract ids; a specification reduced to a single segment is covered by whichever seeds reference it; a package whose boundary scope contains only core clauses renders exactly those clauses; a clause group that genuinely does not apply is written as not_applicable with a reason and at least one segment id.
