# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Add the cross-seed verification layer that turns a set of individually valid seeds into a proven workspace: (a) every declared dependency edge is present as a contract in both the consumer seed and the provider seed with mirror-identical clause content, (b) the extracted contracts form a Workspace Integration Graph whose violations (unknown package, self-loop, duplicate contract id, reverse edge, undeclared edge, forbidden edge, layer violation, cycle, owner collision, proof-lifecycle break, state-mutation conflict, side-effect race, forbidden semantic-flow path, missing test obligation) are all zero, (c) the verified graph yields a deterministic implementation order (serial order plus parallel waves) that must be equivalent to the stage-1 DAG proof, and (d) a walker reads the machine block and the contract block from every RFC-SEED.md in the directory tree so the same verification runs over the published artefacts rather than over renderer state.

### Purpose
The single most dangerous failure of this command is a workspace whose directories cannot actually be coupled: one directory's postcondition that no neighbour can meet, one owner claimed twice, one state mutated by two packages, one forbidden edge that the composition nevertheless requires. Those are invisible per seed and obvious across seeds, so the verification must be a cross-seed proof and must run as a gate, not as an advisory report.

### Motivation
The user's standing requirement is that if the coupling cannot be satisfied the whole workspace is a collapse, and that the implementation order must be derivable mechanically once the contracts are proven. Today stage 2 verifies only allocation parity (seed versus manifest ownership) and never looks across seeds, so nothing prevents a mutually contradictory seed set from being published.

### Constraints
- Verification is read-only over the seeds: it must never repair a seed, and a violation must fail the gate rather than be normalised away.
- Determinism: graph construction, violation ordering and order derivation must be canonical (sorted keys, stable tie-breaks) so that the same seeds always produce the same verdict and the same order.
- The order is verified, never invented: stage 2 derives it and must prove equality with the stage-1 proof; a mismatch is a FAIL even if stage 2's own derivation looks self-consistent.
- No new dependency and no network access; the walker reads only the workspace tree and the manifest.
- Gate identifiers must map onto the stage-1 instruction's gate taxonomy (G4 contract edges/bilateral boundary, G5 WIG, G6.5 re-extraction) so the design stays traceable to the reference document.

### Failure policy
Any violation stops the run before publication and reports the offending contract id, package pair and clause, in English, so the authoring AI can repair the decisions and re-run.

## Acceptance Criteria

- **[Happy path] — A coupled workspace is proven before publication:** for a manifest with several packages and edges, the pipeline reads every staged seed, finds one contract per edge on both sides with mirrored clauses, reports zero violations across every class, derives an implementation order equal to the stage-1 proof, and exposes per-package before/after/parallel_with blocks for injection into the seeds.
- **[Error case] — A contradictory workspace stops the run:** a provider seed whose postcondition is weaker than the consumer's assertion, a contract for an undeclared pair, a cycle among state transitions, a duplicate contract id and an order that diverges from the stage-1 proof each fail with a located violation naming the class, contract id and package pair, and nothing is published.
- **[Edge case] — Degenerate and isolated packages:** a single-package workspace, a package with no external contracts, a core-only clause scope, a seed whose section 1 lacks one of the three references, and a planned leaf without a seed are each handled with the specific message that names the artefact rather than a generic failure.

## Invariants

- [Normal condition] For a workspace to be COMPLETE: every normal edge of the stage-1 manifest appears as exactly one contract in the consumer seed and exactly one mirror contract in the provider seed; the extracted graph has zero violations of every listed class; every clause of every contract carries at least one test obligation; and the derived implementation order equals the stage-1 topological order and levels exactly.
- [Error invariant] A violation never mutates a seed, never rewrites a contract and never publishes: the run exits non-zero with the violation class, the contract id and the package pair, and the workspace remains byte-identical to its pre-run state.
- [Internal state invariant] The graph is a pure function of the parsed seeds plus the manifest: walking the same tree twice yields identical node, edge and violation lists, and the derived order is stable across runs (canonical tie-break by package id).
- [Boundary invariant] Degenerate inputs are explicit: a workspace with a single package and no edges yields an empty graph, an order of one package and a wave list of one; a package declaring no_external_contracts contributes no edges but is still a node; a manifest edge whose boundary scope is core-only yields a contract whose non-core clause groups may be absent with a reason; unknown packages appearing only in a seed are reported as unknown rather than silently dropped.
