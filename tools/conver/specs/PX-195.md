# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Complete stage 2 by publishing, alongside the directory tree and the seeds, the machine final authority WORKSPACIFY-ALLOCATE-MANIFEST.json; by proving after publication that the published artefacts still satisfy every gate (reload: rescan, re-parse, re-extract contracts, rebuild the graph, re-derive the order, re-prove coverage); by removing every intermediate artefact mechanically so the workspace keeps only the tree, the seeds and the manifest; and by rewriting .claude/commands/workspacify-allocate.md so the operator instructions match the corrected design.

### Purpose
Without the manifest the contract verification has no durable, hash-protected record: a consumer cannot tell which contracts a workspace was proven against, and a later change to a seed could not be detected. Without reload verification the manifest would be a claim rather than a proof. Without mechanical cleanup the workspace accumulates staging and intermediate files, which the discarded instruction's 'no extra artefacts' rule correctly forbade but which the corrected design permits only transiently.

### Motivation
The user's requirement is explicit: the coupling must be verifiable one hundred percent mechanically from the stage-1 manifest and the stage-2 manifest together, and intermediate or temporary files are acceptable during the workflow provided the script cleans them up mechanically at the end. This ticket delivers exactly that, plus the operator document that makes the behaviour reproducible.

### Constraints
- The three published artefact families are: the directory tree, the RFC-SEED.md files, and WORKSPACIFY-ALLOCATE-MANIFEST.json. Nothing else may remain at the workspace root after a successful run except what pre-existed (the stage-1 manifest and the co-located specification).
- The reference from a seed to the allocate manifest is one-way (canonical path only) because the manifest records every seed hash; embedding the manifest hash in the seeds would create a hash cycle.
- Publication is atomic with rollback, extending the staging model already delivered by PX-189: a failure leaves the workspace byte-identical.
- Cleanup runs on both success and failure paths and must be idempotent; it must never delete a pre-existing user file, and it must never delete the stage-1 manifest or the specification.
- The command document must stay at least as dense as the stage-1 command document (the density assertion in the command test remains in force) and must not resurrect the discarded framing (manifest as the goal, WIC as forbidden).
- No new dependency; Node.js standard library only.

### Success definition
Success is two-sided: the machine gates all pass on the published artefacts, and the AI records semantic approval; the run reports COMPLETE only when both hold, and never publishes a second time into a non-fresh workspace.

## Acceptance Criteria

- **[Happy path] — A complete workspace is published and re-verified:** from a stage-1 manifest and an approved decisions payload the run publishes the directory tree, one RFC-SEED.md per seed_required package and WORKSPACIFY-ALLOCATE-MANIFEST.json; the manifest self-hash verifies, its seed_index hashes match the files, the coverage proof reports zero uncovered segments, the reload pass reproduces the contract registry, graph hash, implementation order and coverage, and the residue check reports exactly the published set.
- **[Error case] — A failure publishes nothing and leaves no debris:** a gate failure, a reload divergence, a manifest self-hash mismatch or an interrupted publish leaves the workspace byte-identical to its pre-run state, removes the staging root and every intermediate file, and reports the failing gate with the located artefact; a second run against an already-published workspace is BLOCKED rather than merged.
- **[Edge case] — Degenerate and boundary workspaces:** a single-package workspace publishes a manifest with a one-entry seed index and one wave; a package with no external contracts appears in the registry with no contract edges; a workspace whose plan is empty is refused by the fresh-workspace policy; a stale staging directory from an interrupted run is cleaned without touching published content.

## Invariants

- [Normal condition] A run reports COMPLETE only if: every earlier gate passed, the derived implementation order equals the stage-1 proof, the coverage proof shows zero uncovered segments, the published allocate manifest re-hashes to its recorded self-hash, the publish summary reports the tree, seed and manifest counts, and the reload pass reproduces the pre-publication contract registry, graph hash, order and coverage exactly.
- [Error invariant] On any failure the workspace root is left byte-identical to its pre-run state: no directory, no seed, no manifest and no staging or intermediate file remains; the previous allocate manifest, if one existed, is untouched.
- [Internal state invariant] After a successful run the workspace contains exactly the tree, one RFC-SEED.md per seed_required package, and WORKSPACIFY-ALLOCATE-MANIFEST.json; the manifest is canonical JSON whose self-hash covers every field, and every seed hash recorded in it matches the file on disk.
- [Boundary invariant] Degenerate cases are explicit: a workspace with a single package publishes a manifest whose seed index has one entry; a workspace whose plan is empty cannot be published (fresh-workspace policy already blocks a non-empty target); an interrupted run (SIGINT during publish) leaves staging removable by a subsequent run without touching published content; a second run against a published workspace is BLOCKED rather than merged.
