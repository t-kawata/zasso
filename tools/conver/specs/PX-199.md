# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the original long specification auditable before it is decomposed: a machine-generated pulse lists every place where the specification itself is weak (thin normative density, isolated chapters, oversized chapters, normative phrases with no harvested item, near-duplicate or undefined terms, table/prose mismatches), and the AI resolves each candidate in a structured spec_defects record. The run never stops for a human: an unresolved item becomes a residual_question carried to the seeds grill-question section (PX-201), not a question asked now.

### Purpose
The final quality of the RFC-SEED.md set is bounded by the quality of the specification it is transferred from. Today nothing looks at the specification as a document: the harvest either finds candidates or it does not, and a chapter that yields nothing is indistinguishable from a chapter that says nothing important.

### Motivation
Adversarial review inside the workflow keeps finding specification-level defects (a rule stated once and never referenced, a table that contradicts its prose, a term used two ways). Those findings must be produced by the machine as candidates and settled by the AI in the same session, because the human grill happens later, per directory, on the seeds.

### Constraints
- ABSOLUTE: workspacify-tree must never stop for a human, never ask a question in prose, and never defer to a human. Every candidate is either resolved by the AI (spec_defects) or recorded as a residual_question for the later human grill on the seeds.
- The pulse reports candidates only: it never grades prose, never decides importance and never removes a candidate.
- Deterministic output: the same specification text must always yield the same candidate set, sorted by a canonical key.
- No external dependency; Node.js standard library only.
- A candidate is never silently dropped: the gate requires every candidate id to appear either in spec_defects or in residual_questions.

## Acceptance Criteria

- **[Happy path] — a weak specification is audited and resolved:** the pulse reports its candidates, the AI resolves them in spec_defects or records them as residual_questions, the manifest publishes both sets with the required fields, and the run completes without asking a human anything.
- **[Error case] — an unaccounted or badly formed record stops the run:** a candidate missing from both lists, a spec_defect without a rationale, a residual_question without alternatives, or any external-dependency phrase in a free-text field fails the gate with a typed error naming the artefact, and nothing is published.
- **[Edge case] — degenerate and healthy specifications:** single-chapter, empty-inventory, all-healthy and phrase-quoting specifications are each handled with the specific behaviour described above, and the double gate still accepts the published manifest.

## Invariants

- [Normal condition] A COMPLETE manifest carries spec_defects and residual_questions such that every pulse candidate id appears in exactly one of them, every spec_defect carries ai_interpretation, chosen_default and rationale, and every residual_question carries topic, alternatives, chosen_default and why_unresolved.
- [Error invariant] When a candidate is unaccounted for, or a spec_defect lacks one of its required fields, or any payload contains a forbidden external-dependency phrase (TODO, TBD, ask the human, waiting for approval, human review required), finalize fails with a typed error naming the candidate id or the offending field; nothing is published.
- [Internal state invariant] The pulse is a pure function of the normalized specification text plus the harvested inventory: the same input yields identical candidates, ids and ordering, and the ids are stable across runs (pulse-000001 style ids assigned in document order).
- [Boundary invariant] Degenerate inputs are explicit: a specification with a single chapter yields no isolation candidate; a chapter with no normative phrase and no harvested item yields no extraction-gap candidate; an empty inventory yields an empty gap list rather than a crash; a specification where every chapter is healthy yields an empty candidate list and the gate then requires empty spec_defects and residual_questions.

## Notes in Prior Implementation Rounds

- **Implementation steps**: 1) RED — write spec-pulse and spec-defects tests (one case per kind, determinism, coverage, phrase ban, boundaries) plus a fixture specification that is deliberately weak; they fail because the modules do not exist. 2) GREEN — implement spec-pulse.mjs, then spec-defects.mjs, then wire G2/G3, the decisions schema and the finalize publish. 3) Update the tree command document with the pulse review step and the hand-off wording, and the allocate receiver wording. 4) REFACTOR — table-driven kinds, named constants for the phrase list and the density thresholds, one function per kind.
- **Risks**: (a) a pulse that is too noisy makes the AI resolve trivia, so the density threshold must be justified in the code comment and tunable by one constant; (b) the phrase ban can produce false positives in legitimate prose (for example quoting a specification that itself says TBD) — the gate therefore reports the phrase with its field so the AI can rephrase; (c) residual questions carried from stage 1 must reach the seeds in PX-201 or they are lost, so the field name is frozen here and asserted there.
- **Caveats**: the pulse never edits the specification; a specification defect that the AI cannot resolve becomes a residual question, never a stop and never a question to the operator; counting chapters is document structure, so the pulse must ignore code fences exactly as the heading extractor does.
- **Open items**: whether the density threshold should be per chapter or per segment — decided as per chapter with the segment count as evidence, since chapter granularity is what the AI reasons about.
- **Future improvements**: the kind list can be extended with a fixture per new kind; the pulse summary can later feed the drill-rfc-down loop as an input quality measure.
