# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-200: dependency-review: 依存・境界の意味論レビュー材料と判断記録

## Background

### Goal
Give the AI the material it needs to judge the dependency graph and the boundaries as an engineer rather than an acceptor: which declared edges look unnecessary (they serialize implementation without carrying material), which forbidden edges have a viable alternative route, which packages are over- or under-split, and which packages are interface-stability risks because too many consumers depend on them. The AI records a decision per candidate in dependency_reviews; the machine verifies that every candidate has a decision, that the decision shape is complete and that the final graph is consistent with it. No human is asked anything.

### Purpose
The DAG gate proves the graph is well formed, never that it is the right graph. An unnecessary edge forces a provider to be implemented before an unrelated consumer, and an under-split package hides two responsibilities behind one seed; both are design defects that only show up as implementation pain much later.

### Motivation
Adversarial review inside the workflow keeps producing exactly these findings by hand. Turning them into machine-supplied candidates with a recorded AI decision moves the finding earlier, where it is cheap, and leaves an audit trail in the manifest.

### Constraints
- ABSOLUTE: no human hand-back, no prose question, no deferral. A candidate is kept, replaced, merged, split or recorded as residual by the AI in this session.
- Candidates are observations: the review never removes, rewrites or reorders the declared edges; it only reports candidates and validates the recorded decisions.
- Deterministic: identical decisions and package catalog produce identical candidates, ids and order.
- The final DAG stays the authority: a decision that claims an edge was removed must be matched by the published normal_edges.
- Standard library only; no new dependency.

## Acceptance Criteria

- **[Happy path] — the graph is reviewed and decided:** the review reports its candidates, the AI records a decision with rationale for each, the published graph matches the decisions, and the manifest carries the review set without asking a human anything.
- **[Error case] — an unaccounted or inconsistent decision stops the run:** a missing review, an unknown decision value, a missing rationale, a replace_with_port whose edge is still declared or a merge whose packages remain separate fails the gate with a typed error naming the artefact, and nothing is published.
- **[Edge case] — degenerate catalogs:** single-package, chain, empty-edge and fully-connected catalogs each behave as described, and the double gate still accepts the published manifest.

## Invariants

- [Normal condition] A COMPLETE manifest carries dependency_reviews such that every review candidate id appears exactly once, each review states decision in {keep, replace_with_port, merge, split, residual}, a rationale, and the alternatives considered; the published normal_edges and boundaries are consistent with every decision.
- [Error invariant] An unaccounted candidate, an unknown decision value, a missing rationale or a decision inconsistent with the published edges (for example replace_with_port while the edge is still declared) fails the gate with a typed error naming the candidate id and the edge; nothing is published.
- [Internal state invariant] The candidate list is a pure function of (package catalog, edge set, boundary set, ownership table): the same inputs yield identical candidate ids (review-%06d in canonical order) and the same kind assignment.
- [Boundary invariant] Degenerate graphs are explicit: a single package yields no candidates; an acyclic chain yields no unnecessary-serialization candidate; a fully connected pair yields one under-split candidate rather than many; an empty edge set yields an empty candidate list and the gate then requires empty dependency_reviews.
