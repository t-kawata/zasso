# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-204: One verification entry point that reaches every test in the repository, and a discovery method that works on the installed Node

## Background

### Goal
One command runs every automated test this repository owns and reports what it ran, so that a test which exists but is never executed cannot pass unnoticed.

### Purpose
Measured on 2026-09-11, the repository holds 307 test files across three disjoint surfaces and no command reaches all of them. `.claude/tests/run-all.js` globs `tests/**/*.test.{js,cjs}` and therefore cannot see the 124 `.test.mjs` files at all — its glob has no `.mjs` alternative. The Makefile's per-area targets reach 112 of the 120 project `.test.{js,cjs}` files and miss the eight under `reverse/`. The 124 `.mjs` files are reachable only through three ad-hoc suite runners, each of which hard-codes its own directory. Three partial surfaces, no union.

### Motivation
P22-14 through P22-17 wrote 232 tests under `tests/rfc-graph/reverse/`, `tests/tickets/reverse/` and `tests/grill-me-for-rfc/reverse/` that no `make` target reaches. They pass when invoked by hand and are invisible to anyone who runs `make`. Separately, P22-1 recorded as divergence 5 that `node --test <dir>` fails on the installed Node 26 because a directory resolves as a module, which removes the obvious "glob everything" repair. A verification surface assembled by hand is one a session can assemble wrongly without noticing, and the failure is silent: the run is green because it never looked.

### Constraints
The 14 known failures in `.claude/tests` are the PX-142 acceptance baseline and are reported as-is — neither chased nor hidden, and they must not be excluded from the count. The aggregate must not execute any file twice: `tests/rfc-graph/*.test.cjs` is currently reached by both `make test-rfc-graph` and `run-all.js`, and duplicating it would change the reported total. No test may be modified, skipped or filtered to make the aggregate pass. The existing per-area Makefile targets keep their present meaning; the union is added, not substituted.

## Acceptance Criteria

- **[Happy path] — the scenario that confirms this ticket is complete:**
  - `make test` exits 0 on a clean checkout, having executed all 307 test files across the three surfaces, and its report names each surface with its file count, test count, pass count and fail count.
  - The report names the four previously unreachable directories with non-zero counts: `tests/rfc-graph/reverse` (3 files), `tests/tickets/reverse` (3), `tests/grill-me-for-rfc/reverse` (2).
  - The 14 failures in `.claude/tests` appear as `baseline-failures: 14` and the run still exits 0, because the baseline is declared rather than discovered.
- **[Error case] — an error scenario the feature must handle:**
  - A test file is discovered but cannot be executed, because its surface fails to spawn. The aggregate reports the file's path in `missing[]`, names the command it attempted and the platform it ran on, and exits non-zero — even though every test that did run passed. Silent incompleteness is the defect this ticket exists to remove, so it must be impossible for a hole in the surface to produce a green run.
  - A surface whose child process exits 1 is reported with `status: "fail"` and the failing test's name, not merely with an exit code.
- **[Edge case] — a boundary or exception to verify:**
  - A surface directory that exists but holds no test files is reported as `{ files: 0, status: "empty" }`, distinguishable in the report from a surface that ran and passed — the zero-file case must not read as success.
  - A file named `.test.mts` or `.test.ts` under `tests/` is listed in `unsupported[]` with its extension rather than silently ignored, so an extension the runner cannot execute is visible instead of absent.
  - `--surface=project-mjs` runs only that surface and reports the other two as `not-run`, not as passing.
  - Two consecutive runs produce byte-identical `--json` output.

## Invariants

- 【Normal establishment】Every file returned by `discoverTestFiles()` is executed exactly once across the union, the three surface counts sum to the discovered total, and each surface reports `tests === pass + fail` derived from the child's TAP totals rather than from its exit code.
- 【On error】A discovered file that is not executed is named in `missing[]` with its path and the run exits non-zero; a surface whose child exits 1 is reported as `status: "fail"` with the failing test named; a spawn failure names the command attempted and the platform, so a missing Node is never reported as "tests failed".
- 【Internal state】The aggregate writes nothing to the repository — the SHA-256 of every file under `tests/` and `.claude/tests/` is identical before and after a full run — and two consecutive runs produce identical surface summaries.
- 【Boundary】A directory holding zero test files is reported as `{ files: 0, status: "empty" }` and is distinguishable from a surface that ran and passed; an empty repository produces an explicit statement that nothing was found rather than a bare success; the Node version predicate is asserted at `20.x`, `22.0.0` and `26.0.0`.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — tests/run-all-surfaces.mjs -> the three suite runners and .claude/tests/run-all.js (one executed set assembled from three surfaces)

- **Precondition**: Test files exist under `tests/` and `.claude/tests/`; the process runs on Node.js 22 or later; the gitignored `tests/workspacify-reverse/holdout/corpus/` is excluded from the walk.

- **Invariant**: No test file path appears twice across the union, and the reported test total equals the arithmetic sum of the per-surface totals.

### C002 — discoverTestFiles() -> missing[] -> process exit code

- **Precondition**: A file whose name matches `.test.js`, `.test.cjs` or `.test.mjs` exists beneath a test directory.
- **Postcondition**: The file appears in `discovered`; if it is not executed it appears in `missing[]` with its path, and the run exits non-zero even when every executed test passed.
- **Invariant**: The reported total never decreases without a named path accounting for the decrease.

### C003 — .claude/tests/run-all.js -> the aggregate's exit code and baseline accounting

- **Precondition**: `.claude/tests` produces exactly 14 failures, the PX-142 acceptance baseline measured on 2026-09-11.
- **Postcondition**: The run reports `baseline-failures: 14` and exits 0; a fifteenth failure, or a baseline count that has moved, exits non-zero.
- **Invariant**: The aggregate never modifies, skips, filters or re-orders a test to change the count.

### C004 — buildNodeTestArgs(files) -> the child process argv

- **Precondition**: An ordered list of absolute test file paths, non-empty.
- **Postcondition**: The argv is `['--test', ...paths]`, contains the `--test` flag exactly once, and contains no argument that resolves to a directory.
- **Invariant**: Adding a test file under an existing test directory requires no edit to the runner, the Makefile or package.json.

## Boy Scout Rule

- **Functions as verb phrases in the new aggregate.** `discoverTestFiles`, `groupBySurface`, `buildNodeTestArgs`, `runSurface`, `summariseSurface`, `renderSurfaceReport`, `assertNoFileMissing`, `assertNodeVersionSupported` — each name is the action it performs, and the call sequence reads as the processing narrative: discover, group, build argv, run, summarise, report, assert.
- **Variables as domain concepts.** `discoveredFiles`, `surfaceName`, `executedFiles`, `missingPaths`, `baselineFailureCount`, `requiredNodeMajor` — no `data`, `info`, `tmp`, `arr`.
- **Hardcoded values become named constants.** `SURFACE_NAMES`, `TEST_FILE_EXTENSIONS`, `REQUIRED_NODE_MAJOR = 22`, `BASELINE_FAILURE_COUNT = 14`, `HOLDOUT_CORPUS_PATH` — the literal 14 currently lives only in prose in PX-142's record and is named here so the baseline has one definition the test and the runner share.
- **One responsibility per function.** `groupBySurface` is pure and takes paths; `runSurface` owns the child process and returns a result object; rendering never decides and deciding never renders.
- **No error swallowing.** Every child-process failure carries the attempted command and the platform; a missing directory names the path; a surface that ran zero files says so rather than returning an empty success.
- **Boy Scout beyond the immediate scope.** `tests/workspacify-reverse/run-tests.mjs` and its two siblings duplicate the same recursive collector and the same `spawnSync(process.execPath, ['--test', ...files])` line three times; the aggregate extracts that into one module the three runners import, so the discovery rule has a single definition. `.claude/tests/run-all.js` keeps its present behaviour but its `TEST_GLOB` and `repoRoot` resolution are exported so the aggregate reads the same surface definition rather than re-deriving it.

### Exceptions

- **Exception entry — one item:**
  - Item: the aggregate's behaviour on a Node version below 22, where `node --test` has neither the module-mock flag the converge suite uses nor the discovery semantics this runner relies on. The lower bound is not testable on the machine the suite runs on, and it is impossible to test it without a second runtime being installed.
  - Reason: only Node v26.0.0 is installed here, so a run on 20.x cannot be exercised, and installing a second runtime to produce one would change the environment the other 306 test files are measured in. It is not an architectural defect: the behaviour is a pure function of the runtime version, and the version is declared rather than inferred, so what is untestable is the lower bound itself and not the design. The untestable part is a single comparison against a declared constant, and everything that depends on it is tested.

A unit test asserts that predicate directly for `20.x`, `22.0.0` and `26.0.0` by calling the pure version-check function with each string, so the boundary is tested without needing the runtime to be present. `package.json` gains an `engines` field, and the aggregate and the test read the same constant rather than each holding its own copy.
