# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

- 【Normal establishment】`resolveModuleSystem(filePath)` returns `esm` for `.mjs`, `commonjs` for `.cjs`, and for `.js` the `type` field of the nearest ancestor `package.json`, defaulting to `commonjs` when no ancestor declares one. ## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — resolveModuleSystem(filePath) -> the filesystem's own declarations (extension, nearest package.json type)

- **Precondition**: A file path exists under a directory that may or may not carry a package.json; the process can read the filesystem.
- **Postcondition**: The function returns one of `esm`, `commonjs` or `unknown`, together with `decidedBy` naming whether the extension or a package.json decided, and for a `.js` path with no ancestor declaration it returns `commonjs`.
- **Invariant**: The function reads only the extension and package.json `type` fields; it never inspects file contents and never consults Node's module syntax detection, so its verdict does not vary with the runtime.

### C002 — .claude/rules/node.md -> scanScriptDirectories(root) -> the conformance verdict

- **Precondition**: `.claude/rules/node.md` states a per-directory module convention; directories exist under `.claude/scripts/`.
- **Postcondition**: The table parsed from the rule file equals the table derived from the filesystem, and every directory under `.claude/scripts/` resolves to exactly one module system across all its files.
- **Invariant**: The filesystem is the authority and the document is checked against it; a disagreement is reported as a defect in the document, never resolved by editing the source files.

### C003 — git index -> the tracking check -> Tickets.json.p22-ja.bak

- **Precondition**: `Tickets.json.p22-ja.bak` is tracked at blob bf1992ca and matched by no `.gitignore` pattern.
- **Postcondition**: After the change, `git ls-files --error-unmatch Tickets.json.p22-ja.bak` fails, `git check-ignore` matches the path, and the working-tree file's SHA-256 is unchanged from before the change.
- **Invariant**: The operation removes the path from the index only; the working-tree file is never deleted, and no other tracked path is affected.

### C004 — src/ -> npm run build -> .claude/scripts/conver/conver.js

- **Precondition**: `src/entry.ts` exists; the `build` script is declared in package.json; `esbuild` resolves from node_modules; a committed artefact exists at `.claude/scripts/conver/conver.js`.
- **Postcondition**: A fresh build written to a temporary path is byte-identical to the committed artefact, and the check reports `identical: true` with both SHA-256 values; a difference reports both digests and the byte-size delta and exits non-zero.
- **Invariant**: The check writes nothing into `.claude/scripts/conver/` and removes its temporary build output on both the success and the failure path.

## Boy Scout Rule

- **Functions as verb phrases.** `resolveModuleSystem`, `readNearestPackageType`, `scanScriptDirectories`, `groupFilesByDirectory`, `readBundleComparison`, `buildBundleToTemp`, `assertBackupUntracked`, `renderConformanceReport` — the call sequence in the entry point reads as the narrative: resolve, scan, compare, assert, report.
- **Variables as domain concepts.** `resolvedModuleSystem`, `decidedBy`, `nonConformingPaths`, `committedDigest`, `builtDigest`, `byteSizeDelta`, `ignoredPatterns` — no `data`, `info`, `tmp`, `result2`.
- **Hardcoded values become named constants.** `MODULE_SYSTEM = { ESM: 'esm', COMMONJS: 'commonjs', UNKNOWN: 'unknown' }`, `DECIDED_BY = { EXTENSION: 'extension', PACKAGE_JSON: 'package.json' }`, `SCRIPT_ROOT = '.claude/scripts'`, `CONVENTION_RULE_PATH = '.claude/rules/node.md'`, `COMMITTED_BUNDLE_PATH = '.claude/scripts/conver/conver.js'`, `BUNDLE_ENTRY = 'src/entry.ts'`, `UNTRACKED_BACKUP_NAME = 'Tickets.json.p22-ja.bak'`. The esbuild invocation is read from `package.json`'s `build` script rather than re-spelled, so the check cannot drift from the build it is checking.
- **One responsibility per function.** Resolution is pure and reads only the filesystem; scanning owns enumeration; comparison owns the build; rendering never decides and deciding never renders.
- **No error swallowing.** A missing `package.json` ancestor is a stated default, not a swallowed failure; a missing `entry.ts`, a missing esbuild and a missing git tree each name what was absent and what would provide it.
- **Boy Scout beyond the immediate scope.** `.claude/rules/node.md` contradicts the repository in a second place as well: it states "Node.js >=18" while the toolchain measured here is v26.0.0 and `node --test` semantics differ across that range — PX-204 records the Node 26 directory defect. The engine statement is corrected in the same edit, and the new `engines` field PX-204 adds to `package.json` becomes the single declaration both documents point at. `.claude/rules/node.md`'s file-naming and test-layout claims are checked against the filesystem by the same scan rather than left as prose.

### Exceptions

- **Exception entry — one item:**
  - Item: the behaviour of `.js` files whose module system depends on Node's module syntax detection rather than on the `package.json` `type` field — that is, a `.js` file with `import` syntax loaded from a CommonJS-declared directory. This cannot be tested across the Node versions where the heuristic differs, because only one runtime is installed.
  - Reason: the outcome depends on a detection heuristic that changed across Node releases and became unflagged at 22.7, so the behaviour on 20.x and 22.6 is not testable here, and installing a second runtime to exercise it would change the environment every other suite is measured in. It is not a design defect: the ticket does not depend on the heuristic at all, because the check asserts the *declaration*, which is a property of files on disk and is deterministic. Nothing in the design would need redesigning to make the heuristic testable; it is simply a runtime behaviour the ticket declines to rely on.
  - Alternative verification: the resolver reads the same field Node reads and never consults detection, so its verdict is independent of the runtime. A unit test asserts the resolver's output for each `(extension, declared type)` pair by calling the pure function rather than by loading the file, including the contradiction case. The runtime's leniency is pinned rather than assumed: UT-9 asserts that a contradicting file *loads* under Node 26 and is *still* reported by the scan, fixing both facts at once so a future change to the heuristic surfaces as a failing assertion rather than as a silent change of meaning.

- [Implementation steps] (1) Write the failing tests: `resolveModuleSystem` over the five `(extension, declared type)` combinations, the conformance scan, the rule-file-vs-filesystem comparison, the tracking check, and the freshness check. (2) Implement `module-convention.mjs` and make them green. (3) Correct `.claude/rules/node.md`: replace the blanket "CommonJS only" statement with the per-directory table, name the `package.json` `type` field as the authority, and correct the `>=18` engine statement to point at the `engines` field PX-204 adds. (4) Add the `Makefile` targets. (5) `git rm --cached Tickets.json.p22-ja.bak` and add `*.bak` to `.gitignore` — file kept on disk, digest taken before and after. (6) Run the regression gate before and after; it must stay `proved`.
- [Risks] **The largest risk is inverting the Boy Scout rule.** The premise says fourteen files are wrong; they are not. A session that trusts the premise and rewrites `grill-me-for-rfc/` to CommonJS would break the directory, its 46 tests, and the P22-13 and P22-14 code paths that import it. The mitigation is structural rather than advisory: the test derives the convention table from the filesystem, so "what the repository does" is the authority and the document is checked against it, never the other way round. **The second risk is the freshness check becoming flaky.** Building on every run costs seconds and depends on esbuild; if it is wired into the default test target without an escape, a machine without esbuild reports a stale bundle. The check must distinguish "cannot build" from "built and differs". **The third is `git rm --cached` being run carelessly.** `git rm` without `--cached` deletes the working file; the test that digests the backup before and after exists specifically to make that mistake visible rather than silent. **The fourth is history.** Nothing in this ticket removes the blob from the 28 commits; a reader who assumes "untracked" means "gone" will be wrong, and the open item says so.
- [Caveats] The convention table is a measurement of the tree on 2026-09-11; a future directory may legitimately declare either system, and the test asserts the *property* (each directory resolves to exactly one system) rather than the seven present names, so adding a directory does not require editing the test. The rule-file comparison does pin the table's content, so a new directory does require updating `.claude/rules/node.md` — deliberately, because a rule file that silently omits a directory is the defect this ticket is fixing. `specs/P22-1.md` is left as written; its premise is wrong and this ticket's spec is the erratum of record.
- [Open items] **Removing `bf1992ca` from history is left open pending the user's explicit approval.** It requires rebasing 28 commits and a force push, which is outward-facing and hard to reverse; the repository's recorded position is that such an act needs authorisation rather than assumption. Until then the blob remains in every clone and the repository grows permanently by 4.27 MB. Also open: whether the freshness check belongs in the default `make test` target or in a slower target of its own.
- [Future improvements] Extend the conformance scan to the `fe/` frontend and the `tools/conver/src/` TypeScript tree, which have their own conventions. Add a pre-commit hook that runs the freshness check, so a `src/` edit without a rebuild fails at commit time rather than at review time. Generalise the freshness guard into a declaration — a list of `(source entry, committed artefact)` pairs — so a second bundled artefact does not need a second check.
