# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-206: Make the forward rotation independent of the reverse tree: invert the dependency that P22-10 introduced

**Ticket Key**: PX-206 · **Phase**: -1

## Background

### Goal
`forward-extensions.mjs` lives in a forward tree, so no file that existed before this branch depends on `.claude/scripts/workspacify-reverse/`, and a test asserts that property structurally rather than by inspection.

### Purpose
P22-10 introduced a module declaring the reverse-only field vocabulary and placed it inside the reverse tree. Two pre-existing forward files import it, which makes the forward rotation depend on the reverse tree's continued existence — the one direction the whole phase promised not to disturb.

**The measurement that settles the placement question.** A scan of every `.mjs`, `.js`, `.cjs` and `.ts` file in the repository, distinguishing real imports from prose mentions, returns exactly eight files: two real importers inside script trees (`tickets/update-ticket.js` at line 13, `workspacify-allocate/lib/seed-render.mjs` at line 14), four test files, and two files that merely name the module in a comment. **Not one of the eight is inside `workspacify-reverse/`.** `forward-extensions.mjs` is a forward-rotation module that happens to be filed in the reverse tree. Nothing about it is reverse-specific except the field names it declares.

That reframes the defect. It is not that the dependency direction is wrong in the abstract; it is that the module was filed in the wrong tree and the wrong tree then acquired two dependents. The fix is a move, not an inversion.

### Motivation
Measured 2026-09-11, the move happened and the edge is real: the directory-level graph now contains `workspacify-allocate -> workspacify-reverse`, which did not exist before P22-10. The repository already carries two directory-level cycles — `workspacify-tree <-> workspacify-allocate` and `rfc-graph <-> tickets` — so a cycle is not by itself novel, and this ticket does not claim to remove them. What is novel is that a forward tree now depends on the reverse tree. If `workspacify-reverse/` were ever removed, relocated or shipped separately, `update-ticket.js` — the writer the implementation loop uses on every ticket — would fail to load.

### Constraints
**There must remain exactly one declaration of the reverse-only field vocabulary.** Breaking the dependency by copying the field-name list into a forward file would leave two lists that drift, and the drift would be silent: a field added to one and not the other produces an artefact that passes one guard and fails another, or worse, passes both. **The module's forward-mode contract is load-bearing and must survive the move**: in forward mode `extendForwardArtifacts` returns the artefact *itself*, not a copy, because `manifest_hash` participates in the WIG and in reload validation, and a copy that serialised identically today could stop doing so tomorrow. **The regression gate must be run before and after and must stay `proved`.** **No new directory cycle may be introduced**: the destination is chosen so that the edges it creates already exist or run in the permitted direction.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — the repository tree -> collectReverseImporters(root) -> the importer set

- **Precondition**: `.claude/scripts/` exists and holds the seven script directories; source files are readable UTF-8 text.
- **Postcondition**: The function returns every file outside `workspacify-reverse/` whose source contains a real import or require resolving inside that tree, each with the path it imports; files naming the tree only in a comment are excluded; the reverse tree's own files are excluded.
- **Invariant**: The set is recomputed from the tree on every call and is never read from a stored list, so it cannot go stale.

### C002 — the importer set -> assertLayersOneWay({ importers, allowlist }) -> the verdict

- **Precondition**: A declared allowlist of reverse-mode entry points exists, each entry naming the ticket that created it.
- **Postcondition**: The assertion returns `ok: true` when the importer set equals the allowlist, and `ok: false` naming every importer not on the list and every allowlist entry that no longer imports the tree; the test exits non-zero on `ok: false`.
- **Invariant**: The comparison is set equality, not containment: a missing allowlist entry and an extra one both fail, so the list cannot silently accumulate permissions.

### C003 — extendForwardArtifacts(artefact, { kind, mode }) -> the returned artefact

- **Precondition**: An artefact object of a declared kind; a mode of `forward` or `reverse`; in reverse mode, a `reverseFields` object.
- **Postcondition**: In forward mode the function returns the identical object reference it was given; in reverse mode it returns a new object carrying the reverse fields, and `assertReverseAdditions` accepts it.
- **Invariant**: Reference identity in forward mode is the contract, not deep equality: `manifest_hash` participates in the WIG and in reload validation, and a copy that serialised identically today could stop doing so tomorrow. Asserted with strict equality.

### C004 — the moved module -> its six importers -> path resolution

- **Precondition**: `workspacify-allocate/lib/forward-extensions.mjs` exists and `workspacify-reverse/lib/forward-extensions.mjs` does not.
- **Postcondition**: Every importer resolves to the new absolute path; every file importing `forward-extensions.mjs` resolves to the same single destination; `tickets/update-ticket.js` loads and the three suites reproduce 320/226/661 with the gate `proved`.
- **Invariant**: The vocabulary has exactly one declaration — the set of distinct resolved destinations has exactly one element — and the module's exported names are unchanged.

## Boy Scout Rule

- **Functions as verb phrases.** `collectReverseImporters`, `resolveImportSpecifier`, `isRealImport`, `collectAllowlist`, `assertLayersOneWay`, `reportViolations` — the entry point reads as: collect the importers, collect the allowlist, assert they are equal, report.
- **Variables as domain concepts.** `importingPath`, `importedPath`, `allowlistedPaths`, `stalePermissions`, `violations`, `resolvedDestination` — no `data`, `list`, `tmp`, `x`.
- **Hardcoded values become named constants.** `REVERSE_TREE = '.claude/scripts/workspacify-reverse'`, `SCRIPT_ROOT = '.claude/scripts'`, `REVERSE_ENTRY_ALLOWLIST` (each entry carrying the ticket that created it), `IMPORT_SPECIFIER_PATTERN`. The three allowlist entries name their tickets — P22-19, P22-13, P22-16 — so a permission is never anonymous.
- **One responsibility per function.** `isRealImport` is a pure predicate over source text; `resolveImportSpecifier` is a pure path function; `collectReverseImporters` owns the walk; `assertLayersOneWay` owns the comparison and never renders.
- **No error swallowing.** An unresolved specifier is reported with the importing file and the specifier; a missing tree is reported as unavailable rather than as clean; a skipped binary is counted and named.
- **Boy Scout beyond the immediate scope.** `workspacify-reverse/lib/security-lane.mjs` imports `recordAuthority` from `grill-me-for-rfc/normative-decision.js`, which is the reverse tree depending on a forward tree — the permitted direction, and left as it is. ## Notes in Prior Implementation Rounds

- [Implementation steps] (1) Record the baselines: the three suite counts and the gate verdict. (2) Write the failing assertion: collect importers, collect the allowlist, assert equality, plus the purity and export-surface tests. (3) Move `forward-extensions.mjs` to `workspacify-allocate/lib/` with `git mv` so the history follows it. (4) Update the six real importers (two script files, four test files) and correct the two comment references so they do not point at a path that no longer exists. (5) Re-run the three suites and the gate; they must reproduce the baselines exactly. (6) Make one deliberate forward import of the reverse tree and watch the assertion fail, then remove it.
- [Risks] **The largest risk is a partial move.** If `workspacify-reverse/lib/forward-extensions.mjs` is left behind as well as copied, there are two declarations of the field vocabulary and the constraint that forbids it is violated silently — every import still resolves and every test still passes. UT-12 exists specifically to make the leftover file a named failure. **The second risk is a missed importer.** `tickets/update-ticket.js` spells its require across two lines, so a line-oriented search for the import misses it; the move must be verified by loading the module rather than by grepping for the string. **The third is the `.mjs`-from-CommonJS boundary.** If the destination were a `.js` file under a CommonJS tree, `update-ticket.js` would still load but the reverse tree's ESM importers would break; the destination stays `.mjs` for that reason. **The fourth is the gate.** Two of the six files this ticket edits are forward-path files, so a mistake here is a forward-rotation regression, and the gate is the only instrument that would catch it.
- [Caveats] The allowlist is a permission list, and permission lists rot. The stale-entry check is what keeps it honest, and the ticket accepts that a future reverse entry point must be added to it deliberately — that cost is the point, because an unreviewed new dependency is exactly the failure being guarded against. The assertion deliberately does not attempt to remove the two pre-existing cycles (`workspacify-tree <-> workspacify-allocate`, `rfc-graph <-> tickets`); they predate this branch and are out of scope, and claiming otherwise would misrepresent what the test proves.
- [Open items] Whether the reverse tree's dependence on `grill-me-for-rfc/normative-decision.js` should be removed in the same way — it is the same class of shared-vocabulary coupling in the permitted direction. Open because the direction is permitted and the change has no defect behind it, only symmetry. Whether the two pre-existing cycles should be broken is likewise open and is a much larger piece of work.
- [Future improvements] Emit the directory-level dependency graph as a committed artefact so the two cycles and every edge are visible in review rather than recomputed by each session that wonders. Extend the assertion from "no forward file imports the reverse tree" to a declared layer order over all seven script directories, which would also catch the two pre-existing cycles — a separate ticket, because it would require changing code that currently works.
