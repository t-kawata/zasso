# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Every forward-tree source file that P22 modified is covered by at least one frozen value the regression gate reproduces, so a future change to any of them is reported by name rather than discovered by accident.

### Purpose
The gate built by P22-1 covers the workspacify surfaces and nothing else, measured on 2026-09-11 as 25 fixture digests, three forward pipeline pairs, five allocate fixture digests and nine command-file digests. The changes P22 made to `rfc-graph` and to `tickets` sit entirely outside it and rest on unit tests alone.

The difference matters and is the reason this ticket exists. A unit test asserts what its author thought of. A frozen value asserts that nothing moved — including moves the author did not think of. `generateHeaderComment`'s signature changed from seven arguments to five and the header bytes it emits changed with it; no frozen value covers that. `dump-node-context-to-spec.js` carried a defect in which every node id collapsed to the string `[object Object]`, so the map it built was one unusable key; that defect survived because nothing compared the map against a known-good result.

### Motivation
The four uncovered modifications are, measured by `git diff --numstat master...HEAD` on 2026-09-11: `rfc-graph/boundify-helpers.js` +17/-4 (the `HEADER_MARKER_TEXT` extraction and the signature change), `rfc-graph/dump-node-context-to-spec.js` +43/-11 (the `mappedNodeIdOf` repair), `rfc-graph/phasify-omissions.js` +58/-4 (PX-142's `verifyMarkerRewrites` and the plan-text fallback), and `tickets/update-ticket.js` +34/-0 (P22-10's reverse-contamination guard). Each is a forward-path change to a tree the phase promised not to disturb, and each is currently protected only by tests the same ticket wrote.

### Constraints
**The gate must not acquire a value it cannot reproduce.** A volatile field frozen by mistake makes the gate fail on every run, and a gate that always fails is ignored — which destroys the only thing it has. P22-1 already met this problem once: `manifest_hash` was not reproducible across runs because `assembleManifest` hashes `run.generated_at`, `run.run_id` and `run.generator`, and the fix was `stableManifestDigest`, which removes exactly those fields. The same discipline applies here: a value is frozen only after proving it reproduces across two runs and two working directories. **Baselines are captured after the forward code is final, never to make a red gate green.** **The gate must distinguish "cannot build the surface" from "built and differs"** — an unavailable prerequisite reported as drift would make the gate cry wolf. **No forward behaviour may change**: exporting a previously-private pure function is permitted, changing what it computes is not.

- **[Error case] — an error scenario the feature must handle:**

- **[Edge case] — a boundary or exception to verify:**
  - A pure function is frozen as a golden output for a fixed input, with the input stored beside the value so the comparison is reproducible rather than dependent on the current source. `generateHeaderComment` is the fixture: five arguments in, one string out.
  - A surface whose input includes a timestamp or a path that varies by working directory is normalised before freezing, and the normalisation is declared in the baseline rather than applied silently.
  - An empty surface — a directory with no inputs to freeze — reports that it has nothing to freeze and is distinguishable from a surface that was frozen and reproduced.
  - The baseline file after this ticket still parses against the schema P22-1 declared, with the new surfaces added under a new key rather than by widening an existing one.

## Invariants

- 【Normal establishment】Every forward-tree source file P22 modified has at least one frozen value; `capture` freezes them and is idempotent across two runs in two directories; `check` reproduces every value and reports each covered surface by name.
- 【On error】A one-byte change to any covered surface is reported by name with the expected and observed values and exits 1; a surface that cannot be produced at all — a missing fixture, an unresolvable prerequisite — is reported as unavailable with the reason, distinctly from drift, and does not silently count as reproduced.
- 【Internal state】Measurement is read-only: the SHA-256 of every fixture, every command file and every source file the gate reads is identical before and after both `capture` and `check`. The gate writes only its baseline file and its reports, and only under the declared baseline path.
- 【Boundary】A surface whose output is genuinely non-deterministic is recorded as `non-deterministic` with the observed variation and the reason, rather than frozen to a value that would fail on the next run; an empty surface reports that it has nothing to freeze rather than reporting success.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — a forward surface's producer -> captureForwardSurfaces() -> the frozen baseline entry

- **Precondition**: The surface's input fixture exists; the producer is either a pure function imported from a forward module or a CLI invocable from the repository root; the surface is named in the FORWARD_SURFACES table.
- **Postcondition**: The entry is `{ surface, kind, producedFrom, value, normalisation }`; a second capture produces a byte-identical entry; a capture from a different working directory produces the same value.
- **Invariant**: A surface whose two captures disagree is written as `kind: 'non-deterministic'` with both observations rather than frozen to either.

### C002 — the frozen baseline -> compareForwardSurfaces() -> the proved / not proved verdict

- **Precondition**: A baseline exists holding at least one forward-surface entry; the producers are still resolvable.
- **Postcondition**: Each entry is recomputed and compared; a mismatch is reported by surface name with the expected and observed values; a producer that cannot be run is reported as unavailable with its reason, distinctly from a mismatch; the gate exits 1 on a mismatch and 0 otherwise.
- **Invariant**: An unavailable surface never counts as reproduced, and no surface is silently dropped from the comparison when the set of entries changes.

### C003 — generateHeaderComment(headerPaths, mappedNodeIds, crossRefs, sourceBasename, lang) -> the emitted header string

- **Precondition**: Five arguments: a header-paths object carrying graphRelPath, dirsTreeRelPath and sourceRelPath; an array of mapped node ids; a cross-reference list; a source basename; a language key present in COMMENT_SYNTAX.
- **Postcondition**: The function returns a string whose first content line carries HEADER_MARKER_TEXT, which names the graph path, the directory path and the source path, and which lists one line per mapped node; the same five arguments produce an equal string on every call.
- **Invariant**: The function is pure — it performs no I/O and writes no file — and the returned string always contains the exact marker text `Initial Design Artifact — RFC-driven Implementation`, which supreme law 4 forbids altering.

### C004 — the repository's forward-tree diff -> the covered surface set -> the gate's report

- **Precondition**: Every forward-tree source file P22 modified is derivable from `git diff --numstat master...HEAD`.
- **Postcondition**: Each such file is covered by at least one frozen surface, and the report names the surface that covers it; `captureBaselines` leaves the existing `fixtures`, `manifestHashes` and `commandFileDigests` keys byte-identical.
- **Invariant**: The set of surfaces the gate covers is a superset of the set of forward files P22 modified, asserted by a test that recomputes the diff rather than by a stored list.

## Boy Scout Rule

- **Functions as verb phrases.** `freezeHeaderOutput`, `freezeNodeIdPathMap`, `freezeTicketGuard`, `freezeMarkerRewrite`, `freezeChecklistOutput`, `captureForwardSurfaces`, `compareForwardSurfaces`, `normaliseChecklistOutput`, `assertSurfaceReproducible` — the entry point reads as: freeze each surface, assert each reproduces, compare.
- **Variables as domain concepts.** `surfaceName`, `frozenValue`, `observedValue`, `producedFrom`, `normalisationApplied`, `unavailableReason` — no `data`, `expected2`, `tmp`.
- **Hardcoded values become named constants.** `FORWARD_SURFACES` (a table of `{ name, kind, producer, input }`), `NON_DETERMINISTIC_MARKER`, `CHECKLIST_TIMESTAMP_FIELD`, `BASELINE_FORWARD_KEY`. The surface table is one declaration; adding a surface is adding a row, not editing a comparison.
- **One responsibility per function.** Each `freeze*` produces one value and nothing else; `normaliseChecklistOutput` is pure; `compareForwardSurfaces` compares and never produces; rendering never decides.
- **No error swallowing.** An unavailable producer is reported with the reason and the command that would provide it; a non-deterministic value is reported with both observations rather than the last one; a missing fixture names the path.
- **Boy Scout beyond the immediate scope.** `regression-gate.mjs` is at 440 lines and grows a fourth surface kind; the new producers live in `forward-surface-baseline.mjs` so the gate keeps one responsibility — comparing — and stays under the repository's 800-line limit with room to spare. `dump-node-context-to-spec.js` and `update-ticket.js` each hold a pure function the gate needs but do not export; both are exported as part of this ticket, with their JSDoc stating why the export exists rather than being added bare. `phasify-omissions.js` is 1,853 lines, the largest file this ticket touches, and its export list at line 1810 is grouped by ticket; `verifyMarkerRewrites` is moved into the PX-142 group it belongs to rather than left appended to the PX-120 block it currently sits under.

### Exceptions

- **Exception entry — one item:**
  - Item: freezing the raw output of `grill-me-for-rfc/generate-checklist.js` exactly, including the run metadata the command prints. The raw bytes cannot be tested by equality, because they differ on every invocation.
  - Reason: the emitted bytes carry a generation timestamp, so a byte-equality assertion on the raw output is not testable without failing on every run — the failure mode P22-1 named when `manifest_hash` proved non-reproducible. It is not a design defect: the artefact is deterministic once the timestamp is excluded, and the exclusion is declared in the baseline rather than applied silently, so no part of the design needs redesigning to make the meaningful content testable.
  - Alternative verification: the surface is frozen after a named normalisation that replaces the timestamp field with a fixed placeholder, and the normalisation is recorded beside the value so a reader can see what was excluded. A test asserts both halves: that the raw output differs between two runs in its timestamp field, and that the normalised output is identical. The pairing is what makes the exclusion honest — freezing only the normalised value would hide whether the difference is solely the timestamp or something else as well, and a drifting non-timestamp field would then be silently normalised away.

## Notes in Prior Implementation Rounds

- [Implementation steps] (1) Record the baselines: the gate's present `proved` state, its three key digests, and the three suite counts. (2) Write the failing tests: one freeze-and-drift pair per surface, the non-deterministic refusal, the read-only invariants, the byte-identity of the existing keys, and the coverage assertion derived from the git diff. (3) Export `mappedNodeIdOf` and `firstReverseFieldOnForwardTicket` — the only source change, additive. (4) Create the fixtures under `tests/rfc-graph/fixtures/forward-surfaces/`. (5) Write `forward-surface-baseline.mjs` and wire it into the gate's capture and check paths; make the tests green. (6) Run `capture` twice in two directories and diff the baselines. (7) Run `check`, then perturb `HEADER_MARKER_TEXT` by one character and confirm the gate names the header surface and exits 1; restore and confirm `proved`.
- [Risks] **The largest risk is freezing a value that does not reproduce.** P22-1 met this exactly: three runs in one directory produced three different `manifest_hash` values because `assembleManifest` hashes `run.generated_at`, `run.run_id` and `run.generator`. The same trap waits here — a path that varies by working directory, a timestamp in the checklist output, an object key order that depends on insertion history. The mitigation is procedural and must not be skipped: capture twice in two directories and diff before declaring any surface frozen. **The second risk is a gate that fails on every run being ignored.** A gate whose failure is noise has no authority, and this repository has already demonstrated the cost of an instrument nobody trusts. The unavailable-versus-drifted distinction exists for this reason. **The third is scope creep into re-capturing the existing keys.** They are `proved`; touching them would erase the evidence that the surfaces P22-1 froze are intact. UT-25 exists to make that mistake visible. **The fourth is that this ticket freezes what it just wrote.** The tests and the frozen values come from the same session as the surfaces they cover, which is exactly the co-conspirator arrangement the design warns about elsewhere; the mitigation is that the frozen values are derived from the *pre-existing* functions rather than from the tests, and the adversarial step in step 7 is performed against a surface the test author did not write.
- [Caveats] The new frozen values cover the specific units P22 modified, not the whole of `rfc-graph` or `tickets`. A future change to an untouched part of those trees will still be caught only by unit tests. The surface table is a maintained list, and adding a surface is a deliberate act; the coverage assertion derived from the git diff keeps it honest for the P22 changes specifically, and will need re-pointing if the phase boundary moves. The `.mjs`-versus-`.cjs` split matters here: `forward-surface-baseline.mjs` is ESM and must import from CommonJS modules through `createRequire` or a dynamic import, and that boundary is asserted rather than assumed.
- [Open items] Whether the whole of the `phasify-omissions.js` pipeline is deterministic is unmeasured and is left open; the ticket freezes its two modified units and says so rather than implying broader coverage. Whether the git-diff-derived coverage assertion should be a permanent test or a one-time check is open — as a permanent test it will fail once the branch is merged and `master...HEAD` becomes empty, so it must be written to tolerate an empty diff by reporting that it has nothing to check rather than passing vacuously.
- [Future improvements] A general declaration of `(source revision range, forward surface, frozen value)` so coverage is recomputed for any phase rather than the P22 range specifically. Extending the freeze mechanism to `drill-rfc-down`'s header refresh, which shares `generateHeaderComment` and would become cheap once the header surface exists. Emitting the gate's report as a machine-readable sidecar so PX-204's aggregate can include the verdict without parsing prose.
