# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-208: Preserve what the tools do not own: annotation idempotence and generated-region fencing

**Ticket Key**: PX-208 · **Phase**: -1

---

## Background

### Goal
Make two tools that rewrite files they do not wholly own stop destroying content they did not author. Concretely: (1) `annotate-ticket-context-by-git-diff.js` becomes idempotent for a given ticket key, so running it twice leaves a file byte-identical; (2) both `generate-checklist.js` generators rewrite only a fenced region and preserve every byte outside it.

### Purpose
Both defects are violations of a single invariant, stated once here and enforced twice: **a tool that rewrites a file it does not wholly own must be idempotent, and must preserve every byte it did not author.** The project already states the positive half of this — CLAUDE.md's "Everything as Code" requires source modified under a ticket to carry a provenance annotation. A tool that can silently add a second copy of that annotation, or delete a hand-written section, undermines the very traceability it exists to provide.

### Motivation
The annotator defect is not hypothetical and not new: it has produced surviving corruption in four separate ticket generations — PX-159 (three files, each tripled), P22-8, P22-9 (three files), and PX-207, whose frozen fixture drifted and failed 14 downstream tests before being diagnosed. Every workstream that runs `/start-ticket` re-arms it. The generator defect is worse in kind: it destroys human work rather than duplicating machine output, and the command file *instructs* the AI to produce exactly the content the next run deletes (`drill-rfc-down.md:183`), with `--no-backup` on the invocation. `./CheckList.md:137` is a live specimen awaiting the next run.

### Constraints
- The supreme law forbids deleting or altering the `Initial Design Artifact` header; the fence constants must not collide with it or with `[::STUB::]`, `[::TICKET::]` or `[::AMBIGUOUS::]`.
- TDD Red-Green-Refactor is mandatory; every behaviour above is deterministic and directly testable, so no item may be excused as untestable.
- The fix must be a superset of current behaviour: the frozen `checklist-output` forward surface must still reproduce (contract C003). For an input with no human content the fix must produce identical bytes.
- `make check-conventions` must remain green; no new row may appear in `.claude/rules/node.md` by accident.
- The two generators must not drift apart — PX-207 already fixed a defect in one sibling and left the other, and that omission is the reason target B names both files.

## Investigation

### Evidence — the annotator's non-idempotence (target A)

`.claude/scripts/tickets/annotate-ticket-context-by-git-diff.js`, CommonJS (the directory has no package.json of its own and inherits `.claude/package.json` = `commonjs`). Introduced by `bb098474 feat(PX-59): implement code ticket-key annotation and pipeline integration` on 2026-07-23; 7 commits in total, the last `a185494e` on 2026-07-31. P22-1 did not modify it (`git show --stat be80f414` matches `annotate-ticket` zero times); in this branch only P22-14 touched it (+4/-1).

The guard, lines 106-114:

```js
function detectAnnotationAtLine(lines, defLine) {
  const checkIndex = defLine - 2; // line above the definition (0-indexed)
  if (checkIndex < 0 || checkIndex >= lines.length) return null;
  ...
}
```

It reads **exactly one line above the definition**. A file whose annotation sits two or more lines above — because a comment or blank line was interposed by a later edit — is invisible to it. The definition branch at 344-347 then finds `existingAnnot === null` and inserts a second identical annotation. `mergeAnnotation` (121-124) *is* idempotent for the multi-key case ("If the key already exists, returns the original line unchanged"); the defect is the adjacency test, not the merge.

The second path, lines 313-317: when a changed line belongs to no definition, the file-level guard is

```js
const alreadyHasMarker = lines.some(
  (l) => l.includes("[::AMBIGUOUS::]") && l.includes(ticketKey)

```

It recognises only an `[::AMBIGUOUS::]` marker. After `resolve-ambiguous-markers.js --mode=inject-at` has replaced that marker with a `[::TICKET::]` one for the same key, the guard cannot see it and inserts a fresh marker. ## Invariants

- [Normal condition] Running the annotator twice with the same ticket key over an unchanged file leaves the file byte-identical (sha256), and the second run reports `skipped:already-annotated` for every definition it inspects. Regenerating a checklist twice leaves every byte outside the fence identical.
- [Error invariant] No failure path destroys content. The annotator writes a file only when it has changed it; a generator that cannot determine the fenced region — a file with two fence pairs, or neither fences nor the trailing AI-supplement comment — names the path on stderr, exits non-zero, and leaves the file untouched.
- [Internal state invariant] The count of lines carrying an annotation for a given ticket key is non-increasing across runs. The generator's ownership boundary is the fence, not "everything after the last line it wrote": a human region placed between two generated sections is preserved.
- [Boundary invariant] A zero-length file, a file consisting only of a fence pair, and a file whose definitions sit adjacent to their annotations are each handled without throwing. For an input carrying no human content, generated output is byte-identical to the pre-fix generator's output after timestamp normalisation.

## Boy Scout Rule

The two files this ticket rewrites are themselves the Boy Scout target, because both defects are translatability failures before they are logic failures.

- **One function, one responsibility.** `detectAnnotationAtLine(lines, defLine)` currently encodes two ideas at once — "where an annotation may live" and "which ticket keys it names" — and the first is frozen into the expression `defLine - 2`, a magic offset with no name. It is split into `findAnnotationBlockAbove(lines, definitionLine)` returning the contiguous block, and the key lookup moves to the caller. The offset becomes a named constant, or disappears entirely.
- **Function names as verb phrases.** The new shared module exports verbs, not nouns: `splitFencedRegions`, `composePreservedFile`, `migrateLegacyFile`. The existing generator bodies are a single long function that pushes into a `lines` array and then writes; the write becomes `writeFencedChecklist(...)`, so the call site reads as prose.
- **Domain names over generic ones.** `lines` is acceptable inside a renderer, but the module's boundary must not traffic in it: the preserved region is `preservedText`, the generated body is `generatedBody`, and the fence constants are `FENCE_OPEN` / `FENCE_CLOSE` rather than inline string literals. The generator's current `checklistPath` stays as it is; `sessionDir` versus `rfcDir` in the two siblings is left alone, since renaming across the pair would obscure the diff that this ticket's IT exists to compare.
- **Hardcoded values as named constants.** The trailing AI-supplement comment is currently a template literal duplicated verbatim in two files (line 128 and line 124). It moves to the shared module as a single constant, so the two generators cannot drift — the same failure mode PX-207 found when one sibling was fixed and the other was not.
- **No error swallowing.** The generator's current silent `writeFileSync` becomes a write that either succeeds or reports why it refused by path. No `catch` is added that would convert a refusal into a success.
- **Comments must not lie.** The comment above the AMBIGUOUS guard currently describes a check that does not cover the resolved-marker case; it is rewritten to state what the widened guard actually covers, or removed if the code now speaks for itself.

### Exceptions

- Item: `siprs-with-4layers/.claude/scripts/` — the vendored copy of both generators and of the annotator. Reason: it is not testable here, because it is an external artefact rather than this repository's toolchain — a tracked but vendored snapshot of a different project (3675 files, no `.git` of its own, already divergent: `diff` reports its `generate-checklist.js` differs from the canonical one). A fix applied there, and any test asserting that fix, would assert a property of a tree this repository does not own and would be reverted by the next vendor refresh. This is **not a design defect**; it is an ownership boundary. Alternative verification: the root fix is verified against the canonical `.claude/scripts` tree, and because the annotator lives there, running it against the vendored tree can no longer create duplicates there either.
- Item: Non-consecutive repeat annotations — a file carrying the same ticket key above more than one definition, separated by other lines. The tree repair removed 13 consecutive duplicates across 9 files; it deliberately did not touch repeats that are not adjacent. Reason: it is not testable, because no mechanical predicate separates such a repeat from correct behaviour. A file with eight `test(...)` definitions legitimately carries eight annotations for one key, one per definition; `tests/workspacify-reverse/integration/command.test.mjs` is that instance, with 8 occurrences and 0 duplicates, and `check-io-stubs.js` retains PX-158 twice for the same reason. Judging a particular repeat spurious requires reading each site and deciding whether that definition was actually changed by that ticket — a manual review step, not an assertion. The boundary between machine and human judgement here is **not a design defect**: contract C001 is deliberately stated as the count never increasing, which is the machine-checkable half. Alternative verification: the IT that removes the consecutive duplicates and then re-runs the annotator proves the machine-detectable half; the non-consecutive cases remain a human review item by design.
- Item: Whether the fence comment is invisible when `CheckList.md` is rendered. Reason: it is not testable, because visibility is a property of a Markdown renderer, not of the bytes this repository produces. The byte-level half is asserted — the constants are HTML comment delimiters, and a test proves they collide with neither `[::STUB::]`, `[::TICKET::]`, the `Initial Design Artifact` header, nor any token `scan-incomplete-implementations.js` recognises — but "invisible in every renderer" needs a human to look at a rendered document. This is **not a design defect**: the choice of an HTML comment over the project's `[::...::]` marker idiom is deliberate precisely because the static scanner would misread the latter. Alternative verification: a manual render check during review, with the byte-level collision test as the automated half.

FINDING 1 — contract C001 was not met for block comments. FIXED.
C001's precondition promises the guard searches "the contiguous run of comment lines that ends at the definition". The implementation searched only for lines beginning with `//`, so a block comment ended the run. Measured adversarially: an annotation, then `/** doc */`, then a definition produced action=annotated and a second annotation — the exact defect this ticket exists to eliminate, surviving inside the fix.
This is not hypothetical. The tree contains one live instance, .claude/scripts/tickets/list-phases-and-tickets.js:89-94 — a four-key annotation, a JSDoc block, then `function main()`. `detectAnnotationInCommentBlock(lines, 94)` returned null; it now returns {ticketKeys:["PX-99","PX-100","PX-101","PX-114"], lineIndex:89}. A sweep for the shape found exactly this one site, so the blast radius was one latent duplicate and every future one.
Fixed by widening the scan to accept `/*`, `*` and `//` as comment lines. A line beginning with an asterisk is inside a block comment in JavaScript or is a syntax error, so nothing is over-matched. Two tests were written first and failed: a synthetic block-comment fixture, and the live shape read out of list-phases-and-tickets.js so the site cannot regress silently.
Over-suppression was checked at the boundary and does not occur: a definition preceded by a code line still earns its own annotation; a definition preceded by another definition still earns its own; a blank line still ends the block, which is the documented conservative direction.

FINDING 2 — the fence refuses rather than corrupts when the generated body contains a fence string. NOT A DEFECT, recorded.
If a generated body contained the literal closing-fence text, the composed file would carry two pairs, and the next run refuses with "expected one fence pair, found 1 opening and 2 closing markers" while leaving the human region intact. That is the designed failure mode for an ambiguous region — refuse and name the condition — and it cannot lose content. The input itself is unreachable in practice: the body is generated from node titles and fixed text, and the fixed text contains no fence. Recorded so a future reader does not mistake the refusal for a bug.
