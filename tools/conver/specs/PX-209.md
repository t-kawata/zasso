# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-209: The extension set is a decision, not an omission: .cjs, and the census that keeps it honest

**Ticket Key**: PX-209 · **Phase**: -1

## Background

### Goal
Add `.cjs` to SOURCE_EXTENSIONS so the 134 tracked `.cjs` files in this repository can carry provenance annotations, and make the set's completeness a decision that fails a test when it goes stale, rather than an omission nobody can see.

### Purpose
`SOURCE_EXTENSIONS` describes itself as the single source of truth for which files the annotation system supports. Today it is a hand-maintained list that no check compares against the repository, and its own comment records the consequence: a file the mechanism does not know about is never reported on. The mechanism that binds an implementation to the design context it came from silently does not apply to 134 of this repository's own test files, including the test file for the annotation tool itself.

### Motivation
The identical defect was found and fixed once already: P22-4 added `.mjs` for the same reason, and left a comment explaining why such omissions are invisible. `.cjs` was left behind at that moment and has stayed behind through every ticket since. PX-208 found it while implementing a different fix — the file it was editing could not receive its own provenance annotation — and deliberately did not fold it in, because adding an extension changes behaviour repo-wide and the Plan Gate requires that to be ticketed. Without a check, the next extension will be omitted the same way, and the same ticket will be written again.

### Constraints
- `SOURCE_EXTENSIONS` must keep its shape: a Set of dotted lowercase strings, consumed by `Set.has` in three places in the annotator and one in `show-ticket-locations.js`. No call site changes.
- The vendored trees must stay out of the census by path, not by extension, so a vendored `.rs` and a vendored `.h` are excluded identically.
- The census must be derived at check time from `git ls-files`, never from a stored extension list, or it would have the same defect it exists to catch.
- TDD Red-Green-Refactor is mandatory. Every behaviour here is deterministic — a file list, a set membership, a byte comparison — so nothing may be excused as untestable.
- The change widens what the annotator processes. The property PX-208 established — two runs leave a file byte-identical, and the tree-wide count of consecutive duplicate annotations is 0 — must still hold under the widened filter, re-measured rather than assumed.

### Evidence — the omission, and why it is invisible

`.claude/scripts/tickets/lib/scope-detection-constants.js` declares itself, in its own doc comment, "the single source of truth" for the extensions the annotation system supports. Measured against the repository with both vendored roots excluded, it is not:

| .mjs | 261 | yes |

The census is smaller than it first appears, and that is the point: with `siprs-with-4layers/` and `siprs-for-reverse/` excluded by path, exactly four extensions sit at three or more files without a decision — `.md`, `.json`, `.sh` and `.cjs` — and of those only `.cjs` is source this repository owns.

The 134 `.cjs` files are this repository's own tests: `tests/rfc-graph` 35, `tests/drill-rfc-down` 26, `tests/crystalize-readme` 11, `.claude/archive` 6, `.claude/tests` 4, `tests/tickets` 3, `tests/grill-me-for-rfc` 2, and roughly fifty directly under `tests/` including `annotate-ticket-context-by-git-diff.test.cjs` itself. Twelve more sit in the vendored trees. None of the 146 carries a provenance annotation, and none ever has.

The file already names the reason this went unnoticed, in the comment P22-4 left when it added `.mjs` for exactly the same reason: "the omission is invisible, because a file the mechanism does not know about is simply never reported on." `.mjs` was added; `.cjs` was not, and nothing has compared the set against the repository since.

### Evidence — the set is not merely stale, it is unchecked

Two consumers read it:

- `.claude/scripts/tickets/annotate-ticket-context-by-git-diff.js` — `filterSourceFiles` (line 324), `annotateSourceFiles` (481), `verifyAnnotations` (555).
- `.claude/scripts/tickets/show-ticket-locations.js` — line 134, `if (!SOURCE_EXTENSIONS.has(ext)) continue;`.

Neither reports what it skipped. A file excluded by extension produces no output on any path, so the omission cannot surface as a failure, only as an absence. The module has no test of its own: a search of `tests/` for `scope-detection`, `SOURCE_EXTENSIONS` or `findContainingDefinition` finds no test file, so nothing checks the set today by any means.

### Evidence — the parser already handles .cjs; the set is the only barrier

Measured directly:

```js
findContainingDefinition(["#!/usr/bin/env node", "function alpha() { return 1; }", "module.exports={alpha};"], 1, ".cjs")
// => { startLine: 1, name: "alpha", kind: "function" }   — identical to ".js"
```

`detectLanguage` (scope-detection.js:29-31) returns "indent" only for `.py` and `.rb` and "brace" for every other non-empty hint, so the extension selects a parsing strategy and nothing else. `DEFINITION_PATTERN_METAS` is a 16-entry array applied uniformly, not a per-extension map.

Parse quality on real files, ten-file samples: `.cjs` 7/10, `.mjs` 7/10, `.js` 4/10, `.rs` 7/10, `.ts` 8/10. `.cjs` is not a marginal case; it parses at the same rate as the extensions already admitted.

### Evidence — the three exclusions, each measured rather than assumed

- **`.md`**, 417 files. Prose. The checklist generators write Markdown for a human to read, and the parser would match substrings of prose rather than definitions.
- **`.json`**, 100 files. Data. The parse of a JSON file yields no definitions, and annotating a fixture would corrupt a frozen digest.
- **`.sh`**, 18 files, and this one needed measuring rather than assuming: a ten-file sample yielded 0/10 with a definition detected, while a hand-written `function helper() { ` fixture does match. Admitting `.sh` would annotate nothing while claiming support.

### Evidence — what the vendored roots absorb

`siprs-with-4layers/` (3675 tracked files, no `.git` of its own, already divergent from this toolchain) and `siprs-for-reverse/`. Together they hold 2253 C/C++ files — `.h` 1172 and `.c` 645 under `siprs-for-reverse/` alone, plus `.cc` 314, `.cpp` 68, `.hpp` 55 — and 9 `.gn` files under `siprs-for-reverse/vendor/pjsip/third_party/webrtc_aec3/`. Two tracked files carry no extension at all and are skipped by the census rather than counted as an extension with an empty name.

PX-205 built `make check-conventions`: a document that had drifted from the repository was made checkable by deriving the table from the filesystem and comparing it against the written word. `.claude/rules/node.md` now cannot drift from the tree. ## Boy Scout Rule

The file this ticket edits is a constants module that contradicts its own doc comment, so the Boy Scout work is mostly making the comments true rather than restructuring code.

- **Comments must not lie.** The header of `SOURCE_EXTENSIONS` says the module "is the single source of truth" and then explains only why `.mjs` is present. It is not a source of truth in any checkable sense — nothing compares it to the repository — and the comment's own next sentence names the consequence without drawing the conclusion. Rewritten to say what the set is, that a census checks it, where that census lives, and what it cannot check. The sentence explaining why omissions are invisible is kept: it is the reason the check exists.
- **Hardcoded values as named constants.** The census threshold — the number of files at which an extension stops being a one-off and demands a decision — is a judgement, so it becomes a named constant carrying the reason for its value, beside the two sets it governs, rather than a literal inside a comparison.
- **Domain names over generic ones.** The census module traffics in extensions, not in strings: `censusTrackedExtensions` returns a Map keyed by dotted extension, `findUndecidedExtensions` returns the extensions a decision is owed for, and the ignored path prefixes are `ignoredRoots` rather than a bare array. No `data`, `info` or `tmp`.
- **One function, one responsibility.** The census module separates "read what the repository contains" from "decide whether that is accounted for": `censusTrackedExtensions` performs the `git ls-files` call at its outermost edge and returns a plain Map, and `findUndecidedExtensions` is a pure predicate over that Map. The decision can then be tested without a repository, and the reading can be tested without a decision.
- **No error swallowing.** The census does not fall back to an empty list when `git ls-files` fails. An empty census would report "nothing undecided" — the exact false negative this ticket exists to remove — so a failure to read the repository is a failure of the check.
- **Function names as verb phrases.** `censusTrackedExtensions` and `findUndecidedExtensions` are the two exports; neither is a bare noun, and the existing `SOURCE_EXTENSIONS` / `EXCLUDED_SOURCE_EXTENSIONS` / `VENDORED_ROOTS` names stay as constants, which is what they are.
- **Untested code in anything touched.** The constants module has no test of its own today. The new test file covers it, including the two invariants a reader would otherwise have to take on faith: that the exclusion is by path and not by extension, and that every reason string is present.
