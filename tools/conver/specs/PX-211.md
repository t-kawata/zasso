# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-211: Per-command completion loop: drive each slash command to its status transition before advancing

**Ticket Key**: PX-211 · **Phase**: -1

---

## Background

### Goal
Give each of the four status-transitioning commands (make, plan, start, review) its own completion loop that runs inside the single ACP session which already executes it, so a command that ends its turn before its status transition is pushed to finish instead of being reported as done. Concretely, runPhaseToCompletion replaces runPhaseIfNeeded in src/runner.ts, and a new src/supervisor.ts supplies an escalated instruction from the third attempt onward.

### Purpose
conver must be autonomous from the first ticket to the last. Today a command that stops early is treated as complete: runner.ts:287 prints a completion marker the moment runCommand resolves, and the only recovery is a wave-level retry that opens a fresh ACP session and discards the context the agent had built. The completion loop removes both the false marker and the context loss by re-prompting inside the same session.

### Motivation
Observed directly in the P22-2 run: /start-ticket ended its turn with the status still planned while the log printed a completion marker and advanced; the ticket was recovered only a whole wave later. The requirement is explicit: the loop must keep going on the agent own judgement until the ticket set converges to reviewed. Per-ticket implementation perfection is deliberately not required, because /find-omissions measures the residual gap and converts it into omission tickets, so this ticket optimizes for never stopping rather than for never being wrong.

### Constraints
The completion loop must never write Tickets.json. The supervisor must never be able to stop the loop, so its failure mode is fixed: degrade to the template. No new runtime dependency may be added, so the HTTP call uses node:https as notifier.ts:11 already does. The attempt budget is six per phase and exhaustion must not throw, because the existing wave retry is the recovery path. Provider agnosticism (PX-151) must be preserved: no model or provider name may be hardcoded, and the request must be built entirely from SessionConfig.

## Investigation

Evidence gathered by direct source reading. pipelineAvailable is false for this ticket, so no graph query was available and every finding below is anchored to a file and line.

1. The premature-stop defect has two halves. runner.ts:287 writes the completion marker unconditionally after runCommand resolves, and runner.ts:513 is the only post-check, at ticket granularity, through isTerminalStatus. No per-phase postcondition is evaluated anywhere.

2. The phase preconditions already exist as four inline shouldRun literals at runner.ts:482-486. Their complements are exactly the per-phase postconditions, so the completion predicate is derivable and needs no new declaration. This is the single most important finding: the design adds a loop, not a second source of truth.

3. The agent final message is already computed and already discarded. session.ts:334 assigns fullResponse from msg.response when kind === "stop" and session.ts:356 returns it. All six call sites in runner.ts (286, 303, 315, 501, 558, 570) await runCommand without binding the result, so the primary supervisor signal is currently thrown away at every opportunity.

4. runCommand accepts arbitrary prompt text: its signature at session.ts:276 takes a plain string and forwards it to session.prompt. A re-prompt therefore needs no SDK change and no new session, which is what makes in-session re-prompting possible at all.

5. Session lifetime is owned by withSession (session.ts:195) and runWithSession (runner.ts:186), and the four-command callback already runs inside that callback at runner.ts:479-489. A completion loop placed there keeps the session alive for free; one placed outside would force a new session and lose the agent context.

6. The status vocabulary is project-defined rather than schema-validated: todo, made, planned, done, reviewed, remanded, and R<n> matching /^R[1-9]\d*$/ (tickets.ts isRoundStatus; README status table). isTerminalStatusValue at runner.ts:244 tests reviewed or the R pattern.

7. The existing recovery path is wave-level. runner.ts:445-450 builds retryCandidates from pending tickets already in processedDistinct and not in giveUp, and runPhaseIfNeeded re-reads the status before each phase so a completed phase is not re-run. The completion loop must therefore not throw on exhaustion, or it would pre-empt this path.

8. Precedent for the policy object: retryPolicy is exported mutable at runner.ts:115 specifically so tests can shorten delays. completionPolicy follows the same shape so tests can set maxAttempts to 2 and assert exact counts.

9. HTTP precedent: notifier.ts:11 imports node:https and notifier.ts:115-119 switches between https.request and http.request by protocol, but it exposes no injection seam. The supervisor therefore introduces a transport parameter, which the test runner discipline also requires: runner.test.ts:7-8 documents that mock.module() may be called only once per module, making parameter injection the cheaper seam for a new module.

10. Build and test shape: package.json declares type module and test = node tests/run-all-surfaces.mjs; unit suites are compiled by npx tsc and run with node --experimental-test-module-mocks --test over dist files. Makefile:35 enumerates the dist test files explicitly, so the new suite must be added there or it will silently never run. engines.node is >=22.

11. No new dependency is implied: node:https, node:child_process (execSync for the workspace probe) and node:fs are all already used in the codebase.

## Acceptance Criteria

- - [Happy path] A phase whose agent stops early is re-prompted inside the same ACP session. Concretely, with a fixture status of planned for /start-ticket: the loop sends the command, then the template twice, then one generated instruction on the third attempt, the fixture advances to done, exactly one supervisor request is issued, the completion marker is printed, and every prompt carried the same sessionId.
- - [Error case] When the supervisor transport fails the loop continues with COMPLETION_TEMPLATE and never rejects. When the attempt budget is exhausted with the status still unchanged, runPhaseToCompletion resolves without throwing, the fixture bytes on disk are unchanged, and control returns so the existing post-check schedules the wave retry.
- - [Edge case] A phase whose status already satisfies the postcondition at loop entry issues zero extra prompts and prints no in-progress marker. A phase that never converges costs at most 6 prompts and at most 4 supervisor requests, and the next phase still runs when its own precondition holds.

## Invariants

- [Normal condition] isComplete(status) === !shouldRun(status) holds for every PhaseSpec and every status value in {todo, made, planned, done, reviewed, remanded, R1, R2}. A phase is treated as complete exactly when its own precondition no longer holds, so the loop never advances on a status it has not observed. Verified as a property over the vocabulary rather than as four hand-written cases.

- [Error invariant] generateCompletionMessage never rejects and never resolves to an empty string. Transport rejection, non-2xx status, malformed JSON, a missing content array, and empty text each resolve to COMPLETION_TEMPLATE. No supervisor failure can terminate the completion loop, which is the single property that keeps autonomy intact.

- [Internal state invariant] The completion loop never writes Tickets.json; only readTicketStatus touches the file. Status transitions remain the exclusive prerogative of the slash commands, so conver stays a reader of loop state and never a writer, and a conver restart cannot corrupt a partially applied transition.

- [Boundary invariant] The completion loop issues at most completionPolicy.maxAttempts re-prompts and then returns without throwing, so the total runCommand count per phase is bounded by 1 + maxAttempts for every status sequence. Exhaustion degrades to the existing wave retry at runner.ts:513 rather than raising.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — phase pre-condition to post-condition duality

- **Precondition**: A PhaseSpec whose shouldRun predicate is defined over the ticket status vocabulary, and a status string read from Tickets.json by readTicketStatus (runner.ts:224). The four predicates are the inline literals at runner.ts:482-486. Translate as: an input schema of {phase: make|plan|start|review} x {status: todo|made|planned|done|reviewed|remanded|R1|R2}.
- **Postcondition**: isComplete(status) returns true exactly when shouldRun(status) returns false, so the loop advances only on an observed transition. Translate as the state-transition predicate: make completes iff status !== "todo"; plan completes iff status is not in {todo, made}; start completes iff status is not in {todo, made, planned}; review completes iff status === "reviewed" or /^R[1-9]\d*$/ matches.
- **Invariant**: For every status s, shouldRun(s) and isComplete(s) are never both true and never both false. Assertable as a property over the full cross product, not as four hand-written cases.

### C002 — attempt budget to template selection

- **Precondition**: The attempt counter is 1 or 2 (completionPolicy.templateAttempts) and the phase postcondition does not yet hold. Translate as: attempt <= templateAttempts.
- **Postcondition**: The prompt sent through runCommand (session.ts:276) is byte-identical to COMPLETION_TEMPLATE. Translate as a strict string equality assertion on the captured prompt argument.
- **Invariant**: The string sent on attempts 1 and 2 does not depend on status, ticket, or workspace state. Assertable by driving two different statuses and two different tickets through attempts 1 and 2 and asserting the captured prompts are equal to each other and to the constant.

### C003 — supervisor transport to loop liveness

- **Precondition**: generateCompletionMessage is called with any SupervisorRequest and any transport implementation. The transport is a parameter, not a module import, because runner.test.ts:7-8 documents that mock.module() may be called only once per module.
- **Postcondition**: It resolves to a non-empty string and never rejects. Translate as: await returns typeof string and length > 0.
- **Invariant**: Every failure mode resolves to COMPLETION_TEMPLATE: transport rejection, non-2xx statusCode, malformed JSON body, a body with no content array, and a content array whose first text is empty. Assertable as a five-row table asserting every resolved value is the constant.

### C004 — attempt budget to termination

- **Precondition**: completionPolicy.maxAttempts is 6 and the phase postcondition never becomes true. The policy object is exported mutable following the precedent of retryPolicy at runner.ts:115 so tests can set it to 2.
- **Postcondition**: runCommand is invoked once before the loop plus once per attempt, for a total of 1 + maxAttempts = 7, after which runPhaseToCompletion resolves rather than rejecting. Translate as an exact call-count assertion on the injected runCommand.
- **Invariant**: The completion loop performs at most maxAttempts re-prompts for any status sequence. Assertable by driving an adversarial status timeline that never advances and asserting the cap holds.

### C005 — completion loop to ticket file

- **Precondition**: A completion loop runs to any outcome, including budget exhaustion. The only ticket-file reader on this path is readTicketStatus (runner.ts:224).
- **Postcondition**: The bytes of Tickets.json are unchanged. Translate as a deep-equal assertion on the Buffer read before and after.
- **Invariant**: Only readTicketStatus is called on the ticket file by the loop, so status transitions remain the exclusive prerogative of the slash commands. Assertable by asserting no write occurs on the fixture path for the loop duration.

### C006 — completion loop to session lifecycle

- **Precondition**: A phase requires more than one attempt. Sessions are created only by withSession (session.ts:195) via runWithSession (runner.ts:186), and the four-command callback already runs inside that callback at runner.ts:479-489.
- **Postcondition**: Every prompt for that phase is issued on the same AcpSession instance and reports the same sessionId. Translate as reference equality on the session argument captured by the injected runCommand.
- **Invariant**: The completion loop never calls withSession, so no session is created or disposed inside the loop. Assertable by asserting the withSession call count is unchanged by the loop.

### C007 — phase boundary to session callback

- **Precondition**: A phase exhausts its attempt budget with the postcondition still false. The pre-existing catch at runner.ts:590 and the terminal-status post-check at runner.ts:513 are the surrounding recovery path.
- **Postcondition**: Control returns to the caller and the next phase is evaluated by its own shouldRun predicate. Translate as: the session callback continues to the next phase rather than throwing out of it.
- **Invariant**: No phase outcome aborts the enclosing session callback, so remaining phases still run when their preconditions hold. Assertable by exhausting phase one and asserting phase two's command is still dispatched.

## Boy Scout Rule

This ticket touches runner.ts, which is 629 lines and approaching the 800-line ceiling, so the plan deliberately keeps growth out of it: all HTTP, request assembly and truncation live in the new src/supervisor.ts, and runner.ts gains only the loop and its constants.

1. Extract the four anonymous shouldRun literals at runner.ts:482-486 into named PhaseSpec values. Predicates written inline inside a callback cannot be read as prose and cannot be reused for the post-check; naming them is what lets one declaration serve as both precondition and postcondition.

2. Stop discarding return values at the six runCommand call sites. A function whose result is ignored at every call site makes the code read as though runCommand had no result, which is a translatability defect independent of this ticket.

3. Rename runPhaseIfNeeded to runPhaseToCompletion. The old name describes a condition check, while the new behavior is a loop; the new name is a verb phrase describing what the function does, per the functions-are-verb-phrases rule.

4. Extract the payload magic numbers (1500, 800, 512, 3) into completionPolicy instead of inlining them in the builder.

5. readTicketStatus at runner.ts:224 collapses five distinct failure causes (unreadable file, invalid JSON, missing phase, missing ticket, no match) into the single value "todo". The completion loop is sensitive to that collapse, so the touched function gains a named constant for the fallback status and a comment stating why the safe direction is to treat the ticket as not started.

6. getCurrentPhase at runner.ts:85-99 derives a phase name by substring-matching an error message. It sits in the touched file but not on the completion path, so the plan is to leave it alone rather than widen this ticket, and to record it as a follow-up instead of silently rewriting it.

### Exceptions

- The semantic quality of the supervisor message is not asserted. It is not testable because the supervisor is an LLM whose output varies between calls, so asserting on its wording would make the test flaky rather than the design untestable. Reason category: non-determinism. This is not a design defect: the deterministic boundary is fully covered, namely that a well-formed response is passed through byte-for-byte and that every failure mode degrades to COMPLETION_TEMPLATE. The uncovered part is the model judgement itself, which is the intended non-determinism and is exercised as a control-flow branch rather than as content.
- Real end-to-end provider behaviour — latency, rate limiting, and provider-specific HTTP semantics of the supervisor call — is not covered by automated tests. It is impossible to test without a live third-party endpoint, which is an external dependency rather than a property of this repository. Reason category: external dependency / E2E.
