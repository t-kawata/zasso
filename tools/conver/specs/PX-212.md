# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-212: Supervisor instruction extraction: select the text block, not the first content block

**Ticket Key**: PX-212 · **Phase**: -1

---

## Background

### Goal
Make the supervisor deliver a situation-appropriate instruction in production, so that attempts 3 to 6 of the completion loop carry an escalated, situation-aware message rather than the fixed template. The loop is worthless if only the template ever comes back.

### Purpose
PX-211 shipped the supervisor with a completion loop whose entire value above attempt 2 is the generated message. Extraction read content[0] unconditionally, so against the configured provider every call degraded and that value was never delivered once.

### Motivation
Established by live measurement on 2026-09-14 through the real default transport, not by inspection. All four scenarios (plain stall, delegated wait, real blocker, high-pressure escalation) returned COMPLETION_TEMPLATE. The raw body showed content block types [thinking, text]: content[0] is a thinking block with no text field, and content[1] carries a correct, on-target instruction that was being discarded. The generated instruction was already right; only the extraction failed.

### Constraints
The never-throw contract of generateCompletionMessage must be preserved. The repair must not assume any provider-specific block ordering, because assuming the shape is precisely the defect being repaired. No new runtime dependency. The semantic quality of the generated message remains out of scope, as declared in PX-211 testExceptions.

## Investigation

Evidence gathered by live measurement against the configured provider on 2026-09-14, then by reading the code that mis-handled it. No graph query was available (pipelineAvailable is false); every finding is anchored to an observed value or a file and line.

1. Transport is correct. A real request through the default postJsonHttps reached https://api.deepseek.com/anthropic/v1/messages and returned HTTP 200 in 2.4 to 3.9 seconds. Header names sent were content-type, x-api-key, anthropic-version and were accepted. Model was deepseek-flash. The PX-211 request shape is therefore sound.

2. Response shape is the defect. The body is {"content":[{"type":"thinking","thinking":"...","signature":"..."},{"type":"text","text":"Finish the run: ..."}],"stop_reason":"end_turn","usage":{...}}. content[0] is the thinking block and has no text field; content[1] is the instruction.

3. src/supervisor.ts extractInstruction reads parsed.content?.[0]?.text, so it returns null for this shape. generateCompletionMessage then takes the null branch and returns COMPLETION_TEMPLATE with the stderr line "[conver] supervisor 縮退 (empty content): no usable instruction text".

4. Consequence measured end to end. Four scenarios were driven through the real default transport with the real request builder: plain stall, delegated wait, real blocker, and a high-pressure escalation carrying five prior instructions at attempt 6. All four returned COMPLETION_TEMPLATE. The escalation path shipped by PX-211 has therefore never produced a generated message in production.

5. The generated instruction was already correct. The discarded text block read, verbatim: "Finish the run: complete the artefact generation you stopped on, write the real frozen-holdout outputs from src/holdout.rs, and verify they are produced exactly once (re-running must not regenerate or mutate the frozen holdout). Re-run the full suite to confirm all green with the real artefacts in place. Then emit the status transition by running update-ticket.js for P22-2 to move it from planned to done, and confirm the status field reports done. Do not stop, summarize, or return until that transition has been emitted." This names the concrete missing step, assumes the information already exists, and forbids returning early, which is exactly the required stance. The prompt is not the defect.

6. The thinking block cannot be controlled by prompt wording, only by request parameters. A side-by-side probe with the same body plus thinking {type: disabled} returned content block types [text] with content[0].text present. That yields a second, optional fix, but relying on it alone would repeat the very mistake being repaired: assuming a shape instead of tolerating one.

7. Why the existing suite could not catch this. Every test in src/supervisor.test.ts supplies a fake HttpPostJson returning a single-element content array whose head is the text block. The test double encoded the same assumption as the implementation, so no assertion could distinguish correct from incorrect extraction. This is the failure mode the supreme law calls a disguised green.

8. Blast radius is confined. extractInstruction is private to src/supervisor.ts and has exactly one caller, generateCompletionMessage. No other module parses provider responses; notifier.ts posts to Slack and discards the body.

9. The PX-211 testExceptions entry claiming provider compatibility lay outside the system boundary was wrong. The response shape is not a third-party contract detail; it is the contract this code must satisfy, and it was cheap to verify. This ticket removes that exception.

## Acceptance Criteria

- - [Happy path] A response whose content array is [thinking, text] yields the text of the text block, and the completion loop sends it as the next prompt instead of the template. Concretely: the same four scenarios that all degraded on 2026-09-14 return generated instructions.
- - [Error case] A response with no usable text block in any position degrades to COMPLETION_TEMPLATE without rejecting, so the loop keeps running exactly as PX-211 specified. Nothing is fabricated and nothing is truncated into a partial instruction.
- - [Edge case] Block ordering, unknown block types and empty text blocks never raise. The first usable text block wins; several text blocks resolve deterministically to the first; and the absence of any usable text yields the template.

## Invariants

- [Normal condition] extractInstruction returns the text of the first block whose type is text and whose text is a non-empty string, independent of that block position in the content array. For any two responses differing only by leading non-text blocks, the extracted instruction is identical.

- [Error invariant] generateCompletionMessage never rejects. Transport rejection, non-2xx status, malformed JSON, a missing content array, and a content array with no usable text block all resolve to COMPLETION_TEMPLATE. The liveness property established by PX-211 is preserved unchanged.

- [Internal state invariant] No fabricated or partially extracted instruction is ever returned. When no usable text block exists the function returns the template rather than an empty string, a thinking block content, or a truncated fragment.

- [Boundary invariant] Block ordering never causes an exception. An unknown block type before a text block, several text blocks, and an empty text block all resolve deterministically: the first usable text wins, and the absence of any usable text degrades to the template.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — response content array to extracted instruction

- **Precondition**: A parsed response body whose content is an array of blocks, each optionally carrying a string type and a string text
- **Postcondition**: The returned instruction is the text of the first block whose type is text and whose text is a non-empty string, regardless of that block position in the array
- **Invariant**: For any two responses that differ only by the presence of leading non-text blocks, the extracted instruction is identical

### C002 — absent text block to template degradation

- **Precondition**: A parsed response body in which no block has type text with a non-empty string
- **Postcondition**: generateCompletionMessage resolves to COMPLETION_TEMPLATE
- **Invariant**: No fabricated or partially extracted instruction is ever returned when no usable text block exists

### C003 — supervisor failure to loop liveness

- **Precondition**: generateCompletionMessage is called with any transport implementation and any response body
- **Postcondition**: It resolves to a non-empty string and never rejects
- **Invariant**: Every failure mode, including transport rejection, non-2xx, malformed JSON, missing content and unusable blocks, resolves to COMPLETION_TEMPLATE

## Boy Scout Rule

This ticket touches src/supervisor.ts and src/supervisor.test.ts, both created by PX-211, so the Boy Scout work is about leaving the parse path clearer than the fix found it rather than about pre-existing debt elsewhere.

1. Name the concept instead of the index. The function currently expresses "read the first block", which says nothing about what it wants. It will express "find the block that carries the instruction", so the code states its intent rather than its mechanism.

2. Widen the response type annotation to admit that blocks differ by type. Typing content as Array<{ text?: string }> is itself the assumption that produced the bug; the type should say that a block has an optional type and an optional text so that a reader sees the discrimination the code must perform.

3. Keep the extraction total. A helper that returns string or null keeps the degrade decision in one place, which is what allows the never-throw contract to be read off the code rather than inferred.

4. Test naming should describe the situation, not the mechanism. Tests named after the captured production shape (a thinking block preceding the text block) record why the case exists, so a future reader cannot delete it as redundant with the single-text-block case.

5. Record the evidence in the test as a comment naming the endpoint and the date it was captured, so the fixture is traceable to a measurement rather than looking like an invented shape.
