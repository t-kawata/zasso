# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-219: The publication is safe on a host project root: the reload scan names what pre-existed, and a gate that refuses after publication takes the publication back

**Ticket Key**: PX-219 · **Phase**: -1

---

## Background

### Goal
Make the forward (allocate) rotation's `finalize` reach `published: true` on a workspace root that is a host project directory, and leave no published tree behind when a gate refuses after the publication has happened.

### Purpose
`verifyDirectorySet(root, plan)` compares every directory beneath the workspace root against the plan and requires the two sets to agree exactly. The doctrine's own model is a root dedicated to the workspace, holding the specification and the stage-1 manifest as files. In practice a consumer runs the rotation with `workspaceRoot = dirname(manifestPath)`, and that directory is frequently the host project's own root: it holds the specification and the manifest beside `.git`, `docs/`, `node_modules/` and everything else the project already had. `checkExistingOutputPolicy` (G2) passes, because the planned paths themselves are fresh; every gate up to and including G6 passes, so the tree, its 28 seeds and the allocate manifest are published; and then the reload scan reports the pre-existing directories as `unexpected` and fails the run at G6.4.

### Motivation
Two harms, and the second is why this cannot wait. First, a workspace the rotation's own entry gates declared eligible can never be finalised - the false positive is unconditional for this caller shape. Second, and worse: because the publication already happened, the failure leaves a published tree with no verdict, which is the exact partial state the doctrine "a failed run never publishes" forbids. Fixing only the false positive would make the common case pass and leave the failure path unsafe for every other cause - a genuine reload divergence, a hash mismatch, a graph change - so the missing rollback is in scope in the same change.

### Constraints
The fix is already proven in production (gaia) under the same supreme law, so its shape is ported rather than redesigned: `docs/INFO03.md` Appendix A is the change, verified byte-intact and applicable to this tree. `preExisting` must default to the empty list, because strict equality is what the reverse rotation's A1 safety inversion ("every existing path is planned; a single extra path is BLOCKED") relies on. The `unexpected` computation must not be dropped: it is what catches a directory *this run* created outside its plan. `checkExistingOutputPolicy` and `publishStagedTree`'s destination-exists refusal must not be weakened, because together they are the rollback's safety argument. No published artefact schema changes. No `Initial Design Artifact` header is edited and no annotation on an untouched line is tidied. Work item 2 of `docs/INFO03.md` (the staged decisions document must not be swept) is a separate ticket and a separate change of intent, and is not part of this one.

## Acceptance Criteria

- Happy path: `runFinalize` over a workspace root that already holds directories the plan says nothing about reaches `published: true`, reports `G6:PASS`, and reports the reload scan's `unexpected` as empty; the pre-existing entries are still present afterwards and the published tree, seeds and allocate manifest are in place.
- Error case: a divergence that makes G6.4 or G6.5 refuse after the publication has happened leaves the workspace root exactly as the run found it - every entry the publication placed is gone, every pre-existing entry is intact - and the thrown `WorkSpacifyTreeError` still names gateId `G6.4` or `G6.5`.
- Edge case: a caller that passes no `preExisting` (the staging checks, the reverse rotation, `tests/workspacify-allocate/reverse/safety-inversion.test.mjs`) still gets strict equality, and a directory this run created outside its plan is still reported as `unexpected`; a run whose plan is empty still publishes nothing and verifies.

## Invariants

- [Normal establishment] Before `publishWorkspace` runs, `snapshotDirectories(manifestDir)` returns the root's directory set and `new Set(readdirSync(manifestDir))` returns its entry-name set; both are read from the root alone and neither depends on the plan.
- [Error invariant] On a refusal at G6.4 or G6.5 the publication is removed before the `WorkSpacifyTreeError` is thrown, so no run that ends in an error leaves a published entry behind; and every entry present in the pre-publish snapshot survives both the publication attempt and the rollback.
- [Internal state invariant] `unexpected = dirs - ancestorClosedPlan - preExisting` and `missing = ancestorClosedPlan - dirs`: with `preExisting` empty this is exactly the strict set difference `verifyDirectorySet` computed before, so the staging checks and the reverse rotation's A1 inversion keep their meaning.
- [Boundary invariant] `preExisting` defaults to the empty list. A caller that omits it - every caller except `runFinalize` - gets the previous behaviour byte for byte, and a directory created by this run outside its plan is reported whether or not a snapshot was passed.

### C001 — docs/INFO03.md Appendix A - tree-staging.mjs: new export snapshotDirectories, placed beside verifyDirectorySet (:149) and built on walkTree (:203); consumed by run.mjs runFinalize's pre-publish read

- **Precondition**: `root` names an existing directory. It may hold directories at any depth, regular files, and a directory named `workspacify` (the reserved root) at any depth. No assumption is made about what else is present: the caller passes the workspace root, which may be a host project directory holding .git, docs, node_modules and other sources.
- **Postcondition**: `snapshotDirectories(root)` returns a new array holding the root-relative POSIX path of every directory beneath `root`, sorted ascending, each exactly once. No non-directory entry appears. No path equal to `workspacify` or beneath it appears.
- **Invariant**: The returned set is exactly `walkTree(root).dirs` - the same walk `verifyStaging` and `verifyDirectorySet` compare against - so a snapshot and a comparison share one definition of what counts as a directory of the workspace and one exclusion of the reserved root. The call is read-only: it creates, renames and removes nothing.

### C002 — docs/INFO03.md Appendix A - tree-staging.mjs: verifyDirectorySet gains an optional third parameter `{ preExisting = [] }`; consumed by run.mjs runFinalize's reload directory scan (G6.4)

- **Precondition**: `root` is a directory; `plan` is a list of root-relative planned directories; `preExisting` is either omitted or an array of root-relative paths taken from a `snapshotDirectories(root)` call made before the run published.
- **Postcondition**: The returned `unexpected` holds every directory of `root` that is in neither the ancestor-closed plan nor `preExisting`. `missing` holds every planned directory absent from `root`. `ok` is true exactly when both are empty.
- **Invariant**: With `preExisting` omitted or empty, `unexpected` is exactly the set difference between the root's directories and the ancestor-closed plan - the strict equality the reverse rotation's A1 safety inversion depends on. A directory the run created outside its plan is reported whether or not a snapshot was passed, so the scan still catches this run's leakage.

### C003 — docs/INFO03.md Appendix A - publish-allocate-manifest.mjs: new export publishedTopLevelNames; consumed by publishWorkspace (:95-99 today) and by runFinalize's rollback closure

- **Precondition**: `plan.relativeDirs` is an array of root-relative planned directories, possibly empty or absent, and `renderedByPackage` is a Map from package id to an object carrying `package.path`.
- **Postcondition**: The returned array holds each top-level segment of every planned directory and of every rendered package path, plus `ALLOCATE_MANIFEST_FILE_NAME`, de-duplicated and sorted ascending.
- **Invariant**: The result is identical to the inline derivation it replaces, so `publishStagedTree` receives the same names it received before, and the rollback judges exactly the names the publish placed. The `?? []` guard matches the sibling reader `verifyStagedWorkspace` in the same module, so both readers of a plan tolerate an absent `relativeDirs` alike.

### C004 — docs/INFO03.md Appendix A - publish-allocate-manifest.mjs: new export rollbackPublication; consumed by runFinalize's G6.4 and G6.5 refusal paths

- **Precondition**: `manifestDir` is the workspace root; `topLevelNames` is the list a publication placed; `preExistingEntries` is a Set of the root's entry names read before that publication.
- **Postcondition**: For every name in `topLevelNames` absent from `preExistingEntries` and present under `manifestDir`, the entry is removed recursively; the returned `removed` lists exactly those names, sorted. A name present in `preExistingEntries` is never removed and never reported. A name that does not exist is not reported.
- **Invariant**: No entry present in `preExistingEntries` is ever removed - pre-existing content is not this run's to delete - and because `publishStagedTree` refuses to rename onto an existing destination, an entry absent from that Set cannot have pre-existed. `removed` therefore describes the root rather than the intent.

### C005 — docs/INFO03.md Appendix A - run.mjs runFinalize: the pre-publish snapshot bindings, the snapshot passed to verifyDirectorySet, and the rollback calls on the G6.4 and G6.5 refusal paths

- **Precondition**: `runFinalize` has passed every gate through G5 and is about to call `publishWorkspace`; `manifestDir` may be a host project root holding directories the plan says nothing about.
- **Postcondition**: The root's directory set and its entry-name set are read before `publishWorkspace` runs; `verifyDirectorySet` is called with the directory snapshot; and on either a failed reload directory scan (G6.4) or a failed `reloadAndVerify` (G6.5) `rollbackPublication` runs before the `WorkSpacifyTreeError` is thrown, so no published entry survives a refused run.
- **Invariant**: A run that publishes and then refuses leaves the root as it found it; a run that reaches `published: true` has had nothing rolled back. No caller of `verifyDirectorySet` outside `runFinalize` passes a snapshot, so the reverse rotation and the staging checks keep strict equality.

## Boy Scout Rule

Translatability in the code this ticket touches, applied only after every test is green.

1. **`snapshotDirectories` reads as its name.** It returns what it says: the directory set of a root. The alternative - a `walkTree` import in `run.mjs` - would have exposed the walk and made the caller responsible for the reserved-root exclusion, so the function keeps the module's single definition of what a directory of the workspace is. Its doc comment states what it returns and why one walk serves both the snapshot and the comparison.

2. **`publishedTopLevelNames` replaces an anonymous five-line expression with a named one.** Inline, `publishWorkspace` said `[...new Set([...])].sort()` and the reader had to derive the meaning from the parts. Named, the same value reads as "the top-level names a publication places", and the rollback can judge the same set through the same name - one derivation, two consumers, which is the DRY reason and also the reason the two cannot drift.

3. **`rollbackPublication` is a verb with a bounded object.** The old failure path had no name for undoing a publication: G6.4 threw and G6.5 called a function whose name (`removeWorkspaceArtifacts`) describes staging, not the published set. The new name says what is removed and the JSDoc says what is never removed, so the safety argument is legible at the call site instead of inferable from `publishStagedTree`'s behaviour.

4. **The `?? []` guard in the extraction removes a divergence between two readers of the same field.** `verifyStagedWorkspace` already tolerated an absent `plan.relativeDirs`; the inline derivation did not. Extracting through the guarded form leaves one rule for one field in one module.

5. **`runFinalize`'s four new bindings are named for what they are** (`preExistingDirs`, `preExistingEntries`, `topLevelNames`, `rollbackPublicationOfThisRun`) rather than for where they came from, so the sequence reads as prose: read what the root already held, plan the names the publication will place, publish, then verify - and, if the verification refuses, undo the publication.

6. **Boy Scout fixes inside the touched lines.** The doc comment above `verifyDirectorySet` is a false comment once `preExisting` exists - it claims a strict comparison and says nothing about the operator's own directories - so it is rewritten in the same change rather than left to rot. No `unwrap`-equivalent (unchecked `statSync`/`readdirSync`) is added, no hardcoded path is introduced (the reserved root is read from `RESERVED_ROOT_NAME`, the manifest name from `ALLOCATE_MANIFEST_FILE_NAME`), and every new branch is covered by a named case.

7. **Out of scope by the same principle.** `P22-12` and the PX-214/PX-215 annotations in `run.mjs` mark other tickets' work; they are not tidied, renamed or re-flowed, because touching a line to improve it would move the line the reload scan and the annotation verifier read.
