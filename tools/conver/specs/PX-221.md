# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-221: Every recorded source hash fingerprints the text it names, and /explain-seed reads the place of one seed back to the human who must grill it

**Ticket Key**: PX-221 · **Phase**: -1

---

## Background

【Goal】Correct one recorded hash and add one command, delivered as one body of work in one payload. (1) `structure.segments[].sha256` in every `WORKSPACIFY-TREE-MANIFEST.json` must equal the SHA-256 of the segment's own text. Today it equals the SHA-256 of a byte window addressed by the segment's character offsets, so on the Japanese specification the value names no text at all and no gate notices. (2) A new command `/explain-seed` takes exactly one argument — the path to an `RFC-SEED.md` — and does everything else itself: it writes `EXPLAIN-RFC-SEED.md` beside that seed in plain Japanese and prints the same Markdown to stdout, so an AI can hand a human a complete, kind account of where the seed sits in the whole, what it carries, and what the grill must settle.

【Purpose】The grill is the first step a human takes into a package and the step with the least mechanical support: the seed's section 1 JSON and the two manifests already contain the dependency graph, the contract clauses and the owned semantics, but nothing reads them back. A human who does not already hold all of that in their head cannot grill well, and re-deriving it by hand is where attention is lost. Separately, a hash that names no text is worse than no hash, because it looks like traceability and is not: a reader who trusts it is misled by the record itself.

【Motivation】Measured 2026-09-28, read-only, against `~/shyme/gaia`. Replaying the toolchain's own modules reproduces the frozen manifest exactly (`source_hash` 2705c93c…, 919969 bytes, 605946 characters, all 31 segments). Within that reproduction, `sha256Hex(bytes.subarray(byte_start, byte_end))` equals the recorded `sha256` for 31 of 31 segments, and `sha256Hex(sourceText.slice(byte_start, byte_end))` equals it for 0 of 31. The offsets themselves are correct: the character slice begins on a `## ` heading for 31 of 31 segments, and `inventory.*.snippet` equals the character slice for 76 of 76 recorded snippets. `markdown.mjs` documents that P26-4 changed these fields to string offsets — because byte counting put a heading's start in the middle of an earlier line — and that the rename belongs to its own ticket; `buildSegment` was left behind by that change. `verifyReconstruction` cannot see it, because it concatenates contiguous windows and therefore reproduces the input whatever the offsets mean.

【Constraints】The work target is `tools/conver` only. `~/shyme/gaia` is read-only and is used only to confirm behaviour against real data; no test may depend on it — no gaia path, hash or fixture content may appear in test code. The string-offset convention itself stays: the offsets are right and only the hash is wrong, and inverting the convention would move every heading, every inventory reference and every line number. The command takes one argument and nothing else — no output option, no manifest option, no environment variable. The frozen baseline `tests/workspacify-tree/baselines/manifest-hashes.json` is part of the delivery, not bookkeeping, because `install.js` reads it to report a regression verdict.

## Investigation

Measured on 2026-09-28, read-only, against `~/shyme/gaia` (a published two-stage workspace) and against `tools/conver`. The working tree of the work target was clean.

(1) The defect, measured by reproduction. Replaying the toolchain's own modules — `normalizeTextBytes` from `lib/normalization.mjs`, `buildHeadingTree` from `lib/headings.mjs`, `segmentAtHeadings` and `verifyReconstruction` from `lib/segmentation.mjs`, `sha256Hex` from `lib/hash.mjs` — over `GaiaSekkeiShiyousho_v31.md` reproduces the frozen manifest exactly: the recomputed source hash equals `input.source_hash` (`2705c93cd6d82c27b3a6b0ab8dd21d67b0ce38cd43a2b8b7f8c08851a4e39aa7`), `input.source_bytes` is 919969 and `input.source_characters` is 605946, and all 31 segments match on `byte_start`, `byte_end` and `sha256`. The recorded value is therefore the hash of a byte window addressed by a character offset. Worked example: segment `s-000006`, whose heading is `## 4. 成熟度depthと発行資格`, records the hash of the window that begins inside `…genesisに定められた…`.

## Acceptance Criteria

- Happy path: the affected surfaces exit 0 under `node --test`; a non-ASCII fixture's segment records the hash of its own text while an ASCII fixture keeps the value it had; `regression check` exits 0 over a baseline whose diff is exactly one moved manifest hash; and one command run on a seed path writes `EXPLAIN-RFC-SEED.md` beside that seed whose bytes equal what stdout carried, over a workspace assembled entirely from fixtures.

## Invariants

- 【Normal establishment】After the fix, for every document and every segment, `sha256Hex(sourceText.slice(segment.byte_start, segment.byte_end))` equals the recorded `segment.sha256`, and `node .claude/scripts/workspacify-reverse/run.mjs regression check` exits 0 over the regenerated baseline.

- 【Internal state invariant】The offsets stay string offsets: `byte_start`, `byte_end`, `line_start`, `line_end` and `sha256` all describe one interval, so no two of them can disagree about where a segment begins and ends, and `verifyReconstruction` keeps returning `PASS` for the whole document.
- 【Boundary condition】An ASCII-only document keeps the hash it had before the fix, and a document whose first level-2 heading does not sit at offset 0 still yields a preamble segment satisfying the same predicate. The command resolves its inputs for a seed at any depth below the workspace root, because it walks up to the directory holding the tree manifest rather than counting directory levels, and the document it writes is one rendering delivered to two sinks, so the file and the channel cannot differ.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — P26-4 -> segmentation.mjs — the offset semantics the hash must follow

### C006 — workspacify-allocate -> seed_index and the reference block — the hashes the command must verify

- **Postcondition**: every recorded hash is recomputed before a byte is written, and on any mismatch the command exits non-zero and leaves no EXPLAIN-RFC-SEED.md behind.

### C007 — explain-seed -> the human who must grill

- **Precondition**: the seed, the two manifests and the specification are the only inputs.
- **Postcondition**: every fact in the document names its source — a manifest field, a package id, a boundary id, a section id or a line range — and the residual and grill-question section states an absence when the package owns none.
- **Invariant**: a fact the script cannot find is reported as absent rather than smoothed over, because the honesty of the document is the property the human relies on.

### C008 — P26-4 -> partitionStats — the same offset semantics, one function away from buildSegment

- **Precondition**: partitionStats(segments, total) is called with the segments segmentAtHeadings returns and with the length, in the unit those offsets use, of the text the segments partition.
- **Postcondition**: for a document carrying non-ASCII text, covered_bytes equals the length the segments cover, last_byte equals the length of the document, and is_total_partition is true; a gap, an overlap and a truncation each still make it false.
- **Invariant**: the second parameter is the length the offsets index into, so passing a byte length where that length belongs must not be reported as a total partition — the parameter's unit is load-bearing rather than decorative.

## Boy Scout Rule

Translatability plan for the code this ticket touches.

- The fixed function reads as one sentence: a segment knows its offsets, the lines those offsets fall on, and the hash of the text they name. That is only true when the hash is taken over the text, so the change is not an optimisation but the removal of a contradiction inside one record. `buildSegment` receives the text and hashes the slice; `sourceBytes` stays where it belongs, in `verifyReconstruction`, which genuinely works on bytes.
- The new module is a paragraph with one job per file: resolving what the seed names, projecting one package's position from the two manifests, rendering the plain-Japanese document, and verifying every recorded hash before the first byte is written. Function names are verb phrases — `resolveWorkspaceRoot`, `loadSeedIdentity`, `projectPackagePosition`, `renderExplanation`, `verifyRecordedHashes` — and the noun each returns is what the next one consumes, so the call sequence reads as the processing order.
- Variables name domain concepts rather than shapes: `packageId`, `ownedObjects`, `incomingBoundaries`, `grillQuestions`, `specificationQuotation`. No `data`, no `info`, no `tmp`. The document's section titles are named constants, and the document name `EXPLAIN-RFC-SEED.md` is one constant used by both sinks, so the file and the channel cannot drift apart.
- Hardcoded values become named constants: the document name, the document's section order, the maximum number of quotations printed per section, and the report's cap notation, which prints `…and N more` rather than slicing silently.
- No error is swallowed. A missing manifest, an unparseable seed, an unresolvable reference and a hash mismatch each fail loudly with the artefact and the field named; the command reuses the toolchain's existing `WorkSpacifyTreeError` with its `gateId` rather than inventing a second vocabulary for the same failure.
- Existing code touched is left clearer: the doc comment on `lineStartOffsets` already explains why the offsets are string offsets, and the sibling that hashed a byte window with them stops contradicting it rather than gaining a paragraph that apologises for the contradiction.

### Exceptions

- The plain-Japanese prose of the document is not testable as a whole: the wording is free text, and a predicate over it would freeze one phrasing rather than one property. The non-determinism is in the expression and not in the behaviour, and every fact the prose states is deterministic and machine-checkable, so the item is untestable for a non-defect reason and this is not a design defect and not an architectural defect. Alternative verification: the tests assert what makes the prose an explanation — every cited id resolves against a manifest, every stated count equals the count the manifests hold, every specification quotation equals the character slice at its recorded range, and an absent residual set is stated as absent — and the remainder is a manual reading of one finished document per package kind, recorded in the review.
- The real workspace `~/shyme/gaia` is not testable as a test input, because it is an external artefact outside this repository that the tests are forbidden to depend on, so a test reading it would be non-deterministic across machines and would fail wherever that directory does not exist. This is not a design defect and not an architectural defect: the command's own inputs are ordinary files and it is fully testable without the real workspace. Alternative verification: the acceptance test assembles an equivalent workspace from fixtures in a scratch directory and asserts the document, the stdout equality and the exit code; the real-data confirmation is a manual end-to-end run recorded in `investigation` against a mirrored copy in a temporary directory, which is required in any case because the command writes beside its input.
- Whether the document is genuinely useful to a human deciding what to grill is not testable by a predicate, because it is a judgement rather than a measurement, so it is a manual verification and not an automatable one. This is not a design defect and not an architectural defect, because the underlying facts are all deterministic and machine-checkable and only their helpfulness to a reader is not. Alternative verification: completeness against the manifests, the resolution of every cited id, the cap notation on every trimmed list and honesty about absence are tested automatically; the judgement is then made by reading one document for a package that owns semantics and one for a package whose meaning lives entirely in its boundaries, and recording that reading in the review.

|--------|-------|-------------|
| buildSegment hashed bytes.subarray(byte_start, byte_end), mixing a string offset into a byte buffer | buildSegment hashes sourceText.slice(byte_start, byte_end) through the existing sha256Hex | the recorded segment hash now fingerprints the text its offsets name; measured on the v31 specification before the fix, 31/31 segments hashed a byte window and 0/31 hashed their own text |
| the final segment's byte_end was sourceBytes.length, a byte length among string offsets | it is sourceText.length, the same unit as every other offset | one interval, one unit: partitionStats(segments, sourceText.length) reports a total partition for a non-ASCII document instead of refusing it |
