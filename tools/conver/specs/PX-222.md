# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-222: explain-seed separates the facts from the explanation, pre-decides every engineering question, and leaves the human only the judgments that turn on how the result feels to use

**Ticket Key**: PX-222 · **Phase**: -1

## Background

【Goal】Split one command into the three things it was conflating.

(1) `INFO-RFC-SEED.md` — the deterministic facts. The script writes it and prints the same bytes to stdout, and that is the material an AI works from.
(2) `EXPLAIN-RFC-SEED.md` — the explanation. The script writes a kind, easy-to-read frame carrying `[::MUST-FILL::]` markers; the AI fills them with plain-Japanese prose saying where the seed sits in the whole, what it carries, what has already been decided for the reader, and what the grill must settle.
(3) The human's own judgements, written into `<!-- 判断内容を人間が書き込む -->` placeholders the script places wherever a human decision is needed, and left there for `/grill-me-for-rfc` to read.

【Purpose】PX-221 produced one document in which facts and prose were mixed, and the mixing destroyed the thing the document exists for. A reader could not tell where the record ended and the interpretation began, and the AI had no room to be kind, because the format left it nothing to do but restate facts. Separating the two also makes the explanation bounded in a way the facts cannot be: the facts grow with the package, the explanation does not.

【Motivation】The grill is where a human decides, and that decision surface is far too large today. Measured 2026-09-28 against the real workspace: `gaia-foundation` produces a 135,428-character document of which the contract section alone is 97 percent, and across the packages the manifests record 8 unresolved design questions and 45 risky boundaries. Most of that material is engineering, and an AI must decide engineering correctly rather than hand it over. What must reach the human is only the part where the answer turns on how the result feels to the people who will live with it — and nothing else should.

【Constraints】The work target is `tools/conver` only; `~/shyme/gaia` stays read-only and is used only to confirm behaviour against real data; test code must not depend on gaia. The input surface stays one positional seed path, and exactly two documents are written beside the seed. Engineering judgements belong to the AI and must carry traceable grounds; only experiential judgements may be escalated; nothing the manifests recorded as open may disappear. `/grill-me-for-rfc` is not part of this ticket: the human notes are written into the file and left there for that command to read.

- 【Normal establishment】After one run on a seed path, `INFO-RFC-SEED.md` exists and its bytes equal what stdout carried; `EXPLAIN-RFC-SEED.md` exists with all seven sections present, every explanation point an open `[::MUST-FILL::]`, and one `<!-- 判断内容を人間が書き込む -->` for each human-decision item; and after the markers are filled `run.mjs check` exits 0.

- 【Internal state invariant】The two documents have one owner each: INFO is regenerated every run, EXPLAIN is maintained — created when absent, merged when present — and the merge never verifies less than a fresh run would, so the presence of an earlier document changes what is preserved and never what is checked.

A package that owns no residual question still has the human-decision section, saying in full that nothing needs deciding, so an empty section never reads as an omission. A re-run whose facts are unchanged preserves every filled explanation and every human note; one whose facts moved reopens only the affected sections and keeps the human note with a note saying which fact moved.

## Boy Scout Rule

Translatability plan for the code this ticket touches.

- The split is itself a translatability fix. One file that both states facts and explains them reads as neither, and the reader cannot tell which sentences they may rely on. Two files, each with one owner and one tense — the facts in the present, the explanation addressed to a person — read as what they are.
- Function names stay verb phrases and name the act: `renderInfo`, `renderFrame`, `findOpenMarkers`, `findHumanPlaceholders`, `digestSection`, `mergeExplanation`, `verifyExplanation`. The nouns they return are what the next call consumes, so `run.mjs` reads as its own procedure: resolve, verify, render INFO, merge EXPLAIN, print, and separately check.
- The two new predicates are the only places that know what a marker looks like. One constant holds each literal, and both the counter and the gate call the same predicate, so the count and the verdict cannot drift into disagreeing about the same document.
- Variables name the domain: `factDigest`, `keptSections`, `reopenedSections`, `humanDecisionItems`, `openMarkers`, `preDecidedItems`. No `data`, no `info`, no `tmp`. The seven section titles and the two marker literals are named constants, because they are the document's contract with its reader.
- No error is swallowed. An unreadable existing EXPLAIN, a section whose heading cannot be found, a placeholder that appears twice in one item, and a digest that matches nothing all fail loudly with the section named, rather than being merged over.
- Existing code touched is left clearer: `render.mjs` keeps its nine sections but gains a JSDoc saying it renders the facts document and that explanations belong elsewhere; the constant that names the document becomes explicit about which document it names, since the old name silently meant both.

### Exceptions

- Whether the explanation is genuinely kind is not testable as a predicate: kindness is a judgement about prose, and a test that claimed to measure it would be measuring its author's taste. The non-determinism is in the writing and not in the structure, and every structural property behind the judgement is deterministic, so the item is not testable for a non-defect reason and this is not a design defect and not an architectural defect. Alternative verification: the automated suite checks the structure — markers, placeholders, cited ids, section order, counts, digests and length — and the judgement is made by reading one finished document for a package whose meaning is semantic and one for a package whose meaning lives entirely in its boundaries, recorded in the review.
- Classifying one question as engineering or experiential is not testable as a predicate, because it rests on whether the answer turns on how the result feels to use. The classification is a judgement rather than a measurement, so the item is not testable for a non-defect reason and this is not a design defect and not an architectural defect. Alternative verification: the mechanical half is enforced — every recorded open item must appear somewhere, a pre-decision must carry a traceable ground, a human-decision item must name whose experience changes, and an item the facts alone can close is refused — and the review reads the classification for one package of each kind.
- The real workspace is not testable as a test input, because it is an external artefact outside this repository that the tests are forbidden to depend on, so a test reading it would be non-deterministic across machines and would fail wherever that directory does not exist. This is not a design defect and not an architectural defect: the command's inputs are ordinary files and it is fully testable without the real workspace. Alternative verification: the acceptance tests assemble an equivalent workspace from fixtures in a scratch directory, and the real-data confirmation is a manual end-to-end run recorded in `investigation` against a mirrored copy in a temporary directory, which is required in any case because the command writes beside its input.

## Changes in Prior Implementation Rounds

| Before | After | Description |
|--------|-------|-------------|
| one document mixing the recorded facts with the command's own prose, with stdout identical to it | INFO-RFC-SEED.md is the record and is what stdout carries; EXPLAIN-RFC-SEED.md is the explanation, written by the AI against those facts | Split one document into two with one owner each, which is the whole point of the ticket |
| render.mjs rendered the single document and returned a string | render.mjs renders the facts and returns { text, sections } keyed I1..I9, so a digest can be taken per section | Per-section digests are what let a re-run keep one section and reopen another; a whole-document digest would reopen everything whenever anything moved |
| no marker vocabulary and no gate | lib/markers.mjs (one whole-line predicate per token, used by both the counter and the gate), lib/digest.mjs (the section-to-facts mapping, per-section digests, the digest block, moved-fact naming), lib/frame.mjs (seven sections, instructions, placeholders, pre-decisions, the merge, the gate) | The new modules, each with one responsibility |
| run.mjs took one positional seed path and wrote one document | run.mjs takes an operation (info | check) and one seed path; info writes the facts and prints those bytes with the merge report on stderr, check is the gate | The operation selects what is done, never what is read |
| the seven section titles were written inline in nine calls | INFO_SECTION_TITLES names them once, and the explanation refers to them when it says which fact moved | Two copies of a title are two names for one section the moment either is edited |

Both directions are asserted, and the merge prints its counts so an operator can see which way it went. The second risk is the classification: an AI that is asked to decide engineering may decide it wrongly, which is why every pre-decision carries a ground and an override condition rather than a bare assertion.

- Plan decisions settled during /plan-ticket (2026-09-28), each with the measurement or convention behind it. These bind the implementation; a deviation is a change to the design, not a detail.
  DECISION 1 — operation is a required first positional argument, `info` or `check`. A lone seed path is refused with a message naming both operations and the usage. Backward compatibility is not owed: PX-221's single-operation surface is uncommitted, and its only caller is the command file this ticket rewrites.
  DECISION 2 — `renderInfo` returns `{ text, sections }`, where `sections` is keyed `I1`..`I9` in the order the nine headings already have. Per-section digests need the sections separated, and computing them from one concatenated string would make every section's digest move when any section moved.
  DECISION 3 — the per-section digests live in a trailing HTML comment inside EXPLAIN, `<!-- explain-seed:facts {json} -->`, recording for each EXPLAIN section its own digest and the digest of every INFO section feeding it. It cannot be a third file (C010 writes exactly two documents), and an HTML comment is invisible in the rendered document and cannot be mistaken for a section. Recording the feeding INFO digests separately is what lets the merge name which fact moved.
  DECISION 4 — a marker is resolved by replacing its whole line; the gate is "no marker line remains". The placeholder line is kept and the human writes below it, so the anchor survives a re-run. An operator who deletes the placeholder line loses the anchor, and the merge reports the section as unreadable rather than guessing.
  DECISION 5 — E5 is seeded by the script with one item per recorded open id: the package's `handoff_summary.grill_questions[].residual_id` and the ids of its `handoff_summary.risky_boundaries` that touch it. The AI fills each item or moves it to E6 with a decision. Measured against the real workspace: 8 grill questions across 7 of 28 packages and 45 risky boundaries producing up to 10 touches per package, so E5 is 0 to 11 items and 3 packages correctly get the absence statement.
  DECISION 6 — the declared count is itself a marker. The AI resolves it into `人間が決めること: N 件`, and the gate parses N and requires it to equal the number of E5 items and the number of placeholders. Moving an item to E6 therefore forces the summary to stay honest, which a script-written count could not do.
  DECISION 7 — "the facts alone can close it" is enforced mechanically as: an E5 item must cite at least one id from the package's recorded open set. An item citing nothing recorded is refused as `unrecorded-decision` and must be pre-decided. This is the only decidable reading of the rule: if the manifests do not record the question as open, the facts have settled it, and escalating it is the delegation C005 exists to remove.
  DECISION 8 — `check` requires EXPLAIN and does not require INFO. It recomputes the facts from the manifests and the seed, so INFO's presence is not what makes the explanation verifiable; requiring it would tie the gate to a sibling file's existence and weaken its independence. Defined and tested rather than left implicit.
  DECISION 9 — glossary relevance is line-range overlap between a term's `source_refs` and the ranges the package's owned records' quotations carry, deduplicated by `canonical_name`. Measured on the real manifest: 18 of 28 packages match at least one term, the largest match is 140 of 718, and 10 packages correctly match none. The terms are read from `treeManifest.inventory.terms` in the frame, so `projection.mjs` is not touched.
  DECISION 10 — the merge locates a previous section by its `## ` heading. A heading that appears twice, or a section whose body has lost its placeholder anchor, is a fault naming the section; the merge never picks an occurrence and never guesses. Sections are kept only when their recorded digest equals the digest recomputed this run.
  DECISION 11 — the merge report goes to stderr, because stdout must be exactly INFO's bytes (C001). The report states the kept count, the reopened count, and the names of the reopened sections.
  DECISION 12 — the frame renders a risky boundary by id alone, with no topic. Measured: no `handoff_summary.unresolved` entry in the real manifest carries a `boundary_id`, so the lookup in `projection.mjs` that tries to attach a topic to a risky boundary finds nothing and yields `topic: null`. That null is honest — the manifests record no topic for those ids — and `projection.mjs` is out of scope, so the frame prints the id without a topic rather than inventing one.
  DECISION 13 — every function signature keeps at most five comma-separated items in its whole parameter list, counting the names inside a destructured object. Measured cause: `run-quality-checks.js` `many_params` splits the parameter text on commas, so a destructured options object with six names reports six parameters. `buildFrame({ facts, previous })` and `verifyExplanation({ explainText, facts })` are shaped for this.
