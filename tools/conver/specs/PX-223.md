# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-223: Terminal view of the implementation-order DAG of a workspacify workspace

**Ticket Key**: PX-223 · **Phase**: -1

---

## Background

### Goal
Print the implementation order of a workspacify workspace to the terminal from one plain script invocation.

### Purpose
Make the serial spine and the parallel groups readable at a glance, so a person can answer which directory to start with and which directories may proceed together at each stage, without opening a manifest.

### Motivation
The ordering proof already exists in the two manifests and is already verified by the pipeline, so the remaining work is presentation rather than derivation. A browser-rendered view was built first and rejected: the work happens in the terminal, and a page cannot be read where the directories are being implemented.

### Constraints
No browser and no rendered image. No external dependency. No mode or option flags: zero arguments or one seed path, nothing else. English output. The command must run against any output of /workspacify-tree plus /workspacify-allocate, so no package count, level count, layer name or top-level directory name may be written into the source.

## Scope

## Acceptance Criteria

- Happy path: with no argument from a workspace root holding both manifests, the command prints the level plan, the parallel-width row and the critical-chain row, exits 0, and stdout carries no explanatory legend
- Happy path: given the path to an RFC-SEED.md of that workspace, the same plan is printed with that one row marked and a focused block below it listing providers, same-level peers and consumers, and the exit code is 0
- Error case: from a directory with no tree manifest above it, the command names WORKSPACIFY-TREE-MANIFEST.json on stderr, prints no plan, and exits 1
- Error case: given a path whose basename is not RFC-SEED.md, or one naming a directory that no package owns, the command prints no plan and exits 1
- Edge case: a fixture workspace with a different package count, a different level count and a different longest path renders correctly with no hardcoded count or width
- Edge case: a package with many providers emits one line per provider and the level plan above it is byte-identical to the run without a focus

## Invariants

- [Normal establishment] For any workspace root, the derived levels and serial equal the published implementation_order element for element, so the printed plan is the manifest own order and never a second opinion.
- [Invariant on error] Every failure path aborts before any plan text reaches stdout: a missing manifest, an ambiguous root, an undecidable seed path, and a derived order that disagrees with the published one each exit non-zero with a message naming the artefact or the disagreeing index.
- [Internal invariant] The critical chain is built only from declared canonical_edges, so every consecutive pair in the printed chain exists in the manifest and no step is inferred from level adjacency.
- [Boundary invariant] The renderer holds no workspace-specific constant. The path column width is computed from the workspace being printed, and the level label, the alone and parallel words, and the footer widths are named constants that do not depend on the workspace.

- **Invariant**: Disagreement aborts before any output, so the printed picture can never contradict the manifest it claims to show

### C003 — none, defined from investigation of scripts/workspacify-allocate/lib/implementation-order.mjs

- **Precondition**: One argument whose basename is RFC-SEED.md and whose directory resolves inside the workspace root
- **Postcondition**: Exactly one package is identified, and the focused block lists its providers, its same-level peers and its consumers, each with its level number
- **Invariant**: A path outside the workspace, a path that is not an RFC-SEED.md, and a path naming no package all fail rather than resolving to a nearest match

### C004 — none, defined from the approved display contract

- **Precondition**: Any workspace, including one whose longest package path is longer than the terminal width
- **Postcondition**: Every printed line is one item wide; the package path column is padded to the longest path the workspace holds, and a provider or consumer list emits one entry per line
- **Invariant**: No printed line wraps, so the level blocks and the focused block keep their alignment for any package count and any provider count

## Boy Scout Rule

- Function names are verb phrases: resolveWorkspaceRoot, loadWorkspace, deriveLevels, assertMatchesPublished, findCriticalChain, focusPackage, renderPlan, renderFocus.
- Names are domain concepts: level, provider, consumer, critical chain, path width, ordinal. No single-letter names and no generic names such as data, info or tmp.
- One responsibility per function, so the call sequence in run.mjs reads as the flow: resolve the root, load the manifests, derive the levels, prove them against the published order, build the model, render.
- Hardcoded values become named constants: the two manifest file names, the seed file name, the level label, the alone and parallel words, the footer label widths, and the critical-chain wrap width.
- No swallowed errors: every failure raises WorkspacifyOrderError carrying the artefact or field it concerns, and run.mjs is the only place that catches, so no failure is silent.
- Existing code touched by this ticket: the module-system table in .claude/rules/node.md gains the workspacify-order row, which is the improvement the convention check exists to force.

### Risks
The critical chain must be walked through declared edges only. Walking to any package one level earlier draws a spine the manifests never asserted, and that mistake was made once during the rejected prototype, where the printed chain contained steps that were not edges. Every step must be checked against canonical_edges.

### Caveats
The level grouping is a safe coarse grouping: it is exact when every package takes one round, and conservative when durations differ. The binding constraint of one package is its own provider set, which is what the focused block prints, so the level view must not be read as the only prerequisite relation.
