# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-224: explain-seed: state serial and parallel relations from the published order, not from level adjacency

**Ticket Key**: PX-224 · **Phase**: -1

---

## Background

### Goal
`INFO-RFC-SEED.md` §2 「Where the package sits」 must state, separately and with the ground each rests on: (a) which packages must be finished before this one can start — the declared edges and nothing else; (b) which packages may be implemented beside it — the same level, where the level rule guarantees no declared dependency between them; (c) that a different level is not by itself an ordering. `EXPLAIN-RFC-SEED.md` §E2 must then be answerable from those facts.

### Purpose
The reader of an explanation is about to hold a design conversation about one directory, and 「what has to be done first, what can go in parallel」 is the first question that conversation asks. The command exists to hand the human only what only a human can settle, so the serial and parallel axes must arrive already decided and already grounded.

### Motivation
The seed's injected `implementation_order` block is level adjacency written in the vocabulary of dependency, and `render.mjs:renderPosition` prints it as `implemented before it:` / `implemented after it:` / `may be implemented in parallel:`. Measured across all 28 seeds of the gaia workspace: `before` is exactly the whole previous level, `after` exactly the whole next level, `parallel_with` exactly the same-level peers (28/28 each). 25 of 28 seeds therefore carry at least one false statement — 32 false `before` entries, 32 false `after` entries, 55 declared providers not listed, 55 declared consumers not listed. `gaia-core` declares 16 providers and lists 1; `gaia-foundation` has 19 consumers and lists 3; `gaia-easytier-adapter` lists gaia-soul and gaia-invariants as things it waits for (no edge exists to either) and gaia-certificates as following it (nothing consumes it). Meanwhile the two guarantees that ARE provable go unused: of 378 unordered pairs the 40 same-level pairs carry 0 of the 82 edges, so `parallel` follows from the level rule; and 256 of the 338 cross-level pairs carry no edge at all, so reading a level difference as serial would assert 256 false constraints against 82 real ones. E2's `[::MUST-FILL::]` currently instructs the AI to explain 「何の前に来る必要があり、何がこの後に来るのか」, so the AI can only turn level coincidence into dependency.

### Constraints
The command keeps one seed path and the two operations `info` / `check`: no second argument, no flag, no environment variable, no dialogue. The ordering authority stays `workspacify-order` — the longest-path rule and the critical-chain walk must not be re-implemented here. stdout stays the facts document and nothing else. Nothing is written until every recorded hash has been recomputed and agreed, so the order call sits on the read-only path and `check` recomputes it. The gate stays structural: it must not begin judging prose.

## Invariants

- 【Normal establishment】INFO 2 lists serial relations as the declared canonical edges only and parallel relations as the same level; each list names the ground it rests on; the level reported equals the index of the published implementation_order.levels entry holding this package.
- 【Invariant on error】A workspace whose order cannot be read, or whose re-derivation disagrees with the published order, fails with one line naming the artefact before either document is written; no partial order block reaches stdout, and neither document exists afterwards.
- 【Internal state invariant】The order facts are immutable values indexed by package id; no module mutates the parsed manifests, and the renderer derives nothing it was not handed.
- 【Boundary invariant】The workspace root resolved from the seed equals the root workspacify-order resolved; an empty serial set and an empty parallel set are each stated as empty rather than omitted; a difference in level alone never produces a serial claim.

## Boy Scout Rule

- `projection.mjs:175 collectPosition` currently mixes three sources — the seed's injected block, the allocate manifest's levels, and whatever the renderer happens to want — into one function. Split it into reading the published order and reading this package's edges, so neither responsibility hides in the other.
- Rename the misleading vocabulary: `before` / `after` become `waitsFor` / `usedBy` in the projection. A name that says dependency while holding level adjacency is what produced this defect.
- `render.mjs:133 renderPosition` emits a placement line and three lists in one function. Extract the serial block, the parallel block, the plan shape and the denial sentence into named renderers, so the file reads as the statements it makes.
- Replace the inline `' / '`-joined placement string with a named formatter, and settle the ordinal in one place (`order.mjs`) rather than passing a raw serial index into prose.
- No swallowed errors: a non-zero child status, empty stdout, and an unparsable focus block each raise a distinct `ExplainSeedError` with `field` set; none of them falls back to a default.
