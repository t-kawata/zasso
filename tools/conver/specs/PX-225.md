# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-225: explain-seed: record a shared question a neighbour has already settled instead of asking it twice

**Ticket Key**: PX-225 · **Phase**: -1

---

## Background

### Goal
`/explain-seed` must stop asking a human a question a neighbour has already answered. Where a boundary has this package at one end and the package at the other end has recorded a decision for that boundary under its `<!-- 人間の判断 -->` placeholder, `run.mjs info` must read that decision, must not place the boundary in the human's section, and must record it in 「先に決めておいたこと」 with the neighbour's document as the ground it rests on. `.claude/commands/explain-seed.md` must state this rule explicitly, because the command file is where the AI meets it.

### Purpose
An explanation exists to hand a human only what only a human can settle. A boundary is shared: the same `contract-boundary-NNN` is a party-record of exactly two packages, so a question asked at one end is the same question at the other. Measured on the gaia workspace: 45 risky boundaries, 90 question instances spread over 25 of 28 packages. Asking twice costs the human an answer they have already given, and lets the two answers drift apart with nothing in the toolchain to notice.

### Motivation
Today `frame.mjs:266 collectOpenItems` turns every risky boundary touching this package into a human item, and nothing anywhere reads a neighbour's document. `boundary-001` — the shape of a rejected signature verification — is H1 of `crates/foundation/gaia-foundation`'s explanation and will be an H item of `crates/protocol/gaia-soul`'s: the provider is `pkg-0001`, the consumer `pkg-0002`, and `handoff_summary.risky_boundaries` lists the boundary as risky, so both ends ask. The gate cannot repair this on its own: `frame.mjs:736 faultsOfPreDecisions` reports `open-item-as-ground` when a pre-decided item's 根拠 names an id that is an open item in the same document, so an AI writing 「already settled by the neighbour」 while the boundary is still open would be refused. The boundary must therefore leave the open-item list, which means the frame builder must know about the neighbour before it builds the frame — projection, renderer and digest all have to carry it.

### Constraints
One seed path and the two operations `info` / `check` stay: no second argument, no flag, no environment variable, no dialogue. stdout stays the facts document and nothing else. The run stays read-only toward the workspace: the neighbour document is read, never written, and no manifest or seed changes. Only a clearly decided question may be treated as settled; a document that is absent, truncated or unreadable must re-ask rather than settle, matching `digest.mjs`'s own rule for its block — "a block that is absent, truncated or unreadable records nothing rather than a guess". No error is swallowed: an unreadable neighbour document is named on stderr. The gate stays structural: it must not begin judging the prose of a neighbour's answer.

## Investigation

- `frame.mjs:266 collectOpenItems(projection)` builds the human items from `projection.grill.questions` (residuals whose `package_id` is this package) and `projection.grill.risky_boundaries` (boundaries listed in `handoff_summary.risky_boundaries` touching this package). Measured on the gaia manifests: 8 residuals in total, none owned by `pkg-0001` or `pkg-0002`, and 45 risky boundaries; counting both ends of each gives 90 question instances over 25 of 28 packages. `boundary-001` (provider `pkg-0001`, consumer `pkg-0002`) is risky at both ends; `pkg-0001`'s risky set is boundary-001/007/010/013/036/041/042 — 7 items, matching the 7 human items in the explanation already written on disk — and `pkg-0002`'s is boundary-001/003/005/022/026/031/035/037/047, 9 items.
- Ordering makes the lookup sound: for all 45 risky boundaries the provider is a declared predecessor of the consumer, in `dependencies.normal_edges` and in the transitive reduction `dependencies.dag.canonical_edges` (0 missing of 45, measured with the edges read in the direction the manifest writes them, consumer → provider). The provider's document therefore always exists before the consumer's run. Whether the human has written in it is a separate matter, which is why "clearly decided" must be tested rather than assumed.
- Three parties on one boundary is impossible by construction: every record of `dependencies.boundaries` names exactly one `provider_package` and one `consumer_package`. Reading only the neighbour's human section is therefore sufficient and no transitive walk through other packages' pre-decided sections is needed.
- `frame.mjs:736 faultsOfPreDecisions` reports `open-item-as-ground` when a 根拠 names an id that is an open item in the same document, and `frame.mjs:123 GROUND_SOURCE` requires a 根拠 to name a manifest token, of which `boundary-` is one. A settled boundary therefore has to leave `collectOpenItems` rather than merely be moved: while it is open, any ground naming it is refused, and `faultsOfCoverage` (`frame.mjs:748`) also refuses an item that is both asked and decided.
- `frame.mjs:705 faultsOfDecisions` fixes the shape of the neighbour's answer: each `### 判断` item must hold exactly one placeholder (`missing-placeholder` / `duplicate-placeholder`) and its id must be in the open-item set (`unrecorded-decision`). A neighbour document the gate accepts therefore carries exactly one placeholder per item, and the reader may rely on that — while still having to cope with a document the gate never saw.
- `markers.mjs:73 isPlaceholderLine` is a whole-line exact match against `HUMAN_PLACEHOLDER`, so a decision written under the placeholder leaves the placeholder intact and locatable, whereas one written on the same line destroys it and is refused by the gate. `splitItems` (`frame.mjs:158`) and `referenceOf` (`frame.mjs:151`) are module-private and are the only definition of what an item is; the reader must not grow a second one.
- `render.mjs:371 renderInfo` assembles nine numbered parts from `parts` and returns `sections` keyed by id; `digest.mjs:19 INFO_SECTION_IDS` is a frozen list of those nine, and `EXPLAIN_SECTION_FACTS` (`digest.mjs:27`) declares E1←{I2,I3}, E5←{I9}, E6←{I5,I7,I8}. A section digest is `digestText(restsOn.map(id => sections[id] ?? '').join('\n'))` (`digest.mjs:73`), so a tenth section enters the digest of exactly the sections that name it, and `isDigestRecord` (`digest.mjs:80`) refuses a recorded block whose facts no longer name every id in `restsOn` — so adding `I10` to a section's `restsOn` reopens that section once on the first run after the change.
- That reopening is required, not optional. E1 declares 「人間が決めること: N 件」 and `verifyExplanation` (`frame.mjs:807`) reports `count-mismatch` when that number is not the number of human items; E5 would otherwise keep an item whose id is no longer open, which `faultsOfDecisions` refuses as `unrecorded-decision`; and E6 must reopen because the settled items are rendered there. Hence E1, E5 and E6 all rest on the new section.
- `tests/explain-seed/unit/language.test.mjs:43` asserts that facts whose every value is ASCII produce a facts document with no Japanese line, and its header states the reason: Japanese in the facts document is by construction Japanese the tool wrote itself, the specification's own quotations excepted. ## Boy Scout Rule

- `frame.mjs:151 referenceOf` and `frame.mjs:158 splitItems` are the only definition of what an item is, and the new reader needs the same definition. Extract both, with `HUMAN_ITEM_HEADING` and `PREDECIDED_ITEM_HEADING`, into `lib/items.mjs` so the gate and the reader cannot drift — the reason `markers.mjs` already gives for keeping one predicate per token.
- `frame.mjs:266 collectOpenItems` builds the human items and, after this change, also filters them. Split the exclusion into `settledBoundaryIds(projection)`, so the function that decides what the human is asked does not also own the reason an item left the list.
- `render.mjs:340 renderGrillPoints` returns early on an empty list and otherwise builds its boundary list inline. Extract the residual block and the boundary block into named renderers, and give the new section the same shape, so the empty case is stated in one place rather than two.
- `digest.mjs:19 INFO_SECTION_IDS` restates the section ids that `render.mjs` already owns as `INFO_SECTION_TITLES`. Derive the ids from one source, so a tenth section cannot be added in one place and forgotten in the other.
- `projection.mjs` documents itself as reading the two manifests and the seed. Its doc comment gains the third source and the reason, rather than leaving a reader to discover it from an import.
- `frame.mjs:296 collectPreDecidedItems` concatenates four sources into one list. Give the settled items their own named builder and place them first, so a capped list can never drop a decision the human has already made in favour of a clause the facts document already carries.
