# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-228: workspacify-order: mark each directory that already carries an explanation

**Ticket Key**: PX-228 · **Phase**: -1

---

## Background

### Goal
`workspacify-order` prints, for each level of a workspacify workspace, the directories that build at that level, and marks the ones on the critical chain. This ticket adds one mark to that listing: a directory whose package directory holds `EXPLAIN-RFC-SEED.md` prints ` ✅ EXPLAINED` immediately after its path, so a reader sees at a glance which packages are already explained and which are not.

### Purpose
`explain-seed` writes `EXPLAIN-RFC-SEED.md` beside the `RFC-SEED.md` of a package, so the workspace already holds, per directory, the evidence of whether an explanation exists. The implementation order is already the surface a person reads when deciding what to build next, and it currently answers only when to build. Putting the explained state on that same surface removes a manual walk of the tree and keeps the two facts a planner needs — order and readiness — in one picture.

### Motivation
A workspacify workspace can hold dozens of directories across many levels. Reading the plan today says what to do first but not how much of it is already framed for a person. That information exists on disk and appears nowhere in the plan, so the picture is incomplete for the decision it is used for. The cost lands on every planning session, and the fix is one probe.

### Constraints
- The mark is decided by the existence of one directory entry and by nothing else. The document is never opened, parsed or validated, so a zero-byte or half-written explanation counts as present. This keeps the command read-only and free of any dependency on the explanation format.
- A workspace in which no package directory holds the document must render byte for byte as it renders today, so the change is additive for every existing workspace.
- The label is appended and never padded: a package that is not explained prints nothing after its path, no line gains trailing whitespace, and the path column keeps the width it has today.
- No new argument, flag or exit code. The command keeps its single optional seed-path argument and its two exit codes.
- The check costs one `existsSync` per package and no read of any kind, so a workspace of any size stays as fast as it is today.
- The three cases this ticket repairs are red before it starts. Their repair is part of this ticket because both files are already in its change set, and because a Red phase written on top of an unrelated red cannot tell its own failure from the one that was already there.

- `.claude/scripts/workspacify-order/lib/render.mjs` — `renderPackageLine(model, id)` is the only function that prints a package path inside a level. The exported string constants sit together at the top of the module (`FOCUS_MARKER`, `CRITICAL_MARKER`, `CHAIN_ARROW_GLYPH`), which is where a new label constant belongs.

- `.claude/scripts/workspacify-order/lib/levels.mjs` — `buildModel({ root, treeManifest, allocateManifest })` already receives `root` and uses it exactly once, for `workspaceName: basename(resolve(root))`. ## Invariants

- 【Normal establishment】For every package id in the stage-one manifest, the rendered line carries the label if and only if the directory entry `EXPLAIN-RFC-SEED.md` exists under that package path at the moment of the run.
- 【Invariant on error】A missing, unreadable or non-directory package path never throws and never yields a label: the answer degrades to unexplained, which is the state the picture already had, so a probe that cannot look somewhere never invents a fact about it.
- 【Internal state invariant】`model.explainedIds` is a subset of the ids in `model.packages`, and `renderPackageLine` reads only `model.explainedIds`: the renderer stays a pure function of the model and touches no filesystem.
- 【Boundary invariant】The label is appended and never padded, so a line whose package is unexplained ends at its path: no line carries trailing whitespace, and the path column is exactly as wide as it was before this change.

## Boy Scout Rule

- `lib/render.mjs`: the comment above `renderPackageLine` says nothing follows the path on this line, and that sentence becomes false the moment a label can follow it. It is rewritten to state the rule that holds afterwards — the path is never padded, because an unexplained line ends there. A comment that contradicts its code is a bug by this project's own criteria, and leaving it would cost the next reader the same deduction this ticket had to make.
- `lib/render.mjs`: the label literal and its separating space become the named constant `EXPLAINED_LABEL`, placed with `FOCUS_MARKER` and `CRITICAL_MARKER` where the other glyphs are declared, so the glyph appears once in the module instead of once in the code and once in every test that spells it.
- `lib/workspace.mjs`: the probe becomes a named `holdsExplanation({ root, packagePath })` that reuses the module-private `holds`, rather than a second inline `existsSync(join(...))`. The directory-plus-file-name shape is then written once, and the call site in `buildModel` reads as the question it asks rather than as a path expression.
- Names: `holdsExplanation` is a verb phrase and answers a yes-or-no question; `explainedIds` names the domain fact rather than the container, matching `pathOf` and `consumersOf` beside it; `EXPLAIN_FILE_NAME` and `EXPLAINED_LABEL` name the two literals that would otherwise be scattered. No generic name (`data`, `info`, `tmp`) is introduced, and no single-letter variable appears.
- One responsibility per function: `holdsExplanation` answers one yes-or-no question and does not format anything; `buildModel` keeps building the model and delegates the probe; `renderPackageLine` keeps drawing one line and delegates the decision to the model it is handed. Nothing is merged into a function that already had a job.
- No error is swallowed and none is invented: `existsSync` answers false for every reason it cannot read an entry, and false is the truthful answer to the question the picture asks. No `try`/`catch` is added around it, and no `unwrap` equivalent is introduced.
- Existing non-compliance inside the touched region: `renderPackageLine` and `renderWidthRow` carry `[::TICKET::] PX-223` provenance comments from the ticket that wrote them; those are left intact and this ticket's own provenance is added afterwards by `.claude/scripts/tickets/annotate-ticket-context-by-git-diff.js`, so the traceability chain stays machine-written rather than hand-copied.

```js
// A test-local helper, added beside runOrder: the tree digest that makes read-only provable.
function digestTree(root) {
  const entries = [];
  (function walk(directory) {
    const children = readdirSync(directory, { withFileTypes: true })
      .sort((left, right) => left.name.localeCompare(right.name));
    for (const child of children) {
      const absolute = join(directory, child.name);
      entries.push(`${relative(root, absolute)}:${child.isDirectory() ? 'dir' : readFileSync(absolute, 'utf8').length}`);
      if (child.isDirectory()) walk(absolute);
    }
  })(root);
  return entries.join('\n');
}
```
