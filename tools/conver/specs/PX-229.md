# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
The scripts under `.claude/scripts/explain-seed/` must satisfy every contract the command document `.claude/commands/explain-seed.md` states, and the document is authoritative: it is not edited by this ticket, and no script may contradict it. Specifically the scripts must gain a derived three-state ledger over the recorded points (`open | bound(Qn) | settled(ground)`), a new `run.mjs next <path> <n>` operation that appends numbered question blocks across rounds, a `check` that refuses a question binding fewer than two points, an `answers` that exits 0 only when every question carries an answer and no recorded point is unsettled, and a pre-decided ground grammar that accepts a question reference.

### Purpose
The command document is the specification; the scripts are its instrument. The document specifies a loop whose unit of asking is a direction question that settles many points at once: the AI settles every point it can ground, bundles only the ungroundable weighty remainder into at most three axes per round over at most five rounds, and ends only when no point is open. The instrument today answers a different question. `buildFrame` generates one human item per recorded open point at frame time (`frame.mjs:858-861`), `run.mjs` knows only `info | check | answers` (`run.mjs:63`), and `answers` accepts a document as soon as every placeholder carries prose (`run.mjs:291-295`). Every rule the document states about bundling, round caps, continuing numbers and the end condition therefore has nothing enforcing it.

### Motivation
Without these scripts the document's own judge lines cannot be honoured: it calls the two-point minimum a gate rule, the round caps a refusal condition of `next`, and `ledger open = 0` the completion verdict. A rule that no instrument can refuse is a rule the AI asserts about itself, which is exactly the disguised green this project prohibits. The mismatch was found while reading the document against the scripts; the script side is what is missing, so the repair is on the script side.

### Constraints
- The command document is authoritative and is not edited. Its judgement tables (W1-W12, K1-K12, U1-U15) are deliberately not mechanised, and the document says so in its own words: `Prose quality = judgement, not script` and `Gate catches none of the tables`. ## Acceptance Criteria

- **[Happy path]** `node .claude/scripts/explain-seed/run.mjs next <seed> 2` over a seed whose explanation holds two question blocks exits 0, appends two blocks numbered 3 and 4, opens a round separator, and leaves every byte that existed before the call present and in the same order. `check` accepts the authored document, and `answers` exits 0 once every question is answered and the ledger reports nothing unsettled.
- **[Error case]** Each refusal is non-zero with one English line on stderr naming the reason and the observed value, and leaves the explanation byte-identical: a size of 4 or of 0 or of `two`, a sixth round, and a seed whose recorded points are all settled or all bound. A question binding one point while two points are open is refused by `check` with a fault naming the section and the question.
- **[Edge case]** `answers` exits non-zero while any recorded point is bound to an unanswered question or left unattached, even when every placeholder carries prose; it exits 0 only when every point is settled with a ground. A question binding one point is accepted when exactly one point is open. A pre-decision grounded on `Q2 A` is accepted when Q2 exists and carries an answer, and refused when Q2 does not exist or carries none.

## Invariants

- [Normal condition] The ledger's three sets are pairwise disjoint and their union is exactly the recorded open set derived from the projection, for every document and every projection. `unsettled` is `open` union `bound`.
- [Error invariant] A refused `next` writes nothing: the explanation document is byte-identical after the refusal, so a refusal can never leave a half-appended document. A `next` that fails partway writes nothing either.
- [Internal state invariant] Question numbers are written once and never change: `next` numbers new blocks from the highest number already in the document plus one, and no `info` run renumbers, reorders or deletes a question block, a round separator or an answer.
- [Boundary invariant] The two-point minimum is exempt only when fewer than two points are open, and the exemption is decided by the count of open points alone. The round cap refuses at the fifth round regardless of how many points remain open. A question reference is a ground only when the question exists in this document and carries an answer.
