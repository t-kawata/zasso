# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-230: refine what the human brings into a point, and ask it only where the judgement is truly the human's

**Ticket Key**: PX-230 · **Phase**: -1

---

## Background

### Goal
A viewpoint the human raises while answering must stop falling out of the loop. The human's observation is refined by the AI into an orderly, logical point and recorded in the explanation; from that moment it is a point like any other, and it goes through the settle-and-bundle filter every recorded point already goes through. The AI settles it wherever the AI can ground it or the result is light and reversible. Only the weighty, hard-to-reverse, ungrounded remainder is bundled into a direction question and asked as usual — the same two-or-more-points bundle, the same round rules, nothing looser.

### Purpose
The command exists to remove work from the human. A loop that ignores what the human actually said fails at the one moment the human was paying attention, and hands the observation to a later session that has none of the context in which it was raised. Making the human's observation a point keeps the decision where the context is, and keeps the human's burden bounded by the same filter that bounds it everywhere else.

### Motivation
The boundary was found by asking what happens when a free answer raises something no recorded point covers. Nothing happens: the ledger's universe is the set the manifests recorded (`deriveLedger` reads `collectOpenItems(projection)` at ledger.mjs:105), so an observation outside that set is recorded under the placeholder and read by the downstream interview, and no round turns on it. The gate would refuse it as a point even if the AI tried: `faultsOfDecisions` reports `unrecorded-decision` for any bound id the manifests never recorded (frame.mjs:1106-1109).

### Constraints
- The manifests are read-only. `verify-before-write` recomputes every recorded hash before the first byte is written, and the Invariant limits the files this command creates to the two documents, so an added point can live only in `EXPLAIN-RFC-SEED.md`.
- The AI-first rule is unchanged: an added point whose result is light and reversible is settled by the AI, never turned into a question. The point of this ticket is not to ask the human more, it is to stop dropping what the human said.
- The question rules are unchanged: at least two points per question, at most three questions per round, at most five rounds, one recommendation with a reason and an overturning fact, a scope line, and no letter requirement on the answer.
- `MAX_ROUNDS` stays at five. An added point that becomes a question is still a question put to the human, so it counts against the same bound; if the bound is reached with added points unsettled, the documented stop-and-report-residuals path runs and the report names them, which is honest rather than silent.
- The command document is authoritative and is edited by this ticket, because this ticket changes the policy it states. The two other installed copies of the document and of the script tree are resynced, as PX-228 and PX-229 did.

## Investigation

Direct source investigation, because `pipelineAvailable` is false for this ticket (no RFC graph nodes are referenced). Every claim below was read from the source at the commit that closed PX-229.

**Where the universe is fixed.** `deriveLedger` (`lib/ledger.mjs:104`) opens with `const recordedIds = new Set(collectOpenItems(projection).map((item) => item.id));` and every later step — `readSettledPointIds`, the bound filter, the open remainder — is a partition of that set. `collectOpenItems` (`lib/frame.mjs:362`) builds it from `projection.grill.questions` (residual ids) and `projection.grill.risky_boundaries` minus the boundaries a neighbour already settled. Nothing in the document can add to it.

**Where a document-authored point is refused.** `faultsOfDecisions` (`lib/frame.mjs:1095`) reads `const bound = boundPointIds(item.body);` and pushes `unrecorded-decision` for every id not in `openIds`, which is built from `openItems` — the manifest list. So the gate would refuse a question that binds a point the human raised, even if the AI wrote it down.

**What must not change.** `faultsOfCoverage` (`lib/frame.mjs:1192`) filters `openItems` — the recorded list — against the ledger's open set. Because it iterates the recorded list and not the ledger's universe, an added point that is open is invisible to it. That is exactly the behaviour this ticket needs, so the coverage rule is preserved rather than edited: a recorded point carried nowhere is still `missing-open-item`, and an added point recorded but not yet bound is not a fault.

**The maintenance path already carries a block.** The human section is a maintained section since PX-229: `buildFrame` carries a previous body byte for byte when it carries the question shape, and resets it otherwise. An added-point block placed inside that section therefore survives an `info` run for free, and reaches the same shape predicate (`carriesTheShapeThisFrameWrites`, `lib/frame.mjs:822`).

**The reader that must not see a block as content.** `labelledLines` (`lib/frame.mjs:241`) stops collecting at a line beginning `<!--`, and `readHumanNote` (`lib/frame.mjs:323`) stops at the same prefix, so a frame-marked block written as an HTML comment is invisible to the label reader and to the note reader. `splitItems` splits on the question heading, so the block must not begin with `### 判断`.

**What the round step already offers.** `appendQuestionRound` numbers from the highest question number already present and rewrites nothing; `readRoundNumbers` reads the separators; `runNext` refuses only when the round count has reached `MAX_ROUNDS` or when `ledger.open.size === 0` (`run.mjs:290-302`). Widening the universe therefore makes `next` willing to open a round for an added point with no change to `next` itself.

**What `answers` already offers.** `runAnswers` (`run.mjs:382`) exits 0 only when `reading.unanswered.length === 0 && unsettled.length === 0`, and `unsettled` is read from the ledger. Widening the universe is therefore the whole of the loop extension: no new operation, no new round machinery, no change to the verdict's shape.

**Fixture.** `tests/explain-seed/helpers/synthetic-facts.mjs` builds a projection whose recorded open set is exactly `residual-000001` and `boundary-001`, and `syntheticOpenIds` derives it for assertions. `tests/explain-seed/helpers/fill-frame.mjs` authors a document through `appendQuestionRound` and `fillEveryMarker`, so a case can produce an accepted document and then add a block to it.

**Verification command.** `node --test tests/explain-seed/unit/*.test.mjs tests/explain-seed/acceptance/*.test.mjs`, which reports 234 pass and 0 fail at the commit this ticket starts from.

## Acceptance Criteria

- **[Happy path]** A human answer raising something no recorded point covers is refined into an added-point block with a reserved id, an origin quoting the answer and a one-line statement; the AI settles it in the pre-decided section with a decision, a ground and an override condition; `check` accepts and `answers` exits 0 with nothing unsettled, without any question being asked about it.
- **[Error case]** The gate refuses, naming the block, an added-point id without the reserved prefix, an id a recorded point or another block already uses, a block carrying no origin, and a block carrying no statement. Each refusal leaves the document unmodified and exits non-zero.
- **[Edge case]** An added point that is weighty, hard to reverse and ungrounded is bound into one direction question together with at least one other point of the extended universe, and asked as usual with directions, one recommendation, a reason, an overturning fact and a scope line. Binding it alone while two points are open is refused as too-few-bound-points, and `answers` stays non-zero until the point is settled.

## Invariants

- [Normal condition] The ledger's universe is the recorded open set together with the points the document adds, and the three sets are pairwise disjoint with that union as their exact sum. A reserved added id can never equal a recorded id, so the two origins can never be confused.
- [Error invariant] A block that fails any of its four rules is refused and the run stops at the gate: an id without the reserved prefix, an id already used, a block with no origin, a block with no statement. A malformed block never enters the universe, because a point admitted without an origin is a point the AI invented.
- [Internal state invariant] Coverage is read over the recorded points only. An added point that is recorded but not yet bound is carried by its own block, while a recorded point the document carries nowhere is still a fault — so widening the universe can never hide a point the document dropped.
- [Boundary invariant] The two-or-more-points rule and its exemption both count the extended universe: an added point may be bound together with a recorded point or another added point, and may be bound alone only when fewer than two points of the extended universe are open.

### Exceptions

- Item: the refinement itself — whether the AI has turned the human's observation into an orderly, logical point. It is not testable because the property is prose quality over an unbounded input, which is not a deterministic predicate over the document: two readers can disagree about whether a sentence is a point or a remark, and a checker would measure the taste of whoever wrote it. This is not a design defect, because the instrument is deliberately split into a structural gate and a judged layer and the command document assigns this to the judged layer. Alternative verification: the gate refuses a block with no origin, so an unrefined observation cannot enter the universe silently, and the document's judgement tables govern the quality at review time.
- Item: whether the origin quoted in an added-point block is a faithful quotation of the human's answer. It is impossible to test because a quotation can be altered while remaining a syntactically valid quotation, so no reading of the two documents decides it. This is not a design defect: the quote is evidence for a human reader, and the mechanical share of the rule — that an origin line exists and is non-empty — is what a script can hold. Alternative verification: the human's answer stands verbatim under the placeholder, so the origin is compared against it by reading, which the review step does.
- Item: whether the AI chose the correct branch of the settle-and-bundle filter for a given added point. It is not testable because the branch turns on weight and reversibility, which are judgements about consequences rather than predicates over a document. This is not a design defect, because the filter is the one PX-229 built for recorded points and the command document deliberately placed it in the judged layer. Alternative verification: the mechanical share is tested — an added point that does reach the human must be bound with at least two points, so the loosest failure, a bare question, is refused by the gate.

4. Resync the two other script trees and the two other command documents, and prove byte identity with diff -r and diff -q.

### Risks
- A widened universe could hide a recorded point. The coverage rule is therefore deliberately left reading the recorded list, and a unit case pins that a recorded point carried nowhere is still a fault while a recorded-but-unbound added point is not.
- The AI could invent an added point to look responsive. The origin line is required and quotes the human, and the review step's judgement tables cover its fidelity; the mechanical share is that no block enters the universe without one.
- An added point that keeps the loop open past the round bound leaves the run unfinished. The document already defines that path: stop, report the residual points, settle none. The report must name them, and a case pins that the verdict names an unsettled added point.

### Caveats
- The manifests are never written. An added point lives only in the explanation, so the downstream design interview must read the added-point blocks as well as the placeholders; the document states this and the report repeats it.
- The refinement quality and the choice of filter branch stay in the judged layer, as the command document requires; the gate holds only the block's shape.

### Open items
- None. The four decisions the requirement leaves implicit are fixed: the reserved id prefix, the block's home inside the maintained section, the round bound left unchanged, and the origin required.

### Future improvements
- If the round bound later needs to distinguish the AI's axes from the human's agenda, the separator already records the round and can record its origin without moving anything else.
- The added-point blocks would let a later ticket report how much of a finished explanation came from the human rather than from the manifests.
