# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-231: Emit every path that leaves the process home-relative

## Background

Goal. Every absolute path that leaves the process is emitted with this machine's home directory written as a tilde. A path leaves the process when it is written into a document, printed to stdout or stderr, or carried in an error message. There is no exception and no opt-out: the rule is total over emissions.

Purpose. The artefacts this repository commits are meant to be a function of their inputs alone. The two seed documents are written beside the seed and committed, Tickets.json and Status.json are committed, and the specs are re-exports of Tickets.json. A path naming one machine makes the artefact a function of the machine as well, so two people running the same command over the same seed produce different bytes, and the difference is invisible until someone else opens the repository. The conversion removes the machine from the output.

Motivation. A real run over the gaia foundation seed produced EXPLAIN-RFC-SEED.md whose seventh line read 対象の seed: ~/shyme/gaia/crates/foundation/gaia-foundation/RFC-SEED.md. Reading the renderers found a second site the report had not named, INFO-RFC-SEED.md line 12, whose workspace-root line carried the same home directory while the four lines beneath it were already relative to that root. Widening the search beyond this command found the same defect in the committed records: specPath is absolute in 169 of 169 tickets because ensure-ticket.js resolves it, targetStubs file accounts for 345 recorded locations, targetCrimes file for 16, and Status.json carries three more. The repository already solved this problem once, in .claude/scripts/lib/path-utils.js, which implements toHomeRelative and fromHomeRelative and is imported by 16 files; this surface was built without it, and three readers of the stored records do not apply it.

Constraints. The target is ~/shyme/zasso/tools/conver/ only; the two other installed copies of these scripts are out of scope and are resynchronised after this ticket rather than edited within it. A path leaving the process is converted while a path used for filesystem or subprocess work is not, because the filesystem and the operating system do not expand a tilde, so the boundary is the edge of the process rather than the path itself. The authority for the conversion is the existing helper .claude/scripts/lib/path-utils.js, which already handles the boundaries this ticket names, including an empty home directory, an already-tilde path and the home directory itself; no behaviour of that helper changes and no dependency is added. ## Acceptance Criteria

- [Happy path] A run of explain-seed info against a workspace under the home directory produces two documents in which no line contains the home directory, the seed line reads as ~/... and the workspace-root line reads as ~/..., and the command exits 0. A run of the explanation operation produces a header whose seed line reads the same way. Every error message the command can print names its path home-relative.

## Invariants

- [Normal condition] Every path that leaves the process is converted. A path written into a document, printed to stdout or stderr, or carried in an error message passes through toHomeRelative, so the emitted text carries ~/ in place of this machine's home directory.
- [Boundary invariant] The conversion matches at a path-component boundary. A sibling directory whose name merely begins with the home directory, such as ~n beside a home of ~, is returned unchanged, so the character following a produced ~ is always / and no other account can be mistaken for this one.
- [Boundary invariant] A path outside the home directory, a path already written as ~/, and a run in which os.homedir() is empty are all returned unchanged. None of the three raises, because a missing home is not an error the command can act on.
- [Internal invariant] A path used for filesystem or subprocess work stays absolute. readFileSync, statSync, existsSync, mkdirSync and the spawnSync argument list receive the absolute path, because the filesystem and the operating system do not expand a tilde. The rule binds where a path leaves the process, never where it is used inside it.
- [Error invariant] The conversion is total. It never throws, so an error path that reports a path can report it without the reporting itself becoming a new failure mode.
- [Round-trip invariant] A stored path round-trips. fromHomeRelative(toHomeRelative(p)) equals p for any absolute p under the home directory on the machine that performs both, so a record written home-relative resolves correctly on the machine that reads it.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — No RFC graph node exists for this surface, so the edge is internal: the command document explain-seed.md fixes the two documents, and .claude/rules/node.md fixes the module systems they are built in. The rule itself is already implemented by .claude/scripts/lib/path-utils.js, which 16 files import.

- **Precondition**: toHomeRelative receives a string. Five shapes are exercised: (a) an absolute path of which os.homedir() is a prefix followed by a path separator, (b) the home directory itself, (c) an absolute path outside the home directory, such as /tmp/seed/RFC-SEED.md, (d) a path already written as ~/x, and (e) any path at all during a run in which os.homedir() returns an empty string.
- **Postcondition**: (a) returns ~/ followed by the remainder after the home prefix and its separator; (b) returns exactly ~; (c) returns the input unchanged; (d) returns the input unchanged; (e) returns the input unchanged. No shape raises.
- **Invariant**: Whenever the result begins with ~ and is longer than one character, the character that follows is /. A path whose first component merely shares a prefix with the home directory is therefore never converted: with a home of ~, the input ~n/x is returned unchanged, so another account can never be mistaken for this one.

### C002 — Internal edge between the renderers and the command entry point: run.mjs parseArguments produces one absolute seed path and hands it both to the renderers, which print it, and to the readers and the subprocess, which use it.

- **Precondition**: The command holds one absolute seed path produced by resolve(seedArgument), and it must both emit that path and use it. readFileSync and statSync open the seed from it, and spawnSync is given it as the argument to the order view.
- **Postcondition**: The value reaching readFileSync, statSync, existsSync, mkdirSync and the spawnSync argument list is the absolute path, byte-identical to the value produced before this change. The value reaching a document or a message is the converted form.
- **Invariant**: No tilde ever reaches a filesystem call or a subprocess argument, because neither expands one: a tilde handed to readFileSync names a directory called tilde under the working directory rather than the home directory. The command still verifies every recorded hash and produces the same documents as before, apart from the converted lines.

### C003 — Internal edge between a writer and a later reader: ensure-ticket.js and update-ticket.js write Tickets.json, and show-ticket-context.js, resolve-ticket-context.js and sync-ticket-to-spec.js read it.

- **Precondition**: A writer stores a path that lies under the home directory. The stored value is later read on a machine whose home directory differs. The readers currently call path.resolve(ticketsDir, stored), which discards ticketsDir entirely when stored is absolute.
- **Postcondition**: The writer stores the converted form, so the record holds ~/... instead of a path naming one machine. The reader applies fromHomeRelative before path.resolve, so the record resolves beneath the home of the machine doing the reading.
- **Invariant**: fromHomeRelative(toHomeRelative(p)) equals p for any absolute p beneath the home directory on the machine that performs both conversions, so a record written and read on one machine resolves exactly as it did before this change, and a record written on one machine resolves on another instead of silently pointing at a directory that does not exist there.

## Boy Scout Rule

The conversion is the Boy Scout fix this ticket exists to make, and three further translatability repairs are in scope because the ticket touches those exact lines.

1. Name the two roles of a path instead of leaving them implicit. Every site the ticket touches reads better when the value carries the role in its name: the absolute value keeps its present name and the emitted value is bound to a distinct name, so a reader can tell from the call site alone whether a path is about to be used or about to be printed. The helper call is the marker for which one it is.

2. Replace the duplicated rule in show-ticket-context.js. The file carries its own replaceHomeWithTilde beside the imported toHomeRelative, which is two spellings of one rule in one file. The local copy is removed and the imported helper is called, so the file states the rule once.

3. Split the emission out of the two renderers where the interpolation sits in a long line. render.mjs:150 sits in a five-line array literal whose other four members already call relative(), and frame.mjs:1090 sits in a header array. Binding the converted value to a named constant above the literal makes each literal a list of what is printed rather than a list of expressions, which is what makes the block readable top to bottom.

No hardcoded value is introduced: the home directory is read through os.homedir() inside the existing helper, and the tilde is a constant of that helper rather than a literal repeated at 17 call sites.
