# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Invariants

- 【Normal establishment】Every module in .claude/scripts/question-gate/ exports named functions that take plain data and return plain data; no module imports node:fs, so each property is assertable against a fixture rather than against a workspace.
- 【Invariant on error】A refusal is a returned value carrying its own name, never an anonymous throw: each of the four forbidden inferences returns its own kind (flag-is-not-a-ground, foreign-package-doubt, author-only-is-material-not-exemption, weight-alone-does-not-bind) together with the point id it refused.
- 【Internal state invariant】partitionPoints returns three pairwise-disjoint sets whose union is exactly the universe (the points the run records ∪ the points the document adds); unsettled equals open ∪ bound; a point is in exactly one set and is never absent from all three.
- 【Boundary invariant】An axis binds at least two points unless fewer than two are open; at most three axes are opened per round; the overflow stays open — it is neither dropped nor folded into an axis that would then bind a single point.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — The edge between the points a run records and the state each one is in: partitionPoints in .claude/scripts/question-gate/ledger.mjs reads the recorded points, the questions a frame opened and the pre-decided items, and universeOf fixes the set the partition ranges over.

- **Precondition**: partitionPoints({points, questions, preDecided}) is called with points whose ids are strings, questions each carrying a number and a boundIds array, and preDecided each carrying a ground; universeOf({points, addedPoints}) is called with the recorded points and the points the document adds, whose ids are disjoint from the recorded ids by construction.
- **Postcondition**: The return carries open, bound, settled and unsettled as Sets; bound is the set of ids a question's boundIds names and no ground settles; settled is the set of ids a preDecided item carrying a ground names; unsettled equals open ∪ bound; a point named by a question or a preDecided item that is neither recorded nor added is reported as a decision nothing recorded rather than being invented into the universe.
- **Invariant**: The three sets are pairwise disjoint and their union is exactly the universe, so no point can vanish or appear between two readings of the same inputs; unsettled is exactly the set of points no answer has settled yet.

### C002 — The edge between a point about to become a question and the test that decides whether it may: settlePoint in .claude/scripts/question-gate/settle.mjs writes the three lines 決定 / 根拠 / 覆す条件 and refuses a question drafted without them.

- **Precondition**: settlePoint({point, records}) is called for a point whose id is a string and whose records are the grounds this run has already read — manifest ids, neighbour documents, upstream artifacts, or a Qn + letter the human already gave.
- **Postcondition**: The return is either {kind:'settled', decision, ground, override} with ground drawn from the records, or {kind:'question', reason} whose reason is the 決められなかった理由 line naming which records were read and why none was decisive; a question carries no decision and a settlement carries no reason.
- **Invariant**: A point is never returned settled without a ground, and never returned as a question without a reason; the gate's output is the three lines, not a feeling, so a question drafted without them is a defect even if it reads well.

### C003 — The edge between the AI's own judgement that a point belongs to the human and the refusal that checks it: the four refusal kinds exported by settle.mjs are the four inferences /explain-seed records as having each produced a wrong question.

- **Precondition**: A point is offered whose only support is (a) a manifest flag naming it, (b) a doubt filed under another package, (c) a sentence saying only the author can decide, or (d) its own weight.
- **Postcondition**: Each is refused by name — flag-is-not-a-ground, foreign-package-doubt, author-only-is-material-not-exemption, weight-alone-does-not-bind — the refusal carries the point id, and no question is produced for that point in that call.
- **Invariant**: Weight alone never binds a point to a question; the binding condition is weighty AND no ground, and a ground the AI has not looked for is not an absent ground, so the same point offered again with a record that grounds it settles instead of being refused.

### C004 — The edge between the four artifacts a package directory may already hold and the questions a run may still ask: priorDecisions in .claude/scripts/question-gate/prior-decisions.mjs reads RFC-SEED.md, INFO-RFC-SEED.md, EXPLAIN-RFC-SEED.md and RFC-*.md, and the neighbour directories a boundary names, before any question is drafted.

- **Precondition**: priorDecisions({directory, neighbours}) is called on a directory that may hold any subset of the four artifacts and on the neighbour directories the stage-one manifest records for the package ids a boundary names; the reserved id space added-NNN is available for points the document adds.
- **Postcondition**: The return lists, per artifact found, the decisions it carries as {source, decision, ground, artifact}; an artifact whose content decides nothing this run needs contributes no entry; a neighbour document is read and never written.
- **Invariant**: Presence is never a ground — only content is; a decision already grounded by one of the four artifacts is never returned as a question candidate, and an artifact that cannot be read settles nothing rather than being salvaged into a guess.

### C005 — The edge between the numbers a frame assigns and the replies a human writes under them: nextNumbers in .claude/scripts/question-gate/rounds.mjs assigns the numbers, readAnswers in answers.mjs reads the replies, and refineLetterlessAnswer turns a letterless reply into a point.

- **Precondition**: A document carries numbered question items; `next` is asked for n further items while the ledger still holds at least one unsettled point; a reply arrives carrying a letter, or carrying prose and no letter.
- **Postcondition**: Numbers continue from the highest number the document already holds and no existing number is rewritten; a reply carrying a letter is answered; a reply carrying no letter is unanswered and what it raised is recorded as an added point rather than discarded; `next` refuses when no point is open and the refusal names that reason.
- **Invariant**: A number a question was asked under never moves, so a reply always names its question; and a refusal from `next` because nothing is open is a normal end of the loop rather than a failure, which is what makes a run with zero questions a completed run.
