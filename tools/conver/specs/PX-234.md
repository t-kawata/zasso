# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- Happy: with the four prior artifacts present in a fixture package and every node groundable, /grill-me-for-rfc opens zero questions, reaches open-count 0, generates CheckList.md, writes the RFC and its I/O boundary block, and completes — and the same holds for /drill-rfc-down appending to the RFC instead of writing it.

## Invariants

- 【Normal establishment】Both commands derive the same four states from their own existing DesignTree.json — a node is settled when it carries a ground, bound when a question binds it and no ground settles it, open otherwise — and `open-count == 0` remains the completion condition it is today.
- 【Invariant on error】A question that the prior artifacts could have settled is refused by `check`; a run may not bind a node to a question while an artifact in the same directory grounds it, so the count of human questions can only fall for a reason the records support.
- 【Internal state invariant】Every artifact either command generates keeps its name, its shape and its generation condition: grilled $RFC_DIR still receives exactly Status.json, DesignTree.json, CheckList.md and the RFC; drilled $SESSION_DIR still receives exactly its session set; the RFC is still appended and never rewritten; the I/O boundary block is still written into the RFC.
- 【Boundary invariant】A run whose every node is grounded by the prior artifacts opens zero questions and still completes: open-count reaches 0 with no human answer, CheckList is generated, the RFC is written, and no step is skipped because nothing was asked.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — The edge between the prior artifacts a package directory already holds and the questions a run may still ask: priorDecisions reads them, settle-run.js prior records the scan and prints it, and settle-run.js check refuses a question whose block does not account for that scan.

- **Precondition**: A package directory holds any subset of RFC-SEED.md, INFO-RFC-SEED.md, EXPLAIN-RFC-SEED.md and RFC-*.md; a DesignTree.json sits in $RFC_DIR (grill) or $SESSION_DIR (drill) and carries nodes whose ids are the point ids and an additive top-level questions array.
- **Postcondition**: prior reads the directory and its neighbours and writes { scannedAt, directories, artifacts, decisions, grounds } into the tree, printing the decisions in Markdown and writing nothing else. check exits non-zero, naming the node id and the reason, when a question binds a node while the tree records no prior scan (prior-artifacts-not-read), when a block carries no settle trace (missing-settle-trace), or when the scan found artifacts and the block settle trace names none of them (unread-prior-artifact). When every node is grounded, no question is opened and the run continues toward open-count 0. [Refined at plan time: the original postcondition asked the gate to match a design-tree node to an arbitrary document decision, which no predicate can do without a heuristic that would refuse correct runs; the check now reads the record the AI must leave.]
- **Invariant**: Presence is never a ground — only content is; a node already grounded by one of the prior artifacts is never opened as a question, so the number of human questions can only fall for a reason the records support, and a run in which everything is grounded asks nothing.

### C002 — The edge between a design decision the AI can settle and the record of that settlement: update-tree.js settle writes a resolution carrying decision, ground and override, and check demands the ground before the resolution counts as settled.

- **Precondition**: update-tree.js is invoked with `settle <node_id> <json>` where the json carries decision, ground and override, or with `resolve <node_id> <answer_summary>` where the answer is a human reply that entails the decision.
- **Postcondition**: The node questions[] gains an entry carrying resolvedAt and answer together with decision, ground, override and source, where source is "ai" for a settlement and "human" for a resolve; the node status becomes "resolved"; check-all-schema.js validateAll accepts the entry; a settle invocation whose json carries no ground, or carries a ground but no override, is refused and the file is left byte-unchanged.
- **Invariant**: A resolution without a ground is not a settlement — it is refused rather than recorded — so every resolved node in the tree rests on a named record, an upstream document, or the Qn plus the letter the human answered with.

### C003 — The edge between a question block and the nodes it decides: update-tree.js bind records the block, question-gate/ledger.mjs partitions the nodes with it, and check refuses a block that binds fewer than two nodes.

- **Precondition**: A block carries a number, a boundNodeIds array, a scope line and a settle trace; the tree carries the additive top-level questions array that holds the blocks; settle-run.js next opens n empty numbered blocks that the AI later fills with bind.
- **Postcondition**: The block is recorded with its number continuing from the highest the tree already holds and no existing number rewritten; ledger.mjs reports the bound nodes as bound and not settled; check exits non-zero when boundNodeIds holds fewer than two ids, when the block carries no settle trace, when a bound node appears in no block, or when a node appears in none of open, bound and settled.
- **Invariant**: A question binds at least two nodes unless fewer than two are open, and no node vanishes: every node is exactly one of open, bound and settled, so the tree cannot quietly drop a design decision between two runs.

### C004 — The edge between the three command files and the rule they must not diverge on: the delimited block in explain-seed.md, grill-me-for-rfc.md and drill-rfc-down.md is one text in three places, and shared-rule-text.test.mjs compares them byte for byte.

- **Invariant**: The rule text cannot drift: a rule changed in one command file is a red test until it is changed in all three, so the mechanism grill and drill share is one text rather than three texts that agree today.

### Exceptions

- Item: whether a written question is understandable to a person who knows neither the implementation nor the design. Reason: a machine cannot test a human comprehension of a sentence, and the item is not testable for that reason; it is not a design defect, because the mechanical half of the same rule is testable and is tested — the seven lines and their order, define-before-use in readBack, and at least two directions distinguishable by consequence. The item is therefore a judged layer on a tested structure, not an untested behaviour. Alternative verification: shared-rule-text.test.mjs freezes the rule byte for byte across the three command files, and the run report names every item the reading found thin.
- Item: the exact number of questions a real grill session shows on a real project. Reason: a fixture cannot test a count that depends on which records a particular package happens to hold; the cause is the external dependency on the workspace contents, and it is not a design defect, because the relation between the artifacts present and the axes opened is fixed and tested. Alternative verification: ratio.test.mjs fixes that relation (N groundable nodes yield zero axes; two ungroundable points yield exactly one axis binding both; eight yield at most three axes with the overflow left open), zero-question.test.mjs fixes the zero case end to end, and settle-run.js check refuses any question a present artifact grounds, so the count is bounded by the rule rather than by the fixture.
