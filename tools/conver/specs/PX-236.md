# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Invariants

- 【Normal establishment】 Every added point is readable back by readAddedPoints with its id, 出どころ and 論点 unchanged, and its id matches the reserved shape `^added-\d{3}$`.
- 【Invariant on error】 A refused revise leaves both documents byte-identical, and check and answers report the same verdict after the refusal as before it. No partial block is ever written: a block without its closing marker is not a block.
- 【Internal state invariant】 The ledger stays derived, never stored: universe = recorded open set ∪ added points, and open, bound and settled remain pairwise disjoint with the universe as their exact sum. An open point is never the ground of a decision.
- 【Boundary invariant】 The human's section survives an info re-run byte for byte — the person's own words are never destroyed by regeneration — and a question number never moves. Rounds opened before the last cycle marker do not count against the current cycle, and countRounds keeps reporting the lifetime total.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — revise -> EXPLAIN-RFC-SEED.md (added-point block)

- **Precondition**: a resolvable seed path and a payload object {origin: string, statement: string} where origin is the human words verbatim and statement is one line
- **Postcondition**: exactly one added-point block, carrying the next reserved id, the origin verbatim under 出どころ and the statement under 論点, is appended to the end of the human section; every other byte of the document is unchanged
- **Invariant**: readAddedPoints reads the block back with the same id, origin and statement it was written with (round trip)

### C002 — revise -> refusal (no origin, no statement)

- **Precondition**: a payload whose origin is absent, empty or whitespace only, or whose statement is absent, empty or whitespace only
- **Postcondition**: exit non-zero, stderr names the fault kind (uncited-added-point for the origin, unstated-added-point for the statement) and the field, and both documents are byte-identical to their state before the call
- **Invariant**: a refused revise writes nothing: the explanation file hash before and after the call is equal

### C003 — revise -> reserved id allocation

- **Precondition**: a document whose highest existing added id is added-00K, or which holds no added point
- **Postcondition**: the new block carries added-001 when no added point exists and added-0(K+1) otherwise, zero padded to three digits
- **Invariant**: an existing id is never reused, an existing question number never moves, and an answer already written under a placeholder is never rewritten

### C004 — revise -> ledger -> answers and next

- **Precondition**: a revise call that succeeded on a document whose question set is complete
- **Postcondition**: deriveLedger reports the new id in open and in unsettled; answers exits non-zero naming the new id; next accepts because the open set is no longer empty
- **Invariant**: the unsettled set grows by exactly the added ids: no other point changes state

### C005 — revise -> info (frame preservation)

- **Precondition**: a document that carries an added-point block, re-run through info with unchanged facts
- **Postcondition**: buildFrame lists the human section in keptSections, not in reopenedSections, and carries the previous body through unchanged
- **Invariant**: the human own words survive regeneration byte for byte, so a re-entry can never destroy what the person said

### C006 — shared question-gate block -> three command files

- **Precondition**: the three files .claude/commands/explain-seed.md, grill-me-for-rfc.md and drill-rfc-down.md
- **Postcondition**: the text between the begin and end delimiters is byte-identical across the three, and states the re-entry rule
- **Invariant**: each file carries exactly one delimiter pair, and the block names no single command file name

### C007 — revise -> cycle -> round bound

- **Precondition**: a document whose current cycle, opened by the last revise, has already opened MAX_ROUNDS rounds
- **Postcondition**: next exits non-zero naming the cycle bound and writes nothing; revise exits non-zero naming MAX_CYCLES once that many cycles exist
- **Invariant**: rounds opened before the last cycle marker do not count against the current cycle, and countRounds keeps reporting the lifetime total

## Boy Scout Rule

Touched code, and what is improved as it is touched:

- New functions are verb phrases naming their act: `appendAddedPointBlock`, `nextAddedPointId`, `countRoundsInCurrentCycle`, `countCycles`. No `process`, `handle`, `data` or `tmp`.
- New names are domain nouns: added point, reserved id, cycle, current cycle, origin, statement. The document vocabulary already used by the reader (`出どころ`, `論点`, `added-NNN`) is reused rather than paralleled — one name per thing (W19).
- One function, one responsibility: `nextAddedPointId` allocates an id; `appendAddedPointBlock` writes bytes; `countRoundsInCurrentCycle` reads a count. The operation in `run.mjs` validates the payload, then calls them in order, so its body reads as prose: validate, allocate, append, report.
- Hardcoded values become named constants: `MAX_CYCLES` and `CYCLE_MARKER_PREFIX` beside the existing `MAX_ROUNDS`, `MAX_AXES_PER_ROUND` and `MIN_BOUND_POINTS`. No bare `5`, `3` or marker literal inside a function.
- No swallowed errors: every refusal throws `ExplainSeedError` carrying the field, matching the existing contract in `run.mjs`, and a refused call writes nothing.
- Proactive improvement inside scope: `.claude/commands/explain-seed.md:443` (Step 4c) currently instructs a hand-write of a block that has a writer; the instruction is replaced by the call, which removes a duplicated definition of the format — the same reason the writer lives beside the reader (`frame.mjs:423-433`).
