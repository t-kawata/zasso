# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-237: The prior-artifact reader recognises no pre-decided item: the reader tests the heading by equality, the writer always appends a reference

**Ticket Key**: PX-237 · **Phase**: -1

---

## Background

- [Goal] The question gate must read the pre-decided items a package's explanation already carries, so that a run never asks the human something the human has already settled. Today the reader recognises none of them: the predicate it uses is exact equality on a whole heading line, while the writer that produces every such document always appends a reference to that heading. The goal is that the consumer recovers exactly what the producer writes, for input no one has seen yet — not merely that today's documents parse.
- [Purpose] `/grill-me-for-rfc` and `/drill-rfc-down` exist to spend a human's attention only on what is genuinely undecided. Both read the package's prior artifacts before asking anything, and both treat the human's settled items as the strongest available ground. A reader that cannot see those items does not fail loudly; it asks a question the human already answered, which is the precise failure the gate was built to prevent and the one that costs the human's trust in the run.
- [Motivation] The defect is not one file's data. The token `### 先に決めた` is defined twice (`question-gate/prior-decisions.mjs:25`, `explain-seed/lib/items.mjs:18`) and the rule that recognises it is implemented twice with different semantics (`items.mjs:67` prefix, `prior-decisions.mjs:70` equality), with no test on either definition. The overlap between what the writer emits and what the reader accepts is therefore provably empty, and a fix that only makes the current corpus parse recurs at the next change to either spelling. The motivation is to make the class of defect impossible by giving the token and its recognition rule one definition that both sides call.
- [Constraints] The fix must not edit any generated document — 32 `EXPLAIN-RFC-SEED.md` files exist under `~/shyme/gaia` and they are output, not source; editing one fixes one package and hides the defect. It must not hardcode the current corpus (no ordinal list, no reference-name list, no `/^### 先に決めた A\d+ — /`), must not special-case a package or path, and must not loosen `settlePoint`'s rule that a settlement rests on a record the run actually read. Both settle copies must be treated as one behaviour, since leaving `drill-rfc-down/settle-run.js` unchanged would fix half the commands. Tests must hold no dependency on `~/shyme/gaia`; a representative document may be copied into the repository as a fixture, but the suite must pass where that workspace is absent.
- [Observed evidence] On the 32 `EXPLAIN-RFC-SEED.md` files under `~/shyme/gaia`: 480 lines start with the token, 0 lines equal it, and the reader's decision list is empty for every document the project's own writer produces. Two `settle-run.js` copies are byte-identical (402 lines, sha256 `7a59a883da23c6c740174b30775e5a543acfb2fee8affc2736fae1a4fbc8caa0`). The repository holds 16 test files under `tests/question-gate/unit/`, so the report's claim of no tests is inaccurate; the decisive fact is that two of those fixtures write the bare heading the writer never emits, which is why the drift survived.
- [Reported by] `docs/BUG-FIX002.md`, reported 2026-10-06 from `~/shyme/gaia/crates/network/gaia-network` during a `/grill-me-for-rfc` run (pkg-0020). BUG-FIX002's Defect 3 (the `選択肢` label) is investigated here and excluded as a false positive; its acceptance criterion A2 is excluded because this ticket forbids a test dependency on the corpus.

## Invariants

- [Normal condition] The consumer's recognition predicate is the producer's predicate. One definition of each document token exists, and both sides call it, so a change to the spelling cannot reach one side without the other.
- [Error invariant] An artifact that cannot be read settles nothing and is never salvaged into a guess; it is reported as unreadable and stays distinguishable from an artifact that was read and contributed nothing.
- [Internal state invariant] The record of what was read is derived from the reads, not from the entries produced. `priorScan.artifacts` ∩ `priorScan.unreadable` = ∅.
- [Boundary invariant] `settlePoint`'s ground contract is unchanged: a settlement still rests on a record the run actually read, matched by exact membership — never by substring or prefix.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — question-gate/prior-decisions.mjs (consumer) ← explain-seed/lib/items.mjs (producer): the heading token and the rule that recognises it

- **Precondition**: Input is a document text and a heading token. Exactly one definition of the token and of the recognition predicate exists in the tree, and the consumer imports it rather than restating it. The predicate is the producer's rule — `line.startsWith(heading)` — not a pattern fitted to the current corpus.
- **Postcondition**: For every line the producer's own predicate recognises as an item heading, the consumer produces an item. The consumer's item count for a document equals the count of lines that predicate recognises.
- **Invariant**: assert.equal(readLabelledItems(text).filter(isItemHeading).length, splitItems(text, H).length) — the two readers of one document never disagree on what a heading is, and neither uses a narrower rule than the other.

### C002 — grill-me-for-rfc/settle-run.js + drill-rfc-down/settle-run.js ← question-gate/prior-decisions.mjs: `runPrior` records what was read

- **Precondition**: `entriesOfDirectory` is given a directory, a reader and a lister. It already knows the name list and which names were readable; it currently discards that second fact when an artifact yields no entries.

### C003 — question-gate/settle.mjs `settlePoint` — the ground contract (regression guard)

- **Precondition**: A settlement rests on a record the run actually read. `settlePoint` accepts a ground only when `records.includes(ground)`.
- **Postcondition**: `settlePoint` is unchanged by this ticket: a ground absent from the records is still rejected, and the comparison is still exact membership.
- **Invariant**: assert.equal(settlePoint({ ground: 'a ground never read', ... }).ok, false) — the fix must not relax the contract to make settling easier, and must not introduce a substring or prefix match.

## Boy Scout Rule

Touched code is left more translatable than it was found, in the same change that fixes the defect.

- **The doubled constant becomes one definition.** `PREDECIDED_ITEM_HEADING` exists at `prior-decisions.mjs:25` and `items.mjs:18`. The consumer's copy is deleted and the producer's imported, so the name has one meaning and one home. Two constants that agree by coincidence read as two independent facts and are the exact shape that produced this defect.
- **The inlined predicate becomes a named one.** The rule that recognises a heading is currently the body of `splitItems` at `items.mjs:67`, unnamed, so the consumer could not call it and restated it differently. It is extracted to `isItemHeading(line, heading)` — a verb phrase naming what it decides — and called by both sides.
- **`entriesOfDirectory` stops discarding a fact it holds.** It computes readability at line 199 and throws it away in a `continue`; the reader must then re-derive it and gets it wrong. It returns the artifacts read alongside the entries, so the fact is carried rather than recomputed.
- **The false claim in the `settle-run.js` header becomes true.** The header states the two copies cannot drift while nothing enforces it; a byte-identity test turns the claim into a checked fact, or the copies are extracted and the claim becomes structural.
- **The divergent normalisation is named rather than incidental.** `readLabelledItems` trims before testing and `splitItems` does not; whichever normalisation is chosen is expressed once, in the shared predicate, so the difference is a decision instead of an accident.
- **Generalities are named.** The heading token, the separator and the labels are already named constants; the predicate joining them is given the same treatment, so the code reads as "a line opens an item when it starts with the item heading" rather than as a filter whose meaning must be inferred from the comparison operator it uses.
