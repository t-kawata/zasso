# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

【Goal】Implement the /educe-sequences command in this repository, tools/conver. It takes exactly one argument, the path of a specification file, and writes one artifact beside that file: <basename>-sequences.json, where <basename> is the specification file name without its extension. The artifact holds the sequences of the specification, the operations that satisfy them, the steps that carry subject, predicate, object and contract, the adjudications, the section census, and the pins the reading established.
【Purpose】The Gaia programme produced 257 registry rows, 485 manifest entries, 614 decomposed steps, 178 adjudications and 34 check functions, and every one of them was produced by reading. The portable asset is the procedure together with the checks, never the values; the values are what a run establishes about one specification and records in that specification's artifact.
【Motivation】The run cost six rework passes, A to F, because the two measures that actually catch fabrication, the per-step verbatim quote and the attack on the weakest link of the guarantee, were written after the artifact had been declared complete. Measured: the first version of the step file held 1178 steps, every step carried the four required fields, the ordering held and the bijection held; none of it was a reading. A command that standardises the shape without making the shape hard to fake would make the ritual easier and the assurance weaker, so the signature requirement is the centre of the design rather than an addition to it.
【Constraints】Nothing under ~/shyme/gaia is written by this ticket; running the command against that specification is a later decision, and doing so adds one new file to that tree rather than modifying anything in it. No Gaia value lives in the library: no line number, no vocabulary member, no section number, no threshold. Every check must be falsifiable in both directions, red on the defect and green on correct work. The reading phases are protected from automation rather than replaced by it: a machine may falsify and may never discover.
【Decision recorded in this revision】The command takes one argument and no second one. An earlier revision made the pin file a second argument; that is removed, because a pin is a finding and an input that carries a finding keeps the finding outside the artifact where no reader can check it. The consequences this revision adds are four. The pins move inside the artifact. Every pin is then re-derived from the specification text by the checker, because an artifact that supplies its own premises and then checks itself proves nothing. The specification digest and line count are recorded, because a line citation is meaningful only against one revision. And the artifact is designed as a contract surface with stable identifiers and a schema version, so that the implementing packages can check their coverage against it in both directions and the grill can be given it as material.

## Acceptance Criteria

- 【Happy path】The command is invoked with one argument, the fixture specification path; it writes <basename>-sequences.json beside that specification; the engine emits the recorded summary block unchanged and exits 0; every pin is re-derived from the specification before it is consumed; the fixture digests after the run equal the recorded digests; the printed check count and pin count equal the counts the engine declares; and the design document resolves against the repository through the two convention tests.
- 【Error case】An artifact missing pins.predicate.line, a reading missing a required field, a supplied rule whose presupposition is prose, a brief missing the verbatim-quote requirement, a fixture file altered by one byte, and an artifact whose recorded specification digest does not match the specification it is verified against each cause a refusal that names the offending item, with no artifact written and no test weakened; the run exits non-zero and the artifact digest is unchanged.
- 【Edge case】A second run over an unchanged specification writes a byte-identical artifact; a specification changed by one byte makes a verification of the older artifact refuse; a specification file name containing several dots has only its final extension removed; zero arguments, two arguments and a directory argument are each refused with nothing written; every mutation in both corpora reddens the check it names for an attributable reason; every counter-mutation leaves the run green; and the mutation corpus leaves the fixture at its recorded digest.

## Invariants

- 【Normal establishment】The library under .claude/scripts/educe-sequences contains no line number of any specification, no vocabulary member of any specification, and no path belonging to a host project; every specification-specific value is established by a run and recorded in that specification's artifact. A value that appears in the library and in no artifact is a defect of the library.
- 【Artifact identity】The output location is a pure function of the input path: for a specification at <dir>/<basename>.<ext> the artifact is <dir>/<basename>-sequences.json and the rendering is <dir>/<basename>-sequences.md. No flag, environment variable or configuration changes the location, and no second input is required for a run or for a verification.
- 【Pin re-derivation】Every pin in an artifact is re-derivable from the specification text: the predicate line contains its limbs verbatim, each enumeration member occurs inside the range the pin declares, the block partition covers the section list exactly once with no overlap, and a form detector proposes candidates without deciding any of them. An artifact that supplies a wrong pin and then passes its own checks proves nothing, so the pins are checked against the specification rather than trusted.
- 【Invariant on error】rail/integrate.mjs writes nothing when any field of any incoming reading is unproven: it collects every unproven field, names each on stderr with the reading that carried it, exits non-zero, and leaves the artifact byte-identical to its state before the call. A partial write is the failure this module exists to make impossible.
- 【Internal state invariant】A check may propose candidates and may never decide. No check treats a name appearing near a region, a plain span intersection, a coverage relation, or any other structural property as evidence about what a line says; those are the signals that produced the fabrications, and a check built on one inherits their error.
- 【Boundary invariant】The fixture under tests/educe-sequences/fixtures/gaia is byte-frozen: a difference between a fixture file and its SHA-256 in MANIFEST.json fails the run. The run reports drift from the source repository rather than following it, and no fixture file is edited to make a check pass. An artifact whose recorded specification digest does not match the specification it is verified against is refused rather than repaired.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — rail/artifact-schema.json -> rail/engine (a check reads the specification only through pinned values)

- **Precondition**: A specification whose lines are addressable by 1-based index, and an artifact in which pins.predicate.line is an integer, pins.rowSchema.fields is a non-empty array of strings, and every path or range the artifact declares resolves inside the specification. Invalid input: predicate.line absent; rowSchema.fields empty; a block range that runs past the last line; a form entry with no proposing rule.
- **Postcondition**: checkAll(specLines, artifact) returns { verdicts, summary } where verdicts is an array of { check, subject, reason } and summary is the printed block; the block is produced only after every check has run, so a check that throws is reported as a verdict rather than aborting the block.
- **Invariant**: No value read by any check originates in a literal of the library: every line number, vocabulary member, threshold and path is read from the artifact or from the specification text. Asserted by scanning the library sources for 4-to-5 digit numeric literals and for the name of any host project.

### C002 — rail/integrate.mjs -> the artifact on disk (all-or-nothing write)

- **Precondition**: An array of readings in the shape the brief declares, each carrying the fields the artifact requires, and the artifact file as it stands. Invalid input: a reading missing a required field; a reading whose outcome is not one of the declared outcomes; two readings for the same subject.
- **Postcondition**: Either the artifact is written with every incoming field proven, or nothing is written, every unproven field is named on stderr together with the reading that carried it, and the process exits non-zero. The return value is either {written: n} or {refused: [{subject, field, why}]}.
- **Invariant**: When the call refuses, the artifact is byte-identical to its state before the call; asserted by digesting the file before and after every refusal case.

### C003 — rail/integrate.mjs <- the neighbour selection of the engine (the reading must name the neighbour the check selects)

- **Precondition**: A reading whose verdict realizes an entry through a neighbour, and which names that neighbour by id.
- **Postcondition**: The reading is accepted only when the named neighbour is the entry the engine would itself select for that entry; otherwise the reading is refused and the refusal names both the neighbour given and the neighbour the check selects.
- **Invariant**: A worklist whose selection predicate chose a neighbour by coverage rather than by citation can never yield an accepted reading, so the defect that a worklist may carry cannot reach the artifact.

### C004 — rail/integrate.mjs -> rail/engine (a supplied rule and its presupposition line)

- **Precondition**: A supplied-rule reading carrying spec_name, presupposition, grounds, rule, why and override. Invalid input: presupposition given as prose; grounds empty; spec_name absent from every ground.
- **Postcondition**: The rule is written only when presupposition is an integer line and that line contains spec_name literally; otherwise it is refused and both the spec_name and the grounds that were searched are named. The written row carries evidence.grounding.classification equal to designer_supplied and evidence.spec_lines containing the grounds and the presupposition.
- **Invariant**: No rule is stored with a prose presupposition, and no row keeps a defining_section that the rule supersedes, because the check that holds the two records to each other requires the integer and rejects the stale section.

### C005 — rail/falsify.mjs -> rail/engine (a check is trusted only after both directions have been run)

- **Precondition**: A case naming a check, a mutation of the fixture, and the expected verdict; and a counter-case naming an edit that is correct but different. Invalid input: a case whose named check does not exist; a mutation whose expected verdict is not a refusal.
- **Postcondition**: The mutation makes the run red and the reason is attributable to the named check; each counter-case leaves the run green; the restore returns the fixture to its recorded digest. The return value is {red, attributable, counterGreen, restored}.
- **Invariant**: A red whose reason cannot be attributed to the named check is reported as unattributable and the case fails, and a counter-case that reddens is reported as a defect in the check rather than in the fixture.

### C006 — tests/educe-sequences/fixtures/gaia/MANIFEST.json -> the fixture files (the fixture is frozen)

- **Precondition**: A manifest naming every fixture file with its SHA-256 and its byte length, and a fixture root beneath tests/educe-sequences/fixtures.
- **Postcondition**: Every named file exists with the recorded digest and length, and no file exists beneath the fixture root that the manifest does not name.
- **Invariant**: A fixture edited by hand fails the run; drift from the source repository is reported as drift and is never absorbed by editing the fixture.

### C007 — rail/brief.mjs -> briefs/ (a reader is dispatched only with a checked brief)

- **Precondition**: A brief name that exists under briefs/, and a worklist path. Invalid input: an unknown brief name; a worklist path that does not exist.
- **Postcondition**: The rendered text carries exactly one interrogative sentence, the requirement that every step quote its line verbatim, the prohibition on assigning a reader by a line window, and the worklist path.
- **Invariant**: A brief missing any of the four does not render, so no reader is ever dispatched with an unchecked brief, and the four are counted rather than searched for.

### C008 — rail/set.mjs -> the engine output (a set is never derived from a truncated list)

- **Precondition**: A source listing with a declared total and the number of entries actually present. Invalid input: a declared total smaller than the entries present; a listing with no declared total.
- **Postcondition**: Either the complete set is returned, or the call refuses and names the truncation marker it found in the source.
- **Invariant**: When the declared total exceeds the entries present, no set is returned; a partial list is never read as the whole, because a worklist built from what was visible omitted 34 of 74 rows.

### C009 — rail/splice.mjs -> rail/record.mjs (a new check carries its own record)

- **Precondition**: A new check module, the defect that motivated it, its mutation case and its counter-case. Invalid input: a check with no originating defect; a check whose mutation case is absent.
- **Postcondition**: The check is spliced into the engine registry and a rail-exit record is written naming the absence of an analogue in the record, the inputs, the output shape, what reads it, what verifies it and the condition that promotes it.
- **Invariant**: A splice without a record is refused, the record carries no field that is empty, and the count of rail exits is printed on every run so that a growing ad-hoc surface is visible rather than silent.

### C010 — the command frontmatter -> the artifact path (one argument, one derived location)

- **Precondition**: Exactly one positional argument, the path of an existing readable file. Invalid input: no argument; more than one argument; a path that is a directory; a path that does not exist; a path with no extension.
- **Postcondition**: The artifact is written to the directory of the argument as <argument file name without its final extension>-sequences.json, and the exit code is 0 only when the run completed and every check passed. No flag, environment variable or configuration alters the location, and a verification of an existing artifact requires only the specification path.
- **Invariant**: The location is a pure function of the argument: two runs with the same argument write the same path, and no run writes outside the directory of the specification.

### C011 — a second run over an unchanged specification -> the same artifact bytes (idempotence)

- **Precondition**: An artifact produced by a completed run, and a specification whose digest and line count equal the values recorded in that artifact.
- **Postcondition**: A second run writes a byte-identical artifact, and a verification run changes no byte and exits 0. The return value carries the digest before and after, which are equal.
- **Invariant**: Idempotence is asserted by digest rather than by comparison of parsed fields, so a change in key order or whitespace that a reader would not notice still fails.

### C012 — pins in the artifact -> the specification text (an artifact never supplies its own premises unchecked)

- **Precondition**: An artifact carrying pins, and the specification it names. Invalid input: a predicate line that does not contain its declared limbs; an enumeration member that does not occur inside its declared range; a block partition that overlaps or leaves a gap; a form entry that decides rather than proposes.
- **Postcondition**: Each pin is re-derived from the specification by the rule the pin declares, and a pin that fails its own rule is reported as a verdict naming the pin, the rule and the line, with exit non-zero.
- **Invariant**: No check consumes a pin that has not been re-derived in the same run, so an artifact that records a wrong predicate line cannot pass its own verification; this is the property that keeps the single-input design from becoming a self-referential one.

### C013 — the specification file -> the artifact identity (a citation is meaningful only against one revision)

- **Precondition**: A specification file and, for a verification run, an artifact carrying spec.sha256 and spec.lines.
- **Postcondition**: A run records the digest and the line count of the specification it read. A verification run whose specification digest or line count differs from the recorded value is refused with both values named, rather than repaired or re-derived silently.
- **Invariant**: Every line citation in the artifact is valid only against the recorded digest; an artifact whose digest does not match is never partially accepted.

### C014 — rail/render.mjs -> the committed rendering (a rendering is never a store)

- **Precondition**: An artifact, and for the convention test a committed rendering beside it.
- **Postcondition**: The rendering is produced from the artifact, the committed rendering is byte-equal to a re-render, and a rendered file is never read back as a source of records.
- **Invariant**: A hand-edited rendering fails the freshness test, the arrangement tests/check-bundle-fresh.mjs already uses for the committed conver bundle, so the human view cannot drift from the record it is a view of.

### C015 — the artifact -> a consuming package (a contract surface with stable identifiers)

- **Precondition**: An artifact carrying schema_version and an id for every sequence and every operation.
- **Postcondition**: A consumer can check both directions with no other input: every operation the artifact declares is implemented or explicitly excluded by the consumer, and every operation the consumer declares appears in the artifact. The check reports the two difference sets separately.
- **Invariant**: An id, once written, is not renumbered by a later run of the same specification revision; a rename appears as a removal and an addition rather than as a silent renumbering, so a consumer holding an old artifact fails loudly.

### C016 — gates.mjs -> the command file (the phase table is data)

- **Precondition**: The PHASES array, each entry carrying id, name, tag, requires, backTo and maxLoops. Invalid input: a phase with no tag; a requires naming a phase that does not exist; a backTo equal to or greater than its own id; maxLoops below one.
- **Postcondition**: PHASES holds seventeen entries whose ids are 1 to 17, every tag is one of det, read, ad-hoc, every requires names an existing phase, every backTo is null or a lower id, and every maxLoops is at least one.
- **Invariant**: The command file states no phase fact that this array does not carry, so the two cannot drift: a step added to the document without a phase here fails the phase-table test.

### C017 — phases.mjs -> the run order (a phase cannot be entered early)

- **Precondition**: A status recording which phases are done, and a phase whose requires list names phases that are not all done.
- **Postcondition**: runPhase refuses, the refusal names the first missing phase, and no action runs and no exit gate is evaluated.
- **Invariant**: Entering phase 13 before phase 9 is refused rather than performed, because every later gate reads what an earlier phase wrote and a run that continued would check whatever happened to be on disk.

### C018 — phases.mjs -> run-state.mjs (a refusal costs a loop)

- **Precondition**: A phase that has refused, and a status that records the loops it has spent.
- **Postcondition**: The refusal spends one loop, reports the back-edge and the file the reader must produce, and a resumed run reuses the recorded count rather than refunding it.
- **Invariant**: A phase that has spent maxLoops refusals is reported with its count and its last refusal verbatim, so a loop limit is a real limit rather than a suggestion.

### C019 — a [read] phase -> the closing report (signed is not the same as vacuous)

- **Precondition**: A [read] phase that has passed, and the record of what it reported: the number of signed claims, and whether it had anything to read.
- **Postcondition**: The report prints readPhasesSettled with the count that had nothing to read, and reports the run complete when every [read] phase is either signed or vacuous.
- **Invariant**: A phase whose reader never reported and a phase that legitimately found nothing do not print the same, and only the first is incompleteness.

### C020 — run-state.mjs -> the one-argument contract (working state is not a product)

- **Precondition**: A run over a specification in any directory.
- **Postcondition**: The run directory is derived from the specification name and digest and holds status.json, declaration.json, the readings files, the worklists and any scaffolded checks; nothing is written beside the specification except the artifact and, at most, the rendering.
- **Invariant**: The one-argument contract C010 remains a statement about products only: no phase writes into the specification directory, so a verification run still needs nothing but the specification path.

## Boy Scout Rule

- The library is written so that every function name is a verb phrase describing one act: renderBrief, buildWorklist, deriveSet, applyReadings, runCase, spliceCheck, writeRailExit. A reader of the call sequence reads the procedure as prose, which is the property the command itself is about.
- Every value the extraction would otherwise leave as a bare number becomes a named constant in a single declared block per module, and the unused-pin test fails when a declared pin is read by nothing, so the extraction cannot leave a value that nothing reads.
- No error is swallowed: the integrator returns a refusal object and exits non-zero rather than logging and continuing, the engine converts a throwing check into a verdict rather than aborting, and the falsifier reports an unattributable red as unattributable rather than as a pass.
- Existing code touched by this ticket is improved where it violates these rules: the module-system table in .claude/rules/node.md gains the row its own convention test requires, and the Makefile target is written in the declared form rather than in a form that happens to pass. Files outside this ticket that show the same violations are named in the notes rather than edited here, because editing them would exceed the ticket.

### Exceptions

- 【Item】Whether a reader actually opened the line and read it, as opposed to asserting that it did.
【Reason】The act of reading is not testable after the fact: it is not a state a process can observe, and the only machine-visible trace is the signature the reading carries, which is a claim about a past act that no test can re-run. This is not a design defect, because the design does not depend on the act being observable; it depends on every claim carrying an attribution, and attribution is mechanical.
【Alternative】The mechanical half is tested: a claim with no reader reddens the run, a ruling with no adversarial reader reddens the run, and a step with no verdict reddens the run. The honesty of the attribution is carried the way any signed record is carried, and the command states the residual in writing instead of implying that the checks measure it.
- 【Item】That the rail generalises to a specification other than the one it was extracted from.
【Reason】No second specification is available in this repository, and a second specification is exactly what would falsify the pin schema, so the claim is not testable here. This is not a design defect, because the engine is parameterised by construction and the parameter set is small enough to inspect; but inspection is not a second run, and treating it as one would be the error the whole programme is about.
【Alternative】The mutation corpus falsifies the engine against the one specification that exists, which shows the engine is not vacuous. The residual is reported as an open measurement with its promotion rule: a pin that a second specification needs is promoted into the schema on the second use, and the rail-exit count makes that debt visible on every run.
- 【Item】The phases tagged [read] depend on reader agents, whose dispatch is not deterministic in wall-clock time.
【Reason】A live agent cannot be asserted in a unit test, so those phases are not testable end to end. This is not a design defect, because the determinism boundary is deliberate and declared per phase, and everything on the library side of a [read] phase is deterministic and tested.
【Alternative】The reader-facing contract is exercised without a live agent by running the brief renderer, the worklist builder, the output validator and the integrator against readings recorded from the fixture corpus, so every field a reader must supply is proven by a test even though the reader is not.
- 【Item】Roughly three megabytes of frozen specification and artifact fixture are committed to this repository.
【Reason】The size is not testable as a defect: a fixture either matches its recorded digest or it does not, and the size follows from the specification being 1069541 bytes. This is not a design defect, because the alternative, referencing the specification in place, would make the suite depend on another repository and would let the fixture drift with it.
【Alternative】The size is measured and recorded rather than assumed, the fixture digests are held by a convention test, and the source of each fixture file is named in the manifest so that a future reader can re-derive the copy instead of trusting it.
- 【Item】The consumer direction of contract C015 against a real consuming package.
【Reason】The consumers a run is meant to serve are the implementation packages of the target project, and none of them exists in this repository, so the direction is not testable against a real consumer here; a synthetic consumer is a stand-in for one. This is not a design defect, because the artifact declares the contract in its own schema and the check is written against that declaration rather than against a particular consumer.
【Alternative】A synthetic consumer exercises both directions of the check and both difference sets, so the mechanism is proven even though no real consumer is present; the first real consumer is the first genuine test of the direction, and the ticket records that as an open item rather than as a covered one.

## Notes in Prior Implementation Rounds

- 【Implementation steps】Order the work so that each phase lands green on its own: (1) scaffolding, the directory package.json, the module-table row, the Makefile target and the fixture copy with its manifest; (2) the artifact schema and the path derivation, which is what fixes the one-argument contract; (3) the brief renderer and its four briefs, the smallest piece that makes the signature requirement real; (4) the worklist and set builders, with the selection predicate checked against the artifact; (5) the integrator with its three proofs; (6) the extraction of the checks into value-free modules; (7) pin establishment and pin re-derivation, which is what makes the single-input design honest; (8) the two-sided falsification harness with the mutation and counter-mutation corpora; (9) the splice surface and the rail-exit record; (10) the rendering and its freshness convention; (11) the command file itself, whose phases are then all backed by a tested library; (12) the design document and its entries in the two convention tests.
- 【Risks】The largest risk is that the extraction becomes speculative generality: a pin that no check reads, or an option that no specification exercises, is a claim about generalisation that nothing tests. The counter is the unused-pin check. The second risk is that the single-input design turns the artifact into its own authority, since the pins it carries are the premises every check runs on; the counter is pin re-derivation, which proves each pin against the specification text in the same run that consumes it, and a test that disables re-derivation and requires the engine to refuse rather than proceed. The third risk is that the command standardises the shape and thereby makes the ritual easier; the counter is that a signature on every claim and a mutation that must redden are enforced by tests.
- 【Caveats】The fixture is frozen by design and will not follow the specification as it evolves; that is the price of a test that runs without the source repository, and drift is reported rather than absorbed. No Gaia value may be copied into the library during the extraction, including a value that looks harmless such as a threshold. The artifact is written beside the specification, so a project that treats its specification directory as a single hashed unit will see its digest change; the manifests in the target project name files individually, so this is expected to be safe there, and the command records the specification digest so that a change to the specification itself is distinguishable from the addition of the artifact.
- 【Open items】Whether a second specification needs a pin the schema does not carry is open and can only be closed by a second run. Whether the four briefs are the complete set of reader roles is open: a fifth role appears when a defect class appears that no existing reader can be asked about. The grill intake is open and is not part of this ticket: the grill reads its prior material by fixed file name, so giving it the artifact at RFC-writing time needs a change on the grill side. The first real consumer of the artifact is open: the consumer direction of the coverage check is proven against a synthetic consumer here, and its first genuine exercise is in a project that runs the command.
- 【Future improvements】Once a second specification has been run, the pin schema is the natural place to record what the second run needed, and the rail-exit records are the natural input for a promoted check.
