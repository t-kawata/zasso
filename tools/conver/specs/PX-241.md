# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

- 【Goal】Generalise the Gaia sequence-and-operation derivation so that another project can reproduce it, and turn the ad-hoc surface from a scaffold into a library. Three conditions are added to the existing /educe-sequences rail. First, the check constructors are exported and the scaffold emits an executable mutation, so the cost of a new check falls to naming a defect and choosing a subject and a shape. Second, the guarantee moves out of a callable function and into the checks that gate a run: the section census, the operation placement and the sequence-to-operation totality. Third, the declaration names its weakest link before the artifact is built, and phase 13 refuses while that link has no check. A fourth item holds the command file itself, which no test reads today.
- 【Purpose】PX-240 built the rail: seventeen phases over three tags, nine checks, five pins, four reader briefs and one ad-hoc scaffold. Measured at PX-241 time, the three shapes that carry the guarantee in the Gaia record are exactly the three the library is missing. compareCoverage exists at harness.mjs:269 and its only callers are tests, so the surjection PX-240 contract C015 proves is not among the checks that gate a run. The artifact schema declares positions at artifact-schema.json:30 and nothing checks that an operation position is one of them or that its evidence is present, which is the defect Gaia numbered S25. No check requires a section to be explained, which is S20, and CHECKS holds no totality check, which is S24. The nine shapes the engine does carry are grounding, shape and provenance; agreement, self-coverage and exactly-one-bucket are absent.
- 【Motivation】The Gaia programme paid six rework passes A to F because the two measures that catch fabrication, the per-step verbatim quote and the attack on the weakest link of the guarantee, were written after the artifact had been declared complete. Measured there: the first version of the step file held 1178 steps, every step carried the four required fields, the ordering held and the bijection held, and none of it was a reading. The portable asset is the procedure together with the checks, never the values. If the ad-hoc surface stays a scaffold whose generated module returns an empty array and imports nothing, the next specification pays that cost again by hand.
- 【Constraints】Nothing under ~/shyme/gaia is written by this ticket. No Gaia value enters the library: no line number, no vocabulary member, no threshold, no section number. Every new check is falsifiable in both directions, red on the defect and green on correct work. A check may propose and may never decide. The command file must not be restructured: no phase is added, no Step is inserted or renumbered, and no derived count is restated in it.
- 【Decision recorded in this revision】The weakest link is a section of the declaration rather than a phase. Adding a phase would renumber every Step after it, move the ids in gates.mjs:88, and stale both the count statements in the command file at lines 45 and 104; the requirement that the link be named before the artifact exists is satisfied by a declaration that is complete by Step 5, four Steps before Step 9 writes the artifact. The mapping from an entry to its operations is derived from the steps and stored nowhere, which is the resolution Gaia reached at step 9.5 of its own record, where two independently assigned fields agreed because they were the same field. The consumer direction of PX-240 contract C015 deliberately stays outside CHECKS, because a check that gates a run cannot require a consumer that does not exist in this repository.
- 【Decision recorded in this revision, second addendum】The run state moves out of the tool and beside the specification. PX-240 put it at `<tool>/runs/<name>-<sha8>/` and gitignored it, on the argument that the one-argument contract should be a statement about products rather than about everything the run touched. That argument is reversed here, because it costs more than it saves: the declaration and the readings are the evidence for the artifact, and evidence kept under the tool is evidence a reader of the specification cannot find, cannot commit with the artifact and loses when the spec is edited, since a new digest opens a new directory and silently orphans the old one. The run directory is therefore `join(dirname(specPath), 'educe-sequences')`: a pure function of the argument, co-located with the specification, and stable across revisions so that editing the specification produces a refusal naming the directory rather than a quiet new one. PX-240 contract C020 states the opposite invariant and is superseded by contract C015 of this ticket.

## Acceptance Criteria

- 【Happy path】The command is invoked with one argument, the fixture specification path; a run over the recorded declaration and readings writes the artifact beside the specification; checkAll runs twelve checks and returns no verdict; the section census, the operation placement and the totality are each green on the golden artifact; the weakest-link gate passes because the named check is declared; every pin is re-derived before it is consumed; the committed artifact is reproduced byte for byte and its digest equals the recorded digest; the command-file test passes with the phase count and the brief-name list agreeing with the arrays they summarise; and the design document resolves against the repository through the two convention tests.
- 【Error case】A declaration with no weakestLink, a directive naming a tightenedBy that no check carries, an operation marked positioned that no step names, a section no entry starts inside and no adjudication names, a step naming an operation the artifact does not declare, an artifact whose position is outside the declared positions, a scaffold with no originating defect, a scaffold whose import path would not resolve, a scaffolded check whose mutation does not redden, and a rail-exit record whose executed field claims an outcome no run produced each cause a refusal that names the offending item, with no artifact written, no record appended and no test weakened; the run exits non-zero and the artifact digest is unchanged.
- 【Edge case】A second run over an unchanged specification writes a byte-identical artifact; the seven section adjudications and the six step bindings leave the frozen gaia corpus at its recorded digest; each of the three new mutations reddens the check it names for an attributable reason and each counter-mutation stays green; the count of Step headings in the command file is unchanged and the phase ids remain 1 to 17; the fifth brief renders while carrying exactly one interrogative sentence and the other three clauses, and removing any one of them makes it refuse by name.

- 【Pin re-derivation】Every pin is re-derived from the specification text by the rule the pin declares, in the same run that consumes it, and no check consumes a pin that was not re-derived in that run. The three new checks consume no pin directly: they read sections, sequences, steps, operations and adjudications, and they are gated by phase 14 for the pins the artifact carries.
- 【Invariant on error】rail/adhoc.mjs writes nothing when a scaffold is refused. A check with no originating defect, a scaffold whose module would import nothing, a mutation that does not redden, and a record whose executed field claims an outcome no run produced are each refused by name. The generated check body is an incomplete implementation the moment it is written, so it carries a [::STUB::] marker naming this ticket and the defect that motivated it, and that marker is removed only when the execution gate has observed the mutation redden and the counter stay green, and the refusal leaves the run directory byte-identical to its state before the call.
- 【Internal state invariant】A check may propose candidates and may never decide. None of the three new checks treats a name appearing near a region, a plain span intersection or a coverage relation as evidence about what a line says. An entry that covers a section without starting inside it does not explain that section, and an operation marked positioned without a step naming it is refused rather than accepted, so the escape from one check is paid for by evidence the next one requires.
- 【Boundary invariant】The frozen fixture under tests/educe-sequences/fixtures/gaia is byte-frozen: a difference between a fixture file and its SHA-256 in MANIFEST.json fails the run and is never absorbed by editing the fixture. The golden run under tests/educe-sequences/fixtures/spec is regenerated deliberately by this ticket from a recorded run rather than edited, and the committed artifact records the digest of the committed specification, so an artifact that does not match the text it cites is refused rather than repaired.
- 【No renumbering】The phase table keeps seventeen entries whose ids are 1 to 17, and .claude/commands/educe-sequences.md keeps its seventeen Step headings with their numbers and names. The weakest link is a section of the declaration rather than a phase, so no Step is inserted, removed or renumbered and no derived count is restated in the file.
- 【Working state】The run directory is a pure function of the specification path: `join(dirname(specPath), 'educe-sequences')`, holding status.json, the declaration, the readings, the worklists, pins.json and any scaffolded checks. No phase writes under the tool, so the one-argument contract holds for everything the run touches and not only for its products. An existing status recording another specification or another digest is refused by name rather than resumed, because inheriting verdicts taken against another revision would make every line citation in them mean something else without saying so.

## Boy Scout Rule

- Function names: every new function is a verb phrase naming one act. checks.mjs exports agreeOn, coverEvery, placeEach, reachEvery, citeFrom and groundIn as the six constructors, beside pinCheck; adhoc.mjs gains scaffoldModule and runScaffoldCases; engine.mjs gains the three check builders as named functions rather than inline object literals; gates.mjs gains weakestLinkClosed as the one clause the phase 13 gate reads.
- Variable names: the generic names in the touched code are replaced with domain concepts. In the three new checks the locals are the sections no entry starts inside, the operations no step names, the forward names and the backward names, rather than a, b, list and diff. In reading.mjs the flat `entry` local that may hold a sequence or an operation is renamed to the thing it is at each use.
- One function, one responsibility: checkAll stays the loop and the summary, and each new check is built by a named constructor at module scope rather than by an inline closure, so a reader of engine.mjs sees twelve declarations instead of nine literals and five calls.
- Hardcoded values: the position names, the outcome names and the pin kinds already live in artifact-schema.json and PIN_RULES and are read from there; the new checks read the position list from the schema rather than repeating its three members, so a fourth position is a schema edit and not a code edit. The escape positions that totality treats as paid for are named as a constant beside the check rather than written inline twice.
- No swallowed errors: runScaffoldCases returns a refusal object naming the case that failed rather than logging and continuing; checkModuleSource refuses rather than emitting a module whose import would not resolve; writeRailExit throws on an unexecuted record rather than appending a claim.
- Proactive improvement of existing code inside scope: pinCheck moves from module-private to exported, which is the change that makes the other five constructors worth writing; validateDeclaration gains the object-section branch it already needed for any non-array section, rather than a second special case written only for weakestLink; the command file gains the test that PX-240 contract C016 assumed existed. Files outside this ticket that show the same violations are named in the notes rather than edited here, because editing them would exceed the ticket.

### Exceptions

- 【Item】Whether the weakest link the declaration names is the apparatus loosest judgement for this specification, rather than a plausible one.【Reason】The judgement is a reading about the apparatus and it is not testable after the fact: it is not a state a process can observe, and the only machine-visible trace is the declaration that carries it.
