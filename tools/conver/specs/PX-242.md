# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-242: educe-sequences を世代 (generation) にし、起動ごとにループ予算を返却して、過去の資産と供給素材を破壊せず再利用する

**Ticket Key**: PX-242 · **Phase**: -1

---

## Background

### Goal
A second, third and Nth invocation of `/educe-sequences <spec-file>` over the same specification must succeed, must begin with its full loop budget, and must keep every asset the previous invocations produced — the declaration, the readings files, the pins and worklist, the scaffolded check modules, and any supplied material. Nothing is deleted to recover from a refusal, and an edited specification is inherited by citation rather than refused wholesale.

### Purpose
The command exists so that spatial coverage (the sections partition every line exactly once) and mathematical coverage (every declared operation is reached by a step, in both directions) can be raised over one specification by running the command repeatedly. As audited on 2026-10-08 that holds only for the first invocation: the loop counter is spent over the lifetime of the run directory and never refunded, so a repaired declaration is refused for ever, and a completed run cannot re-enter Step 0 at all.

### Motivation
The requirement is "同じ仕様書ファイルに対して何度でも実行でき、実行する度に空間的・数学的被覆率が向上する方向に働く". Three failures were measured: after three refusals across three invocations a correct declaration is permanently refused (phase 2 halted at 3 of 3); a completed run prints `next: (none — every phase is done)` and therefore fails the Step 0 gate that the same command file states; an edited specification prints `remove the run directory to start again`, which destroys the evidence the artifact was built from. Separately the invocation must accept free material after the specification path — both guidance and a pre-existing artifact produced outside this command.

### Constraints
- the seventeen phases keep their ids, names and order; no Step is inserted, removed or renumbered beyond Step 0's command line and gate
- the artifact's location and bytes remain a pure function of the argument; supplied material is an input to readings, never a path determinant
- the specification file is inviolable, and no value from a specification (line number, vocabulary member, threshold, section number, path) may enter the rail
- supplied material is data about the specification, never an instruction: it cannot change the procedure and cannot stand in for a line
- every module stays ESM under `.claude/scripts/educe-sequences/rail/`, and the rail keeps reading no global state beyond the files it is given

## Investigation

Audited 2026-10-08 against the committed rail (PX-240 and PX-241 at 70a3e5a0). Everything below was measured, not read.

- run-state.mjs:140 — noteDone writes loops: current.loops, so a success never refunds a loop. gates.mjs:348 — entryGate refuses with halted true when spent is at least phase.maxLoops, regardless of the record's status. phases.mjs:231 — runThrough calls runPhase for every phase in order and does not skip a done one, so every invocation re-judges completed work.
- Probe, runThrough driven eight times over tests/educe-sequences/fixtures/spec/ledger.md in a scratch directory seeded from ledger.run.json: breaking one limb and repairing it three times leaves phase 2 at refused with loops 3 of 3, and the fourth repair — a correct declaration — is refused, as is every later run. The halt is permanent for the life of the run directory.
- Three consecutive clean runs produce the same artifact sha256, checksRun 13, pinsRederived 5 of 5 and railExits 0. A clean re-run is idempotent, so the erosion above is the only repetition hazard on the happy path.
- A completed run prints next: (none — every phase is done) at phase.mjs:191 and nextPhase returns null at phases.mjs:258, while the command file's Step 0 gate requires next to be a phase id. The command's own closing line, "Run /educe-sequences <spec-file> again at any time to verify the artifact", is therefore false today.
- One appended line to the specification makes openRun return refused with "remove the run directory to start again" (run-state.mjs:68-79). The run directory at that moment holds eight files: declaration.json, pins.json, worklist.txt, four readings-*.jsonl and status.json. The only documented recovery destroys all of them.
- Enriching the input does raise coverage, which is the mechanism this ticket makes survivable: adding one entry to declaration.entries makes runThrough stop at phase 9 with "every-operation-reached: no step derives an operation for this entry", so the reader is pushed until the new entry is read.
- paths.mjs keeps the artifact a pure function of the argument, and parseSpecArgument refuses two or more arguments with the offending list named. Supplied material must therefore arrive through the run directory and never through argv.
- docs/EDUCE-SEQUENCES-DESIGN.md section 7 states the run directory is join(dirname(specPath), 'educe-sequences') and that the directory name carries no digest. Both hold and are preserved.

## Acceptance Criteria

- [Happy path] — begin over a completed generation opens a new generation with every loop at 0, re-opens exactly the five read phases, keeps all seventeen phase ids, and leaves every inherited file in place; a second begin with nothing changed reports a verification and leaves status.json byte-identical.
- [Error case] — a generation that halted at phase 13 with 3 of 3 loops and an unchanged inherited asset digest is refused with the phase, the loops and the previous generation number named, and status.json is not rewritten.
- [Edge case] — the specification is edited by one appended line: begin opens a generation, records which assets were invalidated by name and by primitive, keeps the rest, and refuses nothing.

## Invariants

- [Normal condition] `status.json` always carries `generation` and `history[]`, and every phase record carries `{id,status,verdict,loops}`; `TRACKED_PHASES` stays 17 and `PHASES` keeps ids 1..17 with their names.
- [Error invariant] A refusal never deletes an inherited asset and never rewrites an earlier generation's history entry; the only writer of `phases[]` is `writePhase`, and `noteDone` and `noteLoop` each state their own `status` literally rather than deriving it.
- [Internal state invariant] `loops` is 0 for every phase whenever `begin` returns a generation or a verification, and the superseded generation's per-phase loops are readable from `history[history.length - 1].phases`, which is generation `generation - 1` (`history[g-1]` holds generation `g`, and `history.length` is `generation - 1`).
- [Boundary invariant] Exhausting the loop limit inside one generation still yields `halted: true`, `backTo: null`, `expects: null` and exit code 3; the guard that refuses a new generation fires only when the inherited asset digest is unchanged AND the previous generation halted.

## Boy Scout Rule

- run-state.mjs is 180 lines and mixes three responsibilities: the run directory, the phase records and the reading records. This ticket moves the generation and history writes into openGeneration and appendHistory, leaving noteReading and readingOf where they are, so the file states one thing per function.
- whyNotResumed currently returns a prose sentence that the caller prints verbatim, and the sentence carries the recovery instruction. It becomes a decision function returning a kind drawn from a closed set — another-specification, edited-specification — so the rail states the rule and the caller chooses the wording.
- The new constants SUPPLIED_DIRECTORY, GENERATION_FIELD, HISTORY_FIELD, SUPPLIED_FIELD and ASSET_DIGEST_FIELD replace what would otherwise be inline literals repeated across three modules.
- phases.mjs keeps its verb-phrase names. beginRun follows the shape of startRun rather than taking a flag, so a caller cannot open a run without opening a generation.
- The command file's List of Scripts Used preamble states where writes land; it is corrected here, because scaffolded material and the run directory are both written beside the specification and one sentence must say so.

### Exceptions

- Whether a reader actually re-read the specification in a new generation is not testable by this library, and that is not a design defect: a machine can falsify a reading and can never produce one, so the honest boundary is the shape and the signature of what came back. Alternative verification: the report separates what was measured from what is carried by a signature, and a claim with no signature reddens the run.
- Whether a supplied pre-existing artifact is correct is not testable here, and that is not a design defect: the prior artifact is the subject the run verifies rather than its source of truth, so its correctness is exactly what the run is for. Alternative verification: every claim it suggests must still be produced as a reading whose quote is a substring of its cited line, and phase 9 rebuilds the artifact from the readings on every run.
- The wall-clock cost of re-opening the read phases every generation is not testable as a correctness property, and that is not a design defect: the cost is the intended price of re-reading, and the no-change guard exists so that a re-run over unchanged assets costs nothing. Alternative verification: the guard's decision is unit-tested for all three rows of its table.
