# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-243: 毎世代に問いを発して回答させ、漏れ・矛盾・不足・危険の観点で被覆率を上げる (inquest)

**Ticket Key**: PX-243 · **Phase**: -1

---

## Background

### Goal
Every generation must ask its own questions of the specification and answer them, under four declared lenses — omission, contradiction, deficiency and risk — and the answers must be recorded with a line, a quote and a signature so that the machine can check the shape of the audit without ever pretending to have performed it. A generation in which the audit was not answered must not report itself complete.

### Purpose
Raise coverage across generations rather than within one. Within a generation the loop-back edges already push the declaration and the readings until the checks are quiet; what they cannot do is discover a question nobody asked. The inquest is the carrier for those questions, and because it is re-asked every generation, a specification that changes or an apparatus that was read thinly is re-interrogated rather than re-verified.

### Motivation
The requirement is that the command be used "実行する度に空間的・数学的被覆率が向上する方向に働く" and that the method be "機械的検査だけでなく、readings = 仕様書や設計書の意味論を含めて「深く読み込み直す」ことが重要であり、都度自ら「問い」を発して回答できるか". Measured on 2026-10-08 the rail has no carrier for a question: the declaration schema holds predicate, rowSchema, enumerations, forms, entries, sections, exemptions and weakestLink, and a reading holds subject, outcome, reader and possibly neighbour. The five briefs ask fixed questions. Nothing records what was asked, by which lens, against which subject, or what the answer rested on — so a re-run re-asks the same five questions and cannot raise coverage.

### Constraints
- a machine can falsify a reading and can never produce one: the inquest is a [read] phase, and its gate checks the shape, the signature and the grounding of what came back
- every question and every answer uses the closed vocabulary the command already declares (Yes / No, or A / B / C); a free-form question is a defect in the question and is rewritten, not asked
- an answer is grounded in a line of the specification, never in the supplied material and never in the artifact
- the phase table's id order must equal its dependency order, because the driver runs the phases in array order
- the specification file is inviolable, and no value from a specification may enter the rail

## Investigation

Audited 2026-10-08 against the committed rail (PX-240 and PX-241 at 70a3e5a0).

- The declaration schema in readings.mjs holds predicate, rowSchema, weakestLink, enumerations, forms, entries, sections and exemptions. There is no field for a question, an answer, a lens or the line an answer rests on, so a re-run has nowhere to record having asked anything.
- The five briefs are fixed: BRIEF_NAMES is span, adjudicate, adversarial, reroute and adhoc. PHASE_GUIDANCE asks each of them the same question in every generation, so a second generation asks exactly what the first asked.
- A reading's shape is READING_FIELDS (subject, outcome, reader) plus NEIGHBOUR_FIELD. Nothing in it can carry a question or the line an answer stands on.
- PHASES is ordered by id and runThrough filters by id and iterates the array. phase.backTo is asserted lower than phase.id by tests/educe-sequences/phases.test.mjs. Both facts mean a phase's id must not be lower than the id of anything it requires, which is why the inquest is inserted at 13 rather than appended at 18.
- gate 13 currently refuses the weakest link before building the block: "the run that named its own loosest judgement and then reported a green block would be reporting a guarantee it had already said it could not make". The inquest uses the same idiom, so the audit cannot be skipped any more than the weakest link can.
- isComplete in report.mjs requires a non-null summary, checksRun equal to the declared count, pinsRederived equal to pinsTotal, and every read phase settled. Adding the inquest to readPhases() makes it a completeness condition without changing the exit code of the report subcommand.
- report.mjs returns 0 whenever a summary exists, so "incomplete" currently exits 0. That is preserved: the binding for the audit is that phase 14 cannot run before phase 13, not that the report exits non-zero.
- ledger.run.json carries declaration plus readings {sequences, steps, operations, adjudications}; it has no inquest section, so the fixture must be extended for the through subcommand to reach phase 18.
- The four lenses and the closed answer vocabulary come from the requirement itself: 漏れ・矛盾・不足・危険, answered in the Yes/No or A/B/C vocabulary the command already declares.

## Acceptance Criteria

- [Happy path] — phase 13 asks every declared section and entry under the four lenses, each answer names a line and quotes it, the check block runs only after the audit is answered, and the report prints the asked, answered and exempt counts beside the previous generation's.
- [Error case] — one (subject, lens) pair is unanswered: phase 13 refuses naming the pair, phase 14 is refused entry with 'phase 13 is not done', and the run exits non-zero without printing a green block.
- [Edge case] — a declaration with no sections and no entries passes as vacuous rather than as an absent audit, and the report distinguishes the two.

## Invariants

- [Normal condition] `PHASES` has 18 entries whose ids are 1..18, the inquest is id 13 with tag read, and every phase's backTo is null or lower than its own id.
- [Error invariant] A question whose declared answer is outside the closed vocabulary is refused by name; an answer whose line does not carry its quote is refused by name; neither refusal is repaired by loosening the check.
- [Internal state invariant] `readings-inquest.jsonl` holds one record per (subject, lens) pair, and the set of subjects asked equals the set of sections and entries the declaration declares, less the exemptions.
- [Boundary invariant] A generation in which the inquest was not answered is reported incomplete even when every check is green and the exit code is 0; the count of asked, answered and exempted pairs is printed, and they are never summed with the measured counts of the apparatus.

### C002 — PX-243 -> the inquest coverEvery check -> every subject is interrogated under every lens

### C003 — PX-243 -> placeEach and the readings validator -> the closed vocabulary

- **Precondition**: An inquest record carrying a lens and an answer. Invalid input: a lens outside INQUEST_LENSES, or an answer outside INQUEST_ANSWERS (Yes, No, A, B, C).
- **Postcondition**: A lens outside the set is refused by the readings validator, naming the lens; an answer outside the set is refused by the placeEach check, naming the subject and the answer. Neither refusal is repaired by widening the vocabulary.
- **Invariant**: INQUEST_LENSES and INQUEST_ANSWERS are the only source of the two vocabularies, and neither is restated as a literal in the brief, the checks or the command file.

### C004 — PX-243 -> groundIn and citeFrom -> an answer rests on a line of the specification

- **Precondition**: An inquest record naming a line and a quote. Invalid input: a line beyond the end of the specification, and a quote that the named line does not carry.
- **Postcondition**: The groundIn check returns one verdict naming the line when the line does not carry the quote after whitespace is normalised, including when the line index is out of range; the check returns no verdict when the line carries the quote verbatim.
- **Invariant**: assert.equal(normalise(specLines[record.line - 1]).includes(normalise(record.quote)), true) for an accepted answer, and no check reads the artifact to decide whether an answer is grounded.

### C005 — PX-243 -> renderBrief -> the audit is a re-reading rather than a repetition

- **Precondition**: A run whose history carries generation N-1 with its inquest answers, and a current generation whose declaration declares the same subjects.
- **Postcondition**: The rendered inquest brief names, for each subject, the question and the answer the previous generation recorded under each lens, and states the four lenses and the closed vocabulary. A subject that the previous generation did not carry renders without an answer and is not dropped.
- **Invariant**: every subject the declaration declares appears in the rendered brief exactly once per lens, whether or not the previous generation answered it

### C006 — PX-243 -> isComplete and the report -> an unanswered audit is visible

- **Precondition**: A generation in which every check is green, the artifact is written, pinsRederived equals pinsTotal, and no inquest reading exists for the current generation.
- **Postcondition**: isComplete returns false and the report prints incomplete; the Measured block carries inquestAsked, inquestAnswered and inquestExempt, each beside the previous generation's value.
- **Invariant**: assert.equal(isComplete({summary, status, declaredChecks}), false) while summary.checksRun equals the declared count, and the three inquest counts are printed as separate lines and never summed with the apparatus counts.

## Boy Scout Rule

- The four new checks are built from the constructors in checks.mjs rather than written out, so coverEvery, placeEach, groundIn and citeFrom each gain a production use and the shapes stay in one place.
- The lens and answer vocabularies become named constants (INQUEST_LENSES, INQUEST_ANSWERS) so neither is restated in the brief, in the checks or in the command file.
- report.mjs's healthLines is already a list of strings; the inquest counts are added as lines rather than by widening a summed total, which keeps the "measured is never summed with carried by a signature" rule intact.
- gates.mjs's phase table is data. The renumbering is an edit to that data and to the three lookup tables keyed by id, not a change to the driver, so the driver stays one loop with one responsibility.
- renderBrief currently takes a brief name and a worklist path. The previousAnswers argument is added as an optional third input rather than by teaching the renderer to read the run directory, so the renderer keeps doing one thing.

- [Correction to a prior decision] It was stated when this work was planned that the inquest would be appended as phase 18 without renumbering. That is impossible and the reason is structural: runThrough iterates PHASES in array order, so a phase whose id is lower cannot require one whose id is higher, and gating the check block on the audit is what makes the audit binding rather than advisory. The inquest is therefore inserted as 13 and the five phases after it move by one. Every phase keeps its name and its tag; only the ids move.
- [Risks] The renumbering is the largest risk, because five phase ids and five Step headings move at once and any missed reference fails at run time rather than at compile time. The mitigation is that the phase table is data: one test asserts the ids are contiguous and that backTo is lower than id, another asserts every phase keeps its name and tag, and the command-file test derives its counts from PHASES.length. The second risk is that the inquest becomes a formality answered without reading; the answer's grounding in a line and the adversarial attack on the weakest answer are the available defences, and both are already in the design.
- [Caveats] The fixture gains a readings-inquest.jsonl and the golden artifact is regenerated in the same run that regenerates it, so the two never disagree. The artifact schema does not change, so an artifact written before this ticket still validates; only the declared check count rises.
