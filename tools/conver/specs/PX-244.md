# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-244: scaffold 済み検査を artifact に対して走らせ、昇格を提案可能にし、rail-exit ストアを仕様ごとに分離する

**Ticket Key**: PX-244 · **Phase**: -1

---

## Background

### Goal
A check written during a run through the ad-hoc surface must keep working after that run: it must be loaded and executed against the artifact on every later run, its verdicts must enter the measured block, and the promotion condition it declares must become an actionable proposal. The rail-exit records must live beside the specification they belong to, so that one specification never reads another's ad-hoc history.

### Purpose
The ad-hoc surface is the only mechanism the design has for a defect class no existing check was written for, which is the one genuinely non-mechanical act in the command. Today it produces a record and nothing else: the check is executed once at scaffold time, is never run again, and can never be promoted, so running the command repeatedly cannot raise the coverage that matters most — the coverage of defect classes the thirteen declared checks do not know about.

### Motivation
The requirement is that coverage improve as the command is run repeatedly. Measured on 2026-10-08: checkAll iterates CHECKS and nothing else, so a scaffolded check never touches the artifact; gate 13 requires checksRun to equal ENGINE_DECLARED_CHECK_COUNT, which is CHECKS.length, so a check that did run could not be counted; promoteRecord and promotionCandidates are exported and called from nowhere, and phase.mjs has no promote subcommand, so promotion is unreachable from the command; and RAIL_EXIT_STORE resolves inside the tool tree, which both violates the one-argument contract and lets one specification's records be read by another's run.

### Constraints
- engine.mjs stays synchronous and free of dynamic import: the caller loads the modules and passes loaded checks in, so checkAll remains a function of values
- a check may propose and may never decide: promotion emits a proposal and writes no source file, because editing the rail is a change under a ticket
- the rail-exit store moves into the run directory and the global default is removed rather than kept as a fallback
- every module stays ESM under .claude/scripts/educe-sequences/rail/

## Acceptance Criteria

- [Happy path] — a check scaffolded in one run is loaded and executed on the next run, its verdict enters checksRun, and the promotion candidate count is printed; the tool tree's digest is identical before and after.
- [Error case] — an ad-hoc module with a syntax error is refused by name, is absent from checksAdhoc, and the checks phase refuses rather than reporting a count that would read as a pass.
- [Edge case] — a run with no ad-hoc modules counts exactly the engine's declared checks, and the store for a specification with no records is empty rather than shared with another specification's.

## Invariants

- [Normal condition] `checkAll` returns a summary whose `checksRun` counts the engine checks plus the ad-hoc checks it was given, and whose `checksDeclared` equals the same total.
- [Error invariant] An ad-hoc module that fails to load, exports no check, or exports no mutation is refused by name and never silently omitted from the count, because a check that vanished from the count would read as a check that passed.
- [Internal state invariant] The rail-exit store is `join(runDirectory, 'rail-exits.jsonl')`; no module computes a store path from `import.meta.dirname`, and two run directories never share a record.
- [Boundary invariant] A promotion writes no file under `.claude/scripts/`; the promotion proposal names the record and carries the source to splice, and the count of unpromoted records is printed on every run.

## Boy Scout Rule

- RAIL_EXIT_STORE is a module-level constant that hides a filesystem location inside an import path. It becomes a function of the run directory, railExitStoreFor(runDirectory), so the location is stated where the run is opened and a reader of the run directory finds the records beside what they describe.
- checkAll accumulating a params object is already wide. The ad-hoc checks are added as one named input rather than as a directory, so the function stays a function of values and the loading, which can fail, is answered by a function whose name says so.
- The three ad-hoc refusal reasons in runScaffoldCases are string literals repeated across the scaffold path and the loader. They become named constants so the loader and the executor refuse the same things with the same words.
- runCommand being synchronous is the only reason the product path cannot load modules. Making it asynchronous is the honest fix; wrapping a dynamic import in a synchronous shell would be the workaround this repository's No-Justification rule forbids.
- The existing tool-tree assertion is aimed at the wrong moment: it wraps runThrough, which never writes. It is extended to wrap the path that does, so the test states the invariant it was written to state.

- Whether a scaffolded check is a good check is not testable by the rail, and that is not a design defect: the rail can falsify it and cannot author it, so the honest boundary is that its mutation reddens it and its counter-mutation leaves it silent, both of which are already executed and recorded. ## Notes in Prior Implementation Rounds

- [Implementation steps] Write the unit set first and confirm each fails: checkAll has no adhocChecks parameter, RAIL_EXIT_STORE is a module constant, promote is unreachable and the tool tree is written by scaffold. Then move the store path into the run directory and make it a required argument, updating every caller in the same change. Then loadAdhocChecks. - [Risks] The largest risk is that a scaffolded check that fails to load is silently dropped from the count, which would make a broken check indistinguishable from a passing one; loadAdhocChecks therefore returns problems rather than skipping, and the gate refuses while problems is non-empty. The second risk is that runCommand becoming asynchronous changes an exported signature used by tests; the change is mechanical but every caller is updated in this ticket, and the exit codes are asserted unchanged.
