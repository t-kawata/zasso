# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-245: Measure what each generation added, and stop refusing a repeat over an unchanged set

**Ticket Key**: PX-245 · **Phase**: -1

---

## Background

Goal: /educe-sequences opens one generation per invocation. Two things about how a generation ends and how the next one begins are wrong, and this ticket fixes both.
Purpose: make the return of each generation legible to the human who reads the finished output, and remove a refusal that puts the automatic run in a human's hands.
Motivation (measured): (a) `whyNotNewGeneration` (rail/gates.mjs:432, called at rail/phases.mjs:368) refuses `begin` when the previous generation halted, the inherited asset digest is unchanged and the specification sha256 is unchanged. Its own message says `a new generation over an unchanged set would ask the same question again`. But the specification is inviolable, so the only ways to clear that refusal are a human editing the specification or a human supplying material — an automatic run stopped until a human acts. (b) The audit counts already print beside the previous generation (rail/report.mjs:37-60, `againstPrevious`), while the artifact's own counts do not print at all: `checkAll` computes `rows`, `steps`, `operations` and `sequences` (rail/engine.mjs:401-408) and `healthLines` prints none of them.
Motivation (purpose): the rail cannot know the true size of the specification's sequence and operation space, so it must not gate on growth. What it can do is record what each generation actually produced and show that number beside the one before it, so a human reading the run sees whether the returns are diminishing and decides — outside the run — whether to invoke it again.
Constraint: /educe-sequences runs to completion as one invocation. It never asks, confirms, offers options, or waits for a human mid-run; the human enters only by launching it. A change that makes the run depend on a human act contradicts the command.
Constraint: the specification file is inviolable and no specification value may enter the rail. Every number this ticket prints is derived from the artifact, the status and the specification lines the run already read.
Constraint: a check may propose and may never decide. Growth is therefore never a check's pass condition, and this ticket adds no check.
Constraint: TDD Red -> Green -> Refactor, strict order, Definition of Done D1-D6.

## Acceptance Criteria

- Happy path: `begin` over an entered, halted, unchanged run opens the next generation and prints a notice naming the phase, its loops and the superseded generation, with exit code 0.
- Error case: an artifact carrying no line fields yields `linesReached=0 of N` and raises no exception, so a thin artifact is reported as thin rather than as a crash.
- Edge case: two successive generations with identical counts print `sequences=4 (previous generation: 4)` and nothing refuses; a generation that merges two sequences into one prints a smaller number and still opens.

## Invariants

- [Normal establishment] `coverageOf(artifact)` returns the artifact's own counts (`sequences`, `steps`, `operations`, `rows`) and the union of its declared line numbers clipped to `1..specLines`; `beginRun` over an entered, halted, unchanged status opens the next generation.
- [Error invariant] An absent or non-numeric line field contributes nothing and raises nothing; an artifact that declares no line reaches `linesReached: 0` and no exception escapes.
- [Internal state invariant] No check reads a coverage number as a pass condition, and `ENGINE_DECLARED_CHECK_COUNT` stays equal to `CHECKS.length` (17), so the printed run still reads `checksRun=17 of 17`.
- [Boundary invariant] A declared line of 0 or beyond `specLines` is not counted and a line declared by two records counts once; history is append-only, so a later generation cannot rewrite an earlier generation's numbers.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — PX-242 edge: generation / loop budget — a new generation over an unchanged set

- **Precondition**: A status whose previous generation carries `entered:true` and a phase at its `maxLoops` limit, an asset digest equal to `status.assets.digest`, and a specification whose `sha256` equals `status.spec.sha256`.
- **Postcondition**: `beginRun({specPath, spec})` returns `{ok:true, mode:"new-generation", generation: superseded + 1, notice}` where `notice` is a string matching the phase id, its loops and the superseded generation number; it never returns `ok:false` for this condition.
- **Invariant**: The notice changes no exit code and blocks no generation. For every other status the same call returns `notice: null`.

### C002 — PX-244 edge: the checks block is built from what the run recorded

- **Precondition**: An artifact whose `sequences` carry `firstLine` and `lastLine` and whose `operations` carry `grounding.presupposition`, together with `artifact.spec.lines`.
- **Postcondition**: `coverageOf(artifact).linesReached` equals the cardinality of the union of every declared line number in `1..specLines`.
- **Invariant**: A record with an absent or non-numeric line field contributes nothing and raises nothing; `coverageOf` reads no file and is a pure function of its argument.

### C003 — PX-243 edge: a count printed alone says how much was asked

- **Precondition**: A `summary` carrying the current counts and a `status` whose history holds at least one entry carrying a coverage.
- **Postcondition**: `healthLines({summary, status})` emits one line per measured number, and each line carries `previous generation: N` with the value from the most recent history entry.
- **Invariant**: No measured number is summed with its predecessor; a run whose history is empty prints the number alone with no `previous generation` clause.

### C004 — Supreme law: a check may propose and may never decide

- **Precondition**: Any pair of artifacts whose coverage differs in either direction, including a pair whose coverage is equal and a pair whose later coverage is smaller.
- **Postcondition**: `checkAll({specLines, artifact})` returns the same verdict set and the same `summary.checksRun` for both members of every such pair.
- **Invariant**: No module under rail/ compares a coverage number against a threshold; `ENGINE_DECLARED_CHECK_COUNT` equals `CHECKS.length` and is unchanged by this ticket.

### C005 — PX-242 edge: the history a generation leaves behind

- **Precondition**: A status carrying `n` history entries and a coverage value to record.
- **Postcondition**: `appendHistory(status, {generation, phases, inquest, entered, coverage})` returns a status whose history has `n + 1` entries and whose last entry carries the coverage it was given.
- **Invariant**: The first `n` entries are unchanged; `appendHistory` returns a new array rather than mutating the one it was given, so a later generation cannot rewrite an earlier one's numbers.

## Boy Scout Rule

- Remove the stale `declaredChecks` argument at tests/educe-sequences/inquest.test.mjs:439: rail/report.mjs:46 replaced it with `summary.checksDeclared` and the argument now claims a parameter the function does not take.
- Name the new module for what it derives, not for an act: `coverageOf(artifact)`, matching the rail's existing derivation names (`phaseById`, `loopsOf`, `assetDigestOf`, `generationOf`). A function that performs an act in this ticket keeps a verb name (`beginRun`, `appendHistory`, `buildReport`).
- Rename `whyNotNewGeneration` to `unchangedRepeatReason` because the old name asserts a decision the function no longer makes; a name that contradicts its behaviour is the stale-comment defect in identifier form.
- Keep every printed label in `healthLines` a measurement of the artifact. No label may read as a fraction of the specification's true sequence space, which the rail cannot see.

- [exception] "the notice reads well to a human" is not testable: the clarity of one English sentence has no predicate that can fail. - [exception] "no check anywhere compares a coverage number against a threshold" is not testable behaviourally: it is the absence of a behaviour, a whole-tree property with no call site to observe. - [exception] "a reader asked again will produce more sequences" is not testable: the reader sits outside the rail, is an external dependency, and is non-deterministic. This is not a design defect — the rail's own obligation is only to permit the re-ask, which C001 tests directly; whether more arrives is an empirical outcome across generations. Alternative verification: the per-generation counts this ticket prints let a human observe the outcome across runs, which is the ticket's stated purpose rather than an assertion.
