# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

**(1) No step is grounded in a line.** Of the 614 steps in the artifact, `noLine=614`: not one carries
`line` or `quote`. The supplied `sequence-steps.jsonl` carries both per step (`spec_line`, `quote`,

`groundIn` — the check that a quote is a contiguous substring of its line — exists in `checks.mjs` and is
wired to the inquest answers only. `artifact-schema.json` requires `["id","sequence","operation"]` of a
step. The campaign's rule 7.5 says the per-step line and verbatim quote are what make fabrication
detectable at all: 1178 fabricated steps carried all four fields, the ordering held and the bijection
held, and none of it was a reading. The rail replaced that device with the signature and lost it.

**(2) The predicate is not a criterion.** The run declared the predicate at line 14147 with limbs
`["状態変更を伴うCoreOperationは","少なくとも次の順序で実行する"]` — two phrases of that same line. The
campaign's predicate is 14029 (state change / acceptance of a signed object / opening an external
integration / acceptance of an external result / finalisation / cancellation / expiry / recovery /
persistent event emission), and the supplied registry names it: "the operation satisfies the predicate at
14029". Two failures follow. The pin's re-derivation is a tautology when the limbs are the line's own
words — it proves only that the chosen line contains itself, where nine concepts cannot be satisfied by
quotation. And the pinned predicate never reaches a reader: `renderBrief` substitutes the question, the
verbatim clause, the no-window clause, the worklist path and the inquest lenses, never the predicate. No
decision in the rail returns to it, so the campaign's "the criterion is always the predicate at 14029"
has no counterpart.

**(3) An exclusion cannot be recorded.** `UNREACHED_ESCAPES` is `["suppliedRule","excluded"]`, but
`artifact-schema.json`'s `positions` is `["positioned","singleStep","suppliedRule"]` and `placementOf`
returns `{bucket: operation.position, evidence: ""}` for anything else. An excluded row can be exempt from
the reach check and can never be placed, so the run has to drop it. Measured: the campaign holds 185 rows
(67 positioned / 86 singleStep / 32 suppliedRule) plus 72 excluded; the artifact holds 76 (68 / 0 / 8).
The surjection the run proves is over 76 rows, not over the registry, and the campaign's rule that an
exclusion is a boundary to be recorded with its reason has nowhere to live.

**(4) The section partition is not the level procedures are stated at.** `SECTION_HEADING` is `/^## /`, so
the partition is 32 chapter blocks, while the specification states its procedures at `### ` (292 of them)
and the campaign's census was 430 sections. `placementOf` requires a `singleStep` operation to name a
declared section, and §19.6 is not one of the 32 — which is why the run declared 0 singleStep operations
where the campaign holds 86.

**(5) The mutation corpus selects its subjects by fixture vocabulary.** `harness.mjs` names `'Admit'` for
the mutation `operation-position-outside-the-declared-set` and `'Settle'` for the counter-mutation
`step-rebound-to-another-declared-operation`. Neither name occurs in the Gaia specification or its registry,
so the first threw on `undefined` and the second reddened for the wrong reason: phase 16 could not run. It
was repaired in gaia's installed copy during that run (selecting the artifact's own first operation, and
exchanging the operations of two steps that already carry one) and the source of record was not.

**(6) `~/` is accepted as a path and never expanded.** `looksLikePath` matches a leading `~/`, so a supplied
path written that way is classified as a path, and `existsSync("~/…")` is always false — the invocation is
refused with "the named path does not exist", which names the symptom and hides the cause.

Purpose: a run of `/educe-sequences` over Gaia, with the same material, must reach the quality of the manual
campaign — every step grounded in the line it was read from, a predicate that decides, exclusions recorded

## Invariants

- 【Normal establishment】A reading carries, for every step, an integer `line` inside the specification and a non-empty `quote`; the artifact written from it carries both unchanged, and `checkAll` returns no verdict over it.
- 【Invariant on error】A refusal leaves the artifact byte-identical to its state before the call: `applyReadings` proves every field of every step before `writeArtifact`, so a reading with one ungrounded step writes nothing. ## Boy Scout Rule

Inside scope:

- **Function names stay verb phrases and gain the ones they lacked.** New code is named for what it does: `blocksFromHeadings(specLines, level)` already reads as prose, `placementOf` keeps its one responsibility (a bucket and its evidence) and gains one branch rather than a mode, and the new checks are constructed by the existing `groundIn`/`reachEvery`/`bucketEvery` constructors instead of hand-rolled loops.
- **No hardcoded value where the source has one.** The section level becomes `declaration.sections.level` with `3` as the named default rather than a second regex in the module; `STEP_FIELDS` and `OPERATION_POSITIONS` stay declared once and are read by the schema, so no list of step fields is typed twice.
- **No swallowed error.** The `~` expansion either resolves to a path that exists or refuses by the resolved name — the current shape accepts a token the existence check can never confirm, which is a silence dressed as a refusal.
- **Untested touched code.** Every branch added here gets a test in the same pass: the four new checks, the two new `placementOf` cases, the level default, and the two repaired harness cases.
- **A false comment is corrected, not preserved.** `rail/checks.mjs` describes `groundIn` as the answer to the assembled-quote fabrication while nothing calls it over a step; after this ticket the comment and the call sites agree.

Outside scope, recorded rather than done:

- `run.mjs` still reads the artifact with the strict reader at its first step, so a corrupt `*-sequences.json` stops the product path with a parse error instead of a refusal verdict. Reported by PX-245 as a residual and unchanged here, because it is a different path with a different contract.
- `coverage.mjs` unions `firstLine..lastLine` per entry. Once the cross-reference record exists, a reach that counts absorbed distance can be told from one that counts cited distance; that is a measurement, and it belongs to the run that produces the first wide span.

### Exceptions

- The Gaia artifact is not testable as a test input, because it is an external dependency: it lives in another repository, it is 1.07 MB, and the ticket must not write there. This is not a design defect — the rail takes any specification path and the migration is tested against a synthetic artifact built to the pre-ticket shape, which exercises the same shape gate. The real artifact is exercised by running the command after review.
- Whether a reading is a reading is not testable by any check in this apparatus, because a shape can be satisfied without being a reading — the campaign measured this: 1178 fabricated steps carried all four fields, the ordering held and the bijection held. This is not a design defect and not an architectural defect, because the apparatus does not claim to measure it: what is testable is that the devices the campaign used are present, wired to the artifact, and able to redden, which is what the contract tests assert. The residual is carried by the reader signature, which is recorded per reading and per brief.
