# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-247: Make every line belong to an entry, so no part of the specification can go unread

**Ticket Key**: PX-247 · **Phase**: -1

---

## Background

Goal: the phase driver must refuse a run in which any line of the specification belongs to no entry, so the apparatus cannot finish while the body of the document has never been traversed.

Purpose: the partition (phase 5) already covers every line exactly once, and the census already requires every section to be entered or adjudicated. Neither says anything about the lines inside a section. A section is satisfied by a single entry that starts at its first line, so the union of entry spans may cover a fraction of the document and the run still passes. The one whole-document product the apparatus forces can therefore degenerate to a table of contents, and the reader is never asked about the lines between the entries.

Motivation, measured on this repository rather than asserted. `blocksFromHeadings` (rail/pins.mjs:296) reads only lines matching the heading pattern, so a complete partition is produced without reading one line of prose. `census-every-section-explained` (rail/engine.mjs:276) refuses only a section that no entry starts inside and no adjudication names. `coverageOf` reports `linesReached=N of M` and coverage.mjs states in its own header that nothing there is a pass condition. The golden fixture is the proof: over the 60 lines of ledger.md its four entries span 24-26, 34-35, 49-50 and 59-60, so 51 of 60 lines belong to no entry and every gate passes today. The manual campaign that motivated this rail read the whole specification and produced 185 rows; the rail run that was compared against it produced largely ungrounded steps. The rule this ticket adds is the one the design already states twice — census for sections, reach for operations — applied to the unit both of those are counted in.

Constraints. The rule is enforced by code, not by prose in the command file, because gates.mjs states that the command table is a summary of that module rather than a claim nothing evaluates. No record shape changes: `DECLARATION_SHAPE.entries` already carries `firstLine` and `lastLine` (rail/readings.mjs:35), so a region holding no sequence is recorded as an entry whose outcome is `notASequence`, which is visible and attackable rather than silent. The rule must exist on both verification surfaces — the phase driver and the product path — because run.mjs verifies through `checkAll` and never enters a phase gate. The golden fixture must be brought to the new standard in the same Red phase, or every suite that reads it turns red for the wrong reason.

## Scope

- rail/coverage.mjs — ADD `uncoveredRanges({ spans, lineCount })`, exported, built on the file's existing private `linesBetween` rather than a second range expansion. It returns the maximal contiguous runs of line numbers in 1..lineCount that lie inside no span, ascending, each `{ first, last }`. Before → after: the module measured only how much of the document was reached (`linesReached`); it now also answers which lines were not reached.
- rail/coverage.mjs — MODIFY the module header, which currently states "Nothing here is a pass condition". That sentence becomes false the moment `uncoveredRanges` exists: the counts are not pass conditions because a generation that merges two sequences is an improvement carrying a smaller number, but the line partition is categorical — a line is read or it is not, and the second is a defect in every generation. The header must state the distinction rather than keep a claim the code contradicts.
- rail/gates.mjs — MODIFY phase 5's exit gate (`id: 5`). After the existing partition checks it requires the declaration's entries to leave no line of 1..specLines uncovered, and refuses with `line N belongs to no entry, so nothing was read there`, naming the first uncovered line. The refusal travels the existing back-edge; `PHASE_EXPECTS[5]` carries the requirement to the reader. A new import of `uncoveredRanges` from coverage.mjs (no cycle: coverage.mjs imports nothing local).
- rail/checks.mjs — ADD the ninth constructor `coverEveryLine(contract, { spans, lineCount, label })`: one verdict per uncovered range, so the number of verdicts is bounded by the number of declared spans plus one rather than by the number of unread lines (a 14,000-line gap must not produce 14,000 verdicts). Added to the library rather than hand-rolled in engine.mjs, so the rule that a check is built from a declared shape still holds for the ninth shape.
- rail/engine.mjs — ADD the check `every-line-belongs-to-an-entry`, built from `coverEveryLine`, refusing "a line of the specification that no entry spans, so the body of the document was never read" and scoped to "every artifact, over its sequences and its specification line count". `ENGINE_DECLARED_CHECK_COUNT` follows from `CHECKS.length` and becomes 21 without a second statement of the number.
- rail/phases.mjs — MODIFY `PHASE_EXPECTS[5]` to name the coverage requirement beside the sections, and `PHASE_GUIDANCE[5]` to instruct the reader to name an entry for every line of every section, so no line is left to nobody. This is the channel by which a reader learns what the phase will accept.
- tests/educe-sequences/fixtures/spec/ledger.run.json and ledger-sequences.json — MODIFY so the entries tile 1..60: the four existing entries keep their spans unchanged (widening an entry changes what the span brief asks and what `step-cites-a-line-inside-its-entry-span` permits), and the uncovered runs are covered by new entries whose outcome is `notASequence` and whose ruling carries `predicateLimb: "none-applies"`. This is the mechanic demonstrated in the fixture rather than only asserted in a unit test.
- tests/educe-sequences/line-coverage.test.mjs — ADD the suite. It is written first, in the Red phase, and every test in it fails before the implementation exists.
- tests/educe-sequences/adhoc-run.test.mjs — MODIFY the two literal counts: the assertion that `ENGINE_DECLARED_CHECK_COUNT` is 20 and the assertion that the driver prints `checksRun=20 of 20`, both to 21.
- docs/EDUCE-SEQUENCES-DESIGN.md — MODIFY the stated count at line 112 ("reports 20 checks over 5 pins") to 21, add the paragraph describing the new check and the defect that produced it, and state what the apparatus can and cannot require of a reading: a line may not be left to nobody, but a claim about a line is still a claim.
- .claude/commands/educe-sequences.md — MODIFY Step 5's text and the phase table's row for phase 5, as the summary of gates.mjs rather than as a second statement of the rule.
- NOT changed: rail/artifact-schema.json. The rule reads `sequences[].firstLine/lastLine`, which the schema already requires, so no artifact gains a field and no existing artifact becomes structurally invalid for this reason.
- NOT changed: tests/educe-sequences/fixtures/gaia/. It is consumed by the corpus measurement only (file count and total bytes, tests/conventions/design-measurements.test.mjs:181-187), and `checkAll` is never run over it, so the new check does not touch it.
- Impact: 38 `checkAll` call sites across 16 test files read the golden artifact, so the fixture change carries most of them. Tests that hand-build an artifact with non-tiling sequences (checks, engine, positions, step-grounding, predicate, inquest, coverage) must be brought to the new standard in the same Red phase, and a test that asserts "and the artifact is otherwise whole" will now fail unless its artifact tiles.

## Investigation

Measured in this repository, by reading the source rather than the design's description of it.

- The defect, measured: the golden fixture `tests/educe-sequences/fixtures/spec/ledger-sequences.json` declares four sequences over the 60 lines of ledger.md — `admission` 24-26 (entry, direct), `settlement` 34-35 (entry, viaNeighbour), `settlement-replays-admission` 49-50 (neighbour), `non-operation` 59-60 (neighbour). 51 of 60 lines lie inside no sequence, and `checkAll` returns no verdict over that artifact today.
- The partition cannot close the gap by itself: `blocksFromHeadings` (rail/pins.mjs:296) matches only lines beginning with the heading pattern, so it reads no prose. It also begins at the first heading at the declared level, so in the fixture the partition covers 3-60 and lines 1-2 lie in no block at all; phase 5's gate checks only that the last block ends at `specLines`, never that the first begins at 1.
- The census is at section granularity: `census-every-section-explained` (rail/engine.mjs:276) refuses "a section no entry starts inside and no adjudication names", so an entry that starts inside a section satisfies it however little of the section it spans.
- The record already exists: `DECLARATION_SHAPE.entries = ['id', 'kind', 'firstLine', 'lastLine']` (rail/readings.mjs:35), and `buildWorklist` (rail/reading.mjs:213) turns an entry into the worklist line `id span first-last` that the span brief is dispatched from. A rule over entry spans therefore needs no schema change.
- Two verification surfaces exist and must agree: `run.mjs` verifies through `checkAll` (rail/run.mjs:95, :126) and never enters a phase gate, while the phase driver evaluates gates in gates.mjs; phase 9's gate is the only one that calls `checkAll` today.
- The check registry derives its count from the array: `ENGINE_DECLARED_CHECK_COUNT = CHECKS.length` (rail/engine.mjs:436), and the design document's number is held to it by `tests/conventions/design-measurements.test.mjs:191-196`, which reads `docs/EDUCE-SEQUENCES-DESIGN.md` line 112 ("reports 20 checks over 5 pins"). Two literals elsewhere state the same number: `tests/educe-sequences/adhoc-run.test.mjs:200` and the `checksRun=20 of 20` expectation at :498.
- Blast radius, counted: 38 `checkAll` call sites across 16 test files, nearly all reading the golden artifact, so the fixture carries most of them; direct `entries:` writers are pins, readings, inquest and positions.
- The gaia corpus under `tests/educe-sequences/fixtures/gaia/` (1,069,541-byte specification, 485 manifest rows, 614 step rows) is consumed only by the corpus measurement, which reads MANIFEST.json for a file count and a byte total; `checkAll` is never run over it, so the new check does not touch it.

## Acceptance Criteria

- Happy path: `node --test` over the educe-sequences and conventions impact sets is green; `run.mjs` over the golden fixture reports `checksRun=21 of 21` with no verdicts; `phase.mjs run <spec> 5` passes on a declaration whose entries tile the document; the golden artifact's `linesReached` equals its `specLines`.
- Error case: a declaration leaving line 4 uncovered makes `phase.mjs run <spec> 5` exit 1 and print `line 4 belongs to no entry, so nothing was read there` with the back-edge and the file to produce; `checkAll` over the same artifact returns the check `every-line-belongs-to-an-entry` with a null summary; `run.mjs` writes nothing and exits non-zero.
- Edge case: the measurement that states the defect before the change — 51 of the golden fixture's 60 lines belong to no entry — is 0 after it, and a document whose body precedes its first heading is still fully covered because the preamble is inside the rule.

## Invariants

- Normal establishment: for every artifact over which `checkAll` returns no verdicts, the union of the spans of its sequences covers every line 1..specLines, and a phase-5 PASS implies the same of the declaration it read.
- Invariant on error: a gap produces exactly one verdict per uncovered range with `summary` null, and the phase-5 refusal names the first uncovered line rather than a count; a run that fails this rule writes no artifact and leaves the previous one byte-identical.
- Internal invariant: one implementation of the rule (`uncoveredRanges`) is read by both the gate and the check, so the two verification surfaces cannot disagree about which line is unread.
- Boundary invariant: the rule is stated over the document, not over the partition, so a line before the first heading at the declared level is inside the rule even though the block partition does not reach it; and a span that is malformed covers no line rather than raising.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — PX-247 every line belongs to an entry — the range rule

- **Precondition**: `uncoveredRanges({ spans, lineCount })` where `spans` is a list of `{ firstLine, lastLine }` and `lineCount` is a positive integer; a span whose ends are not integers, or whose `lastLine < firstLine`, is malformed
- **Postcondition**: returns the maximal contiguous runs of line numbers in `1..lineCount` that lie inside no span, ascending, each `{ first, last }`; returns `[]` when every line is covered; never throws for a malformed span, which contributes no coverage
- **Invariant**: the returned ranges are pairwise non-adjacent and non-overlapping, every line they name is inside no span, and the ranges together with the spans' intersection with `1..lineCount` are exactly `1..lineCount`

### C002 — PX-247 every line belongs to an entry — the phase-5 gate

- **Precondition**: a run whose declaration carries `entries[]` with integer `firstLine` and `lastLine`, over a specification of `specLines.length` lines
- **Postcondition**: `phase.mjs run <spec> 5` exits 0 when the entries leave no line uncovered, and exits 1 with `line N belongs to no entry, so nothing was read there` naming the first uncovered line when they do, together with the back-edge and the file the reader must produce
- **Invariant**: a phase-5 PASS implies the union of the entry spans covers every line of `1..specLines`, including any line preceding the first heading at the declared level

### C003 — PX-247 every line belongs to an entry — the check, on both surfaces

- **Precondition**: an artifact whose `sequences` leave at least one line of `1..artifact.spec.lines` uncovered, passed to `checkAll` with the specification's lines
- **Postcondition**: `checkAll` returns one verdict per uncovered range with `check === "every-line-belongs-to-an-entry"` and a reason naming that range, and `summary === null`; `run.mjs` over the same specification exits non-zero and writes nothing
- **Invariant**: every artifact over which `checkAll` returns no verdicts has the union of its sequence spans covering `1..spec.lines`, and the first line named by the check equals the first line named by the phase-5 refusal for the same artifact

### C004 — PX-247 every line belongs to an entry — the fixture and the stated count

- **Precondition**: the golden fixture pair `ledger.run.json` and `ledger-sequences.json` over the 60 lines of `ledger.md`, and the design document's stated check count
- **Postcondition**: the golden artifact's sequences tile `1..60`, `checkAll` over it returns no verdicts, `ENGINE_DECLARED_CHECK_COUNT === CHECKS.length === 21`, and the design document states `21 checks over 5 pins` so `design-measurements` passes
- **Invariant**: the number the document states equals `CHECKS.length`, and the fixture's pre-change measurement of unread lines (51 of 60) is 0 after the change

## Boy Scout Rule

Translatability plan for the code this ticket touches.

- Function names are verb phrases: `uncoveredRanges` answers "which lines are uncovered", `coverEveryLine` builds a check that covers every line, and the check id reads as the rule it states.
- One responsibility per function: `uncoveredRanges` computes ranges and judges nothing; the gate decides what a gap means for the phase; the check decides what it means for an artifact. The two callers share the computation and state their own refusals.
- No duplication: the range expansion is the existing private `linesBetween` in coverage.mjs, which is exported to `uncoveredRanges` rather than copied; the number of checks is derived from `CHECKS.length` rather than restated.
- No magic values: the check id and the refusal wording are named where the other check ids are named, in the check's contract, rather than typed at the call site.
- A false comment is corrected rather than left: coverage.mjs's header claims nothing in the module is a pass condition, and this change makes that claim false; the header is rewritten to state which of the two things it holds is categorical and which is a measurement.
- A comment is added where the code cannot say why: the gate states why the rule is over `1..specLines` and not over the partition (a preamble lies outside the partition and inside the document).

### Exceptions

- Item: the thoroughness of a reading — that a reader actually read a line. Reason: this is impossible to test, because the reading happens outside the apparatus, in a reader, and the gate can inspect only the shape and the signature of what came back, which gates.mjs states as the boundary of the `[read]` tag; no input the rail can construct contains the act of reading. This is not a design defect: the subject itself is a reader's act, so no redesign of this rail makes it observable, and the design's answer is to make every consequence of a reading checkable instead. This ticket adds one more such consequence — the line partition — so the unverifiable part shrinks rather than being exempted. Alternative verification: constructing declarations that leave a gap and asserting the phase-5 refusal and the check verdict, which is the strongest statement the apparatus can make about a line, plus the phase-10 adversarial pass, which attacks every `notASequence` ruling and therefore every entry this ticket adds to the fixture.
- Item: the width at which one entry's span stops being credible. Reason: the numeric bound is not testable, because no threshold has been measured and a test asserting an arbitrary constant would test the constant rather than the behaviour; the design's own position is that the number comes from the first run that produces a wide span. This is not a design defect: the testable part of the property — that a wide span is visible, named and attackable — is tested, and only the numeric bound is absent, which is a missing measurement rather than a missing design. Alternative verification: recorded as a residual carried forward from PX-246, attacked by the adversarial pass at phase 10 and re-asked by the inquest each generation; the bound is added when a run produces a span wide enough to measure.

- UT: [Normal | Boundary | Invariant] C001 — uncoveredRanges returns the runs of lines no span reaches, and raises for nothing
```js
import { uncoveredRanges } from '../../.claude/scripts/educe-sequences/rail/coverage.mjs';

// Precondition: spans carrying integer ends, lineCount a positive integer.
const spans = [{ firstLine: 1, lastLine: 3 }, { firstLine: 6, lastLine: 8 }];

// Postcondition: the maximal contiguous uncovered runs, ascending, one range per gap.
assert.deepEqual(uncoveredRanges({ spans, lineCount: 8 }), [{ first: 4, last: 5 }]);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: 1, lastLine: 8 }], lineCount: 8 }), []);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: 3, lastLine: 4 }, { firstLine: 5, lastLine: 6 }], lineCount: 6 }), [{ first: 1, last: 2 }]);

// Boundary: no spans at all is one range over the whole document; a span reaching
// past the end or starting below line 1 names only lines inside the document; a
// malformed span covers nothing rather than throwing.
assert.deepEqual(uncoveredRanges({ spans: [], lineCount: 3 }), [{ first: 1, last: 3 }]);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: 2, lastLine: 99 }], lineCount: 4 }), [{ first: 1, last: 1 }]);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: -5, lastLine: 2 }], lineCount: 4 }), [{ first: 3, last: 4 }]);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: 'x', lastLine: 8 }], lineCount: 3 }), [{ first: 1, last: 3 }]);
assert.deepEqual(uncoveredRanges({ spans: [{ firstLine: 5, lastLine: 2 }], lineCount: 3 }), [{ first: 1, last: 3 }]);

// Invariant: every line the ranges name lies inside no span, and the ranges are
// never adjacent to one another, because two adjacent ranges would be one range.
const covered = new Set();
for (const span of spans) for (let line = span.firstLine; line <= span.lastLine; line += 1) covered.add(line);
const ranges = uncoveredRanges({ spans, lineCount: 8 });
for (const range of ranges) {
  assert.equal(range.last >= range.first, true);
  for (let line = range.first; line <= range.last; line += 1) assert.equal(covered.has(line), false);
}
for (let index = 1; index < ranges.length; index += 1) assert.equal(ranges[index].first > ranges[index - 1].last + 1, true);
```

- Widening an existing entry's span to cover a gap is the wrong repair and must not be used in the fixture: it changes what the span brief asks, and `step-cites-a-line-inside-its-entry-span` permits a line only inside its entry's own span, so a widened entry silently legalises a step that was previously refused. Gaps are covered by new entries adjudicated `notASequence`.
- A new gap entry with no outcome is refused by `entriesWithoutOutcome` at phase 12, so each one must carry an adjudication with `predicateLimb` naming a declared limb or `none-applies`; omitting it turns a coverage fix into a phase-12 refusal.
- The rule is checked in two places, and a change made in only one of them is invisible in the direction that matters: a driver-only rule lets `run.mjs` accept an artifact the driver refuses, which is the failure this ticket exists to prevent.

Caveats:
- The rule makes an unread line impossible to leave silent. It does not make one impossible to claim: a single entry spanning the whole document, ruled `notASequence`, satisfies phase 5.
