# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Boy Scout Rule

Function names: `extractMembersFromSource` (verb phrase, returns the member set for one selector), `rederiveSourceEnumeration`, `borrowedEnumerationOf`, `escapedOperationsOf`, `renderSequenceDiagram`, `diagramParticipantsOf`. Every new function is a verb phrase whose name says which of the two questions it answers.

One function, one responsibility: `rederiveEnumeration` keeps its rule over the specification's lines, and the sourced rule is a separate function reached through `rederivePin`'s dispatch, rather than one function with an `if (pin.source)` branch — the same split the file already uses for `rederivePredicate`, `rederiveRowSchema` and `rederiveBlocks`. `renderArtifact` gains `renderSequenceDiagram` and `renderPinsBlock` so the page is assembled from named blocks instead of one array literal.

Variable names as domain concepts: `members`, `selector`, `suppliedDocuments`, `operationsEnumerated`, `operationsReached`, `operationsExcused`, `escapedOperations`, `borrowedCensus` — no `data`, `info`, `tmp` or single letters.

Hardcoded values into named constants: `SOURCE_SELECTORS`, `SOURCE_ENUMERATION` (the rule name), `COLUMN_DECIDERS`, `REQUIRED_MEASURED_COLUMNS`, `ESCAPE_SUBJECT_CLASS`. The literal `['suppliedRule', 'excluded']` already has a name (`UNREACHED_ESCAPES`) and the new code reads it rather than repeating it.

No swallowed errors: an unreadable supplied file refuses naming the file rather than degrading to an empty member set, because an empty denominator would silently make every artifact complete. The defaulted `supplied = {}` is not a swallow — it is the state a run with no material is in, and a pin that borrows nothing never consults it.

Proactive improvement of existing code touched here: `run.mjs:151`'s promise gains the module it names, `engine.mjs`'s registry stays the single declaration of the check count, and `harness.mjs:387`'s page gains structure rather than an ever-longer array literal.

### Exceptions

- Whether a reader's escape for an enumerated operation is honest is impossible to test: the apparatus may propose candidates and may never decide, so no check can open a line and rule that the exclusion stated there is wrong. This is not a design defect and not a defect of this ticket — it is the boundary the whole check library is built on (engine.mjs header). The mitigation this ticket adds is that an escape is no longer free: it costs a line inside the specification, an attack at phase 10 and four grounded answers at phase 13, on every generation. Alternative verification: the fixture carries one escaped operation and one escaped entry, and phase 10 and phase 13 are asserted to refuse while either is unattacked or unanswered.
- Whether the borrowed census is itself complete relative to the specification is not testable from inside the rail: `check-registry.mjs` is supplied material, and material may never be executed as an instruction, so the rail cannot run the checker and cannot read its exit code as a proof. This is not a design defect — it is the first half of the material rule, which this ticket must not break. Alternative verification: `provenBy` refuses a borrowed enumeration that names no checker, and the checker's result is recorded as a signed reading that phase 10 attacks, so a naked denominator can never stand. The residual is written into the design document as a condition.
- Whether a third generation's coverage rises is not testable in this repository's suite: it depends on a run over `~/shyme/gaia`, which is outside this repository and which no test may write to. This is not a design defect — the fixture is the repeatable surface and the gaia run is the acceptance the ticket states. Alternative verification: the fixture's borrowed registry carries more members than its golden artifact declares in one revision, so the fixture reproduces the refusal and its repair, and the coverage line is asserted to move from the lower to the higher number across the two fixture generations.

- 【Risks】The largest is scale: the fixture is 60 lines while a real specification can be tens of thousands, and a supplied registry can be megabytes. The extraction must run once per run and be handed into the check context as a value, never re-read per check and never re-read per mutation case — `harness.mjs`'s corpus calls `checkAll` fourteen times, and `engine.mjs:184` already states the rule that answers are handed in rather than looked up. Second: adding subjects to the inquest multiplies its records, so the scope must be the escapes alone, never every declared operation.
- 【Caveats】The extraction is whole-file by construction, and that is load-bearing: a section pointer is the one way a denominator narrows without failing. Totality is the second half of the same rule — an element an extractor cannot read refuses rather than contributing nothing, which is what stops a wrong field or column from narrowing in silence. The entry census is checked for identity only, never for agreement with the artifact's outcome, because comparing them would make the rail decide which adjudication is right.
- 【Open items】Two conditions are written into the design rather than solved. First, the borrowed census's own completeness depends on whatever instrument proved it, which the rail cannot execute and must not pretend to; `provenBy` refuses a naked denominator and the instrument's result is recorded as an attacked reading. Second, keeping the number at zero requires re-running, and the trigger is outside the rail.
- 【Future improvements】A second project with a different registry shape needs a new entry in `SOURCE_SHAPES` and nothing else; the shapes are the extension point. The deciders for the remaining conformance columns are the next layer, and the column-class machinery this ticket adds is what will hold them: a column with no decider must say so, and a column the caller requires may not.
- 【Genericity】The constraint that the rail must serve any project, not the one that motivated it, changes two things from the design as first written. The extraction is a small vocabulary of generic shapes — a field of every JSON row, a column of every table row, the remainder of every marked line — each parameterised by declaration data, rather than two named extractors for one project's registry format; and the columns that must be measured are declaration data rather than a constant naming three transports. Both changes make the rule stronger, because a single totality rule ("an element the extractor cannot read refuses naming it") now closes silent narrowing for every shape at once, and C007 makes the absence of project vocabulary a test rather than a promise.
- 【Frozen corpus】The gaia corpus already exists under `tests/educe-sequences/fixtures/gaia/` and is held to a manifest by C006 and to the design document's stated size by `design-measurements`. This ticket reads it and does not extend it: the fixture's borrowed census uses a synthetic supplied document under `fixtures/spec/supplied/`, which is outside every manifest.

Decisions taken during implementation, recorded because they are not in the plan:
- The generic extraction shapes are total over the elements they claim — a JSON block whose first row is an object, a table under a header naming the column, a document that is a list and nothing else — and an element the extractor cannot read refuses naming that element. Totality is what closes silent narrowing for every shape at once: a wrong field, a wrong column or a truncated file fails loudly instead of shrinking the denominator.
- The borrowed pin kind has its own `pinCheck`, so the correspondence between pin kinds and pin checks holds and `checkAll` re-derives a census even when a caller does not call `rederiveAll` separately. The check reads the supplied documents from the context, never from the filesystem: a check that reached for a file would be deciding by looking around it.
- `agreeOn` gained `when`, because a set nobody supplied is not a set that disagrees with everything: without it the two directions read an absent census as every name in the artifact having left it. It also gained a `direction` on each verdict, because the two directions are different findings and one shape without the direction would make them indistinguishable except by prose.
