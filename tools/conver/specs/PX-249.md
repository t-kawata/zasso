# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-249: Draw every sequence: alias the participants, encode the two characters Mermaid cannot carry, and write a rendering only from a verification that passed

**Ticket Key**: PX-249 · **Phase**: -1

## Background

**Goal.** `*-sequences.json` must be complete enough that every sequence it declares can be drawn mechanically into a sequence diagram carrying every step, each step being an operation — so that the list of operations the REST / WebSocket / CLI interfaces must implement can be planned from the artifact with no omission, and a missing implementation cannot make a sequence unrunnable.

**Purpose.** The artifact is the denominator of the operation list. A diagram that a machine can draw from it is the cheapest proof that the record is whole: a diagram needs a participant on each side of every message, so a step naming no actor or no target is a gap in the record and not a rendering detail.

**Motivation, measured.** `rail/render.mjs` runs today and draws. Measured against mermaid 12.0: (1) the emitter writes participant names into the identifier position, where the sequence lexer refuses `,` and `:` — so of the 68 diagrams the real artifact at `~/shyme/gaia/GaiaSekkeiShiyousho_v32-sequences.json` produces, 51 parse and 17 do not; (2) `;` anywhere in a participant name or a message fails the parse and `#` is silently lost together with everything after it, in both positions, and neither is escaped; (3) `render.mjs` writes the rendering without running any check, so the same artifact emits `[null]` 472 times where a step carries no operation; (4) the drawability check's denominator is the sequences that claim to be a sequence, so a step attached to a region ruled `notASequence` lies outside it and is drawn by nothing.

**Constraints.** Nothing under `~/shyme/gaia` may be written — the artifact there is evidence and the specification is inviolable. The rail ships no runtime dependency and its tests run under bare `node --test`, so the encoding rule is pinned by measurement and by test rather than by parsing the output with mermaid. No project vocabulary may enter the rail: the alias, the escape table and the new check name nothing that belongs to a project.

## Investigation

Measured against mermaid 12.0 with `mermaid.parse` and `mermaid.render` under `jsdom` with a `getBBox` polyfill, over every printable ASCII code point (U+0020 to U+007E) plus U+00A0, U+00E9, U+200B, U+2028, U+2029, U+3000, U+FEFF and U+1F600, in the alias position and in the message position.

The identifier position and the alias position are not the same grammar. A bare `participant <name>` refuses `,` `:` `;` `+` `>` `<` `@`; the alias position `participant P as <name>` refuses only `;`, and the message position refuses only `;`. In both variable positions `#` parses but is silently dropped together with everything after it, and a newline fails the parse. A corrected XML decoder showed `<`, `>` and U+00A0 to be false alarms of an earlier, incomplete measurement, so the escape set is exactly `#` and `;`. `#35;` and `#59;` decode back to `#` and `;` in the rendered SVG.

The real artifact at `~/shyme/gaia/GaiaSekkeiShiyousho_v32-sequences.json` (read only, 569709 bytes, schema_version 2) holds 375 sequences and 663 steps: 67 `direct`, 1 `viaNeighbour`, 307 `notASequence`. Rendering it produced 68 diagrams of which 51 parsed and 17 did not: 15 carry a comma in a participant line and 1 a colon. 472 of the 663 steps carry no `operation`, and the rendering writes `[null]` for each of them. Of the 68 sequences that claim to be a sequence, `every-sequence-is-drawable` would accept 1 and refuse 67 — the check exists and had never been applied to that artifact, because it was generated before the check did.

Read in the rail: `renderSequenceDiagram` at `rail/harness.mjs:397` writes `participant ${name}` and `${step.subject}->>${step.object}` with no alias and no encoding; `renderArtifact` at `rail/harness.mjs:414` draws the sequences whose outcome is in `DIAGRAMMED_OUTCOMES`; `DIAGRAMMED_OUTCOMES` at `rail/engine.mjs:49` is the schema's outcomes minus `notASequence` and `exempt`; `every-sequence-is-drawable` at `rail/engine.mjs:192` takes its sources from that same filter, which is why a step on a `notASequence` entry is outside its denominator; `renderCommand` in `rail/render.mjs` writes with no check at all, while `run.mjs:64-115` performs the verification that `render.mjs` lacks. `coverEvery(contract, { sources, coveredBy, label })` at `rail/checks.mjs:163` is the constructor the new check is built from, so no new shape is introduced.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — PX-249 drawable sequences — the encoding is total and measured

- **Precondition**: `encodeForDiagram(text)` over any string the artifact can hold as `entry.id`, `step.subject`, `step.object`, `step.predicate` or `step.operation`; `MERMAID_ESCAPES` is the frozen map `{ "#": "#35;", ";": "#59;" }`.
- **Postcondition**: The result collapses every run of whitespace to a single space and replaces each `#` with `#35;` and each `;` with `#59;` in one pass, so no `#` introduced by escaping a `;` is escaped a second time; the function never raises, including on the empty string.
- **Invariant**: The escape set is exactly the set measured to be unusable: over every printable ASCII code point and the Unicode whitespace and astral samples, mermaid 12.0 refuses the parse on `;` and silently drops `#` with everything after it, in both the alias and the message position, and alters no other character. A character outside the escape set is therefore carried literally, and the measurement is what the set rests on rather than an assumption.

### C002 — PX-249 drawable sequences — no name reaches the identifier position

- **Precondition**: `renderSequenceDiagram(entry, steps)` over a sequence whose steps carry `subject`, `object`, `predicate` and `operation`, with the participant set taken from `subject` and `object` in step order and the empty and non-string names removed.
- **Postcondition**: Each participant is declared as `participant P<n> as <encodeForDiagram(name)>` with `n` assigned by first appearance, and each step is a message `P<subject>->>P<object>: <encodeForDiagram(predicate)> [<encodeForDiagram(operation)>]`; the number of message lines equals `steps.length`, their order is the artifact's step order, and every identifier used is declared in the same block.
- **Invariant**: The identifier position holds only `P<n>`, so the lexer never sees a name and the diagram is well formed for any name the artifact can hold; a name is carried exactly once, in its `as` clause, and the block is a fenced `mermaid` block whose first content line is `sequenceDiagram`, so a name can neither break the diagram nor escape the fence.

### C003 — PX-249 drawable sequences — every step is in a drawn sequence

- **Precondition**: `checkAll({ specLines, artifact })` over an artifact whose `sequences` carry `outcome` and whose `steps` carry `sequence`.
- **Postcondition**: `every-step-belongs-to-a-drawn-sequence` raises one verdict per step whose sequence names no entry, or names an entry whose outcome is not in `DIAGRAMMED_OUTCOMES`, labelling the verdict with the step id and refusing in the contract's words; a step whose sequence is drawn raises none.
- **Invariant**: The drawability check's denominator is the sequences that claim to be a sequence, so a step attached to a region ruled `notASequence` lies outside it and is drawn by nothing; this check is the other half of the same rule and together they say that every step appears in exactly one diagram — that one asks whether every drawn sequence can be drawn, this one asks whether every step was given a sequence that can be.

### C004 — PX-249 drawable sequences — the rendering is written only from a verification that passed

- **Precondition**: `renderCommand(argv)` with one argument naming an existing specification, an artifact beside it, and the checks loaded from the run directory as `run.mjs` loads them.
- **Postcondition**: The command returns `RENDER_EXIT.OK` and writes `renderPathFor(specPath)` only when the specification digest, the line count, the supplied digest, every pin re-derivation and every check pass; otherwise it returns `RENDER_EXIT.REFUSED` with `renderingPath: null` and a reason naming the first refusal, and writes nothing.
- **Invariant**: The rendering is a product artifact like the artifact itself, so it is held to the same gate: a picture drawn from records nothing has checked is the fabrication this command exists to catch, and it is the harder one to notice because it looks complete. A refused rendering leaves the rendering path byte-identical, and no path writes a rendering from an artifact whose specification has moved.

### C005 — PX-249 drawable sequences — one verification, two product surfaces

- **Precondition**: `verifyArtifact(specPath, options)` extracted from `run.mjs`, returning `{ artifact, summary, refused }` where `refused` is `null` or the first refusal in the shape each surface already prints.
- **Postcondition**: `run.mjs` and `render.mjs` both call it, and for the same defect over the same fixture they refuse with the same rule and the same subject; `run.mjs`'s behaviour over the four run shapes is unchanged.
- **Invariant**: The block appears once in the source, so a later edit to the verification reaches both surfaces or neither; the extraction is behaviour-preserving, asserted by driving both product paths over the same fixture and comparing the acceptance and the refusal.

### C006 — PX-249 drawable sequences — the instrument carries no project's vocabulary

- **Precondition**: Every module beneath `.claude/scripts/educe-sequences/rail/` and every brief beneath `.claude/scripts/educe-sequences/briefs/`, read as text, after the change.
- **Postcondition**: The existing project-token scan reports nothing, so the new constant, the encoder, the check id and the new comments name no project file, no project operation, no project path and no transport word.
- **Invariant**: No project value reaches the rail except as a declaration field or as supplied material, so a second project with different actor names — including names carrying a comma, a colon or a semicolon — draws the same way with no code change.

## Boy Scout Rule

Translatability plan for the touched code.

- Function names: `encodeForDiagram` is a verb phrase naming what it does to the text; `verifyArtifact` names the verification it performs, so `run.mjs` and `render.mjs` each read as one sentence around it.
- Constants: the two escapes become `MERMAID_ESCAPES` and the three fields a message is drawn from become `DIAGRAM_FIELDS`, so neither the renderer nor the check carries a literal list; the inline `["subject", "object", "operation"]` at `engine.mjs:197` is what this removes.
- One responsibility per unit: the encoder encodes, the renderer projects, the check decides. The renderer keeps its existing comment saying it is a projection and not a decision, and the alias rule is the reason that division can hold for any name.
- No swallowed errors: `renderCommand` returns a refusal naming the first failure rather than writing a rendering it could not verify, so the failure reaches the caller instead of a file nobody re-reads.
- Outside scope, found while reading: `renderSequenceDiagram` filtered non-string names while still emitting a message for them, which produced `undefined->>...`; the alias rewrite assigns identifiers from the filtered set and `every-sequence-is-drawable` is the rule that refuses such a step, so the renderer no longer has to guess. Recorded here rather than fixed silently because it changes what a malformed artifact renders as.
