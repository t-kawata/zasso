# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-250: Render a sequence artifact to text: list it, draw it, and print the Mermaid it was drawn from

**Ticket Key**: PX-250 · **Phase**: -1

---

## Background

Goal: a reader holding a <spec>-sequences.json can see which sequences it holds, and read any chosen one as a diagram at a console, with no browser, no SVG and no network.

Purpose: the artifact already carries every field a sequence diagram needs, and the rail already emits Mermaid from them into <spec>-sequences.md. That rendering is a file beside the specification, so a reader at a console cannot see it. Nothing in the tool prints a diagram, and the 68 drawable sequences of the GaiaSekkeiShiyousho_v32 artifact have never been looked at by a human.

Motivation: the request this ticket answers, in three parts — list the sequences; render chosen ones to the console as ASCII; print the raw Mermaid for chosen ones.

Constraints:
- The rail keeps its zero-dependency property. text.mjs is a separate surface and is never a phase, so node --test over the rail still runs with nothing installed.
- The dependency is installed by install.js the way ajv and sql.js already are: one declaration in .claude/package.json, no new mechanism. The request states this directly — follow the method install.js already has.
- The three outputs come from one generator, so a printed diagram and a printed Mermaid can never disagree.
- Measured before the design rather than after. beautiful-mermaid@1.1.3 renders the rail sequenceDiagram source: all 68 drawable sequences of the real artifact, none refused. It widens rather than wraps, so a 160-character message yields 180 columns. It renders a br element inside a message as a line break, which is the fold the width budget uses: the same message went from 143 columns to 64. The install footprint is about 11MB (beautiful-mermaid 2.5M, elkjs 7.7M, entities 684K).

## Invariants

- Normal establishment: after the change, renderSequenceDiagram returns the same bytes it returned before it, and renderArtifact over the golden census artifact equals the committed ledger-sequences.md byte for byte.
- Invariant on error: an invocation that refuses — an unknown id, neither mode given, --mermaid with --width, an artifact that does not exist — writes nothing to stdout and exits non-zero. A refusal is never a partial rendering, and an empty result is never how a failure reads.

## Boy Scout Rule

install-deps.cjs: the plan values are string literals repeated across classifyDependencyAction and resolveTargetDependencies. They become one frozen constant, so a typo in a comparison is a reference error rather than a silently unmatched branch, and the new install-missing value joins the same constant rather than starting a parallel mechanism.
install.js: summaryByStatus is a lookup keyed by the plan union. The new key is added, and a test drives the report with every value of the constant so a future plan cannot be added without its sentence — the failure this map would otherwise produce is an undefined line printed to the user.
harness.mjs: the extraction separates the participant-identifier assignment and the message formatting from the fence. While there, the two filters become a named predicate — a participant is a name that is a non-empty string — so the rule reads as a rule rather than as two inline conditions.
.claude/commands/educe-sequences.md: Step 17 names the product path and stops. It gains the three console commands in the same voice the rest of the file uses, so the surface is discoverable from the procedure and not only from the source.
text.mjs: every refusal returns a reason and a non-zero exit rather than printing nothing, so no error is swallowed. The usage line is generated from the accepted option list rather than typed, so an option cannot be added without appearing in it.
No new hardcoded value is introduced: the width floor, the default budget and the fold separator are named constants, and the separator is the one the measurement showed the library renders as a line break.

const messages = golden().steps.map((step) => `${step.predicate} [${step.operation}]`);

Two design flaws were found by measurement during implementation, not by reasoning, and both changed the design.

First, the planned verdict was "every top-level package in node_modules is declared by the manifest". Measured against this repository .claude, that test fails on a tree that is exactly right: it holds ajv, sql.js and four packages no manifest names, because they are the dependencies of ajv. The verdict was rebuilt around the closure of the declared set, and the test now pins two trees differing only in whether ajv declares the package beside it.

Second, --width was planned as a message budget. Measured through the library over the 68 drawable sequences of GaiaSekkeiShiyousho_v32-sequences.json, it is not: the library spaces lifelines to fit the widest message rather than breaking it, so a 25-participant sequence is 272 columns with messages folded to 6, 430 at 20 and 951 at 80. The budget was moved to the drawing and the drawn mode now narrows the message budget and re-measures the rendering until it fits. At a requested 80 columns the widest of the 68 falls from 951 to 294; 28 remain wider than 80, which is the participant count rather than the messages, and the command prints those and reports the width it reached.

A third flaw was found while writing the new failure path: the rollback removed targetClaudeDir/node_modules unconditionally, so a failed install into a tree that already existed would have deleted it. The rollback is now gated on the plan being the one where this module created the tree, and a test drives a failed install over a pre-existing tree.
