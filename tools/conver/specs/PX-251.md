# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

Goal: the measured line that `/educe-sequences` prints must answer, for any project, how many sequences the specification yields, what composes them, and how many operations an interface must implement — so an implementer can see the surface they must build without reading the artifact by hand.

Purpose: repair a mislabelling defect measured on 2026-10-09 in a consumer (`~/shyme/gaia`). The product path (`rail/run.mjs`, function `report`) printed `sequences=553 steps=283 operations=257 rows=292 linesReached=15971 of 15971` for `GaiaSekkeiShiyousho_v32`. `sequences` was the entry ledger: `artifact.sequences[]` holds 553 records of which 68 claim a sequence and 485 are ruled `notASequence` — the rail *requires* entries to outnumber sequences, because `every-line-belongs-to-an-entry` makes every line of the specification belong to some entry. `operations` counted 257 records of which 109 (`suppliedRule` 10, `excluded` 99) record that the operation must *not* be implemented. `rows` named the heading partition under a word that maps to nothing a reader can check.

Motivation: the run completed 18 of 18 phases and every declared check passed, because these counts are measured and never gated — `coverage.mjs` states it at the head of the file ("The counts are not a pass condition"), and the design document repeats it ("Nothing compares one of these to a threshold"). A wrong number that reads as right therefore survives every gate, and this one survived three generations. The human read `sequences=553`, compared it with `operations=257`, and asked how a bundle of operations can outnumber its members. Nothing in the output answered, and the frozen golden fixture proves the defect is the report's rather than the specification's: `tests/educe-sequences/fixtures/spec/ledger-sequences.json` holds 8 entries of which 2 claim a sequence, and the product path already prints `sequences=8` for it.

Constraints:
- The fix must be generic and must succeed for every project. `tests/educe-sequences/genericity.test.mjs` (C007) reads every module under `rail/` and every file under `briefs/` and refuses a project token; it must pass unmodified. - The artifact's `sequences` section is not renamed. It is read at about 25 sites across twelve modules, it is a required section of `rail/artifact-schema.json`, and renaming it would change every project's artifact digest for a cosmetic gain.
- Scope is this repository. The consumer receives the change only through `make install-to-projects`, and nothing under `~/shyme/gaia` is edited.

## Invariants

- 【Normal establishment】After the change, `coverageLine(coverageOf(artifact))` names one set per term and each term's number is the size of the set its word denotes: `entries` is `artifact.sequences.length`, `sequences` is the entries whose `outcome` is in `DIAGRAMMED_OUTCOMES`, `steps` is `artifact.steps.length`, `operations` is `artifact.operations.length` with its position partition, `placed` and `excused` partition `operations` by the schema's own `escapes`, `sections` is `artifact.pins.blocks.length`, and `linesReached` is the clipped union the current code already computes. `placed + excused === operations` and `sequences <= entries` hold on every artifact.
- 【Invariant on error】A refusal is never a measurement and a measurement is never a refusal. A malformed or thin artifact still produces a line of zeros and `null`s rather than raising — the current `reachedLinesIn`/`linesBetween` clipping is the model — and no count becomes a pass condition: nothing in either surface compares a coverage number to a threshold, and no percentage, ratio or target is printed or computed anywhere in `coverage.mjs`, `report.mjs` or `run.mjs`.
- 【Invariant on internal state】An artifact missing `sequences`, `steps`, `operations`, `pins` or `spec` yields a total line: every key is present, the arrays default to empty, `specLines` defaults to 0, and the three census keys are `null` rather than 0. `coverageOf` reads its argument and mutates nothing, so an artifact handed to it is byte-identical afterwards.
- 【Invariant on the two surfaces】One spelling: for every one of the nine terms, the text the phase driver's block emits for that term equals the text the product path's console line emits for it, and both are produced by `coverageLine` over the same coverage object. A key cannot exist in one surface and not the other.
- 【Boundary invariant】A predecessor is compared only through `PREDECESSOR_KEY_FOR`. Every compared pair counts the same set (`entries`←`sequences`, `sections`←`rows`, `steps`, `operations`, `linesReached`, `specLines`), every key without a counterpart prints `(previous generation: not measured)` by name, and a version-1 record is never spelled by `coverageLine` — so no delta is drawn between two different sets and no absence is silent.
- 【Boundary invariant on the census】`censusSpelling` is total over the three census shapes: no pin borrowed (`none`), a pin borrowed and empty (`0 (reached 0, excused 0)`), and a pin borrowed with members (`<n> (reached <r>, excused <e>)` with `r + e === n`). The artifact's own record count never appears in the census position, and a denominator nobody supplied is never printed as a zero.
- 【Boundary invariant on the artifact's ledger】A neighbour is an entry of the ledger and may claim a sequence, so `sequences` is decided by `outcome` alone and never by `kind`; `entriesByKind` is reported so that the two axes cannot be read as one. On the measured consumer artifact `kind: entry` happens to equal the claiming count (68 and 68), and no arithmetic may assume that coincidence.
- 【Invariant on neutrality】Every changed module and brief remains project-neutral: no project name, project file, consumer path, transport or id convention enters `load.mjs`, `coverage.mjs`, `report.mjs`, `run.mjs` or `briefs/uncovered.md`, every vocabulary member printed comes from `artifact-schema.json` or from the records' own values, and `tests/educe-sequences/genericity.test.mjs` (C007) passes unmodified.
- 【Invariant on the check set】No engine check is added, removed or reordered: `ENGINE_DECLARED_CHECK_COUNT` is unchanged, every `checksRun=N of N` assertion in the suite is unchanged, and `every-step-belongs-to-a-drawn-sequence` keeps its id, its refusal wording and its scope — the brief changes, the check does not.

## Boy Scout Rule

coverage.mjs — `operationSpelling`'s two-branch fallback (a census clause or a bare count) becomes `censusSpelling` with one responsibility: spell the borrowed denominator, or say `none`. The absent case stops being expressed as the artifact's number, which is a readability defect as much as a measurement one: the function's name now says which set it spells.
coverage.mjs — the inline filters (`(artifact.sequences ?? []).length`, the `UNREACHED_ESCAPES.includes(operation.position)` filter repeated in three places across `coverage.mjs` and `engine.mjs`) become one `countBy` helper and one `escaped` predicate, so the partition rule is stated once and reads as a rule rather than as an inline condition. `escapedOperationsOf` in `engine.mjs` and the same filter here become the same derivation.
coverage.mjs — the partition rendering is one `partition(map)` used by every term that carries a composition, rather than a `join` per term, so a term cannot be composed one way in the line and another way in the block.
engine.mjs — the three schema-derived sets move down to `load.mjs` beside `readArtifactSchema`, which is the module that already owns the schema's vocabulary; `engine.mjs` keeps a re-export so its readers do not move. The comment that explains why the vocabulary is read from the schema rather than written in code travels with the declarations, so the reason is not stranded in a module that no longer declares them.
report.mjs — the per-key line construction is driven by the term list rather than by five hand-written calls, so the block and the console line cannot drift: a term added to `coverageLine` without a block line becomes a visible omission rather than a silent asymmetry.
run.mjs — the predecessor's spelling moves beside the mapping in `coverage.mjs`, so `run.mjs` stops half-knowing the shape of a stored record and the two surfaces share one translation of a version-1 record.
briefs/uncovered.md — the rule the reading must follow is stated as a rule, naming the two fields it concerns (`outcome` on the entry, `position` on the operation) in the file's own voice, so the trap of one word in two vocabularies is named where a reader meets it rather than discovered through a refusal.
No new hardcoded value is introduced: the term order, the never-measured phrase, the absent-census word and the partition separators are named constants in one place, and every vocabulary member still comes from `artifact-schema.json`.
