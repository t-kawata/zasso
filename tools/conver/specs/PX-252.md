# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Boy Scout Rule

- `text.mjs` `widestLine` and `foldMessage` measure code points while their own doc-comments say a reader's eye is the measure. They are not corrected here, because the drawn mode is fitted by them and any correction would move every drawing; instead the new measure is named for what it is (`displayColumns`) and the two existing functions gain one line in their comment saying which measure they use and why they keep it. That is the honest state of a touched file: the defect is named where the next reader meets it, and the correction belongs to a ticket about the drawn mode.
- The `inert` table in `parseTextArguments` is built as an object literal keyed by mode with a ternary per flag, in one expression at `text.mjs:297-309`. It grows when a fourth mode is added. It becomes a named function `inertFlagsFor(mode, { wantsAscii, width, wantsSource })` returning the list, so the refusal stays one sentence long and the table reads as a table.
- `parseTextArguments` currently returns `ids` whose legality the mode decides at three separate points (`wantsList && ids.length > 0`, `!wantsList && ids.length === 0`, and the inert list). Adding a mode that accepts an optional selector makes those three into one rule stated once: which modes require a selector, which accept one, which refuse one. The rule becomes a frozen `SELECTOR_RULE` table beside the other constants.
- `drawSequence` and the new sequence renderer both destructure an artifact, find an entry and take `stepsOf`; the new code reuses `stepsOf` rather than restating `steps.filter(step => step.sequence === id)`, so one definition of "the steps a sequence owns" serves both readings — the same reason `participantsOf` is exported for the emitter and the legend.
- The magic numbers the new rendering needs (the label gap, the balanced-tail floor, the arrow glyphs, the maximum indent) become named constants beside `DEFAULT_WIDTH` and `MIN_WIDTH`, because the file already names its budgets and a bare `12` in a fold would be unreadable prose.

### Exceptions

- The suite cannot test the rendering of the real consumer artifact — `~/shyme/gaia/GaiaSekkeiShiyousho_v32-sequences.json`, 116 sequences, 283 steps, 1643 lines — because that file lives outside this repository and a checkout does not carry it: an assertion that read it would fail on every machine but one, which is an external dependency rather than a behaviour under test. It is not a design defect and not an architectural defect: every rule the rendering exercises is asserted over the fixtures the repository does carry, and the rendering itself is recorded as a measurement in `docs/EDUCE-SEQUENCES-DESIGN.md`, which is how PX-250 recorded the drawn mode's measurements.
- Whether a break position is beautiful is not testable by any assertion, because "beautiful" is not a predicate a test can evaluate. It is not a design defect and not an architectural defect: the part of the fold that decides where a line may end is deterministic and is tested exhaustively — the legal cut points, the two forbidden line edges, the budget measured in display columns, totality and losslessness — and only the residue, which of several legal cuts a reader prefers, is left to the eye and recorded in the design document.
- The suite cannot test whether the orientation actually raises the quality of an adjudication or an attack, because that is a property of a language model's reading: it is non-deterministic, it is carried by a signature rather than by a check, and no number this repository computes measures it. It is not a design defect and not an architectural defect: everything mechanical about the delivery is asserted — that the tree reaches the rendered brief, that the brief still asks exactly one question with the tree subtracted from the count, and that every declared brief renders both with an empty tree and with a full one.
