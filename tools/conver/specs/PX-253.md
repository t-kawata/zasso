# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-253: Merge redundant sequences, steps and operations, and refuse a merge that loses one

**Ticket Key**: PX-253 · **Phase**: -1

---

## Background

- [Goal] Make a merge an act that the command file states and the run can verify. When a reader decides that two operations, two steps or two entries are one record, the command file must say how to express it, and the run must refuse a merge that loses a subject the previous generation named.
- [Purpose] Coverage in this apparatus is a density and not a count, and the design already concedes that a generation merging two sequences into one is an improvement carrying a smaller number (`rail/coverage.mjs:11`). The other half is missing: nothing in the command file says a merge is an act, nothing rewards it, and nothing can verify it. A reader sees the cost of a ruling and not the return of a merge, so the act is not performed.
- [Motivation] The artifact is recomposed every generation from the declaration and that generation readings (`rail/artifact.mjs:44-53`), and the previous artifact is not an input to that composition; the only cross-generation memory is the scalar coverage row in the `status.json` history (`rail/run-state.mjs:218-245`). A lossy merge is therefore invisible: the numbers fall, every check re-runs over a well-formed artifact, and no surface can say which subject left.
- [Constraints] Generic across projects: the rule reads identifiers, the declared escape vocabulary and the adjudication vocabulary, and no project-specific field. Do not add a threshold or a ratio to `coverageTerms`. Do not add a production writer of readings files. Do not delete a console reading, and do not touch the briefs. The specification digest, the line count and the supplied digest are already enforced on the product path (`rail/run.mjs:170-188`); the new rule states the same condition for the phase path rather than inventing a second answer.

## Scope

- `rail/reading.mjs` - one new exported rule, in the module that already owns `applyReadings` and the refusal surface. Add `subjectsNamedBy(artifact)`, the set of subjects an artifact names: every `operations[].id`, every `sequences[].id`, every `adjudications[].subject`. Add `vanishedSubjects({previous, next})`, the subjects `previous` names that `next` does not. Both pure, both reading no file.
- `rail/reading.mjs` - the revision guard inside `vanishedSubjects`. It answers `[]` when `previous` is null, when `previous.spec.sha256` or `previous.spec.lines` differ from the ones `next` records, or when `previous.supplied.digest` differs from `next` supplied digest. All three are fields every artifact already carries (`rail/artifact.mjs:40-42`), so the guard adds no parameter and no caller obligation.
- `rail/phases.mjs` - the phase 9 action. Read the artifact being replaced with `readArtifact(ctx.artifactPath)` before composing, call `vanishedSubjects` after composing, and return a non-empty answer as `{ ok: false, problems: [...] }` in the shape the action already uses for an `applyReadings` refusal (`rail/phases.mjs:205-213`).
- `rail/run.mjs` - the rebuild path. After `buildArtifact` and before `applyReadings` (`rail/run.mjs:118`), compare `ground.existing` against the composed artifact and refuse on the same condition. Before: the rebuild path judges only what it built. After: it also judges the transition from the artifact it replaces, which is the one thing a merge changes.
- `rail/run.mjs` - one function spelling the refusal, so the two surfaces print one sentence: the subject, the fact that the previous artifact named it, and the two remedies - name it in the next artifact (an operation with a declared escape position, an entry with a declared outcome), or carry a ruling whose subject is that name.
- `.claude/commands/educe-sequences.md` - a new section stating the merge procedure: the three levels an act can be merged at (an operation, a step, an entry), the file each is expressed in (the readings, the declaration), what the merged record must carry (the union of what the merged records reached, and the rulings they owed), and the phases that must re-run for each level.
- `.claude/commands/educe-sequences.md` - Step 9 (integrate) states the verification: what is compared, what the refusal names, and what the remedy is.
- `.claude/commands/educe-sequences.md` - the Refusals table gains one row naming the vanished-subject refusal and the Step that produces it.
- `.claude/commands/educe-sequences.md` - Steps 2, 8 and 12 each gain one clause pointing at the merge section, because an entry is merged where it is declared (Step 2), an operation is merged where it is read (Step 8), and an entry that stops claiming is ruled at Step 12.
- `docs/EDUCE-SEQUENCES-DESIGN.md` - the design record states the rule, its one-directional shape, and the reason a count comparison would be wrong, beside the existing statement that a merge is an improvement carrying a smaller number.
- `tests/educe-sequences/merge.test.mjs` - a new suite: the unit cases over `subjectsNamedBy` and `vanishedSubjects`, and the driver cases over `phase.mjs run` for phase 9.
- `tests/conventions/educe-sequences-command.test.mjs` - the assertions that read the command file. The new section restates no count, because the rule adds none, and it names no working file of a run, so the C015 path assertion is unaffected. Re-run rather than edited unless a case fails.
- Non-change, with the reason: no new file is added to the run directory. The comparison reads the artifact that is already beside the specification at the moment phase 9 replaces it, so the run gains no record, the `status.json` history keeps its meaning as evidence rather than as a gate input, and no path assertion in the command-file suite moves.

## Acceptance Criteria

- [Happy path] With the merge section stated in the command file and the rule in place, a generation whose composed artifact names every subject the artifact it replaces named reports no refusal and writes, and `node --test tests/educe-sequences/merge.test.mjs` passes over the unit and driver cases.
- [Error case] A generation whose composed artifact omits an operation the artifact beside the specification placed makes `phase.mjs run <spec> 9` exit non-zero, prints one line naming that operation, and leaves the artifact byte-identical - the digest before and after the call is the same. Naming the operation with a declared escape position, or carrying a ruling whose subject is that name, makes the same call pass.
- [Edge case] A generation opened over an edited specification, or over material whose digest moved, refuses the comparison and reports why rather than reporting a loss; the first generation beside a specification, which has no previous artifact, is silent and writes.

## Invariants

- [Normal establishment] At phase 9 the run holds two artifacts: the one beside the specification (`previous`) and the one just composed from this generation declaration and readings (`next`). The rule reads only those two; it writes nothing and opens no file other than the one it is about to replace.
- [Invariant on error] A subject `previous` named and `next` does not name produces a refusal naming that subject, and the artifact on disk is left byte-identical, because the refusal is raised before `applyReadings` performs its write.
- [Internal invariant] The rule never compares two revisions: when `previous.spec.sha256`, `previous.spec.lines` or `previous.supplied.digest` differ from the values the run holds, the answer is silence and never a refusal, because two revisions are not one space.
- [Boundary condition] With no `previous` the answer is silence. With the same subjects named in another order, or with strictly more subjects named, the answer is silence: the rule is one-directional and an addition is never a finding.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — phase 9 action -> vanishedSubjects -> refusal

- **Precondition**: a previous artifact naming operation `O`, and a composed artifact that names neither `O` nor any declared escape position nor a ruling whose subject is `O`.
- **Postcondition**: the run refuses, the refusal names `O`, and the artifact on disk is byte-identical to its state before the call, compared by digest.
- **Invariant**: the refusal is raised before `applyReadings`, so no path writes a partial artifact.

### C002 — a merge of two records into one record

- **Precondition**: the previous artifact names `O1` and `O2`; the composed artifact names one record whose reach is their union, or names `O2` carrying a declared escape position.
- **Postcondition**: `vanishedSubjects` answers `[]` and the run writes the artifact.
- **Invariant**: a merged artifact names every subject the unmerged artifact named; a merge moves names and does not remove them.

### C003 — a generation over an edited specification or over other material

- **Precondition**: `previous.spec.sha256` or `previous.spec.lines` differs from the values the composed artifact records, or `previous.supplied.digest` differs from the material beside the specification.
- **Postcondition**: `vanishedSubjects` answers `[]` and no refusal is produced.
- **Invariant**: the rule is silent whenever the two artifacts do not record the same specification and the same material, because two revisions are not one space.

### C004 — a composed artifact naming subjects the previous one did not name

- **Precondition**: the composed artifact names a subject `O3` the previous artifact did not name, and the previous artifact names nothing the composed one omits.
- **Postcondition**: `vanishedSubjects` answers `[]`.
- **Invariant**: the rule is one-directional: an addition is never a finding, whatever the measured counts do.

### C005 — the command file and the conventions that read it

- **Precondition**: `.claude/commands/educe-sequences.md` as this ticket leaves it.
- **Postcondition**: it states the merge procedure and names the refusal, and `tests/conventions/educe-sequences-command.test.mjs` passes.
- **Invariant**: the file restates no count and names no run-directory file it did not name before.

### C006 — phase driver and product path

- **Precondition**: the same pair of artifacts, presented to `phase.mjs run <spec> 9` and to `run.mjs <spec>` holding the same readings.
- **Postcondition**: both refuse, and the two refusal lines name the same subject.
- **Invariant**: one function spells the sentence for both surfaces, so they cannot disagree about what left.

## Boy Scout Rule

- `rail/reading.mjs`: the new rule is named for what it answers and not for what it reads - `subjectsNamedBy` returns the names an artifact carries, `vanishedSubjects` returns the names that left - so the call site reads as prose: the phase compares the artifact it replaces with the one it composed, and a name that left is the refusal.
- `rail/run.mjs`: the refusal sentence is extracted into one named function rather than spelled twice, because two spellings of one refusal is two things to keep in step; the extraction is required by C006 rather than by taste.
- `rail/phases.mjs`: the phase 9 action already reads as three moves - read the declaration, compose the artifact, apply the readings. The comparison is inserted as a named call between the second and the third so the sequence still reads top to bottom.
- Hardcoded values: none is introduced. The three guarded fields are read by name from the artifact, and the escape vocabulary is read from `artifact-schema.json` through `UNREACHED_ESCAPES` rather than restated in this module.
- Swallowed errors: none. A non-empty answer becomes problems, which the phase driver prints, and a thrown error inside the rule surfaces through the existing check runner rather than being caught.
- Outside scope, found while reading: `rail/reading.mjs:375` `writeReadingsFile` has no caller outside the tests. It is not removed here, because a production writer of readings is a separate decision, and it is not a stub: it is a function the suite uses to build fixtures.
