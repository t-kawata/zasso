# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-254: Make a new generation read again, and say when it read nothing

**Ticket Key**: PX-254 · **Phase**: -1

---

## Background

- [Goal] A generation that re-opens the `[read]` phases must make the reader answer again. Today it re-opens them in the status and every gate then passes on the readings it inherited, so a fifth `/educe-sequences` over an unchanged specification reads nothing, writes an artifact whose nine measured terms are identical to the fourth, and reports a pass.
- [Purpose] The command file states the mechanism - re-asking the reader is how a generation finds what the last one missed - and the apparatus cannot carry it out: a `[read]` gate can see only that the named file exists and is signed, and the file is inherited. An instruction the run cannot perform is worse than no instruction, because a reader reads the pass as a re-inspection.
- [Motivation] Measured on the consumer run after its fifth invocation: `generation: 5`, `entered: true`, `invalidated: []`, all 18 phases `done` with `loops: 0`, the five readings files untouched (mtime 12:25 and 13:50) while status, pins, the worklists and the artifact were written at 16:53, and the nine measured terms identical to generation 4 (`entries=553 sequences=116 steps=283 operations=257 placed=148 excused=109 sections=292 linesReached=15971 of 15971`). Nothing in the output says that no reading was made.
- [Constraints] The forcing must not inspect the reader: no modification-time test, no rule that the file must be newer than the generation. A gate that judges a reader rather than a record is the class of check this apparatus refuses everywhere, and it is trivially satisfied by touching the file. The forcing is instead the removal of the file the gate looks for, which makes the existing existence predicate mean written this generation. Nothing may be deleted - the previous readings are the reader's own work and the thing a re-read is made against. No new required field is added to a reading. The verification branch is kept: `run-state.mjs` records `entered` to separate a generation opened and left alone from one a reader has worked in, `adhoc-run.test.mjs` pins it, and that branch is what makes a bare second `begin` cheap.

## Scope

- `rail/readings.mjs` - the archive name, so it is derived rather than spelled at a call site. Add `ARCHIVE_DIRECTORY = 'archive'` and `archivedReadingsFileName(brief, generation)` returning `readings-<brief>.g<generation>.jsonl`, built from `readingsFileName(brief)` rather than restating it.
- `rail/readings.mjs` - `archiveReadings({ directory, generation })`: move every readings file the `[read]` phases name into `<run dir>/archive/` under its archived name and return the names moved. A file that is not there is skipped rather than refused. The move is `renameSync` inside the run directory, so it is atomic on one filesystem and cannot half-copy a reading.
- `rail/phases.mjs` - `beginRun`. Archive on the new-generation path only, after the `unchanged` decision and before the digest that is recorded. The digest the notice compares keeps its current name and meaning; the recorded digest is measured after the move. Before: one digest served both. After: two, each naming the state it describes.
- `rail/inherit.mjs` - the archive enters what a run inherits, so the halt guard keeps seeing the readings and a moved file is still part of the digest. `inheritedFilesIn` scans `<run dir>/archive/` the way it already scans the ad-hoc directory, and the scan is sorted like the other listings so the digest is a function of the set and not of the order a filesystem returns.
- `rail/gates.mjs` - unchanged, and stated because it is the mechanism: `readBrief` finds no file after the move, so the existing refusal fires and names the file the reader must write. No gate learns about generations, archives or readers.
- `rail/phases.mjs` - `BRIEFS_OF_PHASE` and `claimedBy` are unchanged, and this is stated because it is why `readPhasesSettled` becomes honest with no edit: a claim can no longer be counted from an inherited file, because there is no file to count until the reader writes one.
- `.claude/commands/educe-sequences.md` - Step 0 states what a new generation does: it opens the generation, moves the readings of every `[read]` phase into `<dir of spec-file>/educe-sequences/archive/`, and asks the reader again. The sentence that says a new generation leaves the readings where they are is no longer true and is replaced rather than qualified.
- `.claude/commands/educe-sequences.md` - the reader is told where the previous generation's answers are, so a re-read is made against the previous answer and not blind. The archive path is named in Step 0 and in each Step whose phase is re-opened, in the compressed register the file is written in.
- `.claude/commands/educe-sequences.md` - the run-directory inventory and the List of Scripts Used name the archive directory, so the file remains a summary of what a run writes.
- `tests/conventions/educe-sequences-command.test.mjs` - the working-files list gains the archive directory, so the command file must name it under the run directory. The list is hand-written in that test, which is why this is a scope item rather than an automatic consequence.
- `tests/educe-sequences/regeneration.test.mjs` - a new suite: the archive and its names, the refusal a re-opened `[read]` phase produces, the two digests, the verification branch left intact, and the reader's file being the only source of claims.
- Non-change: the four content tables - Refusals, The Three Tags, the Language Protocol and the Completion Report - gain no row and no vocabulary. The change adds no refusal the table does not already carry, because the refusal it produces is the one a missing readings file has always produced.
- Non-change, with the reason: the brief templates are not edited. The reader is handed the archive path in the Step rather than through a placeholder, because a brief is rendered from a template by `phase.mjs` and a placeholder would carry one generation's path into a file whose point is that it is a function of the brief and the worklist. A later ticket that wants the previous answers rendered into the brief has the archive to render from, which is what this ticket makes possible.

## Acceptance Criteria

- [Happy path] Over the consumer specification, a second invocation of the command after a first generation has produced an artifact opens a generation, moves the five readings files into `<dir of spec-file>/educe-sequences/archive/` under names carrying the superseded generation, and `phase.mjs run <spec> 8` refuses until the span reading is written again. `node --test tests/educe-sequences/regeneration.test.mjs` passes over the unit and driver cases.
- [Error case] A generation that opens with no readings at all is not refused by the archive: the first generation and a generation opened after a partial run both open, and their `[read]` phases refuse for the reason they always did - the file the reader must write is not there.
- [Edge case] A second `begin` over a set in which nothing was entered still reports `verification` and moves nothing, and the repeat-notice answer over an unchanged set is the same answer it was before this ticket, because the digest that drives it is measured before the move.

## Invariants

- [Normal establishment] A generation is opened by `beginRun`. On that path, before the digest it records is measured, every readings file of every `[read]` phase is moved into `<dir of spec-file>/educe-sequences/archive/` under a name carrying the generation that produced it. Nothing is copied and nothing is deleted: the file is renamed, so the previous generation's answers remain readable at the archive path.
- [Invariant on error] A generation that opens with no readings yet is not refused: a readings file that is not there is skipped, because the first generation and a generation opened after a partial run both legitimately hold fewer files than the brief list names.
- [Internal invariant] Two digests are measured and they are different facts. The digest the repeat notice compares is measured before the move (what the run found); the digest recorded for the new generation is measured after it (what the new generation inherits, the archive included). A recorded digest measured before the move would describe a state the generation never held.
- [Boundary condition] A second `begin` over a set in which no phase was entered still reports mode `verification` and moves nothing: `run-state.mjs` records `entered` for exactly that case, and `adhoc-run.test.mjs` pins it. The forcing applies to generations a reader has worked in, which is every generation that has produced an artifact.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — a new generation -> the readings files -> the [read] gate's existence predicate

- **Precondition**: a run directory whose `[read]` phases have passed, holding `readings-span.jsonl` and the other readings files, and a `begin` that opens the next generation.
- **Postcondition**: after the generation opens, `readings-span.jsonl` is absent from the run directory and present at `<run dir>/archive/readings-span.g<previous>.jsonl` with byte-identical content; `phase.mjs run <spec> 8` refuses and names the file the reader must write.
- **Invariant**: no reading is deleted and none is copied: the previous generation's answers remain readable at one path and the run directory holds no file the reader did not write this generation.

### C002 — the archive -> what a run inherits -> the recorded digest and the halt guard

- **Precondition**: a run directory with readings, and a generation opened over it.
- **Postcondition**: `assetDigestOf` after the move differs from the digest measured before it; the new generation's recorded `assets.digest` equals the digest measured after the move; and the archive listing is part of that digest.
- **Invariant**: the digest the repeat notice compares is measured before the move and the digest that is recorded is measured after it, so neither describes a state the run did not hold.

### C003 — a second begin over a set nothing was entered in

- **Precondition**: `beginRun` called twice over one specification with no phase entered in between.
- **Postcondition**: the second call answers `mode: 'verification'`, and no archive directory is created and no readings file moves.
- **Invariant**: `entered` is the fact that separates a generation opened and left alone from one a reader has worked in, and it is read rather than derived.

### C004 — the command file and the run directory it describes

- **Precondition**: `.claude/commands/educe-sequences.md` as this ticket leaves it, and the working-file list `tests/conventions/educe-sequences-command.test.mjs` derives.
- **Postcondition**: the file names `<dir of spec-file>/educe-sequences/archive/` and states that a new generation moves the readings there; the conventions suite passes with the archive directory added to its list.
- **Invariant**: the file states no count it could derive and names no run file outside the run directory.

### C005 — the archive -> claimedBy -> the measured readPhasesSettled

- **Precondition**: a generation opened over a run whose readings were archived, before the reader has written any file.
- **Postcondition**: `claimedBy` answers 0 for every `[read]` phase, so the phase cannot be settled by a claim the previous generation made.
- **Invariant**: a phase is settled only by a claim counted from a file that exists after the generation opened, which is the reading the gate also requires.

## Boy Scout Rule

- `rail/readings.mjs`: the new names are derived - `archivedReadingsFileName` builds on `readingsFileName` rather than restating the pattern - so the archive cannot drift from the file it archives.
- `rail/phases.mjs`: the two digests are named for what they describe (`foundDigest` for the set the run found, the recorded one for what the generation inherits), because one name serving both is exactly how this ticket's central fact would be lost. The archive call sits between them and reads as the middle move of three.
- `rail/inherit.mjs`: the archive scan is extracted into the same shape as the ad-hoc scan, so `inheritedFilesIn` reads as three sentences - the fixed files that are present, the directory scanned, the listing sorted - rather than one expression with a special case inside it.
- Hardcoded values: none is introduced. The archive directory name is a constant with the other file names it sits beside, and the generation in an archived name comes from `status`, not from a literal.
- Swallowed errors: none. A missing readings file is skipped deliberately, and the reason is stated at the skip; a rename that fails is not caught, because a move that cannot happen is a broken run directory and reporting it as an empty archive would hide it.
- Outside scope, found while reading: `rail/report.mjs:26` counts a `[read]` phase settled when `claims > 0`, and `claims` came from a file that could be inherited. This ticket does not edit that line - the archive is what makes the line true - and the reason is recorded in the ticket rather than left for a reader to rediscover.

## RFC Discrepancies found in Prior Implementation Rounds

- The command file stated that a new generation leaves the declaration and the readings exactly where they are, while the design said re-asking the reader is how a generation finds what the last one missed. Neither could be true at once: the gate a [read] phase has can see only that the file exists and is signed, so a reading left in place is a reading that passes without a reader. The file now states the move, and the design document states why the move rather than a check on the reader.

Risks.
- The recorded digest is the sharp edge. Measured before the move it would record a state the new generation never held, and the repeat notice would then answer about a set that no longer exists. The test that asserts the recorded digest equals the post-move digest is the guard.
- The archive is a new file set in a run directory whose sentence says an invocation deletes nothing. The move satisfies that (nothing is deleted) but it does change where a reader finds last generation's answers, so the command file must say where they are; a reader who does not find them re-reads blind, which is worse than inheriting.
- A run directory grows by one readings set per generation. On the consumer run that is about 2.3 MB per generation. It is bounded by the number of generations and nothing prunes it; a ticket that prunes is a different decision and is not taken here.
- The forcing applies to every generation, including one opened to check a rail change. The cheap check remains available and is `rail/run.mjs`, which writes nothing; the command file's Step 0 and the List of Scripts Used are where a reader learns which of the two they want.

Caveats.
- The brief templates are deliberately not edited. The archive path is named in the Step, not rendered into the brief, because a brief is a function of the brief template and the worklist and a placeholder would carry one generation's path into it. A later ticket can render the previous answers into the brief from the archive this ticket creates.
- The archive is a flat directory holding one file per brief per generation. A generation that is superseded twice without being re-read produces two files for one brief; they are distinguished by the generation in the name, and nothing reads them but a reader and the digest.
- The verification branch is kept and is not widened. A bare second `begin` before anything was entered stays cheap; the ticket does not make every invocation read, only every generation that is actually opened.

Open items.
- Whether the archive should be pruned, and at what rule, is settled by the plan against how the run directory is already bounded: the history row per generation is unbounded in the same way, and one rule for both is better than two.
- Whether the reader should be handed the archive path through the brief rather than through the Step is settled by reading the four brief templates during the plan; the ticket states the decision and the reason and the plan confirms it against the templates as they stand.
- Whether `uncovered` should be archived with the other briefs is settled by the plan against `BRIEFS_OF_PHASE`: it is a brief of phase 8, so it moves with phase 8 if the rule is stated over the phase table rather than over a hand-written list.
