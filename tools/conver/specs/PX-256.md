# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-256: Make the sequence artifact an optional material of the grill and the drill, behind a tolerant detector that runs before the strict reader

**Ticket Key**: PX-256 · **Phase**: -1

---

## Background

GOAL
A sequences artifact handed to the pipeline must reach the grill and the drill as a per-package view, and its absence must change nothing about how either command runs.

PURPOSE
Both commands resolve their material mechanically from Status.json alone, and both refuse to run at all when a recorded material path has disappeared. init.js prints Material not found and exits 1 before any phase runs. list-files.js prints Material path not found and exits 1. Today materialPaths holds only seeds a human supplies and never deletes, so the assumption that a recorded path exists is safe.

Recording a generated file there breaks that assumption. The concrete mechanism is already recorded in the live run: educe-sequences/supplied/material.md states that the previous generation absorbed the per-crate sequence artifacts into its own artifact and deleted them from the crates. A view file written into a package directory can therefore disappear between two runs of the same session, and the session then wedges permanently, before any detector can run, because the strict reader executes first.

MOTIVATION
The user requires that the reinforcement be additive, that nothing stop or become unstable without it, and that when the sequence information is available it must be used without omission. A design whose failure mode is a wedged session violates the first requirement even though it is otherwise additive. The ordering of the detector before the strict reader is what closes it, and it is a structural fix rather than a defensive one: a tolerant reader placed before a strict reader makes the strict reader unreachable in the state that would stop it.

CONSTRAINTS
No existing command call line is removed or reordered; additions only. The tolerant reader must precede the strict reader. New file names must not collide with the discriminators already in the code: canon-state.js matches the suffixes -GRAPH.json and -Dirs-Tree.json and the name Tickets.json, so the view must not carry a derived-artifact suffix; guard-edit-surface.js is default-deny, so the new names must be added to the frozen list deliberately. init.js, list-files.js, settle-run.js, session-init.js, canon-state.js and check-all-schema.js are not modified.

## Boy Scout Rule

Translatability plan for the material plumbing.

Function names are verb phrases naming what the reader does: findSequenceMaterial(rfcDir), readMaterialRecords(status), classifyMaterialPath(absolutePath), describeAbsence(). A reader must be able to read the detector top to bottom as prose: read the session records, classify each material path, report what was found or report that nothing was found.

Variable names are domain concepts: materialRecords, sourceArtifactPath, packageViewPath, searchedRecords, absentPaths. Never data, info, tmp, or result.

The detector has one responsibility: report presence. It does not generate the view, does not write, and does not decide what to do about the answer. The generation lives in sequences-slice/run.mjs, so the tolerance and the writing are in different files and neither can silently acquire the other duty.

Hardcoded values become named constants: MATERIAL_LIST_FIELD = materialPaths, LEGACY_MATERIAL_FIELD = researchPath, SOURCE_ARTIFACT_SUFFIX = -sequences.json, VIEW_MARKDOWN_NAME = SEQUENCES.md, VIEW_JSON_NAME = SEQUENCES.json, SESSION_DIR_NAME = drills, EXIT_OK = 0.

No swallowed errors: the detector reads each candidate record inside a try and, on failure to read or parse, adds the path to a searchedRecords list with the reason rather than continuing silently, so the printed answer can always be explained. Because the detector must always exit 0, the error path returns a value rather than throwing.

The probe bug in the earlier investigation came from one script doing reading, joining and counting at once; the same shape is avoided here by keeping the detector free of any join logic.

WHY lib/packages.mjs AND lib/view.mjs ARE IN SCOPE ALTHOUGH THE SCOPE SECTION NAMES run.mjs
C003 requires the projection to be a pure function of its inputs and byte-stable across runs, and C005 requires the package-to-view mapping to be checkable. A CLI that reads, joins and writes in one place is the shape that produced the 0-of-210 misreading this ticket family exists to prevent. The join lives in a pure module, the writing lives in the CLI, and the tests hold them apart.

DECISIONS TAKEN FROM MEASUREMENT, NOT FROM PREFERENCE
- The view stays in the package directory. settle-run.js is the only reader that could have been contaminated, and prior-decisions.mjs artifactNamesOf narrows the list to PRIOR_ARTIFACTS plus /^RFC(-.*)?\.md$/, which SEQUENCES.md does not match. The open item is closed rather than deferred.
- The view is NOT added to the drill's preflight material list. preflight.cjs walks a directory argument and throws Empty material directory when it holds no regular file, and verifyExistence exits 1 on a missing file, so passing a possibly-absent view path would wedge the drill in exactly the way this ticket exists to prevent. The drill reads the view by instruction in the command prose, which cannot fail.
- The detector takes an optional --session-dir. The Scope section says process.argv[2] only, which cannot satisfy C004's requirement that the drill session record be searched first. An optional flag satisfies both without changing the primary API.
- The view carries stable unit ids (op-<operationId>, seq-<sequenceId>, xdir-<sequenceId>) because PX-257 gates on them and a view without ids could not be gated on.
- Tests live at the repository root under tests/, as .test.mjs. The Scope section says .claude/tests/ under the existing discovery glob; measured in PX-255, that glob is tests/**/*.test.{js,cjs} and excludes .mjs, and the tree declares commonjs. The detector's tests go under tests/grill-me-for-rfc/sequences-material/ to follow the per-subsystem convention the repository already uses.
