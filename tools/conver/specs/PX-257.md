# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-257: Turn the distributed units into obligations the existing gates already read, so no sequence or operation is missed and no gate branches on sequences

**Ticket Key**: PX-257 · **Phase**: -1

## Background

GOAL
Every unit the ledger distributes must be discharged at the design layers, and a unit that is not discharged must appear as a machine finding rather than as a silent gap.

PURPOSE
The grill writes RFC.md from a settled design tree, and the drill blocks on verify-step.js, which fails when any high-severity finding remains. Neither currently knows that sequences or operations exist, so a sequence or an operation has no name anywhere in the design artifacts.

The design must add obligations without adding a branch. The obligation is not cover the sequences; it is that the RFC covers everything the session material decides. Sequences are one more material, so the conditional belongs in the input set and never in the gate code. If a gate ever reads as if sequences were present then require something, the artifact has become a precondition of operation and the users requirement is violated.

MOTIVATION
The property that makes this safe already exists in the code and was verified by reading it. verify-consistencies.js emits severity-ranked findings where high is a structural break and low is cosmetic, and verify-step.js fails only on high severity. A check that emits nothing therefore leaves PASS and FAIL mathematically unchanged. The sixth check can be added to the same file with the same severity vocabulary and the same READ-ONLY deterministic contract, and the 22 packages that carry no ledger keep their current verdict.

CONSTRAINTS
The existing six checks of verify-consistencies.js keep their exact semantics. verify-step.js is not modified, because the driver already picks up new findings. check-all-schema.js validateAll keeps validating only Status.json, DesignTree.json and CheckList.md. No gate may name sequences outside the obligation registry. The README states that a gate failing on a real package is a gate nobody can pass, so the sixth check is calibrated against the 22 existing packages before it is trusted, which is why PX-255 precedes this ticket.

## Boy Scout Rule

Translatability plan for the obligation machinery and the gates.

Function names are verb phrases naming the obligation, not the mechanism: registerObligation(materialKind), obligationsFor(session), dischargeUnit(unit, layer), reportNotProved(units, layer), readDistributionLedger(rfcDir), refuseRowAt(rowIndex, reason). The gate must read as prose: read the ledger, check each row against the unit set, report every unit that is not discharged.

Variable names are domain concepts: obligationRegistry, dischargedUnits, notProvedUnits, declaredResiduals, crossBoundarySequences, clauseKeys, specLineRanges. Never data, info, tmp.

One responsibility per module. verify.mjs evaluates the decidable checks and returns findings; it does not format them. sequences-ledger.js formats and prints. check-distribution-ledger.js validates one package ledger and returns the first failure. verify-consistencies.js gains one function, checkUnitPreservation, and one call site.

The critical readability property is negative and must be visible in the source: no gate file contains a branch on the sequences material. The obligation set is computed from the obligation registry, and an empty registry yields an empty loop, so the additivity is readable rather than argued. A reviewer must be able to confirm by reading checkUnitPreservation that an absent ledger produces no finding.

Hardcoded values become named constants: LEDGER_TITLE_SUFFIX = Distribution ledger, LEDGER_COLUMNS = [Unit, Kind, Owner, RFC location, Ground], UNIT_KINDS = [operation, sequence, cross-boundary-sequence, declared-residual], MACHINE_VERDICTS = [proved, not proved], SEVERITY_HIGH = high, SEVERITY_LOW = low, COMPOSITION_CHECK_PATTERN.

No swallowed errors: a ledger row that cannot be read names its row index and the failing cell, matching the divergence-ledger style which names the artifact and the location.
