# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-258: Carry the unit id through the graph, the tickets and the README, and admit educe-sequences into the conformance loop as the requirements ledger producer

**Ticket Key**: PX-258 · **Phase**: -1

## Background

GOAL
The unit id must survive from the specification to the ship layer, so that all necessary sequences and operations being implemented becomes a decidable predicate instead of a proxy.

PURPOSE
The binding vessels already exist at every layer, and each was verified by reading it. Tickets.json carries a nodeIds array described as corresponding to graph nodes. boundify-graph writes an Initial Design Artifact header on every implementation file that cross-references its graph node, and the supreme law protects that header as a traceability chain. crystalize-readme derives the user README from the graph, so the graph is the only route by which a unit can reach the ship layer.

What is missing is that the chain starts at RFC headings rather than at specification units. graphify-rfc splits the RFC by heading into nodes, so a node corresponds to a heading and a unit has no name anywhere downstream. That is why a reader of the finished RFC cannot tell whether the sequences and operations the specification names were ever implemented: the names do not exist past the specification.

MOTIVATION
The ship condition today is RESIDUE zero, which is a product-side proxy. The user requires that the systems shippability be first and foremost that every necessary sequence and operation is implemented. Residual zero can be reached while an operation is entirely absent, because RESIDUE measures whether the user documentation can be written, not whether the operations exist. Making the unit id travel turns the ship condition into a direct predicate over units, and it also makes the five reinvestment consistencies name the units, so an evolution that loses a unit is visible.

CONSTRAINTS
The graph and ticket artifacts are schema-validated and consumed by commands outside this feature, so no existing field may become required. node.schema.json declares additionalProperties false, so a new optional property is the only additive route into a node; the alternative of encoding the id in slug or headingRefs was measured and rejected, because slug is capped at 25 characters with a strict pattern and headingRefs entries must match real headings. The README must not describe a layer the code does not implement.

## Boy Scout Rule

Translatability plan for the propagation work.

Function names are verb phrases naming the carried object: carryUnitIdToNode(node, unitId), readUnitIds(graph), assertUnitPreservation(rfcUnits, graphUnits, ticketUnits), resolveUnitIdsFromPhase(ticketsJson). A reader must be able to read the chain as a sentence: read the unit ids from the RFC sections, read them from the graph, read them from the tickets, and assert the three sets are equal.

Variable names are domain concepts: unitIdsByNode, phaseNodeIds, ticketNodeIds, rfcUnitAnchors, preservedUnits, lostUnits. Never data, info, tmp.

One responsibility per function. The schema edit and the carrying logic are separate: the schema gains an optional property, and a small reader in rfc-graph reads it. The consistency check does no reading of its own; it is handed three sets.

Hardcoded values become named constants: UNIT_ID_PATTERN, NODE_ID_PATTERN = ^N[0-9]{4}$, GRAPH_SCHEMA_PATH, README_RESIDUE_MARKER.

No swallowed errors: a ticket naming a unit id absent from the graph is reported with the ticket id and the unit id, never skipped. A graph that fails schema validation reports the failing property by name and path.

The touched code leaves better than it was found: verify-consistencies.js currently reads node ids only to build the ticket coverage set; the unit-preservation check reuses that read rather than adding a second traversal, so the file does not grow two ways of doing one thing.
