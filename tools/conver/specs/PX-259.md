# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the projection in .claude/scripts/sequences-slice assign every sequence and every operation of a workspace to a directory that must implement it, so that when every directory has discharged its duty the project operative procedures are provably complete. The design is tools/conver/docs/FIX-PLAN006.md, which is this ticket's specification.

### Purpose
The projection keys obligation on inventory ownership alone. lib/ownership.mjs joins an operation result_object_classes to the packages owning those objects, and lib/view.mjs records a sequence only in the views of packages that own a share of it (view.mjs:81-89, the shared = ownerPackageIds.length > 1 expression). A package whose duty is structural rather than object-producing — a port, a transport, a persistence backend, an external provider adapter, or the surface every operation is reached through — therefore receives an empty obligation set. grill-me-for-rfc STEP 1 seeds op-, seq- and xdir- nodes from that view and seeds nothing when it is empty, and sequences-ledger.js:116 prints not proved: no unit is distributed to this package, which is a verdict and not a failure. All of G0-G6 pass and the run declares DONE.

### Motivation
Measured on ~/shyme/gaia on 2026-10-14: 26 packages carry a view, 13 of them have all three unit lists empty, and all 13 have Status.json state DONE. The 13 are exactly the packages whose duty is structural: gaia-core, gaia-ports, gaia-network, gaia-foundation, gaia-invariants, gaia-rest, gaia-transport-adapter, gaia-stripe-adapter, gaia-ekyc-adapter and the four gaia-store-* backends. FIX-PLAN005 section 1.3 already recorded that emptiness as costing nothing, which was sound only while the projection was empty for every package. The relations that assign the missing duty already exist on disk and are already computed elsewhere in conver: the allocate manifest contract_registry holds 84 boundaries each naming a provider_package and a consumer_package, and explain-seed/lib/projection.mjs:148-158 already projects them per package as provides and consumes. The defect is that the sequences projection does not read the model that exists.

### Constraints
Additive only: PX-257 gates on unit ids being present in a package rather than on a count, so the three existing lists keep their exact contents and no id is renamed or retired. No project naming may be encoded: the tool reads columns, ids and package fields and interprets none of them. The two command documents must keep every existing branch, flag, exit code and output meaning, and a legacy target must be reinforced on re-run rather than refused. The widening of the unit id vocabulary is forced by the guarantee, because an obligation that cannot reach the ship layer is not an obligation; it is measured to reclassify nothing (zero existing node ids use ctr-, obl- or xbd- in gaia, zasso and conver).

Functions are verb phrases naming the object they carry: readDeclaredInterfaces, collectCandidateColumns, classifyCarries, classifyServes, buildObligationUnits, measureCoverage, resolveUnassignedDemands. Variables are domain concepts rather than abbreviations: obligationUnits, candidateColumns, uncoveredSpellings, valueJoin, obligationSource, unassignedDemands, unreachedOwnedObjects. One responsibility per function: the candidate rule lives in collectCandidateColumns alone, the spelling rule in one exported helper so both the candidate scan and the cross-check call the same code, and the verdict in measureCoverage, never in a renderer. Hardcoded values become named constants with the measured value beside them: the five unit prefixes beside UNIT_ID_PATTERN, the unit kinds beside UNIT_KINDS, the three source-valued literal 'declared'|'undeclared'|'absent' as one exported frozen list, and the axis names as one frozen list so a renderer cannot invent a fifth. No error is swallowed: every refusal names the file and the reason, and the coverage verdict carries the demand that produced it. Existing code improved where this ticket touches it: view.mjs carries the partition claim in its header while its buildPackageView was never given the relations to make the claim true, so the header is made true rather than reworded; run.mjs reads and discards the allocate manifest at line 121, which is replaced by passing it; and the two literal field lists in material.mjs and distribution-ledger.mjs are kept as the single source of each vocabulary instead of being duplicated at the call sites.
