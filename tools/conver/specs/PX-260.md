# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the guarantee reachable without a human in the loop: every sequence and every operation of a workspace is assigned to the package that must implement it, by mechanical derivation wherever a relation in the artifacts already says so, and by a grounded judgment of the running AI wherever no relation does. The AI records its judgment in a file the tools read, so the next run reinforces rather than repeats.

### Purpose
PX-259 built the decision procedure and left the supply side without a home. The coverage gate measures a workspace and reports the guarantee as not established, naming every demand that no package owes, but the only two sources the projection reads for a surface declaration are the allocate manifest field declared_interfaces and a fence in the package's RFC-SEED.md, and neither can be written: no tool authors declared_interfaces, and guard-edit-surface.js:22-36 freezes RFC-SEED.md, both WORKSPACIFY manifests and both generated view files. A package therefore can never declare a surface, so the serves relation is permanently empty on every real workspace and 61 of the demands measured on gaia have no authoring path at all.

### Motivation
Measured on ~/shyme/gaia on 2026-10-14, read-only. The coverage gate reports: 321 demand(s) assigned, 0 exempted, 145 assigned to nobody, being 50 operations, 5 sequences, 84 boundaries and 6 candidate columns, plus 98 inventory objects owned by packages the ownership join cannot see. ### Constraints

No project naming, layer name or vocabulary may be encoded in the tool: the AI is the party that reads a project's meaning, and the tool only checks completeness, grounding and distribution.

## Acceptance Criteria

- Happy path: after make install-to-projects, a workspace whose demands a relation or a recorded judgment assigns reports that T holds, the view carries the obligation section with the relation and ground of every unit, the rail's report names no unassigned demand, and both gates exit 0 — with no human decision taken anywhere in the run.
- Error case: a workspace whose only coverage would come from exempting an operation or a sequence reports that exemption as refused, names the demand, and reports the guarantee as not established; a workspace with an ungrounded assignment reports it and does not count it.
- Edge case: a workspace carrying no obligation record runs end to end, is told every unassigned demand by axis and id, writes nothing frozen, and on a second run differs only by the demands the first run resolved.

## Invariants

- 【Normal establishment】A workspace whose every demand is assigned — mechanically by ownership, by a contract side or by a surface route, or by a grounded judgment recorded in a package obligation record — reports that T holds, and the report prints the assigned count per axis and the distribution of assignments across packages.
- 【Error invariant】An operation demand or a sequence demand is never exempted. An adjudication naming one is refused as an error naming the demand, so the coverage gate cannot be satisfied while nobody owes the operation: that is the one path by which the guarantee could become vacuous, and it is closed in code rather than left to the judgment of the party being checked.
- 【Internal state invariant】The frozen stage-1 inputs stay frozen (RFC-SEED.md, INFO-RFC-SEED.md, EXPLAIN-RFC-SEED.md, both WORKSPACIFY manifests, SEQUENCES.md and SEQUENCES.json), and the generated artifact is never hand-edited: a judgment is durable because it is recorded in a writable obligation record, not because a generated file was patched.
- 【Boundary invariant】A target that carries no obligation record runs end to end and is told exactly which demands are unassigned, named by axis and id; re-running over an unchanged specification reports the same list and assigns nothing new (idempotence), and re-running after a record is written reports the correspondingly smaller list.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — the package obligation record to the package obligation set

- **Precondition**: a package obligation record at the package root, parseable, carrying serves entries of shape {interfaceId, column, operationSet, valueJoin?} and assignments of shape {unit, ground}; the artifact carries the columns the record names; the allocate manifest carries a contract registry
- **Postcondition**: buildObligationUnits returns the serves units, one assigns unit per assignment whose unitId is the named op- or seq- id, and the package's carries units, sorted with stable ids; a package with no record returns its carries units only
- **Invariant**: no unit is created for a package the record does not name; an assignment naming a unit id outside the artifact's operations and sequences produces a finding and no unit; no id already carried is renamed or retired

### C002 — an adjudication row to the exemption rule

- **Precondition**: an exemptions row of shape {subject, lens, why} with a non-empty why, where subject is an operation id, a sequence id, or a candidate column name
- **Postcondition**: a row whose subject is an operation or a sequence is returned in the refused list naming the demand and the kind that may not be exempted, and the demand remains unassigned; a row whose subject is a candidate column exempts that surface demand and is printed with its ground
- **Invariant**: the verdict is never holds while the refused list is non-empty, so a workspace cannot earn the guarantee by removing the duty instead of placing it

### C003 — the artifact and the workspace to the demand report

- **Precondition**: an artifact carrying pins.enumerations and operation rows, and a workspace root carrying both manifests and every package view
- **Postcondition**: the demand summary names the candidate columns derived from the pins crossed with the operation rows, the boundary count, and every demand that no relation and no assignment covers, by axis and id; its counts agree with measureCoverage over the same root
- **Invariant**: a re-run over an unchanged specification produces a byte-identical report, and a re-run after a record is written reports a strictly smaller unassigned list with no other line moved

### C004 — a recorded judgment to the provenance chain

- **Precondition**: an assignment recorded with a ground naming the specification evidence it rests on, and a unit id of one of the five prefixes
- **Postcondition**: the assignment unit id is accepted by isUnitId, carried by a design node, read back from a generated header and from a ticket, and collected by the consistency verifier; the view prints the ground beside the unit
- **Invariant**: an assignment with an empty ground is reported and never counted toward the verdict, and an id written before this change reads exactly as before

### C005 — the measured partition to the verdict

- **Precondition**: a workspace whose demands are partly assigned by relations and partly by recorded assignments, with the exemptions array available
- **Postcondition**: the report names per axis the assigned count and the relation mix, and one line of distribution across packages; the verdict is holds exactly when every axis has no unassigned demand and the refused list is empty
- **Invariant**: assigned and exempted are never conflated, the partition stays total and disjoint, and a workspace assigning every demand to one package still reports holds with its distribution printed

## Boy Scout Rule

Translatability plan for the modules this ticket touches. Functions are verb phrases naming the object they carry: readPackageObligations, classifyAssignments, refuseUnexemptibleDemand, renderAssignmentDistribution, reportUnassignedDemands. Variables are domain concepts: obligationRecord, assignments, adjudications, refusedExemptions, assignmentDistribution, demandSummary. One responsibility per function: the record reader reads and normalizes, the refuser decides and returns a finding, and the distribution is computed once in the coverage module so no renderer can invent its own. Literals become named constants beside their measured value: the record basename, the record version, the two demand kinds that may never be exempted, and the relation names as one frozen list shared by the coverage module and both renderers. No error is swallowed: an unreadable record names the path, an unknown assignment unit names the id, and a refused exemption names the demand and the rule it broke. Existing code improved where this ticket touches it: lib/obligation.mjs currently reads two sources and defaults silently when neither is present, which is replaced by a three-source precedence that reports which source answered; check-obligation-coverage.js prints totals where it should print the distribution, which is replaced by one computation shared with the view renderer.
