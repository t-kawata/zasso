# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — the package obligation record to the exemption set

- **Precondition**: a package obligation record at the package root whose `adjudications` list carries rows of shape `{ column, ground }` with a non-empty column; a workspace whose candidate columns are derived from the artifact's pins crossed with its operation rows; the artifact carrying the sections and the operation and sequence ids a ground may cite
- **Postcondition**: readPackageObligations returns the adjudications normalized beside serves and assignments; the view carries them as `adjudicatedColumns`; collectAdjudicationRows maps each into a row of `{ subject, lens, why, route: 'record' }`; the refuser receives the artifact rows and the record rows merged and returns one allowed list and one refused list; a column so adjudicated is exempt for the surface axis and reaches no partition of the other three
- **Invariant**: a row from the record and a row from the artifact naming the same demand are decided identically, and neither route can exempt an operation or a sequence; a record with no adjudications list behaves exactly as a record written before this ticket; an adjudication names a column and never a unit, so no unit id is created, renamed or retired by it

### C002 — a recorded ground to the evidence it cites

- **Precondition**: a ground string on an assignment or an adjudication, and an artifact carrying `spec.lines`, `sections[].id`, `operations[].id` and `sequences[].id`
- **Postcondition**: resolveGround returns `{ resolved: false, unresolved: [] }` for a ground carrying no reference at all, `{ resolved: true, unresolved: [] }` when every reference it carries resolves, and `{ resolved: false, unresolved: [...] }` naming each reference that does not; measureCoverage collects the unresolved grounds of every grounded row of both routes and of every grounded assignment, and the verdict cannot be holds while that list is non-empty
- **Invariant**: resolution reads the artifact and never a list compiled into this repository, so a project whose sections are named `s1` and whose sequences are named `G-1` is checked against its own document; a line reference resolves only when the line lies within the artifact's own line count; a ground carrying one resolvable and one unresolvable reference is unresolved A reference that resolves is not a reference that supports the claim: the resolver reads whether a line, a section or an id exists in the artifact, and cannot read whether the sentence on that line says what the ground says it says. That limit is printed by the gate rather than left to be inferred.

### C003 — a declared interface to what the artifact carries and to what its column actually is

- **Precondition**: a declared interface of shape { interfaceId, column, operationSet } in the package obligation record, and an artifact whose operation rows may or may not carry that column, whose pinned enumerations are the vocabularies a column may instantiate
- **Postcondition**: classifyServes reports crossChecked false when no operation row carries the column; it reports foreignValues, the distinct non-empty values of the column that instantiate no member of the declared operationSet; the gate reports a declaration with any foreign value, or with a column no operation row carries, by name as binding nothing, and exits 1
- **Invariant**: a declaration is accepted only when every value of its column instantiates the vocabulary it declares, which is the dual of the candidate rule that accepts a column when at least one value does — candidates over-approximate so no column escapes unremarked, and declarations under-approximate so no column joins the coverage vacuously; the counts a declaration reports are read from the artifact and never from the declaration

### C004 — the measured demand to its durable record

- **Precondition**: a specification carrying an artifact beside it, with or without an allocate manifest and with or without package views beneath the package root
- **Postcondition**: writeDemandRecord writes <dir of spec-file>/educe-sequences/demand.json carrying the facts the artifact states, the partition measured over the workspace and the specification digest it was measured against; the product path writes it when its verification passed and a summary exists, and the phase driver writes it when it holds a summary; a refused run writes no record
- **Invariant**: the record is idempotent — the same specification and workspace produce byte-identical bytes — and on the verification path the artifact is byte-identical before and after the write. The invariant is scoped to the verification path deliberately: a run holding readings writes the artifact, and stating the invariant without that scope would make it false there. The record is a snapshot of the run that wrote it, never the live answer, because a grill run resolves demands without re-running the rail

### C005 — a workspace without the obligation concept to the resolution loop

- **Precondition**: a workspace root that carries no sequences artifact, or an artifact but no allocate manifest; or a workspace that carries both, whose package root holds packages the tree manifest names
- **Postcondition**: check-obligation-coverage.js refuses the root by name and exits 1; the grill STEP 1 states that such a workspace has no measurable demand, that the refusal is the gate answer rather than unfinished work, and that the run proceeds exactly as before this ticket; a workspace that does carry an artifact is measured, its unassigned demands are named by axis and id, and the re-projection the loop names is run for every package the tree manifest names and not for one of them
- **Invariant**: no instruction either command file carries can require an action a refused gate makes impossible; every loop the documents state has a reachable exit on every workspace they admit

### C006 — the units a view holds to the ledger that accounts for them

- **Precondition**: a workspace whose package root holds views carrying unit ids, and whose packages may or may not carry an RFC.md beside those views with a distribution ledger appendix
- **Postcondition**: check-ledger-discharge.js reads each package RFC.md through the slice own readDistributionLedger, reports by package and unit id every unit no ledger accounts for, and reports apart a package with no ledger, a package whose ledger is not well formed, and a package whose well-formed ledger omits named units; it exits 0 only when every unit every view holds is accounted for, and it is named in the STEP 8 condition sentence beside the assignment gate
- **Invariant**: the ledger is parsed by one implementation, the slice own, so the workspace gate and the per-package report cannot disagree; a package that was never grilled is reported rather than silent, because the gate walks the package root and does not depend on a run having happened; and the assignment gate verdict is untouched by this gate, so STEP 1 and STEP 3 keep a contract that a workspace without an RFC can satisfy

## Boy Scout Rule

Translatability plan for the modules this ticket touches. Functions are verb phrases naming the object they carry: readPackageObligations, classifyAdjudications, collectAdjudicationRows, refuseUnexemptibleDemand, findReferences, resolveGround, writeDemandRecord, renderRefusedExemptionLines, renderUnresolvedGroundLines, renderUnboundDeclarationLines, renderUnaccountedUnitLines. Variables are domain concepts: adjudications, adjudicatedColumns, unresolvedGrounds, exemptionRoute, demandRecord, carriedLineCount. One responsibility per function: the ground module decides what a ground cites and nothing else; the refuser decides and returns a finding; the record writer writes one document and never reads the artifact back. Literals become named constants beside their measured value: the run-directory record name, the exemption route names, the reference forms, and the sentence the guarantee boundary is printed with. No error is swallowed: an unreadable record names the path, a refused exemption names the demand and the rule, an unresolved ground names both the reference and the demand that carried it, and a declaration that bound to nothing names the column.
