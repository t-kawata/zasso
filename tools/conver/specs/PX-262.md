# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

Goal: the obligation-coverage verdict must not be pronounced on an artifact that is its own denominator, and the absence of a denominator must be a named finding rather than a silence.
Purpose: close the last hole in the guarantee chain. Every other link is already closed by a named refusal — the specification reaches the tree through the section census, the tree reaches the allocation through checkContractClauseKeys (C3), the allocation reaches the demand through source_coverage, and the demand reaches the distribution through check-obligation-coverage.js. The denominator of the demand set is the one link that is borrowed and whose borrowing is optional.
Motivation, measured in source: the rail guards its two totality checks with when: borrowedCensusOf(context, role) !== null, at every-enumerated-operation-accounted-for and every-censused-entry-adjudicated in .claude/scripts/educe-sequences/rail/engine.mjs. Everything downstream is therefore closed against a denominator that nothing outside the artifact confirmed. Load-bearing prohibition: the rail must never refuse for a missing denominator. Withholding belongs to the gate alone, because inverting the census guard inside the rail would refuse every project that never supplied census material, which is exactly the re-execution case the second constraint requires to be reinforced.

## Acceptance Criteria

- Happy path: a workspace that borrows a census for the operations and entries roles, carries a registered boundary for every declared one, and holds every demand assigned and every ledger row accounted for yields verdict holds from check-obligation-coverage.js and discharged from check-ledger-discharge.js, and a re-run of the rail over the same workspace leaves both verdicts unchanged while restamping the demand record
- Error case: a workspace in which every demand is assigned but no census is borrowed yields verdict not established, one denominator line per unstated axis carrying the axis, the reason and the repair, and exit 1 from the gate — while the rail run over the same workspace exits 0 and writes its record, which is the load-bearing prohibition holding under the case that most tempts a refusal
- Edge case: an old project that never carried the obligation concept, re-run end to end, gains the relation units in its views, gains its OBLIGATION.json and its demand record carrying borrowed false for the axes with no census, is refused by nothing, and is told by the gate which axes are unstated and what to supply — so the re-run reinforces rather than refuses

## Invariants

【Normal establishment】Every demand axis names the external structure it is measured against, and the coverage verdict is pronounced only when all four axes are stated and every demand is placed by a route that resolves — an assignment with a resolving ground, or an exemption allowed by rule.
【Invariant on error】An unstated denominator yields verdict not established with the axis named, never verdict holds, and never a refusal of the run: the rail writes and the gate withholds. The set of refusal sentences reachable inside the rail is unchanged by this ticket.
【Internal invariant】The demand total is invariant under the addition of an exemption — only the relation changes, from assigned to exempted — and the record version selects the rule set, so a record written before this change is read under the rule set it was written under.
【Boundary invariant】With sources omitted, resolveGround reproduces the previous fail-closed answer exactly for every identifier prefix, so every existing caller and its tests keep their behaviour byte for byte.

## Boy Scout Rule

Function names are verb phrases — denominatorOf, gapsIn, renderDenominatorLines, reportObligationState — and these are the only names this ticket adds. Variables name domain concepts: axis, source, members, borrowed, carriedBy, sources, boundaries, surfaces, repair. One function carries one responsibility: denominatorOf measures the four axes and decides nothing, gapsIn decides which axes are unstated and names the repair, the gate renders and exits, and the rail writes and refuses nothing — the existing split between the slice library that decides and the gate that renders is preserved rather than bypassed. Every vocabulary this ticket touches becomes a named frozen constant rather than a literal at the point of use: the four axis names, the four source spellings including unstated, and the record versions, beside the existing DEMAND_AXES, UNIT_KIND_BY_PREFIX and OBLIGATION_RECORD_VERSION. No error is swallowed: an unreadable record still names its path and version, an unstated axis names itself and its repair, and an unresolved ground names the reference and the demand that carried it. Boy Scout improvements inside the files this ticket touches: the two null values in UNIT_KIND_BY_PREFIX stop being anonymous fail-closed answers and become named lookups into the supplied sources, and the demand record grows a documented block rather than an inline object literal at the call site.
