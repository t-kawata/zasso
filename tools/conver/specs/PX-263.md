# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

Goal: express "the obligations, the ownership, the served surfaces and everything else are distributed without omission, and that distribution is checked" as a closed, decidable criterion, implement it as code, and make every clause of it measured at the place it is claimed.

Why this ticket exists at all. Four rounds have closed one named hole each — the relations, the assignment gate, the grounds and the adjudication route, the denominator — and each round left residue that the next round planning discovered. The mechanism is not that the holes were hard; it is that each round scope was a hole rather than a property, and each round definition of done was "the hole I named is closed", which is satisfiable while the property is false. This ticket changes what is produced first: a criterion, not a plan.

The completeness procedure this ticket encodes. Every clause the system claims, in the guarantee sentence a gate prints and in the verdict a gate returns, is enumerated; each clause must have exactly one check that measures it, at the place it is claimed. A clause with no measuring check, or one measured only in another command, is a hole. Applied by hand to the current tree this procedure found a fifth hole that four rounds of hole-chasing missed, which is the evidence that the procedure is worth encoding.

Constraint, absolute: educe-sequences.md and grill-me-for-rfc.md must not lose any existing function, must remain usable exactly as before, and repeated execution must keep evolving the target, including re-execution against old projects that never carried the obligation concept, which must be reinforced and never refused. Two disciplines follow and are load-bearing. First, every tightening lands in the gate verdict and never in the rail run. Second, the accepted denominator is widened and never narrowed, so a workspace that holds today cannot be demoted by this change.

Constraint, absolute: nothing here may be specific to one project. Every clause is written against structures every project has — the artifact pins, the contract registry, the tree manifest, the package records, the distribution ledger — and every clause is measured on a synthetic fixture before it is measured on any real workspace.

The one residual, named rather than closed. Whether the specification names every procedure the project needs is not derivable from the specification, so no clause can measure it. The guarantee is therefore totality relative to the specification. The criterion states this as a boundary line it prints, so that nobody reads a satisfied criterion as a claim about the world. This is not a contradiction with the guarantee requirement: that requirement says implementing every sequence and operation means the required procedures are implemented, and the "means" there is exactly this assumption, so the requirement asks for the assumption to be named rather than eliminated.

【Invariant on error】No short clause refuses a run. The rail writes and the gate withholds, so a project that never carried the obligation concept is reinforced rather than refused, and the set of refusal sentences reachable in the rail is unchanged by this ticket.
【Internal invariant】Every accepted route is widened and none is narrowed, so a workspace whose clause held before this change still holds after it — asserted monotone over the fixture set for the denominator and reproduced exactly for the ground resolver when its optional sources are omitted.

## Boy Scout Rule

Function names are verb phrases — criterionFindings, sectionIdentifiersOf, evaluate — and the only noun-shaped export is CRITERION_CLAUSES, which is a value and not a function. Variables name domain concepts: clause, claim, measuredBy, state, sources, sections, location, carrier. One function carries one responsibility: the criterion evaluates and decides nothing about repair, the completeness gate renders and exits, the discharge gate reads the ledger through the one parser the repository has, and the commit hook decides only whether the command is a git form — the split between the library that decides and the gate that renders is preserved rather than bypassed. Every vocabulary this ticket touches becomes a named frozen constant: the clause ids, the finding states, the reference forms including the new section form, and the guarantee lines, beside the existing DEMAND_AXES, DENOMINATOR_SOURCES and UNIT_KIND_BY_PREFIX. No error is swallowed: an unreadable artifact names its path, a clause that cannot be evaluated reports that rather than passing, a location that does not resolve names the location and the package, and the commit hook names its reason on stderr for input it cannot parse while still exiting 0. Boy Scout improvements inside the files this ticket touches: the guarantee lines stop being string literals inside a renderer and become a named constant the closure test can read, and the two sites that check a ledger location stop disagreeing about how strictly to read the same field.
