# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- Happy path: a run whose supplied/ holds material carrying a census, with a pin declared for each role the material answers for, completes phase 4 and records pins.sourceEnumerations with the members read from each file and each source digest; check-obligation-coverage.js then reports the operations and sequences axes as stated rather than unstated.
- Error case: a run whose supplied/ holds a file no pin names is refused at phase 4 with the file named, the roles no pin answers for named, and both repairs stated; a run whose declared pin reads a document mixing two row shapes is refused with the first offending row named and told to split the document.
- Edge case: a workspace where some allocated packages carry no view, projected by the workspace form of the slice, gains a view for each package the material can carry and a named residue for the rest; running it a second time leaves every existing view byte-identical and reports the same residue.

## Invariants

- 【Normal establishment】Every supplied file is accounted for exactly once: either a declared sourceEnumerations pin names it and the pin records source.file, source.sha256, selector.shape, selector.parameter and members, or the phase-4 gate refuses with the file named. The set of supplied files is partitioned, never both and never neither.
- 【Invariant on error】A supplied file no pin names refuses the phase by name; a declared pin whose selector cannot read its document records the refusal and empty members, and the refusal names the first offending element. No failure path leaves members holding fewer entries than the document states.
- 【Internal invariant】SOURCE_SHAPES stays the closed vocabulary ['jsonFieldRows','tableColumn','markedLines'] and SOURCE_ROLES stays ['operations','entries']; extractMembers stays total over the elements a shape claims, so an element it cannot read is refused by name rather than skipped, and the member count cannot fall without a failure.
- 【Boundary invariant】A re-run over a workspace that already carries views and OBLIGATION.json files rewrites no view byte-wise and deletes nothing; a package the material cannot carry is reported by name and its directory is left exactly as found.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — supplied material -> rail pins

- **Precondition**: The run directory holds a supplied/ directory whose files are readable as text, and the declaration carries sourceEnumerations[] entries whose selector.shape is one of SOURCE_SHAPES and whose selector.parameter is a non-empty string
- **Postcondition**: Every supplied file is accounted for: either a declared pin names it and the pin records source.file, source.sha256, selector and members, or the phase refuses with the file named
- **Invariant**: No supplied file is both named and reported, and no supplied file is neither

### C002 — declaration selector -> census members

- **Precondition**: selector.shape is one of jsonFieldRows, tableColumn, markedLines and selector.parameter is a non-empty string
- **Postcondition**: members holds one entry per element the shape claims, in document order; a document the shape cannot read yields a refusal naming the first offending element and members is empty
- **Invariant**: A member is never dropped silently: an element that cannot be read produces a refusal, so the member count cannot fall without a failure

### C003 — allocation manifest -> package views

- **Precondition**: A workspace holds an allocate manifest naming packages, a tree manifest resolving each package to a directory, and a sequences artifact
- **Postcondition**: Every allocated package the material can carry holds a SEQUENCES.json and SEQUENCES.md matching the single-package projection; every package the material cannot carry is reported by name with its reason
- **Invariant**: The union of projected packages and reported packages is the set the allocation names, and a package already carrying a view is left byte-identical

### C004 — unstated denominator -> refusal reachable by the operator

- **Precondition**: A run holds supplied material that carries a census and records no pin for a role the material answers for
- **Postcondition**: The phase-4 refusal names the supplied file and the roles no pin answers for, so the unstated denominator that check-obligation-coverage.js would report is reachable from the refusal alone
- **Invariant**: The refusal precedes the artifact: a run that would produce an unstated denominator does not close phase 4

### C005 — re-run over an old project -> reinforcement without loss

- **Precondition**: A project written before sourceEnumerations existed is re-run with the current rail, its views already present and its OBLIGATION.json files absent
- **Postcondition**: The run records no pin for a census it was not given, refuses by name when it is given one unpinned, and rewrites no existing view
- **Invariant**: Nothing the project already holds is deleted or overwritten by the re-run

## Boy Scout Rule

Translatability plan for every file touched. Functions: name them by what they do rather than by what they return — suppliedFileNamesOf(runDirectory) reads as 'the supplied file names of this run', unnamedSuppliedFilesOf(pins, names) reads as 'the supplied files no pin names', and reportWorkspaceSlice(...) reads as 'report what the workspace slice did'. Variables: replace index-shaped names with domain names (suppliedFileName, pinNames, rolesAnswered, memberCount) so a refusal line can be read aloud as a sentence. One responsibility per function: the partition predicate lives once and is called by both the gate and the report, so the finding and the refusal cannot disagree about which file is named — the same discipline view.mjs already applies to unboundAssignments. Hardcoded values: the two repairs are named constants (PIN_OR_REMOVE_REPAIRS) rather than repeated prose. Swallowed errors: run.mjs keeps its rule that every failure is a reported reason and exit 0, and the new workspace form keeps it — a package it cannot project is reported, never thrown. Proactive improvement inside the touched code: the phase-4 guidance and the command text are rewritten to state the document shape the selectors read, so a reader no longer needs the rail's source to supply a census.
