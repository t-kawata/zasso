# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-265: Let a supplied file that answers for nothing be declared as such, so an omission stays loud without forcing material to be deleted

**Ticket Key**: PX-265 · **Phase**: -1

---

## Background

- 【Goal】Let the declaration state that a supplied file answers for nothing, so that PX-264's refusal keeps its force where a census was omitted while a run is not made unrunnable by material that is not a census.
- 【Purpose】PX-264 made an unread supplied file loud by refusing at phase 4 when no pin names it. The rule is right in purpose and too strong in effect, because its first repair — declare a pin whose selector reads the file — is unavailable for most material: every census shape is total over the elements it claims, so extractJsonFieldRows refuses a block whose rows disagree, extractMarkedLines refuses a line that does not begin with the prefix, and extractTableColumn refuses a row that stands beneath no header. A JavaScript file, a prose document or a mixed markdown is refused by all three, and the two repairs collapse into removal.
- 【Motivation】Measured on ~/shyme/gaia: the supplied directory holds nine files, of which one is guidance, two are censuses, and six are material the invocation filed. None of the six is a census — all 178 sequence-adjudication entries and all 61 sequence-step sequence ids already occur in declaration.entries, and the 298 section-adjudication rows share no id with declaration.sections — so each is a record of what the operator read. Pinning a reading as a census would make the artifact answer to itself, which is the circularity the borrowed census exists to break. Deleting the material instead loses the record of what the run was given, and contradicts the requirement that a re-run over an existing project stay usable.
- 【Constraints】The change is additive: a census pin behaves exactly as before, an artifact without a material declaration is read identically, and the refusal keeps firing for a file named by neither kind. Nothing project-specific may enter the rail — the vocabulary is 'answers for nothing', not 'is a checker script'. The regression surface is the borrowed-census contract of PX-248 and the artifact schema, both of which are exercised by existing tests.

## Investigation

Measured, not inferred. (1) The rule this ticket relaxes: PX-264's phase-4 gate refuses when unpinnedSuppliedFiles(ctx, pins) is non-empty, and pinnableSuppliedFiles(directory) excludes only MATERIAL_FILE, so every other file in supplied/ must be named by a sourceEnumerations entry. (2) Why the first repair is unavailable: extractJsonFieldRows refuses a fenced block whose rows disagree about the field, extractMarkedLines refuses a line that does not begin with the prefix, and extractTableColumn refuses a row standing beneath no header — each is total over the elements it claims, by design, because a skipped element is a member that leaves a census without anything failing. Measured against gaia's material: jsonFieldRows on procedure-registry.md refuses for kind, purpose, spec_name, id, operation and name, and markedLines on the same file refuses on its first line. (3) What the six non-census files are: check-registry.mjs is a node script of 1935 lines beginning with a shebang and the comment 'Procedure Registry completeness checks'; registry-completeness-checks.md is its 939-line document; section-adjudications.jsonl holds 298 rows keyed section, category and reason; sequence-adjudications.jsonl holds 178 rows keyed entry, category, reason and audit; sequence-steps.jsonl holds 614 rows keyed seq, step, spec_line, subject, predicate, object, contract, operation, quote and grounding; totality-exemptions.jsonl holds one row keyed axis, member and reason. (4) Why none of them is a census: all 178 sequence-adjudication entry ids occur in declaration.entries, all 61 distinct sequence ids in sequence-steps.jsonl occur in declaration.entries, and none of the 298 section-adjudication section ids occurs in declaration.sections — so each is the operator's own record of a reading, and holding the artifact to one would make it answer to itself. (5) The code the change lands in: establishPins maps declaration.sourceEnumerations through extractMembers with the entry's selector, recording members and refusal; rederiveSourceEnumeration checks the role against SOURCE_ROLES when it is present, requires the file beside the run, checks the digest and then compares members both ways; artifact-schema.json requires name, role, source, selector and members of every entry, with source requiring file and sha256 and selector requiring shape and parameter. (6) The gate needs no change: unpinnedSuppliedFiles collects the names from pin.source.file, which a declaration records exactly as a pin does, so a declaration answers for its file without touching the predicate.

## Acceptance Criteria

- Happy path: a run whose supplied/ holds one census and one record, with the census named by a pin carrying a selector and the record named by an entry carrying a ground and no selector, completes phase 4 and phase 6, records the census members from the file and an empty member list for the record, and reports the role the census answers for as borrowed rather than unstated.
- Error case: a supplied file named by neither kind is refused at phase 4 with the file named; an entry carrying no selector and no ground is refused by name; and an entry carrying a selector but no parameter is refused with the shape named, exactly as before this change.
- Edge case: an artifact written before this change, holding sourceEnumerations absent, empty, or with census pins only, loads through the schema check and re-derives every pin with no new problem reported; and a run whose only declaration answers for nothing leaves both the operations and the sequences axes reported as unstated.

## Invariants

- 【Normal establishment】Every supplied file other than the guidance file the invocation writes is named by exactly one sourceEnumerations entry, and each entry is of exactly one kind: a census pin, which carries selector.shape from SOURCE_SHAPES and a non-empty selector.parameter, or a material declaration, which carries no selector and a non-empty ground.
- 【Invariant on error】A supplied file named by neither kind refuses the phase by name. A material declaration whose ground is empty or whitespace refuses by name, because a declaration that says nothing is the silence this ticket exists to convert into a statement.
- 【Internal invariant】A material declaration contributes no member to any census and is never handed to a shape: it records members as an empty list and refusal as null, so the accounting of a census cannot see it and the re-derivation of a census cannot be satisfied by it.
- 【Boundary invariant】An artifact written before this change — one that carries sourceEnumerations absent, empty, or holding census pins only — loads and re-derives exactly as it did, with no new problem reported by the schema check.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — supplied material -> declaration statement

- **Precondition**: The run directory holds a supplied/ directory whose files are readable as text, and the declaration carries sourceEnumerations[] entries each of which is either a census pin (selector.shape is one of SOURCE_SHAPES and selector.parameter is a non-empty string) or a material declaration (no selector, with a ground string explaining what the file is)
- **Postcondition**: Every supplied file other than the guidance file is accounted for: it is named by exactly one entry, of either kind, or the phase refuses with the file named
- **Invariant**: No supplied file is both named and reported, and no supplied file is neither

### C002 — material declaration -> re-derivation

- **Precondition**: A sourceEnumerations entry carries no selector, carries a ground string, and names a supplied file whose bytes are beside the run
- **Postcondition**: Re-derivation checks the digest and the ground and computes no members; the entry records members: [] and refusal: null, and no shape is consulted
- **Invariant**: A material declaration never refuses for the absence of a selector, and never contributes a member to any census

### C003 — census pin -> re-derivation (unchanged)

- **Precondition**: A sourceEnumerations entry carries a selector whose shape is one of SOURCE_SHAPES and whose parameter is a non-empty string, and names a supplied file beside the run
- **Postcondition**: The members are re-extracted from the file and compared with the recorded members in both directions, and a member the file does not carry or a row the pin does not list refuses by name
- **Invariant**: The behaviour of a census pin is exactly what it was before this change, for every shape and every mismatch

### C004 — old artifact -> load and re-derive (backward compatibility)

- **Precondition**: An artifact written before this change carries sourceEnumerations entries that are either absent, empty, or census pins with a selector
- **Postcondition**: The artifact loads and every pin re-derives exactly as it did before, with no new problem reported by the schema check
- **Invariant**: An artifact that carries no material declaration is read identically before and after the change

### C005 — phase-4 gate -> the declaration answers

- **Precondition**: Every supplied file other than the guidance file is named by an entry, at least one of which is a material declaration
- **Postcondition**: The phase-4 gate does not refuse for those files, and the roles answered by census pins are reported as borrowed while the roles answered by nothing stay unstated and are named as such downstream
- **Invariant**: A material declaration silences the unpinned-file refusal for its own file only, and borrows no census for any role

## Boy Scout Rule

Translatability plan for every file touched. Functions: name them by what they answer rather than by what they return — an entry-kind predicate reads as 'the entry that answers for nothing', and the branch in rederiveSourceEnumeration reads as 're-derive a declaration by its digest'. Variables: replace index-shaped names with domain names (suppliedFileName, declarationGround, entryKind) so a refusal line can be read aloud as a sentence. One responsibility per function: the predicate that decides which kind an entry is lives once and is called by the schema check, establishment and re-derivation, so the three cannot disagree about what an entry is — the same discipline PX-264 applied to the partition of supplied files. Hardcoded values: the two kinds are named constants rather than repeated string literals. Swallowed errors: a declaration whose file moved reports both digests rather than an empty member list, so nothing fails quietly. Proactive improvement inside the touched code: the phase-4 guidance and the command text state both kinds, so an operator no longer has to infer the rule from the refusal.

- 【Caveats】A declaration is not an exemption from the axis question: it borrows no role, so a workspace whose censuses are declared away keeps its axes unstated, and check-obligation-coverage.js keeps reporting them. The two mechanisms are independent and the notes on the consuming ticket say so.
