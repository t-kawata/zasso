# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-276: derive the smooth-sequences vocabulary from the artifact instead of a hand-written rules file

**Ticket Key**: PX-276 · **Phase**: -1

---

## Background

Goal: remove SMOOTH-SEQUENCES-RULES.json as a human-authored input and let the detector derive the terminal-status and required-interface vocabularies from what the pipeline already wrote.
Purpose: the two vocabularies are restated facts. The artifact carries every active operation status graph (allowed_status_transitions), the allocate manifest can declare interface columns (declared_interfaces), and the artifact pins the operation columns whose values spell an interface.
Motivation: PX-275 removed project-specific names from the detector by moving them into a file a human must write and keep valid. That created a third source of truth that can drift from the artifact and the manifest, and its only failure mode is exit 2 with no information gained. Every workspace already states the same facts where it states its operations.
Constraints: the replacement field is optional and additive; schema_version stays 3; derivation runs whenever the field is absent; a rules file left on disk is ignored and never opened; an unchanged workspace keeps its verdicts and byte-identical inputs; no project-specific token enters the detector.

## Acceptance Criteria

- Happy path: a fixture with no rules file and an artifact that declares vocabulary exits 0 with findings [] and withheld []; a fixture without the field derives terminalStatuses [closed] and requiredInterfaces [rest, grpc, cli] from its status graph and declared_interfaces and also exits 0 with withheld [].
- Error case: a declared vocabulary with a non-array list or a non-string member exits 2 with INVALID_VOCABULARY and writes no report, while the planted terminal and interface defects still produce S3.transition-out-of-terminal and S3.interface-mapping-missing with repairs.
- Edge case: an underivable terminal or interface vocabulary is named as withheld and exits 0, a malformed or unrelated SMOOTH-SEQUENCES-RULES.json on disk changes nothing, and no detector source contains the removed file name.

## Invariants

- 【Normal establishment】loadVocabulary returns a frozen value whose two lists are arrays of unique non-empty names or null; a declared artifact.vocabulary is returned unchanged in first-seen order.
- 【Invariant on error】a declared vocabulary that violates its shape raises SmoothSequencesError code INVALID_VOCABULARY and run.mjs exits 2 without writing a report; an underivable vocabulary is withheld, never guessed and never treated as a pass.
- 【Internal invariant】checkOperationEnvelope reads only index.vocabulary, workspace.mjs never opens SMOOTH-SEQUENCES-RULES.json, and no module under smooth-sequences names it.
- 【Boundary invariant】derivation never drops a name because one operation lacks it; membership comes from the status graph or the declared interface columns, so a missing mapping remains a finding.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — artifact vocabulary declaration

- **Precondition**: the artifact carries vocabulary as an optional plain object whose terminalStatuses and requiredInterfaces are arrays of non-empty strings
- **Postcondition**: loadVocabulary returns exactly the declared names de-duplicated in first-seen order and performs no derivation
- **Invariant**: a declared list wins over every derivation, including a list naming a status no operation reaches

### C002 — terminal derivation

- **Precondition**: artifact.vocabulary.terminalStatuses is absent or null and at least one active operation declares allowed_status_transitions
- **Postcondition**: the returned set is the union of source statuses whose target list is empty across active operations
- **Invariant**: a status with a non-empty target list in one operation is in the set whenever another operation terminates at it, and S3 flags the transition

### C003 — interface derivation

- **Precondition**: artifact.vocabulary.requiredInterfaces is absent or null
- **Postcondition**: the returned set is the union of allocate-manifest declared_interfaces columns, else collectCandidateColumns(artifact), else null with a withheld entry
- **Invariant**: the set does not depend on operation membership, so a missing column stays required and yields S3.interface-mapping-missing

### C004 — rules file removal

- **Precondition**: the workspace root contains SMOOTH-SEQUENCES-RULES.json with any bytes, or contains no such file
- **Postcondition**: the detector never opens the file and the exit code, findings, withheld list and vocabulary are identical in both cases
- **Invariant**: no module under smooth-sequences names SMOOTH-SEQUENCES-RULES.json or RULES_FILE_NAME
