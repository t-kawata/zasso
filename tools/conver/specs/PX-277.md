# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-277: Make the smooth-sequences repair loop the command body and print telegraphic repair routes

**Ticket Key**: PX-277 · **Phase**: -1

## Background

### Goal
Every finding the smooth-sequences detector emits names, in one telegraphic line, where the defect lives, what it is, why it is wrong, and how to repair it; and `/smooth-sequences` is structured as a repair loop that cannot complete until a fresh run exits 0.

### Purpose
The detector already decides correctly, but `run.mjs:67` prints only the finding count and a path, so the executing AI must open `SMOOTH-SEQUENCES.json` and infer the repair. The command document spends Steps 1-3 describing what one invocation checks rather than what the AI must do; Step 0 and Step 5 invoke the same command twice.

### Motivation
`/smooth-sequences` is the last gate before implementation. A gate whose repair procedure is implicit cannot be executed reliably: the loop, not the detection, is the work. The current `repair` strings even instruct hand-editing generated files — `checks-layer-a.mjs:110` says to add a contract to `WORKSPACIFY-ALLOCATE-MANIFEST.json` — contradicting the command's own never-hand-edit rule, so the executing AI must guess which instruction wins.

### Constraints
Detection stays deterministic and LLM-free; the loop's completion signal is the script's exit code, never an AI judgment. Exit codes stay 0 pass / 1 findings / 2 misuse. Withheld surfaces remain distinct from findings. v2 artifacts remain supported. No new dependency.

## Acceptance Criteria

- [Happy path] A clean workspace prints `0 finding(s)`, `next: none` and `verdict: pass`, and writes schemaVersion 2 reports with no finding lines.
- [Error case] A workspace with a missing interface mapping exits 1, prints one route block naming the specification path, the why and the /educe-sequences producer; the block disappears only after the mapping is repaired and the command is rerun.
- [Edge case] A v2 artifact with no findings exits 0 while listing the Layer B withheld surface and saying not proved; a missing workspace exits 2, prints the misuse repair and next, and writes no report.

## Invariants

- [Normal establishment] Every finding carries non-empty `where`, `why`, `fix` and `producer`; no finding carries `reason` or `repair`.
- [Error invariant] exit 1 always writes both reports and never prints a completion verdict; exit 2 writes no report and names the misuse repair.
- [Internal state invariant] Console, Markdown and JSON derive from the same sorted finding list; `persisted` is computed once from the previous report.
- [Boundary invariant] exit 0 holds if and only if `findings` is empty; withheld surfaces never become findings; no fix instructs hand-editing a generated file.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — finding record

- **Precondition**: a check emits a finding for a workspace defect and supplies where, why, fix and producer
- **Postcondition**: the finding carries non-empty where, why, fix and producer and carries neither reason nor repair
- **Invariant**: a finding missing any of the four fields is rejected before it can be rendered or reported

### C002 — repair route table

- **Precondition**: every checkId literal passed to finding() in the smooth-sequences lib is looked up in REPAIR_ROUTE_BY_CHECK_ID
- **Postcondition**: repairRouteFor returns a where naming the authored surface and a producer naming the command that re-derives the verdict
- **Invariant**: an unknown checkId throws UNROUTED_FINDING, and no route fix instructs hand-editing a generated file

### C003 — console output

- **Precondition**: runCommand runs against a workspace with one or more findings
- **Postcondition**: stdout carries every finding line with checkId, subject, where, why and fix, grouped under a route header naming the producer, and ends with a next line
- **Invariant**: a clean run prints next: none and no finding line

### C004 — exit gate

- **Precondition**: a run has findings
- **Postcondition**: the exit code is 1 and the report is written; the console never renders a completion verdict
- **Invariant**: exit 0 holds if and only if findings is empty; withheld entries are listed and never called proved

### C005 — previous report

- **Precondition**: SMOOTH-SEQUENCES.json from the previous run carries a finding with the same checkId and subject
- **Postcondition**: the new finding carries persisted true and the console marks it
- **Invariant**: a first run, an unreadable previous report or a changed subject marks nothing persisted

### C006 — command document

- **Precondition**: the command document is read as text
- **Postcondition**: its body is Step 0 Prepare, Step 1 Repair loop, Step 2 Complete, and the S1-S7 descriptions live under Reference
- **Invariant**: the document states that the loop's only exit is a fresh exit 0 and that exit 1 cannot be reported as completion
