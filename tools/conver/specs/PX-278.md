# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-278: Make thaw and refreeze a script-owned transaction that guarantees a verified rollback

**Ticket Key**: PX-278 · **Phase**: -1

---

## Background

### Goal
Make thaw and refreeze a script-owned transaction: once a thaw is opened, the workspace either commits a fully verified new generation or is restored byte-identically to the old one. The AI never decides whether the chain is valid, never supplies a hash, and never edits a frozen file in place.

### Purpose
PX-277 made every finding name an authored surface and a producer, but it routed 22 of 31 checkIds to the specification and to allocate finalize. Both are frozen, hash-chained, one-shot artifacts: the tree refuses a different input hash, allocate refuses an existing target, and the grill guard refuses the specification by name. Following PX-277's routes can therefore either desynchronize the manifests silently or deadlock the repair loop.

### Motivation
The pipeline must support change. A freeze is a provenance rule (no silent change), not a ban on change. The safe way to change a frozen artifact is an explicit transaction that derives a new generation in isolation, verifies every link and every grounded judgment, and publishes atomically with rollback. Without that path, /smooth-sequences cannot satisfy its own 'exit 0 only when every finding is closed' gate.

### Constraints
- The live design files are byte-identical during open, derive and verify; only commit writes them.
- No force flag and no hash argument; hashes are computed by the script.
- A broken baseline opens no transaction; a failed refreeze leaves the old generation usable.
- Each link verifies with the digest function of the producer that wrote it.
- The educe reading phases and the grill judgments remain AI work; the transaction orchestrates and verifies them, it does not replace them.
- No new dependency.

## Investigation

- The chain is explicit: `tree.input.source_hash` is the LF-normalized spec SHA-256; `tree.integrity.manifest_hash` is the tree self-hash; `allocate.input_tree_manifest.hash` equals it; `allocate.input_tree_manifest.spec.sha256` and `artifact.spec.sha256` equal the spec hash; `allocate.integrity.manifest_hash` is the allocate self-hash; `seed_index[].sha256` covers every seed (verified on gaia: 5ccc..., 684c..., eb5d...).
- tree refuses an existing manifest with a different input hash (`workspacify-tree/lib/atomic-publish.mjs:33-42`). allocate refuses an existing target (`workspacify-allocate/lib/tree-staging.mjs:123-126`) and re-hashes the co-located spec (`workspacify-allocate/lib/tree-manifest-input.mjs:224`). grill refuses the specification and WORKSPACIFY-* by name (`grill-me-for-rfc.md:47-51`, `guard-edit-surface.js:36-53`).
- educe already opens generations and archives readings (`educe-sequences.md:53,139-142`); the new transaction wraps it rather than replacing it.
- smooth-sequences has no chain check (`grep source_hash` finds none) and PX-277 routes 22 of 31 checkIds to the spec (`repair-route.mjs:26-69,102`).
- `/educe-sequences` and `/grill-me-for-rfc` are `disable-model-invocation: true`; the transaction therefore calls their node scripts, not the slash commands.
- The detector writes only SMOOTH-SEQUENCES.json and .md (`heal-loop.test.mjs`), so the transaction is the only writer of the design artifacts.

## Acceptance Criteria

- [Happy path] A consistent workspace opens a transaction, derives and verifies a candidate, commits, and leaves the live design files byte-identical to staging with the old generation archived and the post-commit detector exiting 0.
- [Error case] A candidate that breaks a chain link or a grounded judgment refuses commit, leaves every live design file byte-identical, and reports the failing link or ground.
- [Edge case] An injected failure at any commit rename or at post-commit verification restores the old generation byte-identically; a persisted journal is recovered before any consumer reads.

## Invariants

- [Normal establishment] The live design files are byte-identical during open, derive and verify; only commit writes them.
- [Error invariant] Any failure leaves the live generation valid and unchanged, or fully rolled back byte-identically.
- [Internal state invariant] The ledger moves monotonically through open, derived, verified, committing and committed; a failed commit ends in commit-failed after rollback.
- [Boundary invariant] No hash is accepted as input, no frozen file is written outside commit, and a broken baseline never opens a transaction.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — frozen baseline

- **Precondition**: the live workspace holds the spec, the tree manifest, the allocate manifest and the sequences artifact with matching recorded hashes
- **Postcondition**: open creates a staging generation and leaves every live design file byte-identical
- **Invariant**: a baseline with any broken link opens no transaction and reports SILENT_CHANGE_DETECTED

### C002 — staging isolation

- **Precondition**: an open transaction holds a candidate specification and a staging root outside the live workspace
- **Postcondition**: every derivation step reads and writes only the staging root, and the live design files stay byte-identical
- **Invariant**: a derivation failure leaves the live workspace byte-identical and the transaction failed

### C003 — pre-commit verification

- **Precondition**: a derived generation exists in staging
- **Postcondition**: commit is allowed only after the chain verifies, every RFC and obligation ground resolves, and the detector on staging exits 0
- **Invariant**: any failing link, ground or finding keeps the live workspace byte-identical and blocks commit

### C004 — commit transaction

- **Precondition**: a verified generation exists and the live baseline is unchanged since open
- **Postcondition**: commit replaces exactly the design artifacts, archives the old generation, and a post-commit chain and detector run passes
- **Invariant**: a failure at any rename restores the live design files byte-identically, and an interrupted commit is resolved before any consumer proceeds

### C005 — no bypass

- **Precondition**: the CLI is invoked with a hash or force argument, or a frozen file is edited outside the transaction
- **Postcondition**: the CLI rejects the argument and the consumers refuse the broken chain
- **Invariant**: a hash is never accepted as input and no frozen file is written outside commit

### C006 — repair loop

- **Precondition**: smooth-sequences emits a finding classified in-place, regeneration or judgment-required
- **Postcondition**: in-place findings keep the existing edit route, regeneration findings name the transaction, and judgment-required findings exit 3
- **Invariant**: exit 0 requires zero findings, a verified chain and no open transaction
