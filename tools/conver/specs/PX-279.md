# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-279: Make the regeneration transaction operable end to end and document its operating procedure

**Ticket Key**: PX-279 · **Phase**: -1

## Background

The PX-278 regeneration transaction has the right states and rollback, but its default producer has never run against a populated workspace. Allocate finalize refuses a non-empty planned directory, so derive fails on a workspace with existing package directories such as the 29 packages in gaia. Derive also accepts the inherited artifact as current, so a changed spec never reaches the educe handoff and verify fails without a machine-readable explanation. Open rejects a decisions-only thaw because it requires a changed spec, although the allocate findings route to regeneration. Verify records a candidate hash that nothing checks and does not bind the verified staging bytes, so a post-verify edit could be committed if the chain and detector still pass. The smooth-sequences command names the transaction but gives no case-by-case operating guide.

### Goal

Make every regeneration finding class completable through one script-owned transaction on a real populated workspace, and make the command document state exactly how to run it for each case.

### Purpose

Give the executing AI, not its memory or judgment, the path from a finding to a refrozen generation: the script owns the change set, the staging isolation, the handoff state, the verified bytes and the atomic commit.

### Motivation

The user asked for a careful execution guide after PX-278. Writing a guide before the default producer works would document a dead path and would let the AI improvise edits to frozen files. The decisive defects must be fixed first, because the discipline must be enforced by the scripts and their internal concealment rather than by AI thinking.

### Constraints

- The current working directory is the workspace root; no parent-directory search.
- Live design files are byte-identical until commit.
- The educe phases remain AI judgment; the script owns the boundary and verifies the artifact digest.
- No new dependency; Node ESM .mjs; node:test with assert/strict.
- Do not change the detector checkIds, hash functions, archive layout or rollback semantics.
- Preserve backward-readable GENERATIONS.json by adding fields, not renaming existing ones.

## Acceptance Criteria

- Happy path: on a populated workspace, open with a spec candidate, derive with the real producers, complete the educe handoff, derive again, verify and commit; the live design is byte-identical until commit and the detector exits 0 after commit.
- Happy path: an allocate decisions only finding opens with --allocate-decisions, derives without rerunning educe, verifies and commits, and the live spec bytes never change.
- Error case: a staged spec or decisions tamper after open returns CANDIDATE_CHANGED; a staged byte tamper after verify returns STAGING_CHANGED; the live tree is restored byte-identically and nothing is committed.
- Edge case: no candidate differs returns NO_CHANGE; an active transaction returns TRANSACTION_OPEN; derive-failed names abort and open as the next action.
- Guide: every regeneration finding class and every transaction state has one exact command, and judgment-required is documented as a stop rather than completion.
- Guide structure: the Reference section contains a case table, a step list, a state table, a failure table and a forbidden-actions list; docs.test.mjs asserts the headings and the exact commands.
- No silent write: every test snapshots the live design tree before open and after each state, and asserts equality until commit.

## Invariants

- Normal establishment: every supplied candidate exists and its hash is recorded before any derivation; the live chain verifies before open; setupDone is true after the one-time setup.
- Error invariant: a refusal writes nothing; the live design tree is byte-identical after open, derive, verify, abort and any commit failure; the ledger records the refusal state.
- Internal state invariant: the ledger state only moves open -> derived -> verified -> committing -> committed, or to aborted, derive-failed, judgment-required or commit-failed as declared; verifiedSnapshot equals the staged design snapshot at verify success.
- Boundary invariant: zero candidates is a usage error; one or more identical candidates is NO_CHANGE; one differing candidate is enough to open; zero packages still derives; a 29-package workspace derives through the same code path.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — staging-lib -> transaction-lib: open change set

- **Precondition**: The live hash chain verifies, no transaction is active, the reason is non-empty, and at least one supplied candidate path exists.
- **Postcondition**: The staging root contains the candidate spec and decisions, and GENERATIONS.json records candidateSpec with candidateHash, candidateAllocateDecisions with its hash, and candidateTreeDecisions with its hash.
- **Invariant**: NO_CHANGE is returned if and only if every supplied candidate equals its live counterpart; no live design file is written before open returns.

### C002 — transaction-lib -> workspacify-tree and workspacify-allocate: one-time setup

- **Precondition**: A transaction is open.
- **Postcondition**: Tree finalize, allocate finalize, educe begin and the authored-document merge run once, setupDone is true in the ledger, and a later derive skips them.
- **Invariant**: Allocate finalize never sees a non-empty planned directory, and the live design tree is byte-identical throughout derive.

### C003 — transaction-lib -> educe artifact: currency check

- **Precondition**: The staging root holds a spec and may hold an inherited artifact.
- **Postcondition**: The transaction reports derived if and only if the artifact spec.sha256 equals the educe raw digest of the staged spec; otherwise it reports educe-pending with the staging spec path and the handoff instruction.
- **Invariant**: A stale artifact is never reported as derived.

### C004 — transaction-lib -> commit-lib: verified bytes binding

- **Precondition**: The transaction is in the derived state with a staged snapshot.
- **Postcondition**: Verify success stores verifiedSnapshot; commit requires the staged snapshot and the staged candidates to match their recorded values.
- **Invariant**: The committed design bytes equal the verified design bytes, and any mismatch writes nothing.

### C005 — regeneration-cli -> operator: guidance output

- **Precondition**: Any subcommand runs and reaches any outcome.
- **Postcondition**: Output names the transaction id, state, staging root, staging spec path and exact next command; a non-zero outcome names the failed chain link, producer, finding or ground.
- **Invariant**: Every non-zero exit either names a runnable repair command or is exit 3 judgment-required.

### C006 — repair-route -> regeneration: decisions-only finding

- **Precondition**: Only workspacify/allocate/DECISIONS.json differs from the baseline and the live chain verifies.
- **Postcondition**: Open succeeds with --allocate-decisions, derive reuses the digest-matching artifact, verify passes, and commit publishes a new allocate manifest without an educe handoff.
- **Invariant**: The live spec bytes are unchanged before and after the transaction.
