# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-280: Make /smooth-sequences self-contained from thaw to refreeze and keep judgment with the AI

**Ticket Key**: PX-280 · **Phase**: -1

## Background

### Goal
Make `/smooth-sequences` the single entry point that drives a regeneration from thaw to refreeze: open, derive, the educe handoff, verify, commit and rerun, with exactly one executable next action at every stop.

### Purpose
The repair loop is the command. An executor must not need to remember a second command or infer which Reference block applies. The script owns the discipline; the AI resolves judgments through the owning design command; the human runs one command.

### Motivation
PX-279 made the transaction operable but left the educe handoff conditional and documented it in a bottom Reference, and implemented `judgment-required` as a human stop. That contradicts the project principle that the AI decides by default, asking a human only direction questions and extremely rarely, and contradicts the document's own rule that the only terminal state is a fresh exit 0. The bottom Reference also forces the executor to map blocks to steps, raising cognitive load and making an already dangerous handoff easier to skip.

### Constraints
- Change only `~/shyme/zasso/tools/conver`; `~/shyme/gaia` remains untouched.
- Never edit a live frozen input in place; every change goes through the transaction.
- Never push.
- No new dependency; Node built-ins only.
- `/smooth-sequences` itself never asks a question; a delegated `/explain-seed` or `/grill-me-for-rfc` may ask direction questions under its own limit (three per round, five rounds).
- Keep the existing exit-code contract except where this ticket redefines exit 3 as an AI handoff.

## Acceptance Criteria

- Happy path: from a regeneration finding, one `/smooth-sequences` invocation drives open, derive, the educe handoff, verify and commit; the handoff is printed with the staged spec and executed in the same invocation; the next detector run exits 0.
- Error case: a ground failure prints `/grill-me-for-rfc` (or `/explain-seed` for an RFC seed) and the staging root; the AI resolves it, runs `continue`, and reaches `committed` without a human decision or a stop-and-report.
- Edge case: a decisions-only candidate reaches `committed` through `continue` without invoking educe; the live specification remains byte-identical.
- Document: the command has no `## Reference`; every operational command sits in the Step that uses it; Appendix A-E hold diagnostic detail only.

## Invariants

- [Normal establishment] The live design files are byte-identical until `commit`; `continue` adds no write path beyond derive, verify and commit.
- [Invariant on error] Every handoff (`educe-pending`, `judgment-required`, `unverified`, `derive-failed`) leaves the live tree unchanged and the ledger in a named state with one executable next action.
- [Internal invariant] `continueTransaction` is orchestration over the existing derive/verify/commit functions; it never accepts a hash, a force flag, or a target path.
- [Boundary invariant] `committed` and `aborted` are terminal: `continue` returns them without mutating the ledger, while `abort` and `derive` refuse them with `TRANSACTION_TERMINAL`.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — design: one invocation reaches the terminal state

- **Precondition**: A transaction is `open` or `derived`; its staged candidate is unchanged; the producer, grounds and detector are supplied.
- **Postcondition**: `continueTransaction` reaches `committed`, or returns one named handoff with an executable `next`; it never returns an unnamed state.
- **Invariant**: It calls only the existing derive, verify and commit functions; it adds no write path and accepts no hash or force argument.

### C002 — design: the educe handoff is inside the command

- **Precondition**: The staged artifact is missing or its `spec.sha256` differs from the staged specification digest after `phase.mjs through` runs.
- **Postcondition**: The result is `educe-pending`; `next` names `.claude/commands/educe-sequences.md`, the staged spec and `continue`; the ledger stays `open`.
- **Invariant**: The live design files are byte-identical and `commit` refuses with `UNVERIFIED_GENERATION`.

### C003 — design: judgment stays with the AI

- **Precondition**: `runGrounds` returns `ok: false` with a reason naming a grill script or an RFC seed.
- **Postcondition**: The result is `judgment-required`; `next` names `/grill-me-for-rfc` on the staging root, or `/explain-seed` for an RFC seed; no human decision is requested.
- **Invariant**: The next action is an executable command; the state is a repair route, not a terminal stop.

### C004 — design: each Step is self-sufficient

- **Precondition**: Read `.claude/commands/smooth-sequences.md`.
- **Postcondition**: Step 1b contains the candidate table, preconditions, open/status/derive, the educe handoff, verify/commit, the state table, failure handling, interrupted commit and forbidden list; Step 1c contains the AI ground route; Appendix A contains the check families.
- **Invariant**: No operational command lives only in an Appendix, and no Step instructs a reader to consult a bottom Reference to act.

### C005 — design: the AI decides by default

- **Precondition**: Any command output or document line produced by this ticket.
- **Postcondition**: The only human surface named is a delegated command's own direction questions, limited to three questions per round and five rounds.
- **Invariant**: No line says `human decision`, `stop and report`, or equivalent; `/smooth-sequences` itself never asks.
