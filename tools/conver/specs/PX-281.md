# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-281: Give /smooth-sequences a generation history under <root>/smooth-sequences/

## Background

- [Goal] Repeated /smooth-sequences runs against one workspace root accumulate generations under <cwd>/smooth-sequences/: status.json records the generation, mode, input digest, report digest and verdict; the current SMOOTH-SEQUENCES.json/.md pair is the newest generation; the superseded pair is renamed into archive/<generation>/ and never deleted; an unchanged input and measurement is a verification that writes nothing.
- [Purpose] The command is a repeated smoothing loop, not a one-shot gate: each pass must compare the workspace with the last measurement, and persisted findings are evidence that the previous repair missed. Overwriting the root report erases that evidence every pass.
- [Motivation] /educe-sequences already owns this model: a run directory beside the specification, status.json with a generation, archive/ holding superseded readings, and a verification that writes nothing. /smooth-sequences is its downstream gate and should not be the only instrument in the pipeline that forgets its own passes.
- [Constraints] The report directory is not a design input: staging, commit and the hash chain must never read or write it. Exit 2 remains write-free, including the directory. The legacy root SMOOTH-SEQUENCES.json/.md are read-only compatibility input and are never moved or deleted. The report file names stay SMOOTH-SEQUENCES.json/.md; only their containing directory changes.

## Acceptance Criteria

- Happy path: a run over a workspace with no history writes smooth-sequences/{SMOOTH-SEQUENCES.json,SMOOTH-SEQUENCES.md,status.json} with generation 1; after a repair, the next run writes generation 2 and moves the first pair to smooth-sequences/archive/1/ byte-identically.
- Error case: every exit-2 run (broken chain, open transaction, malformed artifact) leaves no smooth-sequences/ directory and changes no existing generation file.
- Edge case: an unchanged workspace re-run reports `generation: N (verification; no new generation)`, writes nothing, and leaves status.json byte-identical; a legacy root SMOOTH-SEQUENCES.json supplies persisted but is never moved or deleted.

## Invariants

- 【Normal establishment】A report-writing run increments the generation by exactly one; the superseded pair is moved byte-identically into archive/<previous generation>/ before the new pair is written; status.json is written last and names the generation, mode, input digest, report digest and verdict.
- 【Invariant on error】Every exit-2 path leaves <root>/smooth-sequences/ absent or byte-identical; no partial status is written; an unreadable status or report is treated as no history and never throws.
- 【Internal invariant】The run directory is not a design input: collectDesignFiles, the staging copy, snapshotDesignFiles and the commit target set contain no path beginning smooth-sequences/.
- 【Boundary invariant】The detector writes only under <root>/smooth-sequences/; the legacy root SMOOTH-SEQUENCES.json/.md are read and never modified, moved or deleted; a verification writes nothing at all.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — design: a first report opens generation 1

- **Precondition**: The workspace root is valid and the detector reaches the write step; <root>/smooth-sequences/ has no report and no status.
- **Postcondition**: smooth-sequences/SMOOTH-SEQUENCES.json, .md and status.json exist; status.json names generation 1, mode new generation, the input digest, the report digest and the verdict.
- **Invariant**: No file is written at the workspace root; the report pair and status are the only writes.

### C002 — design: an unchanged pass is a verification, not a new generation

- **Precondition**: A generation N report exists; the input digest equals status.inputDigest and the rendered measurement equals status.reportDigest.
- **Postcondition**: The result is mode verification with generation N; the console prints generation N verification; no file is created, renamed or written.
- **Invariant**: status.json and the report pair are byte-identical before and after.

### C003 — design: a changed pass archives the superseded generation

- **Precondition**: Generation N exists; the input digest or the measurement differs from status.
- **Postcondition**: archive/N/ holds the previous SMOOTH-SEQUENCES.json and .md byte-identically; the run directory holds generation N+1 pair and a status.json naming N+1 and mode new generation.
- **Invariant**: Nothing is deleted; the archived pair stays readable and byte-identical to the pair that was current.

### C004 — design: refusal writes nothing

- **Precondition**: The run ends at exit 2 because the root is invalid, the chain is broken, a transaction is open, or the artifact is malformed.
- **Postcondition**: The run returns exit 2 with report null and the existing stderr code; no smooth-sequences/ directory is created and no generation file changes.
- **Invariant**: The write-free refusal behavior of the detector is preserved.

### C005 — design: the legacy root report is read-only compatibility

- **Precondition**: The workspace root carries SMOOTH-SEQUENCES.json and/or SMOOTH-SEQUENCES.md from a pre-generation run, and smooth-sequences/ has no report.
- **Postcondition**: readPreviousReport returns the legacy JSON so persisted is computed; the run writes generation 1 under smooth-sequences/; the legacy pair stays at the root byte-identically.
- **Invariant**: The legacy pair is never moved, renamed or deleted by this ticket.

### C006 — design: the run directory is not a design input

- **Precondition**: A generation has been written under <root>/smooth-sequences/.
- **Postcondition**: collectDesignFiles(root), snapshotDesignFiles(root), prepareDerivationRoot and the commit target set contain no path beginning smooth-sequences/.
- **Invariant**: The hash chain and every staging/commit comparison are unchanged by the report history.
