# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — design: root generations are read from the run directories

- **Precondition**: The workspace root carries educe-sequences/status.json and may carry smooth-sequences/status.json, each with a positive integer generation; a status may be absent, unreadable or still at generation 0.
- **Postcondition**: The model carries rootCounters.edu and rootCounters.smo as positive integers or null, and every package line renders the 🟤 EDU:n and 🟢 SMO:n marks when the counter is known.
- **Invariant**: An absent, unreadable or zero generation renders no mark; a smooth verification pass does not increment the generation; educe generationOf semantics map a status with phases and no number to generation 1.

### C002 — design: grill sessions are counted at completion

- **Precondition**: A package Status.json carries completedSessions as a non-negative integer, or lacks the field; RFC.md may or may not exist.
- **Postcondition**: The order line renders the 🟠 GRI:n mark when the count is known; when the count is unknown it renders GRILLED if RFC.md exists and nothing otherwise.
- **Invariant**: completedSessions increments exactly once per transition into DONE; resume, inc-loop and a repeated DONE with no transition do not increment; a non-integer or negative value is treated as unknown.

### C003 — design: distributions are counted only when the view changes

- **Precondition**: A package carries SEQUENCES-DISTRIBUTIONS.json with a non-negative distributions and a digest of the projected view JSON; the view may be complete, failed or absent.
- **Postcondition**: The order line renders the 🟡 SEQ:n mark for a complete verdict and the ❌ SEQ:n mark for a failed verdict when the count is known; otherwise it falls back to SEQUENCED or FAILED-SEQ.
- **Invariant**: The counter increments only when the projected view JSON digest changes; an identical re-projection does not increment; the counter lives outside the view and never changes the view bytes.

### C004 — design: field cells have a fixed width

- **Precondition**: A package line carries any subset of the EDU, EXP, GRI, SEQ and SMO marks.
- **Postcondition**: The fields appear in that order; each present label is padded to the global maximum width; an absent middle field occupies a blank cell of the same width; trailing blank cells are trimmed.
- **Invariant**: No line ends in whitespace; the full-width glyphs 🟤, 🔴, 🟠, 🟡 and 🟢 are used and no half-width substitute appears; multi-digit counters keep the following columns aligned.

### C005 — design: the minimal tab run reaches a common column

- **Precondition**: Every package path has a display width, the line prefix is four columns, and TAB_WIDTH is 8 with a minimum gap of one column.
- **Postcondition**: targetColumn = ceil((maxPrefix + 1) / 8) * 8; each marked line carries ceil((targetColumn - prefix) / 8) tabs; expanding tabs at width 8 places every first mark in targetColumn.
- **Invariant**: targetColumn - 8 < maxPrefix + 1 <= targetColumn; the per-line tab count is minimal; a markless line carries zero tabs and ends at its path.

### C006 — design: the plan is total and read-only

- **Precondition**: A status file is corrupt, a directory cannot be read, a counter document is missing, or a package carries no marks.
- **Postcondition**: The affected mark is omitted and the plan still renders with exit 0; no file is written and DesignTree.json is never read.
- **Invariant**: workspacify-order performs zero writes and a malformed input never replaces the picture with a stack trace.

### C007 — design: workspaces without counters render as before

- **Precondition**: A workspace carries no counter documents and no marks, as in the explain-seed order fixture.
- **Postcondition**: renderPlan returns byte-identical output to the current renderer, including the markless package lines and the focus block.
- **Invariant**: Backward compatibility holds without weakening or rewriting the existing expected output in the explain-seed order test.
