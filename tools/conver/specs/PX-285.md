# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

**Ticket Key**: PX-285 · **Phase**: -1

## Background

### Goal
The smooth-sequences gate must be total, monotone and honest. Every check either measures its declared surface against a stated denominator or blocks with a reason. A blocked surface produces the verdict unproven and exit code 4, never pass. A finding cannot vanish because its input surface was removed: it becomes S.evidence-withdrawn unless resolved or waived with a ground.

### Purpose
The detector currently decides the exit code from the finding count alone (run.mjs:179) and treats a missing input as an empty loop (checks-danger.mjs:243-247). The gaia run demonstrated the consequence: S6.boundary-effect-drift was reported executed while 0 of 257 operations carried boundary_effects; the artifact was downgraded from v3 to v2; 1,937 findings fell to 0; provenance printed total 300, preserved 0, missing 0 (provenance.mjs:53). The report could not distinguish not measured from no problem.

### Motivation
The original audit asked whether every sequence and operation was distributed and whether every operation-boundary contract was free of omission, contradiction, deficiency and danger. The current pass answers neither question: the v3 surfaces that carried the evidence were removed and the v2-only checks cannot see them. A gate that can be satisfied by deleting its own inputs is unsound and must be repaired before any further workspace run is trusted.

### Constraints
Change only /Users/kawata/shyme/zasso/tools/conver. Never edit /Users/kawata/shyme/gaia. Read-only observation of gaia on a temporary copy is allowed. Tests run through node --test against the impact set; make test is forbidden. No new dependency, no unwrap-style silent catch, no hardcoded path, no Initial Design Artifact header edit. The report schema and exit code change is deliberate and all in-repo consumers are updated in this ticket.

## Acceptance Criteria

- [Happy path] An authored v3 fixture runs enforce and exits 0 with verdict pass, blocked empty, zero findings and zero unresolved readings.
- [Error case] A v2 fixture runs enforce and exits 4 with verdict unproven, listing 8 S5 checks, 3 S4.contribution checks and S6.boundary-effect-drift as blocked, each with a surface and reason.
- [Edge case] A workspace whose status schemaHistory contains v3 and whose current artifact is v2 exits 4 with UNPROVEN_DOWNGRADE and emits S.evidence-withdrawn for every previous finding that is not resolved; a waiver with an empty ground does not remove it.

## Invariants

- [Normal condition] Every registered check resolves to executed only when each required surface is present and the denominator is greater than zero; otherwise it resolves to blocked with a reason. The union of executed and blocked equals the registry size. The verdict is pass only when findings, blocked entries, and unresolved readings are all zero.
- [Error invariant] An invariant violation is refused, never printed as zero: a provenance count that does not sum, an unreadable status, an unrouted check id, or a missing archived report produces a thrown SmoothSequencesError or a named refusal.
- [Internal state invariant] The detector writes only under <root>/smooth-sequences/. status.json carries findingKeysDigest, schemaHistory and verdict; a superseded report pair is archived, never deleted; a finding cannot disappear without either resolution or a waiver carrying a non-empty ground.
- [Boundary invariant] No file under /Users/kawata/shyme/gaia is modified. report schemaVersion 4 and exit code 4 are the only public contract changes; a v2 artifact remains readable and is reported as unproven rather than pass.
