# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-289: Three-Layer Closure: mechanical obligations, semantic obligations, and the AI judgment protocol

**Ticket Key**: PX-289 · **Phase**: -1

## Background

### Goal
Implement the Three-Layer Closure (TLC) as one atomic protocol change across educe-sequences, smooth-sequences and regeneration: a shared obligation registry for mechanical and semantic obligations, an evidence manifest with phase receipts, a closure gate that treats absence as open, and a finite AI judgment protocol (Context-Rich Worklist -> Proposer -> Attacker -> Decision).

### Purpose
Replace the current pass model, which can report pass while 257 uncovered obligations are unanswered and while a phase verdict is carried without fresh evidence, with a closure model in which every obligation is either mechanically closed or held by an attacked judgment. The gate must stop calling an unmeasured surface clean and must stop treating an AI answer as a fact without a falsifier.

### Motivation
The gaia generation 11 run passed with 0 records in readings-uncovered.jsonl against a 257-member worklist, with archive generations 6 through 10 also empty after generation 5 held 294 records, and with phase 8 recorded done by the carried verdict 553 signed reading(s). smooth-sequences sums unresolved readings from the files only, so absence is indistinguishable from a clean measurement. PX-288 hardened individual readings and checks but did not introduce a single obligation registry, evidence receipts or a judgment protocol; the same class of silent gap therefore remains. The repeat loop persists because a re-run adds no new information when the gate cannot name the missing obligation.

### Constraints
- Atomic protocol change: educe, smooth, regeneration and the command documents ship in one ticket; a partial protocol leaves one side reading a manifest the other does not write.
- No hand-editing of generated files or evidence; every evidence record is produced by its producer or by the judgment protocol.
- Scripts never judge semantics; AI judgments never decide mechanical facts.
- Every new behavior has a red test that fails for absence of implementation; tests are not weakened.
- Backward compatibility: existing v4 reports and legacy readings are readable, but a pass requires a complete certificate.
- New modules are plain ESM .mjs files; no new dependency.

## Acceptance Criteria

- [Happy path] All M1-M12 and J1-J16 red tests turn green; a fixture with complete evidence yields certificate complete and exit 0; report v5 separates proven, judged, accepted and residue and prints every obligation denominator.
- [Error case] An absent, empty, stale or shape-invalid evidence surface yields exit 4 with the named open obligation; a zero-claim check yields vacuous and an incomplete certificate; no path returns pass.
- [Edge case] A 257-member census with 149 mechanically closed operations and 108 reader-required operations reports 108/108 closed, not a bare zero; the same obligation with the same evidence digest yields NO_NEW_EVIDENCE; a third attack round is refused.
- [Invariant] No test is weakened; no template marker remains; no semantic judgment is made by a script and no mechanical fact is decided by an AI judgment.
- [Boundary] A legacy v4 report and legacy readings are readable but not pass; a resolution of two rounds is capped; an unresolved judgment is stuck and requires a design change.

## Invariants

- 【Normal establishment】Every obligation has a stable id, one class (mechanical or semantic), one producer and one acceptance predicate; deriveObligations is deterministic and finite over the same inputs.
- 【Invariant on error】Absent, empty, stale or shape-invalid evidence is open, never clean; a phase verdict without a valid receipt closes nothing.
- 【Internal invariant】Scripts never judge semantics and AI judgments never decide mechanical facts; a semantic obligation closes only with a held judgment carrying contextDigest, basis, falsifier and attack.
- 【Boundary condition】A closed obligation never silently reopens; the same evidence digest is never retried; an unresolved judgment becomes stuck and requires a design change, not another run.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — census and declaration -> obligation registry

- **Precondition**: inputs carrying the operations census, the declaration entries, the package views and the artifact
- **Postcondition**: deriveObligations returns the same sorted obligation ids on a second call and every census member has an obligation
- **Invariant**: no obligation id appears twice

### C002 — absent evidence -> closure state

- **Precondition**: a workspace whose educe-sequences readings directory is absent or whose readings-uncovered file is empty
- **Postcondition**: the closure gate reports the worklist obligations open with MISSING_EVIDENCE and the certificate is incomplete
- **Invariant**: absent evidence never yields a pass verdict

### C003 — phase receipt -> carried verdict

- **Precondition**: a phase receipt whose recorded input digest differs from the current artifact or worklist digest
- **Postcondition**: every obligation produced by that phase is open with STALE_RECEIPT
- **Invariant**: a carried phase verdict without a valid receipt closes no obligation

### C004 — judgment worklist -> judgment record -> attack

- **Precondition**: a judgment worklist item carrying a contextDigest and a falsifier
- **Postcondition**: a judgment record whose contextDigest differs is refused and a held judgment requires an attack outcome of held or a rebutted counterexample
- **Invariant**: a semantic obligation closes only with a held judgment

### C005 — generation g -> generation g+1 closure

- **Precondition**: an obligation closed in generation g and open again in generation g+1 with an unchanged input digest
- **Postcondition**: the transaction gate refuses EVIDENCE_REGRESSION and the same obligation with the same evidence digest is marked stuck with NO_NEW_EVIDENCE
- **Invariant**: closed obligations never silently reopen and the same evidence digest is never retried

### C006 — registered check -> executed or vacuous

- **Precondition**: a registered check with zero evaluated claims
- **Postcondition**: the check status is vacuous and the certificate is incomplete
- **Invariant**: executed always means evaluatedClaims is greater than zero
