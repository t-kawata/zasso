# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-291: Decision-based closure: validate judgments, derive the certificate from decisions, and unify span semantics

**Ticket Key**: PX-291 · **Phase**: -1

---

## Background

### Goal
Replace presence-based semantic closure with validated decisions. A semantic obligation closes only through a record that passes schema, context, freshness, basis and attack checks, and the completion certificate reports decisions rather than obligation states.

### Purpose
Make certificate status `complete` mean every required obligation carries a held decision. A record that merely exists, a generated record, a stale record or a record with an unanchored citation must leave the obligation open.

### Motivation
PX-289/290 produced a complete gaia certificate while `validateJudgmentRecord`, `validateAttackRecord` and `decideJudgment` were unused outside tests. `resolveJudgmentObligations` closed on `obligationId` plus a non-empty basis; `run.mjs` synthesized certificate judgments from already-closed obligations; 1,105 generated judgments cited line 1. The certificate counted record presence, not judgment. The mechanical layer was real, the semantic layer was a facade.

### Constraints
- No live gaia evidence mutation in this ticket; PX-293 owns the live re-evidence.
- Keep legacy reports readable; a schemaVersion 1 record is read but never counted in closure mode.
- Plain ESM, no new dependencies, no TypeScript.
- The resolver is pure and deterministic; every rejection code is testable on a synthetic fixture.
- Existing check, census and mechanical closure behavior stays; only the semantic resolution path changes.

## Scope

## Investigation

- `smooth-sequences/lib/predicates.mjs:171-205`: `resolveJudgmentObligations` closes a JUDGE/DIST/RISK obligation when a record carries `obligationId` and a non-empty `basis`; it does not call `validateJudgmentRecord`, does not compare `contextDigest`, and does not inspect the verdict. - `shared-obligations/judgment.mjs:75-147`: `validateJudgmentRecord`, `validateAttackRecord` and `decideJudgment` exist with the intended semantics but are imported only by `tests/shared-obligations/judgment.test.mjs`; the live path never calls them.
- `smooth-sequences/run.mjs:297-308`: the certificate receives `judgments` synthesized as `{ obligationId: entry.id, state: 'held' }` for every semantic obligation already closed, so `judged.broken` and `judged.unresolved` are structurally zero.

- Live gaia data: 1,105 judgment records (527 `consistent`, 401 `present`, 177 `mitigated`), every `basis[0].line` is 1; 380 attacks share one reason; 924 RISK obligations are closed by 177 generic judgments through prefix matching; 108 escapes use four distinct `why` strings.

## Acceptance Criteria

- [Happy path] The closure-core fixture with valid held decisions yields certificate status complete, judged.held equals the number of held decisions, and assurance.anchoredRatio is 1 with zero generic, reused, stale and provisional records.
- [Error case] Each rejection code (CONTEXT_MISMATCH, WORKLIST_MISMATCH, STALE_EVIDENCE, PROVISIONAL_EVIDENCE, VERDICT_NOT_ALLOWED, NO_ATTACK, SELF_ATTACK, COUNTEREXAMPLE_MISSING, QUOTE_NOT_FOUND, BASIS_OUT_OF_SCOPE, REUSED_BASIS, LEGACY_RECORD) leaves the named obligation open and the certificate incomplete.
- [Edge case] A span row listing 257 operations but stepping 149 yields 149 performed and 108 open semantic obligations in registry, predicates and rail gate; a conflicting verdict on a TRANSLATION obligation never closes it; a line-1 generic basis is rejected.

## Invariants

- 【Normal establishment】Every open semantic obligation has exactly one worklist item, and it closes only through a held decision that names the item obligationId, worklistDigest, contextDigest and artifactDigest.
- 【Invariant on error】A validation failure never deletes or rewrites the record; it appends a rejection with a code and leaves the obligation open or stuck.
- 【Internal state invariant】Certificate judged counts are a pure function of the decision set; no code path derives a held count from obligation state.
- 【Boundary condition】Legacy, provisional and stale records are readable and listed as rejected, but they never enter the closed set.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — judgment record -> semantic obligation

- **Precondition**: a record whose obligationId is an open worklist item and whose worklistDigest, contextDigest and artifactDigest match the current workspace
- **Postcondition**: the obligation receives a decision of held, broken or stuck; only held closes it; broken and stuck leave it open in the certificate
- **Invariant**: no record closes an obligation without a held decision

### C002 — decision set -> completion certificate

- **Precondition**: a decision set produced by decideAll over the current obligation registry
- **Postcondition**: certificate status is complete only if every required obligation is held, mechanically closed or not applicable, and no decision is broken or stuck
- **Invariant**: judged counts are a pure function of decisions, never of obligation state

### C003 — span reading -> performed operation

- **Precondition**: a span row carrying steps[] and operations[]
- **Postcondition**: only steps[].operation counts as performed; operations[] is coverage and does not close READ:UNCOVERED
- **Invariant**: registry, predicates and rail gate call the same span function

### C004 — basis -> anchored citation

- **Precondition**: a basis entry with source, line and quote for an obligation kind
- **Postcondition**: the quote occurs on the cited line and the line is inside the obligation anchor set; otherwise the record is rejected
- **Invariant**: a generic or reused quote never closes an obligation

### C005 — legacy or provisional record -> closure mode

- **Precondition**: a schemaVersion 1 record or a record with provisional true
- **Postcondition**: the record is readable and listed as rejected, and no obligation closes because of it
- **Invariant**: legacy evidence can be read but never counted

## Boy Scout Rule

Split `resolveJudgmentObligations` into `validateRecord`, `decideRecord` and `applyDecision`; each function is one verb phrase and the call sequence reads as validate, decide, apply.
Move the duplicated `ACTIVE_DISPOSITION` and `REALIZED_OUTCOMES` constants into `shared-obligations/registry.mjs` and import them from predicates and gates; one domain concept, one definition.
Name every rejection code as a constant with a repair sentence, so an error reads as a reason and a next action rather than a bare string.
Replace the `0`/`1` status literals in the certificate with the existing `OBLIGATION_STATE` constants and extract the assurance thresholds into named constants.
Remove the `subCheck.denominator ?? 0` fallback from `classifyMechanicalCheck`; an absent denominator becomes an explicit `MISSING_DENOMINATOR` reason instead of a silent zero.
