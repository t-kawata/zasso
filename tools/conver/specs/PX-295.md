# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the smooth-sequences closure gate decide from resolvable evidence and enforce observable semantic effort, so a complete certificate cannot be produced by presence-shaped records alone.

### Purpose
The 2026-10-21 gaia run reported complete while 1,661 of 1,852 judgment records carried no basis quote, 1,451 records cited fields that do not exist, all 2,775 attacks were held, 380 FALSIFY attacks shared one no-act template, all 108 uncovered obligations were escaped, 17 of 18 phase receipts were stale, and JUDGMENT-WORKLIST.json was stale. The gate exists to certify closure, so it must reject these records rather than count them.

### Motivation
A false pass is worse than an honest incomplete: it converts unknown semantic work into a claim of closure. The audit showed the current assurance counters cannot detect the defect they describe: anchoredRatio is 1 by construction, genericBasis only counts BASIS_OUT_OF_SCOPE, and reusedBasis only detects exact basis equality.

### Constraints
- Do not claim semantic truth. The gate certifies resolution, citation, subject-specificity, effort trace, basis sensitivity and blind agreement only.
- Do not auto-backfill the live gaia evidence. Re-authoring is PX-296.
- Keep the v2 legacy path readable. Closure mode (v3 artifact or evidence manifest) is the strict path.
- Frozen inputs remain frozen. Evidence is written only through documented producers.
- Implement in the conver canonical tree and install/sync to gaia. Do not edit installed copies directly.
- TDD Red-Green-Refactor is mandatory. Run the impact set with node --test, not the full suite.

## Acceptance Criteria

- Happy path: the detector accepts a valid fixture with a resolved basis, a literal subject-specific attack, a genuine escape, a fresh reading, matching receipts and a complete effort trace; it exits 0 with certificate schema 3 and all new counters clean.
- Error case: the current gaia evidence fixture exits incomplete and names BASIS_FIELD_UNRESOLVED, CLAUSE_PATH_UNRESOLVED, BASIS_QUOTE_MISSING, ATTACK_SAME_AS_BASIS, ATTACK_TEMPLATE_REUSED, ESCAPE_ACT_CONFLICT, INHERITED_READING and STALE_RECEIPT; no code path converts an open or stuck decision into complete.
- Edge case: a v2 artifact remains readable; an empty worklist is written as [] with remainingOpen: 0; an inherited reading is advisory only under the explicit policy; the 1,451-obligation fixture stays within the impact-set time budget.

## Invariants

- [Normal establishment] Every accepted basis resolves to a real artifact field, contract clause, RFC line, or spec line; every accepted attack quote is a literal substring of the cited source and range; every accepted effort trace meets the minimum search breadth for its kind.
- [Error invariant] A rejection never silently falls back to a weaker check. The named code is emitted, the decision stays open or stuck, and the certificate stays incomplete.
- [Internal state invariant] The certificate is a pure function of the registry, decisions, checks, readings, effort traces and input digests. complete is true only when every required counter is clean.
- [Boundary invariant] v2 artifacts remain readable under the legacy path. Closure mode refuses schema downgrade, stale receipts, inherited readings without policy, phantom basis, template attacks, act-conflicting escapes, and an empty worklist without remainingOpen: 0.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — artifact basis resolution

- **Precondition**: a basis entry names source artifact, an operation id, a field and a quote
- **Postcondition**: accepted only when the field exists, is non-empty and contains the quote
- **Invariant**: no accepted basis has an unresolved artifact field or a missing quote

### C002 — contract registry clause resolution

- **Precondition**: a basis entry names source contract_registry, a boundary id and a JUDGE field
- **Postcondition**: accepted only when the field maps to a real clause path and the quote occurs in that clause
- **Invariant**: no accepted contract_registry basis has an unresolved clause path

### C003 — risk field mapping

- **Precondition**: a RISK obligation names a risk class
- **Postcondition**: the basis resolves to the real artifact field mapped from that class
- **Invariant**: no RISK basis cites a class name instead of the real field

### C004 — distribution fidelity

- **Precondition**: a DIST obligation names a package and a unit
- **Postcondition**: the basis cites the RFC section line and quote and the section contains the unit id or normalized name
- **Invariant**: no DIST basis is satisfied by the view ledger alone

### C005 — quote uniqueness

- **Precondition**: a basis quote and its source field or clause
- **Postcondition**: accepted only when the quote is not reused by another obligation
- **Invariant**: no quote closes two obligations

### C006 — attack quote and range

- **Precondition**: an attack carries searched source, path, range and quote
- **Postcondition**: accepted only when the quote is a literal substring of the cited source and range
- **Invariant**: no accepted attack has a non-literal quote or a zero range

### C007 — attack independence

- **Precondition**: a judgment and its attack
- **Postcondition**: rejected when the attack quote equals the basis quote or the attack text is a reused template
- **Invariant**: no independent attack copies the basis or shares a normalized template

### C008 — counterexample attempt

- **Precondition**: a held judgment or attack
- **Postcondition**: requires a concrete counterexample candidate and a whyItFails statement
- **Invariant**: no held decision lacks a counterexample attempt

### C009 — falsification claim

- **Precondition**: a FALSIFY obligation for an active operation, realized sequence or boundary
- **Postcondition**: the claim and searched range are subject-kind specific
- **Invariant**: no active operation or realized sequence is closed by the no-act template

### C010 — escape grounding

- **Precondition**: an operation with position excluded or suppliedRule and an escape reading
- **Postcondition**: accepted only when the cited line does not order the act and escapeKind agrees
- **Invariant**: no escaped active operation has an act-conflicting quote

### C011 — reading citation and freshness

- **Precondition**: a reading with subject, lens, line and quote
- **Postcondition**: accepted only when the quote occurs on the line and freshness is fresh or explicitly inherited under policy
- **Invariant**: no held reading has a mismatched quote or a silent inheritance

### C012 — phase receipt freshness

- **Precondition**: an evidence manifest with receipts and current input digests
- **Postcondition**: a mismatched receipt is STALE_RECEIPT and keeps the certificate incomplete
- **Invariant**: complete implies every receipt input matches the current artifact

### C013 — worklist persistence

- **Precondition**: a detector run with a remaining open set, possibly empty
- **Postcondition**: the worklist file is rewritten to the remaining set and status records remainingOpen
- **Invariant**: the worklist file always matches the remaining open set

### C014 — certificate completeness

- **Precondition**: registry, decisions, checks, readings, effort traces and input digests
- **Postcondition**: complete only when every new counter is clean and schema is 3
- **Invariant**: anchoredRatio never decides complete and no missing counter passes

### C015 — effort trace

- **Precondition**: a held semantic obligation
- **Postcondition**: requires searched breadth, alternatives, a counterexample attempt, a discriminator and low uncertainty
- **Invariant**: no held obligation lacks an effort trace

### C016 — blind attack

- **Precondition**: a Tier 1 obligation
- **Postcondition**: requires a separately invoked blind attack with blind true and a non-shared source
- **Invariant**: no held Tier 1 obligation lacks a blind attack

### C017 — sampled re-judgment

- **Precondition**: a deterministic sample from the worklist digest
- **Postcondition**: a disagreement is REJUDGE_DISAGREEMENT; agreement increments rejudgeAgreement
- **Invariant**: complete implies rejudgeAgreement is 1 and the sample meets the threshold

### C018 — schema compatibility

- **Precondition**: a closure-mode run with a v3 artifact or evidence manifest
- **Postcondition**: certificate schema 3 and worklist schema 2 are written; v2 stays on the legacy path
- **Invariant**: closure mode never writes or accepts the v2 certificate shape
