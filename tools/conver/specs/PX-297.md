# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-297: Gate integrity: isolate live-workspace coupling, add the only evidence writer, and enforce generation freshness

**Ticket Key**: PX-297 · **Phase**: -1

## Background

### Goal
Make the generic closure gate reject generated, carried or live-workspace-coupled evidence: a record must come from the evidence writer, carry a writer-stamped generation and read time, and cite a clause that is either resolved or explicitly not applicable.

### Purpose
PX-295 and PX-296 produced a complete certificate from evidence generated by scripts/gaia-reevidence/generate.mjs. The generator copied the previous verdicts, stamped reRead, and wrote the readings files directly. The gate accepted the result because it could observe shape, not provenance. This ticket closes that class of shortcut in the conver canonical tree.

### Motivation
A false pass is worse than an honest incomplete. The current gate can reject a phantom basis or a template attack, but it cannot reject a record written by a script that synthesized the answer. The same gap lets an empty contract clause close an obligation and lets a Japanese-only act list miss an English specification. Each of these turns unknown work into a claim of closure.

### Constraints
- Generic code only. Do not touch the gaia artifact, readings or certificate in this ticket.
- Keep the v2 legacy path readable; the v3 path is the strict path.
- TDD Red-Green-Refactor is mandatory. Run the impact set with node --test, not the full suite.
- Implement in the conver canonical tree; do not edit installed copies.
- Do not claim semantic truth. The gate certifies provenance, resolution, effort and generation freshness only.
- Removing scripts/gaia-reevidence and tests/gaia-reevidence is part of this ticket; their evidence remains in the gaia history.

## Acceptance Criteria

- **[Happy path] — A reader-authored batch written through evidence-writer.mjs is accepted, the write receipt matches the file digest, and the certificate counts the records as current-generation evidence.**
- **[Error case] — A batch with a phantom basis, a stale readerGeneration, a reader-supplied readAt, a missing write receipt or an empty clauses object is rejected with its named code and writes no partial evidence.**
- **[Edge case] — A v2 workspace still renders under the legacy path; an English artifact that declares actPatterns detects escape-act conflicts; the removed gaia generator is absent from the shared tree.**

## Invariants

- [Normal establishment] Every accepted record carries readAt and readerGeneration stamped by the evidence writer, and every evidence file has a matching write receipt in the manifest.
- [Error invariant] A rejection never falls back to a weaker check: the named code is emitted, the obligation stays open, and no partial evidence file is written.
- [Internal state invariant] The certificate is a pure function of the registry, decisions, checks, readings, effort traces, write receipts and input digests. complete is true only when every new counter is clean.
- [Boundary invariant] A v2 artifact stays readable under the legacy path; a live workspace path cannot appear in production code; a contract with an empty clauses object does not become not_applicable without an explicit notApplicable declaration.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — evidence writer validation and atomicity

- **Precondition**: a batch of reader-authored records for one evidence kind
- **Postcondition**: every record is validated against its worklist item and either all records are written or none
- **Invariant**: no partial evidence file exists after a rejected batch

### C002 — writer-stamped generation and read time

- **Precondition**: the writer runs for the current generation with a known generation start
- **Postcondition**: the writer stamps readAt and readerGeneration and rejects a reader-supplied value
- **Invariant**: no accepted record carries a reader-supplied readAt or readerGeneration

### C003 — write receipt

- **Precondition**: an evidence file written by the writer
- **Postcondition**: the manifest carries a write receipt with the path, sha256, generation and writer
- **Invariant**: no evidence file without a matching write receipt closes an obligation

### C004 — generation freshness

- **Precondition**: a reading or judgment record with readAt and readerGeneration
- **Postcondition**: a record from an older generation or before the generation start is open with READER_GENERATION_STALE or READING_NOT_REREAD
- **Invariant**: no held decision uses a record whose generation or readAt predates the current generation

### C005 — explicit clause non-applicability

- **Precondition**: a contract whose clauses object lacks the requested kind
- **Postcondition**: the obligation stays open unless clauses.notApplicable explicitly names the kind
- **Invariant**: no obligation becomes not_applicable from an empty clauses object alone

### C006 — act vocabulary

- **Precondition**: an artifact that declares vocabulary.actPatterns
- **Postcondition**: the detector uses the declared act verbs to decide escape-act-conflict
- **Invariant**: no detector source carries a hidden language-specific act list

### C007 — live workspace isolation

- **Precondition**: the production scripts under scripts and .claude/scripts
- **Postcondition**: no file contains an absolute workspace path or a live workspace root
- **Invariant**: no shared-tree producer depends on a live workspace at runtime

### C008 — legacy compatibility

- **Precondition**: a v2 artifact or a legacy evidence file
- **Postcondition**: the legacy path remains readable and the v3 path is used when the manifest exists
- **Invariant**: no v2 report is made unreadable by the new counters

- Split evidence-writer.mjs into one validator per kind and one atomic writer; the function names state the flow: validate the batch, stamp the generation, write once or not at all.
