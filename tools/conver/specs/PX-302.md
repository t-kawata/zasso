# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-302: Assurance honesty: stop reporting unmeasured E3/E4 counters and expose instrument health

**Ticket Key**: PX-302 · **Phase**: -1

---

## Background

### Goal
Make the completion certificate stop reporting E3 (basis sensitivity) and E4 (sampled re-judgment) as clean when no such evidence was supplied, and expose an instrument-health block that a repeated run can compare.

### Purpose
The certificate currently reports `discriminatingRatio: 1` and `rejudgeAgreement: 1` because `decide.mjs` defaults both to 1 when the caller omits the arrays. `run.mjs` never supplies them, and `evidence-writer.mjs` supports only judgment, attack and effort. The gaia generation-14 workspace has no sensitivity or rejudge file. The counters therefore measure nothing but their own default.

### Motivation
/smooth-sequences is used repeatedly to flatten a design across directories. A counter that is constant by construction gives the next iteration no signal: a pass cannot be distinguished from a saturated instrument. The fix is not to build an E3/E4 proof system; it is to stop claiming a measurement that was not taken and to show the instrument's actual discrimination.

### Constraints
- Generic code only. Do not edit the gaia workspace, its artifact, its readings or its certificate.
- TDD Red-Green-Refactor is mandatory. Run the impact set with `node --test`, not the full suite.
- Do not implement E3/E4 evidence generation. Those remain a separate decision; this ticket removes the false claim and adds a diagnostic.
- Keep the v3 certificate readable: a legacy assurance object that still carries 1 and 1 must remain complete.
- The instrument block is a diagnostic and never changes the verdict; only measured counters gate.

## Scope

- Modify `.claude/scripts/shared-obligations/decide.mjs`: `discriminatingRatio` and `rejudgeAgreement` become `null` when the `sensitivity` or `rejudge` array is absent or empty; a numeric ratio is computed only when the array is non-empty.
- Add `.claude/scripts/shared-obligations/instrument.mjs` exporting `summarizeInstrument({ decisions, readings, judgments, attacks, effort })`. It returns inquest `{ records, yes, no, yesRatio }`, attack `{ records, held, broken, unresolved, brokenRatio }`, judgment `{ records, basisQuotes, distinctBasisQuotes, discriminationRatio }`, effort `{ records, distinctAlternatives, distinctDiscriminators }`, and `nonDiscriminating` (true when inquest yes is 0 and attack broken is 0). Every ratio is 0 when its denominator is 0, never NaN.
- Modify `.claude/scripts/shared-obligations/certificate.mjs`: `assuranceIsClean` treats a `null` E3/E4 counter as not measured and a numeric counter as gated; `normalizeAssurance` preserves the nulls; the assurance block reports `notMeasured` with the omitted keys.
- Modify `.claude/scripts/smooth-sequences/run.mjs` to call `summarizeInstrument` with the loaded readings and decisions and pass the result to `buildReport`; the `decideAll` call signature and obligation set stay unchanged.
- Modify `.claude/scripts/smooth-sequences/lib/report.mjs`: `buildReport` accepts and emits `instrument`; `renderConsoleReport` prints one `instrument:` line with the inquest yes ratio, attack broken ratio, judgment quote discrimination and effort distinctness.
- Update `.claude/commands/smooth-sequences.md` Step 6: remove `discriminatingRatio` and `rejudgeAgreement` from the mandatory clean set; state that E3/E4 are not measured unless evidence is supplied; describe `instrument` as a non-gating diagnostic.
- Add `tests/shared-obligations/instrument.test.mjs` and `tests/shared-obligations/instrument-certificate.test.mjs`; extend `certificate-v3.test.mjs`, `decide.test.mjs` and the report tests.
- Before -> After: an absent E3/E4 input yields 1 -> yields `null` and `notMeasured`; a certificate that never measured discrimination -> reports the actual inquest/attack/judgment/effort ratios; no obligation closure changes.
- Out of scope: generating E3/E4 evidence, requiring an independent evaluator, or making instrument health a gate. Those are separate decisions and would make the gate unclosable.
- Out of scope: editing the gaia data or the installed copies. The conver canonical tree is the target.
- Affected: the certificate schema gains an additive `notMeasured` array; consumers that read `discriminatingRatio` must handle `null`; the console gains one diagnostic line.

## Investigation

Evidence gathered from the conver canonical tree (2026-10-22). `shared-obligations/decide.mjs:429-434` defaults `discriminatingRatio` and `rejudgeAgreement` to 1 when the arrays are absent. `smooth-sequences/run.mjs:605-621` calls `decideAll` without `sensitivity` or `rejudge`. `shared-obligations/evidence-writer.mjs:246` accepts only `judgment`, `attack` and `effort`; no writer path exists for sensitivity or rejudge. The gaia generation-14 workspace contains no `*sensitivity*` or `*rejudge*` file, yet `COMPLETION-CERTIFICATE.json` reports both as 1 and `smooth-sequences.md:354` requires both to be 1 under `--require-effort`. `tests/shared-obligations/certificate-v3.test.mjs` asserts a clean v3 assurance carrying 1/1; the new behavior must keep that fixture complete while also accepting a null fixture. `smooth-sequences/lib/report.mjs:261-306` `buildReport` has no `instrument` field, and `renderConsoleReport:414` prints provenance, denominator and readings lines. The measured instrument baseline in gaia is 3768 inquest No answers and 0 Yes, 2460 attacks all held and 0 broken, 1564 judgment records, and 1564 effort records with only 4 distinct alternatives and 4 distinct discriminators.

## Acceptance Criteria

- Happy path: a run with no sensitivity or rejudge evidence emits `complete` when every measured counter is clean, and the certificate names the two counters in `assurance.notMeasured`.
- Error case: a supplied sensitivity or rejudge record with a disagreement keeps the certificate incomplete.
- Edge case: an empty readings set produces zero ratios rather than NaN and reports `nonDiscriminating: true` without failing the run.

## Invariants

- Normal establishment: a measured E3/E4 counter equals the count of ok entries divided by the supplied array length; a null counter means the array was absent or empty.
- Error invariant: a measured dirty counter (not 1) keeps the certificate incomplete; a null counter never does.
- Internal state invariant: `decideAll` never fabricates 1 for an absent input, and `summarizeInstrument` never divides by zero.
- Boundary invariant: a certificate with no readings and no attacks reports zero ratios and `nonDiscriminating: true` without NaN.
