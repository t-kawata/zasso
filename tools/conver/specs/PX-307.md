# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-307: Per-ticket obligation penetration: every view unit and its obligation reaches all owning tickets through RFC, GRAPH and Dirs-Tree, with per-ticket digests and blocking gates

**Ticket Key**: PX-307 · **Phase**: -1

---

## Background

### Goal
Make the distribution of every SEQUENCES view unit mechanical and prove, per ticket, that the unit and its obligation reached the finest granularity. Replace TMP001's scalar downstream digest with per-ticket records whose digest covers placement and obligation, and make every stage a blocking gate.

### Purpose
TMP001 measured that unit-to-section mapping cannot be inferred (80/627 unique heading matches and 529/627 absent in the gaia corpus) and designed a declared map. It nevertheless certified only that adjacent layers were generated from the same map, while the ticket layer carried unit ids only. The per-package view already drops the step and operation payload, so "what must this ticket do" was structurally unrepresentable. This ticket closes that gap.

### Motivation
Without per-ticket obligation records, every ticket can be implemented correctly and some sequence or operation can still be missing from the workspace, and a top-level digest can be copied while a single ticket is stale. PX-306 closed the layer-level checks but left the empty-ledger pass and the optional registry chain. This ticket removes both.

### Constraints
- RFC.md prose and all design decisions remain authored by the AI; the mechanism only declares, propagates, totals and refuses inconsistency.
- /graphify-rfc keeps RFC.md as its only input; no sidecar.
- No existing command argument changes.
- Root commands run at the workspace root; package commands run at the package top.
- A package with no view or an empty view keeps its old verdict (additivity).
- A non-empty view without a map is a failure, not a vacuous pass.
- Writes are atomic; a failed stage writes nothing.
- Verification runs the impact set with node --test; make test is not used.

## Acceptance Criteria

- Happy path: for every view unit, the map, section anchor, graph node, dirs index and every owning ticket record exist; the per-ticket obligations partition the unit payload; all adjacent digests match; the synthetic package and the root fixture pass.
- Error case: a non-empty view with no map, a stale view digest, a missing section, a missing unit at any layer, an invented unit, a digest mismatch, a dropped or duplicated obligation item, a broken sequence order, a stale spec ref or an undeclared owner role each fails with its named code and writes nothing.
- Edge case: no view and empty view keep the old verdict; a view with only residuals still requires a map; a unit with multiple sections anchors in each; a heading with no number matches by exact text.
- Compatibility: existing graphs, dirs trees and Tickets.json without the new optional fields still validate; no command argument changes; graphify reads only RFC.md.
- Verification: the impact set passes with node --test; the existing PX-306 tests stay green; a second run is byte-identical.

## Invariants

- [Normal condition] A package with a non-empty view has a valid map, a regenerated ledger, anchors in every listed section, and equal map and view unit sets.
- [Error invariant] A failed stage writes nothing; the previous artifact remains readable and no partial file is left behind.
- [Internal state invariant] The canonicalizer is single-sourced from sequences-slice/lib/digest.mjs; no second key-sorting or sha256 implementation is introduced.
- [Boundary invariant] Additivity holds: no view or empty view produces no map and no finding; a view with units and no map is always a failure.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — sequences artifact -> per-package view

- **Precondition**: The sequences artifact parses and every operation, sequence and step has an id.
- **Postcondition**: The view four unit arrays partition the artifact units owned by the package, and every operation unit carries its implementation obligation and every sequence unit its ordered steps.
- **Invariant**: No unit is dropped and no unit appears in two ownership buckets.

### C002 — per-package view -> RFC distribution-map

- **Precondition**: A package RFC and its generated view exist.
- **Postcondition**: The distribution-map unit set equals the view unit set, every section resolves to exactly one heading, and the map digest is the sha256 of its canonical body excluding the digest field.
- **Invariant**: A second render over unchanged inputs is byte-identical and no invented or missing unit is accepted.

### C003 — RFC distribution-map -> GRAPH -> Dirs-Tree

- **Precondition**: A valid distribution map and a graph built from the same RFC exist.
- **Postcondition**: Every map unit reaches at least one graph node, one Dirs-Tree path, and every ticket owning a node that carries it.
- **Invariant**: No layer carries a unit outside the map.

### C004 — GRAPH and Dirs-Tree -> Tickets per-ticket distribution

- **Precondition**: Every ticket carries a distribution record derived from the view, the graph and the dirs index.
- **Postcondition**: For each unit the ticket obligations form the kind-specific partition: one operation implementer, one ticket per step, ordered sequence reconstruction, and at least one contract holder per boundary side.
- **Invariant**: The union of ticket obligations equals the unit payload and no item is duplicated where exactly one is required.

### C005 — all layers -> digest chain

- **Precondition**: Each stage writes its artifact from the previous stage digest.
- **Postcondition**: The map digest equals the graph distributionDigest, the dirs distribution.digest and each ticket sourceMapDigest, and the Tickets aggregate is the digest of sorted ticket digests.
- **Invariant**: A failed stage writes nothing and a digest mismatch blocks the stage.

### C006 — view ownership -> operation role

- **Precondition**: A package may have no view, an empty view, or a view with multi-owner operations.
- **Postcondition**: A no-view or empty-view package keeps its old verdict, and a multi-owner operation has exactly one implementer unless a surface split covers the declared surfaces.
- **Invariant**: A non-empty view without a map fails rather than passing vacuously.
