# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-308: Close the distribution guarantee at ticket granularity: exact, content-bound and traceable

**Ticket Key**: PX-308 · **Phase**: -1

## Background

### Goal
Close every hole the 2026-10-23 audit found in the pipeline's distribution guarantee, so that a green split means every sequence and every operation reached the ticket layer exactly once, the layers were generated from one content-bound map, and each ticket can be traced back to the sequence step, operation and spec line it owes.

### Purpose
The current chain proves unit-set coverage (view -> ledger -> graph -> Dirs -> tickets) but not step-level distribution, and several gates accept states that break the guarantee: an empty view can fail the digest chain, a sole owner can declare itself a consumer, a stale view digest is not detected, two tickets can implement the same operation, and a bare operation's specRefs is a line-0 placeholder. The AI also still copies unit ids into ticket.nodeIds by hand even though the machine can append them. This ticket makes the guarantee total, exact, content-bound and inspectable at the ticket layer, and makes the split command run those checks as blocking gates.

### Motivation
Measured on 2026-10-23 against tools/conver:
- an empty view plus a Dirs-Tree returns MISSING_DISTRIBUTION_DIGEST even though the renderer and its tests define an empty view as having no map requirement;
- checkOwnerRoles returns ok for a single-owner operation with role consumer or no role, so no ticket implements it;
- verifyDigestChain returns ok when map.sourceViewDigest is OLD and tickets.distribution.sourceViewDigest is NEW;
- two tickets carrying the same operation both get mode implement and verifyTicketDistribution returns [];
- a bare operation with obligation.specLines [12] gets specRefs [{line:0, quote:op-...}];
- reconstructSequenceOrder has no production caller, so sequence steps are not checked at the command level;
- verify-graph-contracts is invoked without --registry, so the boundary contract-edge check is inactive at graphify;
- check-distribution-ledger.js is not invoked by any command;
- gaia carries 0 distribution-map blocks, 0 unit anchors and no graph/Dirs/Tickets, so the real chain has not yet run.

### Constraints
- Additive and backward-compatible: a package with no units keeps its old verdict; a legacy artifact without distribution remains readable.
- No test may be weakened or deleted to pass; the only tests removed are those of a feature removed by this ticket (check-distribution-ledger.js), with the reason recorded.
- Do not edit gaia or any external workspace; the live migration is a separate operation.
- TDD strict: Red -> Green -> Refactor; every contract has at least one failing test before implementation.
- One ticket: all findings are closed here. If review capacity requires a split, the only defensible split is correctness (C001-C004) versus traceability and wiring (C005-C010); do not split further.
- No new dependency. Keep every existing command, flag, exit code and output that is not named as changed here.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — empty-view-additivity

- **Precondition**: an empty view object and a Dirs-Tree object are supplied with no distribution map
- **Postcondition**: verifyAllTicketCoverage returns valid true and no MISSING_DISTRIBUTION_DIGEST finding
- **Invariant**: a view carrying at least one unit still requires the distribution digest chain

### C002 — owner-role-uniqueness

- **Precondition**: a single-owner operation map entry declares role consumer or omits role
- **Postcondition**: checkOwnerRoles returns OWNER_ROLE_UNDECLARED for the operation
- **Invariant**: a single-owner operation with role implementer passes, and multiple implementers pass only with distinct non-empty surfaces

### C003 — view-to-map-binding

- **Precondition**: the map sourceViewDigest and the tickets distribution sourceViewDigest differ
- **Postcondition**: verifyDigestChain returns DISTRIBUTION_DIGEST_MISMATCH with layer view
- **Invariant**: equal sourceViewDigest values and equal map, graph and dirs digests return ok

### C004 — machine-unit-carriage

- **Precondition**: a ticket input carries only graph node ids whose nodes carry unitIds
- **Postcondition**: add-tickets-for-phase writes the node units into ticket.nodeIds before verifyTicketUnits
- **Invariant**: a second run appends nothing and the unit ids remain unique

### C005 — single-implementing-ticket

- **Precondition**: two tickets in one phase own different nodes that both carry the same operation unit
- **Postcondition**: exactly one ticket carries obligation mode implement and the other carries reference, and verifyTicketDistribution does not report DUPLICATE_UNIT_AT_TICKET
- **Invariant**: no unit has two implementing tickets in the same package phase

### C006 — sequence-step-coverage

- **Precondition**: a view sequence declares ordered steps whose operations are owned by the package
- **Postcondition**: every step appears in exactly one ticket obligation steps array and the reconstructed order equals the declared order
- **Invariant**: a missing, duplicate or consumer-only step yields MISSING_SEQUENCE_STEP, DUPLICATE_SEQUENCE_STEP or SEQUENCE_STEP_WITHOUT_IMPLEMENTER

### C007 — spec-reference-return-path

- **Precondition**: an operation unit carries obligation.specLines with at least one positive line
- **Postcondition**: specRefs contains that line with a quote and SPEC_REF_MISSING is not reported
- **Invariant**: the line-0 fallback is used only when no positive specLines exist

### C008 — boundary-registry-discovery

- **Precondition**: verify-graph-contracts runs with --graph and no --registry inside a workspace with both manifests
- **Postcondition**: the allocate manifest is discovered and a boundary node without a contract edge fails MISSING_BOUNDARY_CONTRACT
- **Invariant**: outside a workspacify workspace the boundary check is skipped without failing

### C009 — distribution-inspection

- **Precondition**: a split Tickets.json carries tickets with distribution records
- **Postcondition**: show-ticket-distribution prints each ticket's units, sequence steps and specRefs
- **Invariant**: a ticket without distribution while the graph carries units exits 1 with MISSING_UNIT_AT_LAYER, and an empty package exits 0

### C010 — distribution-schema

- **Precondition**: a ticket carries an optional distribution object with a units array and digests
- **Postcondition**: the tickets schema validates the distribution shape and rejects a non-array units field
- **Invariant**: a ticket without distribution remains schema-valid
