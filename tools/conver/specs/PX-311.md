# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the final smooth-sequences closure gate require the strict evidence the tool already implements, harden the split verifier so a post-generation edit cannot pass, keep receipt debt out of the obligation count, and re-author the gaia evidence so the strict gate passes with subject-specific records.

### Purpose
The default closure run in gaia generation 101 exited 0 with verdict pass while the same workspace under --require-effort reported wouldExit 4. The default path validates record shape, context/worklist/artifact digests, the verdict vocabulary and quote existence, but it does not require a subject-specific effort trace or quote grounding; 1,570 judgment records share one searched-set signature (1,564 records use it), 639 attack templates cover 2,466 attacks, and templateAttackRatio is 0.718. That is a structural pass, not evidence-backed closure.

### Motivation
The audit measured 1,563 EFFORT_NOT_SUBJECT_SPECIFIC, 7 EFFORT_ANCHOR_MISSING, 8 STALE_RECEIPT and 7 MISSING_WRITE_RECEIPT. The 1,570 substantive judgments decompose into DIST 407, JUDGE 527 and RISK 636; the 4,419 reading obligations close under both modes. The tool is honest about the residue and prints non-discriminating, but the workflow's terminal state lets the weak mode stand in for the final acceptance gate.

### Constraints
Do not weaken E1-E6, the template threshold or any check to make the gaia corpus pass. Do not replace one template with another. Preserve --legacy and the v2 downgrade behavior. Do not add a new detector family; the 48 sub-checks and four closure gates stay. Do not edit generated SEQUENCES.json, the manifests or the artifact. The gaia re-authoring is operational work in the downstream workspace, verified by the strict run; the implementation in this repository is the policy, verifier and reporting change plus the tests.

## Acceptance Criteria

- Happy path: a closure-mode workspace with strict evidence exits 0, verdict pass, certificate complete, evidencePolicy strict.
- Error case: a closure-mode workspace whose evidence has a reused effort signature exits 4 and names EFFORT_NOT_SUBJECT_SPECIFIC; it is never reported as complete.
- Edge case: a ticket whose content was edited after generation fails verification with TICKET_DIGEST_MISMATCH or OBLIGATION_DIGEST_MISMATCH even when the stored digest fields are unchanged.
- Edge case: a certificate with receipt debt separates obligations.open from receipts.open and keeps total=closed+open+stuck.
- Acceptance: gaia strict run after re-authoring exits 0 with templateAttackRatio 0, effortCoverage 1, blindAttackRatio 1, staleReceiptCount 0, no MISSING_WRITE_RECEIPT, and independentAttacks equal to the held judgment count.
- Downstream acceptance: graphify, boundify and split pass verify-all-ticket-coverage on every package with recomputed digests and no unit or boundary-contract loss.

## Invariants

- [Normal establishment] In closure mode (a v3 artifact or an EVIDENCE-MANIFEST plus both WORKSPACIFY manifests) and without --legacy, the run sets strictEvidence=true, records evidencePolicy='strict', and runs the effort, freshness and receipt gates before it can report pass.
- [Error invariant] A workspace whose effort trace reuses another obligation's searched set, whose phase receipt is stale, or whose reader-authored file has no write receipt never returns verdict pass; it returns exit 4 and names EFFORT_NOT_SUBJECT_SPECIFIC, STALE_RECEIPT or MISSING_WRITE_RECEIPT.
- [Internal state invariant] strictEvidence is computed once per run as closureMode || --require-effort || --strict-freshness; every consumer reads that one value, so the index, readings resolver, worklist and decideAll cannot disagree about the policy.
- [Boundary invariant] --legacy keeps the old non-closure path; a workspace without a v3 artifact or evidence manifest keeps its previous behavior; a v2 artifact still produces UNPROVEN_DOWNGRADE.
- [Certificate arithmetic] obligations.total === obligations.closed + obligations.open + obligations.stuck, where obligations.open counts only ids supplied in obligations; receipt debt is reported in receipts and remains visible in open[] but is never counted as an obligation.
- [Ticket digest invariant] A stored distribution.digest or obligationDigest is never accepted without recomputing digestValue from the current content; a mismatch is TICKET_DIGEST_MISMATCH or OBLIGATION_DIGEST_MISMATCH.
