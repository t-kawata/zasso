# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — root *-sequences.json -> SEQUENCES.json (graphify admission)

- **Precondition**: The root artifact declares steps for many sequences, and a package view declares a subset in ownedSequenceUnits, crossBoundarySequenceUnits or obligationUnits.
- **Postcondition**: verifyViewAgainstMap reports SEQUENCE_STEPS_UNDISTRIBUTED only for a step whose sequence the view declares and no step-bearing record carries; a foreign sequence produces no finding.
- **Invariant**: The scope predicate is the view-declared sequence, never the step-bearing record, so an obligation-only sequence keeps its steps checked.

### C002 — WORKSPACIFY-ALLOCATE-MANIFEST.contract_registry -> ctr units

- **Precondition**: The registry has 84 rows and the workspace has 29 package views, each declaring the ctr units for its provider or consumer side.
- **Postcondition**: Every boundary verifier checks only rows whose ctr unit the layer declares; a declared ctr missing its graph node, edge contract, ticket contract or digest is a named finding; a foreign row produces no finding.
- **Invariant**: Global coverage remains smooth S4's job: the tree boundaries and registry rows are 84==84 with identical ids, and S4.boundary-side-mismatch requires both sides.

### C003 — SEQUENCES.json -> RFC distribution map -> GRAPH.json -> Dirs-Tree.json -> Tickets.json

- **Precondition**: A consistent package fixture carries sourceViewDigest, map digest, graph distributionDigest, dirs distribution digest and ticket aggregate digest.
- **Postcondition**: verifyChain exits 0 with zero findings; a stale map, unit-set mismatch or digest mismatch exits non-zero with STALE_DISTRIBUTION_MAP, UNIT_SET_MISMATCH or DISTRIBUTION_DIGEST_MISMATCH.
- **Invariant**: Package scoping does not relax the digest equality at any layer.

### C004 — artifact steps[].contract/contract_prose -> view steps[].contract/contractProse -> ticket obligation.steps

- **Precondition**: An artifact step belongs to a sequence the package view declares, and the view and ticket carry a projected step record.
- **Postcondition**: The view step and the ticket step carry the same canonical contract and prose; a drift yields a named contract-fidelity finding.
- **Invariant**: No schema change is introduced; the comparison is canonical and the view remains the projection of the artifact.

### C005 — graphify output -> boundify Step 0 -> boundify Step 2

- **Precondition**: The graph exists and the Dirs-Tree does not yet exist on the first boundify run.
- **Postcondition**: Step 0 runs a preflight that needs view, map and graph only and passes; Step 2 after generation checks the dirs distribution digest and fails on a stale or missing digest.
- **Invariant**: A missing Dirs-Tree is not an admission failure before generation and is a failure after generation.

### C006 — WORKSPACIFY-ALLOCATE-MANIFEST.json -> root *-sequences.json -> contract_registry

- **Precondition**: findAllocateManifest returns a manifest, so the run is inside a workspacify workspace.
- **Postcondition**: A missing, ambiguous or unreadable artifact or registry exits non-zero with MISSING_SIDECAR or MISSING_REGISTRY; outside a workspace the same absence is skipped as documented.
- **Invariant**: There is no silent fallback to a view-only step set or an empty registry inside a workspace.

### C007 — registry provider_package/consumer_package -> graph boundary edge -> view direction

- **Precondition**: An edge carries a projected boundary contract and the view declares provides or consumes.
- **Postcondition**: A ctr node on the wrong end of the carrying edge yields BOUNDARY_DIRECTION_MISMATCH even when attributes.bidirectional is true; an unrelated bidirectional edge is not rejected.
- **Invariant**: The direction check is bound to the edge that carries the boundary contract, not to the first edge touching the ctr node.

### C008 — contract_registry rows -> graph edge attributes.note

- **Precondition**: The combined note for the boundaries an edge carries exceeds 240 characters.
- **Postcondition**: project-boundary-contracts writes RFC-BOUNDARY-CONTRACTS.json, keeps a note that names the sidecar and a combined digest, and verify reads it; it does not throw without a remedy.
- **Invariant**: The note digest binds exactly the rows the sidecar names, and a tampered sidecar or note fails.
