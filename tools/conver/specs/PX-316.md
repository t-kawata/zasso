# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-316: Bind the smooth pass verdict to the graphify/boundify/split chain through a frozen receipt

**Ticket Key**: PX-316 · **Phase**: -1

## Background

### Goal
Make the downstream chain mechanically require a fresh smooth pass verdict, and the closure completion certificate when the workspace carries one, before it treats a package view as complete.

### Purpose
PX-314 delegates global sequence and operation coverage to smooth S4/S7, but graphify, boundify and split never read the smooth verdict. A stale or hand-edited view can therefore pass the chain when its map is re-rendered, and the chain cannot distinguish a verified distribution from an unverified one.

### Motivation
Measured against gaia: `smooth-sequences/status.json` is `verdict` pass at generation 106 with `inputDigest` `17202de5...`, and `smooth-sequences/COMPLETION-CERTIFICATE.json` is `status: complete` with `assurance` counters closed. The chain contains no code that reads either file. The next stage runs per crate, so the completeness guarantee must be mechanical rather than assumed from the pipeline order.

### Constraints
Only tools/conver is edited; gaia is not edited. No public edge/node/graph schema change; the receipt is a sidecar. Outside a workspacify workspace every check is skipped. The command step structure and the command docs tests are preserved. TDD Red-Green-Refactor is strict; use the impact-set `node --test`. Installed copies are synced through `make install-to-projects`. PX-315 must land first because this ticket sits in front of its order and identity model.

## Investigation

Measured on tools/conver and gaia (read-only).

1) The chain does not read smooth: `grep` over `.claude/scripts` for `smooth-sequences/status.json`, `COMPLETION-CERTIFICATE.json` and `inputDigest` finds no consumer in `rfc-graph`, `sequences-slice` or `tickets`; `verify-chain.mjs`, `attach-unit-ids.js`, `add-tickets-for-phase.js`, `verify-all-ticket-coverage.js` and the three commands never open the smooth status.
2) Smooth input digest: `.claude/scripts/smooth-sequences/run.mjs:271-279` computes `computeInputDigest(root)` from `snapshotDesignFiles(root)`; `.claude/scripts/regeneration/lib/staging.mjs:96-125` defines the snapshot set (root spec, decisions, `*-sequences.json`/`.md`, `educe-sequences/**`, and per-package `PACKAGE_DESIGN_FILES` including `RFC.md` and `SEQUENCES.json`). The helper is exported and can be imported by the gate.
3) gaia status: `smooth-sequences/status.json` is schemaVersion 2, generation 106, `inputDigest` `17202de52898c1b063fed6f2032015520835aa3760f1579fedf5e7c3153f10be`, `reportDigest` `9fc1ebbf...`, `verdict:{exitCode:0,findings:0,blocked:0,withheld:0,readings:0}`, `remainingOpen:0`, `effortDebt:0`. `smooth-sequences/COMPLETION-CERTIFICATE.json` has `status:"complete"` and `inputs:{spec,artifact,evidenceManifest,exemptions}`; `inputs.artifact` is `5536fe4a...`.
4) Ordering hazard: `.claude/commands/graphify-rfc.md:143-146` runs heading deduplication at Step 0 before the Step 1 admission; `.claude/scripts/rfc-graph/deduplicate-headings.js` can overwrite the source RFC. A snapshot check after Step 0 would therefore see a changed `RFC.md` and falsely report a stale verdict. The gate must run before Step 0 and freeze the accepted status digest.
5) Schema constraint: the graph root schema is closed (PX-314 rejects extending it), so a verdict receipt cannot be a graph field; a sidecar beside the graph is the compatible shape. The existing `*-GRAPHIFY-Status.json` is a status file, not a receipt, and is not read by boundify or split.
6) Existing named-code pattern: `verify-chain.mjs:36-49` and `verify-graph-contracts.js` already return named findings and `[ERROR]` / `Cause:` / `Action:`; the new gate follows the same shape.
7) Positive baseline: gaia smooth is pass at generation 106 and the certificate is complete, so the gate should accept the first per-crate run without a smooth rerun; the installed gaia copies of the touched chain scripts are byte-identical to tools/conver.

8) Cross-package invalidation: `snapshotDesignFiles(root)` covers every package `RFC.md` and `SEQUENCES.json`, and graphify Step 0 can deduplicate a package RFC. A package-local receipt that recomputes the whole snapshot would make the next package fail after the first package's write. The receipt is therefore workspace-level and is reused while `statusDigest` and `artifactDigest` match; the full snapshot is recomputed only when a new receipt is needed.

## Acceptance Criteria

- **[Happy path]** A hermetic workspace whose smooth status is pass, whose certificate is complete and whose root artifact hash matches writes `<workspaceRoot>/SMOOTH-VERDICT.json` at graphify and lets graphify, boundify and split proceed with zero findings; the completion report prints `smoothVerdict: pass`.
- **[Error case]** A missing status, a non-pass verdict, a stale input digest, an incomplete certificate, an artifact hash mismatch, a missing receipt and a status or artifact changed after the receipt each exit non-zero with its named code and the `[ERROR]`/`Cause:`/`Action:` shape, never a stack trace.
- **[Edge case]** A project outside a workspacify workspace skips every verdict check and records the skip; a legacy workspace without a certificate but with a pass status is accepted and recorded as legacy; package A's Step 0 dedup does not invalidate package B's receipt; a second `--write` on an unchanged status produces identical receipt bytes.

## Invariants

- [Normal establishment] Inside a workspacify workspace, graphify, boundify and split proceed only when a fresh smooth pass verdict has been accepted, the completion certificate is complete when the evidence manifest exists, and the frozen receipt matches the live status; outside a workspace the gate is skipped and the skip is recorded.
- [Error invariant] A missing status, a non-pass verdict, a stale input digest, an incomplete certificate, an artifact hash mismatch, a missing receipt or a status changed after the receipt exits non-zero with its named code and the `[ERROR]` / `Cause:` / `Action:` shape. An unreadable status or certificate is never treated as pass.
- [Internal state invariant] The graph root/node/edge schemas and the ticket schema are unchanged. The receipt is a sidecar written atomically by the explicit `--write` path; `verify-chain` remains read-only and writes nothing.
- [Boundary invariant] The gate does not change the PX-315 distribution keys, the PX-314 admission scope, the 48-check smooth registry or the 84-row contract_registry. A smooth rerun intentionally invalidates downstream receipts; the repair is to rerun graphify, boundify and split.
