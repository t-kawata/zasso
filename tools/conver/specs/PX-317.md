# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-317: Make the distribution chain prove the artifact denominator, one implementer per active operation, and bind the smooth receipt to live views

**Ticket Key**: PX-317 · **Phase**: -1

## Background

### Goal
Make the graphify -> boundify -> split chain prove that every active operation and every sequence named by the root `*-sequences.json` is present in the package view, that every active operation has exactly one implementing ticket, and that the smooth receipt still binds the package view it certified.

### Purpose
The chain compares view, map, graph, Dirs-Tree and tickets with each other, but never with the artifact denominator. A dropped operation or sequence therefore leaves every layer equal and every gate green. The smooth owner-role check also skips an explicit `undecided` candidate and the renderer writes `consumer` for it, so a multi-owner operation can reach the split with no implementer.

### Motivation
Measured against gaia: 150 active operations, 13 with no implementer in any package map, and smooth verdict pass with zero findings. `op-CreateCivicNeedAsset` has no sequence step and passes every gate. A probe shows `verifyChain` returns `{ok:true,findings:[]}` with an active operation absent from the view. A second probe shows an edited `SEQUENCES.json` is invisible to both `verifySmoothVerdict` and `verifySmoothReceipt` once the receipt exists. The premise that smooth has certified a perfect distribution is therefore false in the live workspace.

### Constraints
Only `tools/conver` is edited; gaia is not edited by this ticket. No node, edge or graph schema change. Outside a workspacify workspace every new check is skipped and the old verdict is preserved. TDD Red-Green-Refactor is strict; use the impact-set `node --test`. The existing test that blesses the `undecided` skip (`tests/smooth-sequences/px310-owner-roles.test.mjs`) is superseded and must be rewritten to the stronger requirement.

## Acceptance Criteria

- [Happy path] A synthetic package whose active operations and sequences are all in the view, with exactly one implementer per active operation, passes smooth, graphify, boundify and split with zero findings.
- [Error case] A dropped active operation, a dropped sequence, zero implementers, two implementers, a step misbinding, or a view edited after the smooth receipt exits non-zero with its named code and never reports a vacuous pass.
- [Edge case] A valid suppliedRule designer_supplied residual, a legacy receipt, an RFC-only edit after the receipt, a package with no units, and a cross-boundary step owned by another package each produce the correct verdict.

## Invariants

- [Normal condition] Every active operation in the artifact is present in the package view (or is a valid `suppliedRule` + `designer_supplied` + zero-step residual), and every sequence with outcome other than `notASequence` is present in the view.
- [Error invariant] A view edited after the smooth receipt never passes: the receipt records a SHA-256 for every package `SEQUENCES.json` and every downstream stage recomputes it. An RFC-only edit made by graphify heading insertion is allowed.
- [Internal state invariant] The view/map/graph/Dirs-Tree/ticket unit sets remain equal, and exactly one ticket carries `mode: "implement"` for each active operation across all phases.
- [Boundary invariant] A step compared between artifact, view and ticket must match on `stepId`, `operationId`, `order`, `line`, `quote`, `subject`, `predicate`, `object`, `contract` and `contractProse`; a field-complete comparison is the boundary.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — root *-sequences.json operations -> package SEQUENCES.json ownedOperationUnits -> distribution map role

- **Precondition**: the root artifact marks an operation active
- **Postcondition**: the package view and map carry the operation and exactly one package declares it the implementer
- **Invariant**: an active operation is present or is a valid suppliedRule designer_supplied residual; zero implementers is always a finding

### C002 — root *-sequences.json sequences and steps -> package SEQUENCES.json sequence units

- **Precondition**: a sequence has an outcome other than notASequence
- **Postcondition**: the package view carries the sequence and every artifact step, and verify-chain reconstructs the same ordered steps
- **Invariant**: the artifact sequence set equals the view sequence set plus declared residuals; no sequence is dropped

### C003 — smooth-sequences status.json and package SEQUENCES.json -> SMOOTH-VERDICT.json -> graphify/boundify/split

- **Precondition**: the smooth receipt was written after a pass verdict
- **Postcondition**: the receipt records a digest for every package view and every downstream stage compares the live digest
- **Invariant**: a view edit after the receipt is STALE_SMOOTH_VERDICT; an RFC.md edit made by graphify heading insertion is not

### C004 — artifact step record -> view step record -> ticket obligation step

- **Precondition**: the artifact and the view declare the same stepId
- **Postcondition**: operationId, order, line, quote, subject, predicate, object, contract and contractProse are equal
- **Invariant**: the comparison is field-complete; a contract-only comparison is insufficient

### C005 — operation ownerPackageIds -> roleCandidate undecided -> distribution map role

- **Precondition**: an operation has more than one owning package
- **Postcondition**: one package declares implementer, or the implementers declare disjoint surfaces
- **Invariant**: undecided is not a pass and the renderer does not silently write consumer for it

- Extract the implementer decision into `requireOneImplementer(unitId, mapRole, viewRole, implementersByUnit)` so the conditional is named after the invariant rather than repeated inline.
- Replace the magic strings `undecided`, `consumer`, `implementer` with the existing exported constants in `distribution-map.mjs`; add a named constant for the receipt schema version.
- Split the receipt verification into `verifyReceiptStatus`, `verifyReceiptArtifact` and `verifyReceiptViews` so each function has one responsibility and the failure names the layer.
- Do not leave a comment that explains why a workaround exists; delete the workaround and name the function after the rule.
