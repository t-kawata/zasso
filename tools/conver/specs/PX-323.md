# PX-323 — Separate build order from implementation order and gate ticket entry on completed prerequisites

## Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow Red → Green → Refactor. No skip, reorder, or parallel execution.

1. **Red** — write failing tests first, covering Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants.
2. **Green** — implement the behavior the tests specify. No hardcoding, input-specific branching, or stubbed returns.
3. **Refactor** — only after green. Apply the Boy Scout Rule; re-run the impact set before and after each step.

## Definition of Done

- D1: tests specify every contract C001–C008.
- D2: the impact set passes with no failure or skip.
- D3: correctness is empirical, not disguised green.
- D4: no intended behavior is untested.
- D5: no test was modified or weakened to reach green.
- D6: no stub remains in the delivered files.

## Background

### Goal

Make the order the pipeline treats as the **implementation order** provably safe at package and ticket granularity, while preserving the **build order** as a separate, still-verified concept.

### Purpose

`workspacify-order/run.mjs` currently prints the order of the template dependency DAG (`WORKSPACIFY-TREE-MANIFEST.json` → `dependencies.dag.implementation_order`) under the name "implementation order". That order is derived from package dependency edges (provider first), not from the artifact's sequences, steps, and boundary contracts. The pipeline never proves that the published order also respects the artifact's runtime prerequisites. As a result, a ticket can enter `make → plan → start → review` while a ticket whose implementation it needs is unfinished.

### Motivation

An entry into the implementation pipeline that cannot be completed is an accident, not a schedule choice. The guarantee must be mechanical:

- the package order displayed and used downstream is a topological order of the union of build dependencies and artifact-derived implementation prerequisites;
- a ticket carries its implementation prerequisites explicitly;
- `/split-to-tickets` proves the per-package and workspace-wide order;
- `/make-ticket` refuses to start while a prerequisite ticket is not implemented.

### Constraints

- Strict TDD; no test modification to pass; additive schema only (`additionalProperties: true` already allows new ticket fields).
- No new dependency crate.
- Case B (`make-ticket` from an instant conversation) and any workspace without a distribution artifact must keep their current behavior.
- Existing consumers of `allocateManifest.implementation_order` remain valid; the build order is preserved, not redefined.
- Verification uses `node --test` on the impact set, not `make test`.

## Investigation

### Evidence gathered in conver and gaia

- `workspacify-order/run.mjs` calls `renderImplementationOrder`; `levels.mjs` `deriveLevels({ packageIds, edges })` puts a package one level after its deepest provider and `assertMatchesPublished` compares the result with `allocateManifest.implementation_order`.
- The edges are the tree dependency edges: `workspacify-tree/lib/dag.mjs:135` writes `implementation_order: computeImplementationOrder(nodeSet, edgeList, cycleList.length)`; `entry-parity.mjs:239` rejects a consumer placed no later than its provider. The order is therefore provider-first dependency order, i.e. build/dependency order.
- Measured in `~/shyme/gaia`: `workspacify-order/run.mjs` prints 29 dirs / 11 levels / 84 dependencies from `dependencies.dag`; the artifact `GaiaSekkeiShiyousho_v32-sequences.json` has 553 sequences, 300 steps and 257 operations, and the 29 package views distribute them. The DAG order does not consult any sequence or boundary row.
- `sequences-slice/lib/view.mjs:152-176` records `ownedSequenceUnits` and `crossBoundarySequenceUnits`; each carries the sequence's ordered steps. The views therefore contain the data needed to derive runtime prerequisites.
- `sequences-slice/lib/distribution-map.mjs:191-197` scopes registry rows to provider/consumer packages; `boundary-contract.mjs` projects `preconditions`, `postconditions` and `invariants` from the registry.
- `tickets/add-tickets-for-phase.js:742-818` already computes `ownerTicketByUnit` and `implementingTicketByUnit` while populating distribution; the same pass can attach prerequisites.
- `tickets/tickets-schema.json` `definitions.ticket` has `additionalProperties: true`; `prerequisites` is additive and needs no schema break.
- `tickets/check-ticket-status.js` gates `plan/start/review` by status but has no cross-ticket prerequisite check.

## Acceptance Criteria

- Happy path: a workspace whose published build order is also a topological order of the artifact-derived implementation prerequisites prints the implementation order and the build order separately; the split gate attaches same-package and cross-package prerequisites; `/make-ticket` passes when every prerequisite is `done`/`reviewed`.
- Error case: a cross-package consumer placed before its provider is `PREREQUISITE_PACKAGE_BEFORE`; a ticket placed before its same-package prerequisite is `PREREQUISITE_NOT_BEFORE`; a prerequisite package without `Tickets.json` is `PREREQUISITE_PACKAGE_UNSPLIT`; an unfinished prerequisite at `/make-ticket` is `PREREQUISITE_NOT_DONE`; a prerequisite cycle is `IMPLEMENTATION_ORDER_CYCLE`.
- Edge case: a ticket with no `prerequisites` exits 0 with `skipped:no-prerequisites`; a workspace without an artifact prints the build order with an explicit label and does not invent a prerequisite; a narrative sequence order with no contract relation creates no edge.

## Invariants

- [Normal establishment] The build order is the published stage-1 DAG order and is never overwritten. The implementation order is a topological order of the union of build edges and derived implementation edges. Every derived edge names its source.
- [Error invariant] A cycle, an unknown source, a self-edge or a duplicate edge is a named failure, never a silent skip. An artifact-backed package without a readable `Tickets.json` prerequisite package fails closed.
- [Internal state invariant] Ticket `prerequisites` is a deterministic function of the graph, the view, the artifact and the registry; re-running split on the same inputs yields the same array in the same order.
- [Boundary invariant] No prerequisite is derived from sequence order alone; only a contract-backed data relation (`consumes` ∩ `produces` or a boundary direction) or a declared graph hard edge creates one. Case B carries no `prerequisites`.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — order:build-vs-implementation

- **Precondition**: A workspace has a tree DAG and an allocate manifest but no artifact-derived order sidecar.
- **Postcondition**: `workspacify-order` prints the published DAG order labelled `build order` and states that the implementation order is not yet derivable; it does not call the DAG order implementation order.
- **Invariant**: The build order remains the published DAG order and is not relabelled.

### C002 — order:package-derivation

- **Precondition**: The artifact views declare operations and sequence steps, the registry declares provider/consumer directions, and the tree manifest declares build edges.
- **Postcondition**: The derived package order is a deterministic topological order of the union; a cycle is `IMPLEMENTATION_ORDER_CYCLE`; every derived edge carries a source.
- **Invariant**: No edge is derived from sequence narrative order alone.

### C003 — order:sidecar

- **Precondition**: A workspace root carries an artifact and the package views.
- **Postcondition**: `WORKSPACIFY-IMPLEMENTATION-ORDER.json` carries `buildOrder`, `implementationOrder`, `prerequisites`, and the source digests; the build order is copied, not recomputed.
- **Invariant**: The sidecar is written atomically and re-running on unchanged inputs yields the same content.

### C004 — prerequisites:ticket

- **Precondition**: Split has populated a ticket with graph hard edges and sequence data relations.
- **Postcondition**: The ticket carries `prerequisites` entries of the form `{ ticket | package, kind, source, boundary? }`; same-package entries name ticket keys, cross-package entries name package ids.
- **Invariant**: No self-edge, no duplicate, every source resolves; a ticket with no distribution carries no `prerequisites` field.

### C005 — prerequisites:split-placement

- **Precondition**: A package's `Tickets.json` carries prerequisites and the workspace order is readable.
- **Postcondition**: `PREREQUISITE_NOT_BEFORE` for a same-package prerequisite placed at or after its dependent; `PREREQUISITE_PACKAGE_UNSPLIT` for a prerequisite package without `Tickets.json`; `PREREQUISITE_PACKAGE_BEFORE` for a cross-package prerequisite placed later in the implementation order.
- **Invariant**: The placement check is topological, not merely numeric; a failure names the prerequisite and the source.

### C006 — prerequisites:entry-gate

- **Precondition**: `/make-ticket` starts for a ticket carrying `prerequisites`.
- **Postcondition**: It exits 1 with `PREREQUISITE_NOT_DONE`, `PREREQUISITE_TICKET_MISSING` or `PREREQUISITE_TICKETS_MISSING` until every implementation prerequisite is `done` or `reviewed`; it exits 0 otherwise.
- **Invariant**: A ticket with no `prerequisites` exits 0 with `skipped:no-prerequisites`; Case B is unchanged.

### C007 — order:split-guarantee

- **Precondition**: `/split-to-tickets` completes a package's tickets.
- **Postcondition**: It runs the package order gate after 5-2 and, when a workspace order sidecar is present, the workspace gate; an unsplit prerequisite package or a later cross-package placement blocks completion.
- **Invariant**: The gate is part of the command, not an optional advisory.

### C008 — compatibility:no-artifact

- **Precondition**: A workspace has no artifact-derived order sidecar, or a ticket has no distribution.
- **Postcondition**: `workspacify-order` still prints the workspace; `make-ticket` skips the gate; `split` writes no prerequisites.
- **Invariant**: Existing behavior is preserved exactly where the new data does not exist.

## Boy Scout Rule

- Function names are verb phrases (`derivePackagePrecedence`, `attachTicketPrerequisites`, `checkPrerequisiteStatus`).
- No `unwrap()`; errors are returned as named findings.
- No hardcoded package ids, ticket keys or paths; constants are named.
- Comments explain why the build and implementation orders are distinct, not what the code does.
