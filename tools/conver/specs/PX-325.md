# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-325: Make implementation ownership, prerequisites, placement, and gates one fail-closed chain

**Ticket Key**: PX-325 · **Phase**: -1

## Background

### Goal
Make the implementation order, ticket prerequisites, split gate, make gate, and workspacify-order display one fail-closed chain, so a ticket cannot enter make -> plan -> start -> review while a prerequisite ticket is unfinished.

### Purpose
PX-323 separated the build order from the implementation order and added a ticket entry gate; PX-324 delivered the per-ticket distribution brief. The remaining defect is that ownership is derived from view presence rather than the implementer role: a foreign view overwrites the local implementer in buildOperationOwners, ownersFromViews marks the operation ambiguous, and deriveSequencePrecedence silently skips the contract-backed edge. The split gate re-derives with the same function, so it passes; the make gate trusts the empty prerequisites field, so it skips. Consolidation also renumbers ticket IDs without remapping prerequisites or implementerTicketId. The display can show a stale or partial sidecar as implementation order, and the spec delivery gate runs before the spec exists.

### Motivation
The requirement is absolute: after /split-to-tickets, all sequences, operations, and boundary contracts must be distributed without omission, contradiction, or loss of pre/post/invariant, and no ticket may start while its prerequisite is incomplete. A silent skip is indistinguishable from a satisfied prerequisite; it turns a pipeline guarantee into an accident.

### Constraints
Strict TDD Red-Green-Refactor; no test weakening; additive schema only; no new dependency; Case B and workspaces without a distribution artifact must keep their current behavior; the published build order must not be rewritten; verification uses node --test on the impact set, then make install-to-projects and a gaia copy check.

### Requirements addressed
1. The pipeline path is /workspacify-* -> /educe-sequences -> /explain-seed -> /grill-me-for-rfc -> /smooth-sequences -> /graphify-rfc -> /boundify-graph -> /split-to-tickets. After split, the make pipeline must mechanically output the target sequences and operations, each step's owner (this ticket, another ticket, another crate directory), and the boundary precondition, postcondition and invariant.
2. make-ticket.md must define clear workflow steps for confirming that output and reflecting it in the ticket design.
3. The mechanism applies automatically only when sequence, operation or boundary information exists; no-information and Case B keep their existing behavior.
4. workspacify-order/run.mjs must display a safe implementation order, and the package and ticket implementation order must be checked at split and after split.
5. A ticket must not enter make -> plan -> start -> review while a prerequisite ticket is unfinished; split guarantees this workspace-wide, and make-ticket checks it at the beginning.

## Acceptance Criteria

- Happy path: a synthetic two-package workspace resolves one implementer, attaches the package prerequisite, blocks make while the provider is planned, passes after it is done, displays a fresh acyclic implementation order, and writes a spec with Distribution Obligations and Work Share.
- Error case: a foreign view cannot overwrite the local implementer; an operation with no implementer is a named finding; an undone provider, a placement inversion, a stale sidecar, a partial view set, or a stale prerequisite set blocks with its named code.
- Edge case: no distribution, no prerequisites, Case B, and ticket-not-found remain skips; a build-only workspace still displays build order with the build label; consolidation remaps every ticket-key reference without manual repair.

## Invariants

- Normal establishment: every operation has exactly one implementer resolution, every ticket prerequisite names its source, and the split, make, and display gates read the same derivation.
- Error invariant: ambiguous ownership, a missing implementer, a stale sidecar, a partial view set, a placement inversion, a missing prerequisite, or a cycle is a named failure, never a silent skip.
- Internal state invariant: prerequisite attachment and consolidation remapping are deterministic functions of the graph, artifact, registry, tree manifest, and ticket order; re-running on unchanged inputs yields the same arrays.
- Boundary invariant: no distribution and Case B write no prerequisites field and keep the old workflow; the build order remains separately preserved; no unsafe order is labeled implementation order.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — ownership:implementer-role

- **Precondition**: An operation unit appears in one or more package views and a distribution role (map or ticket implement unit) is available.
- **Postcondition**: Exactly one implementer is selected; a consumer view never owns the operation for prerequisite purposes; a foreign view never overwrites the local implementer; an undecidable operation emits OWNER_ROLE_UNDECIDED.
- **Invariant**: Ownership is a function of the implementer role, not view presence, and is deterministic.

### C002 — prerequisite:complete-set

- **Precondition**: Package graph, artifact, contract registry and tree manifest are available.
- **Postcondition**: ticket.prerequisites contains every same-package hard graph edge, every resolved cross-package contract relation, and every package-level build or boundary prerequisite; entries are deterministic and deduplicated.
- **Invariant**: No self-edge; every source resolves; no distribution produces no prerequisites field.

### C003 — gate:split-placement

- **Precondition**: Split has attached prerequisites and the sidecar, views or artifact may be stale or partial.
- **Postcondition**: verify-implementation-order fails on PREREQUISITE_SET_MISMATCH, placement inversion, OWNER_ROLE_UNDECIDED, IMPLEMENTATION_ORDER_CYCLE, stale sidecar digest or missing package view; success writes a verifiable sidecar.
- **Invariant**: The build order is preserved separately and no order is derived from partial data.

### C004 — consolidation:reference-remap

- **Precondition**: A phase with fewer than three tickets is merged and ticket IDs are renumbered.
- **Postcondition**: Every ticket-key reference is remapped: prerequisites[].ticket and distribution.units[].obligation.implementerTicketId; relatedTicketIds is regenerated; the post-consolidation order gate passes without manual repair.
- **Invariant**: No reference points to a removed or renumbered key; the remap is deterministic.

### C005 — gate:make-entry

- **Precondition**: make-ticket starts for a ticket in a distributed package.
- **Postcondition**: The gate re-derives prerequisites and placement, compares them with the ticket and sidecar, and exits 1 with PREREQUISITE_SET_MISMATCH, PREREQUISITE_NOT_BEFORE, PREREQUISITE_NOT_DONE or PREREQUISITE_TICKETS_MISSING until every prerequisite is done or reviewed; it covers every provider ticket.
- **Invariant**: The gate never trusts a stale prerequisites field alone; no-distribution, no-prerequisites and ticket-not-found remain skips.

### C006 — display:validated-order

- **Precondition**: workspacify-order reads a sidecar, artifact and views, or neither.
- **Postcondition**: It displays implementation order only if the sidecar or derivation is complete and fresh; a stale sidecar or partial view set is a named failure or explicitly labeled unverified; the build-order fallback is labeled build order.
- **Invariant**: The displayed implementation order is acyclic, covers every package, and is never an unsafe order labeled implementation.

### C007 — make:spec-delivery

- **Precondition**: make-ticket handles a distributed ticket with a spec file.
- **Postcondition**: The spec is written first, then verify-make-distribution runs against it; ## Distribution Obligations is mandatory, and ### Work Share is mandatory when the ticket carries a sequence or ctr unit; a missing required section fails. An operation-only ticket has no Work Share block.
- **Invariant**: The gate cannot pass because the spec is absent; an operation-only ticket is not required to carry Work Share; no-distribution and Case B remain unchanged.

### C008 — brief:message-accuracy

- **Precondition**: A ticket carries a sequence unit and the package view may or may not be readable.
- **Postcondition**: Owner labels and step contracts are accurate; 'other steps: not available' is printed only when the view is genuinely unreadable; otherwise the actual reason is named.
- **Invariant**: No false view-unreadable claim is printed.
