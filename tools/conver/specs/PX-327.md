# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-327: Retract unverified implementation-order sidecars and verify ticket prerequisites workspace-wide

**Ticket Key**: PX-327 · **Phase**: -1

---

## Background

### Goal
Make the implementation-order gates publish a sidecar only after a clean verdict and verify every package's recorded ticket prerequisites at the workspace gate, so neither /split-to-tickets nor /workspacify-order can present an order the pipeline has not proved.

### Purpose
Close two holes found in the PX-326 audit. (1) verifyPackage and verifyWorkspace call writeJsonAtomically whenever write is true, before the verdict is considered; a gate that exits 1 on PREREQUISITE_NOT_BEFORE still leaves IMPLEMENTATION-ORDER.json and WORKSPACIFY-IMPLEMENTATION-ORDER.json, and workspacify-order reads the workspace sidecar (its source digests match) and prints it as the implementation order. (2) verifyWorkspace checks placement of the prerequisites a package already records but never re-derives them, so a Tickets.json with an empty prerequisites array passes the final workspace gate while verifyPackage rejects the same workspace. The workspace-wide guarantee /split-to-tickets claims is therefore not self-contained.

### Motivation
The requirement is absolute: the directory order displayed by workspacify-order must be a safe implementation order, and ticket-level order must be checked at decomposition and after it. A failed gate that still publishes its answer converts a named failure into a trusted artifact. PX-325 already established that a silent skip is indistinguishable from a satisfied prerequisite; an empty prerequisites field has the same shape at the workspace layer.

### Constraints
- TDD Red-Green-Refactor; the Red tests must fail for the absence of the publication guard and the workspace re-derivation.
- Case B, packages without a distribution, and packages without a view or graph keep their current skip behavior.
- No new dependency; no schema change; the sidecar format is unchanged.
- Only public behavior of verifyPackage and verifyWorkspace changes: write mode publishes a verified order and retracts an unverified one; read mode is unchanged.

## Scope

- **Publication guard:** `.claude/scripts/sequences-slice/verify-implementation-order.mjs` — verifyPackage and verifyWorkspace publish their sidecar only when `findings.length === 0`, and remove an existing sidecar when the verdict fails. Before: a PREREQUISITE_NOT_BEFORE verdict still wrote `IMPLEMENTATION-ORDER.json` / `WORKSPACIFY-IMPLEMENTATION-ORDER.json`, and workspacify-order displayed the workspace sidecar as `implementation order ... sidecar`. After: a failed gate leaves no sidecar and the display cannot inherit an unsafe order from it.
- **Workspace prerequisite derivation:** the same file — verifyWorkspace re-derives each package's prerequisites with `buildOperationOwners` + `ticketPrerequisites`, the same functions verifyPackage uses, and reports `PREREQUISITE_SET_MISMATCH` per ticket when the recorded array differs from the derivation. Before: a package with an empty `prerequisites` array passed the workspace gate (verified: verifyPackage returned 1, verifyWorkspace returned 0 on the same workspace). After: the two layers agree.
- **Helpers:** extract `packagePrerequisiteFindings({ workspaceRoot, pkg, view, graph, document, artifact, registry, treeManifest })` so the package gate and the workspace gate share one derivation and one comparison; no rule is duplicated.
- **Entry-gate instructions:** `.claude/commands/plan-ticket.md`, `.claude/commands/start-ticket.md`, `.claude/commands/review-ticket.md` — the success list currently names `skipped:no-distribution`, which `check-ticket-prerequisites.js` never emits. Replace it with the verdicts the gate actually returns (`skipped:no-prerequisites`, `skipped:ticket-not-found`).
- **Display comment:** `.claude/scripts/workspacify-order/run.mjs` — the header says the build order is displayed whenever the artifact and views are absent; an artifact with an unresolved owner actually makes the command refuse. Correct the comment to state that an ambiguous derivation is refused, while the build-order fallback is labelled.
- **Tests:** `.claude/scripts/sequences-slice/verify-implementation-order.mjs` is covered by `tests/sequences-slice/verify-implementation-order.test.mjs`; add the publication and workspace-derivation cases there. `tests/tickets/check-ticket-prerequisites.test.mjs` and `tests/workspacify-order/implementation-order-display.test.mjs` are regression surfaces only.
- **Out of scope:** per-step owner precision for three or more cross-package result-object owners (PX-325 residual); gaia's 20 consumer-only operation roles (upstream data, recorded at PX-325:400); any change to the sidecar schema or to the published build order.

## Investigation

Reproduced with a synthetic workspace holding pkg-1/pkg-2, a hard graph edge N0002->N0001, and a reversed ticket order. verifyPackage({write:true}) returned 1 with PREREQUISITE_NOT_BEFORE and still left crates/pkg-1/IMPLEMENTATION-ORDER.json; verifyWorkspace({write:true}) returned 1 with the same finding and still left WORKSPACIFY-IMPLEMENTATION-ORDER.json; workspacify-order/lib/levels.mjs buildModel then reported orderSource=implementation, orderSourceDetail=sidecar, implementationSerial ['pkg-1','pkg-2']. A second run with correctly ordered tickets but an empty prerequisites array returned verifyPackage=1 (PREREQUISITE_SET_MISMATCH) and verifyWorkspace=0 with no findings. Code sites: verify-implementation-order.mjs:259-268 (workspace write), :380-395 (package write), :245-257 (placement only), :310-322 (package derivation). PX-325 spec:150 states success writes a verifiable sidecar; PX-325 spec:131 states no unsafe order is labelled implementation order; PX-323 spec:24 states the order is provably safe at package and ticket granularity.

## Acceptance Criteria

- Happy path: a workspace whose recorded prerequisites equal the derivation passes verifyPackage and verifyWorkspace, and both sidecars exist after --write.
- Error case: a gate that returns PREREQUISITE_NOT_BEFORE with --write exits 1 and leaves no sidecar at the path it would publish.
- Edge case: an empty prerequisites array with a derivable same-package provider is PREREQUISITE_SET_MISMATCH at the workspace gate, with an error message naming the ticket and the counts.

## Invariants

- [Normal establishment] A gate with zero findings writes its sidecar with source digests and returns 0; a workspace whose recorded prerequisites equal the derivation passes the workspace gate.
- [Invariant on error] A gate with one or more findings returns 1 and leaves no sidecar at its path; a ticket whose prerequisites differ from the derivation reports PREREQUISITE_SET_MISMATCH and names the ticket key.
- [Internal state invariant] The package gate and the workspace gate derive prerequisites with the same operation-owner table and the same ticketPrerequisites function; neither layer re-implements a rule the other applies.
- [Boundary invariant] A package with no view, no graph or no Tickets.json keeps its skip behavior; a ticket with no distribution and no prerequisites keeps its Case B path; the published build order is never rewritten.
