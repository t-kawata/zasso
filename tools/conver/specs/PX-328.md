# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-328: Make the implementer role an authored distribution-ledger fact and filter non-active operations from the implementation order

**Ticket Key**: PX-328 · **Phase**: -1

---

## Background

### Goal
Make the distribution ledger the authored authority for an operation's implementer role, so a multi-owner operation can be resolved through the prescribed render -> split -> smooth pipeline without editing generated JSON, and make the implementation-order derivation honor the artifact's active-operation disposition so framework and excluded operations are not treated as implementer obligations.

### Purpose
Close the two blockers found while diagnosing gaia's OWNER_ROLE_UNDECIDED. (1) The map's `role` is derived only from the view's `roleCandidate`; a multi-owner operation is always `undecided`, so no prescribed surface can record which package implements it. The renderer reads the ledger only on a first bootstrap and then treats the existing map as the authority, so a role cannot be authored through the pipeline. (2) The order derivation records every view operation as needing an owner; smooth intentionally filters to `disposition === 'active'`, so framework and excluded operations (OBJECT_GET, TIME_HANDSHAKE_*, CreatePressReleasePackage, RecordHeatInterventionDecision) are false positives in `make order` and remain after the real roles are fixed.

### Motivation
The requirement is absolute: every sequence and operation must be distributed and implemented, and a correction must flow through the prescribed commands, not through hand-edited generated data. The ledger already states the role in prose (for example gaia-commerce says the act of CreateServiceOrder is its own and the certificate package carries the copy); without a structured authored field the renderer discards that decision and the operator is left with hand-editing the map, which the pipeline overwrites. Separately, `make order` must not report an operation as unimplemented when the artifact says it is not an act to implement.

### Constraints
- TDD Red-Green-Refactor; no test weakening.
- Existing five-column ledgers remain readable; a ledger with no role annotation keeps the current roleCandidate fallback.
- The ledger is the authority for a role only when it carries the annotation; the map is always regenerated by the renderer.
- Case B and workspaces without a distribution keep the current behavior.
- No new dependency; the map schema is unchanged; only the Owner cell grammar is extended.
- The prescribed flow is: install conver, author the ledger roles through the grill re-entry, run complete-run/render-distribution, then smooth; generated JSON is never edited by hand.

## Scope

- **Ledger role grammar:** `.claude/scripts/grill-me-for-rfc/render-distribution.mjs` — parse an Owner cell of the form `pkg-0002 (implementer) + pkg-0004 (consumer)`; the annotation on a row's own package declares that package's role. `bootstrapFromLedger` uses the annotated role over `roleCandidate`; an unannotated ledger keeps the current fallback. `ledgerRowOf`/`ownerCellOf` in `.claude/scripts/sequences-slice/lib/distribution-map.mjs` render the annotation for the row's own package.
- **Ledger is canonical on every render:** `renderDistribution` reads the authored Owner annotations from the current ledger and overlays them onto an existing, otherwise-valid map before computing the digest and re-rendering the ledger. Before: a map that validated was kept unchanged and its ledger overwritten, so an authored role was discarded. After: the ledger's annotated role reaches the map and survives the round trip.
- **Active-operation filter:** `.claude/scripts/sequences-slice/lib/implementation-order.mjs` — add `activeOperationIdsOf(artifact)` (null when the artifact declares no disposition, so old workspaces are unchanged); `ownersFromViewsDetailed`, `deriveSequencePrecedence`, `derivePackagePrecedence` and `ticketPrerequisites` accept it; `buildOperationOwners` in `.claude/scripts/tickets/add-tickets-for-phase.js` and `ownersFromWorkspace`/`verifyPackage`/`verifyWorkspace` in `.claude/scripts/sequences-slice/verify-implementation-order.mjs` compute and thread it; `workspacify-order/lib/levels.mjs` passes it to the ownership and precedence derivation. Non-active operations and their steps no longer produce OWNER_ROLE_UNDECIDED, MISSING_IMPLEMENTER or precedence edges.
- **Scope of the filter:** only `disposition === 'active'` operations are obligations. A valid suppliedRule/designer_supplied residual already lives in the map's `residuals` and is covered by the existing residual rule; it is not required to carry an implementer when it is not a unit. The filter does not change the view, the map, the graph or the ticket unit set.
- **Tests:** `.claude/scripts/grill-me-for-rfc/render-distribution.mjs` gains `tests/grill-me-for-rfc/ledger-role-authoring.test.mjs`; `.claude/scripts/sequences-slice/lib/implementation-order.mjs` gains cases in `tests/sequences-slice/implementation-order.test.mjs`; the workspace and display gates gain regression cases in `tests/sequences-slice/verify-implementation-order.test.mjs` and `tests/workspacify-order/implementation-order-display.test.mjs`.
- **Command documentation:** `.claude/commands/grill-me-for-rfc.md` STEP 8 states the Owner-cell role grammar and that the ledger is canonical for the role; `.claude/commands/smooth-sequences.md` names the repair as authoring the ledger role, not editing the map.
- **Out of scope:** the 13 gaia implementer decisions themselves are design content authored in the package ledgers, not conver code; the application step is the prescribed install -> grill re-entry -> smooth sequence, recorded in the Notes. No change to the sidecar schema, the ticket schema or the published build order.

## Investigation

Gaia diagnosis: the 20 OWNER_ROLE_UNDECIDED operations split into 13 active non-residual operations that need an implementer and 7 operations the artifact marks framework, excluded or a valid declared residual (OBJECT_GET; TIME_HANDSHAKE_COMPLETE/BEGIN/CONFIRM_BINDING; CreatePressReleasePackage; RecordHeatInterventionDecision; SubmitComputeResult, which both package maps already carry as a declared-residual). The authored ledger already states the act for many operations in prose (gaia-commerce §3.26/§3.28/§3.25 and its shared-operation list at lines 5370-5386; gaia-forum §3.6.7; gaia-asset's fifteen-act list), but the renderer ignores it. Only PerformNormalSuccession and PerformLostBodySuccession have a single-owner ledger row; the other 11 active operations carry only co-owner cells, so no mechanical rule can derive the implementer without a structured authored field.

## Acceptance Criteria

- Happy path: an authored ledger role reaches the map and checkOwnerRoles passes for one implementer.
- Error case: an active operation with no implementer annotation or single-owner row remains a named failure; an unknown annotation is ignored.
- Edge case: a legacy ledger and an artifact without dispositions keep their current behavior; a framework/excluded operation no longer appears in the order failure.

## Invariants

- [Normal establishment] A ledger row whose own package is annotated `(implementer)` produces a map unit with `role: implementer` and `implementationSections`; an annotated `(consumer)` produces `role: consumer`; an unannotated row keeps the view roleCandidate fallback.
- [Invariant on error] A role annotation the grammar does not name is not treated as a role; a unit without any implementer remains OWNER_ROLE_UNDECLARED; the render writes nothing when a gate fails.
- [Internal state invariant] The ledger is read before the map is written, and the map is regenerated from the view plus the ledger roles in one pass; the authored role survives a render round trip.
- [Boundary invariant] An artifact that declares no disposition keeps every operation (null filter); an artifact that declares dispositions filters the order to active operations only; the view/map/graph unit sets are untouched.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — render-distribution.mjs#ledger-role

- **Precondition**: The Distribution ledger Owner cell annotates the row's own package as `(implementer)` or `(consumer)`.
- **Postcondition**: renderDistribution produces a map whose unit for that package carries that role (and implementationSections for implementer), and the re-rendered ledger carries the annotation back.
- **Invariant**: The ledger is read before the map is written; an unannotated legacy row falls back to roleCandidate and an unknown annotation is not a role.

### C002 — implementation-order.mjs#active-filter

- **Precondition**: The artifact declares an operation disposition and the caller supplies activeOperationIds.
- **Postcondition**: A non-active operation is skipped by owner resolution and sequence precedence; an active operation with no implementer still produces OWNER_ROLE_UNDECIDED.
- **Invariant**: activeOperationIdsOf returns null when the artifact declares no disposition, so old workspaces keep every operation.

### C003 — verify-implementation-order.mjs#workspace-active

- **Precondition**: The workspace gate reads an artifact with a framework operation and an active operation.
- **Postcondition**: The framework operation contributes no prerequisite finding and the active operation still does; the workspace gate and package gate use the same active set.
- **Invariant**: The active filter never changes the view, map, graph or ticket unit sets.
