# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-329: Derive a reference-unit dependency as an implementation prerequisite

**Ticket Key**: PX-329 · **Phase**: -1

---

## Background

The distribution chain already delivers every sequence step, operation obligation and boundary contract to the ticket, and verify-make-distribution requires a reference unit to name its implementer in the integration test plan. The missing link is the implementation prerequisite: a reference operation unit is a declared dependency on another ticket or package, but ticketPrerequisites derived prerequisites only from graph hard edges, contract-backed sequence relations, build edges and the boundary registry. A consumer ticket could therefore enter make -> plan -> start -> review while the ticket that implements the operation it references was still planned. Requirement 5 forbids this. The fix extends the single derivation used by attachPrerequisites, verify-implementation-order and check-ticket-prerequisites so the same rule is enforced at split time and at every entry point.

## Scope

- Derive a same-package reference-unit prerequisite from obligation.implementerTicketKey.
- Derive a cross-package reference-unit prerequisite from obligation.providers, excluding the local package.
- Suppress a self-edge and a duplicate when a graph, sequence, build or boundary entry already names the same provider.
- Skip a reference to a non-active or residual operation; emit MISSING_IMPLEMENTER when a reference names neither an implementer ticket nor an external provider.
- Add unit tests for the derivation and an integration test proving check-ticket-prerequisites blocks a planned provider.
- Keep no-distribution, no-prerequisites and Case B behavior unchanged.

## Acceptance Criteria

- Happy path: a same-package reference unit becomes a ticket prerequisite and a cross-package reference unit becomes a package prerequisite.
- Error case: a reference unit with no implementer or external provider is a named MISSING_IMPLEMENTER failure, never a silent skip.
- Edge case: self-references, duplicate graph prerequisites, non-active operations, no distribution and Case B remain unchanged.

## Invariants

- [Normal establishment] Every reference operation unit resolves to exactly one implementer ticket or to one or more external provider packages, and the consumer ticket carries the derived prerequisite.
- [Invariant on error] An unresolved reference, a self-reference or a duplicate provider is a named finding or is suppressed deterministically; no reference is silently treated as satisfied.
- [Internal state invariant] ticketPrerequisites is a deterministic function of the tickets, graph, artifact, registry and tree manifest; re-running on unchanged inputs yields the same sorted entries.
- [Boundary invariant] A reference to a non-active or residual operation creates no prerequisite; a ticket with no distribution and Case B keep their old shape and skip the gate.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — distribution:reference:same-package

- **Precondition**: A ticket carries a distribution operation unit whose obligation.mode is reference and whose obligation.implementerTicketKey names another ticket in the same package.
- **Postcondition**: ticketPrerequisites adds a prerequisite entry with ticket=implementerTicketKey, kind=implementation and source=reference:<unitId> to the consumer ticket.
- **Invariant**: No self-edge is created; an existing entry for the same provider is not duplicated; the result is deterministic.

### C002 — distribution:reference:cross-package

- **Precondition**: A ticket carries a reference unit with no implementer ticket and a non-empty obligation.providers list naming another package.
- **Postcondition**: ticketPrerequisites adds a package prerequisite entry for each external provider with kind=implementation and source=reference:<unitId>.
- **Invariant**: The local package is never a prerequisite of itself; duplicate provider entries are suppressed; the result is deterministic.

### C003 — distribution:reference:unresolved

- **Precondition**: A reference unit names neither an implementer ticket nor an external provider package.
- **Postcondition**: ticketPrerequisites emits MISSING_IMPLEMENTER for the unit and attachPrerequisites fails closed.
- **Invariant**: An unresolved reference is never treated as satisfied and never produces a silent empty prerequisite set.

### C004 — entry-gate:reference-prerequisite

- **Precondition**: The split attached a reference-derived prerequisite to the consumer ticket and the entry gate runs for it.
- **Postcondition**: check-ticket-prerequisites exits 1 with PREREQUISITE_NOT_DONE while the provider is not done or reviewed, and exits 0 after it is done or reviewed.
- **Invariant**: No distribution, no prerequisites and Case B remain skips; the gate re-derives the set and rejects a stale or edited field.
