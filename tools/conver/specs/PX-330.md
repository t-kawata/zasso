# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

**Ticket Key**: PX-330 · **Phase**: -1

## Background

The distribution chain already delivers sequences, operations and boundary contracts to a ticket, and the implementation-order gate already blocks a ticket whose prerequisite is unfinished. A fresh audit of the conver scripts found nine remaining defects in that chain. First, merge-contracts-to-tickets attaches every step row of a sequence to every ticket carrying the sequence unit, so a ticket that correctly implements only its own step receives a foreign step contract and verify-make-contracts rejects it. Second, the Work Share table prints only precondition, postcondition and invariant for a foreign step, while the delivery gate requires the step's crossed boundary id from its typed axes, so the required integration entry cannot be written from the script output. Third, the delivery gate matches unit ids, step ids, owner keys and operation fields by substring, so op-1 is satisfied by op-10 and rest is satisfied by restore. Fourth, the displayed implementation order is bound to artifact, view, tree and registry digests but not to the ticket roles the derivation also reads, so editing a role changes the true order while the display keeps showing the recorded one. Fifth, a sequence edge whose consumer operation is implemented by several packages is skipped for every consumer except the alphabetically first implementer, so a real prerequisite is lost. Sixth, the workspace gate skips a package whose GRAPH.json is missing instead of reporting MISSING_DISTRIBUTION_LAYER, so an edited prerequisite set passes the workspace layer while the package layer rejects it. Seventh, verify-make-contracts searches only testUnit while the make workflow documents that a step contract may be planned in testUnit or testIntegration, and the reference-unit package dependency is absent from the package precedence even though it is present in the ticket prerequisites. The fixes must be proved by tests first and must keep the Case B and no-distribution paths unchanged.
One more defect was found during implementation: a provider package that predates the distribution was reported missing even when every one of its tickets was done. Its own ticket statuses now decide completion, and an empty package is still missing.

## Scope

- merge-contracts-to-tickets.js: attach a step contract only to a ticket owning one of the row's operation nodes; drop the sequence-unit fallback
- show-ticket-context.js: render the typed axes (consumes, produces, errors, crosses) for every Work Share step
- verify-make-distribution.js: match unit ids, step ids, owner keys, boundary ids and operation fields as whole tokens rather than substrings
- verify-make-contracts.js: search testUnit and testIntegration for contract clauses, matching the documented make-stage plan

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — step-contract:local-only

- **Precondition**: A sequence is split across tickets and its step sidecar carries rows whose steps belong to different tickets
- **Postcondition**: Each ticket receives only the step contracts its own distribution units carry, and verify-make-contracts passes with its local test coverage
- **Invariant**: Every sidecar row still reaches exactly the ticket that implements the step and no foreign step contract is attached

### C002 — work-share:typed-axes

- **Precondition**: A ticket carries a sequence unit whose view has a foreign step with non-empty typed axes
- **Postcondition**: renderWorkShare prints every non-empty consumes, produces, errors and crosses fact for every step
- **Invariant**: The rendered axes are the same typed facts the delivery gate reads from the view step

### C003 — delivery:whole-token

- **Precondition**: A test plan contains a token that is a prefix or suffix of an owed unit id, step id, owner key, boundary id or operation field
- **Postcondition**: The delivery gate reports the owed item as unplanned
- **Invariant**: Only a whole-token mention satisfies a delivery obligation and no substring match passes

### C004 — display:live-derivation

- **Precondition**: A workspace sidecar exists with source digests and the workspace has an artifact and readable views and tickets
- **Postcondition**: The display refuses the sidecar when the live artifact-derived levels differ and displays it when they agree
- **Invariant**: Ticket-declared roles are part of the order's input even though they are not in the source digests

### C005 — sequence:multi-implementer-consumer

- **Precondition**: A sequence edge reaches an operation implemented by several packages and the consumer package is one of them
- **Postcondition**: The consumer ticket receives a package prerequisite for the earlier operation's packages
- **Invariant**: Every implementer package is considered as a consumer and no implementer is skipped by the first-sorted package id

### C006 — workspace:missing-graph

- **Precondition**: The workspace artifact declares a distribution, a package view exists and the package GRAPH.json is absent
- **Postcondition**: verifyWorkspace reports MISSING_DISTRIBUTION_LAYER, exits non-zero and writes no sidecar
- **Invariant**: The workspace gate and the package gate reject the same state

### C007 — make:contract-plan-fields

- **Precondition**: A contract clause is planned only in testIntegration
- **Postcondition**: verifyMakeContracts accepts the clause and still rejects a clause planned in neither test field
- **Invariant**: Make-stage coverage and the documented testUnit-or-testIntegration rule are one rule

### C008 — order:reference-package

- **Precondition**: A package consumes an operation implemented in another package and no build, boundary or sequence edge orders the two
- **Postcondition**: derivePackagePrecedence adds an implementer-to-consumer edge and the consumer ticket's package prerequisite passes checkPlacement
- **Invariant**: The display, the split gate and the ticket prerequisites read the same reference relation

### C009 — prerequisite:legacy-package

- **Precondition**: A consumer ticket carries a package prerequisite whose package Tickets.json has tickets but no distribution work
- **Postcondition**: Every ticket in that package is done or reviewed and the entry gate passes
- **Invariant**: A provider package is never reported missing merely because its implementation predates the distribution

Implementation notes. The step-contract leak is fixed in merge-contracts-to-tickets by selecting rows through their operation node ids only; the sequence-unit fallback is removed because add-tickets-for-phase already places the operation node in exactly one ticket. Work Share gains an axes column built from the same CONTRACT_AXES vocabulary the gate uses. Token matching escapes the term and requires a non-identifier character on both sides. verify-make-contracts joins testUnit and testIntegration, matching make-ticket Phase 1.6. The implementation-order derivation records consumerPackageIds beside implementerPackageIds, derives reference package edges, and uses every implementer package when attaching a sequence prerequisite. The workspace gate reports MISSING_DISTRIBUTION_LAYER for a view-bearing package whose graph is absent. The display re-derives the order whenever a sidecar exists and refuses a disagreement. make-ticket is corrected where its wording was broader or narrower than the gates. Risk: a reference edge may reveal a real package cycle; the gate then fails closed with IMPLEMENTATION_ORDER_CYCLE instead of hiding the relation. Case B and no-distribution continue to skip every new path.
C009 extends the same compatibility rule to a legacy provider package: when no ticket carries distribution work, every ticket in that package is evaluated, so a completed legacy package satisfies the prerequisite while a todo one still blocks and an empty package stays missing.
