# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-333: Bootstrap a schema-valid graph in /graphify-rfc and align its split and stale-view gates

**Ticket Key**: PX-333 · **Phase**: -1

## Background

### Goal
Make `/graphify-rfc` complete on a package that has `./RFC.md` but no graph: create a schema-valid `RFC-GRAPH.json` carrying `mainLanguage`, define a recorded exception for authoritative tables in the 100-line split gate, and name the repair for a stale-view `STEP_IDENTITY_MISMATCH`.

### Purpose
PX-332 fixed the graphify source at `./RFC.md`. A package without a graph therefore reaches Step 1 with no file to append to, and `crud.js` is the only graph writer. The empty-graph bootstrap it uses is not schema-valid, so the first write fails before any node exists.

### Motivation
Reproduced at HEAD: `crud.js --graph=RFC-GRAPH.json create-nodes --file=nodes.json --source=RFC.md` exits 1 with `must have required property 'mainLanguage'`. `createEmptyGraph()` has omitted the field since it was written (`crud.js:64-66`), while `schema/graph.schema.json:5` has required it since commit daa57694 (2026-07-07). No script writes `mainLanguage`; every existing graph root was authored by hand, and PX-332 tests pre-seed the root (`graphify-cmd.test.cjs:345,395`), which is why the defect stayed invisible. A gaia run also exposed two command-gate gaps: the 100-line rule is declared mandatory while the analyzer advertises an AI override, and `STEP_IDENTITY_MISMATCH` caused by pre-PX-320 views has no documented repair in Step 2.

### Constraints
- `graph.schema.json` keeps `mainLanguage` required; schema relaxation is forbidden.
- `--main-language` is used only when the graph file is first created; an existing graph root is never rewritten by supplying it.
- No other crud subcommand gains a mandatory argument; existing callers keep working unchanged.
- The command Language Protocol table and the First-Class Rule line are frozen.
- The installed command and script copies must stay byte-identical to the conver definition.
- The verifier order comparison is not changed; a stale view is repaired by re-projecting it, not by weakening the gate.

Measured at HEAD (commit 7fec2ae3) before writing the spec.

(1) Bootstrap defect, reproduced:

(2) Code: `crud.js:64-66` returns `{sourceFile, nodes, edges}`; `crud.js:178-188` calls it when the file is absent; `crud.js:584-587` validates the whole graph before every write; `schema/graph.schema.json:5` requires `sourceFile`, `mainLanguage`, `nodes`, `edges`. `git log -S mainLanguage -- crud.js` reports no commit, so the writer never existed; `git blame` shows the required list entered in daa57694 (2026-07-07).

(3) The first write: `graphify-rfc.md:253` runs `crud.js --graph="$graphPath" create-nodes --file=_temp_nodes.json --source="$sourcePath"`. Step 0 writes only the status file, so no earlier call can create the graph.

(4) Why tests missed it: `graphify-cmd.test.cjs:345` and `:395` write a root with `mainLanguage: 'typescript'` before calling crud. `crud.test.cjs:234` asserts the old two-argument empty graph and does not validate it.

(5) Split-gate conflict: the command says "section >100 effective prose lines -> mandatory split" and loops while `Sections exceeding 100 lines != None`; `analyze-source-structure.js:15` calls its output mechanical candidates the AI may override and `:1296` repeats the note; the gaia RFC defect ledger records that splitting its Appendix A/D tables makes `defect-report.js readFirstTable` stop early and undercount defects.

(6) Stale-view measurement: gaia holds 25 `SEQUENCES.json` views and 659 steps; 658 carry the artifact global index rather than the per-sequence position (sample `A-731__1 order=2` where the artifact array index is 2 and the per-sequence position is 0). The artifact has no `order` field; `distribution-map.mjs:160-176` re-bases it to the per-sequence position, and `sequences-slice/lib/view.mjs:129-134` writes the same per-sequence position. The producer and verifier therefore agree; the gaia views predate PX-320.

(7) `annotate-contracts.js` is already corrected: `graphify-rfc.md:295` passes `"$graphPath"`, and `annotate-contracts.js:6` documents a graph path. The gaia copy (`gaia/.claude/commands/graphify-rfc.md:274`) still passes `"$1"` and is an older install.

(8) Distribution: the two command copies and the two crud copies under `../../.claude` and `../../crates/siprs/.claude` are byte-identical to conver before the change (verified with `diff -q`).

(9) Scope check: no zasso `*-GRAPH.json` lacks `mainLanguage`; no graph file needs migration.

## Acceptance Criteria

- [Happy path] A fresh package with `./RFC.md` runs Step 1 through `crud.js create-nodes --main-language=<lang>` and obtains a schema-valid `RFC-GRAPH.json`; the subsequent create-edges and verify calls succeed.
- [Error case] A first write without `--main-language` stops with `MISSING_MAIN_LANGUAGE`, names the create-only contract, and leaves no graph file behind.
- [Edge case] An existing graph root keeps its `mainLanguage` when the flag is supplied; the command records the authoritative-table exception and the stale-view repair, the baseline reports zero findings, and all installed copies match.

## Invariants

- [Normal condition] The graph root created on a fresh package carries `sourceFile`, a non-empty `mainLanguage`, `nodes` and `edges`, and passes `graph.schema.json` unchanged.

- [Internal state invariant] `mainLanguage` is written only at creation; an existing root is not rewritten by the flag, and the step-status state machine is unchanged.
- [Boundary invariant] The schema keeps `mainLanguage` required; the verifier and view producer are unchanged; the Language Protocol and First-Class Rule digests do not move.
