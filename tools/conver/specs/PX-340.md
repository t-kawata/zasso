# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-340: Make the unit-placement gate reject every prose carrier, not the first carrier

**Ticket Key**: PX-340 · **Phase**: -1

---

## Background

### Goal
The unit-placement gate emits UNIT_REQUIRES_FILE whenever any carrier of a unit is a prose node, independent of node id order and independent of whether another carrier is an implementation node.

### Purpose
The gate enforces the PX-319 invariant that a prose node is not an implementation target. Its current first-carrier selection makes that invariant depend on node id sorting, so the same graph can pass or fail for a reason unrelated to the design.

### Motivation
Measured in gaia-foundation: N0043 was a requirement node carrying ctr-boundary-042. The unit also appeared on an implementation node, so unmapped stayed 0 and the graph passed. buildDistributionIndex sorts nodeIds, so a prose id that sorts after the implementation id is never inspected. The report recorded this as a residual risk across several packages.

### Constraints
No new dependency. The three canonical .claude trees stay byte-identical. The existing single-carrier C004 test is not weakened. The gate stays read-only and deterministic. Downstream graph data repairs are out of scope; this ticket only records the new failure set. Boundify placement is PX-339 and is not changed here.

## Acceptance Criteria

- Happy path: a unit carried by both a prose node and an implementation node emits UNIT_REQUIRES_FILE for both node id orders, and the existing single-carrier C004 case stays green.
- Error case: a unit carried only by implementation nodes emits no UNIT_REQUIRES_FILE; a unit with no existing leaf file still emits UNIT_WITHOUT_FILE.
- Edge case: shuffling nodeIds produces the same finding set; the finding code and subject are unchanged; the three canonical copies are sha256-identical.

## Invariants

- [Normal condition] A unit carried by at least one prose node emits UNIT_REQUIRES_FILE with the unit id as its subject.
- [Error invariant] A unit whose carriers are all implementation nodes emits no UNIT_REQUIRES_FILE; a unit with no existing leaf file still emits UNIT_WITHOUT_FILE and is not conflated with the prose refusal.
- [Internal state invariant] The finding set is independent of nodeIds order; the gate writes nothing.
- [Boundary invariant] A prose node that carries no unit produces no finding; an empty distribution index produces no findings.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — distribution unit -> prose carrier refusal

- **Precondition**: A distribution unit lists one or more nodeIds and at least one carrier node has kind rationale, glossary or requirement.
- **Postcondition**: verifyUnitFileCoverage emits UNIT_REQUIRES_FILE for that unit id, regardless of nodeIds order and regardless of whether another carrier is an implementation node.
- **Invariant**: A unit whose carriers are all non-prose emits no UNIT_REQUIRES_FILE; a unit with no existing leaf file still emits UNIT_WITHOUT_FILE.

### C002 — Dirs-Tree distribution index -> gate determinism

- **Precondition**: buildDistributionIndex sorts the nodeIds array for every unit before the gate reads it.
- **Postcondition**: The finding set is identical for any permutation of the same carrier ids, because the gate evaluates every carrier rather than the first one.
- **Invariant**: The finding code and subject remain UNIT_REQUIRES_FILE and the unit id; the gate stays read-only and writes nothing.

## Boy Scout Rule

- Rename the local `carryingNode` to `proseCarrier`, a domain term rather than an incidental first match.
- Keep `PROSE_KINDS` as the single declaration of the prose vocabulary.
- No swallowed errors: a missing node id is skipped explicitly by the map lookup, and the gate remains read-only.

test('C001 a prose carrier is refused whichever carrier id sorts first', () => {
  const root = mkdtempSync(join(tmpdir(), 'px340-order-'));
  try {
    const graph = { nodes: [
      { id: 'N0001', kind: 'architecture', unitIds: ['op-A'] },
      { id: 'N0002', kind: 'requirement', unitIds: ['op-A'] },
    ] };
    const findingsFor = (nodeIds) => verifyUnitFileCoverage({
      graph,
      dirsTree: { distribution: { units: { 'op-A': { nodeIds, paths: [], filePaths: [] } } } },
      root,
    });

    const implementationFirst = findingsFor(['N0001', 'N0002']);
    assert.ok(implementationFirst.some((finding) => finding.code === 'UNIT_REQUIRES_FILE' && finding.subject === 'op-A'));

    const proseFirst = findingsFor(['N0002', 'N0001']);
    assert.ok(proseFirst.some((finding) => finding.code === 'UNIT_REQUIRES_FILE' && finding.subject === 'op-A'));

    assert.deepEqual(proseFirst, implementationFirst);
  } finally {
    rmSync(root, { recursive: true, force: true });
  }
});
