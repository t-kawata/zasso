# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make the /split-to-tickets gate chain sound for any package in any workspacify workspace: one shared edge-ordering definition, ledger-authoritative ownership, package-scoped findings, a feasible work-budget gate, fail-closed phasify, and a closure check that compares the correct pair of contract clauses.

### Purpose
The current gates mix workspace-global state into package-local decisions, ignore the authoritative ledger role for foreign packages, compare a single edge contract's own postcondition with its own precondition, write invalid phase assignments, and enforce a work minimum that no node-granular partition can reach. These are implementation defects, not external data blockers.

### Motivation
A real gaia-foundation run stopped at Step 5-2 with 37 MISSING_IMPLEMENTER and 115 closure findings. Supplying the ledger roles reduces the 37 findings to zero. All 109 inter-ticket closure findings compare the same contract id's postcondition and precondition. phasify reports invalid phases and still writes Tickets.json with exit 0. P1 has 3 nodes but a computed minimum of 6 tickets, and N0008 alone carries 10 contracts against a budget of 2.

### Constraints
- Generic for every project: no package id, node id, operation name, budget value or workspace path may be hardcoded.
- Backward compatible for packages without a distribution view or graph; those keep the old ticket shape.
- No public graph schema change in this ticket; the durable `satisfiedBy` field belongs to PX-344.
- Strict TDD Red -> Green -> Refactor. Tests use synthetic workspaces with arbitrary ids.
- A gate must fail closed on local defects and must not fail on a foreign defect that this package neither owns nor consumes.

## Invariants

- [Normal establishment] Every split gate that decides ordering reads one shared edge-order definition; a synthetic edge with `type` and `attributes.strength` returns the same direction and effective strength in phasify, validate-phasify and verify-implementation-order.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — shared edge-order module -> phasify, validate-phasify, implementation-order

- **Precondition**: Three split components consume one shared edge-order module
- **Postcondition**: A synthetic edge yields one direction and effective strength in phasify, validate-phasify and implementation-order
- **Invariant**: No component defines a private weight or direction table

### C002 — ledger role -> operation ownership

- **Precondition**: A package view leaves a multi-owner operation undecided while its ledger declares one implementer
- **Postcondition**: The package resolves the ledger implementer and reports no MISSING_IMPLEMENTER for an unrelated package
- **Invariant**: A local reference to an undecided operation still fails with a named finding

### C003 — foreign operation -> package gate

- **Precondition**: A foreign operation has no implementer and no local ticket references it
- **Postcondition**: verify-implementation-order --package succeeds while the workspace gate reports the foreign finding
- **Invariant**: No global finding blocks a package that neither owns nor consumes the operation

### C004 — node workload -> work budget gate

- **Precondition**: A node alone exceeds the budget or the minimum ticket count exceeds the node count
- **Postcondition**: The work-budget gate reports WORK_BUDGET_INFEASIBLE and emits no impossible minimum
- **Invariant**: The budget is read from configuration and no project-specific value is hardcoded

### C005 — phasify validation -> Tickets.json write

- **Precondition**: phasify validation returns invalid
- **Postcondition**: Tickets.json is unchanged and the command exits non-zero
- **Invariant**: Dry-run never writes and non-dry-run never writes an invalid phase assignment

### C006 — crossing edge -> ticket closure

- **Precondition**: An edge e crosses a ticket boundary and the target node has an outgoing edge e2
- **Postcondition**: Closure compares post(e) with pre(e2) and passes when the normalized clauses are identical
- **Invariant**: A contract postcondition is never compared with its own precondition

### C007 — satisfiedBy link -> closure predicate

- **Precondition**: A target contract declares satisfiedBy naming the source postcondition or contract id
- **Postcondition**: Closure passes only when the source contract matches that link
- **Invariant**: satisfiedBy equal to the precondition alone never satisfies closure
