# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-347: Size tickets by implementation work and require merge evidence, so over-splitting cannot pass

**Ticket Key**: PX-347 · **Phase**: -1

---

## Background

## Goal
Make `/split-to-tickets` choose the fewest tickets that stay within a measured per-ticket implementation-work ceiling, and make every ticket above one carry evidence that adjacent work was attempted for merge.

## Purpose
Move the ceiling from graph metadata to implementation work. The budget counts operations, sequence steps, owned contracts, distinct implementation files, unit test families, integration test families and module count. Provider-side boundary units, node kinds and graph node count are reported but never sized.

## Motivation
PX-342 introduced a provisional budget of `contracts=2`, `kinds=4`, `files=10`. A real package with 40 provider-side boundary units and 73 nodes produced 33 tickets (2.21 nodes per ticket), more granular than the 3.5 nodes per ticket baseline PX-342 itself called over-split. P0 was exactly `ceil(12/2)=6`; the contract ceiling, not a proven split trigger, set the count. The gate rejected only too few tickets: P3 and P6 passed with four tickets for a two-ticket workload, every split labelled `cohesion`, and no refused merge recorded. `WORK_BUDGET_INFEASIBLE` aborted on a single node carrying 10 boundary units, so the prescribed `--enforce-work-budget` could not complete and was silently omitted. The fix must work for every project, not for one package shape.

## Constraints
- TDD: Red first; the Red set covers every new finding, every excluded metadata case, every package shape and every backward-compatibility path.
- Generic: no package id, path, phase name, contract count or fixture value from a real project appears in code, defaults, comments or tests.
- Backward compatible: existing v1 budget files and existing Tickets.json files remain readable; a caller without the gate keeps the old shape and reports the skip.
- Additive schema: new fields are optional for existing tickets and required by the gate only for new multi-ticket phases.
- No automatic prose merging: the AI writes ticket prose; scripts measure, validate and reject.
- Preserve every existing split gate, the three-ticket phase floor and the Red-Green-Refactor law.

## Acceptance Criteria

- Happy path: a synthetic package with 8 phases, 73 nodes, 53 leaf files and 40 provider-side boundary units produces 10 tickets under the version-2 budget, with P2 and P4 split into two and every other phase one; Step 5-3 consolidates the result into one phase with 10 tickets and every standard gate is green.
- Error case: a discretionary split above the budget floor without a refused merge attempt, a cohesion refusal with fewer than two named behaviours, a refused pair without a valid trigger, a reducible ticket over budget, or a non-record ticket with no `default_files` and no `unlistedFileReason` exits 1 with the named code and writes nothing.
- Edge case: one node with 10 provider boundary units and 12 placement paths but one `default_file` counts as one work unit and one file; an irreducible overage is recorded and does not abort; a package without a view reports `skipped:no-distribution` and a caller without the flag reports `skipped:no-budget-gate`.
- Generality: no real package id, path, phase name, contract count or fixture value appears in code, defaults, comments or tests; sequence-driven and service fixtures pass with their own owned operations, steps and I/O boundaries.
- Backward compatibility: existing v1 budget files and existing Tickets.json files remain readable, no test or implementation is weakened to reach green, and the three-ticket phase floor is unchanged.

## Invariants

- [Normal] Every ticket's effective workload is at or below every budget component, except a component whose overage comes from a single indivisible graph node. A phase has at least one ticket and at most `minimumWorkTickets + acceptedDiscretionaryRefusals`; a budget-forced split is not a discretionary refusal. Every non-final phase has at least three tickets after consolidation.
- [Error] Any reducible overage, missing merge attempt, invalid split reason, or empty `default_files` without `unlistedFileReason` exits 1 before `Tickets.json` is written; no partial file is left.
- [State] Provider boundary units (`ctr-boundary-*`), node kinds and graph nodes never contribute to the effective workload. `files` is the distinct `default_files` set; `modules` is the distinct top-level `src/<module>` set; `testUnit` and `testIntegration` are array lengths; `ownedContracts` counts contract units that are not provider boundary projections.
- [Boundary] A package without a view reports `skipped:no-distribution`; a caller without the gate reports `skipped:no-budget-gate`; a version-1 budget loads with legacy semantics; the version-2 budget is the canonical default; no project-specific constant is required.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — PX-347:workload-components

- **Precondition**: A ticket has graph, Dirs-Tree and optional SEQUENCES context and a default_files list.
- **Postcondition**: workloadOfTicket returns operations, sequenceSteps, ownedContracts, files, testUnit, testIntegration and modules; provider boundary units, kinds and graph nodes contribute zero.
- **Invariant**: Every component is a non-negative integer and the sum of ticket workloads equals the phase workload.

### C002 — PX-347:one-ticket-ceiling

- **Precondition**: A phase workload and a version-2 budget are known.
- **Postcondition**: minimumTicketCount returns the component-wise ceiling of workload divided by budget, at least one; one ticket passes only when every component is within budget.
- **Invariant**: The count is monotonic in workload and non-increasing as the budget grows.

### C003 — PX-347:merge-evidence

- **Precondition**: A phase proposes more than one ticket and carries mergeAttempts.
- **Postcondition**: Every discretionary adjacent pair is merged or refused with a valid trigger and evidence; a budget-forced split is proven by the merged workload exceeding the budget; tickets are at most minimumWorkTickets plus accepted discretionary refusals.
- **Invariant**: A single-ticket phase needs no mergeAttempts.

### C004 — PX-347:split-reason-graph

- **Precondition**: A refused merge names a splitReason and the phase has graph relations.
- **Postcondition**: An intra-phase dependency requires tdd-order, a cross-package edge requires ownership-boundary, an external I/O surface requires disjoint-io, and cohesion names unrelated observable behaviours; a mismatch fails.
- **Invariant**: The reason is never accepted without the matching evidence.

### C005 — PX-347:irreducible-overage

- **Precondition**: A single graph node exceeds a budget component and cannot be divided.
- **Postcondition**: The node id, component, actual and budget are recorded as ACCEPTED_IRREDUCIBLE_OVERAGE and the partition proceeds; a reducible ticket overage fails.
- **Invariant**: A failed reducible validation writes no Tickets.json bytes.

### C006 — PX-347:gate-visibility

- **Precondition**: The canonical split command runs add-tickets-for-phase.
- **Postcondition**: The gate runs with --enforce-work-budget; a missing flag reports skipped:no-budget-gate; a package without a view reports skipped:no-distribution; the success JSON carries the budget report.
- **Invariant**: The gate is never silently absent.

### C007 — PX-347:empty-file

- **Precondition**: A ticket has no default_files.
- **Postcondition**: A non-record ticket without unlistedFileReason returns EMPTY_DEFAULT_FILES; a record ticket or a ticket with unlistedFileReason passes.
- **Invariant**: A file-less ticket is never silently executable.

### C008 — PX-347:phase-consolidation

- **Precondition**: Ticketization is complete for every phase.
- **Postcondition**: Phases with fewer than three tickets merge right-to-left, a small last phase merges backward, and all-small phases collapse to one final phase with all tickets; no ticket is split.
- **Invariant**: Ticket node sets are unchanged and the final phase is exempt only when it is the sole phase.
