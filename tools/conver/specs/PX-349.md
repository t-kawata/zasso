# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-349: Loop-aware conver progress GIF renderer for any workspacify-allocated workspace

**Ticket Key**: PX-349 · **Phase**: -1

## Background

### Goal
Implement node .claude/scripts/conver/draw-progress-gif.js -t <workspace> as a generic conver tool. It accepts any workspace in which both WORKSPACIFY-TREE-MANIFEST.json and WORKSPACIFY-ALLOCATE-MANIFEST.json exist and are readable JSON. It reconstructs the conver five-loop progress and the ticket-growth timeline from the artifacts that exist, writes one self-contained HTML viewer under <workspace>/progress-gif/YYYYMMDDhhmmss.html, and lets the browser Canvas render and download a loop-aware progress GIF. No server, no automatic GIF write by Node, and no branch that exists only for gaia.

### Purpose
Make implementation-space density and ticket growth observable across the full conver loop. A package is a circle whose area is its contract-obligation count and whose fill is its reviewed-obligation ratio. The ring shows the 16 stages in five loop groups. Ticket growth at split, find, and drill is animated at the recovered event time, so the viewer sees that requirements increased rather than implementation disappeared.

### Motivation
The prototype in docs/progress-gif/samples/draw-progress-gif.js is a linear 16-stage renderer with a fixed 640x360 canvas, a 5x7 bitmap font, four colours, no package names, no title, and no ticket-growth timeline. It fails on the manifests-only fixture docs/fixtures/gif-animation/workspace-min.json with ERROR: no dated events found; nothing to draw and exit 3. conver is a five-loop pipeline (README.md:23-48), and ticket growth is created by /split-to-tickets, /find-omissions, and /drill-rfc-down, not only at drill. A project-independent tool is required immediately after /workspacify-allocate.

### Constraints
- Executable gate: both manifests exist and are readable JSON. status, completion_decision, artifact_kind, the hash chain, semantic_review, seed_index, and every later artifact are optional.
- Missing artifact means stage progress zero. Zero events means an initial-state board. Zero packages means an empty board. All three exit zero.
- Node writes HTML only. The browser Canvas renders and downloads the GIF. No local HTTP server.
- No new runtime dependency. Bundle Noto Sans JP under the SIL Open Font License 1.1.
- The workspace is read-only except <workspace>/progress-gif/.
- Visual quality is the sample's level. 300MB is a ceiling, not a target; auto-reduce only when the estimate exceeds it.
- Day-only timestamps render MM/DD --:--. No timestamp or ticket onset is fabricated.
- No gaia-specific id, path, package count, ticket count, or fixture value appears in code, defaults, comments, or tests.
- Source stub scan includes .claude; it excludes node_modules, .git, target, dist, archive, progress-gif, vendor, and fixtures.
- Tests run with node --test on the impact set. make test is not used.

## Boy Scout Rule

- Function names are verb phrases: readManifests, discoverArtifacts, parseTimestamp, countContractObligations, reconstructTicketGrowth, buildLoopEvents, computeLayout, drawFrame, encodeGif, writeHtml, writeSnapshot.
- Variable names carry domain concepts: packageByPath, obligationSet, reviewedObligationCount, ticketCoveredObligationCount, growthEvent, loopSegment, stageProgress.
- One function has one responsibility. parse.js separates manifest reading, artifact discovery, timestamp parsing and state extraction. obligations.js separates graph, boundary and ticket counting. loop.js separates stage events from ticket-growth events. engine.js separates draw calls from GIF encoding.
- Hardcoded values are named constants: STAGE_ORDER, LOOP_GROUPS, GROUP_COLOURS, MIN_CELL, MAX_CELL, DEFAULT_FRAMES, DEFAULT_FPS, SIZE_CEILING_BYTES, SNAPSHOT_SCHEMA.
- No swallowed errors: every file read, JSON parse and browser encode failure produces a named error or a warning with the path and reason. The CLI maps them to exit 2 or 3.
- The new files stay below the 800-line limit; if a module approaches it, split by responsibility rather than adding a comment-heavy block.
- Comments are English and explain why a rule exists, not what the next line does. No gaia-specific value, path or count appears in code, defaults, comments or tests.
- The touched docs/progress-gif files are updated to state that the prototype is a sample and that this ticket is the implementation source of truth.
