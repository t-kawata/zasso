# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-350: Sample-faithful conver progress GIF: preserve the approved sample experience and apply only the agreed improvements

## Background

### Goal
Reimplement tools/conver/.claude/scripts/conver/draw-progress-gif.js and its progress-gif modules so the animation produced for any workspacify-allocated workspace is the approved sample experience, with only the agreed improvement points applied.

### Purpose
The sample in docs/progress-gif/samples/sample-progress.html is the visual baseline: a compact dark board, a left grid of package cells whose interior is a phyllotaxis dot field, additive glow, an activity flash, a vertical 16-stage ladder, and an event stream warped so every stage receives comparable screen time. The improvements below are overlays and metric changes on that grammar. They are not permission to redesign the board.

### Motivation
PX-349 passed its tests but lost the experience. Measured on gaia: 29 packages, canvas 1384x1116, every frame fill 0.00, headline REVIEWED 0/766 0 percent, a circular stage ring instead of the ladder, 3,483 grill events consuming most of the 120 frames, and the final frames reset to educe and the initial date. The sample renders a rising density field at 640x360 and completes in about 2.5 MB. The user rejected the replacement.

### Fixed sample experience (must not change)
- Dark background, one board, left package grid, top header, right vertical ladder.
- Each cell contains a Fermat-spiral dot field of about 110 dots distributed by stage weight.
- Dots light one by one with stage progress; lit dots are colored by group and mixed toward white with density.
- Additive glow whose strength rises with density; a pulsing white ring marks a cell active in the current frame.
- The 16-stage ladder stays vertical, with stage names, per-stage global progress bars and a current-stage highlight.
- The event stream is warped by stage, not by raw event count.
- The first frames hold the initial state and the final frames hold the final state.

### Agreed improvements (the only delta)
1. One circle is one package; the circle count comes from the manifests.
2. Vertical growth is bounded: width and column count stay fixed, cells have a minimum size, the canvas grows only by rows, and the right ladder stays at the top instead of stretching.
3. The package name appears under its circle, wrapped to at most two lines with an ellipsis; the HTML exposes the full name and path on hover.
4. Circle area is proportional to contract obligations; diameter scales with the square root, clamped between a minimum and a maximum. The sample radius shrink by density is abolished. A package with no extracted contract is drawn as an uncertain outline.
5. The inner completion cue is reviewed obligations divided by total obligations. The circle's dot field still shows stage density; the outer ring closes as review completion rises. A fully reviewed cell closes the ring; remanded is not reviewed; zero tickets is not 100 percent.
6. Ticket growth recovered from snapshots, OMISSIONS files, consolidation manifests and drill rounds increases that package's area at the recovered frame, leaves the increase in place, and may lower the completion ratio. A ticket with no contract contributes one scope unit so growth stays observable.
7. Seven command groups use seven colors: discovery teal, dialogue blue, structure violet, implementation orange, convergence yellow, shipping green, evolution pink. The ladder uses the same colors with a gap between groups and highlights the current stage.
8. The headline is the summed reviewed obligations over the summed contract obligations, printed as REVIEWED reviewed/total - percent, with SPLIT split/total beside it. The old weighted 16-stage percentage is removed.
9. The top line is PROGRESS: <basename of the target>.
10. The 5x7 bitmap font is removed. Labels use a bundled modern font (Noto Sans JP variable TTF with its OFL license); the canvas renders with Canvas fillText and measureText.
11. Node only analyzes and writes one self-contained HTML. The browser Canvas draws every frame and downloads the GIF. No server.
12. The SVG-free, dependency-free constraint stays. 300MB is a ceiling, not a target; sample-level size and quality are sufficient.

### Constraints
- The only execution gate is that WORKSPACIFY-TREE-MANIFEST.json and WORKSPACIFY-ALLOCATE-MANIFEST.json exist and are readable JSON. Every later artifact is optional and its absence is progress zero, never an error.
- Any workspacify-allocated workspace must run: zero packages, a root package '.', one package, or forty packages.
- No gaia-specific id, path, package count, ticket count, fixture value, date or branch exists in code, defaults, comments or tests.
- The workspace is read-only except <workspace>/progress-gif/.
- No new runtime dependency. The font is a bundled asset.
- Day-only timestamps render MM/DD --:--; no timestamp or ticket onset is fabricated.
- Tests run with node --test on the impact set; make test is not used.
