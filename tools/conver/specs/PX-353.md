# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-353: Usage snapshot cache: reuse per-file message aggregates to cut progress GIF log scanning

**Ticket Key**: PX-353 · **Phase**: -1

---

## Background

### Goal
Make repeated draw-progress-gif runs reuse usage aggregation work for unchanged Claude Code JSONL files instead of rescanning the whole ~/.claude/projects log tree, while keeping the title numbers identical to a cache-free run.

### Purpose
Reduce the measured 5.89 second scan for 99 files and 1.05 GB of logs, especially when the same workspace is rendered repeatedly.

### Motivation
PX-352 added cumulative usage to the GIF title, but every run re-scans every log file. The progress-gif/snapshots directory currently stores model snapshots only; it is not a usage cache.

### Constraints
- A cached run must produce exactly the same daily series as a cache-free run.
- Only raw unique message records may be cached, never daily aggregates or cost, so price, holiday and date-key changes stay correct.
- Global message.id deduplication across files must be preserved.
- Invalidation uses path plus size plus mtime and inode where available.
- Truncation, rotation, deletion and config-dir or project-key changes invalidate.
- A corrupt, unreadable or schema-mismatched cache falls back to a full scan and never fails GIF generation.
- Writes are atomic and concurrent runs are last-writer-wins.
- The cache lives at <root>/progress-gif/snapshots/usage-cache.json and must not be read as a model snapshot.
- claude-usage.js stays read-only and writes nothing unless a cache path is explicitly supplied.
- The model snapshot, HTML, Markdown report and CLI flags stay unchanged.
- No new dependency; the three script copies stay byte-identical.
- Tests run with node --test on the impact set.

## Scope

- progress-gif/usage-cache.js (new): add readUsageCache, writeUsageCache and validateUsageCache. The header is { schema: 'conver-usage-cache-v1', configDir, projectKey, updatedAt, files }; each file entry is { path, size, mtimeMs, ino, records } and each record is { key, ms, model, miss, hit, out }.
- progress-gif/usage-cache.js: write to a unique temporary path usage-cache.json.tmp.<pid>.<counter> and rename atomically. Remove the temporary file when the write fails. A reader never sees partial JSON.
- progress-gif/usage.js: aggregateUsage accepts optional cachePath and onFileParsed. When cachePath is supplied, read and validate the cache; when it is absent, the function stays fully read-only so claude-usage.js never writes to the target.
- progress-gif/usage.js: for each discovered JSONL file, stat it and compare path, size, mtimeMs and ino with the cache entry. A match reuses cached records without parsing; a mismatch reparses the whole file and replaces its entry.
- progress-gif/usage.js: drop cache entries for files that are no longer discovered, and treat a size decrease or inode change as truncation or rotation.
- progress-gif/usage.js: preserve global deduplication. Merge records from all files by key and keep the maximum value of miss, hit and out plus the maximum timestamp, so file-level sums cannot double count.
- progress-gif/usage.js: replace the per-scan anonymous counter with a stable key filePath:lineNumber for records without message.id or requestId, so an unchanged file keeps the same identity across runs.
- progress-gif/usage.js: apply from/to filtering, isPeak, prices and dateKey after the global merge. The cache never stores date buckets, cost or peak classification.
- progress-gif/usage.js: return cacheStats { filesReused, filesParsed, filesDropped, bypassed }. draw-progress-gif does not print cacheStats.
- draw-progress-gif.js: pass <root>/progress-gif/snapshots/usage-cache.json to aggregateUsage. The file name does not match the 14-digit snapshot pattern, so listSnapshots never reads it.
- claude-usage.js: call aggregateUsage without cachePath so the CLI remains read-only and never creates files in the target directory. Flags, JSON fields, exit codes and stdout stay unchanged.
- Cache failure handling: ENOENT, corrupt JSON, wrong schema, wrong config dir or project key, permission errors and write failures are treated as cache misses. The run falls back to a full scan, returns the same series and keeps exit 0; no report line is added.
- Non-change: the model snapshot schema and contents, HTML/GIF output for the same usage series, Markdown report lines, exit codes and CLI flags are untouched. The only observable differences are scan time and the cache file.
- Dependency and config: no new npm dependency and no configuration file; the cache path is internal and derived from the target workspace.
- Copies: apply the same content to .claude/scripts/conver, tools/conver/.claude/scripts/conver and crates/siprs/.claude/scripts/conver.
- Impact: the first run adds one cache write after the scan; later runs parse only changed files. Memory and cache size grow with the number of unique messages, not with raw line count.

## Source investigation (2026-11-04)

### Current scan path
- draw-progress-gif.js:291 assigns model.usage = await collectUsageSeries(...) on every run; collectUsageSeries at 273-286 calls aggregateUsage.
- progress-gif/usage.js:171 aggregateUsage walks every matching JSONL file via walkJsonl (108) and findCwd (126); there is no cache lookup or write.
- usage.js:202 builds the unique map; 227 keys records by message.id, requestId, or a per-scan anonymous counter; 251 buckets by date and model; 295 builds dailySeries. Prices, holidays and dateKey are applied after dedupe.
- Measured baseline: the zasso tools/conver log tree contains 99 JSONL files, 1.05 GB, and 29,206 unique records; a full claude-usage run takes 5.89 seconds (minimum 5.13 seconds warm).

### Snapshot mechanism
- progress-gif/snapshot.js:10-26 snapshotFromModel stores only schema, generatedAt, workspaceRoot, packages and totals; it contains no usage or cache data.
- snapshot.js:29-39 listSnapshots matches only ^(\d{14})\.json$, so a file named usage-cache.json in the same directory is invisible to the model-snapshot reader.
- draw-progress-gif.js:177/204-207 reads the latest model snapshot only to derive growth events; it does not reuse usage work.

### CLI read-only surface
- claude-usage.js:147-149 calls aggregateUsage(directory, from, to, holidays) without a cache path. Giving aggregateUsage a default cache location would make the CLI write under the target, which would be a behavior change; the cache path must therefore be explicit.

### Dedupe and identity evidence
- The same message.id can appear in multiple files because Claude Code writes one line per content block and resumed sessions can repeat messages. A file-level sum would double count; the global max-by-field merge is required.
- Records without message.id or requestId currently use anonymous-N, which restarts on every scan. A stable filePath:lineNumber key is required for cache reuse.
- The cache must store raw records, not date buckets: prices (DEFAULT_PRICES), holidays and dateKey can change between runs and are applied after the merge.

### Safety evidence
- The cache is advisory: a miss, corrupt file, schema mismatch or write failure can always fall back to the full scan, so correctness never depends on the cache.
- Atomic rename is the only concurrency requirement; two writers may both succeed and the last rename wins because the payload is a complete snapshot of the per-file records observed by that writer.
- The existing test surface is 22 tests across usage.test.mjs (314 lines), cli.test.mjs (165 lines) and source-scan.test.mjs (35 lines); the new cache tests must keep all 22 green and add equivalence, invalidation and fallback coverage.

## Acceptance Criteria

- Happy path: a second draw-progress-gif run with unchanged logs reuses cached records, reports filesReused greater than zero, produces the same usage series and writes the same HTML model as the first run.
- Error case: a corrupt, unreadable, schema-mismatched or unwritable cache falls back to a full scan, produces the same series and keeps exit 0.
- Edge case: appended, truncated, rotated, renamed and deleted log files, duplicate message ids across files, anonymous records, and changed prices, holidays or dateKey all produce the cache-free result.
- Preservation: the first-run result matches PX-352, claude-usage.js remains read-only, and the model snapshot, Markdown report, HTML and CLI flags are unchanged.

## Invariants

- [Normal establishment] A cache hit returns the same records as a fresh parse of the same file, and dailySeries is identical to a cache-free scan.
- [Error invariant] Any cache read, validation or write failure is treated as a cache bypass: the run performs a full scan, returns the same series and exits 0.
- [Internal state invariant] The cache stores only raw unique message records (key, ms, model, miss, hit, out); date filtering, peak/offpeak classification, prices and the date key are applied after the global merge.
- [Boundary invariant] A missing file, size decrease, inode change, or different size or mtime invalidates that file; deleted files are dropped; records without message.id or requestId use a stable file-plus-line key.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — cache identity and invalidation

- **Precondition**: A JSONL file has a cached entry and the current path, size, mtime and inode match the entry.
- **Postcondition**: The cached records are reused and the file is not parsed again.
- **Invariant**: A missing file, a size decrease, an inode change, or a different size or mtime forces a reparse and replaces the entry.

### C002 — global dedupe across files

- **Precondition**: Two files contain records with the same message.id and different streaming snapshots.
- **Postcondition**: The merged series counts that id once with the maximum value of each field and the maximum timestamp.
- **Invariant**: The merged series equals a cache-free scan for the same files.

### C003 — deterministic equivalence

- **Precondition**: The same log files are aggregated once with a warm cache and once with no cache.
- **Postcondition**: Both runs return an identical dailySeries and identical totals.
- **Invariant**: Changing prices, holidays or dateKey after a cache hit still recomputes from raw records and remains identical to a cold scan.

### C004 — cache failure isolation

- **Precondition**: The cache is missing, corrupt, schema-mismatched, unreadable or unwritable.
- **Postcondition**: The run performs a full scan, returns the cache-free series and exits 0; a write failure leaves no partial cache file.
- **Invariant**: No cache failure changes the HTML, GIF, snapshot, report or exit code.

### C005 — read-only CLI and snapshot preservation

- **Precondition**: claude-usage.js runs without an explicit cachePath, and the model snapshot is written after a draw run.
- **Postcondition**: The CLI writes nothing under the target directory, and the model snapshot contains no cache or usage field.
- **Invariant**: The cache file name is ignored by listSnapshots and the snapshot schema is unchanged.

### C006 — atomic concurrent writes

- **Precondition**: Two writers build cache payloads from distinct temporary files.
- **Postcondition**: Both may rename; after both finish the cache parses as complete JSON from one writer.
- **Invariant**: A reader never observes a partial JSON cache file.

## Boy Scout Rule

- New module progress-gif/usage-cache.js with verb-phrase functions: readUsageCache, writeUsageCache, validateUsageCache, fingerprintFile, mergeRecordMaps. Use domain names (fileFingerprints, records, cacheStats, cachePath).
- One responsibility per function: cache I/O, validation, fingerprint comparison, record merging and parsing stay separate.
- Extract the cache schema version, temporary-file suffix and fingerprint fields into named constants; no magic strings or numbers in the aggregator.
- Replace the per-scan anonymous counter with a stable key built from file path and line number.
- Never swallow cache errors: convert every cache read or write failure into an explicit bypass status so the caller can fall back without hiding the failure.
- Keep claude-usage.js read-only by making the cache path an explicit parameter rather than a default.
- Touch only the cache module, usage.js, draw-progress-gif.js, claude-usage.js and the new tests; leave the model snapshot, renderer and HTML code unchanged.
