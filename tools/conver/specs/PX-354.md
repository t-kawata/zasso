# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-354: Aggregated usage cache v2 and right-aligned I/C/O/D title block

**Ticket Key**: PX-354 · **Phase**: -1

---

## Background

### Goal
Shrink the progress-GIF usage cache from a per-line copy of the logs to a per-file unique-message cache with a compact encoding, and render the title bar as a left-aligned name plus a right-aligned "I/C/O/D = <I>M / <C>M / <O>M / $<cost>" block.

### Purpose
The v1 cache stores 120,272 records to carry 29,265 unique messages (15,120,054 bytes; 4.11x redundancy) because every content-block line is stored. The title bar also appends the metrics inline instead of giving them a stable right-aligned position.

### Motivation
User request (2026-11-04): the cache is too granular, and the cumulative tokens and cost should be right-aligned inside the title bar, not appended to the name.

### Constraints
- A warm v2 run must produce exactly the same dailySeries and totals as a cache-free run.
- Only associative pre-aggregation is allowed: merge repeated message.id snapshots within a file by maximum field value. Date buckets, peak classification, prices and cost are never cached.
- Global message.id deduplication across files stays mandatory.
- v1 caches are invalidated by the v2 schema name and fall back to a full scan; no migration code.
- Any cache read, validation or write failure is a cache miss and never fails GIF generation.
- The title block is right-aligned at the progress bar's right edge on the same baseline as the name; the numeric block is never truncated; the name truncates first.
- The legacy title (no usage series) renders exactly as today.
- No new dependency; the three script copies stay byte-identical.

## Investigation

## Source investigation (2026-11-04)

### Cache size evidence
- The v1 cache measured from the zasso tools/conver logs: 15,120,054 bytes, 120,272 stored records, 29,265 unique message keys, redundancy 4.11x (usage-cache.js stores one record per parsed line).
- A v2 payload built from the same data with per-file key merge, a models table and six-element tuples measures 2,151,492 bytes, a 7.03x reduction, with 29,265 stored tuples.
- Max-by-field merge is associative, so merging within a file first and across files second is exactly the current global merge; no correctness is lost.
- Date, peak and cost aggregation cannot be cached: dateKey, holidays and prices are runtime inputs and cross-file duplicate ids would be double counted.

### Current title path
- loop.js:75 formatUsageTitle builds a single string with " | I/C/O = ... | IF-DeepSeek-Flash: $...".
- loop.js:623-625 attaches that string as frame.title only when a usage series and titleName exist.
- engine.js:367-372 selectTitle returns frame.title or the legacy options/header title; engine.js:384-400 draws it left-aligned at header.titleX and fits the width.
- engine.js drawText already supports align right (the percent label uses it at header.percentX).
- layout.js:255-269 defines header.titleX = 12*scale, titleY = 18*scale, barX = 12 and barWidth = baseWidth - 24, so the right edge is width - 12*scale.
- render.test.mjs uses a recording context whose fillText captures text, x, y and font; it can also capture textAlign.

### Test surface

## Acceptance Criteria

- Happy path: a second draw run reuses every unchanged file, the v2 cache is at most a quarter of the v1 size, the usage series is identical, and the title shows the name on the left and the four-value I/C/O/D block right-aligned.
- Error case: a v1, corrupt, foreign or unwritable cache falls back to a full scan, produces the same series and keeps exit zero.
- Edge case: a very long name truncates with an ellipsis while the numeric block stays intact; zero usage keeps the legacy title; duplicate ids across files still count once.

## Invariants

- [Normal establishment] A warm v2 run returns the same dailySeries and totals as a cache-free run, and a reused file returns the same records as a fresh parse.
- [Error invariant] Every cache read, validation or write failure is a bypass: full scan, same series, exit zero.
- [Internal state invariant] The cache stores only per-file unique message tuples plus identity fields; date filtering, peak classification, prices and dateKey are applied after the global merge.
- [Boundary invariant] A missing, changed, rotated or deleted file invalidates its entry; the right title block is never truncated, and the legacy title is unchanged when no usage series exists.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — cache identity and invalidation

- **Precondition**: A cached file entry has path, size, mtime and inode equal to the current file.
- **Postcondition**: The cached tuples are reused and the file is not parsed.
- **Invariant**: A changed, deleted or rotated file reparses or drops its entry.

### C002 — per-file pre-merge and global dedupe

- **Precondition**: One file repeats a message id across content-block lines, and another file contains the same id.
- **Postcondition**: The cache stores one tuple per file key, and the global merge keeps the maximum field values once.
- **Invariant**: The merged series equals a cold scan for the same files.

### C003 — deterministic equivalence

- **Precondition**: The same log files are aggregated with a warm cache and with no cache.
- **Postcondition**: Both runs return identical dailySeries and totals.
- **Invariant**: Changing prices, holidays or dateKey after a hit still recomputes from raw records.

### C004 — cache failure isolation

- **Precondition**: The cache is a v1 schema, corrupt JSON, a foreign config dir or project key, or an unwritable path.
- **Postcondition**: The run performs a full scan, returns the cold series and exits zero, and a write failure leaves no temporary file.
- **Invariant**: A malformed models table, a tuple arity other than six, an out-of-range model index or a negative token value is rejected as a cache miss.

### C005 — read-only CLI and snapshot preservation

- **Precondition**: claude-usage runs without a cache path, and a model snapshot is written after a draw run.
- **Postcondition**: The CLI writes nothing under the target, and the snapshot contains no usage or cache field.
- **Invariant**: The cache file name is ignored by listSnapshots, and the snapshot schema is unchanged.

### C006 — atomic concurrent writes

- **Precondition**: Two writers build cache payloads from distinct temporary files.
- **Postcondition**: Both may rename, and after both finish the cache parses as complete JSON.
- **Invariant**: A reader never observes a partial JSON cache file.

### C007 — size aggregation

- **Precondition**: A log file has many assistant lines but fewer unique keys.
- **Postcondition**: The cache stores one tuple per unique key and no date, peak or cost field.
- **Invariant**: The measured zasso payload is 2151492 bytes versus 15120054 for v1.

### C008 — title segment composition

- **Precondition**: Cumulative tokens and cost are available for a frame.
- **Postcondition**: usageTitleSegments returns left PROGRESS name and right I/C/O/D with four values and ceiling rounding.
- **Invariant**: The right block has exactly four values and no negative number.

### C009 — right-alignment layout

- **Precondition**: A frame carries titleParts and a measureText context.
- **Postcondition**: drawHeader emits the left segment with align left at titleX and the right segment with align right at width minus titleX on the same baseline.
- **Invariant**: leftWidth plus gap plus rightWidth stays within available width; the right block is never truncated; the name truncates with an ellipsis first.

### C010 — legacy title preservation

- **Precondition**: A frame has no titleParts because the usage series is empty.
- **Postcondition**: selectTitleParts returns null and the single legacy title is drawn left-aligned at the base size.
- **Invariant**: No right-aligned call is emitted when titleParts is absent.

## Boy Scout Rule

- usage-cache.js: name the encode and decode responsibilities encodeRecord/decodeRecord and the models table builder buildModelTable; one responsibility per function.
- usage-cache.js: keep CACHE_SCHEMA, CACHE_FILE_NAME and TEMPORARY_SUFFIX as constants; add no magic literals for tuple positions.
- usage.js: parseUsageFile returns already-merged records through one named helper, so parsing and merging stay separate responsibilities.
- loop.js: usageTitleSegments owns the format; formatUsageTitle is a thin compatibility wrapper.
- engine.js: fitTitleLayout owns measurement, shrinking and truncation; drawHeader only places the two segments; TITLE_SEGMENT_GAP and TITLE_ELLIPSIS are named constants.
- Never swallow cache errors: every failure becomes an explicit bypass status.

## Changes in Prior Implementation Rounds

| Before | After | Description |
