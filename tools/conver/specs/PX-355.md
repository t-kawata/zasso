# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-355: Resolve the root package (path '.') in every package enumeration

**Ticket Key**: PX-355 · **Phase**: -1

---

## Background

### Goal
Every sequences-slice and grill reader sees the root package the tree manifest names with path ".", and every consumer of package directories reads one shared enumeration.

### Purpose
The root package is a supported workspacify shape: structure-parity.mjs defines ROOT_PACKAGE_PATH and the platform documents RFC-SEED.md, ./RFC-SEED.md and the root package as one file. A reader that walks only crates/ silently drops the root view, seed and OBLIGATION record, so K8, K5, the projection, the calibration and the rail demand disagree with the workspace.

### Motivation
Crystal exposed the defect: the grill run patched only the installed .claude tree, and make install-to-projects mirrors conver with rsync --delete, so the patch would be deleted. The same root omission exists in five more readers that the crystal patch did not touch.

### Constraints
The tree manifest is the authority; no project-specific ids or paths. A root view is read only when the manifest names a package with path "."; a stray root view without that declaration stays unread. Existing key spellings for declared_interfaces and OBLIGATION records are resolved, not migrated. The legacy package-root readers remain for their current callers. Out of scope: supplying the K1 census, grilling the 22 sibling packages for K5, and complete-run DONE enforcement.

## Invariants

- [Normal condition] Every package tree.workspace.packages names is enumerated exactly once, and the package whose normalized path is "." resolves to the workspace root.
- [Error invariant] A missing or unreadable tree manifest is a fallback to the crates walk, never a throw; an unknown path returns packageId null with a reason naming the normalized path.
- [Internal state invariant] The tree manifest is the only source of package ids and paths; normalizePackagePath is idempotent, uses "/" separators and maps "", "." and "./" to ".".
- [Boundary invariant] A root SEQUENCES.json is read as a package view only when the manifest names a package with path "."; without that declaration it is a stray file and remains unread.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — normalizePackagePath

- **Precondition**: value is a string path, possibly empty, ".", "./", absolute, or using platform separators
- **Postcondition**: returns a POSIX-relative package path with no trailing slash; empty, "." and "./" all return "."
- **Invariant**: normalization is idempotent and preserves non-root path segments

### C002 — packageDirectoriesOf

- **Precondition**: root is an absolute workspace directory; treeManifest is absent or has workspace.packages; fallbackMarkers names the package artifact a caller reads
- **Postcondition**: returns one packageId, packagePath and directory per manifest package, with the "." package resolving to root; without the manifest it returns only crates directories carrying a fallback marker
- **Invariant**: no directory appears twice; the root is included only when the manifest names it, never from file presence

### C003 — resolvePackageByPath

- **Precondition**: packages is the manifest package list; packagePath is absolute or workspace-relative
- **Postcondition**: returns the entry whose normalized path equals the normalized input; empty and "." both match the "." entry
- **Invariant**: a non-matching path returns packageId null and a reason naming the normalized path

### C004 — readWorkspaceObligations

- **Precondition**: root is the workspace root; records live at package/OBLIGATION.json and package/RFC-SEED.md; allocateManifest may key declared_interfaces as pkg-a or crates/alpha
- **Postcondition**: root OBLIGATION.json and root seed serves are included under the "." key; authored keys canonicalize to the manifest package path
- **Invariant**: existing package-root-relative and workspace-relative key spellings still resolve and no record is read twice

### C005 — readWorkspacePackageSegments

- **Precondition**: root is the workspace root and treeManifest names zero or more packages; every package that carries RFC-SEED.md is a candidate
- **Postcondition**: root and nested RFC-SEED.md files are read and keyed by the manifest package path; a seed with no source_segments is an empty list
- **Invariant**: a package with no seed file is skipped, and the package count is the number of seed files read, not the number of manifest entries

### C006 — readViews and findPackageDirectories

- **Precondition**: the workspace root may carry SEQUENCES.json and the tree manifest may name a package with path "."
- **Postcondition**: readViews includes the root view exactly once and findPackageDirectories includes the root directory exactly once
- **Invariant**: when no manifest names "." a root SEQUENCES.json is not read; when no view exists the result is unchanged

### C007 — packageRecordFor

- **Precondition**: obligationsByPath may be keyed by the manifest path (crates/pkg-a, ".") or the legacy package-root path (pkg-a, ..); packageDir is absolute or workspace-relative
- **Postcondition**: the record for the directory is returned under either key, including the root
- **Invariant**: an unknown directory returns null and no record is invented

### C008 — describeEntry

- **Precondition**: directory is the workspace root or a directory beneath it
- **Postcondition**: the root renders as "." in the entry and the repair sentence; a nested relative path is unchanged
- **Invariant**: no entry renders an empty string as its directory
