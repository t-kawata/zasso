# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — graph edges -> phasify SCC condensation (phasify-helpers.orderingEdges, tarjanSCC)

- **Precondition**: Edges contain hard directed ordering edges and non-ordering references or refines edges; node ids are non-empty.
- **Postcondition**: orderingEdges returns exactly the edges with effectiveStrength hard and directionOf non-null; tarjanSCC over that set groups only mutually reachable ordering nodes; applySccToOrder preserves every hard prerequisite before its consumer.
- **Invariant**: For every hard directed edge from provider P to consumer C, C is after P in the applied order; no non-ordering edge can create or move an SCC group.

### C002 — CLI argv -> verify-all-ticket-coverage.main -> readUnitMaterial

- **Precondition**: main receives the arguments after the script name; a Tickets.json exists at the first positional path or at resolveTicketsPath({cwd}); an allocate manifest may exist at the workspace root.
- **Postcondition**: The resolved Tickets.json path is always the first non-flag material argument; a root *-sequences.json beside it is read; the command exits 0 when coverage passes and 1 with MISSING_SIDECAR only when the sidecar is genuinely absent.
- **Invariant**: No argument shape removes the canonical Tickets.json from the material reader; flags are passed through unchanged.

### C003 — distribution map unit -> operation role -> obligation.mode

- **Precondition**: A view unit has unitId op-*, a roleCandidate of implementer, undecided, or null, and the ledger row may have role implementer or consumer and owners string[].
- **Postcondition**: An explicit ledger role wins; otherwise an implementer or consumer roleCandidate wins; otherwise a sole owner equal to packageId yields implementer; otherwise the role stays null or undecided and no implementer is invented.
- **Invariant**: Exactly one ticket implements an operation per package when the ledger or view names an implementer; a consumer role never creates an implementer; sequence units are not assigned an operation role.

### C004 — Tickets.json phases -> populateTicketDistribution -> operation ownership

- **Precondition**: The Tickets document contains zero or more phases in document order; each prior ticket may carry distribution.units with kind operation and obligation.mode implement.
- **Postcondition**: A unit already implemented by a phase before the current one is seeded as prior-owned; the current phase emits obligation.mode reference with the prior ticket durable key; no current ticket emits implement for that unit.
- **Invariant**: Across the whole package, every operation unit has at most one obligation.mode implement; the implementer key is the durable P{phase}-{id} or PX-{id} spelling.

### C005 — phase tickets -> verifySequenceSteps -> MISSING_SEQUENCE_STEP

- **Precondition**: A view declares a step-bearing sequence; a phase carries the sequence node and may implement or reference the step operation.
- **Postcondition**: MISSING_SEQUENCE_STEP is reported only when the phase implements the operation and no ticket carries the step; a reference to a prior-phase implementer produces no finding.
- **Invariant**: The consumer exemption and the implemented-operation predicate are both required; a missing step in the implementing phase is never suppressed.

### C006 — consolidate-phase-tickets key remap -> distribution digest

- **Precondition**: A Tickets document carries per-ticket distribution.units with obligation.implementerTicketKey and stored obligationDigest and distribution.digest.
- **Postcondition**: refreshTicketDistributionDigests recomputes every unit obligationDigest and ticket distribution.digest from the current obligation; writeTicketDistributionAggregate then records the refreshed digests.
- **Invariant**: For every ticket, distribution.digest equals digestTicketDistribution(distribution) after the remap; the aggregate digest is a function of the refreshed ticketDigests only.

### C007 — Tickets.json metadata -> loadGraphEdgesFromTickets

- **Precondition**: Tickets.json has metadata.source, optional metadata.resolvedPaths.graphPath, and sits beside RFC.md and RFC-GRAPH.json or in a nested package.
- **Postcondition**: The graph is read from resolvedPaths.graphPath when present and readable, else from the home-expanded metadata.source with .md replaced by -GRAPH.json, else from the sibling <rfcBasename>-GRAPH.json; null is returned only when no candidate exists or parses.
- **Invariant**: No candidate path is constructed by treating a ~/ path as relative; the chosen path is inside the package directory or explicitly named by metadata.

### C008 — SEQUENCES.json view arrays -> viewUnitMap -> ticket distribution

- **Precondition**: The view may carry the same unitId in obligationUnits and in an owned operation or sequence array; the owned record may carry steps.
- **Postcondition**: The owned record wins; the obligation record is used only when no owned record exists; the resulting distribution unit preserves the owned steps.
- **Invariant**: No unit step list is emptied by a duplicate obligation row; obligation-only units still resolve.
