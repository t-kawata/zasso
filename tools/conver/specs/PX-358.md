# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-358: SCC condensation must normalize graph edges to provider-first order

**Ticket Key**: PX-358 · **Phase**: -1

---

## Background

### Goal
Make condenseOrderingGraph read the implementation order an edge declares, not the raw from/to orientation, so two edges that state the same order are one relation.

### Purpose
phasify must not report a hard constraint violation on a consistent graph, and the implementation order it derives must place every consumer after its provider.

### Motivation
A split in a workspacify package failed Step 4-1 with "hard constraint violations: 1". The graph was consistent: N0016 depends_on N0027 and N0027 constrains N0016 both order N0027 before N0016. The SCC condensation read the raw orientations, grouped the pair, and the group moved one node ahead of a node that constrains it. Any project can write the same pair, so the defect is in the rule, not in that graph.

### Constraints
No project-specific values or paths. A genuine cycle must still fail closed. The rule stays in lib/edge-order.js as the single edge-order authority. No new dependency. CommonJS and ESM consumers both keep working. orderingEdges keeps its raw published meaning.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — graph edge -> provider-first pair

- **Precondition**: Input: a graph edge object with from, to and type. Valid types are the directed types in DIRECTION_BY_TYPE: depends_on, implements, precedes, triggers and constrains. Invalid input: a type with no direction such as references or refines.
- **Postcondition**: Output: a new edge object whose from is the provider and whose to is the consumer, preserving type, attributes and every other field; for provider-is-to the provider is edge.to and the consumer is edge.from; for provider-is-from the provider is edge.from and the consumer is edge.to; a directionless edge returns null.
- **Invariant**: assert(the input edge is not mutated and the returned object is not the input) and assert(directionOf(edge) === provider-is-to implies result.from === edge.to) and assert(directionOf(edge) === null implies result === null).

### C002 — hard directed edges -> SCC components

- **Precondition**: Input: zero or more graph edges including hard directed edges and non-ordering edges, and including the pair A depends_on B plus B constrains A that states one order in opposite raw orientations. Invalid input: none; non-ordering edges are filtered.
- **Postcondition**: Output: the SCC list of the provider-first ordering graph; the agreeing pair yields no component, a genuine mutual depends_on pair yields one component containing both nodes, and non-ordering edge cycles yield no component.
- **Invariant**: assert(condenseOrderingGraph is invariant under the raw orientation chosen for the same order) and assert(a genuine cycle still returns one component) and assert(every component node is joined by a hard directed edge).

### C003 — provider-first pair -> order positions and prerequisite edges

- **Precondition**: Input: the same hard directed edges supplied to kahnTopologicalSort, computeSoftViolations, validate-phasify checkHardConstraints, phasify-omissions check 3 and implementation-order ticketPrerequisites. Invalid input: an edge whose type has no direction.
- **Postcondition**: Output: every consumer places the provider before the consumer; kahnTopologicalSort returns B before A for the agreeing pair; computeSoftViolations reports no violation when the order is provider-first and one violation when reversed; checkHardConstraints and check 3 report no violation for a phase order that places the provider first.
