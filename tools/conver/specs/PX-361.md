# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-361: Graph and Dirs-Tree formula chain with symbol anchors and drill delta support

**Ticket Key**: PX-361 · **Phase**: -1

---

## Background

### Goal
Carry every formula id and digest from RFC-FORMULAS.json into the RFC graph and the Dirs-Tree, including file and symbol anchors, without regenerating a canonical workspace from scratch.

### Purpose
A formula that exists only in the RFC ledger is lost at graphify. The graph must name the node that implements the formula, and the Dirs-Tree must name the leaf file and the symbol that realize it.

### Motivation
The user requires formula and implementation-location penetration to survive graphify and boundify. The existing unit chain proves the pattern; formulas need the same chain.

### Constraints
Backward compatibility: existing graphs without formulaIds remain valid. Graph and Dirs-Tree schemas are additive. Drill delta must carry formulas without full regeneration. No specification edits. Command markdown files touched by this ticket must carry no ticket ids, no change-history prose and no noise.

## Scope

- Add optional formulaIds (array of fx-<digest12>) to .claude/scripts/rfc-graph/schema/node.schema.json and formulaDigest to graph.schema.json; existing graphs remain valid.
- Add .claude/scripts/rfc-graph/attach-formula-ids.js: read RFC-FORMULAS.json, resolve each implementation.rfc_section to a graph node, attach formulaIds, and refuse missing, invented or stale sidecar entries.
- Extend .claude/scripts/rfc-graph/boundify-helpers.js and generate-dir-template.js: write a formulas: header line naming every formula a file realizes; extend the Dirs-Tree with distribution.formulas[formulaId] = {nodeIds, filePaths, symbols}.
- Add .claude/scripts/rfc-graph/verify-formula-file-coverage.js: every formula resolves to a leaf file and a declared symbol; every header formula is on its node; no orphan formula.
- Extend .claude/scripts/rfc-graph/validate-dirs-tree-schema.js to accept the optional formula index and .claude/scripts/sequences-slice/verify-chain.mjs to compare formula sets and digests at graphify and boundify.
- Extend .claude/commands/graphify-rfc.md, .claude/commands/boundify-graph.md and .claude/commands/drill-rfc-down.md: attach formula ids in graphify; project them in boundify; carry them through drill Steps 2 and 3.

## Acceptance Criteria

- Happy path: a fixture formula reaches a graph node, a leaf file and a header, and verify-chain exits 0.
- Error case: a missing node, file or symbol exits non-zero with the formula id and anchor.
- Edge case: a notation-only formula reaches a node and a record ticket without a runtime file.
- Invariant: a stale sidecar digest never mutates the graph or Dirs-Tree.
- Hygiene: graphify-rfc.md, boundify-graph.md and drill-rfc-down.md contain no ticket id and no change-history prose.

## Invariants

- [Normal condition] Every formula id in RFC-FORMULAS.json reaches exactly one graph node and at least one leaf file whose header names it.
- [Error invariant] A stale sidecar, a missing graph node or a missing file/symbol is a named refusal; no partial graph or Dirs-Tree is written.
- [Internal state invariant] The formula set is identical at the RFC, graph and Dirs-Tree layers; the digest is unchanged across layers.
- [Boundary invariant] A formula with no implementation file is allowed only when its ledger class is notation and its realization names an RFC record; it still reaches a node and a ticket.
