# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- Happy path: a formula-bearing fixture drills from spec identity through RFC ledger, sidecar, graph, Dirs-Tree and tickets, and G5 reports zero formula findings with theory parity at every layer.
- Error case: a seed/spec hash mismatch, stale sidecar, ledger/sidecar field divergence, theory mismatch, missing implementation class or symbol, RFC.md origin, missing Tickets.json or changed root round or metadata is a blocking finding; a missing prerequisite is BLOCKED_PREREQUISITE with its producer command; stale INFO/sequences is a named non-blocking finding.
- Edge case: todo, reviewed, done and R<N> tickets keep their status; a notation-only formula reaches a record ticket with a realization test; a declaration-only pre-implementation fixture passes; a single drill completes while other packages owe formulas.
- Anytime: a FRESH run, a resumed run and a VERIFY_ONLY run each converge safely; a no-op run writes no canonical artifact; a second identical run is byte-identical; a concurrent artifact change between stage and approve is refused at the stale baseline, then re-staged and completed without reverting it.
- Edge case (zero formulas): a package owning zero formulas passes without a ledger unless a sidecar exists, in which case the sidecar is validated and projected, and a package owning formulas cannot pass by an unresolved source_segments id.
- Invariant: drill never changes Tickets.json root round, any metadata key or existing ticket statuses; every edit is recorded in Tickets.json.delta.json; a normal evolution run after migration is idempotent; no formula disappears through an unresolved segment or a zero-owned shortcut.
- Hygiene: drill-rfc-down.md contains no ticket id and no change-history prose; shared grill, split and evolution tests stay green.
- Completion: every run ends COMPLETE, BLOCKED_PREREQUISITE or REPAIR_NO_PROGRESS. COMPLETE has every drill gate exit 0 and lists advisories; a repairable finding is never terminal.
- Repair: every finding names the exact command or CRUD operation and the verification command; applying the printed action and re-running reaches COMPLETE.
- Advisory/blocking: an advisory never changes an exit code and never blocks COMPLETE; a blocking finding never exits 0 and is repaired or ends in a named terminal state.

## Invariants

- [Normal establishment] The specification bytes and the seed source_spec hash are identical before Step 1 writes; every owned formula has an RFC ledger row and an RFC-FORMULAS.json entry with the same digest, theory, class, implementation anchor, design and tests. A stale INFO or sequences record is a named finding, never a silent acceptance and never an edited input. A zero-owned package with no sidecar is a valid state: no ledger is required and no formula artifact is added; a zero-owned package with a sidecar validates and projects it.
- [Invariant on error] A seed/spec hash mismatch, unreadable specification, missing sidecar, missing formula row, missing theory, missing implementation class, symbol or design, missing test, invented formula, ledger/sidecar divergence, theory mismatch, RFC.md origin, missing Tickets.json, changed root round, changed metadata or changed existing status is a named refusal; no RFC, graph, Dirs-Tree or Tickets byte is written by the refused step. An unresolved source_segments id is a named refusal before ownership is computed.
- [Internal state invariant] Drill uses the shared spec-formula extractor, ledger parser, graph formula index and ticket merge; no second parser or digest rule is introduced. The Formula ledger is the only RFC region drill regenerates; every other baseline RFC line remains an ordered subsequence. Step 5 uses the formula verifier alone, not the CLI smooth receipt or unit-set layer.
- [Any-time invariant] A run after Tickets.json exists is total: FRESH, MIGRATION, REPAIR, VERIFY_ONLY and resumed runs all converge. A no-op run writes no canonical artifact, a second identical run is byte-identical, and every stage/approve is compare-and-swap against the real artifact digest, root round and status map. A stale staging or delta is refused at the point, then repaired by the printed action and never silently promoted or trusted.
- [Boundary invariant] Root round, every metadata key, existing phase ids, existing ticket ids/phaseIds and existing statuses (including R<N>) survive drill approve; only new tickets, new phases, formulaObligations and fully recorded edits may change. A completed-ticket obligation is reported, never converted into a status change. A single drill does not block on another package workspace S8 residue.
- [Completion invariant] Every run ends in COMPLETE, BLOCKED_PREREQUISITE or REPAIR_NO_PROGRESS. COMPLETE requires every drill gate exit 0 and a report with per-layer evidence and advisories; the workspace S8 rollout gate is reported but is not a drill gate. A repairable finding is repaired and re-verified, never reported as the end state. A finding without an action and a verify command is a defect in the gate, not a valid outcome.
- [Severity invariant] Every finding is blocking or advisory. An advisory never changes an exit code and never blocks COMPLETE; a blocking finding never exits 0 and ends only in COMPLETE, BLOCKED_PREREQUISITE or REPAIR_NO_PROGRESS.
- [Normalization invariant] Paths resolve against the workspace root before comparison; specLocation compares start and end; sidecar parity sorts and trims; a formatting-only difference never fails.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — root specification -> RFC ledger -> sidecar -> graph -> Dirs-Tree -> ticket

- **Precondition**: the seed RFC-SEED.md source_spec.sha256 equals the specification bytes; every source_segments id resolves in WORKSPACIFY-TREE-MANIFEST.json; INFO-RFC-SEED.md and *-sequences.json divergence is a named STALE_SECONDARY_RECORD finding and does not block; RFC-FORMULAS.json is authored for every owned formula with non-empty theory, class, implementation anchor, design and tests; zero owned formulas is a valid state requiring no ledger; the sidecar specPath resolves to the same file as the seed source_spec.path and every specLocation equals the extracted formula line
- **Postcondition**: every owned formula reaches one graph node, one leaf file header and one implementing ticket whose origin path, line and quote equal the sidecar and the specification line text, and whose body, digest, theory, class, implementation anchor, design and tests equal the sidecar; with zero owned formulas and no sidecar the postcondition holds vacuously and no formula artifact is added; a zero-owned package with a sidecar validates and projects that sidecar
- **Invariant**: the formula set, digest, theory, class, implementation anchor, design and tests are identical at the RFC ledger, sidecar, graph, Dirs-Tree and tickets; the ledger and sidecar agree field by field; no formula is missing or invented; a zero-owned package carries no formula artifact unless a sidecar proves it; the ticket origin path, line and quote equal the sidecar and the specification line at every layer; every ticket obligation field equals the sidecar field by field, and the Dirs-Tree symbol set contains the ticket implementation symbol

### C002 — drill approve -> Tickets.json loop state

- **Precondition**: the staging Tickets.json is a byte-for-byte copy of the real Tickets.json, or a missing file is refused by name before staging
- **Postcondition**: root round, every metadata key, existing phase ids, existing ticket ids/phaseIds and existing statuses are preserved; every edited ticket is fully recorded in Tickets.json.delta.json
- **Invariant**: a changed root round, changed metadata value, changed existing status or an unrecorded existing-ticket change is refused before promotion; there is no explicit-entry exception

### C003 — any run time after Tickets.json -> converged RFC/GRAPH/Dirs-Tree/Tickets

- **Precondition**: RFC, GRAPH, Dirs-Tree, Tickets.json and README exist; Tickets.json is the loop state; the seed source_spec matches the specification; the run may start at any step, ticket status or round
- **Postcondition**: a FRESH, MIGRATION, REPAIR, VERIFY_ONLY or resumed run converges to the same verified state; a no-op run writes no canonical artifact; a second identical run adds no change; a valid staging resumes and an invalid one is discarded by name; every approve is compare-and-swap
- **Invariant**: no canonical artifact is overwritten when the real artifact changed since staging or since capture; root round, metadata, existing statuses and ids survive any run; a completed-ticket obligation is reported, never a status change; a stale staging or delta is refused at the point, then repaired by the printed action and never silently promoted

### C004 — gate finding -> repair action -> re-run -> COMPLETE

- **Precondition**: every gate emits code, layer, artifact, formulaId or field, cause, action, verify and route; the run has a selected mode
- **Postcondition**: every repairable finding is repaired through the designated tool and re-verified, and the run ends COMPLETE with every drill gate exit 0; the workspace S8 rollout gate is reported but is not a drill gate; a required input that drill must not create ends BLOCKED_PREREQUISITE with the exact producer command and re-entry condition; a repair that does not clear ends REPAIR_NO_PROGRESS; none of these declares COMPLETE
- **Invariant**: a repairable finding is never terminal; a finding without an action and a verify command is a script defect; no real artifact is promoted before its gate passes; the final report is the only source of COMPLETE; a repairable finding that survives its action and re-run ends REPAIR_NO_PROGRESS; a required input that drill must not create ends BLOCKED_PREREQUISITE with its producer command

### C005 — finding severity -> exit code and terminal state

- **Precondition**: every gate finding carries severity blocking or advisory, an action, a verify command, a route and a terminal state when applicable; the run has one of the four modes
- **Postcondition**: advisory findings are listed and never change an exit code; blocking findings are repaired or end in BLOCKED_PREREQUISITE or REPAIR_NO_PROGRESS; COMPLETE requires zero blocking findings and every drill gate exit 0; the workspace S8 rollout gate is reported but not required
- **Invariant**: no advisory exits non-zero; no blocking finding exits 0; the JSON and Markdown state field is the only source of COMPLETE; the final report carries all findings, advisories, mode, specDigest, owned formula count and converged paths
