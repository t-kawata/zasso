# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-366: Record five-layer execution history and render run markers in progress-gif

**Ticket Key**: PX-366 · **Phase**: -1

---

## Background

### Goal
Every five-layer pipeline command appends a compact execution record to a JSONL history, and draw-progress-gif renders the recorded run dates without changing the output of workspaces that have no history.

### Purpose
The current animation derives drill from one drills/Status.json. Repeated drill runs overwrite that file, so earlier runs vanish, the drill event time moves to the latest updatedAt, blocked runs are invisible, and ticket growth is inferred from the current Tickets.json instead of the run that added it. A per-invocation history gives one record per run: runId, command, stage, packageId, start/finish timestamps, terminal status, and the ticket keys the run added.

### Motivation
Drill is now safe at any time after Tickets.json exists. The user requires repeated executions at arbitrary times to be drawn at their real dates, without double counting or duplicate drawing. History is the missing evidence; the renderer already supports multiple events and key-level growth dedupe.

### Constraints
conver only; other projects receive the change via make install-to-projects. No change to drill gates, Tickets.json schema, RFC artifacts, or the existing stage-progress semantics. History is observability: a write failure prints a warning and never changes a command's exit code. A workspace without history must produce a byte-identical model and frame sequence. History never adds stage progress; repeated runs are run markers and growth.

## Acceptance Criteria

- [Happy path] Run drill twice at different times. .conver-history.jsonl contains two finish records with distinct runId and at values. The GIF shows two run markers at those times, the drill ladder completes at the earliest COMPLETE finish, and the second run adds no progress.
[Happy path] Every one of the 19 pipeline commands leaves one start and one finish record with the correct stage.
[Happy path] A ticket added by a drill run appears once as growth, at the drill run time.
- [Error case] Corrupt one history line. The draw exits 0, uses the valid records, reports the malformed line with its path and line number, and does not discard the file.
[Error case] A blocked drill run records finish status BLOCKED_PREREQUISITE; the GIF shows its marker and no progress change.
[Error case] A history write failure prints a warning and the command continues with its original exit code.
- [Edge case] A workspace with no .conver-history.jsonl produces a byte-identical model, frame sequence, HTML, and snapshot to the current implementation.
[Edge case] A history COMPLETE finish and an artifact stage event for the same run yield one stage event and one growth event, not two.
[Edge case] A start-only (crashed) run appears as a STARTED marker with no progress and no growth.

## Invariants

- [Normal condition] Every instrumented command writes exactly one start record and one finish record with the same runId; the finish is appended after the start.
- [Error invariant] A history write failure or a malformed history line never aborts the command or the draw; it is reported as a warning, and the command exit code and draw exit code stay unchanged.
- [Internal state invariant] History is append-only: an append never truncates, rewrites, or reorders existing bytes. Replaying the same runId and event is idempotent.
- [Boundary invariant] With no history file, analyzeWorkspace and buildFrames produce byte-identical model and frames to the pre-change implementation. With history, no stage progress exceeds 1, and no ticket key contributes more than one growth event.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — run-history start/finish -> .conver-history.jsonl

- **Precondition**: A valid record with runId, event, command, stage in STAGE_ORDER, packageId or null, and an ISO-8601 at; a finish also carries status and addedTicketKeys.
- **Postcondition**: Exactly one JSON line is appended; readHistoryFile returns the record; the same runId and event is not appended twice.
- **Invariant**: Appending never truncates, rewrites, or reorders existing bytes.

### C002 — .conver-history.jsonl -> readHistoryFile

- **Precondition**: The JSONL file contains a line that is not a JSON object or lacks a required field.
- **Postcondition**: readHistoryFile returns the valid records and a warning naming the line; the draw exits 0.
- **Invariant**: One invalid line never discards the remaining lines.

### C003 — history COMPLETE finish -> drill stage event

- **Precondition**: A history COMPLETE finish exists for packageId and the drill stage, and the artifact model already has a drill stage event.
- **Postcondition**: The drill stage event uses the earliest finish time; its increment stays the artifact-derived value; no second stage event is added.
- **Invariant**: The stage progress equals the artifact-derived progress; history changes the drill timing only.

### C004 — history finish records -> run markers and frames

- **Precondition**: Two or more finish records exist for the same packageId and stage, or a finish has status BLOCKED_PREREQUISITE.
- **Postcondition**: Each finish emits a run marker at its own time; the first COMPLETE keeps the stage progress; later and blocked runs add no progress.
- **Invariant**: Stage progress is monotonic and clamped to [0,1]; a blocked run never advances it.

### C005 — history addedTicketKeys -> reconstructTicketGrowth

- **Precondition**: A history finish lists addedTicketKeys and a snapshot, omission, or manifest lists the same ticket key.
- **Postcondition**: Each ticket key appears in at most one growth event, attributed to the history run time; total growth mass does not double.
- **Invariant**: The existing known-key set is respected across all growth sources.

### C006 — no .conver-history.jsonl -> analyzeWorkspace/buildFrames

- **Precondition**: The workspace has no .conver-history.jsonl file.
- **Postcondition**: analyzeWorkspace and buildFrames return the same values as the pre-change implementation; the draw output is byte-identical.
- **Invariant**: History is additive; its absence changes nothing.

### C007 — five-layer command files -> history records

- **Precondition**: The 19 five-layer command files are examined.
- **Postcondition**: Each contains exactly one history start and one history finish with a valid stage and command name.
- **Invariant**: No non-pipeline command is instrumented and no command lacks a finish.
