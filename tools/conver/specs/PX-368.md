# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-368: Drill executes safely at any time after Tickets.json, with no-arg discovery and per-package penetration

## Background

### Goal
Make /drill-rfc-down executable with zero arguments at any time after Tickets.json exists. A resolver discovers README.md (RESIDUE) and the sequences view once, the run branches automatically on their presence or absence, and every file or directory the operator passes is appended as additional material. The drill then proves a per-package penetration chain: view units -> distribution ledger -> GRAPH -> Dirs-Tree -> Tickets, plus the formula chain, and declares COMPLETE only from DRILL-REPORT.json/.md after every per-package gate exits zero.

### Purpose
The README 5-layer loop makes drill the only evolution door after graphify. The newly added requirement says drill must evolve safely at any time after Tickets.json exists, not only at the classic post-ship timing. Today preflight requires README.md, arguments are the entire material list, Step 5 reads the ledger without the view unit set, passes no implementation headers, and session-status prints Complete before Step 5 runs. Those four facts contradict the requirement and the role.

### Motivation
A package that has completed /split-to-tickets but has not run /crystalize-readme has Tickets.json and no README.md; the current preflight refuses it. An operator who drops a design note into the package and runs drill with no arguments loses that note. A view unit that never reached the ledger can go undetected because Step 5 compares the session DesignTree, not the view. A package that is mid-review or whose neighbour is incomplete must still be evolvable, but the current completion path has no per-package report that separates the two scopes.

### Constraints
TDD Red-Green-Refactor only. drill remains the only evolution door; grill remains the upstream design stage. The drill material contract stays given material + README RESIDUE + prior conversation; the grill ./ * discovery is not copied. No workspace-wide gate becomes blocking for one drill: P1 is per-package, P2 is report and advisory. README.md becomes an optional discovered input, not a hard prerequisite. Tickets, RFC, GRAPH, Dirs-Tree, seed and specification remain hard prerequisites. This ticket depends on PX-367 for the uniform repair record and the K1 route. Cross-package API consistency belongs to PX-369.

## Acceptance Criteria

- [Happy path] A package with Tickets.json, no README.md and no arguments runs /drill-rfc-down to Step 5, records readmePresent false, and reaches COMPLETE from DRILL-REPORT.json when every P1 gate exits 0.
- [Error case] A view unit absent from the ledger, an invented ledger row, or a header/unit mismatch exits non-zero, names the unit id and repair, and DRILL-REPORT state is not COMPLETE.
- [Edge case] README present/absent and sequences present/absent each branch automatically; another package incomplete leaves P2 residue reported but does not block this package COMPLETE.

## Invariants

- [Normal condition] Zero-argument drill with no README exits 0, records readmePresent false, skips RESIDUE, and proceeds; explicit arguments are appended after discovered defaults.
- [Error invariant] An explicit argument that does not exist exits non-zero naming the path; a missing Tickets/RFC/GRAPH/Dirs-Tree/seed/spec exits BLOCKED_PREREQUISITE with the producer command.
- [Internal state invariant] The material list is resolved once and recorded; resume reads the record and does not re-discover; arguments never remove a discovered path.
- [Boundary invariant] No sequences view -> the unit chain is vacuous; README absent -> no RESIDUE; another package incomplete -> P2 residue is reported and this package can still COMPLETE.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — preflight.cjs -> drill Step 1

- **Precondition**: Zero arguments and README.md absent in a package that holds Tickets.json
- **Postcondition**: preflight exits 0, reports readmePresent false, and proceeds; an explicit missing argument exits non-zero naming the path
- **Invariant**: README absence never blocks the drill

### C002 — resolver -> session material record

- **Precondition**: A discovered default list and zero or more explicit file or directory arguments
- **Postcondition**: The recorded material list is discovered entries followed by arguments, deduplicated by resolved path, and addedArguments names only the appended arguments
- **Invariant**: An argument never removes or replaces a discovered path

### C003 — resolver -> Step 1 reading

- **Precondition**: README.md and the sequences view may each be present or absent
- **Postcondition**: README present reads RESIDUE; absent skips it; sequences present requires the unit chain; absent makes it vacuous
- **Invariant**: Absence of either optional input changes no other verdict

### C004 — SEQUENCES.json -> Tickets.json

- **Precondition**: A package view holds units and the graph, Dirs-Tree and tickets carry their ids
- **Postcondition**: Every view unit reaches the distribution ledger, the graph, the Dirs-Tree file and exactly one ticket; invented rows and missing units are blocking
- **Invariant**: The unit set at every layer equals the view unit set plus declared residuals

### C005 — drill COMPLETE -> workspace gates

- **Precondition**: Another package in the workspace is incomplete
- **Postcondition**: The workspace gates are reported as P2 residue and the drilled package can still reach COMPLETE
- **Invariant**: No workspace-wide gate blocks a single per-package drill

### C006 — Step 5 gates -> DRILL-REPORT state

- **Precondition**: Step 5 has run the P1 gate set
- **Postcondition**: COMPLETE is written only when every P1 gate exits 0; DESIGN_DONE is the pre-Step-5 state
- **Invariant**: No state other than DRILL-REPORT state declares COMPLETE

### C007 — drill finding -> repair-finding.js

- **Precondition**: A drill gate emits a blocking finding
- **Postcondition**: The finding carries severity, code, layer, artifact, cause, action, verify and route
- **Invariant**: A finding missing action or verify is a script defect
