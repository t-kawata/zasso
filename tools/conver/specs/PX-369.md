# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-369: Cross-package API consistency gate and cross-package re-grill

**Ticket Key**: PX-369 · **Phase**: -1

## Background

### Goal
Add a cross-package API consistency gate that detects the defect class exposed by the crystal-adapter-draw re-grill: a symbol referenced across packages but never declared, a call whose arity or generic arity disagrees with the declaration, a trait and a concrete type carrying the same name, a duplicate definition with a different shape, or a referenced provider with no declared dependency edge. Add an explicit cross-package re-grill mode that requires per-package gate evidence before any generated file outside the invocation package is written.

### Purpose
The re-grill report lists eight cross-package defects: bind arity mismatch; OperationCatalogue and PinnedOperation imported by six packages but undefined in crystal-operation; HostContext with three different field sets; BoundedText<64> used as a generic where the type is non-generic; WebSocketBinding declared as both a trait and a concrete value; a CLI requiring &dyn OperationCatalogue and an undeclared CliBinding::try_new; GrpcBinding generic in one section and non-generic in another; a duplicate CoreOperations in CLI; and an undeclared CanonicalVocabulary dependency in gRPC. The current gates check headings, node mapping, src files, tickets, dangling references, orphan contracts, formulas and units; none parses the Rust surface, so none can catch these.

### Motivation
The user asks whether conver should be fixed before applying the crystal changes. The completion-enforcement and census fixes belong to PX-367, but the eight defects show a separate capability gap: a cross-package re-grill can silently edit seven packages, and no gate proves that the API surface agrees across them. Without this gate the same class will recur, because the RFCs are the only place the signatures exist and no current gate reads them as declarations and uses.

### Constraints
TDD Red-Green-Refactor only. The gate is read-only and deterministic; it writes no RFC, graph, Dirs-Tree, ticket or sidecar. The parser covers Rust code fences and the declaration forms the workspace uses; an unparsed construct is reported as UNPARSED_SURFACE, never silently skipped. No new dependency. The cross-package write mode must not weaken guard-edit-surface default-deny; it is an explicit opt-in that names the edited packages and their gate evidence. The gate is workspace-level: it may be a blocking closure gate for smooth-sequences, a P2 report for drill, and a standalone CLI, but it never blocks a single drill on another package. Crystal-specific fixes are out of scope; the crystal workspace is re-run after PX-367 and PX-368.

## Acceptance Criteria

- [Happy path] A clean workspace with parsed Rust surfaces exits 0 with zero findings; the smooth closure includes the API verdict and the drill P2 report lists it as residue.
- [Error case] Each of the eight defect classes produces its named finding with symbol, package and repair; a cross-package generated write without all-zero evidence is refused.
- [Edge case] An unparsed Rust construct is reported as UNPARSED_SURFACE; a package with no Rust fences is an empty surface, not a finding.

## Invariants

- [Normal condition] Every Rust code fence in every package RFC is parsed or reported as UNPARSED_SURFACE; a clean workspace produces zero findings.
- [Error invariant] A cross-package reference with no provider declaration, a wrong arity, a wrong generic arity, a kind mismatch, a duplicate shape or a missing dependency edge is a finding with code, package, symbol and repair.
- [Internal state invariant] The gate is read-only; it writes no artifact and its output is deterministic across two runs over the same workspace.
- [Boundary invariant] A cross-package generated write outside $RFC_DIR is refused unless --allow-cross-package carries per-package gate evidence; a single drill reports the API verdict as P2 and does not block on another package.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — RFC Rust fences -> workspace symbol table

- **Precondition**: A package RFC carries a cross-package reference to a symbol
- **Postcondition**: The symbol resolves to exactly one declaration in the provider package, or SYMBOL_UNDEFINED names the consumer, symbol and missing provider
- **Invariant**: Every parsed reference has exactly one declaration

### C002 — call site -> declaration

- **Precondition**: A cross-package call supplies arguments
- **Postcondition**: The call arity equals the declared parameter count, or ARITY_MISMATCH names both counts
- **Invariant**: No call is accepted with a different arity than its declaration

### C003 — type use -> declaration

- **Precondition**: A cross-package type use supplies generic arguments
- **Postcondition**: The generic arity equals the declaration, or GENERIC_ARITY_MISMATCH names the symbol
- **Invariant**: A non-generic type is never used with generic arguments

### C004 — declaration -> declaration

- **Precondition**: Two packages declare the same name
- **Postcondition**: The declaration kinds agree, or KIND_MISMATCH names both kinds
- **Invariant**: A name has one kind across the workspace

### C005 — duplicate declaration -> workspace

- **Precondition**: Two packages declare the same name with different shapes
- **Postcondition**: SYMBOL_DUPLICATE names both packages and the differing shape
- **Invariant**: A symbol has one defining package unless an explicit sharing contract exists

### C006 — consumer -> provider

- **Precondition**: A package references a symbol owned by another package
- **Postcondition**: A declared graph edge or allocate boundary exists, or DEPENDENCY_EDGE_MISSING names the missing edge
- **Invariant**: No cross-package reference exists without a declared dependency

### C007 — guard-edit-surface.js -> cross-package write

- **Precondition**: A generated file outside $RFC_DIR is about to be written
- **Postcondition**: The write is refused unless --allow-cross-package names the edited package and every per-package gate exitCode is zero
- **Invariant**: Default-deny outside $RFC_DIR remains the default
