# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-371: Grill completion and cross-package editing are evidence-trustworthy, and the cross-package API gate is precise enough to enforce

## Background

### Goal
Make /grill-me-for-rfc DONE mean that every required gate passed, make a cross-package edit require a package-explicit and gate-backed evidence record, and make verify-api-consistency.mjs precise enough to serve as a blocking cross-package gate.

### Purpose
The crystal-adapter-version-store re-grill exposed five conver defects. The cross-package API gate added by PX-369 is absent from the grill completion path, and on the crystal workspace it reports 4396 blocking findings dominated by false positives (method calls, #[derive], std names), so it cannot be wired in as blocking. Finally, the unstated-denominator repair action tells the reader to run phase.mjs begin <spec-path> "to supply the census", but begin only opens a generation and archives readings; the census lives in declaration.sourceEnumerations and is written by phase 9.

### Motivation
The user asked whether conver must be fixed before applying the crystal changes. PX-367 fixed the completion command but left the state writer and the cross-package edit path open; PX-369 added an API gate but not to the grill path, and its parser is not precise enough to enforce. Without this ticket, a cross-package grill can still produce a DONE that no gate supports, and the API gate cannot be used as evidence.

### Constraints
TDD Red-Green-Refactor only. No crystal edits and no make install-to-projects in this ticket; the user installs later. No new dependencies. ## Acceptance Criteria

- **[Happy path] — complete-run.js writes DONE only with gate evidence:** A package with all ten gates at exit zero and a valid completion receipt reaches DONE; the report lists every gate name and exit code, and completedAt/completedSessions are recorded once.
- **[Error case] — no receipt and no cross-package evidence:** set-state DONE without a receipt exits non-zero and leaves Status.json byte-identical; a generated file outside $RFC_DIR without --package or with fake gate evidence is refused from any cwd.
- **[Edge case] — cross-package API mismatch and parser false positives:** complete-run.js --cross-package refuses DONE on an arity mismatch and reports api-consistency; a fence with a declaration line, #[derive], method calls, &self or std names produces no blocking finding, while the eight PX-369 defect classes still do.

## Invariants

- [Normal condition] Every required gate exits zero and a valid completion receipt is present -> complete-run.js writes state DONE and reports each gate name and exit code.
- [Error invariant] Any required gate exits non-zero, or no valid receipt exists -> DONE is not written, Status.json stays byte-identical, and the refusal names the gate or the missing receipt.
- [Internal state invariant] The completion receipt is written after the gate list is evaluated and is consumed by update-status.js; a replay of a consumed receipt cannot write DONE.
- [Boundary invariant] A generated file outside $RFC_DIR is refused unless --package names the invocation package and --allow-cross-package carries evidence naming verify-api-consistency at exit zero; the same refusal holds from any cwd.

- **Postcondition**: complete-run.js refuses DONE, reports the api-consistency gate, and leaves Status.json unchanged; a clean surface reports the gate at exit zero.

- **Precondition**: A Rust fence contains a function declaration line, a #[derive(...)] attribute, a method call, a &self parameter, or a standard-library name.

- **Invariant**: A blocking reference resolves to exactly one workspace declaration; an unresolvable bare call is not blocking.

- **Postcondition**: The action names /educe-sequences, educe-sequences/declaration.json sourceEnumerations, and phase.mjs through; it does not claim that begin supplies the census.
