# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Make verify-api-consistency precise enough to serve as blocking evidence on a real Rust RFC workspace, and make a cross-package repair authorizable without requiring the workspace to be API-clean before the repair exists.

### Purpose
PX-371 removed method-call, attribute and self-parameter false positives, but the crystal re-grill still reports 610 blocking findings. Multi-line declarations are unparsed and re-read as 0-argument calls, const/async/unsafe functions disappear silently, a nonexistent workspace exits 0, and the guard requires a pre-edit workspace API zero that the cross-package edit itself must create. The gate therefore cannot be trusted, and the repair path is circular.

### Motivation
The user asked conver to resolve every defect exposed by the crystal-protocol-evaluation-plan re-grill. The report confirms the new DONE enforcement works (no false DONE), but the run cannot proceed: five generated-file writes were refused, and the API verdict is dominated by parser artefacts. This ticket makes the verdict trustworthy and the repair path executable.

### Constraints

The parser remains a deterministic line/character reader over Rust code fences; a construct outside the subset is reported, never guessed. The ten required grill gates stay required. ## Investigation

- The PX-371 installed copy in the crystal workspace is byte-identical to the conver source for verify-api-consistency.mjs, parse-rust-surface.mjs and guard-edit-surface.js (SHA-256 match), so the reported behavior is the current implementation, not a stale install.
- verify-api-consistency.mjs --workspace=$HOME/shyme/crystal reports 610 blocking and 297 advisory: SYMBOL_UNDEFINED 422, DEPENDENCY_EDGE_MISSING 61, GENERIC_ARITY_MISMATCH 47, ARITY_MISMATCH 42, SYMBOL_DUPLICATE 25, KIND_MISMATCH 13.
- The parser FUNCTION_LINE (parse-rust-surface.mjs:16) requires the closing parenthesis on the same line. Across the crystal Rust fences there are 332 multi-line function signatures; 291 declarations are reported as declaration shape could not be read, and 254 of those same lines are also emitted as call references with argumentCount 0 because declaredCallNames (:386) only knows recognized declarations.
- callArgumentCount (:173) reads only the current line; 437 call references sit on lines whose parentheses are not balanced, so their argument count is 0.
- pub const fn, pub async fn and pub unsafe fn match neither FUNCTION_LINE nor the unparsed fallback (:327); 32 declarations are silently absent. Example: crates/crystal-protocol-types/RFC.md:501 declares pub const fn from_u64_unchecked, yet CheckedNat::from_u64_unchecked yields 7 SYMBOL_UNDEFINED findings.
- Example of the phantom-reference mechanism: crates/transports/crystal-grpc/RFC.md:409 declares pub fn admit(; the parser reports the line as unparsed and also emits an admit call with 0 arguments, which is then compared with another package's declaration.
- The gate is not pure noise: crates/crystal-protocol-types/RFC.md:684 declares pub fn empty(limit: usize), while other packages call BoundedSeq::empty(); that is a genuine cross-package arity mismatch the gate should keep.
- verify-api-consistency.mjs --workspace=/nonexistent-crystal-root prints 0 blocking, 0 advisory and exits 0: packagesOf() returns an empty list, so the gate fails open. complete-run.js:164 interpolates a null workspace root into --workspace=null, which spawnGate's null check does not catch.
- The cross-package edit path is circular: guard-edit-surface.js:86 requires verify-api-consistency at exit 0 for every edited package; verify-api-consistency.mjs:146 is workspace-wide; complete-run.js:354 adds the same workspace-wide gate under --cross-package. The crystal run therefore refused all five generated-file writes with CROSS_PACKAGE_EVIDENCE_MISSING, and no script produces the evidence file.
- K1 is not a conver defect: SYSTEM-DESIGN-sequences.json has pins.sourceEnumerations empty, educe-sequences/declaration.json has sourceEnumerations empty, and educe-sequences/supplied is empty. The denominator gate correctly reports the axis as unstated. The repair belongs to /educe-sequences and the crystal content, not to this ticket.
- PX-371 parser tests (tests/api-consistency/parse-rust-surface.test.mjs) use only single-line fixtures; there is no multi-line, modifier or trait-method fixture, so the real-workspace gap was not covered.
