# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-373: Evolve an existing Tickets.json in /split-to-tickets without stopping or renumbering

**Ticket Key**: PX-373 · **Phase**: -1

## Background

### Goal
Make /split-to-tickets safe to run against a package that already has Tickets.json. The command must evolve the existing ticket aggregate from the current GRAPH, Dirs-Tree and SEQUENCES instead of replacing its phases, so a /drill-rfc-down evolution can be followed by a concentrated split without losing reviewed statuses, ticket keys, round or authored prose.

### Purpose
/drill-rfc-down Step 4 already evolves Tickets.json through staging, status preservation and compare-and-swap (split-step.js, split-delta-analyzer.js, lib/staging-baseline.js). split-to-tickets is the remaining stage that destroys that state: phasify-graph-and-dirs-files-tree.js:480 assigns existingTickets.phases = ticketsPhases where each phase carries tickets: [] (phasify-helpers.js phasesToTicketsFormat), and consolidate-phase-tickets.js:755-762 renumbers phase and ticket ids. A drill run followed by split therefore loses every reviewed and R<N> ticket.

### Motivation
The operator needs a non-interactive way to concentrate and repair Tickets.json after drill. The command top directive prohibits questions and stopping, while split-to-tickets.md:19 currently says an existing Tickets.json must be asked about and stopped on. An always-converging evolve mode resolves the contradiction without weakening the fresh path.

### Constraints
The command takes no argument (tests/rfc-graph/split-cmd.test.cjs and canonical-paths.test.cjs); the mode is selected by the presence of Tickets.json, never by a flag. The fresh path must stay byte-identical. No phase or ticket renumbering in evolve. Existing status, round, metadata and authored fields are never written. phasify and consolidate are not called in evolve. No new dependency. TDD Red-Green-Refactor only.

## Acceptance Criteria

- Happy path: with Tickets.json present and one new graph node, one run adds exactly one ticket, preserves every existing key and status, and exits 0
- Error case: when the real Tickets.json digest differs from the staging baseline, the run archives and re-stages instead of promoting a stale document, then converges
- Edge case: a phase is inserted between two existing phases without renumbering either, and the implementation-order gate accepts the array order
- Idempotency: a second identical run leaves Tickets.json byte-identical and generation unchanged
- No Tickets.json: the fresh path output is byte-identical to the pre-change golden
- Gates: verify-all-ticket-coverage, verify-chain with stage=split, verify-ticket-closure and the four command-prose tests pass

## Boy Scout Rule

- Function names are verb phrases: deriveTicketDelta, matchNodeIdentity, planTicketPlacement, retireTicket, applyTicketEvolution, archiveTickets, runEvolve, addPhaseNodeIds, insertPhaseAt.
- Variable names are domain concepts: ticketsDocument, graphNode, headingRef, identityRank, retiredFrom, archivePath, stagingPath, conflictClass. No data, info, tmp or x.
- One function, one responsibility: delta derivation never writes; planning never mutates; apply returns a new document; archive only moves the file.
- Hardcoded values become named constants: GRAPH_NODE_ID_PATTERN, DERIVED_TICKET_FIELDS, AUTHORED_TICKET_FIELDS, RETIRED_FIELDS, STAGING_SUFFIX, ARCHIVE_PREFIX, CONFLICT_CLASSES.

- Immutability: every transform deep-clones its input and returns a new document, matching the project coding-style rule.
- Touched code improvement: init-split-to-ticket.sh stops claiming an unconditional overwrite; the new scripts reuse the existing atomic write and digest helpers instead of duplicating them.
