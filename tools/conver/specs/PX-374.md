# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-374: Evidence-based progress-gif timeline and HTML-anchored previous-progress marker

**Ticket Key**: PX-374 · **Phase**: -1

## Background

Artifact files can be created ad hoc by an AI during an unrelated command, so their existence is not evidence that the corresponding stage command ran. The renderer currently infers a split stage event from Tickets.json existence, and the previous-progress marker uses a snapshot value computed by an older model and code path. Both produce a timeline that disagrees with the animation and with the commands that actually ran. This ticket makes stage events execution-evidence based, anchors the previous-progress marker to the newest past HTML render timestamp evaluated against the current model, and fixes the explain stage measurement bug.

### Goal
Make every progress-gif stage event traceable to execution evidence (a .conver-history.jsonl finish record or a command-written stage status file), make the previous-progress marker equal to the current animation's progress at the newest past HTML render timestamp, and make stageProgressOf measure explain from file text.

### Purpose
The animation is a claim about what commands ran and when. A file that an AI created ad hoc (for example Tickets.json during a drill run) must not become a phantom split stage. A snapshot stores a historical value computed by the renderer that produced it; after the model or the renderer changes, that value is not the current animation's state at that time. The marker must be derived from the same state machine that draws the animation, using the HTML filename as the clock.

### Motivation
Two measured defects. (1) gaia pkg-0027/pkg-0028 have Tickets.json but no RFC-SPLIT-Status.json and no split history record; the renderer emitted split events at 2026-11-05T00:00:00Z from the date-only generatedAt, producing a DRILL -> SPLIT regression at frame 167/200 and an '11/05 --:--' header; removing those two events yields zero stage regressions and final progress 0.3289 instead of 0.3302. (2) The 2026-11-05 09:28 HTML embeds previousProgress 0.305193, while its own animation at 2026-11-04T07:16:37Z is 0.315058, a 0.99 percentage-point error; stageProgressOf passes the EXPLAIN-RFC-SEED.md path to factSectionCount, so explain is 0.7 in snapshots while the event path reads file text and reaches 1.0.

### Constraints
- Do not rewrite Tickets.json, RFC artifacts, .conver-history.jsonl, existing HTML files or existing snapshot files; history is evidence and stays immutable.
- Do not change the Tickets.json schema; metadata.generatedAt remains YYYY-MM-DD.
- No new dependencies and no new CLI arguments; dry-run still writes nothing.
- Preserve progress increments for stages that have execution evidence; only unevidenced credit is removed.
- Preserve the existing public exports used by tests and consumers; new helpers are additive.
- Every parsing failure (history line, snapshot, HTML filename) is a warning, never a thrown error; the draw exits 0.
- Tests must be deterministic: fixed fixture stamps and fixed file contents, no wall-clock dependence.

## Invariants

- [Normal condition] Every emitted stage event has a finite t chosen by the hierarchy history finish -> command-written status ISO/runId -> artifact mtime. A status-bearing stage (educe, grill, smooth, graphify, boundify, split, crystalize, drill) emits progress or an event only when its status file or a history finish exists.
- [Error invariant] A malformed history line, snapshot document, HTML filename or unreadable artifact never throws and never aborts the draw; when consulted, it is reported as a warning and the draw exits 0. An unreadable snapshot still supplies its filename clock; its stored value is never used. No partial snapshot or ticket write occurs.
- [Internal state invariant] The timeline is sorted by t, then STAGE_ORDER index, then insertion seq. Package progress and globalStage stay within [0,1]. progressAt is pure and does not mutate the model. The displayed stage index is non-decreasing across frames.
- [Boundary invariant] A day-precision timestamp is never an ordering key or an event instant. The analysis cutoff excludes the current or future HTML. previousProgress is clamped to [0,1] and omitted when null. explain fact sections clamp at 7.

### C001 — artifact existence vs execution evidence

- **Precondition**: package has Tickets.json and has neither RFC-SPLIT-Status.json nor a split finish history record
- **Postcondition**: split stage progress is 0, no split stage event is emitted, and a warning names the package and artifact

- **Precondition**: a history COMPLETE finish, a command-written status time or an artifact mtime exists for (packageId, stage)

### C003 — legacy split status clock

- **Precondition**: RFC-SPLIT-Status.json exists without a split history finish
- **Postcondition**: the split event timestamp equals the runId epoch and progress follows steps.6
- **Invariant**: a command-written status is sufficient execution evidence

- **Precondition**: progress-gif contains YYYYMMDDhhmmss.html files older than the analysis cutoff
- **Postcondition**: previousProgress equals progressAt(model, parseStamp(newestPastHtml))
- **Invariant**: snapshot.overallProgress and projected snapshot stages never position the marker

### C005 — render cutoff

- **Precondition**: an HTML stamp is equal to or later than the analysis cutoff
- **Postcondition**: that HTML is excluded from previous-render selection
- **Invariant**: the current render never becomes its own previous boundary

### C006 — missing HTML fallback

- **Precondition**: no HTML exists and at least one snapshot exists
- **Postcondition**: previousProgress equals progressAt(model, parseStamp(newestSnapshot)) and ignores the stored overallProgress
- **Invariant**: a filename timestamp is a clock; a stored value is not

### C007 — late upstream event

- **Precondition**: a lower-stage event is applied after a higher-stage event
- **Postcondition**: frame.stage is the maximum stage index reached so far and never decreases
- **Invariant**: event timestamps and dates remain chronological

### C008 — explain fact measurement

- **Precondition**: EXPLAIN-RFC-SEED.md contains N fact sections
- **Postcondition**: stageProgressOf explain equals 0.35 + 0.35 + 0.3 * min(1, N/7)
- **Invariant**: factSectionCount receives file text, never a path

### C009 — unverified status-bearing stage

- **Precondition**: a status-bearing stage artifact exists without its status file or history finish
- **Postcondition**: the stage contributes 0 and a warning names the stage, package and artifact
- **Invariant**: unevidenced progress is never credited

### C010 — marker and animation state

- **Precondition**: any model and timestamp t
- **Postcondition**: progressAt(model, t) equals the overallProgress of the last high-resolution frame with frame.t <= t
- **Invariant**: the marker and the animation share one state machine
