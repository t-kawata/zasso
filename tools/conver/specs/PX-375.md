# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-375: Make the progress-gif stage order invariant to mtime and run markers

**Ticket Key**: PX-375 · **Phase**: -1

---

## Background

### Goal
Make the progress-gif animation display the pipeline stages in workflow order (educe, explain, grill, smooth, graphify, boundify, split, drill) on every machine, including a freshly checked-out or copied workspace, and make that order independent of untrusted file mtimes and of history run markers.

### Purpose
The animation is the progress view of the whole pipeline. When it reorders stages it misrepresents progress and erodes trust in the history-backed timeline introduced by PX-374.

### Motivation
On another PC using gaia v0.0.360, progress-gif/20261105170928.html showed EDUCE -> DRILL -> EXPLAIN -> GRAPHIFY -> BOUNDIFY while the same version on the original machine showed the correct order. Two independent causes were found. First, explain has no history record, so its clock is the mtime of INFO-RFC-SEED.md and EXPLAIN-RFC-SEED.md; a checkout or copy rewrites that mtime to now (2026-11-05 09:48:55 JST on the other PC versus 2026-10-26 09:38:14 JST here), which is later than the graphify, boundify and split status times and later than the first drill events. orderGrillAfterExplain then drags every grill event after explain and repairUpstreamOrder drags graphify, boundify and split after grill, while drill stays at its own time. Second, applyEvent advances lastStageIndex for every timeline kind, so a drill start or BLOCKED_PREREQUISITE run marker advances the displayed stage with zero drill progress.

### Constraints
- Do not rewrite historical Tickets.json, RFC artifacts, .conver-history.jsonl, HTML renders or snapshots.
- Do not weaken or delete tests. Red tests must fail for the absence of the fix.
- Keep the evidence gating, the [evidence] warnings and the previous-progress marker semantics added by PX-374.
- Keep buildFrames and progressAt on the same state machine.
- The model stays a deterministic function of the workspace; clamping must be reproducible.

## Acceptance Criteria

- Happy path: on the other-PC shape (explain artifact at 2026-11-05T09:48:55Z, graphify/boundify/split status in October, drill status/history in November) the animation plays EDUCE -> EXPLAIN -> GRILL -> SMOOTH -> GRAPHIFY -> BOUNDIFY -> SPLIT -> DRILL with no stage regression.
- Happy path: a drill BLOCKED_PREREQUISITE or STARTED run marker does not make DRILL the displayed stage before the drill stage event; frame.stage stays at the last real stage event.
- Edge case: an explain artifact time inside [initialT, earliest trusted downstream] is preserved (the 2026-10-26T00:38Z case); with no trusted downstream evidence the current mtime behavior is unchanged.
- Error case: a drill stage event older than split is clamped to the split end; a malformed or missing date falls back to initialT without throwing.
- Regression: all existing progress-gif tests pass, and the previous-progress marker still calls progressAt with the newest HTML stamp.

## Invariants

- 【Normal establishment】For every frame produced by buildFrames, STAGE_ORDER.indexOf(frame.stage) is non-decreasing, and progressAt(model, frame.t) returns the same overallProgress as that frame.
- 【Error invariant】A timeline event whose kind is run or growth never changes state.lastStageIndex or state.lastStage. A malformed or missing timestamp never throws; it falls back to initialT.
- 【Internal state invariant】Per package, once stage events are ordered by STAGE_ORDER their times are non-decreasing; an explain event with timeSource artifact is clamped into [initialT, earliest trusted downstream stage time].
- 【Boundary invariant】When no trusted downstream stage evidence exists, an artifact-only explain event keeps its mtime. When two events share a timestamp, the existing stage-index tie-break keeps explain before graphify.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — loop.js applyEvent stage frontier

- **Precondition**: A timeline event with kind=run (for example a drill BLOCKED_PREREQUISITE history marker) is applied to a fresh frame state.
- **Postcondition**: state.lastStageIndex and state.lastStage are unchanged by that event.
- **Invariant**: Only kind=stage events may advance the displayed stage frontier.

### C002 — loop.js buildTimeline explain evidence

- **Precondition**: A package has an explain stage event with timeSource=artifact at time T, and at least one trusted downstream stage event (graphify, boundify or split) with timeSource=status or history at time D, with T > D.
- **Postcondition**: The explain event time becomes D (the earliest trusted downstream time), and never earlier than initialT.
- **Invariant**: An artifact-only explain event never appears after a trusted downstream stage event of the same package.

### C003 — loop.js repairUpstreamOrder drill clamp

- **Precondition**: A package has a drill stage event at time T and a split stage event ending at time S, with T < S.
- **Postcondition**: The drill stage event time becomes S; a drill event already at or after S is unchanged.
- **Invariant**: Drill never precedes split for the same package.

### C004 — loop.js buildFrames stage sequence

- **Precondition**: A model carries the other-PC-shaped times: explain artifact at 2026-11-05T09:48:55Z, graphify/boundify/split status in October, drill status/history in November.
- **Postcondition**: The first-appearance order of frame.stage equals educe, explain, grill, smooth, graphify, boundify, split, drill.
- **Invariant**: The displayed stage index is non-decreasing across all frames.
