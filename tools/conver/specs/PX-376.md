# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-376: Make the usage cache a portable duplicate-exact cross-machine ledger

**Ticket Key**: PX-376 · **Phase**: -1

---

## Background

### Goal
Make `progress-gif/snapshots/usage-cache.json` a workspace-wide ledger that merges every machine's usage records, restores history from git, and counts every record exactly once.

### Purpose
The current cache is a per-machine rescan cache. It rejects a cache whose `configDir`/`projectKey` differs and drops entries whose files are absent locally, so the rendered total omits every other machine's entire history.

### Motivation
Measured on 2026-11-05: gaia renders $4 from sh02 only (1,709 records) while git history holds sh02 1,709 + kawata 1,340 disjoint records (3,049, $5.1239). crystal holds sh03 2,028 + kawata 3,234 = 5,262 records ($8.2061). doors has one version (fz01, 203 records, $0.4819). The cumulative must be the union.

### Constraints
- Fix only `tools/conver`; the three in-repo copies stay byte-identical.
- No new runtime dependency.
- Absolute duplicate immunity across machines, arbitrary log copies and concurrent use, without operational rules (no serialization rule, no "do not copy logs" rule).
- Per-record identity is retained because daily-only aggregates cannot satisfy absolute duplicate immunity without an operational rule. The daily I/C/O/D view is derived; D is computed from exact integer tokens and rounded up at the third decimal only when materialized.
- Per-file fingerprints remain in the ledger per machine so unchanged files are not reparsed.
- Reports, snapshots, CLI flags and the title format stay unchanged; a usage failure remains a warning and never fails generation.

## Scope

- Change 1: `progress-gif/usage-cache.js` — replace the machine-bound v2 schema with v3 `{schema, machines: {<machineId>: {models, files}}}`; accept v2 and v3; stop requiring `configDir`/`projectKey` equality; export `LEGACY_CACHE_SCHEMA` and `machineIdFor`.
- Change 2: `progress-gif/usage-cache.js` — deterministic serialization: sort machines, files and records; emit one record tuple per line; remove `updatedAt`; keep the atomic temp-file rename.
- Change 3: `progress-gif/usage.js` — merge every foreign machine section into the single `unique` map before bucketing; never drop a foreign entry because its file is absent locally.
- Change 4: `progress-gif/usage.js` — apply fingerprint reuse only to the current machine section; drop a current-machine entry only when its file disappeared; carry foreign sections verbatim on write.
- Change 5: `progress-gif/usage.js` — key anonymous records by `anon:<sha256(raw line)>` so identical lines count once across files and machines.
- Change 6: `progress-gif/usage.js` — add machine identity and idempotent legacy adoption: a v2 section from the current `configDir` is adopted only when at least one of its files exists locally.
- Change 7: new `progress-gif/usage-recovery.js` — read `git log --all --follow` revisions, parse v1/v2/v3 payloads, union records by identity with max fields, and write a v3 ledger.
- Change 8: new `recover-usage-cache.js` CLI — `-d/--directory`, `--cache`, `--write`; read-only unless `--write`; Markdown report; idempotent.
- Change 9: new `tests/conver/usage-ledger.test.mjs` and `tests/conver/usage-recovery.test.mjs`; update `tests/conver/usage-cache.test.mjs` and `tests/conver/cli.test.mjs` to the v3 structure and acceptance semantics.
- Change 10: sync `usage-cache.js`, `usage.js`, `usage-recovery.js`, `recover-usage-cache.js` and their tests to `.claude/scripts/conver` and `crates/siprs/.claude/scripts/conver`.
- Non-change: `DEFAULT_PRICES`, the peak windows, the title format, the report format, the snapshot format and the `claude-usage.js` JSON shape stay unchanged.
- Impact: gaia/crystal/doors restoration runs the new recovery CLI; `make install-to-projects` distributes the new modules and CLI.

## Acceptance Criteria

- Happy path: recovery over gaia's 6 revisions yields 3,049 unique records and $5.1239; crystal yields 5,262 and $8.2061; doors yields 203 and $0.4819. Each derived daily I/C/O view is the sum of the union.
- Error case: a corrupt cache, unknown schema, missing git history or unreadable blob is a bypass; the run exits 0 with a warning and produces the same series as a cache-free scan.
- Edge case: the same message id in two machines counts once with the maximum field values; identical anonymous lines count once; a deleted local file is dropped while a foreign absent file is retained; two unchanged runs produce byte-identical JSON.

## Invariants

- 【Normal establishment】Merging any set of valid cache versions yields a ledger whose record set is the union keyed by record identity; the derived daily series equals a cold scan of the same union.
- 【Invariant on error】An unreadable, corrupt, unknown-schema or damaged cache is a bypass: full scan, same series, exit 0, one warning.
- 【Internal state invariant】The committed ledger stores machine sections of per-file records (identity, ms, model index, miss, hit, out). Prices, peak classification, holidays and cost are applied after the global merge and are never stored.
- 【Boundary invariant】A local file is reused only when its size, mtime and inode match; a local file that disappeared is dropped; a foreign section is never dropped for local absence; an unchanged rerun is byte-identical.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — usage-cache.json committed in the workspace and read on another machine

- **Precondition**: The cache payload contains a machine section whose machineId or configDir differs from the current machine.
- **Postcondition**: Every record in that section is merged into the global unique map, contributes to the daily series, and the section is retained when the ledger is written.
- **Invariant**: A foreign section is never discarded because its files are absent locally.

### C002 — the same logical usage record present in two machine sections or two files

- **Precondition**: Two records share the same identity (message.id, requestId, or anon content hash).
- **Postcondition**: The aggregated series contains exactly one record with the maximum value of each field.
- **Invariant**: The merge is idempotent, commutative and associative; repeating a merge never changes the total.

### C003 — a file entry in the current machine section

- **Precondition**: A current-machine cached file is absent, unchanged, or changed on disk.
- **Postcondition**: An unchanged file is reused, a changed file is reparsed, and an absent file is dropped; a file in a foreign section is retained regardless of local absence.
- **Invariant**: cacheStats.filesDropped counts only current-machine files that disappeared.

### C004 — writing the committed ledger

- **Precondition**: The same record set is written more than once.
- **Postcondition**: The file bytes are identical; machines, files and records are sorted; no volatile updatedAt exists.
- **Invariant**: An unchanged rerun produces no git diff.

### C005 — git history of progress-gif/snapshots/usage-cache.json

- **Precondition**: The repository history contains v1, v2 or v3 payloads of the cache.
- **Postcondition**: Recovery unions every revision by identity with max fields and writes a v3 ledger; v2 sections are migrated into machine sections.
- **Invariant**: Recovery is idempotent and deterministic across repeated runs.

### C006 — records without message.id or requestId

- **Precondition**: Two records have identical raw JSONL lines and no message.id/requestId.
- **Postcondition**: They collapse to one record keyed by anon:<sha256(raw line)>.
- **Invariant**: Different raw lines produce different identities.

### C007 — the daily I/C/O/D view

- **Precondition**: A merged record set carries integer miss/hit/out tokens and timestamps.
- **Postcondition**: Daily I/C/O tokens are exact sums; D is computed from DEFAULT_PRICES and rounded up at the third decimal only when materialized.
- **Invariant**: No stored cost is summed; re-pricing recomputes D from the same tokens.

## Boy Scout Rule

- Extract `machineIdFor(configDir, hostname)`, `parseCachePayload(payload)`, `mergeRecordSets(records)` and `serializeLedger(ledger)` so validation, reading, merging and writing each have one responsibility.
- Name the schema strings, tuple length and machine-id separator as constants; remove the magic `0.003/0.15/0.6` duplication by keeping `DEFAULT_PRICES` as the single source.
- Replace the anonymous `<file>:<line>` key with `anon:<sha256(line)>`; the helper is a verb phrase (`anonymousRecordKey`) and has one responsibility.
- Do not swallow errors: a cache read/parse/write failure becomes an explicit bypass reason carried into `cacheStats` and the warnings list.
- Split `aggregateUsage` into `selectCurrentMachineSection`, `mergeForeignMachines`, `scanLocalFiles` and `buildNextMachines` so the call sequence reads as the merge procedure.
