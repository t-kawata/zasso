# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-377: The pipeline carries the canon through every derived artifact, and a rewrite is never stranded

**Ticket Key**: PX-377 · **Phase**: -1

---

## Background

### Goal
Make the canon-state guard classify the derivation state instead of refusing on artifact presence, and make a canonical RFC rewrite oblige and prove the full re-derivation chain.

### Purpose
A design hole discovered after the RFC has been materialised must be repairable. The current guard refuses any package holding a graph, a directory tree or tickets, and its only route is /drill-rfc-down. That route does not exist when Tickets.json is absent, as in gaia-certificates, so the package is wedged. The guard must distinguish a complete materialisation (tickets exist, lineage fresh) from a partial one (graph and tree exist, tickets absent) and from a stale one.

### Motivation
The gaia re-run exposed the wedge at certificates: drill ended BLOCKED_PREREQUISITE because Tickets.json was absent, and grill refused because RFC-GRAPH.json and RFC-Dirs-Tree.json existed. The formula ledger is only one rail; units, sequence steps, operations, boundary contracts, distribution and formulas must all be re-proven after a rewrite.

### Constraints
- No gaia-specific path, package id or formula count.
- The four commands keep their ownership: grill writes RFC.md and RFC-FORMULAS.json; graphify writes RFC-GRAPH.json; boundify writes RFC-Dirs-Tree.json; split writes Tickets.json.
- Fresh-path outputs are byte-identical; the receipt is additive.
- Existing packages without receipts keep the current behavior until their next chain run.
- TDD: Red tests first, no test weakening, no stubs.

## Investigation

canon-state.js currently reads the directory and refuses on any of Tickets.json, *-GRAPH.json and *-Dirs-Tree.json (lines 47 and 64-82). The command text at grill-me-for-rfc.md 322-328 routes every refusal to /drill-rfc-down. The drill preflight at drill-rfc-down/preflight.cjs 322-328 returns BLOCKED_PREREQUISITE with TICKETS_MISSING_ROUTE_SPLIT_TO_TICKETS when Tickets.json is absent, so the route is not executable for a partial package.
certificates has RFC-GRAPH.json and RFC-Dirs-Tree.json but no Tickets.json; check-formula-coverage reports 363 owned formulas and zero ledger rows. The Dirs-Tree formula index exists only when a sidecar exists (time has 329 entries; certificates has none), so the ledger must be authored before the index can be built.
attach-formula-ids.js resolves a formula section to one graph node (nodeMatchesSection) and builds distribution.formulas from the graph, sidecar and node-to-file paths. The ledger rfcLocation.section is therefore the only authored join key; the file and symbol follow from the graph and Dirs-Tree.
complete-run.js defines REQUIRED_GATES and stage8-gates.js defines REQUIRED_GATE_NAMES; the two lists must change together. The graphify status writer is update-step-status.js with --graphify-status; there is no update-graphify-step-status.js. complete-run.js writes Status.json only after every gate passes, so the rederive receipt gate belongs in REQUIRED_GATES with a named repair.
The existing test canon-state.test.mjs asserts refusal for graph, tree and tickets one at a time. The new contract replaces the graph/tree refusals with partial classification and keeps the tickets refusal only for materialized-fresh.
The generic authoring path is a new spec-formula module: extract owned formulas, match the formula section to exactly one graph node, derive the Dirs-Tree file and planned symbol, and refuse when theory, implementation or tests are not derivable. The gate remains check-formula-coverage; the authoring script never invents a row. The split test extension is .test.cjs because update-split-step-status.js and stage-receipt.js are CommonJS; the canon-state and authoring tests are .test.mjs because those modules are ESM.

## Acceptance Criteria

- Happy path: a package with RFC, graph and Dirs-Tree but no Tickets runs grill to completion, records rederive, and the following graphify, boundify and split produce receipts that match the current RFC digest; verify-chain exits 0.
- Error case: a package with Tickets.json and a fresh lineage returns materialized-fresh and routes to drill; no RFC is written. A stale receipt blocks DONE and leaves Status.json unchanged.
- Edge case: a legacy package without receipts keeps the current behavior, and a stale package is routed to rederive rather than drill; the fresh-path derived bytes are unchanged.

## Invariants

- [Normal condition] Every classifier answer is one of standalone, partial, materialized-fresh and materialized-stale, and names the next owner.
- [Error invariant] A package with Tickets.json absent never receives a drill instruction; a failed rederive never declares DONE.
- [Internal state invariant] Status.json records the rederive chain and sourceDigest exactly once per generation; a failed gate leaves it unchanged.
- [Boundary invariant] A stage receipt is additive: the stage output is byte-identical with or without it, and a missing receipt is legacy, not a failure.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — canon-state -> grill STEP 0

- **Precondition**: The RFC directory exists and every derived artifact that is present is readable.
- **Postcondition**: The script prints exactly one state from standalone, partial, materialized-fresh and materialized-stale, the next owner and the rederive chain when one is owed.
- **Invariant**: The script is read-only, deterministic, names every artifact it reads, and never prints a drill instruction when Tickets.json is absent.

### C002 — grill STEP 5 -> complete-run

- **Precondition**: The grill has written RFC.md and, when formulas are owned, RFC-FORMULAS.json.
- **Postcondition**: Status.json records the rederive chain and the RFC digest; DONE is declared only when every stage receipt matches that digest.
- **Invariant**: A failed gate or a failed rederive leaves Status.json unchanged and never declares DONE.

### C003 — graphify -> boundify -> split

- **Precondition**: A stage runs with a readable RFC and its declared inputs.
- **Postcondition**: The stage status file records sourceDigest, inputDigests, outputDigest and the gate verdicts of that run.
- **Invariant**: The receipt is additive: a stage output is byte-identical with or without the receipt, and a missing receipt is treated as legacy rather than as a failure.

### C004 — RFC-SEED -> RFC-FORMULAS -> graph -> Dirs-Tree

- **Precondition**: The seed names owned source segments and the tree manifest resolves them.
- **Postcondition**: Every owned formula has one ledger row and one sidecar row with its theory, class, implementation site, design and tests; the section resolves to one graph node and the anchor to a Dirs-Tree file and symbol.
- **Invariant**: No formula absent from the specification is accepted, and no owned formula is omitted or given an invented theory or test.
