# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-378: Every post-split ticket mutation is proven against the full chain or rolled back

**Ticket Key**: PX-378 · **Phase**: -1

---

## Background

### Goal
Make every post-split Tickets.json mutation either pass the same full-chain verification that split uses or be rolled back byte-identically.

### Purpose
Tickets.json is written after split by find-omissions, by the resolving-ticket path that consumes the consolidate-stubs manifest, and by any later command that adds or updates tickets. Those changes are legitimate, but a resolving ticket deep-clones the source ticket and preserves nodeIds, so it can claim a unit the source already owns; an omission ticket can add work without a graph node. The chain must remain provable after every such change.

### Motivation
The user identified the mutation points and asked for a guarantee that penetration is not broken there. Without a transactional gate, every command can report success while the union of unit, step, operation, boundary-contract, distribution and formula ownership is silently corrupted.

### Constraints
- No gaia-specific path, package id or ticket key.
- The commands keep their authoring role: find-omissions decides what to add, consolidate-stubs only produces the manifest, crystalize-readme only writes specs and README.
- The gate adds no new verification semantics; it reuses the split-stage verify-chain and the existing closure, contract and formula gates.
- Legacy packages with pre-existing duplicate ownership are grandfathered; only findings newly introduced by the mutation are blocking.
- TDD: Red tests first, no test weakening, no stubs.

## Acceptance Criteria

- Happy path: a status-only update and an omission ticket with no nodeIds both pass the gate, the split receipt records the new Tickets digest, and the package remains green under verify-chain at the split stage.
- Error case: a resolving ticket that inherits nodeIds without an ownership transfer is refused, Tickets.json is restored byte-identically, and the route names either the transfer or the non-owning form.
- Edge case: a legacy package with an existing duplicate is grandfathered, while the same mutation introducing a new duplicate is blocked; a phase merge with a complete remap passes.

## Invariants

- [Normal condition] Every mutation has a manifest and a before/after digest, and the promoted file is the verified file.
- [Error invariant] A failed verification restores the byte-identical snapshot; no partial write survives.
- [Internal state invariant] The split receipt outputDigest equals the promoted Tickets digest, and the mutation manifest is stored beside it.
- [Boundary invariant] Only findings absent before and present after are blocking; pre-existing findings are grandfathered and reported, not silently dropped.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — ticket command -> Tickets.json

- **Precondition**: Tickets.json is readable and a snapshot of its bytes and digest is taken before the mutation.
- **Postcondition**: A successful mutation writes the new file, records the mutation manifest and updates the split receipt; a failed verification restores the snapshot byte for byte.
- **Invariant**: No partial write survives; the before and after digests are both recorded and the rollback is byte-identical.

### C002 — find-omissions -> ticket set

- **Precondition**: The mutation manifest names each added, updated and retired ticket and its origin.
- **Postcondition**: A derived ticket may own units; a resolving or omission ticket is non-owning unless the manifest records an explicit ownership transfer that also reduces the source ticket.
- **Invariant**: No unit, operation, formula or boundary contract has two implementing tickets, and no ticket claims a unit absent from the graph.

### C003 — before snapshot -> after snapshot

- **Precondition**: The verifier has run on the before and after snapshots.
- **Postcondition**: Only findings that are absent before and present after are blocking; pre-existing findings are reported as grandfathered.
- **Invariant**: The delta is deterministic and order-independent, and a mutation that introduces no new finding always passes.

### C004 — mutation gate -> split verifier

- **Precondition**: The package carries a readable graph, Dirs-Tree and tickets.
- **Postcondition**: The gate reuses verify-chain at the split stage, verify-ticket-closure, merge-contracts and merge-formulas in verify mode, and verify-formula-file-coverage when files change.
- **Invariant**: The definition of through is identical before and after the mutation; the gate adds no new verification semantics and no command loses its role.
