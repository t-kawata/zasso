# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-379: Let a grill run complete with a pending rederive debt and discharge it at chain completion

**Ticket Key**: PX-379 · **Phase**: -1

---

## Background

- Goal: a grill run on a package that must rederive completes and records the debt instead of refusing DONE.
- Purpose: the completion gate answers whether the grill design is finished, not whether a downstream stage that has not run yet is finished.
- Motivation: gaia-certificates reached every design gate and stopped only on RECEIPT_MISSING:boundify and RECEIPT_MISSING:split, while boundify itself was blocked by other packages missing ledgers; the grill cycle cannot depend on a later stage that depends on a third package.
- Constraint: no receipt is forged, no obligation is cleared before the chain actually matches the RFC, and a later RFC edit still makes the package materialized-stale.

## Scope

- update-status.js record-rederive: add recordedGeneration, equal to Status.json.grillGeneration when it is an integer and null otherwise; sourceDigest and recordedAt stay unchanged
- update-status.js: add discharge-rederive; return no-obligation when Status.json.rederive is absent, compare every recorded chain stage with compareStageReceipts against digestFile(RFC.md), delete rederive only on zero findings, and report discharged true or the findings
- complete-run.js evaluateRederiveReceipts: keep no-obligation and all-receipts-match as passed; return exitCode 0 with status pending and a detail naming the chain when findings exist and rederive.recordedGeneration equals status.grillGeneration; return exitCode 1 with the findings otherwise
- complete-run.js main: surface the pending rederive summary in the completion JSON so the operator sees the chain to run after DONE
- complete-run.js: leave the gate list, the completion receipt gate names and the DONE writer unchanged
- update-split-step-status.js: after the atomicWrite of a non-audit end-step 6, invoke update-status.js discharge-rederive for the package directory; a subprocess failure prints a warning and leaves the obligation
- update-split-step-status.js: audit mode writes no receipt and therefore calls no discharge
- check-all-schema.js validateOptionalRederive: accept an optional integer recordedGeneration at or above 1, and reject any other present value
- grill-me-for-rfc.md: replace the DONE-waits sentence with DONE carries the debt as pending and names graphify, boundify, split; revise the STEP 8 gate definition to the three-way verdict
- split-to-tickets.md: state that the final non-audit end-step 6 discharges the rederive obligation only when every recorded chain receipt matches the current RFC
- Non-change: canonical RFC rewriting, stage receipt fields, the mutation gate and canon-state classification stay as they are; the debt record is the guard and canon-state already treats it as stale
- Non-change: clear-rederive remains available for an explicit human discharge and is never called by the new automatic path
- Impact: conver grill and split commands; a package with a recorded obligation starts completing and is discharged by its chain; a package with no obligation keeps the legacy path

## Acceptance Criteria

- Happy path: a partial package records a rederive at STEP 0, passes every other gate with rederive-receipts pending, and reaches DONE while Status.json.rederive remains
- Error case: an obligation recorded by an earlier generation with missing or stale receipts keeps DONE refused with RECEIPT_MISSING or RECEIPT_STALE
- Edge case: the final non-audit split step removes the obligation only when graphify, boundify and split receipts all bind the current RFC; any missing or stale receipt leaves it in place without failing split

## Invariants

- Normal establishment: the first begin-run sets grillGeneration to 1; record-rederive stores that same value in recordedGeneration; evaluateRederiveReceipts returns pending only when the two are equal and at least one chain receipt does not match the current RFC digest.
- Error: a record whose recordedGeneration is absent or older than grillGeneration never passes as pending; missing receipts stay RECEIPT_MISSING and stale receipts stay RECEIPT_STALE.
- Internal: completion never deletes or rewrites Status.json.rederive; discharge-rederive is the only automatic writer that deletes it, and it deletes only after compareStageReceipts returns zero findings for the recorded chain.
- Boundary: split persists its own receipt before discharge reads the filesystem; audit mode writes no receipt and triggers no discharge; a discharge failure leaves the obligation and does not fail the split step.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — rederive-receipts gate -> complete-run DONE

- **Precondition**: Status.json.rederive.required is true and recordedGeneration equals Status.json.grillGeneration and at least one stage in the chain has no receipt bound to the current RFC digest
- **Postcondition**: evaluateRederiveReceipts returns exitCode 0 with status pending and complete-run declares DONE while Status.json.rederive remains recorded
- **Invariant**: completion never deletes or rewrites the rederive record

### C002 — rederive-receipts gate -> overdue obligation

- **Precondition**: Status.json.rederive.recordedGeneration is older than Status.json.grillGeneration and a chain receipt is missing or bound to a different RFC digest
- **Postcondition**: evaluateRederiveReceipts returns exitCode 1 with RECEIPT_MISSING or RECEIPT_STALE and complete-run writes neither the completion receipt nor DONE
- **Invariant**: a failed gate writes no completion evidence

### C003 — split end-step 6 -> rederive discharge

- **Precondition**: a non-audit end-step 6 completes with a rederive obligation whose chain receipts all carry the current RFC digest
- **Postcondition**: Status.json.rederive is removed after the split status write and stdout reports discharged true
- **Invariant**: a missing, stale or output-mismatched chain receipt leaves the obligation in place and split still exits zero

### C004 — legacy completion and split paths

- **Precondition**: Status.json carries no rederive record, or a legacy record without recordedGeneration
- **Postcondition**: evaluateRederiveReceipts returns exitCode 0 no rederive owed, discharge-rederive is a no-op, and existing split behavior is unchanged
- **Invariant**: the optional recordedGeneration field keeps every legacy Status.json schema-valid
