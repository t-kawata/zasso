# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-380: Render bilingual stage captions under the progress bar

**Ticket Key**: PX-380 · **Phase**: -1

---

## Background

The header currently shows only the uppercase stage name next to the date. The stage name must carry a one-line description so each phase explains itself. Japanese descriptions are long, so keeping the description at 18px would overflow the header; the name keeps its size and only the description shrinks to fit. An en checkbox switches the caption to English, unchecked by default. No other display change is in scope.

### Goal
The header renders `<date> <NAME>: <description>` with the command name at its current HEADER_STAGE_SIZE and the description at the largest size that fits before the percent block, in the same group colour, and an en checkbox switches the caption language between Japanese (default) and English.

### Purpose
A viewer who does not know the conver stage vocabulary can read what each stage does without leaving the animation. The date and the stage name stay exactly as legible as before; only the explanatory text adapts.

### Motivation
The user asked for the header description in both languages. The fixed 18px size would clip the longest Japanese descriptions, and clipping a user-supplied sentence is worse than reducing only its own size. The browser already has the real font metrics, so the size can be chosen at draw time without changing the board.

### Constraints
- The command name keeps HEADER_STAGE_SIZE; only the description size may change.
- The name and the description share groupColor(stage).
- Exactly one half-width space separates the date from the caption.
- The generated HTML stays self-contained and offline; no network request and no new dependency.
- Ladder labels, board width and height, colours, title, progress bar, percent, and the other controls must not change.
- The output must stay deterministic for a given model, options and font.

## Acceptance Criteria

- Happy path: the default header shows the Japanese caption for the current stage with the name at 18px and the description shrunk only as needed.
- Happy path: checking en shows the English caption on the next draw and in the downloaded GIF.
- Error case: an unknown, empty or null stage draws no caption and does not throw.
- Edge case: every Japanese description fits the narrowest 724px board without touching the percent block.
- Happy path check: stageCaption('educe','ja') is 設計書から要実装操作を抽出し各部へ配布 and stageCaption('educe','en') is List design operations for builders.
- Happy path check: the name run uses HEADER_STAGE_SIZE and the description run uses the fitted size, both with groupColor(stage), while the date keeps HEADER_DATE_COLOUR.
- Error check: stageCaption(null,'ja'), stageCaption('','ja'), stageCaption('unknown','ja') and stageCaption('educe','fr') return null.
- Edge check: the fitted size is never smaller than MIN_DESCRIPTION_SIZE, and the ellipsis fallback keeps the measured width inside the available width.

## Invariants

- [Normal condition] The header always draws the date unchanged, then exactly one measured half-width space, then the uppercase stage name at HEADER_STAGE_SIZE, then the description in groupColor(stage); the name size never changes with the description size.
- [Error invariant] An absent, empty or unknown stage draws no caption and never throws; a missing measureText capability falls back to a length-based estimate.
- [Internal state invariant] STAGE_CAPTIONS is frozen; fitDescriptionSize and ellipsizeDescription are pure with an injected measure function and share no mutable state; the selected language only chooses which table column is read.
- [Boundary invariant] The description size stays in [MIN_DESCRIPTION_SIZE, HEADER_STAGE_SIZE] and its measured right edge never crosses header.percentX minus the measured percent width minus the 12 px gap; when even the minimum does not fit, the description ends with the ellipsis at the minimum size.
