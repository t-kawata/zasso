# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-381: Make progress-gif stage order ordinal and refine the header caption typography

**Ticket Key**: PX-381 · **Phase**: -1

## Background

### Goal
Make the progress-gif animation display every evidenced pipeline stage exactly once, in STAGE_ORDER (educe, explain, grill, smooth, graphify, boundify, split, make, plan, start, review, resolve, consolidate, find, crystalize, drill), regardless of file mtimes, workspace copies, stage re-runs, future-dated timestamps, missing timestamps, or overlapping evidence. Also refine the header caption line under the progress bar to `MM/DD hh:mm  NAME : description` with the description two points smaller than the command name and normal weight.

### Purpose
The animation is the progress view of the whole pipeline; stage order is its primary truth. PX-374 and PX-375 enforced order by rewriting event timestamps, which silently collapsed the date axis and deleted SMOOTH from the animation. Separating the order clock (ordinal) from the evidence clock (timestamps) makes order exact by construction while keeping dates as advisory estimates.

### Motivation
The artifact gaia progress-gif/20261106104748.html (generated on /Users/sh02/shyme/gaia, v0.0.373) plays EDUCE -> EXPLAIN -> GRILL -> GRAPHIFY -> BOUNDIFY -> SPLIT -> DRILL; SMOOTH never appears and the October stages collapse onto 10/30. Rebuilding the same embedded model with ordinal slots produces all eight stages in workflow order with dates 10/26 - 11/05 and zero monotonicity violations. The header also currently prints `11/05 08:57 DRILL: ...`; the requested style is `11/05 08:57  DRILL : ...` with the description about two points smaller and normal weight.

### Constraints
- Do not rewrite historical Tickets.json, RFC artifacts, .conver-history.jsonl, HTML renders or snapshots.
- Do not weaken or delete tests; Red tests must fail for the absence of the ordinal clock and the caption style.
- Keep the evidence gating, [evidence] warnings and the previous-progress marker semantics added by PX-374.
- The model remains a deterministic function of the workspace; do not call Date.now() while constructing frames.
- Keep the three script copies byte-identical: tools/conver/.claude, root .claude, crates/siprs/.claude.
- Never order stages by timestamp; order only by the ordinal stage rank.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — ordinal order clock -> frame stage sequence (replaces PX-375 repairUpstreamOrder)

- **Precondition**: A model whose stage events carry arbitrary, inverted or duplicated evidence timestamps, including a later educe re-run and a grill tail after drill.
- **Postcondition**: buildFrames emits each evidenced stage exactly once in STAGE_ORDER and the frame stage index never decreases; timestamps do not change the sequence.
- **Invariant**: For every frame sequence, stage transitions are a subsequence of STAGE_ORDER and each evidenced stage appears at least once.

### C002 — evidence clock -> progress accumulation

- **Precondition**: A model passed to buildTimeline and progressAt.
- **Postcondition**: Every model.events[i].t keeps its original value and no repair function writes event times.
- **Invariant**: buildTimeline and progressAt are pure with respect to model.events, and frame.evidenceT is the maximum applied evidence time.

### C003 — display-date estimate -> header date

- **Precondition**: A stage with trusted status or history events, or only artifact events, plus the next trusted stage.
- **Postcondition**: displayDate[stage] is the earliest trusted time when present, otherwise the earliest evidence clamped down to the next trusted stage; a forward pass keeps displayDate non-decreasing.
- **Invariant**: displayDate changes never write evidence times and stay within [initialT, generatedAt + 24h].

### C004 — artifact origin -> stage event presence

- **Precondition**: An EXPLAIN-RFC-SEED.md whose mtime precedes the model initialT.
- **Postcondition**: An explain event is still emitted at initialT with an [evidence] warning instead of being dropped.
- **Invariant**: A stage with an existing artifact never disappears from the timeline without a warning.

### C005 — timestamp precision -> ordering key

- **Precondition**: A DesignTree question whose resolvedAt is the date-only string YYYY-MM-DD.
- **Postcondition**: The value is not used as an instant; the event falls back to the design-tree mtime or initialT and an [evidence] warning is recorded.
- **Invariant**: No timeline event carries prec day.

### C006 — clock sanity -> displayed date bound

- **Precondition**: A status or history timestamp later than model.analysisTime plus 24 hours.
- **Postcondition**: An [evidence] warning is recorded and the display estimate is clamped to the analysisTime bound; the stage order is unchanged.
- **Invariant**: Displayed dates never exceed analysisTime plus 24 hours when analysisTime is finite.

### C007 — previous render -> previous-progress marker

- **Precondition**: The newest past HTML render stamp T and the current model.
- **Postcondition**: previousProgress equals the overallProgress after applying the ordinal timeline events whose evidence time is at or before T.
- **Invariant**: The marker is in [0,1] and uses the same state machine as the frames.

### C008 — caption layout -> header drawing

- **Precondition**: A frame with a known stage and a caption in ja or en at scale s.
- **Postcondition**: The header draws the date, two half-width spaces, NAME colon space, then the description; the name is 18*s px weight 600 and the description is 16*s px weight 400 with a 12*s minimum, both in the same colour.
- **Invariant**: The stage name size remains 18*s, the description size never exceeds 16*s, and overflow shrinks or ellipsizes the description only.

### C009 — distribution copies -> byte identity

- **Precondition**: The three progress-gif script trees under tools/conver, root .claude and crates/siprs/.claude.
- **Postcondition**: loop.js, layout.js, engine.js, fonts.js, html.js and viewer.js are byte-identical across the three trees.
- **Invariant**: The copy-identity test passes without excluding a file.
