# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-382: API cross-package gate: resolve Rust imports and re-exports before claiming a defect

**Ticket Key**: PX-382 · **Phase**: -1

---

## Background

### Goal
Make verify-api-consistency.mjs resolve every Rust reference through its import scope and re-exports, so a cross-package claim is made only when the workspace states the dependency.

### Purpose
The current gate builds one workspace-global map from bare declaration names. It therefore treats an external crate import, a crate-local re-export, a glob-imported enum variant, two crates that legitimately declare the same type name, and a trait impl associated function as cross-package defects. The gate exists to prove cross-package agreement, not to re-implement Rust name resolution with a bare-name table.

### Motivation
PX-369 added the gate to smooth closure; PX-371 and PX-372 refined the line parser but never parsed use statements. Measured on the three sample workspaces: gaia reports 802 blocking findings, crystal 231 and doors 103. Gaia last smooth pass was recorded on 2026-10-29, before the gate was added. Concrete false positives: gaia adapters import BoundedValue from gaia_ports, which re-exports it from gaia_foundation, and the RFC states that a re-export is not a second edge; doors-cli imports clap::Command, which the gate resolves to pjsip-prebuilt Command; enum variants imported through OperationErrorCode are reported as undefined types.

### Constraints
The cross-package claim stays strict. Blocking is limited to explicit workspace imports or re-exports whose declaration, shape, arity, generic arity or boundary is missing. External, crate-local and builtin references are out of scope. An unresolved bare symbol becomes a named, counted UNSCOPED_SYMBOL state, never a silent pass. No project names, column names or crate-specific allowlists enter the code. Existing smooth verdicts remain acceptable under their recorded checkSetVersion. Gaia graphify, crystal grill and doors smooth must not gain a new blocking finding from this ticket.

## Acceptance Criteria

- **[Happy path]** A synthetic workspace with an explicit workspace import that resolves to one declaration and a declared boundary produces zero blocking findings, and the JSON summary records the import kind and checkSetVersion.
- **[Error case]** An explicit workspace import with a missing declaration, shape mismatch, arity mismatch, generic arity mismatch or missing boundary produces the named blocking finding against the imported package.
- **[Edge case]** External crate imports, crate:: re-exports, glob enum variants, same-name types in different crates and trait impl methods produce zero blocking findings; unresolved bare symbols are counted as UNSCOPED_SYMBOL, and an unreadable use shape is named.
- **[Sample gate]** The read-only diff on gaia, crystal and doors classifies every delta. Gaia existing verdict remains accepted; crystal current grill and doors current smooth gain no blocking finding.

## Invariants

- [Normal establishment] Every reference parsed from a Rust fence is classified into exactly one import kind: local-crate, workspace-explicit, workspace-glob, workspace-reexport, external, builtin or unresolved. The classification is total over the reference set.
- [Invariant on error] An unreadable use statement or declaration shape is reported as a named UNSCOPED_SYMBOL or UNPARSED_SURFACE finding with its line; it is never silently skipped and never converted into a blocking cross-package claim.
- [Internal state invariant] The workspace symbol table is keyed by package and import path, not by a bare name shared across crates. A declaration in package A and a same-named declaration in package B are independent unless a package imports one from the other.
- [Boundary invariant] A blocking finding is emitted only when an explicit workspace import or re-export names a target whose declaration, shape, arity, generic arity or boundary is missing. External, crate-local and builtin references emit no blocking finding. An existing verdict recorded under an older checkSetVersion remains acceptable to downstream commands.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — api-consistency import resolution

- **Precondition**: An RFC code fence carries a use statement and a reference; the workspace tree manifest provides the crate-to-package map.
- **Postcondition**: Every reference is classified as local-crate, workspace-explicit, workspace-glob, workspace-reexport, external, builtin or unresolved; only an explicit workspace import with a missing declaration, shape or arity mismatch or missing boundary produces a blocking finding.
- **Invariant**: Exactly one classification per reference; an unknown import shape is a named refusal and never a silent skip.

### C002 — api-consistency re-export boundary

- **Precondition**: Package A imports a symbol from workspace crate B; B re-exports the symbol from workspace crate C.
- **Postcondition**: The boundary is checked against B; the declaration is followed to C for shape; no C boundary is required.
- **Invariant**: A re-export is not a second dependency edge.

### C003 — smooth verdict compatibility

- **Precondition**: An existing smooth verdict records a check-set version and a downstream command reads it.
- **Postcondition**: The downstream command accepts the verdict under its recorded version; the new gate applies only on a new run.
- **Invariant**: No retroactive invalidation of an existing verdict.

## Boy Scout Rule

- Extract verb-phrase functions from the parser: parseUseStatements, classifyImport, resolveLocalDeclaration, resolveWorkspaceImport, followReExport, compareCallArity. Each answers one question; the reference loop becomes a call sequence that reads as prose.
- Name domain values instead of bare locals: importedSymbol, importRoot, importKind, receiverPresent, declaredArity, argumentCount. Replace generic names such as entry, row and value in the touched functions.

- Make every parser failure explicit: an unreadable use shape pushes a named record with its line; no try/catch silently returns an empty list.
