# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-383: Smooth evidence model: authored vocabulary, operation citation and typed/prose separation

**Ticket Key**: PX-383 · **Phase**: -1

---

## Background

### Goal
Make the smooth-sequences detector read the vocabulary, applicability, citation level and evidence class a project states, and mechanically verify each declared class instead of assuming the gaia shape.

### Purpose
The current model derives requiredInterfaces only from columns whose values instantiate a pinned vocabulary, requires a step-level quote for every authored fact, and counts prose as typed authored evidence. It therefore cannot express a project whose interfaces are literal columns, whose spec states no interfaces or status machine, or whose contracts are prose.

### Motivation
Measured on the three sample workspaces. Gaia derives requiredInterfaces as initial_status, rest, websocket and cli; initial_status is a status field, not an interface, so the derivation is over-inclusive. Doors derives null because its four interface columns cli, rest, ws and grpc are literalInLine; the derivation is under-inclusive. Crystal declares no columns and no status graphs; both checks should be explicitly not applicable. Doors step quotes are one-word procedure tokens, so operation-level Preconditions and Postconditions cannot be cited under the step-line rule. Crystal contracts are prose. Census selectors differ: gaia uses jsonFieldRows, specSpans and tableColumn; crystal tableColumn; doors markedLines. Smooth currently accepts only jsonFieldRows.

### Constraints
No project names, column names or project-specific deciders enter the code. An explicit empty list is an authored none. A notApplicable entry requires a spec line and quote ground. Typed and prose are separate surfaces. Operation-level citation is additive; existing step citations and jsonFieldRows behavior are unchanged. Old verdicts remain accepted under their recorded checkSetVersion. Gaia pass is preserved, doors blocked count does not increase, and crystal current stage gains no blocking finding.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — smooth vocabulary source resolution

- **Precondition**: An artifact or declaration states one of artifact.vocabulary, allocate declared_interfaces, pins.columns by decider or declaration.interfaces.
- **Postcondition**: requiredInterfaces resolves from the stated source or is withheld with a named reason; an explicit empty list resolves to none.
- **Invariant**: An unknown source withholds the check and never guesses.

### C002 — smooth operation-level citation

- **Precondition**: An authored fact cites an operation line and quote and the artifact carries a spec path.
- **Postcondition**: The quote exists in the spec line and the typed row or quote supports the fact text; otherwise the fact is refused.
- **Invariant**: A vacuous fact that only restates a one-word quote is refused.

### C003 — smooth typed and prose accounting

- **Precondition**: A step carries a typed contract or a contract_prose field.
- **Postcondition**: Typed checks count actual typed facts; prose steps are notApplicable for typed checks; evaluatedClaims equals the actual propositions.
- **Invariant**: Prose never counts as typed authored evidence.

### C004 — census shape parity

- **Precondition**: A sourceEnumerations pin states a selector shape and parameter.
- **Postcondition**: jsonFieldRows, tableColumn, markedLines and specSpans extract members through the same contract; an unknown shape is refused.
- **Invariant**: Educe and smooth accept the same shape set and return the same members.
