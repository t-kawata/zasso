# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- [Happy path] A re-read of an inquest or adversarial file through the documented writer stores every row with `artifactDigest`, `readerGeneration` and `readAt`, writes one receipt per file with a digest equal to the file digest, and `resolveReadingsObligations` closes the `READ:INQUEST` / `READ:ADVERSARIAL` obligations when the answer is No and the quote is on the cited line.
- [Error case] A record without a signature, without an answer, or whose quote is not on the cited line is refused before any file or receipt is written; a record that supplies `readAt` or `readerGeneration` is refused with `WRITER_STAMPED_FIELD`; an applicability key outside the known family set is refused with `INVALID_VOCABULARY` naming the key.
- [Edge case] Existing legacy rows without the three fields remain readable and open with their existing reason (`LEGACY_RECORD`, `READER_GENERATION_STALE`, `READING_NOT_REREAD`); they are never rewritten by the writer. An empty batch writes an empty file and a receipt but remains `MISSING_EVIDENCE`. gaia's pass and its 9 receipts are unchanged; crystal and doors remain unproven and their blocked lines for `S3.interface-mapping-missing` and `S3.transition-out-of-terminal` now name the vocabulary surfaces and the regeneration producer.

## Invariants

- 【Normal establishment】 Every successful write stores all records or none; each stored row carries `artifactDigest` equal to the current artifact digest, `readerGeneration` equal to the educe generation and `readAt` at or after `generationStartedAt`; the manifest has exactly one receipt per written path with the same sha256.
- 【Invariant on error】 A validation failure leaves the target file byte-identical and appends no receipt; a failed atomic rename leaves the previous file intact; no partial batch is visible.
- 【Internal state invariant】 `writeReceipts` stays sorted by path and deduplicated by path; a second write to the same path replaces that path's receipt, not the other path's; the writer never rewrites a row it did not receive in the batch.
- 【Boundary invariant】 An absent or empty reading file is valid on disk but remains an open `MISSING_EVIDENCE` obligation; a `readAt` exactly equal to `generationStartedAt` is fresh; a generation of 0 or null does not require a reader generation stamp but a positive generation does.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — reader-written reading file -> closure freshness gate

- **Precondition**: A batch of records for one of the six rail-written kinds has a readable artifact at the workspace root, a positive educe generation with a string generationStartedAt, and every record carries subject, lens or outcome, answer or verdict, path, line, quote and reader.
- **Postcondition**: The file is written atomically; every stored row carries artifactDigest, readerGeneration and readAt; EVIDENCE-MANIFEST.json has one writeReceipt for the path with sha256 equal to the file digest and generation equal to the educe generation.
- **Invariant**: If any record fails validation, no file bytes and no receipt are written; the count of written rows equals the count of validated rows.

### C002 — closure freshness gate -> reading obligation state

- **Precondition**: An inquest row carries artifactDigest equal to the current artifact digest, readerGeneration equal to the current generation, readAt at or after generationStartedAt, answer No, and a quote that occurs on the cited line.
- **Postcondition**: resolveReadingsObligations returns the obligation as closed with reason null; the same row missing any one of the three freshness fields returns open with LEGACY_RECORD, READER_GENERATION_STALE or READING_NOT_REREAD respectively.
- **Invariant**: No row without all three fields is ever held; the three refusal reasons are distinct and named.

### C003 — check family skipped reason -> blocked report

- **Precondition**: vocabulary.requiredInterfaces is null or vocabulary.terminalStatuses is null for the envelope family.
- **Postcondition**: The blocked entry for S3.interface-mapping-missing names surface vocabulary.requiredInterfaces and producerForBlockedSurface returns the regeneration command; S3.transition-out-of-terminal names surface vocabulary.terminalStatuses and the same producer.
- **Invariant**: A blocked entry caused by an absent vocabulary never reports surface operations or the migrate-v3 --annotations producer.

### C004 — declaration applicability -> check applicability

- **Precondition**: vocabulary.applicability contains a key outside the five declared families, or a known key with applicable false whose ground line and quote are not on the artifact specification.
- **Postcondition**: loadVocabulary throws INVALID_VOCABULARY naming the key or the ground; a known key with a valid ground is returned as notApplicable and the corresponding checks carry the ground.
- **Invariant**: An unknown applicability key can never silently no-op; a notApplicable record without a verified ground is never accepted.

### C005 — legacy reading generation -> new writer

- **Precondition**: An existing readings file contains rows without artifactDigest, readerGeneration or readAt.
- **Postcondition**: The rows remain on disk byte-identical, remain readable, and resolve to their existing open reasons; a new batch written through the writer adds stamped rows without rewriting the legacy rows.
- **Invariant**: The writer never migrates, rewrites or deletes an existing row; legacy compatibility is read-only.
