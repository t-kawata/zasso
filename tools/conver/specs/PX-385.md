# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-385: Produce the operation envelope the specification declares, and make initial_status a first-class surface

**Ticket Key**: PX-385 · **Phase**: -1

---

## Background

### Goal
Make the operation envelope an artifact produced from the axes the specification declares, and make `initial_status` a first-class evidence surface. A project with a status axis gets `initial_status` and `allowed_status_transitions`; a project without one declares `S3.status` notApplicable with a spec-line ground; a project that states transitions but omits the initial status is blocked with the regeneration producer instead of receiving an undefined-subject finding.

### Purpose
Smooth S3 and S4 must measure declared axes or block with the producer that can restore them. The current detector reads operation fields the educe procedure never names, so doors and crystal carry 105 and 31 operations with no `initial_status` or transitions while gaia carries all 257. The fix must not impose gaia's eleven envelope fields on every project; it must make the declared axes producible and the absent axes applicability-grounded.

### Motivation
The doors smooth run shows 0 initial_status and 0 transitions across 105 active operations. Annotating a transition graph makes S3.status-initial-unknown fire for every active operation with the message `initial status undefined`. The operation envelope is not modelled as a surface, and mergeAnnotationsIntoV3 cannot set initial_status. Crystal has the same shape (31 operations, 0/0). Gaia proves the full envelope is producible (257/257/257 and an OperationStatus enumeration).

### Constraints
- The axis set is declaration-driven, never a universal mandatory schema derived from gaia.
- A project that states no status axis must be able to declare S3.status notApplicable with a verified specification line and quote; blocked never becomes pass.
- gaia's pass and envelope counts are unchanged; crystal and doors remain unproven with no increase in blocking.
- Downstream consumers (sequences-slice C6, shared-obligations OPERATION_COLUMNS and property obligations, views, grill and split) are measured before the artifact change is accepted.
- No sample project is edited in this ticket.

## Acceptance Criteria

- [Happy path] A specification that states `initial_status` and an `allowed_status_transitions` map produces both on the artifact operation; every status value is a member of the declared OperationStatus; the view carries `initialStatus` and `allowedStatusTransitions`; sequences-slice C6 is 0; gaia's 257/257/257 counts and its pass are unchanged.
- [Error case] An `initial_status` or transition target outside OperationStatus is refused at the educe phase with a named code and no artifact is written; a project that supplies transitions but omits initial_status gets a blocked `operations[].initial_status` surface and exit 4, not a finding with `undefined`; an applicability record without a verified spec line and quote is refused with INVALID_VOCABULARY.
- [Edge case] A project whose specification states no status axis carries neither field and can declare `S3.status` notApplicable with a spec-line ground; without that declaration the surface stays blocked (unproven, never pass). crystal and doors remain unproven with no increase in blocking; if a downstream C6 or property obligation appears, the producer fixes the enumeration or the project declares applicability, never a waiver.

## Invariants

- 【Normal establishment】 An operation axis is present in the artifact if and only if the specification states it; every present status value is a member of OperationStatus; the view and the artifact agree on initialStatus and allowedStatusTransitions.
- 【Invariant on error】 A non-member status is refused at the educe phase and leaves the previous artifact byte-identical; a failed phase write leaves no partial artifact.
- 【Internal state invariant】 preserveV3Surfaces keeps an authored initial_status only when the same-revision reading carries it; it never invents a value the reading omitted; allowed_status_transitions and initial_status stay consistent (the initial status is a declared status of the map).
- 【Boundary invariant】 An empty allowed_status_transitions map with a member initial_status is valid; a transition target that is terminal only by a ground is not silently added; a generation without a status axis is not an error.
