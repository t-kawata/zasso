# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-389: Close the S8 formula-ownership route and record the check set of every pass

**Ticket Key**: PX-389 · **Phase**: -1

---

## Background

### Goal
Every formula-bearing specification segment can be owned through a grounded tree decision, so smooth's S8 gate reports a missing ledger row (repairable by /grill-me-for-rfc) instead of an unowned formula with no executable route. Every smooth-sequences pass records the digest of the check set that produced it.

### Purpose
S8.formula-unowned currently routes to allocate-decision regeneration, but allocate derives a seed's source_segments only from tree inventory (collectPackageSegments in .claude/scripts/workspacify-allocate/run.mjs). A segment with no harvested inventory item therefore cannot be claimed by any package, and prose-heavy specifications cannot converge. Separately, status.json and the completion certificate name no check set, so a pass produced before the S8 and API gates reads as current.

### Motivation
smooth-sequences must repair a workspace rather than dead-end on a blocked surface, and a completion report must be attributable to the checks that produced it.

### Constraints
No check is weakened: the S8 denominator stays the full extracted formula set, and every owned formula still needs a ledger row with digest, theory, implementation and tests. New fields are optional and absent by default, so an existing manifest yields byte-identical seeds and unchanged verdicts. No edits to gaia, doors or crystal. Existing commands, their order and their interactions are preserved.

## Scope

- workspacify-tree: annotate every segment with the deterministic formula ids whose source lines fall inside it (structure.segments[].formula_ids) using spec-formula extractFormulas/uniqueFormulas; write the field only when non-empty.
- workspacify-tree decisions: add optional segment_ownership [{segmentId, packageId, source:{line, quote}}] with a schema definition.
- workspacify-tree validation: refuse an unknown segment id, an unknown package id, a source line outside the segment, a missing/empty quote and a duplicate segment claim with named codes.
- workspacify-tree gate: every segment with a non-empty formula_ids must be covered either by an owned inventory item or by exactly one grounded segment_ownership entry; add formula_segment_orphan_count to unallocated_count so the manifest cannot publish unowned formula prose.

- workspacify-allocate: collectPackageSegments reads segment_id from a category=segment ownership entry in addition to inventory source_refs; coverage proof treats a segment with formula_ids as material.
- workspacify-allocate: seed-local checks and the authoring packet accept the segment category; existing categories and their order are unchanged.
- smooth-sequences: S8.formula-unowned routes to tree-decision regeneration (open --tree-decisions), not allocate regeneration; S8.segment-coverage for a missing or malformed seed routes to allocate regeneration; update checks-spec-completeness.mjs, repair-route.mjs and smooth-sequences.md.

- Documentation: workspacify-tree.md, workspacify-allocate.md and smooth-sequences.md name the new field, gate and route.
- Non-change: the S8 denominator, ledger row requirements, calibration, blocked-surface policy and every existing category keep their current behavior.
- Impact: existing workspaces without formula_ids/segment_ownership take the current path; regenerated workspaces gain the optional fields and the stricter gate.

## Acceptance Criteria

- Happy path: a prose-heavy specification with formulas and a grounded segment_ownership entry completes tree finalize, allocate finalize and smooth with zero S8.formula-unowned; every formula without a ledger row is S8.formula-missing routed to /grill-me-for-rfc.
- Error case: an unknown segment, unknown package, out-of-range line, missing quote or a formula-bearing segment with no inventory and no grounded ownership is refused by workspacify-tree with the named code; no manifest is published.
- Edge case: a specification with zero formulas gains no new obligation and renders byte-identical seeds; a status.json without checkSetDigest is reported as a previous check set, never as current completion.

## Invariants

- [Normal establishment] Every segment with a non-empty formula_ids is covered by an owned inventory item or by exactly one grounded segment_ownership entry; the owning package's seed carries the segment id.
- [Error invariant] A refused segment claim publishes no manifest and leaves the previous manifest byte-identical; the refusal names the segment, line and code.
- [Internal state invariant] workspace.ownership.entries keeps (category, inventory_ref) unique; a segment entry carries segment_id and exactly one owner; no duplicate row is emitted for a segment already covered by inventory.
- [Boundary invariant] A manifest without formula_ids or segment_ownership renders byte-identical seeds and yields the same smooth verdict; checkSetDigest changes only when a check id, requires entry or claims flag changes.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — smooth S8 blocked surface S8.formula-unowned -> workspacify-tree segment ownership -> seed source_segments -> S8 ownership

- **Precondition**: A workspace specification contains at least one segment with a non-empty formula_ids and no owned inventory item; tree decisions carry one segment_ownership entry whose segmentId exists in structure.segments, whose packageId exists in workspace, whose source.line lies inside the segment and whose source.quote occurs on that line.
- **Postcondition**: The tree manifest publishes the segment's formula_ids and one category=segment ownership row with segment_id; the owning package's RFC-SEED.md reference block carries the segmentId; smooth reports zero S8.formula-unowned for every formula in that segment and reports S8.formula-missing only for formulas without a ledger row.
- **Invariant**: For every segment with a non-empty formula_ids, owned_inventory_ids is non-empty or exactly one grounded segment_ownership entry names it. No formula leaves the S8 denominator. A manifest without formula_ids or segment_ownership renders byte-identical seeds and yields the same smooth verdict as before.

### C002 — smooth-sequences report -> status.json / SMOOTH-SEQUENCES.json / COMPLETION-CERTIFICATE.json

- **Precondition**: A smooth-sequences run reads a workspace with a status.json written by an earlier run, which may carry no checkSetDigest or a different one.
- **Postcondition**: The run writes checkSetDigest, a sha256 over the sorted CHECK_REGISTRY descriptors and the closure gate ids, into status.json, SMOOTH-SEQUENCES.json and COMPLETION-CERTIFICATE.json inputs; the human report prints it; a stored status with a different or absent digest is reported as a previous check set and never as current completion.
- **Invariant**: checkSetDigest is deterministic for the same registry and changes when any check id, requires entry or claims flag changes. Recording it changes no check result, no verdict and no exit code.
