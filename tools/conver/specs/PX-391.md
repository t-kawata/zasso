# PX-391: Draw the progress animation in execution order

## Goal

The progress animation replays events in the order they were executed. A command that ran after a later pipeline stage is drawn after that stage, and the displayed stage may revisit an earlier stage. When the workspace has no `.conver-history.jsonl`, the existing display-date estimate remains the clock and the current animation is unchanged.

## Purpose

`draw-progress-gif` currently builds an ordinal timeline: every event is grouped by `STAGE_ORDER`, and the evidence timestamp is replaced by a per-stage display estimate. A workspace that went to split or drill and then re-ran grill is therefore drawn as if grill had always happened first. On gaia, the latest grill run (2026-11-07 14:03) is drawn at frame 92 of 200 (about 46%) while drill runs occupy frames 163-183 and the animation ends at frame 199. The same ordinal grouping hides doors' educe/explain alternation and crystal's grill/educe interleaving.

## Motivation

The animation is a replay of what happened, not a sanitized view of the pipeline order. PX-381 made the stage order ordinal to survive unreliable artifact mtimes, but the history records introduced by PX-366 carry command timestamps that are reliable enough to order the actual execution. The correction must keep the no-history estimate, which is the only clock available for workspaces created before history existed.

## Constraints

- Time is the ordering basis. The order of records inside `.conver-history.jsonl` is not an execution order and must not be used as one.
- History `at` and trusted status timestamps are stronger evidence than artifact mtimes. When an artifact timestamp conflicts with the command that produced it, the command run's time wins for events inside the run coverage.
- Events for a stage/package with history runs are anchored to the latest run at or before the event time. Events before the first run of that stage/package, and events with no run coverage, use the existing `computeStageDisplayDates` estimate.
- `STAGE_ORDER` remains the ladder layout and the event-weight source; it is not the timeline order.
- The displayed stage follows the latest stage or run event and may move backward.
- A model with no history runs keeps the existing ordinal timeline and frames byte-for-byte.
- `buildTimeline` and `progressAt` do not mutate `model.events`, `model.growthEvents` or `model.runs`.
- No command document and no installed copy under another workspace is edited in this ticket.
- The null-package run rendering defect (`engine.js:741-743`) is out of scope.

## Scope

- `.claude/scripts/conver/progress-gif/loop.js`
- `tests/conver/execution-order.test.mjs`
- Existing tests that encode the ordinal order for a model carrying history runs are replaced by the execution-order contract; the no-history golden is not edited.

## Acceptance Criteria

- C001: a drill run at T1 and a grill run at T2 > T1 produce frames whose stage is drill before grill, and the grill run marker appears after the drill run marker.
- C002: educe/explain runs at alternating times produce alternating displayed stages, including a backward explain-to-educe move.
- C003: a stage event for a package with no matching run uses the display estimate, not another package's run time.
- C004: a model with no runs reports `chronological === false` and keeps the existing ordinal frames.
- C005: every chronological timeline has a non-decreasing `orderT`, and each run marker appears exactly once.
- C006: `progressAt` uses the same order key as the frames on the chronological path.

## Invariants

- The no-history golden `tests/conver/fixtures/no-history-frames.json` is unchanged and matched exactly.
- Every original event time is preserved; only the timeline order and the per-event order key change.
- Each run marker is emitted once and never changes package progress or stage progress.
- The frame count and weight arithmetic are unchanged; only the event order and the displayed stage rule change.
