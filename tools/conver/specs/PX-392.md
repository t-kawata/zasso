# PX-392: Order a status event without run coverage by the display estimate

## Goal

A stage event whose source is a status file and whose stage/package has no history
run is ordered by the `computeStageDisplayDates` estimate, not by the raw status
timestamp. A stage whose status was written by an older run is therefore never
drawn before a later pipeline stage that has command evidence.

## Purpose

PX-391's constraint says every event with no run coverage uses the display
estimate. `executionOrderTime` instead returns the raw status `evidenceT` for
status events, so gaia's eight split status files (runIds from 2026-11-02..04)
are placed in the middle of the 2026-11-05..08 grill stream. The render
`20261108214520.html` shows the displayed stage order
`educe -> explain -> grill -> split -> drill -> boundify -> smooth -> graphify`
instead of the recorded execution order
`drill -> grill -> graphify -> boundify -> smooth -> split`.

## Motivation

Repeated ordering fixes have not closed the chronological path. The status
branch is the one path that escapes the no-run-coverage rule: a stage with no
run in the event's package falls back to the status file's own runId epoch, which
may belong to an earlier execution of that stage. The stage estimate already
folds every trusted status time into the pipeline order through
`computeStageDisplayDates`, so discarding the stale per-event timestamp loses no
evidence.

## Constraints

- Only the chronological path changes. A model with no history runs keeps the
  ordinal timeline and frames byte-for-byte.
- An event with a matching stage/package run keeps the latest-run-at-or-before
  anchor.
- An event before the first run of its stage/package keeps the display estimate.
- An event with no run coverage uses the display estimate for every time source,
  including `status`.
- `STAGE_ORDER` remains the ladder layout and the event-weight source; it is not
  the timeline order.
- `buildTimeline` and `progressAt` do not mutate the model.
- The gaia, crystal and doors workspaces are not modified.
- The three script trees carry byte-identical progress-gif sources.

## Scope

- `.claude/scripts/conver/progress-gif/loop.js` and its root/siprs mirrors
- `tests/conver/execution-order.test.mjs`

## Acceptance Criteria

- C001: a status event for a stage/package with no matching run takes its order
  key from `displayDate`.
- C002: a status event with a matching run still anchors to the latest run at or
  before its evidence time.
- C003: a stale split status is not displayed before a later boundify event in
  the frames.
- C004: a model with no runs keeps `chronological === false` and the ordinal
  frames.

## Invariants

- Every event keeps its original `evidenceT`.
- The chronological `orderT` sequence is non-decreasing.
- Each run marker is emitted once.
- The no-history golden is unchanged.
