# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-394: Condense tickets deterministically and make split finish through the same gate

**Ticket Key**: PX-394 · **Phase**: -1

---

## Background

### Goal
Make ticket condensation a deterministic, script-owned operation so the ticket count equals the minimum contiguous partition of the implementation-ordered ticket sequence under the version-3 work budget, and make `/split-to-tickets` finish through that same operation without nesting commands.

### Purpose
The split pipeline must choose the fewest tickets that stay inside the measured per-ticket implementation-work ceiling. Today the count is decided by AI-authored `splitReason` refusals; the script only measures and rejects some missing evidence. The purpose of this ticket is to move the decision to a reproducible partition algorithm and to keep AI judgment for prose, design and semantics that cannot be computed.

### Motivation
Measured on the current workspaces: 49 implementation packages hold 676 tickets; the applied version-3 contiguous partition reaches 463 (gaia 320 -> 226, crystal 287 -> 203, doors 69 -> 34). gaia-commerce alone is 27 -> 18, matching the independent estimate of 18-20. The existing gate cannot force this reduction. `maximumTicketCount` is `minimumWorkTickets + acceptedRefusals` (`ticket-workload.js:412`); n tickets have n-1 adjacent pairs, so refusing every pair makes the upper bound n. Refusal evidence is unverified prose: the gaia-commerce P1-1 attempt claims a same-ticket prerequisite fails `PREREQUISITE_NOT_BEFORE`, but `implementation-order.mjs:700` explicitly skips a same-ticket hard edge. Phase consolidation then changes adjacency without re-running the work-budget gate, leaving 275 `MERGE_ATTEMPT_MISSING` findings across the current files. Evolve mode skips consolidation entirely to preserve keys (`split-to-tickets.md:134`), so re-running the split cannot repair existing files.

### Constraints
- TDD Red-Green-Refactor, serial only; the Red set covers every finding, every non-gaia shape and the backward-compatibility paths.
- No existing verifier is weakened. Coverage, closure, contract-chain and implementation-order checks stay byte-for-byte equivalent; only the permitted ticket count changes, and only for budget version 3.
- Version 1 and version 2 budget files and existing `Tickets.json` files remain readable and keep their old semantics.
- No automatic AI prose authoring in the core: merged prose is preserved verbatim under provenance headings. An optional AI polish pass is out of scope.
- No command nesting: `/condense-tickets` and the split final gate call the same `condense-tickets.js`; the command document is a thin wrapper.
- Fail closed, archive before write, restore on failure, and make a second identical apply a no-op.
- All 49 implementation packages currently pass `verify-all-ticket-coverage`, `verify-ticket-closure` and `verify-implementation-order`; the change must keep them passing. All their tickets are `todo`; the 38 `reviewed` tickets belong only to the gaia root aggregate, which is out of scope.

## Scope

- [Action] Add the deterministic contiguous partition and the mechanical group merge; keep the existing `workloadOfTicket` as the only workload definition.
- [Detail] The partition is a dynamic program over the ordered ticket array. `best[i]` is the minimum group count for the first i tickets; a group `[j, i)` is admissible when every component sum is within the v3 budget, or when `i - j === 1` (an irreducible ticket). - [Before -> After] Before, the count is `minimumWorkTickets + acceptedRefusals` and any adjacent pair can be refused with prose. After, the count is the partition minimum and every remaining boundary is proven by a budget-forced merge.

## Investigation

- Gate tautology: `maximumTicketCount(minimumWorkTickets, acceptedRefusals)` returns `minimum + acceptedRefusals` (`lib/ticket-workload.js:412`); `collectMergeFindings` accepts one refusal per adjacent pair (`:687-719`); `TICKET_COUNT_ABOVE_MERGE_EVIDENCE` compares against that upper bound (`:962-971`). With n tickets and n-1 refusals, the bound is n.
- False refusal: gaia-commerce P1-1 records a `tdd-order` refusal claiming a same-ticket prerequisite is placed at the same position and fails. `sequences-slice/lib/implementation-order.mjs:700` skips the edge when `providerTicket === consumerTicket`, so the claim is false.
- Phase consolidation: `consolidate-phase-tickets.js` merges phases and renumbers tickets but contains no work-budget or merge-evidence check; gaia-commerce P0 currently reports minimum 6, upper bound 7, actual 12 and five missing attempts.
- Evolve mode: `split-to-tickets.md:134` skips `consolidate-phase-tickets.js` to avoid renumbering; this ticket's condensation does not renumber the survivor, so it can run in evolve mode.
- Measured census: 49 implementation packages, 676 tickets, applied contiguous minimum 463 (gaia 320 -> 226, crystal 287 -> 203, doors 69 -> 34); gaia-commerce 27 -> 18. All 676 implementation-package tickets are `todo`; the 38 `reviewed` tickets belong only to the gaia root aggregate, which also holds the matching `specs/P*.md` files.
- Structural gate health: all 49 packages pass `verify-all-ticket-coverage`, `verify-ticket-closure` and `verify-implementation-order --package`; the only failing evidence is the merge gate this ticket replaces.
- Re-population evidence: `populateTicketDistribution` is idempotent for the unchanged tickets in gaia-commerce P0 and crystal-operation P0; the few differences are stale obligation records that re-population corrects, which is the intended behavior.
- Existing test harness: `tests/tickets/ticket-workload.test.mjs` imports the CommonJS workload module through ESM; `tests/tickets/add-tickets-work-budget.test.cjs` exercises the gate; `tests/consolidate-phase-tickets.test.cjs` covers phase merging. ## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — phase workload and version-3 budget -> partition minimum

- **Precondition**: Every ordered ticket in the phase has a measurable workload vector with the seven implementation components, and the budget provides a positive ceiling for each component.
- **Postcondition**: The partition returns the fewest contiguous groups whose component sums stay within the ceilings, except a single irreducible ticket that exceeds a ceiling alone.
- **Invariant**: No partition with fewer groups exists, and every group is contiguous and covers the ordered tickets exactly once.

### C002 — implementation-ordered ticket array -> contiguous group ranges

- **Precondition**: The ticket array is the implementation order produced by the split and phase consolidation.
- **Postcondition**: Each group is a contiguous range; the union of ranges is the whole array with no gap and no overlap.
- **Invariant**: The merge never reorders a ticket and never combines two non-adjacent tickets.

### C003 — ticket group -> survivor ticket

- **Precondition**: Every member has a key, id, status, nodeIds and authored prose fields.
- **Postcondition**: The earliest member becomes the survivor; nodeIds are unioned; prose is preserved under provenance headings; contracts are unioned by id; the group status follows the least advanced member.
- **Invariant**: No authored text and no node id is lost, and every absorbed key is recorded in condensedFrom.

### C004 — survivor nodeIds and package artifacts -> derived ticket fields

- **Precondition**: The graph, Dirs-Tree, view and root artifact are readable for the package.
- **Postcondition**: distribution, contracts, formulaObligations, prerequisites, default_files and relatedTicketIds are recomputed from those artifacts before the write.
- **Invariant**: No stale derived value from an absorbed ticket reaches the survivor, and a package without a view reports skipped:no-distribution rather than inventing one.

### C005 — apply invocation -> Tickets.json bytes

- **Precondition**: The package is readable, the plan is computed, and the archive destination is writable.
- **Postcondition**: Success writes the archived predecessor and the new Tickets.json atomically; failure restores the archive; a second identical apply writes nothing.
- **Invariant**: No partial write exists at any exit, and the pre-apply bytes are recoverable from the archive.

### C006 — shared condense script -> command and split gate

- **Precondition**: The command and the split gate are given the same package and the same artifacts.
- **Postcondition**: Both produce the same plan digest and apply the same groups; the command document contains no second implementation.
- **Invariant**: The command and the gate cannot diverge because only one module computes the partition.
