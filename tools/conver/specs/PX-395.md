# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-395: Condense every manifest package and add /condense-workspace

**Ticket Key**: PX-395 · **Phase**: -1

---

## Background

### Goal
Condense every package the workspace manifests declare, including the workspace-root package whose path is `.`, and add a no-argument `/condense-workspace` command that runs the same mechanical script over the full manifest-derived target set.

### Purpose
PX-394 added deterministic condensation and a package-level `/condense-tickets`. Its workspace mode discovered targets by walking the filesystem for directories that hold `Tickets.json`, `RFC-GRAPH.json` and `RFC-Dirs-Tree.json`. That rule missed a real package and could pick up working copies.

### Motivation
The crystal workspace's `WORKSPACIFY-TREE-MANIFEST.json` declares `pkg-crystal` at `path: "."`. The filesystem walk excluded the workspace root, so the crystal facade package was never condensed: it still holds 10 tickets where the version-3 partition needs 9. The same walk also discovered a temporary copy (`.condense-trial/gaia-commerce`) during the PX-394 rollout. The manifest is the authoritative package list; it names every package, including `.`, and never names a working copy. The gaia manifest declares 29 packages while only 19 hold tickets; the other 10 must be reported as unsplit rather than silently absent.

### Constraints
- The command takes no argument. `--workspace` remains a script flag, never a command argument.
- Manifest discovery is the default when `WORKSPACIFY-TREE-MANIFEST.json` exists; a workspace without it keeps the existing filesystem fallback.
- A manifest package without `Tickets.json` is `skipped:unsplit`, not an error. A manifest package with `Tickets.json` is a target even when the graph or Dirs-Tree is absent; that package reports `skipped:no-distribution` from the package script.
- `path: "."` is a package. It is not confused with a workspace aggregate: the tree manifest decides membership, not the path depth.
- A `Tickets.json` outside the manifest is reported as `UNLISTED_PACKAGE`; the command does not silently condense it.
- Per-package apply keeps its archive and fail-closed gates. The workspace runner continues after a package failure, reports every failure, and exits 1 if any package failed.
- The workspace implementation order is regenerated once after the package loop, not once per package.
- PX-394's package-level behavior, its no-argument command, and every existing verifier remain unchanged.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — WORKSPACIFY-TREE-MANIFEST.json workspace.packages -> target directories

- **Precondition**: The workspace root holds a readable tree manifest whose workspace.packages array carries a path for every package.
- **Postcondition**: Each distinct manifest path that holds Tickets.json becomes one target, including path '.', in manifest order.
- **Invariant**: The target list contains no duplicate directory and no directory absent from the manifest.

### C002 — manifest package without Tickets.json -> skipped report

- **Precondition**: A manifest row resolves to a directory that does not hold a readable Tickets.json.
- **Postcondition**: The package appears in skipped with reason unsplit or missing-directory and is not passed to applyPlan.
- **Invariant**: A skipped package never produces a write and never aborts the remaining targets.

### C003 — Tickets.json outside the manifest -> unlisted report

- **Precondition**: A directory below the workspace root holds Tickets.json but no manifest row names it.
- **Postcondition**: The directory appears in unlisted and is not condensed by the workspace run.
- **Invariant**: A working copy or an unlisted package can never enter the target list silently.

### C004 — path '.' and command arguments -> package identity and no-argument command

- **Precondition**: The manifest may name the workspace root as a package path, and /condense-workspace may receive ARGUMENTS.
- **Postcondition**: Path '.' is a package target when the root holds Tickets.json; non-empty ARGUMENTS is refused before any script runs.
- **Invariant**: The command exposes no user-facing flag and the root package is not confused with a workspace aggregate.

### C005 — one package failure -> remaining targets

- **Precondition**: The workspace run applies packages sequentially and one package gate fails.
- **Postcondition**: The failed package restores its archive, the remaining targets are attempted, and the run exits 1 with every failure listed.
- **Invariant**: No package failure leaves a partial Tickets.json and no failure suppresses a later package's independent archive.

### C006 — workspace package loop -> workspace implementation order

- **Precondition**: The workspace run has completed its package loop.
- **Postcondition**: When at least one package changed, the workspace implementation-order writer runs exactly once after the loop; when none changed, it is not invoked.
- **Invariant**: The workspace sidecar is written once per run and never per package.

## Boy Scout Rule

- Replace the single `discoverPackages` function with three named responsibilities: manifest discovery, filesystem fallback and the chooser. Each returns the same `{ source, targets, skipped, unlisted }` shape, so `runWorkspace` reads as prose.
- Extract the per-package result formatting and the workspace summary into named functions; no inline ternaries in the loop.
- Use named constants for the manifest file names and the skip reasons (`unsplit`, `missing-directory`).
- Do not swallow a package failure: carry the error into the summary and exit 1.
- Add tests for every new function and for the fallback path.
