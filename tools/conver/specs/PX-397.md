# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-397: Add machine-readable gate findings and deterministic repair tools

**Ticket Key**: PX-397 · **Phase**: -1

---

## Background

### Goal
Every gate emits an actionable repair worklist instead of stopping the pipeline. The pipeline consumes the worklist, applies the repair, and reruns until the finding set is empty and stable.

### Purpose
The implementation pipeline currently mixes verification with judgment and often reports a failure without a mechanical repair route. This ticket builds the common finding schema, the repair plan and loop, the completion certificate, the debt check, and the deterministic tools every later gate will use.

### Motivation
The user requires gates that never stop and never ask a human. A gate must tell the AI what is wrong and how to fix it. Without a shared finding schema and repair tools, each command invents its own stop condition.

### Constraints
No existing gate or command behavior changes. No command Markdown edit. The new tools are additive. Every tool is atomic and refuses invalid input without writing.

## Scope

- .claude/scripts/tickets/lib/gate-finding.js: define and validate the shared finding shape code, asset, problem, fix list and rerun command. Reject a finding that has no executable fix or no rerun.
- .claude/scripts/tickets/repair-plan.js: aggregate findings from multiple gates, deduplicate by finding identity, and order repairs by dependency: contract, test, annotation, spec, formula.
- .claude/scripts/tickets/repair-loop.js: run the gates, apply each executable fix, rerun, and complete only when findings are zero on two consecutive runs with the same digest.
- .claude/scripts/tickets/completion-certificate.js: record the final gate set, each gate digest, the rerun count and the zero-finding proof.
- .claude/scripts/tickets/gate-debt.js: compare finding identities with the previous run and report DEBT_INCREASED when the new set is not a subset of the old set.
- .claude/scripts/tickets/patch-ticket.js: schema-aware atomic append or overwrite for one ticket field. Reject a wrong type or unknown field shape without writing.
- .claude/scripts/tickets/insert-verifies.js: insert an @verifies annotation at a given file and line with deduplication and format generated by buildAnnotation().
- .claude/scripts/tickets/scaffold-test.js: generate a failing test with @verifies and a [::STUB::] marker. Refuse an empty body or a test that cannot fail.
- .claude/scripts/tickets/rewrite-deferral-ticket.js: replace title, background and scope of a deferral clone from a structured seed in one atomic write.
- .claude/scripts/tickets/record-review.js: write instrumentation, rfcDiscrepancies and notes with schema validation and append semantics.
- tests/tickets: fixtures and tests for every tool and for the repair loop. No existing test is modified or removed.

## Acceptance Criteria

- Happy path: a finding with a fix is applied by the loop and the rerun is zero.
- Error case: an invalid or unrepairable finding is reported as a gate defect without writing.
- Edge case: two consecutive zero-finding runs with the same digest produce a completion certificate.

## Invariants

- [Normal establishment] Every gate finding carries code, asset, problem, at least one fix and a rerun command.
- [Error invariant] A finding without a fix or rerun is rejected as a gate defect; no asset is written.
- [Internal state invariant] patch-ticket, insert-verifies, scaffold-test, rewrite-deferral-ticket and record-review either write completely or leave the target byte-identical.
- [Boundary invariant] Existing command Markdown and existing gate output hashes equal the pre-ticket baseline.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — gate detection -> finding

- **Precondition**: a gate detects a problem
- **Postcondition**: the finding carries code, asset, problem, fix list and rerun command
- **Invariant**: a finding without a fix or rerun is rejected

### C002 — repair plan -> repair loop

- **Precondition**: a repair plan has at least one executable finding
- **Postcondition**: the loop applies fixes and reruns until findings are zero twice with the same digest
- **Invariant**: a run that increases finding identities reports DEBT_INCREASED

### C003 — repair tool -> asset file

- **Precondition**: a ticket field or test file is patched
- **Postcondition**: the change is written atomically after schema or line validation
- **Invariant**: an invalid field type or missing target leaves the file unchanged

### C004 — new tools -> existing pipeline

- **Precondition**: the new tools are added without changing existing gates or commands
- **Postcondition**: existing command Markdown and gate output hashes equal the baseline
- **Invariant**: no existing test is modified or removed

- Name the finding identity function `findingIdentity` and the dependency rank `repairRank`, so the plan order is a function of the asset class rather than an inline array.
- Extract `writeTemporaryThenRename(targetPath, bytes)` into a shared helper used by every tool; no duplicated atomic-write logic.
- Replace generic locals (`data`, `info`, `tmp`) with `finding`, `repairPlan`, `ticketDocument` and `targetBytes`.
- Keep each tool under fifty lines and each file under the existing size; split `repair-loop` into `runGateCycle`, `applyFixes` and `isStable`.
- Add why-comments on the three non-obvious rules: a finding without a fix is a gate defect, the loop needs two stable runs, and an empty test body is a stub.
