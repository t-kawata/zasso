# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-399: Wire repair loops into start, review and resolve and prevent reviewed-ticket invalidation

**Ticket Key**: PX-399 · **Phase**: -1

---

## Background

### Goal
start, review and resolve consume the repair worklists and complete without human intervention. resolve cannot change code and leave a reviewed ticket unverified.

### Purpose
PX-397 provides the finding schema and tools. PX-398 provides the gates. This ticket connects them to the three implementation commands, adds a reverify path for ticket changes, and makes reviewed status conditional on a fresh verification pass rather than on a past review.

### Motivation
The largest remaining hole is post-review mutation. resolve can edit code, remove a stub or change a warning suppression after review and no contract, formula or annotation gate is rerun. The ticket status stays reviewed while the evidence is stale.

### Constraints
Existing command roles, Steps, arguments and gate semantics must not change. Command Markdown edits are additive and minimal. Case B and numeric-phase tickets keep their exact flow. No human decision is requested; a stale ticket is repaired and reverified in the same run.

## Scope

- .claude/scripts/tickets/reverify-ticket.js: run the contract, contract-clause, axis, operation, formula, annotation and target gates for one ticket and aggregate findings into one repair plan.
- .claude/scripts/tickets/discover-changed-tickets.js: map changed files to ticket keys through ticket-key annotations and targetStubs, so resolve can find affected tickets without an argument.
- .claude/commands/start-ticket.md: Step 5b and 5c consume the report-mode gates and the repair loop. No existing Step is removed, renumbered or made optional.
- .claude/commands/review-ticket.md: Step 10b and 10c consume the report-mode gates and the repair loop. No existing Step is removed, renumbered or made optional.
- .claude/commands/resolve-ticket.md: Step 9 and 10 rerun annotation, target, contract, formula and reviewed-staleness checks for changed tickets, including the no-argument path.
- completion certificate: start and review record the zero-finding proof; resolve records the reverify proof. The certificate is written beside the ticket record, not as a new ticket field.
- tests/tickets: end-to-end fixtures for each asset class, for resolve after review, and for Case B and numeric-phase non-regression. No existing test is modified or removed.

## resolve-ticket today
- Step 9a and 9b run only when `$ARGUMENTS` is non-empty. Step 9c runs `find-all-stubs`, `scan-crimes.sh` and `validate-no-external-excuses` unconditionally, but none of these checks contracts, clauses, axes, formulas or annotations.
- Step 10 reruns compile, tests and no-excuse; it does not rerun the review gates. A resolve edit can therefore invalidate a reviewed ticket without detection.
- Done explicitly forbids changing ticket status. The certificate is the place to record fresh evidence without changing status.

## Acceptance Criteria

- Happy path: a ticket with a missing contract element, obligation or formula is repaired and reverified to zero.
- Error case: a reviewed ticket invalidated by resolve is detected and cannot remain stale.
- Edge case: Case B and numeric-phase tickets produce byte-identical output and follow the existing flow.

## Invariants

- [Normal establishment] start and review consume report-mode findings and apply the repair plan until the finding set is zero twice with the same digest.
- [Error invariant] resolve that changes code or removes a stub always runs the reverify path; a failure is a finding, never a stop.
- [Internal state invariant] A reviewed ticket whose code changed is reported as REVIEWED_TICKET_STALE until a fresh reverify passes.
- [Boundary invariant] Case B and numeric-phase tickets keep their exact output and command flow; every existing Step, argument and role remains available.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — start -> repair loop

- **Precondition**: start reaches Step 5b with a ticket carrying contracts and distribution
- **Postcondition**: the report gates run and the repair loop reaches zero findings
- **Invariant**: an existing start Step is not removed, renumbered or made optional

### C002 — review -> repair loop

- **Precondition**: review reaches Step 10b with a done ticket
- **Postcondition**: the report gates run and the repair loop reaches zero findings
- **Invariant**: review still runs the final contracts, targets and formula checks

### C003 — resolve -> reverify

- **Precondition**: resolve changes code or removes a stub
- **Postcondition**: every changed ticket is reverified for contracts, clauses, axes, formulas, annotations and targets
- **Invariant**: a repo change cannot skip the reverify path

### C004 — reviewed status -> fresh evidence

- **Precondition**: a ticket is reviewed and a later resolve changes its code
- **Postcondition**: the ticket is reverified and either repaired or marked stale for the next repair loop
- **Invariant**: reviewed status is not treated as a permanent verification certificate

### C005 — new wiring -> existing commands

- **Precondition**: start, review and resolve are updated
- **Postcondition**: their Steps, arguments and roles remain available
- **Invariant**: Case B and numeric-phase tickets keep the existing output and flow
