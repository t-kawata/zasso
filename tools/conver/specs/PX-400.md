# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-400: A deterministic design-amendment transaction for SPEC, RFC, graph, Dirs-Tree and Tickets

**Ticket Key**: PX-400 · **Phase**: -1

---

## Background

### Goal
During implementation (start, review, resolve) the five design artifacts — the workspace-root SPEC, each package RFC.md, RFC-GRAPH.json, RFC-Dirs-Tree.json and Tickets.json — are treated as pre-implementation hypotheses, not as facts proven through implementation. An omission, contradiction, deficiency or danger found in them is resolved during implementation, never deferred and never hand-edited.

### Purpose
The resolution must not be left to AI judgment. A single amendment transaction applies a mechanically verifiable correction, calls the owner generator of each derived artifact, rebuilds every digest, receipt and self-hash, runs a fixed gate manifest, and promotes the result only when no new finding appears. The tool replaces no existing script: it calls the generators and reuses ticket-mutation-gate.js, verify-chain.mjs, verify-graph-integrity.js, validate-dirs-tree-schema.js and canon-state.js.

### Motivation
The four README entry patterns (no artifacts, driven 4-layer project, partial conver project, empty plus specification) mean a command such as /start-ticket may legitimately run when SPEC, RFC.md, graph or Dirs-Tree does not exist. The README invariant says incompleteness is input, never a refusal condition. A shared tool that made an absent artifact an execution requirement would block accurate work with an inaccurate error. The transaction therefore resolves per-artifact state and skips absent artifacts with exit 0.

### Constraints
- No existing script is replaced, deleted or reimplemented; no existing command Step, number, argument or role is changed. Command Markdown edits are additive and telegraphic.
- Derived artifacts (graph, Dirs-Tree, Tickets) are never written by the transaction itself; the owner generator and ticket-mutation-gate.js remain the only writers.
- Owner commands keep their accurate hard prerequisites (graphify needs RFC.md, boundify needs the graph, split needs graph and Dirs-Tree, workspacify-tree needs SPEC). Only the shared tool is existence-gated.
- Missing receipts are legacy, never stale, matching stage-receipt.js. Unreadable and ambiguous artifacts are real failures, not skips.
- Case B and numeric-phase tickets keep their existing behavior.

## Investigation

- README.md defines the five-layer loop and four entry patterns; its load-bearing invariant is that an incomplete conver project must never be blocked and incompleteness is input, not a refusal condition. Pattern 3 keeps only some artifacts, so shared tooling must be existence-gated.
- package-artifacts.js already exposes allowMissing on resolveSourcePath, resolveGraphPath, resolveDirsTreePath, resolveTicketsPath and resolveViewPath; resolveCanonicalPathOrExit exits on absence and must not be used by the shared tool. findSingleSiblingPath refuses two candidates instead of guessing.
- ticket-mutation-gate.js (PX-378) already implements snapshot, verify, promote and byte-for-byte restore for Tickets.json; the amendment transaction reuses it instead of reimplementing the transaction.
- rfc-graph/lib/stage-receipt.js records sourceDigest, inputDigests and outputDigest per stage and treats a missing receipt as legacy, never stale. grill-me-for-rfc/canon-state.js classifies STANDALONE, PARTIAL, MATERIALIZED_FRESH and MATERIALIZED_STALE and names the rederive chain.
- sequences-slice/verify-chain.mjs is the read-only five-layer verifier; rfc-graph/verify-graph-integrity.js checks five graph axes and validate-dirs-tree-schema.js checks six Dirs-Tree items.
- workspacify-tree/run.mjs writes WORKSPACIFY-TREE-MANIFEST.json with input.source_hash and integrity.manifest_hash; render.mjs and atomic-publish.mjs recompute the canonical self-hash and reload-validate it, so the hash tree must be rebuilt by these owners.
- lib/finding-delta.js supplies diffFindings, the zero-new-finding criterion the mutation gate already uses.
- The command inventory shows owners (grill-me-for-rfc, graphify-rfc, boundify-graph, split-to-tickets, workspacify-*) and detectors (find-omissions, drill-rfc-down, educe-sequences, smooth-sequences, explain-seed, consolidate-stubs, make-ticket, plan-ticket). RFC.md and SPEC have no writer script: the grill command writes RFC.md itself, so the append writer is a new path, not a replacement.
- External workspaces measured: gaia holds 261 RFC.md files and 29 graph and Dirs-Tree pairs under a single root tree manifest; crystal and doors have the same shape. These are read-only smoke targets.

## Acceptance Criteria

- Happy path: with all five artifacts present, the transaction appends an amendment to RFC.md, rederives graph, Dirs-Tree and Tickets through their owners, rebuilds every receipt and self-hash, runs the fixed gate manifest with zero new findings, promotes atomically and records an amendment ledger entry.
- Error case: an unreadable artifact or two matching canonical candidates exits 1 with a named error and leaves every file untouched; a gate failure after a write restores every file byte for byte.
- Edge case: a partial project with only Tickets.json, or a project with no artifacts, returns per-artifact skipped states, emits no finding, writes nothing and exits 0; a second identical amendment is a no-op.

## Invariants

- [Normal condition] every artifact operation is existence-gated: a present artifact is verified, an absent artifact is skipped, and a skip is never a finding or a block.
- [Error invariant] no write survives a failed gate: the transaction promotes all five artifacts or restores every one byte for byte.
- [Internal state invariant] derived artifacts are written only by their owner generators and Tickets.json only through ticket-mutation-gate.js; the transaction never writes a derived artifact itself.
- [Boundary invariant] absence is a skip while unreadable, ambiguous or append-target-missing are failures; existing command Steps, numbers, arguments and roles never change.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — amendment-transaction/existence

- **Precondition**: one or more of the five design artifacts is absent
- **Postcondition**: the shared amendment tool reports skipped absent and exits zero without any finding or write
- **Invariant**: artifact absence is an input and never a refusal condition

### C002 — amendment-transaction/owner-prerequisite

- **Precondition**: an owner generator runs without its required input artifact
- **Postcondition**: the owner command fails with its existing named prerequisite error and writes nothing
- **Invariant**: the shared tool adds no new hard prerequisite to any command

### C003 — amendment-transaction/atomicity

- **Precondition**: a gate in the amendment gate manifest fails after a write begins
- **Postcondition**: every modified artifact is restored byte for byte and no partial amendment survives
- **Invariant**: the transaction promotes all artifacts or none

### C004 — amendment-transaction/non-regression

- **Precondition**: the post amendment gate manifest runs
- **Postcondition**: promotion occurs only when diffFindings reports no new finding
- **Invariant**: inherited findings never block a legitimate amendment

### C005 — amendment-transaction/hash-chain

- **Precondition**: RFC.md or SPEC changes during an amendment
- **Postcondition**: each stage receipt sourceDigest equals the sha256 of RFC.md and the tree manifest input source_hash equals the sha256 of SPEC with manifest_hash equal to the canonical self hash
- **Invariant**: the hash chain is rebuilt only by the owner modules

### C006 — amendment-transaction/append-only

- **Precondition**: an amendment appends text to SPEC or RFC.md
- **Postcondition**: every pre-existing byte is unchanged and only the amendment section is appended
- **Invariant**: existing design prose is never rewritten by the tool

### C007 — amendment-transaction/ownership

- **Precondition**: the amendment transaction needs a graph dirs-tree or tickets change
- **Postcondition**: the owner generator and ticket-mutation-gate are called instead of a direct write
- **Invariant**: the transaction never writes a derived artifact itself and never reimplements an existing writer

### C008 — amendment-transaction/report-envelope

- **Precondition**: report mode is requested
- **Postcondition**: stdout is a json envelope carrying gate ticketKey findings skipped and unverifiable with exit zero
- **Invariant**: skips are not findings

### C009 — amendment-transaction/idempotency

- **Precondition**: the same amendment is applied twice
- **Postcondition**: the second run writes nothing and reports the same digest
- **Invariant**: a no-op amendment is never recorded as a new amendment

### C010 — amendment-transaction/accurate-errors

- **Precondition**: an artifact exists but is unreadable or two candidates match the canonical name
- **Postcondition**: the tool exits one with a named error and writes nothing
- **Invariant**: only absence is a skip while unreadable and ambiguous are failures

### C011 — amendment-transaction/command-additivity

- **Precondition**: the Design Amendment Rule is added to start review and resolve
- **Postcondition**: existing steps numbers arguments and roles remain unchanged
- **Invariant**: the addition is telegraphic and additive only

## Boy Scout Rule

- Split state resolution (design-amendment-state) from transaction orchestration (design-amendment) so each function has one responsibility.
- Name artifact kinds and outcomes as domain constants (ARTIFACT_SPEC, ARTIFACT_RFC, STATE_ABSENT, STATE_PRESENT, OUTCOME_PROMOTED, OUTCOME_SKIPPED) instead of bare strings.
- Function names are verb phrases: resolveArtifactState, snapshotArtifacts, applyAmendment, rebuildHashes, runGateManifest, promoteOrRollback.
- Never swallow an error: a failed owner call becomes a named finding with its rerun route; absence alone becomes a skip.
- Extract the gate list into amendment-gate-manifest.js so it is versioned and enumerated rather than discovered dynamically.
- Existing code touched (package-artifacts, canon-state) keeps its behavior; only call sites are added.
