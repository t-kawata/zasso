# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-401: Accurate completion timestamps for implementation stages and contract/package progress rendering

**Ticket Key**: PX-401 · **Phase**: -1

---

## Background

### Goal
Implementation-stage completion times come from explicit snake_case timestamps written by the scripts that actually change status, and the GIF shows two truthful progress surfaces: a workspace CONTRACTS numerator and a per-package reviewed-ticket bar.

### Purpose
The current renderer reconstructs implementation time from date-only ticket fields, file mtimes or the workspace origin, and it draws a failed attempt as if the stage ran. This ticket replaces those substitutes with the post-schema ISO instants and restricts drawing to completion records.

### Motivation
Gaia has one make history record with status BLOCKED_PREREQUISITE for pkg-0027 at 2026-11-09T01:32:30.357Z. The chronological timeline lets that run move the displayed stage to MAKE even though make progress is zero, so the GIF shows a MAKE frame that never completed. Ticket timestamps are date-only (insert-field-template.js:341 writes YYYY-MM-DD; start-ticket.md and review-ticket.md use date +%Y-%m-%d), CRYSTALIZE-Status.json has no timestamp at all, and a false_positive crime has no resolved_at. The renderer therefore falls back to mtime, detected_at or initialT.

### Constraints
New fields are snake_case and are written only at a real status transition; existing camelCase fields remain for compatibility. No historical MAKE-or-later data is backfilled. The migration scans project data only and never commits external workspaces. The package bar reuses existing ticket data and does not change the frame or snapshot schema. Drawing uses completion records only.

## Acceptance Criteria

- Happy path: status transitions to made, planned, done and reviewed write ISO made_at, planned_at, done_at and reviewed_at; the GIF draws one package bar per cell and a CONTRACTS numerator that grows at reviewed_at; the final frame numerator equals model.totals.reviewed and the denominator equals model.totals.covered.
- Error case: a reviewed ticket without reviewed_at is excluded from the numerator with an evidence warning; an unreadable migration target exits non-zero and writes nothing; a failed status update leaves the ticket unchanged.
- Edge case: a package without Tickets.json renders a 0 percent bar; a workspace with no contract-bearing made ticket shows CONTRACTS: 0/?; a BLOCKED or STARTED run is neither drawn nor allowed to advance the stage; a Tickets.json with zero contracts shows CONTRACTS: 0/0.

## Invariants

- [Normal condition] Every generated stage timestamp is an ISO 8601 instant with time; each status change stamps exactly one snake_case field in the same write as the status.
- [Error invariant] A rejected or failed write leaves Tickets.json and the other target JSON unchanged; a migration dry-run writes nothing and an unreadable target exits non-zero without a partial write.
- [Internal state invariant] Per-package contract accounting uses Sets, never double-counts a shared contract id, and counts boundary contracts once per provider/consumer package; the CONTRACTS numerator never exceeds the denominator.
- [Boundary invariant] Before any contract-bearing ticket has a parseable made_at the title reads CONTRACTS: 0/?; a Tickets.json with zero contracts reads CONTRACTS: 0/0; the final numerator and denominator equal model.totals.reviewed and model.totals.covered.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — stage-timestamps/status-transition

- **Precondition**: a ticket update changes status to made, planned, done or reviewed
- **Postcondition**: update-ticket.js writes made_at, planned_at, done_at or reviewed_at as an ISO 8601 instant in the same write
- **Invariant**: one status change stamps exactly one field and never rewrites an existing value

### C002 — stage-timestamps/idempotency

- **Precondition**: a ticket update does not change status, or repeats the same status
- **Postcondition**: no new timestamp field is written and the existing timestamp field is preserved byte for byte
- **Invariant**: timestamp fields are write-once

### C003 — malfeasance/false-positive

- **Precondition**: malfeasance-update.js changes a crime status to false_positive
- **Postcondition**: resolved_at holds the ISO instant of the terminal transition
- **Invariant**: every terminal crime status, resolved or false_positive, has resolved_at

### C004 — crystalize/completion

- **Precondition**: update-step-status.js starts, ends or fails a CRYSTALIZE step
- **Postcondition**: updated_at is written on every update and completed_at is written when the final step completes
- **Invariant**: CRYSTALIZE-Status.json always carries an ISO updated_at after the first write

### C005 — timeline/completion-only

- **Precondition**: the history contains a STARTED, BLOCKED_PREREQUISITE or REPAIR_NO_PROGRESS run
- **Postcondition**: the run is absent from frame.runs, draws no ring, and cannot change frame.stage
- **Invariant**: only COMPLETE finish runs affect the displayed stage

### C006 — timeline/explicit-completion

- **Precondition**: a MAKE, PLAN, START, REVIEW or RESOLVE event has no explicit completion instant
- **Postcondition**: no event is emitted and no initialT, mtime or detected_at substitute is used
- **Invariant**: an implementation stage is drawn only from its own completion field

### C007 — layout/package-bar

- **Precondition**: computeLayout lays out package cells
- **Postcondition**: every cell carries barX, barY, barWidth and barHeight scaled by layout.scale, with one shared width
- **Invariant**: the bar stays inside the cell, below the maximum flash ring and above the label band

### C008 — title/contracts-daily

- **Precondition**: the model carries tickets with made_at, reviewed_at and contract ids
- **Postcondition**: frame.titleParts.right starts with CONTRACTS: n/d where n counts reviewed ticket contract ids at frame.t and d counts made ticket contract ids
- **Invariant**: n never exceeds d; with no contract-bearing made ticket the segment is CONTRACTS: 0/?; the final values equal model.totals.reviewed and model.totals.covered

### C009 — migration/idempotent-dry-run

- **Precondition**: migrate-stage-timestamps.js runs with --dry-run or on an already migrated workspace
- **Postcondition**: it reports the planned changes or no changes, writes nothing in dry-run, and a second apply writes nothing
- **Invariant**: only project data JSON is scanned; .claude, tests and node_modules are never written

### C010 — sync/installed-copies

- **Precondition**: the package source scripts are updated
- **Postcondition**: the root .claude and crates/siprs/.claude copies are byte-identical to the package source
- **Invariant**: no installed copy lags the source
