# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-402: Contiguous ticket identities: renumber after every merge and rewrite all references without dangling keys

**Ticket Key**: PX-402 · **Phase**: -1

---

## Background

### Goal
Make every ticket id dense inside its phase after phase consolidation, condensation and workspace condensation, and prove that every live ticket reference in Tickets.json and every generated artifact is rewritten to the new id in the same operation so no reference dangles.

### Purpose
Condensation merges a contiguous group into its first member and keeps that survivor key. Absorbed ids leave holes: measured on 2026-11-10, gaia has 30 of 58 phases gapped, crystal 20 of 24 and doors 8 of 8, with 550 live tickets over 813 original ids. The holes make `P0-3` look like the third ticket when the phase may hold only two. Dense ids restore a one-to-one reading between a phase's order and its keys.

### Motivation
The user selected option A: contiguous ids with a one-shot repair of the existing workspaces. The current scripts already renumber during phase consolidation (`consolidate-phase-tickets.js` `renumberTicketIds`) but remap only `prerequisites[].ticket` and `distribution.units[].obligation.implementerTicketKey`; prose fields and `changes`/`condensedFrom` are left alone, and 272/191/57 live-field key tokens in gaia/crystal/doors already name keys that no longer exist. A repair that only closes numeric holes would preserve those dangling references.

### Constraints
- Backward compatible: `validateTickets` must accept existing documents until each package is repaired; density is enforced by a new opt-in gate.
- No re-condensation: the repair command renumbers and rewrites references only; it never changes the merge partition.
- Atomic and reversible: archive before write, restore on any gate failure.
- Idempotent: a repaired document writes zero bytes on a second run.
- The PX phase (`phaseId === -1`) is excluded by default because `[::TICKET::] PX-N` source annotations are tied to its ids.
- Historical provenance must stay truthful: `changes` and `condensedFrom` keep the pre-renumber keys, stamped with a generation, and a document-level alias table resolves them. Rewriting history to the new key would make the record false.

### Measured state
- 60 Tickets.json documents, 90 phases, 550 live tickets, 263 absorbed ids, 813 original ids. Every phase satisfies `liveIds union condensedFrom.tickets[].id = 1..N`, so an order-preserving dense map is derivable without guessing.
- 58 of 90 phases are gapped. All 550 tickets are `todo`; there are no done or reviewed ids to protect today.
- Live fields already contain 272 (gaia), 191 (crystal) and 57 (doors) key tokens that name no live ticket. 146/85/38 of them resolve through the current ledger; 28/17/6 distinct keys do not, because `consolidate-phase-tickets.js` renumbered phases and tickets but rewrote only prerequisites and distribution obligations.

### Code evidence
- `lib/ticket-partition.js:296` `remapTicketReferences` replaces keys sequentially. With a permutation `{P0-1 -> P0-2, P0-2 -> P0-3}` the input `P0-1, P0-2` becomes `P0-3, P0-3`; dense renumbering is a permutation, so this function cannot be reused unchanged.
- `lib/ticket-partition.js:499` overwrites `merged.condensedFrom` with the current group only, and `collectPreservedRecord` excludes `condensedFrom`; a survivor that already carries a ledger loses earlier absorbed keys when it is merged again.
- `condense-tickets.js:631` returns NO_CHANGE when `totalBefore === totalAfter`, so a renumber-only migration would never run.
- `consolidate-phase-tickets.js:377` `remapTicketKeyReferences` handles only `prerequisites[].ticket` and `distribution.units[].obligation.implementerTicketKey`.
- `restore-condensed-tickets.js` matches archive tickets by `condensedFrom.tickets[].key`; rewriting those keys would break restore, so they must stay historical and generation-qualified.
- `add-tickets-for-phase.js:1617` builds `distribution.ticketDigests` from `ticketIdentity(ticket)`; `verify-all-ticket-coverage.js` and `verify-chain.mjs` recompute the same digest, so the aggregate must be rebuilt after renumbering.
- `verify-implementation-order.mjs --write` regenerates `IMPLEMENTATION-ORDER.json` for a package and `WORKSPACIFY-IMPLEMENTATION-ORDER.json` for a workspace; the file contains `tickets[].ticket` and `prerequisites[].ticket`.

- `WORKSPACIFY-IMPLEMENTATION-ORDER.json` contains no ticket keys; `RFC-SPLIT-Status.json` and `Status.json` contain none.

## Acceptance Criteria

- **[Happy path]** Running `normalize-ticket-ids.js --workspace=<root> --apply` on gaia, crystal and doors leaves every non-excluded phase with ids 1..N, zero live-field key tokens that name a non-live ticket, a document-level `identity.generation` and an alias entry for every historical key, and a second run prints `NO_CHANGE` and writes zero bytes.
- **[Error case]** A live reference names a key that neither the ledger nor any supplied archive resolves; the apply prints `IDENTITY_HISTORY_UNRESOLVED` with the document, JSON path and key, exits 1, restores the pre-apply archive, and leaves `Tickets.json` byte-identical.
- **[Edge case]** A phase whose old ids are a nontrivial permutation (for example live [1,3,5] mapping to [1,2,3]) rewrites `P0-3` to `P0-2` and `P0-5` to `P0-3` in one pass, never `P0-5` to `P0-3` through the intermediate `P0-2`; `changes` and `condensedFrom` keep the old keys stamped `generation` 0 and render as `P0-5@g0`, while the live section renders `P0-3`.

## Invariants

- [Normal condition] In every non-excluded phase, live ticket ids are exactly 1..N in implementation-array order after consolidation, condensation or repair, with no duplicate key.
- [Error invariant] If any live reference cannot be resolved to a current key, the operation fails with a named finding and restores the pre-apply archive; it never writes a document with a dangling live key.
- [Internal state invariant] `identity.generation` increments by exactly one per effective renumber and never changes on a no-op; `identity.aliases` maps every historical `key@generation` to a current key and never contains a value that is not live.
- [Boundary invariant] The PX phase and every phase named in `identity.excludedPhases` keep their ids and references byte-identical; a phase with one ticket is dense as [1] and is not touched.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — ticket array in implementation order -> dense per-phase identity

- **Precondition**: Each non-excluded phase holds tickets with unique integer ids >= 1, and each ticket carries condensedFrom.tickets[].id for every id it absorbed.
- **Postcondition**: After renumbering, the live ids of the phase are exactly 1..N in implementation-array order, and every absorbed id maps to the same new id as its survivor.
- **Invariant**: The map is total and order-preserving: no live ticket is dropped, duplicated or reordered, and the union of live and absorbed old ids is 1..N.

### C002 — old key map -> every live string field

- **Precondition**: A live field may contain a ticket key token that names an old live key or an absorbed key.
- **Postcondition**: Every such token is replaced exactly once by the current key of the ticket that owns it, in title, background, notes, scope, invariants, instrumentation, investigation, boyScoutPlan, tests, acceptance criteria, unlistedFileReason, prerequisites[].ticket, origin.sourceTicket and distribution obligations.
- **Invariant**: Replacement is single-pass: a key produced by the replacement is never re-examined, so a permutation cannot chain; a token with no owner is a named finding and blocks the write.

### C003 — renumber -> historical provenance

- **Precondition**: changes and condensedFrom carry keys from the generation before the renumber.
- **Postcondition**: Each historical object is stamped with that pre-renumber generation, the document identity.generation becomes that value plus one, and identity.aliases maps every historical key at its generation to a current live key.
- **Invariant**: Historical key strings are never rewritten, every historical key resolves through the alias table, and every alias value is a live key.

### C004 — renumber -> derived fields and generated artifacts

- **Precondition**: A package may carry relatedTicketIds, prerequisites, distribution units and the ticket-digest aggregate; a workspace may carry IMPLEMENTATION-ORDER.json.
- **Postcondition**: After renumbering, relatedTicketIds, prerequisites[].ticket, distribution.units[].obligation.implementerTicketKey/implementerTicketId and distribution.ticketDigests use current keys, and verify-implementation-order --write emits current keys.
- **Invariant**: No derived field keeps a key that is not live, and no digest is computed over an old key set.

### C005 — apply -> archive and atomic write

- **Precondition**: The document is writable and a renumber plan exists.
- **Postcondition**: The pre-apply bytes are archived as Tickets.pre-renumber-<stamp>.json before the atomic write; any failing gate restores the archive; a no-change run writes zero bytes and does not increment the generation.
- **Invariant**: The write is all-or-nothing and idempotent; the second identical apply is byte-identical.

### C006 — excluded phase guard

- **Precondition**: identity.excludedPhases names phases that must keep their identity, and the default contains the PX phase -1.
- **Postcondition**: Excluded phases keep their ids, keys and references byte-identical; their keys are absent from identity.aliases.
- **Invariant**: A renumber never touches an excluded phase, and --include-px is refused unless an explicit annotation-update path is present.

### C007 — dangling live key -> ledger and archive resolution

- **Precondition**: A live reference names a key that is absent from the current live set but may appear in condensedFrom.tickets[] or in a pre-consolidation archive.
- **Postcondition**: The key resolves through the accumulated ledger, or through the nodeIds of a supplied archive to the unique current ticket that owns them; otherwise the apply fails with IDENTITY_HISTORY_UNRESOLVED or IDENTITY_ARCHIVE_AMBIGUOUS.
- **Invariant**: No live dangling reference is silently accepted, and an ambiguous archive mapping is never guessed.

## Boy Scout Rule

- Extract the single-pass key replacer and the dense-map builder into `lib/ticket-identity-renumber.js`, one responsibility per function: `buildDenseRenumberMap`, `buildAliasTable`, `remapLiveReferences`, `stampHistoricalGeneration`, `validateIdentity`.
- Name every boundary: `PX_PHASE_ID`, `DEFAULT_EXCLUDED_PHASES`, `KEY_TOKEN_PATTERN`, `HISTORICAL_FIELDS`, `GENERATION_FIELD`, `ALIASES_FIELD`, `DENSE_FIRST_ID`.
- Replace the sequential `remapTicketReferences` with a single regex pass whose replacer looks up the original token; this is both the correctness fix and the translatability fix, because the function then reads as one sentence: replace each old key once with the key that owns it.
- Remove field-by-field remap tables in favor of an explicit historical-field skip set, so a future ticket field cannot be forgotten.
- Fail loudly: every unresolved live key and every ambiguous archive mapping becomes a named finding, never a silent skip.
- In touched functions, replace generic names (`value`, `entry`) with domain names (`ticketKey`, `historicalRecord`, `liveReferencePath`) where the surrounding code allows it.

### Exceptions

- Exception entry: git commit messages and branch names that contain old ticket keys.
- Item: historical git commit messages and branch names.
- Reason: cannot test an immutable external history: rewriting it would change every commit hash, and the content is an external manual artifact rather than code under test. This is an external-history constraint, not a design defect.
- Alternative verification: the `identity.aliases` table and the generation stamp make the old key resolvable, and a manual audit of commit messages is possible; no source file in the three workspaces carries a ticket key, so there is no code-level reference to test.
- Exception entry: existing `Tickets.pre-condense-*` and `Tickets.pre-evolve-*` archives.
- Item: the bytes of pre-existing archive files.
- Reason: cannot test a rewrite that must not happen: they are the recovery source for `restore-condensed-tickets.js`, and rewriting an archive would destroy the only pre-merge copy and break restore. This is an external immutable-artifact constraint, not a design defect.
- Alternative verification: archives are treated as generation 0, read through the alias table, and exercised by the restore integration test; the repair deliberately never writes them.
- Exception entry: the PX phase and any future phase whose source files carry `[::TICKET::]` annotations.
- Item: source annotations that name a ticket id outside Tickets.json.
- Reason: cannot test an annotation update without coupling it to a source-tree write: the annotation is a source-code reference to the numeric id, and renumbering without rewriting the source would create a live dangling reference outside Tickets.json.
