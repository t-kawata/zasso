# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-403: 5-layer workspace execution: safe implementation order, strict ticket/phase order, package selection, and fail-stop escalation

**Ticket Key**: PX-403 · **Phase**: -1

## Background

### Goal
Make conver.js run at a workspacify workspace root and drive every package directory in the safe implementation order, one ticket at a time, with the package directory as cwd, and with the next command derived from Tickets.json immediately before every execution.

### Purpose
The current loop is a 4-layer implementation: it reads a single Tickets.json from the current directory and never changes cwd (src/runner.ts:657-676). The workspacify layer is now the unit of execution: the workspace root owns WORKSPACIFY-TREE-MANIFEST.json, WORKSPACIFY-ALLOCATE-MANIFEST.json and WORKSPACIFY-IMPLEMENTATION-ORDER.json, and every package has its own Tickets.json. conver must realize the inner four loops per package, in the order the order tool proves safe.

### Motivation
The user requires full 5-layer support with no 4-layer backward compatibility. gaia, crystal and doors all have the root manifests and a Tickets.json in every package; the workspace root must become the only valid entry point. The user also requires strict sequencing: no ticket may be skipped, no phase may be entered out of order, consolidate/find may run only after every ticket in the package is reviewed, and a repeated command must escalate three times and then stop conver.

### Constraints
- Implementation target is tools/conver only. gaia, crystal and doors are read-only; the user applies the no-argument /find-omissions change and any deployment manually.
- Do not add display/TUI code or dependencies; that is PX-404.
- Do not edit the /find-omissions command or its scripts in .claude; conver changes its call to /find-omissions with no arguments, matching the user's manual command update.
- No backward compatibility for -t/--tickets or single-directory execution.
- Every command must run with cwd equal to the package directory, including make, plan, start, review, resolve, epush, consolidate and find.
- The implementation order must be the one .claude/scripts/workspacify-order/run.mjs displays; read it from WORKSPACIFY-IMPLEMENTATION-ORDER.json after the tool validates it, and never invent an order.
- Package selection is by partial name and must be unique; a selection that would leave an earlier pending package unselected is a startup error.
- Top-level intervalMinutes only; watcher filters have no per-filter interval.
- Session-connection retry stays; the supervisor-based completion loop is removed and replaced by the escalation rule.
- Real workspaces are never written by tests.

## Invariants

- [Normal condition] Packages are processed in the implementation order read from WORKSPACIFY-IMPLEMENTATION-ORDER.json after run.mjs validates it; within a package, tickets are selected in Tickets.json array order and only the first non-terminal ticket is eligible.
- [Error invariant] A missing or unreadable Tickets.json, an unknown status, or remanded status stops the package with a named error and sends no command; no fallback status is guessed.
- [Internal state invariant] The command-history singleton holds at most ten executions; the escalation counter for a ticket is 0..3 and resets as soon as the status advances or the ticket changes.
- [Boundary invariant] consolidate and find run only when every ticket in the package is reviewed or round-terminal; find additions continue in the same package and the fourth find round stops with Slack.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — workspace root -> package model

- **Precondition**: cwd contains WORKSPACIFY-TREE-MANIFEST.json, WORKSPACIFY-ALLOCATE-MANIFEST.json and WORKSPACIFY-IMPLEMENTATION-ORDER.json and every package has Tickets.json

- **Invariant**: no later ticket is selected while an earlier ticket is non-terminal

- **Precondition**: a package directory is selected
- **Postcondition**: every session and command runs with cwd equal to that package directory
- **Invariant**: the previous cwd is restored after the package finishes or throws

### C004 — repeated execution -> stop

- **Precondition**: the same ticket and command appear in the last ten executions and status did not advance
- **Postcondition**: three stronger English prompts are sent and then conver stops
- **Invariant**: at most three escalations occur and a Slack stop message is sent before exit

### C005 — all tickets terminal -> consolidate and find

- **Precondition**: every ticket in the package Tickets.json is reviewed or round-terminal
- **Postcondition**: consolidate runs before find and find additions continue in the same package
- **Invariant**: consolidate or find never runs while any ticket is non-terminal
