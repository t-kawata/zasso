# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-408: Stream agent thoughts inline and recolor header status symbols

**Ticket Key**: PX-408 · **Phase**: -1

---

## Background

### Goal
Render each agent thought as one continuously growing, dim line prefixed once with ∴, and render the four header status symbols _ | / x in #d32f2f instead of cyan.

### Purpose
Token-per-line output is unreadable: one thought becomes a column of one-word lines. The status symbols currently share the cyan accent, so they do not read as status markers.

### Motivation
Observed in a real run of `node .claude/scripts/conver/conver.js -c 1 -n 1 ...`: the terminal showed `∴ Let`, `∴ me`, `∴ instead`, ... for a single thought. Reproduction against the built renderer with nine token chunks emitted "∴ Let\n∴  me\n∴  instead\n∴  use\n∴  node\n∴  to\n∴  write\n∴  a\n∴  compact\n".

### Constraints
- The dashboard owns rows 1..N through DECSTBM and saves/restores the cursor on every redraw (src/progress/dashboard.ts:231-243); a write must never leave the cursor in the terminal's pending-wrap state at the last column.
- Agent text is untrusted at the renderer boundary: escape sequences must be sanitized even when split across chunks (src/display/terminal-text.ts:28-35).
- Message chunks stay buffered per turn so markdown code fences and lists survive chunking (specs/PX-404.md:78).
- Non-TTY output is unchanged; the success path adds no runtime log.
- `string-width` becomes a direct dependency; it is already present transitively as wrap-ansi's 8.3.0 (engines node >=20).

## Investigation

Evidence gathered from the current source:

1. Thought rendering defect. src/display/renderer.ts:68-70 handles kind 'thought' by calling #writeLines([`∴ ${event.text}`]) on every event. #writeLines (src/display/renderer.ts:166-172) appends a newline and sanitizes each line. src/display/events.ts:80-81 maps every agent_thought_chunk to { kind:'thought', text }. src/session.ts:384-393 forwards every session_update to display.onUpdate, so token-sized chunks reach the renderer. Reproduction against dist/display/renderer.js with nine token chunks produced exactly: "∴ Let\n∴  me\n∴  instead\n∴  use\n∴  node\n∴  to\n∴  write\n∴  a\n∴  compact\n".

2. Message path is intentionally different. src/display/renderer.ts:25, 65-67, 114-119 buffer message chunks and flush them before a non-message event or on flush(); src/display/renderer.ts:121-131 renders the whole turn through marked/marked-terminal so code fences survive chunking. specs/PX-404.md:78 states this requirement. The fix must not change this path.

3. Fixed header and cursor safety. src/progress/dashboard.ts:231-243 writes SAVE_CURSOR, absolute header rows, then RESTORE_CURSOR. A mid-line cursor is preserved by DECSC/DECRC, but a write that lands in the terminal's last column leaves a pending-wrap state; restoring the cursor can then overwrite the final cell in common emulators. src/display/terminal-text.ts:9-25 documents the fixed-header threat model, and the renderer's sanitizer exists because agent and tool text are untrusted.

4. Split escape leakage. sanitizeTerminalText (src/display/terminal-text.ts:28-35) applies CSI_PATTERN per call. Measured: sanitize('\x1b[3') + sanitize('1mred') = '31mred', while sanitize('\x1b[31mred') keeps the SGR. A streaming writer therefore needs to carry a trailing incomplete escape instead of sanitizing each chunk independently.

5. Lifecycle gaps. src/conver.ts:186-194 constructs DisplayRenderer with process.stdout.columns; src/conver.ts:213 defines onResize as dashboard.handleResize() only, so the renderer never learns the new width; src/conver.ts:215-220 shutdown() stops the dashboard without renderer.flush(), and the Ctrl-C keypress path calls shutdown directly, so an open line would run into the shell prompt. src/session.ts:397-400 already flushes the renderer in the runCommand finally block for normal completion.

6. Header symbol colors. src/progress/model.ts:118-132 maps reviewed to 'x', made to '_', planned to '|', done to '/', todo to its number and unknown to '?'. src/progress/layout.ts:20-24 defines HEADER_BACKGROUND #0b1f3a and PALE_YELLOW #f5e6a8; src/progress/layout.ts:37-43 colors numeric symbols with chalk.white and every other symbol with chalk.cyan. src/progress/layout.test.ts:215-244 asserts the cyan SGR ESC[36m directly.

7. Width measurement. package.json declares wrap-ansi ^10.0.2; node_modules/wrap-ansi/node_modules/string-width is 8.3.0 (engines node >=20). Measured stringWidth('∴ ') = 2, 'あ' = 2, 'a' = 1, '🙂' = 2, and ANSI sequences are ignored. chalk.hex('#d32f2f') at level 3 emits ESC[38;2;211;47;47m; at level 1 it downgrades to ESC[31m. #d32f2f has a 3.32:1 contrast ratio against #0b1f3a, above the 3:1 large-text threshold and visibly darker than #ff0000 (4.13:1).

8. Test surfaces. src/display/renderer.test.ts:9-17 captures chunks with a string[] sink; src/progress/layout.test.ts:86-97 asserts ANSI-stripped equality; src/conver.test.ts:190-225 mocks process.exit and streams, and main() runs with a non-TTY stdout in tests. A testable lifecycle factory is therefore needed to assert flush-before-stop and resize ordering deterministically.

## Acceptance Criteria

- **Happy path** — a thought stream arrives as token chunks and the terminal shows one continuously growing dim line with a single ∴ prefix; the header renders _ | / x in #d32f2f.
- **Error case** — an escape sequence split across two chunks never appears as visible text such as `31m`; Ctrl-C with an open thought line flushes it so the shell prompt starts at column 0.
- **Edge case** — at width 20 no line occupies the last column; resize closes the open line and adopts the new width; todo numbers stay white and unknown-status `?` stays cyan.

## Invariants

- [Normal condition] Every agent_thought_chunk appends to the open thought line; the line is closed only by a non-thought event, flush(), resize(), or process shutdown, and the next output starts at column 0.
- [Error invariant] No incomplete escape sequence and no cursor-movement CSI reaches the terminal; the sanitizer carry is bounded by MAX_ESCAPE_CARRY (256) and discarded when exceeded. The renderer never throws into the execution loop.
- [Internal state invariant] ThoughtLineWriter holds at most one open line; close() is idempotent; the writer never writes into the terminal's last column and never emits a newline for an empty line.
- [Boundary invariant] Visible line width is at most width-1 cells with string-width accounting (wide characters count as two); message buffering, non-TTY output, and ANSI-stripped header text are unchanged.
