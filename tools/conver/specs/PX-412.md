# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

- [Goal] Turn the six implementation packets produced by the law research into normative rules, policy files, templates, detectors, and a gate that forces the same adapter implementation method in every project.
- [Purpose] The current law states behavioral obligations but does not force crate selection, feature sets, API call order, template use, or test shape. This ticket adds the missing implementation-contract layer so the law can verify how an adapter is built, not only what it returns.
- [Motivation] The same AI using make -> plan -> start -> review -> resolve must produce REST, WebSocket, CLI, gRPC, MCP, and A2A adapters with the same architecture, the same dispatcher and verifier wiring, the same forbidden-pattern discipline, and the same test shape. MCP must support stateless profiles and both JSON and SSE responses; A2A must support send and stream through one shared executor with external task state.
- [Constraints] No hand-authored project profile or workspace map. No hand-edited atoms, lock, coverage, or OKF artifacts. No rule text in SKILL.md. No weakening of existing rules. No project names, ticket IDs, or Japanese text in the skill tree. TDD Red-Green-Refactor is mandatory. Implementation skeletons must stay outside context delivery so token cost does not grow with template size.
- [Input] RESEARCH001, RESEARCH002, and RESEARCH003 are research inputs, not proofs. RESEARCH003 labels its skeletons NOT-COMPILED; this ticket converts them into law contracts and templates without recording unexecuted checks as machine_verified.

## Investigation

- Evidence source: RESEARCH001, RESEARCH002, RESEARCH003, the existing `docs/archive/IMPLEMENTATION-SPEC` set, and the current `rust-interface-law` runtime.
- `scripts/lib/gate.mjs` currently treats a registered `scan/<id>` as machine_verified without executing it; this is a false-pass path that must be replaced by detector execution.
- `scripts/lib/scaffold.mjs` validates rule annotations, incomplete markers, secrets, and canonical placeholder crates, but it has no template catalog, placeholder value resolution, merge-required report, or generated equality check.
- `scripts/lib/explain.mjs` maps a rule prefix to a source document and shows code-block examples, but it does not show an effective pin, template path, detector, or implementation test.
- `scripts/commands.mjs` resolves units and phases but has no implementation profile, no effective-policy identity, and no `implementation-check` or `template` command. `renderOkf` maps phases from rule prefixes and source file names; IMP and source document 55 need explicit mapping.
- `scripts/ingest.mjs` has a fixed 18-document source list; a new 55 document must be added and the manifest regenerated.
- `install.js` copies `dist`, `okf`, and `source` but not `templates`; installed skills would not resolve template paths.
- `source/skill-registry.toml` currently holds SK-01..SK-08; implementation-contract invariants are not represented.
- Existing tests cover atom lock, redaction, generic boundary, runtime, integration, bootstrap, scaffold, context phases, render, and applicability; implementation policy, metadata, detector execution, template reconciliation, law identity, and pipeline checkpoints have no tests.
- RESEARCH003 provides six implementation packets with recommended pins, Cargo snippets, NOT-COMPILED skeletons, forbidden patterns, detectors, tests, and skill integration responsibilities. It does not provide compiled evidence; the plan must preserve that distinction.

## Acceptance Criteria

- Happy path: all six interfaces have normative implementation rules, Cargo contracts, API sequences, forbidden patterns, templates, detectors, and tests; implementation-check passes the fixture and gate blocks a missing implementation report.
- Error case: forbidden dependency, forbidden source pattern, unresolved placeholder, missing template, missing report, and law hash mismatch each fail closed with a named finding and a stable exit code.
- Edge case: a compatible project version override is accepted; an incompatible pin fails; an existing file without a marker becomes merge-required and is not written; template bodies never appear in context delivery.

## Invariants

- [Normal establishment] The effective policy is resolved from the skill baseline and the project manifest; every required pin, feature, forbidden edge, template, detector, and test is present before implementation can become machine_verified.
- [Error invariant] A missing implementation report, missing test, zero selected tests, failed detector, unresolved placeholder, missing template, forbidden dependency, or law hash mismatch never becomes a pass.
- [Internal state invariant] Manifest, atoms lock, coverage, OKF nodes, and dist are generated only from the authoritative spec sources; rule registry and rule atoms remain bijective; no generated artifact is hand-edited.
- [Boundary invariant] Gate accepts only a manifest whose spec_version, dist hash, and policy hash match the installed law and project state, unless a scoped and expiring exception exists; every pipeline checkpoint remains at most five lines via a wrapper.

- **Precondition**: A manifest closure and an implementation report exist.
- **Postcondition**: Each IMP rule becomes machine_verified only when every check passes.
- **Invariant**: A missing report, missing test, zero selected tests, or failed detector never becomes a pass.

### C004 — resolve -> manifest law identity

- **Precondition**: The manifest carries spec_version, dist_sha256, and policy_sha256.
- **Postcondition**: Gate compares the manifest identity with the installed skill and project policy state.
- **Invariant**: A mismatch fails unless a scoped, expiring exception exists.

### C005 — pipeline command checkpoints -> law commands

- **Precondition**: The make, plan, start, review, and resolve checkpoints are installed.
- **Postcondition**: Template, implementation-check, gate, and attest are invoked in order.
- **Invariant**: No completion occurs without gate and attest; each checkpoint remains at most five lines via a wrapper.

## Boy Scout Rule

- Extract policy resolution, metadata inspection, detector execution, template rendering, and gate merging into single-responsibility modules with verb-phrase function names.
- Replace hardcoded phase and prefix maps in `scripts/commands.mjs` with named constants shared by the new implementation modules.
- Rename generic helpers such as `writeAtomic` duplicates into a shared script utility only if the extraction does not create a circular dependency; otherwise keep local helpers and document the boundary.
- Ensure every error is propagated with a named finding; no swallowed detector or metadata error.
- Split long command handlers so `implementation-check` and `template` each have one responsibility and return a stable report.
- Add tests before implementation for every new module and extend existing tests rather than duplicating fixtures.
