# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-413: Persist package boundary completion and terminate the watcher at the endpoint

**Ticket Key**: PX-413 · **Phase**: -1

---

## Background

### Goal
Skip /consolidate-stubs and /find-omissions on a package whose ticket set already completed the boundary, persist the boundary completion so the decision survives a process restart, advance to the next package, and terminate the watcher when every selected package is at its endpoint.

### Purpose
The watcher must derive the next action from durable package state, not from an in-memory PackageProgress that every cron tick recreates. A package boundary is a once-per-ticket-set event, not a per-tick event.

### Motivation
The 2026-11-12 overnight run on crystal-adapter-current-authority completed P3-1 at 01:41 JST and then executed the boundary 37/38 times until 08:42 JST: 37 consolidate starts, 38 find completions, 34 blocked preflight records, Tickets.json round 3 to 41, 80 omission artifacts, and commit v0.0.200 with 156 files and 453,268 insertions. runPackageLoop recreated the progress state on every tick, resolvePackageSelection never filtered packages with no pending tickets, and the watcher waited for SIGINT/SIGTERM forever.

### Constraints
Single-process execution is assumed; concurrent conver instances are out of scope. Resolve cadence stays -r N. /find-omissions non-idempotency is accepted, so a missing or stale record reruns the boundary once rather than risking a false skip. The ticket status vocabulary is unchanged. TDD Red-Green-Refactor is mandatory. No new runtime dependency.

## Acceptance Criteria

- **[Happy path]** A package whose tickets are all terminal and whose boundary state is COMPLETE with a matching digest executes no consolidate or find command on every later watcher tick; the loop advances to the next package; when every selected package is endpoint the watcher exits 0.
- **[Error case]** A corrupt, missing, or partially written boundary state is treated as no record: the boundary runs once, writes a valid COMPLETE document, and the next tick skips; a find failure records no COMPLETE find, sends no boundary Slack message, and uses the existing stop notification.
- **[Edge case]** A review after a COMPLETE boundary invalidates it; a find-added ticket with forNextRound set is processed in the same package and triggers a new boundary; a restart between the final review and the boundary still runs the final resolve and the boundary; the boundary message renders both times in the watcher timezone.

## Invariants

- [Normal condition] A package is skipped only when every ticket is terminal, the boundary state digest equals the digest of the current Tickets.json, consolidate and find are both COMPLETE, and no resolve is pending.
- [Error invariant] A missing, corrupt, version-mismatched, or partially written boundary state is treated as no record; the boundary runs again instead of being skipped, and no operator-visible failure is silently converted into a skip.
- [Internal state invariant] The boundary state is replaced atomically (temporary file plus rename); a reader sees either the previous valid document or the new valid document, never a partial one.
- [Boundary invariant] A terminal review after a COMPLETE boundary invalidates that boundary: lastReviewedAt becomes newer than both finishedAt values and the digest changes, so isPackageEndpoint returns false until the boundary runs again.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — step:endpoint-skip

- **Precondition**: Tickets.json is parsed, the package boundary state is read, and every ticket is terminal with no pending resolve.
- **Postcondition**: The package loop executes zero commands and does not rewrite Tickets.json.
- **Invariant**: The endpoint predicate requires a matching ticket-set digest and COMPLETE consolidate and find records.

### C002 — step:boundary-record

- **Precondition**: The consolidate command and the find command have both returned.
- **Postcondition**: The boundary state file stores COMPLETE statuses, finishedAt values, the last reviewed ticket key, and the post-find ticket-set digest.
- **Invariant**: An atomic write leaves either the previous valid document or the new valid document readable.

### C003 — step:watcher-exit

- **Precondition**: Every selected package satisfies the endpoint predicate, or no selected package has pending work.
- **Postcondition**: The scheduler stops and the process exits with code 0.
- **Invariant**: The LoopStoppedError path and the Slack stop message are never used for a normal endpoint exit.

### C004 — step:boundary-notification

- **Precondition**: The consolidate and find commands completed and the boundary state was written.
- **Postcondition**: Exactly one Slack message reports both finish times, the last reviewed ticket key, and the added ticket count.
- **Invariant**: No boundary message is sent when the boundary is skipped or when either command fails.

### C005 — step:review-tracking

- **Precondition**: A ticket transitions to a terminal status during the package loop.
- **Postcondition**: lastReviewedTicketKey and lastReviewedAt are updated, reviewedSinceResolve increments, and the prior boundary record is invalidated.
- **Invariant**: A stale digest or a stale COMPLETE boundary can never satisfy the endpoint predicate after a later review.

### C006 — step:find-added-tickets

- **Precondition**: The find command adds at least one ticket, including a ticket marked forNextRound.
- **Postcondition**: The loop continues in the same package and reruns the boundary after every added ticket is terminal.
- **Invariant**: A non-terminal forNextRound ticket is not treated as absent.

## Boy Scout Rule

- New tools/conver/src/boundary-state.ts owns the durable record and the endpoint predicate. Functions are verb phrases: readBoundaryState, writeBoundaryState, computeTicketSetDigest, isTicketSetTerminal, isPackageEndpoint, markReviewed, markResolved, markBoundaryStarted, markBoundaryCompleted.
- Domain names replace generic ones: ticketSetDigest, lastReviewedTicketKey, lastReviewedAt, reviewedSinceResolve, addedTicketKeys; no data/info/tmp.
- One responsibility per function: the digest, the transition helpers, the predicate, and the atomic writer are separate; the runner only calls them in order.
- Named constants: BOUNDARY_STATE_FILE, BOUNDARY_STATE_VERSION, BOUNDARY_STATUS_IN_PROGRESS, BOUNDARY_STATUS_COMPLETE.
- No swallowed errors: state read failures log a warning and return null; state write failures propagate; the existing Slack non-fatal policy is unchanged.
- Extract formatClockTime and buildBoundaryMessage as pure, testable functions.
- Touched code in runner.ts and conver.ts is split so the call sequence reads as prose: read state, decide endpoint, run package, record review, run boundary, record completion, notify, decide exit.
