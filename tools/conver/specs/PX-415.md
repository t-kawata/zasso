# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Purpose
Condensation is a state transformation. It must reduce work without changing completed ticket meaning, losing provenance, or invalidating the surfaces the omission convergence gate measures.

## Acceptance Criteria

- [Happy path] A package with todo, planned, R1, and reviewed tickets condenses only contiguous todo groups; every non-todo field is byte-identical; the survivor ledger is lossless; find-omissions condense and rebase pass; the second run is NO_CHANGE.
- [Error case] A group containing R2 or planned is refused; duplicate formula id with different content is refused; a marker referencing an absorbed key resolves through aliases or is rewritten; a non-existent marker key still fails consolidate-stubs-gate.
- [Edge case] A package with one todo ticket, no omissions, no archives, a cloned ledger sharing an absorbed key, or a report-only omission target completes without writing or with the expected no-op.
- [Convergence case] After find-omissions condense and rebase, the post-rebase gap-scan digest equals the convergence digest, unrecorded obligations are zero, no duplicate omission ticket is created, and the next find Step 0 does not raise CONVERGENCE_NOT_REACHED.

## Invariants

- [Normal establishment] A merge group contains only tickets whose status is todo; the survivor status is todo; the group is contiguous in implementation order and within the work budget.
- [Invariant on error] A group containing made, planned, done, reviewed, remanded, R<n>, or an unknown status is never merged; mergeTicketGroup refuses it with a typed error and writes nothing.
- [Internal state invariant] Every absorbed key resolves to exactly one survivor through condensedFrom and identity.aliases; a shared historical key owned by cloned ledgers resolves to its originKey survivor and never raises IDENTITY_DUPLICATE_KEY.
- [Boundary invariant] Every authored field of an absorbed ticket, including nested condensedFrom, changes, splitReason, round, contracts, and formulaObligations, is retrievable from the survivor ledger after any number of condensation generations.
- [Convergence invariant] After condense, OMISSION-GAP-SCAN, OMISSION-JUDGMENT-LEDGER, OMISSION-TICKET-INDEX, OMISSION-CONVERGENCE, and OMISSIONS-*.json describe the post-condense ticket set; no unrecorded obligation and no duplicate omission ticket remain.
- [Boundary invariant] find-omissions returns only after condense and rebase gates pass; the boundary digest recorded by conver equals computeTicketSetDigest of the post-condense Tickets.json.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — condense partition policy -> mergeable ticket group

- **Precondition**: The input phase contains tickets with statuses todo, made, planned, done, reviewed, remanded, R1, and R2.
- **Postcondition**: Only a contiguous all-todo group merges; every non-todo ticket is a singleton; the survivor status is todo.
- **Invariant**: No non-todo ticket's status, round, timestamps, or authored fields change; no completed ticket is absorbed.

### C002 — absorbed ticket -> condensedFrom ledger record

- **Precondition**: An absorbed ticket carries nested condensedFrom, changes, splitReason, round, contracts, and formulaObligations.
- **Postcondition**: The survivor ledger record contains every authored field and the recursive nested history.
- **Invariant**: The record deep-equals the pre-merge ticket minus recomputed fields; no field is dropped, invented, or silently overwritten; duplicate formula ids with different content are refused.

### C003 — cloned ledger -> identity renumber map

- **Precondition**: Two clones of a condensed ticket carry the same absorbed key with the same originKey and generation.
- **Postcondition**: The absorbed key is registered under originKey only; the clone does not claim ownership.
- **Invariant**: No IDENTITY_DUPLICATE_KEY for a shared historical key; every historical key resolves to exactly one survivor through identity.aliases.

### C004 — condense key change -> stub marker resolution

- **Precondition**: A stub marker references a ticket key absorbed by condense or renumbered by a later generation.
- **Postcondition**: The validator resolves the marker to the survivor through identity.aliases, and the rewrite path can update the marker transactionally.
- **Invariant**: No orphan marker remains; the next consolidate-stubs-gate and require-consolidated-manifest pass.

### C005 — condense key map -> omission convergence artifacts

- **Precondition**: Condense changes ticket keys, phase ids, and acceptance indices, and the package has OMISSION-GAP-SCAN, OMISSION-JUDGMENT-LEDGER, OMISSION-TICKET-INDEX, OMISSION-CONVERGENCE, and OMISSIONS artifacts.
- **Postcondition**: The rebase rewrites every artifact to the post-condense keys and acceptance criterion hashes, and the post-rebase gap scan digest matches the convergence digest.
- **Invariant**: Unrecorded obligations are zero after adjudication; no duplicate omission ticket is created for the same finding; report-only mode writes nothing.

### C006 — find-omissions Step 9 -> Step 9.5 condense -> conver boundary

- **Precondition**: find-omissions has merged omission phases and is about to return.
- **Postcondition**: Condense and rebase complete inside find-omissions before return; the boundary digest records the post-condense ticket set.
- **Invariant**: The second condense is NO_CHANGE; find returns only after all gates pass; conver advances only when the post-find ticket set is terminal.
