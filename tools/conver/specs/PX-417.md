# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

**Ticket Key**: PX-417 · **Phase**: -1

## Background

### Goal
Implement `/amend-rfc-up`: a command that amends the canonical RFC/SPEC upward from material through the design amendment transaction, rederives downstream artifacts through their owners, and verifies the chain. The command is the upstream counterpart of `/drill-rfc-down`.

### Purpose
`/drill-rfc-down` evolves a materialized canon append-only; it cannot correct an existing design statement. `/grill-me-for-rfc` rewrites the whole RFC but `canon-state.js` stops it on `materialized-fresh`. The missing owner is a correction path that preserves the append-only proof, the digest chain, owner rederive, and continuity.

### Motivation
`rust-interface-law` is a normative authority created after the RFCs. Correcting those RFCs through ad-hoc edits or a second write path would sever the design provenance that `design-amendment.js`, `verify-amendment.js`, and the stage receipts exist to preserve. The command must make the law applicable to existing RFCs without weakening those guarantees.

### Constraints
- Public command interface is material paths only: `argument-hint: [<material file|directory>...]`.
- No thin flags. Package, law manifest, phases, rules, ticket key, apply mode, and report path are derived.
- `design-amendment.js` is the only writer of SPEC/RFC. Owners write GRAPH/Dirs-Tree/Tickets.
- RFC amendments are append-only under `## Design Amendments`; the RFC body is never rewritten.
- Every amendment is ticket-scoped and leaves a ledger entry.
- Dry-run precedes apply; apply only when the internal gate has zero findings.
- Any failure restores every touched file byte-for-byte or reports the committed amendment plus `REDERIVE_PENDING`.
- Design consistency and law conformance are separate axes. `unverifiable` and `not_run` are never reported as pass.
- Command markdown: terminology-heavy, telegraphic, high compression, high density, non-verbose, no information loss, minimal characters.

## Acceptance Criteria

- **[Happy path] — design amendment completes:**
  - material-only invocation in an interface package: law APPLIES, canon materialized-fresh/stale, ticket derived; claims dry-run clean; amendments promoted with ledgers; owners rederive; verify-amendment and cross-artifact verify report zero high findings twice with the same digest; report DESIGN_AMENDED; RFC carries ## Design Amendments; no direct writes.
- **[Error case] — every refusal is safe:**
  - unknown flag, missing package artifact, missing material, missing ticket, law SKIP, invalid claim, dry-run finding, rolled-back amendment, owner failure, or verify high finding stops with a stable code and report; no partial silent write; no COMPLETE.
- **[Edge case] — derived boundaries:**
  - zero material discovery, standalone/partial canon, duplicate claim noChange, RFC without amendment section, multi-package separate invocations, unverifiable/not_run not pass.

## Invariants

- [Normal condition] The command runs only when cwd is a package with Tickets.json and a canonical RFC, the law `applies` returns APPLIES, the canon state is materialized-fresh or materialized-stale, and a ticket key is derivable; it then runs claims -> dry-run -> internal gate -> apply -> owner rederive -> verify.
- [Error invariant] A refusal (unknown flag, missing package artifact, missing material, missing ticket, law SKIP, invalid claim, dry-run finding, rolled-back amendment, owner failure, verify high finding) never leaves a partial silent write; the report names the code, cause, action, and rerun command.
- [Internal state invariant] Every promoted amendment has a ledger entry whose beforeDigest and afterDigest match the file; `verify-amendment.js` amendment-integrity reports AMENDMENT_LEDGER_MISMATCH on any drift; the command itself writes no artifact.
- [Boundary invariant] Zero material arguments trigger discovery of package-local finding documents; no discovered material is MATERIAL_REQUIRED. `standalone` and `partial` canon states are CANON_NOT_AMENDABLE. A duplicated identical claim is a noChange, not a second ledger entry.
