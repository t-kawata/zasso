# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

### Goal
Build /build-okf-skill as a standalone command that produces verified <name>-okf skills. Each generated skill ingests English Markdown sources into an OKF knowledge wiki and exposes deterministic retrieval, citation, freshness, conflict, and answer-verification commands so an AI can work from reliable information.

### Purpose
/build-law-skill already implements the expensive machinery: source measurement, manifest and atom lock, OKF node rendering, redaction, alias and input ledgers, dist bundling, installer, canonical verification, and acceptance mutation. A law skill and a wiki skill differ in semantics, not in that machinery. Reusing the machinery keeps the build deterministic and verified; replacing the rule-gate layer with claim provenance preserves the law skill's proven guarantees while serving a different purpose.

### Motivation
The repository already generates okf/, atoms.lock.json, source/, dist/, and install.js for every *-law skill. A second skill type can reuse those artifacts instead of inventing a second knowledge pipeline. AI work needs cited, current, conflict-aware information; a flat index alone is insufficient. The law verifier and the PX-423 integration closure must remain unchanged, so the OKF path must be additive and isolated.

### Constraints
- English UTF-8 Markdown sources in v1; Japanese source support is a separate decision.
- Generated *-okf skills are standalone; no runtime import from *-law.
- Shared engine modules are copied at build time and guarded by a SHA-256 drift test against rust-interface-law/scripts/lib.
- No edits to CLAUDE.md, make/plan/start/review/resolve, verify-law-skill.mjs, law-verify/*, verify-law-integration.mjs, or rust-interface-law.
- No forced integration checkpoints; the command has no Step 12/12.5 and no Integration Contract section.
- The OKF verifier check contract is separate; the law check_set_version 2 stays byte-identical.
- node --test for the impact set; never make test.
- Generated tree contains no ticket IDs, project names, or CJK.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — User requirement: /build-okf-skill accepts English Markdown and builds a wiki skill.

- **Precondition**: Input paths are repository-relative English UTF-8 Markdown files with at least one heading or paragraph and no NUL byte.
- **Postcondition**: A manifest entry {alias, sha256} and at least one Atom with a line span exist; a source with zero claim-bearing blocks yields INFORMATION_ZERO and no skill write.
- **Invariant**: Sources are read-only; LF normalization makes CRLF and LF hashes equal and does not change Atom identity.

### C002 — Reliability requirement: every wiki statement has a source.

- **Precondition**: Every Atom classified as Claim carries source alias, start_line, and end_line.
- **Postcondition**: Each Claim node frontmatter contains source, span, and content_sha256; the claim registry and Claim Atoms are a bijection.
- **Invariant**: No delivery=must Claim lacks provenance; an unsourced claim is reference with a specific reason or is rejected.

### C003 — AI retrieval requirement: deterministic, cited answers.

- **Precondition**: ask is invoked with a non-empty query against a built lock and index.
- **Postcondition**: Output lists at most 20 node ids in stable rank order; each result carries node, source, span, and content_sha256.
- **Invariant**: The same query and lock produce byte-identical stdout independent of cwd, mtime, and directory order.

### C004 — Freshness requirement: stale knowledge is never presented as current.

- **Precondition**: A source file content changes after a build and its new SHA-256 differs from the lock.
- **Postcondition**: freshness reports every dependent node as stale with expected and actual hashes and names the changed alias.
- **Invariant**: ask, context, and page mark stale nodes and never claim current status for them.

### C005 — Conflict requirement: contradictory knowledge is surfaced, not silently resolved.

- **Precondition**: Two Claim nodes declare contradictory values for the same topic key and are both current.
- **Postcondition**: conflicts returns a symmetric pair with both node ids and the conflicting key in deterministic order.
- **Invariant**: A one-sided declaration is CONFLICT_ASYMMETRIC and blocks install; no automatic deletion or silent winner selection occurs.

### C006 — Answer verification requirement: unsupported assertions are detectable.

- **Precondition**: An answer contains free text plus zero or more [node-id] citations, and each citation optionally quotes a span.
- **Postcondition**: verify-answer resolves every citation, checks the quoted span hash, and lists every uncited assertion with its sentence.
- **Invariant**: verify-answer exits 1 if any citation is unresolved or any assertion is uncited; only a fully cited answer is machine_verified.

### C007 — User requirement: the skill itself exhaustively provides usage scenarios and methods.

- **Precondition**: A generated SKILL.md exists in the staging tree and its description names the skill trigger.
- **Postcondition**: It contains When to Use, Query Recipes, Evidence and Citation, Freshness and Conflict, Update Procedure, Page Authoring, Failure Modes, and Examples with at least two concrete examples.
- **Invariant**: A missing required section or fewer than two examples is USAGE_INCOMPLETE and blocks install.

### C008 — User constraint: no forced gates on CLAUDE.md or the make/plan/start/review/resolve commands.

- **Precondition**: The build runs in a repository whose CLAUDE.md and five pipeline commands exist.
- **Postcondition**: Their bytes are unchanged after the build; no law-skill:checkpoint is added; verify-law-integration is never invoked.
- **Invariant**: The command document contains no Integration Contract section and no Step 12 or Step 12.5.

### C009 — Reuse requirement: shared engine modules are single-source and drift-guarded.

- **Precondition**: okf-engine contains a module listed in source/shared-engine.json with a source hash.
- **Postcondition**: Its SHA-256 equals the corresponding rust-interface-law/scripts/lib module; the drift report lists every shared module and both hashes.
- **Invariant**: A mismatch is ENGINE_DRIFT and blocks install; the build never overwrites the law module or silently accepts drift.

### C010 — User requirement: /build-okf-skill is standalone, like /build-law-skill.

- **Precondition**: The command is read as a standalone Markdown document with no runtime access to another command document.
- **Postcondition**: It names every required script and path and references no other command document, RFC, or external specification.
- **Invariant**: A required script name absent from the command is MISSING_SCRIPT; a link or filename reference to build-law-skill.md is EXTERNAL_REFERENCE.

### C011 — Distribution requirement: the installed skill proves the same bytes as staging.

- **Precondition**: A verified staging tree is installed with install.js into a temporary target directory.
- **Postcondition**: The installed subset (dist, okf, source, tests/fixtures/runtime) is SHA-identical and installed mode passes its required checks.
- **Invariant**: A source/installed mismatch is INSTALLED_SHA_MISMATCH and blocks completion.

## Boy Scout Rule

- Use verb-phrase functions for every new responsibility: measureSources, deriveOkfProfile, extractClaims, renderClaimRegistry, buildKnowledgeCoverage, rankNodes, detectStaleNodes, findConflictPairs, verifyAnswerCitations, auditSkillUsage.
- Use domain nouns for state: source, alias, span, claim, topic, node, citation, freshness, conflict. Do not introduce data, info, tmp, or generic item names.
- One function per responsibility: measuring, extracting, rendering, ranking, freshness, conflict, and answer verification stay separate; no AND/THEN function chains.
- Extract numeric limits into named constants: MAX_ANSWER_NODES=20, MAX_TOPICS=64, MAX_CONFLICT_DEPTH=3, NODE_BUDGET=2500, and put them in one limits module used by both engine and verifier.
- Never swallow errors: every failure carries a named code and a file/line context; rollback paths log the restored path.
- Where a shared module is byte-identical, copy it and record its hash in source/shared-engine.json; where it must differ, rename the law-specific concept (phase -> topic, rule -> claim) and document the difference in DESIGN.md.
- Improve touched code: remove duplicated path resolution by using one resolveSkillPath helper; replace hardcoded 'okf' and 'source' strings with named constants; rewrite any comment that describes what the code already says.
