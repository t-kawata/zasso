# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-425: Rebuild the OKF layer to Open Knowledge Format v0.2 with library-backed bundle, graph navigation, trust, and deterministic context

**Ticket Key**: PX-425 · **Phase**: -1

---

## Background

### Goal
Replace the non-conformant private okf/ cache in *-okf skills with an Open Knowledge Format v0.2 bundle and a library-backed navigation engine. After this ticket, an AI can list a directory, open a concept, follow outgoing and incoming links, resolve a required dependency closure, and receive a deterministic context artifact that carries trust, freshness, and sources.

### Purpose
OKF v0.2 defines concept identity by path, a single required `type`, Markdown body links as graph edges, reserved `index.md`/`log.md`, and a conformance test with exactly three conditions. The current implementation uses synthetic IDs, a flat index table, a key-value log, frontmatter links, no AST, no incoming edges, no conformance/profile split, no trust/freshness, and no `x-requires` closure. It cannot deliver the exploration and reach the format exists for.

### Motivation
PX-424 passed its own verifier but is not OKF v0.2. `docs/RESEARCH/OKF.md` documents the standard and the Node.js libraries. The repository must stop claiming OKF while implementing a private format. PX-425 is the foundation; PX-426 migrates the law layer.

### Constraints
- `docs/RESEARCH/OKF.md` is authoritative; the official spec is GoogleCloudPlatform/open-knowledge-format SPEC.md.
- Use existing libraries; do not hand-roll YAML parsing, Markdown AST extraction, or an OKF read/validation model.
- `okf/` is the bundle root. Reserved `index.md`/`log.md` live directly under it. No non-reserved `.md` without parseable frontmatter and non-empty `type`.
- Concept ID = bundle-relative path minus `.md`; no synthetic identity.
- Conformance has exactly three conditions; broken links, unknown types, unknown keys, and missing index are lint/profile findings, not conformance failures.
- Body Markdown links are the graph; no frontmatter `links`.
- `getOutgoing` and `getIncoming` are both first-class and symmetric.
- `x-requires` closure returns the complete required set; over budget throws `BUDGET_EXCEEDED`, never truncates.
- Deterministic output; no clock timestamps; log entries carry an explicit build date.
- No edits to `*-law` or `rust-interface-law` in PX-425; PX-426 owns that migration.

## Investigation

Evidence from the current tree:
- `.claude/scripts/amend-rfc-up/okf-engine/scripts/lib/okf.mjs` reads only `okf/nodes/*.md` and parses frontmatter with a line regex. It has no bundle scan, no reserved-file handling, no directory model, and no YAML safety.
- `.claude/scripts/amend-rfc-up/okf-engine/scripts/lib/render-okf.mjs` writes `okf/index.md` as a Markdown table and `okf/log.md` as `spec_version`/`nodes`/`lock` key-value lines. It writes `okf/source.md` and `okf/source.baseline.md` as non-reserved `.md` without frontmatter; both violate OKF conformance.
- `.claude/scripts/amend-rfc-up/okf-engine/scripts/commands.mjs` builds `indexRows` from `lock.nodes`; `related` returns only `node.links`; `context` returns node ids only; `ask` ranks `topic`/`summary`/`id`. There is no `getIncoming`, no body-link AST, and no required closure.
- `.claude/skills/rust-interface-law/okf/index.md` is a 2,733-row table; `okf/log.md` is three key-value lines. This is the private format, not OKF v0.2.
- `docs/RESEARCH/OKF.md` sections 5-9 define the official link rules, conformance split, recommended API (`loadBundle`, `getConcept`, `listDirectory`, `resolveReference`, `getOutgoing`, `getIncoming`, `validateBundle`, `lintBundle`, `resolveRequired`, `buildContext`), and the Node.js library candidates. Section Q2 records `@okforest/okf`, `js-okf`, `@jfomhover/okf-validator`, and `pi-okf`, and warns that `js-okf` lacks documented graph APIs and auto-updates timestamps.
- `tools/conver/package.json` already depends on `marked` but not on a YAML parser or a position-aware Markdown AST. `marked` alone cannot supply footnote and source-position edge extraction for the required model.
- Existing tests under `tests/build-okf-skill/` assert the private format (flat index, key-value log, `okf/source.md`, synthetic `CLAIM-XX` ids). They must be rewritten, not preserved.
Additional library evidence: @okforest/okf 0.14.0 already implements the OKF v0.2 read model, including path-based concept ids, YAML frontmatter with uniqueKeys, mdast links/footnotes/code blocks, trust tiers, status, staleness, sources normalization, and Tree.backlinks(id). The engine must wrap these exports rather than re-implement them. The only custom layers left are conformance/lint/profile policy, x-requires closure, context assembly, index/log structure checks, and the CLI.

## Acceptance Criteria

- **[Happy path]** A generated `*-okf` bundle passes `validate --mode conformance`, has path-based concept ids, linked-list index files, a dated log, `sources[]` objects, and trust/freshness metadata; `show` returns body + outgoing + incoming + sources + trust + freshness in one call.
- **[Error case]** A bundle with a broken link, unknown type, unknown key, and missing index still passes conformance; `lint` reports each finding; a root escape returns `blocked` and reads nothing outside the root; an over-budget context throws `BUDGET_EXCEEDED` with no partial output.
- **[Edge case]** A 2,500-concept, 10,000-edge bundle meets the latency and memory budgets, produces byte-identical rebuilds, and every one of the 10+ documented exploration scenarios returns the expected concepts and edges.

## Invariants

- [Normal condition] Every concept id equals its bundle-relative path without `.md`; every non-reserved `.md` has parseable frontmatter with a non-empty `type`.
- [Error invariant] Conformance never fails for a broken link, unknown type, unknown key, or missing index; those are lint/profile findings. A root escape or outside-root read is always blocked.
- [Internal state invariant] `getIncoming` is the exact reverse of `getOutgoing` for resolved concept-to-concept edges; every resolved edge appears in both indexes with the same origin and state.
- [Boundary invariant] A required closure either returns every required concept in deterministic order or throws `BUDGET_EXCEEDED`; it never returns a truncated prefix.

- Replace the line-regex frontmatter parser with a named `parseFrontmatter` that returns `{data, errors}`; no caller may re-implement YAML splitting.
- Replace the hand-written `parseBlocks` monolith with named AST visitors: `collectLinks`, `collectFootnotes`, `collectAssets`; each has one responsibility and a verb name.
