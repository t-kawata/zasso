# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

Re-inspection against the three sufficiency requirements found four concrete defects.

(1) The law CLI emits the undefined variable $OKF for non-Rule pages and for every search row; SKILL.md defines only $LAW, so the drill-down command the script hands the AI cannot be executed as printed. Cause: showCommand selects okf-wiki for any concept without x-rule-id, and search.mjs hardcodes node "$OKF".

(2) The law expand command is an alias of showCommand and never passes hop or stack, so guidance.hop stays 0, backTo stays null, and guidance.state=back is unreachable. The documented escape hatch (back at max hop) does not exist at runtime.

(3) The law outgoing/incoming/neighbors commands return only {id, edges}, and context --rule returns only {required, artifact}. The guidance.mustRun target for a rule is context --rule, so after following the instruction the AI receives no coverage or guidance and cannot read the stop decision the contract promises. SKILL.md line 57 claims every read command returns a Traversal Envelope; that is false for these commands.

(4) build-okf-skill.md maps one concept per level-2 section and nothing else, so text between the document H1 and the first H2 is owned by no concept. The okf coverage check compares concept-inventory ids with atoms.lock ids; it never proves that every source line is mapped. Unlike law, whose coverage-v3 records unmappedHeadings=0 and unmappedRuleRows=0, an okf build can therefore be machine_verified while silently dropping the preamble.

Additionally, the suites are red because the canonical check set moved to v3/36 in PX-427 and PX-428 but four contract surfaces still assert the old counts: build-law-skill.md enumerates 26 checks, tests/build-law-skill/command-file.test.mjs asserts 26, tests/build-okf-skill/command-file.test.mjs asserts version 2 and 30 checks, and tests/build-okf-skill/verifier/verify.test.mjs asserts 12 installed checks (canonical: 16). The law audit also rejects the declared primary input path docs/archive/IMPLEMENTATION-SPEC/EXPERT-REVIEW-PACKAGE.md as an external fixture, which turns the PX-428 input contract into an audit failure.

Goal: every one-hop response carries an executable drill-down list plus explicit stop/expand/back timing and means; every law and okf delivered context can prove why it is complete; docs, tests, and the canonical verifier agree on one check contract. Excess is acceptable only when it does not hide insufficiency, so the fix is additive and keeps legacy response fields.

## Acceptance Criteria

- Happy path: every law read response carries an executable $LAW drill-down and explicit stop/expand/back guidance; hop and back are reachable; context --rule reports sufficient=true and state=stop; search rows are executable as printed
- Error case: an absent id exits 2 with candidates; a missing or nonzero-coverage okf coverage ledger fails the canonical verifier with COVERAGE_MISSING or COVERAGE_GAP and blocks install
- Edge case: a source with H1 preamble and no H2 produces one root concept containing the preamble; a source with H2 sections produces a preamble concept plus one concept per H2, with unmappedLines=0

## Invariants

- 【Normal establishment】Every law read response (show, expand, outgoing, incoming, neighbors, context --rule, list, search) exposes a next command whose prefix is node "$LAW"; no response contains the undefined $OKF variable.
- 【Invariant on error】An absent concept id exits 2 with candidates; an unknown rule id raises UNKNOWN_RULE; a missing or nonzero okf coverage ledger yields COVERAGE_MISSING or COVERAGE_GAP and never machine_verified.
- 【Internal invariant】Response changes are additive: legacy fields (body, outgoing, incoming, sources, trustTier, freshness, required, artifact) keep their names and shapes; frontier and guidance ordering stays deterministic across calls.
- 【Boundary condition】guidance.state=stop if and only if coverage.missing is empty; state=back only when hop >= maxHops; hop is read from the CLI, not hardcoded to 0; backTo names the previous id in --from or null.
