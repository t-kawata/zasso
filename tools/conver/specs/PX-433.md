# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-433: History-driven progress timeline: backfill provenance and remove artifact-projected chronology

**Ticket Key**: PX-433 · **Phase**: -1

## Background

### Goal
Make `.conver-history.jsonl` plus a provenance-labelled backfill ledger the single clock and progress source for the progress-GIF timeline, so the animation replays the commands that actually ran instead of projecting final artifact state with file mtimes.

### Purpose
The current renderer derives stage events from artifact presence, status files, and ticket state in `stageProgressOf`, then attaches artifact mtimes or a per-stage `displayDate`. That dual-clock design produced false chronology: crystal explain emitted 46 events inside a 29ms mtime cluster while the explain history was empty; gaia explain emitted 58 events inside 89ms; gaia credited `consolidate=0.50` to 28 of 29 packages from workspace manifests while only 5 packages had consolidate history; crystal graphify was drawn 175h late and smooth 17.9h early.

### Motivation
The user rejected the artifact-projected preview because the global flow did not match the actual command sequence. A history-only replay of a backfilled ledger produced the approved flow: EDUCE -> EXPLAIN -> GRILL -> SMOOTH -> GRAPHIFY -> BOUNDIFY -> SPLIT -> per-package MAKE/PLAN/START/REVIEW -> RESOLVE/CONSOLIDATE/FIND, with DRILL visible. This ticket turns that prototype into the implementation.

### Constraints
- `.conver-history.jsonl` remains append-only; malformed or unreadable records are warnings and never command failures.
- The backfill must never use artifact mtime as a command time. It uses existing history, status completion fields, ticket explicit timestamps, and git first-commit times, with `source`, `confidence`, and `backfillId`.
- Backfill is one-time and idempotent; rerunning it must not duplicate records.
- A workspace with no history keeps the ordinal estimated path and is explicitly labelled `estimated`.
- `tools/conver/.claude` is the installer source; repository-root `.claude` and `crates/siprs/.claude` are mirrors and must stay byte-identical.
- The external gaia, crystal, and doors repositories are not modified by this ticket; the backfill tool is run operationally after review.

## Investigation

- `tools/conver/.claude/scripts/conver/progress-gif/loop.js:538` `stageProgressOf` is a final-state evaluator: explain at `:547` credits artifact presence; make/plan/start/review at `:621` use ticket status; resolve at `:642` uses Malfeasance; consolidate at `:651` credits 0.5 for any manifest and 1 for any omission; find at `:653` follows omissions. These values are independent of each other, so a later stage can exceed an earlier one.
- `loop.js:344` `resolveStatusTime` prefers the status `runId` epoch (command start); `loop.js:371` `resolveCompletionEvidence` takes the earliest of history finish and status start; `loop.js:1298` `computeStageDisplayDates` forward-clamps a stage to the next stage's trusted time; `loop.js:1433` `executionOrderTime` falls back to `displayDate` when the evidence precedes the first run finish. These are the dual-clock paths that produced the false chronology.
- Measured evidence: crystal explain emitted 46 events all at 2026-11-06T14:10:58.673-.702Z (29ms) with zero explain history; gaia explain emitted 58 events at 2026-11-05T00:48:55.703-.792Z (89ms) with zero explain history. Git first commits place crystal explain at 2026-11-02T15:51+09:00 and gaia explain at 2026-10-05T16:03+09:00.
- Measured evidence: gaia has 28/29 packages with consolidate=0.50 and make=0, while only 5 packages have a consolidate history finish; the 0.50 comes from `manifests.length > 0` at `:651`, not from a package pipeline command.
- Measured evidence: crystal graphify was drawn at 2026-11-14T19:25:41Z from evidence 2026-11-07T12:24:40Z (+175h); crystal smooth was drawn at 2026-11-14T01:33:58Z from evidence 2026-11-14T19:25:41Z (-17.9h); doors grill folded 138 events into 2026-11-05T06:07:26Z.
- Drill evidence: gaia has 11 `drills/Status.json` files with state COMPLETE (2026-11-04T23:57Z to 2026-11-05T07:04Z); doors has COMPLETE drill history at 2026-11-14T13:50:42Z and 17:07:43Z; crystal has only REPAIR_NO_PROGRESS drill history and no drill status. The current COMPLETE-only run-marker filter and evolution suppression make DRILL invisible.

## Invariants

- [Normal condition] History and backfill records are the only timeline clock: every animated pipeline stage event has a record, and its order time equals the record's `at`.

- **Precondition**: A package has implementation records that are out of order.

- **Invariant**: No later implementation stage is displayed ahead of its predecessor.

### C005 — drill status and history -> DRILL row and marker

### C006 — timeline validation -> render publication

- **Precondition**: A timeline violation exists.
- **Postcondition**: validate-timeline reports it and draw-progress-gif exits non-zero without publishing HTML.
- **Invariant**: No HTML is written when validation fails.

### C007 — no-history workspace -> ordinal estimated timeline

- **Precondition**: A workspace has no history or backfill records.
- **Postcondition**: The ordinal estimated timeline is rendered and marked estimated.
- **Invariant**: Existing snapshots without the new fields remain readable.

### C008 — history final state -> artifact final state comparison

- **Precondition**: History-derived and artifact-derived final states are both available.
- **Postcondition**: A parity result within tolerance or a named discrepancy is reported.
- **Invariant**: Artifact state is never used to fill timeline events.
