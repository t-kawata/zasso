# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-441: Incremental source-bound proof reuse across repeated find runs

**Ticket Key**: PX-441 · **Phase**: -1

---

## Background

### Goal
Make repeated /find-omissions runs reuse only the proofs whose experiment inputs are unchanged, and re-prove every proof whose inputs changed, without touching conver.js or the .conver-boundary.json schema.

### Purpose
conver runs find at a package boundary after every ticket is terminal. When find adds tickets, the implementation loop runs, source and tests change, and find runs again up to MAX_FIND_ROUNDS=5. A run can also resume after an interrupted find or a destroyed boundary record. The harness must distinguish these cases per clause instead of per run.

### Motivation
The v3 harness currently gets both directions wrong. isProofFresh compares only the mapped test digest, although proof-engine records digests.source, so an implementation-only change keeps a stale proof PROVEN. Conversely scanClauseCoverage nulls every proof when the whole inventory or test-index digest changes, so one added test re-proves all TESTABLE clauses. The find runner also never invokes the proof runner. This ticket removes both defects.

### Constraints
conver.js and .conver-boundary.json are unchanged. The v3 terminal predicate keeps its strictness, including two identical measurements and zero remainder. No language-specific vocabulary enters harness defaults or tests. Old proof and judgment records must migrate safely and must never be silently reused.

## Acceptance Criteria

- [Happy path] Two consecutive find runs on an unchanged package reuse every fresh TESTABLE proof, execute zero proofs on the second run, and reach exit 0 with the v3 terminal verdict.
- [Error case] Changing a mutation-target source file without changing its test makes exactly that clause stale and re-proven; a TESTABLE clause without a proof plan yields PROOF_PLAN_MISSING and a repair item; changing a lockfile or the proof engine invalidates all proofs with a named reason.
- [Edge case] An adapter without dependencyClosure falls back to package scope, so an unrelated file change re-proves all clauses, while ticket additions and harness artifact rewrites alone invalidate nothing.

## Invariants

- [Normal condition] A PROVEN proof is reusable only when its recorded inputsDigest equals the recomputed digest of clauseKey, mutationFile, mutationFileDigest, mutationDigest, testId, testDigest, commandDigest, closureScope, closureDigest, engineVersion, adapterVersion and toolchainDigest.
- [Error invariant] Any missing, unreadable or unknown input yields CLAUSE_PROOF_STALE or PROOF_INPUTS_UNKNOWN, never PROVEN; CLAUSE_PROOF_FAILED, UNSTABLE and SOURCE_RESTORE_FAILED are never reused.
- [Internal state invariant] CONTRACT-COVERAGE.json is a derived view. A global inventory or test-index digest mismatch is a finding, never a reason to null every proof; the per-clause input tuple alone decides reuse.
- [Boundary invariant] closureScope is explicit. An adapter without a valid dependency closure falls back to scope=package over package source files that exclude harness artifacts; --report-only executes zero proofs and writes zero files.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — proof freshness

- **Precondition**: A PROVEN proof exists with inputsDigest over clauseKey, mutationFile, mutationFileDigest, mutationDigest, testId, testDigest, commandDigest, closureScope, closureDigest, engineVersion, adapterVersion and toolchainDigest.
- **Postcondition**: isProofFresh returns true if and only if every recorded input equals the current recomputed value; otherwise it returns false and names the changed field.
- **Invariant**: A missing, unreadable or unknown input never yields true; restored must be true and status must be PROVEN.

### C002 — coverage scanning

- **Precondition**: Coverage was built against older inventory and test-index digests, and a given clause's own input tuple is unchanged.
- **Postcondition**: The clause remains PROVEN by reusing its proof while bindingValid is false; no global proof nulling occurs.
- **Invariant**: Only clauses whose own tuple changed become stale; unrelated clauses keep their proofs.

### C003 — find runner

- **Precondition**: find-omissions-run executes non-report-only with N TESTABLE clauses and a mixture of fresh, stale and missing proofs.
- **Postcondition**: It executes only stale or missing proofs whose mutation and command are available (from the existing proof or a TESTABLE disposition proof plan), persists inputsDigest, reports reused/rerun/missing counts, and exits 0 or 10 under the unchanged terminal predicate.
- **Invariant**: A fresh proof is never executed; report-only executes no proof and writes no file; a missing proof plan is PROOF_PLAN_MISSING and a repair item; a failed or unstable proof keeps exit 10.

### C004 — dependency closure

- **Precondition**: The adapter may expose dependencyClosure returning a scope in {file, crate, module, package} and a file list, or may be absent, throw or return invalid data.
- **Postcondition**: A valid result is persisted as closureScope plus closureDigest; an absent, throwing or invalid result falls back to scope=package over the package source set.
- **Invariant**: Unknown closure never yields file-level reuse; the package source set excludes harness artifacts and ticket additions alone invalidate nothing.

### C005 — toolchain fingerprint

- **Precondition**: The current runtime version, adapter runner string and the first existing lockfile are observable.
- **Postcondition**: toolchainDigest changes when any of them changes; a missing lockfile still yields a deterministic digest.
- **Invariant**: Any toolchainDigest change invalidates all proofs; a lockfile is never silently excluded.

### C006 — judgment freshness

- **Precondition**: A judgment records status, normativeSource, evidence entries with full-file digests, reason and evidenceDigest.
- **Postcondition**: judgeCoverage reuses the judgment only when the recomputed evidenceDigest matches; otherwise the obligation is unrecorded or stale.
- **Invariant**: A judgment without evidenceDigest is invalid; PASS on a TESTABLE clause still requires a PROVEN proof.

### C007 — conver boundary

- **Precondition**: /find-omissions runs from a conver package boundary and may add tickets to Tickets.json.
- **Postcondition**: Exit codes remain 0 for complete and 10 for incomplete, ticket additions keep their shape, and .conver-boundary.json is neither read nor written by the change.
- **Invariant**: Cache state never alters boundary endpoint decisions; no conver.js file is modified.

### C008 — backward compatibility and observability

- **Precondition**: A v1 proof may lack inputsDigest and a v1 judgment may lack evidenceDigest; proof-input version may be unsupported.
- **Postcondition**: Such records are read without crashing, reported stale once, re-proven or re-judged, and counted under invalidatedBy reasons that sum to the TESTABLE clause count.
- **Invariant**: No legacy or unsupported record is silently reused or turned into PROVEN.

## Changes in Prior Implementation Rounds

| Before | After | Description |
|--------|-------|-------------|
| isProofFresh compared only proof.digests.test | It compares the complete inputsDigest tuple: clause, mutation file bytes, mutation, test, command, closure, engine, adapter and toolchain | Source-bound proof freshness; unknown inputs are stale. |
| A global inventory or test-index digest mismatch nulled every proof | The mismatch is a finding; each clause keeps or loses its proof by its own inputs | Per-clause invalidation removes run-wide re-proofing. |
| find-omissions-run never executed proofs and coverage stored no command or mutation | The run builds entries, executes stale or missing proofs, re-scans and gates on the refreshed coverage | Proof execution is part of the single v3 flow. |
| No first-proof input source existed | A TESTABLE disposition may carry proof {mutation, command}; absent plan is PROOF_PLAN_MISSING | The harness never guesses a mutation or command. |
| judgmentKey ignored evidence content | Judgments carry evidenceDigest over cited file bytes; changed evidence is unrecorded | Judgment reuse is evidence-bound. |
| TypeScript adapter had no dependency closure | It resolves relative imports transitively; unresolved or invalid closures fall back to package scope | File-level reuse where provable, package fallback otherwise. |
| A convergence-only failure created a repair ticket | It exits 10 without a repair; the next identical run is the fixed-point check | A real change does not leave an open repair that blocks its own confirmation. |
