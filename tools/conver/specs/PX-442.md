# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-442: Workspace-level proof isolation and legacy artifact migration

**Ticket Key**: PX-442 · **Phase**: -1

## Background

### Goal
Make /find-omissions converge on a real package whose tests depend on files outside the package and whose v1 artifacts predate PX-441 input binding, without changing conver.js or the boundary contract.

### Purpose
The doors crates/pjsip-prebuilt migration exposed gaps that PX-441 alone cannot close: the proof engine copies only the package, so cargo tests that include_str ../../../doors-core/... cannot compile; 324 v1 proofs and 452 v1 judgments have no input/evidence digest; an unrepairable repair record blocks the v3 repair gate; existing rust proofs use cargo test without -- --exact while the adapter adds it; and conflict groups can remain unticketed because conver ignores find's exit code and stops on the ticket set.

### Motivation
A package can be complete under the old artifacts and still fail to re-enter the new loop. The harness must migrate safely and must make every v3 blocker visible as a ticket or a repair, otherwise conver can declare an endpoint while the v3 terminal verdict is still 10.

### Constraints
No conver.js, src/next-action.ts, src/runner.ts or src/boundary-state.ts change. No weakening of the v3 terminal predicate. No silent reuse of an unbound proof or judgment. No project-name hardcoding in harness defaults or tests.

## Acceptance Criteria

- [Happy path] A package with an external include_str dependency migrates its v1 proofs and judgments, re-proves only the unstable or mismatched proofs, creates no duplicate tickets, and a second find run reuses every adopted proof with zero repair blockers.
- [Error case] A missing external include path yields PROOF_WORKSPACE_INCOMPLETE and REPAIR_REQUIRED, never PROVEN; a mutation on Tickets.json is dropped and ticketed; an evidence file newer than the ledger enumeration leaves its judgment unrecorded.
- [Edge case] An unrepairable repair with a terminal diagnostic ticket is closed, while the same record with an open diagnostic ticket still blocks through open-tickets; a PROVEN conflict still yields a conflict ticket.

## Invariants

- [Normal condition] A proof experiment runs in an isolated tree that preserves the package and every external input required by its mutation and its tests; the command cwd is the package inside that tree.
- [Error invariant] A missing or unreadable required external path yields PROOF_WORKSPACE_INCOMPLETE and REPAIR_REQUIRED, never PROVEN, and never a package-only fallback.
- [Internal state invariant] A proof is adopted only when source, test, command, closure, engine, adapter and toolchain inputs match; a harness artifact is never a stable mutation target.
- [Boundary invariant] conver.js and .conver-boundary.json are unchanged; report-only writes nothing; migration is idempotent and leaves no partial artifact.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — proof workspace

- **Precondition**: A proof mutation target or a test/source include_str/include_bytes path resolves outside the package but inside the project; the caller supplies cwd, mutation files and include paths.
- **Postcondition**: resolveProofWorkspace returns an isolated tree that preserves the package and every required external path at the same relative location; runDetectionProof runs with the package directory in that tree as cwd.
- **Invariant**: No required external path is omitted; cleanup removes the whole tree; package-only isolation is not used when an external path is required.

### C002 — workspace failure

- **Precondition**: A required external path is missing or unreadable, or the isolated copy fails.
- **Postcondition**: resolveProofWorkspace returns PROOF_WORKSPACE_INCOMPLETE with the missing path and runDetectionProof returns REPAIR_REQUIRED, never PROVEN.
- **Invariant**: The real tree is not mutated and the harness never silently falls back to a package-only copy.

### C003 — mutation stability

- **Precondition**: A proof mutation targets a harness artifact such as Tickets.json, OMISSION-*, CONVER-* or _tmp-*.
- **Postcondition**: classifyMutationTarget returns UNSTABLE_PROOF_TARGET; migration drops the proof and creates or reuses an omission ticket requiring a stable target.
- **Invariant**: The clause remains unresolved and is never marked PROVEN; a stable source or normative file is not dropped.

### C004 — legacy proof adoption

- **Precondition**: A v1 proof is PROVEN with restored=true and its source, test and command digests equal the current inputs; the mutation target is stable and the lockfile predates verifiedAt.
- **Postcondition**: adoptLegacyProof writes inputsVersion, inputsDigest, inputs, closureScope, engineVersion, adapterVersion, toolchainDigest and legacyAdoptedAt; isProofFresh returns true.
- **Invariant**: Any mismatch or unknown input prevents adoption; adoption is idempotent and report-only writes nothing.

### C005 — legacy judgment binding

- **Precondition**: A v1 judgment lacks evidenceDigest and every cited evidence file is not newer than the ledger enumeration timestamp.
- **Postcondition**: bindLegacyJudgment writes evidence records with fileDigest and evidenceDigest plus legacyBoundAt; judgeCoverage reuses the judgment.
- **Invariant**: A file newer than enumeration or an unreadable file leaves the judgment unrecorded; binding is idempotent and report-only writes nothing.

### C006 — repair status

- **Precondition**: A repair record has status unrepairable and its diagnostic ticket is terminal or absent.
- **Postcondition**: isOpenRepair returns false and the gate repair check and pendingRepairs ignore the record.
- **Invariant**: pending and in_progress are open; an unrepairable record with an open diagnostic ticket remains blocked through open-tickets; completed and false_positive are closed.

### C007 — command compatibility

- **Precondition**: An existing proof stores command C while the adapter runner is R.
- **Postcondition**: resolveProofPlan returns C for the existing proof and R for a new proof; commandDigest matches C and re-proof executes C.
- **Invariant**: An adapter-runner change alone does not invalidate an existing proof; a proof without a stored command uses the adapter runner.

### C008 — rust runner

- **Precondition**: The Rust test id is a bare function name and the adapter runner contains -- --exact.
- **Postcondition**: The default runner is cargo test {test} and the bare id matches one test.
- **Invariant**: No default --exact is emitted unless test ids are fully qualified.

### C009 — blocker to ticket

- **Precondition**: The v3 remainder contains conflict groups, unclassified clauses, unmapped or proof-missing clauses, or unstable-target clauses.
- **Postcondition**: blockerEntriesOf emits one deduplicated group per contract for every blocking class and the planner covers all blockers.
- **Invariant**: A conflict stays a blocker even when every conflicting clause is PROVEN; an already-owned group is reused, not duplicated.

### C010 — boundary and observability

- **Precondition**: Migration or a find run executes on a package with v1 or v2 artifacts.
- **Postcondition**: The migration report lists adopted, reproved, dropped, workspaceFindings, judgmentsBound, judgmentsUnbound, ticketsCreated and ticketsReused; a second run reports zero changes.
- **Invariant**: conver.js and .conver-boundary.json are byte-identical; report-only leaves the workspace byte-identical; an unsupported version is a named finding, not a crash.
