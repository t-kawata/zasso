# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-444: Absorb generic omission-ticket provenance and project note injection

## Background

Doors' /find-omissions run patched the installed .claude planner locally (commits ffe0d5d and d42f296): generated omission tickets gained splitReason, created_at and a notes clause naming the doors laboratory. Only splitReason and created_at are generic; the laboratory clause is the doors package's contract. Distribution overwrites .claude and deletes the local patch, so the next install reproduces red package contracts. conver must emit the generic provenance itself and provide a project-agnostic way for any package to append its own mandatory ticket note.

### Goal
Every conver-generated omission ticket carries the provenance its own gates and downstream package contracts expect: splitReason when the phase has more than one ticket, created_at, and notes with affected contract ids, source ticket and resolution steps; any package can append a project clause without conver knowing that project.

### Purpose
The v3 omission planner is the only writer of omission tickets. If it omits provenance, every distributed project must patch .claude, and every install destroys that patch. A package-local note artifact makes the project-specific requirement survive distribution while keeping conver project-neutral.

### Motivation
Reproduced in conver: a zero-budget omission plan creates three tickets with no splitReason, and collectPartitionFindings returns SPLIT_REASON_MISSING for P0-2 and P0-3, so conver's own condensation gate rejects its own planner output. In doors, the installed planner patch also supplied created_at and the natenv-okf notes clause; removing it makes px_3_contract::assert_created_todo and p0_4_contract::every_ticket_cites_the_laboratory_and_its_implemented_records_pass fail.

### Constraints
- conver source, tests and docs must contain no project-specific text (no natenv-okf, no Amendment PX-3-1, no doors).
- Existing planOmissionTickets and migrateArtifacts callers must keep working without the new inputs.
- The PX-394 invariant stands: a single-ticket phase carries no splitReason.
- The project note lives in the package root outside .claude so distribution cannot overwrite it.
- TDD Red-Green-Refactor; no test weakening; no stub Green.
- Scope is the v3 measured planner used by find-omissions-run and legacy artifact migration; the legacy applyFindings path is unchanged.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — omission plan → condensation gate

- **Precondition**: planWorkUnitTickets partitions implementation atoms into N contiguous groups and appends each group as one ticket to a single created omission phase.
- **Postcondition**: When N > 1, every created ticket carries splitReason 'budget'; when N === 1, the created ticket carries no splitReason.
- **Invariant**: collectPartitionFindings on the created phase returns no SPLIT_REASON_MISSING or SPLIT_REASON_NOT_PROVEN, and the PX-394 single-ticket invariant is preserved.

### C002 — omission plan → ticket record

- **Precondition**: materializeOmissionTicket creates a ticket record from atoms, unitKey, phaseId and id.
- **Postcondition**: The record carries created_at as a 10-character ISO date (YYYY-MM-DD).
- **Invariant**: Every created ticket has created_at before the plan document is returned, and one plan stamps one date across its tickets.

### C003 — omission atoms → ticket notes

- **Precondition**: The atoms carry group keys and zero or one distinct owner key.
- **Postcondition**: notes names every distinct affected contract id and the source ticket (or 'no single source ticket') and states the resolve/prove/re-run procedure.
- **Invariant**: The generic note is derived only from atoms and rootTicketKey and contains no project-specific token or clause.

### C004 — package note → omission ticket

- **Precondition**: projectDir is provided and contains an optional OMISSION-TICKET-NOTES.json with version 1 and a non-empty notes string, or an explicit ticketNotes string is supplied.
- **Postcondition**: Every created ticket's notes is the generic block followed by one space and the project note verbatim.
- **Invariant**: Absent file leaves the generic block unchanged; a malformed file raises a named refusal before any write; explicit ticketNotes overrides the file; conver never interprets the text.

### C005 — distribution → package contract

- **Precondition**: A package declares its mandatory ticket clause in OMISSION-TICKET-NOTES.json at the package root, and conver is installed over that package's .claude.
- **Postcondition**: Distribution does not remove the package file; generated omission tickets carry the clause, and the package's ticket contract tests that read created_at, notes and splitReason pass.
- **Invariant**: conver source, tests and docs contain no project name or clause; the package file is the only project-specific source.
