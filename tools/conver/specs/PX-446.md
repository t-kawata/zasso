# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you find it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-446: Adopt a pre-existing terminal package without running its boundary

**Ticket Key**: PX-446 · **Phase**: -1

---

## Background

### Goal
A package whose every ticket is terminal when conver first reads it must never execute `/consolidate-stubs` or `/find-omissions`, even when no `.conver-boundary.json` exists or when the record shows an interrupted boundary. conver records the package as a legacy completion and treats it as an endpoint.

### Purpose
The durable boundary record is proof that conver observed the reviews and owes a boundary. Its absence, or an incomplete record, is not proof that the implementation is pending. A package completed before PX-413, completed on another machine whose record was not carried over, completed outside conver, or left with an interrupted boundary has no completed boundary record; today the loop resumes or reruns the boundary before moving to the first package with real work.

### Motivation
On 2026-11-18 a conver run over crystal started `/find-omissions` for `crystal-protocol-types`. The package's 17 tickets had been terminal since 2026-11-12 and its omission artifacts already existed. Later, `crystal-adapter-clock` had `consolidate: COMPLETE` and `find: IN_PROGRESS`; the next start resumed its find instead of reaching `crystal-core P1-9`. The same class of condition affects `crystal-adapter-current-authority` and `gaia-foundation`. Completed packages must not execute find, and an interrupted boundary must not preempt the first pending ticket of the workspace.

### Constraints
- The adoption decision must be deterministic from `Tickets.json` plus the presence/readability of `.conver-boundary.json`; no network, no clock-dependent branch.
- Adoption must not rewrite `Tickets.json`.
- A completed find whose digest differs from the current ticket set still runs the boundary: the ticket set changed.
- A review observed by conver still owes its boundary: a readable record with no started boundary and a review timestamp/`reviewedSinceResolve` is not adopted.
- A review observed by conver after adoption invalidates the adoption and restores the normal boundary path.
- No new runtime dependency. TDD Red-Green-Refactor is mandatory.

## Scope

- **In scope**
  - `tools/conver/src/boundary-state.ts` — add the legacy completion source, the constructor, and the endpoint branch.
  - `tools/conver/src/boundary-state.test.ts` — unit tests for the constructor, the predicate and invalidation.
  - `tools/conver/src/runner.ts` — adopt before `clearForNextRound` when the ticket set is terminal and the boundary did not complete for it: missing, unreadable, or interrupted. Preserve the stale-completed-find and post-review exceptions.
  - `tools/conver/src/runner.test.ts` — adoption, idempotence, unreadable-state, interrupted-boundary, watcher-endpoint and boundary-still-runs tests.
  - `tools/conver/README.md` — the endpoint rule and the adoption rule.
- **Out of scope**
  - A forced-boundary flag. Adoption is the default; forcing a boundary needs its own ticket.
  - Migration of existing packages. The next run adopts them automatically.
  - Concurrent conver processes. Single-process execution remains the assumption.

## Acceptance Criteria

- **[Happy path]** An all-terminal package with no boundary state executes zero commands, writes a legacy completion record with the current ticket-set digest, leaves `Tickets.json` byte-identical, and is endpoint on every later call.
- **[Interrupted boundary]** An all-terminal package whose record shows a started but incomplete boundary (`consolidate` or `find` not null, with no completed find for a different ticket set) adopts the same way and executes zero commands.
- **[Error case]** An all-terminal package with an unreadable (corrupt, version-mismatched or partial) boundary state adopts the same way and logs a warning; it never executes find.
- **[Edge case]** An all-terminal package with a completed find whose digest differs from the current ticket set still runs consolidate and find. An all-terminal package with no started boundary and a review timestamp still runs its resolve and boundary. An empty ticket set adopts without running the boundary. A later review clears the legacy source and restores the boundary path.
- **[Watcher]** `runWorkspaceLoop` reports `allSelectedComplete: true` after adopting a pre-existing terminal package, so the watcher exits 0.

## Invariants

- [Normal condition] An all-terminal ticket set whose boundary did not complete for it — no record, an unreadable record, or a started-but-incomplete record — means "adopt", never "run the boundary".
- [Stale invariant] A completed find (`COMPLETE` or `SKIPPED`) whose digest differs from the current ticket set is not adopted; the boundary runs for the changed set.
- [Review invariant] A readable record with no started boundary and a non-null `lastReviewedAt` or `reviewedSinceResolve > 0` is not adopted; conver observed the review and still owes its boundary.
- [Error invariant] An adopted record is endpoint only while its `ticketSetDigest` equals the digest of the current `Tickets.json` and every ticket stays terminal.
- [State invariant] A review after adoption sets `completionSource` to `boundary`, clears the digest and both command records, and increments `reviewedSinceResolve`, so the adopted record can never satisfy the endpoint predicate again.

## Contracts

### C001 — step:legacy-adoption

- **Precondition**: `Tickets.json` parses, every ticket is terminal, and `readBoundaryState` returns null (missing or unreadable).
- **Postcondition**: `runPackageLoop` executes zero commands, does not rewrite `Tickets.json`, writes a legacy completion record with the current digest, and returns `processed = 0`.
- **Invariant**: The legacy record is endpoint only while the digest matches and the ticket set stays terminal.

### C002 — step:boundary-still-runs

- **Precondition**: A readable boundary state exists, its completed find digest differs from the current ticket set, or it has no started boundary but a review timestamp.
- **Postcondition**: The loop follows the existing command order and runs consolidate and find; it never adopts.
- **Invariant**: A completed find with a stale digest, or a review-created pending boundary, still runs the boundary.

### C003 — step:review-invalidates-adoption

- **Precondition**: A legacy completion record exists and a ticket becomes terminal during a run.
- **Postcondition**: `markReviewed` changes `completionSource` to `boundary`, clears the digest and both command records, and increments `reviewedSinceResolve`.
- **Invariant**: An adopted record can never survive a later review.

### C004 — step:interrupted-boundary-adoption

- **Precondition**: Every ticket is terminal; a readable boundary record has `consolidate` or `find` non-null; and it is not a completed find whose digest differs from the current ticket set.
- **Postcondition**: The loop executes zero commands, writes a legacy completion record, and treats the package as endpoint.
- **Invariant**: A started-but-incomplete boundary is abandoned at startup, not resumed.

### C005 — step:review-boundary-still-runs

- **Precondition**: Every ticket is terminal; a readable boundary record has no started command; and `lastReviewedAt` is non-null or `reviewedSinceResolve` is greater than zero.
- **Postcondition**: The loop runs the pending resolve and/or boundary; it never adopts.
- **Invariant**: A boundary owed by a review survives a process restart.
