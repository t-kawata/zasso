# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-449: Show the running package, command and ticket in a fixed NOW line

**Ticket Key**: PX-449 · **Phase**: -1

---

## Background

### Goal
Add one fixed line at the very top of the progress dashboard that always names the package, command and ticket currently executing. The notation is exactly `NOW: [core] /start-ticket P1-9`, on a dark-green background with white text, and it stays on one terminal row.

### Purpose
The dashboard reports ticket status but not the command the runner is executing. An operator cannot distinguish /make-ticket from /plan-ticket, /start-ticket, /review-ticket, /resolve-ticket or a package boundary, and a long-running command looks identical to an idle loop. The NOW line makes the current action observable without reading the scrolling log.

### Motivation
On 2026-11-18 the user requested an always-visible running-command line and fixed the notation as `NOW: [core] /start-ticket P1-9`. The fixed header already owns terminal rows 1..N through DECSTBM, so a new row must enter the fixed-row budget rather than be painted over the log. Adding a line without correcting the budget would shrink the log below its four-row minimum and, on short terminals, collide with the hidden-package indicators.

### Constraints
- Exactly one row. Dynamic text is sanitized, truncated and padded; it never wraps.
- Fixed rows (NOW + package rows + indicators) must be at most `rows - LOG_MIN_ROWS`; the log keeps at least four rows.
- The NOW line updates immediately on command start and end. The five-second poll only refreshes package status.
- stdout non-TTY and `--no-dashboard` remain complete no-ops.
- The short package name in the NOW line and in the package row come from one derivation over the full workspace list, so scrolling cannot rename the active package.
- Existing dashboard, renderer and runner tests keep passing. TDD Red-Green-Refactor is mandatory.

## Investigation

Confirmed against source on 2026-11-18.
- `src/progress/dashboard.ts:178-245`: `#redraw` builds `lines` from optional up indicator, `renderHeader` rows and optional down indicator; the scroll region is `\x1b[${lines.length + 1};${rows}r` and the cursor is placed at `lines.length + 1`. The stale-row erase loop uses `lines.length`. Therefore prepending one line moves the region and the erase loop consistently; only the capacity arithmetic at line 183 is manual.
- `src/progress/dashboard.ts:183-188`: `maximumHeaderRows = Math.max(0, Math.min(rows - 2, rows - LOG_MIN_ROWS))`, `capacity = Math.min(packages.length, maximumHeaderRows)`, `visibleCount = Math.max(1, capacity - (needsIndicators ? 2 : 0))`. When `capacity < 3` and packages exceed capacity, the two indicator rows plus the one visible row exceed capacity; the existing code can already paint more fixed rows than budgeted. The NOW row reduces capacity by one and makes this reachable on ordinary short terminals.
- `src/progress/layout.ts:19-25,151-195`: `HEADER_BACKGROUND = "#0b1f3a"`, pale-yellow phase labels, dark-red status marks, `truncate` slices code units and `renderHeader` derives short names from the slice it receives. There is no activity renderer and no dark-green constant.
- `src/progress/model.ts:109-131`: package percent and status symbols are pure; `ProgressSnapshot` carries only packages, so activity must be added as separate dashboard state, not polled from Tickets.json.
- `src/runner.ts:82-87`: `DisplayHooks` has only `onUpdate`, `onFlush`, `onPackageStart`. `src/runner.ts:795-803` (`executeCommand`), `575-596` (`runResolve`, including `/epush-branch`) and `622-632` (`runBoundary`) are the three command execution paths. `runBoundary` currently prints only the first line of the command; the same first-line rule is needed for activity.
- `src/conver.ts:214-236,266-273`: the dashboard is built only when stdout is a TTY and `--no-dashboard` is absent; display hooks are created next to it and `dashboard.start()` follows. This is the single wiring point for activity callbacks.
- `src/display/renderer.ts:180-185`: log lines are written with `sanitizeTerminalText` and a trailing newline; the renderer does not position rows, so the dashboard's scroll region fully controls placement.
- `src/display/terminal-text.ts:28-35`: the shared sanitizer deliberately keeps SGR sequences so logs can be colored. The activity line needs stricter handling because its text comes from package names and must not inject color or cursor state.
- `src/progress/short-name.ts:51-65`: `stripCommonPrefix` returns `{ prefix, names }`; the crystal root package keeps its name. Reusing it over the full workspace list is the stable way to render `core`.
- `package.json`: `string-width` is a direct dependency, so accurate wide-character width is available without adding a dependency.
- Test harness: `dashboard.test.ts` injects `write`, `terminalSize`, fake timers and `readSnapshot`, so ANSI geometry and activity transitions are assertable without a real terminal. `runner.test.ts` injects `runCommand` and `withSession`, so hook ordering and the failure path are assertable.

## Acceptance Criteria

- Happy path: while `/start-ticket P1-9` runs for `crystal-core`, row 1 reads exactly `NOW: [core] /start-ticket P1-9` with white text on dark green; package rows start at row 2; the log region starts after every fixed row.
- Error case: an activity label containing control sequences or a newline is sanitized and truncated to exactly one row, and a failing command still clears the NOW line.
- Edge case: on terminals with 5 and 6 rows the fixed region still leaves four log rows; the NOW line stays on row 1 and never wraps, and with `--no-dashboard` no NOW row is written.
- Boundary case: `/consolidate-stubs` and `/find-omissions` render without a ticket key; a resumed find shows only `/find-omissions`, not the multi-line resume directive.

## Invariants

- [Normal condition] When the dashboard is active, the NOW row is always the first fixed row and every painted fixed row is counted in fixedRows.
- [Error invariant] Activity rendering is pure: no control sequence from package, command or ticket data reaches the terminal, and a failed command still clears the NOW row.
- [Internal state invariant] The short package name in the NOW line equals the package row name for the same package, because both derive from stripCommonPrefix over the full workspace list.
- [Boundary invariant] fixedRows <= rows - LOG_MIN_ROWS at every terminal height; with rows < 5 the dashboard does not paint, and with rows = 5 only the NOW row is fixed.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — progress-dashboard/now-line

- **Precondition**: The dashboard is active and CurrentActivity holds packageName crystal-core, command /start-ticket and ticketKey P1-9.
- **Postcondition**: Row 1 is exactly NOW: [core] /start-ticket P1-9 in plain text; in color mode the same visible text has a dark-green background and white foreground.

### C002 — progress-dashboard/fixed-row-budget

- **Precondition**: The workspace has N packages and the terminal reports R rows with the dashboard active.
- **Postcondition**: fixedRows equals one NOW row plus visible package rows plus indicator rows; the scroll region starts at fixedRows + 1, and fixedRows is at most R minus four.
- **Invariant**: The log region keeps at least four rows, and painting, cursor placement and stale-row clearing use the same fixedRows.

### C003 — runner/display-hooks

- **Precondition**: A command starts or ends while the dashboard is running.
- **Postcondition**: onCommandStart fires with package, command and ticket before execution; onCommandEnd fires from finally after completion; setActivity repaints immediately.
- **Invariant**: The NOW line never names a command that already stopped, and timer refreshes do not change the activity.

### C004 — progress-dashboard/one-line-safety

- **Precondition**: Activity text contains ANSI CSI, OSC, newlines or more visible characters than the terminal width.
- **Postcondition**: The text is sanitized, truncated to width minus one plus an ellipsis and padded exactly to the terminal width.
- **Invariant**: No data-derived escape sequence reaches the terminal and the row never wraps.

### C005 — conver/non-tty-display

- **Precondition**: stdout is not a TTY or the run uses --no-dashboard.
- **Postcondition**: No dashboard write occurs, including the NOW line.
- **Invariant**: Display hooks are no-ops when no dashboard exists.
