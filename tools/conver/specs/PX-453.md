# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-453: calc-monthly-icods CLI: monthly ICOD totals sharing draw-progress-gif usage math

## Background

Goal: add tools/conver/.claude/scripts/conver/calc-monthly-icods.js, a CLI that prints per-month ICOD totals as a terminal table. ICOD is the four-part metric used by the draw-progress-gif title bar: cache-miss input tokens in millions, cache-hit input tokens in millions, output tokens in millions, and cumulative USD. Purpose: let a user read monthly usage without rendering the GIF, while reusing the GIF aggregation and price table so the numbers agree. Motivation: the GIF ICOD is a cumulative ceiling-rounded value and cannot answer how much a single month consumed or cost. Constraints: no new dependencies; ESM on Node >=22; implement only inside tools/conver (root .claude and crates/siprs are installed copies that the user later refreshes with make install-to-projects); default range is the latest six months including the current month (M-5..M); the current month is month-to-date; --from and --to accept YYYY-MM and override the default range inclusively; output is a Unicode box table with right-aligned numerics and no ANSI; the same usage-cache.json path as draw-progress-gif is read and written; output must be deterministic; TDD Red-Green-Refactor is mandatory.

## Acceptance Criteria

- Happy: node calc-monthly-icods.js -t <workspace> prints the caption, a six-row Unicode table for the local months M-5..M and a TOTAL row, then exits 0.
- Happy: --from 2026-01 --to 2026-03 prints exactly the three requested inclusive months with monthly totals and a range TOTAL.

## Invariants

- [Normal establishment] For the same logs and range, the rendered table is byte-identical across runs; monthly token sums over the full series equal the final dailySeries cumulative token counts exactly, and monthly cost sums equal the final cumulative cost within 1e-9.
- [Error invariant] Any argument or target-path failure writes an [ERROR] line to stderr, emits no table on stdout, and exits 2; an unexpected failure exits 3. A missing log source is not an error: the CLI renders a zero or cached table, exits 0, and prints the reason as the first stdout line.
- [Internal invariant] formatMillions and formatDollars are the only display rounding; no ANSI escape is emitted except the first-line warning when stdout is a TTY and NO_COLOR is unset; column order and column widths are deterministic for the same rows.
- [Boundary invariant] Date bucketing uses displayDateKey(ms,ms); prices are DEFAULT_PRICES with no holidays and no overrides; the cache path is <target>/progress-gif/snapshots/usage-cache.json; TOTAL is exact-sum-then-ceil, never the sum of displayed cells.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — loop.js usageTitleSegments <-> icod.js formatIcodMetrics

- **Precondition**: cumulative usage object with non-negative integer cacheMissInputTokens, cacheHitInputTokens, outputTokens and a finite non-negative costUsd
- **Postcondition**: formatIcodMetrics returns the ceiling-rounded string ceil(miss/1e6)M / ceil(hit/1e6)M / ceil(out/1e6)M / $ceil(cost) and equals the ICOD block of usageTitleSegments for the same object

### C002 — usage.js dailySeries -> icod.js buildMonthlyUsageRows

- **Precondition**: dailySeries entries with a YYYY-MM-DD date, non-negative integer token fields and a finite non-negative dailyCostUsd
- **Postcondition**: for each month M the row tokens are the sum of entries whose date.slice(0,7) is M and the row costUsd is the sum of their dailyCostUsd; every month in the inclusive range appears and months without entries are zero
- **Invariant**: summing all monthly rows over the full series equals the final cumulative tokens exactly and the final cumulative cost within 1e-9

### C003 — clock -> icod.js resolveDefaultMonthRange

- **Precondition**: a valid Date now and span 6
- **Postcondition**: the result is from=YYYY-MM of now minus 5 months and to=YYYY-MM of now, inclusive, with correct year rollover

- **Precondition**: argv contains -t with an existing directory and optional --from/--to matching a real YYYY-MM month with from <= to
- **Postcondition**: valid input prints only the caption and table to stdout and exits 0; invalid input writes an [ERROR] line to stderr, prints no table, and exits 2
