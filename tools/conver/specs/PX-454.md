# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-454: conver.js: drive workspacify through crystalize end-to-end via -T, fixed SYSTEM-DESIGN.md inputs, and unconditional non-interactive execution

**Ticket Key**: PX-454 · **Phase**: -1

## Background

### Goal
Extend conver.js so one run can execute the complete pipeline from /workspacify-tree through /crystalize-readme, selected by -T, with strict cwd and stage-order discipline.

### Purpose
Make conver.js the complete self-driving pipeline driver rather than an implementation-only loop; every command it sends must complete without human judgment.

### Motivation
The upstream design stages are manual today. Dynamic path arguments (spec-file, tree manifest) and human-directed questions (explain, grill) block unattended execution. The three forward command scripts must therefore derive fixed workspace-root inputs, and conver must send an overriding non-interactive directive to the two stages whose command documents still allow a human question.

### Constraints
- The existing make,plan,start,review,resolve,consolidate,find loop must not change; the work is additive.
- -T accepts only a contiguous slice of the canonical order; gaps, reordering, duplicates, and counts on non-repeatable stages are startup errors.
- Only workspacify, educe and smooth execute at the workspace root; every other stage executes at the package root.
- A package-scoped count N means N full rounds over all packages; a workspace-scoped count N means N consecutive runs.
- Selected stages and repetitions are never skipped because a record says they are complete.
- /workspacify-reverse is out of scope; reverse subcommands keep their existing arguments.
- The command documents receive only minimal argument-contract edits; no new shell commands are added to them.

## Scope

## Acceptance Criteria

- Happy path: a -T run selects a contiguous slice, executes every selected stage in canonical order with the correct cwd and N repetitions, and completes the full workspacify through crystalize pipeline without human input.
- Error case: an invalid -T token or a missing fixed input exits conver non-zero with a named error before or at the affected stage; no partial session is opened for an invalid plan.
- Edge case: the default -T make,plan,start,review,resolve,consolidate,find is byte-identical to the current prompt, cwd and action derivation; explain and grill self-complete without human input, and grill does not use chosen_default to skip a decision.

### C001 — conver.js CLI -T option -> validated stage plan (operator selection)

- **Precondition**: A -T string is supplied, or the default make,plan,start,review,resolve,consolidate,find is used.

- **Precondition**: A stage plan selects a workspace-scoped or package-scoped stage.
- **Postcondition**: The executor opens the ACP session with cwd = workspace root for workspacify, educe and smooth, and cwd = package directory for every other stage.

- **Precondition**: A repeatable stage carries a count N greater than or equal to one.
- **Postcondition**: A workspace-scoped stage runs N consecutive times at the root; a package-scoped stage runs N full rounds over every selected package in implementation order.
- **Invariant**: A package-scoped stage is never run N consecutive times on one package.

### C004 — default -T -> existing runWorkspaceLoop and runPackageLoop

- **Precondition**: The default -T make,plan,start,review,resolve,consolidate,find is used.
- **Postcondition**: The composed prompt, session cwd, next-action derivation, resolve cadence, boundary handling and status transitions equal the current implementation.
- **Invariant**: No additive stage-plan or prompt-override code changes the default make..find path.

### C005 — conver stage -> forward command script argument surface

- **Precondition**: workspacify-tree, workspacify-allocate or educe-sequences is invoked with no argument or an empty token.
- **Postcondition**: The forward script resolves SYSTEM-DESIGN.md for workspacify-tree and educe-sequences, or WORKSPACIFY-TREE-MANIFEST.json for workspacify-allocate, at the workspace root cwd and verifies existence before proceeding.
- **Invariant**: A non-empty argument is refused, and reverse mode keeps its existing arguments.

- **Postcondition**: explain and grill receive the full CRITICAL NON-INTERACTIVE END-TO-END EXECUTION block plus, for grill, the prohibition on chosen_default skipping; educe receives only the fixed-argument override; every other stage receives exactly the current composePrompt output.

### C007 — stage plan -> executor repetition control

- **Precondition**: A stage plan selects a stage and a repetition count N.
- **Postcondition**: The executor runs the stage exactly N times per the cwd and repetition rules, regardless of existing status, history or artifact presence.
- **Invariant**: No selected stage or repetition is skipped because a record says it is complete.

- **Postcondition**: The gate requires only the artifacts the first selected stage needs; pre-split order comes from the allocate manifest implementation_order.levels and post-split order from WORKSPACIFY-IMPLEMENTATION-ORDER.json, with the model re-read after split.
