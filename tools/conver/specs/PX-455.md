# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-455: Add the drill stage and the five-loop workspace scheduler with exact command timing

**Ticket Key**: PX-455 · **Phase**: -1

## Background

### Goal
Make conver.js drive all five loops in one run: conformance (workspacify, educe), upstream (explain, grill, smooth, graphify, boundify, split), implementation (make, plan, start, review, resolve, consolidate, find), shipping (/crystalize-readme), and evolution (/drill-rfc-down). Before every command, recompute exactly one next action naming the loop, stage, package, phase, ticket, and command.

### Purpose
/crystalize-readme leaves RESIDUE; /drill-rfc-down turns it into tickets; the implementation loop must then absorb those tickets and the cycle repeats. The current -T engine traverses a fixed selection list once, so it cannot represent this cycle, cannot skip an upstream stage already satisfied on disk, and has no drill stage.

### Motivation
Command timing is the load-bearing contract. crystalize before every package reaches its endpoint, drill before every package is crystalized, or a missed return to implementation would corrupt both conver and every workspace it drives. The timing must be a total, deterministic function of artifacts plus a minimal in-run phase cursor, and it must be proven by exact-sequence tests.

### Constraints
The implementation loop internals (runPackageLoop, runTicketStep, deriveNextAction, boundary-state predicates) are unchanged. The default -T plan is unchanged. crystalize and drill have no persisted executed flag and no execution counter; they run at phase entry on every cycle. Upstream skip decisions use the existing counter readers in workspacify-order/lib/counters.mjs and the existing artifactStem helper; no second reader is created. All source, comments, logs, and test names are English.

## Acceptance Criteria

- [Happy path] -T make,plan,start,review,resolve,consolidate,find,crystalize,drill on a two-package workspace with a settled implementation runs crystalize for both packages, then drill for both; a drill that adds a ticket returns to implementation, and a drill that adds none completes; the command log matches the exact expected sequence.
- [Error case] -T drill:2, -T drill, and -T find,drill are refused with the named plan errors; a missing RFC-Dirs-Tree.json raises MISSING_STAGE_INPUT; a crystalize action while any package is not endpoint raises IMPLEMENTATION_NOT_SETTLED and issues no command.
- [Edge case] The default plan performs one implementation loop call and no ship or evolve command; -T crystalize performs ship only; -T crystalize,drill with ticket additions ends after evolve; a package added by drill forces implementation; an unreadable counter runs the stage.

## Invariants

- [Normal condition] Every scheduler step derives exactly one action from the current snapshot and run state, and that action belongs to the selected contiguous slice.
- [Error invariant] A missing stage input, a missing stage artifact, an unknown ticket status, or an unmet phase barrier raises a named error and issues no command.
- [Internal state invariant] The only in-run scheduler state is the phase, the ship and evolve cursors, the cycle baseline digests, and the remaining budget; every other fact is re-read from artifacts before each step.
- [Boundary invariant] crystalize runs only when every workspace package is at its implementation endpoint; drill runs only after crystalize finished for every workspace package; the run returns to implementation only when at least one package ticket-set digest changed during the cycle.

## Contracts — mandatory 100% test coverage in TDD Red phase

### C001 — five-loop timing: stage grammar

- **Precondition**: stage plan input selecting drill
- **Postcondition**: drill is accepted only after crystalize and with no count
- **Invariant**: drill remains the last canonical stage

### C002 — five-loop timing: upstream skip

- **Precondition**: a stage and package with a recorded execution count
- **Postcondition**: the stage is skipped when count reaches the target and runs when count is below it
- **Invariant**: an unreadable counter runs rather than skips

### C003 — five-loop timing: ship barrier

- **Precondition**: crystalize selected in the plan
- **Postcondition**: crystalize is issued for every package only after every package is endpoint
- **Invariant**: no crystalize command precedes the endpoint of every package

### C004 — five-loop timing: evolve barrier

- **Precondition**: drill selected in the plan
- **Postcondition**: drill is issued for every package only after crystalize finished for every package
- **Invariant**: no drill command precedes the completion of crystalize for every package

### C005 — five-loop timing: cycle return

- **Precondition**: evolve finished and a package ticket-set digest changed
- **Postcondition**: the next action is the implementation phase
- **Invariant**: a changed digest always returns to implementation before any completion

### C006 — five-loop timing: completion

- **Precondition**: evolve finished and every package digest is unchanged
- **Postcondition**: the scheduler returns complete with no further command
- **Invariant**: ticket counts are never the completion predicate

### C007 — five-loop timing: derivation

- **Precondition**: a pipeline snapshot and run state
- **Postcondition**: exactly one action is returned from the allowed set
- **Invariant**: derivation is deterministic and total

### C008 — five-loop timing: drill invocation

- **Precondition**: a drill action for a package
- **Postcondition**: the command is /drill-rfc-down with zero argv in the package directory and DRILL_OVERRIDE
- **Invariant**: the default prompt composition remains byte-identical
