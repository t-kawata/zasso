# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

The current annotate-ticket-context-by-git-diff.js injects annotations at the first definition in a file regardless of where the actual git diff changes occurred. This creates false provenance links — annotations are placed on code the ticket never touched.\n\nA scope detection engine is required that can answer: 'which definition scope contains a given line number?' The engine must support:\n- Brace depth tracking (for Rust, Go, TS/JS, C#, Java, Kotlin, Swift)\n- Indentation-based fallback (for Python, Ruby)\n\nThis is Ticket-1 of 2 (PX-62 rewrites the annotation pipeline to consume this engine).\n\n### Goal\nProvide a pure-function module findContainingDefinition(lines, targetLine) that, given a source file's lines and a 0-indexed line number, returns the innermost definition (function/struct/class/enum/trait/impl/interface) that contains that line, or null if the line belongs to no definition.\n\n### Purpose\nEliminate false provenance links caused by the current 'first-definition-in-file' heuristic. Every annotation must point to the actual definition the ticket changed, not an unrelated one higher in the file.\n\n### Motivation\nCurrent approach is architecturally broken: detectFirstDefinition() returns the first fn/class/struct in the file, which has zero correlation with the actual git diff changes. ## Acceptance Criteria

- [Happy path] Given a file containing fn foo() { fn bar() {} }, targetLine pointing at a line inside bar returns {startLine: bar-line, name: "bar", kind: "function"} — the innermost containing definition is returned.
- [Happy path] Multiple brace levels correctly identified at varying depths — e.g. a line inside an if inside a method inside a class returns the method (innermost function definition), not the class.
- [Error case] targetLine with no containing definition (e.g. line 0 in `\nfn foo() {}`) returns null.
- [Error case] Unmatched closing brace `}` at depth 0 does not crash or produce negative depth — reset to 0.
- [Edge case] Brace inside a string literal `"hello { }"` or comment `// { }` or regex `/foo{1,3}/` is ignored for depth tracking.
- [Edge case] Python indentation-based scope detection handles mixed tabs/spaces by normalizing to spaces (1 tab = 8 spaces).
- **[Happy path] — Describe the scenario that confirms this ticket is complete:**\n  - All 18 UT and 2 IT pass. findContainingDefinition correctly identifies the containing definition for any changed line across all 13 supported source extensions.
- **[Error case] — Describe an error scenario the feature must handle:**\n  - A file with syntax errors (unmatched brace, incomplete function) does not crash; the engine returns best-effort results for lines before the corruption and null for lines after.
- **[Edge case] — Describe any boundary or exception to verify:**\n  - A line that is itself a definition line (e.g. `fn foo() {`) — the engine must return that definition as containing itself (startLine === targetLine).

## Invariants

- [Normal condition] Brace depth counter always starts at 0 at the beginning of each file scan and accurately reflects current nesting: every `{` increments, every `}` decrements. Indentation level is computed from the first non-comment, non-empty line of each definition.\n- [Error invariant] Even if the source file has malformed braces (unmatched `{` or `}`), depth never goes negative. An unmatched `}` at depth 0 resets to depth 0 (graceful degradation). findContainingDefinition still returns the best-effort result for lines before the corruption.\n- [Internal state invariant] The brace-tracking state machine's string/comment context flags (inString, inLineComment, inBlockComment) are mutually exclusive. Exactly one flag is active at any line position. The state machine transitions correctly on all escape sequences (\", \\, etc.).\n- [Boundary invariant] Lines 0 through lines.length-1 are valid inputs. targetLine < 0 and targetLine >= lines.length always return null. Empty file (lines.length === 0) always returns null for any targetLine.
