# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-62: Rewrite annotation injection to use changed-line-based definition targeting

**Ticket Key**: PX-62 · **Phase**: -1

## Background

Currently annotateSourceFiles() uses git diff --name-only (file-level only) and processFile() calls detectFirstDefinition() which finds the first definition in the entire file. After PX-61 provides findContainingDefinition(), the annotation pipeline must be rewritten to:\n1. Use git diff -U0 to obtain precise changed line numbers\n2. Map each changed line to its containing definition via findContainingDefinition\n3. Deduplicate definitions (multiple changed lines in the same function = 1 annotation)\n4. Inject annotations at each containing definition's start line (not just the file's first definition)\n\nThis is Ticket-2 of 2, depending on PX-61.\n\n### Goal\nRewrite annotateSourceFiles(), processFile(), and verifyAnnotations() to use changed-line-based definition targeting via findContainingDefinition, eliminating the current first-definition heuristic entirely.\n\n### Purpose\nEvery annotation comment must be placed at the actual definition containing the changed lines, not at an unrelated definition. This is the core fix for false provenance links.\n\n### Motivation\nThe current architecture (detectFirstDefinition) is fundamentally broken — it places annotations on code the ticket never touched. This violates the 'Comments must encode provenance' principle and must be fixed before any further ticket processing can rely on annotation accuracy.\n\n### Constraints\n- Must keep the existing CLI interface unchanged (--ticket-key, --verbose, --verify, --check-ambiguous)\n- Must keep mergeAnnotation(), buildAnnotation(), insertAnnotation() unchanged (these are correct)\n- Git diff -U0 parsing must handle unified diff format, new files, binary files, and renamed files\n- Changed lines not containing any definition (e.g. import additions, const declarations) must fall back to [::AMBIGUOUS::]\n- Existing exports (module.exports) must be preserved for testing

## Investigation

- [Evidence gathered from source code analysis]\n\n**Current git diff usage (annotateSourceFiles, lines 272-331):**\n- Line 278-279: `git diff --name-only --diff-filter=AM` — only returns file names, no line numbers.\n- Line 289-294: `git ls-files --others --exclude-standard` — untracked files (new additions). For untracked files, ALL lines are effectively changed.\n\n**What git diff -U0 outputs (example):**\n```\ndiff --git a/src/foo.rs b/src/foo.rs\nindex abc123..def456 100644\n--- a/src/foo.rs\n+++ b/src/foo.rs\n@@ -10,5 +10,7 @@ impl Foo {\n     fn bar() {\n-        old_line\n+        new_line\n+        another_new_line\n     }\n }\n```\nThe hunk header `@@ -10,5 +10,7 @@` means: old start 10 (5 lines), new start 10 (7 lines). The added lines are new lines 10-16 (7 lines starting from 10). Actually, in unified diff, +10,7 means 7 lines starting at line 10 in the new file. Among those 7, the lines that were originally present (context lines) + added lines = 7 total. The actual "changed" lines (added) are those prefixed with + (not ++). But for annotation purposes, we need ALL lines in the new file that are affected — both context and added lines, since context lines indicate the function was modified.\n\nActually, let me reconsider. For annotation, we want to annotate the definition if ANY line within it was touched. So we should collect all line numbers in the new file that appear in any hunk — both context and added lines. If a hunk is `@@ -10,5 +10,7`, then new file lines 10-16 (7 lines) are affected. We should check if any of those lines fall within a definition.\n\n**Note on untracked files:** For untracked files, there's no git diff output. We must read the file's content and annotate ALL definitions in the file (since every line is "new"). This is the same behavior as the current "first definition" but now per-definition.

## Acceptance Criteria

- [Happy path] An annotation is placed at the containing definition of each changed line, NOT at the file's first definition — verified via --verify returning {missing: 0}.
- [Happy path] Multiple changed lines in the same function produce exactly 1 annotation (deduplication works).
- [Error case] git diff fails (non-git dir) gracefully reports 0 files without crash.
- [Error case] Changed line without a containing definition (e.g. import line, top-level const) falls back to [::AMBIGUOUS::] marker.
- [Edge case] Same file changed by two different tickets → mergeAnnotation correctly integrates both ticket keys.
- [Edge case] Config-only or doc-only change (no source files touched) — annotation script exits silently with {total: 0}.
- **[Happy path] — Describe the scenario that confirms this ticket is complete:**\n  - Create a temp git repo with a multi-definition source file, make a change in the second definition, run annotation — annotation appears at the second definition, not the first. --verify passes.
- **[Error case] — Describe an error scenario the feature must handle:**\n  - Run from outside a git repo: parseGitDiffUnified0 fails (execFileSync throws), catch block returns {total:0} with no crash.
- **[Edge case] — Describe any boundary or exception to verify:**\n  - All 30 lines of a 30-line function changed: parseGitDiffUnified0 produces 30 added line numbers, changedLinesToDefinitions maps all 30 to the same containing definition, deduplicateDefinitions produces 1 unique definition → 1 annotation.

## Invariants

- [Normal condition] Every source file modified or added by the current ticket has exactly one annotation per containing definition that was changed. No annotation is placed on definitions that were not modified.\n- [Error invariant] If git diff fails (not a git repo, git error), the script gracefully reports {total: 0, annotated: [], skipped: [], errors: []} without crashing or corrupting files.\n- [Internal state invariant] The mapping from changed lines to definitions is 1-to-1 before deduplication and many-to-1 after: every changed line maps to exactly one containing definition (or [::AMBIGUOUS::]), and every containing definition receives at most one annotation.\n- [Boundary invariant] A changed line that is itself a definition start line (e.g. `fn foo()` was added) receives an annotation at that line (self-containing). A changed line at the very start of the file (line 0) is handled identically.
