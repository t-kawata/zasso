# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

PX-62 rewrote buildAnnotation() and buildMultiAnnotation() to use [::TICKET::] format. However detectAnnotationLine() still uses old regex patterns that do not match the new format, causing mergeAnnotation() to fail on future runs. This gap means stacked duplicate annotations will accumulate on subsequent executions.

### Goal
Make detectAnnotationLine() correctly parse the new [::TICKET::] annotation format so that mergeAnnotation() can detect and merge existing annotations on future runs.

### Purpose
Prevent duplicate stacked annotations from accumulating every time the annotation script runs on a previously annotated function. The merge mechanism (mergeAnnotation) only works if detectAnnotationLine can parse the existing annotation.

PX-62 changed the output format to [::TICKET::] but forgot to update the parser. This is a regression: the annotation system no longer detects its own annotations. Every subsequent /start-ticket execution that touches the same function will stack a new annotation line instead of merging into the existing one.

## Investigation

- [Evidence gathered from source code analysis]

**Current state of detectAnnotationLine()** (annotate-ticket-context-by-git-diff.js, lines 80-96):

```javascript
function detectAnnotationLine(line) {
  if (typeof line !== "string" || !line.trimStart().startsWith("//")) {
    return null;
  }
  // Multi-format: "implemented under tickets: KEY, KEY;"
  const multiMatch = line.match(/implemented under tickets:\s*([^;]+);/);
  if (multiMatch) {
    const keys = multiMatch[1].split(",").map((k) => k.trim()).filter(Boolean);
    return keys.length > 0 ? { ticketKeys: keys } : null;
  }
  // Single-format: "implemented under the KEY ticket"
  const singleMatch = line.match(/implemented under\s+the\s+(P\\d+-\\d+|PX-\\d+)\s+ticket/);
  if (singleMatch) {
    return { ticketKeys: [singleMatch[1]] };
  }
  return null;
}
```

**Current output format** (lines 49-53 and 60-67):
- Single: `// [::TICKET::] PX-63 changes. Details: \`node ... --ticket-key=PX-63 ...\``
- Multi: `// [::TICKET::] PX-61, PX-62 changes. Details: \`node ... --ticket-key=(PX-61|PX-62) ...\``

**Key mismatch**: Single regex looks for "implemented under the KEY ticket" but annotations now contain "[::TICKET::] KEY changes. Details:". Multi regex looks for "implemented under tickets: KEY, KEY;" but annotations now contain "--ticket-key=(KEY|KEY)".

**Affected callers** (all unchanged):
- detectAnnotationAtLine (line 103) — calls detectAnnotationLine at a specific line offset
- mergeAnnotation (line 118) — calls detectAnnotationLine to check existing annotation format

## Acceptance Criteria

- [Happy path] Single format "// [::TICKET::] PX-63 changes. Details: `node ...`" returns {ticketKeys: ["PX-63"]}
- [Happy path] Multi format "// [::TICKET::] PX-61, PX-63 changes. Details: `node ... --ticket-key=(PX-61|PX-63)`" returns {ticketKeys: ["PX-61", "PX-63"]}
- [Error case] Regular comment "// hello world" returns null
- [Error case] Code line "let x = 1;" returns null
- [Edge case] Malformed "// [::TICKET::]  changes. Details: ..." (empty key) returns null
- [Edge case] Empty string returns null

## Invariants

- [Normal condition] A line matching /\[::TICKET::\] ... changes. Details:/ always returns a non-null result with the correct ticket keys extracted
- [Error invariant] Non-comment lines and non-annotation comments always return null. The function never throws.
- [Internal state invariant] The two regex patterns are mutually exclusive: multi-format (parenthesized --ticket-key=(A|B)) is checked first, single-format (bare --ticket-key=KEY) is checked second
- [Boundary invariant] Empty string and whitespace-only strings return null. Ticket key patterns (P\d+-\d+ and PX-\d+) match only valid keys, not arbitrary text
