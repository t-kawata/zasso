# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Background

AMBIGUOUS marker resolution currently relies on AI manually editing files. This is fragile: AI may produce a non-TICKET format comment, breaking the detect--merge cycle.

### Goal
Create a script that mechanically lists definitions in an AMBIGUOUS-flagged file and mechanically inserts a TICKET annotation at a line the AI specifies, then removes the AMBIGUOUS marker.

### Purpose
Eliminate all AI hand-editing of annotation format. AI's only role is to look at the structured output and decide which definition line is correct. The script guarantees the annotation format is always produced by buildAnnotation().

### Motivation
Current start-ticket.md Step 5a Phase 2 instructs AI to manually insert a comment and remove AMBIGUOUS. This is the last remaining path where a non-TICKET format comment could enter the codebase. With PX-63, all automated paths guarantee TICKET format. This ticket closes the manual gap.

### Constraints
- Must import and reuse buildAnnotation(), insertAnnotation(), detectAnnotationLine(), detectFirstDefinition() from annotate-ticket-context-by-git-diff.js
- Must NOT duplicate any annotation format logic
- listDefinitions must be read-only (no file mutation)
- injectAt must be the only file-mutating operation
- Both modes must output structured JSON for reliable AI consumption

## Investigation

- [Evidence gathered from source code analysis]

**Current AMBIGUOUS resolution flow** (start-ticket.md Step 5a Phase 2):
```
1. Read each reported file
2. Identify the first meaningful definition
3. Insert the annotation comment in the standard format at that location
4. Delete the [::AMBIGUOUS::] marker line
5. Re-run --check-ambiguous
```
Steps 2-4 are all manual AI editing with no format enforcement.

**Available functions to import** (from annotate-ticket-context-by-git-diff.js):
- buildAnnotation(ticketKey) -> produces '// [::TICKET::] KEY changes. Details: ...'
- insertAnnotation(lines, lineIndex, comment) -> returns new lines array
- detectAnnotationLine(line) -> parses TICKET format
- detectFirstDefinition(lines) -> finds first definition line
- filterSourceFiles(filePaths) -> filters by extension

**AMBIGUOUS marker format** (from processFile()):
```javascript
const ambiguousComment = `// [::AMBIGUOUS::] Could not locate containing definition for changed line(s) in ticket ${ticketKey} - AI must resolve placement.`;
```
The marker is always at the top of the file, inserted as the first line.

## Acceptance Criteria

- [Happy path] listDefinitions on valid file with AMBIGUOUS returns JSON: {definitions: [{startLine, name, kind}...], ambiguousLine: 'the marker text'}
- [Happy path] injectAt with line number from listDefinitions output inserts TICKET annotation, removes AMBIGUOUS line, file is valid
- [Error case] listDefinitions on file without AMBIGUOUS returns {definitions: [...], ambiguousLine: null} — not an error
- [Error case] injectAt with line number beyond file length returns {success: false, error: 'line number out of range'}
- [Edge case] injectAt at line 0 inserts annotation at file start and removes AMBIGUOUS marker correctly

## Invariants

- [Normal condition] listDefinitions always returns a JSON object with definitions array and ambiguousLine string
- [Error invariant] On file read error, both modes return {success: false, error: message} and exit 1. No partial writes.
- [Internal state invariant] injectAt uses buildAnnotation() to generate the TICKET comment — the format is always correct regardless of AI input. The AMBIGUOUS marker is removed by filtering it out of the file content, not by position-based deletion.
- [Boundary invariant] injectAt with line 0 inserts the annotation at the very beginning of the file content (before line 0). injectAt with the last definition line + 1 is an error.

## Boy Scout Rule

- **Translatability improvements:**
  1. The script has exactly two modes named as verb phrases (listDefinitions, injectAt) — clear intent
  2. Both modes are pure mechanical operations with well-defined inputs and outputs — no AI judgment needed
  3. The mode separation (read-only vs mutate) ensures AI cannot accidentally cause side effects during the investigation phase
  4. All annotation format generation delegates to buildAnnotation() — no format string duplication
