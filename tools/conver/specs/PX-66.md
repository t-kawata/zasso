# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

# Target ticket is PX-66: Schema Foundation — edge + ticket に contracts 必須フィールド追加

**Ticket Key**: PX-66 · **Phase**: -1

## Background

### Goal
edge.schema.json と tickets-schema.json に contracts 必須フィールドを追加し、全パイプラインが契約情報を運搬できる基盤を確立する。validate-tickets.js と validate-edge-contracts.js により contracts の欠落を BLOCK する。

### Purpose
現在のエッジは type（depends_on / implements 等）と note（240文字制限）のみで関係性を表現。contracts 配列を必須とすることで全エッジ接続が明示的な事前条件・事後条件・不変条件を持つことが強制される。

### Motivation
contracts は全契約パイプラインの基盤。PX-67〜PX-71 の全チケットがこのスキーマに依存する。

### Constraints
- 後方互換不要。既存の全 GRAPH.json / Tickets.json は再生成
- contracts は必須（required）、空配列禁止（minItems:1）
- 既存エッジフィールド（from/to/type/attributes）は変更しない
- tickets-schema.json の additionalProperties: true は維持

## Scope

- 【変更】.claude/scripts/rfc-graph/schema/edge.schema.json — properties に contracts 追加、required に contracts 追加。contracts は配列（minItems:1）、各要素は id(C000)/precondition/postcondition/invariant を必須。additionalProperties:false 維持。
- 【変更】.claude/scripts/tickets/tickets-schema.json — ticket 定義の required に contracts 追加。contracts は配列、各要素は id/sourceEdge/precondition/postcondition/invariant を必須。additionalProperties:true 維持。
- 【変更】.claude/scripts/lib/validate-tickets.js — arrayFields に contracts 追加。各契約要素の precondition/postcondition/invariant が非空文字列であることの検証ロジックを追加。
- 【新規】.claude/scripts/tickets/validate-edge-contracts.js — GRAPH.json の全エッジの contracts 配列をスキーマ検証。3-line error template で違反報告。exit 1 on failure。
- 【非スコープ】crud.js の update-edge への contracts 対応 — PX-67（annotate-contracts）で対応。このチケットはスキーマ定義と検証スクリプトのみ。
- 【影響範囲】crud.js create-edges — 将来的に contracts 必須化が必要だが PX-67 で対応。

[Existing tickets-schema.json ticket.definitions]
- 現在の必須フィールド: id, phaseId, title, status

[Existing validate-tickets.js]
- validateTickets() が全チケット走査
- arrayFields に contracts は未登録。strFields にも未登録（contracts は配列要素がオブジェクト）
- 変更点: arrayFields に contracts 追加 + 各要素の precondition/postcondition/invariant の string チェック追加

## Acceptance Criteria

- **[Happy path]** edge.schema.json が Ajv コンパイル可能で contracts 必須スキーマとして動作。validate-tickets.js が contracts ありチケットを PASS。validate-edge-contracts.js が適正 GRAPH.json を PASS。
- **[Error case]** contracts なし GRAPH.json → validate-edge-contracts.js が BLOCK（exit 1）。contracts なしチケット → validate-tickets.js が BLOCK（exit 1）。
- **[Edge case]** contracts 空配列のエッジ → BLOCK。precondition/postcondition/invariant のいずれかが空文字 → BLOCK。contracts.id に重複 → BLOCK。

## Invariants

- 【Normal establishment】全エッジが contracts 配列を持ち、各契約が precondition/postcondition/invariant を非空文字列として持つ。
- 【Invariant on error】contracts 検証失敗時も GRAPH.json / Tickets.json の他のデータ構造は一切変更されない（読み取り専用検証）。
- 【Internal state invariant】validate-tickets.js と validate-edge-contracts.js は副作用ゼロ。ファイル読み取り + 検証 + 結果出力のみ。
- 【Boundary invariant】contracts 配列の最小長は 1（空配列不許可）。precondition/postcondition/invariant の最小長は 1 文字（空文字不許可）。

## Boy Scout Rule

- edge.schema.json: contracts.id を C000 形式（^C[0-9]{3}$）とし、グラフ全体で一貫した命名規則を強制。既存の note（maxLength 240）は維持するが、契約情報は contracts に移行。
- validate-tickets.js: contracts 検証ロジックを既存の arrayFields ループと並立する独立ブロックとして実装し、既存ロジックとの干渉を防ぐ。
- validate-edge-contracts.js（新規）: エラー出力形式は既存の verify.js と同一の 3-line template（[ERROR] / Cause: / Action:）を採用しツール間の一貫性を保つ。
