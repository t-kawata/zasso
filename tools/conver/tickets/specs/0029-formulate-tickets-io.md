# formulate-tickets コマンド群への I/O 境界・不変条件明確化

## Summary

`.claude/commands/formulate-tickets.md` および `formulate-tickets-for-next.md` において、「各チケットは「1チケット・1不変条件」を徹底し」とある「不変条件」の定義を曖昧から明確に改める。不変条件とは「I/O境界における契約の正しさ」であることを明記し、チケットの区切り方と完了判定基準を具体化する。併せて Rust / Go / TypeScript の3言語に対する I/O 境界マッピング表を追記する。

**改修の性質**: 書き直しではなく、既存全文を保持した上での追記と修正。既存の CLI スクリプト、Tickets.json スキーマ、他コマンドとの連携に一切の影響を与えない。

## Background

2026-07-01 の設計レビューにおいて、以下の認識のずれが明らかになった：

- 既存文書では「不変条件」とだけ書かれているが、これが「コード内部で常に成り立つ性質」なのか「コンポーネント境界での契約」なのかが定義されていない
- 実際には「不変条件 = I/O境界における契約の正しさ」であり、チケットのテストはこの契約が守られていることを検証するものであるべき
- 既存の5層モデル（Layer 0〜4）の各層間は本質的にI/O境界であり、不変条件の自然な配置場所だが、そのことが明示されていない
- Rust / Go / TypeScript という具体的な言語での実装時に「不変条件がどの言語要素（pub fn / func / export function / struct / trait等）に対応するか」が即座に判断できない

この改修により、設計書を読む開発者が「1チケット」を正確に区切れるようになり、チケット完了の判断基準が明確になる。

### 具体的な改修内容

1. **「不変条件」の定義拡充（両ファイル・役割セクション）**
   - 既存文: `各チケットは「1チケット・1不変条件」を徹底し、外部I/Oを排除したメモリ内完結の検証可能な単位に区切る。`
   - 追記: この直後に、不変条件とは「そのチケットが実装する I/O 境界において外部と交わす契約」であることを説明する段落を追加する

2. **I/O 境界と言語要素のマッピング表（両ファイル・Step 3 層モデル直後）**
   - 5層モデル（Layer 0〜4）の説明の直後に、各層の I/O 境界が Rust / Go / TypeScript のどの言語要素に対応するかを示すマッピング表を追記する

3. **チケット分解基準の明確化（両ファイル・Step 4 フェーズ設計）**
   - チケットは「I/O 境界の単位で区切る」ことを明記。その単位とは `pub fn`, `trait`, `struct`, `func`, `interface`, `export function`, `class`, `crate`, `package`, `module` などの具象言語要素であることを追記する

### 変更しないもの（Non-scope に含む）

- CRUD スクリプト群（.claude/scripts/tickets/）は一切変更しない
- 5層モデル自体の構造は変更しない（「不変条件」の解釈のみ明確化）
- 既存のフェーズ設計手順（第1段階〜第4段階）は変更しない
- 既存の各Stepの実装スクリプト呼び出しパターンは変更しない

## Investigation

### 証拠1: 改修対象の該当行特定

**formulate-tickets.md** 7行目:
```

```

**formulate-tickets-for-next.md** 7行目:
```
各チケットは「1チケット・1不変条件」を徹底し、外部I/Oを排除したメモリ内完結の検証可能な単位に区切る。
```

両ファイルとも冒頭の役割説明に同一の文章が存在する。ここに、今まで定義されていなかった **「不変条件」の意味** を追記する必要がある。

### 証拠2: 5層モデルの記載位置

**formulate-tickets.md**: 150〜162行目（Step 3）
**formulate-tickets-for-next.md**: 170〜182行目（Step 3）

各層にはすでに「外部依存」の列がある。この表の直後に、各層の I/O 境界がどの言語要素に対応するかのマッピング表を追記する余地がある。

### 証拠3: 言語マッピングの不在

現状、どのファイルにも Rust / Go / TypeScript の言語固有概念（`pub fn`, `trait`, `struct`, `func`, `interface`, `export function`, `class` 等）に関する記述は一切存在しない。プロジェクトはこれらの3言語で実装されているため、追記が有効である。

### 証拠4: 既存ファイルサイズ

- `formulate-tickets.md`: 299行 / 14,241 bytes
- `formulate-tickets-for-next.md`: 320行 / 15,723 bytes

両ファイルとも十分な余裕があり、追記による可読性低下のリスクは低い。

### 証拠5: 会話ログに基づく設計判断

本セッション（2026-07-01）でのやり取りにより、以下の合意が形成された：

1. 「不変条件」は「コード内部の正しさ」ではなく「I/O境界における契約の正しさ」を意味する
2. チケット完了判定はその契約がテストで検証されたかどうかで行う
3. I/O 境界の言語マッピングは参照テーブルとして分離し、核心原則は言語非依存に保つ
4. 改修は「書き直し」ではなく「追記・明確化」に留める

## Notes

### 設計上の判断理由

**なぜ Tickets.json のスキーマ拡張をしないのか**: 今回の改修は「設計書を読む人間の理解を助ける」ためのものであり、データ構造の変更は必要最小限に留める。I/O 境界の情報は既存の `scope` フィールド（型シグネチャを含む形で記述）や `testUnit` フィールドで表現可能であり、新規フィールド追加は過剰である。

**なぜ言語マッピングを別テーブルにするのか**: 核心原則（不変条件 = I/O境界の契約）は言語非依存で記述し、言語固有の具体化は参照テーブルとして分離することで、第4の言語が追加された場合のメンテナンスコストを低減する。

### 依存関係

- 先行実装必須のチケットはなし（独立した文書改修）
- 改修後に、必要に応じて formulate-tickets コマンドを実行して動作確認を行う
