# I/O境界参考情報テンプレート挿入スクリプト

## Summary

grill-me-for-rfc 及び drill-rfc-down の完了ステップとして、RFC ファイルに「split-rfc-to-children のための参考情報 — RFC設計書が示す I/O 境界の手がかり」セクションを機械的に挿入するスクリプトを作成する。テンプレート内の RFC 固有記述が必要な箇所には `<!-- [::IO-INFO-STUB::] ??? -->` 形式のマーカー付きプレースホルダーを置き、AI 自身が内容を記入する方式とする。マーカーが残存していないかを検証する工程も含め、すべてをスクリプトで自動化する。

## Background

### 発端

`/drill-rfc-down` を siprs crate の RFC-ROOT.md に対して実行した際、「split-rfc-to-children を実行する際に安全の参考になる I/O 境界やテストの境界の参考情報」を RFC 内に書き込むべきとの結論に至った。RFC-ROOT.md には Sec 61 としてこのセクションが追記されたが、この作業は現状手動であり、今後の全 RFC に対して同じ品質のセクションを機械的に挿入・検証できる仕組みが必要である。

### 既存の参考実装

RFC-ROOT.md の Sec 61 では、以下のような書き方を採用している：
- 「観測された自然な I/O 境界」として、決めつけずに候補を示す
- 「本セクションの目的と限界」で、参考情報であり事前設計ではないことを明記
- 各境界の属性（同期/非同期、データ形式、結合手段、テスト独立性）を表で示す

このスタイルをテンプレートとして再利用する。

### 決定方式

- テンプレート挿入はスクリプトで機械的に行う
- プレースホルダーには `<!-- [::IO-INFO-STUB::] ここには何を記述すべきかの指示 -->` の形式で AI への指示を埋め込む
- 内容の記入は AI 自身が行う（人間が書くのではない）
- `[::IO-INFO-STUB::]` マーカーの残存を grep で検証し、0 件になるまで「完成宣言」をブロックする

## Scope

### 新規作成するスクリプト

`~/shyme/zasso/tools/conver/.claude/scripts/` 内に以下のスクリプトを作成する：

1. **`insert-io-boundary-template.js`** — 指定された RFC ファイルに対して、I/O 境界参考情報セクションのテンプレートを挿入する。以下の機能を持つ：
   - 入力: RFC ファイルパス
   - 出力: 当該 RFC にテンプレートを追記する
   - テンプレート内で RFC 固有の記述が必要な箇所には `<!-- [::IO-INFO-STUB::] ??? -->` 形式のマーカー付きコメントを挿入する
   - ??? の部分は「何を書くべきか」の説明（例: 「この RFC で使われている主要な型とその I/O 境界の対応表を記述してください」）
   - 既に同名セクションが存在する場合はスキップする（追記の追記を防ぐ）

2. **`check-io-stubs.js`** — RFC ファイル内に `[::IO-INFO-STUB::]` マーカーが残存していないか検証する。
   - 入力: RFC ファイルパス
   - 出力: マーカー残存数と該当行一覧（0 件の場合は成功終了コード 0）
   - 終了コード: 0 = クリア, 1 = 未記入の stub が残っている

### テンプレート内容

テンプレートは RFC-ROOT.md Sec 61 のスタイル（謙虚で決めつけない書き方）を踏襲し、以下のサブセクションを持つ：

| サブセクション | 内容 | RFC 固有記述が必要か |
|--------------|------|-------------------|
| 観測された自然な I/O 境界 | B1 から Bn までの境界候補の一覧表 | yes（どの境界があるかは RFC ごとに異なる） |
| 境界の属性 | 各境界の同期/非同期、データ形式、結合手段、テスト独立性 | yes（表の内容は RFC ごとに異なる） |
| 分割時に注意が必要な依存関係 | 循環または暗黙的依存の指摘 | yes（RFC ごとに依存関係が異なる） |
| テスト分割への参考 | 各境界で切った場合のテスト構成の考察 | yes（テスト分割方針は RFC ごとに異なる） |
| 分割後のファイル構成（一案） | 具体的なファイルツリーの提案 | yes（RFC ごとに異なる） |
| 参考: 本セクションの目的と限界 | 決めつけない但し書き（固定テンプレート） | no（全 RFC で共通） |

### 修正するコマンド定義ファイル

以下の 4 ファイルの「完成宣言」ステップの前に、新たなステップを追加する：

1. `~/shyme/zasso/tools/conver/.claude/commands/grill-me-for-rfc-ja.md`
2. `~/shyme/zasso/tools/conver/.claude/commands/grill-me-for-rfc-en.md`
3. `~/shyme/zasso/tools/conver/.claude/commands/grill-me-for-next-rfc-ja.md`
4. `~/shyme/zasso/tools/conver/.claude/commands/drill-rfc-down.md`

追加するステップの流れ：
```bash
# ステップ N: I/O 境界参考情報の追記
node "$SCRIPT_DIR/insert-io-boundary-template.js" "$TARGET_RFC"

# AI による内容記入（AI がテンプレート内の [::IO-INFO-STUB::] を読み、既存RFC記述から内容を生成して埋める）

# ステップ N+1: 記入漏れ検証
node "$SCRIPT_DIR/check-io-stubs.js" "$TARGET_RFC"
if [ $? -ne 0 ]; then
  echo "エラー: 未記入の [::IO-INFO-STUB::] マーカーが残っています。AI による内容記入が不完全です。"
  exit 1
fi

# 元の「完成宣言」ステップへ進む
```

## Non-scope

- RFC の内容自体の設計判断の質を保証するものではない
- I/O 境界の正しさを保証するものではない（参考情報であり、実際の分割時に新たな発見があればそちらを優先する）
- 既存の RFC に遡って一括挿入するバッチ処理は含めない（各コマンドの完了時に 1 ファイルずつ処理する）
- 人間が内容を記入する作業は一切含めない（すべて AI が行う）

## Investigation

### 事前調査: RFC-ROOT.md Sec 61 の構造

セクションの階層:
```text
## 61. split-rfc-to-children のための参考情報 — RFC設計書が示す I/O 境界の手がかり
### 61.1 観測された自然な I/O 境界
### 61.2 境界の属性
### 61.3 分割時に注意が必要な依存関係
### 61.4 テスト分割への参考
### 61.5 分割後のファイル構成（一案）
### 61.6 参考: 本セクションの目的と限界
```

このうちテンプレートとして固定できるのは 61.6 のみ。61.1〜61.5 は RFC ごとに異なる内容が入る。

### RFC ごとに異なる内容が必要な箇所の分析

各 RFC には以下のような固有情報が存在し、それに基づいて I/O 境界が異なる：

| 固有情報の種類 | テンプレート内での出現箇所 |
|--------------|--------------------------|
| その RFC で定義されているモジュール/クレート構造 | 61.1（境界の候補一覧） |
| 公開 API の型一覧 | 61.2（境界のデータ形式） |
| 非同期/同期待殊パターン | 61.2（同期/非同期属性） |
| 既存の FFI/unsafe 境界 | 61.1（FFI 境界の候補） |
| テスト構成と Docker 依存 | 61.4（テスト分割） |
| 開発中の crate 構成 | 61.5（分割後のファイル構成） |

### 既存コマンド定義ファイルの調査

4 つのコマンドファイルにおける「完成宣言」前後のステップを確認し、挿入位置を特定する必要がある（plan-ticket 時に実施）。

## Test Plan

### ユニットテスト計画

スクリプトは Node.js（CommonJS）で実装する（conver プロジェクトの既存スタイルに従う）。

| テスト対象 | 正常系 | 異常系 | 境界値 |
|-----------|--------|--------|--------|
| `insert-io-boundary-template.js` テンプレート挿入 | 既存 RFC にテンプレートが正しい位置に挿入される | 既にテンプレートが存在する RFC には挿入しない（二重挿入防止） | 空のRFC、最小構成のRFC |
| `insert-io-boundary-template.js` プレースホルダー | マーカー `[::IO-INFO-STUB::]` が正しい箇所に埋め込まれる | — | マーカーが適切な説明文を含んでいるか |
| `check-io-stubs.js` 検証 | マーカー 0 件で exit 0 | マーカー 1 件以上で exit 1 | マーカーが大量にある場合の出力 |
| コマンド定義ファイルの修正 | 挿入位置が正しい（完成宣言の直前） | — | — |

### ユニットテスト不可能な項目（例外）

- **実コマンド定義ファイルへの修正の検証**: テキスト編集の正しさはコードレビューで確認する
- **AI による内容記入の品質**: 記入内容の正しさは検証できない（マーカーの有無のみ確認する）

## Boy Scout Rule — 翻訳可能性計画

- スクリプト内の関数名は処理内容を動詞句で表現する（`insertIoBoundaryTemplate`, `checkForRemainingStubs` 等）
- マジックナンバー（特定の文字列パターン等）は名前付き定数として定義する
- エラーハンドリングは `console.error` で行い、`exit 1` で終了する（握りつぶし禁止）
- コマンド定義ファイルの修正も最小差分（Surgical Diff）で行う
