# RFC完全性検証＋コメントクリーンアップ

## Summary

`/split-rfc-to-children` パイプラインに以下の3機能を追加する：

1. RFCファイルの完全性検証（単一ファイル＋再帰的走査）
2. `<!-- ... -->` コメントブロックの除去
3. generate-child-rfcs.js テンプレートのコメント入れ子解消

これにより、Step 8（詳細記述）完了後のRFCファイル群にスケルトン放置・コメント残骸・入れ子崩れが
ゼロであることを保証する。

## Background

2026-07-03 の `/split-rfc-to-children` テスト実行で3つの問題が確認された。

### 問題1: 孫RFCのスケルトン放置
子RFCまではAIが詳細記述を行っているが、孫RFCは generate-child-rfcs.js が生成した
スケルトンテンプレートのまま放置される。現状パイプラインには「ファイルが不完全かどうか」
を検出する汎用的な機構がない。

`check-rfc-placeholders.js` は `<!-- ??? -->` という特定パターンのみを検出するが、
それ以外の不完全状態（例：空の機械転記ブロック、未記入のセクション等）は検出できない。

### 問題2: `<!-- ... -->` コメントブロックの残存
generate-child-rfcs.js が生成する子・孫RFCのテンプレートには多数のガイダンスコメント
（`<!-- 記述指針 -->`, `<!-- AI記述部 -->`, `<!-- WARNING -->` 等）が含まれている。
これらは Step 8（AIによる詳細記述）のための指示であり、記述完了後はノイズになる。
また後続の `/drill-rfc-down` 等でAIが編集する際に「コメントだから編集してはいけない」
と誤解するリスクがある。

### 問題3: コメントの入れ子
以下の構造が Markdown コメントの入れ子を発生させている：

```
<!-- !!! WARNING: ... !!! -->
<!-- 機械転記ブロック（...） -->
```

WARNING コメントと機械転記ブロックコメントが連続することで、AI や一部のパーサーが
「コメント内で別のコメントが開始された」と誤解する可能性がある。
実際には別個の独立した HTML コメントだが、可読性・保守性を損なう。

## Scope

改修対象は `~/shyme/zasso/tools/conver/.claude` 配下のみ。

### Section A: 単一ファイル完全性チェッカー（新規スクリプト）

`check-rfc-completeness.js` を新設する。1つのRFCファイルを受け取り、以下の基準で
「完全」か「不完全」かを判定する：

**完全と判定される条件（全て満たすこと）**:
1. `<!-- ??? -->` が含まれていない
2. `<!-- 機械転記ブロック -->` と `<!-- /機械転記ブロック -->` の間に空行のみ or 空白のみの内容がない
   （＝転記内容が実際に存在する）
3. ガイダンスコメントブロック（`<!--【記述指針】-->`）が含まれている場合は不完全とする
   （＝記述完了後は削除されるべき）
4. 1行あたりの文字数が著しく少ないだけのセクションがない（簡易的な記述量チェック）

```javascript
// 使用例
node check-rfc-completeness.js path/to/RFC-CHILD.md
// 出力: {"success":true, "complete":false, "issues":["guidance comment remaining", "empty transfer block"]}
```

### Section B: 再帰的走査スクリプト（新規スクリプト）

`check-all-rfcs-completeness.js` を新設する。RFC-TREE.json を読み込み、finalTree から
全 childNode / grandchildNode の directoryName を導出し、対応する RFC ファイルを
開いて Section A の完全性チェックを適用する。

```javascript
// 使用例
node check-all-rfcs-completeness.js RFC-TREE.json
// 出力: {"success":true, "total":5, "incomplete":2, "files":[{"path":"...", "issues":[...]}]}
```

RFC-TREE.json が唯一のソース・オブ・トゥルースであり、正典RFCのファイル名に依存しない。
子ノードのディレクトリ名は `{canonicalBase}-{childId}-{slug}` で導出する。

### Section C: コメント削除スクリプト（新規スクリプト＋パイプライン組み込み）

`strip-rfc-comments.js` を新設する。RFC ファイルから `<!-- ... -->` 形式の HTML コメントを
全て削除する。ただし以下の例外を設ける：

- **Anchor Marker システムの `[::REF-POINTER-BEGIN/END::]` は削除しない**
  （これらは機械転記のための制御マーカーであり恒久的に必要）
- **frontmatter（`---` で囲まれた YAML）は変更しない**
- **機械転記ブロックのマーカー（`<!-- 機械転記ブロック -->`, `<!-- /機械転記ブロック -->`）は削除しない**
  （再実行時の置換位置特定に必要）

```javascript
// 使用例
node strip-rfc-comments.js path/to/RFC-CHILD.md
// 出力: {"success":true, "removed":12}
```

### Section D: generate-child-rfcs.js テンプレートのコメント入れ子解消

WARNING コメントと機械転記ブロックコメントを統合する。現在の：

```html
<!-- !!! WARNING: ... !!! -->
<!-- 機械転記ブロック（generate-child-rfcs.js が更新） -->
```

を以下に変更：

```html
<!-- 機械転記ブロック（generate-child-rfcs.js が更新。自動管理のため直接編集禁止） -->
```

WARNING の内容を機械転記ブロックの開始コメント内に統合し、「直接編集禁止」を
コメント内に含める。これによりコメントの連続が解消される。

全4セクション（`buildResponsibilitiesSection`、`buildIoBoundarySection`、
`buildParentRelationSection`、`buildDependenciesSection`）の同パターンを修正する。

また、AI記述部コメント（`<!--【AI記述部】...-->`）は Step 8 完了後に strip-rfc-comments.js
で削除されることが仕様であるため、残存を許容する。ただし Section C のスクリプトが
確実に削除する範囲として定義する。

**ガイダンスコメントブロック**（`<!--\n【記述指針】\n...-->`）について：
- これらは generate-child-rfcs.js のテンプレートに含まれる
- 各 build*Section 関数内に埋め込まれている（変数 GUIDANCE_* として定数化）
- Section C の `strip-rfc-comments.js` が削除対象とする
- ただし GUIDANCE_* 自体はテンプレート定数として維持され、generate-child-rfcs.js が
  生成時に出力する。Step 8 完了後のパイプラインで strip-rfc-comments.js が削除する

### Section E: split-rfc-to-children.md パイプラインへの組み込み

Step 9（完了報告）の直前に以下の手順を追加：

```
### Step 8b: コメント削除（必須）

```bash
node "$SCRIPT_DIR/strip-rfc-comments.js" "$TREE_PATH"
```

### Step 8c: 完全性検証（必須）

```bash
node "$SCRIPT_DIR/check-all-rfcs-completeness.js" "$TREE_PATH"
```

不完全なファイルがある場合は Step 8（詳細記述）に戻って修正する。
全てのファイルが complete になるまで次に進んではならない。
```

**連番変更**: 現状の Step 9（完了報告）は変更不要。
Step 8（詳細記述）→ Step 8a（コメント削除）→ Step 8b（完全性検証）→ Step 9（完了報告）
の順とする。

## Non-scope

- PX-3/PX-4 で完了済みの機能（Anchor Marker System, add-ref-pointer.js, validate-ref-pointer.js 等）の改修は含まない
- 正典RFC自体のコメント削除は含まない（子・孫RFCのみ対象）
- `/split-rfc-to-children` 以外のコマンドの改修は含まない

## Investigation

### 証拠1: check-rfc-placeholders.js の限界

現在の `check-rfc-placeholders.js` は `<!-- ??? -->` パターンのみを検出する。
空の機械転記ブロックや残存ガイダンスコメントは検出できない。

### 証拠2: 孫RFCのスケルトン状態

generate-child-rfcs.js は孫RFCのディレクトリとファイルを生成するが、AI は子RFCのみ
詳細記述を行い、孫RFCをスキップする傾向がある。パイプラインに検出機構がないため
見逃される。

### 証拠3: generate-child-rfcs.js のテンプレートコメント構造

全4セクションの build*Section 関数が以下の連続コメントパターンを持つ：

```
<!-- !!! WARNING: ... !!! -->
<!-- 機械転記ブロック（...） -->
```

これらを1つのコメントに統合することで入れ子の誤解を防止できる。

### 証拠4: ガイダンスコメントの定数

GUIDANCE_RESPONSIBILITIES, GUIDANCE_IO_BOUNDARY 等の定数が generate-child-rfcs.js に定義されており、
テンプレート生成時に `<!--\n...-->` でラップされて出力される。
