# 進捗ステータス管理＋Step番号リナンバリング

## Summary

`/split-rfc-to-children` のステップ数増加（13ステップ）に伴い、AI の記憶のみに依存した
順次実行が困難になった。RFC-TREE.json に進捗ステータス管理フィールドを追加し、
各ステップの先頭で進捗表示、末尾でステータス更新を行う仕組みを導入する。
あわせて Step 5a の番号を正規化するリナンバリングを実施する。

## Background

2026-07-03 の `/split-rfc-to-children` 実行分析により以下の問題が確認された：

1. **ステップ数超過**: 13ステップ（6サブ含む）となり、AI が全ステップを記憶・順守できない
2. **番号の非互換**: Step 5a が本来 Step 6 であるべき中途半端な番号で、混乱の元
3. **再開不能**: 中断後の再開時に「どの Step まで終わったか」を外部から確認する手段がない
4. **完了条件の曖昧さ**: 「verify-rfc-coverage が通れば完了」だが、全 Step の完了を保証できない

## Scope

改修対象は `~/shyme/zasso/tools/conver/.claude` 配下のみ（明記）。

### Section B: create-rfc-tree.js のスケルトン雛形に静的に埋め込む

`createSkeleton()` 内に全ステップの初期 status を静的に記述する：

```javascript
split_status: {
  steps: {
    "0": "pending",  // 引数パース
    "1": "pending",  // I/O境界参考情報
    "2": "pending",  // RFC-TREE.json作成
    "3": "pending",  // RFC理解
    "3a-1": "pending", "3a-2": "pending", "3b": "pending",
    "3c-1": "pending", "3c-2": "pending", "3-review": "pending",
    "4": "pending",  // 素案ツリー作成
    "5": "pending",  // 検証ループ
    "6": "pending",  // Anchor Marker登録
    "7": "pending",  // Anchor Marker自動挿入＋機械転記
    "8": "pending",  // リンク整合性検証
    "9": "pending",  // 詳細記述
    "10": "pending", // コメント削除
    "11": "pending", // 完全性検証
    "12": "pending"  // 完了報告
  }
}
```

ステップの追加・削除・リナンバリング時は `create-rfc-tree.js` とコマンドファイルを
同時に修正する。これにより「どのステップが存在するか」の唯一の正本がコードに固定される。

### Section C: show-split-rfc-status.js 新設

RFC-TREE.json の `split_status` を読み取り、以下の形式で進捗を標準出力する：

```
【進捗状況】13ステップ中 5ステップ完了

=== 完了 ===
  Step 0: 引数パース
  Step 1: I/O境界参考情報
  Step 2: RFC-TREE.json作成
  Step 3: RFC理解
  ├─ 3a-1: 目的とゴールの把握
  ├─ 3a-2: メタ情報の記録
  ├─ 3b: アーキテクチャ把握
  ├─ 3c-1: 実装詳細（型・API・依存）
  ├─ 3c-2: 実装詳細（テスト・エラー処理・設定）
  └─ 3-review: RFC理解の全体確認
  Step 4: 素案ツリー作成
  Step 5: 検証ループ

=== 未完了 ===
  Step 6: Anchor Marker登録 [PENDING]
  Step 7: Anchor Marker自動挿入＋機械転記 [PENDING]
  ...

【次のアクション】
次に実行すべき Step: Step 6 — Anchor Marker 登録
各 childNode に add-ref-pointer.js で行範囲を登録してください。
完了したら次のコマンドでステータスを更新:
  node .claude/scripts/tickets/update-split-rfc-status.js <TREE_PATH> 6 done
```

**自然言語の指示** はコマンドファイルの各 Step の説明文を直接引用する。
各 Step に「この指示」フィールドを静的に持たせるか、show スクリプト内に
switch-case で指示文を保持する。後者を推奨（コマンドファイル変更時に show も
同時修正が必要だが、スキーマに指示文を持ち込まず分離できる）。

**完了検出**: 全ステップの status が "done" の場合、以下のメッセージを出力して
exit 0 する：

```
【全ステップ完了】/split-rfc-to-children は正常に完了しました。
```

1つでも "pending" があれば exit 1 とする。

### Section D: update-split-rfc-status.js 新設

指定された Step ID の status を更新する：

```bash
node update-split-rfc-status.js <RFC-TREE.json> <stepId> <newStatus>
```

**バリデーション**:
- stepId が `split_status.steps` に存在すること
- newStatus が `pending` / `in_progress` / `done` のいずれかであること
- 前の Step が全て done になっていなくても警告は出すがブロックはしない（柔軟性確保）

### Section E: split-rfc-to-children.md Step 番号リナンバリング

現在の Step 番号を正規化する：

| 旧 | 新 | 内容 |
|----|----|------|
| Step 5a | **Step 6** | Anchor Marker 登録 |
| Step 6 | **Step 7** | Anchor Marker 自動挿入＋機械転記 |
| Step 7 | **Step 8** | リンク整合性検証 |
| Step 8 | **Step 9** | 詳細記述 |
| Step 8a | **Step 10** | コメント削除 |
| Step 8b | **Step 11** | 完全性検証 |
| Step 9 | **Step 12** | 完了報告 |

### Section F: 全 Step への進捗管理組み込み

各 Step の冒頭と末尾に以下の定型文を追加：

**全 Step の先頭**:
```bash
# 進捗表示
node "$SCRIPT_DIR/show-split-rfc-status.js" "$TREE_PATH"
# 自身のステータスを in_progress に更新
node "$SCRIPT_DIR/update-split-rfc-status.js" "$TREE_PATH" "<StepID>" "in_progress"
```

**全 Step の末尾**:
```bash
# 自身のステータスを done に更新
node "$SCRIPT_DIR/update-split-rfc-status.js" "$TREE_PATH" "<StepID>" "done"
```

**完了条件の拡張**:
`Step 12: 完了報告` に以下の条件を追加：
```
通過条件（全て満たすこと）:
1. verify-rfc-coverage.js が valid: true
2. check-rfc-placeholders.js が remaining: 0
3. show-split-rfc-status.js が「全ステップ完了」を出力（exit 0）
```

## Investigation

### 証拠1: 現在の Step 数

現在の `/split-rfc-to-children.md` には 13 の Step（6サブ含む）が定義されている。
Step 5a の番号が正規の連番になっていない。

### 証拠2: create-rfc-tree.js のスケルトン

現在の `createSkeleton()` は以下の構造を生成する：
```javascript
const skeleton = {
  canonicalRfcPath: resolved,
  ...
  split_status: undefined  // ← 未定義
};
```

### 証拠3: rfc-tree-schema.json

トップレベル properties に `split_status` の定義がない。

### 証拠4: 既存の write-rfc-tree-final.js と validate-rfc-tree.js

これらのスクリプトは新しいフィールドを無視する（未知プロパティを許容する）ため、
split_status 追加による影響は受けない。スキーマ検証の `required` 配列に
split_status を追加しない限り、既存の validate-rfc-tree.js の validation も通過する。
