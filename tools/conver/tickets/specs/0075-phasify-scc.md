# phasifyコアアルゴリズム — SCC・重み付きトポロジカルソート・フェーズ合併・検証

## Summary

`phasify-graph-and-dirs-files-tree.js` のコアアルゴリズム部分を実装する。GRAPH.json のノードを、エッジ種別ごとの重みと Dirs-Tree.json のディレクトリ間依存方向に基づいて実装フェーズにグルーピングする。アルゴリズムは「粗→密」の拡散モデルに従い、まず SCC で縮約し、重み∞の Hard 制約でトポロジカルソートし、Soft 制約を重ね、最後にフェーズ合併で下限10ノードを充足する。

## Background

split-to-tickets.md Step 4 の核心は「設計のカケラ（グラフノード）」を「実装の順序（フェーズ）」に変換することである。この変換は以下の数学的定式化に基づく：

- 入力: 重み付き有向グラフ G = (V, E, w) + ディレクトリ割当 dir: V → D + ディレクトリ間依存 F ⊆ D×D
- 出力: フェーズ割当 phase: V → ℕ
- 制約: (1) SCC制約、(2) Hard制約 w=∞ ⇒ phase(u) < phase(v)、(3) ディレクトリ制約、(4) 下限10
- 目的: 逆順 Soft エッジの重み総和を最小化

この定式化とアルゴリズムは、本チケットの Investigation セクションで議論し確定する。

## Scope

1. **重みテーブル定義**: `W` 定数テーブルを実装する。
   - w=∞: depends_on, implements, constrains
   - w=2: precedes
   - w=1: triggers
   - w=0: refines, references, extends, conflicts_with, supersedes, validates, part_of
   - 根拠: 「逆順で実装した場合の再実装コストの相対オーダー」

2. **Phase 1: SCC縮約**: boundify-helpers.js の `tarjanSCC()` を流用し、グラフの強連結成分を検出する。同一 SCC 内のノードは同一フェーズに割り当てる（SCC制約）。

3. **Phase 2: Hard DAG + ディレクトリ制約**: SCC縮約後のグラフから、重み∞のエッジのみで DAG を抽出し、Kahn アルゴリズムでトポロジカルソートする。次にディレクトリ間依存方向（Dirs-Tree.json の dependencyDirections）を重ね、粗い順序を確定する。∞エッジで循環が検出された場合はエラー終了（設計矛盾）。

4. **Phase 3: Soft制約の重ね合わせ**: トポロジカルソート順序に対して、Soft エッジ（w>0）の違反コストを計算する。違反総和が閾値を超える場合は隣接スワップ等で改善を試みる。

5. **Phase 4: フェーズ合併と離散化**: トポロジカル順序を10ノード以上のフェーズに区切る。10ノード未満のフェーズは直前のフェーズに合併する。これを「フェーズ」として ℕ に写像する。

6. **Phase 5: 出力**: 各ノードのフェーズ割当を Tickets.json の phase[].nodeIds に反映する。`--verbose` 時は各 Phase の経過を stdout に表示。

7. **アルゴリズムの正当性保証**: 決定論性（同一入力→同一出力）、単調性（エッジ追加で制約緩和なし）、∞制約の完全遵守、有限性の4性質をテストで保証する。

## Investigation

### アルゴリズム設計（粗→密 拡散モデル）

#### Phase 1: SCC縮約

`boundify-helpers.js` に `tarjanSCC()` が既に実装済み（`boundify-helpers.js:261-313`）。これを流用する。返り値は `{ cycle: string[] }[]` 形式。

176ノードに対して Tarjan SCC を実行した結果、dependencyDirections が2件しかないことから、ほとんどのノードは SCC サイズ1（自己完結）と予想される。ただし part_of(113) により architecture 階層が強い結合を持つ可能性がある。

#### Phase 2: Kahn アルゴリズム

Kahn アルゴリズムは未実装。実装は約20行で済む：

```
function kahnTopologicalSort(nodes, edges) {
  // 1. 入次数を計算
  // 2. 入次数0のノードをキューに入れる
  // 3. キューから取り出して順序に追加、隣接入次数を減らす
  // 4. キューが空になるまで繰り返す
  // 5. 全ノード処理済みでなければ循環エラー
}
```

#### Phase 3: 重みテーブルの数学的根拠

重みは「逆順で実装した場合の再実装コストの相対オーダー」として定義：

| w  | edge type | 数学的意味 |
|----|-----------|-----------|
| ∞ | depends_on | API/機能に依存。逆順なら全行書き換え。絶対制約（循環は設計矛盾） |
| ∞ | implements | 契約の実装。逆順ならインターフェース未確定で実装→全書き換え |
| ∞ | constrains | 制約未定義で実装→アーキテクチャ違反 |
| 2 | precedes | 時間的順序推奨。逆順でも I/F 修正のみ（partial orderの軟化） |
| 1 | triggers | イベント契機。逆順でもモックで代替可能 |
| 0 | refines/references/extends/conflicts_with/supersedes/validates/part_of | 順序制約なし（単なる情報参照〜拡張〜検証） |

∞エッジが DAG を形成しない場合 → エラー終了（設計矛盾: 依存関係に循環がある）。

#### Phase 4: フェーズ合併戦略

フェーズ合併は以下の戦略に従う：

```
1. トポロジカルソート順序を O = [v1, v2, ..., vn] とする
2. O を先頭から走査し、|phase| >= 10 になるまで詰める
3. 最後のフェーズが 10未満 かつ 前のフェーズが存在する → 合併
4. 最後のフェーズが 10未満 かつ 前のフェーズが存在しない（総ノード < 10）→ 警告のみ
```

#### 実データでの予測

176ノード ÷ 10 = 17フェーズ（最小）
実際のフェーズ数は SCC やディレクトリ制約により 17〜20 程度と予想。

### 実データの特徴

Dirs-Tree.json の dependencyDirections は僅か2件：
- src/config → src/security (references)
- src/tests → src/error (depends_on)

ディレクトリ制約による順序制限は非常に緩い。ほとんどの順序決定はエッジの重みに委ねられる。

### エッジ種別分布（アルゴリズム設計への示唆）

| 種別 | 件数 | 重み | 性質 |
|------|------|------|------|
| part_of | 113 | 0(順序無関係) | 階層構造のみ。グループ化に使用 |
| depends_on | 52 | ∞ | 絶対制約。順序の骨格 |
| refines | 15 | 0 | 情報提供。順序制約なし |
| references | 15 | 0 | 情報提供。順序制約なし |
| precedes | 7 | 2 | 弱い順序推奨 |
| triggers | 3 | 1 | 弱い順序推奨（モック可） |
| extends | 2 | 0 | 拡張。順序制約なし |

→ 52本の hard 制約が DAG を形成することを確認すれば、Phase 2 は問題なく完了する。
→ Soft 制約（precedes 7 + triggers 3）は10本。違反コストは最大でも 2×7 + 1×3 = 17。

## Test Plan

### ユニットテスト計画

1. **tarjanSCC 流用テスト**（boundify-helpers.js の既存テストに追加で確認）:
   - 実データ（176ノード）で SCC が正しく計算されること
   - 全ノードが1つ以上の SCC に含まれること（孤立ノードなし）
   - SCC サイズが1のものは全ノード数の大半を占めることの確認

2. **kahnTopologicalSort テスト**:
   - 正常系: DAG（52本の depends_on）で正しいトポロジカル順序が得られること
   - 異常系: 循環依存を含むグラフ → エラー終了（循環ノード一覧を出力）
   - 境界値: エッジ0本 → 入力順のまま出力
   - 境界値: 全ノードが一直線の依存 → そのままの順序

3. **重みテーブルの正当性テスト**:
   - 全エッジ種別（12種）に対して w が定義されていること
   - ∞エッジ種別のみ、循環時にエラーになること
   - Soft エッジ（precedes/triggers）の違反コスト計算が正しいこと

4. **フェーズ合併テスト**:
   - 176ノード → ceil(176/10)〜 程度のフェーズ数になること
   - 全フェーズが10ノード以上であること
   - 総ノード数9（下限未満）の場合 → 警告のみで停止しないこと
   - 最後のフェーズが6ノードで前のフェーズが14ノード → 合併して20ノード1フェーズになること

5. **全体統合テスト**:
   - 実データ（176ノード, 207エッジ）で全フェーズが正しく生成されること
   - 全ノードが最低1フェーズに属すること（カバレッジ100%）
   - 同一 SCC のノードが同一フェーズに属すること
   - ∞エッジで逆転がないこと
   - ディレクトリ間依存方向に違反がないこと
   - 各フェーズが10ノード以上であること
   - `--dry-run` で書き込みが発生しないこと

6. **決定論性テスト**:
   - 同一入力を2回実行 → 同一出力になること
   - エッジを1本追加 → フェーズが若返らないこと（単調性）

### ユニットテスト不可能な項目（例外）

- なし。全アルゴリズムは純粋関数として実装可能。

## Boy Scout Rule — 翻訳可能性計画

- アルゴリズムの各 Phase は独立した関数として抽出：
  - `contractByScc(graph)` — SCC縮約
  - `topologicalSort(contractedGraph)` — Kahn トポロジカルソート
  - `computeSoftViolations(order, softEdges)` — Soft制約違反コスト計算
  - `mergePhases(order, minSize)` — フェーズ合併（下限充足）
  - `assignPhasesToNodes(phaseOrder, originalGraph)` — 縮約前ノードに展開
- 各関数は1責務のみ。関数呼び出しの並びが処理手順の日本語訳になる
- 重みテーブル `WEIGHT` は const オブジェクトとしてファイル先頭に宣言
- エラーは具体的なメッセージ付きで throw（「循環依存検出: N0001→N0005→N0003→N0001」）
- boundify-helpers.js の `tarjanSCC` は既に翻訳可能性を満たしているので流用のみ
