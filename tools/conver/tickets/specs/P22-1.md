# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Acceptance Criteria

- **[Happy path]:** `capture` freezes the baselines and `check` exits 0 on an untouched tree. All nine command-file digests are recorded.
- **[Error case]:** A modified fixture or a damaged command file is reported by name and exits 1, with the expected and actual values shown.
- **[Edge case]:** A second `capture` produces byte-identical JSON, and the SHA-256 of every target is unchanged across both capture and check.
- **[Environment — happy path]:** Running the entry point once, with no arguments, resolves every declared dependency and prints a Markdown report that separates forward readiness from reverse readiness.
- **[Environment — error case]:** A dependency that cannot be resolved is named with the exact command that would provide it on this platform, and the run exits non-zero rather than reporting readiness.
- **[Environment — edge case]:** Running it a second time changes nothing; a file the user modified locally is preserved and reported; and a tool whose absence is declared normal, or whose providing ticket has not converged, is reported as unavailable or not yet required rather than as an error.

## Invariants

- 【Normal establishment】Every fixture under `tests/workspacify-tree/fixtures/` and `tests/workspacify-allocate/fixtures/` has its `manifest_hash` frozen in JSON, and a later `check` reproduces the identical value. Every one of the nine command files has its heading set, Language Protocol table and First-Class Rule line digested. **A single entry point resolves the whole environment**: every declared npm root is installed, every declared external tool is probed, and the outcome is recorded in `ENV-MANIFEST.json`. Each declared dependency states which rotation needs it, so the report can say "the forward rotation is ready, the reverse rotation is not" rather than emitting one undifferentiated verdict that hides the difference.
- 【On error】A missing baseline file, an unreadable fixture, or a non-UTF-8 input produces a descriptive error naming the path and the reason, and exits non-zero. No failure is swallowed into a passing gate. **An unresolved dependency is reported by name together with the exact command that would provide it on this operating system**, and never silently skipped; a dependency that cannot be resolved leaves the run non-zero rather than producing a report that reads as ready. A spawn failure names the command it tried to run and the platform it ran on — "npm install failed" is not an acceptable message for "npm was not found".
- 【Internal state】Measurement is read-only: the SHA-256 of every target file is identical before and after both `capture` and `check`. `capture` is idempotent — running it twice produces byte-identical JSON. **The installer decides what to do with an existing file by comparing three things — the target, the source, and what it installed last time — and never by asking.** A file the user has modified is reported and left untouched; a file that differs from the source only because conver has moved on is updated.
- 【Boundary】Zero allocate fixtures exits 0 with the explicit message that there is nothing to check, rather than being confused with success or failure. A single byte changed in a single fixture is detected. **Running the environment entry point twice is safe**: the second run changes nothing and says so. A declared tool whose absence is expected at this point in the phase is reported as unavailable rather than as an error, and never aborts the run.

## Boy Scout Rule

- New code is written for translatability first: functions as verb phrases (`captureBaselines`, `checkBaselines`, `digestCommandFiles`, `compareDigests`, `resolveEnvironment`, `probeTools`, `decideFileAction`), variables as domain concepts (`fixturePath`, `expectedHash`, `observedHash`, `driftedNames`, `declaredRoot`, `providedBy`, `previousDigest`), one responsibility per function, and no hardcoded path — the fixture roots and the declaration path are named constants.
- **`install.js` violates the Language Protocol and is fixed while touched.** Its header comment (lines 2-8), `showUsage` (lines 62-75) and the JSDoc on `parseArgs`, `collectFilesWithRelative`, `promptOverwrite`, `copyFileWithPrompt`, `showSummary` and `main` are written in Japanese. Code comments must be English. The user-facing usage text may be localised separately, but the explanatory comments must not be.
- **`defaultCommandRunner` is rewritten so the platform decision is testable without a Windows machine**: the command name is resolved from a pure function of the platform, and that function is asserted directly for both `win32` and the POSIX case. A comment explaining why Windows needs `.cmd` is not a substitute for a test that says so.
- `install.js` is at 250 lines and `install-deps.cjs` at 151; the environment work goes into `env-manifest.cjs` and the declaration reader rather than growing either of them past the 800-line limit, and `promptOverwrite` and its readline import are deleted rather than left unused.
- Any `unwrap`-style or throwing access encountered in the touched region of `run.mjs` is replaced with explicit error propagation that names the offending path.
- The usage text in `run.mjs` is updated in the same commit as the subcommand list, so the help output cannot rot into a lie.
- The new gate module is kept under the 800-line limit by separating digest computation from comparison, following the existing `lib/` convention in this directory.
