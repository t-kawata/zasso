# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## This ticket — P22-20

**Goal**: Make the adjudication of boundaries a choice between candidate models rather than the authoring of a model from scratch.

**Purpose**: Assuming that the physical layout is the logical architecture freezes the existing technical debt into the canonical record permanently, which is F14. Presenting candidates converts an open-ended design task into a bounded choice.

**Motivation**: ABOUT-REVERSE 7.4 item 9 and 7.7.1. Because `mappedNodeIds` already exists in the forward index chain, recording mismatches on top of it is cheaper than building a new structure alongside it.

**Constraints**: The human is the adjudicator between candidate models, not their author. The AI's judgement surface is not widened beyond adjudication: generating candidates mechanically and deciding between them are separated deliberately.

## Investigation

- **Measured 2026-09-10.** `mappedNodeIds` exists in the forward index chain at `rfc-graph/boundify-helpers.js:89`, which is why candidates can be recorded on top of it rather than in a new structure. This is the concrete fact behind the 7.4 item 9 claim that the mismatch approach is cheaper.
- The F14 risk has a visible instance in this target: `siprs-for-reverse` has a top-level layout mixing `src/`, `tests/`, `examples/`, `docker/`, `vendor/` and build configuration, which reflects the project's history rather than a clean architecture. Treating that layout as the logical architecture would canonise it permanently.
- The 2-Pass structure follows 7.7.1: vertical at boundaries, horizontal inside. The vertical pass is where a boundary is adjudicated, and the horizontal pass is where a package's interior is understood, which is why Pass 2 must not reason about other packages.
- The card structure is constrained by 7.4.1: a card's subject is a falsifiable proposition, and free-form prose is never demanded. That constraint is what makes a card adjudicable in bounded time.
- The existing gate vocabulary from P22-11 (T5) is reused rather than restated, so the "a missing record is the failure" principle has one definition in the phase.

## Acceptance Criteria

- **[Happy path]:** Multiple candidate models are generated and adjudicated, with every mismatch recorded in `ARCHITECTURE-DELTA`.
- **[Error case]:** A mismatch that is not recorded produces a FAIL, matching T5.
- **[Edge case]:** A package with a single candidate produces a valid single-option card, and no candidate is ever lost.

## Invariants

- 【Normal establishment】Multiple candidate logical models are generated mechanically from the R1 and R2 measurements. Each candidate is presented as a decision card carrying its consequences, its supporting evidence and its counterexamples. Mismatches against the physical structure are recorded in `ARCHITECTURE-DELTA`.
- 【On error】A candidate is never deleted; one that cannot be adjudicated remains `unresolved`. A mismatch that is not recorded is a FAIL, matching T5 in P22-11. A card that demands free-form prose is not emitted.
- 【Internal state】Pass 2 stays local to a package and never reasons about interactions with other packages, which is what keeps the horizontal pass bounded. Candidates are recorded on top of `mappedNodeIds` rather than in a parallel structure.
- 【Boundary】A package with a single candidate produces a card with one option and remains valid. A package with no measurable structure produces no candidate rather than an empty card.
