# Implementation Order (TDD Red-Green-Refactor)

Implementation must strictly follow the **Red → Green → Refactor** sequence. Skipping steps, reordering, or parallel execution is prohibited.

## 1. Red — Fully Implement Failing Tests

Before writing a single line of implementation code, write a failing test suite that achieves 100% coverage of the spec's **Goal, Purpose, Motivation, Constraints, Scope, Acceptance Criteria, and Invariants**. Coverage of these seven elements is mandatory; partial implementation is not acceptable.

When the ticket defines **Contracts** (Precondition/Postcondition/Invariant from graph edge annotation), the Red phase must first translate each Contract into testable form — input schemas, output assertions, and invariant predicates — before implementing them as concrete test code. A Contract whose Precondition/Postcondition/Invariant cannot be expressed as a testable assertion is not yet fully specified.

- Tests must cover all observable behaviors, edge cases, failure modes, and invariants. Any behavior not covered is considered undefined and fails review.
- If a feature is deterministic yet fundamentally untestable, this is not a testing gap but an architectural defect. Redesign the system until it is testable before proceeding to implementation.
- Confirm that all tests fail red due to the absence of implementation. Tests that pass green by accident (e.g., meaningless assertions) are invalid.

## 2. Green — Implement Behavior (No Stubs, No Test Modification)

Implement the **behavior** specified by the tests; do not treat passing the tests as an end in itself. Tests are a means of verifying correctness, not the goal itself.

- Implementations that merely satisfy the literal wording of tests—via hardcoding, input-specific branching, or stubbed return values—are prohibited. The implementation must be a generalized, correct solution.
- If it is impossible to distinguish, via testing, whether an implementation is genuine or a disguised green, this indicates a design flaw caused by insufficient coverage. Add tests until the distinction is possible before proceeding with implementation.
- Modifying, deleting, or weakening tests to make an implementation pass is strictly forbidden. The implementation must conform to the tests; the reverse is never acceptable.
- An implementation whose correctness cannot be proven is invalid. It is not considered complete until it (or its design) is restructured into a provably correct form.

## 3. Refactor — Apply the Boy Scout Rule (Green State Only)

Refactor only after all tests are green. Refactoring in a red state is prohibited.

- Apply the Boy Scout Rule (leave the code cleaner than you found it; readability = translatability) to eliminate `unwrap()` calls, hardcoded values, false comments, and untested code in anything you touch.
- Verify that all tests remain green before and after each refactoring step. If a refactor breaks green, roll it back immediately.

## Definition of Done

Implementation is considered incomplete unless all of the following are satisfied:

- The tests fully and precisely specify the intended behavior.
- The implementation passes all tests green, without exception.
- Correctness is empirically guaranteed by the tests (not a disguised green).
- No gap exists between test coverage and intended behavior.

Green without red, green achieved by modifying tests, and green achieved through stubs are all violations and constitute incomplete work.

## Investigation

- **Measured 2026-09-10.** The target `/Users/kawata/shyme/zasso/tools/conver/siprs-for-reverse` is a git working tree and retains readable history, so R4 has material to work with rather than a degenerate case.
- PX-203 produced a concrete instance of the F17 problem. Ten test files had been named after the ticket keys that generated them (`verify_spec_*.rs`), and source comments carried `@verifies` annotations referencing contract ids. Those tests were written from the design, so they agree with the implementation by construction and cannot detect a divergence between the two. That is precisely the co-conspirator oracle R5.5 exists to expose.
- PX-203 also produced a concrete absent-Red instance: the ten ticket-keyed test files were test-only, and P22-16 later needs to detect exactly this category.
- The TCE requirement is language-specific, and **the earlier wording of this ticket was wrong about Rust.** `rustc` has no official source printer. The available pair is `syn` for parsing plus `prettyplease` for printing — a third-party crate over `syn`'s AST, not the compiler's, and one that can drop comments. That matters here specifically, because comment-borne evidence (`@verifies` annotations and contract-id comments) is part of what this project reasons about, so a normaliser that discards comments discards evidence. **The claim must be weakened accordingly: TCE proves syntactic equivalence under a named configuration and never semantic equivalence.** `i < n` and `i <= n - 1` are not interchangeable once overflow, types, side effects in `n` or undefined behaviour are considered, and general program equivalence is undecidable. A normaliser chosen for a different language would silently discard non-equivalent mutants and manufacture a false clean result, so it is chosen per language and recorded in `docs/P22-ANALYSIS-TECH.md`.
- **The comparison ladder stops at the first step that applies, and never claims more than that step proves.** In order: (1) text identical; (2) token-normalised identical; (3) AST-normalised identical; (4) equal under a limited set of local rewrite rules; (5) the compiler or type checker emits the same IR or the same diagnostics; (6) no test, property or differential implementation could distinguish them; (7) `unknown`. **Step 4 and beyond are unsafe unless the language, the types, the evaluation order, the side effects, the arithmetic model and the configuration are all named.** The ladder is never collapsed into the single word "equivalent" anywhere in the output: a mutant discarded at step 6 and a mutant discarded at step 1 are different kinds of claim, and flattening them is exactly how an undecided mutant comes to be presented as a decided one.
- **Pre-expansion and post-expansion code are two objects, not one.** For each, keep the pre-expansion source a human maintains — with its own `file:line`, review surface and design intent — and the post-expansion form under a fixed configuration, which is what name resolution and type checking actually see. Connect them by a many-to-many provenance graph carrying `origin_span`, `expansion_span`, `configuration_id` and `generator_identity`, never by a one-to-one assumption, because a macro call site and its expansion do not correspond one to one. This corpus makes the distinction concrete rather than hypothetical: `build.rs` and `wrapper.h` mean generated and macro-produced code is present.
- **Reproducibility is a property of the output, not of the tool version.** Where Go normalisation is used, run the formatter at a pinned version **and record its output**, because formatter behaviour is version-scoped and the manual warns that its output can change incompatibly between releases. Pinning the version without storing and comparing the output is not evidence of reproducibility. The request-side verification record in `docs/ABOUT-ANALYSIS-TECH.md` §7 could not confirm the exact manual sentence the expert cited, which is a further reason not to rest the design on that citation alone.
- The dead-code and stub categories have a real population here: the crate is a SIP implementation with an FFI boundary (`wrapper.h`, `build.rs`) and `#[non_exhaustive]` types, both of which generate unreachable and unobservable surfaces.
- ABOUT-REVERSE 7.6 lists F21 alongside F12 and F17; the gap enumeration is the point at which all three are addressed, which is why they share a ticket.
